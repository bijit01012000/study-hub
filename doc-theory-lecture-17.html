    Lecture 17 - Spring Boot Exception Handling

    17 sections · 5,986 words

    Lecture 17

    Scope evidence: "Spring Boot Exception Handling: Make Your APIs Professional" (playlist map, verified). Repo folder = exceptionDemo project: an exception package holding GlobalExceptionHandler plus the custom exceptions ResourceNotFoundException and DuplicateResourceException, the error/validation DTOs (ErrorResponseDto, ValidationErrorResponseDto), and the usual controller, service, repository and entity layers plus notes.

    A professional API does not merely return data; it clearly communicates what happened during the request. That means the response must answer whether the request succeeded, whether the client sent something wrong, whether the resource was missing, and whether the server broke. This lecture builds that story end to end: HTTP status codes, ResponseEntity, custom exceptions, an error response DTO, global validation handling, and one central GlobalExceptionHandler. The target artifact is the exceptionDemo project, and every idea below is a step toward making a beginner CRUD API behave like a production-grade one.

    1. API Response: Communication Between Two Systems

    Every API response is a small message with three main parts:

    Part Meaning Example
    Status code HTTP-level meaning of the outcome 200 OK, 404 Not Found, 500 Internal Server Error
    Headers Metadata about the response, not the data itself Location: /api/students/10, Content-Type: application/json
    Body The actual data, or a human-readable error message {"id":10,"name":"Rahul","email":"rahul@gmail.com"}
    • The status code is for protocol-level meaning. A frontend, mobile app, or another backend service reads it and immediately understands what kind of outcome to expect.
    • Headers carry extra information. For a create operation, Location: /api/students/10 tells the client where the new resource lives, and Content-Type: application/json tells it how to parse the body.
    • The body carries the payload: for success it is the data, and for failure it is the error message.
    HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "message": "Student with id 10 not found"
}

    Mnemonic: a response is S-H-B - Status, Headers, Body. Leave out any one of them and the client is guessing.

    Important: The status code and the body carry different jobs. The status code is the machine-readable verdict the frontend branches on, while the body is the human-readable explanation. A professional API keeps both consistent.

    2. Beginner API vs Professional API

    A beginner API usually answers only one question: "Did I get data or not?" A professional API answers a better question: "Did the server clearly tell the client what happened?"

    Take a single call, GET /api/students/10. Many different things can happen:

    1. The student exists.
    2. The student does not exist.
    3. The ID format is wrong.
    4. The database is down.
    5. There is a bug in the backend code.

    A professional API communicates each case properly instead of collapsing them into one vague response.

    Aspect Beginner API Professional API
    Focus Did data come back? What exactly happened, and why?
    Status codes Almost always 200 OK Code matches the real outcome (201, 204, 400, 404, 409, 500)
    Error format null, plain string, or default HTML Consistent structured JSON error DTO
    Failure signal Service returns null; controller guesses Service throws a meaningful custom exception
    Frontend effort Must reverse-engineer every response Branches on status code and reads a stable shape
    Maintainability Repeated checks in controllers One central handler

    Example professional responses for that one endpoint:

    Case 1: Student exists          -> 200 OK + student JSON
Case 2: Student does not exist  -> 404 Not Found + {"message":"Student with id 10 not found"}
Case 3: Invalid request         -> 400 Bad Request + {"message":"Student id must be a number"}
Case 4: Server error            -> 500 Internal Server Error + {"message":"Something went wrong on the server"}

    Case 2 is important: the request was valid, but the requested resource does not exist. Case 3 means the client sent an invalid request. Case 4 means the client may have sent a valid request, but something failed inside the server.

    3. Common Problems in Beginner CRUD APIs

    Problem 1: everything returns 200 OK. Many beginner APIs return success for almost every operation, including failures:

    Operation Beginner response
    Create student 200 OK
    Fetch student 200 OK
    Update student 200 OK
    Delete student 200 OK
    Student not found 200 OK
    Validation failed Random error response with null

    This is not expressive. The better mapping is:

    Situation Better status code
    New resource created 201 Created
    Resource fetched or updated 200 OK
    Delete successful, no body 204 No Content
    Resource not found 404 Not Found
    Validation failed 400 Bad Request
    Duplicate data 409 Conflict
    Unexpected backend issue 500 Internal Server Error

    Problem 2: repeated error logic in controllers. A beginner controller often checks for a missing resource in every method. For getStudentById, it calls the service, and if the returned Student is null, it builds ResponseEntity.status(HttpStatus.NOT_FOUND).body("Student not found"). This is better than returning null, but the same if (data == null) { return 404; } check reappears in getStudentById, updateStudent, deleteStudent, getCourseById, getTeacherById and getBatchById. Duplicate code makes controllers bulky and easy to get wrong.

    Problem 3: inconsistent error responses. One API may return {"message": "Student not found"}, another just the string "Course not found", another {"error": "Something went wrong", "status": 500}, and yet another may fall through to Spring Boot's default error response. This inconsistency makes the frontend harder to build. A professional backend returns a consistent structure for errors.

    4. Exception Flow and Spring Boot Default Error Handling

    Think about the normal request flow in the exceptionDemo project:

    Client
  |
  v
Tomcat / Embedded Server
  |
  v
DispatcherServlet
  |
  v
Controller
  |
  v
Service
  |
  v
Repository
  |
  v
Database

    Now suppose the service layer returns studentRepository.findById(id).get(). If the student does not exist, findById(id) returns an empty Optional, and calling .get() on an empty Optional throws an exception. That exception then travels backward:

    Repository / Service exception
  |
  v
Controller does not handle it
  |
  v
Spring MVC tries to resolve it
  |
  v
If no custom handler exists, Spring Boot default error handling takes over

    Spring Boot does have default error handling, but the default response may not match the meaning of your business case.

    The default /error mapping

    Spring Boot provides a default /error mapping. When an unhandled error occurs, Spring Boot internally forwards the request to /error:

    • For browser clients, it may show the Whitelabel Error Page.
    • For API clients such as Postman, it usually returns a JSON error response.

    A test endpoint GET /test/500 that throws new RuntimeException("Something went wrong inside server") demonstrates this. Opening http://localhost:8080/test/500 in a browser shows an HTML page beginning with "Whitelabel Error Page". In Postman the response may look like:

    {
  "timestamp": "2026-07-05T11:45:06.511Z",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/test/500"
}

    By default, Spring Boot hides detailed exception messages for safety. For learning or local testing only, the response can be made to include the exception message by adding spring.web.error.include-message=always in application.properties.

    Important: Do not expose internal exception messages in production. Raw messages may reveal implementation details. The include-message switch is a local debugging aid, not a production setting.

    Why the default response is not good enough

    Default error handling is useful, but it is not domain-specific. Suppose the real issue is "Student with id 2 does not exist", yet the response says "status": 500, "error": "Internal Server Error". This is misleading: the server did not fail because of an unknown internal crash, the requested student simply does not exist. The correct response should be 404 Not Found. This gap is one of the main reasons we need custom exception handling.

    5. HTTP Status Codes for REST APIs

    Status codes are grouped into families:

    Category Meaning
    1xx Informational
    2xx Success
    3xx Redirection
    4xx Client error
    5xx Server error

    For a beginner-to-intermediate Spring Boot CRUD API, these codes are enough: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 404 Not Found, 409 Conflict, 500 Internal Server Error.

    Situation Status code
    Data fetched successfully 200 OK
    Data updated successfully 200 OK
    New resource created 201 Created
    Delete successful with no body 204 No Content
    Invalid request body or validation failure 400 Bad Request
    Resource does not exist 404 Not Found
    Duplicate email, username, or roll number 409 Conflict
    Unexpected backend failure 500 Internal Server Error
    • 201 Created is used when a new resource is successfully created. For POST /api/students, the response 201 Created plus the saved student JSON tells the client a new resource exists.
    • 204 No Content means the request succeeded but there is no response body. It is common for delete APIs: DELETE /api/students/1 returns 204 No Content with no body. For deletes both 204 (no body) and 200 OK (with a message) are common, but clean REST APIs often prefer 204.
    • 409 Conflict means the request could not be completed because it conflicts with the current state of the resource. A duplicate email is the classic case: the JSON is valid, the email format is valid, but the email already exists. Other cases include duplicate username, duplicate roll number, version conflict during update, and business rule conflicts.
    • 500 Internal Server Error means something unexpected failed inside the backend: a NullPointerException from a bug, an unexpected runtime exception, a database connection failure, a third-party service failure, a file system error, or a server configuration issue. Use 500 for unexpected server-side failures, never for normal business cases like "student not found".

    Mnemonic for the CRUD status set: "Two-oh-one makes it, two-oh-four says done-and-gone, four-hundred is you, five-hundred is me." (201 create, 204 delete, 4xx client, 5xx server.)

    6. Why ResponseEntity and Its Mental Model

    In a basic controller we may return the Student directly, which returns only the body and lets Spring decide the status code automatically. With ResponseEntity, we control the response explicitly, for example return ResponseEntity.ok(student);. The important difference is control: without ResponseEntity, Spring decides the response status; with ResponseEntity, we explicitly decide the response status, headers, and body.

    Mental model - a ResponseEntity can represent any of these:

    Body + Status
Body + Headers + Status
Status only

    ResponseEntity.ok(student);                                   -> 200 OK + student body
ResponseEntity.status(HttpStatus.CREATED).body(savedStudent); -> 201 Created + saved student body
ResponseEntity.noContent().build();                           -> 204 No Content + no body

    Returning headers with ResponseEntity

    Headers carry extra metadata. For a create API, the Location header is useful because it tells the client where the new resource can be found. After saving, build the URI as URI.create("/api/students/" + savedStudent.getId()) and return ResponseEntity.created(location).body(savedStudent). The result is 201 Created, a Location: /api/students/10 header, and the saved student body. ResponseEntity.created(location) automatically sets both the 201 status and the Location header.

    Common ResponseEntity methods

    Method Meaning Typical use
    ResponseEntity.ok(body) 200 OK with a body Fetch, update
    ResponseEntity.ok().build() 200 OK with no body Success without payload
    ResponseEntity.status(HttpStatus.X).body(body) Any status with a body General control
    ResponseEntity.created(location).body(body) 201 Created + Location header Create
    ResponseEntity.noContent().build() 204 No Content, no body Delete

    Golden rule: The controller owns the success response, and the service owns the business decision. If a controller must inspect data to decide an error status, that decision belongs somewhere else.

    7. Why Error Handling Should Not Live Inside Controllers

    Once beginners learn ResponseEntity, they often start writing all error handling inside the controller. For getStudentById, the method calls the service and then checks if (student == null) to return a 404 response before returning the success response. This looks fine for one method, but in a real project the controller starts doing too many things:

    1. Receive request
    2. Call service
    3. Check null
    4. Decide error status
    5. Decide error message
    6. Build error response
    7. Build success response

    A controller should mainly do three things: receive the request, call the service, and return the response. Business checks should stay in the service layer, and common error response logic should stay in one central place.

    The duplicate-email create method makes the same problem visible: it first calls existsByEmail, and if true returns 409 Conflict with "Email already exists", otherwise it saves and returns 201 Created. Now the controller has too much if-else logic, and the same pattern repeats across many APIs. That is not clean design.

    Problems caused by repeated error logic

    1. Repetition - the same error handling logic appears again and again.
    2. Less readable controllers - controllers become full of if-else blocks.
    3. Weak service layer signals - if the service returns null, the controller has to guess what happened.
    4. Inconsistent error responses - different developers may return different error structures.
    5. Poor separation of concerns - the controller should not contain repeated business error response logic.
    Aspect Errors inside the controller Global exception handler
    Where the check lives Scattered in every method One central class
    Controller size Grows with each endpoint Stays small and readable
    Service signal Returns null, controller guesses Throws a meaningful exception
    Error format Whatever each developer chose One consistent DTO
    Adding a new error Edit many controllers Add one handler method
    Separation of concerns Weak Strong

    8. Better Separation, Global Exception Handling, and the Advice Annotations

    A cleaner design splits responsibility across three layers:

    Layer Responsibility
    Controller Receive request and return success response
    Service Run business logic and throw meaningful exceptions
    Global Exception Handler Convert exceptions into proper HTTP responses

    When an API fails, two things happen: some exception occurs inside backend code, and that exception must be converted into a proper HTTP response. Global exception handling means that instead of handling errors separately inside every controller, we create one central place that catches exceptions and converts them into proper API responses.

    Request comes
  |
  v
Controller calls service
  |
  v
Service either returns data or throws exception
  |
  v
GlobalExceptionHandler catches exception
  |
  v
Proper error response goes back to client

    @ControllerAdvice

    @ControllerAdvice is a Spring annotation used to define common behavior for multiple controllers. In simple words, it allows one class to provide common support to controllers, and that support can include exception handling, data binding configuration, and model attributes. By itself, @ControllerAdvice does not handle exceptions; to actually handle exceptions we need methods annotated with @ExceptionHandler, so the real combination is @ControllerAdvice + @ExceptionHandler.

    @RestControllerAdvice

    In REST APIs we usually return JSON responses. For that, Spring provides @RestControllerAdvice, which is a shortcut for @ControllerAdvice + @ResponseBody. That means exception handler methods return the response content directly as JSON instead of resolving a view or JSP page. For REST API projects, prefer @RestControllerAdvice.

    @ExceptionHandler and the handler class

    @ExceptionHandler is used on a method to handle a specific exception type. For example, a method annotated @ExceptionHandler(RuntimeException.class) that takes a RuntimeException ex returns ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(ex.getMessage()). If a RuntimeException occurs, Spring calls that method. The exception class decides which handler method runs, and Spring tries to use the most specific matching exception handler: if handlers exist for both ResourceNotFoundException and Exception, then ResourceNotFoundException is handled by its specific handler, not the generic one. The recommended package for the project is in.strikes.dtoDemo.exception.

    package in.strikes.dtoDemo.exception;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<String> handleResourceNotFoundException(ResourceNotFoundException ex) {
        return ResponseEntity
            .status(HttpStatus.NOT_FOUND)
            .body(ex.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<String> handleGenericException(Exception ex) {
        return ResponseEntity
            .status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body("Something went wrong. Please try again later.");
    }
}

    This class becomes the central place for API error handling. The generic Exception handler is a safety net: it should not be used for normal business cases like "student not found", "duplicate email", or "validation failed", which deserve specific handlers.

    Interviewer's perspective: The ordering rule here is a favorite question. At runtime Spring matches the exception type to the most specific handler, so a dedicated @ExceptionHandler(ResourceNotFoundException.class) always wins over @ExceptionHandler(Exception.class). The generic handler exists only so that nothing escapes as a raw stack trace.

    9. Custom Exceptions and the Clean Controller

    Why create custom exceptions

    Java already has generic exceptions such as RuntimeException, IllegalArgumentException, and NoSuchElementException, but these do not clearly describe business meaning. RuntimeException does not tell much; ResourceNotFoundException clearly says the requested resource does not exist. Custom exceptions make service-layer code more meaningful. Extend RuntimeException because, in Spring Boot service-layer business errors, unchecked exceptions are commonly used: you do not need to write throws in every method signature, which is simple and practical for beginner projects.

    package in.strikes.dtoDemo.exception;

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String message) {
        super(message);
    }
}

    A second custom exception, DuplicateResourceException, follows the same shape with its own String message constructor.

    Throwing a custom exception from the service layer

    Instead of returning null, the service should clearly say what happened. The bad approach is studentRepository.findById(id).orElse(null). The better approach is studentRepository.findById(id).orElseThrow(() -> new ResourceNotFoundException("Student with id " + id + " not found")). Now the service behavior is unambiguous: if the student exists, return the student; if not, throw ResourceNotFoundException. This is much better than returning null.

    The duplicate check in the service does the same: if studentRepository.existsByEmail(requestDto.getEmail()) is true, it throws new DuplicateResourceException("Student with email " + requestDto.getEmail() + " already exists") instead of returning a flag the controller must interpret.

    Clean controller after using custom exceptions

    Once the service throws a meaningful exception, the controller becomes clean. For getStudentById it calls the service and simply returns ResponseEntity.ok(student). There is no if, no null check, and no 404 logic. The success response stays in the controller, and the error response goes to the global exception handler.

    Update and delete API examples

    The update service fetches with findById(id).orElseThrow(() -> new ResourceNotFoundException(...)), copies the incoming name, email and age onto the existing student, and returns studentRepository.save(existingStudent). The @PutMapping("/{id}") controller takes the @PathVariable Long id and @RequestBody Student student, calls the service, and returns ResponseEntity.ok(updatedStudent).

    The delete service fetches with the same orElseThrow pattern and then calls studentRepository.delete(existingStudent). The @DeleteMapping("/{id}") controller calls the service and returns ResponseEntity.noContent().build(). Flow: if deletion succeeds, the controller returns 204 No Content; if the student does not exist, the service throws ResourceNotFoundException and the GlobalExceptionHandler returns 404 Not Found.

    10. The Error Response DTO, Request Path, and Validation Errors

    Why use an error response DTO

    An exception is a Java-side problem; the client does not understand Java exceptions, it understands HTTP responses. A raw throw new ResourceNotFoundException("Student with id 100 not found") is meaningless to a browser. So our job is to take the Java exception through the GlobalExceptionHandler and emit a standard error response JSON. Instead of returning only a string, we return a structured error response. In the project this DTO is named ErrorResponseDto (the course also shows it as ExceptionResponseDto).

    package in.strikes.dtoDemo.dto;

import java.time.LocalDateTime;

public class ErrorResponseDto {
    private LocalDateTime timestamp;
    private int statusCode;
    private String error;
    private String message;
    private String path;

    public ErrorResponseDto(LocalDateTime timestamp, int statusCode,
                            String error, String message, String path) {
        this.timestamp = timestamp;
        this.statusCode = statusCode;
        this.error = error;
        this.message = message;
        this.path = path;
    }

    public LocalDateTime getTimestamp() { return timestamp; }
    public int getStatusCode() { return statusCode; }
    public String getError() { return error; }
    public String getMessage() { return message; }
    public String getPath() { return path; }
}

    Example response:

    {
  "timestamp": "2026-07-07T10:45:30",
  "statusCode": 404,
  "error": "Not Found",
  "message": "Student with id 100 not found",
  "path": "/api/students/100"
}
    Field Meaning
    timestamp When the error happened
    statusCode HTTP status code returned
    error Short HTTP error name
    message Specific explanation of the failure
    path API endpoint where the error occurred

    Why each field earns its place:

    • timestamp helps backend developers match an API error with logs.
    • statusCode lets frontend code branch programmatically, for example if (error.statusCode === 404) { showNotFoundPage(); }.
    • path matters because one page may call multiple APIs (/api/students/100, /api/courses/5, /api/teachers/8); the error response itself tells which endpoint failed.

    Getting the request path with HttpServletRequest

    Spring injects the current request into a handler method, and request.getRequestURI() returns the failing path. A handler for ResourceNotFoundException builds the DTO with LocalDateTime.now(), HttpStatus.NOT_FOUND.value(), HttpStatus.NOT_FOUND.getReasonPhrase(), ex.getMessage(), and request.getRequestURI(), then returns ResponseEntity.status(HttpStatus.NOT_FOUND).body(errorResponse). Required import: import jakarta.servlet.http.HttpServletRequest;.

    Handling validation errors globally

    Suppose the CreateStudentRequestDto carries Bean Validation annotations: @NotBlank(message = "Name cannot be blank") and @Size(min = 2, max = 50, ...) on name; @NotBlank and @Email(message = "Email must be valid") on email; @NotNull(message = "Age is required") and @Min(value = 18, ...) on age. If the client sends {"name":"","email":"wrong-email","age":15}, validation should fail and the API should return a clean 400 Bad Request.

    The flow is:

    Request comes
  |
  v
Spring binds JSON to DTO
  |
  v
Validation runs because of @Valid
  |
  v
Validation fails
  |
  v
Spring throws MethodArgumentNotValidException
  |
  v
GlobalExceptionHandler catches it
  |
  v
Field-level validation response is returned

    Important point: validation runs only when we use @Valid in the controller, as in createStudent(@Valid @RequestBody CreateStudentRequestDto requestDto). MethodArgumentNotValidException occurs when validation fails on a controller method argument; the most common case is exactly that @Valid @RequestBody parameter.

    A professional validation response tells exactly which field failed and why:

    {
  "timestamp": "2026-07-07T11:20:30",
  "statusCode": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "path": "/api/students",
  "fieldErrors": {
    "name": "Name cannot be blank",
    "email": "Email must be valid",
    "age": "Student must be at least 18 years old"
  }
}

    That response comes from ValidationErrorResponseDto (shown in the course as ValidationExceptionResponseDto), which is the base error DTO plus a private Map<String, String> fieldErrors; with a matching constructor and getter. Field errors are extracted with getBindingResult().getFieldErrors() and folded into a map keyed by field name: for each error, put error.getField() mapped to error.getDefaultMessage().

    @ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ValidationErrorResponseDto> handleValidationException(
        MethodArgumentNotValidException ex,
        HttpServletRequest request) {
    Map<String, String> fieldErrors = new HashMap<>();
    ex.getBindingResult().getFieldErrors().forEach(error ->
        fieldErrors.put(error.getField(), error.getDefaultMessage())
    );
    ValidationErrorResponseDto errorResponse = new ValidationErrorResponseDto(
        LocalDateTime.now(),
        HttpStatus.BAD_REQUEST.value(),
        HttpStatus.BAD_REQUEST.getReasonPhrase(),
        "Validation failed",
        request.getRequestURI(),
        fieldErrors
    );
    return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(errorResponse);
}

    Required imports: org.springframework.web.bind.MethodArgumentNotValidException, java.util.HashMap, java.util.Map.

    11. Bad Requests, 400 vs 409, Categories, and Best Practices

    What is 400 Bad Request

    400 Bad Request means the client sent something wrong. Validation failure is one type of bad request; other examples are invalid JSON, wrong data type in JSON, malformed request body, invalid request format, invalid path variable type, and missing required query parameter.

    Invalid JSON or wrong data type. Suppose the DTO expects private Integer age; but the client sends "age": "twenty". Spring tries to convert "twenty" into Integer, fails, and for an unreadable or malformed body throws HttpMessageNotReadableException; the handler returns 400 Bad Request with a message like "Invalid request body. Please check your JSON format and data types." Required import: org.springframework.http.converter.HttpMessageNotReadableException.

    Invalid path variable type. Suppose the controller expects @PathVariable Long id, but the client calls GET /api/students/abc. Spring cannot convert "abc" into Long and may throw MethodArgumentTypeMismatchException. A clean API returns 400 Bad Request, with a message such as "Invalid value for parameter '" + ex.getName() + "'. Please check the required data type.". Required import: org.springframework.web.method.annotation.MethodArgumentTypeMismatchException.

    Difference between 400 Bad Request and 409 Conflict

    First principle: 400 means the request itself is invalid; 409 means the request may be valid, but it conflicts with existing server data.

    Situation Status code Why
    Invalid email format 400 Bad Request The value is malformed regardless of server data
    Age sent as the string "twenty" 400 Bad Request Wrong data type in the request body
    Invalid path variable abc for a Long 400 Bad Request The request cannot be bound
    Email already exists 409 Conflict The request is valid but clashes with stored data
    Roll number already exists 409 Conflict Valid request, conflicting state

    DuplicateResourceException is handled by its own method that returns an ErrorResponseDto built with HttpStatus.CONFLICT.value(), HttpStatus.CONFLICT.getReasonPhrase(), ex.getMessage() and request.getRequestURI().

    The complete handler class

    The final GlobalExceptionHandler is one @RestControllerAdvice class holding one @ExceptionHandler method per failure type, all returning the standard DTO:

    Handler method Exception Status Response body
    handleResourceNotFoundException ResourceNotFoundException 404 ErrorResponseDto
    handleDuplicateResourceException DuplicateResourceException 409 ErrorResponseDto
    handleValidationException MethodArgumentNotValidException 400 ValidationErrorResponseDto
    handleHttpMessageNotReadableException HttpMessageNotReadableException 400 ErrorResponseDto
    handleMethodArgumentTypeMismatchException MethodArgumentTypeMismatchException 400 ErrorResponseDto
    handleGenericException Exception 500 ErrorResponseDto

    Every method builds its DTO with LocalDateTime.now(), the status value and reason phrase, a human message, and request.getRequestURI().

    Categories of exceptions

    The project handles three major groups:

    1. Business exceptions - meaningful business problems.
    Exception Meaning Status code
    ResourceNotFoundException Requested resource does not exist 404 Not Found
    DuplicateResourceException Resource already exists or conflicts with data 409 Conflict
    1. Request/input exceptions - the client sent incorrect data.
    Exception Meaning Status code
    MethodArgumentNotValidException Validation failed on DTO 400 Bad Request
    HttpMessageNotReadableException Invalid JSON or wrong data type in request body 400 Bad Request
    MethodArgumentTypeMismatchException Wrong type in path variable or request parameter 400 Bad Request
    1. Unexpected exceptions - fallback server-side errors.
    Exception Meaning Status code
    Exception Any unhandled unexpected error 500 Internal Server Error

    Why this makes APIs professional

    • Controllers stay clean.
    • Repeated error logic is removed.
    • Frontend receives consistent error responses.
    • Service layer communicates failures clearly.
    • Status codes match the real meaning of the failure.
    • Debugging becomes easier because error responses contain timestamp and path.
    • Unexpected errors are handled safely through a generic fallback.

    Best practices

    1. Do not return null for missing resources. Prefer orElseThrow(() -> new ResourceNotFoundException(...)) over orElse(null).
    2. Keep success logic in the controller - the controller mainly returns successful responses such as return ResponseEntity.ok(student);.
    3. Keep business checks in the service - whether a student exists, whether an email already exists, whether a roll number already exists, whether the user is allowed to perform the action.
    4. Keep error response logic in the GlobalExceptionHandler - the status code, the error message, and the error response structure.
    5. Use specific handlers before relying on the generic fallback. Specific handlers give meaningful responses; the generic handler is only a final safety net.
    6. Do not expose internal exception messages in production. Avoid .body(ex.getMessage()) for unexpected errors; prefer .body("Something went wrong. Please try again later.") to prevent leaking implementation details.

    Important: Business checks in the service, HTTP mapping in the handler, and success responses in the controller - that is the whole division of labor. Breaking it is what turns a clean API back into an if-else soup.

    12. Myth vs Reality

    Myth Reality
    "Returning 200 OK for every operation is fine" Status codes carry the outcome; use 201 for create, 204 for empty delete, 400/404/409 for failures.
    "If the service returns null, the controller should decide the error" Returning null is a weak signal; the service should throw a meaningful exception.
    "@ControllerAdvice alone handles exceptions" It only declares common behavior; actual handling needs @ExceptionHandler methods.
    "@ControllerAdvice is best for REST JSON" @RestControllerAdvice adds @ResponseBody, so handlers return JSON directly.
    "The generic Exception handler should cover business cases" It is only a safety net; "not found", "duplicate", and validation failures need specific handlers.
    "404 and 500 mean the same kind of failure" 404 is a missing resource the server understood; 500 is an unexpected server-side break.
    "400 and 409 both mean a bad client request" 400 is an invalid request; 409 is a valid request that conflicts with existing data.
    "Exposing raw exception messages helps the frontend" It leaks implementation details; return a safe generic message for unexpected errors.

    13. Common Trap Questions

    Trap 1 - "Everything can just return 200 OK with an error message in the body." Verdict: False. The frontend branches on the status code, so a failure must return a failure status. A 404 body sent with 200 OK forces the client to parse strings to detect errors.

    Trap 2 - "Returning null from the service is a valid way to signal not found." Verdict: False. null forces the controller to guess, repeats checks across endpoints, and produces weak service-layer signals. Throw ResourceNotFoundException instead.

    Trap 3 - "@ControllerAdvice by itself handles exceptions." Verdict: False. @ControllerAdvice defines shared behavior; handling needs @ExceptionHandler. For JSON REST APIs, prefer @RestControllerAdvice (@ControllerAdvice + @ResponseBody).

    Trap 4 - "The generic Exception handler will swallow specific ones." Verdict: False. Spring picks the most specific matching handler, so ResourceNotFoundException runs its own method, and the generic Exception handler covers only what is left.

    Trap 5 - "Validation runs automatically for any request body." Verdict: False. Validation runs only when the controller parameter is annotated with @Valid. Without it, the constraints are never checked.

    Trap 6 - "400 and 409 mean the same: the client messed up." Verdict: False. 400 means the request is invalid on its own (bad JSON, wrong type, invalid path variable); 409 means the request is valid but conflicts with existing server state, such as a duplicate email.

    14. Points to Remember

    1. An API response is Status + Headers + Body (S-H-B); the status code is protocol-level meaning and the body is the human-readable explanation.
    2. A beginner API asks "did I get data"; a professional API asks "did the server clearly tell the client what happened".
    3. Status codes: 200 fetch/update, 201 create, 204 delete with no body, 400 invalid request, 404 missing resource, 409 conflict, 500 unexpected server failure.
    4. ResponseEntity gives explicit control over status, headers, and body; its mental model is Body + Status, Body + Headers + Status, or Status only.
    5. ResponseEntity.created(location) sets both 201 Created and the Location header; noContent().build() returns 204 with no body.
    6. Error handling inside controllers causes repetition, bulky controllers, weak service signals, inconsistent responses, and poor separation of concerns.
    7. Global exception handling puts errors in one central place; the division of labor is controller = success, service = business checks, handler = HTTP mapping.
    8. @RestControllerAdvice = @ControllerAdvice + @ResponseBody; @ExceptionHandler maps a specific exception type to a response, and Spring picks the most specific match.
    9. Custom exceptions (ResourceNotFoundException, DuplicateResourceException) extend RuntimeException and are thrown from the service via orElseThrow, keeping the controller free of if and null checks.
    10. ErrorResponseDto (timestamp, statusCode, error, message, path) and ValidationErrorResponseDto (plus fieldErrors) give consistent JSON; validation needs @Valid, throws MethodArgumentNotValidException, and bad JSON or wrong types map to 400.

    15. Likely Interview Questions

    Question Crisp Answer
    What are the three parts of an API response? Status code (HTTP meaning), headers (metadata), and body (data or error message).
    When do you return 201 and 204? 201 Created when a new resource is created; 204 No Content on a successful delete with no body.
    What is ResponseEntity and why use it? A wrapper that lets the controller explicitly set status, headers, and body instead of letting Spring decide.
    Why is error handling inside controllers bad? It repeats logic, bloats controllers, weakens service signals, and yields inconsistent responses.
    What is global exception handling? One central place (@RestControllerAdvice) that catches exceptions and converts them to proper HTTP responses.
    Difference between @ControllerAdvice and @RestControllerAdvice? @RestControllerAdvice = @ControllerAdvice + @ResponseBody, so handlers return JSON directly.
    What does @ExceptionHandler do? On a method, it handles a specific exception type; Spring runs the most specific matching handler.
    Why custom exceptions? Generic exceptions do not express business meaning; ResourceNotFoundException says exactly what went wrong.
    Why throw from the service instead of returning null? Throwing gives a clear signal and keeps success logic in the controller and error mapping in the handler.
    400 vs 409? 400 = the request is invalid; 409 = the request is valid but conflicts with existing data (e.g., duplicate email).
    How are validation errors handled globally? @Valid triggers validation, Spring throws MethodArgumentNotValidException, and the handler maps field errors to a 400 DTO.
    What does ErrorResponseDto contain? timestamp, statusCode, error, message, path - a consistent error shape the frontend can rely on.
