    Messaging Queues and Kafka

    10 sections · 736 words

    Decoupling producers from consumers, and how Kafka differs from a plain queue.

    1. Messaging Queue Basics

    Tools: Kafka (important) and RabbitMQ. Note that Kafka is not just a messaging queue.

    A queue has a producer that produces (publishes) messages and a consumer that consumes them.

    Benefit of producer/consumer: the producer and consumer can work at their own pace.

    Synchronous vs asynchronous communication

    • Synchronous: MS1 -HTTP GET-> MS2; MS1 waits for the response (200 ms), so it sits idle for 200 ms.
    • Asynchronous: MS1 -HTTP GET-> MS2 returns 200 OK in 200 ms while MS2 does the work. This gives a busy service and a normal service with high throughput. Synchronous throughput is less, and if MS2 goes down the call fails.

    In HLD, throughput is measured in OPS (operations per second).

    2. Ola/Uber/Rapido Example

    A driver vehicle sends GPS at freq = 1 signal/sec.

    Back-of-the-envelope:

    Delhi -> 1 lakh drivers in Ola
Per second -> 1 lakh req/sec

    This value must be added to a DB for fare calculation. A SQL/NoSQL store (Cassandra, Mongo) would put very high load on one DB.

    How Kafka solves it:

    Ola producer (1 lakh/sec) -> Kafka -> workers (consumers) -> DB (SQL)
    • Every DB that exists will not have such high throughput.
    • Kafka is a messaging queue with very high throughput.
    • Workers do bulk upload onto the DB.

    A web server's job is to take the request from the client, process it, and put the data in the DB. DBs are comparatively slower, so latency is higher (data structures like B+ trees and B trees).

    3. Why Kafka Is Useful

    1. Pace matching - producer and consumer run at their own speeds.
    2. Async communication - for example the notification system (consumer/producer feeding APNs, FCM, MailChimp).

    4. In-Depth Architecture of Kafka

    The vocabulary:

    • Cluster.
    • Broker (the Kafka server).
    • Topic.
    • Partition.
    • Offset.
    • Zookeeper / KRaft.
    • Consumer.
    • Consumer group.
    • Producer.

    Topics hold messages; for example topic0 -> rider loc and topic1 -> notifications.

    5. Consumer Groups

    Consumers read from partitions (0-4 in the picture) and are grouped so that work is shared.

    • The system auto-balances: as consumers join, partitions are redistributed.
    • If the number of partitions is less than the number of consumers, some consumers remain idle.
    • One consumer can consume multiple partitions.
    • But one partition can be consumed by only one consumer.

    Example position: consumer group 1, consumer 2, topic 0, partition 0, offset 2.

    6. Why Kafka Does All This

    Consumer groups are fairly new in Kafka. Messaging queues serve two purposes:

    1. Queue (FIFO) - 1 producer to 1 consumer.
    2. Pub/Sub (publisher/subscriber model) - 1 producer to many consumers, i.e. broadcasting. For example, a publisher (Coder Army) broadcasts to subscribers.

    Kafka came from LinkedIn. Zookeeper manages cluster metadata.

    7. Clusters and Replication

    A cluster has multiple brokers, each holding partitions, with leaders and followers:

    • Leader - handles both read and write.
    • Follower - just follows (listens to) the leader.
    • Example: topic 0 spread across Broker1, Broker2, and Broker3, with leaders and followers (Q1, Q2, Q3).

    8. Producing a Message

    • Message fields: key (optional), value (the actual message), topic (for example topic0), partition (optional).
    • Partition selection uses a round robin method or hash % (number of partitions).
    • retry: 03 - a message may be retried before being diverted.

    Dead Letter Queue

    Messages that cannot be processed after retries go to a dead letter queue. Example use: a Discord server or an Ola/Uber server sending a request whose message is a bug that cannot be resolved.

    9. RabbitMQ

    RabbitMQ routes messages through an exchange into queues:

    • Components: producer -> exchange -> queue0/queue1/queue2 -> consumer1/consumer2, with message keys such as 123qwe, 123rty, 456qwe.

    The exchange holds the rules that decide which queue a message goes to:

    • Fan-out: broadcast.
    • Direct exchange: match the message key (MK) to the routing key (RK).
    • Topic exchange: wildcards are allowed (*).

    Keys:

    • Message key: the key that comes with the message.
    • Routing key: the exchange key.

    Topic exchange example: MK: 123qty, RK: 123q*.

    There is also a re-queue mechanism.

    10. Pull vs Push

    • Kafka uses a pull-based technique.
    • RabbitMQ uses a push-based technique.
