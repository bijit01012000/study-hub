      91. Composition over inheritance — why?

      Asked at: Most Java mid-level rounds

      Difficulty: Medium · Topic: OOP

      The question: "What does 'favor composition over inheritance' mean and why?"

      The 30-second answer: Inheritance creates tight coupling — subclass depends on superclass internals, breaks if the parent changes. Composition holds another object as a field and delegates to it — looser coupling, more flexible (you can swap the composed object). The classic example: a stack should HAVEA list, not BE-A list, otherwise it inherits methods it shouldn't expose.

      Step-by-step thought process:

      1. "Inheritance is is-a. Composition is has-a. Misusing inheritance leaks superclass methods you don't want."
      2. "Concrete: if Stack extends ArrayList, your stack accidentally exposes add(index, element) and remove(index) — callers can corrupt stack semantics."
      3. "Composition: class Stack { private final List<E> items = new ArrayList<>(); void push(...) { items.add(...); } }. Only the methods you want are exposed."
      4. "Inheritance also fragilizes: if ArrayList adds a new method in a later JDK, your subclass might silently break invariants."
      5. "Use inheritance for true is-a relationships within a small, controlled hierarchy. Use composition (often with interfaces) for everything else."

      Edge cases to mention:

      • Records (Java 16+) cannot extend other classes — Java is pushing toward composition for data classes
      • Default methods in interfaces give you behavior reuse without inheritance — adopted heavily in modern Java APIs
      • Some patterns (Template Method) genuinely need inheritance — composition isn't a hammer for every nail

      What NOT to say:

      • "Inheritance is always bad" — overreach; it has its place
      • "Composition is faster" — performance is roughly the same; this is a design argument

      Common follow-up: "What does the Liskov Substitution Principle say about inheritance?"

      92. Liskov Substitution Principle — concrete example

      Asked at: Most senior Java rounds · Razorpay · Cred

      Difficulty: Medium-Hard · Topic: OOP

      The question: "State the Liskov Substitution Principle and give a real example of violating it."

      The 30-second answer: A subtype must be substitutable for its supertype without changing program correctness. Classic violation: Square extends Rectangle. If setWidth(5) and setHeight(10) works on Rectangle (area 50), it can't work on Square (a Square would force both to 10, breaking callers that assumed independent dimensions).

      Step-by-step thought process:

      1. "From Barbara Liskov: if S is a subtype of T, then objects of type T can be replaced with objects of type S without breaking the program."
      2. "Square-Rectangle is the textbook violation. Math says a square IS a rectangle, but in OOP, mutating a Rectangle via setWidth/ setHeight should be independent — Square breaks that."
      3. "Real-world violation I've seen: ReadOnlyList extends ArrayList. Adding throws UnsupportedOperationException. Caller types as ArrayList and expects to add — runtime crash."
      4. "How to detect: any subclass that throws on a method it inherited, or weakens preconditions/strengthens postconditions, violates LSP."
      5. "Fix: separate ReadOnlyList and MutableList into distinct interfaces. Don't force inheritance to model a 'special case' that breaks parent contracts."

      Edge cases to mention:

      • Java's Collections.unmodifiableList violates LSP technically — it throws on mutation. Pragmatic trade-off the JDK made
      • Sealed classes (Java 17+) give you a way to control the hierarchy and reason about all subtypes
      • Pre/post conditions: subtype can ACCEPT more (weaker precondition) and PRODUCE less (stronger postcondition) without violating

      What NOT to say:

      • "LSP says inheritance is bad" — it doesn't; it says inheritance has a contract
      • "LSP is theoretical, doesn't apply to real code" — every cast or polymorphic call relies on it

      Common follow-up: "How would you redesign Square and Rectangle to avoid this?"

      93. Interface Segregation Principle

      Asked at: Senior rounds · Razorpay · Walmart Labs

      Difficulty: Medium · Topic: OOP

      The question: "Explain Interface Segregation. Show me when a 'fat interface' is a problem."

      The 30-second answer: Don't force clients to depend on methods they don't use. Split fat interfaces into smaller, role-specific ones. Classic example: Worker interface with work() and eat(). A RobotWorker is forced to implement eat() even though it makes no sense — split into Workable and Eatable.

      Step-by-step thought process:

      1. "Symptom: an interface with 20 methods, where implementations regularly leave half as no-ops or throw UnsupportedOperationException."
      2. "Real example: JDK's Map is fat — put, remove, clear shouldn't apply to read-only views. JDK provides unmodifiableMap that throws on writes — LSP violation born from ISP violation."
      3. "Better design: split into ReadableMap and WritableMap. Read-only views implement only ReadableMap. Callers depend on the narrowest interface they need."
      4. "In Java 8+, default methods make small interfaces ergonomic — you can ship sensible defaults without forcing all implementers to write boilerplate."
      5. "Pragmatic rule: if 50% of implementers throw or no-op a method, that method belongs in a separate interface."

      Edge cases to mention:

      • Don't over-split — 50 tiny interfaces is also hard to use. Aim for cohesive roles, not method-per-interface
      • Marker interfaces (Serializable, Cloneable) are an ISP-related antipattern in modern Java; prefer annotations
      • For external libraries, you often can't change the interface — use Adapter pattern to give callers a narrower view

      What NOT to say:

      • "Just use one big interface for simplicity" — that's exactly the anti-pattern
      • "Default methods solve everything" — they help, but don't eliminate the design question

      Common follow-up: "How do default methods relate to interface segregation?"

      94. Immutability — how to design an immutable class properly

      Asked at: Most Java mid-level rounds · Razorpay · Wells Fargo

      Difficulty: Medium · Topic: OOP

      The question: "How do you make a class truly immutable in Java?"

      The 30-second answer: Make the class final (or use sealed). Make all fields private final. Don't expose setters. Defensively copy mutable arguments in the constructor. Defensively copy any mutable fields when returning them from getters. Or use records (Java 16+), which handle the boilerplate but still need defensive copies for mutable components.

      Step-by-step thought process:

      1. "Class must be final — otherwise a subclass can add mutable state and break the contract."
      2. "All fields private final — final ensures field can't be re-assigned. Private blocks external access."
      3. "No setters. Constructor sets everything; that's it."
      4. "Defensive copy on input: if constructor takes a List<String>, copy it: this.items = List.copyOf(items);. Otherwise the caller still holds a mutating reference."
      5. "Defensive copy on output: getter for a mutable field should return a copy or an unmodifiable view: return List.copyOf(items);. Records don't auto-do this."

      Edge cases to mention:

      • Records (Java 16+) give you immutability for the record's own fields but mutable components (a List inside a record) are still mutable through their getters
      • For deep immutability of complex graphs, you may need to wrap children too — use Collections.unmodifiableList, Map.copyOf, Set.copyOf
      • BigDecimal and LocalDate are immutable — chain returns a new instance, doesn't mutate

      What NOT to say:

      • "Just mark the class final, that makes it immutable" — incomplete; fields could still be mutable
      • "Immutable means thread-safe and that's it" — also enables hash safety, defensive freezing, fewer bugs

      Common follow-up: "What's the difference between an immutable List and an unmodifiable List?"

      95. Builder pattern vs Factory pattern

      Asked at: Most Java mid-level rounds

      Difficulty: Easy-Medium · Topic: OOP / Design Patterns

      The question: "When would you use Builder pattern vs Factory pattern?"

      The 30-second answer: Builder for constructing one object with many optional parameters — readable, immutable result, no telescoping constructors. Factory for choosing which concrete type to instantiate based on input — hides the concrete class from callers. They solve different problems and can be combined.

      Step-by-step thought process:

      1. "Builder: when an object has many fields, especially optional ones. Order.builder().merchantId(...).amount(...).build(); is far cleaner than a 10-arg constructor with most args as null."
      2. "Lombok's @Builder annotation generates the builder for you. Spring uses builder pattern heavily — WebClient.builder(), Customizer.withDefaults()."
      3. "Factory: when callers shouldn't know the concrete type. PaymentGateway.forProvider("razorpay") returns the right implementation; caller just sees PaymentGateway."
      4. "Static factory method on the class itself: Optional.of(value), List.of(a, b, c). Often clearer than new because the name conveys intent."
      5. "Both can combine: a factory method that internally uses a builder, or a builder that produces different concrete subtypes based on configuration."

      Edge cases to mention:

      • For objects with 3-4 required fields and no optionals, a plain constructor is still best
      • Builder with required fields can use staged builders: OrderBuilder.merchantId(...).amount(...).optional(...).build() — type system enforces required-first
      • Records make builders less necessary for simple data classes — but if you need optionals or validation, builder still wins

      What NOT to say:

      • "Always use Builder for everything" — overkill for simple constructors
      • "Factory and Builder are the same" — they solve different problems

      Common follow-up: "How would you design a Builder for an immutable Order with required and optional fields?"

      96. try-with-resources — how does it work?

      Asked at: Most Java mid-level rounds

      Difficulty: Easy-Medium · Topic: Exception handling

      The question: "What does try-with-resources do, and what does the resource need to implement?"

      The 30-second answer: try-with-resources auto-closes resources at the end of the block. The resource must implement AutoCloseable (or Closeable, which is older and throws IOException). On exception, the resource is still closed; if close itself throws, the original exception is preserved and the close exception is added as a suppressed exception.

      Step-by-step thought process:

      1. "Syntax: try (Connection conn = dataSource.getConnection(); Statement st = conn.createStatement()) {... }. Multiple resources, semicolon-separated."
      2. "Resources are closed in REVERSE order of declaration. So st closes before conn — important when resources depend on each other."
      3. "Resource type must implement AutoCloseable (single method: close() throws Exception). Closeable is a subtype that narrows the throws to IOException."
      4. "Java 9+ allows referring to an existing effectivelyfinal variable in the try header: try (existingResource) {... }. Avoids reassignment."
      5. "Exception handling: if the body throws AND close throws, the body's exception is primary; the close exception is added via Throwable.addSuppressed(). Recover both via getSuppressed()."

      Edge cases to mention:

      • Resources are closed even on return inside the block — finally semantics
      • A null resource throws on close — wrap with a non-null check or use an empty Optional pattern
      • Don't catch InterruptedException inside try-with-resources for InputStream/OutputStream — propagate properly

      What NOT to say:

      • "It's just syntactic sugar for try/finally" — true but missed the suppressed exception mechanism
      • "Resource must implement Closeable" — AutoCloseable is the actual requirement (Closeable is a subtype)

      Common follow-up: "What's a suppressed exception and how do you read it?"

      97. Custom exceptions — when and how

      Asked at: Most Spring backend rounds · Razorpay · Walmart

      Difficulty: Easy-Medium · Topic: Exception handling

      The question: "When would you create a custom exception class? How would you design it?"

      The 30-second answer: Create one when the caller needs to programmatically distinguish your error from generic ones — e.g. PaymentDeclinedException vs a generic RuntimeException. Usually extend RuntimeException (unchecked). Include relevant context (orderId, attemptedAmount, declineCode) as fields. Override getMessage() for a useful log line.

      Step-by-step thought process:

      1. "Don't create exceptions just for namespacing — MyAppException extends RuntimeException adds nothing if it has no fields. Use existing exceptions like IllegalStateException for programming errors."
      2. "Do create when callers need to switch on type: catch (PaymentDeclinedException e) vs catch (PaymentTimeoutException e) triggers different recovery."
      3. "Default to unchecked (extends RuntimeException) — Spring and modern Java prefer this. Use checked only when callers MUST handle it (rare)."
      4. "Include context: public PaymentDeclinedException(String orderId, BigDecimal amount, String reason) { super(...); this.orderId = orderId;... }."
      5. "In Spring REST, pair with @ResponseStatus(BAD_REQUEST) or an @ExceptionHandler that maps to an HTTP response. Don't leak stack traces to callers."

      Edge cases to mention:

      • Always preserve the cause: throw new PaymentException("failed", originalIOException); — losing the cause hides the real reason
      • For libraries you publish, document which exceptions your API throws and under what conditions
      • Avoid swallowing exceptions silently — catch (Exception e) { / ignore / } is the most expensive bug pattern

      What NOT to say:

      • "Use checked exceptions for everything to be safe" — modern Java tends the other way; checked exceptions create boilerplate
      • "Just throw RuntimeException directly" — losing the type means callers can't differentiate

      Common follow-up: "How would you map a custom exception to a 400 status code in Spring?"

      98. Exception chaining — preserve the cause

      Asked at: Most Java mid-level rounds

      Difficulty: Easy-Medium · Topic: Exception handling

      The question: "What is exception chaining and why does it matter?"

      The 30-second answer: Exception chaining wraps a low-level exception inside a higher-level one while preserving the original — new ServiceException("payment failed", originalSQLException). The original is accessible via getCause(). Critical because losing the cause hides the actual reason in stack traces.

      Step-by-step thought process:

      1. "Constructors: Exception(message, cause) or initCause(cause) afterwards. Always preserve the original."
      2. "Stack traces print causes via 'Caused by:' lines — gives you the full chain from low to high level."
      3. "Anti-pattern: try {... } catch (SQLException e) { throw new ServiceException("db error"); } — original SQLException is LOST. Should be throw new ServiceException("db error", e);."
      4. "For multiple causes (try-with-resources, parallel ops), use addSuppressed() to attach them to the primary exception."
      5. "Spring's DataAccessException hierarchy wraps native DB exceptions but preserves them as cause — you can dig into the SQLException details if needed."

      Edge cases to mention:

      • The cause field is set-once — initCause throws if called twice. Use Throwable(message, cause) constructor instead
      • getMessage() returns only the immediate message; use a formatter like ExceptionUtils.getRootCauseMessage for chain summaries
      • In structured logging, log the entire exception object — most loggers (SLF4J + Logback) print the full chain

      What NOT to say:

      • "Log and rethrow" — double-logs; either log OR rethrow with cause, not both
      • "Just create a new exception, forget the cause" — destroys the most useful debugging info

      Common follow-up: "What's the difference between getCause() and getSuppressed()?"

      99. Checked exceptions — are they obsolete?

      Asked at: Senior rounds · Razorpay · Cred

      Difficulty: Medium · Topic: Exception handling

      The question: "Some people say checked exceptions are obsolete. What's your view?"

      The 30-second answer: Checked exceptions force callers to acknowledge failures at compile time — a good idea in theory. In practice they create boilerplate, leak through abstraction layers, and lead to catch-and-ignore. Modern Java (Spring, Stream API, CompletableFuture) leans heavily toward unchecked. I default to unchecked, use checked only when the caller can meaningfully recover and the recovery is local.

      Step-by-step thought process:

      1. "Original intent: force callers to handle expected failures. FileNotFoundException on open says 'this might not exist'."
      2. "Problem 1: checked exceptions don't compose with lambdas. stream.map(file -> new BufferedReader(new FileReader(file))) doesn't compile because FileReader throws checked. You're forced to wrap or catch."
      3. "Problem 2: in service layers, low-level checked exceptions either propagate everywhere (every method declares throws SQLException) or get wrapped repeatedly (boilerplate)."
      4. "Problem 3: catchand-ignore is rampant — developers add empty catch blocks just to compile, hiding real failures."
      5. "My rule: throw unchecked for everything in business code. Reserve checked for narrow cases where the caller has a concrete recovery path AND the recovery is local to the caller."

      Edge cases to mention:

      • Callable was created to allow checked exceptions in a runnable-like interface — predates the unchecked-everywhere trend
      • Lombok's @SneakyThrows lets you throw checked exceptions without declaring them — handy but controversial
      • Project Loom and structured concurrency revive interest in checked exceptions for explicit failure handling

      What NOT to say:

      • "Checked exceptions are objectively bad" — there's a real argument both ways
      • "Wrap everything in RuntimeException" — usually right, but loses type info

      Common follow-up: "How does Spring's @Transactional handle checked vs unchecked exceptions for rollback?"
