      123. @PostConstruct vs constructor injection

      Asked at: Most Spring rounds

      Difficulty: Medium · Topic: Spring Core

      The question: "What's the difference between initialization in the constructor and in a @PostConstruct method?"

      The 30-second answer: Constructor runs before any injection happens — so field-injected dependencies are null. @PostConstruct runs AFTER all dependencies are injected — safe to use any injected bean. For constructor injection (preferred), the dependencies ARE available in the constructor.

      Step-by-step thought process:

      1. "Constructor runs at instantiation. With constructor injection, dependencies are passed in — fully usable inside."
      2. "With field/setter injection, the constructor runs first, then Spring sets the fields. Using a field-injected dependency in the constructor — NullPointerException."
      3. " @PostConstruct runs after all injection is complete, before the bean is published. Safe to use any dependency."
      4. "Use @PostConstruct for: validation of injected state, populating caches from a repository at startup, starting background threads tied to the bean's lifecycle."
      5. "Modern preference: constructor injection + perform setup in a method called from the constructor. Avoids @PostConstruct except when you genuinely need post-injection logic."

      Edge cases to mention:

      • @PostConstruct is jakarta.annotation in Spring 6+ — was javax.annotation in earlier versions
      • InitializingBean.afterPropertiesSet() is an alternative — same lifecycle slot, no annotation
      • AOP proxies are wired AFTER @PostConstruct in some configurations — calling proxied methods on this inside @PostConstruct may bypass the proxy

      What NOT to say:

      • "Constructor and @PostConstruct are the same" — different lifecycle slots, different access to dependencies
      • "Always use @PostConstruct for initialization" — constructor injection makes it usually unnecessary

      Common follow-up: "What's the order between @PostConstruct and Spring's AOP proxy wiring?"

      124. @Bean vs @Component — when each?

      Asked at: Most Spring rounds

      Difficulty: Easy · Topic: Spring Core

      The question: "What's the difference between defining a bean with @Bean and with @Component?"

      The 30-second answer: @Component goes on the class — Spring instantiates it via reflection on the constructor. @Bean goes on a method inside a @Configuration class — YOU write the instantiation, can pass args, return any type. Use @Component for your own classes; @Bean for third-party classes you don't own, or when construction logic is complex.

      Step-by-step thought process:

      1. "@Component on your own class: Spring sees the annotation, calls the constructor (with injected args), registers the bean."
      2. "@Bean on a method: @Bean public RestTemplate restTemplate() { return new RestTemplate(); } inside a @Configuration class. You control creation."
      3. "@Bean wins for third-party classes — you can't annotate a class from a library, so @Bean is the only way to register them."
      4. "@Bean wins for conditional or complex construction — if (env.acceptsProfiles("cloud")) return cloudClient(); else return localClient();."
      5. "@Component is shorter for your own classes when constructor injection covers the needs."

      Edge cases to mention:

      • Methods on @Configuration classes are wrapped by CGLIB — calling beanA() from beanB() returns the cached singleton instance, not a new one. Only happens for @Configuration, not @Component
      • @Bean(initMethod=, destroyMethod=) lets you wire up lifecycle methods without implementing JDK interfaces
      • @Bean methods can take parameters — Spring autoinjects them as bean references

      What NOT to say:

      • "Use @Bean for primary beans, @Component for secondary" — both can be primary; that's a separate concern
      • "@Bean is slower" — both are evaluated once at startup; runtime cost is identical

      Common follow-up: "Why do @Configuration class methods return the same instance when called from another @Bean method?"

      125. Spring Data JPA — what does it generate?

      Asked at: Most Spring backend rounds · Razorpay · Swiggy · Walmart

      Difficulty: Easy-Medium · Topic: Hibernate / JPA / Spring

      The question: "How does Spring Data JPA generate implementations from repository interfaces?"

      The 30-second answer: At startup, Spring scans for interfaces extending JpaRepository<Entity, ID>. For each, it creates a proxy at runtime that implements the methods. Method names are parsed by convention — findByMerchantIdAndStatus(...) becomes a SELECT generated automatically. Custom queries via @Query annotation.

      Step-by-step thought process:

      1. "Spring uses bean factory post-processors to scan for Repository interfaces. For each, it creates a JDK or CGLIB proxy backed by SimpleJpaRepository."
      2. "Standard methods (findById, findAll, save, delete) are implemented in SimpleJpaRepository — uses EntityManager under the hood."
      3. "Method-name queries: findByMerchantIdAndStatusOrderByCreatedAtDesc(String, OrderStatus) is parsed — generates SELECT * FROM orders WHERE merchant_id =? AND status =? ORDER BY created_at DESC."
      4. "@Query lets you write JPQL or native SQL: @Query("SELECT o FROM Order o WHERE o.amount >:min"). Use nativeQuery=true for raw SQL."
      5. "For complex queries, define a custom interface (OrderRepositoryCustom) with an implementation class (OrderRepositoryImpl) — Spring Data wires both together."

      Edge cases to mention:

      • Method-name parsing has limits — anything beyond ~3 conditions or with OR logic gets unreadable. Use @Query or Specifications
      • @Modifying is required on @Query for UPDATE/DELETE — Spring otherwise treats them as SELECTs
      • For pagination, return Page<T> from the method — Spring generates COUNT + SELECT with LIMIT/OFFSET

      What NOT to say:

      • "Spring Data uses bytecode generation at compile time" — actually runtime proxies
      • "Just write SQL for everything" — defeats the purpose of derived queries for simple cases

      Common follow-up: "How does Spring Data JPA handle pagination and sorting?"

      126. @Async — how Spring runs async methods

      Asked at: Most Spring backend rounds · Razorpay · Swiggy

      Difficulty: Medium · Topic: Spring Core

      The question: "How does Spring's @Async annotation work? What's the common gotcha?"

      The 30-second answer: @Async on a public method makes the call return immediately — the actual execution runs on a TaskExecutor thread. Requires @EnableAsync on a config class. Common gotcha: self-invocation. Calling this.asyncMethod() from within the same bean bypasses the AOP proxy, so the method runs synchronously.

      Step-by-step thought process:

      1. " @EnableAsync activates the support. Configure the TaskExecutor (ThreadPoolTaskExecutor) — otherwise Spring uses a default that can OOM."
      2. " @Async on a public method: caller gets back immediately. Return void or CompletableFuture<T> (or Future<T>). Spring runs the method on the executor."
      3. "The mechanism is AOP. Spring wraps the bean in a proxy; the proxy intercepts the call and submits a Runnable to the executor."
      4. "Selfinvocation: if method A in bean X calls this.B() and B is @Async, the call bypasses the proxy — runs sync. Inject yourself via a @Lazy self-reference or restructure the code."
      5. "Exception handling: void async methods can't propagate exceptions to the caller. Use a @AsyncUncaughtExceptionHandler for void; with CompletableFuture, exceptions flow through the future."

      Edge cases to mention:

      • Don't use the default SimpleAsyncTaskExecutor in production — it creates a new thread per task with no pool
      • @Async on private methods is ignored — AOP requires public
      • For Spring Boot 3.2+ with virtual threads, set spring.threads.virtual.enabled=true — async tasks use virtual threads

      What NOT to say:

      • "Async makes my code faster automatically" — it shifts work to another thread; doesn't make the work faster
      • "@Async works on private methods" — silently doesn't

      Common follow-up: "How do you handle exceptions from a void @Async method?"

      127. Reflection — when is it appropriate?

      Asked at: Senior Java rounds

      Difficulty: Medium-Hard · Topic: Reflection

      The question: "When would you actually use reflection in real code?"

      The 30-second answer: Rarely in app code; commonly in frameworks. Use cases: dynamic instantiation when class is known only at runtime (plugins, deserialization), reading annotations (Spring scans for @Component, Jackson reads @JsonProperty), generic-purpose tooling (test runners, ORMs). For app code, prefer interfaces and DI over reflection.

      Step-by-step thought process:

      1. "Reflection lets you inspect classes, fields, methods at runtime, and invoke them dynamically. Powerful but slow and breaks encapsulation."
      2. "Frameworks use it everywhere — Spring's DI, Hibernate's entity mapping, Jackson's serialization. As a framework author, reflection is essential."
      3. "App-code use cases: plugin loading (Class.forName(name).getConstructor().newInstance()), reading annotations (field.getAnnotation(JsonProperty.class))."
      4. "Performance: reflective call is 10-100x slower than direct call. JIT can sometimes optimize but don't assume. Cache Method objects if hot."
      5. "Java 9+ module system restricts reflective access to non-exported packages — setAccessible(true) may fail without explicit --add-opens."

      Edge cases to mention:

      • MethodHandles (since Java 7) is the modern alternative — similar power, much better performance, JIT-friendly
      • VarHandle (Java 9) for atomic operations on fields without writing AtomicXxx wrappers
      • Avoid setAccessible(true) if you can — fragile across JDK upgrades

      What NOT to say:

      • "Reflection is always too slow to use" — fine for non-hot paths, frameworks use it everywhere
      • "Reflection is the way to call private methods" — it works but indicates a design smell

      Common follow-up: "What's the difference between Method.invoke() and MethodHandle.invokeExact()?"

      128. Default methods in interfaces

      Asked at: Most modern Java rounds

      Difficulty: Easy-Medium · Topic: OOP / Java 8

      The question: "What problem do default methods in interfaces solve? What are the multiple-inheritance gotchas?"

      The 30-second answer: Default methods (Java 8) let you add methods to interfaces without breaking existing implementations. Used to extend Collection with stream(), forEach(), etc. Multipleinheritance gotcha: if a class inherits the same default method from two interfaces, compile error — must override and explicitly call InterfaceA.super.method().

      Step-by-step thought process:

      1. "Pre-Java 8: adding a method to an interface broke every existing implementation. Default methods let you ship a default implementation."
      2. " interface Collection { default Stream<E> stream() {... } } — every existing implementer gets stream() for free."
      3. "Diamond problem: if class implements two interfaces with the same default method, the compiler can't choose — must override explicitly: void m() { InterfaceA.super.m(); }."
      4. "Default methods give you behavior sharing without inheritance — supports composition-style design with interfaces."
      5. " static methods in interfaces (also Java 8) are factory methods (e.g. List.of(...)) — not inherited by implementers, called via interface name."

      Edge cases to mention:

      • private methods in interfaces (Java 9) — for helper methods used by default methods, don't leak to implementers
      • Class-defined methods ALWAYS win over interface default methods (class > interface)
      • Functional interfaces can have default methods — but only one abstract method

      What NOT to say:

      • "Default methods make Java multi-inheritance" — partial; only behavior, not state
      • "Always provide defaults" — sometimes you want implementers to implement explicitly

      Common follow-up: "How does a class resolve a method when superclass and interface both define it?"

      129. Java memory model — happens-before in 30 seconds

      Asked at: Senior backend rounds · Razorpay · Goldman

      Difficulty: Hard · Topic: Concurrency / JVM

      The question: "What is the happens-before relationship in the Java Memory Model?"

      The 30-second answer: A formal relation that defines when one action's effects are visible to another. If action A happens-before action B, B sees A's writes. Established by: program order (within a thread), synchronized block exit/enter (same lock), volatile write/read (same variable), Thread.start before any action in started thread, all actions in a thread before another thread joins it.

      Step-by-step thought process:

      1. "Without happens-before, the JVM can reorder reads and writes for performance — observable to other threads as 'impossible' interleavings."
      2. "Within a single thread, actions appear to execute in program order — happens-before is intra-thread by default."
      3. "Synchronized: unlocking a monitor happens-before any later locking of the same monitor. So writes inside the first synchronized block are visible inside the second."
      4. "Volatile: a write to a volatile field happens-before any later read of the same field. Two volatile writes-and-reads chain visibility."
      5. "Thread lifecycle: Thread.start() happens-before anything the started thread does. Anything the thread does happens-before Thread.join() returns."

      Edge cases to mention:

      • Final fields: writes inside the constructor happen-before any other thread sees the constructed reference — if the reference is published safely
      • Atomic* operations and many java.util.concurrent classes provide happens-before — that's why you don't need to think about it constantly when using them
      • A ConcurrentHashMap.put happens-before subsequent get for the same key in another thread

      What NOT to say:

      • "Synchronized makes everything visible" — only between blocks on the same lock
      • "Volatile is just visibility, nothing more" — also has happens-before with subsequent reads

      Common follow-up: "Why does volatile guarantee visibility but synchronized also covers atomicity?"

      130. "What would you change in Java if you could?"

      Asked at: Closing question, mid-to-senior rounds

      Difficulty: Soft / signal-question · Topic: Self-awareness

      The question: "If you could change one thing about Java, what would it be?"

      The 30-second answer: This is a signal question testing if you've engaged with the language critically. Pick something specific and grounded — not "Java is too verbose." Strong picks: checked exceptions (or their interaction with lambdas), null references (long-standing pain), erasure preventing reified generics, default constructor verbosity vs records.

      Step-by-step thought process:

      1. "Signal test: are you a thoughtful engineer or someone who never reflects? Wrong: 'Java is perfect.' Right: pick a specific friction and discuss the trade-off."
      2. "Strong pick — null: 'I'd push harder for Optional-by-default in APIs or null-safety in the type system like Kotlin. NullPointerException is still the most expensive runtime bug.'"
      3. "Strong pick — checked exceptions in lambdas: 'I'd revisit how checked exceptions compose with lambdas — currently you wrap every checked-throwing function manually.'"
      4. "Strong pick — erasure: 'Reified generics (a la Valhalla) would eliminate a whole class of workarounds. The fact that you can't do new T[] is a daily annoyance.'"
      5. "Show curiosity, not bitterness: 'I know Valhalla is working on value types and reified generics — exciting direction.'"

      Edge cases to mention:

      • Tie it to your actual experience: 'In a payment service, null on a deeply nested field bit us hard last quarter — I'd love compile-time null safety.'
      • Mention what's GETTING fixed: 'Pattern matching closed a real gap; sealed classes solve hierarchy problems we used to fake with enum-like patterns.'
      • Don't pick something objectively fixed: 'I wish there were lambdas' (added in Java 8) is a no-go

      What NOT to say:

      • "Nothing, Java is perfect" — signals you don't think critically
      • "Java is too verbose" — vague, says nothing
      • "I'd add async/await" — Java solved I/O concurrency differently with virtual threads; shows you don't know

      Common follow-up: "What's your take on Project Valhalla?"
