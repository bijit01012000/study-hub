    Design an LRU Cache

    15 sections · 1,902 words

    LLD Design Problems, problem 15 of 20.

    The Ask

    Build

    • get(key) and put(key, value), both O(1).
    • Fixed capacity, set at construction.
    • put of a new key when full evicts the least recently used entry.
    • get and put both count as a use — the touched entry becomes most recent.
    • Live size and a hit / miss / eviction count.
    • The eviction rule is swappable: LRU now, LFU / FIFO / TTL later.

    Skip

    • A distributed / multi-node cache.
    • Persistence to disk.
    • A background TTL sweeper (lazy expiry only).
    • Thread-safety internals.
    • Serializing the values.

    Our Model

    A map into a recency list. LruCache holds a Map<K, Node> and a doubly linked RecencyList; the eviction rule sits behind an EvictionPolicy.

    Actors and classes

    • Client — cache: Cache<K,V>; calls v = cache.get(k) and cache.put(k, v).
    • Cache (interface) / AbstractCache — get(K): V, put(K, V): void, size(): int. get is final: look up, then a hook; abstract lookup(K): Node; hooks afterHit(Node), afterMiss(K). Template Method, skeleton is optional.
    • CacheDecorator — inner: Cache<K,V>; WriteThroughCache (store on put), StatsCache (count hit / miss), LoggingCache (trace each call). Stack them; the core is untouched.
    • LruCache — map: Map<K, Node>, capacity: int, policy: EvictionPolicy, head, tail: Node (sentinels), stats: CacheStats; get(K): V, put(K, V): void, evict(): void.
    • Node / CacheEntry — key: K, value: V, prev: Node, next: Node; createdAt, lastAccessAt: long, frequency: int. TTL reads createdAt, LFU reads frequency; basic LRU folds this into Node.
    • RecencyList — doubly linked; addFront(Node n): void, remove(Node n): void, lru(): Node (returns tail.prev). head.next is MRU, tail.prev is LRU.
    • EvictionPolicy (interface) — recordAccess(Node n): void, evictNext(): Node. The one rule that changes; never touches the map. LruPolicy (move behind head, evict tail.prev), FifoPolicy (no move on access), MruPolicy (evict head.next), TtlPolicy (evict first node past its ttl, lazy). Same seam, only which node is picked differs.
    • EvictionListener (interface) — onEvict(K key, V value): void. MetricsSink, WriteBackTier, WarmLogTail. Observer: fan out every drop, core untouched.
    • CacheStats — hits, misses, evictions: long, size, capacity: int; hitRate(): double, recordHit(), recordMiss(), recordEviction().

    The invariant

    • map.size == list.size.
    • Every map value is a live list node.
    • head.next is newest, tail.prev is oldest.

    Key operations

    1. get(K key): V — Map miss returns null (-1 in LeetCode 146). On a hit: remove the node, addFront it, return its value. O(1). A read still counts as a use.
    2. put(K key, V value): void — Existing key: overwrite the value, move the node to the front. New key at capacity: evict tail.prev and drop its map key first, then addFront. O(1).
    3. addFront(Node n): void — four pointer writes that splice n between head and head.next. Never sees null because head is a permanent sentinel.
    4. remove(Node n): void — two pointer writes: n.prev.next = n.next, n.next.prev = n.prev. Interior by construction, so no empty or single-node case.

    From memory

    • get(k): n = map[k]; if null miss; remove(n); addFront(n); return n.value.
    • put(k,v): hit: set + move; new + full: evict tail.prev; addFront + map.put.
    • evict when map.size() == capacity; LRU = tail.prev.

    Recall drill: cover the operations column, write the four with their guarantee. Blank on the guarantee means that method is your gap.

    The One Run to Hold in Your Head

    Capacity 3. put A, put B, put C, then get A, then put D. get A moves A behind head; put D is a new key at capacity, so evict tail.prev (B) and drop "B" from the map, then addFront(D). Order is D, A, C. Which nodes and map keys changed?

    The Change

    They want least-FREQUENTLY-used, not least-recently. An LfuPolicy behind the same EvictionPolicy: a map of frequency to a small doubly linked list, plus a minFreq pointer. recordAccess moves the node up one bucket; evictNext drops the tail of the minFreq bucket. Still O(1). Strategy, a second time on this sheet.

    What the Picture Can't Show

    get is a write. Every hit unlinks its node and splices it behind head, so tail.prev is always the true least-recently-used. Skip the move and the list freezes into insertion order.

    If They Make You Code It

    Get and put, the whole thing:

    class LruCache {                                   // K,V
    final int capacity;
    final Map<K,Node> map = new HashMap<>();
    final Node head = new Node(), tail = new Node(); // sentinels

    LruCache(int cap) {
        capacity = cap;
        head.next = tail; tail.prev = head;         // never null
    }
    V get(K key) {
        Node n = map.get(key);
        if (n == null) return null;                 // miss
        remove(n); addFront(n);                     // get is a WRITE
        return n.value;
    }
    void put(K key, V value) {
        if (capacity <= 0) return;                  // holds nothing
        Node n = map.get(key);
        if (n != null) {                            // key exists
            n.value = value; remove(n); addFront(n);
            return;
        }
        if (map.size() == capacity) {               // evict FIRST
            Node lru = tail.prev;
            remove(lru); map.remove(lru.key);       // list AND map
        }
        Node fresh = new Node(key, value);
        addFront(fresh); map.put(key, fresh);
    }
    void addFront(Node n) {                         // splice behind head
        n.prev = head; n.next = head.next;
        head.next.prev = n; head.next = n;
    }
    void remove(Node n) {                           // unlink, both sides
        n.prev.next = n.next; n.next.prev = n.prev;
    }
}

    The Four Hazards

    1. Get that forgets to move the node. get returns the value but leaves the node where it sits. Recency never updates, the front of the list is just the last inserted key, and eviction throws out whatever was put longest ago — not what was used longest ago. The hit rate quietly collapses. Every get does remove(n) then addFront(n), the same as the hit path of put.
    2. Update in place, recency untouched. put on an existing key overwrites n.value and returns. The value is fresh but the node is still near the tail, so the very next eviction drops the key you just wrote. The existing-key branch also does remove(n) + addFront(n).
    3. Insert, then evict. Add the new node and put it in the map, then trim tail.prev. At capacity 1 you evict the node you just added; at any capacity the map briefly holds capacity + 1 entries. Evict while size == capacity, then addFront the new node.
    4. No sentinels. Without a dummy head and tail, addFront and remove branch on empty list, single node, first, last. One missed case is a null pointer or a lost node. Two permanent dummies make every splice interior; capacity 0 makes put a no-op, capacity 1 evicts on every new key.

    Name them before they are asked.

    The Lines They Are Watching

    1. remove(n); addFront(n) inside get — leave it out and the cache silently becomes FIFO.
    2. The capacity check evicts before the insert, so size never passes capacity.
    3. map.remove(lru.key) — the node leaves the map as well as the list, or it leaks forever.
    4. capacity <= 0 guarded first — without it tail.prev is the head sentinel and remove() null-derefs.

    Holding the Recency Order

    Approach Get Put / evict Move on touch Swap the rule Shows the mechanism
    Map + doubly linked list (the answer) O(1) unlink + splice O(1), drop tail.prev relink behind head LFU / FIFO / TTL: change the policy yes
    LinkedHashMap(accessOrder = true) O(1), reorders itself O(1), removeEldestEntry hidden in the map LRU only no, the framework hides it
    Map + min-heap O(log n) sift O(log n) + stale entries push (now, key), delete lazily TTL yes, LFU no partly

    HashMap + a doubly linked list. True O(1) both ways and you can walk every pointer move on the board. LinkedHashMap(accessOrder=true) with removeEldestEntry is the one-line production answer, but it hides the mechanism the question is testing. A heap or an array scan drops you to O(log n) or O(n) and leaves stale entries behind.

    Rejection Signals

    These end the interview:

    • get that returns the value but never moves the node — an LRU cache that evicts in insertion order.
    • Inserting the new node before evicting at capacity — the map holds capacity + 1, or you evict what you just added.
    • Removing the list tail but leaving the key in the map — a later get returns a node no longer in the list.
    • A singly linked list or an ArrayList for recency — deleting an interior node is O(n).
    • Eviction hardcoded inside put with no seam — LFU or TTL then means rewriting the core.
    • Re-sorting by timestamp on every access — O(n log n) per get for an O(1) problem.

    Patterns Used

    Strategy — the EvictionPolicy (LRU / LFU / FIFO / TTL). Decorator — write-through, stats and logging wrap the cache untouched. Observer — an EvictionListener fans out each drop. Template Method — AbstractCache.get() runs lookup then a hit / miss hook.

    Say It Like This

    "A HashMap from key to a list node, and a doubly linked list ordered by recency with dummy head and tail. get and put both unlink the node and splice it behind head, so the front is most recently used. A put that would overflow evicts tail.prev first and drops its map key. Every path is O(1). The eviction rule sits behind an EvictionPolicy, so LFU or TTL is a swap, not a rewrite."

    The Follow-ups That Decide It

    1. get doesn't change the value. Does it change anything? Yes — it moves the node to the front; skip that and it is FIFO.
    2. put a key that already exists. Where does it end up? Value overwritten and the node moved to the front.
    3. Capacity 1, then capacity 0. Cap 1 evicts on every new key; cap 0 put is a no-op, get always misses.
    4. Make it least-frequently-used. Swap in LfuPolicy — freq buckets, each a list, minFreq pointer.
    5. Give every entry a TTL. Store createdAt; on get, expired -> remove + miss. Lazy, no thread.
    6. Make it thread-safe. One lock is fine; striped locks or CHM + a list lock for throughput.
    7. Read-through on a miss. A CacheLoader seam: miss -> load(key) -> put -> return.
    8. Cap total bytes, not entry count. Weigh each entry; evict from the tail until totalWeight <= max.

    Deliberately Not Built

    • Thread safety — one lock around get / put is correct; striped locks or a ConcurrentHashMap plus a lock on the list for throughput. Name it, don't whiteboard it.
    • A TTL sweeper thread — expiry is lazy: check createdAt on read, drop if stale. A background sweep is a cron, not this class.
    • Distributed cache — consistent hashing, replication, invalidation. That is the HLD version of this problem.
    • Persistence — a write-ahead log and a warm-up load on restart. Different problem.
