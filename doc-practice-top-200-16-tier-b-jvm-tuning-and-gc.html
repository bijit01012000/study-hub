      141. G1 vs ZGC vs Shenandoah — pick a collector

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Walmart Labs · Cred

      Difficulty: Hard · Topic: JVM tuning + GC

      The question: "You have a 32GB heap service with strict p99 latency. Which GC and why?"

      The 30-second answer: For 32GB heap with strict tail latency, ZGC (default since Java 15 for tuning targets, generational since Java 23) — sub-millisecond pause times regardless of heap size. G1 is the safe default at smaller heaps (4-16GB) with mixed throughput/latency goals. Shenandoah (Red Hat / OpenJDK) is similar to ZGC in goals, used in RHEL ecosystems.

      Step-by-step thought process:

      1. "G1 (default since Java 9) — region-based, divides heap into ~2048 regions, collects highest-garbage regions first. Stop-the-world young GC, concurrent mixed/old. Pause target tunable via -XX:MaxGCPauseMillis. Good up to ~16GB heaps."
      2. "ZGC (production since 15) — colored pointers, load barriers, fully concurrent. Pause times under 1ms even at 100GB+ heaps. Generational ZGC (default in 23) added young/old separation for throughput."
      3. "Shenandoah — similar story, concurrent compaction via Brooks pointers / forwarding. Used heavily in JBoss/WildFly stacks."
      4. "Trade-offs — ZGC has higher CPU overhead (load barriers on every reference read) and higher heap footprint. For a 4GB latency-tolerant service, G1 is cheaper."

      Edge cases to mention:

      • Parallel GC is still default for -XX:+UseParallelGC workloads optimizing pure throughput (batch jobs)
      • Epsilon GC (-XX:+UseEpsilonGC) is no-op — allocates only, never collects. Used for short-lived benchmarks and OOM testing
      • Don't switch GCs blindly — profile, look at GC logs, measure p99 before tuning

      What NOT to say:

      • "ZGC is always best" — overhead and complexity aren't free
      • "G1 is deprecated" — no, it's the JVM default for most heaps

      Common follow-up: "Show me how you'd read a G1 GC log to find a problem."

      142. Reading a GC log — what to look for first?

      Asked at: Senior rounds at Swiggy · Razorpay · Goldman · Morgan Stanley

      Difficulty: Medium-Hard · Topic: JVM tuning + GC

      The question: "Here's a GC log. Walk me through what you'd look at first."

      The 30-second answer: Four checks — total pause time as a percentage of wall time (>5% is bad), individual long pauses (anything over your latency budget), full GC frequency (full GC in G1 is a failure mode), and allocation rate (high allocation rate causes high young GC frequency).

      Step-by-step thought process:

      1. "Enable structured logs — -Xlog:gc*:file=gc.log:time,uptime,level,tags. Don't try to read raw lines; pipe through gceasy.io or GCViewer for the summary."
      2. "First number — % time in GC. Healthy is under 2%; 5%+ is degraded; 10%+ is broken. This tells you whether you have a GC problem at all."
      3. "Look at p99 / p99.9 pause durations — if your SLA says p99 = 50ms and you have a 200ms G1 mixed pause, you've found the culprit."
      4. "Full GC frequency — in G1, a full GC means concurrent cycle failed (humongous objects, evacuation failure). Look at the cause string: to-space exhausted, humongous allocation, metadata GC threshold."
      5. "Allocation rate — if young gen fills every 200ms, you have a high allocation pressure. Profile with JFR to find the allocation hot spots."

      Edge cases to mention:

      • Humongous allocations (>50% of region size in G1) skip young gen and go straight to old — fix by reducing object size or upping region size
      • Time-to-safepoint can be huge even when GC itself is fast — measured as Total time for which application threads were stopped minus actual GC work
      • Concurrent Mark Cycle aborts in G1 mean the concurrent phase didn't finish in time — usually allocation rate too high

      What NOT to say:

      • "I'd just increase the heap" — bigger heap = longer pauses for non-ZGC collectors; that's the wrong knob most of the time
      • "Restart the JVM" — addresses symptom, not the leak/pressure

      Common follow-up: "What's a humongous object in G1 and why does it matter?"

      143. Heap dump analysis with MAT — finding the leak

      Asked at: Senior rounds at Razorpay · Swiggy · TCS Digital · JP Morgan India

      Difficulty: Medium-Hard · Topic: JVM tuning + GC

      The question: "Your service OOMs every 12 hours. Walk me through your investigation."

      The 30-second answer: Capture a heap dump with jmap -dump:live,format=b,file=heap.hprof or auto-on-OOM via -XX: +HeapDumpOnOutOfMemoryError. Open in Eclipse MAT. Run Leak Suspects report — it identifies dominator trees holding the most retained heap. Drill into the GC roots for the top suspect.

      Step-by-step thought process:

      1. "Always enable -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/dumps in production. When the OOM happens, you have the evidence."
      2. "Open the .hprof in MAT (Memory Analyzer Tool). Run Leak Suspects Report — gives you a list of objects that dominate the retained heap."
      3. "Drill into the top suspect — view the dominator tree, look at retained size (not shallow size). A 100MB ConcurrentHashMap is a leak; a 100MB byte[] is probably a cache."
      4. "Right-click → Path to GC Roots → exclude weak/soft references. That gives you the chain of strong references keeping the object alive — usually points at a static field, a ThreadLocal, or a listener registration."

      Edge cases to mention:

      • Common Java leak patterns — unbounded caches, ThreadLocal not removed in pooled threads, listener/observer registrations not removed, classloader leaks in app servers
      • Heap dumps are sensitive (contain user data, session tokens) — encrypt at rest, restrict access jcmd GC.heap_dump works without going through jmap, often more reliable in containerized environments

      What NOT to say:

      • "I'd add more heap" — masks the leak, eventually OOMs again
      • "I'd just restart the service" — same; the leak is real, find it

      Common follow-up: "What's the difference between shallow heap, retained heap, and dominator tree?"

      144. jcmd, jstat, jmap — when to reach for which?

      Asked at: Senior rounds at Swiggy · Razorpay · Goldman · Walmart Labs

      Difficulty: Medium · Topic: JVM tuning + GC

      The question: "You're SSH'd into a prod box with a misbehaving Java process. What's your toolkit?"

      The 30-second answer: jcmd is the modern Swiss-army — it can do everything jmap/jstack/jinfo used to do. Reach for jstat for cheap GC stats over time. Avoid jmap -histo:live in prod — it triggers a full GC.

      Step-by-step thought process:

      1. " jcmd help — lists every diagnostic command the JVM exposes. The modern recommendation is to use jcmd over the older tools."
      2. " jcmd GC.heap_info — quick view of generation sizes and usage. jcmd Thread.print — thread dump, same as jstack."
      3. " jstat -gcutil 1000 — prints young/old gen utilization every second. Lightweight, doesn't pause the JVM. Use it to spot allocation pressure live."
      4. " jcmd GC.heap_dump /tmp/heap.hprof — full heap dump. Heavy operation, pauses the JVM for seconds — schedule a maintenance window or do it on a canary instance."

      Edge cases to mention:

      • jmap -histo:live does a full GC first to get accurate live counts — never run on a prod node serving traffic
      • JFR (jcmd JFR.start) is the modern profiling answer — low overhead, captures allocation, locks, I/O, GC together
      • Native memory tracking — jcmd VM.native_memory summary shows JVM's view of native allocations (class metadata, code cache, GC overhead)

      What NOT to say:

      • "I'd attach VisualVM" — fine for dev, but prod boxes rarely have a GUI session available
      • "Just enable verbose:gc" — that's a JVM flag, not a runtime diagnostic; needs restart

      Common follow-up: "You see 95% old-gen utilization in jstat. What do you do next?"

      145. Native memory tracking — what's outside the heap?

      Asked at: Senior rounds at Cred · Goldman · Walmart Labs · JP Morgan India

      Difficulty: Hard · Topic: JVM tuning + GC

      The question: "My JVM has -Xmx4g but the process is using 7GB RSS. Where's the extra memory?"

      The 30-second answer: Java heap is one of many memory areas. Outside the heap: thread stacks (1MB each by default × N threads), Metaspace (class metadata), code cache (JIT-compiled native code), direct byte buffers, JNI allocations, GC overhead, and Compressed Class Space.

      Step-by-step thought process:

      1. "Enable NMT — -XX:NativeMemoryTracking=summary at startup. Then jcmd VM.native_memory summary shows the breakdown."
      2. "Common culprits — thread stacks (1000 threads × 1MB = 1GB), direct buffers (often misused for I/O, never freed), Metaspace ballooning from dynamic class generation, code cache filling up from heavy JIT."
      3. "Direct buffers (allocated via ByteBuffer.allocateDirect) live outside the heap, freed by phantomreference cleaner threads — slow GC means slow cleanup means real memory pressure."
      4. "Containers add a wrinkle — if your container limit is 4GB but Xmx is 4GB, you have zero headroom for the non-heap regions and the OOM-killer gets you."

      Edge cases to mention:

      • For containers, set -XX:MaxRAMPercentage=75 instead of -Xmx — JVM uses 75% of container limit for heap, leaves room for non-heap
      • Metaspace doesn't have a default cap until you set -XX:MaxMetaspaceSize — Hibernate proxies and bytecode-heavy apps can fill it JNI memory is invisible to JVM tools — you need OS-level tools (pmap, gdb) to chase JNI leaks

      What NOT to say:

      • "The JVM is leaking" — usually it's not; you're under-counting non-heap
      • "Increase Xmx" — doesn't help; the extra memory isn't in the heap

      Common follow-up: "What's Compressed Oops and when does it stop working?"

      146. JIT compilation tiers — interpreter, C1, C2, Graal

      Asked at: Staff rounds at Flipkart · Cred · Goldman · Walmart Labs

      Difficulty: Hard · Topic: JVM tuning + GC

      The question: "Explain the JVM's tiered compilation. Why does a method get slower before it gets faster?"

      The 30-second answer: HotSpot starts every method in the bytecode interpreter (Tier 0). Hot methods promote to C1 (fast compile, light optimization — Tier 1-3), then to C2 (slower compile, aggressive optimization — Tier 4). Methods can deoptimize and bounce back to the interpreter if assumptions break (e.g., a new class loaded that invalidates a type check).

      Step-by-step thought process:

      1. "Interpreter — every JVM starts here. Bytecode interpreted instruction by instruction. Slow but no compile time."
      2. "C1 (client compiler) — fast compile, basic optimization. Used as the warmup compiler. Captures profiling info: which branches taken, which types observed."
      3. "C2 (server compiler) — slow compile, aggressive optimization. Inlining, escape analysis, vectorization, loop unrolling. The hot path."
      4. "Deoptimization — C2's optimizations are speculative. If profiling said 'only ConcreteImpl here' and a new subclass shows up, the compiled code is invalidated and execution bounces back to the interpreter while C2 recompiles."
      5. "GraalVM JIT — a Java-written C2 replacement with better optimization for polymorphic and lambda-heavy code. Default in Java 17+ via -XX:+UseJVMCICompiler."

      Edge cases to mention:

      • Profile-guided benchmarks need warmup — JMH (Java Microbenchmark Harness) handles this; ad-hoc timing usually measures the wrong thing
      • AOT (ahead-of-time) compilation via jaotc or GraalVM native image trades startup for peak throughput
      • Inlining is the biggest C2 win — methods over -XX:MaxInlineSize (default 35 bytes) won't inline; refactor hot small methods accordingly

      What NOT to say:

      • "Java is compiled" — partly true; the bytecode is, but execution is mostly JIT'd machine code
      • "C2 is always used" — only for hot methods; cold paths stay interpreted forever

      Common follow-up: "What's escape analysis and what optimization does it enable?"

      147. Metaspace OOM — what causes it and how to diagnose

      Asked at: Senior rounds at Razorpay · Cognizant · TCS Digital · Wells Fargo

      Difficulty: Medium-Hard · Topic: JVM tuning + GC

      The question: " java.lang.OutOfMemoryError: Metaspace. Diagnose."

      The 30-second answer: Metaspace holds class metadata, replaced PermGen in Java 8. OOM happens when too many classes are loaded — usually from dynamic class generation (CGLIB proxies, ByteBuddy, JSP recompilation, classloader leaks in app servers). Cap with -XX:MaxMetaspaceSize, diagnose with jcmd GC.class_stats.

      Step-by-step thought process:

      1. "PermGen → Metaspace transition in Java 8 — Metaspace is in native memory by default, sizes dynamically. The OOM means the JVM hit MaxMetaspaceSize (default unlimited, but containers usually cap it)."
      2. "Top culprits — CGLIB / ByteBuddy proxies generating new classes per call instead of caching, Groovy / Kotlin scripting reloading, web containers reloading apps and leaking the old classloader."
      3. "Diagnose with -XX: +UnlockDiagnosticVMOptions -XX:+UnlockExperimentalVMOptions then jcmd GC.class_histogram — shows class count and instance count."
      4. "Look for thousands of classes with synthetic names like Foo$$EnhancerByCGLIB$$abc123 — sign of proxy explosion."

      Edge cases to mention:

      • Classloader leak — a single retained reference to a Class object pins the entire classloader and every class it loaded. Common in static maps holding user-provided classes -XX:MetaspaceSize is the initial size that triggers a class-unload cycle; -XX:MaxMetaspaceSize is the hard cap
      • Hibernate's session factory builds enhanced entity classes — bytecode enhancement can balloon Metaspace if entity hierarchy is large

      What NOT to say:

      • "Add more Metaspace" — same symptom-not-cause trap as heap OOM "PermGen issue" — outdated; PermGen doesn't exist post-Java 7

      Common follow-up: "What's a classloader leak and how do you find one?"

      148. String deduplication — what is it and when does it help?

      Asked at: Senior rounds at Flipkart · Cred · Goldman

      Difficulty: Medium · Topic: JVM tuning + GC

      The question: "What does -XX:+UseStringDeduplication do? When is it worth turning on?"

      The 30-second answer: G1 (and ZGC) can detect String objects whose internal byte[] (the character data) has identical contents and replace them with a shared array — leaving the String objects distinct but sharing their backing storage. Helps apps that hold many duplicate strings in memory (JSON parsing, ORM, logs).

      Step-by-step thought process:

      1. "Strings hold a byte[] (since Java 9 with compact strings) for their characters. Many identical strings means many identical byte arrays — pure waste."
      2. " -XX: +UseStringDeduplication (G1 since Java 8, ZGC since 18) — during young GC, scan promoted Strings. If two Strings have the same content hash, point both at the same byte[]."
      3. "Sweet spot — JSON-heavy services where many entities share enum-like values (status = 'PAID', currency = 'INR'). 20-40% String memory savings reported in production benchmarks."
      4. "Not free — GC does extra work hashing and comparing. Measure first."

      Edge cases to mention:

      • Only deduplicates after a few promotions (avoids deduping short-lived strings)
      • String interning (String.intern()) is a different mechanism — explicit, app-controlled, uses the String Pool table
      • For massive duplicate sets, consider a String cache (Map<String, String>) or pre-interning known values

      What NOT to say:

      • "It interns every string" — wrong; that's String.intern()
      • "Doubles GC pause times" — usually under 5% overhead; measure before claiming

      Common follow-up: "What's the difference between String.intern() and string deduplication?"

      149. Escape analysis and scalar replacement

      Asked at: Staff rounds at Flipkart · Goldman · Walmart Labs · Cred

      Difficulty: Hard · Topic: JVM tuning + GC

      The question: "Why doesn't new Order() always allocate on the heap?"

      The 30-second answer: C2 performs escape analysis — if it can prove an object never escapes its allocating method (no field assignment, no return, no thread publication), it eliminates the heap allocation via scalar replacement — the object's fields become local variables in registers or stack slots.

      Step-by-step thought process:

      1. "Escape analysis classifies allocations — no escape (stays in method), arg escape (escapes only to called methods), global escape (stored in field, returned, published)."
      2. "For no escape, C2 doesn't actually allocate the object at all. Its fields become scalar locals — like inlining the constructor and accessing the fields directly."
      3. "This means lots of intermediate objects (Optional wraps, Stream lambdas, small builders) cost nothing in steady state — they're optimized away."
      4. "Allocation profiling with JFR can mislead — it counts objects the JIT will later eliminate. Interpret with care."

      Edge cases to mention:

      • Synchronized blocks on a non-escaping object are eliminated entirely (-XX: +EliminateLocks)
      • Boxing — autoboxing primitive into wrappers is the #1 escape-killer; prefer primitive types in hot loops
      • Optional is often elided by escape analysis when used purely within a method — return values are a different story

      What NOT to say:

      • "Every new allocates on the heap" — outdated since C2 escape analysis
      • "Stack allocation" — Java doesn't actually allocate on the stack; it does scalar replacement

      Common follow-up: "Why does autoboxing kill performance even though escape analysis is so good?"

      150. JFR — recording flight events in production

      Asked at: Senior rounds at Razorpay · Walmart Labs · JP Morgan India

      Difficulty: Medium-Hard · Topic: JVM tuning + GC

      The question: "What's JFR and why is it the modern profiling answer?"

      The 30-second answer: Java Flight Recorder is a low-overhead (≈1%) JVM-built-in profiler that records GC, allocations, locks, I/O, exceptions, method profiling as events. Open the recording in JDK Mission Control (JMC). Always-on in prod with rolling buffers is a legitimate strategy.

      Step-by-step thought process:

      1. "Trigger via jcmd JFR.start duration=60s filename=/tmp/run.jfr for a one-shot, or -XX:StartFlightRecording=duration=60s,filename=... at JVM startup."
      2. "Continuous recording — -XX:StartFlightRecording=disk=true,maxsize=200M,maxage=2h,settings=profile. Buffer stays on disk, automatically rolls. When something goes wrong, the data is already there."
      3. "Open in JMC — flame graphs, allocation sites, lock contention, GC summary, I/O latency. Goes way beyond what jstat / jstack can show."
      4. "JFR overhead — under 1% with default settings. Under 3% with profile settings. Safe to keep on permanently."

      Edge cases to mention:

      • JFR was Oracle-only before Java 11 — now in OpenJDK
      • Event streaming API (Java 14+) lets you consume events in real-time without writing to disk — useful for in-process observability
      • Combine JFR + async-profiler for the best flame graphs — JFR for system-wide, asyncprofiler for sample-based CPU profiling

      What NOT to say:

      • "Use VisualVM in production" — interactive sampling is high overhead and fragile
      • "JFR is for Oracle JDK only" — no, OpenJDK ships it since 11

      Common follow-up: "How would you set up always-on JFR in a Kubernetes pod?"
