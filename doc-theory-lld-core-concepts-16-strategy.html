    Strategy

    11 sections · 883 words

    Behavioural · Design Patterns · Pattern 07 of 12

    Intent

    Put the calculation that changes behind a one-method interface, let a holder keep one version as a field, and swap it without touching the holder.

    When To Use It

    The Signs

    • One big if or switch on a type or a mode. Every new mode means editing that same method.
    • Two classes that match except for one calculation (sort up, sort down, sort by date).
    • You pick the calculation while the program runs, from a setting or a click.
    • The same method copied a few times with a couple of lines changed.

    Don't Bother If

    • There will only ever be one version.
    • What changes is a number or a setting, not real logic. Pass a value.
    • The branches are two lines each and won't grow.
    • The cost (a few small classes, one extra hop) isn't paying for itself yet.

    Before

    class ParkingLot {
    // problem 1: the ladder
    int fee(Ticket t, String policy) {
        long hrs = hoursParked(t);
        if (policy.equals("HOURLY"))
            return (int) hrs * 30;
        else if (policy.equals("FLAT_DAY"))
            return 400;
        else if (policy.equals("WEEKEND"))
            return isWeekend(t) ? 200 : (int) hrs * 30;
            // a new rule means editing this method
        throw new IllegalArgumentException(policy);
    }
}

    Two problems: the ladder, and one method that owns every rule.

    After

    interface FeeStrategy {
    // the step that changes
    int computeFee(Ticket t);
}
class HourlyFee implements FeeStrategy {
    public int computeFee(Ticket t) {
        return (int) hoursParked(t) * 30;
    }
}
// WeekendFee, FlatDayRate: same shape

class ParkingLot {
    private FeeStrategy fee;
    // keeps one
    ParkingLot(FeeStrategy fee) { this.fee = fee; }
    void setFee(FeeStrategy fee) { this.fee = fee; }
    int fee(Ticket t) {
        return fee.computeFee(t);
        // just calls it
    }
}
// a new rule is a new class. ParkingLot stays the same.

    Or one subclass per rule, which doubles with every new dimension:

    class HourlyLot extends ParkingLot { int fee(..){..} }
class FlatDayLot extends ParkingLot { int fee(..){..} }
class WeekendLot extends ParkingLot { int fee(..){..} }
// add covered vs open as a 2nd choice:
// HourlyCoveredLot, HourlyOpenLot, ... now 6
// add EV-only, now 12. it keeps doubling.

THE VERSIONS. ADD ONE, NOTHING ELSE CHANGES

    How It's Built (3 Steps)

    1. Find the calculation that changes. Put it in an interface with one method: computeFee(Ticket).
    2. Turn each branch into its own class. The body of the old if becomes the body of the method.
    3. The holder keeps one as a field, handed in when it's created, and calls it. No if, no switch, no instanceof.

    Quick Check

    Say "it depends on the ___" and fill the blank with one word: fee, route, ranking. That word is the name of your interface.

    In The Interview

    "The fee depends on the lot's rules, so I'd put it behind a FeeStrategy interface with one computeFee method. ParkingLot keeps one and calls it, it never checks the type. A new rule is a new class."

    How It's Different

    From The Lookalikes

    Vs State. Both keep a swappable object behind an interface. With Strategy, someone outside picks it and it stays put. With State, the object switches itself as things happen.

    Vs Factory. A Factory makes an object. Strategy uses one. They pair up: a factory can pick which version to make from a setting.

    Vs Template Method. Strategy swaps the whole method, held as a field. Template Method keeps a fixed outline in a parent class and lets child classes fill the blanks.

    Vs a lambda. A one-method strategy is just a function, and a lambda is a version with no name. Name a class when it holds data or a name worth searching for.

    They Say: "now add a weekend rate"

    • With it: write one WeekendFee class, hand it to ParkingLot. Done in a minute.
    • Without: they watch you re-open fee(), add an else if, and hope HOURLY still works.

    Watch Out For

    • If a version holds no data, make it once and reuse it. Don't new one every call.
    • Don't hand the version the whole holder (this). Pass only what the method needs, or you've tied them back together.
    • Instead of null checks all over, make a do-nothing version that returns 0.
    • Java shortcut: enum FeeType implements FeeStrategy { HOURLY {..}, WEEKEND {..} } keeps the versions and the list of them in one file.
    • Test each version on its own, no ParkingLot needed. That's the payoff.
