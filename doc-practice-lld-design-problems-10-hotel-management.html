    Design a Hotel Management System

    15 sections · 1,871 words

    LLD Design Problems, problem 10 of 20.

    The Ask

    Build

    • One hotel, many room types (single, double, suite), each a rack rate and a count.
    • Many rooms — a number, a floor, a housekeeping status.
    • Guest searches a date range [checkIn, checkOut) and a type.
    • Find a room of that type with no overlapping booking, reserve it.
    • Later check in, check out, bill nights x rate + extras.
    • Lifecycle: requested -> confirmed -> checked-in -> checked-out, plus cancelled, no-show.
    • Pricing rule is swappable — rack, seasonal, length-of-stay.
    • Live rooms-left count per type per night.

    Skip

    • OTA / channel-manager sync.
    • Real card capture, refunds.
    • Loyalty points, membership tiers.
    • Housekeeping rosters, staff shifts.
    • Dynamic-pricing ML.
    • A database, login.

    Our Model

    Guests reserve, rooms get assigned. One hotel, room types each with a rack rate and a count, rooms typed by that.

    Actors and classes

    • Guest — name, contact, svc: ReservationService; book(type, in, out): Reservation calls svc.search(t, in, out).
    • FrontDesk — res: Reservation; arrive(String resId) calls svc.checkIn(resId), svc.checkOut(resId): Folio.
    • ReservationService (singleton) — types: Map<TypeCode, RoomType>, rooms: Map<TypeCode, List<Room>>, pricing: PricingStrategy, assign: AssignmentStrategy; search(RoomType t, LocalDate in, LocalDate out): List<Room>, reserve(RoomType t, LocalDate in, LocalDate out, Guest g): Reservation, overlaps(...): boolean, checkIn(String resId): void, checkOut(String resId): Folio, cancel(String resId).
    • RoomType — code: TypeCode, rackRate: Money, count: int; roomsLeft(LocalDate night): int (a per-night counter, not a scan).
    • Room (one room's calendar) — number: String, floor: int, type: RoomType, status: AVAILABLE | OCCUPIED | MAINTENANCE, bookings: NavigableSet<Reservation>; freeFor(LocalDate in, LocalDate out): boolean.
    • Reservation — id, guest: Guest, type: RoomType, room: Room (null until assigned), checkIn, checkOut: LocalDate, state: ResState, folio: Money; nights(): long, overlaps(Reservation o): boolean.
    • ResState (abstract) — confirm(), checkIn(), checkOut(), cancel(), noShow(). States: Requested -> Confirmed -> CheckedIn -> CheckedOut; Cancelled and NoShow are terminal.
    • PricingStrategy (interface) — quote(RoomType t, LocalDate in, LocalDate out): Money.
    • AssignmentStrategy (interface) — pickRoom(List<Room> free): Room, eager(): boolean. AssignAtBooking, AssignAtCheckin.

    Half-open nights [in, out)

    overlap when aIn < bOut AND bIn < aOut, strictly <, never <=. A checkout day equal to a check-in day is not an overlap. [3,6) vs [5,9): 3<9 and 5<6 -> clash; [9,12) vs [5,9): 9<9 false -> free.

    The pricing rules

    • RackRate -> nights x type.rackRate.
    • Seasonal -> rack x peak multiplier by date.
    • LengthOfStay -> 7th night free, weekly rate.

    Key operations

    1. search(RoomType t, LocalDate in, LocalDate out): List<Room> — scans that type's rooms (or reads the per-night counter) for one with no booking that overlaps [in, out). Read-only. Empty list when the type is sold out on any night in the range.
    2. reserve(RoomType t, LocalDate in, LocalDate out, Guest g): Reservation — under the inventory lock: re-scan, pick a room, create the Reservation CONFIRMED, insert the booking before the lock releases. Throws NoRoom when the type has no room free for every night.
    3. overlaps(LocalDate aIn, LocalDate aOut, LocalDate bIn, LocalDate bOut): boolean — half-open [in, out): true iff aIn < bOut and bIn < aOut. A checkout day equal to a check-in day is not an overlap. Strictly <, never <=.
    4. checkIn(String resId): void — legal only from CONFIRMED. Assigns a room number now if it was deferred, sets the room OCCUPIED, moves the state to CHECKED_IN. A second call throws.

    roomsLeft: left[type][night]-- on confirm, 0 means type full that night. O(nights), not O(rooms).

    The One Run to Hold in Your Head

    A guest wants a double, 3 nights, Jun 9 to Jun 12. Room 214 has a booking ending Jun 9 and another starting Jun 12. Does 214 fit, what does she pay at Rs 4,000 a night, and which objects touched the request?

    Room 214 fits: its bookings end on the 9th and start on the 12th, both half-open so neither overlaps [9, 12). She pays 3 nights x Rs 4,000.

    The Change

    The hotel lists on Booking.com and Expedia. A ChannelManager adapter pushes roomsLeft out to every OTA and pulls their bookings back in on one internal Reservation shape. Rate-and-availability parity is the hard part, and it is a second source of the last-room race. Adapter.

    What the Picture Can't Show

    The counter and the scan must agree. roomsLeft is the fast answer for a search; each room's booking set is the truth at confirm. Take the inventory lock before the final scan-and-insert, and rebuild the counter from the sets on restart.

    If They Make You Code It

    reserve and overlaps, the whole thing:

    class ReservationService {                       // one instance
    final Map<TypeCode,RoomType> types;
    final Map<TypeCode,List<Room>> rooms;        // per type
    PricingStrategy pricing; AssignmentStrategy assign;
    final Object lock = new Object();            // inventory lock

    Reservation reserve(TypeCode tc, LocalDate in,
                        LocalDate out, Guest g) {
        if (!in.isBefore(out)) throw new BadRange(in, out);
        synchronized (lock) {                    // one writer
            Room pick = null;
            for (Room r : rooms.get(tc))
                if (freeFor(r, in, out)) { pick = r; break; }
            if (pick == null) throw new NoRoom(tc, in, out);
            RoomType t = types.get(tc);
            Reservation res = new Reservation(
                g, t, in, out, pricing.quote(t, in, out));
            res.confirm();                       // -> CONFIRMED
            if (assign.eager()) res.assignRoom(pick);
            pick.bookings().add(res);            // visible now
            return res;
        }
    }

    boolean freeFor(Room r, LocalDate in, LocalDate out) {
        for (Reservation b : r.bookings())
            if (overlaps(in, out, b.checkIn(), b.checkOut()))
                return false;
        return true;                             // nothing clashed
    }

    boolean overlaps(LocalDate aIn, LocalDate aOut, // half-open
                     LocalDate bIn, LocalDate bOut) { // [in, out)
        return aIn.isBefore(bOut) && bIn.isBefore(aOut);
    }
}

    The Four Hazards

    1. Two guests, the last room. The scan is not the commit. With no lock, both guests scan type D on the same dates, both see room 214 free, both confirm. Take the inventory lock, re-scan and insert inside it, one guest wins.
    2. Off-by-one on the checkout day. A guest leaves on the 9th, another arrives on the 9th. Test it with <= and they collide while the room sits empty. Half-open [in, out): aIn < bOut and bIn < aOut, strictly <.
    3. No-show holds the room. A CONFIRMED booking that never checks in blocks the room all night, every night of the stay. At a cutoff (6pm day-of) mark NO_SHOW, bill one night from the folio, release the rest.
    4. Room pinned too early. Fixing room 214 at reserve-time blocks re-rooming, connecting-room and high-floor requests. Reserve the type, assign a number at check-in unless the guest asked for a specific room.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. synchronized (lock) wraps the scan and the insert — two guests cannot both take the last room of a type.
    2. overlaps is aIn.isBefore(bOut) && bIn.isBefore(aOut) — half-open [in, out), so a checkout day is a free night.
    3. pick.bookings().add(res) runs before the lock releases, so the next guest's scan sees the new booking.

    Answering "Is It Available?"

    Approach "How many left?" "Which room?" Book / cancel Overbook guard Best for
    Per-room list + scan (brute scan, the default) O(bookings) per room yes, returns it append / remove re-scan under lock a small hotel
    Per-night counter O(nights) count no — a number only +/-1 per night counter hits 0 most hotels
    Interval tree / room O(log n) per night yes, the exact room O(log n) insert node check under lock one room's calendar churned

    Per-night counter for "rooms left", plus a per-room list when a guest needs a specific room. Rooms of a type are interchangeable, so availability is a count per night, not a calendar per room. Reach for an interval tree only when one room's calendar is edited constantly.

    Rejection Signals

    These end the interview:

    • The overlap test written with <=, so a checkout day blocks the next arrival and every room loses a night.
    • Availability answered by scanning every room's whole booking list on every search, with no per-night counter.
    • One HotelSystem god class doing search, pricing, the folio and check-in with no seam to swap.
    • Pricing by an if on the month or day of week instead of a PricingStrategy.
    • The room number pinned at reservation time, so a connecting-room or high-floor request cannot be met.
    • No answer for a NO_SHOW or for two guests racing the last room — the two cases every interviewer probes.
    • Reservation state as a String set in place, with no guard on REQUESTED jumping straight to CHECKED_OUT.

    Patterns Used

    State — the Reservation lifecycle, one class per state. Strategy — pricing and room assignment. Observer — housekeeping and the front-desk board follow room state. Factory — the service builds a Reservation from a request.

    Say It Like This

    "One hotel, room types each with a rack rate and a count, rooms typed by that. A guest searches a date range and a type; the service scans that type's rooms for one with no booking that overlaps [checkIn, checkOut), or reads a per-night counter, and creates a CONFIRMED Reservation. Nights are half-open, so the checkout day is free. Pricing and assignment are strategies; the lifecycle is State."

    The Follow-ups That Decide It

    1. Guest leaves the 9th, another arrives the 9th. Clash? Half-open [in, out); 9 < 9 is false, no overlap.
    2. Two guests race the last room of a type. Take the inventory lock, re-scan inside it, one wins.
    3. Answer "rooms left" for a whole date range, fast. A per-night counter, O(nights), not a room scan.
    4. A confirmed guest never arrives. Mark NO_SHOW at the cutoff, bill one night, free the rest.
    5. Guest wants room 214, not just "a double". AssignmentStrategy.eager: pin at reserve; else a number at check-in.
    6. Peak-season rates and a 7th-night-free offer. A new PricingStrategy; reserve() is untouched.
    7. Cancellation the night before arrival. State to CANCELLED, free every night, cancel fee on the folio.
    8. A group needs ten rooms of one type for one range. The counter drops by ten atomically under the lock, all or nothing.

    Deliberately Not Built

    • OTA / channel-manager sync — a ChannelManager adapter pushing availability out and pulling bookings in. The ghost; its own integration problem.
    • Real card capture — a PSP behind a thin PaymentGateway. The folio math is the point, the integration is not.
    • Overbooking and the walk — selling past inventory, walking a guest to a partner hotel. An OverbookingPolicy, stated, not stumbled into.
    • Housekeeping scheduling — who cleans which room and when. The Observer carries the status; the roster is another problem.
    • Dynamic pricing — a PricingStrategy that reads demand signals. Drops in, no service change.
