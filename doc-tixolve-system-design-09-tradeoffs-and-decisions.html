    What I Would Do Differently at Real Production Scale

    Data & Storage

    • pgvector → Qdrant or Pinecone: At >10M vectors, purpose-built vector DBs significantly outperform pgvector on ANN search latency and index rebuild time.
    • Fixed chunking → Semantic chunking: Split on paragraph/section boundaries, not token count. Produces coherent chunks that carry complete thoughts. More complex to implement but meaningfully better retrieval quality.
    • Row-level tenant_id → Postgres Row-Level Security (RLS): Enforce tenant isolation at the database level, not just application level. Eliminates the risk of a forgotten WHERE clause exposing cross-tenant data.

    Reliability & Consistency

    • Polling outbox → Debezium CDC: Near-real-time event publishing by reading Postgres WAL directly. No polling overhead. More operationally complex but correct for high-throughput production.
    • At-least-once → Kafka transactions: True exactly-once semantics without maintaining an idempotency key table. Better for high-throughput consumers where the idempotency table becomes a bottleneck.
    • Single LLM provider → Multi-model fallback chain: If Claude API is unavailable, fall back to GPT-4, then local Ollama. Critical for production SLA guarantees.

    Auth & Security

    • Self-hosted Keycloak → Cognito or Auth0: Managed IdP eliminates operational burden of running, patching, scaling Keycloak. Security patches are applied automatically. Worth the cost for a real product.
    • Logical tenant isolation → Physical isolation for sensitive tenants: High-value regulated tenants (HIPAA, financial) get separate schemas with RLS or separate DB instances. Lower-value tenants share logical isolation.

    Observability

    • Logs + Metrics → Add distributed tracing: OpenTelemetry traces across all service hops. The missing pillar for diagnosing latency in the multi-service chat pipeline (which hop is slow?).
    • Fixed N context turns → Summarization: Long conversations need LLM-based summarization of older history, not truncation. Truncation loses important context; summarization preserves the gist at a fraction of the token cost.

    Infrastructure

    • ECS Fargate → EKS (Kubernetes): Mature ecosystem, service mesh (Istio), pod autoscaling, better operational tooling at scale.
    • Single-region → Multi-region: Active-active or active-passive replication for disaster recovery. Requires careful thinking about cross-region Kafka replication and eventual consistency.

    Decisions I Can Defend Under Pressure

    "Why not just use a monolith and avoid all this complexity?"

    For a portfolio project, yes — a monolith would deliver faster. But this project's goal is to demonstrate I can reason about distributed systems, explain trade-offs, and implement patterns (outbox, event-driven, database-per-service) that matter at scale. The complexity is the point. In a real small team product, I'd start with a modular monolith and extract services when scaling pain made it necessary.

    "Why Kafka for internal service events? Couldn't you just use REST calls?"

    For ticket.created → notification: yes, I could call notification-service's REST API directly from ticket-service. But then ticket-service knows notification-service exists — tight coupling. If I add analytics-service later, I modify ticket-service. With Kafka, ticket-service publishes to a topic and never changes when consumers are added or removed. The temporal decoupling is also real: if notification-service is restarting during a deployment, the event waits in Kafka rather than being dropped.

    "The outbox pattern adds complexity — why not just use a transaction + Kafka in the same Spring @Transactional?"

    Spring's @Transactional doesn't span heterogeneous resources (DB + Kafka) without XA transactions (two-phase commit). XA is slow, complex, and rarely available in cloud-managed Kafka. Even with Kafka's transactional producer, if the JVM crashes after the DB commits but before the Kafka commit is flushed, you have inconsistency. The outbox pattern solves this with local DB atomicity only — the most reliable primitive available.
