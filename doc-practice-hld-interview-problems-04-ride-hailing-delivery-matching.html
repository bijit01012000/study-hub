    Design Ride-Hailing & Delivery Matching — Uber/Swiggy

    3 sections · 3,241 words

    Three levels: Level 1 — The Shape, Level 2 — The Defence, Level 3 — The Edges.

    Level 1 — The Shape (Foundation)

    Pacing: 3 min ask · 5 min trace flow · 7 min read why.

    The Ask

    Functional

    • Rider requests a ride from current location
    • Driver location updates continuously online
    • Find nearby available drivers in a radius
    • Match the rider to exactly one driver

    Non-Functional

    • Continuous driver pings, huge volume ← forces async writes
    • Nearby search must be sub-second ← forces a spatial index
    • A 30 s-old ping is nearly worthless ← forces in-memory index

    Agree These First

    2,000,000 ride requests/day · 500,000 active drivers, ~30% concurrently online · drivers ping every 4 s while online. Round, illustrative numbers — not a real company's traffic. Every number on this sheet falls out of these three.

    The Shape

    Components and flow:

    • Driver — Mobile app · pings while online; (1) PUT /location — 37,500 /s
    • Location Service — Ingests pings · writes the index — cheap per ping
    • Rider — Mobile app · requests a ride; POST /ride-request — 23.1 /s
    • Matching Service — Queries the index for nearby drivers, assigns one
    • Geo Index — In-memory spatial structure, geohash-keyed — both services write and read it
    • Trip Store — Durable record once matched · rider, driver, pickup, status

    Data model: driver_location driver_id PK → geohash, lat, lng, status.

    Line weight = traffic: WRITE · pings · 37,500/s; READ · match · 23.1/s.

    Say It Like This

    "Drivers ping every few seconds whether or not anyone wants a ride — that's roughly 1,620 pings for every one ride request, so this is a write-heavy system, unlike most of what gets asked. I'd index driver locations by geohash, not raw lat/lng, because proximity search needs a structure that supports it. Location goes stale fast, so the live-matching path reads from an in-memory index, not a database. And ingestion has to stay cheap — update the entry and return, nothing more, on every single ping."

    Defend It

    Decision Prefer Avoid
    (3) Spatial index Geohash — turns "nearby" into a fast, bounded lookup Raw lat/lng range scan → no simple index, doesn't scale
    (1) Ping ingestion Async, lightweight — update the entry, return, nothing more Heavy sync validation per ping → doesn't survive the volume
    (9) Live-matching read path In-memory index — a 30 s-old ping is nearly worthless anyway Durable store queried live → too slow for live matching

    Capacity Math

    Quantity Derivation Value
    Ride requests 2,000,000/day ÷ 86,400 s 23.1 /s
    Online drivers 500,000 × 30% concurrently online 150,000
    Pings 150,000 online ÷ 4 s interval 37,500 /s
    Ping : request 37,500 ÷ 23.1 — the headline ratio ≈1,620 : 1

    Round hard, out loud. For every one ride request, about 1,620 location pings happen. That's the whole shape of this sheet — the only one in the set where writes dwarf the transaction that actually makes money.

    Before You Draw Anything — The Four Moves

    1. Clarify, don't assume. Ride-hailing or delivery — the difference is small but real. Is multi-stop routing in scope? No — say so. — Two minutes of scoping buys the whole design.
    2. Agree the scale out loud. "2M ride requests/day, 500K drivers, ~30% online, pinging every 4s — that's ~1,620 pings per ride request." Now every choice has a reason. — An unstated number is an undefendable design.
    3. Draw the happy path only. Driver/Rider → Location/Matching Service → Geo Index → Trip Store. Get agreement before adding anything. — Boxes you add before agreement are boxes you'll defend alone.
    4. Name one trade-off unprompted. "I'd index by geohash, not raw lat/lng, because proximity search needs a structure that supports it." — This is the single move that separates L1 from a junior answer.

    What L1 Is Testing

    • Can you produce a shape without being led to it?
    • Does every box have a reason you volunteered?
    • Did you reach for "1,620 pings per ride request" unprompted?

    The Follow-Ups That Decide It

    1. A driver is 50 m away, across a cell boundary. Found? (ref 3 — tests: the geohash edge case — query the cell and its 8 neighbours)
    2. 150,000 drivers ping every 4 seconds. Is this read-heavy or write-heavy? (tests: can you correctly call this write-dominated, unlike most of this set)
    3. Two riders request a ride in the same second and both searches find the same driver. What happens? (ref 6 — tests: double-booking / atomic-assignment awareness)
    4. Walk a rider's request through the happy path, start to finish. (refs 1,2,3,4 — tests: can you trace a coherent shape end to end)
    5. Why two separate services — Location and Matching — instead of one? (refs 1,2 — tests: do you split by traffic shape, not by habit)

    At L1 you are being judged on one thing: can you produce a coherent shape and defend three choices inside it. Depth is page 2 — do not reach for it here. Ghosted boxes are what arrives next; you should be able to guess two of them.

    Level 2 — The Defence (Intermediate)

    Pacing: 5 min ask · 15 min trace flow · 10 min read why · 30 min cover & answer.

    The Ask

    Functional

    • Rider requests a ride from current location
    • Driver location updates continuously online
    • Find nearby available drivers in a radius
    • Match the rider to exactly one driver
    • Live location visible during the trip

    Non-Functional

    • Continuous driver pings, huge volume ← forces async writes
    • Nearby search must be sub-second ← forces a spatial index
    • One driver, one rider at a time ← forces atomic assign
    • A 30 s-old ping is nearly worthless ← forces in-memory index
    • Stay fast when supply is thin ← forces expanding radius

    Out of Scope — Say It Aloud

    • Multi-stop routing
    • In-app payments
    • Turn-by-turn navigation

    Agree These First

    2,000,000 ride requests/day · 500,000 active drivers, ~30% concurrently online · drivers ping every 4 s while online. Round, illustrative numbers — not a real company's traffic. Every number on this sheet falls out of these three.

    The Shape

    Components and flow:

    • Driver — Mobile app · pings while online; (1) PUT /location — 37,500 /s
    • Location Service — Ingests pings · writes the index — cheap per ping
    • Rider — Mobile app · requests a ride; POST /ride-request — 23.1 /s
    • Matching Service — Queries the index for nearby drivers, assigns one
    • Geo Index — In-memory spatial structure, geohash-keyed — both services write and read it · entry carries status: available / on_trip; ≈15 MB for 150K online drivers — fits on one node
    • (6) Atomic Assign — CAS on driver status — exclusive, not racy
    • (10) empty? widen radius ×2, retry
    • (5) Live Location Channel — Trip-scoped push — driver's ongoing pings, live
    • Trip Store — Durable record once matched · rider, driver, pickup, status

    Data model:

    • driver_location driver_id PK · geohash · lat · lng · status · updated_at
    • trips trip_id PK · rider_id · driver_id · status · created_at

    Line weight = traffic: WRITE · pings · 37,500/s; READ · match · 23.1/s; live location, trip-scoped.

    Say It Like This

    "Drivers ping every few seconds whether or not anyone wants a ride — that's roughly 1,620 pings for every one ride request, so this is a write-heavy system, unlike most of what gets asked. I'd index driver locations by geohash, not raw lat/lng, because proximity search needs a structure that supports it. Location goes stale fast, so the live-matching path reads from an in-memory index, not a database. And ingestion has to stay cheap — update the entry and return, nothing more, on every single ping."

    Defend It

    Decision Prefer Avoid
    (3) Spatial index Geohash — turns "nearby" into a fast, bounded lookup; query the cell and its 8 neighbours — a driver 50 m away can sit in the next cell Raw lat/lng range scan → no simple index, doesn't scale
    (1) Ping ingestion Async, lightweight — update the entry, return, nothing more Heavy sync validation per ping → doesn't survive the volume
    (9) Live-matching read path In-memory index — a 30 s-old ping is nearly worthless anyway Durable store queried live → too slow for live matching
    (6) Driver assignment Atomic compare-and-swap on driver status, at assignment Optimistic assign-then-check → both can grab "available"
    (10) Search radius Bounded, expanding — widen only if the search is empty One fixed wide radius, always → wastes cost when unneeded
    (5) Live location during trip A dedicated, trip-scoped 1:1 push channel Reuse the ping pipe → mixes the firehose with one feed

    Capacity Math

    Quantity Derivation Value
    Ride requests 2,000,000/day ÷ 86,400 s 23.1 /s
    Online drivers 500,000 × 30% concurrently online 150,000
    Pings 150,000 online ÷ 4 s interval 37,500 /s
    Ping : request 37,500 ÷ 23.1 — the headline ratio ≈1,620 : 1
    Index memory 150,000 × ~100 B/entry (geohash+lat/lng+id+status+ts) ≈15 MB
    Geohash cell precision 5 — varies slightly by latitude ≈4.9 × 4.9 km

    The index easily fits in memory on one node — ≈15 MB. Storage is not the constraint here, same as it never is on sheet 01. The real constraint is sustained write throughput: 37,500/s.

    What Breaks — Say It Before They Ask

    • (6) Double-booking. Two ride requests land on the same driver within milliseconds of each other. — Fix: atomic compare-and-swap on driver status at assignment time, not read-then-write
    • (10) No drivers found. The initial search radius comes up empty. — Fix: expand the radius progressively, not fail immediately or always search wide

    The Follow-Ups That Decide It

    1. A driver is 50 m away, across a cell boundary. Found? (ref 3 — tests: the geohash edge case — query the cell and its 8 neighbours)
    2. 150,000 drivers ping every 4 seconds. Is this read-heavy or write-heavy? (tests: can you correctly call this write-dominated, unlike most of this set)
    3. Two riders request a ride in the same second and both searches find the same driver. What happens? (ref 6 — tests: double-booking / atomic-assignment awareness)
    4. No drivers are found within the initial search radius. What do you do? (ref 10 — tests: expanding-radius awareness, not a dead end)
    5. Same driver, two requests, same millisecond — what exact mechanism stops a double-booking? (ref 6 — tests: can you name compare-and-swap, not just "there's a lock")
    6. Once a rider is matched, how does their app keep seeing the driver's live location? (ref 5 — tests: a separate, trip-scoped channel, not the ping firehose itself)

    Cover The Sheet · Answer Aloud

    Use it as revision: cover the right rail and the two panels to your left, then walk the numbered path out loud. If you cannot say why a box is there and what breaks it, that box is your gap.

    Level 3 — The Edges (Advanced)

    Pacing: 10 min ask · 25 min trace flow · 15 min read why · 40 min cover & answer.

    The Ask

    Functional

    • Rider requests a ride from current location
    • Driver location updates continuously online
    • Find nearby available drivers in a radius
    • Match the rider to exactly one driver
    • Live location visible during the trip

    Non-Functional

    • Continuous driver pings, huge volume ← forces async writes
    • Nearby search must be sub-second ← forces a spatial index
    • One driver, one rider at a time ← forces atomic assign
    • A 30 s-old ping is nearly worthless ← forces in-memory index
    • Stay fast when supply is thin ← forces expanding radius

    Out of Scope — Say It Aloud

    • Multi-stop routing
    • In-app payments
    • Turn-by-turn navigation

    Agree These First

    2,000,000 ride requests/day · 500,000 active drivers, ~30% concurrently online · drivers ping every 4 s while online. Round, illustrative numbers — not a real company's traffic. Every number on this sheet falls out of these three.

    The Shape

    Components and flow:

    • Driver — Mobile app · pings while online; (1) PUT /location — 37,500 /s

    • Rider — Mobile app · requests a ride; POST /ride-request — 23.1 /s

    • Geo Index — In-memory spatial structure, geohash-keyed — both services write and read it · entry carries status: available / on_trip; ≈15 MB for 150K online drivers — fits on one node
    • (6) Atomic Assign — CAS on driver status — exclusive, not racy
    • (7) Regional Shards — Split by city/region — bounds load per shard
    • (8) Freshness Reaper — TTL sweep — stale pings drop out of results
    • (10) empty? widen radius ×2, retry
    • (5) Live Location Channel — Trip-scoped push — driver's ongoing pings, live
    • Trip Store — Durable record once matched · rider, driver, pickup, status
    • (11) demand spike, one geohash cell

    Data model:

    • driver_location driver_id PK · geohash · lat · lng · status · updated_at
    • trips trip_id PK · rider_id · driver_id · status · created_at

    "Drivers ping every few seconds whether or not anyone wants a ride — that's roughly 1,620 pings for every one ride request, so this is a write-heavy system, unlike most of what gets asked.     Decision Prefer Avoid
    (3) Spatial index Geohash — turns "nearby" into a fast, bounded lookup; query the cell and its 8 neighbours — a driver 50 m away can sit in the next cell Raw lat/lng range scan → no simple index, doesn't scale
    (1) Ping ingestion Async, lightweight — update the entry, return, nothing more Heavy sync validation per ping → doesn't survive the volume
    (9) Live-matching read path In-memory index — a 30 s-old ping is nearly worthless anyway Durable store queried live → too slow for live matching
    (6) Driver assignment Atomic compare-and-swap on driver status, at assignment Optimistic assign-then-check → both can grab "available"
    (10) Search radius Bounded, expanding — widen only if the search is empty One fixed wide radius, always → wastes cost when unneeded
    (5) Live location during trip A dedicated, trip-scoped 1:1 push channel Reuse the ping pipe → mixes the firehose with one feed
    (7) Sharding the index Regional shards — bounds load, keeps matches local One global index → full 37,500/s hits one structure
    (8) Staleness TTL / freshness check — stale entries drop out of results Keep until overwritten → a dead driver stays "current"

    Capacity Math

    Quantity Derivation Value
    Ride requests 2,000,000/day ÷ 86,400 s 23.1 /s
    Online drivers 500,000 × 30% concurrently online 150,000
    Pings 150,000 online ÷ 4 s interval 37,500 /s
    Ping : request 37,500 ÷ 23.1 — the headline ratio ≈1,620 : 1
    Index memory 150,000 × ~100 B/entry (geohash+lat/lng+id+status+ts) ≈15 MB
    Geohash cell precision 5 — varies slightly by latitude ≈4.9 × 4.9 km

    37,500/s is the aggregate. Split by region, each shard sees a fraction of it — sharding here is a throughput bound as much as a locality rule, which is why the write firehose stays manageable.

    What Breaks — Say It Before They Ask

    • (6) Double-booking. Two ride requests land on the same driver within milliseconds of each other. — Fix: atomic compare-and-swap on driver status at assignment time, not read-then-write
    • (10) No drivers found. The initial search radius comes up empty. — Fix: expand the radius progressively, not fail immediately or always search wide
    • (7) Write firehose overwhelms one shard. All pings and searches hit one global structure. — Fix: regional sharding, bounding both write and search load per shard
    • (8) Stale ping treated as current. A driver's connection drops; their last location ages without anyone noticing. — Fix: a freshness check/TTL — past the threshold, treated as unavailable, not silently kept
    • (11) Search-radius thundering herd. An airport/stadium-style spike bursts requests against a few nearby drivers in one geohash cell. — Fix: a genuine capacity problem, not a bug — surge pricing or rider queuing is a product-level answer, worth naming honestly

    1. A driver is 50 m away, across a cell boundary. Found? (ref 3 — tests: the geohash edge case — query the cell and its 8 neighbours)

    3. Two riders request a ride in the same second and both searches find the same driver. What happens? (ref 6 — tests: double-booking / atomic-assignment awareness)
    4. No drivers are found within the initial search radius. What do you do? (ref 10 — tests: expanding-radius awareness, not a dead end)
    5. Same driver, two requests, same millisecond — what exact mechanism stops a double-booking? (ref 6 — tests: can you name compare-and-swap, not just "there's a lock")
    6. Once a rider is matched, how does their app keep seeing the driver's live location? (ref 5 — tests: a separate, trip-scoped channel, not the ping firehose itself)
    7. A driver's phone loses signal mid-trip. Their last ping is three minutes old. What does the rider's app show? (ref 8 — tests: staleness handling in a moving-target context)
    8. How do you make sure a rider in one city never gets matched with a driver in another? (ref 7 — tests: regional sharding awareness)
