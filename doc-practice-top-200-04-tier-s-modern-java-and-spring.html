      41. Records — what they are and when to use them

      Asked at: Razorpay · Cred · Swiggy · senior + mid 2024+

      Difficulty: Easy-Medium · Topic: Java 16+ features

      The question: "What are records in Java 16+? When would you use one instead of a regular class?"

      The 30-second answer: Records are compact syntax for immutable data classes. public record Point(int x, int y) {} auto-generates: constructor, accessors x() / y(), equals(), hashCode(), toString(). Use them for DTOs, value objects, multi-return values — anywhere you'd otherwise write a class with only getters.

      Step-by-step thought process:

      1. " public record User(String name, String email, int age) {} — one line. Equivalent to a class with: final fields, canonical constructor, accessors (no get prefix — just name()), equals based on all components, hashCode based on all components, toString listing all components."
      2. "Records are implicitly final. Cannot extend other classes. Can implement interfaces."
      3. "Components are immutable — no setters generated. You CAN add validation in a compact constructor: public User { if (age < 0) throw new IllegalArgumentException(); }."
      4. "Use cases: REST API request/response DTOs, multi-return values from methods (instead of Pair / Tuple), map keys (auto-correct equals/hashCode), event objects."
      5. "NOT for: mutable entities (e.g. JPA @Entity often needs mutability), classes that need inheritance hierarchies."

      Edge cases to mention:

      • You can override the auto-generated accessor or toString / equals / hashCode if needed — useful for defensive copying of mutable component types
      • Records can have static factory methods and additional non-component methods
      • Pattern matching for records (Java 21) lets you destructure: if (obj instanceof User(var name, var email, var age))

      What NOT to say:

      • "Records replace Lombok @Data" — only for immutable cases; Lombok still wins for mutable entities
      • "Records can have mutable fields" — wrong, components are always final

      Common follow-up: "How does record pattern matching work in Java 21?"

      42. Sealed classes — what problem do they solve?

      Asked at: Senior rounds at product cos

      Difficulty: Medium · Topic: Java 17 features

      The question: "What are sealed classes (Java 17), and when would you use one over an abstract class?"

      The 30-second answer: Sealed classes restrict which classes can extend them. public sealed class Shape permits Circle, Square, Triangle { } — only those three classes can extend Shape. Useful for modeling closed domains (like algebraic data types) and for exhaustive pattern matching.

      Step-by-step thought process:

      1. "Sealed = restricted inheritance. The permits clause lists allowed subtypes; the compiler enforces that no other class can extend the sealed type."
      2. "Each permitted subtype must be one of: final (closed), sealed (further restricted), or non-sealed (re-opens to any subtype)."
      3. "Use when: you have a closed set of variants (Result = Success | Failure; HTTPMethod = GET | POST | PUT | DELETE; Shape = Circle | Square | Triangle)."
      4. "Killer feature: pattern matching switch (Java 21) checks exhaustiveness. switch (shape) { case Circle c ->...; case Square s ->...; case Triangle t ->...; } — compiler errors if you miss a case."
      5. "For libraries: lets you evolve the type hierarchy without breaking users — opposite of abstract classes where anyone could extend unexpectedly."

      Edge cases to mention:

      • Sealed types and permitted subtypes must be in the same module (or same package if not modular)
      • Sealed interfaces work the same way
      • Records often work well as the leaf types of a sealed hierarchy — sealed interface Result permits Success, Failure { } record Success(String value) implements Result {} record Failure(String reason) implements Result {}

      What NOT to say:

      • "Sealed is just a fancy abstract" — misses the exhaustiveness + closed-domain win
      • "Use sealed everywhere instead of abstract" — wrong fit for open hierarchies (e.g. plugins, extensions)

      Common follow-up: "How does sealed help pattern matching switch?"

      43. Pattern matching for switch (Java 21)

      Asked at: Razorpay · Swiggy · 2024+ senior rounds

      Difficulty: Medium · Topic: Java 21 features

      The question: "What's pattern matching for switch in Java 21? Give an example with a sealed hierarchy."

      The 30-second answer: switch can now match on type patterns and decompose data. Combined with sealed types, you get exhaustiveness checking and concise dispatch — like a lightweight version of pattern matching in Kotlin or Scala. Cleaner than instanceof chains.

      Step-by-step thought process:

      1. "Pre-Java-21: dispatch by type via if-else-instanceof chains, or visitor pattern. Both verbose."
      2. "Java 21 pattern matching for switch lets you switch on Object and match by type, optionally binding the value:"
      3. "Code:" 
      String describe(Shape s) {
    return switch (s) {
        case Circle c -> "radius " + c.radius();
        case Square sq -> "side " + sq.side();
        case Triangle t -> "triangle";
    };
}
      1. "If Shape is sealed, the compiler enforces exhaustiveness — adding a new permitted subtype causes compile errors anywhere you forgot to handle it. Safe refactoring."
      2. "Guard patterns let you add conditions: case Square sq when sq.side() > 10 -> "big square"."
      3. "Combined with records (Java 21): record patterns destructure — case Circle(double radius) -> radius * 2."

      Edge cases to mention:

      • case null is now allowed in switch (Java 21) — gives explicit null handling instead of NPE
      • Patterns can be nested: case Container(var content) etc.
      • The arrow form (->) doesn't fall through; the colon form (:) still does — prefer arrow for safety

      What NOT to say:

      • "It's like Kotlin's when" — true but generic; show you've used it
      • "It's just sugar for instanceof" — partly true but the exhaustiveness + records destructuring is more than sugar

      Common follow-up: "How do guards work? Show me a switch where guards matter."

      44. Virtual threads (Java 21) — what changes?

      Asked at: Razorpay · Cred · Swiggy · Meesho 2024+

      Difficulty: Medium-Hard · Topic: Java 21 features

      The question: "What are virtual threads in Java 21? When do they help vs traditional platform threads?"

      The 30-second answer: Virtual threads are lightweight threads managed by the JVM, not the OS. You can have millions of them. Blocking IO unmounts the virtual thread from its carrier (an OS thread), so blocking doesn't waste resources. Huge win for IO-bound server workloads (HTTP handlers, DB calls). No benefit for CPU-bound work.

      Step-by-step thought process:

      1. "Traditional Java threads (now called 'platform threads') are 1:1 with OS threads. Each takes ~1MB stack + OS scheduling overhead. Practical limit: a few thousand."
      2. "Virtual threads are scheduled by the JVM onto a small pool of platform threads (carriers). They use small stacks (~few KB) that grow as needed."
      3. "On blocking IO (file read, socket read, JDBC call), the virtual thread UNMOUNTS from its carrier — the OS thread is free to run another virtual thread. Massive concurrency without thread starvation."
      4. "Create one per request: Executors.newVirtualThreadPerTaskExecutor(). Spring Boot 3.2+ supports running Tomcat with virtual threads via a single config flag."
      5. "Sweet spot: web servers, microservices, gateway apps — any code that's mostly waiting on IO. NOT useful for CPU-bound work (compression, encryption, ML inference)."

      Edge cases to mention:

      • synchronized blocks PIN the virtual thread to its carrier — can't unmount. Use ReentrantLock for code that might block while holding a lock.
      • ThreadLocal still works but is more expensive per virtual thread — Java 21's ScopedValue is the replacement
      • Native code (JNI) also pins the virtual thread until the native call returns

      What NOT to say:

      • "Virtual threads make CPU-bound work faster" — false; you can't beat physical cores
      • "Just use them everywhere" — pinning issues mean you still need to know what blocks

      Common follow-up: "What does 'pinning' mean and when does it happen?"

      45. Structured concurrency (Java 21 preview)

      Asked at: Forward-looking senior rounds

      Difficulty: Medium-Hard · Topic: Java 21 features

      The question: "What's structured concurrency in Java 21, and what problem does it solve?"

      The 30-second answer: A new API (preview in Java 21) that treats a group of concurrent tasks as a single unit of work — like try-with-resources for tasks. If the parent scope exits, child tasks are automatically cancelled. Prevents thread leaks and orphaned async work that plagued CompletableFuture chains.

      Step-by-step thought process:

      1. "Problem: CompletableFuture chains have no parent-child relationship. If you spawn three async calls and forget to handle one, it runs to completion in the background — silently wasting resources."
      2. "Structured concurrency: try (var scope = new StructuredTaskScope.ShutdownOnFailure()) { var f1 = scope.fork(() -> callA()); var f2 = scope.fork(() -> callB()); scope.join(); scope.throwIfFailed();... }."
      3. "All forks live within the scope. When the scope exits (normally or via exception), any still-running forks are cancelled."
      4. "Two strategies built-in: ShutdownOnFailure (cancel siblings on first failure — call A and B in parallel, fail fast) and ShutdownOnSuccess (cancel siblings on first success — race them, take the winner)."
      5. "Together with virtual threads: clean, structured, scalable concurrency that reads top-to-bottom."

      Edge cases to mention:

      • Still in preview as of Java 21 — JEP 453, expected to stabilize in a future release
      • Custom scopes via subclassing StructuredTaskScope for application-specific policies Designed to work with the existing Thread API — Thread.currentThread() works as expected inside forks

      What NOT to say:

      • "It's like async/await" — closer, but Java's version is more about lifecycle management
      • "Use it everywhere" — preview API, lock-in risk if you ship before GA

      Common follow-up: "How does this compose with virtual threads?"

      46. Sequenced collections (Java 21)

      Asked at: Java-21-aware rounds

      Difficulty: Easy-Medium · Topic: Java 21 features

      The question: "What's the new SequencedCollection interface in Java 21? What gap does it fill?"

      The 30-second answer: A new interface for collections with a defined encounter order. Adds uniform methods: getFirst(), getLast(), addFirst(), addLast(), removeFirst(), removeLast(), reversed(). Implemented by List, LinkedHashSet, LinkedHashMap, Deque. Replaces the awkward list.get(0) / list.get(list.size()-1) patterns.

      Step-by-step thought process:

      1. "Pre-21: getting the first/last element required different code for each collection — list.get(0), set.iterator().next(), deque.getFirst(). Inconsistent and ugly."
      2. "SequencedCollection is a new interface (under Collection in the hierarchy) with first/last access methods."
      3. "Three new interfaces: SequencedCollection, SequencedSet, SequencedMap (separate hierarchies — Map isn't a Collection)."
      4. "List and Deque now extend SequencedCollection; LinkedHashSet implements SequencedSet; LinkedHashMap implements SequencedMap. Your existing ArrayList, LinkedList, ArrayDeque, LinkedHashSet, LinkedHashMap all gain the new methods automatically."
      5. " reversed() returns a view that iterates in reverse — no copying. Modifications to the view affect the original."

      Edge cases to mention:

      • Not all collections are sequenced — HashSet and HashMap aren't (no defined order)
      • reversed() on a List returns a List view; iteration order is reversed but indices still go 0..size
      • Slight gotcha: addFirst on an immutable collection throws UnsupportedOperationException

      What NOT to say:

      • "It's just a wrapper around the old methods" — true sort of, but the uniformity is the win
      • "Use it instead of List" — it's not a replacement, just an enhancement

      Common follow-up: "How does this change how you'd implement an LRU cache?"

      47. Text blocks — what changed in Java 15

      Asked at: Easy, modern Java rounds

      Difficulty: Easy · Topic: Java 15 features

      The question: "What's a text block in Java 15? Solve me a problem you'd actually use it for."

      The 30-second answer: Triple-quoted multi-line strings. Eliminates the escape-hell of embedded JSON, SQL, HTML in Java source. """multi-line text""". Automatic indentation normalization based on the closing delimiter position.

      Step-by-step thought process:

      1. "Pre-15: multi-line strings required \n and + concatenation, especially painful for embedded JSON/XML/SQL."
      2. "Java 15: text blocks. Open with """, content on subsequent lines, close with """. The position of the closing delimiter determines the 'indentation baseline' — leading whitespace up to that column is stripped."
      3. "Example: embedding SQL — String sql = """\n SELECT id, name, email\n FROM users\n WHERE active = true\n """; — clean, readable, no concatenation."
      4. "Embedded quotes don't need escaping inside text blocks (except triple-quote sequences themselves)."
      5. "Newlines are normalized to \n regardless of source file line endings."

      Edge cases to mention:

      • String.formatted(args) (Java 15+) is a fluent alternative to String.format(template, args) — pairs nicely with text blocks
      • Embedded expressions are NOT supported (no string interpolation as of Java 21) — template strings were preview in Java 21 + 22 (JEP 430, 459), then withdrawn in Java 23
      • Trailing newline can be suppressed with \ at the end of a line

      What NOT to say:

      • "Use string concatenation, it's just as readable" — no, embedded JSON in concatenation is unreadable
      • "Text blocks support string interpolation" — wrong, not yet

      Common follow-up: "How would you do string interpolation in Java?"

      48. Java 21 ScopedValue vs ThreadLocal

      Asked at: Java-21-aware senior rounds

      Difficulty: Medium-Hard · Topic: Java 21 features

      The question: "What's ScopedValue (Java 21), and why is it preferred over ThreadLocal in modern Java?"

      The 30-second answer: ScopedValue is an immutable, scoped alternative to ThreadLocal. Value is set for the duration of a specific code block (ScopedValue.runWhere), then automatically cleared. Solves ThreadLocal's leak problems in virtual-thread / thread-pool environments.

      Step-by-step thought process:

      1. "ThreadLocal sticks values to threads. In a thread pool or virtualthread environment, threads are reused, and ThreadLocal values leak across requests unless explicitly cleared."
      2. "ScopedValue is bound for the duration of a run or call block: ScopedValue.runWhere(USER, currentUser, () -> doWork());. After the lambda returns, the binding is automatically removed."
      3. "Immutable per binding — can't be reassigned mid-scope. Nesting allowed (inner runWhere shadows outer)."
      4. "Designed to play well with virtual threads — millions of virtual threads each with bounded scoped values, no leak risk."
      5. "Use cases: per-request user/tenant context, transaction context, observability tags."

      Edge cases to mention:

      • Reads are slightly cheaper than ThreadLocal (no map lookup, just a threadlocal stack)
      • Inherits across virtual thread forks within the same structured concurrency scope
      • Still in preview as of Java 21 (requires --enable-preview) — API expected to stabilize in a future release

      What NOT to say:

      • "ScopedValue replaces ThreadLocal everywhere" — gradually; both exist for now
      • "It's like Spring's RequestContextHolder" — adjacent but lower-level

      Common follow-up: "How does this work with virtual threads forking children?"

      49. Spring Boot 3 + Java 17 baseline — what changed?

      Asked at: Spring backend rounds 2024+

      Difficulty: Medium · Topic: Spring ecosystem

      The question: "You're upgrading a Spring Boot 2 app to Spring Boot 3. What are the major breaking changes?"

      The 30-second answer: (1) Java 17 minimum (was 8). (2) Jakarta EE 9 migration — javax. packages renamed to jakarta. across the entire app. (3) New observability stack — Micrometer Observation replaces Sleuth. (4) Native compilation via Spring AOT. (5) Hibernate 6 with new query semantics.

      Step-by-step thought process:

      1. "Java 17 baseline — your build must use JDK 17+. Many libraries also dropped Java 8/11 support around the same time."
      2. " javax. → jakarta. is the most disruptive change. Every javax.persistence, javax.servlet, javax.validation import needs updating. IDE refactor tools help; openrewrite recipe automates much of it."
      3. "Spring Sleuth (distributed tracing) is replaced by Micrometer Tracing + Micrometer Observation API."
      4. "Spring AOT processing + GraalVM native image support — your jar can build to a standalone binary with sub-second cold start. Useful for serverless."
      5. "Hibernate 6 changes: stricter SQL generation, new ID generators, and some JPQL behavior changes — test your queries carefully."

      Edge cases to mention:

      • Spring Security 6 has breaking changes too (lambda-style DSL replaces fluent builder)
      • Spring Boot 3.2 added virtual thread support — one config flag flips Tomcat to virtual threads
      • Native compilation has constraints (reflection, dynamic proxies need hints) — not zero-effort

      What NOT to say:

      • "Just bump the version, it'll work" — Jakarta migration alone is a multi-day refactor on real codebases
      • "Native compilation is faster at runtime" — startup yes, throughput often slightly worse

      Common follow-up: "How would you enable virtual threads in a Spring Boot 3 app?"

      50. "What's your favourite Java feature added in the last 3 years?"

      Asked at: Closing question, all levels

      Difficulty: Soft / signal-question · Topic: Self-awareness

      The question: "What's your favourite Java feature added in the last 3 years, and why?"

      The 30-second answer: This is a signal question. They're checking if you actually keep up with the language. Pick something concrete, recent (Java 17 or later), and explain a real use case where it changed your code for the better. Records, pattern matching, virtual threads, sealed classes — any of these work if you can talk about them concretely.

      Step-by-step thought process:

      1. "This is a personality/curiosity signal. Wrong answer: 'I don't know, I just write code.' Correct answer: pick one and explain how it affected your work."
      2. "Strong picks for 2024-26:"
      3. " Virtual threads (Java 21) — 'I migrated our gateway service to virtual threads and our p99 latency dropped 30% because we stopped queuing on the thread pool.'"
      4. " Records (Java 16) — 'I deleted ~2000 lines of DTO boilerplate when we adopted records across our REST layer.'"
      5. " Pattern matching for switch (Java 21) — 'Our event-handling code became exhaustive at compile time — we used to find missed event types in prod.'"
      6. " Text blocks (Java 15) — 'We embedded SQL in code without losing readability or fighting concatenation.'"

      Edge cases to mention:

      • If the interviewer is on an old Java version, mention it but pivot: "Records are great but I know team's on Java 11 — I've also gotten a lot of value from the Java 8 stream API improvements."
      • Show curiosity: "I've been playing with structured concurrency in Java 21 — too early to use in production but I like where it's heading."
      • Don't just list — pick ONE and tell a 30-second story about it

      What NOT to say:

      • "I don't really follow Java updates" — instant downgrade
      • "Lambdas" (added in Java 8, ~12 years ago) — shows you stopped paying attention
      • "Generics" (Java 5) — even worse

      Common follow-up: "Have you tried virtual threads in production? What surprised you?"
