      21. ThreadLocal — what it is and the classic memory leak

      Asked at: Razorpay · Cred · senior backend

      Difficulty: Medium-Hard · Topic: Concurrency

      The question: "What's ThreadLocal? Why does it cause memory leaks in thread pool environments?"

      The 30-second answer: ThreadLocal stores a value per thread — each thread sees its own copy. Memory leak: in a thread pool, threads are reused. ThreadLocal values aren't cleared between tasks. Over time, ThreadLocal entries accumulate per thread, and the GC can't reclaim them because the thread still holds a reference.

      Step-by-step thought process:

      1. " ThreadLocal<T> is conceptually a map from Thread → T. Each thread has its own ThreadLocalMap, accessed via the ThreadLocal instance as the key."
      2. "Use cases: per-request context (security principal, transaction ID) without passing it through every method signature; thread-confined caches; SimpleDateFormat instances (since SimpleDateFormat isn't thread-safe)."
      3. "The leak: in a thread pool (Tomcat, ExecutorService), thread instances are reused for many tasks. If a task sets a ThreadLocal value and doesn't remove it, the value sticks to that thread forever."
      4. "Even worse — ThreadLocalMap's entries use weak references for the KEY (the ThreadLocal instance) but strong for the VALUE. If the ThreadLocal goes out of scope, the key becomes weakly reachable, but the value is still strongly held."
      5. "Fix: always pair threadLocal.set(value) with threadLocal.remove() in a finally block, OR use Java 21's ScopedValue for the same use case without the leak risk."

      Edge cases to mention:

      • InheritableThreadLocal copies values to child threads at creation time — usually NOT what you want with thread pools
      • ScopedValue (Java 21) is the modern replacement — immutable, scoped to a run block, automatically cleared
      • Major frameworks (Spring, SLF4J MDC) have ThreadLocal cleanup as a common bug source

      What NOT to say:

      • "ThreadLocal is just thread-safe storage" — true but misses the lifecycle/leak issue
      • "Just don't use ThreadLocal" — too absolute; it has valid uses if you're disciplined

      Common follow-up: "How does Java 21's ScopedValue fix these issues?"

      22. Deadlock — how does it happen, how do you detect/avoid it?

      Asked at: Common in mid-to-senior rounds

      Difficulty: Medium-Hard · Topic: Concurrency

      The question: "Walk me through a classic deadlock scenario and tell me how you'd prevent it."

      The 30-second answer: Deadlock requires four conditions (Coffman's): mutual exclusion, hold-andwait, no preemption, circular wait. Classic scenario: Thread A locks resource 1 then tries for 2; Thread B locks 2 then tries for 1. Avoidance: enforce a global lock ordering (always acquire resources in the same order), use tryLock with timeout, or use higher-level constructs (concurrent collections).

      Step-by-step thought process:

      1. "Coffman's four conditions — all four must hold for deadlock. Break any one and deadlock is impossible."
      2. "Classic two-thread, two-lock deadlock: A holds L1 wants L2; B holds L2 wants L1. Both block forever."
      3. "Detection: jstack on a running JVM shows BLOCKED threads with their wait targets. Java even logs 'Found one Java-level deadlock' when threads hold mutual locks."
      4. "Prevention #1 — lock ordering: define a global order for all locks (e.g. by ID). Always acquire in ascending order. Breaks the circular-wait condition."
      5. "Prevention #2 — Lock.tryLock(timeout) instead of unbounded acquire. If timeout fires, release everything you hold and retry."
      6. "Prevention #3 — avoid holding locks across calls to unknown code (especially callbacks, lambdas). You don't know what locks the callee might try to acquire."

      Edge cases to mention:

      • Livelock: threads aren't blocked but keep retrying and getting nowhere (e.g. two polite people stepping aside in a corridor)
      • Starvation: a thread never gets a chance to run because higher-priority threads dominate — not technically deadlock but adjacent problem
      • Synchronized blocks acquire a single monitor; you can't selectively unlock them — ReentrantLock gives more control

      What NOT to say:

      • "Just don't use locks" — sometimes you must; advice is unhelpful
      • "Increase thread count to avoid deadlock" — actually makes it worse

      Common follow-up: "How do you detect deadlocks in a production system without taking a thread dump?"

      23. CompletableFuture — chaining async work without callback hell

      Asked at: Cred · Razorpay · Swiggy · backend rounds

      Difficulty: Medium-Hard · Topic: Async + concurrency

      The question: "Show me how you'd use CompletableFuture to call three services in parallel and combine the results."

      The 30-second answer: CompletableFuture.supplyAsync(call1), similar for call2 and call3, then CompletableFuture.allOf(f1, f2, f3).thenApply(v -> combineResults(f1.join(), f2.join(), f3.join())). Use thenCompose to chain dependent async calls (flatMap), thenCombine to combine two independent ones.

      Step-by-step thought process:

      1. " CompletableFuture.supplyAsync(supplier) runs the supplier on the ForkJoinPool (or specified Executor) and returns a future."
      2. "For parallel-then-combine: kick off all three with supplyAsync, get three futures. allOf returns a CompletableFuture<Void> that completes when all complete. After that, .join() on each gives the result."
      3. "For chaining (B depends on A's result): futureA.thenCompose(a -> callB(a)). thenCompose is flatMap; thenApply is map."
      4. "For combining two independent ones: futureA.thenCombine(futureB, (a, b) ->...)."
      5. "For fallback on error: .exceptionally(throwable -> fallbackValue) or .handle((value, throwable) ->...)."

      Edge cases to mention:

      • Default executor is the common ForkJoinPool — if your async work is IObound and blocks, you can starve the pool. Pass a dedicated Executor.
      • .join() is unchecked; .get() throws checked InterruptedException + ExecutionException
      • Java 21 virtual threads + structured concurrency (preview) is the new shiny — often a cleaner alternative

      What NOT to say:

      • "Use Future.get() in a loop" — defeats the purpose; you're blocking
      • "Use RxJava" — out of scope unless asked; CompletableFuture is the question

      Common follow-up: "How does this change with Java 21 virtual threads?"

      24. ExecutorService and the dangers of newFixedThreadPool

      Asked at: Senior backend rounds

      Difficulty: Medium · Topic: Concurrency

      The question: "What's wrong with Executors.newFixedThreadPool(10) in production?"

      The 30-second answer: It uses an unbounded LinkedBlockingQueue for tasks. If submission rate > processing rate, the queue grows unboundedly — eventually OOM. Production code should construct ThreadPoolExecutor directly with a bounded queue and a sensible RejectedExecutionHandler.

      Step-by-step thought process:

      1. " Executors.newFixedThreadPool(10) is a convenience method. Under the hood: new ThreadPoolExecutor(10, 10, 0, MILLISECONDS, new LinkedBlockingQueue<Runnable>())."
      2. "The LinkedBlockingQueue with no capacity argument is unbounded. If tasks arrive faster than 10 threads can process them, the queue fills with millions of tasks before anything fails — OutOfMemoryError, with confused stack traces."
      3. " newCachedThreadPool() is worse — it creates unlimited threads, can OOM faster."
      4. "Production: construct ThreadPoolExecutor directly. Pick a bounded queue (e.g. new ArrayBlockingQueue<>(1000)) and a RejectedExecutionHandler — CallerRunsPolicy (pushes back on submitter), AbortPolicy (throws), or your own that drops to a dead-letter queue."
      5. "Pre-compute pool size: CPU-bound ~ Runtime.getRuntime().availableProcessors(); IO-bound ~ much higher; mixed = profile."

      Edge cases to mention:

      • Spring's @Async defaults to a SimpleAsyncTaskExecutor (new thread per task!) unless configured. Always configure a TaskExecutor bean.
      • Java 21 virtual threads change the calculus — for IO-bound work, Executors.newVirtualThreadPerTaskExecutor() is now sensible
      • ThreadFactory lets you set thread names — critical for debugging stack dumps

      What NOT to say:

      • "newFixedThreadPool is the standard choice" — popular but production-dangerous
      • "Just use more threads" — backpressure, not threads, is the answer

      Common follow-up: "How does this change with Java 21 virtual threads?"

      25. synchronized — the difference between method-level and block-level

      Asked at: Common at all levels

      Difficulty: Medium · Topic: Synchronization

      The question: "What's the difference between synchronized on a method versus a synchronized block?"

      The 30-second answer: synchronized on an instance method = locks on this. synchronized on a static method = locks on the Class object. synchronized(obj) { … } block = locks on obj. Block-level is preferred because it lets you (a) lock on a private dedicated object (no external code can lock it), (b) shrink the critical section to just the code that needs it.

      Step-by-step thought process:

      1. " public synchronized void m() { … } is equivalent to public void m() { synchronized(this) { … } }."
      2. " public static synchronized void m() { … } locks on MyClass.class — the Class object."
      3. " synchronized(this) is dangerous in libraries — external code can also acquire this as a lock, causing deadlocks you can't predict."
      4. "Best practice: declare a private final Object: private final Object lock = new Object(); and use synchronized(lock) { … }. No one outside can lock it."
      5. "Block scope lets you shrink the critical section to JUST the racy part. Method-level synchronization is often coarser than necessary, hurting throughput."

      Edge cases to mention:

      • synchronized is reentrant — same thread can re-acquire the same lock without deadlocking itself
      • ReentrantLock offers tryLock, fairness, interruptible acquisition, and condition variables — capabilities synchronized doesn't have
      • Locking on a boxed Long/Integer/ String is unsafe — the JVM may intern values, you might be locking on the same object as unrelated code

      What NOT to say:

      • "synchronized is always slow, avoid it" — modern JVMs have biased locking and lightweight locking; uncontended synchronized is fast
      • "Lock on Class.class for static methods" — works but unusual; the implicit lock is the same Class object

      Common follow-up: "When would you use ReentrantLock over synchronized?"

      26. Producer-consumer with BlockingQueue

      Asked at: Common in design rounds

      Difficulty: Medium · Topic: Concurrency

      The question: "Design a producer-consumer system in Java. How would you handle backpressure?"

      The 30-second answer: Use a bounded BlockingQueue between producers and consumers. Producers call put() (blocks if full); consumers call take() (blocks if empty). The bounded queue provides natural backpressure — when full, producers slow down.

      Step-by-step thought process:

      1. " BlockingQueue<Task> interface; common impl: ArrayBlockingQueue<>(capacity) for bounded, LinkedBlockingQueue for optionallybounded."
      2. "Producer threads: queue.put(task) — blocks if the queue is full. Naturally throttles producers when consumers can't keep up. This is backpressure."
      3. "Consumer threads: queue.take() — blocks if empty. No busy-wait, no polling."
      4. "Bounded is critical — unbounded queues just defer the problem until OOM."
      5. "For shutdown: poison-pill pattern (insert a sentinel object consumers check for and exit on), or use ExecutorService + future for clean shutdown."

      Edge cases to mention:

      • offer(task, timeout) and poll(timeout) are the non-blocking variants with timeout — useful when you need to log "queue full, dropping" instead of blocking
      • For very-high throughput: Disruptor library (LMAX) outperforms BlockingQueue by orders of magnitude SynchronousQueue has zero capacity — every put must directly match a take, useful for handoff patterns

      What NOT to say:

      • "Use wait() and notifyAll() " — outdated; BlockingQueue is the modern idiom
      • "Use a List and synchronize on it" — reinventing the wheel badly

      Common follow-up: "What if you needed different priority levels for tasks?"

      27. ReentrantLock vs synchronized — when to choose which?

      Asked at: Senior rounds

      Difficulty: Medium · Topic: Concurrency

      The question: "When would you use ReentrantLock instead of synchronized?"

      The 30-second answer: When you need: (1) tryLock with timeout, (2) interruptible lock acquisition, (3) fairness policy, (4) multiple Condition variables (more flexible than one wait/notify), (5) lock metrics (isHeldByCurrentThread, getHoldCount). Otherwise, synchronized is simpler and equally fast.

      Step-by-step thought process:

      1. " synchronized is concise, automatic release on exception, and the JVM heavily optimizes it (biased locking, lightweight locking, lock coarsening). Default choice."
      2. "Switch to ReentrantLock when you need a capability synchronized lacks:"
      3. " tryLock() or tryLock(timeout) — attempt acquisition without blocking forever. Useful for deadlock avoidance."
      4. " lockInterruptibly() — block but allow interrupt. synchronized blocks are not interruptible."
      5. " new ReentrantLock(true) — fair lock; threads acquire in FIFO order. Slower but prevents starvation."
      6. "Multiple Condition objects on one lock — replaces the limitation that synchronized has only one wait set per monitor. Classic example: producer-consumer with separate notFull and notEmpty conditions."

      Edge cases to mention:

      • ReentrantLock requires manual lock.unlock() in a finally block — exception-unsafe if you forget
      • ReentrantReadWriteLock allows multiple concurrent readers OR one writer — good for read-heavy data structures
      • StampedLock (Java 8+) adds optimistic reads — faster than ReentrantReadWriteLock under heavy read load

      What NOT to say:

      • "ReentrantLock is always faster than synchronized" — wrong; modern JVMs make synchronized very fast in uncontended cases
      • "synchronized is deprecated" — completely false

      Common follow-up: "What's the optimistic-read pattern in StampedLock?"

      28. wait/notify vs Condition — what changed?

      Asked at: Mid-level + senior rounds

      Difficulty: Medium · Topic: Concurrency primitives

      The question: "How does Condition (from java.util.concurrent.locks) improve over wait/notify?"

      The 30-second answer: Object's wait/notify has ONE wait queue per object — you can't selectively wake the right kind of waiter. Condition (paired with Lock) lets you have MULTIPLE condition variables on one lock — notFull and notEmpty for a bounded buffer, etc. Plus await(timeout, unit) is friendlier than wait(millis).

      Step-by-step thought process:

      1. "Object.wait() / notify() / notifyAll() work in synchronized blocks. One wait set per object monitor."
      2. "Classic problem: bounded buffer with producers waiting on 'not full' and consumers on 'not empty'. With one wait set, you must call notifyAll() and waiters check their condition — wakes up everyone, wasted work."
      3. " Lock + multiple Condition: final Condition notFull = lock.newCondition(); final Condition notEmpty = lock.newCondition();. Producer calls notFull.await() — only waits on full-buffer. Consumer signals notFull.signal() after taking — only wakes producers."
      4. "Cleaner semantics, less spurious wakeup, better throughput in contention."
      5. "Also: awaitNanos, awaitUntil(date), awaitUninterruptibly() give finer control than wait()."

      Edge cases to mention:

      • Always wait in a loop checking the condition predicate — spurious wakeups exist in both wait/notify and Condition
      • signal() wakes one waiter; signalAll() wakes all. Prefer signalAll if uncertain — correctness over performance
      • BlockingQueue / Semaphore wrap these primitives — usually you should use the higher-level construct

      What NOT to say:

      • "wait/notify and Condition are the same" — they aren't; the multi-condition support is the key win
      • "Use wait without holding the lock" — runtime exception; both wait and await require holding their respective lock

      Common follow-up: "Why do you always wait in a while-loop instead of an if?"

      29. Memory model — happens-before relationship

      Asked at: Senior rounds at top product cos

      Difficulty: Hard · Topic: JMM

      The question: "What's the happens-before relationship in the Java Memory Model? Give an example."

      The 30-second answer: Happens-before is a partial ordering on operations across threads. If A happens-before B, then B sees A's effects (writes visible, reads see the new value). Established by: synchronization (lock release happens-before subsequent acquire), volatile writes (happens-before subsequent volatile reads of the same variable), thread start, thread join, final field freezes.

      Step-by-step thought process:

      1. "Without happens-before, the JVM and CPU are free to reorder operations within a thread — your reads might see stale values, writes might be invisible to other threads."
      2. "The JMM defines specific operations that establish happens-before: synchronized exit → synchronized entry on same monitor; volatile write → subsequent volatile read of same variable; Thread.start() → first action in started thread; final action in thread → Thread.join() in another thread."
      3. "Practical example: double-checked locking requires volatile on the instance field. Without it: thread A's writes (object construction) might not happen-before thread B's read (the null check), and B might see the reference assigned before the object is fully constructed."
      4. " AtomicInteger.set and get also establish happens-before — that's why Atomic classes are useful for inter-thread communication beyond just numerical operations."
      5. "If you have no happens-before relationship, you have no guarantee that one thread's writes are visible to another."

      Edge cases to mention:

      • Final fields have special "freeze" semantics — guaranteed visible to other threads after the constructor returns
      • Static initializers establish happens-before for all reads of static fields — useful for safe singletons via inner-class idiom
      • Volatile is transitive in interesting ways — see "JSR-133 cookbook" for the formal model

      What NOT to say:

      • "Threads share memory, so they see each other's writes" — wrong, that's the whole problem JMM solves
      • "Volatile makes everything thread-safe" — only for visibility, not for compound operations

      Common follow-up: "How does this connect to the double-checked locking pattern?"

      30. ForkJoinPool and work-stealing

      Asked at: Senior backend + parallelism-heavy rounds

      Difficulty: Medium-Hard · Topic: Parallelism

      The question: "What's ForkJoinPool, and how does work-stealing work?"

      The 30-second answer: ForkJoinPool is a thread pool optimized for divide-and-conquer recursion. Each worker thread has its own deque of tasks. When a worker's deque is empty, it STEALS tasks from another worker's deque. Used internally by parallel streams and CompletableFuture by default.

      Step-by-step thought process:

      1. "Designed for tasks that can be split into smaller tasks (RecursiveTask / RecursiveAction). Submit a big task, it forks subtasks, the pool processes them in parallel, you join the results."
      2. "Each worker has a local deque (double-ended queue). The worker pushes/pops from one end (LIFO — good cache locality for the just-created subtask)."
      3. "When a worker's deque is empty, it tries to steal from another worker's deque — but from the OTHER end (FIFO). This minimizes contention with the owning worker."
      4. "Result: idle threads pick up work automatically; no central queue contention; good cache locality for the busy path."
      5. "Java's ForkJoinPool.commonPool() is shared by parallel streams, CompletableFuture, and any code that uses it directly. Be careful about blocking IO in pool threads — it starves the pool."

      Edge cases to mention:

      • For blocking IO, use ManagedBlocker to signal the pool to spawn a replacement thread
      • Java 21 virtual threads largely replace the need for ForkJoinPool for IO-bound work
      • Parallel stream performance depends heavily on the Spliterator's split quality — for poorly-splitting sources, parallel is slower

      What NOT to say:

      • "Work-stealing means stealing tasks from the main thread" — wrong, workers steal from each other
      • "Always use parallelStream() for performance" — pool starvation, splitting overhead, and contention often make sequential faster

      Common follow-up: "Why might parallelStream() actually be slower than stream()?"
