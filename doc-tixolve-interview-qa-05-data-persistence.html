      Data & Persistence

      0 sections · 416 words

      24. Explain database-per-service and its benefit.

      Each service owns its schema; no cross-service joins. That gives schema autonomy — ticket-service can add a column or change a type without coordinating with anyone. In a shared DB, every migration is a cross-team negotiation and one service's bad query can lock another's tables. It also prevents the "lazy join" that silently couples services and makes them impossible to split later.

      25. How do you manage schema migrations?

      Flyway, versioned SQL per service (V1__…, V2__…). Each service migrates its own DB on startup. This keeps schema changes in version control, ordered, and repeatable — and reinforces database-per-service because each service's migrations only touch its own tables.

      26. I see a V3__add_optimistic_lock_version.sql. Explain optimistic locking here.

      JPA @Version. Each update reads the current version, and the UPDATE includes WHERE version = ?; if someone else updated the row in between, zero rows match and Hibernate throws OptimisticLockException. I use it in the ingestion pipeline (document status transitions) and auth. It's "optimistic" because it assumes conflicts are rare and only pays the cost on actual collision — no row locks held during the long-running work. Pessimistic locking would hold a DB lock across the whole ingestion, which is exactly what I want to avoid.

      27. Why VARCHAR + CHECK constraint for status/priority instead of a native Postgres enum?

      ALTER TYPE... ADD VALUE can't run inside a transaction and historically needs an exclusive lock — so adding a new ticket status becomes a downtime migration. With VARCHAR + CHECK, adding a status is a transactional DROP/ADD CONSTRAINT that runs online. Slightly weaker DB-level typing, but Hibernate's @Enumerated(STRING) + bean validation enforce valid values before anything reaches the DB.

      28. Why store embeddings in a separate chunk_embeddings table?

      Three reasons: (1) different access pattern — embeddings are only touched via the <=> vector operator, never SELECT *, so separating them avoids dragging 768 floats into every chunk read; (2) reembedding isolation — switching embedding models (768→1536 dims) only rewrites chunk_embeddings, leaving source text untouched; (3) future multi-model support — one chunk could hold multiple embedding rows for A/B testing retrieval.

      29. Why raw JDBC for embeddings instead of JPA?

      Hibernate can't map float[] to pgvector's vector(768) type. So chunks go through JPA but embeddings use JdbcTemplate with an explicit ?::vector cast. I use saveAndFlush on the chunk first so the INSERT fires before the embedding insert, because chunk_embeddings has an FK on chunk_id.
