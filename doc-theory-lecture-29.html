    Lecture 29 — Hibernate Internals

    20 sections · 4,770 words

    Lecture 29

    Scope evidence: "Hibernate Internals | Persistence Context, L1 Cache & Transactions" (playlist map, verified). Repo folder is the hibernateInternalsDemo project: entity model.Student, repository repository.StudentRepository, service service.StudentService with @Transactional, controller controller.StudentController, plus HibernateInternalsDemoApplication and application.properties. Coverage below = core components, the persistence context, @PersistenceContext, transactions and @Transactional, lifecycle states, dirty checking, flushing and write-behind, the first-level cache, and EntityManager methods.

    Hibernate becomes far easier to reason about once we stop seeing it as a SQL generator. Internally it owns an in-memory workspace called the persistence context, tracks the entity objects placed inside it, detects changes, and synchronizes them with the database inside a transaction. This lecture builds that mental model, which every later Spring Data lecture assumes.

    1. The Core Hibernate Components

    Four components form the backbone, each with a different job and lifetime. Confusing them is the source of most beginner bugs.

    Component Responsibility Typical lifetime
    EntityManagerFactory Creates EntityManager instances and stores shared ORM metadata Entire application
    EntityManager Provides operations for interacting with entities and the persistence context One unit of work or transaction
    Persistence Context Stores and tracks managed entity instances Usually one transaction
    Database Transaction Ensures a group of database operations succeeds or fails as one unit One business operation

    The relationship is a straight chain:

    EntityManagerFactory -> creates -> EntityManager
EntityManager -> interacts with -> Persistence Context
Persistence Context -> synchronizes through Hibernate -> Database

    Two lifetime facts matter in interviews:

    • The EntityManagerFactory is expensive to create and is normally shared for the application's lifetime (one per persistence unit).
    • An actual EntityManager is short-lived and must not be shared concurrently between threads; it is one unit of work, not an application-wide service.

    Important: The factory is heavy and long-lived; the manager is light and short-lived. Reading this the other way around explains almost every "why is my entity stale" question.

    2. JPA, Hibernate, and Spring Boot

    Three layers cooperate, and each answers a different question.

    JPA is the specification. Jakarta Persistence, commonly called JPA, defines a standard contract for object-relational mapping in Java. It provides interfaces, annotations, and rules such as EntityManagerFactory, EntityManager, @Entity, @Id, and @GeneratedValue. JPA defines what persistence operations should do; it does not contain the ORM engine that performs them.

    Hibernate is the provider. Hibernate implements the JPA contract and does the actual work: mapping entities to tables, generating SQL, interacting with JDBC, tracking entity state, performing dirty checking, managing the persistence context, and coordinating synchronization with the database. Hibernate also offers its own native API, which mirrors the JPA types:

    JPA API Hibernate native API
    EntityManagerFactory SessionFactory
    EntityManager Session

    SessionFactory extends EntityManagerFactory and Session extends EntityManager, so Hibernate supports the standard JPA API while exposing Hibernate-specific features too.

    Spring Boot's role. Our code normally uses JPA types (jakarta.persistence.Entity, jakarta.persistence.EntityManager, jakarta.persistence.Id) while Hibernate works underneath as the provider. Coding against JPA keeps persistence code provider-independent, so Hibernate could be swapped for another provider with fewer changes than if the code depended on Hibernate-specific APIs.

    Golden rule: Spring Boot configures, JPA specifies, Hibernate implements. Keep those three verbs in that order and the stack stops being mysterious.

    Mnemonic: Spring Sits, JPA Says, Hibernate Does (S-S-D) - configuration, contract, execution.

    3. The Persistence Context

    A persistence context is Hibernate's in-memory workspace for managed entities. Picture it as a map keyed by entity identity, pointing at live Java objects:

    Persistence Context
+----------------------------------+
| Student#1 -> Student object      |
| Student#2 -> Student object      |
| Student#7 -> Student object      |
| Tracks identity and state        |
+----------------------------------+

    Suppose we execute Student student = entityManager.find(Student.class, 1L);. If the entity is not already available in the current persistence context, Hibernate may:

    1. execute a SELECT;
    2. create a Student object from the returned row;
    3. place that object in the persistence context;
    4. begin managing its state.

    The context is responsible for much more than storage. It supports:

    • entity identity;
    • lifecycle state management;
    • automatic change detection;
    • first-level caching;
    • transactional write-behind;
    • synchronization with the database.

    EntityManager is the main JPA interface for interacting with that context. Its operations (persist, find, remove, flush, detach, clear, refresh) touch an entity, the context, or the synchronization between them.

    4. @PersistenceContext in Spring

    An EntityManager can be injected into a Spring repository using @PersistenceContext:

    @Repository
public class StudentRepository {

    @PersistenceContext
    private EntityManager entityManager;

    public Student findById(Long id) {
        return entityManager.find(Student.class, id);
    }
}

    The name is meaningful: we ask Spring for an EntityManager connected to the persistence context appropriate for the current operation.

    Why Spring does not inject one permanent EntityManager. Repositories are singleton beans by default, so one repository object serves many request threads. A real JPA EntityManager, like a Hibernate Session, is not thread-safe, so sharing one physical instance would be unsafe. Spring injects a shared proxy instead, routing each call to the transaction-associated EntityManager and then to the persistence context. Two concurrent transactions can use the same repository with different persistence contexts.

    Interviewer's perspective: The killer detail is "proxy, not a single instance." Candidates who say "Spring injects one EntityManager" fail the thread-safety follow-up immediately.

    5. Transactions from First Principles

    Consider a bank transfer that debits one account and credits another. If the first statement succeeds and the second fails, money is deducted but never added. A transaction treats both as one logical operation, BEGIN ... COMMIT, and on failure runs ROLLBACK. The region between beginning and completing is the transaction boundary.

    Unit of work. A unit of work is the complete set of persistence actions needed for one business operation. Changing a student's email may involve:

    1. retrieving the student;
    2. checking business rules;
    3. modifying the entity;
    4. detecting the change;
    5. generating SQL;
    6. executing SQL;
    7. committing the transaction.

    All belong to one logical unit. The transaction decides whether the database changes succeed together; the persistence context tracks the entities involved.

    Database, Hibernate, and Spring transactions are three layers around the same work:

    • Database: understands BEGIN; UPDATE ...; COMMIT;.
    • Hibernate native API: open a Session, call session.beginTransaction(), session.persist(student), then transaction.commit(), catching exceptions to transaction.rollback() and closing the session in finally.
    • Spring: removes that repetitive code.
    @Transactional
public void createStudent(Student student) {
    entityManager.persist(student);
}

    Conceptually Spring begins a transaction, executes the method, flushes pending changes, then commits; if a rollback-triggering exception occurs, it rolls back instead:

    Begin transaction
        |
        v
Execute method
        |
        v
Flush pending changes
        |
        v
Commit

    Begin transaction
        |
        v
Execute method
        |
        v
Exception
        |
        v
Rollback

    By default Spring rolls back for unchecked exceptions such as RuntimeException and Error; checked-exception behavior can be configured with attributes such as rollbackFor.

    6. How @Transactional Works

    Spring applies @Transactional through an AOP proxy. The annotated method is not called directly; a generated proxy intercepts the call, opens the transaction, invokes the real method, then commits or rolls back. A StudentService with an @Transactional updateStudent(Long id) method is wrapped this way:

    • the controller calls the StudentService proxy;
    • the TransactionInterceptor begins a transaction (or joins one per propagation rules);
    • StudentService.updateStudent() runs;
    • after the method completes or throws, the proxy commits or rolls back.

    Because the proxy owns the transaction boundary, a call from one method to another method on the same object may bypass the proxy. This is the usual self-invocation limitation of proxy-based AOP: a same-class call never passes through the interceptor, so no new transaction is applied.

    Important: @Transactional is proxy-based. Self-invocation (this.otherMethod()) skips the proxy, so the annotation on the inner method does nothing.

    7. Complete Transaction and Persistence Context Flow

    Put everything together with this service method:

    @Transactional
public void updateStudent(Long id) {
    Student student = entityManager.find(Student.class, id);
    student.setName("Rohan");
}

    Step 1: The call reaches the service proxy (controller -> StudentService proxy).

    Step 2: Spring starts the transaction. The interceptor creates or joins a transaction per the propagation rules.

    Step 3: An EntityManager is associated with the transaction (transaction -> EntityManager -> persistence context).

    Step 4: Hibernate executes find(). It first checks the persistence context for Student#id; if present it returns the managed instance, otherwise it queries the database, creates the entity, and manages it.

    Step 5: The managed entity is modified. student.setName("Rohan"); needs no explicit update method, because Hibernate tracks the managed object.

    Step 6: Hibernate flushes. Before commit it synchronizes pending changes by running UPDATE students SET name = 'Rohan' WHERE id = ?;.

    Step 7: The database transaction commits. After a successful commit the changes are durable. When the transaction-scoped context ends, its entities are no longer managed.

    Important: In step 5 there is no update() call and no SQL. The UPDATE appears only at flush in step 6. That gap is dirty checking plus write-behind working together.

    8. Why Transactions Belong in the Service Layer, and Which Operations Need One

    A repository method is often one database action, while a business operation may span several calls - enrolling a student may fetch a student and course, create an enrollment, and record a payment. If each call had its own transaction, part of the operation could commit while a later part failed. The service layer is normally the better boundary because it represents the complete use case:

    • repository methods perform persistence operations;
    • service methods define which operations must succeed or fail together.

    Repository-level @Transactional can be useful, but it should not divide one business operation into unrelated transaction boundaries.

    Which operations require a transaction? For a normal transaction-scoped JPA persistence context:

    Operation Transaction required? Purpose
    find() Not normally required without locking Retrieve an entity by primary key
    persist() Yes Make a new entity managed and schedule its insertion
    merge() Yes Copy state into a managed instance
    remove() Yes Mark a managed entity for deletion
    flush() Yes Synchronize pending changes with the database
    refresh() Yes in normal application usage Reload an entity's state from the database

    A basic find() may work without @Transactional, but modifying data belongs inside a clearly defined transaction.

    Interviewer's perspective: The expected nuance is "reads can work transactionless, writes must not." "Every operation needs a transaction" and "none do" both miss the persistence context's scope.

    9. Entity Lifecycle States

    An entity instance moves through four main lifecycle states:

    1. Transient - a new Java object not yet known to Hibernate.
    2. Managed - associated with the current persistence context.
    3. Detached - was managed, no longer associated with its context.
    4. Removed - managed but scheduled for deletion.

    Managed is central because dirty checking, automatic updates, first-level caching, relationship synchronization, and flushing all depend on it.

    State Associated with context? Tracked/dirty-checked? Represents a row? Typical entry Typical exit
    Transient No No Not yet new Student() persist() -> Managed
    Managed Yes Yes Yes (if from DB) persist(), find() detach(), clear(), context ends -> Detached; remove() -> Removed
    Detached No No May still context ends, detach(), clear() merge() -> Managed copy returned
    Removed Yes (as scheduled deletion) Deletion is dirty-checked Scheduled for deletion remove() flush -> row deleted

    Transient. new Student() creates an object that exists in Java memory, is not associated with a context, is not tracked by Hibernate, and normally does not yet represent a stored row. @Entity makes instances eligible for persistence; it does not make every new object managed automatically.

    Managed. An entity is managed when it is associated with the current context. A new entity becomes managed through persist(); an entity returned by find() is managed too. Hibernate does not create a second copy on persist() - the same Java object becomes managed.

    Important: Managed does not mean "already written to the database." persist() makes the entity managed, but the INSERT may be delayed until a flush; timing can depend on identifier generation. Managed describes the relationship with the context, not whether SQL has executed.

    Detached. A detached entity was previously managed, still exists as a Java object, may still represent a row, but is no longer associated with its original context. It becomes detached when the context ends, when detach() removes one entity, or when clear() detaches every managed entity and empties the context. Changes after detachment are not automatically detected.

    Removed. Calling remove(student) on a managed entity tells Hibernate the row should be deleted at flush. remove() is primarily a lifecycle transition: it does not necessarily execute DELETE at that exact line.

    Removed vs detached:

    Detached Entity Removed Entity
    Hibernate has stopped managing it Hibernate is managing its deletion
    Its database row should remain Its database row is scheduled for deletion
    Later field changes are not dirty-checked Deletion is synchronized during flush

    detach(student) does not delete the student; remove(student) does.

    10. The Entity Lifecycle Diagram and merge()

    The full set of transitions, in one picture:

    new Student()
        |
        v
    TRANSIENT
        |
        | persist()
        v
     MANAGED
      /     \
 remove()    detach()
    |          \
    v           v
 REMOVED      DETACHED
                 ^
                 | context ends
                 |
             (managed objects become detached)

 DETACHED --merge()--> Managed copy returned

    Important rule about merge(). merge() does not reattach the same detached Java object. Calling Student managedStudent = entityManager.merge(detachedStudent); copies the detached object's state into a managed instance and returns that instance. So detachedStudent stays detached while managedStudent is the managed value. Always use the returned object for further managed operations; the supplied object is left untouched, and many bugs come from reusing the detached reference after a merge.

    11. Managed Identity and the First-Level Cache

    Within one persistence context, Hibernate keeps one managed object per entity type and primary key. Calling find(Student.class, 1L) twice in the same context normally satisfies first == second, because both references point to the same managed Java object. This is the identity map principle: one database identity is represented by one managed instance within a context. Without it, two objects for the same row could hold conflicting values in one unit of work.

    First-level cache. The context provides Hibernate's first-level cache, keyed conceptually by entity type plus primary key. It is:

    • enabled by default;
    • impossible to disable like an optional external cache;
    • local to one persistence context;
    • normally transaction-scoped in a Spring application;
    • the guarantee behind managed entity identity.

    Lookup behavior:

    • first lookup (miss): Hibernate runs a SELECT, creates the object, and stores and manages it;
    • second lookup (hit): it returns the already-managed object with no second SELECT.

    Inside one transaction, repeated find() calls hit the cache; in a later independent transaction, find() issues a fresh SELECT because that transaction uses a different context. The first-level cache is not application-wide.

    Important Query Limitation: Primary-key lookups such as find() can be satisfied from the context. A JPQL or Criteria query may still execute SQL even if matching entities are already managed; Hibernate preserves identity by returning existing managed instances where applicable, but the query is not automatically skipped in every case.

    12. Dirty Checking and Flushing

    Dirty checking. Dirty does not mean invalid. An entity is dirty when its current managed state differs from the state Hibernate previously knew - a snapshot of name = "Rahul" against the current name = "Rohan".

    This is visible in updateStudent above: there is no entityManager.update(student) call, and JPA defines no EntityManager.update() method. The object from find() is managed, so Hibernate detects its changed state and generates the UPDATE. The sequence is:

    • find() runs and the entity becomes managed;
    • a field value changes;
    • a flush occurs;
    • dirty checking detects the change;
    • the UPDATE is generated.

    When it happens. A setter does not normally execute SQL immediately: the Java object changes, the entity stays managed in memory, and only at flush does Hibernate detect the changes and execute SQL. Hibernate compares current state with an earlier snapshot during flushing; depending on configuration and enhancement it may use more optimized techniques.

    Only for managed entities. If you find() an entity, detach() it, then call a setter, the change is not written automatically because the entity is detached. Setting the same value again - setName("Rahul") when it was already "Rahul" - normally produces no state change, so no update is needed for that field.

    Flushing synchronizes the changes represented by the context with the database by executing the required INSERT, UPDATE, or DELETE statements. Flush is not commit:

    flush() commit()
    Sends pending SQL to the database Successfully completes the transaction
    Changes are still part of the current transaction Changes become durable
    Can be followed by rollback Ends the transaction successfully

    A flushed UPDATE can still be undone by a later ROLLBACK; SQL execution does not mean commit.

    Automatic flush. With the common AUTO flush mode, Hibernate flushes before commit and before certain queries whose results could be affected by pending changes. The typical flow is:

    • transaction begins;
    • SELECT runs;
    • the student becomes managed;
    • setName("Rohan") is called;
    • the method returns;
    • flush issues the UPDATE;
    • commit completes the transaction.

    Manual flush. entityManager.flush(); is useful when SQL must run before the method ends - to surface a constraint violation earlier, to synchronize before later database work, or to control memory during batch processing with clear().

    Golden rule: flush talks to the database; commit makes the outcome final. Every rollback test exists because those are not the same event.

    13. Transactional Write-Behind and Batch Processing

    Hibernate calls the persistence context a transactional write-behind cache. In a write-through approach each change would immediately cause SQL; with write-behind, changes accumulate and are sent later at a flush. Delaying synchronization lets Hibernate:

    • avoid unnecessary work;
    • order SQL statements;
    • group operations;
    • support JDBC batching;
    • synchronize at a suitable point in the transaction.

    Write-behind does not remove the need for transactions; it works inside one so the database can still commit or roll back the resulting SQL as a unit.

    Batch processing with flush() and clear(). Persisting 100,000 entities in one loop keeps every entity managed, so the context grows very large and memory plus management work explode. A common pattern flushes and clears every 100 inserts:

    for (int i = 0; i < 100_000; i++) {
    Student student = createStudent(i);
    entityManager.persist(student);
    if ((i + 1) % 100 == 0) {
        entityManager.flush();
        entityManager.clear();
    }
}

    The two operations differ:

    Operation Effect
    flush() Executes pending SQL; entities remain managed
    clear() Detaches all managed entities and empties the persistence context

    This controls persistence-context memory; actual JDBC batching also depends on Hibernate's batch configuration.

    Important: flush() alone does not free memory because entities stay managed; clear() frees them but does not write SQL. You need both, in that order, for a memory-safe batch.

    14. clear(), detach(), refresh(), and the EntityManager Method Reference

    How clear() and detach() affect the cache. If you find() an entity, call entityManager.clear(), then find() again, the second lookup may run another SELECT, and first == second is normally false: first is the old detached object, second a new managed one. The two differ in scope: detach() detaches one entity, clear() detaches every managed entity. A later lookup after either may need to load and manage the entity again.

    Refreshing an entity. The cache can hold values older than the database if another transaction or external process changed the row. If a managed entity holds name = "Rahul" and the database becomes name = "Aman", the Java object does not update automatically; reload it with entityManager.refresh(student), which replaces the current managed state with the latest database state. refresh() discards unsynchronized in-memory changes, so use it deliberately.

    Quick reference of important EntityManager methods:

    Method Main effect
    persist(entity) Makes a new entity managed and schedules insertion
    find(Type.class, id) Finds by primary key and returns a managed entity
    merge(entity) Copies state into a managed instance and returns it
    remove(entity) Marks a managed entity for deletion
    contains(entity) Checks whether the instance is managed
    detach(entity) Detaches one entity
    clear() Detaches all entities
    flush() Synchronizes pending changes with the database
    refresh(entity) Replaces current entity state with database state

    Mnemonic: P-F-M-R (Persist, Find, Merge, Remove) are entity operations; F-C-D-R (Flush, Clear, Detach, Refresh) are context and synchronization operations.

    15. Myth vs Reality

    Myth Reality
    "An @Entity object is automatically managed" No. new Student() is transient until it is associated with a persistence context
    "Calling a setter immediately executes an UPDATE" No. A setter changes the Java object; Hibernate detects the change during flush
    "Managed means the SQL has already executed" No. Managed describes the entity's relationship with the persistence context
    "flush() and commit() are the same" No. Flush executes pending SQL inside the transaction; commit completes it
    "detach() deletes the database row" No. It only stops the current context from managing that object
    "merge() makes the same detached object managed" No. It returns a managed instance with copied state; the supplied object stays detached
    "The first-level cache is shared across the application" No. It belongs to a single persistence context
    "A singleton repository shares one physical EntityManager" Normally no. Spring injects a proxy routing calls to the transaction-associated EntityManager
    "Dirty checking works on detached objects" No. Dirty checking applies only to managed entities

    16. Common Trap Questions

    Trap 1 - "I called persist(), so the row exists in the database." Verdict: False. persist() makes the entity managed and schedules the insertion. The INSERT may be delayed until a flush, and it only becomes durable at commit.

    Trap 2 - "flush() and commit() are interchangeable." Verdict: False. Flush executes pending SQL inside the transaction and can still be rolled back; commit ends the transaction and makes the changes durable.

    Trap 3 - "The first-level cache is a global application cache." Verdict: False. It is the persistence context itself, local to one context, normally one transaction. A later transaction issues a fresh SELECT.

    Trap 4 - "merge() reattaches my detached entity." Verdict: False. merge() copies state into a managed instance and returns it. The detached object you passed in stays detached, so keep and use the return value.

    Trap 5 - "Changing a detached entity will be saved automatically." Verdict: False. Dirty checking only applies to managed entities. After detach(), clear(), or the transaction ending, changes are not automatically detected.

    Trap 6 - "detach() deletes the row." Verdict: False. detach() only removes the entity from the context. remove() marks a managed entity for deletion, and even that sends DELETE at flush.

    Trap 7 - "A singleton repository must share one EntityManager." Verdict: False. Spring injects a shared proxy routing each call to the EntityManager bound to the current transaction, so concurrent requests use different persistence contexts.

    17. Points to Remember

    1. EntityManagerFactory is heavy and application-scoped; EntityManager is light and transaction-scoped, and is not thread-safe.
    2. Spring Boot configures, JPA specifies, and Hibernate implements; SessionFactory extends EntityManagerFactory and Session extends EntityManager.
    3. The persistence context is the in-memory workspace; the first SELECT result is created as an object, placed in the context, and managed.
    4. @PersistenceContext injects a shared proxy, not one physical EntityManager, because repositories are singletons.
    5. A transaction is a boundary around a unit of work: BEGIN ... COMMIT, with ROLLBACK on failure; Spring rolls back by default on unchecked exceptions and Error.
    6. @Transactional works through an AOP proxy, so self-invocation bypasses it and propagation rules decide whether a transaction is created or joined.
    7. Transactions usually belong in the service layer because one business operation may span several repository calls that must succeed or fail together.
    8. Lifecycle states are Transient, Managed, Detached, Removed; only managed entities are dirty-checked, and merge() returns a managed copy.
    9. Dirty checking compares current managed state with Hibernate's earlier snapshot, and flushing converts changes into INSERT/UPDATE/DELETE SQL.
    10. flush() sends SQL but does not commit; clear() empties the context for batching; the first-level cache is per context and refresh() reloads database state.

    18. Likely Interview Questions

    Question Crisp Answer
    What is the persistence context? Hibernate's in-memory workspace storing and tracking managed entities, keyed by type and primary key, synchronizing changes with the database.
    EntityManagerFactory vs EntityManager? The factory is heavy, application-scoped, and creates managers; the manager is a short-lived, non-thread-safe unit-of-work API.
    JPA vs Hibernate vs Spring Boot? JPA is the specification, Hibernate the provider implementing it, Spring Boot the layer configuring the persistence infrastructure.
    Why does Spring inject a proxy for EntityManager? Repositories are singletons across threads and a real EntityManager is not thread-safe; the proxy routes to the transaction-bound manager.
    What does @Transactional do? An AOP proxy opens a transaction around the method, flushes, then commits or rolls back for exceptions per its attributes.
    Why do transactions belong in the service layer? A business operation may call several repositories; the service boundary makes them commit or roll back as one unit.
    Which operations require a transaction? Writes (persist, merge, remove, flush, normally refresh); a plain find() usually works without one.
    Name the four lifecycle states. Transient, Managed, Detached, Removed.
    Does merge() make the passed object managed? No. It copies state into a managed instance and returns it; the argument stays detached.
    What is dirty checking? Comparing a managed entity's current state with its earlier snapshot during flush to decide which UPDATEs to generate.
    flush() vs commit()? Flush executes pending SQL within the transaction and can be rolled back; commit finalizes the transaction and makes changes durable.
    What is the first-level cache? The persistence context: per-transaction, always on, keyed by type and primary key, guaranteeing one managed instance per row.

Transaction-scoped persistence context ends -> entities become detached
    • Factory is application-scoped; manager and persistence context are transaction-scoped.
    • JPA specifies, Hibernate implements, Spring Boot configures - and injects a proxy, not a physical manager.
    • The persistence context is the first-level cache, identity map, and transactional write-behind buffer at once.
    • Four lifecycle states - Transient, Managed, Detached, Removed - and only managed entities are dirty-checked.
    • Setters never execute SQL directly; flushing generates SQL, and committing makes it durable.

    One-line takeaway: Hibernate does not translate individual method calls into SQL - it manages entity state inside a persistence context and synchronizes that state with the database within a transaction boundary, which is why dirty checking, the first-level cache, flushing, and @Transactional are one idea seen from four angles.
