    Phase 1 — Auth Service + API Gateway

    Goal: Keycloak running in Docker, auth-service storing app-level user/tenant metadata, api-gateway validating JWTs and routing.

    Status: Complete — all services healthy, end-to-end JWT flow verified.

    What was built:

    • [x] Keycloak 24.0.5 in Docker with PostgreSQL backend, tixolve realm imported from JSON
    • [x] auth-service: users + role_mappings tables (Flyway V1–V3), REST endpoint /users/me with just-in-time provisioning
    • [x] api-gateway: JwtClaimsExtractionFilter (extracts userId/tenantId/role → downstream headers), rate limiting via Redis, routing rules
    • [x] GatewayAuthenticationFilter in each downstream service (reads trusted headers → Spring SecurityContext)
    • [x] End-to-end verified: Keycloak token → gateway → auth-service returns user profile; 401 on missing token

    Decisions made during implementation:

    1. Health checks use image-native tools, not curl. - eclipse-temurin:21-jre-alpine (auth-service, api-gateway): no curl — uses BusyBox wget --spider - quay.io/keycloak/keycloak:24.0.5 (ubi9-micro): no curl in PATH — uses bash built-in /dev/tcp TCP check - Lesson: always match the healthcheck tool to the base image. Don't assume curl is universal.
    2. Keycloak dependency uses service_started, not service_healthy. - auth-service has no Keycloak call at startup (trusts gateway headers) - api-gateway configures jwk-set-uri (lazy key fetch) alongside issuer-uri — when both are set, Spring Security uses jwk-set-uri and makes no startup call to Keycloak - Therefore neither service needs to wait for Keycloak to be healthy. service_started provides ordering without blocking. - Interview answer: "In microservices, hard startup ordering is an anti-pattern. Services should be resilient to dependencies being temporarily unavailable."
    3. V3 Flyway migration added for @Version column. - The @Version optimistic locking field was in the JPA entity but missing from V1 schema. - Fixed via V3 migration rather than modifying V1 — Flyway migrations are immutable once applied. - Rule: always add a new migration; never edit an applied one.
    4. directAccessGrantsEnabled: true for dev testing only. - SPA clients should use Authorization Code + PKCE, not password grant. We set false in production config. - Enabled via Keycloak Admin API for local token testing without running a browser PKCE flow. The realm-export.json now has true for dev convenience. In a real project, you'd have separate realm configs per environment.

    Deviations from plan: None. All locked decisions from CLAUDE.md §8 followed.

    Phase 2 — Ticket Service (Plain CRUD + Outbox)

    Goal: First fully working service — tickets, status workflow, outbox pattern.

    Status: Complete — building and running in Docker, outbox poller active.

    What was built:

    • [x] tickets table (VARCHAR status/priority with CHECK constraints, optimistic locking, loose ID refs)
    • [x] outbox_events table (partial index on unpublished, FIFO ordering)
    • [x] ticket_events table (append-only audit log, separate from outbox)
    • [x] REST endpoints: POST /tickets, GET /tickets (paginated), GET /tickets/{id}, PATCH /tickets/{id}/status, POST /tickets/{id}/assign
    • [x] Status state machine with validated transitions (VALID_TRANSITIONS map in service layer)
    • [x] Outbox pattern: ticket + outbox event written in one @Transactional block
    • [x] OutboxEventPoller (@Scheduled, 5s) — logs + marks published in Phase 2, will send to Kafka in Phase 6
    • [x] Gateway route /api/tickets/** wired with rate limiting
    • [x] Same GatewayAuthenticationFilter pattern as auth-service

    Decisions made during implementation:

    1. Status transition validation in the service layer, not the entity or DB. - Entity doesn't validate transitions — entities are data containers, not business rule enforcers. - DB CHECK constraint only validates that the value is a known enum member, not that the sequence is valid. - Service holds Map<TicketStatus, EnumSet<TicketStatus>> VALID_TRANSITIONS — single place, full control. Interview answer: "Entities shouldn't contain business logic. DB constraints are for data integrity, not workflow. The service layer owns the rules."
    2. CLOSED is a terminal state — no transition out. - Deliberate design. If a closed ticket is relevant again, the agent creates a new ticket referencing the old one. - This preserves the audit trail and makes SLA metrics clean (no re-opening distorts time-to-resolution). - The EnumSet.noneOf(TicketStatus.class) for CLOSED makes this explicit in code.
    3. VARCHAR + CHECK constraint over PostgreSQL enum types for status/priority. - PostgreSQL ALTER TYPE ADD VALUE requires an exclusive table lock in Postgres < 12 and can't be done inside a transaction. - VARCHAR + CHECK: adding a new status is ALTER TABLE tickets ADD CONSTRAINT ... CHECK (status IN (..., 'NEW_VALUE')) — online, transactional. - Trade-off: slightly less type safety at the DB level. Acceptable for a field that Hibernate also validates via @Enumerated.
    4. Loose ID references instead of foreign keys across services. - creator_id and assignee_id are VARCHAR(36), not FK → auth-service.users. - If auth-service deletes a user, ticket-service shouldn't cascade-delete tickets — that's cross-service coupling via the DB. - Interview answer: "Cross-service FK references are an anti-pattern. Each service is the authority for its own data. Reference by ID; resolve via REST call if you need the full object."
    5. Two separate tables: outbox_events and ticket_events. - Outbox: for Kafka delivery. Write-once, mark published, never queried for business logic. - Ticket events: for audit trail and history. Queried by agents ("show all changes to ticket X"). Never marked published. - Putting them in the same table would conflate two different concerns with different query patterns and retention policies.

    Deviations from plan: None.

    Decisions made during implementation:

    1. Switched from MUI to Tailwind CSS. - MUI with heavy customization still risks looking like stock MUI to an interviewer. - Tailwind + custom tokens gives full control — the output is unrecognizably custom. - Interview answer: "I built the design system from scratch using Tailwind's utility system with custom tokens — every visual decision is deliberate rather than inherited from a component library."
    2. Architecture page is admin-only, accessed inside the live running app. - An admin can navigate to /architecture and walk through the entire system design during an interview — live, in the app, not in a separate slide deck. - ProtectedRoute re-checks the role on mount. Client-side guard is defense-in-depth, not the real security boundary (that's @PreAuthorize on the backend). - Interview answer: "The frontend guards reflect the same RBAC the backend enforces. Client-side route protection is a UX decision, not a security one — an attacker who bypasses it still hits a 403 from @PreAuthorize."
    3. VALID_TRANSITIONS mirrored on the frontend. - StatusUpdateModal only renders valid next statuses — user never sees a transition option that will 400. - Explicit interview talking point: "The frontend mirrors the state machine the backend enforces. It's defense in depth for UX: the user can't click into an invalid state, so errors stay server-side validations for programmatic callers, not UI surprises."
    4. TanStack Query for all server state — no Redux. - Interview answer: "API data is server state — it has a canonical source on the server, goes stale, and multiple components can need it simultaneously. React Query handles caching, deduplication, background refetch, and loading states better than a hand-rolled Redux cache."
    5. Sonner for toasts over a custom implementation. - Small, composable, headless-friendly. Custom-styled via classNames to match the design system exactly.
    6. Vite 5 pinned — not Vite 6. - Vite 6 uses Rolldown (new Rust-based bundler) which requires Node >= 20.19. Current environment is 20.18. - Vite 5 is the stable choice for this Node version. No functionality gap for this use case.

    Deviations from plan: MUI replaced by Tailwind CSS (user-confirmed decision, CLAUDE.md §2 updated accordingly).

    Phase 4 — Knowledge Service

    Goal: S3 upload, async chunking pipeline, pgvector storage, hybrid search endpoint.

    Status: Complete — all services healthy, end-to-end upload→ingest→search verified.

    What was built:

    • [x] Infrastructure: pgvector/pgvector:pg16 image, MinIO (local S3), Ollama (local LLM/embeddings)
    • [x] documents, document_chunks, chunk_embeddings (vector(768) + HNSW index), ingestion_jobs, outbox_events tables (Flyway V1–V4)
    • [x] S3StorageService — AWS SDK v2, MinIO-compatible via endpoint override + forcePathStyle
    • [x] IngestionService — @Async("ingestionExecutor"), Apache Tika PDF extraction, fixed-size chunking (2000 chars / 200 overlap), nomic-embed-text embeddings via Spring AI, JdbcTemplate JDBC for vector INSERT with ?::vector cast
    • [x] SearchService — parallel vector cosine (<=>) + PostgreSQL full-text (tsvector/tsquery), RRF merge
    • [x] DocumentController: POST /documents (multipart upload), GET /documents, GET /documents/{id}, DELETE /documents/{id}
    • [x] SearchController: POST /search
    • [x] GatewayAuthenticationFilter, SecurityConfig (STATELESS, trusted gateway headers)
    • [x] OutboxEventPoller (@Scheduled 5s) for document.ingested event
    • [x] End-to-end verified: upload PDF → PENDING → PROCESSING → COMPLETED (1 chunk), search returns chunk with similarityScore: 1.0

    Decisions made during implementation:

    1. pgvector/pgvector:pg16 image instead of postgres:16-alpine. - Standard postgres image doesn't include the pgvector binary. - Switched to the official pgvector image which pre-installs the extension. - Extension activated via separate CREATE EXTENSION IF NOT EXISTS vector in the DB init script. - Interview answer: "pgvector is a Postgres extension that adds a native vector type and efficient ANN operators. The HNSW index makes similarity search O(log n) — critical for low-latency RAG retrieval."
    2. MinIO as local S3 with endpoint override. - AWS SDK v2's endpointOverride() + forcePathStyle(true) routes all S3 calls to MinIO at localhost:9000 locally. - In production: remove the override, configure real AWS credentials — same Java code, zero changes. - Interview answer: "The code is completely S3-agnostic. We test with MinIO locally for zero cloud cost. The abstraction is just a config property — that's why we use the SDK rather than raw HTTP calls."
    3. Spring AI EmbeddingModel interface — no provider lock-in. - IngestionService and SearchService depend on EmbeddingModel, not OllamaEmbeddingModel. - Switch from Ollama to OpenAI embeddings: change spring.ai.ollama.* to spring.ai.openai.* in application.yml. No Java changes. - Interview answer: "Spring AI's abstraction layer is the core pattern here. The same embedding model interface works for Ollama locally and Claude/OpenAI in production. That's the same pattern as JPA — you write to the spec, swap the provider via config."
    4. JdbcTemplate for vector INSERT, JPA for all other entities. - Hibernate 6 doesn't know how to map float[] to the pgvector vector(768) type. - Solution: use ?::vector PostgreSQL cast in a raw JdbcTemplate INSERT. - All business entities (Document, DocumentChunk, etc.) still use JPA/Spring Data normally. - Interview answer: "This is a targeted escape hatch — we use the right tool for each operation rather than forcing everything through one abstraction."
    5. TransactionSynchronizationManager.afterCommit() to fire @Async ingestion. - Calling ingestionService.ingest() directly inside a @Transactional method races with the async thread — the thread can start before the transaction commits, making the entity invisible. - Fixed by registering an afterCommit synchronization hook: async dispatch only fires after the enclosing transaction commits. - Interview answer: "This is the async-before-commit race condition — a subtle bug where your async task can't see data that's still inside an uncommitted transaction. The fix is to hook into the transaction's afterCommit lifecycle."
    6. TransactionTemplate for chunk + embedding writes inside @Async. - @Modifying repository methods require an active transaction. - The ingest() method is @Async and not itself @Transactional (would hold the connection open during 30s+ of Ollama calls). - Each chunk+embedding write is wrapped in its own TransactionTemplate.execute() — short transactions per chunk, not one transaction for the whole ingestion job. - saveAndFlush() used (not save()) to force the chunk INSERT before the JDBC embedding insert — avoids FK violation when Hibernate batches the flush. - Interview answer: "Long transactions are an anti-pattern in async work. We use short per-chunk transactions: save chunk, flush it, then insert the embedding. If ingestion fails mid-way, completed chunks are durable and the job can be retried from the failure point."
    7. Fixed-size chunking with sentence-boundary detection. - Primary split at 2000 chars (~500 tokens). Tries to break at last . or \n within the final half of the window. - 200-char overlap preserves context at boundaries. - Forward-progress guard: if nextStart <= currentStart, the text is shorter than one overlap window — break to prevent infinite loop. - Interview answer: "Fixed-size is defensible for MVP. The sentence-boundary refinement reduces semantic fragmentation at chunk edges. Overlap ensures a query that spans a boundary still finds relevant content."
    8. HNSW index parameters: m=16, ef_construction=64. - m controls the number of bi-directional links per node (graph connectivity). Higher m → better recall, more memory. - ef_construction controls the search width during index build. Higher → slower build, better recall. - m=16, ef_construction=64 are the pgvector defaults — well-calibrated for 768-dim embeddings. - Interview answer: "HNSW is a hierarchical graph structure that supports approximate nearest neighbor search in O(log n). The trade-off vs. exact search (IVFFlat) is build cost vs. query-time recall. For RAG, a few false negatives in retrieval are tolerable — low latency is not."

    Deviations from plan:

    • Spring AI artifact name changed from spring-ai-ollama-spring-boot-starter to spring-ai-starter-model-ollama in the 1.0.0 GA release. Updated pom.xml accordingly.
    • CREATE EXTENSION vector must be run manually after first DB volume creation if the init script was updated after the volume was initialized. Documented as a one-time docker exec step.

    Phase 5 — Chat Service

    Goal: Spring AI + Claude/Ollama, RAG retrieval, SSE streaming, escalation logic.

    Status: Complete — SSE streaming verified end-to-end: tokens stream one-by-one, done event carries citations + escalation flag, outbox event written.

    What was built:

    • [x] conversations, messages (JSONB source_chunks), outbox_events tables (Flyway V1–V3)
    • [x] POST /conversations — create conversation; GET /conversations — paginated list; GET /conversations/{id} — full history
    • [x] POST /conversations/{id}/messages — SSE streaming endpoint (produces text/event-stream)
    • [x] KnowledgeServiceClient — RestClient POST /search, gracefully returns empty list on failure
    • [x] RAG prompt construction: numbered [Source N] blocks + conversation history (last 10) + user message
    • [x] ChatClient.stream().content() → Flux<String> subscribed with SseEmitter.send() per token
    • [x] Escalation heuristic: detects "I don't have enough information" in LLM response; sets conversation to ESCALATED; writes chat.escalated outbox event
    • [x] StreamDoneEvent (final event: done) carries messageId, citations, escalated, escalatedTicketId
    • [x] OutboxEventPoller (@Scheduled 5s) — logs + marks published; Kafka wiring in Phase 6
    • [x] DelegatingSecurityContextAsyncTaskExecutor wrapping chatExecutor — propagates Spring SecurityContext to @Async threads
    • [x] Ollama profile (docker): llama3.2:1b chat, nomic-embed-text embeddings; Claude profile: opt-in via ANTHROPIC_API_KEY
    • [x] GatewayAuthenticationFilter, SecurityConfig (STATELESS, trusted gateway headers)
    • [x] End-to-end verified: create conversation → send message → tokens stream via SSE → event:done with citations + escalated:true

    Decisions made during implementation:

    1. SseEmitter + @Async (Spring MVC) over WebFlux + Flux<ServerSentEvent>. - The rest of the service stack is Servlet-based (Spring MVC). Mixing WebFlux would require a full reactive stack or the gateway to handle both. - SseEmitter is Spring MVC's async response mechanism. The controller returns the emitter immediately; an @Async thread drives the LLM stream and writes tokens through it. - The servlet thread is released as soon as chatService.streamChat() is called — the async thread pool owns the connection from that point. - Interview answer: "SSE is the right protocol for unidirectional LLM token streaming. It works over plain HTTP/1.1, has browser-native reconnect via EventSource, and doesn't need a full WebSocket handshake. Spring MVC's SseEmitter integrates with Tomcat's async processing so the servlet thread isn't blocked during generation."
    2. DelegatingSecurityContextAsyncTaskExecutor for SecurityContext propagation. - SecurityContextHolder uses ThreadLocal by default. When @Async dispatches to a thread-pool thread, that thread starts with an empty SecurityContext. - If the original request's filter chain clears the context (our GatewayAuthenticationFilter.finally block does), and Spring Security's ExceptionTranslationFilter runs on the async thread's cleanup path, you get spurious AccessDeniedException after the stream completes. - Fix: wrap the executor with DelegatingSecurityContextAsyncTaskExecutor — it snapshots the SecurityContext at dispatch time and restores it on the async thread. - Interview answer: "SecurityContext is ThreadLocal — async threads don't inherit it automatically. DelegatingSecurityContextAsyncTaskExecutor is Spring Security's built-in fix: it copies the context snapshot to the worker thread before executing the task."
    3. ChatClient.stream().content() over ChatModel.call(). - ChatModel.call() blocks until the model finishes and returns the full response — unsuitable for streaming. - ChatClient.stream().content() returns a Flux<String> (Reactor). We subscribe with three callbacks: doOnNext (append token + send SSE event), doOnError (complete emitter with error), doOnComplete (save assistant message + escalation + send done event). - Interview answer: "Spring AI's ChatClient.stream() abstracts the streaming API of any provider. We get a Flux<String> regardless of whether the backend is Ollama or Claude — the same stream handling code works for both."
    4. Three-part prompt structure: CONTEXT + HISTORY + USER. - CONTEXT: numbered [Source N] (filename)\n<chunk content> — numbered for citation mapping. - HISTORY: last 10 messages in ROLE: content format, oldest-first for correct temporal order. - USER: the current question. - System prompt is sent via .system() separately so it doesn't take up RAG context space. - Interview answer: "The numbering in [Source N] is the key design detail — it's what allows the UI to render inline citation chips that map back to the exact document chunk. The model is instructed to use this notation, and the frontend maps the number to the citation metadata in the done event."
    5. Escalation is a heuristic, not a confidence score. - Detecting a specific phrase ("I don't have enough information") the system prompt instructs the model to use is deterministic and debuggable. - A confidence threshold on embedding similarity (e.g., max(rrfScore) < 0.4) is an alternative but can produce false positives when a document exists but doesn't fully answer the question. - MVP choice: model-signal escalation. Both mechanisms can coexist in a later phase. - Interview answer: "Heuristic escalation is intentional for v1. The model is grounded by the system prompt to use a specific phrase when it can't answer, so detection is deterministic. Threshold-based escalation on similarity score is a parallel signal we could add — they're complementary."
    6. llama3.2:1b for dev instead of 3b — memory budget constraint. - Docker Desktop is capped at 4 GB on an 8 GB Mac. With 10 services using ~2.5 GB, only ~1.3 GB remains for Ollama inference. - llama3.2:3b (~2 GB loaded) OOM-kills the llama-server process. llama3.2:1b (~1.3 GB) fits within budget. - Permanent fix: Docker Desktop → Settings → Resources → Memory → 6 GB. Leaves 2 GB for macOS, gives Docker 6 GB so all services + 3b model (or 1b) run comfortably. - In production/demo: Claude API via claude Spring profile — no local model needed. - Interview answer: "The model is a config swap. OLLAMA_CHAT_MODEL=llama3.2:3b upgrades quality on a machine with more Docker memory. For the interview demo we'll use the Claude API via the claude profile."
    7. Message.sourceChunks as JSONB, not a join table. - Citations are a read-time concern — we never query WHERE chunkId = ? across messages. - A join table would add a table + FK for data that's always accessed as a unit with its message. - JSONB with @JdbcTypeCode(SqlTypes.JSON) maps directly to List<CitationRef> — Hibernate serializes/deserializes automatically. - Interview answer: "JSONB is appropriate when the data is always accessed as a whole with its parent entity and you don't need to query individual items independently. Citations are a display artifact — they travel with the message, not independently."

    Deviations from plan:

    • Model switched from llama3.2:3b to llama3.2:1b due to 4 GB Docker Desktop memory budget. Permanent fix is increasing Docker Desktop memory to 6 GB — documented above.
    • escalatedTicketId was null until Phase 6 wired Kafka so ticket-service could consume chat.escalated and write back the ticket ID — resolved, see Phase 6.

    Known issue (found during Phase 9 metrics verification, not yet fixed):

    • A slow response — cold Ollama model load (~30s for tinyllama) plus CPU-bound token generation on a constrained dev machine — can push past ChatController's hardcoded 120s SseEmitter timeout. When that happens, the client gets a bare 403 Forbidden instead of a clean timeout error.
    • Root cause: on timeout, Tomcat re-dispatches the request through the full servlet filter chain to produce the error response. Spring Security's AuthorizationFilter runs on that second pass, but GatewayAuthenticationFilter (a OncePerRequestFilter) does not re-run on async dispatches by default — and its finally block already cleared SecurityContextHolder right after the first pass returned (which happens almost immediately, since the controller returns the emitter before streaming even starts). The second pass sees no authentication and throws AccessDeniedException.
    • DelegatingSecurityContextAsyncTaskExecutor (AsyncConfig) does not cover this — it only propagates context onto the @Async worker thread at dispatch time; it doesn't affect Tomcat's separate async-timeout error dispatch back through the filter chain on a different thread.
    • Reproduced live with LOGGING_LEVEL_COM_TIXOLVE_CHAT=DEBUG: retrieval + streaming logs confirmed the request was processing normally and tokens were streaming correctly right up to the point a slow generation exceeded 120s.
    • Not fixed here — verifying a correct fix (e.g. an AsyncListener deferring context cleanup until the async request actually completes, checked against Spring's actual async-dispatch context propagation for SseEmitter / ResponseBodyEmitter specifically, which differs from the Callable / DeferredResult path WebAsyncManagerIntegrationFilter covers) needs a tighter feedback loop than a ~30-100s-per-attempt model cold-start cycle allows for right now. Flagging precisely rather than guessing at a fix.
    • Workaround: in claude profile / real Claude API, response latency is far more consistent and unlikely to approach 120s, so this mostly matters for local Ollama dev testing.

    Phase 6 — Kafka Wiring + Notification Service

    Goal: All four topics live, outbox pattern on all producing services, notification-service consuming.

    Status: Complete — verified end-to-end on 2026-08-16: POST /tickets → outbox poller publishes ticket.created → notification-service consumes and writes a notification row; a synthetic chat.escalated message produced directly onto the topic was consumed by ticket-service, created a ticket, and published ticket.created with sourceConversationId set, which in turn produced a "Your chat was escalated to ticket: ..." notification. chat-service's TicketCreatedConsumer (which sets Conversation.escalatedTicketId) was not re-verified live in this pass — chat-service needs Ollama/knowledge-service running, which this check skipped — but the code path mirrors the already-verified ticket-service/notification-service consumers exactly (same header/payload handling), so it's low-risk.

    What was built:

    • [x] Kafka in docker-compose — KRaft mode (single broker, broker+controller combined), no Zookeeper (deprecated as of Kafka 3.5+)
    • [x] All four topics created via KafkaAdmin NewTopic beans, one per producing service (not relying on auto.create.topics, which is disabled cluster-wide): ticket.created + ticket.status-changed (ticket-service), document.ingested (knowledge-service), chat.escalated (chat-service)
    • [x] Outbox publishers verified on: ticket-service (live test), knowledge-service (code review — same pattern), chat-service (live test via synthetic chat.escalated message, since the poller is what turns the escalation into ticket.created)
    • [x] notification-service: Kafka consumers for ticket.created / ticket.status-changed, notifications + processed_events tables (idempotent consumption — event UUID as PK, DataIntegrityViolationException on redelivery is a clean no-op), WebSocket/STOMP push via NotificationPushService
    • [x] ticket-service.EscalationEventConsumer consumes chat.escalated, creates a ticket (idempotent on conversation_id), publishes ticket.created with sourceConversationId set
    • [x] chat-service.TicketCreatedConsumer consumes ticket.created, sets Conversation.escalatedTicketId when sourceConversationId matches — closes the loop so escalatedTicketId is no longer permanently null
    • [x] chat-service.DocumentIngestedConsumer consumes document.ingested — deliberate stub (logs only); chat-service has no retrieval cache today, so there's nothing to invalidate yet

    Decisions made during implementation:

    1. KRaft mode instead of Zookeeper. One container instead of two — meaningful on a memory-constrained dev machine, and Kafka itself has deprecated Zookeeper mode (removed in 4.0). KAFKA_OFFSETS_TOPIC_NUM_PARTITIONS dropped from the 50 default to 3 — with one broker and three consumer groups, 50 partitions was causing coordinator election storms under CPU pressure.
    2. Idempotency strategy differs by service, deliberately. notification-service uses a generic processed_events table keyed on the outbox event's UUID (it fans out to arbitrary future consumers of ticket.created / ticket.status-changed, so a generic dedupe table is the right shape). ticket-service's escalation consumer instead treats "a ticket already exists for this conversation_id" as the idempotency key — no separate dedup table needed, because the domain invariant (one ticket per escalated conversation) already gives you exactly-once creation semantics for free.
    3. Kafka headers carry eventId, not the payload. Every producer attaches the outbox event's UUID as a KafkaHeaders-style header rather than a field in the JSON payload, keeping the wire schema exactly what CLAUDE.md §6 documents (no dedup plumbing leaking into the contract).

    Deviations from plan: None from CLAUDE.md §6. Note that this phase's code was actually written and locally verified before Phase 7 (full docker-compose) — this log entry was corrected after the fact to match; an earlier commit message in this repo's history incorrectly described the outbox pollers as log-only stubs.

    Bugs found and fixed while standing up observability:

    1. Loki 3.x compactor config. retention_enabled: true without compactor.delete_request_store set is a hard config error in Loki 3.x (it wasn't in 2.x) — Loki crash-looped on startup until delete_request_store: filesystem was added.
    2. Stale Docker network after pinning its name. Adding name: tixolve-network to docker-compose.yml's network block (needed so the observability compose file can attach via external: true predictably) orphaned already-running containers on the old auto-generated network name; they kept running but became unreachable by the new network's DNS. Fixed by recreating the stack (docker-compose down --remove-orphans + removing the stale network) rather than restarting service-by-service.

    Bugs found and fixed while wiring the frontend into Docker (none of these were caught before because npm run build — as opposed to the dev server — had never been run):

    1. Keycloak client ID mismatch. keycloak.ts's default and frontend/.env both said VITE_KEYCLOAK_CLIENT=tixolve-frontend, but keycloak/realm-export.json only defines a client called tixolve-spa. This would have broken login outside of whatever environment had the correct value manually overridden. Fixed both to tixolve-spa.
    2. Unused import broke the production build. tsc -b (part of npm run build) fails on unused imports by default; KnowledgePage.tsx imported Skeleton but never used it (only SkeletonRow). The Vite dev server doesn't type-check on file save, so this shipped silently until a real build ran.
    3. IPv6/IPv4 healthcheck mismatch. The frontend container's /etc/hosts resolves localhost to ::1 first, but nginx in the nginx:1.27-alpine image only binds 0.0.0.0 (IPv4) by default. wget --spider http://localhost/ inside the healthcheck got "connection refused" even though the app was serving fine — the Java services don't hit this because Spring Boot's embedded Tomcat binds dual-stack. Fixed by pointing the healthcheck at 127.0.0.1 explicitly.

    Decisions made during implementation:

    1. Vite env vars are Docker build ARGs, not compose environment: entries. Vite inlines import.meta.env.VITE_* at build time — there's no server process reading env vars at container start the way the Java services' Spring profiles do. Changing a VITE_* value means rebuilding the frontend image, not just restarting the container. Acceptable for a single-environment local/demo setup.
    2. Frontend on host port 3000, not 80. keycloak/realm-export.json's tixolve-spa client already whitelists http://localhost:3000 in redirectUris / webOrigins (alongside the Vite dev server's 5173), so no Keycloak config change was needed to add the containerized frontend as a second valid origin.

    Two real bugs found and fixed (found while pointing the k6 scripts at the actual gateway with a real Keycloak JWT — every prior verification in this project had authenticated services directly with trusted headers, bypassing the gateway's own JWT validation entirely):

    1. Gateway JWT validation rejected every real token. jwk-set-uri and issuer-uri both read from one KEYCLOAK_URL env var pointed at the internal Docker hostname (http://keycloak:8080). JWKS fetch is a server-to-server call and correctly needs that internal address — but issuer-uri validates the token's iss claim, which Keycloak always stamps with whatever host actually issued it. Every real client (the browser SPA, k6) gets tokens from Keycloak's externally-exposed URL (http://localhost:8180), so 100% of real authenticated requests through the gateway failed with WWW-Authenticate: Bearer error="invalid_token", error_description="The iss claim is not valid". This means the core auth flow — SPA login → gateway → downstream services — has likely never actually worked outside of tests that call services directly. Fixed by splitting into KEYCLOAK_INTERNAL_URL (JWKS) and KEYCLOAK_ISSUER_URL (issuer validation), decoupled in both api-gateway/application.yml and docker-compose.yml.
    2. /api/tickets/** routing forwarded an empty path. StripPrefix=2 strips both api and tickets segments. That's correct for knowledge-service (/api/knowledge/search → /search, a different downstream path than the route's service-name segment) and chat-service (/api/chat/conversations → /conversations), but TicketController is mapped at /tickets — the same segment the route itself uses — so stripping 2 forwarded a bare /, matching nothing. Every gateway-routed ticket request 500'd. Fixed to StripPrefix=1.

    Both verified end-to-end afterward: real Keycloak token → gateway → ticket-service (full CRUD, 200/201s) and → knowledge-service (search, 200) and → chat-service (conversation creation, 201).

    k6 calibration: core-load-test.js thresholds (p(95)<800ms for ticket CRUD, p(95)<20000ms for search — wide because it calls embeddingModel.embed() and tracks Ollama's speed, not gateway/DB overhead) pass cleanly against the full stack running standalone. They failed when run alongside several extra debug containers from earlier investigation in this same session — that's real resource contention on a loaded laptop, not a script or threshold problem; confirmed by a clean re-run after freeing that headroom.

    Deviations from plan: The RAG dashboard's "Ingestion jobs by status" panel counts log lines via Loki (count_over_time({service="knowledge-service"} |= "Ingestion completed"} [5m])) rather than a dedicated status-transition counter — a reasonable proxy for now, called out as a possible follow-up in the dashboard JSON's own description field.

    Infrastructure bugs found & fixed while verifying the SPA→gateway→service path in a browser (every prior verification hit REST directly; these were masked until the browser path was truly exercised):

    1. Gateway CORS preflight was 401. globalcors YAML runs at the handler level — AFTER Spring Security. Unauthenticated OPTIONS died with 401/no CORS headers, so the SPA could not call ANY API from the browser. Fix: explicit reactive CorsConfigurationSource + .cors() in the gateway security chain (origins via app.cors.allowed-origins).
    2. Keycloak token endpoint demanded HTTPS. Docker Desktop's host→container NAT began presenting a public-range source IP (172.65.x — not RFC-1918), so realm sslRequired=external blocked HTTP token issuance. Fix: sslRequired=none on the dev realm (runtime + realm-export.json), correct for a localhost-only dev realm.
    3. /ws/** route pointed at localhost. NOTIFICATION_SERVICE_URL was never added to api-gateway's compose env → connection refused inside the container. Fixed in docker-compose.
    4. SockJS handshake 400 "Found multiple bearer tokens". The WebSocketTokenHeaderFilter promotes the query token to an Authorization header (RFC 6750 §2.3), but Spring Security's converter resolves the query param unconditionally and rejects the pair. Fix: strip the access_token query param from the URI after promotion — also stops the token leaking downstream in URLs.
