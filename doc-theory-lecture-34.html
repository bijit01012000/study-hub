    Lecture 34 — Spring @Transactional Propagation & Isolation Levels

    20 sections · 4,760 words

    Lecture 34

    Scope evidence: "Spring @Transactional Propagation & Isolation Levels Explained" (playlist map, verified). Repo folder is the transactionDemo project: OrderService with propagation demos (placeOrder(), reserveStock()), PaymentAuditService used for the REQUIRES_NEW audit example, Order and PaymentAudit entities, OrderRepository/PaymentAuditRepository, OrderController, TransactionDemoApplication, application.properties, plus the lecture notes.

    @Transactional is where declarative transaction management meets the real world: it decides how a method joins, creates, suspends, or refuses a transaction, and how concurrent transactions are allowed to see each other's data. This lecture reads the annotation attribute by attribute, then walks the propagation modes with concrete call flows, and finishes with propagation versus isolation, the rollback-only trap, and the three read phenomena. Every rule here has a name, and every name hides a trap that interviewers love to trigger.

    1. The @Transactional Attribute Reference

    @Transactional is the annotation that tells Spring how a method participates in a transaction.

    @Transactional(
    propagation = Propagation.REQUIRED,
    isolation = Isolation.READ_COMMITTED,
    timeout = 5,
    readOnly = false,
    rollbackFor = IOException.class
)

    The five important attributes and what each one is responsible for:

    Attribute Responsibility
    propagation Decides whether the method joins, creates, suspends, or rejects a transaction
    isolation Controls how concurrent transactions can observe one another's changes
    timeout Sets the maximum time allowed for the transaction
    readOnly Provides a hint that the transaction will only read data
    rollbackFor Adds exception types that should cause rollback
    • propagation is about method-to-method calls: does the callee reuse the caller's transaction or start its own?
    • isolation is about concurrency: what can two transactions running at the same time see of each other?
    • timeout, readOnly, and rollbackFor are per-transaction tuning knobs.

    Mnemonic for the five attributes: P-I-T-R-R (Propagation, Isolation, Timeout, ReadOnly, RollbackFor).

    2. Default @Transactional Behaviour

    A bare @Transactional is not "no configuration"; it is a stack of defaults.

    @Transactional
public void performOperation() {
    // Business operations
}

    The annotation uses the following defaults:

    Setting Default
    Propagation Propagation.REQUIRED
    Isolation Isolation.DEFAULT
    Read-only false
    Timeout Default of the underlying transaction infrastructure
    Rollback RuntimeException and Error
    • Default propagation: REQUIRED. If a transaction exists, join it; if no transaction exists, create one.
    • Default isolation: DEFAULT. Spring asks the underlying transaction infrastructure for its default, which is commonly determined by the database.
    • Default read-write behaviour: readOnly = false. The transaction is treated as a normal read-write transaction.
    • Default timeout: the infrastructure default. This does not mean a timeout can never occur. Timeout rules may still come from the transaction manager, database, connection pool, JDBC driver, query, or lock-acquisition settings.

    Important: A missing timeout attribute means "use the infrastructure default", not "run forever". Timeouts can still fire from the layers below Spring.

    3. Commit and Rollback Rules

    A transaction normally commits when all three conditions are satisfied:

    1. The transactional method completes normally.
    2. The transaction has not been marked as rollback-only.
    3. The actual commit operation succeeds.

    Return values such as false, null, Optional.empty(), or ResponseEntity.badRequest() do not represent transaction failure. They are ordinary Java return values, and Spring does not inspect their business meaning to decide whether to roll back.

    Rollback for Runtime Exceptions

    By default, an unchecked exception causes rollback when it escapes the transactional method.

    @Transactional
public void transfer() {
    debit();
    throw new IllegalStateException("Transfer failed");
}

    The flow is:

    RuntimeException escapes the method
        |
        v
Default rollback rule matches
        |
        v
Transaction rolls back

    Common examples matched by the default rule include IllegalArgumentException, IllegalStateException, NullPointerException, DataIntegrityViolationException, and custom subclasses of RuntimeException.

    Rollback for Error

    An Error also triggers rollback by default: OutOfMemoryError, StackOverflowError, AssertionError, and LinkageError. An Error usually represents a serious JVM or environment failure rather than an ordinary business problem, but it still matches Spring's default rollback policy.

    Checked Exception Behaviour and rollbackFor

    A checked exception does not trigger rollback under Spring's traditional default policy.

    @Transactional
public void transfer() throws TransferException {
    debit();
    throw new TransferException("Transfer failed");
}

public class TransferException extends Exception {
}

    The default flow is:

    Checked exception escapes the method
        |
        v
Default rollback rule does not match
        |
        v
Spring proceeds towards commit

    This does not mean checked exceptions are harmless; it only describes the default rollback rule. Use rollbackFor when a checked exception should cause rollback:

    @Transactional(rollbackFor = TransferException.class)
public void transfer() throws TransferException {
    debit();
    throw new TransferException("Transfer failed");
}

    Multiple types can be configured at once:

    @Transactional(
    rollbackFor = {
        TransferException.class,
        IOException.class
    }
)
public void transfer() {
    // Business operations
}

    Golden rule: normal completion commits; RuntimeException and Error roll back by default; checked exceptions commit unless you name them in rollbackFor.

    4. The Proxy Requirement

    @Transactional is normally applied through a Spring-generated proxy. Therefore, the method must be invoked through that proxy for transactional interception to occur.

    Caller --> Spring proxy --> transactional interceptor --> your method
    • If the call enters through the proxy, Spring can start, join, or suspend transactions around your method.
    • If the call bypasses the proxy (for example, a plain new, or a method calling another method on this), no interception happens and the annotation has no effect.

    Interviewer's perspective: "Why did my @Transactional method do nothing?" is almost always a proxy question - the method was called internally, not through the proxy.

    5. Propagation Modes at a Glance

    Propagation answers one central question: what should this transactional method do when it is called with or without an existing transaction?

    Propagation mode If a transaction exists If no transaction exists
    REQUIRED Join it Create a transaction
    REQUIRES_NEW Suspend it and create a new transaction Create a transaction
    SUPPORTS Join it Run without a transaction
    MANDATORY Join it Throw an exception
    NOT_SUPPORTED Suspend it and run without a transaction Run without a transaction
    NEVER Throw an exception Run without a transaction
    NESTED Create a savepoint inside it Create a transaction

    Transaction Suspension

    Suspending a transaction does not temporarily commit it. It means Spring pauses its association with the current transaction and its resources while another scope executes. The suspended transaction has neither committed nor rolled back; it resumes after the inner scope completes.

    Propagation modes that may suspend an existing transaction are:

    • REQUIRES_NEW: suspends the outer transaction and starts a new transaction.
    • NOT_SUPPORTED: suspends the outer transaction and runs without a transaction.

    Mnemonic for the modes: REQUIRED joins, REQUIRES_NEW owns, NESTED saves a spot, MANDATORY demands, NEVER refuses, NOT_SUPPORTED ignores, SUPPORTS follows.

    6. Propagation.REQUIRED: Join or Create

    REQUIRED is Spring's default propagation mode.

    @Transactional
public void placeOrder() {
    // Business operations
}

    It is equivalent to:

    @Transactional(propagation = Propagation.REQUIRED)
public void placeOrder() {
    // Business operations
}

    Its rule is simple: if a transaction exists, join it; if no transaction exists, create one.

    Joining an Existing Transaction

    Consider an outer method that calls three transactional services:

    @Transactional
public void checkout() {
    orderService.createOrder();
    inventoryService.reserveStock();
    paymentService.createPaymentRecord();
}

    If all three inner methods use REQUIRED, they participate in the same physical transaction:

    Transaction A
|-- createOrder()
|-- reserveStock()
`-- createPaymentRecord()

    They normally share the same physical database transaction, JDBC connection, transaction-bound EntityManager, persistence context, and final commit-or-rollback decision. The inner methods create separate logical transaction scopes, but they do not create independent physical transactions.

    Inner Transaction Settings Do Not Override the Outer

    Suppose the outer method declares isolation = Isolation.READ_COMMITTED, timeout = 30, and the inner reserveStock() declares propagation = REQUIRED, isolation = Isolation.SERIALIZABLE, timeout = 5. The inner method joins an already-running physical transaction, so it cannot normally replace that transaction's characteristics:

    Effective physical transaction:
Isolation -> READ_COMMITTED   (outer wins)
Timeout   -> 30 seconds       (outer wins)

    Outer Failure After Inner Success

    @Transactional
public void placeOrder() {
    orderRepository.save(order);
    inventoryService.reserveStock();

    throw new IllegalStateException(
        "Failure after inventory reservation"
    );
}

    Even if reserveStock() completes successfully, both operations roll back because they belong to the same physical transaction. An inner REQUIRED method cannot commit independently.

    When to Use REQUIRED

    REQUIRED is appropriate when all participating operations represent one business unit of work and must share one final outcome. Typical examples: placing an order, transferring money, creating an invoice, registering a student, reserving inventory, cancelling a booking, updating employee information.

    7. The rollback-only Trap: UnexpectedRollbackException

    A subtle problem occurs when an inner REQUIRED method fails but the outer method catches the exception:

    @Transactional
public void placeOrder() {
    orderRepository.save(new Order());
    try {
        inventoryService.reserveStock();
    } catch (InsufficientStockException exception) {
        System.out.println("Stock reservation failed");
    }
    System.out.println("Order method completed normally");
}

    The execution flow is:

    1. The outer method starts Transaction A.
    2. reserveStock() joins Transaction A.
    3. reserveStock() throws a RuntimeException.
    4. Its transactional interceptor marks Transaction A as rollback-only.
    5. The outer method catches the Java exception.
    6. The outer method completes normally and attempts to commit.
    7. Transaction A cannot commit because it is already rollback-only.
    8. Spring rolls it back and throws UnexpectedRollbackException.

    Catching the original exception prevents it from propagating further in Java. It does not remove the rollback-only state already placed on the shared transaction.

    Inner REQUIRED fails -> interceptor sets rollback-only on shared tx
        |
        v
Outer catches exception and "succeeds"
        |
        v
Commit attempt fails -> Spring rolls back -> UnexpectedRollbackException

    Important: Catching an inner exception cannot resurrect a transaction that has already been marked rollback-only. The shared physical transaction remembers.

    8. Propagation.REQUIRES_NEW: Suspend and Resume

    REQUIRES_NEW always executes the method inside a new physical transaction. If an outer transaction exists: suspend it, create a separate transaction, and after the inner transaction completes, resume the outer transaction.

    @Service
@RequiredArgsConstructor
public class OrderService {

    private final PaymentAuditService paymentAuditService;

    @Transactional
    public void placeOrder() {
        // Transaction A
        paymentAuditService.recordAttempt();
        // Transaction A resumes
    }
}

    @Service
@RequiredArgsConstructor
public class PaymentAuditService {

    private final PaymentAuditRepository paymentAuditRepository;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordAttempt() {
        paymentAuditRepository.save(new PaymentAudit());
    }
}

    The flow is:

    1. placeOrder() starts Transaction A.
    2. recordAttempt() is invoked through the PaymentAuditService proxy.
    3. Spring suspends Transaction A.
    4. Spring starts Transaction B.
    5. recordAttempt() executes inside Transaction B.
    6. Transaction B commits or rolls back.
    7. Spring releases Transaction B's resources.
    8. Spring resumes Transaction A.

    Separate Physical Resources

    In a typical single-database JPA application, the transactions use separate resources:

    Outer Transaction A
|-- EntityManager A
|-- Persistence Context A
`-- JDBC Connection A

Inner Transaction B
|-- EntityManager B
|-- Persistence Context B
`-- JDBC Connection B

    Because the transactions are independent, the inner transaction may define its own isolation level, timeout, read-only status, and rollback rules.

    Inner Commits, Outer Rolls Back

    @Transactional
public void outer() {
    orderRepository.save(...);
    paymentAuditService.saveAudit();
    throw new RuntimeException();
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void saveAudit() {
    paymentAuditRepository.save(...);
}

    Expected result:

    Audit transaction   -> commits
Order transaction   -> rolls back

    The audit remains committed because it completed in a separate physical transaction.

    Inner Rolls Back, Outer Continues

    @Transactional
public void outer() {
    orderRepository.save(...);
    try {
        paymentAuditService.saveAuditAndFail();
    } catch (RuntimeException exception) {
        System.out.println("Audit failed");
    }
    order.markCompleted();
}

    The inner transaction can roll back without marking the outer transaction as rollback-only. If the exception is caught and the outer transaction remains valid, the outer transaction can still commit. If the exception is not caught, it reaches the outer transactional boundary; the outer transaction may then roll back because it received a RuntimeException, not because the two physical transactions share rollback state.

    9. REQUIRES_NEW in Practice: Audit Logging and Visibility

    Visibility of Outer Uncommitted Data

    Suppose Transaction A inserts a new order but has not committed it:

    Transaction A:
INSERT order id = 101
Status: uncommitted

    Transaction B starts through REQUIRES_NEW and attempts to load that order:

    @Transactional(propagation = Propagation.REQUIRES_NEW)
public void recordOrderAudit(Long orderId) {
    Order order = orderRepository.findById(orderId)
        .orElseThrow();
}

    Transaction B generally cannot assume that it can see Transaction A's uncommitted insert. An independent transaction should not depend casually on uncommitted state owned by the suspended outer transaction.

    Common Use Case: Audit Logging

    REQUIRES_NEW is commonly used when an audit record must be preserved even if the main business transaction fails. It should be used deliberately because it needs an additional physical transaction and typically another database connection while the outer resources remain suspended.

    Important: REQUIRES_NEW is a resource decision, not just a code convenience. It consumes a second connection and suspends the outer transaction until the inner one finishes.

    10. Other Propagation Modes: SUPPORTS, MANDATORY, NOT_SUPPORTED, NEVER

    Propagation.SUPPORTS

    If a transaction exists    -> join it
If no transaction exists   -> run without a transaction

    SUPPORTS means that a transaction is welcome but not required. It can be suitable for read helper methods, calculations that may use transaction-bound entities, methods called both inside and outside larger workflows, and infrastructure helpers that do not require atomic writes. Its behaviour can change depending on the caller, so it should not be used for a write operation that requires a guaranteed transactional boundary.

    Propagation.MANDATORY

    If a transaction exists    -> join it
If no transaction exists   -> throw an exception

    MANDATORY creates a clear contract: the caller must establish the transaction. For example, stock reservation may be designed only as a building block of a larger operation such as placing an order or replacing an order item; it should never execute independently.

    @Transactional(propagation = Propagation.MANDATORY)
public void reserveStock() {
    // Business operations
}

    Calling this method without an active transaction causes an exception. Calling it from a transactional service makes it join the existing transaction.

    MANDATORY versus REQUIRED:

    REQUIRED   -> join an existing transaction or create one
MANDATORY  -> join an existing transaction or fail

    Use REQUIRED when the method can represent an independent business operation. Use MANDATORY when it should only be part of a transaction defined by its caller.

    Propagation.NOT_SUPPORTED

    If a transaction exists    -> suspend it and run without a transaction
If no transaction exists   -> run without a transaction

    The method always executes non-transactionally.

    Propagation.NEVER

    If a transaction exists    -> throw an exception
If no transaction exists   -> run without a transaction

    NEVER establishes the opposite contract to MANDATORY: the method must not execute inside a transaction.

    11. Propagation.NESTED: Savepoints

    NESTED normally does not create a second independent physical transaction. It uses the existing physical transaction and creates a database savepoint.

    Suppose Transaction A has completed two operations:

    Operation 1
Operation 2
SAVEPOINT S1
Operation 3
Operation 4

    If a failure occurs after S1, the transaction can execute:

    ROLLBACK TO SAVEPOINT S1;

    This discards Operations 3 and 4 while retaining Operations 1 and 2. The outer transaction remains active and still owns the final commit-or-rollback decision.

    If no outer transaction exists, NESTED behaves like REQUIRED and creates a new transaction, because there is no existing transaction in which to create a savepoint.

    NESTED requires support from the chosen transaction manager and underlying resource. It is commonly associated with JDBC savepoints and should not be assumed to work identically in every JPA configuration.

    Interviewer's perspective: NESTED is the mode where candidates most often guess. The correct sentence is "a savepoint inside the existing physical transaction", not "a second independent transaction".

    12. Isolation and the Three Read Phenomena

    Propagation controls the relationship between transactional method calls. Isolation controls the relationship between transactions executing concurrently. Concurrent execution is unavoidable because many users may place orders, transfer money, book seats, update inventory, and read reports at the same time.

    The database must balance two competing objectives:

    Correctness  <->  Concurrency

    Stronger isolation offers more protection but can increase blocking, retries, deadlocks, and resource usage. Weaker isolation allows more concurrency but exposes the application to more anomalies.

    Dirty Read

    A dirty read occurs when one transaction reads a change made by another transaction that has not committed.

    Initial state (Account A = 10,000):

    Time Transaction T1 Transaction T2
    1 Begins
    2 Updates balance to 2,000
    3 Begins
    4 Reads balance as 2,000
    5 Rolls back
    6 Balance returns to 10,000 Continues using 2,000

    T2 used a value that never became part of the committed database state.

    Non-Repeatable Read

    A non-repeatable read occurs when a transaction reads the same row twice and receives different committed values.

    Initial state (Account A = 10,000):

    Time Transaction T1 Transaction T2
    1 Begins
    2 Reads balance as 10,000
    3 Begins
    4 Updates balance to 8,000
    5 Commits
    6 Reads the same row again
    7 Receives 8,000

    The second value is not dirty because T2 committed it. The problem is that the same row did not produce a repeatable value inside T1.

    Phantom Read

    A phantom read concerns a set of rows selected by a condition rather than a change to one previously read row. T1 runs:

    SELECT *
FROM employee
WHERE salary > 100000;

    It receives three employees. T2 then inserts a new matching row and commits:

    INSERT INTO employee(name, salary)
VALUES ('Employee D', 120000);

    When T1 repeats the original query, it receives four employees. The additional matching row is the phantom.

    Time Transaction T1 Transaction T2
    1 Begins
    2 Finds 3 matching employees
    3 Inserts a matching employee
    4 Commits
    5 Repeats the query
    6 Finds 4 matching employees

    How Databases Implement Isolation

    Databases do not necessarily lock an entire table for every transaction. Depending on the database and isolation level, they may use row and range locks, shared and exclusive locks, Multi-Version Concurrency Control (MVCC), consistent snapshots, predicate locking, conflict detection, or transaction aborts and retries. The same isolation level may therefore have different performance characteristics and edge-case behaviour across database systems.

    13. Spring Isolation Levels Compared

    Spring provides the following options: Isolation.DEFAULT, Isolation.READ_UNCOMMITTED, Isolation.READ_COMMITTED, Isolation.REPEATABLE_READ, and Isolation.SERIALIZABLE.

    Isolation.DEFAULT is not an additional database isolation level created by Spring. Spring does not request a different isolation level; it uses the default of the underlying transaction infrastructure.

    PostgreSQL DEFAULT  -> READ COMMITTED
MySQL InnoDB        -> REPEATABLE READ

    The comparison table an interviewer expects:

    Isolation level Dirty read Non-repeatable read Phantom read
    READ_UNCOMMITTED Possible Possible Possible
    READ_COMMITTED Prevented Possible Possible
    REPEATABLE_READ Prevented Prevented Standard permits it; the actual database may prevent it
    SERIALIZABLE Prevented Prevented Prevented

    READ_UNCOMMITTED

    The weakest standard isolation level. A transaction may observe another transaction's uncommitted changes.

    @Transactional(isolation = Isolation.READ_UNCOMMITTED)
public void generateReport() {
    // Business operations
}

    Dirty read          -> Possible
Non-repeatable read -> Possible
Phantom read        -> Possible

    It is rarely suitable for business operations because decisions may be based on data that is later rolled back.

    READ_COMMITTED

    A transaction cannot read another transaction's uncommitted changes.

    @Transactional(isolation = Isolation.READ_COMMITTED)
public void performOperation() {
    // Business operations
}

    Dirty read          -> Prevented
Non-repeatable read -> Possible
Phantom read        -> Possible

    Each statement may see the latest data committed before that statement begins, so two reads inside one transaction can still produce different results.

    REPEATABLE_READ

    In the standard isolation model:

    Dirty read          -> Prevented
Non-repeatable read -> Prevented
Phantom read        -> May occur

    Actual behaviour depends on the database implementation. For example, an MVCC-based database may prevent some phantom-read scenarios even though the SQL standard permits them at this level.

    SERIALIZABLE

    SERIALIZABLE is the strongest standard isolation level. Concurrent transactions must produce a result equivalent to some valid serial order. For two transactions, the result should be equivalent to either "T1 completes, then T2 completes" or "T2 completes, then T1 completes".

    The transactions may still overlap physically. The database can enforce serializable behaviour using locks, MVCC, predicate or range locks, conflict detection, or transaction abortion and retry.

    Dirty read            -> Prevented
Non-repeatable read   -> Prevented
Phantom read          -> Prevented
Serialization anomaly -> Prevented

    14. Choosing the Right Isolation Level

    Do not choose the strongest isolation level automatically. Choose the weakest level that still preserves the correctness rules of the business operation. Consider:

    • What incorrect outcome can occur if data changes during the transaction?
    • Does the method read the same row or query result more than once?
    • Can two users update the same business data concurrently?
    • Can the operation tolerate a retry?
    • What are the database's actual guarantees at the chosen level?
    • Would optimistic or pessimistic locking solve the specific problem more precisely?

    Golden rule: isolation is a trade-off, not a trophy. Pick the weakest level that keeps the business invariant true, and let the database's real guarantees - not the label - decide.

    15. Myth vs Reality

    Myth Reality
    "Catching the inner exception prevents rollback" Only if propagation created a separate transaction; a shared REQUIRED transaction is already rollback-only, so commit throws UnexpectedRollbackException
    "REQUIRES_NEW just starts a new logical scope" It suspends the outer transaction and starts a new physical transaction with its own connection and persistence context
    "A REQUIRED inner method can override outer isolation/timeout" It joins the existing physical transaction, so the outer settings win
    "readOnly = true forbids all writes" It is a hint to the infrastructure, not an enforcement guarantee
    "No timeout means the transaction never times out" Spring falls back to the infrastructure default; timeouts can still come from the DB, pool, or driver
    "Checked exceptions roll back by default" They do not; use rollbackFor to include them
    "A private/self-invoked @Transactional method still works" Interception needs the proxy; bypassing it disables the annotation
    "SERIALIZABLE means transactions actually run one after another" They may overlap physically; the database only guarantees an equivalent serial result

    16. Common Trap Questions

    Trap 1 - "Catching the inner exception fixes the rollback." Verdict: False. With REQUIRED, the inner failure marks the shared transaction rollback-only, and the outer commit then throws UnexpectedRollbackException.

    Trap 2 - "REQUIRES_NEW is only a new logical transaction scope." Verdict: False. It suspends the outer transaction and creates an independent physical transaction with separate resources.

    Trap 3 - "The inner REQUIRED method can set its own isolation and timeout." Verdict: False. It joins the already-running physical transaction; the outer isolation and timeout remain in effect.

    Trap 4 - "readOnly = true blocks writes." Verdict: Misleading. It is a hint that the transaction only reads; enforcement is not guaranteed.

    Trap 5 - "A missing timeout attribute means no timeout." Verdict: False. Spring uses the default of the underlying transaction infrastructure, and lower layers can still time the operation out.

    Trap 6 - "Checked exceptions roll back like runtime exceptions." Verdict: False. Checked exceptions commit by default; add them with rollbackFor.

    Trap 7 - "Calling a @Transactional method from the same class still gets a transaction." Verdict: False. The call bypasses the proxy, so no transactional interception happens.

    17. Points to Remember

    1. @Transactional attributes: propagation, isolation, timeout, readOnly, rollbackFor (mnemonic P-I-T-R-R).
    2. Defaults: propagation = REQUIRED, isolation = DEFAULT, readOnly = false, infrastructure timeout, rollback on RuntimeException and Error.
    3. A transaction commits only when the method completes normally, the transaction is not rollback-only, and the commit itself succeeds.
    4. false, null, Optional.empty(), and ResponseEntity.badRequest() are ordinary return values; Spring does not roll back because of them.
    5. Checked exceptions commit by default; use rollbackFor to force rollback.
    6. @Transactional works through a Spring proxy, so the method must be invoked through the proxy.
    7. REQUIRED joins or creates; REQUIRES_NEW suspends and starts a new physical transaction; NESTED creates a savepoint inside the existing transaction.
    8. An inner REQUIRED failure marks the shared transaction rollback-only, and a later commit throws UnexpectedRollbackException.
    9. Suspending a transaction neither commits nor rolls it back; it pauses its association and resumes after the inner scope.
    10. Isolation trades correctness for concurrency; pick the weakest level that preserves the business rules, and remember the database implementation decides the real behaviour.

    18. Likely Interview Questions

    Question Crisp Answer
    What does @Transactional do? Declares transactional boundaries around a method via a Spring proxy, using propagation, isolation, timeout, readOnly, and rollbackFor.
    What is the default propagation? REQUIRED: join an existing transaction or create one.
    What is the default rollback rule? RuntimeException and Error roll back; checked exceptions do not unless listed in rollbackFor.
    REQUIRED vs REQUIRES_NEW? REQUIRED joins the current transaction; REQUIRES_NEW suspends it and starts a new physical transaction.
    REQUIRED vs MANDATORY? REQUIRED creates a transaction if none exists; MANDATORY throws if none exists.
    What does NESTED do? Creates a database savepoint inside the existing transaction when supported; behaves like REQUIRED with no outer transaction.
    What is a dirty read? Reading uncommitted data written by another transaction that may later roll back.
    Non-repeatable vs phantom read? Non-repeatable: the same row returns different committed values; phantom: the same condition returns a different set of rows.
    Which isolation prevents dirty reads only? READ_COMMITTED prevents dirty reads but allows non-repeatable and phantom reads.
    What is Isolation.DEFAULT? Spring uses the underlying infrastructure's default, not a level Spring invents (PostgreSQL -> READ COMMITTED, MySQL InnoDB -> REPEATABLE READ).
    Why does UnexpectedRollbackException occur? An inner REQUIRED method marked the shared transaction rollback-only, so the outer commit could not succeed and Spring rolled back.
    What does transaction suspension mean? Pausing the association with the current transaction and its resources without committing or rolling back.

    19. Final Summary

    @Transactional attributes: propagation, isolation, timeout, readOnly, rollbackFor
        |
        v
Defaults: REQUIRED / DEFAULT / readOnly=false / infra timeout / rollback RuntimeException + Error
        |
        v
Commit needs: normal completion + not rollback-only + successful commit
        |
        v

        |

    REQUIRED      -> join existing or create
    REQUIRES_NEW  -> suspend outer, create new physical transaction, resume outer
    NESTED        -> savepoint inside the existing transaction when supported
    SUPPORTS      -> join if present, else no transaction
    MANDATORY     -> join or throw
    NOT_SUPPORTED -> suspend and run non-transactionally
    NEVER         -> throw if a transaction exists
        |
        v
Rollback-only trap: inner REQUIRED failure + outer catch -> UnexpectedRollbackException
        |
        v
Isolation: READ_UNCOMMITTED < READ_COMMITTED < REPEATABLE_READ < SERIALIZABLE
        |
        v
Phenomena: dirty read -> non-repeatable read -> phantom read
    • Propagation decides the relationship between transactional method calls; isolation decides the relationship between concurrent transactions.
    • REQUIRED shares one physical transaction, so one failure can roll back everything and a caught exception cannot clear the rollback-only marker.
    • REQUIRES_NEW buys independence with a second physical transaction and connection, and the outer transaction resumes only after the inner one finishes.
    • NESTED is a savepoint, not a second independent transaction, and it depends on transaction-manager and resource support.
    • Isolation is a correctness-versus-concurrency trade-off, and the actual behaviour depends on both the chosen level and the database implementation.

    One-line takeaway: @Transactional is easy to annotate and hard to master - propagation decides who owns the transaction, isolation decides what concurrent transactions may see, and the proxy is the silent gate that makes either one work.
