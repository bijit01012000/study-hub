      LLMOps, monitoring and deployment

      0 sections · 4,052 words

      Module 14 · 9 questions · 1 practical drill

      Operate a service with no simple correctness signal.

      Q14.1 — Walk me through tracing one request through retrieval, rerank, generation and a tool call, end to end.

      Weak answer: "We log the request with an ID, plus the response and latency. If something breaks we look up that ID in our logging tool to see what happened."

      Why it fails: - One log line covers four distinct stages, so a failure has nothing specific to attach to. - No document ids, prompt version or model id are captured, so a bad rerank or drift has no cause to point to.

      Instant rejection: - Cannot name what a retrieval span should carry versus a generation span. - Treats a request id as the same thing as a trace across stages.

      Model answer: 1. On our code-search copilot, one trace id covers four spans: retrieval, rerank, generation, and a tool call span when the model opens a file. 2. The retrieval span carries the query text, the top-k document ids and their similarity scores, so I can see exactly what came back. 3. The rerank span carries the same ids after reordering plus how many were dropped, since a reranker once quietly returned eight instead of twenty. 4. The generation span carries the prompt version hash, the model id and version string, and token counts, because our provider updates models in place. 5. We trace 100% of tool-call requests since they are consequential, and sample 10% of plain Q&A, because full tracing roughly doubled our logging bill.

      Follow-ups: 1. TECHNICAL — A user reports a wrong tool call happened. What do you check first, second, third? · Whether specific spans are named in order, retrieval, rerank, generation, tool call, not just 'the logs'. 2. FAILURE — Two requests five minutes apart get different answers. What must your trace show? · Whether model id, prompt version and doc ids are captured, since any could explain it. 3. MEASUREMENT — What does full tracing cost per request, and would you sample it? · Whether tracing overhead and storage cost are weighed, not just the design in the abstract. 4. FAILURE — A reranker quietly returns fewer documents than asked, for weeks. How does tracing catch that? · Whether spans carry counts and ids, so a silent drop is visible without knowing to look.

      Tip: If you've added correlation ids or structured spans across services to debug a multi-step failure, that is the same instinct this question wants. Don't claim you've traced an LLM pipeline. Say you've built structured, per-stage logging to debug a multi-step system before.

      Numbers worth quoting: - One span per pipeline stage - Doc ids and scores per span - 100% tool calls, 10% plain Q&A - Model id pinned per response

      Q14.2 — Your feature has no pass or fail test suite. What do you actually monitor once it is live?

      Weak answer: "We watch latency, error rate and token spend on a dashboard, plus uptime. If those look healthy we're generally in good shape."

      Why it fails: - Every metric named is infrastructure. None of them says whether the answers are actually good. - A service can be fast, cheap and error-free while confidently returning wrong answers to everyone.

      Instant rejection: - No proxy for quality at all, nothing about refusals, regenerations or corrections. - Cannot name a signal specific to this product, only a generic infra list.

      Model answer: 1. On our code-review bot, latency and errors are necessary but say nothing about whether reviews are useful, so I track a separate set of cheap proxies. 2. Refusal and hedge rate matters most. A spike usually means something upstream changed and the model got uncertain, not that code quality dropped. 3. Comment count and length per pull request matter too. A collapse to near zero comments on a real diff is a cheap, strong warning sign. 4. The product-specific one is suggestion accept rate, how often an author applies the bot's diff, our closest thing to ground truth without labelling. 5. These are not a substitute for the labelled golden-set eval run before shipping a change. That is Module 8's territory, a different exercise entirely.

      Follow-ups: 1. TECHNICAL — Latency and errors are green but the model got worse at one question type. What moves? · Whether any quality-adjacent signal exists, since infra metrics are blind to this. 2. MEASUREMENT — What is your regeneration rate, and what does a spike tell you that errors do not? · Whether user-behaviour proxies, regenerate, edit, abandon, are tracked as quality signals. 3. TECHNICAL — For an internal code-review bot, name a proxy specific to that product, not a generic one. · Whether the candidate derives a product-specific proxy instead of reciting a generic list. 4. TRADEOFF — A proxy signal moves. How do you tell a real regression from a shift in what users ask? · Whether a proxy move is confirmed, not just alerted on and acted on blind.

      Tip: If you've watched user behaviour, like retries, abandons or manual overrides, as a proxy for a system with no clean pass or fail signal, say that. Don't claim you've monitored an LLM in production. Say you've built proxy metrics for a system you could not directly grade before.

      Numbers worth quoting: - Infra metrics can't show quality - Regeneration rate as a proxy - Accept rate near ground truth - Confirm before acting on a spike

      Q14.3 — Your model provider deprecates the version you run in production. What do you actually do?

      Weak answer: "We'd just switch to the version they recommend, newer is usually better anyway, so we update the config name and redeploy."

      Why it fails: - Treats a forced migration as a non-event, when a successor model can change output format, refusals and latency. - No evaluation gate before the swap reaches production, and no deadline or fallback plan mentioned.

      Instant rejection: - No mention of pinning an exact version in the first place, or why that matters. - Assumes the deadline and the outcome are entirely out of their hands.

      Model answer: 1. This happened on a document-summarisation tool. The provider gave 90 days notice a version would retire, and I now track that on a calendar, not an inbox. 2. We pin an exact model version string rather than an alias like latest, so nothing changed the moment the notice went out, and history shows what ran when. 3. The response was running the replacement through the full regression suite, broken down by document type, not just the aggregate pass rate. 4. Aggregate looked fine but legal-contract summaries got more verbose and dropped a clause type, so we fixed the prompt for that type and reran the suite. 5. We staged the cutover at 10% of traffic, watched it, then rolled out fully three days before the old version went dark, with a second provider tested as fallback.

      Follow-ups: 1. TRADEOFF — The new model passes on average but regresses on 3% of traffic. Do you ship it? · Whether an aggregate pass is enough, or segment-level regression is checked first. 2. FAILURE — How would you know a deprecation was coming, not find out the week of cutover? · Whether provider notices are tracked proactively, not discovered by an outage. 3. TECHNICAL — Why pin an exact model version instead of always pointing at the latest? · Whether unpinned references mean silent behaviour change with no deploy on your side. 4. TRADEOFF — The deadline is in four days and the replacement isn't clearing your eval bar. Options? · Whether real fallbacks exist, another provider, smaller scope, an extension, not panic.

      Tip: If you've pinned a dependency version and tracked its deprecation calendar instead of always pointing at latest, that is the same discipline. Don't claim you've handled a model deprecation. Say you've managed a forced dependency upgrade against a hard vendor deadline before.

      Numbers worth quoting: - Pin exact versions, not latest - 90 day deprecation notice - Check pass rate by segment - Stage cutover before old version

      Q14.4 — You believe a new prompt or model version is better, not forced. How do you get it into production safely?

      Weak answer: "We test the new prompt against a handful of examples, then update the config value live. Prompts aren't code, so we skip the deploy pipeline."

      Why it fails: - "Push the change directly" sends the new version to 100% of traffic instantly, no way to catch a regression first. - "Prompts aren't code" is stated as a virtue, when it is exactly what removes review, CI and rollback in one move.

      Instant rejection: - No staged exposure at all, the change is all or nothing on day one. - No record of which version served which response, so a complaint cannot be attributed later.

      Model answer: 1. On our search feature I treat a prompt change like a code change, even though it ships through a config table ops can edit directly. 2. A change is routed to 10% of query traffic behind a version flag first, with the previous version still serving the other 90%. 3. I watch that slice against our proxy signals, regeneration rate, escalation rate, for a full day to cover normal traffic patterns before expanding. 4. I ship one change at a time. Bundling a prompt tweak with a model bump once cost us a week untangling which one caused a regression. 5. Every response logs the exact version id that produced it, so a complaint from the rollout window can be traced to the new slice or the old one.

      Follow-ups: 1. TECHNICAL — What fraction of traffic sees the new version first, and what has to stay healthy to expand it? · Whether a staged rollout with explicit gating metrics exists, or it's all-or-nothing. 2. TRADEOFF — You run a model upgrade and a prompt tweak the same week. Which caused the metric to move? · Whether changes ship and are attributed one at a time, not bundled. 3. FAILURE — Your rollout queue backs up during a spike. What breaks first? · Whether the rollout mechanism itself has been stress-tested, not just designed on paper. 4. MEASUREMENT — What's your gate for expanding from 10% to 100%, a time window or a metric threshold? · Whether expansion is decided by a measured signal, not a calendar.

      Tip: If you've shipped a config or feature-flag change behind a percentage rollout instead of to everyone at once, that is the same mechanism. Don't claim you've staged a prompt rollout. Say you've used traffic splitting or a canary release for a risky config change before.

      Numbers worth quoting: - 10% first, expand on signal - One change at a time, always - Version id logged per response - Watch a full day before expanding

      Q14.5 — Nobody's labelled anything, no user complained, but answers seem quietly worse. How do you catch that?

      Weak answer: "We'd wait for user feedback or support tickets, and spot-check a few recent responses manually to see if they still look reasonable."

      Why it fails: - Waiting for complaints is the absence of detection, and the question already rules that signal out. - No proxy metric named that moves on its own and prompts investigation before a user notices.

      Instant rejection: - "Spot-check manually" isn't triggered by anything and depends on someone deciding to look that day. - No baseline or threshold, so any single noisy day would be read as a crisis.

      Model answer: 1. On our document-QA tool I track a small set of signals against a rolling baseline, because nobody grades anything day to day. 2. Citation rate, the share of answers with a verifiable source reference, has caught a real issue twice. A healthy pipeline sits near 90%. 3. The second time, citation rate slid to 76% over five days with nothing in our deploy log. The model id had, it turned out, changed under us. 4. I also track regeneration rate and answer length, since a model getting quietly hedgier tends to get longer and vaguer at the same time. 5. Before acting I check whether the query mix itself shifted, then pull twenty flagged transcripts by eye to confirm before escalating to a labelled eval.

      Follow-ups: 1. TECHNICAL — Name three signals you'd track continuously that need nobody to label anything. · Whether concrete unsupervised proxies exist, not a fallback to manual review. 2. FAILURE — Citation rate drops from 92% to 78% in a week, no code change on your side. First hypothesis? · Whether the candidate connects an unexplained metric shift to provider-side drift. 3. TRADEOFF — How do you tell drift in the model apart from drift in what users are asking? · Whether input-distribution shift is treated as a confound, not ignored. 4. MEASUREMENT — What's the false-positive cost of this monitoring, and how do you stop it crying wolf? · Whether alerts need thresholds and confirmation, not raw sensitivity.

      Tip: If you've watched an error rate or a support-ticket rate drift against a baseline with no one grading individual cases, that is this instinct. Don't claim you've caught silent model drift. Say you've tracked an unsupervised proxy metric to catch a slow regression before.

      Numbers worth quoting: - Citation rate near 90% baseline - Length and hedging shift together - Confirm with a manual sample first - Escalate to labelled eval only then

      Q14.6 — A prompt shipped through config this morning, not a deploy, and things got worse. Roll it back?

      Weak answer: "We'd go into the config and change the prompt text back to what it was before. Since it's not a code deploy, we don't wait for a build."

      Why it fails: - "Back to what it was before" assumes someone has the exact old text, true only if the prompt was versioned somewhere. - No confirmation that the rollback reached production and actually improved the proxy signals.

      Instant rejection: - No version history for prompts at all, rollback means reconstructing text from memory or a chat message. - No process fix, this same failure can clearly happen again the same way.

      Model answer: 1. We treat the config-stored prompt as a versioned artefact even though it ships outside our deploy pipeline. Every version has a hash and is retained. 2. Rollback means flipping a pointer to the previous version id, the same mechanism used for staged rollout, just run in reverse. 3. I didn't close the incident on the revert alone. I watched citation rate and regeneration rate for the next hour to confirm they actually recovered. 4. This was the second same-day, full-traffic prompt incident, because the config path skips the review a code change gets by default. 5. So the config system now requires the same version-then-10%-then-expand path as a model change, keeping the speed but not the blast radius.

      Follow-ups: 1. TECHNICAL — Where does 'what it was before' come from, is there version history for prompts? · Whether prompts are versioned, or rollback depends on memory. 2. MEASUREMENT — How do you confirm the rollback actually fixed it, rather than assuming the revert worked? · Whether proxy signals are watched post-rollback, not closed on faith. 3. FAILURE — Second time a bad prompt reached 100% of traffic before anyone noticed. What changes now? · Whether the candidate closes the loop, or treats each incident as isolated. 4. TRADEOFF — What's genuinely harder here than rolling back a bad code deploy, and what's easier? · Whether the candidate names what a config artefact loses, review and CI, and gains, speed.

      Tip: If you've reverted a feature flag or a config value to a known-good version and then watched metrics recover, that is the same discipline. Don't claim you've rolled back a live prompt. Say you've reverted a risky config change and verified recovery against real metrics before.

      Numbers worth quoting: - Prompt hash versioned, always - Rollback is a pointer flip - Confirm recovery for an hour - Second incident forces a fix

      Q14.7 — Your provider is rate-limiting you, or is down. What happens to your feature, and what should happen?

      Weak answer: "If we hit a rate limit we retry, and if the provider is down the feature just errors until it comes back. It's their infrastructure, not ours."

      Why it fails: - "We retry" with no backoff detail risks hammering the same endpoint and making a rate limit worse. - "Not something we control" abandons queueing, caching and degraded responses, all of which are in the candidate's own system.

      Instant rejection: - No distinction between a rate limit, which is manageable with backpressure, and a genuine outage. - No degraded mode considered, an outage simply becomes a full outage of the feature too.

      Model answer: 1. On our document pipeline I treat a 429 and a 5xx differently. A rate limit gets exponential backoff with jitter and a local queue in front of the call. 2. That queue also lets me prioritise, interactive user requests jump ahead of an overnight bulk job competing for the same quota. 3. A genuine outage trips a circuit breaker. After a run of failures I stop calling the provider for a cooldown window instead of retrying into it. 4. During that window the feature degrades visibly, queued items show as delayed, and the interactive path serves the last good result, not an error page. 5. We keep a second provider configured but I don't fail over automatically, our prompt was tuned against one model's output shape, that's a manual call.

      Follow-ups: 1. TECHNICAL — Retry with what backoff, and what stops every client retrying in lockstep? · Whether exponential backoff with jitter is understood, not naive immediate retry. 2. FAILURE — The provider is down for twenty minutes. What does the user see during that window? · Whether a degraded-mode experience exists, or the feature just fails visibly. 3. TRADEOFF — You're rate-limited, not down. Does every request get treated equally, or does something get shed? · Whether requests are prioritised under quota pressure, not treated uniformly. 4. TRADEOFF — Would you fail over to a second provider automatically? What has to be true first? · Whether failover is known to need a validated, compatible output contract, not a spare key.

      Tip: If you've added retry with backoff, a queue, or a circuit breaker for a flaky downstream dependency, that is the same design instinct. Don't claim you've handled a model provider outage. Say you've built graceful degradation for a third-party API failure before.

      Numbers worth quoting: - Backoff with jitter, not raw retry - Queue absorbs bursts, doesn't drop - Circuit breaker stops the - hammering - Failover needs a validated contract

      Q14.8 — How would you compare two model versions before committing, without exposing every user to the worse one?

      Weak answer: "We'd run the new model for a couple of weeks, see how it feels next to the old one, then decide which to keep based on how it seems."

      Why it fails: - "See how it feels" names no metric, so nothing but impression decides a winner. - No shadow-mode option for a model nobody trusts yet, and no stopping rule to end the comparison.

      Instant rejection: - No control group, only the new model is watched, with nothing run under the same conditions to compare against. - Assumes a live split is the only option, with no zero-risk way to test first.

      Model answer: 1. For a model I'm not ready to trust, I start in shadow mode, it processes a copy of live traffic, the response is logged, and no user ever sees it. 2. I compare it against the incumbent's actual served response on the same requests using the label-free proxies from Q14.5, since I still have no labels. 3. On a search-ranking assistant, shadow mode surfaced a higher refusal rate on ambiguous queries that an offline eval's small sample had missed entirely. 4. Once shadow looks competitive I move to a real A/B split, a defined 10% actually served, with the win condition pre-registered before the test starts. 5. It came in faster and cheaper with citation rate within noise of the incumbent, that combined trade-off is what decided it, not one metric alone.

      Follow-ups: 1. TECHNICAL — What's the difference between shadow-testing a model and A/B testing it? · Whether 'response discarded, zero risk' is distinguished from a real user-facing split. 2. MEASUREMENT — In shadow mode, how do you compare two responses the user never saw, with no label for either? · Connects to the label-free proxy signals from Q14.5, applied to a controlled comparison. 3. TRADEOFF — The new model is faster and cheaper but citation rate is two points lower. Do you ship it? · Whether a multi-metric trade-off is reasoned about, not decided by one number. 4. FAILURE — What would make you stop the test early, in either direction? · Whether a stopping rule exists for a clear win and a clear regression alike.

      Tip: If you've run a canary or a dark-launch that processed real traffic without ever serving the result to a user, that's the same shadow-mode idea. Don't claim you've A/B tested a model. Say you've run a canary or shadow deployment with a pre-agreed metric and stopping rule before.

      Numbers worth quoting: - Shadow mode carries zero user risk - Pre-register the win condition - 10% split, not a full swap - Stop early on a clear regression

      Q14.9 — DRILL: overnight the assistant got hedgier with fewer citations. Nobody deployed. Write the runbook. (practical drill)

      Weak answer: "N/A, this is a drill. A weak attempt jumps to "the provider changed something" as the only cause, with no order and no confirm step."

      Why it fails: - Treats "the provider changed the model" as the only hypothesis, when a config edit or a doc-index change fit the same symptom. - No ordering, listing five things to check without saying which comes first is a list, not a runbook.

      Instant rejection: - Never confirms the regression is real and sized before investigating a cause. - No branch point between a generation-side fault and a retrieval-side fault.

      Model answer: 1. Step one: confirm and size the regression, pull citation-rate and hedge-rate proxies for 48 hours and check it's a real step-change, not noise. 2. Step two: enumerate what could change with no deploy, our pinned model version, the config-stored prompt, or the doc index being reindexed overnight. 3. Step three: pull full traces on ten degraded responses and read what was actually retrieved, not just the final answer, per Q14.1. 4. Branch here: if retrieved context is wrong or stale, this is retrieval-quality, hand off into that diagnosis rather than treating it as a model issue. 5. If context looks right but the model under-uses it, check the prompt hash and model id against known-good, then apply rollback while root-causing continues.

      Follow-ups: 1. TECHNICAL — What's the very first thing you check, before forming any hypothesis? · Whether the regression is confirmed against Q14.2/Q14.5 proxies before guessing. 2. FAILURE — Nobody deployed. What could still have changed without your deploy log showing it? · Whether provider model update, config prompt edit and upstream doc change are all named. 3. TECHNICAL — The symptom tracks one document category, not time of day. Where does the runbook send you? · Whether a retrieval-shaped symptom is routed to retrieval diagnosis, not the model. 4. TRADEOFF — You've found the cause. What's the fastest safe mitigation while the real fix is worked out? · Whether the Q14.3/Q14.6 rollback and version-pin mechanics are reached for as a stopgap.

      Tip: If you've run a structured incident triage, confirm, isolate, branch, mitigate, root cause, for any production regression, that's this exact shape. Don't invent a GenAI incident story. Say you'd apply the same triage discipline you'd use for any live quality regression with no obvious cause.

      Numbers worth quoting: - Confirm before investigating - Three no-deploy causes to check - Branch: retrieval fault vs model - Mitigate first, root cause after
