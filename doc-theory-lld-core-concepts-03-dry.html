    DRY

    10 sections · 706 words

    Principle · LLD Core Concepts · Concept 03 of 09

    The Idea

    Don't Repeat Yourself.

    You'll See This

    • The same validation rule copy-pasted in two or three places.
    • A magic number (a tax rate, a limit) hardcoded in multiple files.
    • Two functions identical except for one hardcoded value.

    One authoritative home.

    Before

    class SignupForm {
    boolean validate() {
        return age >= 18 && age <= 120; // the rule
    }
}
class ProfileForm {
    boolean validate() {
        return age >= 18 && age <= 120; // same rule, copied
    }
}
// the minimum age changes: did you find both copies?

    The rule, copied twice.

    After

    class AgeRule {
    // the rule's one home
    static boolean isValid(int age) {
        return age >= 18 && age <= 120;
    }
}
class SignupForm {
    boolean validate() { return AgeRule.isValid(age); }
}
class ProfileForm {
    boolean validate() { return AgeRule.isValid(age); }
}
// the rule changes once. every caller picks it up.

    Don't Bother If

    • Two blocks look alike today but change for unrelated reasons: that's coincidence, not duplication.
    • "De-duplicating" two things that only look alike right now is its own smell.

    Quick Check

    Not "does this look the same." Ask "if the rule changes, do I edit it in two places?"

    How It's Built

    The Shape

    AgeRule
    + isValid(age): bool
    the rule lives here, once

SignupForm
ProfileForm
    both call in

BOTH CALL IN. NEITHER HOLDS ITS OWN COPY OF THE RULE

    The Move (3 Steps)

    1. Find the same rule, not just similar-looking code, repeated in two or more places.
    2. Give the rule one named home: a method, a constant, a class.
    3. Point every caller at that one home and delete the copies.

    In The Interview

    "SignupForm and ProfileForm both hardcoded the same 18-120 age check. If the minimum age changes, someone has to remember both places. I pulled it into one AgeRule.isValid() and had both forms call it."

    How It's Different

    The Confusion Pairs

    DRY vs coincidental duplication. Two blocks that look alike by accident, not because they express the same rule, should stay separate.

    DRY vs a deliberate copy. Test fixtures copied into 3 test files on purpose, so one test's edit can't break another, is a correct exception.

    DRY vs abstraction cost. Merging 2 uses into 1 shared function is fine. Merging 5 unrelated uses into 1 function with 6 boolean flags is worse than the duplication.

    DRY vs YAGNI. DRY removes duplication that exists now. It isn't a license to build a shared framework for duplication that might exist later.

    They Say: "the minimum age changes to 16"

    • With it: one line changes in AgeRule. Both forms pick it up automatically.
    • Without: whoever edits it greps the codebase and hopes they found every copy.

    Watch Out For

    • Two blocks that look identical but express different rules that happen to match today aren't a DRY violation: merging them is a coupling mistake.
    • DRY applies to knowledge, not lines of code: two unrelated 3-line blocks that look similar aren't a violation.
    • Over-applying DRY produces one giant configurable function nobody can read: the fix became worse than the duplication.
    • Copy-pasted test setup across test files is often a deliberate exception, not an oversight.
    • A shared constant used by two unrelated modules can quietly couple them: changing it for one breaks the other.
