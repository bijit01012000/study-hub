    Template Method

    11 sections · 812 words

    Behavioural · Design Patterns · Pattern 12 of 12

    Intent

    Fix the skeleton and order of an algorithm in a final method of a parent class, and let subclasses fill only the named steps that vary.

    When To Use It

    The Signs

    • Several classes run nearly the same procedure, differing in a step or two.
    • Copy-pasted algorithms with small edits.
    • You want to fix the skeleton and the step order, and let subclasses fill the blanks.
    • A recipe whose stages never change.

    Don't Bother If

    • There is only one version of the procedure.
    • The steps recombine freely in other orders (that is Strategy).
    • What varies is data, not behaviour. Pass a value.
    • Subclassing to swap one line is heavier than a lambda.

    Before

    class Espresso {
    Cup make() {
        boilWater();
        grindFine();
        pourThroughPuck();
        return cup;
    }
}
class Latte {
    Cup make() {
        boilWater();
        grindFine();
        pourThroughPuck();
        steamMilk();
        pourMilk();
        return cup;
    }
}
// boil + grind + pour copied; a change to boil() edits both

    Copy-paste the recipe.

    After

    abstract class Beverage {
    final Cup prepare() {
        // the fixed order
        boilWater();
        brew();
        pourInCup();
        if (wantsCondiments()) addCondiments();
        return cup;
    }
    void boilWater() {...}       // stable, shared
    void pourInCup() {...}
    abstract void brew();        // subclass fills
    abstract void addCondiments();
    boolean wantsCondiments() { return true; } // hook
}
class Latte extends Beverage {
    void brew() { pullShot(); }
    void addCondiments() { steamAndPourMilk(); }
}
// prepare() is final: nobody can reorder the steps

    Structure

    «ABSTRACT»
Beverage
    prepare() «final»
    calls the steps in this order

    FIXED ORDER
    1 boilWater()       concrete
    2 brew()            abstract
    3 pourInCup()       concrete
    4 addCondiments()   abstract

    wantsCondiments() «hook»
    default: return true

    EXTENDS
    brew() { pullShot(); }
    addCondiments() { }

Latte
    EXTENDS
    brew() { pullShot(); }
    addCondiments() { steamMilk(); }
    wantsCondiments() { ... }

prepare() is final: nobody reorders the steps
subclass fills this

THE PARENT OWNS THE ORDER; CHILDREN FILL THE BLANKS

    How It's Built (3 Steps)

    1. Write the procedure once as a final method that calls the steps in order.
    2. Make the varying steps abstract; give the stable ones a body in the parent.
    3. Add hooks: an optional step with a default (wantsCondiments() returns true) that a subclass may override.

    Quick Check

    Write the procedure as numbered steps. If the numbers and their order are fixed and only a couple of step bodies change per case, that is a Template Method.

    In The Interview

    "The brew sequence is a Template Method. prepare() is final and calls boil, brew, pour, then addCondiments. Espresso fills brew and leaves addCondiments empty; Latte fills both and overrides the wantsCondiments hook. Nobody can reorder the steps."

    How It's Different

    From The Lookalikes

    Vs Strategy. Strategy composes a whole swapped-in object held as a field, chosen at runtime. Template Method is subclassing: the parent's final method calls abstract steps the child overrides. Strategy when steps recombine freely; Template Method when the sequence is law.

    Vs Factory Method. Factory Method is often one of the steps a Template Method calls: the step that creates a product. They pair up.

    Vs a plain abstract method. An abstract method is just one blank. Template Method is the final orchestrator that calls several of them in a fixed order.

    Vs config-driven steps. A data-driven recipe table lets non-developers edit the flow. Template Method fixes the flow in code; a subclass, not a config row, adds a variant.

    They Say: "add iced coffee, which skips boiling"

    • With it: a chillWater() override of the water step, or a hook the skeleton already calls. The order still holds.
    • Without: a fourth near-copy of the whole make() method, and the next change touches all four.

    Watch Out For

    • Make the template method final, or a subclass quietly reorders or drops a step.
    • Keep the number of abstract steps small. Many blanks means the skeleton is not really shared.
    • Give hooks a sane default so a subclass only overrides what it cares about.
    • Do not let a step call back into the template method. That is an infinite loop.
    • If the steps recombine in many orders, switch to Strategy. Template Method locks the order on purpose.
