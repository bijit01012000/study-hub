    Q39. Describe a time when you anticipated potential problems and developed preventive measures.

    4 sections · 543 words

    Core message: I don't anticipate problems by being clever in the moment — I build detection into the platform so anticipation becomes a system property.

    Framework

    S — Situation. At Rakuten, alerting was threshold-based: problems surfaced only at breach. Predictable pattern — post-damage alerts, on-call firefighting, alert fatigue from noisy static thresholds.

    T — Task. I anticipated the class of problem: slow-burn degradations — CPU creep, log-volume drift — that never cross a threshold until too late.

    A — Action. Proposed Isolation Forest anomaly detection on KPI time series — max CPU, log volume — emitting confidence bands, not binary alarms.

    • Proved it before trusting it: a two-week shadow run against historical incidents — ~40% had detectable early precursors.

    • Integrated with restraint: a "needs attention" severity that doesn't page.

    • Complemented the tracing rollout that cut MTTD ~35%: detect faster, then detect before.

    R — Result. ~40% of incidents caught early, before threshold breach.

    • MTTR cut ~25% — smaller fires are cheaper fires.

    • Alert noise stayed down — the new severity doesn't page.

    L — Lesson. Anticipation is a system property, not a personal virtue — vigilance doesn't scale; platform detection does.

    Read it straight

    On the observability platform at Rakuten, alerting was purely threshold-based — problems surfaced only at breach. The pattern was predictable: firefighting, alerts firing after the damage, alert fatigue from noisy static thresholds. What I anticipated was the class of problem: slow-burn degradations — CPU creep, log-volume drift — that never cross a static threshold until it's too late. So I proposed an anomaly detection service running Isolation Forest on KPI time series — max CPU usage, log volume — producing confidence bands instead of binary alarms, so "unusual but not yet broken" became visible. And I proved it before trusting it: a twoweek shadow run against real historical incidents, before it could touch anyone's pager. That's where I got the number that justified the project — about 40% of incidents had detectable early precursors. I integrated it with restraint: a "needs attention" severity that informs the on-call without paging, so early signals don't wake anyone at 3 a.m. for noise. This was the second half of one philosophy — the tracing rollout that cut MTTD around 35% was the first: detect faster when things break, then detect before they break.

    Roughly 40% of incidents were caught early, MTTR fell about 25% — smaller fires are cheaper fires — and alert noise stayed down because the new severity doesn't page. Anticipation is a system property, not a personal virtue.

    Revision bullets

    • Isolation Forest on KPI time series, confidence bands

    • Two-week shadow run before any paging

    • ~40% of incidents had detectable early precursors

    • "Needs attention" severity informs without paging

    • Earlier tracing rollout cut MTTD ~35%

    • MTTR cut ~25%; noise stayed down

    If they push deeper

    • What if the shadow-run had shown no precursors? → I'd have shelved it honestly — that's exactly why we shadowran before wiring it to alerting.

    • Why not page on anomalies? → Early signals are probabilistic; paging on them recreates the fatigue we were fixing.
