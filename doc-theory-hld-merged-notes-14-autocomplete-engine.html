    Autocomplete Engine

    9 sections · 989 words

    Also known as: design the top-k most searched queries.

    1. The Problem

    Given a prefix, return the most popular matching queries. Google is the reference. Example for the prefix sw (with frequencies):

    Suggestion Frequency
    swing 1000
    swiggy 800
    swan 700
    swim -

    The initial lookup is expected to be O(1).

    Clarifying questions

    • How many autocomplete suggestions are needed? 6 suggestions.
    • How are search results decided? Based on popularity (frequency).
    • Search key length? 100.
    • Which languages are supported? English.
    • Should we sort? Yes.
    • Case sensitive? No.
    • Daily active users? 5 million DAU.

    2. Services

    • Data Gathering Service - responsible for collecting information.
    • Data Query Service - given a search query or prefix, returns the top 6 most searched results.

    The data gathering service stores data in a SQL DB. A basic frequency table starts empty:

    Query Frequency
    switch 2
    swing 4
    swim 7
    swirl 3
    swan 6

    3. First Approach: Query the Table

    For the prefix sw, the Data Query Service returns swim, swan, swing, swirl, and switch:

    select * from frequency
where query like 'prefix%'   -- {sw}
order by frequency DESC
limit 6;

    When the dataset is small, this solution is OK (O(n)). When the data is huge, it is very slow.

    4. Next Solution: Tries

    A trie splits the prefix one character at a time. English uses 26 letters. For sw?, the tree holds swim, swing, swan, and swirl.

    A trie node is commonly modelled as:

    Tries {
  Tries *Children[26];
  bool eow;
  int freq;
}

    Problems remain with normal tries, so the ordinary autocomplete trie must be modified. Define:

    • p: length of the prefix being searched.
    • n: total number of nodes in the trie.
    • c: number of children of a given node.

    Top K most frequent queries:

    1. Find the prefix -> O(p).
    2. Traverse the subtree from this node to get all valid children -> O(c).
    3. Sort the result on the basis of frequency -> O(c log c).

    Total time complexity: O(p) + O(c) + O(c log c). Worst case: traverse the complete trie.

    5. Making It Fast

    1. Limit the max length of the query (100 characters max). Users rarely search for very long strings, so p is small and O(p) becomes O(1).
    2. Cache the top 6 results for each node. k is small (6), so cache them at each node. For the node w, the cache holds swim(7), swan(6), swing(4), swirl(3).

    With these, finding the prefix is O(1) and sorting is unnecessary (already sorted), so total complexity is O(1) + O(1) = O(1).

    Trade-off: space increase to decrease time complexity.

    6. How to Cache

    The data gathering service is a real time vs almost real time decision:

    • Real-time search prediction is almost impossible, so this is an almost real-time system.
    • Why? Top suggestions may not change much, and it is not practical to update the tries on every request.
    • This is about real time vs timely updates. Twitter may use a more real-time system than our engine, but not for Google search.

    Analytics logs

    • A raw table about search queries that is not indexed.
    • The SQL table is append only with columns like Query and timestamp.

    Aggregator service

    • Aggregates data to be processed further (format correction).
    • Non real-time system: aggregate once a week.
    • More real-time system: aggregate once a day.
    • Aggregated data is an SQL table with Query, time, and freq.

    Pipeline: analytics logs -> aggregator service -> aggregated data -> trie cache / trie DB / workers.

    • Workers: a set of servers that perform async operations to build the trie DS and store it in the Trie DB.
    • Trie cache: keeps tries in memory for faster reads and holds the weekly updated information.
    • Trie DB (NoSQL): persistent storage. Tries are stored as key/value (MongoDB/Cassandra).

    7. Serializing the Trie

    The trie is serialized into key/value pairs (a hashmap):

    • key: every prefix in the trie.
    • value: the data for each trie node (the top 6 results).

    Example entries: sw -> swim, swan, swing, swirl and swi -> swing, swirl, swim.

    First run of the service: 1 lakh analytics logs in one week -> 10K aggregated data -> build tries.

    8. Flow

    1. A search query is sent to the LB.
    2. The LB routes it to our server.
    3. The server tries to fetch data from the cache DB, if it exists.
    4. If it does not exist, replenish data from the DB to the cache (when the cache is full or the cache is down).

    9. Further Optimisations

    1. AJAX requests per keystroke instead of full HTTP requests: the browser sends /search/query=sw, then swi, then swin as AJAX, so the web page is not refreshed at each letter.
    2. Client-side caching: cache results at the browser side to decrease load on the server.
    3. Offensive/abusive words: filter them out with a set of rules.
    4. Scaling the DB: a sharding key can shard on the basis of the first English character, for example a to z across DB1 to DB26. But distribution is uneven (x is less, a is more), so a shard mapping table is used (aa to am, an to az, etc.), with web servers, DB, and a single server.
    5. Multiple languages: Hinglish (Hindi in English letters) and Unicode character encoding standards for all characters of every language in the world.
    6. Different countries: use different servers so results can be country specific, and use a CDN (cache) for a better response.
