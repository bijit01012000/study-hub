    Design a Parking Lot

    15 sections · 1,673 words

    LLD Design Problems, problem 01 of 20.

    The Ask

    Build

    • Many floors, each a set of spots.
    • 3 sizes: bike, car, truck.
    • A smaller vehicle may take a bigger spot, never the reverse.
    • Many entry and exit gates.
    • Entry: auto-pick a free spot that fits, hand out a ticket.
    • Exit: price by time parked, free the spot.
    • Fee rule is swappable.
    • Live free-spot count for the board.

    Skip

    • Real card / cash processing.
    • Gates, sensors, cameras.
    • Booking a spot ahead, passes.
    • Many lots, one operator.
    • A database, login.

    Our Model

    One lot to floors to spots. A ParkingLot owns many ParkingFloors; each floor holds many ParkingSpots. Gates hand out Tickets; pricing and payment sit behind interfaces.

    Actors and classes

    • EntryGate — id, lot: ParkingLot; issueTicket(Vehicle): Ticket calls lot.park(v).
    • ExitGate — id, lot, pay: PaymentStrategy; checkout(Ticket): Receipt calls r = lot.unpark(id) then pay.collect(r.fee).
    • ParkingLot (singleton) — floors: List<ParkingFloor>, fee: FeeStrategy, live: Map<String, Ticket>; park(Vehicle v): Ticket, unpark(String id): Receipt, freeCount(): Map<SpotType, int>, setFee(FeeStrategy).
    • Ticket — id, plate, floorNo, spotId, entryAt, exitAt: Instant, state: TicketState; minutesParked(): long. Returned by park(), cleared by unpark().
    • FeeStrategy (interface) — computeFee(Ticket t): Money. The one step that changes, never touches the lot.
    • PaymentStrategy (interface) — collect(Money): boolean; CashPayment, CardPayment, UpiPayment.
    • Vehicle (abstract) — plate: String, type: VehicleType; type(): VehicleType. Subtypes: Car -> CAR, Bike -> BIKE, Truck -> TRUCK, each super(plate, type).
    • ParkingFloor — no: int, free: Map<SpotType, Deque<ParkingSpot>>; findFreeSpot(VehicleType): ParkingSpot, onFreed(ParkingSpot).
    • ParkingSpot — id: String, type: SpotType, free: boolean, parked: Vehicle; fits(Vehicle v): boolean, assign(Vehicle), release(). Holds 0..1 car.

    Relationships: ParkingLot 1 owns 1.. ParkingFloor; a floor owns 1.. spots; a spot holds 0..1 Vehicle.

    The fit rule

    Smaller fits bigger. fits is true when spot.size >= vehicle.size; a bike fits a car spot, a truck does not fit a car spot. Full means every floor's free[size] is empty.

    Rows are the vehicle, columns the spot size:

    Vehicle Bike spot Car spot Truck spot
    Bike yes yes yes
    Car no yes yes
    Truck no no yes

    The fee rules

    • HourlyFee -> Rs 30/hr, round up.
    • FlatDayFee -> Rs 400 flat.
    • WeekendFee -> Rs 200 Sat/Sun, else hourly.

    Key operations

    1. park(Vehicle v): Ticket — lowest floor with a spot that fits. Locks the spot and re-checks free before assigning. Throws LotFullException when every floor is full for that size.
    2. unpark(String id): Receipt — removes the ticket in one step; a second call throws InvalidTicketException. Frees the spot before payment. Fee comes from the current FeeStrategy.
    3. findFreeSpot(VehicleType): ParkingSpot — peeks the head of free[size], else the next larger size's list. O(1) and non-destructive, which is exactly why the claim still needs a lock. Null when this floor has nothing that fits.
    4. computeFee(Ticket t): Money — reads minutesParked(), rounds up to the hour. Never touches ParkingLot; a new rule is a new class.

    Recall drill: cover the operations column, write the four with their guarantee. Blank on the guarantee means that method is your gap.

    The One Run to Hold in Your Head

    A car enters at gate 2. Floor 1 is full, floor 2 has C-14 free. She parks 3h 10m, weekend rate on. What does she pay, and which objects touched the request?

    The Change

    They ask for "the spot nearest the entrance" or "fill floor 1 first". Pull findFreeSpot out of ParkingFloor into a SpotAssignmentStrategy. Floors just expose their free lists; the strategy ranks them. Strategy, a second time on this sheet.

    What the Picture Can't Show

    The race: two cars scan at once, both see C-14 free. The fix is not a class, it is a lock on the spot (or a CAS on free) with a re-check after you take it.

    If They Make You Code It

    The gate lists its four key operations:

    1. park(Vehicle v): Ticket
    2. unpark(String id): Receipt
    3. findFreeSpot(VehicleType): ParkingSpot
    4. computeFee(Ticket t): Money

    Park and unpark, the whole thing:

    class ParkingLot {                                  // one instance
    private final List<ParkingFloor> floors;
    private FeeStrategy fee;                        // swappable rule
    private final Map<String,Ticket> live = new ConcurrentHashMap<>();

    Ticket park(Vehicle v) {
        for (ParkingFloor f : floors) {             // lowest floor first
            ParkingSpot s;                          // retry THIS floor
            while ((s = f.findFreeSpot(v.type())) != null) {
                synchronized (s) {
                    if (!s.isFree()) continue;      // lost it, peek again
                    s.assign(v);                    // one spot, one winner
                }
                Ticket t = new Ticket(v.plate(), f.no(), s.id(), now());
                live.put(t.id(), t);
                return t;
            }
        }
        throw new LotFullException(v.type());
    }

    Receipt unpark(String id) {
        Ticket t = live.remove(id);                 // read + delete once
        if (t == null)
            throw new InvalidTicketException(id);
        t.close(now());
        spotOf(t).release();                        // free now, before payment
        Money due = fee.computeFee(t);              // current rule prices
        return new Receipt(t, due);
    }
}

    The Four Hazards

    1. Two cars, one spot. findFreeSpot is not the commit. With no lock, both cars see C-14 free and both assign.
    2. Rounding the bill. 61 minutes — one hour or two? Pick ceil(minutes / 60) and say it out loud. The boundary is where money leaks or the customer argues. One rule, stated, in computeFee, not scattered.
    3. Lost ticket. No entryAt to bill from. Do not guess the time: a flat max-day charge, mark the ticket LOST, move on.
    4. Spot leak. Assign succeeds, then new Ticket throws or the process dies — the spot shows full forever. Assign and register the ticket in one guarded step; a sweeper reconciles free against live tickets.

    Name them before they are asked: lock the spot (or CAS on free) and re-read isFree inside.

    The Three Lines They Are Watching

    1. synchronized (s) + re-check isFree() — two cars get C-14, one assigns.
    2. live.remove(id) — reads and deletes at once, so no double charge.
    3. release() runs before payment, never after.

    Finding a Free Spot

    Approach Find Assign / free Board count "Nearest gate" Extra memory
    Scan every spot (brute force, the default) O(spots) each entry O(1) count all spots re-sort each time none
    Free-list per size O(1) peek O(1) pop / push list.size() no order a deque per (floor, size)
    Distance tree / gate O(log n) O(log n) subtree size built in a tree per gate

    Free-list per (floor, size). O(1) both ways and the entrance board is just size(). Move to a distance tree only when they ask for "nearest gate" or "fill floor 1 first".

    Rejection Signals

    These end the interview:

    • Assigning a spot with no lock and no re-check — two cars take the last spot.
    • One ParkingLot god class doing search, pricing and payment — no seams to swap.
    • Pricing with instanceof or a switch on vehicle type instead of a strategy.
    • Freeing the spot only after the card clears — billing holds the spot hostage.
    • No answer for a lost ticket or a full lot — the two cases every interviewer probes.
    • Entry time stored on the Vehicle, not the Ticket — the same car's second visit bills wrong.
    • One spot class per size: BikeSpot / CarSpot / TruckSpot — three empty classes. Use one ParkingSpot plus SpotType; size is data, not behaviour.
    • if (v instanceof Truck) inside unpark — replace it with fee.computeFee(t), so hourly, flat-day, weekend and first-15-free stay untouched.

    Patterns Used

    Strategy — fee, payment, and (page 2) spot placement. Singleton — one ParkingLot. Factory — build Vehicle / Spot from a type code. Observer — the board follows spot freed / taken.

    Say It Like This

    "One lot, many floors, each floor a list of spots typed by size. Entry: lowest floor with a free spot that fits, lock it, hand back a ticket. Exit: find the ticket, a FeeStrategy prices the stay, free the spot. Fee and payment are strategies, so a new rule never reopens the lot."

    The Follow-ups That Decide It

    1. Two cars reach the last spot together. Walk the steps. Lock the spot, re-check free, one wins.
    2. Bike in a car spot? Car in a bike spot? Smaller fits larger, never the reverse.
    3. Free spots per floor for the board, no scan. free[size].size(), or a counter kept by an Observer.
    4. Lost ticket — what do you charge? A flat max-day charge, state LOST, do not guess the entry time.
    5. Make the first 15 minutes free. A new FeeStrategy; the lot is untouched.
    6. "Give the spot nearest the entrance." SpotAssignmentStrategy over a per-gate distance tree.
    7. A truck needs two adjoining car spots. Assignment reserves a run; release frees the whole run.
    8. Ten entry gates, one lot. Contention is per-spot / per-free-list, never one global lock.

    Deliberately Not Built

    • Reservations / passes — a hold table with expiry, and a check at entry. A different question.
    • A real payment gateway — a PSP behind PaymentStrategy. The seam is the point; the integration is not.
    • Many lots, an operator view — that is the HLD version of this problem: sharding, a control plane.
    • Persistence — spots and tickets in a DB, a reconciler on restart. Name it and move on.
    • Surge pricing — a FeeStrategy that reads live occupancy. Drops in, no lot change.
