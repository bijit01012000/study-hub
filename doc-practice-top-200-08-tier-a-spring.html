      78. Spring Bean lifecycle — full picture

      Asked at: Most Spring backend rounds · Razorpay · Swiggy · Walmart

      Difficulty: Medium · Topic: Spring Core

      The question: "Walk me through the full lifecycle of a Spring bean."

      The 30-second answer: Instantiation → populate properties (dependency injection) → *Aware callbacks (BeanNameAware, ApplicationContextAware) → BeanPostProcessor.before → @PostConstruct and InitializingBean.afterPropertiesSet → custom init method → BeanPostProcessor.after → bean is ready to serve → on shutdown: @PreDestroy → DisposableBean.destroy → custom destroy method.

      Step-by-step thought process:

      1. "Container loads bean definitions (XML, annotations, Java config). Creates the bean — constructor injection happens here. Singleton beans are typically eagerly created at startup."
      2. "Field/setter dependencies are populated next. Aware interfaces let beans get context references (BeanName, BeanFactory, ApplicationContext)."
      3. "BeanPostProcessors get a chance to wrap the bean — this is how AOP proxies (@Transactional, @Async) get inserted. postProcessBeforeInitialization runs before init callbacks."
      4. "Initialization callbacks run in order: @PostConstruct (JSR-250), then InitializingBean.afterPropertiesSet, then any custom init method declared in @Bean(initMethod=...)."
      5. " postProcessAfterInitialization runs — this is where AOP proxies are commonly wired in. Then the bean is in the ready-to-use pool."
      6. "On shutdown: @PreDestroy, then DisposableBean.destroy, then custom destroy method."*

      Edge cases to mention:

      • Prototype beans don't get destroy callbacks — Spring instantiates them but doesn't track them after handoff
      • @PostConstruct runs AFTER all injection is complete — that's why field-injected dependencies are safe to use there but not in the constructor
      • A bean throwing in afterPropertiesSet aborts container startup

      What NOT to say:

      • "Beans are just created with new" — misses Spring's entire value proposition "@PostConstruct is the constructor" — wrong, it runs after constructor + injection

      Common follow-up: "When does the AOP proxy get applied — before or after @PostConstruct?"

      79. @Autowired vs @Inject vs @Resource

      Asked at: Most Spring rounds · TCS · Infosys · Wipro · Cognizant

      Difficulty: Easy-Medium · Topic: Spring Core

      The question: "What's the difference between @Autowired, @Inject, and @Resource?"

      The 30-second answer: @Autowired is Spring-specific; injects by type by default. @Inject is JSR-330 (jakarta.inject); also by type. @Resource is JSR-250; injects by NAME first, then by type. Most Spring projects use @Autowired; @Inject is portable across DI containers; @Resource gives you name-based injection for free.

      Step-by-step thought process:

      1. " @Autowired — Spring's own. Default required=true. Combine with @Qualifier("beanName") when multiple candidates exist."
      2. " @Inject (from jakarta.inject since Spring 6 / Spring Boot 3) — standard JSR-330. Same type-first behavior. No required=false equivalent; use Optional<T> instead."
      3. " @Resource (from jakarta.annotation) — JSR-250. If name attribute is set, uses that bean name. Otherwise, by field/parameter name, falling back to type."
      4. "For new code: prefer constructor injection (no annotation needed since Spring 4.3 with single constructor) over field injection. Testability + immutability."
      5. "Concrete: @Autowired on the field is fine for legacy code, but private final PaymentService paymentService; injected via constructor is what I write in new code."

      Edge cases to mention:

      • When multiple beans match, @Autowired fails unless one is @Primary or you add @Qualifier
      • @Resource without name falls back to field name — confusing if you rename the field
      • Constructor injection makes the dependency required and the field final — both wins

      What NOT to say:

      • "All three are basically the same" — name-vs-type resolution actually matters
      • "Use field injection because it's shorter" — kills testability

      Common follow-up: "Why is constructor injection preferred over field injection?"

      80. @Component vs @Service vs @Repository vs @Controller

      Asked at: TCS · Infosys · most Spring rounds

      Difficulty: Easy · Topic: Spring Core

      The question: "What's the difference between @Component, @Service, @Repository, and @Controller?"

      The 30-second answer: All four are stereotypes — they register the class as a Spring bean. @Component is the generic one. @Service, @Repository, @Controller are semantic specializations. @Repository adds automatic JPA/JDBC exception translation. @Controller (and @RestController) are recognized by Spring MVC's handler mapping. Functionally, @Service is equivalent to @Component.

      Step-by-step thought process:

      1. "All four are meta-annotated with @Component. Spring's component scan picks them all up the same way."
      2. "@Service is a marker for business-logic beans. Functionally identical to @Component. The annotation exists for clarity in code reviews and architecture diagrams."
      3. "@Repository adds value: a BeanPostProcessor (PersistenceExceptionTranslationPostProcessor) wraps the bean so any Hibernate/JDBC native exceptions become Spring's DataAccessException hierarchy."
      4. "@Controller is recognized by Spring MVC — methods annotated with @RequestMapping / @GetMapping become URL handlers."
      5. "@RestController = @Controller + @ResponseBody on every method — returns are serialized to JSON instead of treated as view names."

      Edge cases to mention:

      • You can write custom stereotypes — meta-annotate your own annotation with @Component
      • If you skip the stereotype and use only @Bean in a @Configuration class, the class isn't a stereotype but the returned object is a bean
      • For multi-module apps, set basePackages on @ComponentScan or @SpringBootApplication to avoid scanning the world

      What NOT to say:

      • "They're all the same" — misses @Repository's exception translation
      • "@Service is for services so it runs on a different thread" — completely wrong

      Common follow-up: "What does @Repository actually add over @Component?"

      81. @Transactional propagation — full breakdown

      Asked at: Razorpay · Swiggy · Cred · most product co backend rounds

      Difficulty: Hard · Topic: Spring Core

      The question: "Explain @Transactional propagation modes. When would you use REQUIRES_NEW vs REQUIRED vs NESTED?"

      The 30-second answer: REQUIRED (default) — join existing transaction or start one. REQUIRES_NEW — suspend the outer transaction and start a new one. NESTED — use a savepoint in the outer transaction. MANDATORY — must be inside an existing transaction. NEVER — must NOT be in a transaction. SUPPORTS — use one if present. NOT_SUPPORTED — suspend any existing transaction.

      Step-by-step thought process:

      1. "REQUIRED is the workhorse. Same behavior whether called standalone or nested — caller's commit/rollback wins."
      2. "REQUIRES_NEW for audit logs and notifications — even if the outer business transaction rolls back, we still want the audit row committed. Watch out: the outer transaction is suspended; if the inner one deadlocks waiting for resources held by the outer, you're stuck."
      3. "NESTED uses a JDBC savepoint. Inner rollback rolls back to the savepoint; outer commit/rollback applies to everything. Only works with JDBC; not supported by JTA."
      4. "MANDATORY is a defensive check — 'fail loudly if I'm called without a transaction' for repository-layer methods that must be in one."
      5. "NEVER and NOT_SUPPORTED for read-only operations that shouldn't be in a transaction (long reports, calls to external systems)."

      Edge cases to mention:

      • @Transactional only works on PUBLIC methods called THROUGH a Spring proxy — internal this.method() calls bypass the proxy and bypass the transaction. Self-invocation gotcha
      • REQUIRES_NEW requires a new connection from the pool — if your pool is small and the outer transaction also holds one, you can deadlock the pool
      • Default rollback rule: rolls back on RuntimeException only. Checked exceptions DON'T roll back unless you specify rollbackFor

      What NOT to say:

      • "Just use REQUIRED everywhere" — sometimes you genuinely need REQUIRES_NEW for audit/notification semantics
      • "Spring handles all the connections automatically" — true at runtime, but you must understand the model to avoid pool deadlocks

      Common follow-up: "What happens if a method annotated @Transactional calls another @Transactional method on the same bean?"

      82. Spring profiles and conditional beans

      Asked at: Most Spring Boot rounds · Razorpay · Walmart Labs

      Difficulty: Medium · Topic: Spring Boot

      The question: "How do Spring profiles work, and when would you use @ConditionalOn... annotations?"

      The 30-second answer: Profiles are named configuration sets activated via spring.profiles.active=prod (or env var SPRING_PROFILES_ACTIVE). Beans/configs annotated with @Profile("prod") only register when that profile is active. @ConditionalOn... goes deeper — register a bean only if a property is set, a class is on the classpath, another bean exists, etc.

      Step-by-step thought process:

      1. " @Profile("dev") on a @Configuration or @Bean — only loaded when 'dev' profile is active. Multiple profiles supported: @Profile({"dev", "test"})."
      2. "Activation: spring.profiles.active=prod in application.properties, command line -Dspring.profiles.active=prod, or env var SPRING_PROFILES_ACTIVE=prod."
      3. "Profilespecific config files: application-prod.yml is loaded automatically when 'prod' is active, overriding values from application.yml."
      4. "@ConditionalOnProperty — load only if a property has a specific value. Useful for feature flags: @ConditionalOnProperty("feature.newcheckout.enabled")."
      5. "@ConditionalOnClass / @ConditionalOnMissingBean — Spring Boot's autoconfiguration is built on these. 'If Tomcat is on the classpath, configure embedded Tomcat'."

      Edge cases to mention:

      • @Profile("!prod") negates — load when 'prod' is NOT active
      • Beans without @Profile load in all profiles — be explicit if a bean is environment-specific @ConditionalOnMissingBean is evaluated AFTER all user beans are processed — used for sensible defaults that user code can override

      What NOT to say:

      • "Use system properties for environment switching" — fragile compared to profiles "@Profile is just a comment" — it's evaluated at bean registration time

      Common follow-up: "How does Spring Boot's autoconfiguration use @Conditional under the hood?"

      83. Spring Boot autoconfiguration — how does it work?

      Asked at: Most Spring Boot rounds · Razorpay · Swiggy · Wells Fargo

      Difficulty: Medium-Hard · Topic: Spring Boot

      The question: "How does Spring Boot's autoconfiguration mechanism work?"

      The 30-second answer: At startup, Spring Boot reads META-INF/spring/ org.springframework.boot.autoconfigure.AutoConfiguration.imports (was spring.factories before Boot 3) to find all autoconfiguration classes. Each is a @Configuration with @ConditionalOn... annotations that decide whether it applies based on classpath, properties, and existing beans. Run --debug flag to see what got configured and why.

      Step-by-step thought process:

      1. " @SpringBootApplication includes @EnableAutoConfiguration. That triggers the AutoConfigurationImportSelector to read the imports file."
      2. "Each entry is a class like DataSourceAutoConfiguration. It's a @Configuration class loaded with all its @ConditionalOn... guards."
      3. "Common guards: @ConditionalOnClass(DataSource.class) — only run if DataSource is on classpath. @ConditionalOnMissingBean — only register if user hasn't defined one. @ConditionalOnProperty — only if a property is set."
      4. "Result: include spring-boot-starter-data-jpa, get JPA + Hibernate + a DataSource configured from your properties. Add your own @Bean DataSource and Spring Boot backs off."
      5. "Debugging: --debug flag prints the autoconfiguration report — every condition's positive and negative matches. The actuator /conditions endpoint shows the same in production."

      Edge cases to mention:

      • Boot 3 changed from spring.factories to AutoConfiguration.imports — older tutorials are outdated
      • @EnableAutoConfiguration's exclude lets you remove a specific config — useful when a starter brings in something you don't want
      • Custom starters: build your own autoconfiguration by writing your own META-INF/ spring/...imports file

      What NOT to say:

      • "Spring Boot just guesses what you want" — it's a deterministic system of conditions, not magic
      • "Autoconfiguration runs every request" — it runs at startup only

      Common follow-up: "How would you write your own custom autoconfiguration?"

      84. Spring scopes — singleton vs prototype vs request

      Asked at: Most Spring rounds

      Difficulty: Easy-Medium · Topic: Spring Core

      The question: "What scopes does Spring support and when would you use each?"

      The 30-second answer: singleton (default) — one instance per container. prototype — new instance every time the bean is requested. request — one per HTTP request. session — one per HTTP session. application — one per ServletContext. websocket — one per WebSocket session. Almost everything is singleton in practice.

      Step-by-step thought process:

      1. "Singleton — the default. Container creates one instance, returns it everywhere. Stateless services, repositories, controllers — all singleton."
      2. "Prototype — new instance every time getBean() or @Autowired is resolved. Use for stateful beans that need fresh state per use."
      3. "Request — one instance per HTTP request. Useful for holding request context (current user, locale). Web-only."
      4. "Session — one per HTTP session. Use for user-specific state. Beware: session beans get serialized if you have session replication."
      5. "Critical gotcha: injecting a prototype/request bean into a singleton — the singleton captures one instance forever. Use ObjectProvider<T>, Provider<T>, or scoped proxy (@Scope(value=..., proxyMode=TARGET_CLASS)) to get a fresh instance per call."

      Edge cases to mention:

      • Singleton scope in Spring is per-container, not JVM-wide — different from the singleton design pattern
      • Prototype beans don't get destruction callbacks — Spring drops the reference after handoff
      • For thread-per-request models with virtual threads, request scope still works (Spring's request context propagates)

      What NOT to say:

      • "Spring singletons are like the singleton design pattern" — close but not identical, mention per-container
      • "Prototype beans are thread-safe" — depends on the bean; scope doesn't grant thread safety

      Common follow-up: "How do you safely inject a prototype bean into a singleton?"
