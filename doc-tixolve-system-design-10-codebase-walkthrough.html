    Section 10 of 11

    Written after a full deep scan of the repo (docs + all services + frontend + infra). Purpose: a single source of truth for "what this project is, where it stands, and what's left" — so any future session (or the user) can pick up exactly where things are without re-scanning.

    1. What This Project Is

    Tixolve — an AI-powered enterprise knowledge assistant + support ticketing platform, built as a portfolio/interview project. Not a real SaaS.

    The pitch (one line): Users chat with an AI that answers from uploaded company documents with cited sources (RAG). When the AI can't resolve something, it auto-escalates to a human support ticket.

    Guiding principle (from CLAUDE.md): every architectural choice must be one the user can defend in a technical interview. Textbook-correct patterns over shortcuts. The complexity is deliberate — it demonstrates distributed-systems reasoning (outbox, event-driven, database-per-service, gateway trust boundary), and the user openly acknowledges a modular monolith would ship faster.

    Critical priority note (frontend_priority_prompt.md): the frontend is the primary deliverable — the interviewer judges it first and most heavily. A less feature-complete app with an excellent, polished UI beats a functionally complete app with a mediocre UI. Visual/interaction quality is a hard requirement: every async state handled (loading/empty/error), all interactive element states styled, consistent spacing/typography scales, responsive by default, accessibility basics, real-sounding copy.

    2. Locked Stack & Hard Rules (from CLAUDE.md — do not violate)

    Layer Choice
    Frontend React + TypeScript + Vite + Tailwind (MUI was replaced in Phase 3 — user-confirmed decision)
    Server state TanStack React Query (no Redux, no inline fetch in components)
    Backend Java 21 + Spring Boot microservices, Spring Cloud Gateway
    Auth Keycloak (Auth Code + PKCE) + Spring Security JWT at gateway only
    DB PostgreSQL, database-per-service, pgvector for embeddings
    Messaging Kafka (KRaft mode), outbox pattern everywhere
    AI Spring AI abstraction — Ollama locally, Claude API (claude profile) for demos
    Storage S3 API (MinIO locally, real S3 in AWS demos)
    Cloud AWS ECS Fargate — on-demand only, torn down after demos (cost discipline is locked)

    Non-negotiable rules:

    • No service reads another service's tables. Cross-service reads = REST; side effects = Kafka.
    • knowledge-service and chat-service stay separate (different scaling profiles: async batch vs sync/latency-sensitive).
    • Gateway is the sole trust boundary — downstream services trust X-User-Id / X-Tenant-Id / X-User-Role headers and never re-validate JWTs.
    • Outbox pattern for all Kafka producers — no naive dual-writes.
    • Four Kafka topics: ticket.created, ticket.status-changed, document.ingested, chat.escalated.
    • Design tokens: ink #14181F, paper #F7F7F5, teal #2E4B4F, amber #C97A3F (status/priority only), slate #5B6470; IBM Plex Sans/Mono; 6px radius; light+dark themes.
    • Build order locked; when asked "what's next," default to the next unfinished item.

    4. Implementation Reality (verified by code scan)

    Backend services (all real, production-shaped code)

    • api-gateway (8080): JwtClaimsExtractionFilter (ordered LOWEST_PRECEDENCE - 100), Redis token-bucket rate limiting per route, split KEYCLOAK_INTERNAL_URL (JWKS) vs KEYCLOAK_ISSUER_URL (iss validation) — the Phase 9 fix. Also a WebSocketTokenHeaderFilter promoting /ws?access_token= to Bearer for STOMP.
    • auth-service (8081): users + role_mappings (Flyway V1–V3), just-in-time user provisioning, /users/me. No Kafka/Redis — by design.
    • ticket-service (8082): tickets, outbox_events, ticket_events (audit) tables; VALID_TRANSITIONS state map in service layer (CLOSED terminal); outbox poller @5s with eventId header for consumer dedup; consumes chat.escalated (idempotent on conversation_id — the domain invariant is the idempotency key).
    • knowledge-service (8083): documents/document_chunks/chunk_embeddings (vector(768) + HNSW m=16, ef_construction=64, GIN FTS index)/ingestion_jobs (Flyway V1–V4); Tika extraction; 2000-char chunks / 200 overlap with sentence-boundary detection + forward-progress guard; afterCommit hook to fire async ingestion (avoids the async-before-commit race); short per-chunk TransactionTemplate transactions; hybrid search = parallel vector <=> + full-text, RRF merge (k=60); JdbcTemplate ?::vector cast for embeddings (Hibernate can't map them); S3Presigner for downloads.
    • chat-service (8084): conversations/messages (JSONB source_chunks citations); SSE via SseEmitter + @Async (MVC, not WebFlux — deliberate); DelegatingSecurityContextAsyncTaskExecutor for SecurityContext propagation to async threads; RAG prompt with numbered [Source N] blocks + last-10 history; escalation = deterministic heuristic on the model's "I don't have enough information" marker phrase; final done SSE event carries messageId/citations/escalated/escalatedTicketId; consumes ticket.created (sets escalatedTicketId) and document.ingested (deliberate log-only stub — nothing to invalidate yet).
    • notification-service (8085): Kafka-only inbound (no REST — correct); consumes both ticket topics; processed_events idempotency ledger; STOMP over SockJS at /ws, user-destination push.

    Frontend (all real — this matches the "frontend is primary" priority)

    • All routes live: / dashboard, /tickets(+/:id), /knowledge(+/:id), /chat(+/:id), /notifications, /architecture (admin-only demo page with SVG system diagram), /403, 404. Only /settings is a placeholder ("Coming in Phase 9").
    • CitationChip is fully implemented — the signature element: numbered mono chip, click-to-expand source popover.
    • Chat streaming is real: POST + text/event-stream via fetch ReadableStream with a custom SSE frame parser (EventSource can't POST), abort support, token refresh.
    • Notifications are real: STOMP over SockJS via gateway /ws, reconnect + heartbeat + beforeConnect token refresh, de-dupe, session-capped at 50.
    • TanStack Query hooks per feature: tickets (5 hooks), knowledge (4 hooks), chat (3 hooks + standalone streamChat()); notifications use the STOMP client directly (no query hooks — no read API exists server-side).
    • Dockerized (nginx multi-stage, port 3000; Vite env vars are build ARGs).

    Infra

    • docker-compose.yml: 14 services, all enabled with healthchecks (pgvector:pg16, Redis, Keycloak 24.0.5 with Postgres backend, all 6 Java services, MinIO + init, Ollama, Kafka 3.8 KRaft, frontend).
    • Observability compose (separate file): Prometheus scraping all services, Grafana with 2 real provisioned dashboards (Platform Overview + RAG Pipeline — meters match code, not decorative), Loki + Promtail with structured JSON logs (traceId / tenantId / userId via MDC).
    • Custom Micrometer metrics: knowledge_ingestion_queue_depth, knowledge_embedding_duration_seconds, knowledge_search_requests/hits_total, chat_messages_total, chat_messages_escalated_total.
    • k6: core-load-test.js (tickets + search, ramped VUs) and ai-load-test.js (chat, 1 VU by design), calibrated against the live gateway with real JWTs.

    5. Key Interview-Grade Decisions Worth Remembering

    • Outbox over dual-write / XA: @Transactional can't span DB + Kafka without XA; outbox gives local-atomicity-only, at-least-once from producer side.
    • Idempotency strategy differs per service, deliberately: notification-service uses a generic processed_events table (event UUID as PK); ticket-service uses the domain invariant (one ticket per escalated conversation) as its natural idempotency key. Kafka headers carry eventId, not the payload — wire schema stays clean.
    • KRaft over Zookeeper, 3 partitions instead of 50 default (coordinator election storms under CPU pressure on one broker).
    • VARCHAR + CHECK over PG enum types (online migration possible; ALTER TYPE locks).
    • Loose ID refs, no cross-service FKs (no cascade coupling).
    • Outbox + ticket_events are separate tables (delivery concern vs audit concern, different query/retention patterns).
    • afterCommit async dispatch + short per-chunk transactions in ingestion (long transactions in async work are an anti-pattern).
    • JdbcTemplate escape hatch only for vectors; JPA everywhere else.
    • SSE over WebSocket for chat (unidirectional); WebSocket/STOMP for notifications (real push).
    • Escalation is a deterministic heuristic, not a confidence threshold — debuggable; threshold-based escalation is the complementary future signal.

    6. Known Issues & Honest Gaps

    Open bug

    • SSE 120s timeout → 403 (chat-service, unfixed, precisely diagnosed): a slow cold Ollama load can exceed ChatController's hardcoded 120s SseEmitter timeout. On timeout, Tomcat re-dispatches through the filter chain; GatewayAuthenticationFilter (OncePerRequestFilter) doesn't run on async dispatches and its finally already cleared the SecurityContext → second pass sees no auth → AccessDeniedException surfaces as bare 403. DelegatingSecurityContextAsyncTaskExecutor does NOT cover this (different thread path). Deliberately not fixed — needs a tighter feedback loop (e.g., AsyncListener deferring context cleanup); mostly matters for local Ollama dev, not Claude profile.

    Deliberate stubs / absent pieces

    1. DocumentIngestedConsumer (chat-service) — intentional log-only stub.
    2. /settings route — placeholder page.
    3. TicketDetailPage activity timeline — ticket_events exists but isn't rendered from the frontend (Phase 3 polish comment).
    4. Notifications have no durable read API — frontend holds them in session state only; read state not persisted.
    5. Escalation is heuristic-marker only (no similarity-threshold signal).
    6. Zero automated tests anywhere (no Java src/test, no frontend tests) — the biggest engineering gap, acknowledged in INTERVIEW_QA as an honest gap.
    7. No CI — no .github/workflows.
    8. Redis used only by the gateway (rate limiting); no service-level caching.
    9. No Resilience4j circuit breaker on chat→knowledge REST call (documented as next step).
    10. notification-service doesn't consume chat.escalated directly (matches CLAUDE.md §6 topic table; MVP bullet "chat escalated notifications" is covered via ticket.created fan-out instead).

    Resolved bugs (history worth knowing)

    • Phase 9: gateway JWT issuer mismatch (iss claim vs internal hostname — split into internal/issuer URLs) and /api/tickets/** StripPrefix=2 → StripPrefix=1 (empty forwarded path). These mean the true SPA→gateway→service path only started working in Phase 9.
    • Phase 7: Loki 3.x delete_request_store config, stale Docker network after naming it, Keycloak client ID mismatch (tixolve-frontend → tixolve-spa), unused-import build failure, IPv6 healthcheck mismatch in nginx.

    7. Doc Discrepancies Noticed (docs slightly stale vs code)

    • docs/FRONTEND.md still says MUI as the component library and references an MUI theme — the actual stack is Tailwind CSS (switched in Phase 3, CLAUDE.md updated but this doc wasn't).
    • docs/AI_RAG.md citation section mentions a "custom MUI component" — same stale reference.
    • docs/DATA_ARCHITECTURE.md shows vector(1536) in the schema example; actual code uses vector(768) (nomic-embed-text).
    • docs/KAFKA_EVENTS.md / DATA_ARCHITECTURE.md show outbox poll interval as 100ms; actual pollers are 5s (fixedDelay = 5000).
    • BUILD_LOG Phase 5 says llama3.2:1b; the compose default chat model in code is tinyllama (smaller, for the memory-constrained machine). Minor.
    • Chunking: docs say "~500 tokens / 50 overlap"; implementation uses 2000 chars / 200 overlap (equivalent intent, char-based).

    None of these affect correctness — they're doc polish candidates.

    8. What's Left (candidate next steps)

    Per the locked build order, Phases 1–7 and 9 are done; Phase 8 (AWS) is deferred by design. The realistic remaining work:

    1. Frontend polish pass (highest priority per frontend_priority_prompt.md) — walk every screen's states at desktop + mobile widths; /settings page; ticket activity timeline rendering; notification read-state UX.
    2. Automated tests — biggest honest gap; some service-layer + controller tests would strengthen the interview story.
    3. CI (GitHub Actions) — build + test + Docker builds.
    4. Small backend completions — durable notifications read API, escalation similarity-threshold signal, Resilience4j on chat→knowledge, fix the SSE-timeout 403 properly.
    5. Doc refresh — fix the MUI/vector-dim/poll-interval discrepancies listed in §7.
    6. Phase 8 when needed — ECS Fargate demo deploy, on-demand only, minimal footprint, flag always-on costs (NAT GW, RDS, MSK, ALB).

    9. Session History Context (from Claude Code transcripts)

    Timeline: One long working session (Aug 16 → Aug 19, 2026) carried the project from Phase 6 verification through Phase 9 completion. Nothing meaningful has happened since — the repo's last activity is the Phase 9 commit. 17 commits total on main, clean tree. Several short aborted sessions (all just "hi") on Aug 16.

    Working style established in that session (worth mirroring):

    • User drives with short imperatives ("continue working on next phase", "finish calibrating k6 thresholds and commit everything"); the assistant does the heavy lifting autonomously, including long-running Docker monitoring.
    • Work is landed in focused logical commits (e.g., gateway fixes / metrics+dashboard / k6 suite / docs) after diff review. Verification loop is live-stack based: bring containers up, wait for healthchecks, run real requests, record results honestly in BUILD_LOG (including "verified by code review only" caveats).

    Environment constraints confirmed in session:

    • Dev machine is memory/CPU constrained (8 GB Mac; Docker Desktop recommended bump to 6 GB). Heavy debug containers caused k6 threshold failures that were pure resource contention — always re-check under a clean baseline before blaming the code.
    • Ollama cold starts (~30s) dominate local chat verification time; this is what caused the SSE-timeout investigation to be deferred.

    k6 calibrated baselines (standalone clean run): create_ticket p95 89–141ms · list_tickets p95 203–315ms · search p95 1.3–2.0s (Ollama-embedding-bound, environment-dependent).

    Key historical insight from the session (good interview material): all Phase 1–8 verifications hit services directly with trusted headers, bypassing the gateway's JWT validation. Phase 9's k6 run was the first time anything hit the real authenticated gateway path — and it immediately surfaced two latent bugs (JWT issuer mismatch, ticket route StripPrefix). The lesson: "verify through the real ingress, not the shortcut path."
