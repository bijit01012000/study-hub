    Problems in Multithreading | Race Condition, Visibility, Ordering Explained

    23 sections · 4,821 words

    Lecture 50

    Scope evidence: "Problems in Multithreading | Race Condition, Visibility, Ordering Explained" (playlist map, verified) plus the lecture's own repo notes, which enumerate the six problems — race conditions, atomicity, visibility, ordering, thread interference and data inconsistency — starting from shared resources. Repo evidence: 2 Demo files.

    Multithreading lets several threads make progress within one program, improving responsiveness and performance, but it also creates problems whenever threads touch the same mutable data without coordination. The lecture's repo notes enumerate six related problems — race conditions, atomicity, visibility, ordering, thread interference and data inconsistency — and stress that they are connected but not identical. This note follows the same arc: it begins with shared resources and critical sections, dissects each problem in turn, and closes with the tools that prevent them. The central lesson is that thread-safe code must rest on Java Memory Model guarantees, never on assumptions about CPU caches or execution timing.

    1. Shared Resources and the Critical Section

    A shared resource is any data or object that more than one thread can access. Typical examples from the notes include an int count, a List<Integer> numbers and a BankAccount account; more broadly, shared resources include objects in heap memory, static variables, shared collections, files, database connections and network resources.

    A resource becomes dangerous only when it is both shared and mutable. Immutable data can be shared safely because its state cannot change after creation.

    A critical section is the part of the program that reads or modifies shared mutable data and therefore requires controlled access. It is the location where incorrect thread interleaving can cause a problem, and it may hold a single statement or several related statements.

    class Counter {
    int count = 0;          // shared resource
    void increment() {
        count++;            // critical section
    }
}

    For count, the shared resource is the field and the critical section is count++. When a critical section spans several lines, all of them belong to one logical unit:

    if (balance >= amount) {       // part of the same critical section
    balance = balance - amount;
}

    The condition check and the update must be treated together, because another thread can slip between them.

    Important The pattern to fear is shared + mutable. Removing either property — by confining the data or by making it immutable — removes the danger before any lock is needed.

    Memory aid: shared resource = the noun; critical section = the verb that touches it.

    2. Race Conditions: Definition and Interleaving

    A race condition occurs when the correctness of a program depends on the unpredictable timing or execution order of multiple threads. In simple terms, multiple threads race to access or modify the same shared state, and the final result depends on which thread executes first.

    The canonical culprit is count++. It looks like one Java statement, but conceptually it performs three operations:

    1. Read count
    2. Add 1
    3. Write the updated value

    Because these steps can interleave with another thread, count++ is not atomic.

    Consider two threads calling increment() when count = 0. The expected execution is Thread-1: 0 → 1, then Thread-2: 1 → 2, giving the expected final result count = 2. But the following interleaving is equally possible:

    Step Thread-1 Thread-2
    1 Reads count = 0
    2 Reads count = 0
    3 Calculates 1
    4 Calculates 1
    5 Writes 1
    6 Writes 1

    The final result is count = 1. Two increments were attempted, but one update was lost. This is a race condition, and its defining feature is that the program may produce the correct result sometimes and an incorrect result at other times — which is exactly what makes it hard to detect and reproduce.

    3. Complete Race Condition Program

    The repo Demo runs two threads that each increment a shared counter 100,000 times. The expected result is 200000, but a possible result is an arbitrary smaller value such as 173482.

    // Demo.java — two threads increment a shared counter without coordination
class Counter {
    int count = 0;                         // shared resource
    void increment() {
        count++;                           // read → add → write (not atomic)
    }
}

public class Demo {
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Runnable task = () -> {
            for (int i = 1; i <= 100_000; i++) {
                counter.increment();
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(counter.count);  // expected 200000; may be lower
    }
}

    The exact incorrect value is not guaranteed; it depends on thread scheduling and the number of overlapping updates. There is no single wrong answer to observe — only a right answer that is not reliably produced.

    4. Atomicity: Definition and Why It Matters

    An operation is atomic when it appears to other threads as one indivisible action: no other thread can observe or interfere with it halfway through. It starts, completes as one unit, and other threads do not see an intermediate state.

    Atomicity in multithreading is about preventing unsafe interleaving. A thread can be paused by the scheduler between individual operations, so if a task contains several dependent steps and those steps are unprotected, another thread can interfere between them.

    count++ expands conceptually into:

    int temporary = count;      // read
temporary = temporary + 1;  // modify
count = temporary;          // write

    Because these are separate read, modify and write operations, another thread can run between them. The counter race condition is fundamentally caused by a lack of atomicity.

    5. Check-Then-Act and the Money-Transfer Problem

    The check-then-act pattern is a classic atomicity failure. A bank withdrawal performs two related actions — check whether enough balance exists, then deduct the amount:

    void withdraw(int amount) {
    if (balance >= amount) {          // check
        balance = balance - amount;   // act
    }
}

    Suppose balance = 1000 and two threads each attempt to withdraw 800:

    1. Thread-1 checks balance → sufficient
    2. Thread-2 checks balance → sufficient
    3. Thread-1 deducts 800
    4. Thread-2 deducts 800

    Both threads made their decision using the old balance. The condition check and the update must therefore be treated as one atomic operation.

    The same issue appears in a money transfer: deduct from Account A, then add to Account B. If only the first step completes, the system is inconsistent. No other thread should observe a partially completed state where money has been deducted but not yet credited; the complete transfer must be protected as one logical operation.

    6. Solving Atomicity Problems

    The repo notes give three common solutions, and the correct choice depends on the complexity of the operation.

    1. Using synchronized — wrap the whole logical unit:
    synchronized void increment() {
    count++;
}
    1. Using atomic classes — for simple state transitions:
    AtomicInteger count = new AtomicInteger();
count.incrementAndGet();
    1. Using explicit locks — when advanced features are required:
    Lock lock = new ReentrantLock();

    7. Atomic and Non-Atomic Operations (Including long and double)

    A simple read or write of most Java primitive values and object references is atomic:

    int x = 10;
x = 20;
int y = x;
Object value = new Object();

    Another thread will not observe half of an int value or half of an object reference. But atomicity alone does not guarantee visibility: a write may be atomic yet still not become visible without a proper happens-before relationship.

    Several everyday operations are not atomic:

    Operation Why it is not atomic
    count++ / count-- read → modify → write
    x += 5 conceptually x = x + 5; contains a read and a write
    Check-then-act (if (balance > 0) withdraw();) another thread can change balance between check and action
    list.add(1) / map.put(key, value) may perform several internal operations; thread safety depends on the collection
    if (!map.containsKey(key)) map.put(key, value); the check-then-put sequence is not atomic even on a thread-safe map

    For collections, the notes state plainly: ArrayList is not thread-safe, HashMap is not thread-safe, and ConcurrentHashMap is designed for concurrent access. Even so, a sequence of method calls may still need extra synchronization; the complete check-then-put is not automatically atomic unless an atomic API such as putIfAbsent() is used.

    The long and double case deserves its own rule. The Java Language Specification permits a non-volatile long or double read or write to be treated as two separate 32-bit operations. On most modern JVMs and processors these operations are implemented atomically, but portable Java code should not depend on that implementation detail. Declaring them volatile guarantees atomic reads and writes:

    volatile long value;
volatile double amount;

    This still does not make compound operations atomic: value++ remains a read-modify-write sequence even when value is volatile.

    8. Visibility Problems

    A visibility problem occurs when one thread updates shared data but another thread does not reliably observe the updated value. The first thread may have performed the write correctly; the problem is that another thread has no synchronization guarantee requiring it to see that write.

    Visibility problems occur because modern systems improve performance through CPU caches, processor registers, compiler optimizations, JVM optimizations and instruction reordering. A simplified mental model is:

    Thread → CPU registers and caches → Shared memory

    This model is useful for understanding the problem, but the Java Memory Model does not define visibility as simply reading directly from RAM or CPU cache. The important rule is: without a happens-before relationship, one thread is not guaranteed to observe another thread's write.

    The repo example uses a flag that an updater thread sets to true while an observer thread loops while (!flag). The expected behavior is that the updater changes flag to true and the observer exits the loop. However, without proper synchronization the observer is not guaranteed to detect the update. A possible result is that Flag updated to true prints while the observer continues looping: the write happened, but another thread did not reliably observe it.

    9. Using volatile for Visibility

    Declaring the flag volatile closes the visibility gap:

    static volatile boolean flag = false;

    A volatile write happens-before every subsequent volatile read of the same variable. Therefore, if Thread-1 writes flag = true and Thread-2 later reads flag, Thread-2 must observe the updated value. volatile also prevents certain reorderings around volatile reads and writes.

    What volatile guarantees:

    1. Visibility
    2. Ordering guarantees around the volatile access
    3. Atomic reads and writes of the volatile variable itself

    It is best suited for simple state communication where one thread writes a value and other threads read it, for example volatile boolean running, volatile boolean shutdownRequested or volatile int currentState.

    What volatile does not guarantee: it does not make compound operations atomic. With volatile int count = 0, the increment still performs read count → add 1 → write count, and two threads can still read the same old value and overwrite one another. Hence:

    volatile  → visibility and ordering
volatile  ≠ compound-operation atomicity

    For atomic increments use AtomicInteger.incrementAndGet(), or protect the operation with synchronization.

    10. Visibility Through Synchronization

    synchronized provides visibility through monitor operations, which create happens-before relationships. When Thread-1 releases a monitor and Thread-2 later acquires the same monitor, Thread-2 can observe writes made before Thread-1 released it.

    synchronized (lock) {
    count++;
}

    The guarantee depends on both threads coordinating through the same monitor. It is not enough for one thread to synchronize while another thread accesses the same state without synchronization.

    11. Ordering Problems and Reordering

    Ordering refers to the sequence in which memory operations become observable. A programmer may write:

    int data = 0;
boolean ready = false;

// Thread-1
data = 10;
ready = true;

// Thread-2
if (ready) {
    System.out.println(data);
}

    The intended logic is: write data → mark data as ready → another thread observes ready → another thread reads data. Without synchronization, that ordering is not guaranteed between threads.

    Reordering happens because compilers, the JVM and processors may reorder instructions to improve performance, using techniques such as instruction scheduling, register allocation, pipelining, store buffering and common-subexpression elimination. Reordering is permitted as long as behavior remains valid according to single-thread semantics and the Java Memory Model.

    The consequence is the classic example. With initial state int data = 0; boolean ready = false;, a programmer expects Thread-2 to print 10. But without a happens-before relationship, Thread-2 is not guaranteed to observe the write to data merely because it observes ready as true. It could observe ready = true and data = 0. This may happen because of visibility effects, reordering, or both.

    12. Preventing Ordering Problems

    With volatile — declare the publication flag as volatile:

    int data = 0;
volatile boolean ready = false;

    The volatile write and read establish the required ordering:

    write data = 10
  → volatile write ready = true
  → volatile read ready == true
  → read data

    If Thread-2 observes the volatile write to ready, it must also observe the preceding write to data. This is the safe-publication pattern.

    With synchronized — the same monitor works for both sides:

    synchronized (lock) {
    data = 10;
    ready = true;
}

synchronized (lock) {
    if (ready) {
        System.out.println(data);
    }
}

    The guarantee comes from monitor release followed by subsequent acquisition of the same monitor. It is more accurate to say that synchronization creates ordering and visibility guarantees between threads; the JVM may still reorder internal instructions when doing so does not violate those guarantees.

    Happens-before rule What it orders
    Program order Actions in one thread appear in source order to that same thread
    Monitor lock A release of a monitor happens-before every subsequent acquire of the same monitor
    Volatile variable A write to a volatile field happens-before every subsequent read of that field
    Thread start A call to Thread.start() happens-before any action in the started thread
    Thread termination All actions in a thread happen-before another thread returns successfully from join()
    Transitivity If A happens-before B and B happens-before C, then A happens-before C

    13. Thread Interference

    Thread interference occurs when operations from multiple threads interleave in a way that causes one thread to disturb the work of another:

    Thread-1 reads count
Thread-2 reads count
Thread-1 writes new value
Thread-2 overwrites that value

    It is usually the visible effect of shared mutable state, non-atomic operations, missing synchronization and unsafe interleaving. The lost update above is both a result of interference and an example of a race condition.

    14. Race Condition vs Thread Interference

    The terms are related but emphasize different aspects:

    Aspect Race condition Thread interference
    Emphasis The broader correctness problem The harmful overlapping of operations
    Description The result depends on thread timing or ordering One thread's operation disrupts another thread's operation
    Relationship A superset framing of timing-dependent bugs The mechanism that produces many race conditions
    Example Two threads increment the same counter Lost update when one write overwrites another
    Overlap A lost update is an example of a race condition The same lost update is a result of interference

    15. Data Inconsistency and Its Forms

    Data inconsistency means the state stored by the program no longer matches its expected rules or real-world meaning. Race conditions, visibility problems, ordering problems and interference can all produce it. The notes list six common forms:

    1. Lost update — two threads perform an update, but one update is overwritten (count++).
    2. Stale read — one thread observes an older value because the latest update is not visible (while (!flag), may continue using a stale value).
    3. Inconsistent read — a thread observes related fields from different logical moments, for example accountBalance reflects the new state while transactionStatus still reflects the old state.
    4. Partial update — only part of a multi-step operation is visible or completed, for example money deducted from Account A but not yet credited to Account B.
    5. Check-then-act failure — a thread acts on a condition that was true when checked but became false before the action (if (balance >= amount) balance -= amount;).
    6. Unsafe publication — a thread receives a reference to an object before the object's state has been safely made visible, so it may observe default or stale field values.

    16. Preventing Multithreading Problems

    The notes present a toolkit; the correct choice depends on the shape of the problem.

    1. Using synchronized — when several operations must execute as one unit, multiple fields form one consistency rule, mutual exclusion and visibility are both required, or threads must later coordinate with wait() and notifyAll().
    2. Using atomic classes — AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference, useful for simple atomic state transitions without protecting a larger compound operation.
    3. Using explicit locks — ReentrantLock provides interruptible lock acquisition, timed lock attempts, fairness policies and multiple condition objects, but requires manual release, usually inside finally.
    4. Using thread-safe collections — ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue, ConcurrentLinkedQueue; the choice depends on whether the workload is read-heavy, write-heavy, blocking or non-blocking.
    5. Using immutability — a properly constructed and safely published immutable object can be read by many threads, removing many synchronization requirements by design.
    6. Avoiding shared mutable state — the safest shared mutable state is the state that is not shared; techniques include thread-local variables, method-local variables, message passing, immutable snapshots, task confinement and dividing work so each thread owns separate data.
    // Demo2.java — an immutable object can be shared without locks
final class User {
    private final String name;
    private final int age;

    User(String name, int age) {
        this.name = name;
        this.age = age;
    }

    String name() { return name; }
    int age()     { return age; }
}

    // Demo2.java — AtomicInteger makes the whole increment one atomic unit
import java.util.concurrent.atomic.AtomicInteger;

public class AtomicDemo {
    static AtomicInteger count = new AtomicInteger();
    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) {
                count.incrementAndGet();
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(count.get());   // exactly 200000
    }
}

    // Demo2.java — volatile closes the visibility gap for a stop flag
public class VisibilityDemo {
    static volatile boolean flag = false;   // write happens-before later read
    public static void main(String[] args) throws InterruptedException {
        Thread updater = new Thread(() -> {
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            flag = true;
            System.out.println("Flag updated to true");
        });
        Thread observer = new Thread(() -> {
            while (!flag) { }               // waits until the latest value is seen
            System.out.println("Detected flag change");
        });
        updater.start();
        observer.start();
        updater.join();
        observer.join();
    }
}

    Important Immutability and reduced sharing are design-level fixes that eliminate whole classes of problems; synchronization and atomics are the fallback when sharing is unavoidable.

    17. Comparison Tables and Choosing the Correct Tool

    The six problems share a root cause but differ in what goes wrong and how it is fixed:

    Problem Cause Symptom Fix
    Race condition Result depends on thread timing or ordering Non-deterministic wrong result (counter off) Synchronization, atomics or reduced sharing
    Atomicity problem A multi-step operation is interrupted or interleaved Lost update, partial update (count++) synchronized, atomic class, explicit lock
    Visibility problem One thread does not observe another thread's write Stale read (non-volatile stop flag) volatile or a happens-before via locking
    Ordering problem Operations observed in an unexpected order Publication flag seen before data volatile on the flag, or same-monitor locking
    Thread interference Threads overlap and disturb each other's work Lost update Mutual exclusion and atomic units
    Data inconsistency State violates expected rules Incorrect balance or stale data Correct mechanism for the guarantee required

    volatile, synchronized and the atomic classes are often confused; their guarantees differ sharply:

    Aspect volatile synchronized Atomic classes
    Visibility Yes Yes Yes (for the atomic variable)
    Ordering Yes, around the access Yes, across monitor boundaries Yes (for the atomic variable)
    Mutual exclusion No Yes No
    Compound-operation atomicity No Yes Yes, for the operations it provides
    Blocking Never blocks May block acquiring the monitor Usually lock-free (CAS)
    Suitable for One writer, many readers of a status flag Several statements that must be one unit Simple atomic state transitions
    Caveat count++ stays non-atomic Both threads must use the same monitor Does not cover a larger compound operation

    Choosing the mechanism is a matter of matching the requirement to the guarantee:

    Requirement Suitable mechanism
    Simple visible status flag volatile
    Atomic counter update AtomicInteger
    Several statements must be atomic together synchronized or Lock
    Concurrent map access ConcurrentHashMap
    Producer-consumer communication BlockingQueue or wait() / notifyAll()
    State that should never change Immutable object
    Avoid sharing entirely Thread confinement or message passing

    Interviewer's perspective The three questions that unlock every concurrency question are: atomicity — can another thread interfere halfway? visibility — can another thread see the latest value? ordering — in what order do writes become observable? Name the guarantee the code lacks, then name the tool that supplies it.

    18. Myth vs Reality

    Myth Reality
    "count++ is one Java statement, so it is atomic." It is a read → modify → write sequence and can interleave; one update can be lost.
    "volatile makes any variable thread-safe." It gives visibility, ordering and atomic single reads/writes, but not compound-operation atomicity.
    "synchronized is only about mutual exclusion." It also creates visibility and ordering guarantees through monitor happens-before boundaries.
    "A thread-safe collection makes a sequence of calls atomic." It protects its own operations; check-then-put still needs putIfAbsent() or a lock.
    "Once a write completes, every thread sees it." Without a happens-before relationship, another thread is not guaranteed to observe the write.

    19. Common Trap Questions

    Trap 1 — "Is count++ atomic?" No. It reads, modifies and writes; without protection two threads can read the same old value and overwrite each other, producing a lost update.

    Trap 2 — "A simple int read or write is atomic — so it is also safe." Atomicity holds, but visibility does not automatically follow. A non-volatile read may return a stale value without a happens-before relationship.

    Trap 3 — "Does volatile fix the counter race condition?" No. volatile int count does not make count++ atomic. Use AtomicInteger or synchronization for the compound operation.

    Trap 4 — "Are non-volatile long and double reads and writes atomic?" The JLS permits them to be treated as two 32-bit operations. Most JVMs implement them atomically, but portable code should use volatile to guarantee it — and even then value++ is not atomic.

    Trap 5 — "If one thread synchronizes, that is enough." No. Both threads must coordinate through the same monitor; one thread synchronizing while another accesses the state unsynchronized provides no guarantee.

    Trap 6 — "Java forbids instruction reordering." Reordering is allowed as long as single-thread semantics and the Java Memory Model are respected. Volatile accesses and monitor boundaries constrain which reorderings are permitted.

    Trap 7 — "A ConcurrentHashMap makes check-then-put atomic." No. if (!map.containsKey(key)) map.put(key, value); is still two calls; use putIfAbsent() for atomicity.

    20. Points to Remember

    1. Shared mutable data is the primary source of concurrency problems.
    2. count++ is not atomic even though it is one Java statement.
    3. A race condition depends on unpredictable thread timing.
    4. Atomicity prevents unsafe interleaving of a logical operation.
    5. Visibility determines whether one thread can observe another thread's writes.
    6. Ordering determines how operations become observable between threads.
    7. volatile provides visibility and ordering guarantees but does not make compound operations atomic.
    8. synchronized provides mutual exclusion, visibility and ordering through monitor boundaries.
    9. All threads must follow the same synchronization policy.
    10. Thread-safe collections protect their own operations, but a sequence of calls may still require atomic coordination.
    11. Immutable objects and reduced sharing simplify concurrent design.
    12. Correct concurrent code should be based on Java Memory Model guarantees, not assumptions about CPU caches or execution timing.

    21. Likely Interview Questions

    Question Crisp Answer
    What is a race condition? A correctness failure whose result depends on the unpredictable timing or order of threads accessing shared state.
    Is count++ atomic? No — it is read, add, write, and can interleave; protect it with synchronization or an atomic class.
    What is a critical section? The code region that reads or modifies shared mutable data and therefore needs controlled access.
    Why is shared mutable state dangerous? Multiple threads can interleave unsafely on it; immutable or unshared data avoids the problem.
    What is atomicity? An operation that appears to other threads as one indivisible action with no observable intermediate state.
    What is the check-then-act problem? A condition is checked and acted on separately, so it can change in between; the check and action must be atomic together.
    What is a visibility problem? One thread writes shared data but another thread is not guaranteed to observe the updated value.
    What does volatile guarantee? Visibility, ordering around the access, and atomic reads/writes of that variable — but not compound-operation atomicity.
    How does synchronized provide visibility? Monitor release happens-before a later acquire of the same monitor, so writes become observable.
    What is an ordering problem? Memory operations may become observable in an unexpected order because of reordering without a happens-before relationship.
    Race condition vs thread interference? A race condition is the broader timing-dependent correctness problem; interference is the harmful overlapping of operations that produces it.
    What causes data inconsistency? Race conditions, visibility, ordering and interference can all leave state violating its expected rules (lost update, stale read, partial update).

    22. Final Summary

    shared mutable state + multiple threads
        → missing coordination
        → unsafe interleaving / reordering / stale caches
        → race conditions and thread interference
        → lost updates, stale reads, ordering failures
        → data inconsistency
    • Shared resource → dangerous only when shared and mutable; immutable data is safe.
    • Critical section → the code that touches that state; its steps must be one logical unit.
    • Race condition → correctness depends on timing; count++ is not atomic.
    • Atomicity → can another thread interfere halfway? Fixed by synchronized, atomic classes or locks.
    • Visibility → can another thread see the latest value? Fixed by volatile or a happens-before via the same monitor.
    • Ordering → in what order do writes become observable? Fixed by a volatile publication flag or shared-monitor locking.
    • Thread interference and data inconsistency → the visible effects: lost updates, stale reads, partial updates.
    • Prevention → synchronization, volatile, atomic classes, explicit locks, thread-safe collections, immutability and reduced sharing.

    Golden rule Name the guarantee the code lacks — atomicity, visibility or ordering — then apply the smallest mechanism that supplies exactly that guarantee, and make every thread follow the same synchronization policy.

    One-line takeaway: shared mutable state plus missing coordination produces race conditions, atomicity failures, visibility and ordering faults, interference and data inconsistency — and the Java Memory Model, not CPU timing, tells you which tool restores each guarantee.
