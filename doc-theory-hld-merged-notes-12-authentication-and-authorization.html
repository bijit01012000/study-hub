    Authentication and Authorization

    11 sections · 1,188 words

    Who you are versus what you are allowed to do.

    1. Definitions

    • Authentication: who you are. What is your identity? Handled at sign-up and login.
    • Authorization: what you can do. Access control and access policies.

    In the flow, a client talks to the application over HTTP; the server authenticates (login with username and password) and then authorizes (access rights).

    2. Requirements

    1. User registration (sign up): allow users to register by providing the necessary information.
    2. Login: authenticate users based on their credentials.
    3. Multi-Factor Authentication (MFA): implement a robust MFA system.
    4. Password recovery: provide a secure process for users to recover their passwords.
    5. Session management: efficiently manage user sessions to ensure security - in a stateless architecture we still need to manage sessions.
    6. Access control: manage user roles (admin, user, etc.) to control what they can access.

    3. Back-of-the-Envelope Calculation

    User traffic: 100K users per day.
QPS = 100000 / 86400 = 1.15 req/sec

    Storage: we must store user details for authentication and authorization, assuming 5KB per user and estimating for 5 years.

    Total storage = 100000 * 365 * 5 * 2^10 * 5
              = 0.1 * 10^6 * 365 * 5 * 5 * 2^10
              = 914 * 2^20 * 2^10
              = 914 * 2^30
              = ~914 GB

    4. 1FA vs MFA

    • 1FA: username and password go to the auth DB; the authentication server returns OK to the client (for example Instagram).
    • MFA: the same flow plus a notification server, which sends a second factor.

    5. Session Management

    • In a stateless architecture, HTTP requests carry no memory of earlier requests, so sessions must be managed explicitly.
    • A sessionId can be stored on the server side (DB/cache) and sent by the client in HTTP/HTTPS headers.
    • Two styles:
    • Session Ids (session-based auth).
    • Token Ids (token-based auth) -> JWT.
    • Session means connection. The DB holds a session table with user, sessionId, and a TTL (for example 15 mins).
    • The client (browser) can hold the sessionId in cookies.

    6. Token-Based Authentication (JWT)

    A more secured way. On login, the auth server generates a token, using a secretKey. The token is an encrypted object containing:

    • User info (name, email).
    • Permissions (roles -> authorization).
    • TTL (time to live).

    The client stores tokens in HTTPOnly cookies. Types of tokens:

    1. Access token.
    2. Refresh token.

    6.1 Access Token Flow

    1. Every request after authentication arrives with an access token.
    2. The application server decrypts the access token using its own secret key.
    3. It checks the TTL of the access token.
    4. If not expired, the application server checks user permissions.
    5. The user is then allowed to interact.

    6.2 Refresh Token

    • Access token TTL: short (for example 1 hour).
    • Refresh token TTL: long (for example 1 day).

    When the access token is expired, the user generates a new one:

    POST /generate/token
Headers: refresh token
Response: access token

    6.3 JWT in Practice

    GET /user/profile
Authorization: Bearer eY123adB121adB

    Secret key flow: token -> encrypt -> encrypted token -> decrypted token (secret key).

    6.4 Why Two Tokens?

    • The access token is sent with every HTTP request. If a hacker steals it, it has only a limited time to be exploited.
    • The refresh token is never sent to API calls; it is used only when a new token needs to be generated.

    Gmail example (web browser):

    1. Log in to Gmail; the access token is valid for 1 hour.
    2. Leave the browser unattended for 3 hours.
    3. The browser auto-refreshes: Gmail silently uses the refresh token to get a new access token.
    4. After a few days the refresh token expires, and Gmail asks you to sign in again.

    7. How Passwords Are Stored

    1. First way - plain text: store { username: "aditya", password: "aditya123" } directly. This is bad.
    2. Store hashed passwords: aditya123 -> hash(aditya123) -> qwe1234 -> save to DB.

    A rainbow table is a huge data set of commonly used passwords. Basic algorithms include SHA-1, SHA-256, Bcrypt, and Argon2; a password like password123 or aditya123 can be brute-forced through permutation and combination (A-Z, 0-9, a-z).

    1. Salt and Pepper technique: - User: aditya; password: aditya123. - Salt: a random string, for example tyu78, so aditya123 + tyu78. - hash(aditya123tyu78) = wer3247. Store the salted and hashed password plus the salt in the DB (hashPassword: wer3247, salt: tyu78). - Pepper: a predefined string, for example asdf123, kept at a very, very secure location. Combine: aditya123 -> aditya123tyu78 -> asdf123aditya123tyu78, then hash(asdf123aditya123tyu78) = were324, stored as the hash password with the salt. - The pipeline: plain password -> plain password + salt + pepper -> hash -> store hash to DB.

    7.1 Good Hash Functions

    • A hash function for passwords should be slow, not fast.
    • Basic hash functions such as SHA-1, SHA-256, and MD5 can hash billions of records in a second, enabling a rainbow attack (password -> hash in microseconds).
    • Why slow is good: slow hash functions make it infeasible for an attacker to run a rainbow attack. Good algorithms include Argon2, bcrypt, and scrypt, which take milliseconds.
    • The user experience is not impacted, but the hacker's experience is; a brute-force attack becomes infeasible.

    8. Authorization

    Authorization is about access rights. Three models:

    1. Role Based Access Control (RBAC): roles such as admin, member, owner. For example, admin can kick a member out; a member and owner have their own privileges.
    2. Policy Based Access Control (PBAC): dynamic rules/privileges called policies. For example, some users can access paid questions; a new policy could be "no more than 3 requests per second".
    3. Access Control List (ACL): highly granular control. Individual permissions can be turned on/off, and different permissions can be on/off for every user.

    9. API Endpoints

    POST www.instagramclone.com/register
{
  "username": "aditya",
  "fullName": "",
  "password": "",
  "mobileNo": "",
  "email": ""
}

POST /login
{
  "username": "",
  "password": ""
}

POST /logout
Mark user session as inactive (revoke authentication).

    Others:

    • /create/{userId}
    • /grant/{userId}/{permissionId}
    • /revoke/{userId}/{permissionId}
    • /expire/{sessionId}
    • /validate/{sessionId}

    10. Table Structure

    • User table - basic user info: userId, email, name, username, role, createdAt, updatedAt, etc.
    • Credential table - credentialID, email (FK), access_token, refresh_token.
    • Password table - passwordId, email (FK), hashed_Password, salt, last_login, etc.
    • Session table - active sessions of a user (history): sessionId, email (FK), last_logged_in, etc.

    11. Flows

    • User registration: client /register -> auth server -> DB stores user, password, session.
    • Login: client /login -> auth server validates password, generates an access token and a refresh token -> DB.
    • Session management: the refresh token sits in the DB; the refresh flow returns a new access token.
    • Complete flow: DNS -> client -> LB -> rate limiting -> web tier -> auth server -> app server -> notification server -> DB tier.
    • Logout: client /logout -> auth server marks the session inactive -> returns OK.
