    Lecture 37 — Spring Security Authentication Internals

    22 sections · 3,831 words

    Lecture 37

    Scope evidence: "Spring Security Authentication Internals | Complete Login Flow" (playlist map, verified). Repo folder is the springPracticalDemo project: config.SecurityConfig, entity.CustomUserDetails, service.CustomUserDetailsService, service.AuthService, service.RoleService, entity.User, entity.Role, repository.UserRepository, repository.RoleRepository, dto.UserRegisterRequestDto/UserRegisterResponseDto, controller.UserController/controller.RoleController, and application.properties.

    Authentication turns a plain HTTP request into a trusted identity, and Spring Security does it inside servlet filters before DispatcherServlet ever runs. This lecture opens the hood: how filters get into Tomcat, how a chain is selected, how an unverified username/password claim becomes a verified Authentication, and how that result is stored for authorization. Everything below is the database-backed username-and-password path.

    1. Where Spring Security Works

    Spring Security's servlet support is built on servlet filters:

    HTTP Request -> Servlet Filters -> Spring Security Filters -> DispatcherServlet -> Controller

    Security runs before the controller to establish who is sending the request, whether the identity is valid, what authorities it holds, and whether access is allowed. The key principle is Protection -> Authentication -> Exception Handling -> Authorization. A simplified order:

    Stage Concern
    Exploit protection CSRF and similar protections
    Authentication form login (UsernamePasswordAuthenticationFilter), HTTP Basic (BasicAuthenticationFilter)
    Anonymous authentication attach an anonymous identity when no credentials exist
    Security context handling load and later store the SecurityContext
    Exception translation turn auth errors into HTTP responses
    Authorization decide whether the authenticated user may proceed

    Authentication must happen before authorization: Spring Security cannot decide whether a user has ROLE_ADMIN until it has established who that user is.

    Important: The controller never sees an unauthenticated request for a protected path. Security either produces an authenticated identity or stops the request in the filter layer, so business code can assume "there is a user".

    2. DelegatingFilterProxy: The Bridge

    DelegatingFilterProxy is a real servlet filter known to Tomcat. It does not implement all of Spring Security; it finds a filter bean managed by Spring and delegates to it:

    doFilter(request, response, chain):
    Filter springFilter = findFilterBeanInSpring();
    springFilter.doFilter(request, response, chain);

Tomcat -> DelegatingFilterProxy -> FilterChainProxy

    It bridges the servlet-container lifecycle with Spring-managed filter beans. Tomcat only knows servlet filters; the security work lives in Spring beans, and this class is the adapter between them.

    3. FilterChainProxy and SecurityFilterChain

    FilterChainProxy is the central filter of Spring Security's servlet architecture, standing in front of one or more SecurityFilterChain objects:

    FilterChainProxy
|-- SecurityFilterChain for /api/**
|-- SecurityFilterChain for /admin/**
+-- SecurityFilterChain for every other request

    For every request it asks which SecurityFilterChain should process it, then runs that chain's filters. A SecurityFilterChain is a request matcher plus an ordered list of security filters:

    interface SecurityFilterChain:
    boolean matches(HttpServletRequest request);
    List<Filter> getFilters();

    Example chains:

    Chain 1: /api/**
    Filters: SecurityContextHolderFilter, BearerTokenAuthenticationFilter,
             ExceptionTranslationFilter, AuthorizationFilter

Chain 2: every request
    Filters: SecurityContextHolderFilter, CsrfFilter,
             UsernamePasswordAuthenticationFilter, BasicAuthenticationFilter,
             AnonymousAuthenticationFilter, ExceptionTranslationFilter,
             AuthorizationFilter

    The precise list depends on the features enabled through HttpSecurity.

    Interviewer's perspective: The two names are easy to confuse. FilterChainProxy is the single dispatcher; SecurityFilterChain is one of the routes it can pick. One proxy, many chains.

    4. SecurityFilterChain Matching and Ordering

    A RequestMatcher decides whether a chain applies by inspecting request path, HTTP method, headers, servlet path, parameters, and dispatcher type. For GET /api/users, the matcher /api/** returns true and /admin/** returns false.

    First matching chain wins: FilterChainProxy invokes only the first matching SecurityFilterChain. With Chain 1: /api/** then Chain 2: /**, both match /api/users, but Spring Security selects Chain 1 and stops; it never combines filters from two chains. So chains run most specific to most general:

    1. /api/**
2. /admin/**
3. /**

    If no chain matches, the request is unprotected, so a fallback chain is useful:

    @Bean
SecurityFilterChain fallback(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated());
    return http.build();
}

    If no securityMatcher(...) is configured, the chain normally applies to every request.

    Important: "First matching chain wins" is what makes ordering matter. A broad /** chain declared first swallows every request, and the specific chains below it never run.

    5. HttpSecurity: The Chain Builder

    HttpSecurity is a builder that describes and constructs a SecurityFilterChain:

    http
    .csrf(Customizer.withDefaults())
    .formLogin(Customizer.withDefaults())
    .httpBasic(Customizer.withDefaults())
    .authorizeHttpRequests(auth -> auth.anyRequest().authenticated());

http.csrf(...)                  -> CSRF protection
http.formLogin(...)             -> form-login filters and handlers
http.httpBasic(...)             -> HTTP Basic authentication
http.authorizeHttpRequests(...) -> authorization rules

    It describes which features are enabled, which filters are required and in what order, which providers they use, and which authorization rules apply; return http.build(); produces the concrete SecurityFilterChain.

    6. Authentication Filters: Form Login vs HTTP Basic

    Different mechanisms receive credentials in different forms. Form login arrives as POST /login with Content-Type: application/x-www-form-urlencoded and body username=aditya&password=secret123, handled by UsernamePasswordAuthenticationFilter. HTTP Basic arrives as Authorization: Basic YWRpdHlhOnNlY3JldDEyMw==, handled by BasicAuthenticationFilter.

    A filter does not authenticate every request. UsernamePasswordAuthenticationFilter looks for a form-login request such as POST /login; for an ordinary GET /courses it just continues the chain (chain.doFilter(request, response);). So the filter's presence does not mean an attempt happens on every request; it first checks whether the request carries the mechanism it understands.

    Aspect Form login HTTP Basic
    Filter UsernamePasswordAuthenticationFilter BasicAuthenticationFilter
    Credential location Request body, form-encoded Authorization header, Base64
    Trigger request POST /login Any request carrying the header
    Backend after the filter Same AuthenticationManager + provider Same AuthenticationManager + provider

    Important: Seeing UsernamePasswordAuthenticationFilter in the chain does not mean every call re-authenticates. The filter only acts when the request carries its mechanism; otherwise it steps aside and the chain continues.

    7. Authentication and the Request Token

    The request holds plain values username = aditya and password = secret123. Spring Security converts them into a standard object, commonly a UsernamePasswordAuthenticationToken. Before verification:

    UsernamePasswordAuthenticationToken
|-- principal = "aditya"
|-- credentials = "secret123"
|-- authorities = []
+-- authenticated = false

    At this stage the token is only a claim: someone says they are Aditya and offers secret123 as proof, but Spring Security has not accepted it. The unauthenticated token is created as:

    UsernamePasswordAuthenticationToken token =
    UsernamePasswordAuthenticationToken.unauthenticated(username, password);

    principal is the claimed identity and credentials is the claimed proof. The filter must not contain database or password logic; its job is to extract credentials, create an Authentication, and send it to the engine.

    Interviewer's perspective: The same class, UsernamePasswordAuthenticationToken, represents both the unverified claim and the verified result. The difference is the three fields: authenticated, authorities, and whether credentials are still present.

    8. AuthenticationManager: Entry Point

    AuthenticationManager is the entry point into Spring Security's authentication engine:

    interface AuthenticationManager:
    Authentication authenticate(Authentication authentication)
            throws AuthenticationException;

    It receives an unauthenticated token and produces one of two outcomes:

    Unauthenticated Authentication
    -> AuthenticationManager.authenticate(...)
        +-- Success -> Authenticated Authentication
        +-- Failure -> AuthenticationException

    The interface says nothing about databases or BCrypt: it only turns one Authentication into another or throws, which lets Spring Security swap mechanisms without changing the caller.

    9. ProviderManager and AuthenticationProvider

    AuthenticationManager is an interface; its most common implementation is ProviderManager. An app can support many mechanisms -- database username/password, JWT, OTP, LDAP, SAML, remember-me, custom -- and ProviderManager coordinates the available AuthenticationProvider objects:

    ProviderManager
|-- DaoAuthenticationProvider
|-- JwtAuthenticationProvider
|-- RememberMeAuthenticationProvider
+-- CustomOtpAuthenticationProvider

    Each provider understands a particular token type via boolean supports(Class<?> authenticationType);. DaoAuthenticationProvider supports UsernamePasswordAuthenticationToken; JwtAuthenticationProvider supports a JWT token. When ProviderManager receives a UsernamePasswordAuthenticationToken, it finds a supporting provider, which does the verification. For database username/password this is DaoAuthenticationProvider.

    Mechanism Provider Token it consumes
    Database username/password DaoAuthenticationProvider UsernamePasswordAuthenticationToken
    JWT JwtAuthenticationProvider JWT authentication token
    Remember-me RememberMeAuthenticationProvider remember-me token
    One-time password CustomOtpAuthenticationProvider custom OTP token

    10. UserDetails and UserDetailsService

    Our app has its own User entity, but Spring Security does not know its structure and should not depend on our persistence model. It uses two contracts:

    UserDetails        -> Spring Security's view of one user
UserDetailsService -> Strategy for finding that user

    Our entity may carry id, username, password, email, name, createdAt, preferences, and roles; Spring Security mainly needs username, stored password, authorities, enabled state, and account/credential expiration and lock state. UserDetails is its view of one user:

    interface UserDetails:
    String getUsername();
    String getPassword();
    Collection<? extends GrantedAuthority> getAuthorities();
    boolean isAccountNonExpired();
    boolean isAccountNonLocked();
    boolean isCredentialsNonExpired();
    boolean isEnabled();

    Spring Security is effectively saying: store users however you want, but give me an object satisfying this contract. UserDetailsService answers the other question via UserDetails loadUserByUsername(String username); -- given a username, how should Spring Security load that user? So UserDetails is one user (the result) and UserDetailsService is the finder.

    Aspect UserDetails UserDetailsService
    Role One loaded user (the result) The strategy that loads a user (the finder)
    Key method getUsername(), getPassword(), getAuthorities() loadUserByUsername(String username)
    Count Represents a single user Can load any user by username
    Example CustomUserDetails CustomUserDetailsService
    Failure none (it is data) throws UsernameNotFoundException if absent

    The service is where our repository meets Spring Security:

    @Service
@RequiredArgsConstructor
public class CustomUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    @Override
    public UserDetails loadUserByUsername(String username) {
        User user = userRepository
            .findByUsername(username)
            .orElseThrow(() -> new UsernameNotFoundException("User not found"));
        return new CustomUserDetails(user);
    }
}

    The final line converts our application's User into Spring Security's UserDetails view. If email is the login identity, the same contract can query by email with findByEmail(email).

    11. CustomUserDetails vs Spring's Built-in User

    An app may contain com.coderarmy.entity.User, and Spring Security also provides org.springframework.security.core.userdetails.User. They are not the same class: the application User is a database entity and domain model, while Spring Security's User is a built-in UserDetails implementation. We do not have to use that concrete class; a custom adapter often makes the bridge clearer:

    class CustomUserDetails implements UserDetails:
    private final User user;
    getUsername()    -> user.getUsername();
    getPassword()    -> user.getPassword();
    getAuthorities() -> user.getRoles().stream()
                            .map(role -> new SimpleGrantedAuthority(role.getName()))
                            .toList();
    isEnabled()      -> user.isEnabled();

    This adapts our database entity to the interface Spring Security understands. The custom class is not compulsory: we can instead build Spring Security's User directly with withUsername(...).password(...).authorities(...).disabled(!user.isEnabled()).build(). The custom class is useful when the mapping should be explicit or when we need extra domain-user properties.

    Golden rule: UserDetails is a contract, not a class. Our entity is the truth; CustomUserDetails (or the built-in User) is the read-only view Spring Security consumes.

    12. DaoAuthenticationProvider

    We now have a user-loading flow: Spring Security -> username -> UserDetailsService -> UserRepository -> Database User -> CustomUserDetails -> UserDetails. We still need one component that can receive the request, load the user, obtain the stored encoded password, compare it, check account state, and return a trusted result. That component is DaoAuthenticationProvider, an AuthenticationProvider designed for username/password authentication using a UserDetailsService and a PasswordEncoder:

    DaoAuthenticationProvider -> UserDetailsService -> UserRepository -> Database
                          -> PasswordEncoder -> BCryptPasswordEncoder -> verification

    DAO stands for Data Access Object: user information is retrieved from a user-data source before credentials are verified.

    13. The Complete Internal Login Flow

    The full flow is one sequence:

    HTTP Request -> Authentication Filter
    -> Unauthenticated UsernamePasswordAuthenticationToken
    -> AuthenticationManager -> ProviderManager -> DaoAuthenticationProvider
         |-- UserDetailsService -> Repository -> Database
         +-- PasswordEncoder -> Password verification
    -> Authenticated UsernamePasswordAuthenticationToken
    -> SecurityContext -> SecurityContextHolder -> Authorization -> Controller

    Mnemonic for the login steps: C-T-P-L-A-P-S-C-A-C -- Credentials, Token, Provider selected, Load user, Account status, Password, Success token, Context, Authorization, Controller.

    1. The filter extracts credentials: UsernamePasswordAuthenticationFilter for form login, BasicAuthenticationFilter for HTTP Basic.
    2. It creates an unauthenticated token (principal="aditya", credentials="secret123", authorities=[], authenticated=false) and calls authenticationManager.authenticate(token);.
    3. ProviderManager picks the provider supporting UsernamePasswordAuthenticationToken: DaoAuthenticationProvider.
    4. The provider reads the claimed username and calls userDetailsService.loadUserByUsername("aditya");.
    5. CustomUserDetailsService runs findByUsername, throwing UsernameNotFoundException if absent, else returning new CustomUserDetails(user).
    6. Account state is checked: isEnabled(), isAccountNonLocked(), isAccountNonExpired(), isCredentialsNonExpired(); a disabled account fails even with the right password.
    7. The password is verified with passwordEncoder.matches(rawPassword, userDetails.getPassword());, which checks the stored BCrypt representation; the raw password is never re-encoded and string-compared.
    8. On success the provider returns a trusted token: principal=CustomUserDetails, credentials erased/null, authorities=ROLE_USER, authenticated=true.
    9. The result is stored: Authentication -> SecurityContext -> SecurityContextHolder.
    10. Authorization runs rules like .requestMatchers("/admin/**").hasRole("ADMIN") and .anyRequest().authenticated(); the controller then executes and never re-checks the password.
    Aspect Unauthenticated token Authenticated token
    When Created by the filter before verification Returned by the provider after verification
    principal The claimed username string A UserDetails / CustomUserDetails object
    credentials The raw password Erased or null
    authorities Empty list [] Populated, e.g. ROLE_USER
    authenticated flag false true
    Meaning A claim, not yet trusted A verified identity

    14. What Happens When Authentication Fails

    User not found throws UsernameNotFoundException("User not found"). A wrong password makes passwordEncoder.matches("wrongPassword", storedEncodedPassword) return false, so authentication fails, commonly through a BadCredentialsException. It can also fail on invalid account state: disabled, locked, expired, or expired credentials. In every case nothing trusted is stored in the security context.

    Important: BadCredentialsException is deliberately vague about which half failed. Spring Security avoids revealing whether the username existed, a small but real protection against account enumeration.

    15. Form Login, HTTP Basic, and Registration: Shared vs Separate Flows

    Form login and HTTP Basic receive credentials differently but share the same database-authentication engine:

    Form Login  -> UsernamePasswordAuthenticationFilter
HTTP Basic  -> BasicAuthenticationFilter
Both        -> UsernamePasswordAuthenticationToken -> AuthenticationManager
            -> DaoAuthenticationProvider -> Database authentication

    The filters differ only in HTTP credential format; the verification is identical. Registration stores a new user while login verifies an existing one:

    Registration: Client -> AuthService -> PasswordEncoder.encode(...)
    -> BCrypt hash -> UserRepository -> Database

Login: Client -> Authentication filter -> AuthenticationManager
    -> DaoAuthenticationProvider -> PasswordEncoder.matches(...) -> Authenticated

    Registration uses passwordEncoder.encode(rawPassword);; login uses passwordEncoder.matches(rawPassword, storedEncodedPassword);.

    Aspect Registration Login
    Goal Store a new user Verify an existing user
    Encoder method encode(rawPassword) matches(rawPassword, storedEncodedPassword)
    Who runs it AuthService (a normal service) Filters + AuthenticationManager + provider
    Password in DB Stored as a BCrypt hash Read and compared, never re-encoded for comparison
    Output Saved user + response DTO Authenticated Authentication
    Role selection Server assigns the default role Roles are read from the loaded user

    The server should assign the default role: a normal registration request must not choose an administrative role, so a payload like {"username": "hacker", "password": "123", "role": "ROLE_ADMIN"} is rejected by design. Instead the server runs roleRepository.findByName("ROLE_USER").orElseThrow() and adds that role. The endpoint should also return a response DTO rather than the entity containing the stored password.

    Golden rule: encode when you create, matches when you verify. Never encode the login password and compare hashes as strings; BCrypt is salted, so the same password encodes differently every time.

    16. Project Structure, CSRF, Testing, and the Final Mental Model

    A possible structure:

    entity/ User.java, Role.java          repository/ UserRepository.java, RoleRepository.java
dto/ RegisterRequest.java, UserResponse.java
security/ CustomUserDetails.java, CustomUserDetailsService.java
service/ AuthService.java             controller/ AuthController.java, TestController.java
config/ SecurityConfig.java

    Spring Security can auto-build much of this when the required beans exist, but creating the provider explicitly makes the dependencies visible:

    @Configuration
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Bean
    public DaoAuthenticationProvider authenticationProvider(
            CustomUserDetailsService userDetailsService,
            PasswordEncoder passwordEncoder) {
        DaoAuthenticationProvider provider = new DaoAuthenticationProvider(userDetailsService);
        provider.setPasswordEncoder(passwordEncoder);
        return provider;
    }

    @Bean
    public SecurityFilterChain securityFilterChain(
            HttpSecurity http, DaoAuthenticationProvider provider) throws Exception {
        http
            .csrf(csrf -> csrf.disable()) // classroom demo only
            .authenticationProvider(provider)
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/register").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated()
            )
            .formLogin(Customizer.withDefaults())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}

    CSRF and the Postman demo: with CSRF enabled, POST /register can be rejected if Postman sends no valid token, so the classroom demo temporarily disables it with .csrf(csrf -> csrf.disable()). That is a demo decision, not a production recommendation.

    Testing an authenticated endpoint: because of .anyRequest().authenticated(), /profile requires authentication, and /me displays the current Authentication:

    @GetMapping("/me")
public Map<String, Object> me(Authentication authentication) {
    SecurityContext context = SecurityContextHolder.getContext();
    Authentication current = context.getAuthentication();
    return Map.of(
        "username", current.getName(),
        "authorities", current.getAuthorities(),
        "authenticated", current.isAuthenticated()
    );
}

    Suggested demonstration sequence:

    1. Create the default ROLE_USER role in the roles table.
    2. Register via POST /register with {"username":"aditya","password":"secret123"} and show the DB stores an encoded password, not the raw one.
    3. GET /me without credentials returns no protected data.
    4. GET /me with HTTP Basic (aditya / secret123) returns the authenticated username and authorities.
    5. A wrong password fails even though the user exists.
    6. A disabled account (enabled = false) fails even with the correct password, proving account state is part of the decision.

    Final mental model, four layers: receive credentials (UsernamePasswordAuthenticationFilter or BasicAuthenticationFilter), represent the request (UsernamePasswordAuthenticationToken), authenticate it (AuthenticationManager -> ProviderManager -> DaoAuthenticationProvider), and load/verify the user (UserDetailsService -> UserRepository -> Database, plus PasswordEncoder). After success: Authenticated Authentication -> SecurityContext -> SecurityContextHolder -> Authorization -> Controller.

    17. Myth vs Reality

    Myth Reality
    "Spring Security checks authentication inside the controller" It runs in servlet filters before DispatcherServlet; the controller sees an already-decided request.
    "Every request with an authentication filter re-authenticates" A filter acts only when the request carries its mechanism; otherwise it continues the chain.
    "All matching SecurityFilterChains are combined" Only the first matching chain runs; the rest are never consulted.
    "UserDetailsService returns the database entity" It returns a UserDetails; CustomUserDetails converts the entity into that contract.
    "DaoAuthenticationProvider compares passwords as strings" It delegates to PasswordEncoder.matches(...), which verifies against the salted BCrypt hash.
    "The authenticated token still keeps the raw password" Credentials are erased or set to null after success so the raw password is not retained.
    "ROLE_ADMIN may be chosen by the client at signup" The server assigns the default role; registration must not pick an admin role.

    18. Common Trap Questions

    Trap 1 - "The controller should verify the password again." Verdict: False. By the time the request reaches the controller, authentication is done and the result is in the SecurityContext; re-checking duplicates work and re-opens the risk of leaks.

    Trap 2 - "If /api/** and /** both match, both chains run." Verdict: False. The first matching chain wins; Spring Security does not merge filters from later chains, which is why specific matchers must be declared first.

    Trap 3 - "UsernamePasswordAuthenticationToken is only the verified result." Verdict: False. The same class carries both states. Before verification it has authenticated=false, empty authorities, and raw credentials; after success those fields change.

    Trap 4 - "AuthenticationManager knows about the database." Verdict: False. It only promises authenticate(...) -> result or AuthenticationException; its ProviderManager implementation delegates to a supporting AuthenticationProvider such as DaoAuthenticationProvider.

    Trap 5 - "A disabled account still authenticates if the password is right." Verdict: False. Account state (isEnabled, lock, expiry) is checked and can fail authentication even with a correct password.

    Trap 6 - "CSRF being disabled in the demo is production guidance." Verdict: False. Disabling CSRF was a temporary classroom decision for a short Postman demo; the right production setting depends on how clients authenticate.

    19. Points to Remember

    1. Spring Security runs in servlet filters before DispatcherServlet, in the order Protection -> Authentication -> Exception Handling -> Authorization.
    2. DelegatingFilterProxy bridges the servlet container (Tomcat) and Spring-managed filter beans.
    3. FilterChainProxy chooses the first matching SecurityFilterChain; chains run most specific to most general, with a /** fallback.
    4. HttpSecurity is the builder; http.build() produces the concrete SecurityFilterChain.
    5. Authentication filters extract credentials and create a token; they never query the database, and their presence does not mean every request is authenticated.
    6. UsernamePasswordAuthenticationToken starts as an unverified claim (authenticated=false, empty authorities) and later becomes the verified identity.
    7. AuthenticationManager (usually ProviderManager) routes the token to the AuthenticationProvider that supports(...) it; DaoAuthenticationProvider handles username/password.
    8. UserDetails is one user (the result); UserDetailsService.loadUserByUsername is the finder; CustomUserDetails adapts our entity.
    9. DaoAuthenticationProvider combines UserDetailsService with PasswordEncoder; registration uses encode(...), login uses matches(...).
    10. On success the authenticated object is stored in the SecurityContext via SecurityContextHolder, then authorization runs and the controller executes; credentials are erased.

    20. Likely Interview Questions

    Question Crisp Answer
    What is the security filter order? Protection -> Authentication -> Exception Handling -> Authorization, with anonymous/context handling around them.
    What does DelegatingFilterProxy do? It is a servlet filter that finds a Spring-managed filter bean and delegates to it, bridging Tomcat and Spring.
    What does FilterChainProxy do? It picks the first matching SecurityFilterChain and runs that chain's filters.
    What does HttpSecurity do? It is a builder describing enabled features, filters, providers, and authorization rules; build() creates the chain.
    Does UsernamePasswordAuthenticationFilter authenticate every request? No; it only acts on a form-login request it recognizes, otherwise it continues the chain.
    What is UsernamePasswordAuthenticationToken? Spring Security's Authentication for username/password; unauthenticated first, authenticated after provider verification.
    What is AuthenticationManager? The authentication entry point (authenticate returns a result or throws); its common implementation is ProviderManager.
    UserDetails vs UserDetailsService? UserDetails is one user (the result); UserDetailsService is how to find that user (the finder).
    What does DaoAuthenticationProvider combine? A UserDetailsService (load the user) and a PasswordEncoder (verify the password), then checks account state.
    Why encode for registration and matches for login? encode stores a salted hash; matches verifies a raw password against that hash, since BCrypt hashes differ per call.

    21. Final Summary

    HTTP Request
    -> DelegatingFilterProxy -> FilterChainProxy -> SecurityFilterChain
    -> Authentication Filter -> token (authenticated = false)
    -> AuthenticationManager -> ProviderManager -> DaoAuthenticationProvider
         |-- UserDetailsService -> UserRepository -> Database -> CustomUserDetails
         +-- PasswordEncoder.matches(raw, encoded)
    -> Authenticated Authentication -> SecurityContext -> SecurityContextHolder
    -> Authorization -> Controller
    • Security is a filter-layer concern: Protection -> Authentication -> Exception Handling -> Authorization.
    • DelegatingFilterProxy bridges the container; FilterChainProxy selects the first matching SecurityFilterChain.
    • Authentication filters extract credentials and build a token; they never touch the database.
    • ProviderManager routes by token type to DaoAuthenticationProvider, pairing UserDetailsService with PasswordEncoder.
    • Success stores a verified Authentication in the SecurityContextHolder; failure raises an AuthenticationException.
    • Registration (encode) and login (matches) are separate flows; the server assigns roles and returns a DTO.

    One-line takeaway: Spring Security turns a plain request into a trusted identity by extracting credentials into a token, letting the right provider verify it against the database and encoder, and storing the verified result in the SecurityContextHolder so authorization and the controller can trust it.
