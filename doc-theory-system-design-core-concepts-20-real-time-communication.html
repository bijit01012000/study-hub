    Real-Time Communication

    6 sections · 617 words

    Four ways to get a live update. Networking & Communication, concept 20 of 36.

    The Idea

    How does a client find out something changed without the user hitting refresh? Four answers, each trading simplicity for how real-time and how expensive it is to hold open.

    Mechanism How it works Cost
    Polling client asks anything new every few seconds, whether or not there is anything wasteful, and delay up to the poll interval
    Long polling server holds the request open until there is something to say less wasteful, still one request per update
    SSE one long-lived connection, server pushes events whenever it wants, one-way only auto-reconnects, plain HTTP
    WebSockets one long-lived connection, either side sends anytime, fully two-way the right call for chat, live collaboration

    Polling and long polling both cost one request per update, they just differ in how wasteful the wait between updates is. SSE and WebSockets both hold one connection open instead, which is cheaper per update but means the server has to keep far more connections alive at once.

    • Polling and long polling both run over plain, ordinary HTTP requests, nothing special needed on either end.
    • WebSockets start as a normal HTTP request and use the HTTP Upgrade mechanism to switch protocol.
    • SSE never upgrades at all: it is just an ordinary HTTP response whose body keeps streaming.

    Watch Out For

    • WebSockets bypass normal HTTP load balancing assumptions. A connection is pinned to one server for its whole life, which needs its own scaling plan.
    • Polling too aggressively, chasing lower latency, can produce more load than a properly designed WebSocket or SSE connection would have.

    Where You Will See It

    • Slack and Discord, built on WebSockets for real-time messaging.
    • Stock tickers and live sports scores, a classic SSE use case.
    • Older web apps, and some mobile clients, still using long polling where WebSocket support was historically inconsistent.

    How It Connects

    • HTTP/1.1 vs HTTP/2 vs HTTP/3: WebSockets start as a normal HTTP request before upgrading protocol; SSE just keeps a plain HTTP response streaming, no upgrade involved.
    • Load Balancing: the live connection itself is pinned to whichever server accepted it, but a reconnect only needs sticky routing back to that same server if its session state lives there too; externalize that state and any server can pick the reconnect up.
    • Message Queues: often sit behind a WebSocket server, fanning updates out to many connected clients.

    Follow-Up Questions

    1. A dashboard needs to update every few minutes and does not need to feel instant. What is the simplest fit? Polling. It is wasteful per-request, but the simplicity is worth it when the delay does not matter.

    2. A chat app needs messages to arrive instantly in both directions. What fits? WebSockets: a single long-lived, two-way connection, the right tool when both sides need to send at any time.

    3. A live sports score feed only needs the server pushing updates, never the client sending anything back. What fits, and why not WebSockets? SSE. It is simpler than WebSockets and runs over plain HTTP, and the feed only needs one direction anyway.

    4. Long polling and short polling both poll. What is actually different about long polling? The server holds the request open until it has something to say, instead of answering immediately with nothing, cutting out most of the wasted round trips.

    Recall It As

    Polling asks. Long polling waits. SSE pushes one way. WebSockets push both ways.
