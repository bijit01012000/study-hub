    Java Exception Handling from Scratch | Exceptions vs Errors

    17 sections · 3,951 words

    Lecture 43

    Scope evidence: "Java Exception Handling from Scratch | Exceptions vs Errors" (playlist map, verified). Repo evidence: 4 Demo files.

    An exception is a recoverable, abnormal condition that arises while a program runs and that the application is expected to detect, handle and recover from. An error is a serious, JVM-level failure that the application is not expected to handle: memory is exhausted, the call stack has overflowed, or a class could not be linked. Both are objects, both descend from Throwable, and both can be thrown, yet they occupy opposite ends of the recoverable/unrecoverable divide. This lecture builds exception handling from that distinction: the Throwable hierarchy, checked versus unchecked exceptions, the mechanics of try/catch/finally, try-with-resources, catch ordering and multi-catch, exception chaining, and the pitfalls that turn good error handling into silent failure.

    1. What an Exception Is and What an Error Is

    An exception is a runtime event that disrupts the normal instruction flow but which a well-written program can anticipate and survive. Reading a file that does not exist, parsing text that is not a number, or opening a network socket that is unreachable are all ordinary conditions: the program can catch the problem, inform the user, retry, or fall back. Handling them is part of the program's contract.

    An error is a fault in the runtime itself, not in the application's logic. When the heap is full (OutOfMemoryError), when a recursive call never terminates (StackOverflowError), or when a class references code that cannot be linked (LinkageError), there is no sensible recovery for the application. The correct response is to let the error propagate, log it, and terminate the affected thread or process — not to swallow it and continue.

    The central design consequence: both can be caught mechanically, because both are Throwable objects, but the judgment of whether one should be caught is what separates a professional handler from a dangerous one. Catch exceptions; report and stop on errors.

    2. The Throwable Hierarchy: Everything Is an Object

    Java models every abnormal outcome as an instance of a class rooted at java.lang.Throwable. The hierarchy splits into exactly two branches:

    Throwable
|-- Error                                   (unrecoverable, JVM-level)
|     |-- OutOfMemoryError
|     |-- StackOverflowError
|     +-- LinkageError
+-- Exception                               (recoverable, application-level)
      |-- RuntimeException  (unchecked)
      |     |-- NullPointerException
      |     |-- ArithmeticException
      |     |-- ArrayIndexOutOfBoundsException
      |     +-- IllegalArgumentException
      +-- checked exceptions
            |-- IOException
            |-- SQLException
            +-- ClassNotFoundException

    Three facts follow from the tree:

    1. Every throwable is an object. A thrown exception is an instance carrying a message, a stack trace, an optional cause, and possibly suppressed exceptions. It can be stored, passed, logged and inspected.
    2. Error and Exception are siblings, not parent and child. RuntimeException sits under Exception, so unchecked exceptions are still exceptions, not errors.
    3. Throwable is the common catch-all. Catching Throwable catches errors too and is almost always a mistake; catching Exception still misses errors.

    Important Only instances of Throwable (and its subclasses) may be used with throw and may appear in a catch clause. You cannot throw an arbitrary object.

    3. Exception vs Error

    Aspect Exception Error
    Meaning Recoverable, abnormal application condition Serious JVM-level failure
    Origin Application logic or an external resource The runtime/environment itself
    Recoverable Yes — handle, retry, or report Normally no — stop the affected work
    Declared checked Some are (checked) Never checked
    Root branch Exception Error
    Typical classes IOException, SQLException, NullPointerException OutOfMemoryError, StackOverflowError, LinkageError
    Should an app catch it? Yes, the ones it can act on No — let it propagate and log
    Recoverable stance Part of robust control flow A signal to terminate, not to continue

    Reading the table by rows: the two branches answer the same question — can the application do anything meaningful about this? — with opposite answers. The tree shape (Section 2) and the handling policy (this table) are the two halves of the same design.

    4. Checked vs Unchecked Exceptions

    A checked exception must be either caught or declared in the method's throws clause; the compiler refuses to compile otherwise. An unchecked exception (every RuntimeException and Error) carries no such obligation — the compiler does not track it at all.

    Aspect Checked exceptions Unchecked exceptions
    Root Exception (excluding RuntimeException) RuntimeException (and Error)
    Compiler enforcement Declare with throws or catch, or compile error None — no declaration required
    Typical examples IOException, SQLException, ClassNotFoundException, InterruptedException NullPointerException, ArithmeticException, ArrayIndexOutOfBoundsException, NumberFormatException, ClassCastException
    Signals A recoverable condition the caller can act on (I/O, network, DB) A programming bug or an invariant violation
    When to use For conditions outside the program's control that a caller can reasonably handle For defects that should be fixed, not handled
    Typical handling Catch, wrap, retry, or declare and let a higher layer decide Validate inputs first; fix the code path

    The design guidance is the useful part: use a checked exception when the caller genuinely has a reasonable recovery path and the language should force it to acknowledge that path; use an unchecked exception when the caller could not have done anything sensible, because the code itself is wrong.

    Interviewer's perspective "Why are some exceptions checked?" Checked exceptions encode a recoverable obligation in the type system: the compiler forces every caller either to handle the condition or to declare it upward, so an external failure (a file, a socket, a database) cannot be silently ignored. Unchecked exceptions are reserved for programmer errors, where forcing a declaration on every method would add noise without adding safety.

    5. The Mechanics of try, catch and finally

    The try block contains the code that may fail; one or more catch blocks handle specific failure types; an optional finally block runs cleanup whether or not an exception is thrown. finally executes on the normal path, on the exception path, and even when a return, break or continue leaves the try — the only things that prevent it are System.exit() and a JVM crash.

    // Demo.java — try/catch/finally: the finally block always runs
public class Demo {
    public static void main(String[] args) {
        try {
            int result = 10 / 0;                 // throws ArithmeticException
            System.out.println(result);          // never reached
        } catch (ArithmeticException e) {
            System.out.println("Caught: " + e.getMessage());   // / by zero
        } finally {
            System.out.println("finally always runs");         // cleanup lives here
        }
    }
}

    The execution model in four steps:

    1. The JVM enters the try block and executes statements in order.
    2. A statement throws; the JVM constructs the throwable object and immediately abandons the rest of the try.
    3. The JVM searches the catch clauses top to bottom for the first matching type and runs that handler.
    4. Whether a handler ran or not, the finally block executes before control leaves the construct.

    finally is the pre-try-with-resources idiom for releasing resources (closing files, sockets, locks). It is correct but verbose, which is precisely the problem try-with-resources solves.

    Important A finally block that executes return overrides any earlier return and can even discard an in-flight exception. Avoid return inside finally.

    6. try-with-resources: Automatic, Ordered Cleanup

    Since Java 7, try-with-resources declares resources in the try header and closes them automatically. Any object implementing AutoCloseable (directly, or through Closeable) qualifies: streams, readers, writers, database connections, sockets. The compiler generates the closing calls, and they run in reverse order of declaration — the last resource opened is the first one closed, mirroring the dependency order of nested wrappers.

    // Demo2.java — try-with-resources closes the reader even if an exception is thrown
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class Demo2 {
    public static void main(String[] args) {
        try (BufferedReader br = new BufferedReader(new FileReader("data.txt"))) {
            String line;
            while ((line = br.readLine()) != null) {
                System.out.println(line);
            }
        } catch (IOException e) {              // IOException is checked
            System.out.println("I/O error: " + e.getMessage());
        }                                      // br.close() runs here automatically
    }
}

    The comparison with the manual idiom is decisive:

    Aspect try/catch/finally try-with-resources
    Closing code Written by hand in finally Generated by the compiler
    Null-safety Must null-check before close() Handled automatically
    Suppressed exceptions Easily lost or clobbered by hand Preserved as suppressed exceptions
    Resource order Programmer's responsibility Guaranteed reverse order
    Verbosity High for several resources One declaration per resource
    Prone to leaks Yes, if a branch forgets to close No — every declared resource closes
    Preferred since Pre-Java 7 Java 7 onward

    With multiple resources, declare them separated by semicolons and they close right-to-left, so a wrapper is closed before the stream it wraps.

    Memory aid "Open left to right, close right to left" — the resource declared last is the one finalized first, so a wrapper is closed before the stream it wraps.

    7. Multiple Catch Blocks, Multi-catch and Catch Order

    A single try may have several catch blocks so that different failure types get different responses. When several handlers share identical code, Java 7's multi-catch merges them into one clause: catch (IOException | SQLException e). The parameter of a multi-catch is implicitly final and its static type is the nearest common supertype, so only members shared by all alternatives are visible on e.

    Order matters. The JVM selects the first matching clause, so a subclass must be caught before its superclass. Catching Exception first and IOException second is a compile-time error, because the later clause is unreachable.

    // Demo3.java — multi-catch handles unrelated checked types in one clause
import java.io.IOException;
import java.sql.SQLException;

public class Demo3 {
    static void work(int mode) throws IOException, SQLException {
        if (mode == 1) throw new IOException("disk failed");
        if (mode == 2) throw new SQLException("query failed");
    }

    public static void main(String[] args) {
        try {
            work(1);
        } catch (IOException | SQLException e) {   // e is effectively final
            System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }
}

    The two ordering rules to memorize:

    1. Specific before general. catch (FileNotFoundException e) must precede catch (IOException e), which must precede catch (Exception e).
    2. Multi-catch cannot combine a type with its own subclass. catch (IOException | FileNotFoundException e) does not compile; one is redundant and the compiler rejects it.

    8. Useful Throwable Methods and Exception Chaining

    Every throwable carries diagnostic state. Four methods are used constantly:

    Method Returns Purpose
    getMessage() String The human-readable description passed to the constructor
    printStackTrace() void Writes the full stack trace to System.err
    getCause() Throwable The wrapped original exception, or null
    getStackTrace() StackTraceElement[] The frame array, for programmatic inspection
    toString() String Class name plus message, e.g. java.io.IOException: disk failed

    Exception chaining is the practice of wrapping a low-level exception in a higher-level one while preserving the original as the cause. Because the cause is retained, a log shows both the business-level message and the true root cause; when the cause is dropped, the original failure is lost forever.

    // wrap-and-rethrow: preserve the original cause so the root cause is never lost
class DataAccessException extends Exception {
    DataAccessException(String message, Throwable cause) {
        super(message, cause);                 // cause is stored for later getCause()
    }
}

class Service {
    static void load() throws DataAccessException {
        try {
            throw new java.io.IOException("config file missing");
        } catch (java.io.IOException e) {
            throw new DataAccessException("Could not start service", e);   // keep the cause
        }
    }
}

    Interviewer's perspective "What is exception chaining?" Wrapping a caught exception inside a new exception while passing the original as the cause argument, so no diagnostic information is lost. Without the cause, the new exception tells you what failed at a high level but not why.

    9. throw and throws

    The two keywords are distinct and easily confused:

    1. throw is a statement used inside a method to actually raise a throwable: throw new IllegalArgumentException("age must be positive");. It takes exactly one Throwable object. (Statement-level detail is expanded in Lecture 44.)
    2. throws is a clause in a method signature that declares which checked exceptions the method may let escape: void read() throws IOException. It documents the recoverable obligations the caller must meet.
    static int parseAge(String text) throws NumberFormatException {  // unchecked: declaration optional
    int age = Integer.parseInt(text);                            // may throw NumberFormatException
    if (age < 0) {
        throw new IllegalArgumentException("age must be positive");  // raise it yourself
    }
    return age;
}

    Checked exceptions must be declared; unchecked ones may be declared for documentation but the compiler does not require it.

    10. Best Practices for Exception Handling

    1. Catch the most specific type you can actually handle, not Exception or Throwable.
    2. Never swallow an exception. An empty catch block hides failure and makes bugs invisible; at minimum log it.
    3. Log with context — the operation, the inputs, and the exception object — not just the message string.
    4. Do not use exceptions for normal control flow. Exceptions are for exceptional conditions, and they are far more expensive than ordinary branches.
    5. Fail fast. Validate arguments at the boundary and reject bad input immediately with a precise exception.
    6. Close resources — prefer try-with-resources over manual finally cleanup.
    7. Preserve the cause when wrapping; never replace a low-level exception with a vague one.
    8. Restore interrupted status in catch (InterruptedException e) by calling Thread.currentThread().interrupt() and then handling the abort.
    9. Document declared exceptions in Javadoc @throws tags so callers know the obligations.
    10. Keep handlers honest: if you catch and continue, the program state must still be valid.

    Golden rule Handle what you can fix, wrap what you cannot, and never hide what you do not understand.

    11. The Pitfall Catalogue

    Pitfall Example What happens Fix
    Catching too broadly catch (Exception e) Masks bugs and unrelated failures in one handler Catch the specific types you can handle
    Catching Throwable catch (Throwable t) Catches Errors such as OutOfMemoryError and continues in a broken state Catch Exception, not Throwable
    Empty catch (swallow) catch (IOException e) {} Failure disappears; later state is corrupt Log, wrap, or rethrow
    finally returns finally { return x; } Overrides an earlier return and discards a pending exception Never return from finally
    Losing the cause throw new ServiceException("failed") Root cause is gone Pass the caught exception as the cause
    Out-of-bounds access arr[arr.length] ArrayIndexOutOfBoundsException at runtime Check bounds or iterate the array safely
    Divide by zero a / b with b == 0 ArithmeticException for integers Validate the divisor before dividing
    Resource leak FileReader with no close File handles leak until the process ends Use try-with-resources
    Checked exception in a lambda list.forEach(s -> read(s)) where the body throws IOException Lambda cannot throw checked exceptions; compile error Wrap in a try/catch inside the lambda and rethrow unchecked
    Wrong catch order catch (Exception e) before catch (IOException e) Compile error: unreachable second clause Put specific types before general ones

    The common thread: every pitfall either hides a failure or leaks a resource, and both are cured by being specific — about the type, the cause, and the closure.

    12. Myth vs Reality

    Myth Reality
    "Errors and exceptions are the same thing" Both extend Throwable, but Error is an unrecoverable JVM failure and Exception is a recoverable application condition.
    "Catching Exception is a safe catch-all" It hides bugs and still misses Errors; catching it broadly is an anti-pattern, not safety.
    "The finally block runs only when an exception is thrown" It runs on every exit from the try — normal, exceptional, return, or break (System.exit and JVM crash excepted).
    "finally is as good as try-with-resources" try-with-resources closes in reverse order, is null-safe, and preserves suppressed exceptions; hand-written finally is error-prone.
    "Unchecked exceptions do not need to be handled at all" They compile without handling, but they still crash the thread if nothing handles them; they should be prevented or handled deliberately.

    13. Common Trap Questions

    Trap 1 — Catching the wrong root: "Which of these is an Exception and which an Error: OutOfMemoryError, IOException, StackOverflowError, SQLException?" IOException and SQLException are exceptions (recoverable, and checked). OutOfMemoryError and StackOverflowError are errors (unrecoverable). An application should not try to handle either error.

    Trap 2 — finally and return: "A try returns 1 and its finally returns 2. What does the method return?" 2. A return in finally overrides any previous return and even discards an in-flight exception; it is a well-known trap and a reason never to return from finally.

    Trap 3 — Unreachable catch: "Why does try { ... } catch (Exception e) { } catch (IOException e) { } fail to compile?" Because Exception is a supertype of IOException, the first clause always matches, so the second is unreachable — a compile-time error. Order handlers from the most specific type to the most general.

    Trap 4 — Swallowed exception: "A method catches NumberFormatException and returns 0. What is the bug?" Returning 0 hides malformed input and lets the program continue with a wrong value. That is exception swallowing; the handler should at least log and communicate the failure.

    Trap 5 — Losing the cause: "A service wraps an IOException as ServiceException but logs only 'service failed'. What went wrong?" The original IOException was not passed as the cause, so the root cause is lost. Construct the wrapper with super(message, cause) and surface getCause().

    Trap 6 — finally versus try-with-resources: "Two resources are opened in a try-with-resources. In what order do they close?" In reverse order of declaration — the last opened is the first closed. The same discipline applies to hand-written finally, which is why try-with-resources is preferred.

    Trap 7 — Checked inside a lambda: "Why does names.forEach(n -> Files.readAllBytes(Path.of(n))) not compile?" readAllBytes throws the checked IOException, but the Consumer contract does not declare checked exceptions, so the lambda cannot propagate it. Wrap the call in a try/catch inside the lambda (and rethrow as unchecked) or restructure the code.

    14. Points to Remember

    1. Throwable is the root; Error and Exception are its two branches, and RuntimeException sits under Exception.
    2. An exception is recoverable and should be handled; an error is an unrecoverable JVM failure and should not be caught.
    3. Checked exceptions must be caught or declared with throws; unchecked exceptions (all RuntimeExceptions) carry no compiler obligation.
    4. finally runs whether or not an exception is thrown — including on return — except for System.exit() and a JVM crash.
    5. try-with-resources closes any AutoCloseable automatically, in reverse declaration order, and preserves suppressed exceptions.
    6. Catch the most specific type first; a subclass after its superclass is a compile error because the clause is unreachable.
    7. Multi-catch (catch (A | B e)) merges handlers with identical bodies; its parameter is implicitly final.
    8. getMessage(), printStackTrace(), getCause() and getStackTrace() are the standard diagnostic methods.
    9. Wrap-and-rethrow with the original as the cause to preserve the root cause; never drop it.
    10. Best practices: catch specifically, never swallow, log with context, fail fast, close resources, and never use exceptions for ordinary control flow.

    15. Likely Interview Questions

    Question Crisp Answer
    Difference between Exception and Error? Exception is a recoverable application condition an app can handle; Error is a serious JVM-level failure (OutOfMemoryError, StackOverflowError) that apps should not attempt to handle.
    What is the Throwable hierarchy? Throwable is the root; Error and Exception are its subclasses; RuntimeException extends Exception, and unchecked exceptions are RuntimeException plus Error.
    Checked vs unchecked exceptions? Checked must be caught or declared in throws; unchecked (RuntimeException) need no declaration and typically signal programming bugs.
    Does finally always run? Yes — on normal exit, on exception, and on return/break — except when System.exit() is called or the JVM crashes.
    Why is try-with-resources preferred? It closes every AutoCloseable automatically in reverse order, is null-safe, and preserves suppressed exceptions, avoiding resource leaks.
    What is multi-catch? A single catch (A \| B e) clause that handles several unrelated exception types with identical handling; e is implicitly final.
    Why must specific catch blocks precede general ones? The first matching clause is selected; a general clause before a specific one makes the later clause unreachable and fails compilation.
    What is exception chaining? Wrapping a caught exception inside a new one while passing the original as the cause, so no diagnostic information is lost.
    throw vs throws? throw raises a throwable inside a method; throws declares in the signature which checked exceptions the method may let escape.
    Why not catch Throwable? It catches Errors too, and continuing after an unrecoverable JVM failure leaves the application in an undefined state.
    What is exception swallowing? An empty or silent catch block that discards the failure without logging, wrapping, or rethrowing it, hiding the bug.
    Why can a lambda not throw a checked exception? The functional interface (Consumer, Function) does not declare checked exceptions, so the lambda body must handle them internally.

    16. Final Summary

    throw statement --> JVM builds a Throwable object (message + stack trace + cause)
      |
      v
search enclosing try blocks for the first matching catch (specific before general)
      |
      +--> match found    --> run the handler
      +--> no match       --> run finally, then propagate to the caller
                                  |
                                  +--> still uncaught --> default handler logs it, thread dies

Throwable ⊃ Error (unrecoverable)  and  Exception ⊃ RuntimeException (unchecked) + checked
    • Definitions -> exception = recoverable and handled; error = unrecoverable JVM failure.
    • Hierarchy -> Throwable roots both Error and Exception; RuntimeException marks unchecked.
    • Checked vs unchecked -> the compiler forces declaration or catch for checked; unchecked signals bugs.
    • Control flow -> try guards, catch handles, finally always cleans up (System.exit excepted).
    • Resources -> try-with-resources closes AutoCloseable objects in reverse order; preferred over manual finally.
    • Handlers -> specific before general; multi-catch merges like handlers; never swallow or catch Throwable.
    • Diagnostics -> preserve the cause with wrap-and-rethrow so the root cause survives.

    Golden rule Catch what you can recover from, declare what you cannot, clean up in every path, and never let a failure vanish without a trace.

    One-line takeaway: exceptions are recoverable and yours to handle, errors are the JVM's to crash on, and disciplined handling means catching specific types, closing resources automatically, and always preserving the cause.
