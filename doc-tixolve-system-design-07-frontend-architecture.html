    Frontend Architecture

    8 sections · 1,000 words

    Section 7 of 11

    Tech Stack

    Tool Purpose
    React + TypeScript UI framework — type safety catches bugs at compile time
    Vite Build tool — native ES modules in dev, no bundle step, instant HMR
    Material UI (MUI) Component library — fully customized theme, not defaults
    TanStack React Query Server state management — caching, background refetch, deduplication
    React Router Client-side routing
    Keycloak JS PKCE auth flow integration

    Why Vite over CRA? CRA is deprecated and Webpack-based. Vite dev server starts in milliseconds (no bundle step — serves ES modules directly to the browser). HMR is near-instant. Production build uses Rollup.

    Custom MUI Theme (Design Tokens)

    The app does NOT use MUI's default purple/blue theme. Every color, font, and radius is overridden:

    // shared/theme/tokens.ts
export const tokens = {
  palette: {
    ink:     '#14181F', // dark surfaces, text on light
    paper:   '#F7F7F5', // light backgrounds
    primary: '#2E4B4F', // deep teal — buttons, links, active states
    amber:   '#C97A3F', // warm amber — status badges, priority indicators ONLY
    slate:   '#5B6470', // neutral — secondary text, borders
  },
  typography: {
    body: 'IBM Plex Sans', // all UI text
    mono: 'IBM Plex Mono', // ticket IDs, timestamps, citation refs, code
  },
  shape: {
    borderRadius: 6, // consistent — not MUI's varied defaults
  }
}

    Both light and dark themes are required. Not simply color-inverted — accent shifts slightly warmer in dark mode. Driven by one shared token object.

    Why bother with a custom theme for a portfolio project? Default MUI looks identical to every other MUI app. A custom theme signals you can work with a design system rather than just dropping in defaults. It's a visible differentiator in interviews and demos.

    Why mirror backend service boundaries in the folder structure? A developer working on tickets never needs to touch the chat folder. Clear ownership by feature, not by technical layer. This avoids the classic React antipattern: components/, hooks/, utils/ folders where everything is jumbled by type.

    State Management

    TanStack React Query — Not Redux

    Redux solves client-side state (UI toggles, wizard steps, local preferences). API data is server state — fundamentally different:

    Need Redux approach TanStack Query built-in
    Caching Manual Automatic, configurable stale time
    Background refetch Manual Automatic when window re-focuses
    Deduplication Manual Two components requesting same data = one HTTP call
    Loading/error states Manual reducers isLoading, isError, data from useQuery
    Optimistic updates Manual rollback logic useMutation onMutate + onError rollback
    Pagination Manual useInfiniteQuery built-in

    Using Redux for server state means reinventing a cache on top of Redux with more boilerplate for the same outcome.

    Rule: No inline fetch() or axios.get() calls in components. Every API call lives in a named hook in the feature's hooks/ folder. Components only consume hooks.

    // features/tickets/hooks/useTickets.ts
export function useTickets(filters: TicketFilters) {
  return useQuery({
    queryKey: ['tickets', filters],
    queryFn: () => ticketApi.list(filters),
    staleTime: 30_000,
  });
}

// features/tickets/components/TicketListPage.tsx
function TicketListPage() {
  const { data, isLoading, isError } = useTickets({ status: 'OPEN' });
  // No fetch logic here — component is pure presentation
}

    Routes

    Real multi-page routes — not tab-switching within one page:

    /login                    → Keycloak PKCE redirect
/                         → Role-aware dashboard
/chat                     → New conversation
/chat/:conversationId     → Existing conversation with history
/tickets                  → Ticket list (filter/sort/search)
/tickets/:id              → Ticket detail + event timeline
/knowledge                → Document list (Admin only)
/knowledge/:documentId    → Document detail + ingestion status
/notifications            → Notification list
/settings                 → User preferences

    Route guards check for valid token in memory. On reload: attempt silent refresh via httpOnly cookie. If that fails: redirect to /login which triggers Keycloak PKCE flow.

    Layout

    • Desktop (>960px): Persistent left sidebar showing icon + label for each route section
    • Tablet (600–960px): Collapsed sidebar showing icons only (expand on hover/click)
    • Mobile (<600px): Bottom navigation bar, max 5 icons — no hamburger-only nav

    Token Handling in the Frontend

    Page load
  → Check: is access_token in memory?
      → Yes: proceed
      → No: attempt silent refresh
          browser sends httpOnly cookie to /token/refresh automatically
      → Success: store new access_token in memory, proceed
      → Fail (expired/revoked): redirect to /login

API call
  → Axios interceptor adds: Authorization: Bearer <access_token>
  → On 401 response: trigger silent refresh, retry original request once
  → If refresh fails: redirect to /login

    SSE Integration (Chat Streaming)

    Chat responses stream token by token from chat-service via SSE. The frontend handles this with the browser's native EventSource API (or a polyfill for POST-based SSE):

    // Token-by-token streaming
const eventSource = new EventSource(`/api/chat/conversations/${id}/stream`);

eventSource.onmessage = (event) => {
  setStreamingContent(prev => prev + event.data);
};

eventSource.addEventListener('done', () => {
  eventSource.close();
  // Finalize message, parse citations
});

    Tokens are appended to the message in real time. Citation chip rendering happens after the full response is received.
