    Command

    11 sections · 858 words

    Behavioural · Design Patterns · Pattern 10 of 12

    Intent

    Turn a whole request into a first-class object that captures its receiver, its arguments and how to reverse it, so an invoker can run, queue, log or undo it without knowing what it does.

    When To Use It

    The Signs

    • You need to undo, redo, queue, log or replay operations.
    • A button or menu item wired straight to a method call.
    • "Do this on all selected items", or "do this later".
    • A history of the actions a user took.

    Don't Bother If

    • The action runs once, now, never undone or queued.
    • A plain function or Runnable already covers it.
    • There is no receiver or arguments worth capturing.

    Before

    class TextEditor {
    Document doc; int cursor;
    void onKey(char c) { doc.insert(cursor++, c); }
    void onDelete() { doc.delete(cursor, 1); }
    // button to method call, wired straight through
    // no way to undo, no history, no macro
}

    The call is inline.

    After

    interface Edit { void apply(Document d); void undo(Document d); }

class DeleteEdit implements Edit {
    private final int pos;
    private String removed; // filled in by apply()
    public void apply(Document d) {
        removed = d.text(pos, 1); // capture BEFORE the change
        d.delete(pos, 1);
    }
    public void undo(Document d) { d.insert(pos, removed); }
}

class Editor {
    final Deque<Edit> undo = new ArrayDeque<>(), redo = new ArrayDeque<>();
    void run(Edit e) { e.apply(doc); undo.push(e); redo.clear(); }
    void undo() { Edit e = undo.pop(); e.undo(doc); redo.push(e); }
}
// InsertEdit is the mirror image; a macro is just a List<Edit>.

    Or a hand-rolled undo that only remembers the last key:

    char lastChar; int lastPos; // only the last key
void onKey(char c) {
    doc.insert(cursor, c);
    lastChar = c; lastPos = cursor++; // remember one thing
}
void undo() { doc.delete(lastPos, 1); } // a delete? no idea
// redo? macros? "undo the last five"? none of it.

EACH COMMAND CAPTURES ITS RECEIVER, ITS ARGS, AND HOW TO REVERSE

    How It's Built (3 Steps)

    1. A Command interface: execute(), and undo() if you need it.
    2. One class per action, capturing the receiver and the arguments in its constructor or on first execute().
    3. An invoker runs, stacks, logs or schedules commands without knowing what they do.

    Quick Check

    Ask "do I need to hold this action as a thing to run later, undo, or record it?" If yes, wrap the call in an object.

    In The Interview

    "Every edit is a Command with apply and undo. The editor pushes it on the undo stack and never looks inside. A delete captures the removed text so undo can put it back. Redo is the same stack the other way."

    How It's Different

    From The Lookalikes

    Vs Strategy. A Strategy swaps how one step is done, held as a field. A Command turns a whole request into an object you can store, queue and reverse.

    Vs a lambda / Runnable. A lambda is one function. A Command adds undo, metadata, a name, and a place in a queue or history.

    Vs Memento. A Memento stores a snapshot of state to restore. A Command stores the action plus how to reverse it. Command is cheap per step; Memento is simple but heavy.

    Vs Chain of Responsibility. CoR is about who handles a request. Command is about turning the request itself into a first-class object.

    They Say: "now support a macro that repeats an edit 10 times"

    • With it: a CompoundEdit holds a list of Commands and applies or undoes them as one. It is a Command.
    • Without: a special-case loop in the editor, and undo that only half-works.

    Watch Out For

    • undo() must capture enough to reverse: the removed text, not just the position. Capture it on apply, before the change.
    • A fresh command must clear the redo stack, or redo replays a stale action into a diverged document.
    • Bind the receiver once: a field on the command, or handed in by an invoker that holds one document. Never re-resolve "the current document" at undo time.
    • A CompoundEdit is a Composite of Commands. A macro recorder is just a growing command list.
    • Commands should be immutable once created, so the history cannot change under you.
