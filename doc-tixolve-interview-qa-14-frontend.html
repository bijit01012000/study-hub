      78. Why TanStack Query over Redux?

      They solve different problems. Redux is for client state — UI toggles, form state, preferences. API data is server state: it has a remote source of truth, goes stale, is fetched by many components, and needs background sync. TanStack Query gives caching, refetch-on-focus, request dedup (two components, one HTTP call), loading/error states, and optimistic updates out of the box. Using Redux for server state is rebuilding all that by hand.

      79. Why no inline fetch in components?

      Separation of concerns. One hook file per resource per feature. If a URL or shape changes, I edit one hook, not every component. Components become pure presentation — declare the data they need, render it — and are trivially testable by mocking the hook instead of fetch.

      80. How is the frontend structured?

      Feature folders mirroring the backend boundaries: features/chat, features/tickets, features/knowledge, features/notifications, features/auth, plus app/ (shell, routing, theme) and shared/ (design tokens, reusable components). It's a real multi-page app with routes (/chat/:id, /tickets/:id, etc.), not tabs-in-a-page.

      81. Tell me about the design system.

      Custom Tailwind with locked design tokens — no component library. A defined palette (ink, paper, deep teal primary, warm amber reserved strictly for status/priority), IBM Plex Sans for UI and IBM Plex Mono for data (ticket IDs, timestamps, citation refs), a consistent 6px radius, and both light/dark themes from one shared token object where the accent shifts slightly warmer in dark mode. The signature element is the expandable numbered citation chip in chat.

      82. How does the frontend render a streaming response?

      It opens an EventSource to the SSE endpoint, appends each data: token to the message as it arrives, and on the done event reads the citation list + escalation flag to render citation chips and, if escalated, a link to the created ticket.
