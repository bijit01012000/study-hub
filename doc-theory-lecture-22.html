    Lecture 22 — Spring AOP (Cross-Cutting Concerns & Proxies)

    22 sections · 5,394 words

    Lecture 22

    Scope evidence: "Spring AOP | Cross-Cutting Concerns & Proxies" (playlist map, verified). The repo folder is the aopIntroductionDemo project: its service package holds StudentService, StudentServiceImpl, ExecutionTimeService, LoggingServiceUtil and LoggingDecorator, alongside controller.StudentController, repository.StudentRepository, dto.Student and the AopIntroductionDemoApplication entry point, plus these lecture notes.

    Every real application begins as pure business logic: create a student, place an order, process a payment. Then production reality arrives - logging, security, transactions, auditing, caching, timing - and none of it belongs to the domain rule it surrounds. This lecture follows the three naive attempts to separate those concerns (utility methods, inheritance, manual wrappers), shows exactly why each falls short at scale, and then introduces the mechanism Spring AOP uses to solve the problem: the proxy. The end state is a mental model in which business intent stays visible and cross-cutting policy lives in one module, applied automatically.

    1. A Simple Business Method

    Consider a student-management application. A service class manages students, and one method creates them:

    // service/StudentServiceImpl.java - business logic only
@Service
public class StudentServiceImpl implements StudentService {

    private final StudentRepository studentRepository;

    public StudentServiceImpl(StudentRepository studentRepository) {
        this.studentRepository = studentRepository;
    }

    @Override
    public Student createStudent(Student student) {
        return studentRepository.save(student);
    }
}

    The responsibility of createStudent() is easy to understand:

    Receive student
      |
      v
Save student
      |
      v
Return saved student

    This is the business logic of the method. A business method answers a domain-related question, such as:

    • How is a student created?
    • How is an order placed?
    • How is a payment processed?
    • How is money transferred?
    • How is inventory updated?

    The method is currently focused on one responsibility, so its intent is immediately visible. Reading the method tells you exactly what the application does; nothing else competes for attention.

    Important: A business method should primarily express business intent. Everything that is not the domain rule itself is a candidate to be moved out of the method and applied around it.

    2. Real Applications Need More Than Business Logic

    A production application may also need to:

    • Log when a method begins
    • Log whether it succeeds or fails
    • Measure execution time
    • Check whether the caller has permission
    • Record an audit event
    • Start, commit, or roll back a transaction
    • Collect application metrics
    • Retry temporary failures
    • Cache a result
    • Mask sensitive information

    These requirements are important, but they are not part of the core process of creating a student. None of them answers "how is a student created?" - they answer "how does the application behave while creating one?"

    If all of them are added directly to createStudent(), the method becomes difficult to read because most of its code no longer represents student-related business logic. The method still works, but the reason it exists is buried under ten other reasons it was modified.

    Same method, two different jobs:
  "create a student"          -> business logic
  "log, secure, time, audit"  -> everything else

    A typical application therefore contains two broad categories of responsibility, and the next section names them.

    3. Business Logic vs Supporting Logic

    Business logic represents the rules and operations of the application's domain. Examples:

    • Creating a student
    • Placing an order
    • Processing a payment
    • Updating inventory
    • Approving a loan

    Business logic differs from one feature or domain to another. The rule for approving a loan has nothing to do with the rule for updating inventory.

    Supporting or infrastructure logic helps the application operate safely, reliably, securely, and observably. Examples:

    • Logging
    • Security checks
    • Transaction management
    • Auditing
    • Performance monitoring
    • Caching

    This logic is usually not specific to students, orders, payments, or inventory. The same supporting behaviour may be required across many unrelated features.

    Aspect Business logic Supporting logic
    What it expresses The rules and operations of the domain Infrastructure that keeps the app safe, reliable, secure, observable
    Examples Create student, place order, process payment, update inventory, approve loan Logging, security, transactions, auditing, monitoring, caching
    Variability Differs from feature to feature and domain to domain Same behaviour is needed across many unrelated features
    Where it belongs In the business class In a separate, dedicated module
    Test focus Correct domain outcome Correct operational behaviour around the method

    The distinction is the seed of the whole lecture: one category belongs inside the method, the other does not, and mixing them is what hurts.

    4. What Is a Concern? Core vs Cross-Cutting

    A concern is a responsibility or area of interest within an application. Examples:

    • Student management is one concern.
    • Logging is another concern.
    • Security is another concern.
    • Payment processing is another concern.
    • Transaction management is another concern.

    Core business concerns normally belong to a particular feature or module:

    Student concern  -> StudentService
Order concern    -> OrderService
Payment concern  -> PaymentService

    These concerns are organized vertically. Each feature has its own classes and methods, and each class groups behaviour related to that one capability.

    Cross-cutting concerns are required across many business modules:

          Logging
         |
         v
StudentService <- Security -> OrderService
         |
         v
      PaymentService
         |
         v
      Auditing

    These concerns cut horizontally across otherwise unrelated features. They are therefore called cross-cutting concerns.

    A concern becomes cross-cutting when the same kind of behaviour must be applied in many different parts of the application. The moment you find yourself writing the same non-business step in a second service, the concern has become cross-cutting.

    5. Common Cross-Cutting Concerns

    The source names five recurring examples, each with a reason why it cannot stay inside one business class.

    Logging. The application may need to record which method was called, when it started, whether it completed successfully, whether it failed, which arguments were supplied, and how long it took. The same logging requirement may apply to student, order, payment, inventory, and user services.

    Security. Suppose only administrators are allowed to delete students. A permission check must run before the delete operation. Similar checks may also be needed before refunding payments, changing user roles, or approving requests.

    Performance measurement. Suppose we want to identify slow methods. A timer must run before the method, and the elapsed time must be calculated after the method finishes. Without a reusable mechanism, this timer would have to be added manually to every method that needs monitoring.

    Auditing. Certain business operations may need a permanent record, including who performed the operation, what operation was performed, when it happened, and whether it succeeded or failed.

    Transaction management. Database operations may require a transaction to begin before the business method and then commit or roll back after the method completes.

    Concern Typical timing What a business method would otherwise embed
    Logging Before, after, and on failure start/finish/failure messages and argument data
    Security Before permission checks and role validation
    Performance Before and after a start timestamp plus elapsed-time calculation
    Auditing After success or failure who/what/when and outcome records
    Transactions Around begin, commit, and rollback calls

    Interviewer's perspective: A strong candidate names the category before the example. "Logging is a cross-cutting concern because every service needs it and no service owns it" beats a memorized list, because it explains why AOP exists at all.

    6. The Two Major Problems: Scattering and Tangling

    Cross-cutting concerns create two major architectural problems when they are implemented directly inside business classes.

    6.1 Scattering

    Scattering means that the implementation of one concern is spread across many locations. For example, logging code may appear in:

    StudentService
OrderService
PaymentService
InventoryService
UserService
ReportService

    The logging concern is now scattered throughout the application.

    Imagine an application containing 20 service classes with five methods each. Logging, auditing, or performance code may have to be added and maintained in approximately 100 different methods. If the logging format or auditing policy changes, many classes may need to be modified.

    Problems caused by scattering:

    • The same concern is repeated in many places.
    • Developers may implement it differently.
    • A required method may be missed.
    • A small policy change may require edits across the entire codebase.
    • Maintenance becomes expensive.

    6.2 Tangling

    Tangling means that a single method contains code belonging to multiple unrelated concerns. Consider this payment method:

    // Tangled: one method owns five unrelated concerns
public Payment processPayment(PaymentRequest request) {
    // Logging concern
    log.info("Processing payment");
    // Security concern
    securityService.checkPermission("PROCESS_PAYMENT");
    // Performance concern
    long start = System.currentTimeMillis();
    try {
        // Business concern
        Payment payment = gateway.charge(request);
        // Auditing concern
        auditService.record("PAYMENT_COMPLETED");
        return payment;
    } catch (Exception exception) {
        // Logging concern
        log.error("Payment failed", exception);
        // Auditing concern
        auditService.record("PAYMENT_FAILED");
        throw exception;
    } finally {
        // Performance concern
        metrics.record(System.currentTimeMillis() - start);
    }
}

    This one method is responsible for business logic, logging, security, auditing, performance measurement, and exception-related behaviour. The problem is not that these responsibilities are unnecessary. The problem is that they are implemented together in the same method.

    Scattering = one concern, many methods.
Tangling   = one method, many concerns.

    They are two views of the same bad habit: the concern and the method are not separated.

    7. Consequences of Scattering and Tangling

    Tangling and scattering are not aesthetic complaints; they produce concrete engineering damage. The source lists six consequences:

    1. The business intent becomes difficult to see.
    2. Supporting behaviour may be applied inconsistently.
    3. Changes become more expensive.
    4. Developers can forget mandatory behaviour.
    5. Testing becomes more complicated.
    6. The method becomes harder to maintain.

    Compare the two versions below. The tangled version is the same shape we saw in Section 6, now for the student operation: a start timestamp, a log call, a permission check, a try/catch/finally, an audit record on success, and a metrics record on exit. The focused version is the business operation and nothing else: public Student createStudent(Student student) { return studentRepository.save(student); }.

    The second version communicates the business operation immediately. The challenge is to keep the method this clean while still applying the required supporting behaviour. Every attempt in Sections 8 to 10 is an answer to that challenge.

    Tangled method Focused method
    Reader must scan past logging, security, audit, timing Reader sees the domain rule on line one
    Changing a policy edits many methods Changing a policy edits one place
    A missing step is easy to overlook Applying the step is systematic
    Unit tests must arrange every support service Tests focus on the business outcome

    Golden rule: If a business method is hard to read because of code that has nothing to do with its name, the problem is not the developer - the problem is the missing separation mechanism.

    8. First Attempt: Utility Methods

    A common first solution is to centralize repeated code inside a utility class. LoggingServiceUtil exposes static helpers such as logStart(methodName), logEnd(methodName), and later logSuccess(...) and logFailure(...), all implemented once so nobody repeats the message-formatting logic.

    The service can then call the utility methods:

    // First attempt: the utility hides the implementation, not the invocation
public Student createStudent(Student student) {
    LoggingServiceUtil.logStart("createStudent");
    Student result = studentRepository.save(student);
    LoggingServiceUtil.logEnd("createStudent");
    return result;
}

    This is better than duplicating the complete logging implementation, but it does not solve the fundamental problem.

    The invocation is still scattered. Every business method must still contain calls such as LoggingServiceUtil.logStart(...) and LoggingServiceUtil.logEnd(...). The logging implementation is centralized, but the decision about where and when to invoke it remains scattered across business methods.

    Developers must remember to call it. Nothing automatically guarantees that every required method invokes the utility. A developer may:

    • forget to call logStart();
    • call logStart() but forget logEnd();
    • use inconsistent method names or messages;
    • handle failure differently in different methods.

    Success and failure paths still require boilerplate. The utility avoids repeating the internal logging implementation, but every business method still contains control-flow boilerplate: the method calls logStart, opens a try, saves, calls logSuccess on the happy path, and catches the exception to call logFailure before rethrowing. That control flow is repeated in every method that needs it.

    Utility methods centralize what the concern does, but not where and when the concern is applied. That "where and when" gap is exactly what the next two attempts also fail to close by hand.

    9. Second Attempt: Inheritance

    Another possibility is to place common behaviour inside a base class. An abstract BaseService defines protected logStart(methodName) and logEnd(methodName) methods once, and a service such as StudentService extends it. Inside createStudent, the service still calls logStart("createStudent"), saves, calls logEnd("createStudent"), and returns the result.

    Inheritance shares the implementation of logStart() and logEnd(), but every method must still invoke them manually. It provides access to shared behaviour; it does not automatically execute that behaviour around selected methods.

    Why inheritance does not solve the problem - it creates additional design problems:

    • Java supports only single class inheritance.
    • A service may already need to extend another class.
    • Unrelated classes are forced into an artificial inheritance hierarchy.
    • Logging, security, auditing, and other unrelated concerns may get mixed into one large base class.
    • The parent-child relationship does not naturally represent these concerns.
    Inheritance gives the method the tools.
It still makes the method use the tools by hand.

    10. Third Attempt: Manual Wrappers

    A stronger solution is the wrapper or decorator approach. It leans on the interface we already met in Section 1: the StudentService interface declares Student createStudent(Student student);, and the real StudentServiceImpl implements it with nothing but the repository call.

    Now create a wrapper that implements the same interface. LoggingDecorator holds a StudentService target, and its own createStudent runs the support code around the target call:

    // service/LoggingDecorator.java - the right idea, built by hand
public class LoggingDecorator implements StudentService {

    private final StudentService target;

    public LoggingDecorator(StudentService target) {
        this.target = target;
    }

    @Override
    public Student createStudent(Student student) {
        long start = System.currentTimeMillis();
        LoggingServiceUtil.logStart("createStudent");
        try {
            Student result = target.createStudent(student);
            LoggingServiceUtil.logSuccess("createStudent");
            return result;
        } catch (Exception exception) {
            LoggingServiceUtil.logFailure("createStudent", exception);
            throw exception;
        } finally {
            ExecutionTimeService.record("createStudent", System.currentTimeMillis() - start);
        }
    }
}

    The caller receives the wrapper instead of directly receiving the real service:

    Controller
    |
    v
LoggingDecorator
    |
    v
StudentService

    The original business class remains clean because the wrapper surrounds the real method invocation. The wrapper performs three fundamental actions:

    Run supporting behaviour before
    |
    v
Call the real business object
    |
    v
Run supporting behaviour after

    This is close to the basic execution model used by Spring AOP. AOP did not invent the idea of wrapping behaviour. It provides infrastructure for creating and applying such wrappers systematically.

    Important: The manual wrapper is the conceptual breakthrough of this lecture. Everything Spring AOP does later is automation of this exact pattern, not a new idea.

    11. Limitations of Manual Wrappers and What a Better Solution Must Provide

    Manual wrappers can work in a small application, but they become expensive at scale.

    A wrapper is needed for every service type. A wrapper written for StudentOperations cannot automatically wrap unrelated service interfaces such as OrderOperations or PaymentOperations. Separate wrappers may be required for student services, order services, payment services, inventory services, and user services.

    Multiple concerns require multiple layers. Suppose a service needs security, logging, performance measurement, and auditing. The object chain may become:

    Controller
    |
    v
SecurityStudentService
    |
    v
LoggingStudentService
    |
    v
PerformanceStudentService
    |
    v
AuditingStudentService
    |
    v
StudentService

    Manual object construction becomes complicated. Someone must create all wrappers in the correct order and inject the final outer wrapper wherever the service is needed.

    The same boilerplate appears again. Each wrapper contains similar delegation and exception-handling code. The concern has moved out of the business class, but wrapper creation and maintenance remain manual.

    A scalable solution should satisfy four requirements.

    • Requirement 1 - keep common behaviour in one place. Logging, security, auditing, or performance logic should have a dedicated module rather than being repeated in business classes.
    • Requirement 2 - select where the behaviour should apply. We need a way to express rules such as "apply to all service methods", "apply only to methods annotated with @TrackExecutionTime", or "apply to every method whose name starts with save".
    • Requirement 3 - control when the behaviour should run. Supporting logic may need to run before the method, after the method, only after successful completion, only after an exception is thrown, or around the complete method execution.
    • Requirement 4 - avoid modifying every business method. We do not want every method to contain infrastructure calls before the business logic. The application should apply cross-cutting behaviour without requiring the caller or business method to manage it manually. The mechanism should remain largely transparent to the business code and its caller.
    Approach Reuses implementation? Applies behaviour automatically? Where it breaks down
    Utility method Yes, centralized in one class No - every method must call it The invocation is still scattered; easy to forget
    Inheritance Yes, shared in a base class No - still invoked manually Single inheritance, artificial hierarchy, mixed concerns
    Manual wrapper Yes, one decorator class Yes, but assembled by hand One wrapper per service type, nested layers, manual wiring
    AOP proxy Yes, one aspect module Yes - Spring builds and manages the proxy Needs pointcuts and container integration, not hand wiring

    12. Aspect-Oriented Programming and OOP vs AOP

    This is the problem that Aspect-Oriented Programming, or AOP, is designed to solve. AOP provides a way to modularize cross-cutting concerns instead of mixing them into business classes.

    The essential idea is:

    Keep business logic in business classes
           +
Keep cross-cutting logic in a separate module
           +
Define where and when that logic should apply
           =
Combined behaviour at runtime

    With AOP, the business method can remain focused: createStudent is once again just return studentRepository.save(student);. Logging, security, performance measurement, or auditing can be applied around it through separate AOP configuration.

    Object-Oriented Programming and Aspect-Oriented Programming are not competitors. They organize different dimensions of an application.

    OOP organizes business capabilities vertically:

    StudentService
    |- createStudent
    |- updateStudent
    |- deleteStudent
OrderService
    |- placeOrder
    |- cancelOrder
    |- getOrder
PaymentService
    |- makePayment
    |- refundPayment
    |- getPayment

    Each class groups behaviour related to a particular business capability.

    AOP organizes behaviour horizontally:

              Logging
             |
             v
StudentService <- Performance -> OrderService
             |
             v
        PaymentService
             |
             v
          Auditing

    AOP captures behaviour that spans several business capabilities.

    Dimension OOP AOP
    Organizes Core business capabilities Shared behaviour across capabilities
    Direction Vertical - one class per capability Horizontal - one concern across classes
    Basic unit Class Aspect
    Solves Domain modelling and reuse of domain code Separation of cross-cutting concerns
    Relationship The base organization A complement, not a competitor

    OOP organizes the core business capabilities. AOP organizes behaviour that cuts across those capabilities. AOP complements OOP by modularizing concerns that do not fit neatly inside one business class.

    13. The Three Fundamental AOP Questions and What Is an Aspect

    AOP can be understood through three questions.

    Question 1: What should happen? Examples: log method execution, measure execution time, check permission, create an audit record. The code that performs this additional action is called advice.

    Question 2: Where should it happen? Examples: all methods in StudentService, all service-layer methods, methods whose names begin with save, methods annotated with @TrackExecutionTime. The rule that selects the relevant method executions is called a pointcut.

    Question 3: When should it happen? Examples: before the method, after the method, after successful completion, after an exception, around the complete method execution. The timing determines the type of advice.

    A simple mental model:

    What should happen?         -> Advice
Where should it apply?      -> Pointcut
When should it run?         -> Advice type

    An aspect is a module that contains a cross-cutting policy. It normally brings together:

    • the cross-cutting action that must run;
    • the rule that decides where it should run;
    • the timing of that action.

    For example:

    PerformanceAspect
    |- Which methods should be measured?
    |- How should their execution time be measured?

AuditAspect
    |- Which operations require auditing?
    |- What information should be recorded?
    |- Should both success and failure be recorded?

    An aspect therefore represents a complete cross-cutting concern as a separate module.

    Interviewer's perspective: The three questions (what, where, when) map one-to-one onto advice, pointcut, and advice type. If a candidate can answer "what is a pointcut?" with "the where of the three questions", they clearly understand AOP rather than reciting vocabulary.

    14. How Spring AOP Applies an Aspect: The Proxy

    Spring AOP normally creates a proxy around a Spring-managed target object. The target is the real object containing the business logic.

    Target Object: StudentService target object
Proxy Object:  StudentService proxy

    When AOP is applied, the caller normally receives a proxy instead of directly receiving the target. The proxy looks compatible with the target from the caller's perspective, but it can intercept method calls and apply additional behaviour.

    Runtime flow:

    Controller
    |
    v
AOP proxy
    |
    v
Cross-cutting logic before the method
    |
    v
Actual StudentService method
    |
    v
Cross-cutting logic after the method
    |
    v
Controller receives the result

    Conceptually, the proxy's createStudent calls logBefore(), then target.createStudent(student) inside a try, then logSuccess(result) and returns; on an exception it calls logFailure(exception) and rethrows. The target here is the real StudentServiceImpl bean.

    The actual business method remains unchanged. Spring creates and manages the interception layer instead of requiring us to write a separate wrapper for every service.

    The key difference from the manual wrapper is ownership: with AOP, the caller still asks for StudentService, and Spring hands back a proxy that satisfies the same contract. The wiring is done by the IoC container, not by hand.

    15. Manual Wrapper vs Spring AOP Proxy

    Manual Wrapper Spring AOP
    Written manually for a specific service type Proxy infrastructure is created and managed by Spring
    Delegation code must be repeated Interception logic is reusable
    Wrappers must be assembled manually Spring integrates proxies with the IoC container
    Selection logic is hard-coded into wrapper creation Pointcuts define where advice applies
    Multiple concerns create nested wrapper classes Multiple advices can be applied through AOP configuration
    Becomes difficult to scale Designed for systematic cross-cutting behaviour

    The comparison makes the whole lecture click: the wrapper pattern is correct but manual; Spring AOP is the same pattern, automated and container-aware.

    16. Important AOP Terms at a Glance and the Final Mental Model

    The vocabulary of this lecture, collected in one place:

    Term Meaning
    Concern A responsibility or area of interest in the application
    Cross-cutting concern A concern needed across multiple unrelated modules
    Aspect A module that represents a cross-cutting concern
    Advice The action that runs, such as logging or timing
    Pointcut The rule that selects where advice should run
    Join point An execution point, such as a method call, where advice can be applied
    Target The real Spring bean containing the business logic
    Proxy The wrapper object created by Spring to intercept calls to the target
    Weaving Linking the aspect with the target to build the advised proxy; in Spring AOP this happens at runtime via the proxy

    Mnemonic for the seven core terms - Aspect, Advice, Pointcut, Join point, Target, Proxy, Weaving - read A-A-P-J-T-P-W as: "All Aspects Point to Join points, Targets, Proxies and Weaving."

    Without AOP:

    Business method
    |- Logging
    |- Security
    |- Performance measurement
    |- Auditing
    |- Actual business logic

    With AOP:

    Business class
    |- Actual business logic
Separate aspect
    |- Logging/security/auditing logic
    |- Rule defining where it applies
    |- Rule defining when it runs
Spring proxy
    |- Combines both behaviours at runtime

    The complete idea can be summarized as:

    Caller
    |
    v
Spring AOP proxy
    |
    v
Advice runs
    |
    v
Target business method runs
    |
    v
Remaining advice runs
    |
    v
Result returns to caller

    17. Myth vs Reality

    Myth Reality
    "AOP is a replacement for OOP" AOP complements OOP; it organizes the horizontal concerns that OOP classes cannot own cleanly.
    "A utility class solves the cross-cutting problem" It centralizes the implementation but the invocation is still scattered and still easy to forget.
    "Inheritance applies behaviour automatically" It only shares methods; every business method must still call them by hand.
    "A manual wrapper is the same as Spring AOP" The wrapper is the same idea built by hand; Spring creates, orders, and injects the proxy automatically.
    "Cross-cutting concerns are optional extras" Security, transactions, and auditing are mandatory in production and are exactly the behaviour developers forget.
    "A pointcut is the code that runs" A pointcut only selects where; the action that runs is the advice.
    "The proxy changes the business class" The business class is untouched; Spring wraps it with a proxy that the caller receives instead.
    "Any method can be advised regardless of how it is called" Spring AOP intercepts calls that go through the proxy; internal self-invocation bypasses it.

    18. Common Trap Questions

    Trap 1 - "AOP means writing no extra code at all." Verdict: False. The cross-cutting code still exists; AOP moves it into a separate aspect module and applies it automatically, so the business class stays clean but the aspect is still code you write.

    Trap 2 - "Utility methods and AOP are basically the same." Verdict: False. A utility centralizes what the concern does; it does not control where and when it runs. Every business method still calls the utility, so scattering and forgetting remain.

    Trap 3 - "Inheritance solves cross-cutting concerns." Verdict: False. Inheritance shares behaviour but never applies it automatically, and it forces unrelated services into one hierarchy under Java's single inheritance rule.

    Trap 4 - "A manual wrapper is a scalable design." Verdict: Misleading. It demonstrates the right idea, but one wrapper per service type plus one layer per concern produces a deep, manually assembled object chain.

    Trap 5 - "Advice is a rule and pointcut is a method." Verdict: False. It is the reverse: advice is the action that runs; a pointcut is the rule selecting where it runs.

    Trap 6 - "Spring AOP edits my business class to add logging." Verdict: False. The target stays unchanged. Spring creates a proxy around the Spring-managed bean, and the caller receives the proxy.

    Trap 7 - "Calling one method of the same class from another applies the aspect." Verdict: False. Spring AOP intercepts calls that pass through the proxy; a self-invocation inside the target does not cross the proxy and therefore is not advised.

    19. Points to Remember

    1. Business methods should primarily express business intent; everything else is a candidate to be applied around them.
    2. Logging, security, performance measurement, auditing, transactions, and caching are common cross-cutting concerns.
    3. A concern becomes cross-cutting when the same kind of behaviour must be applied in many different parts of the application.
    4. Implementing these concerns directly causes scattering (one concern in many methods) and tangling (one method owning many concerns).
    5. The damage is concrete: hidden intent, inconsistent behaviour, expensive change, forgotten mandatory steps, harder testing, harder maintenance.
    6. Utility methods centralize implementation but still require manual invocation, so the decision of where and when stays scattered.
    7. Inheritance shares code but does not automatically apply behaviour, and it forces unrelated classes into one hierarchy.
    8. Manual wrappers demonstrate the correct idea (before, call, after) but do not scale: one wrapper per type, one layer per concern, manual assembly.
    9. AOP keeps cross-cutting logic in a separate aspect: advice defines what happens, a pointcut defines where, and the advice type defines when.
    10. Spring AOP applies aspects through a proxy around a Spring-managed target; OOP organizes business capabilities vertically while AOP organizes shared behaviour horizontally.

    20. Likely Interview Questions

    Question Crisp Answer
    What is a cross-cutting concern? A responsibility needed across many unrelated modules, such as logging, security, or auditing, that no single business class should own.
    Why do cross-cutting concerns hurt a codebase? Implementing them inline causes scattering and tangling, which hide business intent and make changes and testing expensive.
    What are scattering and tangling? Scattering is one concern spread across many methods; tangling is one method containing several unrelated concerns.
    Why do utility methods not solve it? They centralize the implementation but every business method must still remember to call them, so invocation stays scattered.
    Why does inheritance not solve it? It only shares methods; it cannot apply behaviour automatically and it forces unrelated classes into a single hierarchy.
    What is a manual wrapper and its limit? A decorator that runs support code around the target; correct in concept, but it needs one wrapper per type and layer and manual assembly.
    What is AOP in one sentence? A way to modularize cross-cutting concerns into separate aspects and apply them automatically without editing business methods.
    Is AOP a replacement for OOP? No; OOP organizes business capabilities vertically and AOP organizes shared behaviour horizontally. They are complementary.
    What is an aspect? A module that packages a cross-cutting policy: the action, the rule for where it applies, and its timing.
    What is the difference between advice and a pointcut? Advice is the action that runs; a pointcut is the rule that selects where it runs.
    What is a proxy in Spring AOP? A wrapper object Spring creates around the target bean so it can intercept method calls and run advice before and after.
    What are the three fundamental AOP questions? What should happen (advice), where should it apply (pointcut), and when should it run (advice type).
