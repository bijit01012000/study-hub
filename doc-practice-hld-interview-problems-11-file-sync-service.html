    Design a File Sync Service

    3 sections · 3,515 words

    Three levels: Level 1 — The Shape, Level 2 — The Defence, Level 3 — The Edges.

    Level 1 — The Shape (Foundation)

    Pacing: 3 min ask · 5 min trace flow · 7 min read why.

    The Ask

    Functional

    • Edit locally — the Dropbox problem — syncs everywhere
    • Large files sync incrementally, not whole-file
    • Notify other devices fast, not by polling

    Non-Functional

    • Files can be very large (GBs) ← forces chunking
    • Same content exists in many places ← forces content-addressing
    • Devices learn of changes fast ← forces push, not polling

    Agree These First

    20 M active users, ~50 GB each · ~4 MB content-defined chunks · ~5 M sync events/day · ~3 chunks/sync · ~30% of chunks are duplicates. Illustrative, round numbers, not any named company's.

    The Shape

    Components and flow:

    • Client A — Local files on disk · change watcher — detects edits via fs events, not a scan
    • (9) manifest — only changed chunks
    • Sync Service — Takes the new manifest · works out which chunks are genuinely new
    • Chunk Store — Content-addressed · chunk ID = hash(content) — only new chunks get written here; ≈700 PB stored after ~300 PB deduped away
    • Metadata Store — Which chunks make up which version of which file
    • Client B — A second device · notified of the change; what Client B is missing

    Data model: files file_id PK → latest_version.

    Line = data vs control: WRITE · manifest/chunk; READ · chunk delivery.

    Say It Like This

    "Two copies, one truth, and a client I can't fully trust — that's the frame. Client A watches for local changes, then chunks the changed file — I'd content-address each chunk, hash of its own bytes, so identical content anywhere already exists and dedupes for free. Client B gets pushed a notification, not polled, and pulls only the chunks it's missing. Concretely: edit one paragraph in a 100 MB file of ~4 MB chunks and only 4 MB moves, not 100 — 25×. Boundaries come from the content, so an insert doesn't shift them."

    Defend It

    Decision Prefer Avoid
    (9) Chunking Content-defined chunks — a rolling hash cuts on the bytes Fixed byte offsets → an insert shifts every later boundary
    (2) Content-addressed Chunk ID = hash(content) — identical bytes anywhere store once Arbitrary chunk IDs → every copy stored separately, no dedup possible
    (10) Push, not poll Server pushes "this file changed" the instant it does Poll every few seconds → wastes bandwidth and battery, usually for nothing

    Capacity Math

    Quantity Derivation Value
    Before dedup 20 M users × 50 GB each 1,000 PB (1 EB)
    Dedup saved 1,000 PB × ~30% duplicate ≈300 PB
    Actual stored 1,000 PB − 300 PB — the headline number ≈700 PB
    Sync events 5,000,000/day ÷ 86,400 s 58 /s
    Chunk writes 58/s × ~3 chunks/event 174 /s
    Worked example 100 MB file, ~25 × 4 MB chunks, 1 changed → moves 4 MB not 100 25×

    Round hard, out loud. 1,000 PB before dedup is a deliberately enormous number — say it, then say what shrinks it: dedup saves ~300 PB, and a small edit moves one 4 MB chunk, not the whole file.

    Before You Draw Anything — The Four Moves

    1. Clarify, don't assume. Single-user sync across their own devices, or shared folders across multiple users? Say shared folders — it's the harder, more interesting case — and scope to it explicitly. — Two minutes of questions buys the whole design.
    2. Agree the scale out loud. "20 M users, ~50 GB each, 4 MB chunks, ~5 M sync events a day." Now every later choice has a reason. — An unstated number is an undefendable design.
    3. Draw the happy path only. Client A → Sync Service → Chunk Store / Metadata Store → Client B. Get agreement before adding anything. — Boxes you add before agreement are boxes you'll defend alone.
    4. Name one trade-off unprompted. "I'd chunk files and content-address them, not sync whole files, because most edits only touch a small part of a large file." — This is the single move that separates L1 from a junior answer.

    What L1 Is Testing

    • Do you treat the client as real state, not just a UI?
    • Do you reach for chunking + content hashing unprompted?
    • Did you scope to shared folders — the harder case — on purpose?

    The Follow-Ups That Decide It

    1. You insert a paragraph on page 2 of a 200-page document. What gets uploaded? (ref 9 — tests: fixed-size boundaries would all shift — content-defined chunking, not just "chunking")
    2. Two different users both have a copy of the same file. Do you store it twice? (ref 2 — tests: content-addressed dedup awareness)
    3. How does another device find out a file changed, without constantly asking? (ref 10 — tests: push vs polling awareness)
    4. Why is the client itself part of this design, not just a browser tab? (tests: do they see the client as real, stateful data, not a UI)
    5. A file hasn't changed. Does Client B ever have to talk to the Chunk Store about it? (refs 1,10 — tests: can they trace the happy path without a wasted hop)

    At L1 you are being judged on one thing: can you produce a coherent shape and defend three choices inside it. Depth is page 2 — do not reach for it here. Ghosted boxes are what arrives next; you should be able to guess two of them.

    Level 2 — The Defence (Intermediate)

    Pacing: 5 min ask · 15 min trace flow · 10 min read why · 30 min cover & answer.

    The Ask

    Functional

    • Edit locally — the Dropbox problem — syncs everywhere
    • Large files sync incrementally, not whole-file
    • Notify other devices fast, not by polling
    • Queue offline edits; sync on reconnect
    • Detect conflicts from concurrent offline edits

    Non-Functional

    • Files can be very large (GBs) ← forces chunking
    • Same content exists in many places ← forces content-addressing
    • Devices learn of changes fast ← forces push, not polling
    • Clients are often offline / unreliable ← forces resumable sync
    • Devices can edit concurrently, offline ← forces conflict detection

    Out of Scope — Say It Aloud

    • Real-time co-editing (CRDTs) — a harder problem
    • File sharing / permissions model
    • The client app's UI itself

    Agree These First

    20 M active users, ~50 GB each · ~4 MB content-defined chunks · ~5 M sync events/day · ~3 chunks/sync · ~30% of chunks are duplicates. Illustrative, round numbers, not any named company's.

    The Shape

    Components and flow:

    • Client A — Local files on disk · change watcher — detects edits via fs events, not a scan; chunks the changed file before anything leaves the device
    • (9) manifest — only changed chunks
    • Sync Service — Takes the new manifest · works out which chunks are genuinely new; checks the Chunk Store before accepting anything
    • Chunk Store — Content-addressed · chunk ID = hash(content) — only new chunks get written here; ≈700 PB stored after ~300 PB deduped away
    • Metadata Store — Which chunks make up which version of which file; manifest only — never holds a chunk's bytes
    • (4) Notify Channel — Push — "this file changed" — separate from the chunk transfer itself
    • (5) Local Chunk Cache — Checked before any remote round trip — recognises chunks it already has
    • Client B — A second device · notified of the change; fetches only the chunks it doesn't already have; what Client B is missing

    Data model:

    • files file_id PK · owner_id · latest_version
    • chunks chunk_hash PK · size · ref_count
    • manifests file_id + version PK → ordered chunk_hash list

    Line = data vs control: WRITE · manifest/chunk; READ · chunk delivery; SIDE · notify + GC check.

    Say It Like This

    "Two copies, one truth, and a client I can't fully trust — that's the frame. Client A watches for local changes, then chunks the changed file — I'd content-address each chunk, hash of its own bytes, so identical content anywhere already exists and dedupes for free. Client B gets pushed a notification, not polled, and pulls only the chunks it's missing. Concretely: edit one paragraph in a 100 MB file of ~4 MB chunks and only 4 MB moves, not 100 — 25×. Boundaries come from the content, so an insert doesn't shift them."

    Defend It

    Decision Prefer Avoid
    (9) Chunking Content-defined chunks — a rolling hash cuts on the bytes Fixed byte offsets → an insert shifts every later boundary
    (2) Content-addressed Chunk ID = hash(content) — identical bytes anywhere store once Arbitrary chunk IDs → every copy stored separately, no dedup possible
    (10) Push, not poll Server pushes "this file changed" the instant it does Poll every few seconds → wastes bandwidth and battery, usually for nothing
    (3) Metadata vs chunks Separate stores — a manifest of hashes, not the bytes themselves One combined store → can't dedupe chunks without duplicating manifests too
    (4) Notify ≠ transfer Notify is separate from the fetch — client decides when/how to pull Push the bytes directly → no room to dedupe locally first, or to be offline
    (5) Local cache first Check locally — a restored folder's chunks are already recognised Always ask the server → a round trip for chunks you already have

    Capacity Math

    Quantity Derivation Value
    Before dedup 20 M users × 50 GB each 1,000 PB (1 EB)
    Dedup saved 1,000 PB × ~30% duplicate ≈300 PB
    Actual stored 1,000 PB − 300 PB — the headline number ≈700 PB
    Sync events 5,000,000/day ÷ 86,400 s 58 /s
    Chunk writes 58/s × ~3 chunks/event 174 /s
    Worked example 100 MB file, ~25 × 4 MB chunks, 1 changed → moves 4 MB not 100 25×
    Chunks stored ≈700 PB ÷ 4 MB/chunk, illustrative ≈175 billion

    Two different savings — don't conflate them. Chunking saves bandwidth (4 MB moves, not 100 MB); content-addressing saves storage (~300 PB never gets written twice). Neither number implies the other.

    What Breaks — Say It Before They Ask

    • (1) Sync loop / thrash. A races B: A uploads, B downloads and re-notifies, A redownloads its own change, and so on. — Fix: version numbers or vector clocks, so a device recognises a change it already has and stops propagating it
    • (6) Conflict silently resolved wrong. Two offline edits merge or overwrite incorrectly, quietly losing one person's changes. — Fix: explicit conflict detection — never silent last-writer-wins on a genuine concurrent edit
    • (8) GC deletes a chunk still in use. A chunk shared across many files and users gets reclaimed because one file's reference was removed. — Fix: reference counting (or mark-and-sweep) across the whole store — never a per-file-only check

    The Follow-Ups That Decide It

    1. You insert a paragraph on page 2 of a 200-page document. What gets uploaded? (ref 9 — tests: fixed-size boundaries would all shift — content-defined chunking, not just "chunking")
    2. Two different users both have a copy of the same file. Do you store it twice? (ref 2 — tests: content-addressed dedup awareness)
    3. How does another device find out a file changed, without constantly asking? (ref 10 — tests: push vs polling awareness)

    Cover The Sheet · Answer Aloud

    Use it as revision: cover the right rail and the two panels to your left, then walk the numbered path out loud. If you cannot say why a box is there and what breaks it, that box is your gap.

    Level 3 — The Edges (Advanced)

    Pacing: 10 min ask · 25 min trace flow · 15 min read why · 40 min cover & answer.

    The Ask

    Functional

    • Edit locally — the Dropbox problem — syncs everywhere
    • Large files sync incrementally, not whole-file
    • Notify other devices fast, not by polling
    • Queue offline edits; sync on reconnect

    Non-Functional

    • Files can be very large (GBs) ← forces chunking
    • Same content exists in many places ← forces content-addressing
    • Devices learn of changes fast ← forces push, not polling
    • Clients are often offline / unreliable ← forces resumable sync
    • Devices can edit concurrently, offline ← forces conflict detection

    Out of Scope — Say It Aloud

    • Real-time co-editing (CRDTs) — a harder problem
    • File sharing / permissions model
    • The client app's UI itself

    Agree These First

    20 M active users, ~50 GB each · ~4 MB content-defined chunks · ~5 M sync events/day · ~3 chunks/sync · ~30% of chunks are duplicates. Illustrative, round numbers, not any named company's.

    Components and flow:

    • Metadata Store — Which chunks make up which version of which file; manifest only — never holds a chunk's bytes
    • (4) Notify Channel — Push — "this file changed" — separate from the chunk transfer itself
    • (5) Local Chunk Cache — Checked before any remote round trip — recognises chunks it already has
    • (7) Offline Queue — Local edits queue while disconnected · replays in order on reconnect
    • (8) Conflict Detector — Diverging manifests, same file, both offline → surfaced, never silently merged
    • (9) Garbage Collector — Reclaims a chunk only once zero files, anywhere, still reference it
    • Client B — A second device · notified of the change; fetches only the chunks it doesn't already have; what Client B is missing

    Data model:

    • files file_id PK · owner_id · latest_version
    • chunks chunk_hash PK · size · ref_count

    (4) Notify ≠ transfer Notify is separate from the fetch — client decides when/how to pull Push the bytes directly → no room to dedupe locally first, or to be offline
    (5) Local cache first Check locally — a restored folder's chunks are already recognised Always ask the server → a round trip for chunks you already have
    (6) Explicit conflict Surface it, keep both versions if needed — costs a moment's attention Silent last-writer-wins → one person's offline edits vanish, unnoticed
    (7) Compact the queue Collapse to final state before replay — weeks of edits, one sync Replay every intermediate edit → an unbounded backlog, most already superseded

    Quantity Derivation Value
    Before dedup 20 M users × 50 GB each 1,000 PB (1 EB)
    Dedup saved 1,000 PB × ~30% duplicate ≈300 PB
    Actual stored 1,000 PB − 300 PB — the headline number ≈700 PB
    Sync events 5,000,000/day ÷ 86,400 s 58 /s
    Chunk writes 58/s × ~3 chunks/event 174 /s
    Worked example 100 MB file, ~25 × 4 MB chunks, 1 changed → moves 4 MB not 100 25×

    Per-user chunks ~50 GB ÷ 4 MB, before any dedup ≈12,500

    At ~175 billion chunks, "is anyone still using this one?" is itself a hard question — exactly why garbage collection has to check every reference, across every file and every user, before it deletes anything.

    What Breaks — Say It Before They Ask

    • (1) Sync loop / thrash. A races B: A uploads, B downloads and re-notifies, A redownloads its own change, and so on. — Fix: version numbers or vector clocks, so a device recognises a change it already has and stops propagating it

    • (7) Offline queue grows unbounded. A device offline for weeks accumulates a large backlog of local edits. — Fix: compact the queue — collapse repeat edits to one file into one final state before replay
    • (3) Partial sync leaves a file broken. A sync is interrupted mid-transfer, crash or dropped connection, partway through a file's chunks. — Fix: a file is never "synced" until every one of its chunks is verified present locally

    1. You insert a paragraph on page 2 of a 200-page document. What gets uploaded? (ref 9 — tests: fixed-size boundaries would all shift — content-defined chunking, not just "chunking")
    2. Two different users both have a copy of the same file. Do you store it twice? (ref 2 — tests: content-addressed dedup awareness)
    3. How does another device find out a file changed, without constantly asking? (ref 10 — tests: push vs polling awareness)
    4. Why is the client itself part of this design, not just a browser tab? (tests: do they see the client as real, stateful data, not a UI)
    5. A file hasn't changed. Does Client B ever have to talk to the Chunk Store about it? (refs 1,10 — tests: can they trace the happy path without a wasted hop)
    6. A device is offline for two weeks, then reconnects. What happens? (ref 7 — tests: offline queue / resumable sync, not "it just reuploads everything")
    7. Two people edit the same file at the same time, both offline, then both come back online. What happens? (ref 6 — tests: conflict detection, not a silent overwrite)
    8. A chunk is referenced by ten thousand different files. One of those files gets deleted. Can you delete the chunk? (ref 8 — tests: reference-counting / garbage-collection awareness)
