    Application Flow

    10 sections · 1,503 words

    Section 2 of 11

    Purpose: understand how the whole application works, end to end, in plain language — and walk an interviewer through it confidently.

    Companion to ARCHITECTURE.md — when explaining, open that file and show the "Request Flow — Chat (Happy Path)" and "Request Flow — Escalation" sections (they contain the step-by-step diagrams). Even better: log into the app as admin and open the /architecture page — the system diagram is built into the live application, so you can explain the architecture inside the product during a demo.

    The One-Paragraph Story

    A user logs in and chats with an AI assistant. Behind the scenes, the AI searches the company's uploaded documents, builds an answer grounded in them, and streams it back with clickable citations showing exactly which document each claim came from. If the AI can't answer, it says so — and the system automatically creates a support ticket and notifies the user, all through events on a message bus. That's the whole product: knowledge assistant + ticketing system, connected by an event pipeline.

    The Cast (6 services + 1 frontend)

    Think of it as a company with departments. Each service owns its own data and never reads another service's database.

    Service In one sentence
    api-gateway The front door. Checks every visitor's ID (JWT) and stamps approved requests with "who is this?" headers.
    auth-service The HR department. Stores app-level user details and roles.
    ticket-service The help desk. Tickets, their status workflow, and who's assigned.
    knowledge-service The library. Stores documents, cuts them into searchable pieces, finds the right piece for any question.
    chat-service The AI receptionist. Takes a question, asks the library for context, asks the LLM for an answer, streams it back.
    notification-service The PA system. Listens for events and pushes notifications to the user's browser.

    Frontend — React app. Talks to the gateway only, never to services directly.

    Two supporting actors: Keycloak (issues ID badges / JWTs) and Kafka (the internal mail system between departments).

    Flow 1 — Login (getting an ID badge)

    Show: ARCHITECTURE.md → "API Gateway Detail"

    1. User clicks login → browser redirects to Keycloak (the identity provider).
    2. User enters credentials → Keycloak redirects back with a one-time code.
    3. Frontend exchanges the code for a JWT (a signed ID badge). It lives only in browser memory — never localStorage — so a script-injection attack can't steal it.
    4. Every API call now carries Authorization: Bearer <token>.

    Why it's secure: only the gateway checks the badge. It validates the signature, then stamps the request with trusted headers (X-User-Id, X-Tenant-Id, X-User-Role) before forwarding. Downstream services never touch JWTs — they just trust the gateway's stamp. One security checkpoint instead of six.

    Flow 2 — Creating a Ticket (the simple case)

    Show: live demo — Tickets page → create ticket

    1. User fills the form → frontend calls POST /api/tickets via the gateway.
    2. Gateway validates the JWT, stamps headers, routes to ticket-service.
    3. ticket-service validates the status transition rules (e.g., can't reopen a CLOSED ticket), saves the ticket and an outbox event in the same database transaction.
    4. Response returns to the user in milliseconds. Done.

    The outbox pattern (the #1 interview topic): writing to the DB and publishing to Kafka are two separate operations — a crash between them leaves them inconsistent (the "dual-write problem"). Fix: save the business data and the event row in one transaction. A background poller then publishes the event row to Kafka and marks it done. Crash-safe either way. → Show KAFKA_EVENTS.md "Outbox Pattern" for the diagram.

    Flow 3 — Uploading a Document (building the library)

    Show: live demo — Knowledge page → upload a PDF → watch status go PENDING → PROCESSING → COMPLETED

    1. Admin uploads a PDF → knowledge-service saves the raw file to S3 (MinIO locally) and returns immediately.
    2. An async background job starts (upload can take 30s+ — the user must not wait staring at a spinner): - Extract text from the PDF (Apache Tika) - Chunk it into ~2000-character pieces with 200-char overlap (so an answer split across a boundary is still findable) - Embed each chunk into a vector (a list of numbers capturing its meaning) via Ollama - Store in Postgres+pgvector with a fast similarity index
    3. When done → emits document.ingested to Kafka (via outbox).

    Why S3 first? If processing fails, the original file is safe — retry without re-upload.

    Flow 4 — The Chat (the star of the demo)

    Show: ARCHITECTURE.md → "Request Flow — Chat (Happy Path)" diagram, then live demo — Chat page

    1. User types a question → frontend POSTs it to chat-service (via gateway).
    2. chat-service synchronously calls knowledge-service's /search with the question. - Search is hybrid: vector similarity (finds meaning) + Postgres full-text (finds exact keywords like product names/IDs). Results are merged with Reciprocal Rank Fusion. - Analogy: one librarian who understands what you mean, plus one who's great at Ctrl+F. Combine their shortlists.
    3. chat-service builds a prompt: system instructions + the retrieved chunks numbered [Source 1], [Source 2] ... + last 10 conversation turns + the question.
    4. It calls the LLM via Spring AI's ChatClient — an abstraction, so the provider is a config swap: Ollama locally (free), OpenCode Zen / Claude API for the demo. Zero code changes between them.
    5. The answer streams token-by-token over SSE (Server-Sent Events) — same protocol a browser uses natively, ideal for one-directional streaming. The user sees words appear like ChatGPT does.
    6. On completion, the message + citations are saved to the chat database. The frontend renders the [Source N] references as clickable chips that expand to show the exact document passage.

    The interview one-liner: "The AI never answers from its training data — it answers only from retrieved documents, and every claim carries a verifiable citation. That's what makes enterprise RAG auditable."

    Flow 5 — Escalation (when AI admits defeat) — THE signature flow

    Show: ARCHITECTURE.md → "Request Flow — Escalation" diagram. This is the flow that connects everything.

    1. The system prompt instructs the LLM: "If the context doesn't contain the answer, reply with exactly: 'I don't have enough information…'". When chat-service detects that phrase, it knows the AI failed.
    2. chat-service writes a chat.escalated event to its outbox (same transaction as saving the message) → poller publishes it to Kafka.
    3. ticket-service consumes the event and creates a ticket automatically — linked back to the conversation. (It's idempotent: one conversation can never create two tickets.)
    4. ticket-service emits ticket.created (outbox → Kafka).
    5. notification-service consumes it, saves a notification, and pushes it to the user's browser over WebSocket — they see it live.
    6. chat-service also consumes ticket.created and stamps the conversation with the ticket ID — so the chat page now shows "escalated to ticket #123." The loop is closed.

    Why Kafka instead of a direct REST call? chat-service doesn't know or care that ticket-service exists. Tomorrow you could add an analytics service consuming the same event and nothing upstream changes. If ticket-service is restarting, the event waits in Kafka instead of being lost.

    Flow 6 — Notifications (the PA system)

    1. Frontend connects to notification-service once at login (WebSocket via the gateway).
    2. Whenever an event arrives on Kafka (ticket.created, ticket.status-changed), notification-service writes it durably, then pushes it to the right user's socket.
    3. Duplicates are impossible to double-process: every consumed event's ID is recorded in a processed_events table — a redelivered message is detected and skipped.

    The Rules That Hold It Together (memorize these 3)

    1. No service reads another service's database. Ever. Need data? REST call. Need to react? Kafka event.
    2. Every Kafka publish goes through the outbox — business data + event in one DB transaction. Never "save then publish" as two steps.
    3. The gateway is the only security checkpoint — services trust its stamped headers and never re-validate JWTs.

    If an interviewer pushes ("isn't this over-engineered?"), the honest answer is in ARCHITECTURE.md's "Why Microservices?" section: knowledge ingestion is async batch work; chat is latency-sensitive streaming — different scaling profiles. And for this project, demonstrating distributed-systems patterns is the point; a modular monolith would ship faster and I can articulate exactly why I didn't choose it here.

    Suggested 5-Minute Interview Walkthrough Order

    1. Open the /architecture page in the running app (or ARCHITECTURE.md) — one glance at the diagram.
    2. Tell the one-paragraph story (top of this file).
    3. Demo Flow 4 (chat) — upload a doc first if needed, ask a question, show streaming + open a citation chip.
    4. Demo Flow 5 (escalation) — ask something the docs can't answer; watch the ticket appear and the notification arrive. "This is three services collaborating through events, and the user did nothing."
    5. Land the 3 rules above. Offer KAFKA_EVENTS.md / TRADEOFFS.md when they go deeper.
