    Security and data protection

    9 sections · 3,874 words

    Module 10 - 9 questions - 1 practical drill

    Think like an attacker and defend data at every trust boundary.

    Backend security interviews separate people who bolt on "we used JWT" from people who can reason about authorization at the object level, secret handling, and what an attacker actually does. Follow-ups drill into the OWASP realities: broken object-level authorization, token handling, and PII exposure.

    Inside this module: Object authorization - Token safety - Secrets - PII protection

    Q10.1 - How did you handle authentication and authorization in your service?

    What it really tests: Whether the candidate distinguishes authn from authz and enforces per-request, per-object permission checks.

    Weak answer: "We used JWT tokens. When a user logged in they got a token, and we validated it on each request to make sure they were authenticated."

    Why it fails: - Only covers authentication (who you are), not authorization (what you can do). - Validating the token proves identity, not permission for the specific resource. - No object-level authorization - the #1 API vulnerability. - No mention of what's in the token or how permissions are checked.

    Follow-up ladder: 1. FAILURE - A valid token holder requests another user's record by id - what stops them? - Broken object-level authorization (BOLA). 2. TECHNICAL - Authentication vs authorization - where does each happen? - The core distinction. 3. TRADEOFF - What's inside the token, and what do you never put there? - Claims and PII discipline. 4. MEASUREMENT - Where do you enforce permissions - gateway or service? - Defence in depth.

    Answer framework: 1. Authn establishes identity (token) 2. Authz checks permission per request 3. Object-level check on every resource access 4. Least-privilege claims/scopes 5. Enforce in the service, not only the gateway 6. Short token lifetimes 7. Audit sensitive access

    Rejection signals: - Only does authentication, thinks that's authorization. - No object-level permission check. - Trusts the token for access, not the resource ownership. - Puts sensitive data in the token.

    Model answer skeleton: Authentication and authorization are two separate checks and both run on every request. Authentication verifies identity - we issued a signed JWT at login and validated its signature and expiry on each call.

    But a valid token only proves who you are, not that you're allowed to touch a specific resource, so on top of it I enforce authorization, and specifically object-level authorization: when a user requests /orders/{id}, I check that the order belongs to that user before returning it.

    Skipping that is broken object-level authorization - BOLA - which is the single most common API vulnerability, where anyone with a valid token just increments an id and reads other people's data.

    The token carries minimal claims - user id and roles/scopes - and never PII or secrets, since a JWT payload is only base64-encoded, not encrypted.

    I enforce permissions in the service itself, not only at the gateway, as defence in depth, keep token lifetimes short with refresh tokens, and audit access to sensitive records.

    Q10.2 - You're using JWTs. Walk me through how you'd get the security details wrong.

    What it really tests: Deep JWT knowledge - the alg=none attack, verification, expiry, revocation - framed to surface real pitfalls.

    Weak answer: "As long as you validate the token signature and set an expiry, JWTs are secure. We used a secret key to sign and verify them."

    Why it fails: - Doesn't mention the alg-confusion / alg=none attack. - No revocation strategy - JWTs are hard to invalidate before expiry. - Symmetric secret shared across services is a wider blast radius than asymmetric. - No mention of validating audience/issuer claims.

    Follow-up ladder: 1. TECHNICAL - What's the alg=none / algorithm-confusion attack? - Knows to pin the algorithm server-side. 2. FAILURE - A token is compromised before it expires - how do you revoke it? - Revocation / short TTL + denylist. 3. TRADEOFF - Symmetric vs asymmetric signing across services - which and why? - Key-distribution blast radius. 4. TECHNICAL - Which claims must you validate beyond the signature? - aud/iss/exp validation.

    Answer framework: 1. Pin the signing algorithm server-side 2. Never trust the token's alg header 3. Validate signature, exp, aud, iss 4. Short TTL + refresh for revocation 5. Denylist for emergency revoke 6. Asymmetric (RS256) so services only hold the public key 7. No sensitive data in payload

    Rejection signals: - Unaware of alg=none. - No revocation plan. - Shares one symmetric secret everywhere. - Only validates the signature, not the claims.

    Model answer skeleton: The classic way to get JWTs wrong is trusting the token's own alg header - an attacker sets alg: none or switches an RS256 token to HS256 and signs it with the public key as the HMAC secret, and a naive library accepts it. So I pin the expected algorithm server-side and never let the incoming token dictate it.

    Second, revocation: JWTs are valid until they expire, so a stolen token works until then - I keep TTLs short (minutes) with refresh tokens, and maintain a denylist for emergency revocation of specific tokens or sessions.

    Third, key distribution: I sign with an asymmetric key (RS256) so only the auth service holds the private key and every other service verifies with the public key - a shared symmetric secret means any one compromised service leaks the ability to mint tokens for all of them.

    And I validate more than the signature - expiry, audience, and issuer - so a token minted for another service or tenant is rejected.

    Finally nothing sensitive goes in the payload, because it's only base64, readable by anyone.

    Q10.3 - How did you protect sensitive data - PII, payment details - at rest and in transit?

    What it really tests: Encryption practices, key management, and what not to store or log.

    Weak answer: "We used HTTPS for data in transit and encrypted the database, so the data was protected both ways."

    Why it fails: - "Encrypted the database" is vague - disk encryption doesn't protect against app-level access. - No key management discussion. - No mention of not storing what you don't need (e.g. raw card numbers). - Ignores PII in logs, backups, and non-prod environments.

    Follow-up ladder: 1. TECHNICAL - Full-disk encryption vs field-level - what does each actually protect against? - Threat-model-appropriate encryption. 2. TRADEOFF - Where do the encryption keys live, and who can access them? - Key management / KMS. 3. MEASUREMENT - How do you avoid storing card numbers at all? - Tokenisation / data minimisation. 4. FAILURE - How does PII leak even with encryption on - logs, backups, staging? - The overlooked leakage paths.

    Answer framework: 1. TLS 1.2/1.3 in transit 2. Encryption at rest, field-level for the most sensitive 3. Keys in a KMS with access control and rotation 4. Data minimisation / tokenisation 5. Redact PII from logs 6. Protect backups and non-prod copies 7. Audit and access controls

    Rejection signals: - "HTTPS and encrypted DB" with no depth. - No key management. - Stores data it doesn't need. - Ignores PII in logs/backups/staging.

    Model answer skeleton: In transit everything is TLS 1.3 with strong cipher suites, including service-to-service internally, not just at the edge. At rest I distinguish disk encryption from field-level: full-disk protects against a stolen drive but not against anyone with database access, so for the most sensitive fields I encrypt at the application/field level so even a DB dump is useless without the keys.

    Those keys live in a KMS with tight access control, rotation, and audit - never hard-coded or in config.

    The strongest control, though, is not storing what I don't need: I never stored raw card numbers, I tokenised through the payment processor so we held a token, not the PAN, which took us largely out of PCI scope.

    And I watch the leakage paths people forget even when encryption is on - PII sprayed into logs, unencrypted backups, and production data copied into a staging environment with weaker controls - so I redact PII at the log boundary, encrypt backups, and mask or synthesise data in non-prod.

    Access to sensitive records is role-limited and audited.

    Q10.4 - How do you prevent SQL injection and similar injection attacks?

    What it really tests: Whether the candidate understands parameterisation and input handling, not just "we sanitise inputs".

    Weak answer: "We sanitised user inputs and validated them before using them in queries, so malicious input couldn't get through."

    Why it fails: - "Sanitising" via blocklists is fragile and bypassable. - Doesn't name parameterised queries / prepared statements - the actual fix. - Conflates input validation (defence in depth) with the real defence. - No mention of ORMs or least-privilege DB accounts.

    Follow-up ladder: 1. TECHNICAL - Why are parameterised queries the real fix, not input sanitising? - Separating code from data. 2. FAILURE - Where does string-concatenating a query still sneak in? - Dynamic query / ORDER BY edge cases. 3. TRADEOFF - How does a least-privilege DB account limit the damage? - Defence in depth. 4. MEASUREMENT - How does the same idea apply to NoSQL or command injection? - Generalising the principle.

    Answer framework: 1. Parameterised queries / prepared statements 2. Never concatenate user input into queries 3. Input validation as defence in depth, not the primary control 4. Watch dynamic query parts (ORDER BY, table names) 5. Least-privilege DB account 6. ORM used safely 7. Same principle for NoSQL/command/LDAP injection

    Rejection signals: - Relies on sanitising/blocklists. - Doesn't know parameterised queries are the fix. - Concatenates input into SQL anywhere. - Uses an over-privileged DB account.

    Model answer skeleton: The real fix isn't sanitising - blocklists are always one clever encoding away from being bypassed - it's parameterised queries, also called prepared statements, which send the SQL structure and the user data to the database separately so input can never be interpreted as code. I never concatenate user input into a query string.

    Input validation still happens, but as defence in depth, not the primary control.

    The place injection still sneaks in even with an ORM is the dynamic parts you can't parameterise - an ORDER BY column, a table name, or a raw-SQL escape hatch - so those I whitelist against a fixed set rather than pass through.

    I also run the app on a least-privilege database account, so even if something slipped through, the account can't drop tables or read unrelated schemas, limiting the blast radius.

    And the same principle generalises: NoSQL injection, OS command injection, and LDAP injection all come from mixing untrusted data with a command, and the answer is always to separate data from code - parameterise, never interpolate.

    Q10.5 - How do you manage secrets - API keys, database passwords in your services?

    What it really tests: Secret management maturity - no secrets in code/repos, use of a secrets manager, rotation.

    Weak answer: "We stored them in environment variables and config files that weren't committed to the repo, so they stayed out of the code."

    Why it fails: - Config files and env vars still sprawl and leak (crash dumps, process listings, CI logs). - No central secrets manager. - No rotation strategy. - "Not committed" relies on discipline; secrets often end up in git history anyway.

    Follow-up ladder: 1. TECHNICAL - Why is a secrets manager better than env vars/config? - Central control, audit, rotation. 2. FAILURE - A secret leaks - how fast can you rotate it, and is that automated? - Rotation readiness. 3. MEASUREMENT - How do you keep secrets out of git history and CI logs? - Leak-prevention hygiene. 4. TRADEOFF - How do services authenticate to the secrets manager itself? - The bootstrap-trust problem.

    Answer framework: 1. Central secrets manager (Vault/KMS/cloud) 2. No secrets in code or git 3. Injected at runtime, short-lived where possible 4. Rotation, ideally automated 5. Scanning to block secrets in commits/CI 6. Least-privilege access per service 7. Audit access

    Rejection signals: - Secrets in config files or committed anywhere. - No secrets manager. - No rotation. - Same secret shared broadly with no audit.

    Model answer skeleton: Secrets live in a dedicated secrets manager - Vault or a cloud KMS/secrets service - not in code, config files, or env vars baked into images. The service fetches them at runtime and, where possible, they're short-lived dynamic credentials the manager issues and expires, so a leaked secret has a small window.

    Env vars and config feel convenient but they sprawl - into crash dumps, process listings, and CI logs - and 'not committed' relies on discipline that fails, so I run secret-scanning in pre-commit and CI to block anything that looks like a key from ever landing in git history.

    Rotation is the real test: a secret will leak eventually, so I make sure rotation is quick and ideally automated, and that the app can pick up a rotated secret without a redeploy.

    Each service gets least-privilege access to only the secrets it needs, and access is audited.

    The one bootstrap problem is how a service authenticates to the secrets manager itself, which I solve with workload identity - the platform vouches for the pod/instance - rather than a chicken-and-egg static credential.

    Q10.6 - An attacker is hitting your login endpoint with credential stuffing. What defences do you have?

    What it really tests: Understanding of brute-force/credential-stuffing defences beyond "add a captcha".

    Weak answer: "We'd add rate limiting on the login endpoint and maybe a captcha to slow down the attacker."

    Why it fails: - Rate limiting by IP alone is bypassed by distributed attacks (botnets). - No account lockout / progressive delay. - No detection of credential stuffing patterns. - Doesn't address that the passwords are already breached (stuffing uses known pairs).

    Follow-up ladder: 1. FAILURE - The attack comes from thousands of IPs - how does IP rate limiting fail? - Distributed-attack awareness. 2. TRADEOFF - How do you protect accounts without locking out real users (DoS)? - Lockout vs usability. 3. TECHNICAL - How does MFA change the calculus entirely? - Defence that defeats stuffing. 4. MEASUREMENT - How do you detect a stuffing attack in progress? - Anomaly detection.

    Answer framework: 1. Rate limit per account and per IP 2. Detect distributed patterns (failure-rate anomaly) 3. Progressive delays / risk-based challenges 4. MFA as the real defeater 5. Check against breached-password lists 6. Bot detection / device fingerprinting 7. Alert on spikes 8. Avoid lockout-as-DoS

    Rejection signals: - Only IP rate limiting. - No MFA consideration. - Naive lockout enabling a DoS on real users. - No detection of the attack pattern.

    Model answer skeleton: Credential stuffing uses real username/password pairs from other breaches, so the passwords are already valid somewhere - which changes the defence.

    Rate limiting helps but IP-based limiting alone fails against a botnet spread over thousands of IPs each making a few attempts, so I also limit per account and, more importantly, watch the global failed-login rate for the anomaly of many accounts failing from many IPs, which is the signature of stuffing.

    I use risk-based challenges - a captcha or step-up only when the request looks suspicious - rather than blanket friction, and progressive delays instead of hard lockouts, because a naive lockout lets an attacker deny service to real users just by failing their logins.

    The real defeater is MFA: even a correct stolen password doesn't get in without the second factor, so I push MFA hard for anything sensitive.

    I also check new and reset passwords against known-breached-password lists so users can't pick a stuffable password, and I alert the security team on stuffing spikes so we can respond in real time.

    Q10.7 - How do you make sure one authenticated user can't access another user's data?

    What it really tests: Object-level / row-level authorization - BOLA - the most common real API vulnerability, from a design angle.

    Weak answer: "Since they're authenticated with their own token, they can only access their own account. The token identifies them."

    Why it fails: - Confuses authentication with per-resource authorization. - Assumes the token restricts data access - it only proves identity. - No ownership check on the requested resource. - Exactly the BOLA vulnerability the question probes.

    Follow-up ladder: 1. TECHNICAL - They change the id in the URL to someone else's - what's your server-side check? - Explicit ownership verification. 2. FAILURE - Why isn't 'they have a valid token' enough? - Authn is not authz. 3. TRADEOFF - How do you enforce this consistently across hundreds of endpoints? - Centralised/systematic enforcement. 4. MEASUREMENT - How does row-level security in the DB help as a backstop? - Defence in depth.

    Answer framework: 1. Never trust client-supplied ids for access 2. Verify resource ownership against the authenticated principal on every access 3. Centralise the check (middleware/policy) 4. Don't expose or trust sequential ids alone 5. Row-level security as a backstop 6. Audit access 7. Test with cross-account attempts

    Rejection signals: - Thinks a valid token restricts data access. - No ownership check on resources. - Relies on obscure ids instead of authorization. - No systematic enforcement.

    Model answer skeleton: The dangerous assumption is that a valid token limits what data you can reach - it doesn't, it only says who you are. If /orders/1234 returns whatever order 1234 is, then any authenticated user just changes the number and reads someone else's order - that's broken object-level authorization, the most common API vulnerability in the wild.

    So on every resource access I verify ownership server-side: does this order's user_id match the authenticated principal, or does their role grant access - and I never trust a client-supplied id as authorization.

    To keep it consistent across hundreds of endpoints I centralise the check into a policy layer or middleware rather than hand-rolling it per handler, because the one endpoint someone forgets is the breach.

    As a backstop I use database row-level security so even a buggy query can't return another tenant's rows, and I audit access to sensitive records.

    And I explicitly test it - automated tests that authenticate as user A and try to read user B's resources and assert a 403 - because this is too important to leave to code review.

    Q10.8 - What's your approach to input validation and why does it matter beyond security?

    What it really tests: Whether validation is a deliberate boundary discipline (allowlist, at the edge) covering both security and data integrity.

    Weak answer: "We validated inputs to make sure they were the right type and not empty, and rejected anything that looked malicious."

    Why it fails: - "Looked malicious" implies blocklisting, which is weak. - Type/empty checks are shallow - no range, format, or business-rule validation. - No mention of validating at the trust boundary consistently. - Doesn't connect validation to data integrity, not just security.

    Follow-up ladder: 1. TECHNICAL - Allowlist or blocklist validation - which and why? - Allowlist superiority. 2. TRADEOFF - Where in the stack do you validate - and can you trust internal callers? - Trust-boundary discipline. 3. MEASUREMENT - How does bad validation corrupt data, not just create a vuln? - Integrity angle. 4. FAILURE - How do you validate without rejecting legitimate edge cases? - Balancing strictness and usability.

    Answer framework: 1. Validate at every trust boundary 2. Allowlist valid shapes, don't blocklist bad ones 3. Type, range, format, and business-rule checks 4. Reject early with clear errors 5. Don't trust internal callers blindly 6. Protects both security and data integrity 7. Balance strictness with real edge cases

    Rejection signals: - Blocklist mindset ("looks malicious"). - Only shallow type checks. - Trusts internal input implicitly. - No integrity motivation.

    Model answer skeleton: I validate at every trust boundary using allowlists - define exactly what a valid input looks like and reject everything else - rather than blocklists that try to enumerate bad input and always miss a case.

    That means type, range, format, and business-rule checks: not just 'is this a string' but 'is this a currency we support, in a plausible amount, matching the expected pattern'.

    I validate at the edge where untrusted data enters, and I don't blindly trust internal callers either, because a bug or a compromised service upstream can send garbage - defence in depth means each service guards its own inputs.

    Crucially this isn't only a security control: weak validation lets malformed data into the database that quietly corrupts reports, breaks downstream consumers, and is far more expensive to clean up later than to reject up front.

    The balance I watch is not being so strict that I reject legitimate edge cases - international names, unusual but valid emails - so I validate against real-world formats rather than naive assumptions, and return clear field-level errors so callers can fix their input.

    Q10.9 - [DRILL] Threat-model a GET /users/{id}/documents/{docId} endpoint. List every way it could leak data and the control for each.

    What it really tests: Whether the candidate can systematically threat-model an endpoint rather than react to a single vuln.

    Weak answer: N/A - drill. A weak attempt only checks authentication and stops.

    Why it fails: - Only considers whether the caller is logged in. - Misses object-level authorization on both id and docId. - Ignores enumeration, injection, and PII-in-logs. - No rate limiting or audit.

    Follow-up ladder: 1. FAILURE - How does the caller reach another user's docId even with a valid token? - Nested BOLA on both ids. 2. TECHNICAL - How do sequential ids enable enumeration, and how do you stop it? - Enumeration defence. 3. MEASUREMENT - What sensitive data might leak into logs or errors here? - PII leakage paths.

    Answer framework: 1. Authn: valid token required 2. Authz: verify the user owns {id} AND owns {docId} 3. Enumeration: non-sequential ids + authz 4. Injection: parameterise the lookup 5. PII: redact ids/content from logs and errors 6. Rate limit + audit access 7. Test cross-account and enumeration attempts

    Rejection signals: - Only checks authentication. - Misses ownership check on docId. - Ignores enumeration or injection. - Logs sensitive data.

    Model answer skeleton: Drill output: first, authentication - a valid token is required, but that's the floor, not the control. The main risk is broken object-level authorization on both ids: I must verify the authenticated user actually owns {id} and that {docId} belongs to that user, because an attacker with a valid token will swap in someone else's id or a doc id that isn't theirs - checking only one of the two is a common miss.

    Sequential ids invite enumeration - scripting through docIds to harvest documents - so I use non-guessable ids (UUIDs) and rely on the authorization check, not obscurity, as the real defence.

    The lookup is parameterised so a crafted id can't inject.

    For leakage, I make sure document contents, ids, and any PII never land in logs or error messages, and that a not-found for an unauthorized doc returns 404, not 403, so I don't confirm the doc exists.

    I rate-limit to blunt scraping, audit access to documents for forensics, and I'd write tests that authenticate as user A and try to fetch user B's documents and assert they're denied.
