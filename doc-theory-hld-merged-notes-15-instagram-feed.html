    Design an Instagram Feed

    10 sections · 868 words

    A read-heavy social feed: pre-compute where possible and handle celebrities gracefully.

    1. Features and Questions

    Features to design:

    • Create post (image/video/reel).
    • Follow/Unfollow.
    • See his/her own feed.

    Clarifying questions:

    • How many users can we follow? Unlimited.
    • Daily active users? 20 million.

    2. Functional and Non-Functional Requirements

    Functional requirements:

    1. User can create a post (image/video/reel).
    2. User can follow another user.
    3. User can see his/her own feed.

    Non-functional requirements:

    1. Availability is more important than consistency.
    2. Scalable (it could handle billions of users).

    3. Back-of-the-Envelope Calculation

    DAU: 20 million

QPS:
  Read  -> feed read (1 req)
  Write -> POST (1 req)
  User opens/refreshes feed -> 10 times a day.
  User posts -> 1 picture a day (1 MB).
  write : read = 1 : 10

Storage unit: assuming 5 years.

    The open questions to answer are the read QPS, the write QPS, and the storage unit.

    4. Social Media Interaction and Graph DB

    • Facebook, Instagram, and LinkedIn are social graphs.
    • A Graph DB (for example Neo4J, NoSQL) fits them:
    • Facebook: friend is a bi-directional connection (U1 <-> U2), an undirected graph.
    • Instagram: follow is a uni-directional connection (U1 -> U2), a directed graph.
    • LinkedIn: a hybrid approach (connection/follow).

    5. API Endpoints

    1. Posting something (user -> image/video/reel):

    POST /create/post/{userId}
Body:
{
  caption,
  content (img/video/reel),
  timestamp
}
Response: 200 OK

    2. Following a user (directed graph):

    Idempotent APIs -> dedupe double requests. Even if a double request comes, our API does not do anything wrong. When the request signature is identical, the API treats double calls as one.

    • The client may send the same request twice (/create/post/{userID} {} repeated).
    • The request carries headers such as UUID and IdempotentID; if two requests share uuid = 1234, only the first is processed and the second is deduplicated while the first is still processing.

    Idempotency by method:

    • GET and PUT are idempotent by default.
    • POST is not idempotent.

    Following a user is idempotent by default:

    u1 -> u2 (follow) -> Graph DB -> Neo4J
PUT : /user/{userId}
Response: 200 OK

    3. View our feed:

    GET : fetch/feed/{userId}

    6. High-Level Overview

    1. User posting something (img/video/reel):

    • Store metadata in a simple key-value store (Amazon DynamoDB): postId, type, timestamp.
    • Store the content (img/video/reel) in Amazon S3.

    2. User following other users:

    • Stored in the Graph DB (Neo4J).
    • Reasons: many-to-many relationships; the relationship is easily modelled by a graph; that is why a graph DB is used.

    3. User viewing his/her own feed:

    • A user sees posts from the accounts they follow, in reverse chronological order.
    • Flow: 1. Fetch the user's following list. 2. Fetch all the new posts from this list (metadata). 3. Sort the list in reverse chronological order.

    The Feed Service reads from a Feed Cache (list of postIds), the Graph DB, the Post DB, and Amazon S3, with a Feed DB behind the cache.

    7. Pull-Based vs Push-Based

    Instagram is read far more than written, so data fetching should be fast: reads should be smart, while writes can be slower.

    Two modes:

    • Pull based model (read slow):
    • Cons: slow.
    • Pros: better for users that are inactive.
    • Push based model (read is fast):
    • A user posts -> the post is pre-computed into their followers' feed cache.
    • This is pre-calculation / pre-compute.
    • Pros: read is faster.
    • Cons: bad for inactive users.

    A second problem with push: the hot-key problem / celebrity problem. Virat Kohli has an Instagram account with 250M followers, so pushing to every follower is expensive.

    8. Push-Based Flow

    1. User posting something:

    1. Fetch the followers list of the current user.
    2. Add the postId to the feed cache.
    3. Store a list of pairs <userId, postId>.

    Feed cache, post service, feed DB, and graph DB all participate.

    2. When a user sees his/her own feed: everything is pre-computed, so the Feed Service reads <userId, postId> pairs from the Feed Cache, backed by the Post DB and Graph DB.

    Problems? Both approaches have disadvantages -> hybrid approach.

    9. Hybrid Approach

    1. Every user has a boolean variable isPreComputed. - Virat Kohli (250M followers): pull based. - Follower count <= 1 million (fewer followers): push based. - People with more followers: pull based. - People with fewer followers: push based.
    2. Limit the number of posts in the feed cache (for example 200 people's data, about 90% of people); fetch the next 200 -> pagination.

    10. Kafka for Fan-Out

    A user with many followers (for example 500K) triggers a heavy fan-out:

    Post Service -> Kafka -> Workers -> <userId, postId> -> Feed Cache
Post DB / Graph DB on the write side.

    Reasons to use Kafka:

    1. Cache/DB throughput is less.
    2. To make the API call async.

    Final layout: client -> LB -> Post Service -> Amazon DynamoDB (POST DB) and Follow Service -> Graph DB, with Kafka feeding Workers and the Feed Cache, and the Feed Service reading from the cache and the Feed DB.
