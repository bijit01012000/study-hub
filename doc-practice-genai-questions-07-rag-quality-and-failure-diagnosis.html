      RAG quality and failure diagnosis

      0 sections · 3,889 words

      Module 07 · 9 questions · 1 practical drill

      Tell a retrieval failure from a generation failure, with evidence.

      Q7.1 — How do you evaluate retrieval quality?

      Weak answer: "We used RAGAS to score the pipeline, mainly faithfulness and context precision, and once the numbers looked reasonable we shipped it."

      Why it fails: - Cannot say where the reference answers or relevance labels came from. "Looked reasonable" is not a measurement. - Conflates faithfulness, a generation metric, with context precision, a retrieval one, without saying what each scores.

      Instant rejection: - No mention of classic IR metrics, recall@k, precision@k, MRR, or why an LLM-judged metric was chosen over them. - Never ran the eval against the retriever alone, only against the full pipeline's final output.

      Model answer: 1. We built a golden set of 150 real support queries from production logs, and hand-labelled the chunk IDs that actually contained the answer. 2. Against that we ran the retriever alone, recall at 10 around 0.81, meaning roughly a fifth of the labelled answer chunks never reached the top 10. 3. Separately, on the full pipeline, we ran faithfulness and context precision with an LLM judge, two different failure surfaces on separate dashboards. 4. When we shipped a new embedding model, golden-set recall was the regression gate before generation metrics even reran. 5. The aggregate number said retrieval was fine for months while one deprecated FAQ category silently returned stale chunks the average absorbed.

      Follow-ups: 1. MEASUREMENT — Where did your ground-truth query-to-chunk mapping come from, hand-labelled or LLM-generated? · Whether real ground truth exists or the score is self-referential. 2. TECHNICAL — What's the difference between what context precision measures and what faithfulness measures? · Retrieval-stage versus generation-stage metric literacy. 3. FAILURE — What did you do when the eval score looked fine but one query type was clearly failing? · Whether an aggregate score was broken down per category. 4. TRADEOFF — Why not just use recall@k and precision@k instead of an LLM-judged metric? · Knowing classic IR metrics need labels while LLM-judged metrics substitute a judge model.

      Tip: If you've built a labelled test set for a search or classification feature and tracked precision or recall against it, that's the same discipline. Don't claim you've run RAGAS in production. Say you understand the difference between a retrieval metric and a generation metric, and why ground truth matters.

      Numbers worth quoting: - 150-query golden set - recall@10 around 0.81 - Retrieval gate before generation - Break scores down per category

      Q7.2 — Walk me through precision versus recall in retrieval. Which did you tune for, and why?

      Weak answer: "Recall matters more, if you don't retrieve the right chunk the model has no chance. So we set k high and leaned on the reranker."

      Why it fails: - States the trade-off as one-sided, ignoring what a high k costs: noisier context, more tokens, more room for a wrong chunk. - Treats reranking as a free fix rather than a second stage with its own behaviour and latency cost.

      Instant rejection: - No numbers at all, doesn't know what k was or what the resulting precision looked like. - Never ties the choice to the task. Recall-first suits legal discovery but is risky for a bot citing contradictory chunks.

      Model answer: 1. Precision@k is what fraction of the top-k chunks are actually relevant. Recall@k is what fraction of all relevant chunks made it into the top k. 2. We tuned for recall at first-stage retrieval, k=20, because a missed chunk is unrecoverable, nothing downstream conjures information never retrieved. 3. We didn't hand k=20 to the generator. We reranked down to the top 4, where we optimised precision, past 5-6 chunks faithfulness dropped about 8 points. 4. The shape was recall-first at retrieval, precision-first at what reaches the prompt, with the reranker unable to recover a chunk retrieval missed. 5. For a compliance-style system I'd shift the calculus toward precision and abstention, since a confidently wrong citation is worse than an admitted miss.

      Follow-ups: 1. MEASUREMENT — What was precision@k doing to the generated answer when k was high, did you measure that? · Whether the precision cost was measured against generation quality. 2. FAILURE — Give me a case where high-recall retrieval actively made the final answer worse. · Concrete awareness that noisy context can get cited into a wrong claim. 3. TRADEOFF — How would your answer change for a system where a wrong answer is worse than no answer? · Whether the choice is task-dependent or a fixed habit. 4. TECHNICAL — What's the actual mechanism by which a reranker trades against your first-stage recall ceiling? · Understanding reranking reorders, it cannot recover recall the first stage missed.

      Tip: If you've tuned a search feature's result count against user complaints about noise versus missed results, that's the same trade-off, different shape. Don't claim you've tuned retrieval precision or recall. Say you understand the trade-off and which way you'd lean for a given task's cost of being wrong.

      Numbers worth quoting: - Recall-first at k=20 - Rerank down to top 4 - Faithfulness drops past 5-6 chunks - Reranker cannot fix lost recall

      Q7.3 — How do you catch a case where the model answered from its own knowledge, not the retrieved context?

      Weak answer: "We instruct the model to only answer from the provided context and say it doesn't know otherwise. That's mostly worked for us."

      Why it fails: - A prompt instruction is a mitigation attempt, not a detection mechanism. It doesn't tell you when the model ignores it. - "Mostly worked" has no measurement behind it, no rate, no test, no example caught.

      Instant rejection: - No distinction drawn between the model being right by coincidence and the model being genuinely grounded in the context. - No ablation or entailment check mentioned that would actually surface this failure.

      Model answer: 1. The dangerous version is invisible. The model answers correctly because it already knew the fact, not because it read the chunk, until the source changes. 2. First, an ablation test on the golden set: rerun generation with the retrieved context stripped. If the answer barely changes, context wasn't load-bearing. 3. We found this on about 12% of the golden set, concentrated in well-known category facts rather than our own specific pricing or policy details. 4. Second, an entailment-style check maps each claim in the answer to a supporting span in the context, catching coincidence even without ablation. 5. We alert if the unsupported-claim rate climbs on a rolling sample, since a slow drift usually means the corpus changed under a topic the model already knows.

      Follow-ups: 1. FAILURE — How would you tell the model being grounded from the model being right by coincidence? · Whether they see this failure as invisible exactly when it doesn't matter. 2. TECHNICAL — What's the ablation test, strip the context and rerun, actually supposed to show you? · If the model answers the same with no context, it wasn't using it. 3. MEASUREMENT — How would you build an automated check for this rather than spot-checking by eye? · Entailment-style faithfulness scoring, does every claim trace to a span. 4. TECHNICAL — Which topics in your corpus are most at risk of this, and why those specifically? · Recognising well-known topics are where the model needs context least.

      Tip: If you've tested a feature by removing an input to see if the output actually depended on it, that's the same ablation instinct this question wants. Don't claim you've caught ungrounded answers in production. Say how an ablation test would reveal it and why a prompt instruction alone can't.

      Numbers worth quoting: - Strip context, rerun, compare - ~12% of golden set ungrounded - Entailment maps claim to span - Alert on rising unsupported rate

      Q7.4 — How do you handle grounding, citations and attribution so an answer actually traces to a real source?

      Weak answer: "Every answer includes a link to the document it was pulled from, so the user can go check the source themselves if they want."

      Why it fails: - Shows a citation exists but never checks it supports the claim beside it, which is a citation-shaped hallucination. - Document-level attribution is far weaker than claim-level. A document can be cited right while the sentence is not.

      Instant rejection: - Pushes all verification onto the user, with no internal check before the answer ships. - No mention of what happens when the citation is wrong, no detection, no metric, no correction path.

      Model answer: 1. Early on we shipped document-level citations, and it made wrong answers look more trustworthy, the citation was real and topical but not specific. 2. That's citation-shaped hallucination. The answer looks sourced, so people stop checking it, exactly when they shouldn't. 3. We moved to claim-level attribution, tracking which chunk each sentence ties to, and verifying that chunk actually entails that sentence. 4. We measure this as a citation-accuracy rate on the golden set, what fraction of citations actually support the claim, treating under 90% as not ready. 5. For a compliance answer I'd want the system to refuse rather than cite loosely, since a confidently wrong, plausibly-cited claim costs more there.

      Follow-ups: 1. FAILURE — What stops the model citing a real, relevant document next to a claim it doesn't actually support? · Understanding citation-shaped hallucination. 2. TECHNICAL — Is your attribution at the document level or the claim level, and why does that matter? · Sentence-level traceability versus the false confidence of document-level citation. 3. MEASUREMENT — How would you measure your citation accuracy rate, and what's acceptable? · Whether citation correctness is tracked as its own metric. 4. TRADEOFF — What do you do differently for a high-stakes domain like compliance versus general support? · Whether attribution rigour scales with the cost of being wrong.

      Tip: If you've built an audit trail or changelog that ties a specific claim to a specific source record, not just a general reference, say that plainly. Don't claim you've measured citation accuracy. Say you understand the gap between a document-level link and a verified, claim-level source.

      Numbers worth quoting: - Claim-level, not document-level - Citation accuracy under 90% fails - Citation-shaped hallucination - High stakes: refuse, do not guess

      Q7.5 — What happens when a query's answer genuinely isn't in the corpus? How do you detect that?

      Weak answer: "If the retrieved chunks aren't relevant, the model should recognise that and tell the user it doesn't have that information."

      Why it fails: - Leaves detection to the generator, exactly where weak chunks produce a fluent, unjustified answer instead of abstaining. - No similarity threshold, classifier, or feedback loop described, so corpus gaps never get identified or filled.

      Instant rejection: - Assumes the model reliably self-reports uncertainty, not a safe assumption at the surface-fluency level models operate at. - No mention of what happens to flagged queries afterward. They just dead-end at a refusal message.

      Model answer: 1. We don't trust the model to notice it's out of scope, a weakly related chunk is often similar enough that it answers confidently from it anyway. 2. We gate on retrieval score. Below a threshold chosen against a labelled set of 60 in-scope and 60 out-of-scope queries, the request routes to abstention. 3. We accepted that refuses some genuinely answerable borderline queries, measured at roughly 4% of in-scope traffic, against answering from noise. 4. Every flagged query gets logged and reviewed weekly, which is how we found a real gap, a run of queries about an undocumented refund edge case. 5. That cluster became a ticket to write the missing document, not a threshold to keep tuning around.

      Follow-ups: 1. MEASUREMENT — What's the actual signal you gate on, and how was the threshold chosen? · Concrete detection mechanism versus hoping the model notices. 2. TRADEOFF — What's the failure mode when your threshold is set too low versus too high? · Understanding too strict refuses answerable queries, too loose lets weak matches through. 3. TECHNICAL — What do you do with queries flagged as unservable, does anything happen to them afterward? · Whether they feed corpus-gap analysis or just dead-end. 4. FAILURE — Give me a case where a query looked in-scope but wasn't, and the system got it wrong. · A concrete instance, not a hypothetical description.

      Tip: If you've built a fallback or "no results" path gated on a confidence score rather than trusting a downstream component to self-report, say that. Don't claim you've tuned an abstention threshold. Say you'd gate on a retrieval-side signal and review what gets flagged, rather than trust the model.

      Numbers worth quoting: - 60 in-scope, 60 out labelled set - ~4% of traffic refused, accepted - Weekly review of flagged queries - Gap found, became a doc ticket

      Q7.6 — How do you handle a question that needs information from two or more documents to answer?

      Weak answer: "We just increase k so we pull back more chunks, and the model is usually good enough to piece the pieces together itself."

      Why it fails: - A single query is anchored to the phrasing asked. Widening k pulls more chunks like that phrasing, not the second document. - No mention of decomposing the question into sub-queries, or verifying each hop was actually retrieved before generation.

      Instant rejection: - Misses that this fails silently. The model gives a fluent, half-correct answer from the one hop it found, reading as complete. - No cost acknowledged for decomposition, extra retrieval round-trips and latency, versus applying it to every query.

      Model answer: 1. Widening k doesn't fix multi-hop. The query embedding is anchored to how the question was asked, and the second hop's document shares little vocabulary. 2. We saw this on a question about the refund window for a plan an enterprise tier replaced. Retrieval missed the changelog naming the old plan. 3. What worked was decomposing the question into sub-queries, resolving which plan was replaced first, then retrieving again for that entity's policy. 4. We only generate once both hops surfaced a chunk above the relevance threshold, and flag likely multi-hop queries with a cheap classifier first. 5. We now measure per-hop coverage for the multi-hop subset, since the failure we'd been missing was a confident answer using only the first hop.

      Follow-ups: 1. TECHNICAL — Why doesn't widening k reliably fix this, mechanically? · Understanding a single embedding is anchored to the first hop's phrasing, not the second. 2. MEASUREMENT — How would you detect a multi-hop answer is missing a hop, rather than just being wrong? · Whether per-hop retrieval coverage is checked, not just final correctness. 3. TRADEOFF — What does query decomposition buy you here, and what does it cost? · Extra round-trips and latency in exchange for coverage. 4. FAILURE — What does a silent multi-hop failure look like to a user, how would they even notice? · Recognising the answer looks complete while quietly omitting a hop.

      Tip: If you've broken a complex query into sub-queries against separate data sources and joined the results, that's the same decomposition instinct. Don't claim you've solved multi-hop retrieval. Say why widening k doesn't fix it and how you'd decompose a question that needs two sources.

      Numbers worth quoting: - Widening k misses the 2nd hop - Decompose, then retrieve per hop - Classifier flags likely multi-hop - Measure coverage per hop, not final

      Q7.7 — Your corpus has conflicting versions of the same document. How do you deal with that?

      Weak answer: "We run deduplication on ingestion to strip out exact duplicates before they get indexed."

      Why it fails: - Exact-text dedup catches copies but does nothing for two documents that genuinely disagree because one is outdated. - No recency or authority signal. Nothing tells the retriever or generator that one version supersedes the other.

      Instant rejection: - No detection mechanism for when the model has already blended two conflicting chunks into one confident, contradictory answer. - Treats this purely as ingestion hygiene, with no generation-time or retrieval-time response at all.

      Model answer: 1. Exact-match dedup handles the boring case, the same PDF re-uploaded twice. The dangerous case is two coherent documents that genuinely disagree. 2. I tag every document with an effective-date and status at ingestion, and link a deprecated document to its replacement where known. 3. At retrieval time I filter out anything marked superseded by default, and only surface it if the query is explicitly about history or an audit. 4. For unclean cases I added a generation-time check: if retrieved chunks contradict each other on the same fact, flag it rather than let the model pick one. 5. We deliberately didn't delete old versions, support agents still legitimately query historical policy, the fix was visibility, not erasing the record.

      Follow-ups: 1. TECHNICAL — What's the difference between a duplicate and a conflict, and why does dedup only catch one? · Exact-match dedup versus semantically similar but contradictory documents. 2. TECHNICAL — What signal would tell the retriever that one of two conflicting chunks is stale? · Recency or authority metadata, or an explicit supersession link. 3. FAILURE — How would you detect afterwards that the model blended two conflicting sources? · Concrete detection, not just prevention. 4. TRADEOFF — What's the cost of aggressively archiving old versions versus keeping them retrievable? · Old content is sometimes still needed; blunt removal has its own failure mode.

      Tip: If you've handled two conflicting rows or records in a system by tagging one authoritative and one superseded, rather than deleting either, say that. Don't claim you've resolved document conflicts in a live RAG system. Say how you'd tag recency and authority and detect a blended, contradictory answer.

      Numbers worth quoting: - Dedup catches copies, not - conflicts - Effective-date and status tags - Superseded docs filtered by default - Flag conflicting chunks at gen time

      Q7.8 — You get a bad answer from the RAG pipeline. How do you tell if it's retrieval or generation at fault?

      Weak answer: "I'd look at the answer, see what went wrong, then check both the retrieved chunks and the prompt to figure out where the issue is."

      Why it fails: - "Check both" isn't a procedure. It doesn't say in what order, or what result at each step tells you to stop. - No isolation experiment described. Never separates the two stages so one test can decisively rule one out.

      Instant rejection: - Jumps straight to reading the prompt, the classic reflex that wastes time tuning generation when the real defect is upstream. - No mention of the one test that actually splits the search space, running generation on hand-fed, known-good context.

      Model answer: 1. First I confirm the answer is in the corpus at all. If not, this is a coverage gap rather than retrieval against generation, and I stop there. 2. I pull the chunks retrieved for that query and check three things: is the answer chunk there, what rank did it get, did it survive truncation. 3. If it was not retrieved or ranked highly, that is a retrieval fault. No prompt wording recovers a chunk that was never fetched. 4. If the chunk was there and ranked well, I run the decisive test. Hand-write the correct context, feed it to the generator, hold everything else constant. 5. Right with hand-fed context means retrieval was at fault. Still wrong means generation is misreading correct information.

      Follow-ups: 1. TECHNICAL — What's the one experiment that, run once, tells you which side of the pipeline is at fault? · The decisive test: hand-feed known-good context and rerun, splitting retrieval from generation. 2. MEASUREMENT — Before that test, what do you check in the retrieved chunks themselves? · Whether the right chunk was retrieved at all, and if it survived truncation. 3. FAILURE — Why is jumping straight to prompt tuning the wrong first move? · No prompt wording recovers information the retriever never fetched. 4. TECHNICAL — How do you turn this into something repeatable across many bad-answer reports? · Whether the procedure became a checklist or tool, not a one-off session.

      Tip: If you've isolated a bug by swapping in a known-good input to see if a downstream component still failed, that's the exact same isolation instinct. Don't claim you've diagnosed a live RAG failure. Say you'd hand-feed known-good context to split retrieval from generation before touching either.

      Numbers worth quoting: - Check corpus coverage first - Inspect rank and truncation - Hand-feed known-good context - One test splits both stages

      Q7.9 — DRILL: Wrong answers rose this week, no deploy happened. Build your diagnostic checklist, in order. (practical drill)

      Weak answer: "N/A, this is a drill. A weak attempt lists retrieval, generation and the prompt as an unordered bag, with no sequence or decisive test."

      Why it fails: - No ordering at all, and ignores the strongest clue in the prompt itself, something changed silently without a deploy. - No decisive isolation test anywhere, and no quantifying of the regression before diagnosing it as real.

      Instant rejection: - Doesn't consider silent causes: index drift, a provider-side model version bump, corpus edits, or a shift in traffic mix. - No mitigation instinct while still mid-diagnosis, waits to finish every step before doing anything about it.

      Model answer: 1. First, quantify. Pull this week's golden-set score against last week's baseline plus a sample of real bad-answer reports, "feels worse" needs a number. 2. Say recall at 10 dropped from 0.81 to 0.68, now it's real and retrieval-shaped. Second, since there was no deploy, check what changes without one. 3. Did the index rebuild cleanly, did an upstream model get a silent version bump, did new documents land, did the traffic mix shift toward a weak query type. 4. Third, for failing queries, pull retrieved chunks and check rank and truncation, that's how I once found a reindex had silently changed chunk boundaries. 5. Fourth, run the hand-fed-context test on any query where retrieval looks fine. If I confirm a cause early, like a bad reindex, I roll it back immediately.

      Follow-ups: 1. TECHNICAL — What do you check first, specifically because there was no deploy? · Suspecting silent-change causes, index drift, model version bumps, corpus edits. 2. MEASUREMENT — How do you confirm this is a real regression and not noise first? · Quantifying against a baseline before treating an anecdote as a trend. 3. TECHNICAL — Where does the hand-fed-context isolation test sit in your checklist, and why? · Placing the decisive test after coverage and chunk inspection, not instead of them. 4. FAILURE — What's the first thing you'd roll back to stop the bleeding mid-diagnosis? · Mitigation-first instinct even before the full root cause is known.

      Tip: If you've built an ordered incident-response checklist for a system regression, quantify first, check recent silent changes, then isolate, say that. Don't invent a specific RAG regression story. Say how you'd order the checklist and why you'd suspect a silent cause before touching any code.

      Numbers worth quoting: - Quantify before diagnosing - Suspect silent causes, no deploy - Inspect rank, then hand-feed test - Roll back a confirmed cause early
