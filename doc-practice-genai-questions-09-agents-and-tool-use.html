      Agents and tool use

      0 sections · 4,100 words

      Module 09 · 9 questions · 1 practical drill

      Defend an autonomous loop past the happy path.

      Q9.1 — Walk me through what's actually different between this and three LLM calls chained in a fixed order.

      Weak answer: "It's an agent because every step is an LLM call, not hardcoded logic, and nobody reviews it before it goes out."

      Why it fails: - The steps are fixed at design time. Nothing decides at runtime to skip, retry or call something else instead. - "No human reviewing it" describes supervision, not who picks the next action. A fixed pipeline can run unattended too.

      Instant rejection: - Calls anything with an LLM call in it an agent, regardless of who actually controls the branching. - Cannot point to one place where the system's path actually forks based on a tool result.

      Model answer: 1. My alerting pipeline ran three fixed LLM calls every time: summarise, look up the runbook, post to Slack, always the same order. No result ever changed the next step, so that's a workflow with LLM calls in it. 2. Incident triage was different. The model had , , and , and chose turn by turn which one to call based on the last result. 3. When came back clean, it skipped entirely and checked a downstream dependency instead, a branch nothing in my code specified in advance. 4. My real test: not whether an LLM is involved, not whether a human watches, but whether the model picks the next action from current state rather than me fixing it upstream. 5. I still default to a fixed pipeline for alert-to-ticket, because every alert needs the same three steps, and that's cheaper and easier to test than a planning loop I don't need.

      Follow-ups: 1. TECHNICAL — If the knowledge base search returns nothing, what does the system actually do next? · Whether there's real runtime branching or the next step runs regardless. 2. FAILURE — The draft contradicts the source it just retrieved. Who or what catches that before it ships? · Awareness that a fixed chain has no self-correction step built in. 3. TRADEOFF — If the task really is the same three steps every time, why make it an agent at all? · Recognises a fixed workflow is often the cheaper, safer choice. 4. MEASUREMENT — Watching an unlabelled trace, how would you tell an agent from a chain wearing agent language? · Names an observable signal: step count and order varying across runs.

      Tip: If you've built a state machine or a saga where the next step depends on the last result, you've made a similar branching-versus-fixed call. Don't claim you've built an agent. Say you've drawn the line between a fixed sequence and logic that branches on runtime state before.

      Numbers worth quoting: - 3 fixed calls, one workflow - Model picks the next action - Step count varies run to run - Fixed pipeline is often cheaper

      Q9.2 — How did you define your agent's tools, and what does the model actually see for each one?

      Weak answer: "I gave the model a Python function per tool with a clear name, a docstring and typed arguments, and it reads the function to decide."

      Why it fails: - The model never sees the function body or type hints, only whatever gets serialised into the tool definition. - No mention of what makes a description actually work: explicit scope, exclusions, and disambiguation from similar tools.

      Instant rejection: - Believes the model reads source code or docstrings directly rather than a served tool definition. - No plan for what happens when several similar tools are registered and the model has to pick one.

      Model answer: 1. For incident triage the model gets three things per tool: a name, a description and a JSON schema for input. It never sees my code, so the description carries all the selection signal. 2. Early on the model called , a ten-minute rebuild, when the phrasing was just 'it's stuck'. Rewording both descriptions to state scope fixed it. 3. The schema constrains argument shape, a required , an enum, so a malformed call gets rejected before it reaches my code. 4. Past about fifteen tools, selection accuracy dropped, and every definition was billed as input tokens whether used or not, so I grouped tools by domain and loaded only the relevant group. 5. I test description changes like a prompt change: a fixed set of deliberately ambiguous requests, checking which tool gets picked before and after each wording tweak.

      Follow-ups: 1. TECHNICAL — and exist. What stops the wrong one firing on a vague prompt? · Understands description precision, not model intelligence, disambiguates tools. 2. FAILURE — The model calls a tool with a parameter that isn't in your schema. What actually happens? · Real knowledge of schema validation versus a silently broken call. 3. TRADEOFF — You've registered 40 tools. What does that do to selection accuracy and your token bill? · Knows every tool definition is billed as input tokens on every turn. 4. MEASUREMENT — How did you actually check your tool descriptions were good, not just readable? · Whether selection is tested on held-out ambiguous cases or trusted on vibes.

      Tip: If you've written a clear API doc or function comment so a teammate calls the right one without reading the source, that's the same skill. Don't claim you've tuned tool descriptions for an LLM. Say you've written interface docs precise enough to stop the wrong function being called.

      Numbers worth quoting: - Name, description, schema only - ~15 tools before accuracy drops - Every tool costs input tokens - Test wording on ambiguous cases

      Q9.3 — Describe the loop your agent actually runs. What happens each iteration, and what stops it?

      Weak answer: "It keeps calling tools, logs, schema, source table, until it's figured out the cause and can answer. It stops once it's confident."

      Why it fails: - "Once it's confident" enforces nothing. The model can loop indefinitely or stop early on a fluent wrong diagnosis. - No step cap or budget, and no sign of handling oscillation if it re-checks the same log three iterations apart.

      Instant rejection: - "It stops when it's done" with no enforced condition actually behind that claim. - Never considered detecting repeated or oscillating tool calls at all.

      Model answer: 1. For the pipeline-triage agent, each iteration sees the full trace so far, the original alert plus every tool call and result, and picks one next action or stops. 2. If iteration 1's shows a schema mismatch, iteration 2 sees that log and picks next, not a repeat check. History drives the plan. 3. I never relied on the model deciding it was confident. I set a hard cap of 8 iterations, validated against forty historical pipeline failures where the median was 3. 4. After every tool call I also check whether the same tool ran with the same arguments in the last 3 steps. That catches oscillation before it burns the budget. 5. Three exits: a structured diagnosis result, hitting the step cap and returning what was found so far, or the oscillation check firing and escalating immediately.

      Follow-ups: 1. TECHNICAL — What's new in context by iteration 5 that wasn't there on iteration 1, and why does that matter? · Understands the loop conditions on the full accumulated history, not just the last result. 2. FAILURE — The model checks the same table schema twice, three iterations apart. What notices that? · Whether oscillation detection exists or only a step cap catches it late. 3. TRADEOFF — A hard cap of 8 versus 'stop when confident', what does each get wrong? · Sees a cap can cut off a real investigation while confidence-only can run forever. 4. MEASUREMENT — Across a hundred runs, how would you find your average and worst-case step count? · Whether termination is measured empirically, not assumed from one test.

      Tip: If you've written a retry loop with a max-attempts count and a check for repeated failures, you've built the same termination logic. Don't claim you've capped an agent loop. Say you've bounded a retry or polling loop and added a check for it going in circles before.

      Numbers worth quoting: - Step cap of 8, tested on 40 cases - Median 3 iterations to resolve - Same call, same args, 3 steps - 3 exits: found, capped, escalated

      Q9.4 — On step ten, what does the agent actually have access to, and where does that come from?

      Weak answer: "The conversation history is the memory, every result gets added to the messages, and on crash we replay from the last message."

      Why it fails: - Treats the growing message array as the only state. Nothing is described as persisted outside the model's context. - "Replay the conversation" assumes that's safe, but a tool side effect that already ran gets re-run too.

      Instant rejection: - Equates conversation history with the system's memory, with nothing persisted outside it at all. - No idempotency story for a tool call that may have already executed before a crash.

      Model answer: 1. I think in three layers: the model's in-turn scratchpad, the full tool-call history it reasons over, and state I persist outside the run entirely. 2. For an onboarding agent provisioning five systems, that's a database row per job with a status per system: VPN granted, email pending, Slack not started. 3. If the process dies after granting VPN access but before logging it, a naive restart that just replays the conversation would grant it a second time. 4. So every tool that changes real state checks the persisted record first. A retry against an already-granted system becomes a no-op, not a repeat. 5. Past about fifteen steps I summarise older results down to their outcome and drop raw payloads, accepting I might lose an error message's exact wording.

      Follow-ups: 1. FAILURE — Step seven grants VPN access, then the process crashes. On restart, how do you know it fired? · Whether outcomes are persisted independently of the conversation, or the system guesses. 2. TECHNICAL — At step twenty the history is long. What do you do about it, and what might you lose? · Awareness that summarising unbounded context can drop a needed detail. 3. TRADEOFF — Why keep separate persisted state at all, if the model can reread its own history for that? · Understands history dies with the run while external state survives restarts. 4. MEASUREMENT — How would you verify a retried step is actually idempotent, rather than assume it? · Whether idempotency is tested by replaying a step twice and checking state.

      Tip: If you've kept a job status table so a retried worker checks what already happened before acting again, that's the same instinct. Don't claim you've built agent memory. Say you've made a retried job idempotent by checking persisted state before it acts.

      Numbers worth quoting: - Scratchpad, history, and a store - Persist outcomes, not just intent - Check state before every retry - Summarise past roughly 15 steps

      Q9.5 — Your agent can issue a refund directly. What happens on failure, and why no human first?

      Weak answer: "If the refund fails we retry a couple of times then log it. Anything risky like refunds always gets human approval first, so we're covered."

      Why it fails: - Retrying blind on a payment call with no status check risks a double refund if the first call actually succeeded. - "Always human approval" is a blanket rule with no criterion, so it either bottlenecks or gets quietly skipped under load.

      Instant rejection: - No distinction between reversible and irreversible actions, the real basis for where the checkpoint sits. - "Log the error" is treated as a full failure path, with no escalation or record of the state left behind.

      Model answer: 1. I split actions by reversibility. Read-only and easily-reversible actions, an order lookup, a small coupon, run unattended by default. 2. Irreversible, high blast-radius actions, a refund over a threshold, a cancelled subscription, always stop for a human before executing, not after. 3. On a refund timeout the next call is never a blind retry. It's a status check against the provider's idempotency key first. 4. Only if that comes back not found does it retry, reusing the same idempotency key so even a race cannot cause a double refund. 5. I checked three months of approval logs and found humans amending about 4% of proposed refunds, mostly amount mismatches, so the gate was catching real errors.

      Follow-ups: 1. FAILURE — The refund call times out and you don't know if it fired. What does the agent do next? · Whether it checks real status before any retry, or retries blind. 2. TECHNICAL — Which actions run with no human at all, and what actual rule put them there? · A reversibility or blast-radius rule, not a uniform policy for everything. 3. TRADEOFF — Approval before every refund versus after with fast reversal, what does each cost you? · Sees pre-approval trades speed for safety, post-hoc trades risk for throughput. 4. MEASUREMENT — How do you know the human checkpoint catches real errors, not just rubber-stamps? · Whether the override or reject rate is actually measured over time.

      Tip: If you've decided which actions in a system can run unattended based on how reversible they are, that's the same judgement call. Don't claim you've set an agent's human checkpoint. Say you've drawn a reversibility line for automation in a system before.

      Numbers worth quoting: - Split by reversibility, not risk - Status check before any retry - Same idempotency key on retry - Roughly 4% of approvals amended

      Q9.6 — A per-file step cap runs across 3,000 files. What stops a runaway bill, and where does that cap alone fail?

      Weak answer: "Each file is capped at 10 iterations, so the worst case per file is bounded, and across 3,000 files the total cost is predictable."

      Why it fails: - Treats iteration count as cost. A later iteration carries a longer context, so it costs far more than the first. - No batch-level control at all, so a systemic failure across many files still burns the full budget unnoticed.

      Instant rejection: - Believes a per-run step cap alone bounds the cost of a large batch of runs. - No human-operable stop for a batch already running, only automatic per-file ceilings.

      Model answer: 1. A per-file cap of 10 only bounds one file. I ran a pilot of 100 files and tracked actual cost, not just iteration count, per file. 2. The median file finished in 2 iterations for a rupee or two, but a tail file with a gnarly generic type hit the cap and cost close to ₹90. 3. So I added a per-file budget ceiling of ₹120 on top of the step cap. Past that it stops and gets flagged for manual review instead. 4. A batch-level circuit breaker watches the rolling failure rate over the last 50 files. Above 30% needing escalation, the whole job pauses and pages me. 5. I also added a manual stop on the job dashboard that kills every in-flight run at once, because a bad batch shouldn't need a terminal to stop it.

      Follow-ups: 1. TECHNICAL — Files 40 and 41 both hit 8 iterations for different reasons. How do you spot that early? · Whether iteration counts are monitored across runs, not judged in isolation. 2. FAILURE — The first 50 files fail the same way, your core assumption was wrong. What stops the other 2,950? · A circuit breaker on systemic failure rate, not just a per-file cap. 3. TRADEOFF — A step cap of 10 versus a spend cap of ₹120 per file, what does each catch that the other misses? · Sees step count and real cost diverge as context grows within a run. 4. MEASUREMENT — How would you size that per-file budget instead of picking a number that feels safe? · Whether the ceiling comes from a measured pilot run, not intuition.

      Tip: If you've set a spend alert on a cloud job, or a circuit breaker that halts a batch on a rising error rate, that's this same instinct. Don't claim you've capped agent spend. Say you've set a cost ceiling and a kill switch on a batch job before, not just a retry limit.

      Numbers worth quoting: - Typical file: a rupee or two - Tail file: close to ₹90 - Per-file ceiling: ₹120 - Pause batch above 30% failing

      Q9.7 — You'd split this into an orchestrator plus a subagent per table. Convince me that beats one agent alone.

      Weak answer: "Each subagent focuses on one table so they're more accurate, and running in parallel gets through all the tables faster."

      Why it fails: - "More accurate because focused" isn't argued. One agent seeing the full picture might catch a cause two tables share. - Only counts wall-clock speed, with no mention of the token-cost multiplier from N contexts plus an orchestration layer.

      Instant rejection: - No awareness that subagents without shared context can duplicate or contradict each other's findings. - Assumes the split is obviously correct with no case made for when a single agent is better.

      Model answer: 1. I only split into subagents when the failing tables are genuinely independent, different source systems, no shared upstream job between them. 2. Two of our tables once failed from one upstream job that dropped a column. Each subagent rediscovered it separately, roughly double the tokens a single agent noticing the shared cause would have spent. 3. Ten subagents each carrying their own history, plus an orchestrator summarising all ten, cost several times more than one agent working the list in sequence. 4. My rule: split only when tables are truly independent, and make the orchestrator's merge step explicit about conflicting root causes, not assume reports combine cleanly. 5. I default to one sequential agent with the full table list in context whenever failures might share a cause, which for us was most of the time.

      Follow-ups: 1. FAILURE — Tables A and B share a root cause. Does the subagent for B find it too, and then what? · Awareness subagents without shared context duplicate discovery work. 2. MEASUREMENT — What's the token cost of ten subagents on ten tables versus one agent working sequentially? · Knows multi-agent systems carry a real, often much higher token cost. 3. TRADEOFF — When would one sequential agent genuinely beat ten independent subagents? · Can argue the single-agent case, not just concede its downsides. 4. TECHNICAL — The orchestrator merges ten reports. What happens when two of them disagree? · Whether a real reconciliation step exists in the orchestrator.

      Tip: If you've decided whether to parallelise a batch job or run it in one process because the sub-tasks weren't truly independent, that's this call. Don't claim you've built a multi-agent system. Say you've weighed parallelism against shared state and coordination cost in a batch job before.

      Numbers worth quoting: - Split only if truly independent - Shared cause found twice, wasted - N agents cost several times one - Orchestrator reconciles conflicts

      Q9.8 — The migration passed the test suite. Convince me you'd still catch a bad run, or admit you wouldn't.

      Weak answer: "If the code compiles and tests pass, that's what matters, so that's what I score. I don't care how many tries it took."

      Why it fails: - Passing once says nothing about whether the approach generalises. Five wrong turns and a lucky fix fail worse next time. - Ignores unsafe intermediate actions a passing final state can hide, like editing a file outside scope and reverting it.

      Instant rejection: - Believes a passing final state guarantees the intermediate steps were safe or correct. - No step-level reference or rubric to grade a trajectory against, only the end diff.

      Model answer: 1. A migration run once passed the test suite after three attempts, two of which briefly broke an unrelated file before self-correcting. The end diff hid all of that. 2. Now I score the trajectory: was each tool call the right one given what was known then, and were there redundant or self-contradicting edits along the way. 3. That needs a reference, a per-category rubric like correct import change, correct call site, no edits outside the target file, graded step by step. 4. A 3-step run that goes straight to the right fix outscores a 9-step run that flailed through two wrong APIs first, even though both technically passed. 5. Building that rubric and picking a sampling rate is general evaluation practice, covered in Module 8. What's agent-specific is grading each step, not only the end.

      Follow-ups: 1. FAILURE — Tests pass, but a file was edited outside scope on step 3, reverted on step 6. What score? · Whether unsafe intermediate actions are penalised even after later cleanup. 2. MEASUREMENT — One run took 3 steps, another took 9 with two failed calls. Same score? · Whether trajectory quality, not just the end state, factors into scoring. 3. TECHNICAL — What does step-level labelling need that a pass or fail on the final diff doesn't? · Understands a reference trajectory is needed for each step, not only the end. 4. TRADEOFF — Grading every step by hand doesn't scale. What do you actually do at volume? · Realistic about sampling or automated step checks versus full manual review.

      Tip: If you've code-reviewed a PR that passed CI but took a messy path to get there, you've already judged a trajectory, not just an outcome. Don't claim you've built agent evaluation. Say you've judged a solution's approach and safety, not only its passing test, before.

      Numbers worth quoting: - End state can hide 3 wrong turns - Score steps, not just the diff - Shorter, cleaner run scores higher - Rubric defined per task category

      Q9.9 — [DRILL] Specify an invoice-matching agent: the tools, what stops the loop, and every failure path. (practical drill)

      Weak answer: "N/A, this is a drill. A weak attempt names two tools, says it stops when matched, and has no plan for a partial match."

      Why it fails: - No answer for the invoice that doesn't cleanly resolve, no PO found or one outside tolerance. - No idempotency on . A retried call risks a duplicate payment, the worst failure here.

      Instant rejection: - "Stops when matched" isn't a bounded termination, and gives no exit for an invoice it can't resolve. - Tool names given with no scope, nothing distinguishes what will and won't do.

      Model answer: 1. Tools: , read-only; by vendor and amount range, explicitly returning zero, one or several candidates, never assuming one. 2. takes tolerance as an explicit parameter, I'd set 2% from a month of manually-approved invoices, not left for the model to eyeball. 3. is irreversible and idempotent on invoice id, so a retried call against an already-paid invoice is a no-op. is always safe. 4. Termination: the loop ends at exactly one of three states, approved, flagged, or a hard cap of 4 steps reached, which flags by default rather than guessing. 5. On a payment timeout the next call is , never a retry of itself. Every approval over ₹ 50,000 gets a same-day human spot-check.

      Follow-ups: 1. TECHNICAL — returns three plausible POs. What actually resolves that? · Whether ambiguity resolves to a defined rule or an escalation, not a guess. 2. FAILURE — times out and you don't know if it fired. What's the very next call? · A status check before any retry, given a duplicate payment is the costliest mistake. 3. TRADEOFF — A 0.5% tolerance versus 5%, what does tightening or loosening actually cost? · Sees tolerance as a dial: too tight floods review, too loose approves mismatches. 4. MEASUREMENT — How many steps should one invoice reasonably take, and what happens past that? · A termination tied to a measured distribution, with a defined exit for outliers.

      Tip: If you've designed a reconciliation job with tolerance thresholds and a manual-review queue for anything ambiguous, that's the same shape. Don't invent an agent story. Say you'd apply the same scoped tools, explicit tolerance and idempotent write you'd use in any matching job.

      Numbers worth quoting: - Tolerance: 2%, from real approvals - Cap: 4 steps, then flag - Idempotent on invoice id - Spot-check above ₹50,000
