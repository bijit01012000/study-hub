      AI / RAG — Ingestion

      0 sections · 528 words

      43. What is RAG and why not fine-tuning?

      Retrieval-Augmented Generation retrieves relevant passages at query time and injects them into the prompt, so the model answers from those, not training weights. Fine-tuning bakes knowledge into weights: expensive to redo when docs change, still hallucinates, and you can't audit which source produced an answer. RAG updates instantly on re-index, is auditable via citations, and reduces hallucination because the prompt says "answer only from context."

      44. Walk me through the ingestion pipeline.

      Async on a dedicated ingestionExecutor pool. (1) Upload PDF → S3 (MinIO locally); return 201 with PENDING immediately. (2) Apache Tika AutoDetectParser streams the file and extracts plain text. (3) Fixed-size chunking ~2000 chars (~500 tokens) with 200-char overlap, trying to break on a sentence boundary in the back half of the window. (4) Each chunk → Spring AI EmbeddingModel (Ollama nomic-embed-text, 768 dims) → written to pgvector via JdbcTemplate with ?::vector. (5) In one final @Transactional completeIngestion: status → COMPLETED, chunk count recorded, document.ingested written to the outbox.

      45. Why is embedding done outside the transaction, per chunk?

      Each embed call hits Ollama and can be slow. If I held a DB transaction open across that inference, I'd pin a connection for seconds per chunk and exhaust the pool under load. So I embed outside any transaction, then write the chunk + embedding in a short per-chunk transaction. The trade-off: those per-chunk writes aren't one atomic unit, but that's fine — if the job dies partway, the document stays non-COMPLETED and no document.ingested event fires, so nothing downstream sees a half-ingested doc.

      46. So how is document.ingested still safe if chunks are written non-atomically?

      Because the event is only written in the final completeIngestion transaction alongside the status flip to COMPLETED. Either the document is COMPLETED and the event is in the outbox, or neither. The earlier per-chunk writes are durable work but don't gate the event. It's the outbox pattern giving me a clean atomic "done" boundary.

      47. What's the async-before-commit race, and did you hit it?

      If you call an @Async method from inside a @Transactional method, the async thread can start before the outer transaction commits — it opens a new connection, tries to load the row you "just saved," and gets not-found because the row isn't visible yet. The fix is to dispatch the async work only after commit, via a TransactionSynchronizationManager afterCommit hook. It's nasty because it passes every unit test (tests rarely run realistic async threading) and only surfaces under real concurrency.

      48. Why fixed-size chunking? Isn't semantic chunking better?

      Semantic/recursive chunking gives better retrieval quality but adds complexity. Fixed-size with overlap is defensible for an MVP, and hybrid search + RRF compensates for some boundary-split damage. I sentence-align the cut when I can. Semantic chunking is an explicit "with more time" item.

      49. What does the overlap buy you?

      Continuity across boundaries. If an answer straddles a chunk cut, the 200-char overlap means the surrounding sentence appears in both neighbors, so retrieval still surfaces a chunk containing the full context instead of a sentence sliced in half.
