    Lecture 03 — Master Apache Maven in one video

    22 sections · 4,725 words

    Lecture 03

    Scope evidence: "Master Apache Maven in one video | POM, Dependencies & Lifecycle" (playlist map, verified). The repo lecture folder carries a MavenDemo project (org/example/MavenDemo with Main, Demo, Demo2, and controller/HelloController) alongside these notes.

    This lecture answers the question every beginner eventually asks: why does a Java project need a build tool at all? It starts from the raw journey of .java to .class, shows why sharing loose class files breaks down, introduces the JAR and the classpath, and then explains exactly how Maven standardizes structure, dependencies, builds, and packaging. Everything is grounded in the source notes: JARs, pom.xml, coordinates, starters, transitive dependencies, repositories, settings.xml, and the lifecycle rule that running one phase runs every earlier phase.

    1. The Basic Journey of Java Code

    Before Maven, we need the base flow of a Java program in our heads:

    Hello.java  -- compiled by javac -->  Hello.class  -- run by JVM -->  output
    • .java file = source code written by the developer.
    • .class file = compiled bytecode understood by the JVM.

    Java code is never executed as .java files directly. First it is compiled into .class files, and then the JVM runs those .class files. This is the same "write once, run anywhere" contract from earlier lectures, seen from the build side.

    Important: The compiler (javac) and the runtime (JVM) are two separate steps. Maven does not remove either one; it automates the step in between and everything around it.

    2. What Happens in a Real Java Project

    A real project is never one class. It may have many files:

    User.java
Order.java
Payment.java
EmailService.java
InvoiceGenerator.java
Main.java

    After compilation, each source file becomes its own .class file:

    User.class
Order.class
Payment.class
EmailService.class
InvoiceGenerator.class
Main.class

    Now imagine sharing this project with another developer. Sending many separate .class files is not practical because:

    • files can get misplaced;
    • package/folder structure can break;
    • some files may be missed;
    • resource files may not be included;
    • running the project becomes confusing.

    Java needed a standard way to bundle compiled code and related files together. That standard bundle is the JAR.

    3. JAR Files: What They Are and Why We Need Them

    JAR stands for Java Archive. A JAR file is a packaged bundle for Java projects - think of it as a ZIP file designed specifically for Java.

    A JAR file can contain:

    • .class files;
    • folders/packages;
    • images;
    • properties files;
    • metadata;
    • configuration files.

    In simple words: a JAR file is a standard way to package Java compiled code and related resources into one file.

    There are two major reasons JAR files matter:

    1. To share Java code easily. Package compiled .class files into one calculator.jar; another developer adds that JAR and uses your compiled code. This is how many Java libraries are shared.
    2. To use external libraries. When we say "I am using Spring Core," practically our project is using Spring Core JAR files. A library is often just compiled Java code packaged as a JAR.

    4. Library JAR vs Application JAR (and the Fat JAR)

    First, the library-versus-application distinction:

    Term Meaning
    Library Code created for other developers to use inside their projects. It usually does not run independently.
    Application Code created for the end user. It can run as a complete program, usually with a main() method or an application entry point.

    For the same calculator.jar: if it only provides reusable calculator functions it is a library JAR; if it contains a complete runnable program it is an application JAR.

    A second, sharper distinction matters for Spring Boot:

    Aspect Normal library JAR Spring Boot executable JAR
    Contains your compiled code Yes Yes
    Contains external dependency JARs inside Usually no Can include them
    How dependencies are described Separately via Maven pom.xml Bundled so the app runs as one JAR
    Runnable on its own Usually not Yes

    A normal library JAR usually does not contain all of its dependency JARs inside it; its dependency information is managed separately through Maven using pom.xml. A Spring Boot application, however, is commonly packaged as an executable JAR that can contain the application code along with required dependencies. That is why we often call the Spring Boot output a fat JAR or executable JAR.

    Golden rule: A library says "use my classes." An application says "run me." A fat JAR tries to be both by carrying its whole dependency world inside one file.

    5. External Libraries and the Classpath

    Suppose your Java code uses an external JAR. Conceptually the flow is:

    Your Java code
      +
External JAR file
      |
      v
Compiled together
      |
      v
Run by JVM

    During compile time and runtime, Java must know where to find the required classes. For example, Java may need to know: "This class is not in my project; it is inside this external JAR." This connection is handled by the classpath.

    The classpath is the place where Java searches for classes. Java searches for classes in:

    • your own project classes;
    • external JAR files;
    • other configured class locations.

    If the class is present in your project, Java finds it there. If it is inside an external JAR, Java must know the location of that JAR. In simple words: the classpath tells Java where to search for required classes.

    Important: The classpath is not a folder you edit by habit; it is the search list the tools build for the compiler and the JVM. Maven's job includes assembling that list so you rarely do it by hand.

    6. Where Maven Comes In

    If a project needs only one external JAR, we can manually download it and add it to the project. But real projects usually need many third-party libraries, and then many problems appear:

    • Where should we download these JARs from?
    • Which version should we use?
    • What if one JAR depends on another JAR?
    • What if two teammates use different versions?
    • What if we forget to add one required JAR?
    • What if version 1 works, but version 2 breaks compatibility?

    This is exactly where Maven becomes useful. Maven says: do not manually download and manage JAR files. Tell me what dependency your project needs, and I will download and manage the required JARs for you.

    7. What Maven Is and What It Does Practically

    Maven is a project management and build automation tool for Java projects. It is important to understand that Maven does not exist only because of Spring - Maven is independent of Spring. You can use Maven with:

    • Core Java projects;
    • Spring projects;
    • Spring Boot projects;
    • Hibernate projects;
    • many other Java-based projects.

    In simple words, Maven helps us manage project structure, dependencies, builds, packaging, and project configuration in a standard way. Practically, Maven mainly helps with these things:

    1. It gives a standard project structure.
    2. It compiles Java code.
    3. It runs tests.
    4. It creates JAR/WAR files.
    5. It downloads external JAR libraries.
    6. It manages dependency versions.
    7. It uses plugins to perform build-related tasks.

    This makes Java projects more consistent and easier to work with, especially in teams.

    Interviewer's perspective: A strong answer names Maven as a build and dependency-management tool that is framework-independent. Saying "Maven is a Spring tool" is the fastest way to look like you have only copied tutorials.

    8. Maven and IDEs: One Standard Tool for Every Editor

    Maven can be used from the command line:

    mvn clean install

    Most modern IDEs also support Maven directly, such as IntelliJ IDEA, Eclipse, and VS Code. Every IDE may have its own project structure, but Maven gives a standard structure that works across tools. That is why Maven is helpful in real projects.

    9. Convention Over Configuration and the Standard Project Structure

    Maven follows a principle called Convention over Configuration. This means Maven already assumes a standard project structure. If we follow that structure, we do not need to manually configure everything.

    For example, Maven expects main Java code inside src/main/java and test code inside src/test/java. Because of this standard convention, Maven automatically knows where to find source code, test code, resources, and where to place generated output.

    A typical Maven project looks like this:

    my-maven-project/
|-- pom.xml
|-- src/
|   |-- main/
|   |   |-- java/
|   |   `-- resources/
|   `-- test/
|       |-- java/
|       `-- resources/
`-- target/

    Each part has one job:

    Path What it holds
    pom.xml Information about the complete Maven project
    src/main/java Main Java source: controller, service, repository, utility, main classes
    src/main/resources Non-Java files: application.properties, application.yml, config files, static files, templates
    src/test/java Test code: unit tests and integration tests
    src/test/resources Resources needed only during testing: test config files, test data files
    target Generated output: compiled .class files, test reports, generated sources, final JAR/WAR, temporary build files

    The target folder is created by Maven during the build process. If we delete it, Maven can recreate it during the next build - so target is generated output, not source code.

    Golden rule: Follow the convention and Maven stops asking questions. Break the convention and you start paying rent in configuration files.

    10. pom.xml: The Heart of a Maven Project

    Every Maven project has a file called pom.xml. POM stands for Project Object Model. The pom.xml file is the heart of a Maven project because it tells Maven:

    • what the project is;
    • which version the project has;
    • what type of output should be created;
    • which external libraries are needed;
    • which plugins should be used;
    • whether there is any parent configuration.

    Every pom.xml starts with a root <project> tag. A simple POM may look like this:

    <project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.coderarmy</groupId>
    <artifactId>calculator-app</artifactId>
    <version>1.0.0</version>
</project>

    The extra xmlns lines define the XML namespace and structure. For beginners, we do not need to deeply focus on them at this stage.

    11. Maven Coordinates, SNAPSHOT, Packaging, and Properties

    Maven coordinates

    These three tags uniquely identify a project or dependency:

    Tag Role Example
    <groupId> The organization, company, or domain that owns the project com.coderarmy
    <artifactId> The name of the project or module calculator-app
    <version> Which version of the project is being built 1.0.0

    Together they are called Maven coordinates. Mnemonic: remember GAV - GroupId, ArtifactId, Version.

    <modelVersion>4.0.0</modelVersion> tells Maven which POM model version this file follows; most Maven projects use 4.0.0.

    SNAPSHOT

    Sometimes we see versions like <version>1.0.0-SNAPSHOT</version>. SNAPSHOT means the project is still under development. In simple words:

    • 1.0.0 -> stable release version;
    • 1.0.0-SNAPSHOT -> development version, not considered a final stable release yet.

    packaging

    The <packaging> tag tells Maven what type of output should be created.

    Packaging Meaning
    jar Creates a JAR file
    war Creates a WAR file, usually for traditional web applications
    pom Used for parent or aggregator projects

    If we do not mention packaging, Maven defaults to jar.

    properties

    The <properties> tag defines reusable values in the POM:

    <properties>
    <maven.compiler.source>17</maven.compiler.source>
    <maven.compiler.target>17</maven.compiler.target>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>

    Here we are telling Maven: use Java 17 source code, compile it for Java 17, and use UTF-8 encoding. Properties make the POM cleaner because the same value can be reused in multiple places.

    12. Dependencies: Starters and Transitive Dependencies

    The <dependencies> section contains external libraries required by the project. For example, the MySQL driver is declared as mysql:mysql-connector-j:8.x.x in coordinates form. Each dependency is identified using Maven coordinates: groupId + artifactId + version. When Maven reads this dependency, it downloads the required JAR file from a Maven repository. The same pattern applies to a Hibernate dependency: declaring org.hibernate.orm:hibernate-core:6.x.x tells Maven the project needs Hibernate Core, and Maven downloads the Hibernate JAR and manages its required supporting dependencies.

    Kind of dependency What it is Example
    Library dependency A single external JAR you need mysql-connector-j, hibernate-core
    Starter dependency A group of related dependencies for one feature spring-boot-starter-web
    Transitive dependency A dependency of your dependency B and C pulled in because A needs them

    In Spring Boot projects we commonly use starter dependencies:

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

    A starter dependency does not mean only one JAR. It usually brings a group of related dependencies needed for a particular feature; for example, spring-boot-starter-web brings dependencies related to web application development.

    Transitive dependencies work like this:

    Your project needs A
A needs B
B needs C

    If you add dependency A, Maven can automatically download B and C as well. These are called transitive dependencies: dependencies of your dependencies. This is one of the biggest reasons Maven is useful - without Maven, we would have to manually find and download every required JAR.

    Important: Starters are convenience bundles, not single files. One starter line can quietly add a dozen JARs to your classpath, all at versions chosen to work together.

    13. Maven Plugins

    Dependencies are libraries that our project uses. Plugins are tools that Maven uses to perform tasks. Maven plugins can help with:

    • compiling code;
    • running tests;
    • creating JAR files;
    • creating reports;
    • running a Spring Boot application;
    • packaging the application.

    For example, the Spring Boot Maven plugin helps package and run Spring Boot applications. In simple words: a dependency is used by our application code; a plugin is used by Maven during the build process.

    14. Maven Repositories: Local, Central, Remote, and settings.xml

    Maven downloads dependencies from Maven repositories. A Maven repository is a storage place where Maven artifacts are kept. Artifacts can include JAR files, WAR files, POM files, plugins, and other build artifacts. At a beginner level, remember these three types:

    Repository What it is Location / examples
    Local A folder on your own computer ~/.m2/repository
    Maven Central A huge public repository of open-source Java libraries Spring, Hibernate, Jackson, JUnit, MySQL Connector
    Remote Any Maven repository not on your local machine Nexus, Artifactory, GitHub Packages, Maven Central

    Local repository

    The local repository is a folder on your own computer. Default location:

    • Mac/Linux: ~/.m2/repository
    • Windows: C:\Users\<your-username>\.m2\repository

    The local repository has two main jobs:

    1. It caches downloaded dependencies.
    2. It stores your own locally installed artifacts.

    When Maven downloads a dependency for the first time, it stores it in the local repository. Because of this, the first build may be slower, but later builds are faster because dependencies are already cached.

    What happens during mvn install?

    mvn install builds the project and stores the final artifact in the local Maven repository, for example at ~/.m2/repository/com/example/MavenDemo/1.0/. This allows other local Maven projects on the same machine to use that artifact.

    Maven Central repository

    Maven Central is a huge public repository where many open-source Java libraries are published. When we add a public dependency in pom.xml, Maven usually downloads it from Maven Central if it is not already available locally.

    Remote repository and private repositories

    A remote repository is any Maven repository that is not on your local machine - available through the internet, a company network, or a private repository server. In companies, not every JAR is public; a company may create internal libraries that should only be used inside the organization, using private repositories like Nexus, Artifactory, or GitHub Packages. A private repository can be configured in pom.xml like this:

    <repositories>
    <repository>
        <id>company-repo</id>
        <url>https://repo.company.com/maven2</url>
    </repository>
</repositories>

    settings.xml

    settings.xml is Maven's user-level configuration file, usually found inside the .m2 folder: ~/.m2/settings.xml. It can contain user-specific settings such as repository credentials, proxy settings, mirror configuration, and a custom local repository location. For beginners it is enough to remember: pom.xml is project-level configuration, while settings.xml is user/machine-level Maven configuration.

    Important: pom.xml describes the project for everyone; settings.xml describes your machine for yourself. Credentials and mirrors belong in settings.xml, never in a shared POM.

    15. How Maven Searches for a Dependency (and Why Deleting .m2 Fixes Things)

    Suppose pom.xml declares com.fasterxml.jackson.core:jackson-databind:2.17.0. Maven roughly follows this process:

    1. Read pom.xml.
    2. See that a dependency is required.
    3. Check the local repository first.
    4. If found locally, use it.
    5. If not found locally, check remote repositories.
    6. Download the JAR and POM.
    7. Store them in the local repository.
    8. Use them in the project build.

    That is why the first build is usually slower than later builds: the first time, Maven downloads dependencies; after that, Maven uses the cached dependencies from the local .m2 repository.

    Sometimes dependency files inside the local repository become corrupted or incomplete, for example because:

    • a download failed in between;
    • the internet disconnected during a dependency download;
    • a partial JAR file got saved;
    • metadata became inconsistent.

    In such cases, deleting the problematic dependency folder from .m2/repository forces Maven to download it again. That is why deleting .m2/repository or a specific dependency folder sometimes fixes Maven dependency errors. However, deleting the entire .m2/repository means Maven will need to download all dependencies again.

    16. The Maven Lifecycle: Three Lifecycles and the Phase Rule

    A Java project has a build journey, for example: check project -> compile code -> run tests -> create JAR -> store/deploy artifact. Maven calls this ordered build journey a lifecycle. In simple words: a Maven lifecycle is a standard sequence of steps Maven follows to build and manage a project.

    The heart of the Maven lifecycle is this rule:

    Important: When we run a Maven phase, Maven automatically runs all earlier phases of that lifecycle before it.

    For example, mvn package does not only run package - it runs the earlier required phases first:

    validate -> compile -> test -> package

    Similarly, mvn install runs:

    validate -> compile -> test -> package -> verify -> install

    Maven has three main lifecycles:

    Lifecycle Purpose
    Clean Cleans old build output
    Default Builds, tests, packages, installs, and deploys the project
    Site Generates project documentation and reports

    Clean lifecycle

    The clean lifecycle removes old build output. Common command: mvn clean. Usually this deletes the target folder. This is useful when we want a fresh build.

    Default lifecycle phases

    The default lifecycle is the main build lifecycle. Important phases: validate -> compile -> test -> package -> verify -> install -> deploy. Each phase represents one step in the build journey.

    Phase Meaning
    validate Checks whether the project is valid
    compile Compiles .java files into .class files
    test Runs test cases
    package Creates JAR/WAR file
    verify Performs additional checks on the packaged output
    install Stores artifact in local .m2 repository
    deploy Uploads artifact to a remote Maven repository

    Detail worth knowing:

    • validate checks whether pom.xml is present, readable, has required project details, and that the project structure is valid enough to continue (mvn validate).
    • compile compiles the main Java code (mvn compile); the flow is src/main/java -> target/classes, so source files become .class files inside target/classes.
    • test runs the test cases (mvn test); Maven compiles and runs tests from src/test/java, verifying the code works before packaging.
    • package creates the final packaged output (mvn package); for a normal Java project this usually creates a JAR inside target, for example target/MavenDemo-1.0.jar. For web applications it may create a WAR depending on the packaging type.
    • verify checks whether the packaged output is valid (mvn verify); in bigger projects it can include integration tests, code quality checks, coverage checks, and extra validation.
    • install builds the project and stores the final artifact in the local Maven repository at ~/.m2/repository (mvn install); useful when another local project needs to use this project as a dependency.
    • deploy builds the project and uploads the final artifact to a remote Maven repository (mvn deploy), such as company Nexus, company Artifactory, GitHub Packages, or another remote Maven repository.

    Interviewer's perspective: deploy is often confused with pushing code to GitHub. GitHub usually stores source code; a Maven remote repository stores built artifacts like JAR files so that other projects can use them as dependencies.

    Site lifecycle

    The site lifecycle generates project documentation and reports. Command: mvn site. Output usually goes inside target/site. This is separate from the normal build flow.

    What happens when we run mvn clean install?

    Maven runs two lifecycle commands together:

    mvn clean install = clean old output
                  + build the project again
                  + run tests
                  + package the project
                  + install the artifact into local .m2 repository

    First Maven runs the clean lifecycle and deletes old build output, usually the target folder. Then Maven runs the default lifecycle up to the install phase: validate -> compile -> test -> package -> verify -> install.

    Mnemonic for the default phases: "Very Cool Tigers Play Violin In Delhi" - Validate, Compile, Test, Package, Verify, Install, Deploy.

    Maven archetypes

    A Maven archetype is a project template: a starter template with a predefined folder structure and configuration. It can generate projects quickly instead of creating everything manually (template -> project structure + basic configuration + boilerplate files). Modern Spring Boot projects are usually created using Spring Initializr, but Maven archetypes are still useful to understand as a Maven concept.

    17. Myth vs Reality

    Myth Reality
    "Maven is a Spring tool" Maven is independent of Spring; it works with Core Java, Spring, Boot, and Hibernate projects
    "A JAR is only .class files" A JAR can also hold folders, images, properties, metadata, and config files
    "A library JAR contains all its dependencies" Usually it does not; dependencies are managed separately through pom.xml
    "mvn package only packages" It also runs all earlier phases: validate, compile, and test
    "Maven Central and the local repo are the same" Central is public and remote; the local repo is the cache at ~/.m2/repository
    "Deleting .m2 is always a safe quick fix" It works when files are corrupt, but forces re-download of every dependency
    "pom.xml and settings.xml do the same job" POM is project-level; settings.xml is user/machine-level configuration
    "mvn deploy pushes source to GitHub" Deploy uploads the built artifact to a Maven repository, not source to GitHub

    18. Common Trap Questions

    Trap 1 - "Maven only works with Spring." Verdict: False. Maven is independent of Spring and works with plain Core Java, Spring, Spring Boot, and Hibernate projects.

    Trap 2 - "A JAR is just a renamed ZIP with class files." Verdict: Half-true and misleading. It is ZIP-like and can hold .class files, but also packages, images, properties, metadata, and config files, and it carries Java-specific meaning.

    Trap 3 - "One spring-boot-starter-web means one JAR." Verdict: False. A starter usually brings a group of related dependencies needed for that feature.

    Trap 4 - "mvn package runs only the package phase." Verdict: False. Running a phase runs all earlier phases: validate, compile, test, then package.

    Trap 5 - "The first Maven build being slow means something is wrong." Verdict: False. The first build downloads dependencies into the local .m2 repository; later builds use that cache and are faster.

    Trap 6 - "Deleting .m2/repository is harmless." Verdict: Misleading. It can fix corrupted or partial downloads, but deleting the whole repository forces Maven to re-download every dependency.

    Trap 7 - "pom.xml and settings.xml are interchangeable." Verdict: False. pom.xml is project-level configuration; settings.xml (~/.m2/settings.xml) is user/machine-level configuration for credentials, proxies, and mirrors.

    19. Points to Remember

    1. .java is source, .class is bytecode; javac compiles and the JVM runs.
    2. Real projects have many classes, so loose .class files are hard to share and easy to break.
    3. A JAR (Java Archive) is a ZIP-like standard bundle of compiled code and resources.
    4. Library JAR = code for other developers; application JAR = runnable program with an entry point.
    5. A normal library JAR usually hides no dependencies; a Spring Boot executable/fat JAR bundles them to run as one file.
    6. The classpath tells Java where to search: project classes, external JARs, and other configured locations.
    7. Maven is a framework-independent project management and build automation tool; pom.xml is its heart.
    8. Coordinates are groupId + artifactId + version (GAV); 1.0.0-SNAPSHOT means under development.
    9. Dependencies come from repositories: local (~/.m2/repository), Maven Central, and remote/private repos; settings.xml is user-level.
    10. The phase rule: running a phase runs all earlier phases; mvn clean install cleans, builds, tests, packages, and installs.

    20. Likely Interview Questions

    Question Crisp Answer
    What is Maven? A project management and build automation tool that standardizes structure, dependencies, builds, and packaging for Java projects.
    Why do we need JAR files? To bundle compiled .class files and resources into one shareable, standard file instead of many loose files.
    Library JAR vs application JAR? A library JAR is reusable code for other projects; an application JAR is a runnable program with an entry point.
    What is a fat JAR? A Spring Boot executable JAR that can contain application code plus required dependencies so it runs as one file.
    What is the classpath? The search path where Java looks for classes: project classes, external JARs, and configured locations.
    What is POM? Project Object Model - pom.xml, the file that tells Maven what the project is, its dependencies, and its build.
    What are Maven coordinates? groupId + artifactId + version, used to uniquely identify a project or dependency.
    What does SNAPSHOT mean? The version is under development and is not a final stable release.
    Dependency vs plugin? A dependency is used by application code; a plugin is a tool Maven uses during the build.
    What are transitive dependencies? Dependencies of your dependencies; Maven downloads them automatically.
    Local vs Maven Central vs remote repository? Local is your machine cache (~/.m2/repository), Central is public, remote is any other (often private) repository.
    What does mvn clean install do? Cleans old output, then builds the project through validate, compile, test, package, verify, install.

    • .java -> .class -> JAR turns loose bytecode into one shareable artifact.
    • Library JAR vs application JAR vs Spring Boot fat JAR depends on what the archive is for.
    • Classpath tells Java where to search; Maven assembles it from pom.xml.
    • Coordinates (GAV), packaging, properties, dependencies, and plugins all live in the POM.
    • Repositories flow from the local cache to Central and remote/private repositories.
    • The phase rule means one command triggers every earlier phase.

    One-line takeaway: Maven exists because real Java projects need a standard way to manage structure, dependencies, builds, packaging, and the sharing of artifacts - and once pom.xml and the lifecycle rule click, the whole build stops feeling like magic.
