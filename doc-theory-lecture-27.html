    Lecture 27 — Spring JDBC Complete Tutorial

    23 sections · 4,022 words

    Lecture 27

    Scope evidence: "Spring JDBC Complete Tutorial | JdbcTemplate, DataSource, HikariCP" (playlist map, verified). Repo folder for this lecture is the springJDBCDemo project: a JdbcTemplate-based repository.StudentRepository, repository.StudentRowMapper, service.StudentService, controller.StudentController, model.Student, SpringJdbcDemoApplication, and application.properties, plus the lecture notes.

    Spring JDBC keeps SQL under our control while removing the repetitive JDBC infrastructure around it. This lecture moves from raw JDBC, through the template idea and the DataSource abstraction, into pooling and HikariCP, then through create, read, update and delete with JdbcTemplate. It closes with row mapping and exception translation, so every CRUD call has a clear path from controller to database and back.

    1. The Problem with Raw JDBC

    Consider one simple requirement: insert a student into the database.

    INSERT INTO students(name, email, age)
VALUES (?, ?, ?);

    Written with raw JDBC, the repository method carries a lot of code that has nothing to do with the requirement itself.

    public boolean save(Student student) {
    String sql = "INSERT INTO students(name, email, age) VALUES (?, ?, ?)";
    try (
        Connection connection = DriverManager.getConnection(URL, USERNAME, PASSWORD);
        PreparedStatement preparedStatement = connection.prepareStatement(sql)
    ) {
        preparedStatement.setString(1, student.getName());
        preparedStatement.setString(2, student.getEmail());
        preparedStatement.setInt(3, student.getAge());
        return preparedStatement.executeUpdate() == 1;
    } catch (SQLException exception) {
        exception.printStackTrace();
        return false;
    }
}

    Only the SQL, the three parameter binds, and the execute call are database-specific work. The rest is infrastructure:

    • opening a connection;
    • creating a PreparedStatement;
    • closing the statement and the connection;
    • catching SQLException;
    • repeating the same workflow in every method.

    Insert, update, delete and select all share this shape. Spring JDBC removes the repetition without removing control over SQL.

    Important: Raw JDBC gives full control, but the boilerplate around that control repeats in every method. The repetition, not SQL, is the problem.

    2. The Template Idea Behind Spring JDBC

    Most JDBC operations follow one algorithm:

    1. Obtain a database connection.
    2. Create a statement.
    3. Bind parameter values.
    4. Execute the statement.
    5. Process the result.
    6. Handle SQL exceptions.
    7. Close JDBC resources.

    Some steps are identical every time (obtain connection, create statement, execute statement, handle exceptions, close resources); only the SQL statement and the parameter values change per query.

    2.1 Fixed Parts vs Changing Parts

    Spring separates the responsibilities:

    Developer handles Spring handles
    SQL query Connection management
    SQL parameter values Statement execution workflow
    Row-to-object mapping Resource cleanup
    Business interpretation of the result Exception translation

    This is the Template Method idea: Spring provides the fixed JDBC workflow and the developer supplies the operation-specific parts. The central class is JdbcTemplate. Spring JDBC still uses Connection, PreparedStatement, ResultSet and SQLException internally; Spring only manages their lifecycle.

    Mnemonic for the fixed workflow: "Great Coders Bind Every Parameter, Handle Cleanup" = Get connection, Create statement, Bind, Execute, Process result, Handle exceptions, Close resources.

    3. Understanding DataSource

    3.1 A Connection Provider

    Before using JdbcTemplate, we need to know where database connections come from. That is the job of DataSource, a Java interface in javax.sql. Its important method is Connection getConnection(). A DataSource is a connection provider that hands out Connection objects; it is not itself a database connection.

    Connection connection = dataSource.getConnection();

    4. DriverManager vs DataSource

    4.1 Injecting a Provider

    Raw JDBC commonly creates connections with DriverManager.getConnection(URL, USERNAME, PASSWORD), which forces the repository to know the URL, the username, the password, and how connections are created. With DataSource, a provider is injected instead, so the repository asks for a connection without knowing how it was made.

    public class StudentRepository {
    private final DataSource dataSource;
    public StudentRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }
}

    A repository should mainly care about database operations related to its domain, such as student queries; connection configuration stays outside it.

    Aspect DriverManager DataSource
    Kind Static connection-acquisition mechanism Injectable connection-provider abstraction
    Knows connection details Repository knows them Configuration stays outside the repository
    Typical use Small raw JDBC programs Managed applications
    Pooling Does not itself represent pooling Can be implemented by a connection pool

    5. Connection Pooling

    A connection pool maintains a controlled collection of database connections that can be reused. Instead of creating a new physical connection for every query, the application borrows an existing connection and returns it after use.

    5.1 Connection Creation Without a Pool

    Creating a database connection may involve several steps:

    Java app -> network established -> database server contacted
        -> credentials verified -> session created -> connection returned

    Without pooling, every operation follows this lifecycle: create connection -> execute SQL -> physically close connection. For a small console application this may be acceptable, but a web application handling many concurrent requests repeatedly pays that cost:

    Request -> Create connection -> Query -> Close   (repeated for every request)

    5.2 How a Connection Pool Works

    A pool creates and manages a limited number of database connections (for example, Connection 1 through Connection 5). When repository code calls dataSource.getConnection(), the pool returns an available connection. When the code calls connection.close(), the connection is generally not physically destroyed: the pool intercepts the call and returns the connection for reuse.

    Borrow connection -> execute operation -> call close() -> connection returned to pool

    5.3 When Every Connection Is Busy

    If the maximum pool size is three and all three are in use, a fourth request waits until another request finishes and returns its connection. If none becomes available within the configured timeout, the pool throws an exception, protecting the database from unlimited simultaneous connections.

    5.4 Why Connections Must Be Limited

    Each connection consumes memory, socket resources, session state, transaction resources, and database capacity. Letting every request open its own connection can overwhelm the database, so a pool improves performance through reuse, stability through controlled concurrency, and resource management on both sides.

    6. DataSource Does Not Always Mean Connection Pooling

    DataSource is only an interface, so implementations differ: one may create a new physical connection every call, another may return a pooled connection.

    DataSource != Connection Pool
A connection pool can implement DataSource

    6.1 Dependency Inversion in Practice

    HikariDataSource is a DataSource implementation backed by the HikariCP pool. Repository code depends on the DataSource interface, not on HikariDataSource, so the implementation can change without touching repository logic: development may use a simple provider and production a pool. This is dependency inversion in practice.

    Golden rule: Program against javax.sql.DataSource, not a concrete pool class, so neither development nor production leaks into repository code.

    7. HikariCP

    7.1 What HikariCP Manages

    HikariCP is a JDBC connection-pool implementation that Spring Boot commonly uses when it is available. It ships with starters such as spring-boot-starter-jdbc and spring-boot-starter-data-jpa. It manages maximum pool size, minimum idle connections, connection timeout, idle timeout, maximum connection lifetime, borrowing and returning connections, and connection validation. Common properties are:

    maximumPoolSize
minimumIdle
connectionTimeout
idleTimeout
maxLifetime

    8. Creating a Spring JDBC Project

    8.1 Required Dependencies

    Add the Spring JDBC starter org.springframework.boot:spring-boot-starter-jdbc and the MySQL JDBC driver com.mysql:mysql-connector-j with runtime scope. For a REST application, also include spring-boot-starter-web. The starter provides Spring JDBC infrastructure; the driver provides database-specific connectivity.

    8.2 Database Configuration

    Configure the database in application.properties:

    spring.datasource.url=jdbc:mysql://localhost:3306/student_db
spring.datasource.username=root
spring.datasource.password=your_password

    Boot reads settings from spring.datasource.* and can usually infer the JDBC driver from the URL, so spring.datasource.driver-class-name is rarely needed. Pool settings go under spring.datasource.hikari.*:

    spring.datasource.hikari.maximum-pool-size=10
spring.datasource.hikari.minimum-idle=5
spring.datasource.hikari.connection-timeout=30000
spring.datasource.hikari.idle-timeout=600000
spring.datasource.hikari.max-lifetime=1800000
    Property Purpose
    maximum-pool-size Maximum connections managed by the pool
    minimum-idle Minimum idle connections the pool tries to keep
    connection-timeout Maximum wait for a connection before failure
    idle-timeout How long an idle connection may stay before removal
    max-lifetime Maximum lifetime of a pooled connection

    A larger pool does not automatically improve performance; size it using expected concurrency, average query duration, database capacity, number of application instances, and load tests.

    9. How Spring Boot Creates the DataSource Bean

    Boot detects Spring JDBC and the driver, reads spring.datasource.*, detects an available pool, prefers HikariCP, creates and configures a DataSource, and registers it as a Spring bean. Conceptually it builds a HikariDataSource and sets its URL, username and password. This bean is usually created automatically; if the application defines its own DataSource bean, Boot backs away from its default datasource auto-configuration.

    To verify the configured implementation, inject the DataSource into a component and print its class in a @PostConstruct method. A typical output is:

    class com.zaxxer.hikari.HikariDataSource

    Interviewer's perspective: "How does your repository get a connection?" The strong answer is: "It does not create one. It receives a DataSource bean from Boot's auto-configuration, normally a HikariDataSource backed by HikariCP."

    10. Introducing JdbcTemplate

    JdbcTemplate (org.springframework.jdbc.core.JdbcTemplate) is Spring's main abstraction for JDBC operations: insert, select, update, delete, batch operations, stored procedures, and generated-key retrieval. The common methods are update(), query() and queryForObject(). It does not create connections itself; it needs a DataSource:

    JdbcTemplate -> requests a connection from -> DataSource -> provides -> Connection

    10.1 Responsibilities of JdbcTemplate

    Conceptually the bean is new JdbcTemplate(dataSource), configured automatically by Boot and injected into a @Repository; an unconfigured new JdbcTemplate() is unnecessary. Responsibilities handled for an update operation:

    1. Ask DataSource for a connection.
    2. Create a PreparedStatement.
    3. Bind parameter values.
    4. Execute the statement.
    5. Read the affected-row count.
    6. Close the statement and release the connection.
    7. Translate SQLException when necessary.

    For a select operation it additionally obtains the ResultSet, iterates the rows, calls the RowMapper for each row, collects the mapped objects, closes the ResultSet and statement, releases the connection, and translates SQL exceptions.

    Important: JdbcTemplate is stateless and thread-safe once configured, so a single injected instance is reused across the whole application.

    12. Create, Update and Delete with JdbcTemplate.update()

    update() is used for SQL statements that change database state: INSERT, UPDATE and DELETE. The save operation with positional binding:

    @Repository
public class StudentRepository {
    private final JdbcTemplate jdbcTemplate;

    public StudentRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public boolean save(Student student) {
        String sql = """
            INSERT INTO students(name, email, age)
            VALUES (?, ?, ?)
            """;
        int rowsAffected = jdbcTemplate.update(
            sql,
            student.getName(),
            student.getEmail(),
            student.getAge()
        );
        return rowsAffected == 1;
    }
}

    12.1 Binding and Affected Rows

    The values bind by position: first ? -> student.getName(), second ? -> student.getEmail(), third ? -> student.getAge(). Order must match placeholders; passing age first is wrong because the first placeholder is name. Spring uses prepared-statement execution internally when parameters are supplied.

    update() returns the affected-row count, so rowsAffected == 1 confirms the insert. Spring removes explicit connection handling, PreparedStatement creation, parameter setters, try-with-resources, manual cleanup, and repeated catch blocks, but not responsibility for correct SQL, parameter order, or interpreting the count. An update uses UPDATE students SET name = ?, email = ?, age = ? WHERE id = ? (order name, email, age, id); 1 means one row updated and 0 means none matched. A delete uses DELETE FROM students WHERE id = ?. update() serves insert, update and delete because each changes state and returns a count.

    13. Read Operations: RowMapper, query() and queryForObject()

    A write operation usually returns an affected-row count. A select returns rows and columns that must be converted into Java objects, and Spring uses RowMapper for that conversion.

    RowMapper<T> converts one ResultSet row into one Java object through T mapRow(ResultSet resultSet, int rowNumber) throws SQLException. If a query returns ten rows, Spring calls the mapper ten times; Spring handles iteration, the mapper handles one row.

    public class StudentRowMapper implements RowMapper<Student> {
    @Override
    public Student mapRow(ResultSet resultSet, int rowNumber) throws SQLException {
        Student student = new Student();
        student.setId(resultSet.getLong("id"));
        student.setName(resultSet.getString("name"));
        student.setEmail(resultSet.getString("email"));
        student.setAge(resultSet.getInt("age"));
        return student;
    }
}

// In StudentRepository:
private final RowMapper<Student> studentRowMapper = new StudentRowMapper();

public List<Student> findAll() {
    String sql = """
        SELECT id, name, email, age
        FROM students
        """;
    return jdbcTemplate.query(sql, studentRowMapper);
}

    query() suits zero, one or many rows; it returns a List<Student> and gives an empty list when nothing matches. A stateless mapper can be reused across queries, and because RowMapper is a functional interface it can also be a lambda. queryForObject() expects exactly one row; it runs a primary-key query such as SELECT id, name, email, age FROM students WHERE id = ? and returns a single mapped Student.

    13.1 queryForObject() Behaviour

    Rows returned Behaviour of queryForObject()
    Exactly one row Returns the mapped Student
    Zero rows Throws EmptyResultDataAccessException
    More than one row Throws IncorrectResultSizeDataAccessException

    For a primary-key lookup more than one row is impossible, so the common missing case is zero rows. A missing row can become Optional.empty(): catch only EmptyResultDataAccessException, not every DataAccessException, because "student does not exist" and "server unavailable" are different situations. Alternatively, query() plus stream().findFirst() avoids exception handling, at the cost of stating the one-row expectation less clearly.

    Method Use when Returns No rows Many rows
    update() INSERT, UPDATE, DELETE int affected-row count 0 n
    query() Zero, one or many rows expected List<T> empty list full list
    queryForObject() Exactly one row expected single T EmptyResultDataAccessException IncorrectResultSizeDataAccessException

    14. Custom RowMapper vs BeanPropertyRowMapper

    14.1 Choosing a Mapper

    A custom mapper calls the right getter for each column and gives explicit control. Spring's BeanPropertyRowMapper is configured by passing the target class; the query itself is unchanged. It matches columns to JavaBean properties (id -> id, name -> name, email -> email, age -> age) and maps underscore names to camel case (first_name -> firstName). The target class needs a no-argument constructor and public setters.

    Aspect Custom RowMapper BeanPropertyRowMapper
    Code volume More explicit lines Reduced mapper code
    Control Full control over conversions Less control over conversions
    Naming Column names chosen by us Depends on naming conventions
    Debugging Mapping logic is visible Mapping problems may be less obvious
    Best for Complex joins and custom logic Simple tables, prototypes, straightforward mappings
    Mechanism Direct getter/setter calls Reflection and metadata-based mapping

    A custom RowMapper is usually better when mapping logic is complex or explicit control matters.

    15. Spring JDBC Exception Translation

    Raw JDBC throws SQLException, a checked exception, so callers must catch it or declare it. It is also very broad: the same type may mean invalid SQL, a duplicate key, a constraint violation, a connection failure, an authentication failure, a deadlock, a timeout, an invalid column name, or a syntax error. Developers may inspect getSQLState(), getErrorCode() and getMessage(), and vendor error codes differ across MySQL, PostgreSQL and Oracle.

    Spring catches SQLException and translates it into its data-access hierarchy, rooted at DataAccessException:

    Database error -> JDBC driver throws SQLException -> JdbcTemplate catches it
    -> Spring examines the exception -> a suitable DataAccessException subtype is thrown

    15.1 Checked vs Unchecked

    This hierarchy is vendor-independent. SQLException is checked (extends Exception); DataAccessException is unchecked (extends NestedRuntimeException), so repository methods need not catch or declare it. Failures such as a down server, wrong credentials, a missing table or invalid SQL usually cannot be resolved in the repository and propagate to centralized handling.

    16. Common Spring Database Exceptions

    • DuplicateKeyException: a unique or primary-key constraint is violated (for example a duplicate unique email); often converted into a domain exception such as EmailAlreadyExistsException.
    • DataIntegrityViolationException: a broader integrity or constraint violation (not-null, foreign-key, check-constraint, some unique violations); DuplicateKeyException is a more specific case.
    • BadSqlGrammarException: invalid SQL, for example SELEKT id FROM students; or SELECT unknown_column FROM students;.
    • CannotGetJdbcConnectionException: failure to obtain a connection, from a down server, wrong host or port, network failure, invalid credentials, or a pool timeout.
    • EmptyResultDataAccessException: at least one result was expected but none arrived, commonly from queryForObject().
    • IncorrectResultSizeDataAccessException: the row count does not match the expected size (expected one, received three).

    17. Repository Abstraction, Portability and Execution Flow

    Translation improves portability: moving from MySQL to PostgreSQL, raw JDBC handling may depend on MySQL error codes, while Spring JDBC handles a common DuplicateKeyException. Repository abstraction means controller and service need not know whether the repository uses raw JDBC, Spring JDBC, JPA or Hibernate:

    Controller -> Service -> Repository -> Spring JDBC / JPA / another mechanism

    Persistence details stay inside the repository and can change with limited impact on higher layers.

    Area Raw JDBC Spring JDBC
    SQL control Full control Full control
    Connection handling Manual Managed through DataSource
    Statement creation Manual Managed by JdbcTemplate
    Parameter binding Manual setter calls Positional method arguments
    Result-set iteration Manual Managed by JdbcTemplate
    Row mapping Manual Provided through RowMapper
    Resource cleanup Manual Automatic
    Exception model Checked SQLException Unchecked DataAccessException hierarchy
    Connection pooling Configured separately Commonly provided through Boot and HikariCP
    Boilerplate High Significantly reduced

    Complete Execution Flow

    Insert:
StudentRepository.save(student) -> JdbcTemplate.update(sql, parameters)
    -> DataSource / HikariCP provides a pooled connection
    -> JdbcTemplate creates PreparedStatement, binds values, executes
    -> Database returns affected-row count
    -> statement closed; connection returned to pool -> count returned

Select:
StudentRepository.findAll() -> JdbcTemplate.query(sql, rowMapper)
    -> connection from DataSource -> PreparedStatement executed -> ResultSet
    -> JdbcTemplate iterates; RowMapper converts each row -> Student
    -> List collected -> ResultSet/statement closed, connection returned
    -> List<Student> is returned

    Golden rule: Spring JDBC changes who manages the plumbing, not who writes the SQL. We keep the SQL and the mapping; Spring keeps the lifecycle and the exceptions.

    18. Myth vs Reality

    Myth Reality
    "Spring JDBC replaces JDBC" It still uses JDBC internally: Connection, PreparedStatement, ResultSet, SQLException
    "Spring JDBC removes SQL" We still write SQL, parameters, mapping and result handling
    "DataSource always means a connection pool" DataSource is only an interface; a pool is one possible implementation
    "queryForObject returns null when no row exists" It throws EmptyResultDataAccessException; use query() or Optional for absent rows
    "update() is only for UPDATE statements" It also handles INSERT and DELETE, returning an affected-row count
    "A bigger pool is always faster" Every connection costs resources; pool size must be measured and tuned
    "SQLException handling disappears in Spring" It is translated into the unchecked DataAccessException hierarchy, not erased

    19. Common Trap Questions

    Trap 1 - "DataSource is a connection pool." Verdict: False. DataSource is an interface that provides connections; HikariDataSource is a pool-backed implementation of it. DataSource does not always mean pooling.

    Trap 2 - "queryForObject returns null when no row is found." Verdict: False. It throws EmptyResultDataAccessException. Catch only that exception if an absent row should become Optional.empty().

    Trap 3 - "Spring JDBC means no more SQL." Verdict: False. SQL, parameter order and row mapping remain the developer's job; only infrastructure and exception translation move to Spring.

    Trap 4 - "update() only runs UPDATE statements." Verdict: False. update() runs any state-changing statement: INSERT, UPDATE and DELETE, returning the affected-row count.

    Trap 5 - "Larger pool size always means better performance." Verdict: False. Each connection consumes memory, sockets and database capacity. Pool size depends on concurrency, query duration, database capacity and load tests.

    Trap 6 - "Spring hides and swallows database errors." Verdict: False. It translates checked SQLException into unchecked DataAccessException subtypes that still propagate to centralized error handling.

    20. Points to Remember

    1. Raw JDBC repeats connection, statement, binding, cleanup and exception code in every method.
    2. Spring JDBC keeps SQL under our control and moves infrastructure to JdbcTemplate.
    3. The template workflow is: get connection, create statement, bind, execute, process, handle, close.
    4. DataSource is a Java interface that provides Connection objects; it is not a connection.
    5. DriverManager is static and repository-aware; DataSource is an injectable connection-provider abstraction.
    6. Pooling reuses connections; close() returns a connection to the pool instead of destroying it.
    7. DataSource does not always mean pooling; HikariCP is Boot's default pool, reachable through HikariDataSource.
    8. update() handles INSERT/UPDATE/DELETE; query() returns a list; queryForObject() expects exactly one row.
    9. RowMapper maps one row to one object; BeanPropertyRowMapper reduces code but gives less explicit control.
    10. Spring translates checked SQLException into unchecked DataAccessException subtypes, improving portability.

    21. Likely Interview Questions

    Question Crisp Answer
    What problem does Spring JDBC solve? It removes repetitive JDBC infrastructure code (connections, statements, cleanup, exception handling) while keeping SQL under developer control.
    What does JdbcTemplate manage for you? Connection acquisition, statement creation, parameter binding, execution, result iteration, resource cleanup, and SQLException translation.
    What is a DataSource? A Java interface that provides Connection objects; it abstracts where and how connections come from.
    DriverManager vs DataSource? DriverManager is a static, repository-aware acquisition mechanism; DataSource is an injectable provider abstraction that a pool can implement.
    What is connection pooling and why use it? Reusing a bounded set of connections instead of opening and closing them per request, improving performance, stability and resource use.
    What is HikariCP? A JDBC connection pool, commonly used by Spring Boot and reachable through HikariDataSource.
    How does Spring Boot create the DataSource? It detects Spring JDBC and the driver, reads spring.datasource.*, prefers HikariCP, then builds and registers the DataSource bean.
    update() vs query() vs queryForObject()? update() for INSERT/UPDATE/DELETE returning an int; query() returns a List; queryForObject() expects exactly one row.
    What does queryForObject() throw for zero rows? EmptyResultDataAccessException; for too many rows, IncorrectResultSizeDataAccessException.
    What is RowMapper? An interface that converts one ResultSet row into one Java object; Spring iterates, the mapper maps.
    Custom RowMapper vs BeanPropertyRowMapper? Custom gives explicit control; BeanPropertyRowMapper maps columns to bean properties automatically but depends on naming and gives less control.
    What is exception translation? Spring converts checked SQLException into the unchecked DataAccessException hierarchy, making handling vendor-independent.
