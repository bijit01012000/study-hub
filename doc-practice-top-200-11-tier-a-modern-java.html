      100. Records — design rules and gotchas

      Asked at: Most modern Java rounds · Razorpay · Swiggy

      Difficulty: Medium · Topic: Java 17/21 modern features

      The question: "What are records in Java? When should you use them and what are the limitations?"

      The 30-second answer: Records (GA in Java 16) are immutable data carriers — record Order(String id, BigDecimal amount) {} generates the constructor, accessors (id(), not getId()), equals, hashCode, toString. Final by default. Can't extend other classes (always extends Record). Can implement interfaces and have additional methods.

      Step-by-step thought process:

      1. "Syntax: record Order(String id, BigDecimal amount, Customer customer) {}. The header declares the components."
      2. "Generated: canonical constructor, accessor per component (order.amount() — no get prefix), equals and hashCode based on ALL components, toString printing all components."
      3. "Compact constructor for validation: public Order { if (amount.signum() < 0) throw new IllegalArgumentException("negative amount"); }. No arg list, no this assignments — just validation/normalization."
      4. "Can implement interfaces, add static factories, add additional methods. Cannot extend another class (it implicitly extends java.lang.Record)."
      5. "Cannot have instance fields beyond the components. Cannot be subclassed unless you mark the record abstract — wait, records are final. Use sealed interfaces with record implementations for hierarchical data."

      Edge cases to mention:

      • Records with mutable components (List, Date) are NOT deeply immutable — copy in compact constructor and on access if true immutability matters
      • Serialization: records have a different protocol than regular classes — they serialize as a record stream, decoupled from class evolution rules
      • Pattern matching for records (Java 21) enables if (obj instanceof Order(var id, var amount, var customer)) — destructuring

      What NOT to say:

      • "Records are just classes with less boilerplate" — true at one level, but the semantic guarantees (immutability, value equality) are the bigger deal
      • "Use records for entities" — JPA's mutating nature fights records; use them for DTOs and value objects

      Common follow-up: "How does record pattern matching work in Java 21?"

      101. Sealed classes — what problem do they solve?

      Asked at: Most modern Java rounds · Razorpay · Walmart Labs

      Difficulty: Medium · Topic: Java 17/21 modern features

      The question: "What are sealed classes and what problem do they solve?"

      The 30-second answer: Sealed classes (GA in Java 17) restrict which classes can extend them — you list the permitted subtypes. This enables exhaustive pattern matching, gives the compiler complete knowledge of a hierarchy, and prevents arbitrary extension. Useful for domain models with a closed set of variants (Order can be Paid, Pending, or Cancelled — nothing else).

      Step-by-step thought process:

      1. "Syntax: sealed interface OrderStatus permits Paid, Pending, Cancelled {}. Each permitted type must be in the same module (or same package if unnamed module)."
      2. "Permitted subtypes must declare themselves: final class Paid implements OrderStatus, non-sealed class Pending implements OrderStatus, etc."
      3. "Subtype modifiers: final (can't be extended further), sealed (continues the restriction), or non-sealed (opens up — anyone can extend)."
      4. "Combined with pattern matching: switch (status) { case Paid p ->...; case Pending p ->...; case Cancelled c ->...; } — compiler verifies exhaustiveness."
      5. "Real-world example: I model PaymentResult as sealed — Success, Declined, GatewayError. Anywhere I handle results, the compiler tells me if I miss a case after adding a fourth variant."

      Edge cases to mention:

      • permits clause is optional if all permitted subtypes are in the same file — compiler infers
      • Records work great as sealed subtypes — sealed interface Shape permits Circle, Square where Circle and Square are records
      • Sealed plus pattern matching is Java's answer to algebraic data types (sum types) from FP languages

      What NOT to say:

      • "Sealed is just final" — final prevents ALL extension; sealed allows a controlled list
      • "Sealed is for performance" — primary win is type safety and exhaustiveness checking

      Common follow-up: "How does sealed combine with switch pattern matching for exhaustiveness?"

      102. Pattern matching switch (Java 21)

      Asked at: Modern Java rounds · Razorpay · Swiggy

      Difficulty: Medium-Hard · Topic: Java 17/21 modern features

      The question: "What did Java 21 add to switch with pattern matching?"

      The 30-second answer: Switch now supports type patterns — case Order o ->... matches type and binds the variable. Plus guard clauses with when — case Order o when o.amount() > 1000 ->.... Plus record deconstruction — case Order(var id, var amount, var customer) ->.... Plus null handling — case null ->.... Combined with sealed types, you get compiler-enforced exhaustiveness.

      Step-by-step thought process:

      1. "Old switch: only constants — int, String, enum. New switch: any type via type patterns. case Integer i ->...."
      2. "Type pattern binds the variable in the arm — no cast needed. Replaces if (x instanceof Order) { Order o = (Order) x;... } boilerplate."
      3. "Guards refine the match: case Order o when o.status() == PAID -> handlePaid(o);. Multiple guards can target the same type."
      4. "Record deconstruction: case Order(String id, BigDecimal amt, Customer c) ->... binds all components."
      5. "Null in switch: case null -> handleNull(); lets you handle null explicitly. Previously switch would NPE."

      Edge cases to mention:

      • For sealed types, the compiler verifies exhaustiveness — missing a permitted subtype is a compile error
      • Order of cases matters when patterns overlap — more specific patterns first
      • case null, default ->... combines null and default arms

      What NOT to say:

      • "Pattern matching is just instanceof in a switch" — also handles records, guards, exhaustiveness
      • "Available since Java 11" — type patterns in switch are GA in Java 21

      Common follow-up: "How does exhaustiveness checking work with sealed types and switch?"

      103. Text blocks — when do they help?

      Asked at: Most modern Java rounds

      Difficulty: Easy · Topic: Java 17/21 modern features

      The question: "What are text blocks and what problem do they solve?"

      The 30-second answer: Text blocks (GA in Java 15) are triple-quoted multi-line strings. They preserve formatting without escape gymnastics — embed SQL, JSON, HTML naturally. The compiler strips incidental leading whitespace based on the closing """ position, so you can indent without polluting the content.

      Step-by-step thought process:

      1. "Syntax: opening """ on a line by itself (with optional whitespace), content on subsequent lines, closing """."
      2. "Incidental whitespace removal: the compiler finds the indentation of the closing delimiter and strips that much from every line."
      3. "Concrete: String sql = """\n SELECT id, amount FROM orders\n WHERE merchant_id =?\n """; — the four leading spaces are stripped."
      4. "Escape sequences still work. \s is space (useful at line ends), \ at end of line suppresses the newline."
      5. "String interpolation is NOT in text blocks — use String.format or .formatted(). JEP 459 (templated strings) was withdrawn."

      Edge cases to mention:

      • Trailing whitespace on each line is stripped — use \s if you need a trailing space to be preserved
      • A text block is still just a String — concatenation, equality, formatting all work normally
      • Don't use for short one-liners; the syntax is heavier than worth it

      What NOT to say:

      • "Text blocks support template variables" — they don't; template strings were withdrawn
      • "Available since Java 13" — preview in 13 and 14, GA in Java 15

      Common follow-up: "How would you build a multi-line SQL query with parameters using text blocks?"

      104. Virtual threads — the basics

      Asked at: Modern Java rounds · Razorpay · Swiggy · Cred

      Difficulty: Medium-Hard · Topic: Java 17/21 modern features

      The question: "What are virtual threads and when do they help?"

      The 30-second answer: Virtual threads (GA in Java 21, JEP 444) are lightweight threads scheduled by the JVM, not the OS. Millions can run on a few platform threads. Designed for I/O-heavy concurrency — each request gets a dedicated thread that blocks on I/O cheaply. Don't help CPU-bound work. Don't pin to platform threads under synchronized in Java 24+ (JEP 491).

      Step-by-step thought process:

      1. "Platform thread = OS thread, ~1MB stack, expensive to spawn. Virtual thread = ~few KB, scheduled on a small pool of carrier (platform) threads."
      2. "Create: Thread.startVirtualThread(runnable); or Executors.newVirtualThreadPerTaskExecutor(). Spring Boot 3.2+ enables them with one property."
      3. "When a virtual thread blocks on I/O (network, file, sleep), it unmounts from its carrier — the carrier picks up another virtual thread. Net effect: 'one thread per request' scales to millions."
      4. "CPUbound work doesn't benefit — only one carrier runs at a time. Use ForkJoinPool or platform thread pools for parallel computation."
      5. "Pre-Java 24, synchronized blocks pinned a virtual thread to its carrier — couldn't unmount during I/O. Java 24 JEP 491 fixed this; synchronized no longer pins."

      Edge cases to mention:

      • Virtual threads are NOT pooled in the traditional sense — create one per task, throw it away. ThreadLocal lifecycle changes accordingly
      • Don't make virtual threads daemon by default in production — explicit shutdown matters
      • Profiling tools, thread dumps work with virtual threads, but old monitoring may show overwhelming thread counts — adjust dashboards

      What NOT to say:

      • "Virtual threads make everything faster" — true for I/O-heavy, irrelevant for CPUbound
      • "They replace ExecutorService" — they complement it; newVirtualThreadPerTaskExecutor() IS an ExecutorService

      Common follow-up: "What does it mean for a virtual thread to be pinned to its carrier?"

      105. ZGC and the move to default-generational

      Asked at: Senior backend rounds · Goldman · Walmart Labs

      Difficulty: Hard · Topic: Java 17/21 modern features / JVM

      The question: "What's ZGC and why did generational ZGC become the default?"

      The 30-second answer: ZGC is a concurrent low-latency garbage collector — sub-millisecond pauses on heaps from MBs to TBs. Original ZGC treated the whole heap uniformly. Generational ZGC (JEP 439, default in Java 23 via JEP 474) splits into young and old generations, exploiting the weak generational hypothesis — most objects die young — for much better throughput at the same pause goals.

      Step-by-step thought process:

      1. "ZGC is concurrent — marking and relocation happen alongside application threads. Pauses are ~sub-millisecond regardless of heap size."
      2. "Generational ZGC adds the young/old split. Young gen collects frequently and cheaply because most short-lived objects die there. Old gen collects rarely."
      3. "For a service with 1000 reqs/sec creating short-lived objects per request, generational ZGC drops both pause times and CPU spent on GC."
      4. "Enable: -XX:+UseZGC (and -XX:+ZGenerational pre-Java 23 if you want generational explicitly). Java 23+: it's the default mode for ZGC."
      5. "Pick ZGC when: latency-sensitive (real-time bidding, trading, low p99 APIs), large heaps (>4GB), can afford ~10-15% throughput hit vs Parallel GC."

      Edge cases to mention:

      • ZGC and Shenandoah compete in the same niche — both concurrent, both low-pause. Shenandoah is RedHat-led, ZGC is Oracle-led
      • Monitoring: GC pauses are tiny but GC CPU usage may be high — check both
      • For heaps under ~4GB, G1 may be a better fit — overhead of ZGC isn't justified

      What NOT to say:

      • "ZGC has zero pauses" — sub-millisecond, not zero
      • "Always use ZGC" — depends on your latency vs throughput trade-off

      Common follow-up: "What's the trade-off between ZGC and G1 for a typical microservice?"

      106. ScopedValue vs ThreadLocal (Java 21+)

      Asked at: Senior modern Java rounds · Razorpay · Cred

      Difficulty: Hard · Topic: Java 17/21 modern features / Concurrency

      The question: "What is ScopedValue and why is it preferred over ThreadLocal for virtual threads?"

      The 30-second answer: ScopedValue (preview in Java 20, evolving) is an immutable, scoped alternative to ThreadLocal. Set via ScopedValue.where(KEY, value).run(() ->...) — value is visible only inside the lambda. No set() / remove() issues, no lingering state in pooled threads. Designed for the virtual-thread era where ThreadLocal-per-thread doesn't scale to millions of threads.

      Step-by-step thought process:

      1. "Declare: public static final ScopedValue<RequestContext> CONTEXT = ScopedValue.newInstance();."
      2. "Bind and run: ScopedValue.where(CONTEXT, ctx).run(() -> handleRequest());. Value is set for the duration of run."
      3. "Read inside: RequestContext c = CONTEXT.get();. Throws if not bound."
      4. "Immutable — no set() to change mid-scope. To rebind, nest another where(...).run(...). This makes reasoning easier."
      5. "Virtual thread context: millions of virtual threads each carrying ThreadLocal state would be huge memory pressure. ScopedValue shares structures more efficiently and avoids lifecycle bugs."

      Edge cases to mention:

      • Still a preview API as of Java 21 — syntax may evolve in future versions Works with structured concurrency: a parent's scoped values are inherited by child tasks
      • ThreadLocal still works for legacy code; ScopedValue is the recommended direction for new code

      What NOT to say:

      • "ScopedValue replaces ThreadLocal everywhere today" — it's preview; mature only in Java 24+
      • "ScopedValue is mutable" — explicitly immutable, that's the point

      Common follow-up: "How does ScopedValue interact with structured concurrency?"
