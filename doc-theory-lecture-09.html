    Lecture 09 — Spring Boot Core

    24 sections · 3,852 words

    Lecture 09

    Scope evidence: "Spring Boot Core | @SpringBootApplication, Auto Configurations" (playlist map, verified). Repo folder is a Maven project (SpringCoreDemo) containing the classes in.strikes.AppConfig, in.strikes.Main, in.strikes.OrderService, in.strikes.PaymentService, in.strikes.UserService, plus this lecture's notes.

    Spring Core taught us how the IoC container manages objects, but it made us start that container by hand every time. This lecture shows the repetitive startup work Spring Boot removes, then opens the box on the one annotation that does most of the magic: @SpringBootApplication. We walk from a manual Maven setup to a running Boot application, then dissect @SpringBootConfiguration, @ComponentScan, and @EnableAutoConfiguration. By the end, "Boot is magic" becomes "Boot is Spring Core plus a smart, condition-based startup system."

    1. Why Spring Boot After Spring Core?

    Till now we learned how Spring Core manages objects using the IoC container. In a pure Spring Core project we start the container manually, provide a configuration class, fetch a bean, and call a method:

    @Configuration
@ComponentScan(basePackages = "in.strikes")
public class AppConfig {
}

ApplicationContext context =
        new AnnotationConfigApplicationContext(AppConfig.class);

OrderService orderService = context.getBean(OrderService.class);
orderService.placeOrder();

    This shows how Spring works internally, but in real applications the setup becomes repetitive. Every Spring application needs the same common startup work:

    Start application
Create Spring container
Read configuration
Scan components
Create beans
Load properties
Prepare application context
Inject dependencies

    Spring Boot solves this repetitive startup problem. It uses Spring Core and gives us a simpler way to start, configure, and run the Spring container.

    Golden rule: Spring Boot does not replace Spring Core. Spring Boot uses Spring Core internally and only adds a standard, convenient startup and configuration layer on top.

    A common beginner misunderstanding is Spring Boot = Web API. That is not correct. Spring Boot can be used for console applications, web applications, database applications, batch applications, and microservices. Boot itself is not only about web development; web behavior comes later when we add web-related dependencies.

    Important: Spring Core gives us IoC and dependency injection. Spring Boot gives us a standard way to start and configure the application.

    2. Setting Up a Spring Boot Project

    There are two common ways to create a Spring Boot project:

    1. Create a Maven project manually and add Spring Boot dependencies.
    2. Use Spring Initializr to generate a ready-made project structure.

    In real projects, Spring Initializr is usually preferred because it creates the correct project structure, parent configuration, dependencies, and plugin setup. The manual route teaches what those pieces are, but leaves every one of them for us to wire correctly.

    Approach What we do Trade-off
    Manual Maven project Create pom.xml, add parent + dependencies + plugin by hand Full understanding, more error-prone
    Spring Initializr Generate structure, parent, dependencies, plugin Fast and correct, hides wiring details

    Interviewer's perspective: Knowing both routes is the point. Initializr is the professional default; the manual route proves you know what Initializr actually produced.

    3. The Parent POM and the Starter Concept

    In Spring Boot projects we commonly use a special parent in pom.xml:

    <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.x.x</version>
    <relativePath/>
</parent>

    The parent helps Maven by providing common Spring Boot project configuration. It manages dependency versions, plugin versions, Java version configuration, build defaults, and encoding settings. The main benefit is version compatibility: if we later add dependencies like Spring JDBC, Hibernate, Validation, Jackson, or Spring Web, we do not have to manually decide every version. Maven can ask the Spring Boot parent "which version of this dependency should I use?" and the parent provides compatible versions, which reduces version mismatch problems.

    A starter, meanwhile, is a dependency shortcut. Instead of adding many related dependencies one by one, we add one starter and Maven brings the required dependencies transitively:

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter</artifactId>
</dependency>

    spring-boot-starter is the basic starter for a non-web Spring Boot application. It gives us the basic Spring Boot setup, logging, and core Spring Boot infrastructure.

    Important: A starter does not mean one single library. A starter means a collection of commonly needed dependencies bundled behind one artifact name.

    Mnemonic: Parent sets the versions, starter sets the dependencies. The parent answers "which version," the starter answers "which libraries."

    4. Spring Core Startup vs Spring Boot Startup

    In Spring Core we manually did four things end to end:

    1. Create ApplicationContext manually.
    2. Provide the configuration class manually.
    3. Fetch the bean manually.
    4. Trigger application logic manually.

    In Spring Boot we get a standard startup mechanism: SpringApplication.run(MyApplication.class, args). This single line starts and prepares the Spring application context for us. Compare the two side by side:

    Concern Spring Core Spring Boot
    Container creation new AnnotationConfigApplicationContext(AppConfig.class) SpringApplication.run(...)
    Configuration class Written manually with @Configuration Supplied by @SpringBootApplication
    Component scanning Declared manually via @ComponentScan Included in @SpringBootApplication
    Bean retrieval context.getBean(OrderService.class) Beans are injected where needed
    Triggering logic Manual call after getBean CommandLineRunner runs after startup
    Auto-configuration Not present @EnableAutoConfiguration applies defaults

    The developer no longer babysits the container lifecycle; SpringApplication.run() does it.

    5. The Same Application in Spring Boot

    A basic Spring Boot application starts like this:

    package in.strikes;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class SpringBootCoreDemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(SpringBootCoreDemoApplication.class, args);
    }
}

    Here we did not manually write new AnnotationConfigApplicationContext(...), @Configuration, @ComponentScan, or context.getBean(...). The reason is that @SpringBootApplication already combines the common setup required for a Spring Boot application.

    6. Adding Components and Running Startup Logic

    We can create normal Spring components just like in Spring Core. A PaymentService marked @Component is created by Spring, and an OrderService that declares a constructor dependency receives PaymentService through constructor injection. This is still Spring Core behavior: Spring sees @Component and creates beans, and it sees the constructor dependency and injects it. Boot does not change dependency injection; it just starts the container more conveniently.

    In Spring Core we manually fetched the bean and called the method. In Spring Boot we usually do not fetch beans manually from the context. To run code after application startup, we use CommandLineRunner:

    package in.strikes.runner;

import in.strikes.service.OrderService;
import org.springframework.boot.CommandLineRunner;
import org.springframework.stereotype.Component;

@Component
public class AppRunner implements CommandLineRunner {
    private final OrderService orderService;

    public AppRunner(OrderService orderService) {
        this.orderService = orderService;
    }

    @Override
    public void run(String... args) {
        orderService.placeOrder();
    }
}

    CommandLineRunner is a Spring Boot interface. Its run() method executes after the Spring application context is created and ready. This is useful for console-based Spring Boot applications, testing startup logic, or running some code immediately after the application starts.

    7. Understanding SpringApplication.run()

    The most important line in a Spring Boot application is SpringApplication.run(SpringBootCoreDemoApplication.class, args). This line:

    • Starts the Spring Boot application.
    • Creates the application context.
    • Reads configuration and properties.
    • Performs component scanning.
    • Creates beans.
    • Applies auto-configuration.
    • Injects dependencies.
    • Runs startup hooks like CommandLineRunner.run().

    It also returns the application context as a ConfigurableApplicationContext. Technically we can still fetch beans manually with context.getBean(OrderService.class), but in real Spring Boot applications that is not the usual approach. The preferred approach is to let Spring inject dependencies wherever they are needed.

    Interviewer's perspective: "What does SpringApplication.run() return?" It returns a ConfigurableApplicationContext. Knowing that the return value is a live context, not void, is a small detail that signals real familiarity.

    8. Understanding @SpringBootApplication

    @SpringBootApplication is not a small annotation. It is a combination annotation. It roughly combines @SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan. So a class annotated with @SpringBootApplication is conceptually similar to writing all three annotations explicitly on the same class.

    Annotation Purpose
    @SpringBootConfiguration Marks the main configuration class of the Spring Boot application
    @EnableAutoConfiguration Enables Spring Boot's automatic configuration mechanism
    @ComponentScan Scans the current package and subpackages for Spring components

    We already studied @Configuration and @ComponentScan in Spring Core. The major new concept here is @EnableAutoConfiguration.

    Mnemonic: C-A-S - Configure (@SpringBootConfiguration), Auto-configure (@EnableAutoConfiguration), Scan (@ComponentScan).

    9. @SpringBootConfiguration

    @SpringBootConfiguration is Spring Boot's version of a configuration marker. In Spring Core we used a class annotated @Configuration containing @Bean methods, and that told Spring: this class contains bean definitions.

    In Spring Boot, the main class indirectly gets @SpringBootConfiguration because of @SpringBootApplication. That means the main class can also define beans through @Bean methods, because it is treated as a configuration class too. In real projects we usually keep the main class clean and create separate configuration classes when needed.

    Marker Meaning
    @Configuration Regular Spring configuration class
    @SpringBootConfiguration Main Spring Boot application configuration marker

    @SpringBootConfiguration also helps Spring Boot tests locate the main application configuration automatically.

    10. @ComponentScan in Spring Boot

    In Spring Core we manually wrote @ComponentScan(basePackages = "in.strikes") on our configuration class. This told Spring: go inside the in.strikes package and find classes marked with @Component, @Service, @Repository, or @Controller.

    In Spring Boot we usually do not write @ComponentScan manually because it is already included inside @SpringBootApplication. By default, Spring Boot scans the package where the main application class is present and all its subpackages.

    in.strikes
|-- SpringBootCoreDemoApplication.java
|-- service
|   |-- PaymentService.java
|   `-- OrderService.java
`-- runner
    `-- AppRunner.java

    Here the main class is inside in.strikes, so Spring Boot scans in.strikes and all packages under it. This is why Spring Boot applications usually keep the main application class in the root package.

    Correct structure:                 Less ideal structure:
in.strikes                         in.strikes.app
|-- SpringBootCoreDemoApplication  `-- SpringBootCoreDemoApplication.java
|-- controller                     in.strikes.service
|-- service                        `-- PaymentService.java
|-- repository
`-- config

    In the less ideal structure, PaymentService may not be scanned automatically because it is outside the main class package hierarchy.

    11. Changing the Component Scan Base

    Yes, we can manually change component scanning. If required, we provide base packages as @SpringBootApplication(scanBasePackages = "in.strikes"). This tells Spring Boot to scan from in.strikes even if the main class is placed somewhere else. However, the better practice is to place the main class in the root package and let Spring Boot scan naturally.

    Important: The default scan root is the package of the main class. Moving the main class up or down silently changes which components Boot finds.

    12. @EnableAutoConfiguration

    @EnableAutoConfiguration tells Spring Boot: look at my project setup and automatically configure useful things for me. Spring Boot checks:

    • Which dependencies are present.
    • Which classes are available on the classpath.
    • Which beans already exist.
    • Which properties are configured.

    Then it creates useful default beans only when needed. For example, Boot may check: Is a web dependency present? Is a database dependency present? Is Spring Security present? Has the developer already created a custom bean?

    Based on these checks, Spring Boot applies its pre-written configuration classes. Examples of common auto-configuration classes are DataSourceAutoConfiguration, WebMvcAutoConfiguration, JacksonAutoConfiguration, and TaskExecutionAutoConfiguration.

    Simple meaning: @EnableAutoConfiguration = apply Spring Boot's ready-made configurations when conditions match.

    13. How Auto-Configuration Works Internally

    When the application starts, SpringApplication.run(...) runs. Spring Boot sees @SpringBootApplication, and inside it auto-configuration is enabled via @EnableAutoConfiguration. Then Spring Boot considers auto-configuration classes. Conceptually, an auto-configuration class looks like this:

    @AutoConfiguration
@ConditionalOnClass(SomeLibrary.class)
public class SomeLibraryAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    public SomeService someService() {
        return new DefaultSomeService();
    }
}

    These classes are not blindly applied. They are applied only when their conditions match. Meaning:

    If SomeLibrary is present in the project
AND the developer has not already created a SomeService bean
THEN create a default SomeService bean.

    This is the core idea of Spring Boot auto-configuration.

    14. Manual Configuration vs Auto-Configuration

    In Spring Core the developer writes the configuration manually in something like an AppConfig class with @Bean methods. Here the developer directly tells Spring: create this bean.

    In Spring Boot, many configuration classes are already written for us. They are provided by Spring Boot or sometimes by third-party starters. Spring Boot applies them only when the right conditions are satisfied.

    Aspect Manual Configuration Auto-Configuration
    Who writes it Developer Spring Boot or third-party starters
    When applied Always, as written Only when conditions match
    Trigger Explicit @Bean / @Configuration Classpath, existing beans, properties
    Control Total Default, overridable by our beans
    Typical source Our AppConfig XxxAutoConfiguration classes

    So auto-configuration does not mean random configuration. It means: pre-written configuration plus condition-based activation.

    15. Classpath-Based Decision Making and the Web Dependency

    Classpath means the set of classes and libraries available to the application at runtime. In Maven terms:

    Dependency added in pom.xml
        |
        v
Maven downloads JARs -> they become available on the classpath
        |
        v
Spring Boot checks the available classes -> auto-configuration decisions

    When we add a dependency, we indirectly give Spring Boot a signal. spring-boot-starter tells Spring Boot: this is a basic Spring Boot application. But if we do not add spring-boot-starter-web, then Spring Boot does not treat the application as a web application. It checks:

    Do I see web server classes? No.
Do I see Spring MVC web classes? No.
Should I start Tomcat? No.

    So the application starts like a normal console application. You will not see Tomcat started on port 8080, precisely because no web-related classes are present on the classpath.

    Later, when we add spring-boot-starter-web, Maven brings web-related libraries. Then Boot sees that web classes are present, embedded server support is present, and Spring MVC infrastructure is present. Now Spring Boot understands: this looks like a web application. So it configures web-related beans and starts an embedded server such as Tomcat. That is why a Boot web application keeps running and listens for HTTP requests.

    Important: Adding a dependency is a configuration command. It changes the classpath, and the classpath changes what Spring Boot decides to configure.

    16. The Three Main Checks in Auto-Configuration

    Spring Boot commonly checks three things:

    1. Is the required class present?
    2. Is the required bean missing?
    3. Is the required property enabled?

    Conceptual example:

    @AutoConfiguration
@ConditionalOnClass(PaymentGateway.class)
public class PaymentAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    public PaymentGateway paymentGateway() {
        return new DefaultPaymentGateway();
    }
}

    Meaning:

    If PaymentGateway class exists
AND the developer has not created a PaymentGateway bean
THEN create a default PaymentGateway bean.

    This is why Spring Boot feels automatic but still remains controlled.

    Check Annotation Question asked
    Class present @ConditionalOnClass Is a specific class or library available in the project?
    Bean missing @ConditionalOnMissingBean Has the developer not already created this bean?
    Property enabled property condition Is the required property enabled in configuration?

    @ConditionalOnClass is a condition that matches only when a particular class is present on the classpath: apply this configuration only if a specific class or library is available. This is how Spring Boot detects what kind of application we are building.

    @ConditionalOnMissingBean is a condition that matches only when a required bean is not already present in the Spring container: create this bean only if the developer has not already created one. This is very important because Spring Boot does not want to override our custom configuration unnecessarily.

    Mnemonic: the three checks are C-M-P - Class, Missing bean, Property.

    17. Our Beans vs Auto-Configured Beans and the Startup Flow

    In a Spring Boot application, beans can come from two main sources.

    1. Beans created from our code. These are developer-defined beans, discovered through component scanning or explicit configuration, using @Component or a @Bean method inside a @Configuration class.

    2. Beans created by Spring Boot auto-configuration. These come from Spring Boot's pre-written configuration classes, provided by Spring Boot or by a third-party starter. They are not classes we write in our application.

    Source How defined Who wins on conflict
    Our beans @Component, @Service, @Bean Ours - Boot backs off
    Auto-configured beans XxxAutoConfiguration with conditions Only if we did not define one

    A simplified Spring Boot startup flow looks like this:

    Application starts
        |
        v
SpringApplication.run() is called
        |
        v
Application context is created
        |
        v
User configuration is processed
        |
        v
Component scanning finds our classes
        |
        v
User-defined beans are registered
        |
        v
Auto-configuration classes are considered
        |
        v
Conditions are checked
        |
        v
Missing default beans are created
        |
        v
Dependencies are injected
        |
        v
Application context becomes ready
        |
        v
CommandLineRunner / ApplicationRunner runs, if present

    18. @ComponentScan vs @EnableAutoConfiguration

    These two annotations solve different problems.

    Annotation What it does
    @ComponentScan Finds our application classes marked with @Component, @Service, @Repository, @Controller, etc.
    @EnableAutoConfiguration Applies Spring Boot's ready-made configurations based on classpath, beans, and properties.

    Simple comparison:

    @ComponentScan finds our code.
@EnableAutoConfiguration applies Boot's default setup.
Both are included inside @SpringBootApplication.

    Interviewer's perspective: The classic question is "what does @SpringBootApplication contain?" The strong answer names all three and explains that scanning finds your beans while auto-configuration supplies the ones you did not write.

    19. Myth vs Reality

    Myth Reality
    "Spring Boot = Web API" Boot also builds console, database, batch, and microservice apps; web behavior only appears with web dependencies
    "Spring Boot replaces Spring Core" Boot uses Spring Core internally; it only adds a standard startup and configuration layer
    "A starter is one library" A starter is a collection of commonly needed dependencies pulled transitively
    "Auto-configuration runs blindly" It applies pre-written configuration only when conditions match
    "Boot overrides my beans" @ConditionalOnMissingBean makes Boot back off when we define our own
    "You must call getBean in Boot" Inject dependencies instead; Boot prepares the context for you
    "A basic starter starts Tomcat" Only a web starter brings web classes, so only then does an embedded server start
    "@Configuration and @SpringBootConfiguration are identical" @SpringBootConfiguration is Boot's main-app marker and helps tests locate the app

    20. Common Trap Questions

    Trap 1 - "Spring Boot is a web framework." Verdict: False. Boot is a startup and auto-configuration layer. It is not web-only; adding spring-boot-starter-web is what turns it into a web app.

    Trap 2 - "A starter equals a single dependency." Verdict: False. A starter is a shortcut for a curated set of dependencies that Maven resolves transitively.

    Trap 3 - "Auto-configuration means Spring configures everything always." Verdict: False. It means pre-written configuration plus condition-based activation; if conditions fail, nothing is applied.

    Trap 4 - "Spring Boot ignores my custom bean and uses its default." Verdict: False. @ConditionalOnMissingBean ensures our bean wins; Boot only creates the default when we have not defined one.

    Trap 5 - "The main class does nothing but call run()." Verdict: Misleading. The main class is also a configuration class via @SpringBootConfiguration; it can define @Beans itself.

    Trap 6 - "Moving the main class does not matter." Verdict: False. Default scanning covers the main class package and below; moving it can put components out of scan range.

    Trap 7 - "Auto-configuration needs my @Bean for every class on the classpath." Verdict: False. Conditions decide whether a configuration is considered; default beans are created only when missing and only when the class is present.

    21. Points to Remember

    1. Spring Boot does not replace Spring Core; it uses Spring Core and adds standard startup plus configuration.
    2. SpringApplication.run(...) starts the app, creates the context, scans, auto-configures, injects, and runs startup hooks.
    3. @SpringBootApplication combines @SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan (CAS).
    4. @SpringBootConfiguration is Boot's main-application configuration marker and helps tests find the app.
    5. @ComponentScan finds our classes; by default it scans the main class package and all subpackages.
    6. @EnableAutoConfiguration applies Boot's ready-made configurations from classpath, beans, and properties.
    7. Auto-configuration works through conditions: class present, bean missing, property enabled (CMP).
    8. @ConditionalOnMissingBean is why our own beans take preference over Boot's defaults.
    9. Adding a dependency changes the classpath, and the classpath drives what Boot configures; a web starter starts an embedded server.
    10. spring-boot-starter-parent supplies compatible dependency and plugin versions, reducing version mismatches.

    22. Likely Interview Questions

    Question Crisp Answer
    What does Spring Boot add over Spring Core? A standard way to start and configure the application: SpringApplication.run, starters, auto-configuration, sensible defaults.
    What does SpringApplication.run() do? Starts the app, creates the context, reads config, scans components, creates beans, applies auto-configuration, injects dependencies, runs startup hooks.
    What does @SpringBootApplication contain? @SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan.
    Difference between @Configuration and @SpringBootConfiguration? @Configuration marks any config class; @SpringBootConfiguration marks the main Boot app config and helps tests locate it.
    What is @ComponentScan in Boot? It discovers our @Component/@Service/@Repository/@Controller classes, defaulting to the main class package and below.
    What does @EnableAutoConfiguration do? Applies Spring Boot's pre-written configurations when classpath, bean, and property conditions match.
    What is a starter? A dependency shortcut bundling a set of commonly needed dependencies that Maven resolves transitively.
    Why use spring-boot-starter-parent? It manages compatible dependency and plugin versions, Java version, build defaults, and encoding.
    When is an auto-configuration applied? Only when its conditions match: required class present, required bean missing, required property enabled.
    What does @ConditionalOnMissingBean mean? Create this bean only if the developer has not already defined one.
    Why does a basic starter not start Tomcat? No web server or MVC classes are on the classpath, so web auto-configuration conditions fail.
    What happens when you add spring-boot-starter-web? Web classes appear, so Boot configures web beans and starts an embedded server such as Tomcat.

    23. Final Summary

    Spring Core: manual container + config + getBean + trigger
        |
        v
Spring Boot: SpringApplication.run() starts and prepares the context
        |
        v
@SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
        |
        v
@ComponentScan finds OUR beans (main package and below)
        |
        v
@EnableAutoConfiguration applies BOOT's ready-made configuration classes
        |
        v
Conditions decide: class present? bean missing? property enabled?
        |
        v
Classpath (dependencies) drives the decisions; web starter starts Tomcat
        |
        v
Context ready, dependencies injected, CommandLineRunner runs
    • Spring Boot = Spring Core + smart startup and configuration, not a replacement.
    • @SpringBootApplication = CAS: Configure, Auto-configure, Scan.
    • @ComponentScan finds our code; @EnableAutoConfiguration supplies Boot's setup.
    • Auto-configuration = pre-written configuration plus condition-based activation (CMP).
    • @ConditionalOnMissingBean lets our beans win; dependencies change the classpath and the classpath changes the configuration.

    One-line takeaway: Spring Boot is not magic; it is Spring Core plus a smart startup and configuration system that uses dependencies, properties, and conditions to prepare the application automatically.
