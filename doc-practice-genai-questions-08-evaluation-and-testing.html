      Evaluation and testing

      0 sections · 5,963 words

      Module 08 · 13 questions · 1 practical drill

      Measure a system that answers differently every time.

      Q8.1 — You changed a prompt, model or retrieval step. How do you actually know it made things better?

      Weak answer: "I ran the new prompt on a few tricky examples, read the outputs, and they looked better, so we shipped it."

      Why it fails: - No fixed comparison set and no baseline score recorded, so "better" has nothing to be checked against next time. - One person's read of a handful of outputs is not a score, and it never checks whether passing cases still pass.

      Instant rejection: - Only ever looks at one blended average, never at which specific cases flipped from pass to fail. - Ships once a number looks favourable, with no threshold agreed before the change was made.

      Model answer: 1. Before any change I run the current version against a fixed, versioned set pulled from real traffic, around 80 cases, and record pass rate plus every per case result, not just the average. 2. I run the new version through the identical set and do a paired comparison: which cases flipped from fail to pass, and which flipped the other way round. 3. Last time the baseline was 71% and the new prompt hit 79%, but two refund policy cases regressed, so I read those transcripts before shipping. 4. A net gain that quietly breaks one whole category is not a clean win, so I check segments, not only the topline number. 5. I only ship once the gain clears a threshold agreed beforehand, and I record which version of the set produced which score.

      Follow-ups: 1. TECHNICAL — What stops your comparison set from being a different handful of examples each time you check? · Whether a fixed, versioned set exists at all, not a fresh sample every run. 2. FAILURE — Your eval score rises but users start complaining. What does that tell you about the eval? · Recognising a gap between an offline proxy and the real online outcome. 3. TRADEOFF — The average score rises but one category clearly got worse. Do you still ship? · Whether one aggregate number is enough, or segment results matter before shipping. 4. MEASUREMENT — How many examples were in that comparison, and how do you know it wasn't just noise? · Basic sense of sample size against the size of a real effect, nothing more.

      Tip: If you have compared a change against a fixed regression suite or benchmark before merging, that is the same discipline this question wants. Do not claim you have run a paired before and after eval. Say you would fix the comparison set and record a baseline before touching anything.

      Numbers worth quoting: - Fixed set, not a fresh sample - Compare paired, not average only - Agree ship threshold in advance - Check segments, not just topline

      Q8.2 — How do you build a golden set for this feature, and keep it useful over time?

      Weak answer: "Early on we wrote twenty examples of good questions and expected answers, and ran the model against those on every change."

      Why it fails: - Examples written by the builder encode their own assumptions, not what users actually ask, with no new cases added later. - No rubric behind "expected answer", and the set was never revisited as real usage patterns shifted after launch.

      Instant rejection: - The set has never grown since launch, and nobody can say which version produced last quarter's number. - One person wrote every example, with no domain reviewer and no version history at all.

      Model answer: 1. I pull the first 40 to 50 cases from real transcripts and tickets, stratified across common intents plus the hard ones, like ambiguous multi part questions. 2. A domain owner and I label each case against a short written rubric, and where we disagree we fix the rubric, not just pick a winner. 3. The set lives under version control next to the code, so a score from three months ago stays reproducible against the set that made it. 4. Each week I fold genuinely new failures and escalations in, and each quarter I retire cases that no longer match real usage. 5. I keep a held out slice nobody prompts against directly, because tuning until every case passes optimises for the test, not the product.

      Follow-ups: 1. TECHNICAL — Where do new cases come from after launch? · Mining real traffic, failures and escalations into the set, not imagining more examples. 2. FAILURE — Six months in, the set stops flagging regressions users clearly hit. What happened? · Golden set decay, the set no longer reflects current traffic or usage. 3. TRADEOFF — Would you rather have 300 loosely reviewed examples or 60 carefully labelled ones? · Coverage against label quality, and which a small team can actually sustain. 4. MEASUREMENT — How many labelled examples before a pass rate difference is trustworthy, not noise? · A concrete minimum sample size, and why small sets give unreliable swings.

      Tip: If you have built a test fixture or regression suite from real bug reports rather than invented cases, that is the same instinct. Do not claim you have run a golden set. Say you would source cases from real usage and revisit them on a schedule, not write them once.

      Numbers worth quoting: - 40 to 50 cases to start - Version the set with the code - Retire stale cases quarterly - Hold out a slice from tuning

      Q8.3 — Tell me about using an LLM to judge your own model's outputs. Where does that go wrong?

      Weak answer: "We used a frontier model as a judge to score answers from 1 to 5 on overall quality, and tracked the average across releases."

      Why it fails: - A 1 to 5 scale is not reproducible, nobody can say what separates a 3 from a 4, and the boundary moves run to run. - No awareness of known judge biases, so the score may reward longer or first listed answers rather than better ones.

      Instant rejection: - The judge's verdicts were never checked against an independent human label on the same cases. - The judge's model and prompt are not version pinned, so old and new scores cannot be compared.

      Model answer: 1. I score pass or fail, not a 1 to 5 scale, because nobody can define what separates a 3 from a 4 consistently across runs. 2. Before trusting the judge at all I validate it against a small human labelled set, the way I'd calibrate any automated check. 3. I run comparisons in both orderings and average, because position alone can flip a verdict on an otherwise identical pair. 4. I watch for the judge rewarding longer answers, the verbosity trap, and since our judge shares a vendor with production, I check for self preference too. 5. I pin the judge's model and prompt version, so a score from three releases back stays comparable, and re-validate whenever either changes.

      Follow-ups: 1. TECHNICAL — If you swap the order of the two answers, does the verdict change? · Position bias, and whether swap and average catches it before trusting a verdict. 2. FAILURE — Your judge is the same model family as what it scores. What bias does that risk? · Self preference bias specifically, not bias treated as an abstract idea. 3. TRADEOFF — Why choose binary pass or fail over a 1 to 5 score for the judge? · Reproducibility of a binary call versus a scale nobody can define consistently. 4. MEASUREMENT — How do you know the judge's verdict still matches a human reviewer today? · Whether validation happened once and was forgotten, or repeats on any judge change.

      Tip: If you have code reviewed with a checklist, or trusted a linter's verdict only after checking it against real bugs, that same scepticism applies here. Do not claim you have built an LLM judge. Say you would validate it against human labels and watch for it rewarding style over correctness.

      Numbers worth quoting: - Binary pass or fail, not 1-5 - Swap order, average the verdict - Same vendor: check self preference - Pin judge model and prompt version

      Q8.4 — What's the difference between evaluating this offline and what you measure once it's live?

      Weak answer: "We ran our eval set before every release, and if it passed we shipped. Dashboards mostly caught outages, not quality."

      Why it fails: - Treats an offline pass as proof of quality, with no distinct online quality signal separate from uptime monitoring. - No mechanism to catch real traffic drifting away from what the fixed eval set actually covers.

      Instant rejection: - Cannot name an online metric distinct from the offline pass rate, uptime is the only thing watched live. - No plan for feeding a discovered online failure back into the offline set.

      Model answer: 1. Offline is my fast, cheap gate, a regression set that runs in CI and catches known failure modes before a real user sees anything. 2. It can only tell me about what's already in the set, so it's blind to distribution shift and failures nobody wrote a case for. 3. Online gives a causally clean answer, once live behind a canary I watch an outcome metric, escalation rate, not the offline pass rate. 4. Last quarter offline pass rate climbed from 74% to 82% while escalation stayed flat, that gap meant the set rewarded answers that looked complete but weren't. 5. I fixed two rubric items from that gap and fed the real online misses back into the offline set, which is why I need both, not one.

      Follow-ups: 1. TECHNICAL — Give me a failure your offline set would never catch. · Understanding offline is bounded by what is in the set, not real drift or adversarial queries. 2. FAILURE — Your offline score climbs release over release but the online outcome is flat. What do you check? · Recognising the eval set may be overfit, or a judge that has drifted from real experience. 3. TRADEOFF — Why not evaluate everything online and skip the offline set entirely? · Offline is fast and reproducible for iteration, online needs live traffic and time. 4. MEASUREMENT — What's the online metric that tells you this is actually working? · An outcome metric, like escalation rate, as distinct from the offline pass rate.

      Tip: If you have watched a staging test suite pass while a live metric like error rate or churn stayed flat, that gap is the same signal. Do not claim you've run online evaluation. Say you understand a passing test suite is not proof of real world quality.

      Numbers worth quoting: - Offline: fast, cheap, bounded - Online: slower, causally real - Watch outcome, not just uptime - Feed online misses back offline

      Q8.5 — The model gives a different answer every run. How do you regression test that in CI?

      Weak answer: "We set temperature to zero for consistency, then diffed the result against an expected output string in the test."

      Why it fails: - Temperature zero reduces variance, it doesn't remove it, model or backend updates still shift the output. - Exact string diffing fails a correct answer worded differently, which is common and not actually a regression.

      Instant rejection: - Tests with exact string matching against a single golden answer, with no property check at all. - Treats one run as a verdict, with no repeated sampling to see the spread.

      Model answer: 1. I stopped expecting determinism, temperature zero or not, provider side updates alone have shifted wording with nothing on our end changed. 2. Tests check properties, not strings: does the answer contain the required facts, is the output schema valid, does it pass a lightweight rubric. 3. A differently worded correct answer passes, a fluently worded wrong one doesn't, which exact string diffing could never tell apart. 4. For edge cases I run the case several times, not once, and record a pass rate rather than a single true or false result. 5. I only multiply runs on cases flagged borderline or previously flaky, and single run the ones that have stayed solid for months.

      Follow-ups: 1. TECHNICAL — What do you check instead of exact string equality? · Assertion based checks, required facts present, schema valid, over brittle string matching. 2. FAILURE — A case passes 8 out of 10 times in CI. Is that a pass or a fail? · Separating acceptable variance from a genuine regression, not treating flakiness as binary. 3. TRADEOFF — Running every case several times multiplies CI time. How do you decide how many runs? · Spending repeated runs where variance is highest, not uniformly across every case. 4. MEASUREMENT — How many times do you run a case before you trust the pass rate? · Repeated sampling and a pass rate with a sense of its own spread, not one boolean.

      Tip: If you have written a flaky test suite that reruns a case or checks a property instead of an exact value, that's the same instinct. Do not claim you've regression tested a non-deterministic model. Say you'd check properties and run cases repeatedly, not diff one string.

      Numbers worth quoting: - Temp zero reduces, not removes - Check properties, not strings - Repeat runs on flaky cases - Pass rate, not one boolean

      Q8.6 — How do you catch hallucination once this is live, without a labelled correct answer to check?

      Weak answer: "We ran each question through the model a few times and checked if the answers agreed, if consistent we trusted the answer."

      Why it fails: - Self consistency sampling multiplies inference cost per request, sound for pre deployment, not viable on every live call. - A model can be confidently and repeatably wrong, agreement across samples isn't the same thing as correctness.

      Instant rejection: - Only knows notebook scale techniques and would apply them to all production traffic regardless of cost. - No cheap always on signal for the overwhelming majority of traffic that never gets sampled.

      Model answer: 1. I can't triple sample every request, so the always on layer is cheap, a groundedness check flagging claims not in the retrieved context. 2. I also run a schema validator for structured output and track a rolling hedging rate, a jump in 'not sure' language often signals something upstream broke. 3. Self consistency sampling is real but expensive, I reserve it for a risk weighted slice, low confidence outputs and policy sensitive categories. 4. I sample about 2% of traffic for human review, weighted toward those same risk categories, not uniform random which mostly reviews the easy cases. 5. When a user flags a wrong answer later, it gets added to the golden set and rechecked against the judge, that gap is exactly what our metrics missed.

      Follow-ups: 1. TECHNICAL — What's a signal you can compute on every single request, not just a sampled few? · Cheap always on checks, groundedness against context, schema validators, hedging rate. 2. FAILURE — A user reports a wrong answer weeks later, nothing flagged it. What's missing? · A feedback loop that feeds real misses back into monitoring and the eval set. 3. TRADEOFF — When is self consistency sampling still worth doing, given the cost? · Recognising it as a pre deployment tool, not something applied to all live traffic. 4. MEASUREMENT — What do you send for human review, and how do you choose the sample? · Risk weighted sampling, high stakes and low confidence cases, not uniform random.

      Tip: If you have added a sanity check or schema validator in front of a fragile pipeline instead of trusting every output, that's the same instinct. Do not claim you've caught hallucination in production. Say you'd use a cheap always on check plus risk weighted human sampling, not a certainty claim.

      Numbers worth quoting: - Groundedness check on every call - Hedging rate as a leading signal - Sample ~2%, weighted by risk - Feed user misses back to eval

      Q8.7 — This task has no single correct answer, summaries, support replies. How do you pick metrics?

      Weak answer: "We used an LLM judge to give a general helpfulness and quality score from 1 to 10, and tracked it across releases."

      Why it fails: - One undifferentiated score conflates separate failure modes, accurate but curt, or complete but far too long. - A 1 to 10 scale has no shared definition of what separates adjacent scores, so it isn't reproducible.

      Instant rejection: - Cannot name the specific dimensions, tone, completeness, policy adherence, that actually matter for this feature. - The rubric was written once at launch and never revisited as understanding improved.

      Model answer: 1. For a support reply I split quality into three dimensions, factual correctness, completeness against what was asked, and tone. 2. Each has its own short written rubric and its own binary pass or fail, scored independently, not blended into one number. 3. Completeness and concision genuinely pull against each other, I score both and look at cases where one improved at the other's expense. 4. The rubric isn't mine to own, our support lead defined good tone, and when she flagged passing transcripts as clearly bad, we added a missing criterion. 5. I keep a small holistic human read alongside the decomposed scores, so a rubric that's drifted from what users feel gets caught early.

      Follow-ups: 1. TECHNICAL — Break 'quality' into the two or three dimensions that actually matter for this feature. · Task specific decomposition, correctness, tone, completeness, instead of one generic label. 2. FAILURE — A rubric says an answer passed, but the person reading transcripts says it is bad. What now? · Recognising rubric under specification rather than dismissing the expert's read. 3. TRADEOFF — Two dimensions trade off, completeness and concision. How do you score that? · Scoring dimensions separately and surfacing the trade off, not averaging it away. 4. MEASUREMENT — How do you check the rubric still reflects what users feel, not just what it once did? · A standing sanity check against real reaction, not a rubric trusted forever.

      Tip: If you have split a code review checklist into separate checks, readability, correctness, tests, instead of one vague "looks good", that's the same idea. Do not claim you've built a quality rubric for an open ended task. Say you'd decompose it into a few named, checkable dimensions.

      Numbers worth quoting: - Split quality into 2-3 dimensions - Binary rubric per dimension - Score trade-offs, don't blend - Domain owner defines "good"

      Q8.8 — What does running your evals actually cost, and how much evaluation is enough?

      Weak answer: "We just ran the eval script before every deploy, it didn't cost extra since we already paid for the API anyway."

      Why it fails: - Ignores that judge and eval calls are a second inference bill on top of production traffic, not folded in for free. - Ignores human labelling time, usually the genuinely expensive, rate limiting part of a real eval process.

      Instant rejection: - No stopping rule, running everything every time isn't a considered cost decision, it's the absence of one. - Never tracked judge spend as its own line, even though it can rival the feature's own inference cost.

      Model answer: 1. I track eval spend as its own line, our judge calls alone once ran close to a fifth of what the feature spent on tokens. 2. The bigger cost is human time, a labeller reviewing 50 cases with a rubric took about ninety minutes, that's the real bottleneck. 3. I optimise for binary pass or fail judgments over granular scores, they're faster to label and I reuse that set to recalibrate the judge. 4. I run a fast fifteen case subset on every commit, the full suite nightly, and a human reviewed sample weekly. 5. My stopping rule isn't a fixed target, it's whether the last ten cases added caught anything the existing set didn't.

      Follow-ups: 1. TECHNICAL — Where does human labelling time actually go, and how do you make it cheaper? · Binary judgments over granular scores, and reusing labels to calibrate a judge. 2. FAILURE — The eval suite grew to twenty minutes and people started skipping it. What do you do? · Recognising a suite too slow to run gets bypassed, worse than a smaller suite people trust. 3. TRADEOFF — Full suite every commit, or a fast subset daily and the full suite nightly? · A tiered cadence, cheap checks constant, expensive judge review on a schedule. 4. MEASUREMENT — Roughly what fraction of your LLM spend is the judge itself, versus the feature being judged? · Whether judge spend was ever tracked as its own line item at all.

      Tip: If you have tracked CI minutes or a third party API bill as its own line and set a budget against it, that's the same discipline. Do not claim you've priced an eval suite. Say you'd separate judge spend, labelling hours and CI time as three distinct costs.

      Numbers worth quoting: - Judge spend, its own budget line - Binary labels are faster to reuse - Tiered cadence: fast, then full - Stop when new cases add nothing

      Q8.9 — [DRILL] Design the eval suite for a support feature launching in two weeks. (practical drill)

      Weak answer: "N/A, this is a drill. A weak attempt invents a handful of cases, uses an unvalidated judge, and has no online metric or cost plan."

      Why it fails: - The golden set is invented in an afternoon, not pulled from real transcripts or escalations. - No validated judge and no online metric distinct from the offline pass rate, the plan ships and hopes.

      Instant rejection: - Judge never checked against a human label, even briefly, before gating a release decision. - No cost or cadence plan, nobody owns a schedule or a budget for any of it.

      Model answer: 1. Week one, I pull 60 cases from real support transcripts and past escalations, stratified across common intents plus the known hard ones. 2. I write a binary rubric with the support lead, hold out 20 for human labels, build the judge on the other 40, and check it before trusting it. 3. Release gate is the offline suite passing plus a 5% canary, the online metric I actually watch is escalation to human rate, not pass rate. 4. In production I run a cheap groundedness check on every reply and sample 2% for human review, weighted toward low confidence cases. 5. What ships in two weeks is exactly that, 60 cases, a validated judge, one online metric, expanding the set waits until after launch.

      Follow-ups: 1. TECHNICAL — Where do the golden set's cases actually come from, and how many before launch? · Real traffic sourcing and a defensible minimum sample size, not an invented handful. 2. FAILURE — Your judge and your feature's model share a vendor. What do you do in this two week window? · Applying self preference bias awareness concretely, not just naming it. 3. TRADEOFF — What's the minimum viable suite you'd actually ship with, and what gets added after launch? · Prioritising under a real deadline instead of describing an idealised suite. 4. MEASUREMENT — What's the one online number that tells you this is actually working after launch? · Choosing a real outcome metric distinct from the offline pass rate.

      Tip: If you have shipped anything behind a canary with a held out test set and one metric you actually watched live, that's the same shape. Do not invent a support launch story. Say you'd apply the same staged, validated, metric driven approach to any two week deadline.

      Numbers worth quoting: - 60 cases, stratified by intent - 20 held out for human labels - 5% canary before full launch - Watch escalation, not pass rate

      Q8.10 — How do you actually check that your LLM judge agrees with what a human reviewer would say?

      Weak answer: "We spot-checked a handful of the judge's scores ourselves and they looked reasonable, so we trusted it going forward."

      Why it fails: - A handful of self-reviewed scores is not a labelled comparison against an independent human judgment. - No agreement metric was ever computed, so "looked reasonable" has no number behind it at all.

      Instant rejection: - The judge was never compared against an independent, blind human label on the same cases. - Uses raw agreement instead of a metric that accounts for how rare real failures are.

      Model answer: 1. I treat the judge like a classifier I need to validate, not an oracle I trust by default, so before it gates anything I build a labelled comparison set first. 2. I take a sample of real outputs, have a domain reviewer label each one pass or fail independently and blind to the judge's verdict, then run the judge on the same cases. 3. I measure true positive and true negative rate against those human labels, not raw agreement, because a judge that mostly says pass can look accurate while catching nothing. 4. Where the judge and the human disagreed, I read the actual transcripts rather than assuming the human was right, because sometimes the rubric itself was ambiguous. 5. I pin the judge's model and prompt version once validated, and re-run this whole calibration whenever either changes, since an unvalidated judge is worse than no judge.

      Follow-ups: 1. TECHNICAL — Walk me through the actual comparison: what did the human see, and what did the judge see? · A real blind, independent labelling process, not a shared or leading setup. 2. FAILURE — Only 8% of outputs actually fail. Why is 90% raw agreement between judge and human not good news? · Recognising raw agreement is misleading when failures are rare, versus true positive and true negative rate. 3. TRADEOFF — A human-labelled calibration set costs real reviewer time. How big did you make it? · A defensible sample size decision, not an arbitrarily small or large set. 4. MEASUREMENT — How often do you re-run this calibration, and what would make you redo it? · Recalibration triggered by a judge, prompt or model change, not a one-off check.

      Tip: If you have validated any automated check against a manual, ground-truth process, for example a linter or a fraud rule against human review, describe that. Do not claim you have calibrated an LLM judge if you haven't. Say you understand why raw agreement misleads and how you would build the comparison.

      Numbers worth quoting: - TPR and TNR, not raw agreement - Blind human labels, judge unaware - Recalibrate on any prompt change - Disagreements read, not assumed

      Q8.11 — How do you measure whether two human labellers actually agree, and what do you do when they don't?

      Weak answer: "We had one person label everything, so there wasn't really a disagreement to measure in the first place."

      Why it fails: - A single labeller means there's no way to know if the labels reflect a shared standard or one person's idiosyncrasies. - Skips agreement measurement entirely rather than explaining why it genuinely wasn't needed here.

      Instant rejection: - Never had two independent labellers review the same cases at all. - Assumes low agreement means the annotators are careless rather than checking the rubric.

      Model answer: 1. I always have at least two labellers independently score a shared subset of cases before I trust a rubric, because an untested rubric is one only one person has ever applied. 2. I compute agreement in a way that accounts for chance rather than plain percentage match, since a skewed label distribution can look consistent even when the rubric is unclear. 3. When agreement came back low on one category, my first move was reading the disagreeing cases together with both labellers, not assuming one of them was careless. 4. That review usually surfaced a genuinely ambiguous rubric line, for example what counts as "complete" for a partial answer, and fixing the wording raised agreement more than retraining did. 5. I re-measure agreement after any rubric change on a fresh batch, because a rubric explained verbally to fix one disagreement can drift again next time someone new labels.

      Follow-ups: 1. TECHNICAL — What did you actually compute, plain per cent agreement or something that corrects for chance? · Awareness that raw agreement overstates consistency on skewed or easy labels. 2. FAILURE — Agreement between two labellers comes back low on one category. What's your first move? · Investigating the rubric for that category before doubting the annotators. 3. TRADEOFF — Getting to high agreement can mean an ever more detailed rubric. When do you stop refining it? · Balancing rubric precision against diminishing returns and labeller fatigue. 4. MEASUREMENT — How many labellers, and how many cases, before you trust the agreement number itself? · A defensible sample size and labeller count, not a single pair on a handful of cases.

      Tip: If you have run a code review checklist or a QA rubric with more than one reviewer and hit disagreement, that's the same problem: an unclear standard, not careless reviewers. Do not claim you have measured formal inter-annotator agreement if you haven't. Say you understand low agreement usually points at the rubric, not the people.

      Numbers worth quoting: - Two labellers minimum, - independent - Low agreement: fix rubric first - Chance-corrected, not raw percent - Re-measure after rubric changes

      Q8.12 — Your eval set says one run scored 3 points higher than another. How do you know that's real?

      Weak answer: "If the new number is higher than the old one, that generally means the change was an improvement."

      Why it fails: - Treats any positive difference as meaningful with no sense of the set's own run-to-run noise. - No mention of how the eval set's size affects how big a difference has to be before it means anything.

      Instant rejection: - No concept of a noise floor: re-running the same unchanged version twice and seeing it move. - Cannot say roughly how large a difference would actually convince them on a set this size.

      Model answer: 1. Before I trust any difference, I check the noise floor: I run the unchanged baseline twice through the same set and see how much the score moves with nothing actually changed. 2. On a 30 to 50 case set, I've regularly seen that noise floor sit around 2 to 3 points from sampling variance alone, so a 3-point gain there isn't something I'd act on by itself. 3. Once the set grows past roughly 100 to 150 labelled cases, that same noise floor narrows enough that a 3-point move starts being genuinely informative rather than chance. 4. I don't just eyeball the topline. I look at which specific cases flipped between runs, because a real improvement flips more cases pass than fail, while noise flips both ways evenly. 5. Where I can't afford a large set, I widen the margin I require before shipping instead, so on a small set I look for a much bigger gap than I would on a large one.

      Follow-ups: 1. TECHNICAL — On a 30-case eval set, how big does a swing need to be before you'd call it real, not noise? · Some working sense of how small sets produce wide, unreliable swings. 2. FAILURE — You shipped on a 3-point gain that turned out to be noise. What would have caught that? · A concrete practice, like re-running the baseline itself, that would expose the noise. 3. TRADEOFF — A bigger eval set is more trustworthy but costs more to run and label. How do you size it? · Balancing statistical confidence against real labelling and compute cost. 4. MEASUREMENT — What do you report: a single pass rate, or a pass rate with some sense of its own uncertainty? · Reporting a range or confidence interval, not a bare point estimate presented as fact.

      Tip: If you have ever looked at A/B test results and asked whether a lift was statistically significant before shipping, that instinct is exactly what's needed here. Do not claim you have run formal significance tests on an eval set if you haven't. Say you know a small set needs a bigger gap before you trust it.

      Numbers worth quoting: - 30 cases: noise floor ~2-3 points - 100+ cases narrows the floor - Re-run baseline to find the floor - Small set needs a bigger gap

      Q8.13 — The output is different every run. How do you set a threshold that actually catches a real regression?

      Weak answer: "We require the eval suite to pass 100% before merging, so any failure blocks the change until it's fixed."

      Why it fails: - A 100% bar on non-deterministic output guarantees ordinary sampling variance blocks a genuinely good change. - Treats every failing case the same, with no distinction between expected variance and an actual regression.

      Instant rejection: - No baseline pass rate for the unchanged system was ever measured before setting the bar at 100%. - Cannot describe what happens when a flaky case fails once, beyond blocking the merge outright.

      Model answer: 1. I first measure the unchanged system's own pass rate over repeated runs, because that baseline variance is the floor any threshold has to sit above, not a guessed number. 2. For most cases I run five samples and set a per-case bar under that, for example needing four out of five to pass, rather than demanding a single deterministic pass. 3. I don't apply one blanket suite-wide percentage. I track each case's own historical pass rate over time and treat a real drop from its own baseline as the regression signal. 4. A case going from 10 out of 10 for months to 6 out of 10 gets flagged even if still technically above a generic threshold, because that shift is bigger than its normal noise. 5. I accept the suite doesn't gate on a clean 100%, and I explain that trade-off up front, because chasing 100% on non-deterministic output just trains people to ignore false blocks.

      Follow-ups: 1. TECHNICAL — How many times do you actually run a case before deciding it passed or failed, one or several? · Repeated sampling per case, not a single run treated as a verdict. 2. FAILURE — A case that's passed 10 out of 10 for months suddenly drops to 6 out of 10. Regression or noise? · Treating a real shift in a case's own historical pass rate as signal, not a coin flip. 3. TRADEOFF — A stricter threshold catches more regressions but blocks more good changes. How do you set it? · Weighing false blocks against missed regressions rather than picking an arbitrary bar. 4. MEASUREMENT — How did you actually derive your threshold number, rather than picking something that felt safe? · A threshold set from measured baseline variance, not intuition.

      Tip: If you have set alert thresholds on a noisy production metric, like error rate, where you had to avoid paging on normal jitter, that's the same reasoning applied here. Do not claim you have tuned a real regression threshold if you haven't. Say you'd measure baseline variance first rather than pick a round number.
