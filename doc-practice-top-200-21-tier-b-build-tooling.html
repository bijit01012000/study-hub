      196. Gradle vs Maven — pick a build tool

      Asked at: Senior rounds at Razorpay · Swiggy · Cred · Walmart Labs

      Difficulty: Medium · Topic: Build / tooling

      The question: "You're starting a new Java service. Maven or Gradle? Why?"

      The 30-second answer: Maven — XML, declarative, larger plugin ecosystem, slower builds, easier for newcomers. Gradle — Groovy/Kotlin DSL, programmatic, much faster (incremental + build cache + daemon), used by Android and modern OSS. For greenfield Spring Boot services in 2026, Gradle (with Kotlin DSL) is the modern pick; for legacy enterprises, Maven dominance is real.

      Step-by-step thought process:

      1. "Maven — pom.xml, lifecycle phases (validate, compile, test, package, install, deploy), convention over configuration. Easy to read, hard to customize."
      2. "Gradle — build.gradle.kts (Kotlin DSL preferred over Groovy), task-based DAG. Incremental compilation, build cache, daemon — typically 2-5x faster than Maven for full builds, 10x for incrementals."
      3. "Plugin ecosystem — Maven has more, Gradle catching up. Spring Boot, Kotlin, Android all first-class on Gradle."
      4. "Switching cost — Maven config is more portable; Gradle DSL is more powerful but harder to read for newcomers. Pick what your team can maintain."

      Edge cases to mention:

      • Gradle's dependency resolution can produce different versions than Maven's "nearest wins" — read the resolution rules
      • Maven Wrapper (mvnw) and Gradle Wrapper (gradlew) — both let CI use a pinned tool version without global install; always use the wrapper in repo
      • Multimodule — Gradle composite builds vs Maven reactor; Gradle handles cross-module incremental better

      What NOT to say:

      • "Gradle is always better" — Maven still dominates enterprise; team familiarity matters
      • "Maven is dead" — no, deeply entrenched in Apache, Spring ecosystem

      Common follow-up: "What's the Gradle build cache and how does it work?"

      197. Dependency convergence and conflicts

      Asked at: Senior rounds at Razorpay · Swiggy · TCS Digital · Wells Fargo

      Difficulty: Medium-Hard · Topic: Build / tooling

      The question: " NoSuchMethodError at runtime that wasn't there yesterday. How do you debug?"

      The 30-second answer: Transitive dependency conflict — you compile against Jackson 2.15 but a different library brought in Jackson 2.13 that won. Diagnose: mvn dependency:tree or gradle dependencies. Force the version via (Maven) or constraints (Gradle). Spring Boot's BOM (spring-boot-dependencies) is the easy answer in Spring projects.

      Step-by-step thought process:

      1. "The cause — Java classpath has one class per FQN. Two versions on the path, classloader picks one based on order. NoSuchMethodError happens when the chosen version doesn't have the method your code expects."
      2. " mvn dependency:tree -Dincludes=com.fasterxml.jackson.core — shows the tree filtered to Jackson. Look for multiple versions appearing."
      3. "Resolution — Maven uses nearest-wins (shortest path from root). Gradle uses highest-version-wins by default. Both can be overridden."
      4. "Best practice — use a BOM (Bill of Materials). Spring Boot's BOM aligns all Spring + commonly-used deps to compatible versions. Just import</scope> it or use platform(...) in Gradle."

      Edge cases to mention:

      • mvn enforcer:enforce with dependencyConvergence rule fails build on conflicts — opinionated but catches issues early
      • Shading (maven-shade-plugin) repackages dependencies under different package names to avoid conflicts; common for libraries like AWS SDK
      • Java module system can also catch some issues at module load time, but classpath mode is what most apps run in

      What NOT to say:

      • "Exclude all transitive dependencies" — fragile; you'll miss something
      • "Use the latest version of everything" — incompatible upgrades happen; pin via BOM

      Common follow-up: "What's a BOM and why does Spring Boot ship one?"

      198. Multi-module project structure

      Asked at: Senior rounds at Razorpay · Swiggy · Wells Fargo · TCS Digital

      Difficulty: Medium · Topic: Build / tooling

      The question: "How would you structure a multi-module Maven / Gradle project?"

      The 30-second answer: One root with shared config. Modules split by bounded context or layer — core (domain models), service (business logic), web (controllers), infra (external integrations). Avoid common modules that grow into kitchen-sink dependencies. Spring Boot 3 + Gradle multi-project is a clean default.

      Step-by-step thought process:

      1. "Maven — in parent pom. Each module is a directory with its own pom inheriting from parent. Build via mvn install at root."
      2. "Gradle — settings.gradle.kts lists include(":core", ":service", ":web"). Modules depend on each other via implementation(project(":core"))."
      3. "Module split — by bounded context (orders, payments, inventory) for large services, by layer (domain / app / infra) for hexagonal architecture. Avoid mixing styles."
      4. "Single deployment artifact — Spring Boot module produces the executable jar, depends on all the others. Other modules are libraries with no main class."

      Edge cases to mention:

      • Cyclic dependencies — both Maven and Gradle reject them. If you have one, your module split is wrong
      • Test source dependencies — Gradle testFixtures lets one module's test code reuse fixtures from another; Maven needs jar + test-jar packaging
      • Version alignment — define versions in root dependencyManagement (Maven) or gradle.properties (Gradle), inherit everywhere

      What NOT to say:

      • "Put everything in one module for simplicity" — works to ~50k LOC, painful beyond
      • "More modules is always better" — over-modularization adds build overhead without benefit

      Common follow-up: "How would you avoid a 'common' module turning into a dumping ground?"

      199. JLink and JPackage — bundling a runtime

      Asked at: Senior rounds at Razorpay · Goldman · Walmart Labs

      Difficulty: Medium-Hard · Topic: Build / tooling

      The question: "How do you ship a Java app that doesn't require the user to install a JDK?"

      The 30-second answer: jlink (Java 9+) creates a custom JRE containing only the modules your app uses — typically 30-50MB instead of 200MB+ full JDK. jpackage (Java 14+) wraps that into an OSnative installer (.msi, .dmg, .deb, .rpm) with launcher script and app icon. Alternative: GraalVM Native Image for a single static binary.

      Step-by-step thought process:

      1. " jdeps --print-module-deps myapp.jar — lists the JDK modules your app uses. Maybe 30, out of ~80 in the full JDK."
      2. " jlink --module-path $JAVA_HOME/jmods --add-modules --output myruntime — builds a stripped JRE. Distribute alongside your app."
      3. " jpackage --type msi --name MyApp --input app/ -main-jar myapp.jar --runtime-image myruntime — wraps it into a Windows installer. Same flags for dmg, deb, rpm, etc."
      4. "For server-side, container images (Docker eclipsetemurin:21-jre-jammy base) are easier. JLink/JPackage are about desktop / CLI tools targeting end users."

      Edge cases to mention:

      • Reflection / dynamic class loading breaks JLink — if your app loads classes by name not in jdeps output, JLink misses them. Use --add-modules to force
      • Cross-platform — JLink must run on the target OS (you can't build a Windows runtime from Linux without a Windows toolchain). JPackage similarly
      • Native Image alternative — single static binary, even smaller, but loses some dynamic Java features

      What NOT to say:

      • "Just bundle the full JDK" — wasteful (10x size), increases attack surface
      • "JLink works for any jar" — non-modular jars (no module-info.class) work as automatic modules, but reflection-heavy ones may break

      Common follow-up: "What's the difference between JLink + JPackage and GraalVM Native Image?"

      200. Concurrency final boss — design a thread-safe cache with TTL

      Asked at: Staff rounds at Razorpay · Swiggy · Cred · Flipkart · Walmart Labs · Goldman

      Difficulty: Hard · Topic: Concurrency advanced

      The question: "Design a thread-safe in-memory cache with per-entry TTL. Walk me through your design choices."

      The 30-second answer: Use ConcurrentHashMap<K, CacheEntry<V>> where CacheEntry holds value + expiry timestamp. Read path: get entry, check expiry, return value or null. Write path: put with current time + ttl. Cleanup: lazy on read + a scheduled task to evict expired keys. Honest answer: just use Caffeine — it solves all of this and more.

      Step-by-step thought process:

      1. "Naive — Map<K, V> + Map<K, expiryTimestamp>. Two maps means atomicity problems; combine into one entry class."
      2. " record CacheEntry<V>(V value, long expiresAt). Map is ConcurrentHashMap<K, CacheEntry<V>>. Get: lookup, check expiresAt > now, return value or evict + return null."
      3. "Eviction policy — purely lazy (only on read) lets stale entries pile up if rarely read. Background ScheduledExecutorService.scheduleAtFixedRate(this::evictExpired, 1, 1, MINUTES) walks and removes."
      4. "Honest answer in an interview — Caffeine is the production answer. It does W-TinyLFU eviction, size-based and time-based, with no allocation in the hot path. Mention it explicitly."

      Edge cases to mention:

      • Read-through cache pattern — on miss, call a loader function, store the result. Caffeine's LoadingCache handles concurrent loads for the same key (only one loader runs) Refresh-ahead — when entry is close to expiry, refresh proactively to keep cache warm. Caffeine refreshAfterWrite
      • Memory bound — without max size, cache leaks. Always set both expireAfterWrite and maximumSize

      What NOT to say:

      • "Use Hashtable " — synchronized on every op, terrible under concurrency
      • "Use synchronized blocks" — works but loses ConcurrentHashMap's segment-free concurrency

      Common follow-up: "Why is Caffeine's eviction algorithm (W-TinyLFU) better than LRU for typical workloads?"
