    Design a Pub-Sub System

    15 sections · 1,768 words

    LLD Design Problems, problem 20 of 20.

    The Ask

    Build

    • In-process Broker, Topics, publish a Message to a topic.
    • Subscribe and get every message published after subscribing.
    • At-least-once: an append-only log per topic, each subscriber its own offset.
    • Deliver at the offset, the subscriber acks to advance.
    • nack or ack-timeout redelivers, dead-letter after N.
    • Per-topic FIFO, one in-flight per subscriber.
    • Backpressure: a slow subscriber lags (shared log) or fills a bounded queue with a stated overflow policy.

    Skip

    • Multi-node / partitioning / replication / a wire protocol (Kafka, the HLD).
    • Exactly-once.
    • On-disk persistence past naming a WAL.
    • A schema registry.
    • Consumer-group rebalancing detail.

    Our Model

    Topics, log, per-subscriber offset. A Broker holds topics and subscriptions; each Topic is an append-only log and each Subscription keeps its own cursor into it.

    Actors and classes

    • Publisher — topic: String; publish(Message m) calls broker.publish(topic, m).
    • App1 / App2 / Worker — implement onMessage(m), then acks. The handler may throw.
    • Broker (singleton) — topics: Map<String, Topic>, subs: Map<String, List<Subscription>>, sweeper: Sweeper; publish(String topic, Message m): void, subscribe(String topic, Subscriber s): Subscription, ack(String subId, long offset): void.
    • Topic — name: String, log: List<Message> (grows only); append(Message m): long, at(long offset): Message, size(): long.
    • Message (value) — id: String, topic: String, payload: byte[], at: Instant. An opaque blob to the broker.
    • Subscriber (interface) — name: String; onMessage(Message m): void. Your handler runs here, may throw.
    • Subscription (one per subscriber) — id: String, sub: Subscriber, offset: long, inFlight: Message, deadline: Instant, tries: int; deliverNext(): void, advance(long offset).
    • Sweeper — scan(): void; redelivers past-deadline in-flight messages, dead-letters after MAX_REDELIVERY. Runs on a timer.
    • DeliveryPolicy / OverflowRules (interface) — onOverflow(Subscription s, Message m): void. The one rule for a full bounded queue. BlockPublisher (publish waits for room), DropOldest (evict the head), DropNewest (reject the incoming message). Same seam; only the overflow move differs.
    • RetentionPolicy (interface, seam) — keepUntil(Topic t): long. Caps how far back the shared log is kept. KeepAll, MaxAge, MaxSize.
    • DeadLetter (value, seam) — topic: String, message: Message, tries: int, lastError: String. Parked after N failed deliveries.

    Relationships

    Broker owns 1.. topics and 1.. subscriptions per topic. A Subscription reads at its offset; a Message is read, never removed.

    The invariants

    • caughtUp when offset == topic.size().
    • lag(sub) = topic.size() - offset.
    • 1 in-flight per sub; FIFO per topic.
    • Retention, not reading, frees the log.

    Key operations

    1. publish(String topic, Message m): void — appends to the topic log (O(1)), then wakes every Subscription on that topic. Never blocks on a subscriber unless the DeliveryPolicy says BlockPublisher.
    2. subscribe(String topic, Subscriber s): Subscription — a new Subscription starts at the current tail (offset == size), so it sees only messages published from now on.
    3. ack(String subId, long offset): void — advances that subscription's offset past the acked message and clears inFlight. An ack for an old offset is a no-op (idempotent).
    4. deliverNext(): void — if caught up, return. Else hand topic.at(offset) to the subscriber with a visibility deadline; one message in flight at a time so order holds.

    From memory

    • deliverNext: if (offset==size) return; m=at(offset); onMessage(m); deadline=now+VIS.
    • ack(off): if (off==offset) offset++; inFlight=null (old / dup ack: no-op).

    Recall drill: cover the operations column, write the four with their guarantee. Blank on the guarantee means that method is your gap.

    The One Run to Hold in Your Head

    Topic orders. Sub A is caught up at offset 5, sub B is slow at offset 2. A publisher appends m5. Walk what each subscriber does next, and what happens if B never acks m3.

    The same array, two cursors: A.offset = 5, B.offset = 2. B acks 2 -> B.offset = 3. B is silent on m3, so the sweeper redelivers m3. M3 fails three times -> m3 goes to dead-letter, B.offset = 4. A is caught up, so deliverNext() returns at once.

    The Change

    Several subscribers share a group and each message goes to exactly ONE member, so a topic's throughput scales across the group. Subscription offset becomes per-group, delivery picks a free member, and rebalancing hands partitions around when a member joins or leaves.

    What the Picture Can't Show

    The log is not a queue. A read does not remove anything. Two subscribers on one topic each hold their own offset into the same array, so a slow one only lags. Retention, not consumption, frees a slot.

    If They Make You Code It

    Publish, deliver and the sweeper:

    class Broker {                                     // one singleton
    Map<String,Topic> topics;
    Map<String,List<Subscription>> subs;
    Map<String,Subscription> byId;

    void publish(String topic, Message m) {
        Topic t = topics.get(topic);
        long off = t.append(m);                    // O(1), append-only
        for (Subscription s : subs.get(topic))
            s.deliverNext();                       // wake, never block
    }
    void ack(String subId, long off) {
        Subscription s = byId.get(subId);
        if (off == s.offset) {                     // idempotent
            s.offset++; s.inFlight = null; s.tries = 0; }
    }
}

class Subscription {
    long offset; Message inFlight; Instant deadline; int tries;
    void deliverNext() {
        if (offset >= topic.size()) return;        // caught up
        if (inFlight != null) return;              // one in flight
        Message m = topic.at(offset); inFlight = m;
        deadline = clock.now().plus(VIS_TIMEOUT);
        try { sub.onMessage(m); } catch (Exception e) { return; }
    }
}

class Sweeper {                                    // runs on a timer
    void scan() { for (Subscription s : all) {
        if (s.inFlight == null || !now().isAfter(s.deadline)) continue;
        if (++s.tries > MAX_REDELIVERY) {          // dead-letter
            dlq.add(s.topic, s.inFlight);
            s.offset++; s.inFlight = null; s.tries = 0;
        } else { s.inFlight = null;                // free the slot,
            s.deliverNext(); }                     // offset unmoved
    } }
    // per-sub queue variant: DeliveryPolicy.onOverflow fires here
}

    The Four Hazards

    1. Slow subscriber, unbounded growth. With per-sub queues a lagging consumer's queue grows without limit, then OOM. A bounded queue + a stated DeliveryPolicy (block the publisher / drop-oldest / drop-newest); with the shared log, a RetentionPolicy caps how far back the log is kept.
    2. A subscriber that never acks. inFlight is pinned and redelivery repeats forever. A visibility timeout redelivers, then dead-letter after MAX_REDELIVERY; never an unbounded retry loop.
    3. Losing a message with fire-and-forget. If delivery does not wait for an ack and the process restarts, the in-flight message is gone. At-least-once needs the ack + the persisted offset, so a restart resumes from the last acked offset.
    4. Publishing while the subscriber set changes. Iterating subs.get(topic) while another thread subscribes or unsubscribes throws, or a mid-delivery unsubscribe NPEs. Snapshot / copy-on-write the list; tombstone a removed subscription instead of deleting mid-loop.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. if (offset >= topic.size()) return — caught up, the read is not destructive.
    2. if (inFlight != null) return — one in flight, so per-topic order holds; the sweeper clears it first, so deliverNext() re-reads the same unacked offset.
    3. if (off == s.offset) in ack — idempotent; an old or duplicate ack does nothing.

    The Delivery Model

    Approach Copies of a message Slow consumer Replay New bug surface
    Shared log + per-sub offset (Kafka-style) one only lags, needs a retention bound yes, seek an offset retention + offset bookkeeping
    Per-subscriber queue (RabbitMQ-style) N its own bounded queue, natural backpressure no, gone after delivery N queues to bound
    Sync direct-call observer (no broker) none blocks the publisher and every other subscriber no a throwing subscriber breaks the loop

    Shared log + per-subscriber offset. One copy, replayable, a slow consumer only lags. Reach for per-subscriber queues when subscribers are truly independent and you want per-consumer backpressure with no retention tuning.

    Rejection Signals

    These end the interview:

    • Treating the topic as a queue that pops on delivery, so a second subscriber gets nothing.
    • No ack at all (fire-and-forget) while claiming at-least-once.
    • An unbounded per-subscriber queue with no overflow policy.
    • Retrying a stuck message forever with no visibility timeout and no dead-letter.
    • Delivering several messages to one subscriber at once, so acks and the offset desync.
    • Iterating the subscriber list while it is being modified.

    Patterns Used

    Observer — subscribers observe a topic, decoupled by the broker. Strategy — DeliveryPolicy and RetentionPolicy. Factory — a Topic on first publish. Iterator — a subscriber walks the log at its offset.

    Say It Like This

    "Each topic is an append-only log. A publish appends and wakes the subscribers on that topic. Every subscriber keeps its own offset, gets the message at that offset with a visibility deadline, and acks to advance. No ack in time, the sweeper redelivers, then dead-letters after N. A slow subscriber only lags; retention, not reading, frees the log."

    The Follow-ups That Decide It

    1. Two subscribers on one topic, one slow. What does each see? Each has its own offset; the slow one only lags.
    2. A subscriber never acks m3. Visibility timeout, redeliver, dead-letter after N.
    3. New subscriber on a topic with 1000 messages. From where? The tail; only new messages, unless it asks to replay from an offset.
    4. Publisher outruns a subscriber forever. Bounded queue + DeliveryPolicy, or a retention bound on the shared log.
    5. Keep ordering with a slow onMessage. One in flight per subscriber; or partition by key.
    6. Make each message go to exactly one of N workers. A consumer group (the ghost).
    7. The process restarts. Resume from the last persisted acked offset; in-flight unacked messages redeliver.
    8. A subscriber throws inside onMessage. No ack, the sweeper retries, dead-letter after N; the publish loop is not affected.

    Deliberately Not Built

    • Exactly-once — needs idempotent consumers or a transaction protocol. At-least-once + an idempotency key is the honest answer.
    • Persistence — the log is in memory here; a real one is a segmented WAL with fsync.
    • Partitioning across nodes — the page-2 ghost. One-of-N delivery + rebalancing.
    • A schema registry / serialization — the payload is an opaque blob here.
    • A real broker — that is Kafka, the HLD version. Name it, move on.
