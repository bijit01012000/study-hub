    Design a Chess Game

    15 sections · 1,887 words

    LLD Design Problems, problem 06 of 20.

    The Ask

    Build

    • An 8x8 board of squares, two players alternate turns.
    • Standard set: king, queen, rook, bishop, knight, pawn.
    • A move is a from-square to a to-square.
    • Legal: the piece can make it, the path is clear, the target is empty or an enemy, and it does not leave your own king in check.
    • Each piece type generates its own moves.
    • Special: castling, en passant, promotion, the two-square pawn open.
    • Detect check, checkmate, stalemate; the game ends.
    • Undo and a move history you can replay.

    Skip

    • A chess engine or AI.
    • Clocks and time control.
    • Opening books, PGN / FEN detail.
    • Threefold-repetition bookkeeping.
    • Network transport, a database, login.

    Our Model

    An 8x8 board of squares, a Game that holds the board, whose turn it is, and a history stack. Each Piece generates its own pseudo-moves; the Game filters them by king safety.

    Actors and classes

    • Player — color: Color, game: Game; move(Square from, Square to, Piece promo) calls game.makeMove(resolve(from, to, promo)).
    • Game (the context) — board: Board, toMove: Color, history: Deque<Move>, enPassant: Square, castling: CastlingRights, state: GameState; legalMoves(Square from): List<Move>, makeMove(Move m): void, inCheck(Color c): boolean, status(): GameState, undo().
    • Board — squares: Square[8][8], kings: Map<Color, Square>; pieceAt(Square s): Piece, set(Square, Piece), kingSquare(Color c): Square, attacked(Square s, Color by): boolean.
    • Square — file: int 0..7, rank: int 0..7, piece: Piece (nullable); offset(int df, int dr): Square, equals / hashCode by file and rank.
    • Piece (abstract) — color: Color, square: Square, hasMoved: boolean; pseudoMoves(Board b, Square from, Game g): List<Move>, attacks(Square s, Board b): boolean. 6 subtypes.
    • Move (Command) — from, to: Square, piece: Piece, captured: Piece, flags: castle | ep | promo, prevCastling, prevEnPassant, rook; apply(Board b, Game g): void, undo(Board b, Game g): void.
    • GameState (interface) — recompute(Game g): GameState. States: Active, Check, Checkmate, Stalemate, Draw.
    • BoardObserver (interface) — onMove(Move m): void; MoveLog, PgnWriter, Clock.
    • MoveHistory — moves: Deque<Move>; push(Move), pop(): Move. Each Move unapplies itself.

    Relationships: Game owns 1 board and 1 history; the board owns 64 squares; a square holds 0..1 piece.

    The six piece types

    • King -> one step any way, castles.
    • Queen -> any ray, any distance.
    • Rook -> rank / file rays, castles.
    • Bishop -> diagonal rays.
    • Knight -> the 8 L jumps, hops pieces.
    • Pawn -> push, two-open, capture, e.p., promote.

    The five states

    • Active -> normal play.
    • Check -> the mover must escape it.
    • Checkmate -> in check, no legal move; game over.
    • Stalemate -> not in check, no legal move; draw.
    • Draw -> 50-move, repetition, insufficient material, agreement.

    Pseudo-moves, then the king-safety filter: pseudoMoves is shape only; legalMoves = pseudo AND the king still safe after the move. check when an enemy pseudo-move hits my king.

    Key operations

    1. legalMoves(Square from): List<Move> — every pseudo-move the piece on from can make, each one simulated and kept only if it does not leave this side's king in check. Empty when it is not your turn or the square is empty.
    2. pseudoMoves(Board b, Square from, Game g): List<Move> — the per-piece Strategy step. Shape only: slide or step by this piece's pattern, stop at the first blocker, take an enemy. Ignores check, pins and whose turn it is.
    3. makeMove(Move m): void — rejects anything not in legalMoves(m.from). Applies it (the rook too, on a castle), pushes to history, flips the side, recomputes check / mate / stalemate.
    4. inCheck(Color c): boolean — true when any enemy piece attacks c's king square right now. One board scan. Runs after every simulated move, so it stays cheap and side-effect free.

    legal when a pseudo-move AND the king safe after it. Each ray / step from sq; stop at the first piece; take it only if it is an enemy. for m in pseudo: apply(m); keep if !inCheck(me); undo(m).

    The One Run to Hold in Your Head

    White rook on e4, white king on e1, black rook on e8. White tries Re4 to h4. Is it legal? Walk pseudoMoves, then the king-safety filter, and name every object the request touches.

    The black rook pins the white rook to its king; the 7 rank moves expose the king. It is rejected.

    The Change

    They ask the machine to play. An Engine calls legalMoves, applies each, scores the position, and searches a few plies deep with alpha-beta. It only consumes the rules; not one rule class changes. A new object on the same seam.

    What the Picture Can't Show

    The full-board scan. inCheck asks the board whether any enemy piece attacks the king square, and it runs after every simulated move. So legalMoves is per-piece generation times a board scan — fine for a game, far off engine speed. Bitboards if they push.

    If They Make You Code It

    legalMoves, makeMove, and Move.undo:

    class Game {                                     // the context object
    Board board; Color toMove = WHITE;
    Square enPassant; CastlingRights castling;
    final Deque<Move> history = new ArrayDeque<>();

    List<Move> legalMoves(Square from) {
        Piece p = board.pieceAt(from);
        if (p == null || p.color != toMove) return List.of();
        List<Move> out = new ArrayList<>();
        for (Move m : p.pseudoMoves(board, from, this)) {
            m.apply(board, this);                    // simulate the move
            if (!inCheck(toMove)) out.add(m);        // my king stays safe
            m.undo(board, this);                     // restore, every time
        }
        return out;
    }

    void makeMove(Move m) {
        if (!legalMoves(m.from).contains(m)) throw new IllegalMove(m);
        m.apply(board, this);                        // also hops the rook on castle
        history.push(m);                             // the undo stack
        toMove = toMove.opposite();                  // flip the side to move
        refreshStatus();                             // Active / Check / Mate / Draw
    }

    boolean inCheck(Color c) {
        return board.attacked(board.kingSquare(c), c.opposite());
    }
}

class Move {                                     // Command + a little Memento
    void undo(Board b, Game g) {                 // unapply, restore all of it
        b.set(to, captured); b.set(from, piece); // captured may be null
        if (castle) rook.undo(b);                // the rook slides back too
        g.castling = prevCastling;               // castling rights restored
        g.enPassant = prevEnPassant;             // en-passant target restored
    }
}

    The Four Hazards

    1. A move that leaves your king in check. The piece's pattern says the move is fine, but it opens a line on your own king (a pin). Pattern-matching alone lets it through. Simulate: apply, inCheck(me), then drop it.
    2. Castling. Illegal through, out of, or into check, or if the king or that rook has moved, or a square between them is occupied. King and rook !hasMoved, path empty, and none of the 3 king squares attacked.
    3. En passant. Legal only on the ply immediately after the enemy pawn's two-square jump. Wait one move and it is gone. enPassant set now, cleared next.
    4. Checkmate vs stalemate. Both are "the mover has no legal move". If in check -> checkmate, game over; if not in check -> stalemate, a draw. The check bit alone decides.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. apply then inCheck then undo — you must simulate, never pattern-match. A pin is only visible with the move on the board.
    2. undo restores the captured piece, the castling rights and the en-passant target — not just the two squares.
    3. legalMoves(m.from).contains(m) — makeMove trusts nothing; the same filter guards every entry point.

    Generating a Piece's Moves

    Approach Readability Move-gen speed King-safety Use when
    Switch on type sinks past 3 pieces fine apply + scan never, really
    PseudoMoves per piece (the default) one rule per class fine for a game apply + scan every interview
    Attack tables / bitboards (engine-grade) bit tricks, opaque fastest by far a danger-square mask you are building an engine

    Polymorphic pseudoMoves, one method per piece. Adding a piece or a fairy variant is a new subclass and nothing else moves. Reach for bitboards only when you are actually building an engine and profiling says move generation is the wall.

    Rejection Signals

    These end the interview:

    • Validating a move by the piece's pattern alone, never simulating — a pinned piece moves, or the king walks into check.
    • undo that only swaps the two squares — the captured piece, castling rights and en-passant target are lost.
    • One switch (pieceType) for move generation, edited for every piece and every special move.
    • Castling coded as "king moves two" with no check on the three king squares, the rook, or hasMoved.
    • En passant allowed whenever the pawns line up, not only the ply after the two-square jump.
    • No line between checkmate and stalemate — both are "no legal move"; only the check bit separates them.

    Patterns Used

    Strategy — per-piece move generation, one method each. Command — a Move applies and unapplies itself over a history stack. State — Active / Check / Checkmate / Stalemate / Draw. Factory — the starting position and the promotion piece.

    Say It Like This

    "An 8x8 board of squares, a Game that holds the board, whose turn it is, and a history stack. To move, the piece generates its own pseudo-moves; the Game simulates each and keeps only those that do not leave its king in check. A Move object applies and undoes itself, restoring the captured piece, castling rights and the en-passant target. After each move the Game recomputes its state: check, checkmate, stalemate or draw."

    The Follow-ups That Decide It

    1. A pinned knight is asked to move. Simulate: apply, inCheck(me), then drop it.
    2. King and rook unmoved, but f1 is attacked. Castling through check is illegal; test all 3 king squares.
    3. Black just pushed a pawn two squares past yours. En passant, this ply only; enPassant set now, cleared next.
    4. A pawn reaches the eighth rank. Promotion; the Move carries the choice, default queen; undo restores the pawn.
    5. No legal move and the king is not in check. Stalemate, a draw; the State goes to Stalemate.
    6. Make the machine play a move. An Engine over legalMoves; the rules engine is untouched.
    7. Undo three moves, then branch. Pop three Moves, each unapplies itself; history is the command stack.
    8. Threefold repetition claim. Hash each position into a multiset over history; third time allows the draw.

    Deliberately Not Built

    • A chess engine / AI — minimax, alpha-beta, an eval function. A separate object that only reads legalMoves.
    • Clocks and time control — a per-player timer, increments, flag-fall. Orthogonal to the rules.
    • PGN / FEN import-export — a parser and a writer around the move list. Named, not modelled.
    • Threefold repetition — a position-hash multiset over history. Mentioned; bookkeeping skipped.
    • Network transport — two clients, a server relays moves. A thin seam behind makeMove.
