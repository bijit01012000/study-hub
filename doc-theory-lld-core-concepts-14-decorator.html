    Decorator

    11 sections · 788 words

    Structural · Design Patterns · Pattern 05 of 12

    Intent

    Attach behaviour to one object at runtime by wrapping it behind the same interface, so features stack in any order without a subclass per combination.

    When To Use It

    The Signs

    • A subclass per feature combo: BufferedGzipEncryptedWriter.
    • You want to add behaviour to one object at runtime, not the class.
    • Optional add-ons, logging, retry, metrics, layered on and off.

    Don't Bother If

    • There is one feature and it is always on.
    • The behaviour needs the target's private internals.
    • You want to change the interface. That is Adapter.

    Before

    class RetryChannel extends EmailChannel {
    Result send(Message m) { ...retry, then super.send... }
}
class RetryRateLimitedChannel extends RetryChannel {
    Result send(Message m) { ...rate-limit, then super... }
}
class RetryRateLimitedMeteredChannel extends
        RetryRateLimitedChannel { ...one more layer... }
// 3 features = 7 subclasses, and only for Email

    Class per combo.

    After

    interface NotificationChannel { Result send(Message m); }

abstract class ChannelDecorator implements NotificationChannel {
    protected final NotificationChannel inner;
    ChannelDecorator(NotificationChannel inner) { this.inner = inner; }
}
class RetryingChannel extends ChannelDecorator {
    RetryingChannel(NotificationChannel c) { super(c); }
    public Result send(Message m) {
        Result r = inner.send(m);
        for (int i = 1; i < MAX && !r.ok(); i++) {
            sleep(backoff(i));
            r = inner.send(m); // MAX attempts total
        }
        return r;
    }
}
// RateLimited, MeteredChannel: wrap the same way
NotificationChannel c = new MeteredChannel(
    new RateLimited(new RetryingChannel(new EmailChannel())));
// stack in any order. EmailChannel never knew.

    Or flags inside the class:

    Result send(Message m, boolean retry,
            boolean rateLimit, boolean meter) {
    if (rateLimit && !allow()) return Result.dropped();
    if (meter) metrics.mark("send");
    if (retry) { for (int i = 0; i < MAX; i++) {...} }
    return transport.send(m);
}
// every caller passes four booleans it half-understands

    Structure

    «INTERFACE»
NotificationChannel
    + send(m): Result
    same interface in and out

ChannelDecorator
    - inner: NotificationChannel
    holds one
    forwards every call to inner

EmailChannel
    the real send

RetryingChannel
RateLimited
MeteredChannel
    each does its bit,
    then calls inner

Metered( RateLimited( Retrying( Email ) ) )
WRAP, DON'T SUBCLASS. STACK IN ANY ORDER

    How It's Built (3 Steps)

    1. Put the core and every decorator behind ONE interface. NotificationChannel with the one method callers use.
    2. A base decorator holds an inner of that interface and forwards every method straight to it.
    3. Each concrete decorator overrides the one method it cares about: do its part, then call inner.method(). Wrap to compose.

    Quick Check

    Want to mix add-ons freely at runtime? Make each one an object that wraps the same interface.

    In The Interview

    "I would make RetryingChannel a Decorator over NotificationChannel. It wraps EmailChannel, retries on a transient failure, and the fan-out code just calls send(). RateLimited and Metered wrap the same way, in any order."

    How It's Different

    From The Lookalikes

    Vs Adapter. An Adapter changes the interface and adds nothing. A Decorator keeps the same interface and adds behaviour, and you stack several.

    Vs Composite. A Composite is a tree of many child objects treated as one. A Decorator is a chain of wrappers around one object.

    Vs Proxy. A Proxy keeps the interface and controls access (lazy load, remote, permission). A Decorator adds features, and you usually have many.

    Vs Strategy. A Strategy swaps an inner algorithm held as a field. A Decorator wraps the whole object from the outside, changing what happens before and after.

    They Say: "now add metrics to SMS too"

    • With it: reuse MeteredChannel, wrap it around SmsChannel. No new subclass.
    • Without: a MeteredSmsChannel, and next week a MeteredRetryingSmsChannel.

    Watch Out For

    • Order matters. retry(log(x)) logs once per attempt; log(retry(x)) logs once. Decide deliberately.
    • Keep the interface small, or every decorator carries a pile of dead pass-through methods.
    • A decorator must honour the wrapped object's contract (Liskov). Do not quietly change return semantics.
    • You cannot easily pull one decorator out of a deep stack. If you need that, keep a list and rebuild the chain.
    • == identity and instanceof see the outermost wrapper, not the core. Provide an unwrap() if callers need the real thing.
