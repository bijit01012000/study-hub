    Lecture 18 — Spring Boot Profiles & YAML Explained

    25 sections · 4,035 words

    Lecture 18

    Scope evidence: "Spring Boot Profiles & YAML Explained | Dev vs Prod Configuration" (playlist map, verified). Repo lecture folder is the profileDemo project (entry point ProfileDemoApplication): application.properties plus application-dev.properties, application-prod.properties and application-staging.properties, a profile-aware NotificationService with NotificationServiceImpl and DummyNotificationServiceImpl, and controllers used to show profile-driven values.

    An application is never only code; it is code plus configuration. This lecture moves changeable values (port, database URL, credentials, messages) out of Java classes into configuration files, then shows how YAML makes them readable and how profiles let one build behave differently across dev, test, staging and prod. The rule: same code, same build, different environment, different configuration.

    1. Why Configuration Is Needed

    A real-world application is a combination of two things:

    Application = Code + Configuration

    Code contains the actual business logic. Examples from the lecture: create student, fetch student, update student, delete student, connect to database, send email, run server.

    But to run that code properly, the application also needs values that are not business logic:

    Question the app must answer Kind of value
    Which port should the application run on? server port
    Which database should it connect to? datasource URL
    What is the database username? credential
    What is the database password? secret
    What should the application name be? identity
    Which environment is currently active? profile
    What message should be shown to the user? message

    These values are called configuration values. The Java code stays the same while these values change per environment.

    In real projects, the same Spring Boot application may run in several places:

    • Local machine
    • Testing server
    • Staging server
    • Production server

    Important: Configuration is any value that can change without changing Java code. If changing it forces you to edit a .java file, it was probably placed in the wrong layer.

    2. The Problem With Hardcoding Values

    Hardcoding means writing fixed values directly inside Java classes:

    String dbUrl = "jdbc:mysql://localhost:3306/student_db"; String username = "root"; String password = "root";

    This looks simple but creates three serious problems.

    Problem 1: Code becomes difficult to change. If the database URL changes, hardcoded code forces you to open the Java file, update it, rebuild, and redeploy. A database URL is not business logic; it is environment-specific configuration.

    Problem 2: Same code cannot easily run in multiple environments. Local may use root/root, production prod_user/strong_secure_password. Hardcoding locks the code to one environment; a professional application follows: same code, different configuration.

    Problem 3: Sensitive information can leak. A password written into Java and pushed to GitHub can be exposed. Passwords, API keys and tokens must never be hardcoded.

    Golden rule: If a value differs between environments, or is a secret, it does not belong in a .java file. It belongs in configuration.

    3. application.properties: What It Is and Why That Name

    Spring Boot provides a special config file: application.properties, which holds application configuration in one central place. Instead of writing values inside Java code, we write them here, for example:

    • spring.application.name=student-management-app
    • server.port=8081
    • app.welcome.message=Welcome to Student Management App

    Why is it named application.properties? Because Spring Boot automatically looks for that exact file name at startup. If the file exists, Spring Boot loads its values. application is the fixed default name; .properties is the format.

    Interviewer's perspective: The file is auto-detected by name, not registered anywhere; this is Boot's convention-over-configuration in action.

    4. Basic Key-Value Format and Reading Values With @Value

    The format of a properties file is simple: key=value.

    Line Key Value
    server.port=8081 server.port 8081
    spring.application.name=student-management-app spring.application.name student-management-app
    app.owner=Coder Army app.owner Coder Army

    Spring's @Value annotation injects configuration values into Java variables. Given app.welcome.message=Welcome to Student Management App, a WelcomeController uses @Value("${app.welcome.message}") private String welcomeMessage; and returns it from a @GetMapping("/welcome") method. This is called property injection.

    5. Limitations of application.properties

    For small projects application.properties is readable, but as the project grows it becomes large and repetitive. The lecture lists three limitations.

    5.1 Flat structure. application.properties stores values in a flat key-value format. Example keys: app.name, app.version, app.owner, app.support.email, app.support.phone. The values are related, but the file shows no hierarchy.

    5.2 Repeated prefixes. For grouped configuration, prefixes repeat again and again:

    • notification.email.enabled=true
    • notification.email.subject=Welcome
    • notification.email.from=no-reply@studentapp.com
    • notification.email.retry.count=3
    • notification.sms.enabled=false
    • notification.sms.provider=twilio
    • notification.sms.retry.count=2

    5.3 Lists are not very clean. A list becomes one comma-joined string, for example app.supported-cities=Delhi,Mumbai,Bangalore,Pune. Fine for a small list, but bigger lists or nested objects become difficult to read.

    Important: application.properties is not wrong. The problem is that a flat format stops expressing hierarchy once configuration grows.

    6. Introduction to YAML

    YAML solves the readability problem of large configuration files. The same data has a natural hierarchy:

    • app
    • name
    • version
    • owner
    • support
      • email
      • phone

    YAML writes this in a structured way: .properties is flat key-value, .yml is structured and nested. YAML converts flat configuration into structured configuration without changing the values.

    7. How Spring Boot Understands YAML

    YAML looks nested, but internally Spring Boot understands it as normal property keys. Given server: then port: 8081, Spring Boot sees server.port=8081. Given spring:, application:, name: student-management-app, it sees spring.application.name=student-management-app.

    So YAML is not a different configuration system; it is a cleaner way to write the same configuration. Under the hood Spring Boot reads YAML using the snakeyaml library and flattens it to the same key-value model that properties files use.

    Spring Boot supports application.properties, application.yml and application.yaml. For a project, stick to one format: keeping both .properties and .yml for the same purpose can create confusion about which value is used.

    8. application.properties vs application.yml

    Aspect application.properties application.yml
    Format Flat key-value Structured, nested
    Hierarchy Hidden in dotted keys Visually obvious via indentation
    Repeated prefixes Repeated on every line Written once as a parent key
    Lists Comma-joined string Proper list with - items
    Nested objects Hard to read Readable blocks
    Strictness Forgiving spacing Indentation-sensitive
    Best for Small, simple configuration Large, grouped, nested configuration

    Reading the table: both formats produce the same property keys; YAML just shows the shape of the data. Use one format per project to avoid ambiguity.

    9. YAML Syntax and Indentation Rules

    YAML is strict about indentation. In .properties: server.port=8081. In YAML: server: then port: 8081 indented underneath: server is the parent, port the child, and the spaces show port belongs inside server.

    The lecture gives seven rules.

    Rule Statement Good Bad
    1 Every key is followed by a colon app:, name: Student Management App name Student Management App
    2 Put a space after the colon key: value key:value
    3 Indentation defines relationship app:, indented support:, deeper email: ... flattened, unindented keys
    4 Use spaces, not tabs two spaces per level tab characters
    5 Same-level keys share indentation name, version, owner aligned mixed indentation
    6 Comments use # # Server configuration other comment markers
    7 Strings may be quoted or not name: Student Management App no restriction

    Rule 3 in words: nested app then support then email: support@studentapp.com means app.support.email=support@studentapp.com. Flatten the indentation and the hierarchy is destroyed. YAML uses spaces, not dots, to show structure. Rule 7 adds that quotes help when a value contains special characters, placeholders or symbols.

    Golden rule: In YAML, indentation is structure. Two spaces are conventional, tabs are forbidden, and sibling keys must line up exactly.

    10. Converting application.properties to application.yml

    The conversion is mechanical. Every dot becomes a level of nesting. Consider these properties:

    • server.port=8081
    • spring.application.name=student-management-app
    • app.name=Student Management App
    • app.version=1.0
    • app.owner=Coder Army
    • app.welcome.message=Welcome to Student Management App
    • app.support.email=support@studentapp.com
    • app.support.phone=9999999999

    The equivalent application.yml:

    server:
  port: 8081
spring:
  application:
    name: student-management-app
app:
  name: Student Management App
  version: 1.0
  owner: Coder Army
  welcome:
    message: Welcome to Student Management App
  support:
    email: support@studentapp.com
    phone: 9999999999

    Notice app is written once instead of five times and support groups its children; that reduction is why YAML is preferred for larger configuration.

    11. Real-World Configuration: Database and JPA

    Database configuration is the classic grouped example. In application.properties:

    • spring.datasource.url=jdbc:mysql://localhost:3306/student_db
    • spring.datasource.username=root
    • spring.datasource.password=root

    In application.yml the same values become spring: then datasource: then url, username and password underneath, so all database configuration groups under spring.datasource.

    JPA follows the same pattern. In application.properties:

    • spring.jpa.hibernate.ddl-auto=update
    • spring.jpa.show-sql=true

    In application.yml this becomes spring: then jpa: then hibernate: then ddl-auto: update, with show-sql: true under jpa, grouping related values together.

    Important: Grouping is the whole benefit. spring.datasource and spring.jpa show at a glance which values belong to which subsystem.

    12. Lists and Lists of Objects in YAML

    Suppose one key has multiple values: supported cities Delhi, Mumbai, Bangalore and Pune. In .properties this is one long string, app.supported-cities=Delhi,Mumbai,Bangalore,Pune. In YAML we write a proper list using the - symbol, where each - represents one item.

    The - marker means the parent holds an ordered collection, so YAML can also represent a list of objects: app: then team-members:, with - name: Rohit plus role: Backend Mentor, - name: Mohit with role: DSA Mentor, and - name: Aditya with role: Spring Mentor.

    Shape .properties YAML
    List of scalars app.supported-cities=Delhi,Mumbai,Bangalore,Pune supported-cities: with - Delhi, - Mumbai lines
    List of objects painful and repetitive - name: Rohit with an indented role: line

    For complex nested configuration, Spring Boot also provides @ConfigurationProperties, which is better when binding multiple related values, lists, or nested objects into a Java class.

    13. Reading YAML Values: Dot Notation and Lists

    Even though YAML is nested, we read values using dot notation. Given app: then name: Student Management App, Spring treats it like app.name=Student Management App, so Java reads it with @Value("${app.name}") private String appName;.

    Way 1: individual list items. @Value("${app.supported-cities[0]}") private String firstCity; reads Delhi, showing YAML lists are index-based.

    Way 2: comma-separated value as a list. Given app.supported-cities=Delhi,Mumbai,Bangalore,Pune, @Value("#{'${app.supported-cities}'.split(',')}") private List<String> supportedCities; converts the string into a Java List<String>.

    14. Why Profiles Are Needed

    We already moved values into application.properties or application.yml. The next real-world problem is: the same application needs different values in different environments.

    Spring Boot lets the same code read from properties files, YAML files, environment variables and command-line arguments. In real projects the app runs in development, testing, staging and production. The Java logic (create, fetch, update, delete student, validate request, handle exception, connect to database) stays the same, but values change. Example: local uses jdbc:mysql://localhost:3306/student_db, production uses jdbc:mysql://prod-db-server:3306/student_db. Same logic; different database location.

    Example without profiles. Local config might be server.port: 8080 with a spring.datasource at localhost root/root; production needs url: jdbc:mysql://prod-server:3306/student_db with prod_user/prod_password. The bad approach is to comment local config, uncomment production, run, then reverse it. This is risky: one wrong uncommented line can connect your local application to the production database. So we need a clean way to separate environment-specific configuration.

    15. Spring Profiles: Creating Profile-Specific Files

    A profile is a named environment or mode (dev, test, staging, prod). It answers: which environment configuration should Spring Boot use right now? If dev is active, use development config; if prod is active, use production config. We just tell Spring Boot "run with the prod profile" and it loads the matching configuration.

    Spring Boot supports profile-specific configuration files using this naming pattern: application-{profile}.properties. Examples:

    • application-dev.properties
    • application-test.properties
    • application-prod.properties

    Project structure:

    • src/main/resources
    • application.properties
    • application-dev.properties
    • application-test.properties
    • application-prod.properties

    Meaning of each file:

    File Purpose
    application.properties Common/default file; values common to all environments
    application-dev.properties Development; e.g. server.port=8081, DEV message
    application-test.properties Testing; e.g. server.port=8082, TEST message
    application-prod.properties Production; e.g. server.port=8080, PROD message

    The same concept works with YAML: use application-dev.yml / application-prod.yml (or the .yaml extension). A YAML project has application.yml, application-dev.yml, application-test.yml and application-prod.yml. The common application.yml sets spring.application.name: student-management-app for all profiles. Each profile file sets its own server.port, app.message and datasource: dev uses student_dev, test uses student_test with test_user/test_password, prod uses jdbc:mysql://prod-server:3306/student_prod with prod_user/prod_password. A DemoController reads app.message with @Value, so the same endpoint prints the DEV or PROD text depending on the active profile.

    16. Common File Plus Profile-Specific File: Precedence

    Spring Boot does not ignore the common file. With the dev profile active it loads application.properties plus application-dev.properties. The common file gives shared values (spring.application.name, server.port); the profile file gives environment-specific values (app.message).

    When the same key exists in both, the profile file wins. Given server.port=8080 and app.message=Common message in the common file, and server.port=8081 plus app.message=DEV message in application-dev.properties, the final values under dev are server.port=8081 and app.message=DEV message.

    Scenario Result
    Key only in common file Common value is used
    Key only in profile file Profile value is used
    Key in both files Profile-specific value overrides the common value

    Important: Profile-specific configuration overrides common configuration: the common file gives defaults, the profile file overrides them.

    17. Activating a Profile

    Creating profile-specific files is not enough; you must tell Spring Boot which profile is active. There are several ways.

    Method How Example
    Inside properties/YAML set the active profile key spring.profiles.active=dev
    Command line pass an argument to the JAR java -jar app.jar --spring.profiles.active=prod
    Maven pass a run property mvn spring-boot:run -Dspring-boot.run.profiles=dev
    Environment variable set an OS variable SPRING_PROFILES_ACTIVE=dev

    Using application.properties. Write spring.profiles.active=dev; on startup Spring Boot sees it and loads the dev-specific configuration.

    From the command line. Run the built JAR with java -jar student-management-app.jar --spring.profiles.active=dev (or =prod). The same JAR behaves as dev or prod purely by argument: code is same, build is same, environment decides.

    While running with Maven. During development, mvn spring-boot:run -Dspring-boot.run.profiles=dev starts with the dev profile active.

    Using environment variables. The variable name is SPRING_PROFILES_ACTIVE. On macOS/Linux: export SPRING_PROFILES_ACTIVE=dev then java -jar app.jar; on Windows PowerShell: $env:SPRING_PROFILES_ACTIVE="dev".

    Why env vars? In production, values come from the platform (Docker, Kubernetes, cloud, CI/CD, server config). Instead of shipping spring.profiles.active: prod inside the project, production sets SPRING_PROFILES_ACTIVE=prod, which is cleaner and safer.

    Interviewer's perspective: Avoid hardcoding the prod profile inside the packaged application. The same JAR should run in any environment, so pass the active profile from outside: command line, environment variable, Docker, Kubernetes, or CI/CD.

    A mnemonic for the four activation routes is C-P-M-E: Config file, Parameters (command line), Maven, Environment variable.

    18. @Profile Annotation and Conditional Beans

    Till now profiles changed values: each environment had its own port, message and database. Sometimes we want more: different Spring beans or classes created based on the active profile.

    Suppose we have a notification feature. In development we do not send real emails; in production we do. So we create two implementations of the same interface:

    public interface NotificationService {
    void sendNotification(String message);
}

@Service
@Profile("dev")
public class DevNotificationService implements NotificationService {
    @Override
    public void sendNotification(String message) {
        System.out.println("DEV MODE: Notification not actually sent. Message: " + message);
    }
}

@Service
@Profile("prod")
public class ProdNotificationService implements NotificationService {
    @Override
    public void sendNotification(String message) {
        System.out.println("PROD MODE: Real notification sent. Message: " + message);
    }
}

    The problem @Profile solves: if both classes are only marked @Service, Spring creates both beans, and injecting @Autowired private NotificationService notificationService; becomes ambiguous (which bean should be injected?). That can cause an error because multiple beans of the same type are available. We need to create DevNotificationService only when dev is active and ProdNotificationService only when prod is active. That is exactly what @Profile does.

    The syntax is @Profile("dev"): create this bean only when dev is active. Under dev only DevNotificationService is created; under prod only ProdNotificationService. In short: @Service creates the object, @Profile gates it on the active environment.

    A complete demo has the interface NotificationService, a DevNotificationService (@Service @Profile("dev")), a ProdNotificationService (@Service @Profile("prod")), and a NotificationController mapped to /api/notification that injects NotificationService and calls sendNotification("Welcome to the application"). The controller never changes; only the injected implementation changes.

    Important: @Profile changes which beans exist, not which values they read. @Service creates the object; @Profile gates the creation on the active environment.

    19. Profile-Specific Files vs @Profile (Quick Comparison)

    This distinction is very important and is a common source of confusion.

    Use profile-specific files when the class or logic stays the same but configuration values change. Examples: server port, database URL, username, password, logging level, custom messages, feature flags, JPA show-sql, third-party API URLs. Here application-dev.yml might set server.port: 8081, while application-prod.yml sets server.port: 8080; the Java class does not change. Use files when you need different configuration values.

    Use @Profile when environments need different implementations. Examples: DevEmailService vs ProdEmailService, DummyPaymentService vs RealPaymentService, LocalStorageService vs CloudStorageService, FakeNotificationService vs RealNotificationService. The implementation itself differs. Use @Profile when you need different beans/classes.

    Topic Use case Example
    application.properties Simple key-value configuration server.port=8081
    application.yml Structured and nested configuration spring.datasource.url grouped under spring.datasource
    Profile-specific files Different values for different environments application-dev.yml, application-prod.yml
    spring.profiles.active Tells Spring Boot which profile to use dev, test, prod
    Command-line profile Run same JAR with different profiles --spring.profiles.active=prod
    Environment variable profile Activate from OS/server/deployment platform SPRING_PROFILES_ACTIVE=prod
    @Value Read a single configuration value @Value("${app.message}")
    @Profile Create bean only for a specific profile @Profile("dev")

    Golden rule: profile files change values, @Profile changes beans. If only a number or string moves, use a file; if the whole class changes, use @Profile.

    20. Myth vs Reality

    Myth Reality
    "Hardcoding is fine for small apps" It breaks when the URL changes or a secret leaks; move values to configuration
    "application.properties and application.yml are different systems" YAML is flattened to the same property keys; same system, cleaner syntax
    "Keeping both .properties and .yml is harmless" It creates confusion about which value is used; pick one format
    "Tabs and spaces are interchangeable in YAML" Tabs are forbidden; indentation defines structure and must use spaces
    "Spring Boot ignores the common file when a profile is active" It loads common plus profile-specific; the profile value wins on conflicts
    "Creating profile files is enough" You must also activate a profile; files alone do nothing
    "You should hardcode prod in the JAR" Pass the active profile from outside so the same JAR runs anywhere
    "Profiles and @Profile do the same thing" Profiles change values; @Profile changes which beans are created

    21. Common Trap Questions

    Trap 1 - "Profiles and @Profile are the same concept." Verdict: False. Profile-specific files change configuration values for an environment; @Profile conditions bean creation. Values vs beans.

    Trap 2 - "The common file is overridden and ignored." Verdict: False. Spring Boot loads the common file plus the active profile's file together. Only the same keys are overridden, and the profile-specific value wins.

    Trap 3 - "YAML is a completely different configuration system." Verdict: Misleading. Spring Boot flattens YAML to the same property keys via snakeyaml, so @Value("${app.name}") works the same.

    Trap 4 - "Tabs are acceptable in YAML if the file looks aligned." Verdict: False. YAML is indentation-sensitive; use spaces (usually two) and never tabs.

    Trap 5 - "Creating application-dev.properties activates dev automatically." Verdict: False. Files do not activate anything; you must set spring.profiles.active, use --spring.profiles.active, a Maven property, or SPRING_PROFILES_ACTIVE.

    Trap 6 - "Hardcoding the prod profile in application.yml is production-ready." Verdict: False. The same JAR should run in any environment, so pass the active profile from outside the packaged application.

    Trap 7 - "More @Value annotations are always better." Verdict: False. For complex nested configuration, lists, or grouped values, prefer @ConfigurationProperties.

    22. Points to Remember

    1. Application = Code + Configuration; configuration values change without changing Java code.
    2. Hardcoding causes difficult changes, environment lock-in, and leaked secrets.
    3. Spring Boot auto-detects application.properties by name at startup.
    4. Format is key=value; @Value("${key}") injects a single value.
    5. .properties is flat and repetitive; .yml is nested and readable.
    6. YAML indentation defines hierarchy: spaces only, two-space convention, no tabs.
    7. @ConfigurationProperties is preferred over many @Value calls for nested or list config.
    8. A profile is a named environment (dev, test, staging, prod); files follow application-{profile}.properties.
    9. Spring Boot loads the common file plus the active profile file; the profile value overrides on conflicts.
    10. @Profile creates beans only for a matching profile; profile files change values, @Profile changes beans.

    23. Likely Interview Questions

    Question Crisp Answer
    Why do we need configuration at all? Code holds business logic; configuration holds changeable values (port, DB URL, credentials, messages) so code stays stable.
    What is application.properties and why that name? The central config file Spring Boot auto-loads at startup by its fixed name; .properties is the format.
    How do you read a config value in Spring Boot? With @Value("${key}") for single values, or @ConfigurationProperties for grouped/nested values.
    What are the limitations of .properties? Flat structure, repeated prefixes, and awkward lists/nested objects as configuration grows.
    What is YAML and how does Spring Boot understand it? A structured config format; Spring Boot reads it (snakeyaml) and flattens it to the same property keys.
    Name key YAML indentation rules. Colon after each key, space after colon, indentation defines hierarchy, spaces not tabs, sibling keys aligned, # comments.
    Why do we need profiles? One application must run with different values across dev, test, staging, and prod without code changes.
    What is the naming pattern for profile files? application-{profile}.properties or application-{profile}.yml, e.g. application-dev.yml.
    What happens when the same key exists in common and profile files? The profile-specific value overrides the common value; other common keys remain.
    How do you activate a profile? Set spring.profiles.active, use --spring.profiles.active, -Dspring-boot.run.profiles with Maven, or SPRING_PROFILES_ACTIVE.
    What does @Profile do? Creates a bean only when the named profile is active, avoiding multiple-bean ambiguity for the same interface.
    Profile files vs @Profile? Profile files change values; @Profile selects different bean implementations per environment.

@Profile: create different beans per environment
    • Code stays the same; configuration changes per environment.
    • application.properties is flat; application.yml shows the same data as a hierarchy.
    • YAML is strict: spaces, not tabs; indentation is structure.
    • Profiles choose the environment; profile-specific values override common values.
    • @Profile selects beans/classes; profile files select values.

    One-line takeaway: put changeable values in configuration, express them readably in YAML, and use profiles plus @Profile so one build and one JAR behave correctly in dev, test, staging, and prod.
