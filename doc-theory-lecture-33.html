    Lecture 33 — Spring Transactions

    17 sections · 3,722 words

    Lecture 33

    Scope evidence: "Spring Transactions | ACID, @Transactional, Commit & Rollback" (playlist map, verified). Repo lecture folder contains the transactionDemo project: Account and TransferRecord entities, a TransferService with an @Transactional transfer method, repositories (AccountRepository, TransferRepository), controllers (AccountController, TransferController) and application.properties.

    A bank transfer looks like one action to the user but touches the database as several separate SQL statements. If the debit succeeds and the credit fails, money quietly disappears unless the whole thing is treated as one indivisible unit of work. This lecture builds that idea: what a database transaction is, what ACID guarantees, how begin/commit/rollback work, how JDBC, JPA, Hibernate and Spring layer over the same transaction, and how @Transactional marks a declarative boundary.

    1. What Is a Database Transaction?

    A database transaction is a group of database operations that the database treats as one logical unit of work. Consider a bank transfer. The initial state is:

    Account A = Rs. 10,000
Account B = Rs. 5,000

    To transfer Rs. 1,000 from Account A to Account B, the application executes two updates:

    UPDATE account SET balance = 9000 WHERE id = 1;
UPDATE account SET balance = 6000 WHERE id = 2;

    Technically these are two separate SQL statements. From the business perspective they represent one operation: transfer Rs. 1,000 from Account A to Account B. The complete operation should move the database from one valid state to another:

    Before:  Account A = Rs. 10,000   Account B = Rs. 5,000   Total = Rs. 15,000
After:   Account A = Rs.  9,000   Account B = Rs. 6,000   Total = Rs. 15,000

    Important: A transaction is not defined by the number of SQL statements. It is defined by the business operation whose steps must succeed or fail together. A transaction is a unit of work that must be completed fully or not applied at all.

    2. ACID Properties: The Four Guarantees

    ACID describes the guarantees required for reliable transaction processing:

    Letter Property One-line meaning
    A Atomicity All operations succeed together or are all discarded together.
    C Consistency The database moves from one valid state to another valid state.
    I Isolation Concurrent transactions do not corrupt each other's work.
    D Durability A committed transaction survives later failures.

    Mnemonic for ACID: "All Changes In Database" -- All-or-nothing (Atomicity), Consistent state (Consistency), Isolated from others (Isolation), Durable after commit (Durability).

    These are not unrelated definitions: together they describe whether a database can safely execute a business operation despite failures and concurrency. Each is examined below through the same money-transfer example.

    3. Atomicity, Consistency, Isolation, Durability

    3.1 Atomicity

    Atomicity means that all operations inside a transaction succeed together or all of them are discarded together. In the transfer example the atomic unit is a debit of Account A and a credit of Account B. Both operations must succeed. If Account A is debited but Account B cannot be credited, the debit must also be rolled back. Both balances change, or neither balance changes.

    Important: Without atomicity, a failure between the two updates could cause money to disappear. Atomicity is what makes "all or nothing" true for a multi-step business operation.

    3.2 Consistency

    Consistency means that a transaction should move the database from one valid state to another valid state. Suppose the business rule is that an account balance cannot be negative. The current balance is Account A = Rs. 500, and the application attempts to transfer Rs. 1,000. If the operation leaves the account at Rs. -500, the business rule has been violated and the database is now in an invalid state.

    Consistency depends on correctly defined rules and their enforcement through application logic, database constraints, or both. A transaction does not invent these rules; it ensures that the committed result does not contain only part of the intended operation. In the transfer example, consistency can include rules such as:

    • account balances must remain valid;
    • the total amount of money must not change because of an internal transfer;
    • the sender and the receiver must both exist.

    3.3 Isolation

    Isolation deals with transactions executing concurrently. Suppose Account A contains Rs. 10,000 and two transactions run at approximately the same time: T1 withdraws Rs. 1,000 and T2 withdraws Rs. 8,000. Without sufficient isolation both may read the same initial balance of Rs. 10,000, then write different values: T1 writes Rs. 9,000 and T2 writes Rs. 2,000. Depending on the order, one update may overwrite the other and the final balance may not reflect both withdrawals correctly.

    Isolation answers one question: what is one transaction allowed to observe while another transaction is still executing? It does not necessarily mean that only one transaction can execute at a time. Databases allow concurrency, but they control how concurrent operations interact.

    3.4 Durability

    Durability means that once a transaction has committed successfully, its changes should survive later failures. Suppose the database confirms "transfer completed successfully", then the application crashes, the server loses power, and the database restarts. After recovery the committed transfer should still exist. Commit is a promise that the database has accepted the transaction as a permanent result.

    4. ACID as One Combined Guarantee

    The four ACID properties are not unrelated definitions. Together, they describe whether a database can safely execute a business operation despite failures and concurrency. For the bank transfer:

    Property Guarantee
    Atomicity Both balances change, or neither changes.
    Consistency Money is not created or destroyed, and all business rules remain valid.
    Isolation Concurrent operations do not corrupt the transfer.
    Durability Once committed, the transfer survives subsequent failures.

    Together, ACID answers one central question: can the database safely move from one valid state to another despite failures and concurrent activity?

    Golden rule: Atomicity controls the grouping of the statements, Consistency controls the meaning of the resulting state, Isolation controls the interaction between concurrent transactions, and Durability controls the fate of the result after a crash. No single property is sufficient on its own.

    5. Transaction Boundary

    A transaction boundary defines where a transaction begins and where it ends. In Spring, a service method can represent the boundary of a business transaction:

    @Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    debitAccount(fromId, amount);   // UPDATE account ...
    creditAccount(toId, amount);    // UPDATE account ...
    recordTransfer(fromId, toId, amount);
}

    Conceptually, the successful execution is:

    Begin transaction -> Debit sender -> Credit receiver -> Record transfer -> Commit transaction

    If an eligible failure occurs before successful completion:

    Begin transaction -> Perform database operations -> Exception -> Rollback transaction

    The transaction normally begins before the annotated method executes. It commits after the method completes successfully, or rolls back when a qualifying exception leaves the method.

    Interviewer's perspective: The boundary is a business decision, not a technical accident. If two repository calls belong to one use case, they belong inside one service method and therefore inside one transaction. Splitting the boundary wrongly is how partial writes become possible.

    6. Begin, Commit and Rollback

    Every transaction has the same three-part lifecycle.

    • Begin -- start the transaction. At the JDBC level this is connection.setAutoCommit(false);, which corresponds to starting a database transaction. With autocommit disabled, individual SQL statements are not committed automatically; the application must explicitly commit or roll back.
    • Commit -- accept the transaction's changes as its final result via connection.commit();. After a successful commit the changes become durable according to the guarantees of the database.
    • Rollback -- discard the changes made by the current uncommitted transaction via connection.rollback();.

    Important: Rollback does not mean manually executing another UPDATE statement to restore every previous value. The database maintains the information required to undo or discard the uncommitted work. That is why rollback is cheap to express and safe to rely on.

    7. Transaction Layers: JDBC, JPA, Hibernate and Spring

    JDBC, JPA, Hibernate and Spring are often presented as four different transaction systems. In a Spring application they are different APIs and abstraction layers coordinating the same underlying database transaction:

    Service Method
    |
    v
Spring Transaction Management
    |
    v
JPA EntityManager / Hibernate Session
    |
    v
JDBC Connection
    |
    v
Database Transaction

    Each layer exposes its own API for the same destination:

    Layer API used What it hides Who commits/rolls back
    JDBC Connection, setAutoCommit, commit, rollback Raw low-level control The developer, manually
    JPA EntityTransaction (begin, commit, rollback) Direct JDBC connection handling The application (still boilerplate)
    Hibernate Session and its Transaction (beginTransaction, commit) JPA operations and JDBC The application (native API)
    Spring @Transactional All of the above boilerplate Spring, on the method's behalf

    The lower layers still exist and still contain boilerplate: JDBC needs the connection opened, autocommit disabled, commit on success, rollback on failure and safe closing; JPA hides JDBC but keeps its own manual boilerplate; Hibernate exposes its native session.beginTransaction(). As the JPA provider, Hibernate ultimately implements the JPA operations and drives JDBC and the database.

    Spring removes that boilerplate from business methods. The method contains only business logic, and Spring handles the surrounding workflow:

    Open or obtain required resources
    |
    v
Begin transaction
    |
    v
Execute business method
    |
    v
Commit on success
    |
    v
Roll back on eligible failure
    |
    v
Release resources

    Important: Spring does not replace the database transaction. It manages the lower-level transaction API on behalf of the application. All four layers ultimately drive one database transaction.

    8. Spring's @Transactional

    In a Spring Boot application the commonly used annotation is org.springframework.transaction.annotation.Transactional. It tells Spring that the method or class should execute within a Spring-managed transaction.

    • Method-level -- annotate a specific method when only selected operations require transaction management. The transaction applies to that method.
    • Class-level -- annotate the class when all relevant public methods should use transactional behavior. The class-level annotation provides a default transactional configuration that a method-level annotation can refine.
    Aspect Method-level Class-level
    Where it is written On one method On the class
    Scope Only that method All public methods by default
    Typical use One transaction-sensitive operation A whole transactional service
    Override -- A method-level annotation refines it

    @Transactional also carries behavioral hints such as readOnly. Marking a method readOnly tells Spring and the provider that the unit of work does not modify data, which lets the provider skip dirty-checking work and may help the database optimize the transaction.

    @Transactional(readOnly = true)
public Account getAccount(Long id) {
    return accountRepository.findById(id).orElseThrow();
}

    Interviewer's perspective: readOnly is a hint about intent, not a security fence. It is most useful on query methods and should not be used to "protect" a method that actually writes.

    Transaction boundaries are generally placed in the service layer because a service method represents a complete business use case and may coordinate multiple repository operations. In the transactionDemo project, TransferService owns the @Transactional transfer method, uses AccountRepository to move money, and TransferRepository to record the TransferRecord.

    9. Rollback Rules: Runtime vs Checked Exceptions

    @Transactional does not roll back for every possible failure. By default it rolls back only for unchecked failures -- RuntimeException and Error -- while checked exceptions do not trigger a rollback unless you ask for one.

    Exception type Example Default behavior How to change it
    RuntimeException (unchecked) IllegalArgumentException, custom business exception Roll back noRollbackFor to exclude
    Error OutOfMemoryError, AssertionError Roll back noRollbackFor to exclude
    Checked exception IOException, custom checked exception Commit (no rollback) rollbackFor to include

    The three controls an interviewer expects:

    • rollbackFor -- also roll back for the listed exception types (commonly used to include a checked exception).
    • noRollbackFor -- do not roll back for the listed exception types, even though they would normally qualify.
    • Default -- RuntimeException and Error roll back; checked exceptions do not.
    @Transactional(rollbackFor = InsufficientFundsException.class)  // checked -> now rolls back
public void transfer(Long fromId, Long toId, BigDecimal amount)
        throws InsufficientFundsException {
    debit(fromId, amount);
    credit(toId, amount);
    recordTransfer(fromId, toId, amount);
}

@Transactional(noRollbackFor = AuditWriteException.class)        // logged, still commits
public void transferAudited(Long fromId, Long toId, BigDecimal amount) {
    debit(fromId, amount);
    credit(toId, amount);
}

    Important: The rollback decision is made by Spring's transaction interceptor using the exception that leaves the method. If your checked exception should undo the work, you must say so with rollbackFor -- the default will not do it for you.

    10. Proxy Interception and the Self-Invocation Problem

    @Transactional is declarative: Spring applies it through a proxy that wraps the bean and intercepts calls into transactional methods. The proxy opens the transaction before the method runs and commits or rolls it back after the method returns or throws.

    A direct consequence: the annotation only takes effect when the call passes through the proxy. When one method of the bean calls another method of the same bean, the call never leaves the object, so the proxy is skipped.

    @Service
public class TransferService {

    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        this.debit(fromId, amount);    // BUG: self-invocation, proxy skipped
        this.credit(toId, amount);     // @Transactional on debit() never fires
    }

    @Transactional
    public void debit(Long id, BigDecimal amount) {
        // runs with NO transaction because it was called internally
    }
}

    The fix is to keep the transactional method as the entry point external callers invoke, or to split it into a separate bean so the call crosses a proxy boundary.

    Important: The method must be called through the proxy. A transactional annotation on a method that is only ever invoked internally by the same bean is silently ignored -- no exception, no warning, just the missing transaction.

    11. Complete Mental Model

    When Spring executes a transactional service method, the process can be understood as follows:

    Caller invokes service method
    |
    v
Spring starts or joins a transaction
    |
    v
Repository operations use resources participating in that transaction
    |
    v
Method completes successfully -> Commit
        or
Method fails with a rollback-eligible exception -> Rollback

    The key idea is: @Transactional defines the boundary of a business operation, while Spring coordinates the underlying persistence and database transaction APIs needed to execute it safely. A full worked transfer reads like this:

    @Service
public class TransferService {

    private final AccountRepository accountRepository;
    private final TransferRepository transferRepository;

    public TransferService(AccountRepository accountRepository,
                           TransferRepository transferRepository) {
        this.accountRepository = accountRepository;
        this.transferRepository = transferRepository;
    }

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        debit(fromId, amount);          // UPDATE account SET balance = ...
        credit(toId, amount);           // UPDATE account SET balance = ...
        transferRepository.save(        // INSERT INTO transfer_record ...
                new TransferRecord(fromId, toId, amount));

        // success -> Spring commits after this method returns
        // failure -> Spring rolls back when RuntimeException/Error leaves
    }

    private void debit(Long id, BigDecimal amount) { /* ... */ }
    private void credit(Long id, BigDecimal amount) { /* ... */ }
}

    The debit, the credit and the transfer record all participate in one transaction. Either all three are committed together, or none of them are.

    12. Myth vs Reality

    Myth Reality
    "A transaction means a single SQL statement." A transaction can wrap many statements; it is defined by the business operation, not the statement count.
    "ACID is four separate features you enable one by one." ACID is one combined guarantee about surviving failures and concurrency.
    "Rollback means running reverse UPDATE statements." The database keeps undo information for uncommitted work; rollback discards it, it does not rewrite rows.
    "JDBC, JPA, Hibernate and Spring have separate transactions." They are different APIs over the same underlying database transaction.
    "@Transactional rolls back for any exception." By default only RuntimeException and Error roll back; checked exceptions commit unless rollbackFor is set.
    "Spring replaces the database's transaction." Spring manages the lower-level transaction API; the actual transaction is the database's.
    "Adding @Transactional to a private method makes it transactional." Interception is proxy-based; self-invocation and non-public entry points bypass the proxy.

    13. Common Trap Questions

    Trap 1 - "Two UPDATE statements are automatically one transaction." Verdict: False. Two separate SQL statements are two separate units unless a transaction boundary groups them. The bank transfer is one logical unit of work, not two.

    Trap 2 - "Rollback undoes work by running the opposite SQL." Verdict: False. Rollback discards the current uncommitted transaction; the database maintains the information required to undo the work.

    Trap 3 - "ACID means only one transaction can run at a time." Verdict: False. Isolation controls how concurrent transactions interact; it does not force serial execution.

    Trap 4 - "@Transactional rolls back on a checked exception by default." Verdict: False. By default RuntimeException and Error roll back; a checked exception commits unless rollbackFor includes it.

    Trap 5 - "Putting @Transactional on a method always starts a transaction when it runs." Verdict: False. The call must pass through Spring's proxy. Self-invocation from the same bean silently skips the transaction.

    Trap 6 - "Spring transactions are a different transaction than the database's." Verdict: False. Spring coordinates JDBC/JPA/Hibernate, which all drive the same database transaction.

    Trap 7 - "Once committed, a change can still be lost on a crash." Verdict: False. Durability guarantees that a successfully committed transaction survives later failures -- that is the promise commit makes.

    14. Points to Remember

    1. A database transaction is a group of operations the database treats as one logical unit of work.
    2. A transaction is defined by the business operation, not by the number of SQL statements.
    3. Atomicity: all operations succeed together or are all discarded together.
    4. Consistency: the database moves from one valid state to another, respecting rules and constraints.
    5. Isolation: it controls what one transaction may observe while another is still executing, without forbidding concurrency.
    6. Durability: once committed, changes survive crashes, restarts and power loss.
    7. Lifecycle: begin (setAutoCommit(false)), commit, rollback; rollback discards uncommitted work rather than rewriting rows.
    8. JDBC, JPA and Hibernate expose different transaction APIs over the same underlying database transaction; Spring removes the boilerplate.
    9. @Transactional is declarative and proxy-based; by default it rolls back on RuntimeException and Error, and rollbackFor/noRollbackFor adjust that behavior.
    10. Transaction boundaries belong in the service layer, and the method must be called through the proxy -- self-invocation bypasses it.

    15. Likely Interview Questions

    Question Crisp Answer
    What is a database transaction? A group of operations the database treats as one logical unit of work, completed fully or not applied at all.
    What does ACID stand for? Atomicity, Consistency, Isolation, Durability.
    Explain Atomicity with the transfer example. Debit A and credit B both happen, or both are rolled back -- both balances change or neither does.
    Explain Consistency. The transaction moves the database from one valid state to another, honoring rules such as "balance cannot be negative".
    Explain Isolation. It controls what a transaction may observe while another runs concurrently, preventing lost updates.
    Explain Durability. A committed transaction survives later failures such as crashes or power loss.
    Why are ACID properties described together? Together they answer whether the database can move between valid states safely despite failures and concurrency.
    What is a transaction boundary? The point where a transaction begins and ends; in Spring it is usually a @Transactional service method.
    What do begin, commit and rollback do? Begin starts the transaction; commit accepts changes as final and durable; rollback discards uncommitted changes.
    How do JDBC, JPA, Hibernate and Spring relate? They are different APIs and abstraction layers coordinating the same underlying database transaction.
    Which exceptions trigger rollback by default? RuntimeException and Error; checked exceptions do not unless rollbackFor is specified.
    Why must a @Transactional method be called through the proxy? Spring applies transactions via a proxy; self-invocation never leaves the object, so the proxy and its transaction are skipped.
