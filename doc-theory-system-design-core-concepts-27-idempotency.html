    Idempotency

    6 sections · 505 words

    Doing it twice equals doing it once. Messaging & Async, concept 27 of 36.

    The Idea

    An operation is idempotent if doing it twice has exactly the same effect as doing it once. Networks retry: a client that never gets a response might resend the same request, and if charging a card is not idempotent, that retry charges it a second time for the same order.

    The usual fix is an idempotency key: the client sends a unique ID with the request, and the server remembers which IDs it has already processed. A repeat arrives with the same key, the server recognises it and just returns the original result instead of doing the action again.

    Same key, same result: Client retries with key X -> Server checks has it seen key X before? -> yes -> same result, no re-charge.

    Watch Out For

    • Generating a new idempotency key on every retry defeats the purpose. The key has to represent the logical request, not the individual attempt.
    • Storing processed keys forever is wasteful. Most systems expire them after a reasonable window, like 24 hours, once a retry that late is unlikely.
    • Checking whether a key exists and then processing it as two separate steps leaves a race: two retries arriving nearly together can both pass the check before either has stored the key. The key has to be reserved atomically, in the same step as the check, or both can still slip through and double-charge the card.

    Where You Will See It

    • Stripe's API, which documents idempotency keys explicitly for exactly this payment-retry scenario.
    • Any REST API's PUT method, which is idempotent by definition: setting a value to X twice has the same effect as once.
    • Message queue consumers, which need idempotent processing since most queues guarantee at-least-once delivery, not exactly-once.

    How It Connects

    • Message Queues: at-least-once delivery is common, which makes idempotent consumers a near-default requirement.
    • Circuit Breaker: retries triggered by a circuit breaker reopening need the same idempotency guarantee.
    • Distributed Locks: a different tool for a related problem, preventing concurrent execution instead of tolerating repeated execution.

    Follow-Up Questions

    1. A payment request times out on the client side, but the server actually processed it. The client retries. What happens without idempotency? The card gets charged a second time for the same order.

    2. How does an idempotency key actually prevent the double charge? The server remembers which keys it has already processed, and on a repeat, returns the original result instead of running the charge again.

    3. Is a GET request naturally idempotent? Yes, by design. Reading data repeatedly should never change anything, unlike POST, which often is not idempotent by default.

    4. Where should an idempotency key be generated, client or server? The client, since it needs to send the same key on every retry of the same logical request.

    Recall It As

    Networks retry by nature. Idempotency makes a retry harmless instead of dangerous.
