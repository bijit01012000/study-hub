    Rate Limiting

    11 sections · 679 words

    Capping how many requests a client may send in a window of time.

    1. The Problem

    When a client (r1, r2, r3) can hit the server freely:

    1. A client can send too many requests within a timeframe (DoS/DDoS).
    2. Server cost is expensive - each request is expensive.

    Rate limiting answers the question: how many requests can a client send in any timeframe?

    2. Where to Apply It

    1. Client side - the worst option, because a malicious client can ignore it.
    2. Server side.
    3. Middleware - an API Gateway doing rate limiting between front end and backend.

    Application use cases:

    • Server-side languages (Java, C++, JavaScript, Python).
    • Third-party rate-limiter providers, for example Amazon AWS API Gateway.

    3. What to Limit On

    1. IP address basis.
    2. UserId basis.
    3. Other ways (primary key, candidate key).

    4. Response Codes and Headers

    • 200: OK.
    • 429: Too many requests.

    Example: 2 req/sec on the basis of userId. Excess requests are dropped, often into a message queue.

    Headers can advertise the policy:

    • X-api-limit: 2
    • x-duration: seconds

    5. The Five Algorithms

    1. Token Bucket.
    2. Leaky Bucket.
    3. Fixed Window Counter.
    4. Sliding Window Log.
    5. Sliding Window Counter.

    6. Token Bucket

    Elements: a token builder, the bucket, a request pool, the server, and a drop path. Example settings: bucket size 20, inflow 10 tokens/sec.

    Rules:

    1. The token builder pushes tokens in fixed intervals.
    2. If the bucket is full, new tokens overflow (are overthrown).
    3. Whenever a request comes, it takes a token from the bucket if one is available, then goes to the server.
    4. If the bucket is empty, the request is dropped.

    Used by: Amazon.

    • Pros: simple to implement; can handle burst traffic for a short duration.
    • Cons: deciding the bucket capacity and inflow.

    7. Leaky Bucket (Global Rate Limiting)

    Elements: a bucket that acts as a queue, an outflow, the server, a request pool, and a drop path. Example: 1000 users, IP-level uniqueness; bucket capacity 3, outflow 2 req/sec. Used by Shopify.

    • Pros: simple to implement, and even with burst traffic the server will not crash.
    • Cons: if a DoS/DDoS happens, the server misses valuable requests (the main request can starve).

    Application scope: 100 APIs managed API-wise.

    8. Fixed Window Counter

    In a fixed interval (say a second or a minute), only a specific number of requests may arrive. With a fixed counter of 3, requests 1-3 are allowed and request 4 is rejected.

    • Cons: if burst traffic arrives at the edges of the window, it may lead to a server crash and high latency.

    9. Sliding Window Log Algorithm

    Considered the best algorithm for rate limiting, but strict, slow, and memory consuming. Example: 3 req/sec.

    Algorithm:

    1. It stores each request in a log file.
    2. Whenever a request comes, it first removes all outdated requests from the file.
    3. Then it logs the new request and checks the counter limit: if the limit is reached, the request is dropped; otherwise it goes to the server.

    It relies on epoch timestamps (as on Linux).

    10. Sliding Window Counter Algorithm

    A hybrid approach (for example 7 req/minute) that uses a rolling window weighted 70%/30%.

    Formula:

    No. of req in current interval
  + No. of req in previous interval * 70%

= 4 + 5 * 0.7 = 7.5

    11. Building Our Own Rate Limiter

    Which algorithm to implement? -> Fixed Window Counter.

    • Expected counter 3, current counter 3.
    • Store the counter in a DB? SQL or NoSQL works, but a DB is slow.
    • Better: an in-memory cache such as Redis.

    Components: client -> rate limiter -> workers -> server, with a DB and Redis cache. The limiter uses INCR; when the count exceeds the limit (for example 5) it returns 429 Too many requests and drops the request. Rules are held in the workers/cache. A messaging queue such as Kafka can carry dropped or deferred work.
