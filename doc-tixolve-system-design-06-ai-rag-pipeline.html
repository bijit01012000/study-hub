    AI / RAG Pipeline

    8 sections · 855 words

    Section 6 of 11

    What is RAG?

    Retrieval-Augmented Generation — instead of relying on the LLM's static training data, you retrieve relevant passages from your own document store at query time and inject them into the prompt. The LLM generates an answer grounded in those retrieved passages.

    Why not fine-tuning?

    • Fine-tuning bakes knowledge into model weights — expensive to re-run every time documents change
    • Fine-tuned models still hallucinate
    • Fine-tuning requires GPU training infrastructure
    • RAG is dynamic (documents update immediately), auditable (cite the exact source passage), and cheaper to iterate

    Ingestion Pipeline (knowledge-service)

    PDF Upload via REST
  → S3 (raw storage, durable)
  ← returns job ID immediately
  → Async ingestion job starts
      1. Fetch file from S3
      2. Extract text (Apache PDFBox / Tika)
      3. Chunk text: ~500 tokens per chunk, 50-token overlap
      4. Embed each chunk: Spring AI EmbeddingModel
      5. Store chunk + embedding in pgvector (knowledge_db.chunks)
      6. Store tsvector for full-text search on same row
      7. Update ingestion_jobs status → COMPLETED
  → Write document.ingested to outbox → Kafka

    Why store raw file in S3 before processing? If the chunking job fails, the original file is safe — you can re-trigger ingestion without re-uploading. Storage is decoupled from processing. You can also serve the original document for download without re-constructing it from chunks.

    Why async job instead of synchronous processing? Chunking and embedding a 200-page PDF can take 30–60 seconds. A synchronous HTTP request would timeout. Return immediately with a job ID, let the caller poll /ingestion-jobs/{id} for status. Standard pattern for long-running operations.

    Chunking Parameters — Why These Numbers?

    Parameter Value Reasoning
    Chunk size ~500 tokens Carries a coherent thought; fits comfortably in prompt context. Too small = loss of context; too large = dilutes similarity score, noisy retrieval
    Overlap 50 tokens Prevents answers from falling on chunk boundaries. Without overlap, a sentence split across chunk N and N+1 scores poorly for both. With overlap, the boundary content appears fully in at least one chunk

    Production upgrade: Semantic chunking — split on paragraph or section boundaries instead of fixed token count. Produces more coherent chunks at the cost of variable chunk sizes. Not in MVP but noted as the right direction.

    Retrieval + Chat Pipeline (chat-service)

    User message arrives (POST /conversations/{id}/messages)
  → Load last N conversation turns from chat_db (context window management)
  → Call knowledge-service /search
      returns top-K chunks: {id, content, documentName, sourcePage, score}
  → Build prompt:
      [System]  "Answer only using the provided context below.
                 Cite sources as [1], [2], etc.
                 If the context doesn't contain the answer, say so and suggest
                 creating a support ticket."
      [Context] "[1] {chunk1 content}\n[2] {chunk2 content}\n..."
      [History] last N turns (user + assistant messages)
      [User]    current message
  → Call Spring AI ChatClient.stream()
  → Stream tokens via SSE to browser
  → On completion: persist full assistant message + citation IDs to chat_db
  → Evaluate escalation condition

    Context Window Management

    Conversation history is trimmed to the last N turns (configurable, default 10 turns = 20 messages). This prevents exceeding the LLM's context window as conversations grow long.

    Production upgrade: Summarize older conversation history instead of truncating. Keeps the gist of earlier turns without consuming all context tokens.

    Escalation Logic

    Two independent escalation signals:

    Signal Condition Meaning
    Low retrieval confidence Max cosine similarity of all retrieved chunks < 0.6 The knowledge base has no relevant content — AI is answering blind
    Model signal LLM structured output includes a low-confidence flag The model itself signals it cannot answer reliably

    Either signal triggers: publish chat.escalated to Kafka (via outbox) with conversationId, userId, conversation summary, and suggested priority.

    LLM Provider Abstraction (Spring AI)

    All LLM calls go through Spring AI's ChatClient / ChatModel interfaces — never a hardcoded provider SDK.

    // This code works with Ollama locally and Claude in production
// The provider is selected by Spring profile — zero code change
@Service
public class ChatOrchestrationService {
    private final ChatClient chatClient;  // Spring AI interface

    public Flux<String> streamResponse(String prompt) {
        return chatClient.prompt(prompt).stream().content();
    }
}

    Local dev: --spring.profiles.active=ollama → Ollama in Docker, zero API cost, works offline. Demo/prod: -spring.profiles.active=claude → Claude API.

    Switching providers is a config change. No code changes. No cost surprise during development.

    Citation System (Frontend)

    The signature UX element of the application:

    1. Retrieved chunks are numbered [1], [2], ... in the prompt
    2. The model is instructed to reference them by number in its response
    3. Frontend parses [1], [2] patterns in the streamed response
    4. Renders them as expandable inline citation chips (custom MUI component)
    5. Expanding a chip shows: source document name, page number, and the exact passage used

    Why this matters for the interview: It demonstrates the full RAG loop is closed — not just "AI answers questions" but "AI answers with verifiable, auditable sources." This is what makes RAG trustworthy for enterprise use cases.
