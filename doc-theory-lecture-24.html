    Lecture 24 — Spring AOP Pointcuts & Types of Proxies

    19 sections · 4,307 words

    Lecture 24

    Scope evidence: "Spring AOP Pointcuts & Types of Proxies" (playlist map, verified). Repo folder is the aopDemo project, extended with aspect.ApplicationPointcuts and service.StudentServiceInterface so the JDK-proxy versus CGLIB-proxy behaviour can actually be demonstrated, and it ships a PracticeQuestions.pdf alongside Notes.pdf for extra drilling.

    A pointcut is the address label on an aspect: the advice says what extra behaviour runs, and the pointcut expression says exactly which method executions receive it. This lecture covers the full pointcut vocabulary - execution(), within(), @annotation() and bean(), wildcards, boolean composition, named @Pointcut declarations, and the advanced args()/@args()/this()/target() designators. Then it descends one level into the proxy machinery, where JDK interface proxies and CGLIB subclass proxies decide what those designators can actually see. Getting pointcuts wrong produces silent no-ops or noisy over-logging; getting proxy types wrong produces advice that never fires on self-calls. Master both and Spring AOP stops feeling like magic.

    1. What Is a Pointcut Expression?

    Two ideas sit at the centre of Spring AOP:

    1. Advice - defines what additional behaviour should run: logging, security, auditing, or performance tracking.
    2. Pointcut expression - defines where that advice should run.
    @Before("execution(* getStudent(..))")
public void logBeforeMethod() {
    System.out.println("Method is about to execute");
}

    Reading the three parts:

    • @Before defines when the advice runs.
    • execution(* getStudent(..)) selects the target methods.
    • logBeforeMethod() contains the additional behaviour.

    Important: A pointcut expression does not execute a method. It only decides whether a method execution should be intercepted, so a wrong expression is the usual reason an aspect appears to do nothing.

    The single sentence to carry forward is: a pointcut answers "Which method executions should receive the aspect behaviour?" Everything else in this lecture is a way of answering that question precisely.

    2. The execution() Designator and Its Full Signature

    execution() is the most commonly used pointcut designator in Spring AOP. It selects methods from their signatures, and it can match on:

    • access modifier
    • return type
    • declaring class
    • method name
    • parameters
    • declared exceptions

    The complete syntax is:

    execution(
    modifiers-pattern?          // optional
    return-type-pattern         // required
    declaring-type-pattern?     // optional
    method-name-pattern(parameter-pattern)
    throws-pattern?             // optional
)

    The parts marked with ? are optional. The essential parts are return type + method name + parameters. So the broadest commonly used expression is:

    execution(* *(..))

    where * means any return type, * means any method name, and (..) means zero or more parameters.

    An exact match is painfully specific. Given this service:

    package com.coderarmy.student.service;

public class StudentService {
    public Student getStudent(Long id) {
        return null;
    }
}

    the exact pointcut is:

    execution(public com.coderarmy.student.model.Student com.coderarmy.student.service.StudentService.getStudent(java.lang.Long))
    Part Meaning
    public The method must be public
    com.coderarmy.student.model.Student The return type must be Student
    com.coderarmy.student.service.StudentService The method must belong to StudentService
    getStudent The method name must be getStudent
    java.lang.Long It must accept exactly one Long argument

    This matches only that exact signature. Real applications use broader expressions so that one pointcut can cover multiple related methods.

    3. Wildcards: * and ..

    The meaning of a wildcard depends on where it appears.

    The * wildcard matches anything in one position or one naming segment:

    Requirement Expression
    Any return type execution(* StudentService.getStudent(..))
    Any method name execution(* *(..))
    Method names beginning with get execution(* get*(..))
    Method names ending with Student execution(* *Student(..))
    Method names containing Student execution(* *Student*(..))
    Exactly one parameter of any type execution(* *(*))

    Concrete matches: get* -> getStudent()/getAllStudents()/getStudentById()/getStudentCount(); *Student -> getStudent()/createStudent()/deleteStudent(); *Student* -> getStudent()/getStudentById()/createStudentAccount()/updateStudentDetails(); (*) -> exactly one parameter of any type, and it does not match zero or multiple; (..) -> zero or more parameters of any type.

    The .. wildcard represents zero or more elements, and again it depends on context:

    execution(* *(..))                 // inside a parameter list: zero or more parameters
com.coderarmy.student.service..*   // inside a package pattern: the package and all subpackages

    Inside a parameter list, (..) matches getAllStudents(), getStudent(Long id), search(String name, Integer age, String city), and updateStudent(Long id, Student student) alike.

    Inside a package pattern, com.coderarmy.student.service..* matches:

    • com.coderarmy.student.service.StudentService
    • com.coderarmy.student.service.impl.StudentServiceImpl
    • com.coderarmy.student.service.internal.StudentValidator

    By comparison, com.coderarmy.student.service.* matches only classes placed directly inside service; it does not include service.impl or other subpackages.

    Important: * is one package or type-name segment; .. is zero or more package segments. Swapping .* for ..* is the classic reason a pointcut silently under-matches.

    4. Common execution() Patterns

    Consider a normal service:

    public class StudentService {
    public Student getStudent(Long id) { return null; }
    public List<Student> getAllStudents() { return null; }
    public Student createStudent(Student student) { return null; }
    public Student updateStudent(Long id, Student student) { return null; }
    public void deleteStudent(Long id) { }
}

    Match a method name everywhere:

    execution(* getStudent(..))

    This can match any interceptable method named getStudent, including methods in controllers, services, or other classes. A safer expression pins the declaring class:

    execution(* com.coderarmy.student.service.StudentService.getStudent(..))

    Match every method:

    execution(* *(..))

    This is extremely broad and should normally be restricted by package, class, bean name, or annotation.

    Match public methods:

    execution(public * *(..))

    The modifier is optional. Public methods are the safest and most common targets in proxy-based Spring AOP; private methods cannot be intercepted through normal proxy overriding.

    Match all public methods in the service layer:

    execution(public * com.coderarmy.student.service..*.*(..))
    Part Meaning
    public Public methods only
    first * Any return type
    com.coderarmy.student.service..* Any class in the package or its subpackages
    second * Any method name
    (..) Any number and type of arguments

    Interviewer's perspective: These parameter forms are the sharpest filter in interviews. () is exactly zero, (*) is exactly one, (*, *) is exactly two, (..) is zero-or-more, (Long, ..) fixes only the first parameter, and (.., Student) fixes only the last. Bland answers like "(..) means all parameters" miss the point that the count itself is being matched.

    5. The within() Designator and the Four Core Designators

    execution() focuses on a method signature. within() focuses on the class or package where the method is declared:

    • execution() -> Which method signature should match?
    • within() -> Inside which class or package should methods match?
    within(com.coderarmy.student.service.StudentService)   // exact class
within(com.coderarmy.student.service.*)                // classes directly inside the package
within(com.coderarmy.student.service..*)               // package and all subpackages

    Practical use:

    @Before("within(com.coderarmy.student.service..*)")
public void logServiceMethod() {
    System.out.println("Service method called");
}

    The two designators may produce similar results for a basic service-layer requirement:

    execution(* com.coderarmy.student.service..*.*(..))
within(com.coderarmy.student.service..*)

    The difference is expressive power. execution() can filter by modifier, return type, method name, and parameters. within() only restricts the declaring class or package. They can also be combined:

    within(com.coderarmy.student.service..*)
&& execution(public * get*(..))

    That means: match public methods beginning with get, but only inside the service layer.

    The four designators you will use most often, side by side:

    Designator Matches on Example Scope
    execution() Method signature (modifier, return type, name, params) execution(public * get*(..)) Any matching method execution
    within() Declaring class or package within(com.coderarmy.student.service..*) Every method declared in that region
    @annotation() Annotation on the executing method @annotation(Transactional) Only methods that opt in
    bean() Spring bean name bean(*Service) Every method on matching beans

    Mnemonic: E-W-A-B - Execution (signature), Within (location), Annotation (method opt-in), Bean (name). And remember the one-liner: execution asks WHAT the method looks like; within asks WHERE it lives.

    6. The @annotation() Designator

    @annotation() matches methods that carry a specified annotation. Given:

    @Transactional
public void transferMoney() {
}

    the pointcut is:

    @annotation(org.springframework.transaction.annotation.Transactional)

    It means: match a method execution when the method has the specified annotation. @annotation() is used for method-level annotations; class-level annotation matching is handled by @within() and @target().

    Why annotation-based matching is useful: a package-based pointcut applies behaviour throughout an architectural region, while an annotation-based pointcut applies behaviour only to methods that explicitly opt in. Common use cases include auditing selected operations, measuring execution time, recording sensitive actions, custom authorization, and idempotency protection.

    A custom annotation plus an around advice:

    @Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface TrackExecutionTime {
}

@Around("@annotation(com.coderarmy.aop.TrackExecutionTime)")
public Object measureExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
    long start = System.currentTimeMillis();
    Object result = joinPoint.proceed();
    long end = System.currentTimeMillis();
    System.out.println("Execution time: " + (end - start) + " ms");
    return result;
}

    Golden rule: Package and layer pointcuts buy coverage; annotation pointcuts buy consent. Reach for @annotation() whenever a behaviour should apply only to methods that ask for it, and reserve within() for behaviour that truly belongs to a whole region.

    7. The bean() Designator

    bean() matches methods using the Spring bean name rather than the Java class name. For:

    @Service
public class StudentService {
}

    the default bean name is normally studentService, so the pointcut is:

    bean(studentService)

    In an advice:

    @Before("bean(studentService)")
public void beforeStudentService() {
    System.out.println("Student service method called");
}

    Wildcard matching is supported too:

    bean(*Service)

    which can match studentService, teacherService, paymentService, emailService, and (in the practice set) notificationService. bean() is specific to Spring AOP and works with Spring-managed bean names.

    Important: Bean names are case-sensitive. bean(*Service) matches studentService but the exact-name form bean(studentService) will not match StudentService; check the actual bean name before blaming the advice.

    8. Combining Pointcut Expressions (&&, ||, !)

    Pointcut expressions can be combined with boolean operators:

    &&   // AND
||   // OR
!    // NOT

    AND - &&: both expressions must match.

    within(com.coderarmy.student.service..*)
&& execution(public * *(..))

    Matches public methods inside the service layer.

    OR - ||: at least one expression must match.

    within(com.coderarmy.student.service..*)
|| within(com.coderarmy.student.controller..*)

    Matches methods in either the service layer or the controller layer.

    NOT - !: the negated expression must not match.

    within(com.coderarmy.student.service..*)
&& !execution(* getHealth(..))

    Matches service methods except methods named getHealth. Another example:

    within(com.coderarmy.student..*)
&& !within(com.coderarmy.student.repository..*)

    Matches application methods except repository methods.

    Use parentheses to keep complex expressions readable:

    (
    within(com.coderarmy.student.service..*)
    || within(com.coderarmy.student.controller..*)
)
&& execution(public * *(..))

    Interviewer's perspective: A realistic "exclude one thing" answer is within(service..*) && !execution(* clearCache()). The follow-up is almost always: "and if clearCache were overloaded?" The correct upgrade is !execution(* clearCache(..)), because () binds to the zero-argument overload only, while (..) excludes every overload.

    9. Named Pointcuts with @Pointcut and Centralized Classes

    Long expressions are often reused across multiple advice methods. Repeating them creates duplication and makes maintenance harder. A named pointcut assigns a reusable name to an expression:

    @Pointcut("within(com.coderarmy.student.service..*)")
public void serviceLayer() {
}

    The method body remains empty; its name represents the pointcut expression. Reuse it in an advice:

    @Before("serviceLayer()")
public void beforeServiceMethod() {
    System.out.println("Before service method");
}

    Note that serviceLayer() is not called as a normal Java method. Spring resolves it as a pointcut declaration.

    When several aspects share the same layer definitions, keep them in one class. Here is the aopDemo ApplicationPointcuts shape:

    package com.coderarmy.student.aop;

import org.aspectj.lang.annotation.Pointcut;

public class ApplicationPointcuts {

    @Pointcut("within(com.coderarmy.student.controller..*)")
    public void controllerLayer() {
    }

    @Pointcut("within(com.coderarmy.student.service..*)")
    public void serviceLayer() {
    }

    @Pointcut("within(com.coderarmy.student.repository..*)")
    public void repositoryLayer() {
    }

    @Pointcut("execution(public * *(..))")
    public void publicMethod() {
    }

    @Pointcut("serviceLayer() && publicMethod()")
    public void publicServiceMethod() {
    }
}

    Reference it from another aspect using its fully qualified name:

    @Aspect
@Component
public class LoggingAspect {

    @Before("com.coderarmy.student.aop.ApplicationPointcuts.serviceLayer()")
    public void logBeforeServiceMethod() {
        System.out.println("Service method called");
    }
}

    This creates one architectural definition of each layer. If a package changes, the expression needs to be updated in only one place. That is exactly why the aopDemo project grew a standalone ApplicationPointcuts class instead of scattering the packages across every aspect.

    10. Advanced Designators: args() and @args()

    args() checks runtime argument types:

    @Before("args(com.coderarmy.student.model.Student)")
public void beforeStudentArgument() {
    System.out.println("Student argument received");
}

    It matches when the runtime argument is compatible with Student.

    @args() checks annotations on the runtime classes of the arguments:

    @TrackData
public class Student {
    private String name;
}

    @Before("@args(com.coderarmy.annotation.TrackData)")
public void beforeMethod() {
    System.out.println("Annotated argument received");
}

    When new Student() is passed, Spring checks the runtime class of that object. Because Student carries @TrackData, the pointcut matches.

    • args(Type) -> runtime argument type.
    • @args(AnnotationType) -> annotation on the runtime argument type.

    Important: @args() does not check whether the method parameter itself is annotated. It inspects the runtime class of the object that is passed in. That distinction is the whole point of the designator, and it is a favourite exam edge.

    Consistent parameter forms carry over here: args(Student) matches exactly one runtime argument compatible with Student, while args(Student, ..) matches a call whose first argument is Student and which may carry additional arguments.

    11. this(), target(), @within(), and @target()

    Spring AOP normally places a proxy in front of the actual Spring bean:

    Caller -> Spring proxy -> Actual target bean

    In pointcut terminology:

    • Proxy object -> this
    • Actual bean object -> target

    Therefore:

    • this(Type) -> checks the Spring proxy type.
    • target(Type) -> checks the actual target bean type.
    • @within(Annotation) -> checks the annotation on the type where the method is declared.
    • @target(Annotation) -> checks the annotation on the runtime target object's class.

    Consider an interface plus its implementation:

    public interface StudentOperations {
    void addStudent();
}

@Service
public class StudentService implements StudentOperations {
    @Override
    public void addStudent() {
        System.out.println("Student added");
    }
}
    • target(com.coderarmy.student.service.StudentService) matches because the actual bean is a StudentService.
    • this(com.coderarmy.student.service.StudentOperations) matches under a JDK dynamic proxy because the proxy implements StudentOperations.

    @within() and @target() look identical in ordinary classes but diverge under inheritance. With:

    public class BaseService {
    public void save() {
        System.out.println("Saving");
    }
}

@TrackExecution
@Service
public class StudentService extends BaseService {
}

    when studentService.save() executes:

    • @target(TrackExecution) matches, because the runtime target object is a StudentService.
    • @within(TrackExecution) does not match, because save() was declared inside the unannotated BaseService.

    Comparison table:

    Designator Checks Example
    this(Type) Spring proxy type this(StudentOperations)
    target(Type) Actual target bean type target(StudentService)
    @within(Annotation) Annotation on the declaring type @within(Audited)
    @target(Annotation) Annotation on the runtime target object's class @target(TrackExecution)

    Keep the four separate: this/target compare types, while @within/@target compare annotations, and only target/@target look at the real bean behind the proxy.

    12. JDK Proxy vs CGLIB Proxy and Configuring the Proxy Type

    The difference between this() and target() becomes most visible with JDK interface-based proxies.

    JDK proxy - exposes the implemented interfaces:

    Proxy type  -> StudentOperations
Target type -> StudentService

    It follows that, under a JDK proxy:

    • this(StudentOperations) -> matches
    • target(StudentService) -> matches
    • this(StudentService) -> normally does not match

    because the proxy implements StudentOperations, but it is not a subclass of the concrete StudentService class.

    CGLIB proxy - subclasses the target class:

    StudentService
      ^
StudentService$$SpringCGLIB$$...

    Therefore both can match under CGLIB:

    this(com.coderarmy.student.service.StudentService)
target(com.coderarmy.student.service.StudentService)

    Summary:

    Aspect JDK dynamic proxy CGLIB proxy
    Based on Implemented interfaces Subclassing the target class
    Exposes The interfaces only The concrete class (and its methods)
    this(InterfaceType) Matches Matches only if that type is in the hierarchy
    this(ConcreteClass) Normally does not match Matches
    target(ConcreteClass) Matches Matches
    Requires interfaces Yes No
    Chosen when Interface(s) implemented Class-based proxying / no interface

    Mnemonic: JDK joins Interfaces, CGLIB clones Classes.

    Configuring the proxy type. Spring Boot normally uses class-based proxying for AOP auto-configuration:

    spring.aop.proxy-target-class=true

    To prefer JDK interface-based proxies:

    spring.aop.proxy-target-class=false

    JDK proxies require interfaces. If a class does not implement an interface, Spring uses a class-based proxy instead.

    In plain Spring Framework, the choice is made on the annotation:

    @Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true)
public class AopConfig {
}

    @Configuration
@EnableAspectJAutoProxy(proxyTargetClass = false)
public class AopConfig {
}

    The default value of proxyTargetClass in @EnableAspectJAutoProxy is false. In a normal Spring Boot application, the application property is generally preferred, because Boot already provides AOP auto-configuration.

    Interviewer's perspective: "Why does this(StudentService) fail even though the bean is a StudentService?" Because under a JDK proxy the caller-facing object is a proxy implementing StudentOperations, not a subclass of StudentService. The precise answer separates this (proxy surface) from target (real bean) and then names the proxy type that caused it.

    13. Quick Reference and Practical Guidelines

    Full designator reference:

    Designator What it checks Example
    execution() Method signature execution(* service..*.*(..))
    within() Declaring class or package within(service..*)
    @annotation() Annotation on the method @annotation(TrackExecutionTime)
    bean() Spring bean name bean(*Service)
    @within() Annotation on the declaring type @within(Audited)
    @target() Annotation on the runtime target class @target(Audited)
    args() Runtime argument types args(Student)
    @args() Annotations on runtime argument types @args(TrackData)
    this() Spring proxy type this(StudentOperations)
    target() Actual target bean type target(StudentService)

    Practical guidelines:

    1. Prefer pointcuts that represent clear architectural boundaries. within(com.coderarmy.student.service..*) is safer than execution(* *(..)).
    2. Use execution() when matching depends on method name, return type, modifier, or parameters.
    3. Use within() when the requirement applies to a complete class, package, or application layer.
    4. Use @annotation() when selected methods should explicitly opt into the aspect behaviour.
    5. Use named pointcuts instead of repeating long expressions.
    6. Keep pointcuts narrow enough to understand and test. Overly broad expressions can produce excessive logs, unnecessary overhead, and unexpected behaviour.
    7. Remember that Spring AOP works through Spring-managed proxies: External caller -> Spring proxy -> target method. A direct internal call from one method to another method in the same object normally bypasses the proxy and does not trigger the advice.
    8. Only Spring-managed beans are proxied, so a new StudentService() constructed by hand is never advised.

    The four designators worth mastering first are execution(), within(), @annotation(), and bean(). The advanced designators - args(), @args(), this(), target(), @within(), @target() - become useful when inheritance, runtime argument types, or proxy implementation details matter.

    14. Myth vs Reality

    Myth Reality
    "within() and execution() are interchangeable" within() restricts the declaring class/package only; execution() can filter modifier, return type, name, and parameters.
    "service.* also catches subpackages" .* is one segment (direct types only); ..* is zero or more segments (package plus subpackages).
    "(..) means exactly all parameters" (..) is zero or more; (*) is exactly one; () is exactly zero; (*, *) is exactly two.
    "this() and target() mean the same thing" this() checks the proxy type; target() checks the real bean. They diverge sharply under JDK proxies.
    "@annotation() also matches class-level annotations" @annotation() is for method-level annotations; class-level matching belongs to @within() and @target().
    "@args() checks the annotation on the parameter" @args() checks the annotation on the runtime class of the argument object, not on the parameter declaration.
    "Spring AOP advises private methods and self-calls" The proxy overrides/intercepts calls from outside; private methods and internal same-object calls are not intercepted normally.

    15. Common Trap Questions

    Trap 1 - within() and execution() do the same job. Verdict: False. within() only selects by declaring class or package. execution() selects by signature details - modifier, return type, method name, and parameters. They overlap on simple layer matching and diverge the moment you need signature filtering.

    Trap 2 - the wildcard * in a package pattern includes subpackages. Verdict: False. com.coderarmy.student.service.* matches only classes directly inside service. Use com.coderarmy.student.service..* for the package and all subpackages.

    Trap 3 - (*) and (..) are both "any parameters". Verdict: False. (*) is exactly one parameter of any type and ignores methods with zero or multiple parameters; (..) is zero or more. () is exactly zero and (*, *) is exactly two.

    Trap 4 - this() and target() are interchangeable. Verdict: False. this(StudentOperations) matches the proxy surface; target(StudentService) matches the real bean. Under a JDK proxy this(StudentService) normally fails because the proxy is not a subclass of the concrete class.

    Trap 5 - @annotation() also matches a class-level annotation. Verdict: False. @annotation() matches a method that carries the annotation. Class-level annotation matching is done by @within() (declaring type) and @target() (runtime target class), which also differ under inheritance.

    Trap 6 - bean(*Service) matches bean names regardless of case. Verdict: False. bean() matches Spring bean names, and bean names are case-sensitive; bean(studentService) is not the same as a StudentService-derived name.

    Trap 7 - Spring AOP intercepts private methods and internal self-calls. Verdict: False. Proxy-based Spring AOP cannot intercept private methods through normal proxy overriding, and a direct internal call from one method to another in the same object bypasses the proxy, so the advice does not run.

    16. Points to Remember

    1. Advice defines what behaviour runs; a pointcut expression defines where it runs, and it only decides interception, never execution.
    2. execution() selects by signature - modifier, return type, declaring class, method name, parameters - and its essential parts are return type + method name + parameters.
    3. * matches one position or one naming segment; .. matches zero or more elements, whether in a parameter list or across package segments.
    4. () is exactly zero parameters, (*) exactly one, (*, *) exactly two, (..) zero or more, (Long, ..) fixes the first, (.., Student) fixes the last.
    5. within() selects by declaring class or package (service.* direct, service..* plus subpackages) and cannot filter by signature.
    6. @annotation() matches a method-level annotation; @within() and @target() handle class-level annotations (declaring type versus runtime target).
    7. bean() matches Spring bean names (case-sensitive) and supports wildcards such as bean(*Service).
    8. Combine pointcuts with &&, ||, and !, and use parentheses to keep complex expressions readable.
    9. Named @Pointcut methods have empty bodies, are referenced by name or fully qualified name, and can be centralized in a class such as ApplicationPointcuts.
    10. args()/@args() inspect runtime arguments; this() is the proxy, target() is the real bean; JDK proxies expose interfaces, CGLIB proxies subclass the class, and proxyTargetClass (or spring.aop.proxy-target-class) chooses between them.

    17. Likely Interview Questions

    Question Crisp Answer
    What is a pointcut expression? The rule that selects which method executions receive an aspect's advice; it decides interception, not execution.
    What does execution() match on? The method signature: access modifier, return type, declaring class, method name, parameters, and declared exceptions.
    What is the broadest common pointcut? execution(* *(..)) - any return type, any method name, zero or more parameters.
    Difference between * and ..? * matches one position/naming segment; .. matches zero or more elements (parameters or package levels).
    Difference between within() and execution()? within() selects by declaring class/package only; execution() filters the signature (modifier, return type, name, params).
    Difference between @annotation() and @within()? @annotation() tests a method-level annotation; @within() tests an annotation on the declaring type.
    What does bean() match? Methods on Spring beans by bean name, with wildcards like bean(*Service); names are case-sensitive.
    How do you combine pointcuts? With && (both match), || (either matches), and ! (must not match), plus parentheses for clarity.
    What is a named pointcut? A @Pointcut-annotated method with an empty body whose name represents an expression, reusable across advice methods.
    Difference between this() and target()? this() checks the Spring proxy type; target() checks the actual target bean type; they differ under JDK proxies.
    JDK proxy versus CGLIB proxy? JDK proxies are interface-based and expose interfaces; CGLIB proxies subclass the target class; proxyTargetClass selects.

    advice   -> WHAT behaviour runs

             v

             |

             |

             |

(internal self-calls and private methods bypass the proxy)
    • execution() and within() answer "what signature" versus "what location"; narrow layer pointcuts beat execution(* *(..)).
    • @annotation() and bean() add opt-in and name-based selection.
    • Boolean composition plus named @Pointcut declarations keep expressions reusable and centralized.
    • Advanced designators (args(), @args(), this(), target(), @within(), @target()) matter for runtime types, annotations, and proxy details.
    • Proxy type decides what this() can see: JDK exposes interfaces, CGLIB subclasses the class.

    One-line takeaway: A pointcut is a precise selector for method executions, and the proxy underneath decides what that selector can even see - so write narrow, named pointcuts and always reason about whether the caller is hitting the proxy or bypassing it.
