    Executor Framework Deep Dive | ThreadPool, Future & Callable

    26 sections · 5,126 words

    Lecture 56

    Scope evidence: "Executor Framework Deep Dive | ThreadPool, Future & Callable" plus the lecture's own repo notes (task vs execution separation; manual threads do not scale), playlist map, verified. Repo evidence: 4 Demo files.

    Lecture 48 taught the raw machinery: create a Thread, hand it a Runnable, and let the JVM schedule it. That model explains multithreading, but it does not survive contact with production, because creating one platform thread per task consumes native memory, invites context-switching overhead, and offers no natural upper bound. The Executor Framework replaces "create a thread" with "submit a task to an execution policy": the caller describes the work as a Runnable or Callable<V>, and an ExecutorService decides when, where and on which worker it runs. This lecture walks through the hierarchy (Executor to ExecutorService to ThreadPoolExecutor), the result handle Future<V>, the factory methods of Executors, the tuning parameters of ThreadPoolExecutor, queue behaviour, lifecycle and rejection policies, and scheduled execution.

    1. Why Manual Thread Creation Does Not Scale

    The manual approach looks harmless:

    // Demo.java — one thread per task: convenient for a demo, dangerous in production
public class ManualThreadsDemo {
    static void process(int request) {
        System.out.println("Processing " + request +
                " on " + Thread.currentThread().getName());
    }

    public static void main(String[] args) {
        for (int request = 1; request <= 5; request++) {
            int id = request;
            new Thread(() -> process(id)).start();
        }
    }
}

    This works, but the code is responsible for defining the task, deciding how it is executed, creating the thread, and managing its lifecycle all at once. Repeatedly creating threads introduces six concrete problems:

    1. Threads consume resources. A platform thread is generally backed by an operating-system thread, so each one needs native stack memory, JVM and OS bookkeeping, CPU scheduling time, and context-switching effort. The exact stack size depends on the JVM, OS and configuration, but a very large number of threads consumes substantial native memory.
    2. Context-switching overhead. When many runnable threads compete for a limited number of cores, the OS repeatedly saves one thread's state, restores another's, and disrupts CPU-cache locality, spending CPU time on scheduling rather than useful work. Too many active threads can reduce performance instead of improving it.
    3. Thread creation has a cost. Creating and destroying an OS thread is more expensive than a lightweight Java method call, and the application pays that cost for every single task.
    4. No thread reuse. A manually created thread follows create thread → execute one task → terminate thread, so the next task requires another thread.
    5. No natural upper bound. new Thread(() -> process(request)).start() inside a loop will keep creating threads; if requests arrive faster than they are processed, creation continues until memory is exhausted or the application becomes unresponsive.
    6. Difficult lifecycle management. After start(), the application must coordinate completion, interruption and shutdown by hand; join() and interrupt() help, but they are not a task-management system.

    Memory aid Creating one thread for every task is like hiring a new chef for every order and dismissing the chef after one dish. A thread pool is the kitchen that keeps its cooks on staff.

    2. What Is the Executor Framework?

    The Executor Framework is Java's built-in abstraction for submitting tasks without directly managing the threads that execute them. Its central idea is: separate task submission from task execution.

    Without an executor, new Thread(() -> processOrder(order)).start(); forces the code to decide what should run, which thread runs it, and when that thread is created. With an executor, the code only submits the task and lets the executor decide whether it should run immediately, wait in a queue, run on an existing worker thread, cause another worker to be created, or be rejected because the system is overloaded.

    The framework normally works with two separate concepts:

    Concept Responsibility
    Task (Runnable / Callable) Describes the work that must be performed
    Executor Decides how and when the task will run

    A thread is a low-level execution unit; an executor is a higher-level abstraction that manages task execution using threads. This separation is what makes the code easier to test and change.

    3. Core Architecture and Type Hierarchy

    Every executor-based system follows the same pipeline:

    Task (Runnable or Callable)
        ↓
Executor / ExecutorService
        ↓
Task Queue
        ↓
Worker Threads
        ↓
Task Execution

    The type hierarchy is equally consistent. The general execution branch runs Executor → ExecutorService → AbstractExecutorService → ThreadPoolExecutor, while scheduled execution adds ExecutorService → ScheduledExecutorService → ScheduledThreadPoolExecutor.

    Important ThreadPoolExecutor is the concrete engine underneath most pools; Executors, by contrast, is only a utility class of factory methods. Knowing which is which is the first step in tuning a pool deliberately.

    4. The Executor Interface

    Executor is the smallest abstraction in the framework, with a single method:

    public interface Executor {
    void execute(Runnable command);
}

    execute() requests that the task be executed and takes a Runnable that describes the task. The interface does not define exactly where, when or on which thread it must run, so implementations may behave very differently. A DirectExecutor runs the command on the current thread with command.run(); a NewThreadExecutor does new Thread(command).start(); a thread pool obtained from Executors.newFixedThreadPool(4) is a third implementation. Rather than a shorter way to create threads, an executor is an abstraction for how work is executed.

    5. The ExecutorService Interface

    ExecutorService extends Executor and adds the features required for practical task management:

    ExecutorService = task execution
              + task results
              + task cancellation
              + bulk task operations
              + lifecycle management

    Its important methods are execute(...), submit(...), invokeAll(...), invokeAny(...), shutdown(), shutdownNow() and awaitTermination(...). Any production code that needs a result, a cancellation handle or controlled shutdown uses ExecutorService, not the bare Executor.

    6. execute() vs submit()

    execute() accepts a Runnable, returns nothing, does not return a Future, and is suitable for fire-and-forget tasks. submit() returns a Future representing the submitted task, and it accepts a Callable, a Runnable, or a Runnable with a predefined result. For a successfully completed Runnable, future.get() returns null; the overload submit(Runnable, result) yields the supplied value instead (for example "SUCCESS").

    // submit a Callable, a Runnable, and a Runnable with a predefined result
Future<Integer> fromCallable = executor.submit(() -> 10 + 20);
Future<?> fromRunnable = executor.submit(() -> System.out.println("Task completed"));
Future<String> withResult = executor.submit(() -> System.out.println("Saving data"), "SUCCESS");
    Feature execute() submit()
    Accepted task Runnable Runnable or Callable
    Return value Nothing Future
    Per-task cancellation through Future No Yes
    Completion tracking No direct handle Available through Future
    Task exception Reaches the worker thread's uncaught-exception mechanism Stored in the Future
    Typical use Fire-and-forget task Result, cancellation or completion tracking

    Cross-reference Runnable is a functional interface, so lambdas target-type against it (Lecture 37). Callable<V> is likewise functional, which is why executor.submit(() -> 10 + 20) reads so cleanly.

    7. Runnable vs Callable

    Runnable declares void run(), cannot return a value, cannot declare checked exceptions, and can be passed to both execute() and submit(). Callable<V> declares V call() throws Exception, returns a value, may throw checked exceptions, and is submitted through submit(), invokeAll() or invokeAny().

    @FunctionalInterface
public interface Runnable {
    void run();
}

@FunctionalInterface
public interface Callable<V> {
    V call() throws Exception;
}
    Feature Runnable Callable<V>
    Method run() call()
    Return value No Yes
    Checked exceptions Cannot declare them Can declare them
    Can be passed to execute() Yes No
    Can be passed to submit() Yes Yes

    The practical rule: if the task must produce a value or may fail with a checked exception, use Callable<V>; otherwise Runnable is enough.

    8. Future — a Handle to an Asynchronous Result

    A Future is a handle to the result or completion state of an asynchronous task. The task is submitted now, it may finish later, and the Future represents its pending result. Submitting is asynchronous, but retrieval can block.

    ExecutorService executor = Executors.newFixedThreadPool(2);
Future<Integer> future = executor.submit(() -> {
    Thread.sleep(1000);
    return 10 + 20;
});
System.out.println("Main thread can do other work");
Integer result = future.get();
System.out.println("Result: " + result);
executor.shutdown();
    Method Purpose
    get() Waits for completion and returns the result
    get(timeout, unit) Waits only for the specified duration
    isDone() Checks whether the task has completed
    isCancelled() Checks whether the task was cancelled
    cancel(true) Requests cancellation and may interrupt the running task

    Important future.get() is blocking. If the result is ready it returns immediately; otherwise the calling thread waits. Submitting is asynchronous, but calling get() right away makes the caller behave synchronously at that point, so the pattern is asynchronous execution plus blocking retrieval.

    9. Timed get() and Cancellation

    A timed call prevents the caller from waiting forever:

    try {
    Integer result = future.get(2, TimeUnit.SECONDS);
    System.out.println(result);
} catch (TimeoutException exception) {
    System.out.println("Task did not finish in time");
}

    future.cancel(true) requests cancellation; passing true means that, if the task is already running, the executor may interrupt its worker thread. Cancellation is cooperative: the task must respond correctly to interruption, as in a loop that checks Thread.currentThread().isInterrupted(). Calling cancel(true) does not forcibly terminate arbitrary Java code.

    Golden rule A Future that is never inspected hides two things: its result and its failure. Treat ignoring a Future as a code smell unless the task is genuinely fire-and-forget.

    10. Exception Handling — execute() vs submit()

    With execute(), the exception is not returned to the submitting thread; it becomes an uncaught exception on the worker thread and is normally reported through that thread's UncaughtExceptionHandler. In a pool, the failed worker may terminate and be replaced when required. Task-level try/catch gives controlled recovery.

    With submit(), the exception is captured by the task's Future. future.get() throws ExecutionException, and the original task exception is available through exception.getCause().

    // execute(): exception escapes to the worker thread's uncaught-exception handler
executor.execute(() -> {
    int result = 10 / 0;
});

// submit(): exception is stored and re-thrown wrapped by get()
Future<Integer> future = executor.submit(() -> 10 / 0);
try {
    Integer result = future.get();
} catch (ExecutionException exception) {
    Throwable actualCause = exception.getCause();
    System.out.println("Task failed: " + actualCause.getMessage());
}
    Aspect execute(Runnable) submit(Callable/Runnable)
    Where the exception goes Worker thread's uncaught-exception mechanism Captured inside the Future
    How the caller sees it Usually not directly future.get() throws ExecutionException
    Original cause n/a exception.getCause()
    Easy to miss? Possible in logs Yes, if get() is never called

    11. Managing the Executor Lifecycle

    Worker threads are normally non-daemon, so an active executor can keep the JVM running even after main() completes; an executor that is no longer needed must be shut down.

    • shutdown() stops accepting new tasks, allows previously submitted tasks to complete, initiates an orderly shutdown, and returns immediately without waiting for termination. Submitting after shutdown throws RejectedExecutionException.
    • shutdownNow() stops accepting new tasks, removes tasks that have not started, returns them as a list, and attempts to interrupt actively running tasks. It does not guarantee that running tasks stop immediately; tasks must cooperate with interruption.
    • awaitTermination(timeout, unit) waits up to the specified duration for the executor to terminate and is normally called after shutdown() or shutdownNow().
    // graceful shutdown pattern
executor.shutdown();
try {
    if (!executor.awaitTermination(10, TimeUnit.SECONDS)) {
        executor.shutdownNow();
        System.out.println("Executor did not terminate");
    }
} catch (InterruptedException exception) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}

    Because ExecutorService is AutoCloseable in modern Java, try-with-resources is the cleanest form: close() shuts the executor down and waits for submitted tasks to finish before returning.

    try (ExecutorService executor = Executors.newFixedThreadPool(2)) {
    executor.execute(() -> System.out.println(
            "Running on " + Thread.currentThread().getName()));
}
System.out.println("Executor closed automatically");

    Important Try-with-resources gives an orderly shutdown plus termination wait. If you need to cancel queued work instead, call shutdownNow() explicitly.

    12. Working With Multiple Tasks — invokeAll() and invokeAny()

    invokeAll(tasks) executes a collection of Callable tasks and waits until all of them complete. It blocks until every task finishes, returns one Future per task, and the returned futures follow the same order as the input list; a completed task may have completed successfully or exceptionally. invokeAny(tasks) executes multiple tasks and returns the result of one that completes successfully, cancelling the unfinished tasks once a result is available; it returns the first successful result, not necessarily the first task that terminates.

    List<Callable<Integer>> tasks = List.of(() -> 10, () -> 20, () -> 30);
List<Future<Integer>> futures = executor.invokeAll(tasks);
for (Future<Integer> future : futures) {
    System.out.println(future.get());
}
Integer first = executor.invokeAny(tasks);

    invokeAny() is useful when the same answer can be obtained from several independent sources, such as three redundant servers.

    13. ThreadPoolExecutor — Why a Pool Needs Rules

    A complete thread pool requires a controlled number of worker threads, a queue for waiting tasks, rules for creating additional threads, rules for removing idle threads, and a policy for handling overload. ThreadPoolExecutor provides this configurable execution engine, processing incoming tasks through workers and a work queue in one continuous flow.

    Executors is a utility class containing factory methods; ThreadPoolExecutor is the concrete class that performs the actual thread-pool management.

    Executors            = convenient factory methods
ThreadPoolExecutor   = configurable execution engine

    Factory methods are convenient, but direct construction is useful when the application needs explicit control over queue capacity, maximum threads, thread naming and rejection behaviour.

    14. ThreadPoolExecutor Constructor Parameters

    A commonly used constructor exposes every knob at once:

    ThreadPoolExecutor executor = new ThreadPoolExecutor(
        corePoolSize, maximumPoolSize, keepAliveTime, timeUnit,
        workQueue, threadFactory, rejectionHandler);
    Parameter Meaning
    corePoolSize Target number of core worker threads
    maximumPoolSize Maximum number of worker threads allowed
    keepAliveTime Maximum idle time for excess (and, if enabled, core) threads
    TimeUnit Unit of keepAliveTime
    workQueue Holds tasks waiting to execute
    ThreadFactory Controls how worker threads are created
    RejectedExecutionHandler Handles tasks that cannot be accepted

    Three details repay close reading:

    • corePoolSize. When a new task arrives and fewer than this many workers exist, the pool normally creates another worker even if one is idle. Core threads are not necessarily created when the executor object is constructed; by default they start as tasks arrive, though prestartCoreThread() and prestartAllCoreThreads() create them in advance. Core threads are retained even when idle unless core-thread timeout is enabled via allowCoreThreadTimeOut(true).
    • maximumPoolSize. New threads beyond the core size are created only when all core workers are occupied, the current count is below the maximum, and the work queue cannot accept another task. With an unbounded queue the queue never fills, so the pool normally does not grow beyond corePoolSize.
    • keepAliveTime. When the number of workers exceeds corePoolSize, an excess worker is removed after being idle for the keep-alive duration.

    Interviewer's perspective "Why did my maximumPoolSize have no effect?" Almost always because the default work queue was unbounded, so the queue never rejected a task and the pool never needed extra threads. maximumPoolSize is only consulted after the queue is full.

    15. The Submission Decision Flow

    For a typical ThreadPoolExecutor, the simplified decision process is:

    1. Worker count below corePoolSize?   Yes → create worker and run task
2. Otherwise, can the queue accept?   Yes → enqueue task
3. Otherwise, below maximumPoolSize?  Yes → create extra worker and run task
4. Otherwise                          → reject task

    The order matters: the executor fills core threads first, then fills the queue, and only then creates threads beyond the core size. With corePoolSize = 2, maximumPoolSize = 4 and a queue capacity of 2, tasks 1 and 2 each create a worker, tasks 3 and 4 go to the queue, task 5 and task 6 create extra workers once the queue is full, and task 7 is rejected because both the maximum worker count and the queue are full.

    16. Work Queue Types

    The work queue stores submitted tasks that are waiting for a worker, and its choice directly affects memory usage, latency, maximum concurrency, overload behaviour, and whether maximumPoolSize is ever used.

    Queue Capacity Behaviour Typical use
    ArrayBlockingQueue<>(100) Bounded, fixed at construction Predictable overload handling; lets the pool grow beyond core size once full Backpressure when memory must be protected
    LinkedBlockingQueue<>() Effectively unbounded without a capacity; optionally bounded Can accumulate a huge backlog Commonly used by fixed thread pools
    SynchronousQueue<>() No internal storage Each task must be handed directly to a worker; otherwise a new worker is created Cached thread pools 
    BlockingQueue<Runnable> bounded = new ArrayBlockingQueue<>(100);

    Important An unbounded queue does not make an executor safe. It merely moves overload from thread creation to memory consumption, hiding it temporarily while the backlog grows.

    17. Executor Factory Methods

    Executors provides ready-made pools. Each factory method is a shorthand for a specific ThreadPoolExecutor configuration:

    Factory method Core / max Queue Notable behaviour
    newFixedThreadPool(n) n / n Unbounded LinkedBlockingQueue Fixed concurrency; tasks wait; queue can grow excessively under sustained overload; completion order not guaranteed
    newCachedThreadPool() 0 / very large SynchronousQueue Creates threads on demand, reuses idle workers, removes idle workers after 60s keep-alive; risks creating too many platform threads for long/blocking tasks
    newSingleThreadExecutor() 1 / 1 Unbounded internal queue Sequential execution with automatic thread reuse and worker replacement; a slow worker causes a large backlog
    newScheduledThreadPool(n) n / large Delayed work queue One-time delayed and periodic tasks 
    ExecutorService fixed = Executors.newFixedThreadPool(3);
ExecutorService cached = Executors.newCachedThreadPool();
ExecutorService single = Executors.newSingleThreadExecutor();
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);

    The single-thread executor guarantees sequential execution, but it does not make unrelated shared state thread-safe if other threads touch that state directly. The cached pool benefits many short-lived asynchronous tasks with a controlled submission rate, but a cached (or fixed) pool can create too many platform threads when long-running or blocking tasks arrive rapidly.

    18. Scheduled Execution — Fixed Rate vs Fixed Delay

    ScheduledExecutorService supports one-time delayed tasks, fixed-rate periodic tasks and fixed-delay periodic tasks, and is generally preferred over the legacy Timer for concurrent scheduled execution. scheduler.schedule(task, 2, TimeUnit.SECONDS) runs a task once after a delay relative to submission time.

    scheduler.scheduleAtFixedRate(task, initialDelay, period, unit) bases intended start times on a fixed schedule: initialDelay, initialDelay + period, initialDelay + 2 × period, and so on. If one execution takes longer than the period, the next starts late, and executions of the same periodic task never overlap. scheduler.scheduleWithFixedDelay(task, initialDelay, delay, unit) measures the delay after the previous execution finishes, so End 1 → wait delay → Start 2.

    Feature Fixed Rate Fixed Delay
    Scheduling basis Planned start times Previous completion time
    Tries to maintain frequency Yes No
    Waits after task finishes Not necessarily Yes
    Same task overlaps with itself No No
    Common use Metrics collection, regular-cadence polling Cleanup or retry work needing a pause after completion 
    ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);
scheduler.scheduleAtFixedRate(
        () -> System.out.println("Fixed rate tick"),
        0, 2, TimeUnit.SECONDS);
scheduler.scheduleWithFixedDelay(
        () -> System.out.println("Fixed delay tick"),
        0, 2, TimeUnit.SECONDS);

    Important If a periodic task throws an uncaught exception, its future executions are suppressed. Handle expected failures inside the task when later executions must continue.

    19. Rejection Policies

    A task may be rejected when the executor has been shut down, or when the pool is at maximumPoolSize and its bounded queue is full. A RejectedExecutionHandler decides what happens:

    Policy Behaviour When it fits
    AbortPolicy (default) Throws RejectedExecutionException Immediate, visible failure; silently losing work is unacceptable
    CallerRunsPolicy Runs the rejected task on the calling thread, slowing the producer (natural backpressure); discards it if the executor is already shut down Overload where throttling the producer is acceptable
    DiscardPolicy Silently drops the task Only when dropping work is explicitly acceptable and monitored
    DiscardOldestPolicy Removes the queue head and retries the new task Fresh information matters more than stale queued work; dangerous when every task must run 
    ThreadPoolExecutor executor = new ThreadPoolExecutor(
        2, 4, 30, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(10),
        new ThreadPoolExecutor.CallerRunsPolicy());

    This creates two core workers, at most four workers, a queue of ten tasks, a thirty-second timeout for excess idle workers, and caller-runs behaviour during overload.

    20. Design Principles for Production Executors

    • Separate tasks from threads. Write application logic as Runnable or Callable tasks and let the executor own worker management: business logic → task, concurrency policy → executor configuration. This makes the code easier to test and change.
    • Do not assume more threads always mean better performance. The useful number depends on available CPU cores, whether tasks are CPU-bound or I/O-bound, task duration, blocking time, memory limits and downstream capacity. Too many threads for CPU-bound work (image processing, compression, encryption, numerical calculations) add scheduling overhead without adding CPU; more concurrency can help I/O-bound work (database, network, file operations), but the pool must still respect connection, service and memory limits.
    • Prefer bounded resources. A production executor should control queue capacity, maximum worker count, submission rate, task timeout, rejection behaviour and downstream concurrency. An unbounded queue merely moves overload from thread creation to memory consumption.
    • Preserve interruption. Never silently ignore InterruptedException; catch it, restore the flag with Thread.currentThread().interrupt(), and return. Restoring the flag lets higher-level code observe the cancellation request.
    • Name worker threads. A custom ThreadFactory that sets names such as order-worker-1 makes logs and production debugging far easier than opaque Thread-8.
    • Monitor the pool. getPoolSize(), getActiveCount(), getQueue().size(), getCompletedTaskCount(), getTaskCount() and getLargestPoolSize() reveal whether the queue is growing, whether the pool reaches its maximum, whether tasks complete fast enough, and whether the executor is frequently overloaded.

    Memory aid Business logic is the task; concurrency policy is the executor. When tuning, ask "am I CPU-bound or I/O-bound?" before changing any number.

    21. Myth vs Reality

    Myth Reality
    "An executor is just a shorter way to create threads." It is a complete task-execution system: queuing, results, cancellation, scheduling, lifecycle and overload handling.
    "maximumPoolSize always controls concurrency." With an unbounded queue the queue never fills, so the pool normally stays at corePoolSize and maximumPoolSize is never reached.
    "submit() makes exceptions disappear." The exception is stored in the Future; it is easy to miss only because get() was never called.
    "shutdown() waits for running tasks to finish." It returns immediately; use awaitTermination() to wait. shutdownNow() interrupts and returns queued tasks.
    "cancel(true) kills the task immediately." Cancellation is cooperative; the task must respond to interruption for it to stop promptly.
    "More threads always mean more throughput." Beyond the useful concurrency, extra threads add context switching and resource pressure, reducing performance.

    22. Common Trap Questions

    Trap 1 — Unbounded queue: "I set corePoolSize = 2, maximumPoolSize = 8, but only two threads ever run. Why?" The default LinkedBlockingQueue is effectively unbounded, so it never fills and the pool never needs extra threads. Use a bounded ArrayBlockingQueue to make maximumPoolSize reachable.

    Trap 2 — Silent failure: "I called submit(...) and nothing happened when the task failed." The exception is captured in the Future. Unless get() is called, the failure is never observed; execute() instead routes it to the worker's uncaught-exception handler.

    Trap 3 — Shutdown semantics: "After shutdown(), is everything finished?" No. shutdown() only stops new submissions and lets accepted tasks complete; it returns immediately. Call awaitTermination() if you must wait.

    Trap 4 — Cancellation: "cancel(true) will stop my CPU loop, right?" Only if the loop checks interruption (isInterrupted() / handles InterruptedException). Cancellation is cooperative and does not forcibly terminate Java code.

    Trap 5 — Periodic task death: "My scheduled job ran once, then never again. Why?" An uncaught exception in a periodic task suppresses all future executions. Catch failures inside the task.

    Trap 6 — Blocking get(): "submit() is asynchronous, so my main code never blocks." Submission is asynchronous, but future.get() is blocking and makes the caller wait for the result. Use the timed overload to bound the wait.

    Trap 7 — Sequential does not mean safe: "The single-thread executor makes my shared state thread-safe." It only serializes its own tasks. If other threads access the same state directly, synchronization is still required.

    23. Points to Remember

    1. Manual threads do not scale: they cost native memory and creation time, cause context-switch overhead, have no reuse and no upper bound, and complicate lifecycle management.
    2. The Executor Framework separates task submission from task execution: the task describes the work, the executor decides how and when it runs.
    3. Executor has one method, execute(Runnable command), and says nothing about where or when the task runs; ExecutorService adds results, cancellation, bulk operations and lifecycle.
    4. execute() is fire-and-forget; submit() returns a Future that tracks result, completion and cancellation.
    5. Runnable returns nothing and cannot throw checked exceptions; Callable<V> returns a value and may throw checked exceptions.
    6. Future.get() is blocking, get(timeout, unit) bounds the wait, isDone()/isCancelled() inspect state, and cancel(true) requests a cooperative interruption.
    7. Exceptions from execute() reach the worker's uncaught-exception mechanism; exceptions from submit() are stored and re-thrown by get() as ExecutionException with the cause via getCause().
    8. shutdown() is orderly, shutdownNow() interrupts and returns queued tasks, and awaitTermination() waits for termination; worker threads are non-daemon and must be shut down.
    9. ThreadPoolExecutor fills core threads, then the queue, then grows to maximumPoolSize, and then rejects according to the chosen RejectedExecutionHandler.
    10. Bounded queues, explicit maximumPoolSize, timeouts, named threads, interruption preservation and monitoring are what make a pool production-ready.

    24. Likely Interview Questions

    Question Crisp Answer
    Why is creating threads manually not ideal? Each task pays thread-creation cost, consumes native memory, causes context-switch overhead, offers no reuse or upper bound, and complicates lifecycle management.
    What is the core idea of the Executor Framework? Separate task submission from task execution: submit a Runnable/Callable, and let the executor decide how and when it runs.
    Difference between Executor and ExecutorService? Executor defines only execute(Runnable); ExecutorService adds submit, invokeAll, invokeAny, shutdown, shutdownNow and awaitTermination.
    Difference between execute() and submit()? execute() takes a Runnable, returns nothing, and exposes exceptions via the worker; submit() returns a Future and stores exceptions in it.
    Runnable vs Callable? Runnable.run() returns void and cannot declare checked exceptions; Callable.call() returns a value and may throw checked exceptions.
    What is a Future? A handle to the result or completion state of an asynchronous task, supporting get, get(timeout), isDone, isCancelled and cancel.
    Is future.get() blocking? Yes. It returns immediately if the result is ready, otherwise the caller waits; the timed overload bounds that wait.
    What does cancel(true) do? It requests cancellation and may interrupt a running worker; cancellation is cooperative and requires the task to respond to interruption.
    shutdown() vs shutdownNow()? shutdown() stops new tasks and lets accepted tasks finish; shutdownNow() removes queued tasks, returns them, and attempts to interrupt running tasks.
    Why did maximumPoolSize not take effect? The work queue was unbounded, so it never filled and the pool never grew beyond corePoolSize.
    scheduleAtFixedRate vs scheduleWithFixedDelay? Fixed rate schedules against planned start times and tries to keep regular frequency; fixed delay waits a set period after each execution finishes.
    What happens if a periodic task throws? Its future executions are suppressed until it is rescheduled; handle expected failures inside the task.
    Which rejection policy provides backpressure? CallerRunsPolicy, because the submitting thread runs the task and is temporarily unable to submit more.

    25. Final Summary

    Runnable / Callable
        ↓  submit()
ExecutorService (Executor + lifecycle + results)
        ↓
ThreadPoolExecutor: corePoolSize → workQueue → maximumPoolSize → reject
        ↓
Worker Threads (reused)  →  Future<V> (result / completion / cancel)
    • Manual threads → do not scale: costly creation, context switching, no reuse, no upper bound, hard lifecycle.
    • Executor framework → separates task definition from execution; Executor (execute) → ExecutorService (submit, lifecycle) → ThreadPoolExecutor (the configurable engine).
    • Tasks → Runnable (no return, no checked exceptions) or Callable<V> (returns value, may throw) submitted with submit() to get a Future<V>.
    • Future → get() blocks, get(timeout) bounds the wait, isDone()/isCancelled() inspect, cancel(true) requests cooperative interruption; its limits motivate CompletableFuture in Lecture 57.
    • Pools → Executors factories are convenient, but direct ThreadPoolExecutor construction exposes core/max size, keep-alive, bounded queue, thread factory and rejection policy.
    • Flow → core threads, then queue, then maximumPoolSize, then rejection; an unbounded queue prevents the pool from ever growing past core size.
    • Lifecycle → shutdown() orderly, shutdownNow() interrupts and returns queued tasks, awaitTermination() waits, try-with-resources closes cleanly.
    • Scheduled → scheduleAtFixedRate targets planned start times; scheduleWithFixedDelay waits after completion; uncaught exceptions stop future runs.
    • Production → bounded resources, named threads, preserved interruption, pool monitoring, and pool sizing matched to CPU-bound or I/O-bound work.

    Golden rule Do not think, "I need to create a thread." Think, "I need to submit a task to an execution policy." The executor owns the threads; the task owns only the work.

    One-line takeaway: the Executor Framework turns thread juggling into task submission backed by a configurable pool, a Future for every result, and an explicit rejection policy for overload.
