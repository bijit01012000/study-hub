    Chain of Responsibility

    11 sections · 959 words

    Behavioural · Design Patterns · Pattern 11 of 12

    Intent

    Pass a request along a linked chain of handlers so that one of several can process it, without the sender hard-coding which one.

    When To Use It

    The Signs

    • A request that one of several handlers might process, and the sender should not pick which.
    • A growing if (canA) ... else if (canB) ... else if (canC) ....
    • You want to add, remove or reorder steps without touching the others.
    • A filter or middleware pipeline in front of the real work.

    Don't Bother If

    • One object always handles the request.
    • The set of handlers is fixed, tiny, and won't change.
    • Every step must run regardless. That's a plain pipeline.
    • Order doesn't matter and nothing is passed on.

    Before

    class ATM {
    void dispense(int amt) {
        // one method, one ladder
        if (amt >= 2000) { int n = amt / 2000; amt %= 2000; give(2000, n); }
        if (amt >= 500) { int n = amt / 500; amt %= 500; give(500, n); }
        if (amt >= 100) { int n = amt / 100; amt %= 100; give(100, n); }
        if (amt > 0) throw new IllegalStateException("cannot make exact");
    }
}

    One big if-ladder.

    After

    abstract class NoteHandler {
    protected NoteHandler next;
    private final int denom;
    NoteHandler(int denom) { this.denom = denom; }
    void setNext(NoteHandler n) { this.next = n; }
    void handle(Dispense d) {
        int n = Math.min(d.remaining / denom, stockOf(denom));
        d.give(denom, n);
        d.remaining -= denom * n;
        if (d.remaining > 0 && next != null) next.handle(d);
    }
}
// Note2000, Note500, Note100: super(denom), one line each

    Wiring the chain, and adding a 200 note as one new link:

    NoteHandler head = new Note2000(), mid = new Note500();
head.setNext(mid); mid.setNext(new Note100());
head.handle(new Dispense(3600));
// 1x2000, 3x500, 1x100
// a 200 note is one new Note200 link. nothing else moves.

    Adding a 200 note to the old ladder, by contrast, shifts every branch:

    if (amt >= 2000) { ... }
if (amt >= 500) { ... }
if (amt >= 200) { int n = amt / 200; amt %= 200; give(200, n); }
if (amt >= 100) { ... }
// wedged mid-ladder
// re-test all four branches. out of 500s? another inner guard.

    Structure

    «INTERFACE»
Handler
    + handle(req): void
    - next: Handler
    each handler tries, then calls next

Client
    holds the head

H2000      H500       H100
denom 2000 denom 500  denom 100
    next       next

each handler takes its part, then calls next with the rest

A WITHDRAWAL OF 3600
3600 -> 2000 x1 -> 1600 -> 500 x3 -> 100 -> 100 x1 -> 0

THE CLIENT ONLY HOLDS THE HEAD

    How It's Built (3 Steps)

    1. A Handler interface with handle(request) and a next link to the following handler.
    2. Each concrete handler does its part. If the request is not fully handled it calls next.handle(request).
    3. Wire the chain once in code or from config, and give the caller only the head.

    Quick Check

    Ask "could any one of several things handle this, and I'd rather not hard-code which?" If yes, link them and pass the request to the head.

    In The Interview

    "The ATM breaks a withdrawal into notes with a chain. The 2000 handler takes as many as it can, passes the remainder to 500, then 100. Adding a 200 note is one new link in the chain, nothing else moves."

    How It's Different

    From The Lookalikes

    Vs Decorator. Every Decorator in the stack runs and passes through. In a Chain, a handler can stop the request (first match wins) or take only its part.

    Vs a pipeline / middleware. A pipeline runs every stage in order. A Chain is the "stop at the first that can handle it" variant, though the two blur: a filter chain is a CoR where nobody consumes.

    Vs Observer. Observer broadcasts the same event to every listener. A Chain passes one request along, and usually one handler consumes it.

    Vs a switch statement. A switch is closed: adding a case edits it. A Chain is open: a new handler is a new link, and order is data.

    They Say: "now the machine is out of 500s"

    • With it: the 500 handler sees stock 0, gives none, passes the whole remainder on. The chain still works.
    • Without: a new guard in the middle of the if-ladder, and you re-test every branch.

    Watch Out For

    • Decide up front: "first handler that can, wins and stops" or "every handler may take a piece". They lead to different handle() bodies.
    • A request can fall off the end unhandled, and a take-a-piece chain is greedy, so it can refuse a split that exists (₹600 from a ₹500 and three ₹200s stalls). Use DP when that matters.
    • Do not let a handler know its position in the chain. It only knows next.
    • Keep each handler single-purpose. One denomination, one rule.
    • Build the chain from config so operations can reorder or disable steps without a redeploy.
