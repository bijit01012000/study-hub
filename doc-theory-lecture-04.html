    Lecture 04 — Dependency Injection & IoC Explained

    19 sections · 3,658 words

    Lecture 04

    Scope evidence: "Dependency Injection & IoC Explained | Loose Coupling in Spring" (playlist map, verified). Repo lecture folder is a CoreDemo Maven project (in.coderarmy packages) plus these notes.

    Java already gives us classes, objects, constructors, interfaces, inheritance, and packages, so it is fair to ask why Spring Core exists at all. This lecture answers that by following one small requirement change: an order service that starts by sending email and later must send SMS. Step by step, the design moves from a class that builds its own dependency, to an interface, to Dependency Injection, and finally to the Spring IoC Container that does the wiring for us. The point is not Spring syntax yet; it is the reasoning that makes Spring necessary.

    1. Why Do We Need Spring Core?

    Java ships with powerful building blocks:

    • Classes
    • Objects
    • Constructors
    • Interfaces
    • Inheritance
    • Packages

    A natural question follows: if Java already gives us all these features, why do we need Spring Core?

    Spring Core is not mainly about building web applications. That part comes later with Spring MVC and Spring Boot. The core idea of Spring is simpler:

    Spring helps us create objects, manage dependencies, and connect objects together in a clean and scalable way.

    In small programs, object creation looks easy. But in real applications, one class depends on another class, which depends on another class, and this chain keeps growing. That is exactly where Spring Core becomes useful.

    Small program:  few objects, easy wiring
Real program:   object -> object -> object -> ... (chain keeps growing)

    Important: Spring Core is the foundation. Before Spring MVC, Spring Boot, Spring Data JPA, or Spring Security, you must understand this core idea of creating, managing, and connecting objects.

    2. Understanding a Dependency

    Suppose we have an EmailService class with a sendEmail() method:

    // Incorrect: OrderService builds its own concrete dependency
class EmailService {
    public void sendEmail() {
        System.out.println("Email sent");
    }
}

class OrderService {
    private EmailService emailService = new EmailService();

    public void placeOrder() {
        System.out.println("Order placed");
        emailService.sendEmail();
    }
}

    Now suppose OrderService needs to send an email after placing an order. Here, OrderService depends on EmailService. In simple words:

    A dependency is something a class needs in order to complete its work.

    So the line private EmailService emailService = new EmailService(); means OrderService is creating its own dependency. It works, but it creates a design problem.

    3. The Problem: Tight Coupling

    There are two broad design styles:

    • Tightly Coupled Design -> Hard to change
    • Loosely Coupled Design -> Easier to change

    Real-life example: imagine a person wants to travel from Delhi to Chandigarh.

    • Tightly coupled thinking: "I can travel only by this one specific car, with this one specific driver, from this one specific company." If that car is unavailable, the person is stuck.
    • Loosely coupled thinking: "I need transportation. It can be a car, bus, train, or cab." Here the person is not dependent on one fixed option; the person only cares about the service: transportation.
    Aspect Tightly Coupled Design Loosely Coupled Design
    Dependency target One specific concrete class An abstract service / interface
    Effect of change Hard to change Easier to change
    Real-life analogy One specific car, driver, company Any transportation
    Testing Hard, needs the real thing Easy, can substitute a fake
    Reuse Poor, bound to one implementation Good, works with many implementations
    Flexibility Low High

    4. Tight Coupling in Code, and What It Exactly Is

    In the previous example, OrderService directly creates EmailService:

    OrderService
     |
     | directly creates
     v
EmailService

    Now suppose the requirement changes. Instead of email, we now need to send SMS. We write a SmsService class with a sendSms() method, and then we must modify OrderService to hold private SmsService smsService = new SmsService(); and call smsService.sendSms().

    The problem is not that the notification requirement changed. The real problem is that a change in notification logic forced us to modify OrderService. That means OrderService is tightly coupled to a specific notification class.

    Tight coupling means:

    One class is directly dependent on a specific concrete class.

    In our case, OrderService is directly dependent on EmailService. This makes the code harder to change, test, and reuse.

    Use Code shape Verdict
    Incorrect private EmailService emailService = new EmailService(); Concrete class chosen inside the business class
    Better private NotificationService notificationService = new EmailService(); Interface type, still creating the object inside
    Correct Constructor receives NotificationService from outside No creation inside; loosely coupled

    5. First Improvement: An Interface

    To make the design better, we can introduce a NotificationService interface with a void sendNotification() method. Then different notification services implement it: EmailService and SmsService both override sendNotification(). Now OrderService can depend on the interface instead of a concrete class:

    // Correct: depend on the interface and receive it through the constructor
interface NotificationService {
    void sendNotification();
}

class OrderService {
    private NotificationService notificationService;

    OrderService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    public void placeOrder() {
        System.out.println("Order placed successfully");
        notificationService.sendNotification();
    }
}

    This is better than before because the variable type is now an interface: NotificationService. But there is still one issue when the field itself does the creation.

    6. Why an Interface Alone Is Not Enough

    Even though we are using an interface, this declaration is still a problem: private NotificationService notificationService = new EmailService();. Because the object creation is still concrete - new EmailService() - OrderService is still deciding which implementation to use. The important point is:

    Creating objects is not the problem. Creating them in the wrong place is the problem.

    OrderService is a business class. Its job should be order-related logic, not deciding which notification object to create. Currently, OrderService is doing two things:

    1. Handling order-related logic.
    2. Creating and deciding the notification service.

    This breaks two important design principles:

    • S -> Single Responsibility Principle
    • O -> Open-Close Principle

    The main idea is:

    Dependency is normal. Tight dependency is the problem.

    Interviewer's perspective: The decoupling journey has a trap. Using an interface already feels "done," but the new keyword still hard-codes the choice. The genuine fix is moving creation out of the class, and strong candidates can explain why the interface alone was only half the solution.

    7. The Solution: Dependency Injection

    Instead of creating the dependency inside OrderService, we provide the dependency from outside, as the OrderService constructor in Section 5 shows. Now OrderService does not create EmailService or SmsService. It simply says:

    "Give me something that can send a notification."

    That "something" is represented by the NotificationService interface. The class no longer knows or cares which implementation it is holding.

    Main
     |
     | creates EmailService
     v
NotificationService
     |
     | injected into
     v
OrderService  ->  calls notificationService.sendNotification()

    Three things are now true at once:

    • OrderService depends only on NotificationService.
    • OrderService does not create EmailService or SmsService.
    • OrderService receives its dependency from outside.

    8. What Is Dependency Injection?

    Dependency Injection means:

    A class receives the objects it depends on from outside, instead of creating those objects itself.

    Object creation now happens outside, in Main:

    public class Main {
    public static void main(String[] args) {
        NotificationService notificationService = new EmailService();
        OrderService orderService = new OrderService(notificationService);

        orderService.placeOrder();
    }
}

    Now the dependency is provided from outside. This means:

    • OrderService depends only on NotificationService.
    • OrderService does not create EmailService.
    • OrderService receives the dependency from outside.

    This is called Dependency Injection.

    A simpler way to remember it:

    Do not create your dependency. Receive your dependency.

    Or:

    A class should ask for what it needs, not build everything by itself.

    Mnemonic: DI = "Do not Instantiate; Inject."

    Two important clarifications:

    • Dependency Injection is not only a Spring concept. It is a design principle that we can use in plain Java also.
    • Spring did not invent Dependency Injection. Spring automates it.

    Golden rule: A dependency is never a problem by itself. The problem is a class deciding which concrete dependency to build. Receive it; do not build it.

    9. Benefits of Dependency Injection

    Benefit 1: Easy to change implementation. If we want to switch from email to SMS, we do not need to change OrderService. We only change the object passed from outside: NotificationService notificationService = new SmsService(); and then pass it into the constructor. OrderService remains unchanged.

    Benefit 2: Easier to test. For testing, we may not want to send a real email or SMS, so we can create a fake implementation, FakeNotificationService, that implements NotificationService and prints "Fake notification for testing" from its sendNotification() method. Now we can test OrderService without depending on real email or SMS logic. In the CoreDemo repo, implementations such as EmailService, SmsService, PopUpNotificationService, and FakeEmailService all sit behind the NotificationService interface for exactly this reason.

    Benefit 3: More reusable code. The same OrderService can work with multiple implementations: EmailService, SmsService, WhatsAppService, FakeNotificationService. This makes the design flexible and reusable.

    Benefit Before DI After DI
    Change implementation Edit OrderService Change only the object passed from Main
    Testing Must use the real email/SMS Swap in a fake implementation
    Reuse One hard-coded implementation Works with many implementations
    Coupling Tight Loose

    10. Types of Dependency Injection

    There are mainly three common types of Dependency Injection.

    1. Constructor Injection. The dependency is provided through the constructor, as shown in Section 5. Constructor injection is usually preferred because it makes required dependencies clear. If OrderService cannot work without NotificationService, constructor injection is a good choice.

    2. Setter Injection. The dependency is provided through a setter method:

    // Correct: setter injection suits optional or changeable dependencies
public void setNotificationService(NotificationService notificationService) {
    this.notificationService = notificationService;
}

    Setter injection is useful when the dependency is optional or can be changed later.

    1. Field Injection. In Spring, we will also discuss field injection later.
    Aspect Constructor Injection Setter Injection Field Injection
    How provided Through the constructor Through a setter method Directly into the field
    Best when Dependency is required Dependency is optional or changeable Covered later with Spring
    Clarity Highest: required deps visible Medium Low
    Object state Fully initialized after construction May be set after construction Set by the framework
    Recommendation Usually preferred For optional dependencies Discussed later in Spring

    11. What Is IoC? (and How It Relates to DI)

    IoC stands for Inversion of Control. To understand IoC, first ask: in the earlier code, who was controlling the creation of EmailService? The answer is OrderService was controlling object creation. So the control was inside OrderService.

    After Dependency Injection, OrderService no longer creates EmailService. The object is created outside and passed to OrderService. This movement of control is called Inversion of Control.

    Simple definition:

    • Earlier: the class created what it needed.
    • Now: the class receives what it needs.

    That reversal is called Inversion of Control. It is called "inversion" because the normal control flow is reversed:

    Earlier:
OrderService
     |
     | creates
     v
EmailService

After Dependency Injection:
Main
     |
     | creates
     v
EmailService
Main provides EmailService
     |
     | to
     v
OrderService

    So the control moved from inside the class to outside the class.

    Now the relationship between IoC and DI. IoC and DI are closely related, but they are not exactly the same. IoC is the idea (the principle). DI is the technique to achieve that principle. Dependency Injection is one way to implement that idea. When we give dependencies from outside instead of creating them inside the class, we are using Dependency Injection to achieve Inversion of Control.

    Concept Role Meaning
    IoC Principle Control of object creation moves out of the class
    DI Technique Provide dependencies from outside instead of creating them
    Relationship DI implements IoC DI is one way to achieve the IoC principle

    Two clarifications worth stating plainly:

    • IoC is not a Spring invention. Any code where an outside party creates and hands over the dependency is already inverted.
    • DI is not the only possible technique, but it is the one this course uses, and the one Spring automates.

    12. Where Spring Fits In: The IoC Container, Spring Core, and Beans

    In plain Java, we moved object creation outside OrderService. But now Main is doing all the object creation and wiring: new EmailService() and new OrderService(notificationService). This is fine for small applications. But in large applications, there may be hundreds of classes and dependencies. If Main creates and connects everything manually, it becomes messy. So we need something that can:

    • Create objects
    • Manage objects
    • Connect objects together

    That is where Spring comes in.

    The Spring IoC Container is responsible for:

    • Creating objects
    • Managing objects
    • Injecting dependencies
    • Connecting classes together

    In plain Java, Main was acting like a small container. In Spring, the Spring IoC Container does this work automatically.

    At a high level, Spring Core does three major things:

    1. Creates objects.
    2. Manages objects.
    3. Connects objects together.

    This is the foundation of Spring. Mnemonic for the three jobs: CMC = Create, Manage, Connect.

    What is a Bean? In normal Java, we call them objects. In Spring, objects managed by Spring are called beans.

    Important: Every Spring bean is an object, but every object is not necessarily a Spring bean.

    Example: EmailService emailService = new EmailService(); is a normal Java object. But if Spring creates and manages EmailService, then it becomes a Spring bean.

    13. Manual Java Flow vs Spring Flow

    Plain Java flow:

    Main
     |
     | creates
     v
EmailService
Main
     |
     | creates
     v
OrderService
Main injects EmailService into OrderService

    In this flow, Main is responsible for creating and connecting objects.

    Spring flow:

    Spring IoC Container
     |
     | creates
     v
EmailService Bean
Spring IoC Container
     |
     | creates and injects dependency
     v
OrderService Bean

    In this flow, Spring creates the objects and connects them automatically.

    Aspect Manual Java Flow Spring Flow
    Who creates objects Main Spring IoC Container
    Who injects dependencies Main Spring IoC Container
    Control In our hands, inside Main Inverted to the container
    Boilerplate Grows with every class Handled by Spring
    Large applications Becomes messy Clean and scalable
    Resulting objects Ordinary Java objects Spring beans

    The shift is easy to state and easy to miss: in manual flow, we are the container; in Spring flow, the container is Spring. Everything explained in this lecture is the reasoning behind moving that responsibility out of our hands.

    14. Myth vs Reality

    Myth Reality
    "Dependency Injection is a Spring concept" DI is a plain design principle usable in core Java; Spring merely automates it
    "Using an interface makes the design loosely coupled" Only if the object creation also moves out; new EmailService() inside the class still couples it
    "Creating dependencies is the problem" Creating is fine; creating them in the wrong place is the problem
    "IoC and DI are the same thing" IoC is the principle; DI is one technique that implements it
    "Spring creates all Java objects" Only objects it manages are beans; a plain new object is not a bean
    "Field, setter, and constructor injection are equally clear" Constructor injection makes required dependencies explicit and is usually preferred
    "OrderService is wrong to depend on anything" A dependency is normal; a tight dependency is the problem

    15. Common Trap Questions

    Trap 1 — "Spring Core is for building web applications." Verdict: False. Spring Core is about creating, managing, and connecting objects. Web support arrives later with Spring MVC and Spring Boot.

    Trap 2 — "If OrderService uses the NotificationService interface, it is loosely coupled." Verdict: Not yet. The declaration says private NotificationService notificationService = new EmailService();, so OrderService still chooses the implementation. Loose coupling needs the creation moved outside.

    Trap 3 — "Dependency Injection means Spring injects dependencies." Verdict: Too narrow. DI is a plain Java design principle; Main can inject by hand. Spring only automates the injection.

    Trap 4 — "IoC and DI are interchangeable words." Verdict: No. IoC is the principle (control of creation moves outside the class); DI is the technique that achieves it.

    Trap 5 — "Two responsibilities in one class are fine as long as it works." Verdict: It works but violates the Single Responsibility Principle and the Open-Close Principle, which is exactly why OrderService had to be edited for an SMS change.

    Trap 6 — "Every Java object is a Spring bean." Verdict: False. Every bean is an object, but an object created with plain new and not managed by Spring is not a bean.

    Trap 7 — "Setter injection is always better because it is flexible." Verdict: Misleading. Setter injection suits optional or changeable dependencies; constructor injection is usually preferred because required dependencies become explicit.

    16. Points to Remember

    1. Spring Core exists to create, manage, and connect objects cleanly and scalably, not mainly for the web.
    2. A dependency is something a class needs to complete its work; OrderService depends on NotificationService.
    3. Tight coupling means one class directly depends on a specific concrete class, making code hard to change, test, and reuse.
    4. Introducing an interface changes the variable type but new EmailService() inside the class still hard-codes the choice.
    5. Creating objects is not the problem; creating them in the wrong place is the problem.
    6. Dependency Injection means a class receives its dependencies from outside instead of creating them: "Do not create your dependency. Receive your dependency."
    7. Benefits of DI are easy to change, easier to test with fakes, and more reusable code across implementations.
    8. The three common DI types are constructor, setter, and field injection; constructor injection is usually preferred for required dependencies.
    9. IoC is the principle that control of object creation moves outside the class; DI is the technique that implements it.
    10. Spring Core creates, manages, and connects objects through the Spring IoC Container, and Spring-managed objects are called beans.

    17. Likely Interview Questions

    Question Crisp Answer
    Why do we need Spring Core when Java already has classes and interfaces? To create, manage, and connect objects in a clean and scalable way as dependency chains grow.
    What is a dependency? Something a class needs to complete its work; OrderService needs a notification service.
    What is tight coupling? One class is directly dependent on a specific concrete class, making change, testing, and reuse hard.
    Why is using an interface alone not enough? If new EmailService() still runs inside the class, the class still chooses the implementation.
    What is Dependency Injection? A class receives the objects it depends on from outside instead of creating them itself; it is a plain design principle, not Spring-specific.
    What are the benefits of DI? Easy to change implementation, easier to test with fakes, and more reusable code.
    What are the types of DI? Constructor injection, setter injection, and field injection.
    Why is constructor injection usually preferred? It makes required dependencies explicit and guarantees the object is initialized.
    What is IoC? Inversion of Control: control of object creation moves from the class itself to an external system.
    What is the relationship between IoC and DI? IoC is the principle; DI is one technique used to achieve it.
    What is a Spring bean? An object that Spring creates and manages; every bean is an object, but not every object is a bean.
    What does the Spring IoC Container do? It creates objects, manages them, injects dependencies, and connects classes together.
