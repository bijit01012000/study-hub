    The project you can defend

    1 sections · 572 words

    Module 02 · 9 questions · 1 practical drill

    Defend what you actually built, at whatever scale you built it.

    This module drills one project from nine angles, the way a real interviewer would. It assumes you have not shipped GenAI in production, most candidates for these roles have not. What you do have is a side project, a proof of concept, or a work task that touched an LLM, and that is plenty if you can defend it with real decisions and real numbers. A weak answer lists tools. A strong one traces one request end to end, names what was actually built versus borrowed, and owns a real failure. The scenario running through all nine questions is one support assistant, drilled from nine different directions, because that is exactly what a real deep dive does to your one real project.

    Inside this module: Individual scope · Decisions vs defaults · What broke · Production delta

    Retries are part of the contract. Design the duplicate path before production does it for you.

    Diagram labels: CLIENT, API, DEPENDENCY, request, 200ms budget, retry + same key.

    How to work this module: Answer each question out loud in 90 seconds before reading the model answer. Then check you named a number, the alternative you rejected, and what actually failed. Those three are what the follow-ups are hunting for.

    Concept checkpoints

    Q2.1 — Walk me through the most substantial thing you've built with an LLM, start anywhere.

    What it really tests: Whether the candidate can narrate one real project as a sequence of decisions, or only has a tool tour.

    Q2.2 — Why use an LLM here at all? What did you consider and rule out first?

    What it really tests: Whether a simpler approach was weighed with real evidence, or an LLM was the default from the start.

    Q2.3 — Which parts of that system were the model's, and which parts were yours?

    What it really tests: Whether a precise line exists between what the model contributes and what the surrounding code contributes.

    Q2.4 — What did the first version get wrong once real people actually used it?

    What it really tests: Whether a specific real failure story exists, not a sanitised "tuned the prompts, got better".

    Q2.5 — How did you actually know it was working? What did you measure?

    What it really tests: Whether any real evaluation happened, even a small one, or outputs were just read and judged by feel.

    Q2.6 — What did it actually cost to run, and how did you find that out?

    What it really tests: Real per-request cost attribution, versus a vague "the bill seemed fine" with no breakdown.

    Q2.7 — If you were rebuilding this today, what would you do differently?

    What it really tests: Whether the reflection names a real decision and its real cost, not a safe "add more tests" deflection.

    Q2.8 — This was a side project. What would have to change to run it at real scale?

    What it really tests: Whether the gap between a personal project and production is reasoned honestly, not "add more servers".

    Q2.9 — DRILL: rewrite five bullets about your LLM project as decisions, not features.

    What it really tests: Forces vague project language into a set of real, defensible decisions before an interviewer finds the gap.
