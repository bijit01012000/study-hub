    Design a Notification Service

    15 sections · 1,960 words

    LLD Design Problems, problem 19 of 20.

    The Ask

    Build

    • Notify a user across EMAIL, SMS, PUSH, IN_APP.
    • Fired by a domain event: "order shipped", "password changed".
    • Per-user channel preferences decide where it goes.
    • A do-not-disturb window skips channels — unless the notification is CRITICAL.
    • Dedup: same key inside a window is dropped.
    • Rate-limit per user.
    • Render the body per channel from a Template.
    • Fan out: each channel sends independently.
    • Each send: retry, exponential backoff, jitter; after N -> dead-letter.

    Skip

    • Provider SDKs (SES / Twilio / FCM).
    • A template-authoring UI.
    • Open / click analytics.
    • User management, a preference UI.
    • A real message broker (name it).
    • Localisation detail.

    Our Model

    A domain event is published, a listener calls notify, a filter chain trims the channel set, a Template renders one Message per channel, and each channel is sent on its own task wrapped in retry.

    Actors and classes

    • OrderService — ship(o), changePassword(u); calls bus.publish(new OrderShipped(userId)).
    • EventBus (singleton) — subscribe(Class, Listener), publish(DomainEvent): void. In-process; a broker swaps in here.
    • NotificationListener (subscriber) — svc: NotificationService; onEvent(DomainEvent e) calls svc.notify(e). Maps event to userId, type, key.
    • NotificationService — chain: Filter (prefs > DND > dedup > rate), templates: TemplateRegistry, channels: ChannelFactory, pool: ExecutorService (one task per channel), dlq: DeadLetterStore; notify(Event e): void, resolveChannels(User u, Event e): List<Channel>, send(Message m, Channel c): Result, retry(Message m, int attempt): void.
    • Filter (interface, strategy) — handle(FilterCtx c): void; a chain of responsibility, drop a channel or dropAll and stop. PreferenceFilter, DndFilter, DedupFilter, RateLimitFilter.
    • FilterCtx — user: User, event: DomainEvent, dedupKey: String, priority: Priority, channels: Set<ChannelType> (mutable); drop(ChannelType t), dropAll(String reason). CRITICAL skips DndFilter + RateLimitFilter.
    • Template (interface) — render(ChannelType c, Map model): Message; one per event type, a body per channel. OrderShippedTemplate, PasswordChangedTemplate. TemplateRegistry — forEvent(String type): Template; unknown type -> skip + log, never crash the fan-out.
    • Message (value, one per channel) — to: String, channel: ChannelType, subject, body: String, notifId: String, idempotencyKey: String. key = hash(notifId + channel), built by the Template.
    • NotificationChannel (interface) — send(Message m): SendResult, type(): ChannelType. SES / Twilio / FCM sit behind this as a thin seam. EmailChannel, SmsChannel, PushChannel, InAppChannel.
    • RetryingChannel (decorator) — inner: NotificationChannel, max, base, cap, jitter; send(m) tries inner.send(m); on TRANSIENT, schedules attempt + 1 after backoff(n). backoff(n) = min(base * 2^n, cap) + rand(jitter). RateLimitedChannel, MetricsChannel wrap the same way.
    • SendResult (value) — status: SENT | TRANSIENT | PERMANENT, providerId, error: String. TRANSIENT -> retry; PERMANENT -> DLQ now.
    • DeadLetterStore — save(FailedSend f): void (message + channel + attempts + lastError). A job or a human drains it.

    Relationships

    An event publishes on the bus; the listener maps it; the service runs the filter chain, looks up a Template, renders per channel, and fans out to channels. A RetryingChannel decorates any channel.

    Key operations

    1. notify(Event e): void — loads the user, builds a FilterCtx, runs the chain, renders one Message per surviving channel, then submits one task per channel. Returns at once; it never waits on a provider.
    2. resolveChannels(User u, Event e): List<Channel> — preferences minus the DND window, unless priority is CRITICAL. Then dedup on the key and the per-user rate limit. Empty list -> nothing sends, no error.
    3. send(Message m, Channel c): Result — one provider call behind the channel Strategy. Idempotent on m.idempotencyKey. Returns SENT, TRANSIENT (retry) or PERMANENT (straight to the DLQ).
    4. retry(Message m, int attempt): void — re-runs send after backoff(attempt) — base times 2^n plus jitter, capped. After MAX_ATTEMPTS it writes to the dead-letter store. Never a tight loop.

    The invariants

    • send c when c in prefs, not in DND (or CRITICAL), key not seen.
    • Each surviving channel is its own task, so a slow provider never blocks the others.
    • To DLQ when attempts == MAX or the result is PERMANENT.

    Recall drill: cover the operations column, write the four with their guarantee. Most people forget notify returns before any provider is called.

    The One Run to Hold in Your Head

    "Order shipped" fires for a user at 02:30. She wants EMAIL + PUSH, DND is 22:00-07:00, nothing critical. The same event is redelivered a minute later. What goes out, on which channel, and when does EMAIL's retry give up?

    Preferences give EMAIL + PUSH; DND drops PUSH, so only EMAIL sends (DND skips channels unless CRITICAL). The redelivery is dropped by DedupFilter on the key. EMAIL's transient failure backs off 1s, 2s, then dead-letters after 3 tries.

    The Change

    They ask to "stop hammering users — roll low-priority notifications into one 9am digest". A DigestBatcher coalesces non-critical messages per user into a scheduled bucket; a timer flushes the bucket as one send. CRITICAL still goes straight through. Chain of Responsibility gains a link, the channels never change.

    What the Picture Can't Show

    Two races. A retry can fire after the first attempt already delivered (a slow provider ACK) — the fix is an idempotencyKey per notification + channel, deduped at the provider or a sent-log. And a crash mid fan-out loses the rest — persist the intent first (an outbox), a worker resumes it.

    If They Make You Code It

    Notify and sendWithRetry, the whole thing:

    class NotificationService {
    Filter chain;                           // prefs > DND > dedup > rate
    TemplateRegistry templates;
    ChannelFactory channels;
    ExecutorService pool;                   // fan-out, one task per channel
    ScheduledExecutorService clock;
    DeadLetterStore dlq;

    void notify(DomainEvent e) {
        User u = users.load(e.userId());
        var c = new FilterCtx(u, e, e.key(), e.priority());
        chain.handle(c);                    // drops channels, or all
        if (c.channels().isEmpty()) return;
        Template t = templates.forEvent(e.type());   // or skip
        for (ChannelType ct : c.channels()) {
            Message m = t.render(ct, e.model());     // one per channel
            Channel ch = channels.get(ct);
            pool.submit(() -> sendWithRetry(m, ch, 0));
        }
    }

    void sendWithRetry(Message m, Channel ch, int attempt) {
        SendResult r = ch.send(m);          // m carries an idempotencyKey
        if (r.status() == SENT) return;
        int n = attempt + 1;
        if (r.status() == PERMANENT || n == MAX_ATTEMPTS) {
            dlq.save(new FailedSend(m, ch.type(), n, r.error()));
            return;
        }
        Duration d = backoff(attempt);      // base*2^n + jitter, capped
        clock.schedule(() -> sendWithRetry(m, ch, n), d);
    }
}

    The Four Hazards

    1. One provider blocks the fan-out. If channels send in a loop on one thread, a hung EMAIL provider stalls PUSH, SMS and the caller behind it. Submit one task per channel, each with a timeout, so SMS must not wait on PUSH.
    2. Retry storm. A provider 500s and every worker retries at once, on a tight loop — the provider and the queue both fall over. Exponential backoff + jitter + a max-attempts cap, then dead-letter; never a spin.
    3. Duplicate send on retry. The first attempt actually delivered, but the ACK was slow, so a retry fired and the user gets two SMS. An idempotencyKey per notification + channel, deduped at the provider or a sent-log.
    4. DND silences a critical alert. Quiet hours are respected, but a password-changed security alert still has to go out at 2am. A priority flag — CRITICAL bypasses DndFilter and RateLimitFilter, nothing else.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. pool.submit(() -> sendWithRetry(...)) — each channel is its own task. A hung SMS provider never blocks PUSH.
    2. ch.send(m) with m.idempotencyKey — a retry after a slow success is dropped at the provider, not sent twice.
    3. backoff(attempt) + MAX_ATTEMPTS then dlq.save — bounded backoff with jitter, never a tight loop.

    Running the Fan-Out

    Approach Caller waits A crash means Retry home Back-pressure Reach for it
    Inline send (the default) on the slowest provider the notification is lost the caller's loop none, threads pile up a script, low volume
    Queue + worker pool per channel returns at once resumes if the intent was persisted a delayed executor / delay queue a bounded queue per channel a service, real traffic
    External broker + consumers (the HLD build) returns at once broker replays consumer redelivery consumer lag cross-service, huge fan-out

    A bounded queue with a per-channel worker pool, retries on an in-process delayed executor (a delay queue if it must survive a restart). Persist the intent first — an outbox — so a crash resumes mid fan-out. A real broker is the same shape in another process: the HLD answer.

    Rejection Signals

    These end the interview:

    • Fanning out on the caller's thread — one slow provider stalls every other channel and the request.
    • Retrying in a tight loop with no cap — a dead provider becomes a self-inflicted DoS.
    • No idempotency key — a retry after a slow success sends the same SMS twice.
    • A DND window that also silences a CRITICAL security alert — quiet hours need a bypass.
    • A switch on channel type inside the service instead of a NotificationChannel strategy.
    • Checking the rate limit before preferences — burning tokens on a user who opted out.

    Patterns Used

    Strategy — a NotificationChannel per channel, and a Template per event. Observer — the service subscribes to domain events on the bus. Decorator — retry / rate-limit / metrics wrap a channel. Chain of Responsibility — prefs -> DND -> dedup -> rate-limit.

    Say It Like This

    "An event is published on a bus; a listener calls notify. A chain of filters — preferences, DND, dedup, rate-limit — trims the channel set; CRITICAL skips DND and rate-limit. A Template renders one Message per surviving channel. Each channel is a Strategy; the service submits one task per channel so they never block each other. Every send is wrapped by a decorator that retries with backoff and jitter, then dead-letters after N."

    The Follow-ups That Decide It

    1. One provider hangs 30s. The other channels? Each channel is its own task; a timeout fails it, others unaffected.
    2. A retry fires but the first attempt delivered. idempotencyKey per notif + channel, deduped at the provider.
    3. 2am, a password-changed alert must go. CRITICAL priority bypasses DndFilter and RateLimitFilter.
    4. The same event is delivered to the listener twice. DedupFilter on the key within a window drops the second.
    5. A provider is down for an hour. Transient fails back off to MAX, then the DLQ; a job drains it.
    6. "Roll 3am emails into a morning digest." A DigestBatcher link in the chain; critical still goes straight through.
    7. Add WhatsApp as a channel. A new NotificationChannel impl + a factory line; nothing else.
    8. The process dies mid fan-out. Persist the intent first (outbox); a worker picks up the unfinished sends.

    Deliberately Not Built

    • Provider SDK integration — SES / Twilio / FCM behind the channel seam. The seam is the point; the integration is not.
    • A template-authoring UI — how a Template is written and stored. Assume it is registered.
    • Open / click analytics — a separate pipeline reading delivery events. A different question.
    • A real message broker — Kafka / SQS behind EventBus. Named, not built — the HLD version.
    • The outbox / no-lost-sends — persist the intent, a worker resumes it. Name it and move on.
