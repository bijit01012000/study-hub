    Lecture 15 — Spring MVC Architecture

    22 sections · 4,900 words

    Lecture 15

    Scope evidence: "Spring MVC Architecture | DispatcherServlet, HandlerMapping & JSP Flow" (playlist map, verified). Repo folder contains two Maven projects: SpringMVCDemo (in.strikes.Main, config.WebConfig, controller.StudentController, entity.Student, repository.StudentRepository, service.StudentService) and JSPDemo (in.strikes.Main, config.WebConfig, controller.HelloController, webapp/WEB-INF/views/home.jsp) plus notes.

    Spring MVC is the web framework that receives HTTP requests, finds the right controller method, and sends a response back. This lecture opens the black box we have been treating as magic: DispatcherServlet, HandlerMapping, HandlerAdapter, argument resolvers, and Jackson. It then builds the same Student API twice, first by hand on plain Spring MVC with embedded Tomcat, then as a Spring Boot starter app, and finishes with the JSP view flow so we can see that "MVC" covers both JSON APIs and HTML pages.

    1. What Is Spring Web MVC?

    Spring Web MVC, commonly called Spring MVC, is Spring's web framework used to build:

    • web applications;
    • REST APIs;
    • backend services that handle HTTP requests.

    Officially, its module name is spring-webmvc. Spring MVC is built on top of the Servlet API. That means that even though we never write doGet() or doPost() directly, the application still works through servlet-based request handling internally.

    Cell Meaning
    Name Spring Web MVC (Spring MVC)
    Artifact spring-webmvc
    Built on The Servlet API
    We write @GetMapping, @PostMapping, controller methods
    We do not write doGet(), doPost(), doPut(), doDelete()
    Handles Web pages, REST APIs, HTTP backend services

    Important: Spring MVC never removes servlets; it hides them. Somewhere under every @GetMapping a servlet is still receiving the request. The central servlet is DispatcherServlet.

    2. Spring Boot's Role: Automation, Not Replacement

    Spring Boot does not replace Spring MVC. Spring Boot simply makes Spring MVC easier to use. In a traditional Spring MVC application we manually configure many things:

    • Tomcat setup;
    • Spring application context;
    • DispatcherServlet registration;
    • DispatcherServlet mapping;
    • component scanning;
    • JSON conversion.

    Spring Boot does most of this automatically. In a Spring Boot CRUD project we usually write methods like @GetMapping("/{id}") public Student getStudent(@PathVariable Integer id) { return studentService.getStudent(id); }. We do not write doGet(), doPost(), doPut(), or doDelete(). But internally, someone still has to receive the HTTP request from Tomcat, understand the URL and the HTTP method, and then call the correct controller method. That internal web system is Spring MVC, and its central servlet is DispatcherServlet.

    Interviewer's perspective: "Is Spring MVC separate from Spring Boot?" A strong answer: Spring MVC is the web framework (a module of the Spring Framework); Spring Boot is the automation layer that configures it. Boot wraps Spring MVC, it does not replace it.

    3. DispatcherServlet: The Front Controller

    DispatcherServlet is the front controller of Spring MVC. It receives incoming HTTP requests and coordinates the complete request-processing flow. A simple mental model:

    Client
   |
   v
Tomcat
   |
   v
DispatcherServlet
   |
   v
Controller Method
   |
   v
Response

    Why do we need it? In a pure Servlet application we may create a different servlet for every URL:

    /student/create  -> CreateStudentServlet
/student/get     -> GetStudentServlet
/student/update  -> UpdateStudentServlet
/student/delete  -> DeleteStudentServlet

    Each servlet may handle its own URL matching, request parsing, response writing, JSON conversion, and error handling. This becomes repetitive as the project grows. Spring MVC solves this with one central servlet: all requests first come to DispatcherServlet, and it forwards each request to the correct controller method. That is why it is called DispatcherServlet: it dispatches the request to the correct handler.

    Pure Servlet approach Spring MVC approach
    One servlet per URL family One front controller for all URLs
    URL matching repeated in each servlet HandlerMapping maps URLs centrally
    JSON conversion repeated per servlet HttpMessageConverter + Jackson centrally
    Error handling scattered Coordinated through the front controller
    Hard to scale with features Grows cleanly with controllers

    DispatcherServlet is not magic. It is still a servlet. Tomcat knows how to call servlets, so when a request comes, Tomcat sends the request to DispatcherServlet. DispatcherServlet then takes help from other Spring MVC components to process the request.

    4. High-Level Spring MVC Flow and Its Components

    The complete request path, end to end:

    Client sends HTTP request
   |
   v
Tomcat receives request
   |
   v
Tomcat sends request to DispatcherServlet
   |
   v
DispatcherServlet asks HandlerMapping:
"Which controller method should handle this request?"
   |
   v
HandlerMapping returns the matching controller method
   |
   v
DispatcherServlet uses HandlerAdapter to call that method
   |
   v
Request data is assigned to method parameters
   |
   v
Controller calls Service
   |
   v
Service calls Repository
   |
   v
Response is returned
   |
   v
Spring converts Java object to JSON
   |
   v
Client receives response

    DispatcherServlet is the coordinator. It does not do everything by itself; it takes help from multiple Spring MVC components.

    Component Responsibility
    DispatcherServlet Central servlet that receives and coordinates requests
    HandlerMapping Finds which controller method should handle the request
    HandlerAdapter Actually invokes the selected controller method
    HandlerMethodArgumentResolver Resolves method parameters like path variables, query parameters, request body
    HttpMessageConverter Converts JSON to Java object and Java object to JSON
    Jackson Common JSON library used for the conversion

    Mnemonic for the main flow: T-D-H-A-C-S-R-R - "Tommy Drives His Aston Car, Serving Real Responses" (Tomcat, DispatcherServlet, HandlerMapping, HandlerAdapter, Controller, Service, Repository, Response).

    Golden rule: DispatcherServlet coordinates, HandlerMapping finds, HandlerAdapter invokes, argument resolvers fill parameters, and message converters translate. Every component has exactly one job.

    5. HandlerMapping: Finding the Right Controller Method

    DispatcherServlet receives the request, but it does not directly know which controller method to call. For example, if this request comes:

    GET /students/1

    DispatcherServlet needs to know that this should call the method getStudent(Integer id) mapped by @GetMapping("/{id}"). This matching is done by HandlerMapping. HandlerMapping is the Spring MVC component that maps an HTTP request to the correct controller method. It checks things like the URL path, the HTTP method, controller annotations, and method-level mappings.

    Example: a StudentController annotated with @RestController and @RequestMapping("/students") declares @GetMapping("/{id}") public Student getStudent(@PathVariable Integer id) and @PostMapping public Student createStudent(@RequestBody Student student).

    Spring internally understands:

    GET  /students/1  -> getStudent()
POST /students    -> createStudent()

    Even if two URLs look similar, the HTTP method can change the meaning:

    GET  /students  -> fetch students
POST /students  -> create student

    When Does HandlerMapping Build This Mapping?

    When the Spring MVC application starts:

    1. @ComponentScan finds controller classes.
    2. Spring creates controller objects as beans.
    3. HandlerMapping reads annotations like @RequestMapping, @GetMapping, @PostMapping, @PutMapping, and @DeleteMapping.
    4. It builds an internal mapping table.

    Example internal mapping table:

    GET    /students/{id}  -> StudentController.getStudent()
POST   /students       -> StudentController.createStudent()
PUT    /students/{id}  -> StudentController.updateStudent()
DELETE /students/{id}  -> StudentController.deleteStudent()

    At runtime, HandlerMapping uses this prepared mapping table to quickly find the correct controller method. HandlerMapping only finds the correct method; it does not execute it.

    6. HandlerAdapter: Actually Invoking the Method

    HandlerMapping only finds the correct method. It does not execute the method. The actual method invocation is done by another Spring MVC component called HandlerAdapter.

    Simple flow:

    DispatcherServlet asks HandlerMapping:
"Which method should handle this request?"

HandlerMapping replies:
"StudentController.getStudent()"

DispatcherServlet then asks HandlerAdapter:
"Please call this method properly."

HandlerAdapter then prepares method arguments and invokes the controller method.
    Aspect HandlerMapping HandlerAdapter
    Job Find the matching handler method Invoke the selected handler method
    Input HTTP request (URL + method) The chosen method + resolved arguments
    Output The handler reference The method return value
    Runs argument resolvers No Yes, via argument resolvers
    Analogy The directory that finds the room The key that opens the door

    Important: Confusing these two is the most common Spring MVC interview slip. HandlerMapping answers "which method?", HandlerAdapter answers "call it now".

    7. How Request Data Reaches the Controller

    In a web API, request data usually comes from three places:

    1. Path variable
    2. Query parameter
    3. Request body

    Spring MVC uses argument resolvers to extract this data and assign it to controller method parameters.

    7.1 Path Variable

    Example request:

    GET /students/10

    Controller method: @GetMapping("/{id}") public Student getStudent(@PathVariable Integer id). Spring compares the request URL /students/10 with the endpoint /students/{id} and assigns id = 10. This is handled by Spring MVC's argument resolution mechanism.

    7.2 Query Parameter

    Example request:

    GET /students?name=Rohit

    Controller method: @GetMapping public List<Student> getStudents(@RequestParam String name). Here Spring extracts name = Rohit. Tomcat already parses the HTTP request and makes query parameters available through the servlet request object. Spring MVC then reads those values and assigns them to controller method parameters.

    7.3 Request Body

    Example POST request:

    POST /students
Content-Type: application/json

{
  "name": "Rohit",
  "email": "rohit@example.com",
  "mobile": "9999999999"
}

    Controller method: @PostMapping public Student createStudent(@RequestBody Student student). Here Spring MVC reads the JSON body and converts it into a Java object Student student. This is mainly done using HttpMessageConverter + Jackson.

    8. Who Converts JSON to a Java Object?

    In most Spring MVC and Spring Boot applications, JSON conversion is handled by Jackson. Spring MVC uses HttpMessageConverter to convert:

    • JSON -> Java Object
    • Java Object -> JSON

    Example input:

    {
  "name": "Rohit",
  "email": "rohit@example.com"
}

    gets converted into Student student. And when a controller returns return student;, Spring converts that Java object back into a JSON response.

    Direction Producer Mechanism
    JSON to Java object Jackson HttpMessageConverter reads @RequestBody
    Java object to JSON Jackson HttpMessageConverter writes the response
    Form/other types Other converters Same HttpMessageConverter contract

    Important: Spring does not parse JSON by itself. HttpMessageConverter is the contract; Jackson is the library commonly plugged in behind it. The no-argument constructor on the model matters because Jackson needs it while converting JSON into a Java object.

    10. pom.xml: The Three Manual Dependencies

    Because we are not using Spring Boot, we manually add the required dependencies.

    <dependencies>
    <!-- Spring MVC -->
    <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-webmvc</artifactId>
        <version>6.1.6</version>
    </dependency>
    <!-- Embedded Tomcat -->
    <dependency>
        <groupId>org.apache.tomcat.embed</groupId>
        <artifactId>tomcat-embed-core</artifactId>
        <version>10.1.20</version>
    </dependency>
    <!-- JSON conversion using Jackson -->
    <dependency>
        <groupId>com.fasterxml.jackson.core</groupId>
        <artifactId>jackson-databind</artifactId>
        <version>2.17.0</version>
    </dependency>

    Explanation of each dependency:

    Dependency What it brings
    spring-webmvc DispatcherServlet, @RestController, @Controller, @RequestMapping, @GetMapping, @PostMapping, HandlerMapping, HandlerAdapter, ViewResolver support
    tomcat-embed-core Lets us start Tomcat directly from main(); tomcat.start(); Tomcat embedded inside our Java application
    jackson-databind Converts JSON -> Java object and Java object -> JSON behind HttpMessageConverter

    With tomcat-embed-core we do not install external Tomcat or deploy a WAR file. Instead we can run tomcat.start(), which means Tomcat is embedded inside our Java application.

    11. The Layered Code: Student, Repository, Service, Controller

    Student.java

    Student is a simple model class representing one student with id, name, email, and mobile. A no-argument constructor is important because Jackson needs it while converting JSON into a Java object.

    StudentRepository.java

    The repository is annotated with @Repository. This tells Spring that this class belongs to the repository layer and that Spring should create and manage its object inside the IoC container. Conceptually this is the database layer. Here we are not using MySQL; we use Map<Integer, Student> as an in-memory database, with a currentId counter. It exposes save, findById, findAll, update, and delete. In a real project this repository would talk to the database using JDBC, JPA, Hibernate, or Spring Data JPA.

    StudentService.java

    The service is annotated with @Service. This tells Spring: this class belongs to the service layer, please create and manage its object inside the IoC container. The service layer contains business logic. Right now the logic is simple, but in real applications this layer may contain validation, business rules, calculations, calls to multiple repositories, and transaction handling.

    Constructor injection: public StudentService(StudentRepository studentRepository) { this.studentRepository = studentRepository; }. This is dependency injection. The service needs the repository, but it does not create the repository object manually. We do not write new StudentRepository(); instead we ask Spring to provide the object. This keeps the code loosely coupled and easier to test.

    StudentController.java

    @RestController
@RequestMapping("/students")
public class StudentController {
    private final StudentService studentService;

    public StudentController(StudentService studentService) {
        this.studentService = studentService;
    }

    @PostMapping
    public Student createStudent(@RequestBody Student student) {
        return studentService.createStudent(student);
    }

    @GetMapping("/{id}")
    public Student getStudent(@PathVariable Integer id) {
        return studentService.getStudent(id);
    }

    @GetMapping
    public Collection<Student> getAllStudents() {
        return studentService.getAllStudents();
    }

    @PutMapping("/{id}")
    public Student updateStudent(@PathVariable Integer id,
                                 @RequestBody Student student) {
        return studentService.updateStudent(id, student);
    }

    @DeleteMapping("/{id}")
    public Student deleteStudent(@PathVariable Integer id) {
        return studentService.deleteStudent(id);
    }
}

    Explanation of @RestController: this class will handle REST API requests, and the return value of its methods should be written directly in the HTTP response body. So when a method returns a Student object, Spring converts it into JSON. @RestController is basically a shortcut for @Controller + @ResponseBody.

    Explanation of @RequestMapping("/students"): this defines the base URL for the controller, so every API inside the class starts with /students.

    Explanation of @PathVariable Integer id: take the value from the URL path and assign it to this variable. For /students/1, id = 1.

    Explanation of @RequestBody: read the JSON request body and convert it into a Student object using Jackson through HttpMessageConverter.

    12. WebConfig and App.java: Wiring Spring MVC by Hand

    WebConfig is very important because we are not using Spring Boot, so we must manually tell Spring MVC what to do.

    • @Configuration: this class contains Spring configuration.
    • @EnableWebMvc: enables Spring MVC features. Without it, annotations such as @RestController, @Controller, @RequestMapping, @GetMapping, @PostMapping, @PathVariable, and @RequestBody may not work fully. It also enables Spring MVC infrastructure such as HandlerMapping, HandlerAdapter, message converters, and controller handling.
    • @ComponentScan(basePackages = "in.strikes"): scan this package and find Spring-managed classes, so Spring finds StudentController, StudentService, and StudentRepository and manages them inside the IoC container.

    App.java is the main class where we manually start embedded Tomcat and register Spring MVC. Step by step:

    1. Create Tomcat: Tomcat tomcat = new Tomcat();
    2. Set port: tomcat.setPort(8080); so the server runs at http://localhost:8080.
    3. Create connector: tomcat.getConnector(); initializes the connector that listens for HTTP requests.
    4. Create web context: contextPath = "" and docBase = src/main/webapp; tomcat.addContext(...) creates the web application context. With an empty context path the API runs at http://localhost:8080/students, not under an app-name prefix.
    5. Create Spring web context: new AnnotationConfigWebApplicationContext() - this is where Spring manages controllers, services, repositories, and configuration classes.
    6. Register config class: springContext.register(WebConfig.class); tells Spring to use WebConfig, so it knows Spring MVC should be enabled, which package to scan, and which classes become beans.
    7. Create DispatcherServlet: new DispatcherServlet(springContext); - we pass the context because DispatcherServlet needs access to the IoC container.
    8. Register with Tomcat: Tomcat.addServlet(context, "dispatcherServlet", dispatcherServlet);
    9. Map it: context.addServletMappingDecoded("/", "dispatcherServlet"); tells Tomcat to send all requests to DispatcherServlet.
    10. Start server: tomcat.start(); tomcat.getServer().await(); - start() starts the server, await() keeps it running. Without await(), main() may finish and the application may stop immediately.

    Important: DispatcherServlet needs the Spring context because after receiving a request it must know which controllers exist, which URL maps to which method, which services and repositories are available, and which message converters exist. All of that lives in the IoC container.

    13. Running It, and What Spring Boot Auto-Configures

    Run App.java from the IDE, then test the APIs using Postman or a browser:

    POST   http://localhost:8080/students
GET    http://localhost:8080/students
GET    http://localhost:8080/students/1
PUT    http://localhost:8080/students/1
DELETE http://localhost:8080/students/1

    In the manual Spring MVC application we configured many things ourselves: added the Spring MVC dependency, added the embedded Tomcat dependency, added the Jackson dependency, created Tomcat manually, created the Spring web context manually, registered WebConfig manually, created DispatcherServlet manually, registered DispatcherServlet with Tomcat, mapped DispatcherServlet to /, and started Tomcat manually. In Spring Boot, most of this is automatic. Spring Boot web applications include an embedded web server by default when we use spring-boot-starter-web; for servlet-based applications it brings embedded Tomcat by default.

    Same app in Spring Boot: pom.xml mainly needs spring-boot-starter-web, and the main class becomes:

    @SpringBootApplication
public class StudentApplication {
    public static void main(String[] args) {
        SpringApplication.run(StudentApplication.class, args);
    }
}

    That is it. The controller, service, repository, and model can remain almost the same.

    Work Manual Spring MVC Spring Boot
    Add Spring MVC dependency Manually add spring-webmvc Included in starter
    Add embedded Tomcat Manually add tomcat-embed-core Included in starter
    Add Jackson Manually add jackson-databind Included in starter
    Start Tomcat Manually in App.java Automatic
    Create Spring web context Manual Automatic
    Register DispatcherServlet Manual Automatic
    Map DispatcherServlet Manual Automatic
    Enable Spring MVC @EnableWebMvc Auto-configured
    Component scanning @ComponentScan Via @SpringBootApplication
    Run application Custom Tomcat code SpringApplication.run()

    Golden rule: Spring Boot is not a different web framework. It performs the exact same manual steps, in the same order, once, so you never write them again.

    14. @Controller vs @RestController

    @Controller is traditionally used when we want to return web pages. Example: @Controller public class HomeController { @GetMapping("/home") public String home() { return "home"; } }. Here return "home"; does not mean response body "home". It means: find and return the home view page. That view page could be home.jsp.

    @RestController is used for REST APIs. Example: @RestController public class StudentController { @GetMapping("/student") public Student getStudent() { return new Student(1, "Rohit", "rohit@example.com", "9999999999"); } }. Here the return value means: convert this Java object into JSON and send it in the HTTP response body. So return student; becomes:

    {
  "id": 1,
  "name": "Rohit",
  "email": "rohit@example.com",
  "mobile": "9999999999"
}
    Aspect @Controller @RestController
    Typical purpose Return views/pages Return data/JSON
    Return value meaning Logical view name HTTP response body
    Body annotation Needs @ResponseBody per method Implicit @ResponseBody
    Common partner ViewResolver + JSP HttpMessageConverter + Jackson
    Example return "home"; -> home.jsp return student; -> JSON
    Shortcut for Itself @Controller + @ResponseBody

    Simple difference: @Controller usually returns views/pages; @RestController usually returns data/JSON.

    15. Why ViewResolver Exists and the JSP Flow

    Spring MVC was not created only for REST APIs. Originally, Spring MVC was also heavily used to create full web applications where the backend returned HTML pages. In that style the controller does not return JSON; it returns the name of a view page. This job is done by ViewResolver. If the controller returns return "home"; and the resolver is configured with resolver.setPrefix("/WEB-INF/views/"); and resolver.setSuffix(".jsp");, then Spring converts home into /WEB-INF/views/home.jsp. ViewResolver maps logical view names to actual view files.

    JSP MVC project structure:

    src
  main
    java
      in
        strikes
          App.java
          config
            WebConfig.java
          controller
            HomeController.java
    webapp
      WEB-INF
        views
          home.jsp
      resources
        css
          style.css

    Important: JSP files are kept inside WEB-INF so users cannot directly access them from the browser. The request should go through the controller first.

    For JSP support we need Tomcat's JSP engine, called Jasper. Add tomcat-embed-jasper because JSP pages require Tomcat's JSP engine.

    WebConfig for JSP adds a ViewResolver bean and resource handling:

    @Configuration
@EnableWebMvc
@ComponentScan(basePackages = "in.strikes")
public class WebConfig implements WebMvcConfigurer {
    @Bean
    public ViewResolver viewResolver() {
        InternalResourceViewResolver resolver =
            new InternalResourceViewResolver();
        resolver.setPrefix("/WEB-INF/views/");
        resolver.setSuffix(".jsp");
        return resolver;
    }

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/resources/**")
                .addResourceLocations("/resources/");
    }
}

    addResourceHandlers allows the browser to access static files like CSS. For example /resources/css/style.css will load src/main/webapp/resources/css/style.css. Without this configuration, CSS may not load properly because with @EnableWebMvc we are manually controlling Spring MVC configuration.

    HomeController uses @Controller and a Model to send data to the JSP: model.addAttribute("title", "Spring MVC"); and model.addAttribute("message", "Welcome to Spring MVC with JSP");, then returns "home".

    home.jsp is the View. It receives data from the Model; ${title} and ${message} come from the controller:

    <!DOCTYPE html>
<html>
<head>
    <title>${title}</title>
    <link rel="stylesheet" href="/resources/css/style.css">
</head>
<body>
    <h1>${title}</h1>
    <p>${message}</p>
</body>
</html>

    style.css is created at src/main/webapp/resources/css/style.css and styles the page (font family, background color, padding, heading color, paragraph size).

    16. REST API vs JSP Flow, and the Final MVC Meaning

    In the REST API example, we mainly returned JSON, so the focus was:

    Controller -> Service -> Repository -> JSON Response

    The REST API did not really need JSP files or static web pages. But in the JSP example we return a view page, so the flow becomes:

    Controller -> Model -> ViewResolver -> JSP Page

    The JSP example needs src/main/webapp because it contains JSP files, CSS files, and static resources. Here docBase becomes more important because Tomcat needs to find the actual web application files.

    Aspect REST API flow JSP/ViewResolver flow
    Controller annotation @RestController @Controller
    Return value Java object Logical view name
    Conversion HttpMessageConverter + Jackson -> JSON ViewResolver -> JSP path
    Needs webapp No Yes (src/main/webapp)
    Output JSON response body Rendered HTML page
    Core path Controller -> Service -> Repository Controller -> Model -> ViewResolver -> JSP

    Final MVC meaning: Spring MVC stands for Model - View - Controller.

    Part Meaning
    Model Data sent from controller to view
    View JSP page or UI page
    Controller Handles request and decides response/view

    Example flow for a web page:

    User opens /home

    Interviewer's perspective: "Is MVC old-fashioned?" No. @RestController is MVC too: the controller is the Controller, the returned object is the Model, and Jackson's JSON is the view. The pattern never left; only the View implementation changed from JSP to JSON.

    17. Myth vs Reality

    Myth Reality
    "Spring Boot replaces Spring MVC" Boot automates Spring MVC configuration; Spring MVC still runs underneath
    "DispatcherServlet does everything alone" It coordinates; HandlerMapping, HandlerAdapter, resolvers, and converters do the work
    "HandlerMapping invokes the controller" HandlerMapping only finds the method; HandlerAdapter invokes it
    "@RestController returns web pages" It returns data/JSON written to the response body
    "@Controller returning 'home' means body 'home'" It means the logical view name for ViewResolver to resolve
    "Spring parses JSON by itself" HttpMessageConverter is the contract; Jackson is the common library behind it
    "JSP files can be opened directly by the browser" They live under WEB-INF and must be reached through the controller

    18. Common Trap Questions

    Trap 1 - "DispatcherServlet is the controller." Verdict: False. DispatcherServlet is the front controller and coordinator. The actual handler is the @Controller / @RestController class and its mapped method.

    Trap 2 - "HandlerMapping calls the controller method." Verdict: False. HandlerMapping only finds the matching method; HandlerAdapter prepares arguments and actually invokes it.

    Trap 3 - "@RestController is just another name for @Controller." Verdict: False. @RestController = @Controller + @ResponseBody, so return values go straight into the response body as JSON.

    Trap 4 - "JSON to Java conversion is done by Spring's own parser." Verdict: False. Spring MVC uses HttpMessageConverter as the abstraction; Jackson is the common library used behind the scenes.

    Trap 5 - "ViewResolver generates the HTML page." Verdict: False. ViewResolver only maps a logical view name to a view file such as /WEB-INF/views/home.jsp; the JSP renders the HTML.

    Trap 6 - "Path variable and query parameter are the same thing." Verdict: False. /students/10 is a path variable (@PathVariable); /students?name=Rohit is a query parameter (@RequestParam).

    Trap 7 - "You cannot build Spring MVC without Spring Boot." Verdict: False. You add spring-webmvc and tomcat-embed-core, write @EnableWebMvc + @ComponentScan, and start embedded Tomcat manually. Boot only removes that boilerplate.

    19. Points to Remember

    1. Spring Web MVC (artifact spring-webmvc) is Spring's web framework, built on the Servlet API.
    2. Spring Boot does not replace Spring MVC; it auto-configures the manual setup.
    3. DispatcherServlet is the front controller: one central servlet that receives and coordinates every request.
    4. HandlerMapping maps URL and HTTP method to a controller method; it only finds, never invokes.
    5. HandlerAdapter prepares arguments (via argument resolvers) and actually invokes the controller method.
    6. Request data arrives as path variable, query parameter, or request body; Spring resolves each into method parameters.
    7. JSON <-> Java conversion goes through HttpMessageConverter, with Jackson as the common library.
    8. @RestController = @Controller + @ResponseBody; @Controller returns views, @RestController returns data.
    9. ViewResolver maps a logical view name to a real file, e.g. home -> /WEB-INF/views/home.jsp.
    10. JSP files live under WEB-INF (not directly reachable); Boot's spring-boot-starter-web supplies the embedded server.

    20. Likely Interview Questions

    Question Crisp Answer
    What is Spring MVC? Spring's web framework (module spring-webmvc), built on the Servlet API, for web apps, REST APIs, and HTTP backend services.
    What is DispatcherServlet? The front controller: one central servlet that receives every request and coordinates the Spring MVC components.
    Why is DispatcherServlet called a front controller? Because all requests pass through it first and it dispatches each to the correct handler method.
    What does HandlerMapping do? It maps an HTTP request (URL + method) to the correct controller method using a mapping table built at startup.
    What does HandlerAdapter do? It prepares method arguments and actually invokes the selected controller method.
    How does HandlerMapping know the mappings? At startup: component scan finds controllers, Spring creates beans, HandlerMapping reads @RequestMapping/@GetMapping etc., and builds a table.
    How does request data reach a controller method? Argument resolvers read path variables, query parameters, and the request body and assign them to parameters.
    Who converts JSON to a Java object? HttpMessageConverter, commonly backed by Jackson (jackson-databind).
    @Controller vs @RestController? @Controller returns views; @RestController (a @Controller + @ResponseBody shortcut) returns data/JSON in the body.
    Why does ViewResolver exist? To map logical view names (like home) to real view files (like /WEB-INF/views/home.jsp).
    Why are JSP files kept in WEB-INF? So browsers cannot access them directly; requests must go through the controller first.
    How does Spring Boot change this setup? It auto-configures the embedded server, DispatcherServlet, Spring MVC, scanning, and JSON via spring-boot-starter-web.
