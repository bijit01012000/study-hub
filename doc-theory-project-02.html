    Project 02 — GateKeeper: API Management & Control Plane

    19 sections · 5,780 words

    Project 02

    Scope evidence: "Building a Production-Style API Gateway in Spring Boot | GateKeeper Project | #2" (playlist map, verified). Repo folder is the SpringBoot Project 2/code/gatekeeper monorepo: three Maven modules (api-management-service, smart-gateway-service, analytics-service), each with a Spring Boot application class, a config.SecurityConfig, a controller.HealthController and a dto.responseDto.HealthResponse, plus pom.xml and application.properties; in this part api-management-service also gains a service.HealthService.

    GateKeeper is a production-style API gateway built as three separate Spring Boot microservices, and the whole design turns on one question: which problem does each service own? This part starts the project by building the API Management Service, which is the control plane, and by fixing the vocabulary, ownership model, database shape and API contract before any controller is written. The goal is not three random Spring Boot apps; it is a clean split between deciding what the gateway should do and actually doing it to live traffic. Every later part of the project rests on the boundaries established here.

    1. The GateKeeper Monorepo: Three Services in One Repo

    GateKeeper consists of three Spring Boot microservices that live together in a single Maven monorepo under SpringBoot Project 2/code/gatekeeper:

    1. api-management-service -- stores the configuration that tells the gateway what to do. This is the Control Plane, and it is the service we start building in this part.
    2. smart-gateway-service -- handles the actual application traffic and applies configuration to incoming requests. This is the Data Plane.
    3. analytics-service -- records and summarizes what happened while traffic passed through GateKeeper. Its job is primarily observation and reporting.

    The three services are deliberately different in responsibility, not just in name. Creating three Spring Boot applications does not automatically create a good architecture; the important part is deciding which problem each service owns.

    Module Package root Key classes (this part)
    api-management-service in.coderarmy.gatekeeper.management ApiManagementServiceApplication, config.SecurityConfig, controller.HealthController, dto.responseDto.HealthResponse, service.HealthService
    smart-gateway-service in.coderarmy.gatekeeper.gateway SmartGatewayServiceApplication, config.SecurityConfig, controller.HealthController, dto.responseDto.HealthResponse
    analytics-service in.coderarmy.gatekeeper.analytics AnalyticsServiceApplication, config.SecurityConfig, controller.HealthController, dto.responseDto.HealthResponse

    Each module also carries its own pom.xml and application.properties, so each can be built, run and deployed independently. In this part the api-management-service is the one that grows beyond the health skeleton: it gains a HealthService, keeping the controller thin and pushing the health logic into a dedicated service class.

    Important: The repo is a monorepo (one repository, three Maven modules), but that does not make it a monolith. Each module is an independently runnable Spring Boot application with its own dependencies and configuration.

    2. GateKeeper Architecture: Control Plane vs Data Plane

    The clearest way to understand GateKeeper is to split it into a control plane and a data plane.

    • The Control Plane is the part of the system where gateway configuration is created and managed.
    • The Data Plane is the part of the system through which real application requests travel.

    In GateKeeper the mapping is exact:

    • API Management Service = Control Plane
    • Smart Gateway Service = Data Plane
                +---------------------------+
            |  API Management Service   |
            |       Control Plane       |
            +-------------+-------------+
                          | route configuration
                          v
                     +---------+
                     |  MySQL  |
                     +----+----+
                          ^ read configuration
                          |
            +-------------+-------------+
            |   Smart Gateway Service   |
            |         Data Plane        |
            +-------------+-------------+
                          | request events
                          v
            +---------------------------+
            |     Analytics Service     |
            |   Reporting / Observation |
            +---------------------------+

    The one-line mnemonic is the anchor for the whole project: Control Plane decides, Data Plane does. The control plane holds the decisions (which organizations exist, where a route forwards, what the rate limit is), while the data plane carries out those decisions on the request path.

    Aspect Control Plane Data Plane
    Question it answers What should happen? Make it happen.
    GateKeeper service API Management Service Smart Gateway Service
    Nature of work Configuration management Live request processing
    Typical operations Create, update, version, audit routes Match, forward, rate limit, timeout
    Stores data? Yes, in MySQL No, reads active config
    Who calls it Management users Customers / end users
    Failure impact Config changes blocked Traffic path affected

    Golden rule: Configuration management and live request processing solve different problems. Keeping them separate is what makes the architecture easier to evolve, test and reason about.

    3. The Three Services and Their Responsibilities

    The API Management Service stores the configuration that tells the gateway what it should do. The questions it answers include:

    • Which organizations exist?
    • Where should a route forward traffic?
    • Which routes belong to an organization?
    • What is the rate limit?
    • What is the response timeout?
    • Which HTTP methods are allowed?
    • Is a route active?
    • Which headers should be added or removed?

    The Smart Gateway Service reads configuration created through API Management and applies it to incoming requests. Its future responsibilities include route matching, request forwarding, rate limiting, header manipulation, timeout enforcement and idempotency checks.

    The Analytics Service records and summarizes what happened while traffic passed through GateKeeper: number of requests, failed requests, response times, route usage and rate-limit violations.

    Service Plane / role Owns Example outputs
    API Management Service Control Plane Configuration of organizations and routes Organization list, route config, policies
    Smart Gateway Service Data Plane Live traffic handling Forwarded requests, rate-limit decisions
    Analytics Service Reporting Observation and reporting Counts, failures, latency, violations

    Interviewer's perspective: A weak candidate says "GateKeeper has three microservices." A strong candidate says "configuration, request processing and observation are three different problems, so they are three different services," and can justify why each boundary exists.

    4. Important Terminology: A Shared Vocabulary

    Before designing the database or the APIs, GateKeeper fixes a common vocabulary.

    Organization. A company that uses GateKeeper, for example FoodFast or QuickShop. In this project an organization is also our tenant; there is no separate Tenant entity. The words are used in slightly different senses:

    • we say organization when talking about the database or business model;
    • we say tenant when talking about ownership and isolation.

    Management User. A human or machine identity allowed to configure or read GateKeeper. Examples: platform-admin, foodfast-admin, gateway-service. These identities belong to GateKeeper itself.

    Tenant Customer. A customer of an application that uses GateKeeper, for example a FoodFast customer or a QuickShop customer. A FoodFast customer is not a GateKeeper management user. This distinction becomes extremely important when implementing authentication.

    Route. A rule describing how a public API path maps to a backend service, for example /foodfast/orders/** forwards to the FoodFast Order Service. A route can also carry policies such as allowed methods, rate limits, timeouts, header rules and idempotency configuration.

    Term Meaning Example Belongs to
    Organization (tenant) Company using GateKeeper FoodFast, QuickShop GateKeeper business model
    Management User Identity allowed to configure/read GateKeeper platform-admin, foodfast-admin, gateway-service GateKeeper
    Tenant Customer End user of an app using GateKeeper FoodFast customer, QuickShop customer The tenant application
    Route Mapping of a public path to a backend service, plus policies /foodfast/orders/** -> FoodFast Order Service An organization

    Important: An organization and a tenant are the same thing in this project. There is no separate Tenant entity; the difference is only the sense in which we use the word (database/business model vs ownership/isolation).

    5. Multi-Tenancy and Tenant Identity in the Public Path

    Suppose two companies use the same GateKeeper installation. FoodFast exposes an authentication service on :8091, a restaurant service on :8092 and an order service on :8093. QuickShop exposes an authentication service on :8101, a catalog service on :8102 and an order service on :8103.

    Tenant Service Port
    FoodFast Authentication Service 8091
    FoodFast Restaurant Service 8092
    FoodFast Order Service 8093
    QuickShop Authentication Service 8101
    QuickShop Catalog Service 8102
    QuickShop Order Service 8103

    Both companies may expose an /orders API. That immediately creates a problem: how can one shared gateway distinguish FoodFast /orders from QuickShop /orders?

    One approach is to make the tenant part of the public path:

    FoodFast  -> /foodfast/orders/**  -> FoodFast Order Service
QuickShop -> /quickshop/orders/** -> QuickShop Order Service

First path segment identifies the tenant:
  /foodfast/...  -> FoodFast
  /quickshop/... -> QuickShop

    The first path segment now identifies the tenant. This also makes tenant ownership explicit while resolving routes, which prevents one tenant's configuration from accidentally matching another tenant's traffic.

    Explicit tenant identity is a design principle, not just a convenience. Because routes belong to organizations, the identity of a route is organization_id + route_id, and it is that pair -- not the route id alone -- that must be unique.

    Golden rule: Tenant identity must be explicit. If the tenant is not part of how a route is identified, two companies with the same path will collide, and isolation becomes guesswork.

    6. Actors in the GateKeeper System

    GateKeeper has four important types of actors:

    1. PLATFORM_ADMIN -- owns and operates GateKeeper.
    2. TENANT_ADMIN -- manages one organization's gateway configuration.
    3. GATEWAY_SERVICE -- a machine account used by the Smart Gateway.
    4. TENANT CUSTOMER -- uses FoodFast or QuickShop, not GateKeeper Management.

    In one line each: PLATFORM_ADMIN owns and operates GateKeeper; TENANT_ADMIN manages one organization's gateway configuration; GATEWAY_SERVICE is the machine account used by Smart Gateway; TENANT CUSTOMER uses FoodFast or QuickShop, not GateKeeper Management.

    Understanding these actors before designing authentication prevents multiple security problems later. The first three are management-side identities that exist inside GateKeeper; the fourth is a customer identity that exists inside a tenant application.

    Actor Type Scope Example
    PLATFORM_ADMIN Human Whole GateKeeper platform Platform Admin
    TENANT_ADMIN Human One organization foodfast-admin
    GATEWAY_SERVICE Machine Read configuration gateway-service
    TENANT CUSTOMER Human One tenant application FoodFast customer

    7. Platform Administrator and Tenant Administrator

    The Platform Administrator operates GateKeeper itself. It can perform operations such as:

    • create organizations;
    • create the first administrator for an organization;
    • activate organizations;
    • suspend organizations;
    • soft-delete organizations;
    • view organizations;
    • view infrastructure health.

    Conceptually: Platform Admin -> Create FoodFast, and Platform Admin -> Create QuickShop.

    However, the platform administrator is not responsible for FoodFast's business operations. It should not:

    • place FoodFast orders;
    • access customer accounts;
    • authenticate FoodFast customers;
    • manage FoodFast's restaurant data.

    GateKeeper manages API infrastructure, not the tenant application's business domain.

    The Tenant Administrator is per organization. Each organization has a TENANT_ADMIN: FoodFast -> foodfast-admin, and QuickShop -> quickshop-admin.

    A tenant administrator logs into GateKeeper Management and manages gateway configuration belonging to only its own organization. It can configure:

    • routes;
    • allowed HTTP methods;
    • timeouts;
    • rate limits;
    • idempotency;
    • header rules;
    • route activation.

    It should never be able to modify QuickShop routes. Concretely, foodfast-admin manages FoodFast routes only.

    For this project, the model is intentionally simplified to 1 Organization -> 1 Tenant Administrator. This is the core idea behind tenant isolation. Features such as multiple developers, viewer roles, invitations, billing users and subscription plans are outside the current scope.

    Important: A tenant administrator's power ends at its own organization's boundary. The platform administrator's power is broad over the platform but deliberately silent on tenant business data.

    8. Gateway Service Account, Tenant Customers, and the Security Boundary

    The Smart Gateway also needs to communicate with API Management. Instead of giving it a human account, GateKeeper creates a machine identity: GATEWAY_SERVICE. Its job is simple: Smart Gateway asks for active configuration from API Management.

    The Gateway Service account can read configuration; it cannot modify it. For example:

    • allowed: GET active routes;
    • not allowed: POST route, PUT route, DELETE route.

    This follows the principle of least privilege.

    Tenant customers are different from management users. Suppose a FoodFast customer places an order. That user might have a token issued by FoodFast: FoodFast Customer -> (FoodFast JWT) -> Smart Gateway -> token passed forward -> FoodFast Backend.

    GateKeeper does not turn that customer into a GateKeeper management user. The customer does not log into GateKeeper Management; the customer's credential belongs to FoodFast. Administrative configuration and customer authentication are completely separate concerns.

    Identity Credential owner Can configure GateKeeper? Appears on customer requests?
    foodfast-admin GateKeeper Yes, for FoodFast only No
    gateway-service GateKeeper No, read-only No
    FoodFast customer FoodFast No Yes (FoodFast token)

    Important: Management credentials are never customer credentials. The foodfast-admin account exists only to configure FoodFast inside GateKeeper and is never sent when a customer places an order.

    9. Who Validates What: Gateway Policy vs Tenant Authentication

    There are two different types of validation happening in GateKeeper.

    GateKeeper validation. The gateway asks questions such as:

    • Does a route match this request?
    • Is the route active?
    • Has the rate limit been exceeded?
    • Is this HTTP method allowed?
    • Does an idempotent POST contain an Idempotency-Key?
    • Which headers should be added?
    • Which headers should be removed?
    • What timeout should be used?

    These are gateway concerns.

    Tenant authentication. FoodFast is responsible for questions such as:

    • Is this customer logged in?
    • Is the JWT valid?
    • Can this user access order 123?
    • Does this customer own the payment method?
    • Can this user cancel this order?

    These are application concerns.

    Therefore the trust boundary is clean: GateKeeper validates gateway policy, while FoodFast validates FoodFast user identity and authorization.

    This creates a clean trust boundary and allows GateKeeper to manage infrastructure policies without taking ownership of every tenant's customer identity system.

    Question Owner Type
    Does a route match this request? GateKeeper Gateway policy
    Is the route active? GateKeeper Gateway policy
    Has the rate limit been exceeded? GateKeeper Gateway policy
    Is this HTTP method allowed? GateKeeper Gateway policy
    Is the JWT valid? Tenant (FoodFast) Application
    Can this user cancel this order? Tenant (FoodFast) Application

    Interviewer's perspective: The trap answer is "the gateway validates the JWT." The correct answer is that the gateway validates gateway policy, while the tenant backend validates the tenant's user identity and authorization. Confusing the two collapses the trust boundary.

    10. Designing the Database From First Principles

    Instead of starting by creating JPA entities, GateKeeper starts with the questions the system needs to answer. This helps the database structure emerge naturally from the business requirements. The questions include:

    • Which companies use the system?
    • Who can operate it?
    • What configuration does the gateway need?
    • What values can repeat?
    • How do we retain configuration history?
    • Who changed the configuration?

    Answering these questions leads to the tables: organizations, management_users, api_routes, route_allowed_methods, route_header_rules, route_configuration_versions and control_plane_audit_records.

    organizations
  |
  +---- 0..1 management_users
  |
  +---- many api_routes
  |        |
  |        +---- many route_allowed_methods
  |        +---- many route_header_rules
  |
  +---- many route_configuration_versions
  |
  +---- many control_plane_audit_records

    At this point the database structure reflects the major business concepts instead of being a collection of arbitrary tables.

    Golden rule: Design the database from business questions, not from entities. When the questions are clear, the tables fall out; when entities come first, the schema is usually wrong.

    11. Organizations, Users, Routes, Versioning, and Auditing

    Organizations. The question "which companies are using GateKeeper?" yields an organizations table with these columns:

    • id -- primary key;
    • name -- human-readable company name;
    • slug -- URL-safe identity;
    • status -- lifecycle state;
    • created_at, updated_at, deleted_at -- audit timestamps.

    The name is meant for humans (name = FoodFast), while the slug is a URL-safe identity (slug = foodfast). Having both is what makes routes like /foodfast/orders/** possible.

    Organization status is a state, not a boolean. A simple active = true/false does not describe enough states, so an organization has a status with values:

    Status Meaning
    PENDING Provisioned but not ready to use the system
    ACTIVE Can use GateKeeper Management and its gateway configuration
    SUSPENDED Temporarily cannot use the system; data still exists and can be reactivated
    DELETED Soft-deleted but information retained for historical purposes

    Management users and roles. The question "who is allowed to operate the GateKeeper control plane?" yields roles PLATFORM_ADMIN, TENANT_ADMIN and GATEWAY_SERVICE, plus a management_users table with these columns:

    • id -- primary key;
    • organization_id -- nullable tenant link;
    • role_id -- one of the three roles;
    • username -- login identity;
    • password_hash -- stored credential hash;
    • enabled -- whether the account may log in.

    Not every management user belongs to an organization:

    • platform-admin -> organization_id = NULL
    • gateway-service -> organization_id = NULL
    • foodfast-admin -> organization_id = FoodFast
    • quickshop-admin -> organization_id = QuickShop

    Platform-level identities belong to GateKeeper itself; tenant administrators belong to a particular organization. For this version each organization has only one tenant administrator, so a uniqueness constraint can be applied to management_users.organization_id. Platform-level users still have organization_id = NULL, and MySQL allows multiple NULL values in this type of unique constraint, so multiple platform-level accounts can coexist while still enforcing one organization-bound administrator.

    API routes. The question "what information does the Smart Gateway need to process a request?" yields the api_routes table with these columns:

    • organization_id -- the owning tenant;
    • route_id -- the tenant-scoped route id;
    • name -- human-readable label;
    • path_pattern -- public path that matches;
    • target_base_url -- where traffic forwards;
    • target_path_prefix -- rewrite/prefix on the way out;
    • requests_per_minute -- rate limit;
    • response_timeout_ms -- timeout enforcement;
    • idempotency_enabled -- idempotency handling on/off;
    • active -- whether the route is live;
    • configuration_version -- current config version pointer.

    A route contains both routing information and gateway policy.

    Route identity is tenant-scoped, so the important uniqueness rule is UNIQUE (organization_id, route_id). This means route_id does not have to be globally unique: FoodFast + orders and QuickShop + orders is perfectly valid, because the organization is part of the identity. Conceptually: Route Identity = Organization + Route ID.

    Route field Purpose
    organization_id Tenant ownership
    route_id Tenant-scoped route identity
    name Human-readable label
    path_pattern Public path that matches, e.g. /foodfast/orders/**
    target_base_url Where traffic forwards
    target_path_prefix Rewrite/prefix applied on the way out
    requests_per_minute Rate limit
    response_timeout_ms Timeout enforcement
    idempotency_enabled Idempotency handling on/off
    active Whether the route is live
    configuration_version Current config version pointer

    Allowed methods and header rules. A route may allow multiple HTTP methods (GET, POST, PUT, DELETE). Storing them all in one route column would make the model harder to manage, so they are represented separately:

    • route_allowed_methods -- one row per allowed method, a one-to-many relationship;
    • route_header_rules -- one row per header rule, for example add X-Tenant-ID, remove X-Internal-Header, add X-Gateway-Version.

    Both allowed methods and header rules are children of the live route; if the live route is deleted, these live child records can also be deleted.

    Route configuration versioning. Routes change over time. If we only update api_routes, the previous configuration disappears, but configuration history can be extremely useful, so GateKeeper creates route_configuration_versions with these columns:

    • organization_id -- owning tenant;
    • route_id -- the route the version belongs to;
    • version_number -- monotonic version;
    • change_type -- what kind of change happened;
    • configuration_snapshot -- the full config at that point;
    • created_at -- when the version was written.

    Every route mutation creates a version:

    Mutation Version change_type
    CREATE Version 1 CREATED
    PUT Version 2 UPDATED
    Deactivate Version 3 DEACTIVATED
    Activate Version 4 ACTIVATED
    DELETE Version 5 DELETED

    Configuration history should survive route deletion. A configuration version should not depend on the live route continuing to exist: if /orders is deleted, we may still need to know what configuration existed before deletion. Therefore route_configuration_versions deliberately does not depend on the live route through a foreign key that would cause its history to disappear. Live state and historical state have different lifecycles: the live route may be deleted, the route history should remain.

    Control plane auditing. Versioning answers "what did the route configuration look like?" but it does not completely answer "who performed the operation?" For that, GateKeeper needs auditing, and creates control_plane_audit_records with these columns:

    • organization_id -- tenant context;
    • actor -- who performed the operation;
    • action -- what was attempted;
    • resource_type and resource_id -- what was touched;
    • correlation_id -- trace link across services;
    • duration_ms -- how long it took;
    • result -- success or failure;
    • details -- extra context;
    • created_at -- when it happened.

    An audit record can tell us, for example: actor foodfast-admin, action UPDATE_ROUTE, resource orders, result SUCCESS, duration 31 ms.

    Concern Question it answers Example
    Versioning What did the configuration look like? Version 3 of the FoodFast orders route
    Auditing Who attempted which operation, and what happened? foodfast-admin attempted UPDATE_ROUTE, result SUCCESS

    A useful mental model: version history is state history, audit history is operator/action history. Both are valuable, but they should not be confused.

    Important: Live state and historical state have different lifecycles. Deleting a route should not automatically destroy its configuration history, so version records deliberately avoid a foreign key that would cascade-delete them.

    12. Designing APIs Before Writing Controllers

    Once the actors, ownership model and database relationships are clear, we can design the API contract. A good API should make two things obvious: who is making the request, and what operation they are allowed to perform. Controllers should come after these boundaries are understood.

    The publicly accessible management APIs begin with:

    Method Path Purpose
    GET /health Check whether API Management is running
    POST /api/auth/login Authenticate GateKeeper management users

    The health endpoint lets us check whether API Management is running. The login endpoint lets GateKeeper management users authenticate; these users include identities such as PLATFORM_ADMIN, TENANT_ADMIN and GATEWAY_SERVICE, depending on how authentication is configured.

    Why there is no public registration API. GateKeeper does not provide an endpoint such as POST /api/auth/register. The reason is architectural: GateKeeper manages management accounts, not customer accounts. Organizations and their administrators are provisioned through GateKeeper's controlled management flow, and a random user should not be able to register themselves as TENANT_ADMIN or PLATFORM_ADMIN. Similarly, FoodFast customers do not register with GateKeeper; their accounts belong to FoodFast. FoodFast customer registration -> FoodFast, whereas GateKeeper management account creation -> GateKeeper.

    These are two completely different identity systems.

    Interviewer's perspective: "Why no register endpoint?" is a design question, not a REST question. The answer is that registration would let an anonymous user grant themselves a management role, which breaks the control-plane trust model.

    13. Key Design Principles

    The control-plane flow currently looks like this:

    1. Platform Administrator provisions FoodFast.
    2. FoodFast gets a FoodFast Tenant Admin.
    3. The Tenant Admin configures routes.
    4. API Management Service stores the configuration in MySQL.

    Later, Smart Gateway can consume that configuration:

    1. Smart Gateway connects as the GATEWAY_SERVICE identity.
    2. It requests active route configuration from API Management.
    3. API Management returns the active configuration to Smart Gateway.

    Actual customer traffic follows a different path:

    1. FoodFast Customer sends a FoodFast credential.
    2. Smart Gateway applies gateway policies.
    3. FoodFast Backend validates the FoodFast customer.
    4. Tenant business logic runs.

    It is important not to mix these two flows. In the management flow, authentication belongs to GateKeeper. In the customer flow, authentication of the end user ultimately belongs to the tenant application.

    The design principles that fall out:

    1. A microservice must own a clear problem. API Management -> configuration, Smart Gateway -> request processing, Analytics -> observations.
    2. Separate control plane from data plane. Configuration management and live request processing solve different problems, and keeping them separate makes the architecture easier to evolve.
    3. Tenant identity must be explicit. Routes belong to organizations; organization_id + route_id together identify a route, preventing one tenant's configuration from becoming another tenant's.
    4. Management users are not application customers. foodfast-admin and a FoodFast customer are completely different identities; mixing them creates architectural and security problems.
    5. The gateway enforces gateway policy. GateKeeper deals with routing, rate limiting, timeouts, headers, idempotency and route activation; the tenant backend continues to own application-level authorization.
    6. Design the database from business questions. Ask which companies use the system, who can operate it, what configuration the gateway needs, what values can repeat, how history is retained and who changed the configuration; the tables emerge naturally.
    7. Live state and historical state have different lifecycles. Deleting a route should not destroy its configuration history.
    8. Versioning and auditing are different. Versioning answers what the configuration looked like; auditing answers who performed the operation and what happened. A mature control plane usually needs both.
    Do Do not
    Give each service one clear problem Assume three apps equal good architecture
    Keep control plane and data plane separate Mix configuration with live traffic
    Make the tenant explicit in route identity Let /orders collide across tenants
    Keep management and customer identities apart Send foodfast-admin on customer requests
    Own gateway policy in the gateway Own the tenant's business authorization
    Design tables from business questions Start from entities and guess the tables

    14. Myth vs Reality

    Myth Reality
    "GateKeeper is one gateway app." It is three Spring Boot microservices: API Management (control plane), Smart Gateway (data plane) and Analytics (reporting).
    "The organization and the tenant are different entities." They are the same concept; there is no separate Tenant entity, only two senses of the word.
    "A tenant customer is a GateKeeper user." A tenant customer is an end user of FoodFast/QuickShop and never logs into GateKeeper Management.
    "The gateway is a boolean active flag." Organization status has PENDING, ACTIVE, SUSPENDED and DELETED states, which a boolean cannot express.
    "route_id must be globally unique." Route identity is organization_id + route_id; FoodFast + orders and QuickShop + orders can coexist.
    "The gateway validates the customer's JWT and authorization." GateKeeper validates gateway policy; the tenant backend validates its own user identity and authorization.
    "gateway-service can create and update routes." It is a read-only machine identity: it may GET active routes but not POST, PUT or DELETE.
    "Versioning and auditing are the same thing." Versioning = what the config looked like; auditing = who did what and what happened.
    "Deleting a route should delete its history." Configuration history is deliberately kept alive after the live route is deleted.
    "GateKeeper needs a public register endpoint." It must not: account creation is a controlled management flow, not open registration.

    15. Common Trap Questions

    Trap 1 - "The API Management Service is the data plane." Verdict: False. API Management is the Control Plane; the Smart Gateway Service is the Data Plane. Remember the mnemonic: Control Plane decides, Data Plane does.

    Trap 2 - "Organization and tenant are two separate tables." Verdict: False. An organization is the tenant in this project; there is no separate Tenant entity. The word choice only signals the sense being used (business model vs isolation).

    Trap 3 - "The Smart Gateway should validate the customer's JWT and authorization." Verdict: False. The gateway validates gateway policy (route match, active flag, rate limit, allowed methods, idempotency key, header rules, timeout). The tenant backend validates its own customer's identity and authorization.

    Trap 4 - "A FoodFast customer is a GateKeeper management user." Verdict: False. The customer's credential belongs to FoodFast. foodfast-admin is a GateKeeper management identity used only to configure FoodFast inside GateKeeper.

    Trap 5 - "route_id should be globally unique." Verdict: False. Route identity is organization_id + route_id; the unique rule is UNIQUE (organization_id, route_id), which is what lets two tenants both have an orders route.

    Trap 6 - "gateway-service can create routes because it is a service account." Verdict: False. It is least-privilege and read-only. It can request active configuration (GET active routes) but cannot POST, PUT or DELETE routes.

    Trap 7 - "Configuration version history can be a foreign key on api_routes." Verdict: False. route_configuration_versions deliberately does not depend on the live route through a cascading foreign key, because history must survive route deletion.

    16. Points to Remember

    1. GateKeeper is three Spring Boot microservices in one monorepo: api-management-service, smart-gateway-service and analytics-service.
    2. API Management = Control Plane (decides); Smart Gateway = Data Plane (does); Analytics = observation and reporting.
    3. An organization is the tenant; there is no separate Tenant entity, only two senses of the word.
    4. Management users (platform-admin, foodfast-admin, gateway-service) belong to GateKeeper; tenant customers belong to the tenant app.
    5. A route maps a public path to a backend service and carries policies: allowed methods, rate limits, timeouts, header rules, idempotency.
    6. Tenant identity is explicit in the public path (/foodfast/orders/**, /quickshop/orders/**), and route identity is organization_id + route_id.
    7. Four actors: PLATFORM_ADMIN, TENANT_ADMIN, GATEWAY_SERVICE, TENANT CUSTOMER; each has a distinct scope.
    8. gateway-service follows least privilege: it reads active configuration and cannot modify it.
    9. The gateway validates gateway policy; the tenant backend validates customer identity and authorization.
    10. The schema (organizations, management_users, api_routes, route_allowed_methods, route_header_rules, route_configuration_versions, control_plane_audit_records) emerges from business questions, with versioning and auditing kept distinct.

    17. Likely Interview Questions

    Question Crisp Answer
    What is GateKeeper? A production-style API gateway built as three Spring Boot microservices: API Management (control plane), Smart Gateway (data plane) and Analytics (reporting).
    What is the control plane vs the data plane? The control plane decides what should happen (configuration); the data plane makes it happen (live traffic). API Management vs Smart Gateway.
    What does the API Management Service store? Configuration: organizations, route targets, routes per organization, rate limits, timeouts, allowed methods, active flag and header rules.
    What will the Smart Gateway Service do? Route matching, request forwarding, rate limiting, header manipulation, timeout enforcement and idempotency checks, using configuration it reads.
    What does the Analytics Service record? Request counts, failed requests, response times, route usage and rate-limit violations -- observation and reporting.
    What is an organization? A company using GateKeeper (FoodFast, QuickShop); in this project it is also the tenant, with no separate Tenant entity.
    Organization vs management user vs tenant customer? Organization = company/tenant; management user = GateKeeper identity that configures/reads it; tenant customer = end user of the tenant's app.
    What is a route? A rule mapping a public API path to a backend service, plus policies like allowed methods, rate limits, timeouts, header rules and idempotency.
    Why does /orders not collide across tenants? Tenant is the first path segment (/foodfast/..., /quickshop/...) and route identity is organization_id + route_id.
    Who validates what? GateKeeper validates gateway policy (route match, active, rate limit, method, idempotency key, headers, timeout); the tenant validates its own user identity and authorization.
    Why is there no public registration API? GateKeeper manages management accounts, not customer accounts; open registration would let users self-assign TENANT_ADMIN or PLATFORM_ADMIN.
    Why is gateway-service read-only? It is a machine identity for the Smart Gateway, and least privilege means it can read active configuration but not modify it.
