    Lecture 01 — Introduction to Spring & Spring Boot

    18 sections · 2,797 words

    Lecture 01

    Scope evidence: "Spring Boot & Spring Framework Full Course | Spring Boot Full Course #1" (playlist map, verified). Repo lecture folder contains notes only (no code folder). Coverage below = client-server basics, HTTP request/response, why Core Java is not a web framework, Servlets + containers, Spring ecosystem, Spring Boot vs Spring, microservices. Deeper topics referenced forward to their own lectures.

    Modern backend development is a layered story. A browser talks HTTP, a container translates HTTP into Java calls, Spring organizes the Java objects, and Spring Boot automates the setup. This lecture builds that whole mental model so every later lecture has a "why" attached. Understanding this history removes the magic from Spring Boot before we write the first line of code.

    1. Client-Server Architecture: The Starting Point

    Every web interaction starts with one structural idea:

    Your Browser (client)  ---- talks to ----  Amazon Server
    • Client = the side that asks. Examples: browser, mobile app, React frontend, Postman.
    • Server = the side that listens, processes, and responds. Examples: Amazon, YouTube, a bank server, your own Spring Boot application.

    A server typically performs real work before answering: checking login details, fetching database rows, applying business rules, and saving data.

    Client asks.
Server responds.

    Important: A Spring Boot application is itself a server. Once we run our JAR, our program becomes the "server side" of the same architecture.

    2. HTTP: The Language of the Web

    Both sides need a common language to communicate. That language is HTTP: HyperText Transfer Protocol.

    HTTP is the rulebook that defines:

    • how a request should look;
    • how a response should look;
    • which method is used;
    • which URL is called;
    • what data is sent;
    • which status code is returned.

    HTTP is an application-layer protocol that works on top of TCP/IP. Client and server never exchange text randomly; they follow this format strictly.

    3. Anatomy of an HTTP Request

    An HTTP request contains four main parts:

    Part Meaning Example
    Method The action wanted POST
    URL / path Target functionality /login
    Headers Metadata about the request Content-Type: application/json
    Body Actual data being sent {"email": "abc@gmail.com"} 
    POST /login
Content-Type: application/json

{
  "email": "abc@gmail.com",
  "password": "12345"
}

    Mnemonic for the four parts: M-U-H-B (Method, URL, Headers, Body).

    HTTP Methods

    The first line is the request line: method, path, and HTTP version.

    Method Meaning Example use
    GET Read data Fetch a list of orders
    POST Create data Place a new order
    PUT Replace data completely Update an entire user profile
    PATCH Update data partially Change only the phone number
    DELETE Remove data Cancel an order

    GET requests usually carry no body; they mainly fetch data. POST, PUT, and PATCH carry bodies.

    HTTP Headers

    Headers are key-value pairs that describe the request:

    Accept: application/json
Content-Type: application/json
Authorization: Bearer <token>
Host: www.coderarmy.in

    Headers matter constantly in real Spring work: authentication, JSON handling, API communication, and request metadata all travel through headers.

    4. Anatomy of an HTTP Response and Status Codes

    An HTTP response contains three parts: status code, headers, and body.

    HTTP/1.1 200 OK
Content-Type: application/json

{
  "message": "Login successful"
}
    Status code Meaning
    200 Request successful
    201 Resource created
    400 Bad request (client-side problem)
    404 Resource not found
    500 Internal server error (server-side problem)

    Interviewer's perspective: Expect questions like "compare GET vs POST" or "what does 404 mean exactly." These basics decide whether you look like someone who has actually built APIs or just copied them.

    5. Normal Java Program vs Web Application

    A normal Java program runs inside the JVM, the Java Virtual Machine. javac compiles .java source into .class bytecode; the JVM loads and executes it. The result is "write once, run anywhere" (WORA): the same bytecode runs on Windows, macOS, or Linux wherever a JVM exists.

    But the two life cycles differ completely:

    Normal Java program          Web application
Start                        Start
Run instructions             Keep running
Finish                       Wait for requests
Exit                         Process requests
                             Send responses

    A web server is a program that stays alive continuously and listens for incoming requests. It never simply "runs once and exits."

    6. Why Core Java Alone Is Not Enough

    Core Java gives us classes, objects, inheritance, collections, threads, and files. It does not give us web concepts: HTTP requests, URLs, headers, cookies, sessions, or REST APIs.

    Java can do networking since Java 1.0 via java.net:

    ServerSocket server = new ServerSocket(8080);

    This listens on port 8080. But what arrives is only a raw TCP stream of bytes:

    GET /users HTTP/1.1
Host: localhost:8080

    To the JVM this is just data. Nothing in the language knows that GET means "fetch", that /users is an endpoint, or that Host is a header.

    Building a web app in bare Core Java would mean handling all of this ourselves:

    1. Open a port using ServerSocket.
    2. Read raw input streams.
    3. Parse the HTTP request manually.
    4. Extract the method, URL, headers, and body.
    5. Route the request to the correct Java logic.
    6. Create the HTTP response in the correct format.
    7. Manage multiple users using threads.
    8. Handle errors, malformed requests, and connection behavior.
    // Incorrect: routing as if-else soup mixed with plumbing
if (url.equals("/users")) {
    // user logic
} else if (url.equals("/orders")) {
    // order logic
}

    // Correct: standard layer that converts HTTP into Java method calls
// This layer already exists: the Servlet container. See Section 7.

    This translation gap needed a standard solution.

    7. Servlets and the Servlet Container

    A Servlet is a Java object that can handle HTTP requests: a special Java class designed for web applications. It runs inside a Servlet Container that sits between the web world and our Java code.

    Browser          Servlet Container         Java Servlet
HTTP request --> opens port, parses HTTP --> doGet()/doPost() call

    What the container handles for us:

    • opening a port such as 8080 and listening for requests;
    • reading TCP bytes and parsing HTTP;
    • creating request and response objects;
    • managing threads and calling servlet methods;
    • sending HTTP responses and handling connections.

    Container examples: Apache Tomcat, Jetty, Undertow. We meet all three again as embedded containers in Lecture 09.

    Important: The container converts "GET /hello" from HTTP text into Java method calls. That single sentence is what Servlet technology is for. Full servlet internals arrive in Lecture 14.

    8. Why Spring Was Needed

    Servlets closed the "Java does not understand HTTP" gap. But large enterprise apps built directly on Servlets still hurt:

    • too much boilerplate code;
    • too many configurations;
    • tight coupling between classes;
    • difficult testing and maintenance;
    • repeated plumbing across projects.

    The missing piece was a system that organizes objects, wires dependencies, and centralizes configuration. That is the Spring Framework: it introduced IoC (Inversion of Control), Dependency Injection, and Bean management. We go deep on IoC/DI in Lectures 04-05.

    Golden rule: Spring does not manage our business logic. It manages our objects and the wires between them, so business logic can stay clean.

    9. The Spring Ecosystem: Projects Map

    Spring is not one library. It is an ecosystem, and each project solves one specific problem:

    Project Problem it solves In this series
    Spring Core IoC, DI, beans, configuration L04-L08
    Spring MVC Web layer: controllers, REST APIs L14-L21
    Spring Data Database access with less boilerplate L26-L32
    Spring Security Authentication, authorization, JWT, OAuth L35-L39
    Spring AOP Cross-cutting concerns: logging, transactions L22-L25
    Spring Boot Auto-configuration and embedded server L09 onward
    Spring AI AI model integration: OpenAI, Gemini, RAG (modern addition)

    Without Spring Core, none of the other projects would exist; it is the base of the ecosystem.

    10. JDBC to Hibernate to JPA to Spring Data JPA

    The data story has one evolution line worth memorizing:

    JDBC -> Hibernate -> JPA -> Spring Data JPA

    JDBC forced us to write SQL by hand, open connections, execute queries, handle result sets, and close resources. Hibernate introduced ORM: it maps Java objects to database tables. JPA is the standard specification that defines how ORM should work; Hibernate is one of its implementations. Spring Data JPA then reduces the remaining repository boilerplate.

    Layer What it is Role
    JDBC Low-level API Raw SQL + connections, all manual
    Hibernate ORM implementation Maps objects to tables
    JPA Specification Defines the ORM contract
    Spring Data JPA Spring abstraction Repository-style data access 
    Spring Data JPA -> Hibernate -> JDBC -> Database

    Mnemonic: "JDBC crawled so Hibernate could walk, Hibernate walked so Spring Data JPA could fly."

    Important: JPA tells what should be done. Hibernate actually does it. Asked as "JPA vs Hibernate," the answer is spec vs implementation.

    11. What Spring Boot Is (and Is Not)

    Spring Boot is not a replacement for Spring. It is an automation layer on top of Spring that speeds up application creation:

    • starter dependencies;
    • embedded servers;
    • auto-configuration;
    • sensible defaults;
    • production-ready features;
    • far less manual configuration.

    Spring Boot is opinionated: it makes default assumptions called opinions. Add the web starter and it assumes a web application, then configures embedded Tomcat, Spring MVC setup, an application structure, JSON support, and basic error handling automatically.

    The trade-off is worth stating plainly: Boot hides fundamentals; it does not replace them. Real skill still lives in Spring Core, Spring MVC, DI, beans, HTTP, servlets, databases, and security concepts.

    12. Spring vs Spring Boot, and Where Microservices Fit

    Feature Spring Framework Spring Boot
    Role Core features and modules Auto-configuration and quick setup
    Configuration Manual Sensible defaults
    Flexibility Full control Opinionated, overridable
    Position Foundation of the ecosystem Built on top of Spring 
    Spring Boot uses Spring.
Spring Boot does not replace Spring.

    Microservices are not a Spring module. They are an architecture style: a large application split into independent services (User, Order, Payment, Notification) that are developed, deployed, and scaled separately. Spring Boot is the tool usually chosen to build them because each Boot app is an independent, production-ready unit.

    Interviewer's perspective: A strong answer separates concept from tool: "Microservices = architecture; Spring Boot = one common way of building them."

    13. Myth vs Reality

    Myth Reality
    "Spring Boot replaces Spring" Boot automates Spring on top of it; the framework remains
    "JPA is an implementation" JPA is a specification; Hibernate implements it
    "Core Java cannot do networking" It can (java.net/ServerSocket); it just lacks HTTP semantics
    "A web app is a normal program that exits" Web servers start, listen, and keep running
    "HTTP can only carry HTML" HTTP carries any content type: JSON, XML, files
    "Microservices need Spring Boot" Microservices are style; Boot is a common tool, not a requirement
    "GET requests can carry a body" GET is for fetching; bodies belong to POST/PUT/PATCH

    14. Common Trap Questions

    Trap 1 — "Spring Boot is a replacement for Spring." Verdict: False. Boot is an opinionated automation layer; under every Boot app there is the full Spring Framework.

    Trap 2 — "Hibernate and JPA are the same thing." Verdict: False. JPA is the specification, Hibernate is the implementation. Spring Data JPA rides on top of both.

    Trap 3 — "Spring Boot makes Spring fundamentals unnecessary." Verdict: False. Boot defaults fail the moment you need real configuration, debugging, or security work; fundamentals decide employability.

    Trap 4 — "Java cannot be a server." Verdict: False. ServerSocket proves Java canlisten on a port; what Java lacks is built-in HTTP parsing, which the servlet container supplies.

    Trap 5 — "The servlet container and the servlet are the same." Verdict: False. The servlet is our Java class handling requests; the container (Tomcat) owns ports, threads, parsing, and lifecycle around it.

    Trap 6 — "A web application stops when startup finishes." Verdict: False. Unlike a normal program, a server starts and then blocks forever waiting for requests.

    Trap 7 — "Spring Boot is a microservices framework." Verdict: Misleading. Boot builds independent apps conveniently; microservices are an architecture style that may even exist without Boot.

    15. Points to Remember

    1. Client asks, server responds; browser, Postman, and mobile apps are all clients.
    2. HTTP is the rulebook: how methods, URLs, headers, bodies, and status codes look on both sides.
    3. Request parts: Method, URL, Headers, Body (remember MUHB).
    4. GET reads, POST creates, PUT replaces, PATCH updates partially, DELETE removes.
    5. Status codes divide into 2xx success, 4xx client error, 5xx server error.
    6. javac compiles to bytecode; the JVM runs it anywhere: "write once, run anywhere."
    7. Normal programs exit; web servers start and keep listening for requests.
    8. Core Java can open ports but cannot parse HTTP; servlet containers close that gap.
    9. Spring = IoC + DI + beans for clean, testable, loosely coupled enterprise code.
    10. Spring Boot = automation on top of Spring: starters, embedded Tomcat, auto-config.
    11. JPA is the contract, Hibernate is the implementation, Spring Data JPA is the convenience.
    12. Microservices are an architecture style; Spring Boot is the usual tool that builds them.

    16. Likely Interview Questions

    Question Crisp Answer
    What is client-server architecture? Clients request; servers process and respond over the network.
    What is HTTP and why do we need it? The request/response rulebook of the web, defining format, methods, headers, and status codes on top of TCP/IP.
    GET vs POST? GET reads data via the URL with no body; POST sends data in the body, typically to create.
    What do 404 and 500 mean? 404: requested resource not found (client side); 500: server-side failure.
    Why is Core Java insufficient for web apps? Java can open sockets but has no HTTP parsing, routing, threading-per-request, or request/response objects.
    What is a Servlet? A Java class that handles HTTP requests, managed by a container that calls doGet/doPost.
    What does a servlet container do? Listens on a port, parses HTTP, builds request/response objects, manages threads, and invokes servlets (Tomcat, Jetty, Undertow).
    What is the Spring Framework? The Java framework providing IoC, DI, and bean management for loosely coupled, testable applications.
    Difference between Spring and Spring Boot? Spring = core features and modules; Spring Boot = opinionated auto-configuration layer on top of Spring.
    What is opinionated about Boot? It sets sensible defaults (embedded Tomcat, JSON, error handling) that you can still override.
    JPA vs Hibernate? JPA = specification defining ORM rules; Hibernate = the implementation that executes them.
    Are microservices a Spring module? No; they are an architecture style. Spring Boot is just a common tool used to build them.
