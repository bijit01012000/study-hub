    Design a Coffee Machine

    15 sections · 1,917 words

    LLD Design Problems, problem 05 of 20.

    The Ask

    Build

    • A menu of drinks: espresso, latte, cappuccino, americano.
    • Each drink is a recipe — an ingredient map: water, beans, milk, sugar.
    • Every drink shares one prep skeleton: boil, brew, pour, condiments.
    • Only the varying steps differ: grind and extract, milk, foam.
    • Check ingredients before starting, decrement on use.
    • Dispense the cup, report low ingredients.
    • Admin: refill, set a recipe, run a cleaning cycle.
    • Cup size (S/M/L) scales every quantity.

    Skip

    • Real heater, pump, pressure hardware.
    • Card / UPI payment — a thin seam.
    • App and IoT connectivity, OTA recipes.
    • Grinder wear and dose calibration.
    • A database, login.

    Our Model

    One machine, recipes, inventory. The prep sequence is a Template Method; the varying steps are filled by each drink subclass.

    Actors and classes

    • Customer — machine: CoffeeMachine; pick a drink, customise, pay, calling machine.order(spec).
    • Admin — machine: CoffeeMachine; refill(Ingredient, n), setRecipe(name, r), runCleaning() enters MAINTENANCE.
    • CoffeeMachine (singleton) — menu: Map<String, Recipe>, inv: Inventory, size: SizeStrategy, pay: PaymentTerminal, state: RUNNING | MAINTENANCE; order(DrinkOrder o): Cup, refill(Ingredient i, int n), setRecipe(String, Recipe), runCleaning(). Builds a Beverage, then calls prepare().
    • Beverage (abstract) — prepare(): Cup (final, runs boil -> brew -> pour -> condiments), brew(): void, addCondiments(): void, wantsMilk(): boolean (hook), boilWater(), pourInCup() fixed.
    • Recipe — name: String, type: BeverageType, base: Map<Ingredient, int> in ml / g, milk: boolean, sugar: int; needs(): Map<Ingredient, int> scaled by size, missing(): Set<Ingredient>. A recipe never runs itself; Beverage drives the steps.
    • Inventory — stock: Map<Ingredient, int>, onLow: List<StockListener>; hasIngredients(Recipe r): boolean, consume(Map<Ingredient, int>) atomic, refill(Ingredient, int), low(): Set<Ingredient>. consume() fires onLow when a count drops below par.
    • SizeStrategy (interface) — scale(Map<Ingredient, int> base): Map<Ingredient, int>. One multiplier per cup size, applied to every ingredient.
    • PaymentTerminal (interface) — charge(Money): boolean. A thin seam; no real PSP here. CardTerminal, CashBox, UpiTerminal.
    • DrinkOrder — base: Recipe, size: Size, shots: int, milk: Milk, sugar: int. Built by DrinkBuilder: .shots(2).milk(OAT).sugar(0).build() clones base and applies tweaks.

    The brew skeleton

    boilWater() brew() pourInCup() addCondiments(), then if (wantsMilk()) steamMilk() (default false = black). run when inv.hasIngredients(recipe); varies in brew() + addCondiments(). One sequence, two blanks: prepare() is final, so no subclass can reorder or drop a step.

    The size rules

    • Small -> base quantities, x1.
    • Medium -> x1.5, round to int ml / g.
    • Large -> x2.
    • The cup itself -> S 240, M 360, L 480 ml.

    Recipe.needs() applies this before hasIngredients; size never reaches brew() or addCondiments().

    The four concrete drinks

    • Espresso -> 30 ml at 9 bar, no milk.
    • Latte -> double shot, steam 200 ml, foam.
    • Cappuccino -> 1 shot, 1/3 milk, 1/3 foam.
    • Americano -> shot + hot water, no milk.

    Each fills brew() + addCondiments().

    Key operations

    1. prepare(): Cup — the template method, final. Runs boilWater, brew, pourInCup, then addCondiments, in that order. A subclass cannot reorder or skip a step. Guards on Inventory first, commits once after the pour.
    2. brew(): void — abstract step. Grinds and extracts: Espresso pulls 30 ml at 9 bar, Latte a double shot. This and addCondiments are the only places two coffees differ.
    3. addCondiments(): void — abstract step. Milk, foam, sugar. Reached only when the wantsMilk() hook is true, so a black Americano runs straight past it.
    4. hasIngredients(Recipe r): boolean — true when every ingredient the recipe needs, scaled to the cup size, is in stock. Checked and consumed under one lock before boilWater, so a second order cannot pass the same last shot.

    Recall drill: cover the operations column, write the four with their guarantee.

    The One Run to Hold in Your Head

    The hopper holds 20 g of beans. A large Latte is 18 g and 200 ml scaled x2 — 36 g and 400 ml. Which check fails, at which step, and what has the machine already done when it stops?

    The Change

    They add member pricing or "every 10th coffee free". Payment is a thin seam now. Pull a LoyaltyPricing the machine asks before charge(), keyed by a member id. Recipes and the brew skeleton never change. Strategy, a second time on this sheet.

    What the Picture Can't Show

    The brew is not atomic. The guard passes, the grinder runs, then the last of the milk is gone before the pour. Reserve the whole recipe up front, or check and consume under one lock, and abort before the cup fills.

    If They Make You Code It

    Prepare and one concrete Latte:

    abstract class Beverage {
    protected final Inventory inv;
    protected final Recipe recipe;
    protected Cup cup;

    final Cup prepare() {                            // FINAL: sequence is law
        synchronized (inv) {                         // guard AND take
            if (!inv.hasIngredients(recipe))
                throw new OutOfIngredients(recipe.missing());
            inv.consume(recipe.needs());             // taken up front
        }
        boilWater();                                 // fixed step
        brew();                                      // subclass fills this
        pourInCup();                                 // fixed step
        if (wantsMilk()) steamMilk();                // hook, default false
        addCondiments();                             // subclass fills this
        return cup;
    }

    private void boilWater() { heater.hold(92); }
    private void pourInCup() { cup = new Cup(recipe.size()); }
    protected boolean wantsMilk() { return false; }
    abstract void brew();                            // varies
    abstract void addCondiments();                   // varies
}

class Latte extends Beverage {                       // fills the two blanks
    void brew() { shot(recipe.grams(), 2); }         // double
    protected boolean wantsMilk() { return true; }
    void addCondiments() {
        pour(steamedMilk); foam(10);                 // 10 mm foam
    }
}
// Americano: brew() = shot + hot water, no milk

    The Four Hazards

    1. Runs out mid-brew. The guard is not the commit. Water and beans pass hasIngredients, then the milk drains between the grind and the pour. Reserve the whole recipe up front, or check and consume under one lock, and abort before the cup fills.
    2. Two orders, one inventory. Both drinks clear the stock check on the last shot of beans, then both call consume. The count goes negative. consume() is atomic — CAS or synchronized on Inventory — and re-reads stock inside.
    3. A subclass rewrites the sequence. Someone overrides prepare() and pours before brewing, or drops boilWater. The skeleton is gone. prepare() is final; only brew() and addCondiments() are open, plus the wantsMilk() hook.
    4. Cleaning starts on a queued brew. A descale cycle begins while an order is in flight — the drink is contaminated or the run fails. Cleaning takes the same machine lock: it drains the in-flight prepare(), then a MAINTENANCE state blocks new orders.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. prepare() is final — a subclass cannot reorder or drop a step; boil always precedes brew.
    2. hasIngredients and consume sit in one synchronized (inv) block — the guard and the take are the same step, so two orders cannot both clear the last shot.
    3. wantsMilk() is a hook with a default — Espresso inherits false and never touches milk; Latte overrides.

    Holding the Brew Sequence

    Approach New drink The sequence Recombine steps Who edits it Read at a glance Cost
    Template Method (the default) a subclass, 2 methods law, final enforces it inherit or override one a developer whole flow, one class rigid if steps mix a lot
    Strategy per step wire up N step objects assembled each call, can drift any step, any drink a developer spread over step classes more classes + wiring
    Recipe table a new row, no code encoded in the engine swap a column a barista / ops one table + one runner build the schema + engine

    Template Method. The prep order is genuinely invariant — boil, then brew, then pour, then condiments — so lock it with final and open only brew() and addCondiments(). Move to a recipe table when non-devs must add drinks; reach for per-step Strategy only when steps recombine freely across many drinks.

    Rejection Signals

    These end the interview:

    • An overridable prepare() every drink re-implements — one skips pourInCup, another brews before boiling.
    • hasIngredients checked but consume never runs, or runs before the pour — the count drifts from the cup.
    • Two orders clear the stock check on the last shot with no lock — both brew, one gets water.
    • Quantities as a double — 0.1 + 0.2 drift slowly empties the hopper by surprise.
    • Milk steps copied into every milk drink instead of a wantsMilk() hook and one steamMilk().
    • A cleaning cycle that can start mid-brew — no MAINTENANCE state, no shared lock.
    • Cup size handled by an if inside each recipe, so a fourth size edits them all.
    • if (size == LARGE) ml *= 2 copied into every recipe instead of a SizeStrategy.

    Patterns Used

    Template Method — the fixed prep skeleton, brew + addCondiments open. Strategy — size scaling now, pricing on page 2. Builder — a custom DrinkOrder (extra shot, oat milk, no sugar). Observer — the display and refill pager follow low stock.

    Say It Like This

    "A menu of recipes, each an ingredient map in millilitres and grams. The prep sequence is a Template Method: prepare() is final and runs boil, brew, pour, condiments in that order. Espresso and Latte are subclasses that fill brew() and addCondiments(), with a wantsMilk() hook. Inventory guards before the first step and commits once after the pour. Size is a Strategy, a custom drink is a Builder."

    The Follow-ups That Decide It

    1. Add a Cappuccino. A Beverage subclass: brew() one shot, addCondiments() 1/3 milk 1/3 foam, wantsMilk() true.
    2. Beans run out mid-brew. Reserve the recipe up front, or check and consume under one lock; abort before the pour.
    3. Oat milk, extra shot, no sugar. A DrinkBuilder assembles a DrinkOrder; base recipe is cloned and tweaked, skeleton unchanged.
    4. Small / medium / large cups. A SizeStrategy scales every quantity; the sequence never moves.
    5. Why is prepare() final? Boil -> brew -> pour -> condiments is invariant; only the two varying steps are open.
    6. Low on beans — who is told? Inventory fires lowStock(bean); an AlertBus fans out to the display and a refill pager.
    7. Run a descale cycle. A MAINTENANCE state takes the machine lock, drains the in-flight order, blocks new ones.
    8. "Every 10th coffee free." A LoyaltyPricing strategy asked before charge(); recipes and brew untouched.

    Deliberately Not Built

    • Real heater and pump — PID temperature, pressure curves, flow meters. The sim just calls boilWater(). Hardware, name it.
    • Payment — a PSP behind PaymentTerminal. The seam is the point; the integration is not.
    • Grinder wear — burr life, dose drift, calibration. Modelled as a fixed grams number.
    • App and IoT — remote ordering, telemetry, over-the-air recipes. That is the HLD version.
    • Persistence — recipes, stock and the in-flight order in a store, replayed on boot. Name the recovery.
