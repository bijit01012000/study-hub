    YAGNI

    10 sections · 705 words

    Principle · LLD Core Concepts · Concept 04 of 09

    The Idea

    You Aren't Gonna Need It.

    You'll See This

    • A plugin system or abstract base class with exactly one real implementation.
    • An interface with one implementer and no second one planned.
    • A generic Map<String,Object> param instead of the 2 fields actually used.

    Built for what's real.

    Before

    interface PaymentPlugin {
    // one plugin exists: "card"
    void process(Map<String,Object> params);
}
class PaymentRegistry {
    Map<String,PaymentPlugin> plugins = new HashMap<>();
    void register(String key, PaymentPlugin p) {
        plugins.put(key, p);
    }
    void process(String key, Map<String,Object> params) {
        plugins.get(key).process(params);
    }
}
// a registry, a Map contract, for a method that isn't there

    Built for methods that don't exist.

    After

    class CardPayment {
    void process(String cardNumber, int amountPaise) {
        ..
    }
}
// no registry, no plugin interface, no Map<String,Object>.
// when a real second method shows up, extract the
// interface then, from two real examples instead of a guess.

    Don't Apply It If

    • A second real case already exists, or is on this quarter's roadmap: build the seam.
    • The flexibility is cheap (a config value instead of a hardcoded number).

    Quick Check

    Is there a second real case today? If the honest answer is "maybe someday," that's YAGNI talking.

    How It's Built

    The Shape

    CardPayment
    + process(card, amt)
    concrete. no interface yet.
    the one real case, built plainly

«PaymentPlugin»
    not written
    extract this once a 2nd real payment method exists

ONE CONCRETE CLASS TODAY. THE INTERFACE WAITS.

    The Move (3 Steps)

    1. Build the one real case as concrete code: no interface, no registry.
    2. Ship it. Wait for a genuine second case to actually show up.
    3. Only then extract the interface: you'll know its real shape from two real examples, not a guess.

    In The Interview

    "There's only one payment method today, so I wrote CardPayment as a concrete class with no plugin interface. If a second method shows up, I'll extract a PaymentPlugin interface then, from two real examples."

    How It's Different

    The Confusion Pairs

    YAGNI vs OCP. OCP says stay open to extension. YAGNI says don't build the extension point until it's needed. They disagree on when, not on the goal.

    YAGNI vs a config value. Hardcoding a number vs reading a config value is cheap either way. That's not what YAGNI is warning about.

    YAGNI vs under-engineering. YAGNI isn't "skip error handling" or "skip tests." It targets speculative structure, not correctness.

    YAGNI vs a real second client. If a second consumer of this code exists today, building for it isn't speculation, it's the actual requirement.

    They Say: "add UPI as a second payment method"

    • With it: extract PaymentPlugin from the two real classes you now have, it writes itself.
    • Without: you're maintaining a registry and a Map contract nobody ever validated against a real second case.

    Watch Out For

    • "We might need it later" with no named upcoming case is the tell: that's speculation, not a requirement.
    • YAGNI targets structure (interfaces, plugin systems), not things you clearly need now like input validation.
    • Skipping the seam costs one refactor later; building it early and guessing wrong costs a wrong abstraction everywhere.
    • In a take-home, premature structure sometimes reads as thorough. Say out loud that you know it's premature if you add it.
    • YAGNI and DRY can pull different ways: don't merge two things into one flexible function to avoid duplication that hasn't happened yet.
