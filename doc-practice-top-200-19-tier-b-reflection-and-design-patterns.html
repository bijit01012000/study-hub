      177. Reflection — performance cost and how to mitigate

      Asked at: Senior rounds at Razorpay · Swiggy · Flipkart

      Difficulty: Medium-Hard · Topic: Reflection / Annotations / Bytecode

      The question: "How expensive is reflection? When does it actually matter?"

      The 30-second answer: Field access via reflection is 10-100x slower than direct access; method invocation similar. Matters in hot loops, not in framework startup. Mitigate: cache Method / Field objects (don't getMethod per call), use MethodHandle (faster than Method.invoke), or generate bytecode at startup (ASM/ByteBuddy) and invoke directly.

      Step-by-step thought process:

      1. " Class.getMethod / getField does linear search + security check. Costly. Call once at init, cache the Method object."
      2. "Even with cached Method, invoke() boxes primitives, packs args into Object[], has security checks. 10x slower than direct call."
      3. " MethodHandle (Java 7+) — JIT-friendly, comparable to direct call after warmup. The modern fast-reflection answer."
      4. "Bytecode generation — frameworks like Jackson and Spring generate perclass accessor classes (ASM / ByteBuddy) at startup, then invoke them with no reflection cost. Highest setup cost, lowest steady-state cost."

      Edge cases to mention:

      • setAccessible(true) for private fields — Java 9+ module system restricts this; add --add-opens to JVM args or use Lookup.privateLookupIn (Java 9+) Reflection in native image (GraalVM) requires explicit reflection-config hints
      • For one-off CLI tools, reflection is fine — no warmup, no high QPS

      What NOT to say:

      • "Always avoid reflection" — frameworks rely on it; it's a steady-state hot-path question, not blanket
      • "Reflection caches itself" — partial; JVM caches some lookups but you can't rely on it

      Common follow-up: "How does MethodHandle differ from Method.invoke?"

      178. Retention policies — SOURCE, CLASS, RUNTIME

      Asked at: Senior rounds at Razorpay · TCS Digital · Cognizant

      Difficulty: Medium · Topic: Reflection / Annotations / Bytecode

      The question: " @Retention(RetentionPolicy.RUNTIME) — what's the alternative?"

      The 30-second answer: SOURCE — annotation discarded by the compiler, never in .class files (Lombok's @Getter, @Override). CLASS (default) — in the .class file but not loaded by the JVM, so unreadable at runtime (used by static-analysis tools). RUNTIME — loaded into Class metadata, reflectable (Spring's @Component, JPA's @Entity).

      Step-by-step thought process:

      1. "SOURCE — annotation processor sees it (during compilation), then it disappears. Lombok generates getters from @Getter at compile time, then strips the annotation."
      2. "CLASS — annotation lives in bytecode but JVM doesn't load it into reflection-accessible metadata. Useful for tools like SpotBugs, Checker Framework that parse class files directly."
      3. "RUNTIME — JVM loads it, accessible via clazz.getAnnotation(...). Required for runtime frameworks (Spring, JPA, JAX-RS)."
      4. "Default if no @Retention specified is CLASS, which is almost never what you want — be explicit."

      Edge cases to mention:

      • Memory cost — RUNTIME annotations live in Metaspace; thousands of annotations per class adds up
      • Annotation processors (javax.annotation.processing.Processor) run at compile time regardless of retention — Lombok uses this hook
      • @Inherited works only on class-level annotations and only at one level up

      What NOT to say:

      • "RUNTIME is always best" — wastes memory if you only need compile-time
      • "Annotations execute code" — no, annotations are metadata; processors/frameworks read them

      Common follow-up: "Write me a quick annotation processor that fails compilation if a class is missing @Override."

      179. ASM, Javassist, ByteBuddy — when to reach for which

      Asked at: Staff rounds at Razorpay · Flipkart · Cred · Walmart Labs

      Difficulty: Hard · Topic: Reflection / Annotations / Bytecode

      The question: "Three Java bytecode libraries. When do you use each?"

      The 30-second answer: ASM — low-level, byte-by-byte control, maximum performance, painful API. Javassist — high-level, accepts Java source strings, slower at runtime, less popular today. ByteBuddy — modern fluent API, type-safe builders, used internally by Mockito and many recent frameworks. Default choice for new code: ByteBuddy.

      Step-by-step thought process:

      1. "ASM — the foundation. Used by every major bytecode library under the hood. Direct visitor-based API, you write opcode-by-opcode. Hard to use, fast."
      2. "Javassist — older alternative. Lets you write Java source code as a String, compiles it to bytecode internally. Easier for simple modifications, slower at scale."
      3. "ByteBuddy (Rafael Winterhalter, ~2014) — modern. Fluent builder pattern, AspectJ-style matchers, type-safe. Mockito uses it to subclass mock classes; many AOP libraries adopted it."
      4. "Pick: ByteBuddy for new code (90% of cases). ASM only when you need raw control and performance. Javassist if you're maintaining legacy."

      Edge cases to mention:

      • Java module system (Java 9+) restricts bytecode manipulation across module boundaries — ByteBuddy / ASM need --add-opens for some operations
      • Generated classes inflate Metaspace — cache and reuse them, don't generate per-call
      • GraalVM native image can't see runtimegenerated classes — use AOT processing instead

      What NOT to say:

      • "Use the JDK Proxy API" — only handles interfaces, no class extension
      • "Bytecode manipulation is hacky" — it powers Mockito, Spring proxies, Hibernate, distributed tracing agents

      Common follow-up: "How does Mockito create mocks for non-final classes?"

      180. Annotation processors at compile time

      Asked at: Senior rounds at Razorpay · Cred · Walmart Labs

      Difficulty: Hard · Topic: Reflection / Annotations / Bytecode

      The question: "Lombok works at compile time. How?"

      The 30-second answer: Lombok implements a javax.annotation.processing.Processor. The Java compiler discovers it via META-INF/services/ javax.annotation.processing.Processor. The processor inspects annotated source elements, generates new code (Lombok modifies the AST directly — a controversial design), and the compiler emits classes with the generated code baked in.

      Step-by-step thought process:

      1. "Standard pattern — implement AbstractProcessor, declare which annotations you handle (@SupportedAnnotationTypes), implement process(...) to inspect the AST."
      2. "Most processors generate new source files via Filer — MapStruct, Dagger, AutoValue. Compiler sees them and compiles them in the same round."
      3. "Lombok cheats — it modifies the existing AST in place using internal compiler APIs. Powerful, but breaks across compiler versions."
      4. "Build integration — processors are on the annotationProcessor classpath. Maven: in compiler plugin. Gradle: annotationProcessor configuration."

      Edge cases to mention:

      • IDE integration — IntelliJ has built-in support for many processors; for unknown ones, enable annotation processing in settings
      • Processors can produce errors via Messager — fail the build with descriptive messages
      • JEP 8242972 — Java 23+ improvements to processor APIs for streaming compilation models

      What NOT to say:

      • "Lombok is reflection-based" — opposite; it's compile-time, no runtime cost
      • "Annotation processors run at runtime" — no, compile time only

      Common follow-up: "What's the difference between Lombok and MapStruct philosophically?"

      181. Strategy pattern — when to actually use it in Java

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · TCS Digital

      Difficulty: Medium · Topic: Design patterns

      The question: "Walk me through a real Strategy pattern use in Java code — not the textbook example."

      The 30-second answer: Strategy = encapsulate interchangeable algorithms behind a common interface. Real Java use — payment gateway selection at runtime. PaymentGateway interface, RazorpayGateway, StripeGateway, PayUGateway implementations, a registry (Map<String, PaymentGateway> autowired by Spring) picks one by name. Avoids massive switch over gateway type.

      Step-by-step thought process:

      1. "Define the contract — interface PaymentGateway { PaymentResult charge(Order order); }."
      2. "Implement per provider — @Component("razorpay") class RazorpayGateway implements PaymentGateway, same for stripe, payu."
      3. "Spring autowires Map<String, PaymentGateway> — keys are bean names. Caller does gateways.get(order.getGatewayCode()).charge(order). No switch."
      4. "Adding a new gateway = adding one class. No edits to the dispatcher. That's the Strategy win — open/ closed principle."

      Edge cases to mention:

      • For two strategies, the pattern is overkill — just use an if. Reach for it when you have 3+
      • Java 8+ — for stateless strategies, a Function<X, Y> lambda often suffices over a full interface
      • Don't conflate Strategy with State — Strategy is set externally; State changes itself based on transitions

      What NOT to say:

      • "Use enums with abstract methods" — works for closed sets but breaks open/ closed for unknown providers
      • "Inheritance is simpler" — couples behavior; the point of Strategy is composition

      Common follow-up: "How would Spring help you implement this without a giant switch?"

      182. Observer pattern in Spring — ApplicationEventPublisher

      Asked at: Senior rounds at Razorpay · Swiggy · TCS Digital

      Difficulty: Medium · Topic: Design patterns

      The question: "Show me Observer pattern in real Spring code."

      The 30-second answer: Spring's ApplicationEventPublisher and @EventListener are Observer pattern. Publisher emits events (publishEvent(new OrderPlacedEvent(...))), listeners subscribe via annotation. Listener can be @Async for off-thread processing. Decouples the publisher from listeners — publisher doesn't know who's listening.

      Step-by-step thought process:

      1. "Inject ApplicationEventPublisher and emit — publisher.publishEvent(new OrderPlacedEvent(orderId)). No reference to listeners anywhere."
      2. "Listener — @Component class NotificationListener { @EventListener public void onOrderPlaced(OrderPlacedEvent e) {... } }. Spring finds the matching method by parameter type."
      3. "Default events are synchronous — they run in the publisher's thread inside the publisher's transaction. Use @Async @EventListener for fire-and-forget."
      4. " @TransactionalEventListener(phase = AFTER_COMMIT) — listener fires only after the publishing transaction commits. Avoids the trap of acting on data that may roll back."

      Edge cases to mention:

      • Synchronous events propagate exceptions back to the publisher — failures abort the transaction
      • Multiple listeners for one event — order via @Order(1), parallel execution if all @Async
      • Event hierarchy — listener on a parent class catches subclass events too

      What NOT to say:

      • "Spring events are like Kafka" — same conceptual model but in-process only, not durable
      • "Use static observers" — fragile, hard to test, no DI

      Common follow-up: "What's the difference between @EventListener and @TransactionalEventListener?"

      183. Template method — real-world use

      Asked at: Senior rounds at TCS Digital · Cognizant · Wells Fargo

      Difficulty: Medium · Topic: Design patterns

      The question: "Where do you see Template Method pattern in Spring / JDK?"

      The 30-second answer: Spring's JdbcTemplate.execute(...) — the template handles connection acquisition, exception translation, and cleanup; you fill in the SQL bit via a callback. JDK's AbstractList, AbstractMap — concrete subclasses fill in the minimum, base class provides everything else. The pattern: invariant scaffolding in the base, variable steps as abstract / protected hooks.

      Step-by-step thought process:

      1. " JdbcTemplate.query(sql, rowMapper) — JdbcTemplate handles getting a connection from the pool, preparing the statement, looping the ResultSet, closing everything. You only write the RowMapper."
      2. " AbstractList implements iterator, containsAll, equals, hashCode in terms of get(int) and size() — subclasses only define those two."
      3. "The pattern shape — base class has a public final method that orchestrates, calling protected abstract steps. Subclasses can't change the orchestration, only the steps."
      4. " final on the public method is the contract — it's what prevents subclasses from breaking the invariants."

      Edge cases to mention:

      • Template Method is one of the few GoF patterns where inheritance is the right answer, not composition
      • Functional style — pass the variable behavior as a lambda; JdbcTemplate.execute(con -> {... }) is closer to that style
      • Don't over-template — if you have one varying step, just pass a callback

      What NOT to say:

      • "Just use the Strategy pattern" — different shape; Strategy is full algorithm replacement, Template fills in steps
      • "It's the same as Builder" — no, Builder constructs an object; Template runs an algorithm

      Common follow-up: "How does JdbcTemplate translate SQLException into Spring's DataAccessException hierarchy?"

      184. Visitor pattern — when does it earn its complexity?

      Asked at: Senior rounds at Cred · Goldman · Flipkart

      Difficulty: Hard · Topic: Design patterns

      The question: "Visitor is notoriously hated. When is it the right tool?"

      The 30-second answer: Visitor when you have a closed hierarchy of types (sealed classes, AST nodes, geometry shapes) and an open set of operations you want to add without modifying the types. Each operation = a Visitor implementation. Without it: instanceof chains scattered across the codebase or polluting the types with every operation.

      Step-by-step thought process:

      1. "Use case — interpreter or AST processor. You have Expression types (Literal, BinaryOp, Variable). You want to add evaluation, type-checking, code generation, formatting — without piling them into each Expression class."
      2. "Each type accepts a visitor: interface Expression { R accept(Visitor<R> v); }. Each type implements accept by calling the matching visitor method: v.visitLiteral(this)."
      3. "Operations become standalone classes: class Evaluator implements Visitor<Integer>, class Formatter implements Visitor<String>. Add a new op = add a new Visitor."
      4. "Java 21+ sealed types + pattern matching switch make Visitor mostly obsolete — switch over a sealed hierarchy is exhaustive at compile time, no Visitor boilerplate."

      Edge cases to mention:

      • Adding a new type requires updating every Visitor (closed-types, openoperations is the trade-off)
      • Double dispatch — Java has no native double dispatch, Visitor simulates it via the accept-then-callback pattern
      • Hibernate's HQL parser, Jackson's JsonNode tree, Eclipse JDT AST all use Visitor

      What NOT to say:

      • "Use it for all polymorphism" — over-engineering for non-AST cases
      • "It's the same as Strategy" — Strategy is one algorithm at a time; Visitor handles many type-specific behaviors at once

      Common follow-up: "How do sealed classes and pattern matching switches replace Visitor in Java 21+?"

      185. Builder pattern — JDK's StringBuilder is misleading

      Asked at: Senior rounds at Razorpay · TCS Digital

      Difficulty: Medium · Topic: Design patterns

      The question: "What's the Builder pattern? Show me a real Java example."

      The 30-second answer: Builder solves constructors with many parameters — instead of new Order(a, b, c, d, e, f), you get Order.builder().merchantId(...).amount(...).currency(...).build(). Each setter returns this for chaining. build() validates invariants and constructs the immutable result. Lombok's @Builder generates the boilerplate.

      Step-by-step thought process:

      1. "Telescoping constructors get unwieldy with 5+ params. Builder makes the call site readable — you see field names, not positions."
      2. "Pattern — inner static Builder class with mutable fields, fluent setters returning this, build() constructs the outer (often immutable) object."
      3. " StringBuilder is not this pattern — it's an Appendable for mutable string construction, not a builder for a target type. Common interview confusion."
      4. "With records (Java 16+), the use case shrinks — records compress simple value types. For records with 10+ fields, Builder still beats positional constructor."

      Edge cases to mention:

      • Immutability — Builder fields can be mutable during construction; the built object is typically immutable
      • Validation in build() — throw if required fields missing
      • Lombok @Builder generates the inner class for you; @SuperBuilder handles inheritance

      What NOT to say:

      • "StringBuilder is the textbook example" — it's not Builder pattern
      • "Builders are slow" — one extra object allocation; negligible

      Common follow-up: "How would Lombok's @Builder differ from a hand-written one?"
