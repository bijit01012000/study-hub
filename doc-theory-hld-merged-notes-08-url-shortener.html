    Design a URL Shortener (Bit.Ly Clone)

    12 sections · 1,088 words

    An HLD open-ended question: turn a long URL into a short one and redirect back.

    1. The Problem

    The system takes a long URL and returns a short URL (for example www.bit.ly/aQw12). When the short URL is opened in a browser, the user is redirected to the original long URL. The clone is referred to as Bit.Ly.

    Clarifying questions

    • How many URLs are we targeting? About 20 million URLs.
    • Example long URL: www.example.com/api/v1/userId=1&userName=Aditya.
    • Example short URL: www.bit.ly/aQw12.
    • How small should the short URL be? As short as possible.
    • Which characters may be used? 0-9, a-z, A-Z.

    2. Flow

    1. A user comes to our service with a long URL.
    2. We give back a short URL.
    3. The user puts the short URL in a browser and is redirected to the long URL.

    Two tasks: short URL generation and user redirect.

    3. Back-of-the-Envelope Calculation

    QPS:

    20 million URLs generated per day.

Write operations: 20 million / day
Write ops/sec:
20 * 2^20 / 86,400
= 0.0002314814815 * 2^20
= 231.48 * 10^-6 * 2^20
= 231 * 2^-20 * 2^20
~ 231 operations/sec

Read operations (write : read = 1 : 10):
Read ops/sec = 231 * 10 = 2310 operations/sec

    Storage unit (assume 5 years, 20 million records/day):

    20 * 2^20 * 365 days * 5 years records
= 36,500 * 2^20 records
= 36.5 * 10^3 * 2^20 records
= 36.5 * 2^10 * 2^20 records
= 36.5 Billion records to store

Assume 1 record = 100 bytes:
36.5 Billion * 100 bytes
= 36.5 * 2^30 * 0.1 * 2^10
= 3.65 * 2^40
= ~3.65 TB

    4. API Endpoints

    Two endpoints:

    1. Generate a short URL.
    2. Redirect to the long URL.

    Generate a short URL - any of these shapes:

    POST : www.bit.ly/api/v1/generate
       Query param: longURL = value

POST : www.bit.ly/api/v1/generate/{{longURL}}

POST : www.bit.ly/api/v1/generate
       Body: { "longURL": value }

Return: shortURL

    Redirect to the long URL:

    GET : www.bit.ly/{{shortURL}}
Response: Redirect to Long URL

    5. How to Redirect

    When www.bit.ly/QW123 is opened, the service can answer 200 OK with the long URL, or a redirect status.

    Status codes:

    • 301 - permanent redirection.
    • 302 - temporary redirection.

    Trade-off:

    • 301 (bit.ly/QW123 -> long URL): the browser caches the destination, so the server stays small and DB read queries are minimum.
    • 302 (bit.ly/QW123 -> service -> long URL): the server must be scalable and DB reads are optimized, but we can collect user metrics.

    Decision: use 302 for this application.

    6. Initial Flow

    1. URL shortening (POST).
    2. URL redirect (GET).

    The mapping is Long URL --> short URL, conceptually a hash map/hash table:

    table.get(shortURL) = longURL

Key:   short URL
Value: Long URL

    7. Generating the Short URL

    The obvious idea is a hash function: LONG URL --> Hash Function --> SHORT URL, using SHA-1, MD5, SHA-256, or UUID.

    Hash value length: the allowed symbols are 0-9, a-z, A-Z, giving 10 + 26 + 26 = 62 characters. Using permutations:

    1 character  -> 62 possible URLs
2 characters -> 62^2
3 characters -> 62^3
n characters -> 62^n

    We need 62^n >= 36.5 Billion. At n = 6, 62^6 is about 56 billion records, so N = 6 (www.bit.ly/_ _ _ _ _ _).

    Collisions

    Hashing with existing algorithms produces very long values and leads to too many collisions, so a hash + collision removal loop is needed:

    Long URL --> shortURL (hash)
              |
        exists in DB?
        yes -> generate temp, retry
        no  -> save to DB

    Disadvantages: DB hits increase, and it is slow because of the recursive calls.

    8. Base X Approach

    Instead of hashing to a string, convert a number from base 10 to base 62 using the 62 characters:

    Number Base 62
    0 0
    1 1
    9 9
    10 a
    11 b
    35 z
    36 A
    61 Z

    Example: convert 14320 into base 62.

    14320 / 62 = 230 remainder 60
  230 / 62 =   3 remainder 44
    3 / 62 =   0 remainder 3

Digits (high to low): 3, 44, 60
44 -> I, 60 -> Y
3 44 60 = 3IY

    So www.example.com can be stored as id 14320, short URL 3IY, giving www.bit.ly/3IY.

    • Advantage: collision is impossible.
    • Disadvantages: 1. Need a unique ID generator. 2. URL length is not fixed. 3. It is easy to figure out the next generated short URL (if the id is incremented by 1).

    Example: long URL https://www.example.com/get/code/userId=124, unique ID 14320, short URL base62(14320) = 3IY.

    9. The Unique ID Generator

    We need to build a unique ID generator. In a distributed system, multiple DBs (shards) each generate their own IDs, so two IDs can be the same. The alternative is a centralized ID generator.

    10. Storing and Redirection

    Storing: client POST -> LB -> server -> longURL -> cache -> DB.

    Redirection: client GET shortURL -> LB -> server -> 302 -> longURL from cache/DB.

    11. Distributed URL Shortener

    What if the unique ID generator produces a value that, converted to base 62, is more than 6 digits? Not possible: 62^6 is about 56 billion unique records, while only 36.5 billion need to be stored. A cache sits in front of the DB.

    12. NoSQL vs SQL Choice

    The mapping starts as a hash map, which maps naturally to NoSQL (Amazon DynamoDB; MongoDB is more complicated). Moving to a SQL DB is presented as a better design because:

    1. Production-level queries like "for a particular user, how many URLs have been generated so far" are easier.
    2. SQL supports complex queries efficiently.
    3. Write operations are faster in SQL than in NoSQL.

    The SQL table uses indexing:

    Column Role
    ID primary key
    shortURL indexed
    longURL value

    Two hash functions are now at play:

    1. Find the shard (DB) - SHA-1.
    2. Find the shortURL from the longURL - MD5.

    The flow also checks whether the long URL already exists: if it does, return the existing short URL; if not, run the hash function and create one.
