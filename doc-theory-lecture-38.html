    Lecture 38 - Spring JWT Authentication

    22 sections · 4,637 words

    Lecture 38

    Scope evidence: "Spring JWT Authentication | JWT Internals & Stateless Security" (playlist map, verified). Repo folder is the springPracticalDemo project extended for JWT: config.SecurityConfig, controller.AuthController, controller.UserController, controller.RoleController, dto.LoginRequestDto, dto.LoginResponseDto, entity.CustomUserDetails, entity.User, entity.Role, repository.UserRepository, repository.RoleRepository, service.JwtService, service.AuthService, service.CustomUserDetailsService, and application.properties.

    Every HTTP request arrives with no memory of the requests before it, so authentication cannot be "done once and remembered" unless the client and server agree on a credential that keeps travelling. This lecture follows the whole story: why a server-side session exists, why it is called stateful, why a JWT is a stateless client-carried credential, why Base64URL is encoding and not encryption, why the signature is what protects a token, and how Spring Security turns a signed JWT into the same Authentication a password login produces.

    1. The Problem: Authentication on Every Request

    Consider a protected endpoint such as /profile that returns the logged-in user's name. If the request carries valid credentials, authentication succeeds:

    GET /profile + Authorization: Basic ...   -> authentication succeeds

    But a second request without credentials is a completely separate HTTP request:

    GET /profile   -> 401 Unauthorized

    Why? HTTP does not automatically remember that a previous request was authenticated.

    Authenticating one request does not automatically authenticate future requests. If the server wants to remember an authenticated client, it needs an identifier travelling with later requests.

    Important: HTTP is stateless. "The user logged in earlier" is knowledge the server must reconstruct each request, from stored state keyed by an identifier or from a credential the client re-sends.

    2. Session-Based Authentication

    After a successful username/password login, Spring Security has an authenticated Authentication object:

    Authentication
|-- Principal
|-- Authorities
|-- authenticated = true

    Instead of discarding this state after the request, the server can associate it with an HTTP session:

    Server: Session ABC123 -> SecurityContext -> Authentication
        (Principal: aditya, Authorities: ROLE_USER)

    The client receives only the session identifier; the value ABC123 by itself tells us almost nothing. In a Spring Boot servlet application the session ID commonly travels through a cookie:

    Cookie: JSESSIONID=ABC123

    Session login flow: the client sends username/password; the server authenticates, creates an HttpSession and SecurityContext, and replies with Set-Cookie: JSESSIONID=ABC123. A future request sends that cookie, and the server finds session ABC123 to restore the Authentication.

    JSESSIONID does not normally contain the username, password, or roles. It is essentially an identifier that points to server-side session state.

    Interviewer's perspective: "Where is the user stored after login?" With sessions, the answer is the server (a session store); the cookie only holds a pointer. That single fact is what makes sessions stateful and what JWT later removes.

    3. Session Management and Why Sessions Are Stateful

    A typical session-based configuration enables form login, HTTP Basic, and session creation, and Spring Security can persist the SecurityContext using an HttpSession-backed SecurityContextRepository. SessionCreationPolicy controls how Spring Security behaves with HTTP sessions:

    Policy Creates session? Uses existing session? Mental model
    ALWAYS Yes Yes Always session-based
    IF_REQUIRED When needed Yes Create a session when security requires one
    NEVER No Yes Do not create a session, but use one if it already exists
    STATELESS No No (for restoring the SecurityContext) Authenticate each request independently

    For session-based authentication, IF_REQUIRED is common. For JWT authentication later, STATELESS is used. With a session, the request may contain only Cookie: JSESSIONID=ABC123, but the server still has to remember what that session represents: ABC123 -> Aditya, XYZ456 -> Rohit, PQR789 -> Priya.

    Authentication state therefore exists on the server. This is why session-based authentication is called stateful authentication. At scale that means the server keeps and consults a session entry for every authenticated client, so the "who is this" knowledge lives in server-side storage rather than in the request itself.

    Important: "Stateful" is not a bug, it is a design. It becomes a scaling concern because every authenticated client needs a server-held entry, and any server that answers the request must be able to find that entry.

    4. Why JWT? A Stateless, Client-Carried Credential

    JWT stands for JSON Web Token. The central idea is a question:

    Can a user authenticate once without the server maintaining a
separate session entry for every authenticated client?

    With a session, JSESSIONID = ABC123 -> Session Store -> SecurityContext -> Authentication. A JWT can instead carry claims such as {"sub":"aditya","roles":["ROLE_USER"],"iat":1786570000,"exp":1786573600}. The server can use information inside the token to reconstruct authentication for each request:

    JWT -> claims -> Authentication -> SecurityContext

    The server no longer needs to preserve the user's Authentication object in an HTTP session. That is what "stateless" buys: the credential itself carries enough information to rebuild the identity, so a protected request does not depend on a stored session entry.

    Interviewer's perspective: The best one-line answer for "why JWT?" is "so the server does not have to remember a session per user; the token carries the claims and the client re-sends them on every request."

    5. The Security Problem With Client-Carried Data

    Suppose the token contains "roles": ["ROLE_USER"]. What prevents a client from changing it to "roles": ["ROLE_ADMIN"]? The server needs to answer two questions:

    Was this information issued by a trusted party?
Has the information been modified after it was issued?

    That is the purpose of the signature.

    Important: Because the payload travels through the client, it must be assumed hostile. The signature is the only reason the server can trust a claim it did not personally keep.

    6. Why Not Send Plain JSON? Base64URL Is Encoding, Not Encryption

    A naive token could be raw JSON such as {"sub": "aditya", "role": "ROLE_USER"}. But raw JSON is inconvenient as a transport format: it contains spaces, braces, quotes, and possibly line breaks; the same JSON can be formatted differently; tokens should be easy to transport as a compact string; and cryptographic signing needs a precise byte representation.

    JWT therefore uses Base64URL encoding for its compact representation. For example:

    {"sub":"42"}   ->   eyJzdWIiOiI0MiJ9

    Base64URL provides a URL-safe textual representation of bytes and generally removes trailing padding. The important point is:

    Base64URL is encoding, not encryption.

    Anyone with the token can decode the header and payload; no key is required merely to decode. So JWT payloads are not hidden data, and Base64URL does not compress: encoded data is larger than the original bytes.

    Golden rule: Base64URL encodes, it never encrypts. If you would not write a value on a postcard, do not put it in a JWT payload.

    7. Why Encoding Alone Is Insecure, and Why a Plain Hash Is Not Enough

    Suppose the token is only Base64URL(payload) with payload {"sub": "user-42", "role": "STUDENT"}. An attacker could:

    1. Decode the payload.
2. Change STUDENT to ADMIN.
3. Encode it again.
4. Send the modified value.

    The server would have no cryptographic way to know whether the data was genuinely issued by it. We need:

    Integrity    -> the protected data has not been modified.
Authenticity -> the protected data was created by someone
                possessing the trusted signing key.

    A naive next idea might be a hash: token = payload + SHA256(payload). But an attacker can modify the payload and calculate a new SHA-256 hash themselves:

    Original:            role = STUDENT
Attacker changes:    role = ADMIN
Attacker calculates: SHA256(modified payload)

    A plain hash can answer "does this hash match this data?" but it cannot answer "was this data produced by my trusted server?". To establish authenticity, the calculation must depend on a secret or private key that the attacker does not possess.

    Important: A hash detects accidental corruption; it does not establish origin. Only a keyed or private-key calculation ties the data to a trusted issuer.

    8. Structure of a Signed JWT: HEADER.PAYLOAD.SIGNATURE

    A signed JWT commonly has three parts, each Base64URL encoded:

    HEADER.PAYLOAD.SIGNATURE          (example shape: xxxxx.yyyyy.zzzzz)

    The header names the algorithm and type, for example { "alg": "HS256", "typ": "JWT" }: alg specifies the cryptographic algorithm used to sign the token, and typ describes the token type. The payload holds claims such as iss, sub, aud, role, iat, and exp.

    Common JWT claims:

    Claim Meaning
    iss Issuer - who issued the token
    sub Subject - who or what the token represents
    aud Audience - which application/API should accept it
    iat Issued At - when the token was created
    exp Expiration Time - when the token expires
    jti Unique identifier for the token

    The JWT standard defines registered claims, but not every claim is mandatory; the application or protocol decides which are required. Custom claims are allowed, such as { "roles": ["ROLE_USER"] }. Because the payload is readable, never store passwords, API keys, card numbers, or private personal information.

    The signature protects the encoded header and encoded payload:

    Base64URL(header) + "." + Base64URL(payload)  -> signing input
signature = cryptographic_sign(signingInput, signingKey)
Final JWT: Base64URL(header) . Base64URL(payload) . Base64URL(signature)

    Mnemonic for the three parts: H-P-S (Header, Payload, Signature). A signed JWT is always three parts; a four-part JWE is a different thing.

    9. Symmetric Signing With HS256 and Symmetric Keys

    HS256 means HMAC using SHA-256:

    signature = HMAC-SHA256(secretKey,
                        Base64URL(header) + "." + Base64URL(payload))
headerEncoded.payloadEncoded + secret key -> HMAC-SHA256 -> signature

    The client receives headerEncoded.payloadEncoded.signature. What happens if the payload changes? The original payload contains "role": "STUDENT" and an attacker changes it to "role": "ADMIN". The payload encoding changes, which means the signing input changes:

    Original: header.originalPayload
Modified: header.modifiedPayload

    Without the secret key, the attacker cannot calculate the correct HMAC for the modified input. When the modified token reaches the server:

    Server recalculates expected signature using its secret
-> Expected signature != token signature
-> Reject token

    The JWT signature does not physically prevent someone from editing the token. It makes unauthorized modification detectable. With HS256, the signing key equals the verification key: the same secret is used to create and verify the HMAC (Issuer: HMAC(message, secret), Verifier: HMAC(message, same secret)).

    Advantages: simple, fast, convenient when one trusted application both issues and validates tokens. Limitation: every service that verifies the token must know the same secret, so anyone who has the shared secret can not only verify tokens but also create valid tokens; if one service is compromised, the shared signing secret may also be compromised.

    10. Asymmetric Signing and Symmetric vs Asymmetric

    Asymmetric cryptography uses a key pair with different responsibilities:

    Private key -> creates signatures
Public key  -> verifies signatures

    Common JWT signature algorithms include RS256 (RSA signature with SHA-256) and ES256 (ECDSA signature with SHA-256). For RS256, conceptually:

    signature = Sign(privateKey, Base64URL(header) + "." + Base64URL(payload))
Verification: Verify(publicKey, signingInput, signature)

    A typical architecture becomes: the authentication server holds the private key plus the public key, while the course, payment, and admin services receive only the public key.

    The resource services can verify signatures using the public key but cannot create new valid signatures. This model is useful when one authorization server issues tokens and multiple APIs validate them.

    Property HS256 RS256 / ES256
    Key model Shared secret Private/public key pair
    Signing Secret key Private key
    Verification Same secret key Public key
    Can verifier create tokens? Yes, if it has the secret No, if it only has the public key
    Simple for one application Yes More setup
    Useful for multiple independent APIs Less ideal Very useful

    Mnemonic: HS = "Handshake secret, same key both ways"; RS = "Read with public, Sign with private."

    Interviewer's perspective: If asked "why pick RS256 over HS256?" the answer is distribution of trust: with RS256, verifiers can check tokens without being able to mint them, so a compromised verifier does not become a token factory.

    11. JWT Tampering Experiment

    A useful way to understand JWT security is to create a token, decode it, modify its payload, and verify it again. Original shape A.B.C (A header, B payload, C signature) with payload {"sub": "aditya", "role": "STUDENT"}. Changing the role to ADMIN makes the encoded payload B2; a tool with the secret can produce a valid C2, but an attacker cannot.

    A.B2.C2

    But a real attacker who does not know the secret cannot calculate C2. The attacker's tampered token would instead look like:

    A.B2.C     (original header + modified payload + original signature)

    The payload can still be decoded and may visibly show "role": "ADMIN", but signature verification fails because the signature was created for the original payload:

    Modified signing input -> Old signature no longer matches -> Invalid Signature

    This demonstrates the central security property of a signed JWT: the payload is readable and editable, but unauthorized changes cause signature verification to fail.

    Important: Never trust a decoded payload until the signature has verified. Reading a JWT is not the same as validating it.

    12. JWT Authentication Flow and the Resource Server Dependency

    There are two major flows in the application. Login flow:

    POST /auth/login { "username": "aditya", "password": "123456" }
-> AuthenticationManager -> DaoAuthenticationProvider
-> CustomUserDetailsService -> Database -> PasswordEncoder
-> Authentication successful -> Generate JWT -> Return token

    Future protected request:

    GET /profile + Authorization: Bearer eyJhbGciOi...
-> Extract JWT -> Validate JWT -> Identify user
-> Create Authentication -> SecurityContext -> Authorization -> Controller

    Add Spring Security Resource Server support with the dependency spring-boot-starter-oauth2-resource-server from org.springframework.boot. Spring Security Resource Server can authenticate requests using bearer JWTs, including custom JWTs issued by the application itself.

    Important: Resource Server support does not require you to run a full OAuth2 Authorization Server. It is the piece that understands Authorization: Bearer <JWT> and validates it.

    13. JwtEncoder vs JwtDecoder: Secret, SecretKey, Encoder

    Spring Security separates token creation and token validation into two responsibilities:

    JwtEncoder -> CREATE / SIGN JWT
JwtDecoder -> READ / VERIFY / VALIDATE JWT

    For this application, HS256 is used, so the same secret key signs and verifies. This keeps the demonstration simple because the same Spring Boot application both issues and validates the token.

    Aspect JwtEncoder JwtDecoder
    Responsibility Create and sign a JWT Read, verify, and validate a JWT
    Input JwtClaimsSet via JwtEncoderParameters The encoded token string
    Output A Jwt whose getTokenValue() is the string A trusted Jwt with validated claims
    Uses the key to Sign Verify
    HS256 key Shared secret key Same shared secret key
    Concrete class NimbusJwtEncoder NimbusJwtDecoder

    Generate a sufficiently long Base64-encoded secret with openssl rand -base64 32. Configuration:

    jwt.secret=${JWT_SECRET}
jwt.issuer=coderarmy-api
jwt.expiry=900

    Here 900 seconds = 15 minutes. For classroom demos the secret can temporarily live in application.properties; in production, never commit signing secrets to Git. Create the SecretKey, then the JwtEncoder:

    @Bean
public SecretKey jwtSecretKey(@Value("${jwt.secret}") String secret) {
    byte[] decodedKey = Base64.getDecoder().decode(secret);
    return new SecretKeySpec(decodedKey, "HmacSHA256");
}

@Bean
public JwtEncoder jwtEncoder(SecretKey secretKey) {
    return NimbusJwtEncoder.withSecretKey(secretKey)
            .algorithm(MacAlgorithm.HS256)
            .build();
}

    Conceptually the Base64 config value decodes to raw key bytes forming the SecretKey, which both encoder and decoder share. The application depends on the JwtEncoder abstraction; NimbusJwtEncoder implements it.

    Interviewer's perspective: Expect "why do you need both an encoder and a decoder if you use one secret?" The answer is separation of concerns: signing and verification are different operations with different trust assumptions, and asymmetric setups make the split even more visible.

    14. Login DTOs, JwtService, and /auth/login

    LoginRequestDto carries username and password; LoginResponseDto (a record) carries accessToken. The client sends { "username": "aditya", "password": "123456" } and the server replies { "accessToken": "eyJhbGciOiJIUzI1NiJ9..." }. Create JwtService:

    @Service
public class JwtService {
    private final JwtEncoder jwtEncoder;

    @Value("${jwt.expiry}")
    private long expiry;

    @Value("${jwt.issuer}")
    private String issuer;

    public JwtService(JwtEncoder jwtEncoder) {
        this.jwtEncoder = jwtEncoder;
    }

    public String generateToken(Authentication authentication) {
        Instant now = Instant.now();
        List<String> authorities = authentication.getAuthorities()
                .stream()
                .map(GrantedAuthority::getAuthority)
                .toList();
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer(issuer)
                .issuedAt(now)
                .expiresAt(now.plusSeconds(expiry))
                .subject(authentication.getName())
                .claim("authorities", authorities)
                .build();
        Jwt jwt = jwtEncoder.encode(JwtEncoderParameters.from(claims));
        return jwt.getTokenValue();
    }
}

    The service receives an already authenticated Authentication (Principal -> aditya, Authorities -> ROLE_USER, Authenticated -> true) and converts that result into claims:

    • issuer produces "iss": "coderarmy-api"; it identifies who issued the JWT, and the decoder can later accept tokens only from this issuer.
    • subject from authentication.getName() produces "sub": "aditya"; it identifies who the token represents.
    • issuedAt produces the iat claim recording when the token was created.
    • expiresAt(now.plusSeconds(expiry)) produces the exp claim; after this time the token should no longer be accepted.
    • .claim("authorities", authorities) adds { "authorities": [ "ROLE_USER" ] }.

    Why store authorities in the JWT? sub answers who the user is and authorities answers what they may do, so later requests skip the JWT -> username -> database -> UserDetails lookup and go straight from JWT (sub, authorities) -> Authentication. This is what makes the example stateless.

    Create /auth/login in AuthController: build an unauthenticated UsernamePasswordAuthenticationToken from the request, call authenticationManager.authenticate(authenticationRequest), and return new LoginResponse(jwtService.generateToken(authentication)). Password authentication is unchanged; JWT generation happens only after it succeeds.

    username + password
-> UsernamePasswordAuthenticationToken unauthenticated
-> AuthenticationManager -> DaoAuthenticationProvider
-> CustomUserDetailsService -> Database -> PasswordEncoder
-> Authentication (authenticated = true)
-> JwtService -> JwtEncoder -> JWT

    Important: Token issuing lives behind a successful authentication. JwtService never decides who the user is; it only translates an already authenticated Authentication into signed claims.

    15. Authenticating Future Requests: Decoder, Converter, and the Final SecurityFilterChain

    JWT creation is only half of the process. When a token comes back from the client, the application must turn JWT string -> verify signature -> validate claims -> trusted Jwt object. This is the responsibility of JwtDecoder:

    @Bean
public JwtDecoder jwtDecoder(SecretKey secretKey,
                             @Value("${jwt.issuer}") String issuer) {
    NimbusJwtDecoder decoder = NimbusJwtDecoder
            .withSecretKey(secretKey)
            .macAlgorithm(MacAlgorithm.HS256)
            .build();
    decoder.setJwtValidator(
            JwtValidators.createDefaultWithIssuer(issuer));
    return decoder;
}

    The decoder uses the same HS256 secret key that was used by the encoder, and it configures validation for the expected issuer. What the decoder checks, for an incoming HEADER.PAYLOAD.SIGNATURE:

    Is this structurally a valid JWT?
-> Can the signature be verified using the trusted secret key?
-> Are the standard claims valid?
-> Is the issuer correct?
-> Is the token currently valid?

    Only after these checks can the resulting claims be treated as trusted authentication data.

    Map JWT authorities into Spring Security. Resource Server normally maps scopes like { "scope": "read write" } to SCOPE_read and SCOPE_write. This app stores ROLE_USER/ROLE_ADMIN in a custom authorities claim, so Spring must read that claim and add no prefix via a JwtGrantedAuthoritiesConverter (setAuthoritiesClaimName("authorities"), setAuthorityPrefix("")):

    JwtGrantedAuthoritiesConverter:
    setAuthoritiesClaimName("authorities");
    setAuthorityPrefix("");
JwtAuthenticationConverter:
    setJwtGrantedAuthoritiesConverter(authoritiesConverter);

    The empty prefix is important because the token already contains ROLE_USER; exactly ROLE_USER is wanted, keeping .hasRole("USER") and .hasRole("ADMIN") compatible. The final SecurityFilterChain:

    csrf disabled
sessionManagement: SessionCreationPolicy.STATELESS
authorizeHttpRequests:
  permitAll: /auth/login, /register
  hasRole("ADMIN"): /admin/**
  authenticated: anyRequest
oauth2ResourceServer: jwt -> jwtAuthenticationConverter

    Why SessionCreationPolicy.STATELESS? It means Spring Security should not use the HTTP session to preserve authentication between requests. Each protected request must carry its own authentication material, in this case Authorization: Bearer <JWT>:

    Request + Bearer JWT -> JWT validation -> Authentication
-> SecurityContext -> Authorization

    After the request completes the application does not rely on an HTTP session to remember that authentication. Why oauth2ResourceServer().jwt()? Spring Security packages bearer-token JWT authentication under Resource Server support, which can protect an API with a custom JWT without implementing a full OAuth2 Authorization Server:

    Protected request -> Authorization: Bearer <JWT>
-> Spring Security Resource Server -> JWT validation -> Authentication

    Important: CSRF is disabled here because this is a stateless bearer-token API. The empty authority prefix matters just as much: a stray SCOPE_ or ROLE_ prefix silently breaks every .hasRole(...) rule.

    16. Two Providers, End-to-End Flow, and Session vs JWT

    The application now uses two authentication mechanisms. DaoAuthenticationProvider handles username + password and authenticates login credentials; JwtAuthenticationProvider handles a JWT and authenticates future bearer-token requests. Both produce the same core Spring Security abstraction, Authentication, keeping the architecture consistent regardless of how identity is proven.

    Session authentication vs JWT authentication:

    Session-Based Authentication JWT-Based Authentication
    Server stores authentication state Authentication information is reconstructed from the token
    Client usually sends JSESSIONID Client sends a bearer JWT
    Session ID points to server-side state Token carries claims
    Commonly stateful Can be stateless
    Server restores SecurityContext from session Server validates token and creates authentication per request

    Golden rule: In both models the server still produces an Authentication; the difference is only where the facts live. Sessions keep them on the server; JWTs make the client carry them back, protected by a signature.

    17. Myth vs Reality

    Myth Reality
    "JWT is encrypted, so the payload is secret" Header and payload are Base64URL encoded, not encrypted; anyone can decode them. Only the signature protects integrity.
    "Once you sign a JWT, nobody can edit it" The payload is readable and editable; the signature makes unauthorized edits detectable, not impossible.
    "Base64 is encryption" Base64URL is an encoding; no key is needed to decode it, and it does not compress.
    "A SHA-256 hash proves who issued the token" A plain hash can be recomputed after editing; authenticity needs a secret or private key.
    "HS256 and RS256 are interchangeable" With HS256 every verifier holds the signing secret and could mint tokens; RS256 verifiers hold only the public key.
    "JWT stores no authentication data anywhere" It is stateless between requests; the token still carries the claims the server trusts.
    "You can authorize on a decoded token before verification" Claims are trusted only after signature and claim validation. Decoding is not validating.

    18. Common Trap Questions

    Trap 1 - "JWT payloads are encrypted." Verdict: False. Header and payload are Base64URL encoded, readable by anyone; never put passwords, API keys, card numbers, or private data inside.

    Trap 2 - "The signature stops an attacker from editing the token." Verdict: False. It cannot block edits; it makes them detectable. A changed payload changes the signing input, so the old signature no longer matches.

    Trap 3 - "A plain hash is enough to secure a token." Verdict: False. An attacker can recompute a plain hash after editing; authenticity needs a secret or private key they lack.

    Trap 4 - "HS256 and RS256 differ only in algorithm name." Verdict: False. HS256 uses one shared secret, so any verifier can also create tokens; RS256 verifiers hold only the public key.

    Trap 5 - "You need an OAuth2 Authorization Server to use Spring's JWT support." Verdict: False. spring-boot-starter-oauth2-resource-server plus oauth2ResourceServer().jwt() validate custom bearer JWTs without a full Authorization Server.

    Trap 6 - "You should keep the default authority prefix." Verdict: False. By default scopes map to SCOPE_read style authorities; this app reads ROLE_USER from the authorities claim with an empty prefix.

    Trap 7 - "JWT makes the login step optional on future requests." Verdict: False. The token is only issued after a successful password login; later requests skip the database lookup, not the login.

    19. Points to Remember

    1. HTTP is stateless, so each request must carry or trigger its own proof of identity.
    2. Session auth is stateful: the server keeps one session entry per client; the client sends only JSESSIONID.
    3. STATELESS disables session auth; each request must carry Authorization: Bearer <JWT>.
    4. A signed JWT is HEADER.PAYLOAD.SIGNATURE, each part Base64URL encoded.
    5. Base64URL is encoding, not encryption: anyone can decode it; it does not compress.
    6. The signature gives integrity and authenticity; it makes tampering detectable, not impossible.
    7. HS256 signs and verifies with one secret; RS256/ES256 sign with a private key and verify with a public key.
    8. JwtEncoder creates and signs tokens; JwtDecoder verifies the signature and validates claims.
    9. Store sub and authorities so later requests rebuild authentication without a database lookup.
    10. JwtAuthenticationConverter reads authorities with an empty prefix so .hasRole(...) matches; DaoAuthenticationProvider does passwords, JwtAuthenticationProvider does tokens.

    20. Likely Interview Questions

    Question Crisp Answer
    Why can't the server remember a login from one request to the next? HTTP is stateless; each request is isolated, so a credential must be re-sent or looked up.
    Why is session auth called stateful? The server stores a session entry per client; the cookie only points at it.
    What does JWT stand for and what is the core idea? JSON Web Token; a client-carried credential whose claims rebuild authentication without a stored session.
    Is a JWT encrypted? No; header and payload are Base64URL encoded and readable. Only the signature protects integrity.
    What is Base64URL and why use it? An encoding giving bytes a URL-safe compact form; not encryption, and it does not compress.
    Why is Base64URL alone insecure? An attacker can decode, change, re-encode, and resend; without a keyed signature the server cannot detect it.
    Why is a plain SHA-256 hash not enough? The attacker recomputes the hash after editing; authenticity needs a secret key they do not possess.
    What are the three parts of a signed JWT? Header, payload, signature, dot-separated, each Base64URL encoded.
    Difference between HS256 and RS256? HS256: one shared secret signs and verifies. RS256: private key signs, public key verifies.
    What does JwtEncoder do versus JwtDecoder? Encoder creates/signs from a JwtClaimsSet; decoder verifies the signature and validates claims.
    What does the decoder check? Structure, signature against the trusted key, standard claims, issuer, and current validity.
    Why set an empty authority prefix? The authorities claim already holds ROLE_USER; no extra prefix keeps .hasRole("USER") matching.
