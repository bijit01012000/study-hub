    KISS

    10 sections · 697 words

    Principle · LLD Core Concepts · Concept 05 of 09

    The Idea

    Keep It Simple.

    You'll See This

    • A one-line loop rewritten as a dense chain nobody reads in one pass.
    • A full strategy hierarchy built for two cases that will only ever be two.
    • Config-driven logic standing in for what's really one constant.

    Plain, not clever.

    Before

    int cost = w<=1
    ? (exp?300:100)
    : (w<=5
    ? (exp?500:250)
    : (exp?900:400));
// reads like a puzzle.
// what does each branch mean?
// which case is the express
// surcharge actually applied to?
// you have to trace it to know.

    Clever.

    After

    int shippingCost(double weightKg, boolean express) {
    if (weightKg <= 1)
        return express ? 300 : 100;
    if (weightKg <= 5)
        return express ? 500 : 250;
    return express ? 900 : 400;
}
// same logic. one weight band per line.
// a name on the method says what it computes.

    Don't Oversimplify

    • Simple isn't "fewest lines." A 5-minute-to-parse regex isn't simple.
    • Don't collapse two genuinely different cases into one terse branchless line.

    Quick Check

    If you'd have to explain your own code to yourself tomorrow, it wasn't simple, it was clever.

    How It's Built

    The Shape

    weight <= 1kg?
weight <= 5kg?
else: top band

THREE FLAT CHECKS. READ TOP TO BOTTOM, NO NESTING.

    The Move (3 Steps)

    1. Write the straightforward version first: the one a teammate reads in 10 seconds.
    2. Only add structure when the straightforward version is provably breaking down: growing, duplicated, hard to test.
    3. If you can't say the clever version out loud in one sentence, rewrite it as the boring version.

    In The Interview

    "The shipping cost was one nested ternary three levels deep. I rewrote it as three flat if-checks with a name on the method. Same behaviour, but you read it top to bottom without holding three conditions in your head at once."

    How It's Different

    The Confusion Pairs

    KISS vs YAGNI. YAGNI is about not building structure you don't need. KISS is about not writing code that's harder to read than it needs to be, even for something you do need.

    Simple vs simplistic. Simplistic skips a real edge case to look clean. Simple handles the real cases plainly.

    Simple vs short. A golfed one-liner is short and often not simple. Simple is measured by how fast a reader follows it, not by character count.

    KISS vs SOLID. SOLID can add classes. KISS asks whether those classes are earning their complexity today.

    They Say: "walk me through this shipping-cost function"

    • With it: you read it out loud in one breath, because it reads like the sentence it represents.
    • Without: you're re-deriving what each branch of the ternary means as you go.

    Watch Out For

    • A "simple" abstraction with 6 config parameters isn't simpler than 2 concrete classes: count real complexity, not class count.
    • Simplicity is judged by the reader, not the writer. Obvious to you after writing it doesn't mean obvious to someone else.
    • Don't use KISS as cover to skip a real edge case. "Simpler" without handling nulls isn't simpler, it's incomplete.
    • A 200-line "does everything" method isn't simple either. KISS argues for clarity, not for avoiding structure entirely.
    • Optimize for the next reader in a diff a year from now, not for typing less today.
