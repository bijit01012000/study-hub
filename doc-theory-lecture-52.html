    Inter Thread Communication in Java | wait(), notify(), notifyAll() Deep Dive

    23 sections · 3,975 words

    Lecture 52

    Scope evidence: "Inter Thread Communication in Java | wait(), notify(), notifyAll() Deep Dive" plus the lecture's own repo notes (producer-consumer, intrinsic monitor, IllegalMonitorStateException, spurious wakeups), playlist map, verified. Repo evidence: 3 Demo files.

    Inter-thread communication is required when one thread cannot continue safely until another thread changes some shared state. Instead of repeatedly checking that state, a thread can pause and allow another thread to perform the required work. Java provides three methods for this purpose - wait(), notify() and notifyAll() - and they work with an object's intrinsic monitor lock. This lecture builds the producer-consumer box, shows why synchronized alone is not enough, derives the guarded-block pattern, and closes on why these methods belong to Object.

    1. The Producer-Consumer Problem: A One-Slot Box

    Consider a shared box that can hold only one item:

    class Box {
    private int item;
    private boolean hasItem = false;
}

    Two threads use this box: the producer places an item into the box, and the consumer removes the item from the box. The rules are strict:

    • If the box is empty, the consumer must wait.
    • If the box is full, the producer must wait.

    The producer and the consumer are not only competing for access to the shared object. They also depend on the state created by each other. This dependency is the entire reason inter-thread communication exists.

    Memory aid The producer and consumer are dancing partners, not just rivals. Each one's next legal move depends on the state the other left behind.

    2. Why synchronized Alone Is Not Enough

    The synchronized keyword ensures that only one thread can execute a synchronized section for the same monitor at a time. That is necessary, but it is not sufficient.

    class Box {
    private int item;
    private boolean hasItem = false;

    synchronized void produce(int value) {
        item = value;          // no check: may overwrite an unconsumed item
        hasItem = true;
        System.out.println("Produced: " + item);
    }

    synchronized void consume() {
        System.out.println("Consumed: " + item);   // no check: may consume an empty box
        hasItem = false;
    }
}

    This code protects the shared data from simultaneous access, but it does not enforce the producer-consumer rules. Possible problems include:

    • The producer may overwrite an item before it is consumed.
    • The consumer may consume when the box is empty.
    • The consumer may run repeatedly without waiting for a new item.

    Therefore synchronized provides mutual exclusion and memory visibility, but it does not automatically provide condition-based waiting.

    Aspect synchronized only synchronized + wait/notify
    Protects shared data Yes Yes
    Enforces a condition No Yes
    Behaviour when condition is false Thread runs anyway, or spins Thread waits efficiently
    CPU usage while waiting Wasted in a spin loop Thread sleeps, no CPU burned
    Coordination between threads None Explicit signalling
    Correctness of producer-consumer Broken Correct

    3. Busy Waiting - Spinning That Holds the Lock

    One possible approach is to keep checking the condition continuously:

    while (!hasItem) {
    // keep checking
}

    This technique is called busy waiting or spinning. The thread repeatedly asks: Is the item available? Is the item available? The thread is not performing useful work, but it continues consuming CPU time.

    A producer-consumer implementation based on busy waiting may look like this:

    class Box {
    private int item;
    private boolean hasItem = false;

    synchronized void produce(int value) {
        while (hasItem) {
            // keep looping
        }
        item = value;
        hasItem = true;
        System.out.println("Produced: " + item);
    }

    synchronized void consume() {
        while (!hasItem) {
            // keep looping
        }
        System.out.println("Consumed: " + item);
        hasItem = false;
    }
}

    This version has an additional serious problem: the thread holds the monitor lock while looping. The other thread cannot enter the synchronized method to change the condition, so the loop can never end. Even declaring the shared flag volatile does not completely solve the problem. volatile can make the latest value visible between threads, but it does not:

    • Pause a thread
    • Release a monitor lock
    • Provide notification
    • Make multiple operations atomic

    Important Busy waiting while holding the monitor is a self-inflicted deadlock: the waiter never lets the other thread in, and the other thread never gets to change the condition the waiter is spinning on.

    4. The Better Approach: Pause, Release, Wake, Recheck

    Instead of repeatedly checking the condition, a thread should follow a disciplined five-step workflow:

    1. Check whether it can proceed.
    2. Pause if the condition is not satisfied.
    3. Release the monitor so another thread can change the condition.
    4. Wake up when another thread signals that the state may have changed.
    5. Recheck the condition before continuing.

    Java supports this workflow through wait(), notify() and notifyAll().

    5. Mental Model: Shared Resource, Condition, Waiting and Notification

    Most inter-thread communication problems contain three elements: a shared resource, a condition, and a waiting-and-notification mechanism. For the producer-consumer problem:

    • Shared resource: the Box
    • Condition: whether the box contains an item
    • Waiting: the consumer waits when the box is empty
    • Notification: the producer notifies after adding an item

    The reverse also applies:

    • Waiting: the producer waits when the box is full
    • Notification: the consumer notifies after removing the item

    6. What wait() Does

    When a thread calls wait() on an object:

    1. It releases that object's monitor lock.
    2. It enters the waiting set associated with that object.
    3. It enters the WAITING state for an untimed wait().
    4. It remains there until it is notified, interrupted, or wakes spuriously.
    5. Before returning from wait(), it must acquire the same monitor lock again.

    The canonical guarded form is:

    synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    // Continue after the condition becomes true
}

    Important wait() releases only the monitor on which it is called. If the thread holds locks for other objects, those locks are not automatically released.

    Why releasing the lock is essential: suppose the consumer acquires the monitor and discovers that the box is empty. If wait() did not release the monitor, the sequence would be:

    Consumer holds the lock
   → Producer cannot enter
   → Producer cannot add an item
   → Condition can never change

    The system would become stuck. Therefore wait() performs two connected actions: it releases the monitor and it pauses the current thread. This allows another thread to acquire the same monitor and change the shared condition.

    7. Monitor Ownership and IllegalMonitorStateException

    A thread can call wait() only when it owns the monitor of the same object.

    Correct:

    synchronized (lock) {
    lock.wait();
}

    Incorrect:

    lock.wait();   // throws IllegalMonitorStateException

    A thread cannot wait on or release a monitor that it does not own. The same rule applies to notify() and notifyAll().

    Inside a synchronized instance method, the lock is the current object, represented by this:

    synchronized void consume() throws InterruptedException {
    wait();   // equivalent to this.wait()
}

    Here the thread already owns the monitor of this, so the call is valid.

    8. The Waiting Set and the Intrinsic Monitor

    A useful conceptual model is that every Java object can participate in monitor-based synchronization through two facilities:

    1. An intrinsic monitor lock
    2. A waiting set associated with that monitor

    When a thread calls lock.wait(), the following happens:

    Thread releases lock's monitor
   → enters lock's waiting set
   → waits for a signal or another permitted wake-up

    The waiting set belongs to the object, not to the thread. A simple consumer illustrates the mechanism:

    class Box {
    private int item;
    private boolean hasItem = false;

    synchronized void consume() throws InterruptedException {
        while (!hasItem) {
            wait();
        }
        System.out.println("Consumed: " + item);
        hasItem = false;
    }
}

    The consumer releases the Box monitor while waiting. This allows the producer to enter another synchronized method on the same object and produce an item.

    9. What notify() Does - and What It Does Not Do

    When a thread calls lock.notify(), one thread waiting on that object's monitor is selected for wake-up. The selected thread does not continue immediately: it must first reacquire the same monitor. Conceptually:

    One waiting thread is selected
   → it becomes eligible to compete for the monitor
   → notifying thread continues holding the monitor
   → notifying thread exits the synchronized section
   → awakened thread may acquire the monitor
   → awakened thread returns from wait()

    A common misunderstanding is that notify() immediately hands the lock to the waiting thread. It does not.

    synchronized (lock) {
    lock.notify();
    // Current thread still owns the monitor here
}

    The awakened thread cannot continue past wait() until the notifying thread releases the monitor by leaving the synchronized section.

    If several threads are waiting on the same monitor, notify() selects one of them. The selection is arbitrary and should be treated as non-deterministic. The programmer cannot safely assume that a particular producer or consumer will be selected. Just like wait(), notify() must be called while owning the monitor of the same object, otherwise IllegalMonitorStateException is thrown.

    10. notifyAll(): Waking Every Waiting Thread

    notifyAll() wakes all threads waiting on the same object's monitor.

    lock.notifyAll();

    This does not mean that all threads execute simultaneously. The process is:

    All waiting threads become eligible to compete for the monitor
   → only one thread acquires the monitor at a time
   → each awakened thread rechecks its condition
   → threads whose conditions are still false wait again

    11. notify() vs notifyAll() and Why notify() Can Be Risky

    Suppose producers and consumers are both waiting on the same Box monitor:

    • Producer 1 waits for space
    • Producer 2 waits for space
    • Consumer 1 waits for an item
    • Consumer 2 waits for an item

    If the box is full and a consumer removes the item, a producer should wake up. However, notify() may select another consumer. That consumer checks the condition, discovers that the box is empty, and waits again. Meanwhile, all producers may remain asleep even though space is available. This can leave the system stuck even though progress is logically possible.

    notifyAll() avoids relying on the runtime to select the correct category of thread. Every waiting thread gets an opportunity to recheck its own condition.

    Method Behaviour Advantage Risk or Cost
    notify() Wakes one arbitrary waiting thread Lower wake-up overhead May wake a thread whose condition is still false
    notifyAll() Wakes all waiting threads Safer when different conditions share one monitor More threads wake and compete unnecessarily

    Use notify() when:

    • Only one category of thread is waiting.
    • Any selected waiting thread can safely proceed.
    • The waiting conditions are simple and well controlled.

    Use notifyAll() when:

    • Different types of threads wait on the same monitor.
    • Multiple conditions are involved.
    • Correct thread selection cannot be guaranteed.
    • Safety and clarity are more important than minor wake-up overhead.

    For basic monitor-based application code, notifyAll() is usually the safer default.

    12. Spurious Wakeups and the while Golden Rule

    A thread waiting through wait() is permitted to wake up even when no useful condition change has occurred. This is known as a spurious wakeup. A thread may also receive a notification even though the condition it needs is still false. Therefore waking up does not prove that the required condition is true.

    Incorrect:

    if (!hasItem) {
    wait();
}
System.out.println("Consumed: " + item);

    If the thread wakes while hasItem is still false, it continues with invalid state.

    Correct:

    while (!hasItem) {
    wait();
}
System.out.println("Consumed: " + item);

    After every wake-up, the condition is checked again.

    Golden rule Always place wait() inside a loop that checks the guarded condition. Never write if (!condition) { wait(); }; the loop handles spurious wakeups, a notification received by the wrong type of waiting thread, the condition changing again before the awakened thread reacquires the lock, and multiple threads competing for the same shared state.

    13. The Guarded Block Pattern

    A guarded block executes only when a required condition is true. Otherwise, the thread waits. The condition is called the guard condition.

    synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    // Perform the protected operation
    lock.notifyAll();
}

    For the consumer the guard is while (!hasItem) { wait(); }. For the producer the guard is while (hasItem) { wait(); }.

    A guarded block combines five things:

    • Monitor ownership
    • Condition checking
    • Waiting
    • State modification
    • Notification

    14. Complete Producer-Consumer Implementation

    class Box {
    private int item;
    private boolean hasItem = false;

    public synchronized void produce(int value)
            throws InterruptedException {
        while (hasItem) {
            wait();
        }
        item = value;
        hasItem = true;
        System.out.println(
            Thread.currentThread().getName()
            + " produced: " + item
        );
        notifyAll();
    }

    public synchronized int consume()
            throws InterruptedException {
        while (!hasItem) {
            wait();
        }
        int value = item;
        hasItem = false;
        System.out.println(
            Thread.currentThread().getName()
            + " consumed: " + value
        );
        notifyAll();
        return value;
    }
}

    The producer waits while the box is full. The consumer waits while the box is empty. After changing the shared state, each method calls notifyAll(). The shared state must be changed before notification so that awakened threads can observe the new condition after reacquiring the monitor.

    public class Main {
    public static void main(String[] args) {
        Box box = new Box();

        Thread producer = new Thread(() -> {
            for (int value = 1; value <= 5; value++) {
                try {
                    box.produce(value);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
            }
        }, "Producer");

        Thread consumer = new Thread(() -> {
            for (int count = 1; count <= 5; count++) {
                try {
                    box.consume();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    return;
                }
            }
        }, "Consumer");

        producer.start();
        consumer.start();
    }
}

    A possible output is:

    Producer produced: 1
Consumer consumed: 1
Producer produced: 2
Producer produced: 3
Consumer consumed: 3
Consumer consumed: 2

    The exact scheduling order is controlled by the JVM and the operating system, but the rules of the box remain protected.

    15. Handling InterruptedException

    wait() declares InterruptedException because another thread may interrupt a waiting thread.

    try {
    box.consume();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}

    When the method cannot completely handle the interruption, a common practice is to restore the interrupt status with Thread.currentThread().interrupt(). The thread can then stop its current task or allow a higher-level component to decide how to respond.

    Important An empty catch block that swallows InterruptedException hides the interruption and can make cancellation unreliable. Handle it deliberately: stop, propagate, or restore the flag.

    16. sleep() vs wait()

    Both pause a thread, but they are not interchangeable.

    Feature Thread.sleep() wait()
    Declared in Thread Object
    Main purpose Pause for a duration Wait for a condition to change
    Releases monitor lock No Yes
    Requires monitor ownership No Yes
    Common thread state TIMED_WAITING WAITING
    Wakes because of Time completion or interruption Notification, interruption, timeout, or spurious wakeup

    sleep() keeps the monitor:

    synchronized (lock) {
    Thread.sleep(1000);
}

    The thread pauses, but it continues holding lock during the sleep period.

    wait() releases the monitor:

    synchronized (lock) {
    lock.wait();
}

    The thread pauses and releases lock, allowing another thread to enter a synchronized section guarded by the same monitor.

    17. Why wait(), notify() and notifyAll() Belong to Object

    The methods wait(), notify() and notifyAll() are declared in the Object class. They are not declared in Thread because the waiting mechanism is associated with an object's monitor. In Java, a thread does not wait on another thread. It waits for a condition protected by a particular object's monitor.

    synchronized (box) {
    box.wait();
}

    Here box is the monitor object. The current thread owns box's monitor and enters box's waiting set. Another thread must synchronize on the same box object and call box.notify() or box.notifyAll(). Calling wait() on one object and notify() on another object does not establish communication between their waiting sets.

    Interviewer's perspective "Why are wait() and notify() in Object and not Thread?" Because the lock and the waiting set belong to the object, not to the thread. Since every object can be a monitor, the coordination methods must be available on every object, which means they live on Object.

    18. Myth vs Reality

    Myth Reality
    "synchronized already coordinates cooperating threads." It provides mutual exclusion and visibility only; condition-based waiting needs wait/notify.
    "notify() hands the lock to the waiting thread." The notifier keeps the monitor until it exits synchronized; the awakened thread must reacquire it.
    "wait() is just sleep() without a time." wait() releases the monitor and needs a notification; sleep() keeps the monitor and ends by time.
    "An if check around wait() is enough." Spurious wakeups and false notifications require a while loop that rechecks the condition.
    "wait/notify can be called like any ordinary method." They require ownership of the object's monitor, otherwise IllegalMonitorStateException.

    19. Common Trap Questions

    Trap 1 - "Both methods are synchronized, so the producer-consumer problem is solved." No. Mutual exclusion prevents simultaneous access but does not enforce conditions. Without wait/notify the producer can overwrite and the consumer can underflow.

    Trap 2 - "notify() immediately starts the waiting thread." No. The notifying thread keeps the monitor until it leaves the synchronized section; only then can the awakened thread reacquire it and return from wait().

    Trap 3 - "if (!hasItem) wait(); is safe because notify wakes the right thread." No. Spurious wakeups and notifications that reach the wrong category of thread mean the condition must be rechecked in a while loop, never a single if.

    Trap 4 - "I can call lock.wait() without owning lock." No. Calling wait(), notify() or notifyAll() without owning the same object's monitor throws IllegalMonitorStateException.

    Trap 5 - "notify() wakes waiting threads in FIFO order." No. It selects an arbitrary waiting thread; the choice is non-deterministic and must not be relied upon.

    Trap 6 - "Thread.sleep() releases the monitor while it sleeps." No. sleep() holds the lock for the whole interval; only wait() releases the monitor.

    Trap 7 - "wait() and notify() are Thread methods." No. They are declared in Object, because waiting is tied to an object's monitor, not to a thread.

    Trap 8 - "I can notify before changing the shared state." No. Change the shared state first, then notifyAll(), so awakened threads observe the new condition after reacquiring the monitor.

    20. Points to Remember

    1. Call wait(), notify() and notifyAll() only while owning the same object's monitor.
    2. Call these methods on the same object that is used for synchronization.
    3. wait() releases the relevant monitor; sleep() does not.
    4. notify() and notifyAll() do not immediately release the monitor.
    5. A notified thread must reacquire the monitor before continuing past wait().
    6. Always check the condition using while, not if.
    7. Change the shared state before sending the notification.
    8. Prefer notifyAll() when multiple conditions or different waiting-thread types share one monitor.
    9. Keep the condition check and the state modification inside the same synchronized region.
    10. Handle InterruptedException deliberately instead of silently ignoring it.

    21. Likely Interview Questions

    Question Crisp Answer
    Why is inter-thread communication needed? Threads often depend on state changed by each other; instead of polling, they pause and are signalled when the state may have changed.
    Why is synchronized alone not enough? It gives mutual exclusion and visibility but not condition-based waiting, so producers can overwrite and consumers can underflow.
    What does wait() do? Releases the object's monitor, enters its waiting set, moves to WAITING, and reacquires the monitor before returning.
    What does notify() do? Wakes one arbitrary thread waiting on the same monitor; that thread must still reacquire the monitor before proceeding.
    What does notifyAll() do? Wakes all threads waiting on the same monitor; they compete for it one at a time and each rechecks its condition.
    When does wait() throw IllegalMonitorStateException? When the calling thread does not own the monitor of the object on which wait() is invoked.
    Why must wait() be inside a while loop? Spurious wakeups and false notifications mean waking does not prove the condition is true; the loop rechecks it.
    Does notify() transfer the lock? No. The notifier keeps the monitor until it exits the synchronized section.
    notify() vs notifyAll()? notify() wakes one arbitrary thread with lower overhead; notifyAll() wakes all and is safer when different conditions share a monitor.
    How does wait() differ from sleep()? wait() is in Object, releases the monitor and waits for a condition; sleep() is in Thread, keeps the monitor and waits for a duration.
    Why are wait/notify declared in Object? Because the monitor lock and waiting set belong to the object, and every object can be a monitor.
    How should InterruptedException be handled? Do not swallow it; stop the task, propagate it, or restore the interrupt status with Thread.currentThread().interrupt().

    22. Final Summary

    Execution-flow trace of consumer waiting and producer notifying:

    1.  Consumer acquires the Box monitor.
2.  Consumer checks hasItem.
3.  hasItem is false.
4.  Consumer calls wait().
5.  Consumer releases the Box monitor.
6.  Consumer enters the Box waiting set.
7.  Producer acquires the Box monitor.
8.  Producer adds an item.
9.  Producer sets hasItem to true.
10. Producer calls notifyAll().
11. Consumer becomes eligible to compete for the monitor.
12. Producer exits the synchronized method.
13. Producer releases the monitor.
14. Consumer reacquires the monitor.
15. Consumer returns from wait().
16. Consumer rechecks hasItem.
17. Consumer removes the item.

    The awakened thread continues from the wait() call only after reacquiring the monitor.

    Canonical guarded-block snippet:

    synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    // Use or modify shared state
    lock.notifyAll();
}

    Arrow flow:

    synchronized        → protects the shared state (mutual exclusion + visibility)
   |
   +-- while (!condition) → wait()  → releases the monitor, pauses the thread
   |
   +-- another thread changes state, condition becomes true
   |
   +-- notifyAll()     → waiting threads wake, compete, recheck, proceed
    • synchronized → protects the shared state.
    • wait() → releases the monitor and pauses the thread.
    • notify() → wakes one arbitrary waiting thread.
    • notifyAll() → wakes all waiting threads.
    • while condition check → ensures the thread proceeds only when the state is valid.
    • Guarded block → monitor ownership + condition check + waiting + state change + notification.

    Golden rule Hold the monitor to examine the condition, call wait() inside a while loop to release it and pause, and call notifyAll() after changing the state - never if, never before the change.

    One-line takeaway: synchronized makes threads take turns, but wait() inside a while loop plus notifyAll() after the state change is what makes cooperating threads wait for the right condition without busy waiting.
