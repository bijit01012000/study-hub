      107. JPA entity lifecycle — full picture

      Asked at: Most Spring backend rounds · Razorpay · Walmart Labs

      Difficulty: Medium · Topic: Hibernate / JPA

      The question: "What are the JPA entity states and how does an entity transition between them?"

      The 30-second answer: Four states: NEW (just instantiated, no DB row), MANAGED (in persistence context, changes tracked), DETACHED (was managed, persistence context closed), REMOVED (marked for delete, pending flush). Transitions: persist() NEW→MANAGED, merge() DETACHED→MANAGED, remove() MANAGED→REMOVED, end-of-transaction MANAGED→DETACHED.

      Step-by-step thought process:

      1. "NEW: new Order(). Object exists in JVM, no DB awareness. No identity yet (unless you set it manually)."
      2. "MANAGED: em.persist(order) or query result. Persistence context tracks every change to the object's fields — dirty checking flushes them on commit."
      3. "DETACHED: persistence context closed (transaction commit + EM close), or entity explicitly detached. Changes no longer tracked. To re-attach, use merge() which returns a managed copy."
      4. "REMOVED: em.remove(managed) marks it for delete. Actual DELETE SQL runs at flush. Until flush, it's still in the persistence context."
      5. "Dirty checking: at commit (or flush), JPA compares managed entities to their snapshots. Any field difference triggers UPDATE SQL. Why you don't call save() after mutating a managed entity."

      Edge cases to mention:

      • merge() does NOT return the same instance — it returns a managed copy. Order merged = em.merge(detached); — work with merged, not detached
      • Detached entities lose lazy collections — accessing them throws LazyInitializationException
      • In Spring Data JPA, save() calls persist for new entities and merge for ones with an ID — convenient but masks the state difference

      What NOT to say:

      • "Entities are always managed" — they're managed only inside a session and an attach
      • "save() is the universal verb" — JPA distinguishes persist, merge, remove

      Common follow-up: "What's the difference between persist and merge?"

      108. Lazy vs eager loading — and the N+1 problem

      Asked at: Most Spring backend rounds · Razorpay · Swiggy · Walmart Labs

      Difficulty: Medium-Hard · Topic: Hibernate / JPA

      The question: "Explain lazy vs eager loading. What's the N+1 problem and how do you fix it?"

      The 30-second answer: Lazy = related entities loaded on first access via a proxy (one query for parent, additional queries per child access). Eager = loaded immediately with the parent (single query with JOIN). N+1 is the classic lazy-loading trap: fetch N orders, then call order.getCustomer() in a loop — that's N additional queries. Fix with JOIN FETCH, entity graphs, or batch fetching.

      Step-by-step thought process:

      1. " @ManyToOne and @OneToOne are eager by default. @OneToMany and @ManyToMany are lazy by default."
      2. "Lazy works via a Hibernate proxy. order.getCustomer() triggers a SELECT for that customer. Convenient — but in a loop, you trigger N queries."
      3. "N+1: SELECT * FROM orders (1 query) + N calls to getCustomer() (N queries). Spot it by enabling SQL logging."
      4. "Fix 1: JOIN FETCH in JPQL. SELECT o FROM Order o JOIN FETCH o.customer WHERE.... Loads orders + customers in one query."
      5. "Fix 2: @EntityGraph(attributePaths = "customer") on the repository method. Fix 3: @BatchSize(size = 50) on the association — Hibernate batches the lazy loads."

      Edge cases to mention:

      • Default @OneToOne as eager is often wrong — almost always make it lazy unless you always need the related entity
      • LazyInitializationException — fetching a lazy field after the session closed. Use Open-Session-in-View (controversial) or fetch eagerly in repository methods
      • For lists, JOIN FETCH on a @OneToMany returns duplicate parents — use SELECT DISTINCT or Set<> collections

      What NOT to say:

      • "Make everything eager to avoid N+1" — eagerly loads way too much, slow queries
      • "Hibernate caches it so N+1 doesn't matter" — first-level cache only saves within same session

      Common follow-up: "How does an EntityGraph differ from JOIN FETCH?"

      109. First-level cache and dirty checking

      Asked at: Most Spring backend rounds · Razorpay · Walmart Labs

      Difficulty: Medium · Topic: Hibernate / JPA

      The question: "What's the first-level cache in Hibernate and how does dirty checking use it?"

      The 30-second answer: First-level cache (a.k.a. persistence context) is scoped to the EntityManager / Session. Every managed entity lives there as a snapshot. Dirty checking compares the current entity state to the snapshot at flush — any difference becomes an UPDATE. Disabled per-entity via @Immutable or via setReadOnly().

      Step-by-step thought process:

      1. "Every entity loaded or persisted goes into the persistence context — keyed by entity class + primary key."
      2. "Within one session, em.find(Order.class, id) twice returns the SAME object (identity equality). Second call skips the DB."
      3. "Hibernate stores a snapshot of each entity's fields at load time. At flush (commit or explicit flush()), it compares current vs snapshot — emits UPDATE for any field that changed."
      4. "No need to call save() for mutations on a managed entity — the changes are detected automatically."
      5. "Persistence context is per-EM, not shared. A second EM has its own snapshot — stale data possible if you don't refresh."

      Edge cases to mention:

      • For batch jobs processing millions of rows, the persistence context grows unbounded — call em.clear() periodically or use StatelessSession to avoid heap pressure @DynamicUpdate makes Hibernate emit UPDATE only for changed columns instead of all columns — useful for wide tables
      • Read-only optimization: @Immutable (entity-level) or setReadOnly(true) on a query — Hibernate skips snapshot and dirty checking

      What NOT to say:

      • "First-level cache is shared across requests" — it's per-session/EM, request-scoped at best
      • "I always need to call save()" — managed entity mutations auto-flush

      Common follow-up: "What's the difference between first-level and second-level cache?"

      110. @Transactional readonly and flush modes

      Asked at: Senior Spring backend rounds · Razorpay · Cred

      Difficulty: Medium-Hard · Topic: Hibernate / JPA

      The question: "What does @Transactional(readOnly=true) actually do?"

      The 30-second answer: readOnly=true does several things: hints the JDBC driver (some can route to read replicas), tells Hibernate to skip dirty checking and snapshots (memory + CPU savings), sets the flush mode to MANUAL so accidental updates don't get flushed. It's a perf optimization for query-only methods, not a security feature — you can still mutate, just nothing is flushed.

      Step-by-step thought process:

      1. "On the JDBC connection, Spring sets setReadOnly(true). Many JDBC drivers ignore it; some (like PostgreSQL with the right config) route to a read replica."
      2. "On the Hibernate session, flush mode becomes MANUAL — no automatic flush at commit. So even if you mutate managed entities, nothing is written to DB."
      3. "Hibernate skips storing the original snapshot per entity (since dirty checking won't run) — substantial memory savings for queries returning many rows."
      4. "NOT a security boundary. A read-only transaction can still call INSERT/UPDATE/DELETE if you bypass the persistence context (native query, em.flush() manually)."
      5. "Apply readOnly=true to all your query/get methods. Don't apply at the class level if some methods mutate."

      Edge cases to mention:

      • For pure read methods on a service, the perf gain on Hibernate's snapshot skipping is noticeable when returning thousands of entities
      • readOnly + REQUIRES_NEW gets you a true new read-only transaction — useful for fetching auxiliary data in the middle of a write flow Connection routing to replica needs driver-specific config (e.g. AWS Aurora's ROLE-aware driver)

      What NOT to say:

      • "readOnly prevents writes" — it doesn't enforce; it just avoids flushing
      • "Always read-only is faster" — true for reads; harmful if the method actually writes

      Common follow-up: "How would you route read-only queries to a database replica?"

      111. REST HTTP verbs — semantics and idempotency

      Asked at: Most backend rounds · Razorpay · Swiggy · Wells Fargo

      Difficulty: Easy-Medium · Topic: REST / API design

      The question: "What are the HTTP verb semantics, and which are idempotent?"

      The 30-second answer: GET = read, safe + idempotent. PUT = replace whole resource, idempotent. PATCH = partial update, NOT necessarily idempotent. POST = create or non-idempotent action. DELETE = remove, idempotent (deleting twice still results in no resource). Safe = no server state change. Idempotent = same effect whether called once or N times.

      Step-by-step thought process:

      1. "GET is for reads — no side effects, safe, idempotent. Should be cacheable. Never put state-changing logic in a GET handler."
      2. "PUT replaces the entire resource at a URL. Idempotent: PUT /orders/123 with the same body twice has the same final state."
      3. "PATCH applies a partial update. Idempotency depends on the patch semantics — JSON Merge Patch is idempotent, but a delta patch ("increment counter by 1") is not."
      4. "POST is the non-idempotent verb. POST /orders typically creates a new order each call. Use idempotency keys in headers (Razorpay style) to make retries safe."
      5. "DELETE is idempotent — first call removes the resource, subsequent calls return 404 or 200 but don't change state further."

      Edge cases to mention:

      • Idempotency keys (an Idempotency-Key header) let you make POST safe to retry — server stores the result and replays it
      • HEAD is like GET but returns no body — useful for cache validation
      • OPTIONS is for CORS preflight and feature discovery — usually framework-handled

      What NOT to say:

      • "POST is always for create and PUT is always for update" — too narrow; PUT can create too if the URL is known
      • "Idempotent means safe" — different concepts; GET is both, DELETE is idempotent but not safe

      Common follow-up: "How would you implement idempotency for POST /payments?"

      112. REST status codes — pick the right one

      Asked at: Most backend rounds

      Difficulty: Easy-Medium · Topic: REST / API design

      The question: "Walk me through the major HTTP status code categories and the common codes."

      The 30-second answer: 2xx success: 200 OK, 201 Created (POST), 204 No Content (DELETE / update with no body). 3xx redirection: 301 permanent, 302 found, 304 Not Modified. 4xx client error: 400 bad request, 401 unauthenticated, 403 unauthorized, 404 not found, 409 conflict, 422 unprocessable entity, 429 rate limited. 5xx server error: 500 generic, 502 bad gateway, 503 service unavailable, 504 gateway timeout.

      Step-by-step thought process:

      1. "2xx — success. 200 for general success with body. 201 + Location header for resource creation. 204 for success with no body."
      2. "3xx — caller should look elsewhere. 301/302 redirects, 304 'use your cached copy' for conditional GETs."
      3. "4xx — caller's fault. 400 for malformed input. 401 for missing/bad auth. 403 for authenticated-but-not-allowed. 404 for missing. 409 for conflicts (e.g. duplicate). 422 for semantically wrong input. 429 for rate limited."
      4. "5xx — server's fault. 500 for uncaught error. 502 when an upstream returned bad response. 503 when overloaded or maintenance. 504 when upstream timed out."
      5. "Pick the most specific one. 422 vs 400 matters — 422 means 'I understand the syntax but the data is invalid'. 409 vs 400 matters — 409 means 'conflict with current state' (e.g. version mismatch)."

      Edge cases to mention:

      • Don't return 200 with {"status": "error"} in body — use the actual error code. Frameworks (axios, browser caches, retries) react to status, not body
      • 401 vs 403 is THE most-confused pair — 401 = 'who are you?', 403 = 'I know you, you can't do this'
      • 429 should include a Retry-After header so clients know when to retry

      What NOT to say:

      • "Just return 200 for everything and put status in the body" — fights the HTTP ecosystem
      • "5xx means the server crashed" — 5xx is any server-side failure, including known/handled ones

      Common follow-up: "What status code would you return when a customer tries to delete an order that's already shipped?"

      113. API versioning strategies

      Asked at: Most backend rounds · Razorpay · Swiggy

      Difficulty: Medium · Topic: REST / API design

      The question: "How would you version a REST API? What's the trade-off?"

      The 30-second answer: Three common strategies: URL versioning (/v1/orders), header versioning (Accept: application/vnd.api+json;version=1), query parameter (/orders?v=1). URL is most explicit and discoverable but pollutes routes; header is cleanest but harder to debug; query param is rare in serious APIs. Pick URL versioning for public APIs (industry standard), header for internal microservices.

      Step-by-step thought process:

      1. "URL versioning: /v1/orders, /v2/orders. Pros: visible in logs and dashboards, easy to test in browser, clear in docs. Cons: a resource isn't really 'at' two URLs — REST purists object."
      2. "Header versioning: Accept: application/vnd.merchant.v1+json or custom API-Version: 1. Pros: same URL, cleaner. Cons: invisible in URLs, harder to debug from a curl history."
      3. "For most public APIs (Stripe, Razorpay, AWS), URL versioning wins on discoverability."
      4. "Within a version, keep backward compatibility: add fields, don't remove; deprecate before removing; document breaking changes loudly."
      5. "Major version bumps for breaking changes only. Adding an optional field is NOT a breaking change."

      Edge cases to mention:

      • For internal microservices, consider no versioning + strict contract testing — every consumer is upgraded together
      • Spring's @RequestMapping(value = "/orders", headers = "X-API-Version=2") supports header-based routing
      • Deprecation: respond with Deprecation and Sunset HTTP headers (RFC 8594, 8295) when an endpoint will go away

      What NOT to say:

      • "Just never version — keep it backward compatible forever" — eventually you need to break things
      • "Bump version for every field addition" — that's not a breaking change

      Common follow-up: "How would you migrate clients from v1 to v2 without breaking anyone?"

      114. Idempotency in payments — how to implement

      Asked at: Razorpay · Cred · most fintech rounds

      Difficulty: Medium-Hard · Topic: REST / API design

      The question: "How would you make POST /payments idempotent?"

      The 30-second answer: Accept an Idempotency-Key header (UUID). On first call: process the payment, store the (key → response, status) in a table with a TTL. On subsequent calls with the same key: return the stored response without reprocessing. If the first call is in flight, return 409 or block briefly. Index on key for fast lookup.

      Step-by-step thought process:

      1. "Client generates a unique key per logical payment attempt (UUID). They send it in Idempotency-Key header on retries."
      2. "Server stores (key, request_hash, response, status, created_at, expires_at). Status is PROCESSING initially, then COMPLETED."
      3. "On retry: lookup by key. If PROCESSING and within timeout, wait or 409. If COMPLETED, return stored response — same body, same status code, even the same headers."
      4. "Verify the request body matches what was originally sent (hash check). Mismatch = client is reusing a key incorrectly — 422 with clear error."
      5. "TTL the idempotency records — typically 24 hours. Old keys aged out to prevent table bloat."

      Edge cases to mention:

      • Race condition on first request: two simultaneous calls with same key. Use a UNIQUE constraint on key column — second insert fails, the loser polls for the winner's result
      • For high throughput, store in Redis instead of the main DB — but persistence trade-off matters for payments Stripe and Razorpay both use this exact pattern — read their docs for the exact contract

      What NOT to say:

      • "Just check if the payment already exists" — race conditions; need an explicit idempotency record
      • "Idempotency is automatic for REST" — it isn't for POST; you have to build it

      Common follow-up: "What happens if two requests with the same idempotency key arrive at the same instant?"
