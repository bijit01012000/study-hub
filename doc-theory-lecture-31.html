    Lecture 31 — JPA Cascading, Lazy Loading & N+1 Problem

    17 sections · 4,505 words

    Lecture 31

    Scope evidence: "JPA Cascading, Lazy Loading & N+1 Problem | EntityGraph in Spring Boot" (playlist map, verified). The repo folder jpaRelationshipDemo (package com.coderarmy.jpaRelationshipDemo) extends the relationship demo with cascading + fetch demos: model.Department, model.Student, model.Profile, the repositories StudentRepository, DepartmentRepository, ProfileRepository, the services StudentService, DepartmentService, and SQL logging configured in application.properties.

    JPA relationships do more than connect two entity classes: they also raise three practical questions about lifecycle, timing, and hidden cost. This lecture answers all three with three tools -- cascading (what happens to related entities on save/delete), fetch strategies (when related data is loaded), and query-level fetch plans such as entity graphs (how to avoid a large number of hidden SQL queries). The payoff is being able to keep object graphs small by default while still fetching exactly what each use case needs, and being able to see and control the SQL Hibernate actually runs.

    1. The Three Practical Questions JPA Relationships Raise

    A relationship between two entities does not just express "these classes are linked." It forces us to make three decisions that directly shape correctness and performance:

    1. What should happen to related entities when one entity is saved or deleted? (Cascading)
    2. When should related data be loaded from the database? (Fetch strategy)
    3. How can we avoid executing a large number of hidden SQL queries? (Query-level fetch plan)

    The mapping itself only declares the link. The behavior underneath is governed by cascading, fetch strategies, and query fetch plans:

    Question Mechanism that answers it Where it is configured
    Save/delete propagation CascadeType On the relationship mapping
    When to load related data FetchType / lazy proxies On the relationship mapping (static)
    Avoid hidden queries per use case Entity graph / fetch join On the specific repository method or query

    Important: These are separate axes. Choosing cascade says nothing about loading, and choosing LAZY says nothing about saving. Interviewers deliberately mix them to see if you treat them as one knob.

    A Student touches many other entities, and those entities have relationships of their own:

    Student
  +-- Department
  +-- Address
  +-- Profile
  +-- Courses
  +-- Projects
  +-- Certificates
  +-- Comments

    That fan-out is exactly why the timing question matters: load everything eagerly and a tiny operation can drag a huge portion of the database into memory.

    2. Cascading: Propagating a Persistence Operation

    A cascade propagates a persistence operation from one entity to another through a mapped relationship. In plain terms: "when I do this to the parent, also do it to the related objects."

    Suppose an Order contains multiple OrderItem objects:

    @Entity
@Table(name = "orders")
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(
        mappedBy = "order",
        cascade = CascadeType.PERSIST
    )
    private List<OrderItem> items = new ArrayList<>();
}

    The OrderItem side holds the foreign key:

    @Entity
public class OrderItem {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne
    @JoinColumn(name = "order_id")
    private Order order;
}

    Now consider a single call:

    entityManager.persist(order);

    Because the relationship uses CascadeType.PERSIST, Hibernate also persists the items contained in order.getItems(). Conceptually, the single call behaves like:

    persist(order);
persist(item1);
persist(item2);
persist(item3);

    The application does not need to call persist() separately for every OrderItem.

    Cascade is not enabled by default. JPA does not automatically cascade every operation across relationships. With a plain mapping:

    @OneToMany(mappedBy = "order")
private List<OrderItem> items;

    the call entityManager.persist(order) does not automatically persist new OrderItem objects. This is intentional: related entities do not always share the same lifecycle.

    Important: Cascading is a lifecycle decision, not a convenience switch. Add it only after asking whether the related objects really should follow the parent's operation.

    3. Cascade Does Not Mean Relationship Ownership

    Cascading and relationship ownership solve two different problems, and conflating them is one of the most common modeling mistakes:

    • Relationship ownership decides which side controls the foreign-key value.
    • Cascading decides whether a persistence operation should propagate to a related entity.

    In the Order / OrderItem example:

    • OrderItem is the owning side because it contains the order_id foreign key.
    • The Order.items collection is the inverse side because it uses mappedBy = "order".
    OrderItem  (owning side)   --> owns order_id column
Order.items (inverse side) --> mappedBy = "order" (mirror only)

    Adding an item only to the inverse collection is not enough to set the foreign key correctly. Both sides of the object relationship should be maintained:

    public void addItem(OrderItem item) {
    items.add(item);
    item.setOrder(this);
}

    Usage:

    Order order = new Order();
OrderItem item1 = new OrderItem();
OrderItem item2 = new OrderItem();
order.addItem(item1);
order.addItem(item2);
entityManager.persist(order);

    Golden rule: The helper method keeps the Java object graph consistent; CascadeType.PERSIST is what allows the items to be persisted through the order. Ownership writes the foreign key; cascade propagates the operation. They are different jobs.

    4. CascadeType.PERSIST

    CascadeType.PERSIST propagates the persist operation:

    @OneToMany(
    mappedBy = "order",
    cascade = CascadeType.PERSIST
)
private List<OrderItem> items;

    When a new order is persisted with entityManager.persist(order), new items reachable through the relationship are persisted as well.

    This cascade is useful when:

    1. the parent and children are created together;
    2. the child belongs to the parent's lifecycle;
    3. saving the parent should also save its newly created children.

    It should not be added merely for convenience. The correct question is:

    If this parent is persisted, should these related objects always be persisted with it?

    If the answer is not an unconditional yes, do not cascade persists -- persist the children explicitly instead.

    5. CascadeType.REMOVE and the Full CascadeType Set

    CascadeType.REMOVE propagates deletion from one entity to related entities:

    @OneToMany(
    mappedBy = "order",
    cascade = CascadeType.REMOVE
)
private List<OrderItem> items;

    Now entityManager.remove(order) conceptually becomes:

    remove(Order)
  +-- remove(Item A)
  +-- remove(Item B)
  +-- remove(Item C)

    Possible SQL:

    DELETE FROM order_item WHERE id = 1;
DELETE FROM order_item WHERE id = 2;
DELETE FROM order_item WHERE id = 3;
DELETE FROM orders WHERE id = 100;

    The child rows are normally deleted before the parent row so that the foreign-key constraint is not violated.

    When does REMOVE make sense? When the child belongs exclusively to the parent. An OrderItem normally has no independent meaning without its Order, so deleting the items when the order is deleted is usually reasonable. It becomes dangerous when the related entity is shared. For example:

    @ManyToMany
private Set<Course> courses;

    If many students share the same course, deleting one student must not delete the course itself. Therefore, CascadeType.REMOVE is usually inappropriate on shared many-to-many relationships.

    The full set of cascade types. JPA provides six values, and their meaning can be summarized as follows:

    Cascade type Propagated operation
    PERSIST Persist new related entities
    MERGE Merge the state of related detached entities
    REMOVE Remove related entities
    REFRESH Reload related entities from the database
    DETACH Detach related entities from the persistence context
    ALL Apply all the cascade types above

    Multiple cascade types can be selected at once:

    @OneToMany(
    mappedBy = "order",
    cascade = {
        CascadeType.PERSIST,
        CascadeType.REMOVE
    }
)
private List<OrderItem> items;

    CascadeType.ALL should be used only when the related entity genuinely shares the complete lifecycle of the parent. (Many-to-many and shared references are the usual places where ALL turns into a data-loss bug.)

    Mnemonic for the six values -- "Please Merge Records, Recheck Detached Attachments" maps to Persist, Merge, Remove, Refresh, Detach, All.

    6. Relationship Loading and the Fetch Plan

    Fetching an entity by its primary key is straightforward:

    Student student = entityManager.find(Student.class, 1L);

    However, a Student may be related to many other entities (Department, Address, Profile, Courses, Projects, Certificates, Comments), and those entities may contain further relationships of their own. If Hibernate loaded every reachable entity whenever one Student was requested, a small operation could load a huge portion of the database.

    Hibernate therefore needs a fetch plan:

    Which relationships are required now, and which relationships can wait until they are actually used?

    The fetch plan is the bridge between the object graph you model and the amount of SQL the database actually runs.

    Concern Question it settles
    Default timing Should a relationship load now or later? (FetchType)
    Per-use-case graph What does this specific operation need? (entity graph / fetch join)
    Hidden cost How many extra statements appear when I navigate a relationship?

    7. Static Fetch Strategy: LAZY vs EAGER and the Defaults

    A fetch strategy can be configured directly in the entity mapping:

    @ManyToOne(fetch = FetchType.LAZY)
private Department department;

    This is called a static fetch strategy because it becomes part of the entity's mapping metadata. It acts as the default whenever the entity is loaded, for example entityManager.find(Student.class, 1L). The default can still be overridden for a particular use case through a fetch join, an entity graph, or another query-specific fetch plan.

    JPA defines exactly two fetch types:

    Fetch type Conceptually Spec-level nature
    LAZY Load the relationship when it is first needed A hint -- the provider is asked to delay loading, but the spec does not absolutely require it to
    EAGER Load the relationship as part of loading the entity A requirement -- the provider must make the relationship available eagerly

    Hibernate supports lazy loading extensively:

    • to-many relationships are represented using lazy persistent collections;
    • to-one relationships can be loaded lazily through proxies or bytecode enhancement.

    Important: EAGER is a promise, LAZY is a request. That asymmetry matters when you reason about what Hibernate is allowed to do.

    Default fetch types. JPA defines the following defaults, and they are worth memorizing because they explain most "surprise" SQL:

    Relationship Default fetch type
    @OneToMany LAZY
    @ManyToMany LAZY
    @ManyToOne EAGER
    @OneToOne EAGER

    Therefore, to-many relationships are lazy by default, while to-one relationships are eager by default. (Memory aid: "to-many waits, to-one races.")

    These defaults should not automatically be treated as the best choice for every application. In practice, many teams explicitly configure to-one relationships as lazy:

    @ManyToOne(fetch = FetchType.LAZY)
private Department department;

    This keeps the default object graph small and allows each query to request the relationships required by its use case.

    8. How Lazy Loading Works

    Consider:

    @Entity
public class Student {
    @Id
    private Long id;
    private String name;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;
}

    When the student is loaded with entityManager.find(Student.class, 1L), Hibernate can initially execute:

    SELECT id, name, department_id
FROM student
WHERE id = 1;

    The Student is loaded, but its Department may be represented by an uninitialized proxy. Conceptually:

    Student
  +-- id = 1
  +-- name = Rahul
  +-- department = not initialized yet

    Accessing only the department reference does not necessarily initialize it:

    Department department = student.getDepartment();

    Accessing data that requires the real department state can trigger initialization:

    String departmentName = student.getDepartment().getName();

    Hibernate may then execute:

    SELECT id, name
FROM department
WHERE id = 10;

    Lazy loading therefore defers the cost of fetching an association until that association is actually used.

    Interviewer's perspective: The subtle point is that touching the reference is not the same as touching the state. getDepartment() may hand back the proxy without a query; getDepartment().getName() forces the proxy to initialize and issues SQL.

    9. Why Lazy Loading Is Useful

    Lazy loading is useful because different use cases need different parts of the same entity graph. For example:

    • a student list may need only id and name;
    • a student details page may also need department and profile;
    • an administration report may need department, courses, and projects.

    Using one large eager graph for all three cases wastes database work and memory. Lazy mapping provides a small default graph; each use case can then explicitly fetch the associations it needs.

    However, lazy loading creates another risk: database queries can be triggered implicitly while Java code navigates relationships. This is how the N+1 problem commonly appears -- invisible until you either count the SQL or notice the latency.

    Golden rule: Keep relationships lazy by default and fetch the required graph explicitly for each use case. Lazy is the safe default; the fetch plan is the tool that makes a specific operation cheap.

    10. The N+1 Query Problem and Whether Lazy Loading Is Bad

    The N+1 problem occurs when:

    1. one query loads a collection of parent entities; and
    2. additional queries are executed while accessing a relationship for each parent.

    Suppose Student.department is lazy:

    @ManyToOne(fetch = FetchType.LAZY)
private Department department;

    Load all students:

    List<Student> students = studentRepository.findAll();

    Hibernate first executes one query:

    SELECT id, name, department_id
FROM student;

    Now iterate through the results:

    for (Student student : students) {
    System.out.println(student.getDepartment().getName());
}

    Each department access may initialize a lazy proxy:

    SELECT * FROM department WHERE id = 1;
SELECT * FROM department WHERE id = 2;
SELECT * FROM department WHERE id = 3;
-- additional queries

    The total pattern is:

    1 query for the students
+
N additional relationship queries

    The Java loop looks harmless, but every relationship access may involve a database round trip.

    First-level cache and the exact query count. The term "N+1" describes the query pattern; it does not guarantee that exactly N additional SQL statements will always be executed. Suppose 100 students belong to only three departments. The initial query loads all students (1 student query). As departments are accessed, Hibernate may need only 3 department queries, because once a department has been loaded into the current persistence context, Hibernate can reuse that managed entity for other students referencing the same department. The result may therefore be 1 + 3 rather than 1 + 100.

    The first-level cache can reduce duplicate primary-key lookups within one persistence context, but it does not solve the underlying fetch-plan problem. The important issue remains: relationship access is causing additional SQL statements that were not visible in the original repository call.

    N+1 during collection iteration. The classic to-many example begins by loading departments:

    List<Department> departments = departmentRepository.findAll();

    Suppose Department.students is lazy:

    @OneToMany(
    mappedBy = "department",
    fetch = FetchType.LAZY
)
private List<Student> students;

    Now iterate over every collection:

    for (Department department : departments) {
    for (Student student : department.getStudents()) {
        System.out.println(student.getName());
    }
}

    Hibernate may execute:

    SELECT * FROM department;
SELECT * FROM student WHERE department_id = 1;
SELECT * FROM student WHERE department_id = 2;
SELECT * FROM student WHERE department_id = 3;

    There is one query for all departments and one additional query for the student collection of each department. This is a true N+1 pattern: 1 parent query + N collection queries.

    Does N+1 mean lazy loading is bad? No. The N+1 problem can make it appear that lazy loading is bad and eager loading is the solution, but that conclusion is too broad. Lazy loading is useful when an association is not required; the problem arises when the application knows it will access an association for every result but does not include that association in the query's fetch plan. The correct principle is: keep relationships lazy by default and fetch the required graph explicitly for each use case.

    Changing the mapping to EAGER is not a reliable N+1 solution. With:

    @ManyToOne(fetch = FetchType.EAGER)
private Department department;

    JPA requires the departments to be available eagerly, but it does not require Hibernate to obtain everything using one join query. Depending on the query and provider behavior, Hibernate may still execute secondary selects. EAGER also applies globally: it loads the association even in use cases that do not need it. Therefore:

    • LAZY controls the default timing;
    • a query-level fetch plan controls what a specific operation needs;
    • neither setting should be chosen without considering the use case and the generated SQL.

    Interviewer's perspective: The expected answer is not "switch to EAGER." It is "keep LAZY, fetch the graph for this use case." Candidates who reach for EAGER globally are trading one hidden query pattern for another and paying for data they do not use.

    11. Detecting and Preventing N+1: SQL Logging and Entity Graphs

    One of the simplest ways to detect N+1 during development is to inspect the SQL generated by Hibernate. Enable SQL logging in application.properties:

    spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

    For parameter values in modern Hibernate versions, logging can also be configured through the application's logging settings:

    logging.level.org.hibernate.SQL=DEBUG
logging.level.org.hibernate.orm.jdbc.bind=TRACE

    Now run the use case and inspect:

    1. how many SQL queries are executed;
    2. whether queries repeat inside a loop;
    3. which Java relationship access triggers each query;
    4. whether the same association is fetched even when it is not required.

    Important: SQL logging is especially useful while learning because it makes the hidden database work visible. A "single" repository call is rarely a single statement once lazy relationships are involved.

    Preventing N+1 with an entity graph. An entity graph defines which associations should be fetched for a particular operation. Suppose the default mapping remains lazy:

    @ManyToOne(fetch = FetchType.LAZY)
private Department department;

    In Spring Data JPA:

    public interface StudentRepository
        extends JpaRepository<Student, Long> {

    @EntityGraph(attributePaths = "department")
    List<Student> findAll();
}

    This method requests department as part of its fetch plan. The important design is:

    Default entity mapping:   Student.department = LAZY
Specific repository method: fetch Student + Department

    The mapping remains small for other operations, while this method fetches the association it knows it will need. Hibernate commonly satisfies this graph using a join, although the exact SQL strategy is controlled by the persistence provider. The entity graph defines what must be fetched, not one universally guaranteed SQL statement.

    Fetching multiple attributes:

    @EntityGraph(
    attributePaths = {
        "department",
        "profile"
    }
)
List<Student> findAll();

    Conceptually, this repository method requests:

    Student
  +-- Department
  +-- Profile

    Both attributes become part of that method's fetch plan.

    Nested attribute paths. Spring Data JPA also supports nested paths:

    @EntityGraph(
    attributePaths = {
        "department.manager"
    }
)
List<Student> findAll();

    This asks for:

    Student
  +-- Department
      +-- Manager

    Nested graphs should be selected carefully. Fetching several large collections in one operation can produce a very large joined result and duplicate rows at the SQL level.

    A JOIN FETCH query is the JPQL equivalent lever when you want the fetch plan expressed in the query itself rather than via an annotation:

    SELECT s FROM Student s JOIN FETCH s.department

    Golden rule: One repository method, one fetch plan. Keep the mapping lazy, then let each method declare the graph it actually needs -- that is how you remove hidden queries without bloating every other use case.

    12. Myth vs Reality

    Myth Reality
    "Cascade and ownership are the same thing" Ownership decides which side writes the foreign key; cascading decides whether a persistence operation propagates. Separate concerns.
    "Cascading is on by default" JPA does not cascade automatically; without a cascade setting, persist(order) does not persist new children.
    "CascadeType.ALL is always the safest choice" ALL is correct only when the child shares the parent's complete lifecycle; on shared or many-to-many references it can delete data you did not intend to touch.
    "FetchType.LAZY always defers the query" LAZY is a hint, not an absolute guarantee; the spec only requires EAGER to be eager.
    "To-one is lazy by default" In JPA, @ManyToOne and @OneToOne are EAGER by default; only @OneToMany and @ManyToMany default to LAZY.
    "N+1 always means exactly N extra queries" The first-level cache can collapse duplicates; 100 students in 3 departments may cost 1 + 3, not 1 + 100. The pattern is named, not counted.
    "Switch to EAGER to fix N+1" EAGER is global and does not force a single join; it loads data everywhere and may still emit secondary selects. Fetch the graph per use case instead.
    "An entity graph guarantees one SQL statement" The graph defines what must be fetched; the provider chooses the strategy (commonly a join, but not guaranteed).

    13. Common Trap Questions

    Trap 1 - "Does entityManager.persist(order) save the order's items?" Verdict: Only if the relationship is configured with CascadeType.PERSIST (or ALL). With a plain @OneToMany(mappedBy = "order"), new OrderItem objects are not persisted automatically.

    Trap 2 - "I added the item to order.getItems(); will the foreign key be set?" Verdict: Not reliably. OrderItem is the owning side because it holds order_id; you must set both sides, which is why the addItem helper calls item.setOrder(this).

    Trap 3 - "CascadeType.REMOVE on a many-to-many is convenient." Verdict: Usually wrong. If students share courses, deleting one student must not delete the course; REMOVE on shared many-to-many relationships can delete shared data.

    Trap 4 - "@ManyToOne is lazy by default." Verdict: False. @ManyToOne and @OneToOne default to EAGER; @OneToMany and @ManyToMany default to LAZY. Teams often override to-one to LAZY deliberately.

    Trap 5 - "Accessing student.getDepartment() triggers the SQL." Verdict: Not necessarily. Getting the reference may return an uninitialized proxy; it is accessing the department's state (for example getName()) that forces initialization and issues the query.

    Trap 6 - "N+1 proves lazy loading is broken." Verdict: No. Lazy loading is fine when an association is unused; N+1 appears when you access an association for every row without adding it to the query's fetch plan. Fix the plan, not the fetch type.

    Trap 7 - "Set the mapping to EAGER and N+1 disappears." Verdict: Not reliably. EAGER is global and does not guarantee a single join; Hibernate may still run secondary selects, and now every use case pays for data it may not need.

    14. Points to Remember

    1. JPA relationships raise three questions: what happens on save/delete (cascade), when related data loads (fetch), and how to avoid hidden queries (query-level fetch plan).
    2. A cascade propagates a persistence operation across a mapped relationship; it is not enabled by default.
    3. Ownership decides which side controls the foreign key; cascading decides whether operations propagate. They are different concerns.
    4. CascadeType.PERSIST saves reachable new children with the parent; add it only when the child belongs to the parent's lifecycle.
    5. CascadeType.REMOVE deletes children before the parent; it is dangerous on shared many-to-many references and is safe only for exclusive children.
    6. The six cascade values are PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL; ALL only when the child shares the parent's entire lifecycle.
    7. FetchType.LAZY loads on first use (a hint); FetchType.EAGER loads with the entity (a requirement).
    8. Defaults: @ManyToOne and @OneToOne are EAGER; @OneToMany and @ManyToMany are LAZY; many teams set to-one to LAZY to keep the default graph small.
    9. Lazy loading returns an uninitialized proxy; accessing real state initializes it and issues SQL, which is how N+1 (1 parent query + N relationship queries) appears; the first-level cache can reduce duplicates but not the pattern.
    10. Detect N+1 with SQL logging (show-sql, format_sql, Hibernate log levels) and prevent it with a query-level fetch plan such as @EntityGraph(attributePaths=...) (or JOIN FETCH), keeping the mapping lazy.

    15. Likely Interview Questions

    Question Crisp Answer
    What is cascading in JPA? It propagates a persistence operation from one entity to related entities through a mapped relationship.
    Is cascade enabled by default? No; without a cascade setting, operations do not propagate across the relationship.
    Cascade vs relationship ownership? Ownership decides which side writes the foreign key; cascade decides whether operations propagate.
    When is CascadeType.REMOVE appropriate? When the child belongs exclusively to the parent; it is usually wrong on shared many-to-many references.
    List the cascade types. PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL (all six, with ALL meaning the rest).
    What are the default fetch types? To-one (@ManyToOne, @OneToOne) is EAGER; to-many (@OneToMany, @ManyToMany) is LAZY.
    LAZY vs EAGER? LAZY loads on first use and is only a hint; EAGER loads with the entity and is a requirement.
    How does lazy loading work? A proxy or lazy collection is created; accessing its real state initializes it and runs the missing query.
    What is the N+1 problem? One query loads parents, then one extra query per parent runs when a relationship is accessed: 1 + N.
    Does the first-level cache prevent N+1? No; it avoids duplicate primary-key lookups in one persistence context but not the underlying fetch-plan issue.
    How do you fix N+1? Keep mapping lazy and add a query-level fetch plan such as @EntityGraph(attributePaths=...) or JOIN FETCH.
    How do you detect N+1? Enable SQL logging (spring.jpa.show-sql=true, spring.jpa.properties.hibernate.format_sql=true) and count statements.

    16. Final Summary

    JPA relationship
        |
        +--> 1. Lifecycle: what happens on save/delete?   --> Cascading (CascadeType)
        |           PERSIST  saves new children
        |           REMOVE   deletes children (exclusive children only)
        |           MERGE / REFRESH / DETACH / ALL
        |
        +--> 2. Timing: when is related data loaded?      --> Fetch strategy (FetchType)
        |           LAZY  = on first use (hint)  -> proxy / lazy collection
        |           EAGER = with the entity (requirement)
        |           defaults: to-one EAGER, to-many LAZY
        |
        +--> 3. Cost: how to avoid hidden queries?         --> Query-level fetch plan
                    N+1 = 1 parent query + N relationship queries
                    detect  -> SQL logging (show-sql, format_sql)
                    prevent -> @EntityGraph(attributePaths) / JOIN FETCH
    • Causality split: ownership writes the foreign key; cascading propagates operations -- never confuse the two.
    • Cascade set: PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL; use ALL/REMOVE only for children that share the parent's whole lifecycle.
    • Fetch defaults: to-one eager, to-many lazy; many teams deliberately make to-one lazy to keep the default graph small.
    • Lazy mechanics: proxy stays uninitialized until real state is accessed, which is when the extra query fires.
    • N+1: a pattern, not a fixed count; the first-level cache collapses duplicates but does not fix the fetch plan.
    • Fix: keep mapping lazy, add a per-use-case graph (@EntityGraph / JOIN FETCH), and verify with SQL logging.

    One-line takeaway: Cascading decides what happens to related entities, fetch type decides when they load, and an entity graph decides what a specific query fetches -- keep mappings lazy by default, propagate operations only where the lifecycle truly is shared, and let each use case state the graph it needs.
