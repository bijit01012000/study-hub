    Lecture 20 — Spring Boot Filters (Modify Requests, Response, Headers & Bodies)

    23 sections · 4,183 words

    Lecture 20

    Scope evidence: "Spring Boot Filters | Modify Requests, Response, Headers & Bodies" (playlist map, verified). Repo lecture folder is the filterDemo project with a filters package (RequestFilter, ResponseHeaderFilter, ResponseBodyFilter, SpringDemoFilter, DummyFilter, AuthenticationFilter), a configuration.FilterConfig, controller.StudentController, dto.Student, dto.StudentResponseDto, service.StudentService, and FilterDemoApplication.

    A servlet Filter can do more than inspect a request and response: it can change what the client receives and what downstream sees. The rules are not symmetric: response headers and status are easy to change, response bodies need a wrapper, request headers and parameters are read-only, and the request body is a stream. This lecture covers those cases plus the registration and scoping tools (@Component, FilterRegistrationBean, OncePerRequestFilter, shouldNotFilter()).

    1. Modifying the HTTP Response: Headers and Status

    A Filter can add or replace response headers before passing the request further through the chain.

    @Component
public class ResponseHeaderFilter implements Filter {

    @Override
    public void doFilter(
        ServletRequest request,
        ServletResponse response,
        FilterChain chain
    ) throws IOException, ServletException {
        HttpServletResponse httpResponse = (HttpServletResponse) response;
        httpResponse.setHeader("X-Application-Name", "Student Management API");
        chain.doFilter(request, response);
    }
}

    The client receives a header similar to X-Application-Name: Student Management API.

    setHeader() versus addHeader():

    • setHeader("X-Application-Name", "Student API") replaces the existing value.
    • addHeader("X-Feature", "Students") then addHeader("X-Feature", "Courses") adds values without replacing the previous one.

    A Filter can assign an HTTP status directly: httpResponse.setStatus(HttpServletResponse.SC_UNAUTHORIZED);. The constant SC_UNAUTHORIZED is HTTP status 401 Unauthorized.

    A Filter can also stop processing and return a complete response by itself. It sets the status, content type, and encoding, writes JSON with httpResponse.getWriter().write(...), and returns. Because the method returns without calling chain.doFilter(), the request never reaches the next Filter or the controller.

    Important: chain.doFilter(request, response); means "continue processing the request." A bare return; without calling the chain means "stop processing the request here."

    Interviewer's perspective: For real authentication and authorization, Spring Security is generally the correct solution. Authentication failures are commonly handled through components such as AuthenticationEntryPoint, not a homemade Filter.

    2. Why Add Headers Before the Response Is Committed

    Downstream code may write and flush the response. Once that happens, the response can become committed. A committed response means its status and headers may already have been sent to the client. After that point, changing them may have no effect or may cause an error.

    State can be checked with httpResponse.isCommitted(). Add headers early when they should be present on every response. Logic that depends on the final result may need to run after chain.doFilter() and must account for the response possibly being committed.

    3. Modifying the Response Body (and Why getBody() Does Not Exist)

    Suppose a controller returns {"name": "Aditya", "age": 25}. The desired response nests that data under a data field and adds an application field beside it.

    A normal HttpServletResponse has no response.getBody() method.

    Why? The controller or Spring MVC writes response data to response.getWriter() or response.getOutputStream(), and the data moves progressively toward the client. The ordinary response is a destination for writes, not a Java object from which the complete body can later be read. To inspect or replace the body after downstream processing, the response must first be wrapped.

    4. ContentCachingResponseWrapper and copyBodyToResponse()

    Spring provides ContentCachingResponseWrapper, which stores a copy of the response body so it can be accessed after the controller has executed. The filter creates it, passes it through the chain, reads the cached bytes afterwards, optionally replaces the body, then copyBodyToResponse() copies the final body to the real response.

    Example:

    @Component
public class ResponseBodyFilter implements Filter {

    @Override
    public void doFilter(
        ServletRequest request,
        ServletResponse response,
        FilterChain chain
    ) throws IOException, ServletException {
        HttpServletResponse httpResponse = (HttpServletResponse) response;
        HttpServletRequest httpRequest = (HttpServletRequest) request;

        ContentCachingResponseWrapper wrappedResponse =
            new ContentCachingResponseWrapper(httpResponse);
        chain.doFilter(httpRequest, wrappedResponse);

        byte[] originalBodyBytes = wrappedResponse.getContentAsByteArray();
        String originalBody = new String(originalBodyBytes, StandardCharsets.UTF_8);
        String modifiedBody = """
            {"originalResponse": %s, "processedBy": "ResponseBodyFilter"}
            """.formatted(originalBody);

        wrappedResponse.resetBuffer();
        wrappedResponse.setContentType("application/json");
        wrappedResponse.setCharacterEncoding(StandardCharsets.UTF_8.name());
        wrappedResponse.getOutputStream().write(modifiedBody.getBytes(StandardCharsets.UTF_8));

        wrappedResponse.copyBodyToResponse();
    }
}

    The important steps:

    1. Wrap the real response: new ContentCachingResponseWrapper(httpResponse).
    2. Pass the wrapper through the chain: the controller writes into wrappedResponse, not the original response.
    3. Read the cached body: wrappedResponse.getContentAsByteArray().
    4. Clear the body: resetBuffer() clears the buffer while keeping status and headers.
    5. Write the replacement: wrappedResponse.getOutputStream().write(modifiedBodyBytes).
    6. Copy to the real response: wrappedResponse.copyBodyToResponse().

    Golden rule: Always call copyBodyToResponse() with ContentCachingResponseWrapper; otherwise the client may receive an empty response because the data remains inside the wrapper.

    Mnemonic for the response-body dance - W-R-R-W-C: Wrap, Run the chain, Read the bytes, reset and Write, then Copy to the real response.

    5. Limitations of Manually Modifying a Response Body

    The wrapper example is useful for understanding wrappers, but manually rebuilding JSON inside a Filter is uncommon in normal application code. Potential problems include:

    • The original body may be empty.
    • The body may not contain JSON.
    • Binary responses such as files or images must not be treated as text.
    • Buffering large responses consumes memory.
    • Headers such as Content-Length, ETag, or compression headers may become invalid after modification.
    • Exceptions and error dispatches require careful handling.
    • Streaming responses are not suitable for complete-body caching.

    The expression "...".formatted(originalBody) assumes originalBody is already valid JSON. For production JSON transformation, use Jackson rather than building JSON by hand. For globally changing controller response bodies in Spring MVC, ResponseBodyAdvice is often cleaner than a servlet Filter.

    6. Modifying Request Data and the Request Wrapper Concept

    Request modification is generally more complex than response-header modification. Suppose the client sends GET /api/students with Authorization: Bearer abc123. The Filter can read it with httpRequest.getHeader("Authorization"), but the original request has no setter: httpRequest.setHeader("Authorization", "Bearer new-token"); does not exist.

    HttpServletRequest is primarily a read-oriented interface. To change what downstream code sees, the normal technique is to pass a wrapper instead of the original request. A custom request wrapper normally extends HttpServletRequestWrapper, calls super(request), and overrides methods such as:

    • getHeader(String name)
    • getHeaders(String name)
    • getHeaderNames()
    • getParameter(String name)
    • getParameterMap()
    • getParameterValues(String name)
    • getInputStream()
    • getReader()

    Downstream components receive the wrapper and observe the values returned by its overridden methods; the wrapper delegates everything else to the original request.

    Interviewer's perspective: Request mutation through wrappers is valid but should be used carefully. Business-level transformations are often better placed in Spring MVC, validation, Jackson configuration, or the service layer.

    7. Modifying Query Parameters

    Query parameters are also read-only on the original request. For GET /products?page=1, this method does not exist: request.setParameter("page", "2");.

    To change how downstream code reads parameters, a wrapper must consistently override:

    • getParameter(String name)
    • getParameterMap()
    • getParameterValues(String name)
    • getParameterNames()

    Overriding only getParameter() may be insufficient because Spring MVC or another library may read the complete parameter map instead.

    Use this carefully because the same parameters may be consumed by:

    • @RequestParam
    • Data binding
    • Validation
    • Other Filters
    • Spring MVC infrastructure

    8. Understanding the Request Body as a Stream

    Request-body handling is more sensitive than reading headers or query parameters. Request information is exposed through methods such as getHeader, getHeaderNames, getParameter, getParameterMap, getMethod, and getRequestURI.

    However, httpRequest.getBody(); does not exist. The request body is accessed as a stream with request.getInputStream(), or as a reader with request.getReader().

    Why a stream? The body can contain many kinds of data: JSON, XML, plain text, PDF documents, images, videos, multipart form data, and other binary content.

    The servlet container cannot assume:

    • that the body contains text;
    • that it contains JSON;
    • which Java class it should become;
    • how large it is;
    • which parser should process it;
    • which character encoding should be used.

    At the HTTP level, the body is a sequence of bytes arriving from the client. Spring MVC selects an HttpMessageConverter, Jackson handles JSON when applicable, and a Java object results; with @RequestBody, Jackson converts those bytes into the required object.

    9. Why the Request Body Cannot Be Read Repeatedly

    An input stream has a current position, and each read moves it forward. Suppose the client sends {"name": "Aditya"}. The position advances through the bytes: { -> " -> n -> a -> m -> e -> " -> : -> .... After the bytes are consumed, the stream is at its end, and the original network bytes are not placed back at position zero.

    Consider a controller that reads the body with @RequestBody Student student. If a Filter reads the same body first with httpRequest.getReader(), the Filter may print it successfully, but when Spring MVC later tries to create the object the stream may already be empty, and the controller can fail with:

    Required request body is missing

    The same issue occurs when the Filter uses getInputStream() and inputStream.readAllBytes() instead.

    getReader() and getInputStream() are two views of the same body; reading through either consumes it, and the Servlet API does not allow mixing both methods on one request.

    10. Why Java and Tomcat Do Not Rewind the Body

    Automatic repeated reading would require the server to buffer the complete body. A 2 GB video would have to be received, stored in memory or on disk, and kept for possible repeated reads, consuming large amounts of memory or disk. Doing this for every request would:

    • increase latency;
    • reduce throughput;
    • create denial-of-service risks;
    • be unnecessary for most requests.

    Streaming therefore lets the server process data without storing every body in full.

    Important: The stream design is a deliberate trade-off, not a bug. Unreadable-again bodies are the price of streaming large payloads efficiently.

    11. Re-reading or Replacing a Request Body

    A Filter that must read and still preserve the body needs a request wrapper. Typical use cases include:

    • logging selected request data;
    • masking sensitive fields before logging;
    • decrypting an encrypted payload;
    • sanitising input;
    • replacing or transforming request content.

    The strategy: read the original stream once, store the bytes in a byte array, pass a custom HttpServletRequestWrapper, and let the wrapper return a fresh stream over the cached bytes so Spring MVC can read the body normally. The wrapper overrides both getInputStream() and getReader(); each call creates a new ByteArrayInputStream(cachedBody) that begins at position zero, so the cached body can be read again.

    public class CachedBodyRequestWrapper extends HttpServletRequestWrapper {

    private final byte[] cachedBody;

    public CachedBodyRequestWrapper(HttpServletRequest request) throws IOException {
        super(request);
        this.cachedBody = request.getInputStream().readAllBytes();
    }

    @Override
    public ServletInputStream getInputStream() {
        ByteArrayInputStream buffer = new ByteArrayInputStream(cachedBody);
        return new ServletInputStream() {
            @Override public int read() { return buffer.read(); }
            @Override public boolean isFinished() { return buffer.available() == 0; }
            @Override public boolean isReady() { return true; }
            @Override public void setReadListener(ReadListener listener) { }
        };
    }

    @Override
    public BufferedReader getReader() {
        return new BufferedReader(
            new InputStreamReader(getInputStream(), StandardCharsets.UTF_8));
    }
}

    Mnemonic for the request fix - R-C-W-F: Read once, Cache the bytes, Wrap the request, give a Fresh stream.

    Important: Caching a request body stores it in memory unless a disk-backed strategy is used. Before buffering, consider maximum request size, file uploads, multipart requests, sensitive information, passwords and tokens, and performance.

    Golden rule: Never log complete request bodies blindly. Logs can expose credentials, personal data, access tokens, and financial information.

    12. Choosing the Correct Layer

    Before modifying data in a Filter, consider whether another Spring mechanism is more suitable.

    Requirement Usually better suited mechanism
    Authentication and authorization Spring Security
    Standard controller response envelope ResponseBodyAdvice
    Exception response formatting @RestControllerAdvice
    JSON field conversion Jackson configuration or custom deserializer
    Controller argument creation HandlerMethodArgumentResolver
    Input validation Bean Validation
    Business-data transformation Service layer
    Low-level HTTP concern Filter

    Filters fit concerns that belong at the servlet or HTTP boundary.

    13. Registering Filters in Spring Boot (@Component vs FilterRegistrationBean)

    There are multiple ways to register and scope a Filter.

    Approach 1: register with @Component. Spring Boot detects the Filter bean and registers it with the servlet container, generally mapped broadly to /*. Use it when the Filter should apply broadly and advanced options are unnecessary.

    Approach 2: register with FilterRegistrationBean, which gives explicit control over URL patterns, order, name, dispatcher types, whether registration is enabled, and async support. Suppose a Filter should apply only to /api/* and not to /actuator/*, /swagger-ui/*, or /static/*; it can restrict the Filter at registration time.

    Step 1: create a normal Filter class (a plain RequestLoggingFilter implements Filter that logs the request URI and calls the chain). Do not annotate it with @Component when the same instance will be registered manually.

    Step 2: register it in a configuration class. In FilterConfig (annotated @Configuration), a @Bean method creates a FilterRegistrationBean<RequestLoggingFilter>, sets the filter, URL patterns, setOrder(1), and a name, then returns it. The Filter then applies to /api/students and /api/orders/10, but not to /hello or /actuator/health, unless another pattern matches. Registering multiple patterns: addUrlPatterns("/api/*", "/admin/*").

    Step 3: avoid duplicate registration. Do not use both @Component and setFilter(new RequestLoggingFilter()) for the same Filter, or it can run more than once; choose one strategy.

    Aspect @Component FilterRegistrationBean
    Registration style Automatic bean detection Explicit bean in a config class
    Mapping Usually broad (/*) Exact URL patterns you choose
    Order control Indirect setOrder(...)
    Name control Default bean name setName(...)
    Dispatcher types Not exposed Configurable
    Enable/disable Not exposed Configurable
    Best for Broad, simple Filters Precise URL and order control

    14. Controlling Filter Order

    When multiple Filters are registered, their order determines the path of the request and response. registrationBean.setOrder(1) sets the order, and a lower value runs earlier on the request. With LoggingFilter at order 1 and AuthenticationFilter at order 2, the request flows Client, LoggingFilter, AuthenticationFilter, DispatcherServlet, Controller; the response returns in reverse. This nesting happens because each Filter runs code before and after chain.doFilter().

    Interviewer's perspective: Filter order is a classic interview follow-up. "Which filter runs first?" is answered by the order value on the request path, and by the reverse on the response path.

    15. Filtering Specific URLs and OncePerRequestFilter

    A Filter can inspect the current URI and decide whether to run its custom logic. An ApiFilter implements Filter reads httpRequest.getRequestURI(); if the URI does not start with /api/ it just calls the chain and returns, otherwise it runs the API-specific logic first.

    This works, but the Filter is still invoked for every URL in its servlet registration and decides internally. Use it when the condition is small, depends on more than a simple URL pattern, or when the Filter is already registered broadly. For clean URL-level registration, FilterRegistrationBean is clearer.

    Implementing the servlet Filter interface directly is valid. Spring also provides OncePerRequestFilter, an abstract Spring class for HTTP request filtering. It overrides doFilterInternal(HttpServletRequest, HttpServletResponse, FilterChain) instead of doFilter, so no manual casting is needed.

    @Component
public class RequestLoggingFilter extends OncePerRequestFilter {

    private static final Logger logger =
        LoggerFactory.getLogger(RequestLoggingFilter.class);

    @Override
    protected void doFilterInternal(
        HttpServletRequest request,
        HttpServletResponse response,
        FilterChain filterChain
    ) throws ServletException, IOException {
        logger.info("{} {}", request.getMethod(), request.getRequestURI());
        filterChain.doFilter(request, response);
    }
}

    Advantages of OncePerRequestFilter:

    • direct access to HttpServletRequest and HttpServletResponse;
    • no manual casting from ServletRequest and ServletResponse;
    • designed for Spring-based web applications;
    • provides extension methods for controlling filtering behaviour;
    • prevents duplicate execution within the same dispatch using an internal request attribute.

    Important: The name does not mean the Filter can never run again for every possible dispatch. Servlet processing includes dispatch types such as REQUEST, ASYNC, ERROR, FORWARD, and INCLUDE; OncePerRequestFilter gives once-per-dispatch protection plus hooks for async and error dispatch.

    When extending OncePerRequestFilter, URL-exclusion logic can be placed in shouldNotFilter(). An ApiLoggingFilter overrides protected boolean shouldNotFilter(HttpServletRequest request), reads the URI, and returns !path.startsWith("/api/").

    Understanding the return value:

    • return true; means do not run doFilterInternal() for this request (skip).
    • return false; means run doFilterInternal() for this request.

    In the example, return !path.startsWith("/api/") produces false for /api/students, so the Filter runs, and true for /hello, so the Filter is skipped.

    16. Comparing URL-Scoping and Filter vs OncePerRequestFilter

    Approach Where the decision occurs Best suited for
    FilterRegistrationBean URL patterns at registration Clean, broad URL-pattern control
    Manual URI check inside doFilter() Inside Filter execution Small or custom runtime conditions
    OncePerRequestFilter.shouldNotFilter() Spring Filter hook Clean exclusions in a Spring-specific Filter

    General guidance:

    • Use FilterRegistrationBean when the Filter should not be registered for unrelated paths at all.
    • Use shouldNotFilter() when the inclusion rule naturally belongs inside a OncePerRequestFilter.
    • Use manual checks only when they stay simple or depend on custom request information.
    Point Filter OncePerRequestFilter
    API Jakarta Servlet API Spring Framework
    Request type ServletRequest HttpServletRequest
    Response type ServletResponse HttpServletResponse
    Casting required Usually yes No
    Main method doFilter() doFilterInternal()
    Built-in skip hook No dedicated Spring hook shouldNotFilter()
    Dispatch protection Must manage manually if needed Built-in once-per-dispatch mechanism
    Portability outside Spring Greater Spring-specific

    Both are valid; in a Spring Boot app, OncePerRequestFilter often yields cleaner code.

    Aspect Request wrapper Response wrapper
    Base class HttpServletRequestWrapper ContentCachingResponseWrapper
    Direction Incoming request Outgoing response
    What it changes Headers, parameters, body Body (after caching)
    Key methods getHeader, getParameter, getInputStream, getReader getContentAsByteArray, resetBuffer, copyBodyToResponse
    Re-read support Yes, over cached bytes Yes, via cached copy
    Cost Memory to buffer request body Memory to buffer response body

    17. Practical Guidelines

    Prefer a Filter for:

    • low-level request and response logging;
    • correlation or trace IDs;
    • compression or encoding concerns;
    • cross-origin handling when not using existing framework support;
    • request timing across the complete servlet flow;
    • HTTP-boundary concerns that apply before Spring MVC;
    • security-chain integration.

    Avoid using a Filter for:

    • core business logic;
    • database operations unrelated to the HTTP boundary;
    • normal DTO mapping;
    • controller-specific behaviour;
    • complex response restructuring when ResponseBodyAdvice is sufficient;
    • authentication systems that should use Spring Security;
    • blind logging of passwords, tokens, or complete request bodies.

    18. Myth vs Reality

    Myth Reality
    "A Filter can read the request body and the controller still gets it." Reading the stream consumes it; the controller may fail with "Required request body is missing" unless a caching wrapper is used.
    "HttpServletResponse has a getBody() method." It does not; the body goes to a stream, so a response wrapper is needed to inspect it later.
    "Forgetting copyBodyToResponse() is harmless." The client may receive an empty response because the data stays inside the wrapper.
    "setHeader() and addHeader() are the same." setHeader() replaces the value; addHeader() appends another value.
    "Request headers and query parameters can be set directly." The request is read-only; a wrapper must override the getters to change what downstream sees.
    "OncePerRequestFilter runs exactly once ever." It gives once-per-dispatch protection, not once for every possible dispatch such as ERROR or ASYNC.
    "A Filter is the best place for JSON transformation." ResponseBodyAdvice or Jackson configuration is usually cleaner; manually rebuilding JSON is uncommon.
    "@Component plus FilterRegistrationBean is fine for one Filter." It can create duplicate registrations and run the logic more than once.

    19. Common Trap Questions

    Trap 1 - "Read the body in a Filter to log it; the controller will still bind it." Verdict: False. getReader() and getInputStream() consume the same body, so the controller can fail with "Required request body is missing" unless the body is cached and re-served through a wrapper.

    Trap 2 - "A response body can be read back with response.getBody()." Verdict: False. No such method exists on HttpServletResponse; the body goes to an output stream, so ContentCachingResponseWrapper is required.

    Trap 3 - "You can skip copyBodyToResponse()." Verdict: False. Without it, the client may receive an empty response because the final body remains inside the wrapper.

    Trap 4 - "setHeader() and addHeader() do the same thing." Verdict: False. setHeader() replaces the existing value; addHeader() adds another value alongside it.

    Trap 5 - "Request headers and parameters can be modified directly on the request." Verdict: False. HttpServletRequest is read-oriented; setHeader() and setParameter() do not exist. A wrapper must override the getters.

    Trap 6 - "Registering with both @Component and FilterRegistrationBean is harmless." Verdict: False. It can produce two registrations and execute the Filter logic more than once. Choose one strategy.

    Trap 7 - "OncePerRequestFilter guarantees the Filter runs exactly once, ever." Verdict: Misleading. It prevents duplicate execution within the same dispatch; other dispatch types such as ERROR, ASYNC, FORWARD, and INCLUDE can still involve the Filter.

    20. Points to Remember

    1. A Filter can stop a request by returning without calling chain.doFilter().
    2. Add important response headers before the response becomes committed (isCommitted() checks this).
    3. A normal HttpServletResponse does not expose the completed body through getBody().
    4. ContentCachingResponseWrapper allows the response body to be inspected after downstream processing.
    5. Always call copyBodyToResponse() when using ContentCachingResponseWrapper to preserve the final response.
    6. The original HttpServletRequest provides no setters for headers or query parameters.
    7. Request wrappers change what downstream components see without changing the original request object.
    8. Reading a request body in a Filter can consume the stream before the controller receives it.
    9. Re-readable request bodies require caching and overridden getInputStream() and getReader().
    10. Buffering request or response bodies has memory, performance, privacy, and security costs, so use the narrowest appropriate layer.

    21. Likely Interview Questions

    Question Crisp Answer
    How does a Filter modify a response header? Cast to HttpServletResponse, call setHeader() or addHeader() before chain.doFilter().
    setHeader() vs addHeader()? setHeader() replaces the existing value; addHeader() adds another value.
    Why add headers before chain.doFilter()? Downstream code may flush and commit the response; after that, status and headers may no longer change.
    How do you change a response body in a Filter? Wrap the response in ContentCachingResponseWrapper, read getContentAsByteArray(), resetBuffer(), write the new body, then copyBodyToResponse().
    What happens if you forget copyBodyToResponse()? The client may get an empty body because the content stayed inside the wrapper.
    How can request headers or parameters be modified? Only through an HttpServletRequestWrapper that overrides the relevant getters.
    Why can a request body not be read twice? It is a stream with a read position; once consumed, it is at the end and the bytes are not rewound.
    Why does Tomcat not rewind the body automatically? Buffering every body would cost memory and disk, add latency, reduce throughput, and create DoS risk.
    How do you make a request body re-readable? Read it once, cache the bytes, wrap the request, and return a fresh ByteArrayInputStream from the overridden getInputStream() and getReader().
    @Component vs FilterRegistrationBean? @Component maps broadly; FilterRegistrationBean gives explicit URL, order, name, dispatcher, and enable control.
    How is Filter order controlled? setOrder(n); lower values run earlier on the request and later on the response.
    What is shouldNotFilter() for? A OncePerRequestFilter hook returning true to skip doFilterInternal() for matching requests.

    • Filters mutate at the HTTP boundary: headers and status are simple, bodies need wrappers.
    • The request is read-oriented; only a wrapper changes what downstream code sees.
    • The request body is a one-pass stream; re-reading needs caching plus overridden getInputStream() and getReader().
    • Register with @Component for broad simple use, or FilterRegistrationBean for URL and order control; never both for one Filter.
    • OncePerRequestFilter plus shouldNotFilter() is the cleaner Spring-native option.
    • Use the narrowest correct layer; buffering bodies costs memory and privacy.

    One-line takeaway: a Filter can change almost anything in the request/response exchange, but headers and status are free, bodies require wrappers on both sides, and the request body is a single-pass stream that must be cached and re-wrapped to be read again.
