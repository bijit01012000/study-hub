    Singleton

    12 sections · 884 words

    Creational · Design Patterns · Pattern 03 of 12

    Intent

    Guarantee exactly one instance of a class and provide a safe, controlled point of access to it.

    When To Use It

    The Signs

    • A config, pool, ID generator or registry that must be exactly one, but nothing enforces it.
    • new calls for it in three or four places, each team making its own.
    • It's threaded through every constructor just so deep code can reach it.
    • A bug from having two: caches that disagree, two counters, two schedulers.

    Don't Bother If

    • You need shared behaviour, no state. A static utility class is enough.
    • A DI container can hold it in singleton scope for you.
    • Its life is one request or task. Make one, pass it down, drop it.
    • The cost (a hidden global, harder tests) buys nothing here.

    Before

    class Config {
    // no guard
    public Config() { load("app.conf"); }
}
Config a = new Config(); // AuthModule
Config b = new Config(); // Billing
Config c = new Config(); // ReportJob
a.reload(); // only a sees the new file
// three configs now, and they disagree

    No guarantee.

    After

    class Config {
    private Config() { load("app.conf"); }
    // no one else can new it

    private static class Holder {
        static final Config I = new Config();
        // built once, on first touch
    }
    public static Config get() {
        return Holder.I;
        // JVM guarantees one, safely
    }
}
// Holder loads lazily: I is built on the
// first get() call, and only once.

// or, simplest thread-safe form:
// enum Config { INSTANCE; ... } also
// serialization- and reflection-safe

// best: take Config as a constructor param,
// keep get() as the default wiring

    Or a naive lazy field, which races:

    class Config {
    private static Config instance;
    static Config get() {        // no lock
        if (instance == null)    // two threads see null
            instance = new Config(); // both build one
        return instance; } }
// 'synchronized' fixes it but locks every read;
// double-checked locking then needs 'volatile'

    Quick Check

    Ask "if there were two of these, what would break?" Nothing means no Singleton. "The counts drift" or "the cache splits" means yes.

    Structure

    Config
    SINGLETON
    - instance: Config          static, underlined
                                constructor is private
    - Config()                  private ctor
    + getInstance(): Config     returns the one

Client -> Config.getInstance()
Client -> Config.getInstance()
    both reach the same object

ONE PER CLASSLOADER, NOT PER PROCESS

    How It's Built (3 Steps)

    1. Make the constructor private so nobody outside the class can new it.
    2. Hold the one instance in a private static field, created safely: a static holder class, or an enum.
    3. Expose getInstance() that hands back that one. Better, inject it rather than call getInstance() everywhere.

    In The Interview

    "ParkingLot is a Singleton so every gate reads the same floor map. I'd give it a private constructor and a static holder, but I'd inject it into the gates rather than call getInstance() inside them, so a test can pass a fake lot."

    How It's Different

    From The Lookalikes

    Vs a static utility class. That has methods and no instance, no state, no lifecycle. A Singleton is one real object with state you could, in principle, have made many of.

    Vs Monostate. Monostate lets you make many instances that all share static fields: looks normal, behaves as one. Singleton enforces literally one object.

    Vs DI "singleton scope." The container owns the instance and injects it, so a test can swap it. The Singleton pattern owns itself, which is what makes it hard to test.

    Vs a plain global. A global has no lazy init, no thread-safe creation, no single point that controls it. A Singleton wraps all three.

    They Say: "how do you test code that calls getInstance()?"

    • With it: you don't. The lot is a constructor parameter, so the test passes a stub. The Singleton is just the default wiring.
    • Without: every test shares one global lot, state leaks between tests, and you add a reset() that only exists for tests.

    Watch Out For

    • Double-checked locking needs the field volatile, or a half-built object leaks. Just use the static holder idiom instead.
    • An enum singleton is thread-safe, serialization-safe and reflection-safe for free. Reach for it first.
    • It's a hidden dependency: code that calls getInstance() doesn't declare what it needs. Inject so the wiring is visible.
    • It's one per classloader, not per machine. In a cluster there are many. Don't assume global uniqueness.
    • Careful with mutable business state in it. A Singleton cache is fine; a Singleton "current user" is a bug.

    How To Say It

    Nearly every problem sheet's top-level service is a Singleton, usually an injected one.
