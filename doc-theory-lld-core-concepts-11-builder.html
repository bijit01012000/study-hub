    Builder

    10 sections · 889 words

    Creational · Design Patterns · Pattern 02 of 12

    Intent

    Assemble one complex object field by field on a separate mutable draft, then validate once and hand back something immutable.

    When To Use It

    The Signs

    • A constructor with 6+ parameters, and half of them optional.
    • Telescoping constructors: new X(a), then X(a,b), then X(a,b,c), one per combination.
    • new Pizza(true, false, null, 12) where you cannot tell what an argument means.
    • An object newed, then mutated into shape by a dozen setters before it is usable.

    Don't Bother If

    • The object has 2 or 3 fields, all required.
    • Nothing is optional and the set will not grow.
    • The language gives you named or default arguments.
    • The cost, a parallel builder class to keep in sync, is not paying for itself yet.

    Before

    class Pizza {
    // a constructor per combination
    Pizza(int size) {...}
    Pizza(int size, Crust c) {...}
    Pizza(int size, Crust c, boolean cheese) {...}
    Pizza(int size, Crust c, boolean cheese,
          boolean pepperoni) {...}
    // each optional field doubles the list
}
// and the call site reads as noise:
new Pizza(12, THIN, true, false, null);
// true? false? null? no way to tell

    Hard to read.

    After

    Pizza p = Pizza.builder()
    .size(12).crust(THIN).cheese().pepperoni().build();
// one call, and every choice is named

class Pizza {
    // immutable: fields all final
    private final int size;
    private Pizza(Builder b) { this.size = b.size; ... }
    static Builder builder() { return new Builder(); }

    static class Builder {
        private int size; private Crust crust;
        private boolean cheese;
        Builder size(int s) { this.size = s; return this; }
        Builder crust(Crust c) { this.crust = c; return this; }
        Builder cheese() { this.cheese = true; return this; }
        Pizza build() {
            if (size == 0) throw new IllegalStateException("needs a size");
            return new Pizza(this);
            // built once, then immutable
        }
    }
}
// a new option is one setter and one check. nothing else stirs.

    Or one setter per field on the product itself, which is observable half built:

    Pizza p = new Pizza();
// empty, not yet valid
p.setSize(12);
p.setCrust(THIN);
p.setCheese(true);
// ... eight more setters, in any order
bake(p);
// only here does it fail: size never set

    Structure

    Client -------------------------+
    picks the options          |
                               v
PizzaBuilder            Pizza.builder() hands you one
    MUTABLE DRAFT
    - size, crust, sauce
    - toppings: List
    + size(int): this
    + crust(Crust): this
    + cheese(): this
    + build(): Pizza
    each setter returns the builder (return this)
    one setter per field

Pizza  build()
    IMMUTABLE
    final int size
    final Crust crust
    final List toppings

BUILD() VALIDATES, THEN CONSTRUCTS THE PIZZA ONCE

    How It's Built (3 Steps)

    1. Give the product a private constructor that takes the Builder, and expose a static builder(). Nothing else can make one.
    2. The Builder holds the same fields, one setter per field, each ending return this so the calls chain.
    3. build() checks the invariants, constructs the product once, and hands back something immutable.

    In The Interview

    "The DrinkOrder has a dozen options, so I would give it a builder: order().extraShot().oatMilk().noSugar().build(). The setters just record choices; build() rejects an impossible combo and returns an immutable order."

    How It's Different

    From The Lookalikes

    Vs Factory Method. A Factory picks which subclass to make from a type. A Builder makes one class but assembles it field by field, with validation at the end.

    Vs a fluent setter chain. Those setters mutate the real thing, so it is observable half built and never immutable. A Builder holds a draft; build() is the only thing that makes a product.

    Vs named arguments. Named or default args are a language feature: no staged validation, no place to compute a derived field. A Builder is a real object you can pass around and extend.

    Vs Prototype. Prototype copies an existing object and tweaks it. Builder starts from nothing and adds.

    They Say: "now add a 'decaf' option"

    • With it: add one decaf() setter and one line in build(). Nothing else moves.
    • Without: a 13th constructor parameter, or a 13th mutable setter and a prayer that the order is still consistent.

    Watch Out For

    • build() must copy the builder's collections (defensive copy), not share them, or a later setter call mutates a finished product.
    • Validate in build(), not in each setter. Setters accept anything; the whole picture is only known at build time.
    • A Director (a class that runs a fixed recipe of builder calls) is optional. Skip it unless you truly reuse recipes.
    • Don't also leave the product's constructor public. The builder is the only door in.
    • For a class hierarchy, use a self-referential generic builder so SubBuilder.size() still returns the sub-builder.
