      Top 200 Java Questions — Tier S: Core Java & Collections

      0 sections · 5,989 words

      Tier S — Asked in 80%+ of Java interviews (50 Qs). These are the same 50 questions from 01 Top 50 Most-Asked. Reproduced here so this file stands alone. If you have already worked through Top 50, skim Tier S and move directly to Tier A.

      1. HashMap internals — what happens when you call put()?

      Asked at: TCS · Infosys · Razorpay · Swiggy · almost every Java interview

      Difficulty: Medium · Topic: Collections

      The question: "Walk me through what happens internally when you call put("key", "value") on a HashMap."

      The 30-second answer: Hash the key → bitwise-AND with (capacity - 1) to find a bucket → if empty, place entry; if not, walk the bucket's chain (linked list, or red-black tree if bucket has ≥ 8 nodes AND map size ≥ 64) → resize if size > capacity × 0.75.

      Step-by-step thought process:

      1. "First, hashCode() is called on the key, then a supplemental hash mixes the high bits down — this reduces collisions when capacity is small."
      2. "Index is computed via (capacity - 1) & hash — works because capacity is always a power of 2."
      3. "If the bucket is empty, entry goes in. Otherwise we walk the existing chain — comparing each entry's key via equals()."
      4. "In Java 8+, when a single bucket has 8 or more nodes AND the table's capacity is ≥ 64, that bucket is converted to a red-black tree — O(log n) lookups instead of O(n)."
      5. "After insert, if size > capacity × loadFactor (default 0.75), the map resizes — capacity doubles, every entry rehashed."

      Edge cases to mention:

      • Null keys are allowed and stored in bucket 0
      • Two keys with the same hashCode end up in the same bucket but are distinguished via equals() — so a broken equals() / hashCode() contract causes silent overwrites or duplicates
      • Treeification requires BOTH conditions (bucket ≥ 8 AND table capacity ≥ 64) — when capacity is below 64, the map resizes instead of treeifying

      What NOT to say:

      • "It's just a hashtable" — interviewer wants depth, not category labels
      • "It uses chaining" — true but stale; Java 8 added treeification, mention both
      • "Treeification happens at 8 entries" — wrong, it's 8 entries in one bucket + table capacity ≥ 64

      Common follow-up: "What's different about ConcurrentHashMap's put()?"

      2. String immutability — why is String immutable in Java?

      Asked at: TCS · Infosys · Accenture · most fresher rounds

      Difficulty: Easy · Topic: Strings

      The question: "Why is String immutable in Java? Walk me through the design reasoning."

      The 30-second answer: Five reasons — security (paths, URLs, class names can't be mutated after validation), thread-safety (no synchronization needed), hashcode caching (computed once, reused forever — critical for HashMap keys), String Pool (sharing requires immutability), and class loader integrity (class names passed to loaders can't change mid-load).

      Step-by-step thought process:

      1. "Security — String is used for filesystem paths, network URLs, classloader inputs. If mutable, validated-then-mutated attacks become trivial."
      2. "Thread safety — multiple threads can share a String reference with zero synchronization, because the value can't change."
      3. "HashMap performance — String's hashcode is cached on first call. If String were mutable, the cached hash would become stale, breaking every hash-based collection."
      4. "String Pool — JVM interns string literals so identical strings share memory. Sharing only works if values can't be modified through one reference."
      5. "Class loading — when Class.forName("com.foo.Bar") runs, the class name string flows through the loader. Mutability would let other code race to change it mid-load."

      Edge cases to mention:

      • String is final so even subclassing can't break the contract
      • The value array is private final (Java 9+: byte[] instead of char[] for compact strings) StringBuilder/StringBuffer give you mutability when you actually need it — use them in loops to avoid creating N intermediate strings

      What NOT to say:

      • "Because Java just made it that way" — non-answer, downgrades you
      • "It's immutable for performance" — partial; performance is one of five reasons, not the main one

      Common follow-up: "What's the difference between == and .equals() for Strings? When does the String Pool help vs hurt?"

      3. ArrayList vs LinkedList — which one when?

      Asked at: Almost every Java interview, fresher to senior

      Difficulty: Easy-Medium · Topic: Collections

      The question: "When would you choose ArrayList over LinkedList, and when the reverse?"

      The 30-second answer: ArrayList = backed by an array, O(1) random access, O(n) insert/delete in the middle. LinkedList = doubly-linked nodes, O(n) random access, O(1) insert/delete if you already have the node reference. Default to ArrayList unless you're doing heavy middle-of-list mutations with iterators.

      Step-by-step thought process:

      1. "ArrayList wraps an Object[]. Random access via index is one memory lookup — O(1). Adding to the end is amortized O(1); when capacity fills, the array is doubled."
      2. "Insert or delete in the middle of an ArrayList requires shifting every subsequent element — O(n)."
      3. "LinkedList is a doubly-linked list. Random access requires walking from head or tail to the index — O(n)."
      4. "Insert/delete in LinkedList is O(1) only if you have the node reference (e.g. via an iterator). If you have just an index, you still walk O(n) to find the node."
      5. "In practice, ArrayList wins almost always. CPU cache locality favors arrays. LinkedList's per-node memory overhead (prev + next pointers) hurts on large datasets."

      Edge cases to mention:

      • LinkedList is also a Deque — useful if you need queue + stack semantics from one collection
      • ArrayList's remove(int) is O(n); remove(Object) is also O(n) because it does a linear scan first
      • For large insert-heavy workloads, ArrayDeque often outperforms both

      What NOT to say:

      • "LinkedList is faster for inserts" — true only with cached node references; misleading as a blanket claim
      • "Just use Vector for thread safety" — Vector is legacy; use Collections.synchronizedList() or CopyOnWriteArrayList instead

      Common follow-up: "What about CopyOnWriteArrayList? When does that make sense?"

      4. == vs equals() vs the hashCode contract

      Asked at: Razorpay · Swiggy · most product cos · senior-to-fresher

      Difficulty: Medium · Topic: OOP fundamentals

      The question: "Explain the difference between == and .equals(). Then explain the hashCode contract."

      The 30-second answer: == compares references (same object in memory?). .equals() compares logical equality (same content). The contract: if a.equals(b), then a.hashCode() == b.hashCode() — always. The reverse is NOT required: two objects with the same hashCode can have equals() return false. Breaking this contract corrupts HashMap, HashSet, and every hash-based collection.

      Step-by-step thought process:

      1. " == on objects is identity equality — are these two references pointing to the exact same memory location?"
      2. " .equals() defaults to == in Object, but most classes override it to compare logical content (Strings compare characters, Integers compare values)."
      3. "The hashCode contract: equal objects (per equals) MUST return the same hashCode. The reverse is not required — collisions are allowed."
      4. "If you override equals() without overriding hashCode(), your objects break HashMap. You'd add a key, then get() would return null because the lookup hash points to a different bucket than the stored hash."
      5. "The standard implementation: derive hashCode from the same fields used in equals — usually Objects.hash(field1, field2, …)."

      Edge cases to mention:

      • Objects.equals(a, b) is null-safe — use it instead of a.equals(b) when either side might be null
      • Records (standardized Java 16, preview from Java 14) auto-generate equals/hashCode based on all components — one big reason to use records for data classes
      • For mutable fields used in equals/hashCode: never mutate after adding to a hash collection; it corrupts the collection

      What NOT to say:

      • " equals() checks if two objects are the same" — vague, says nothing
      • "Override equals() but not hashCode() — Java will figure it out" — actively wrong, will be silently broken

      Common follow-up: "Why must you use Objects.hash() instead of just adding hashCodes?"

      5. volatile vs synchronized vs atomic — when each?

      Asked at: Razorpay · Cred · senior backend rounds

      Difficulty: Medium-Hard · Topic: Concurrency

      The question: "What's the difference between volatile, synchronized, and AtomicInteger? Give me a use case where each is the right pick."

      The 30-second answer: volatile = visibility only (writes flush to main memory, reads from main memory), no atomicity. synchronized = mutual exclusion AND visibility, allows compound actions. Atomic* = lock-free atomic operations (CAS) for single variables — faster than synchronized for simple counters and flags.

      Step-by-step thought process:

      1. " volatile guarantees that a write to the variable is visible to all threads immediately — no thread-local caching. But it does NOT make compound operations atomic. volatile int counter; counter++; is still a race condition."
      2. " synchronized blocks (or methods) acquire a monitor on an object. Only one thread executes inside the block at a time. Also has visibility guarantees — exiting a synchronized block flushes writes, entering one reads fresh values."
      3. " AtomicInteger, AtomicLong, etc. use Compare-And-Swap (CAS) hardware instructions. Lockfree, much faster than synchronized for simple operations like incrementAndGet()."
      4. "Use volatile for: status flags read by many threads, written rarely (like shutdownRequested)."
      5. "Use synchronized for: compound operations on shared state (check-then-act, multi-field updates)."
      6. "Use Atomic for: counters, flags with read-modify-write semantics, where contention is moderate."

      Edge cases to mention:

      • volatile ensures happens-before relationship — useful for doublechecked locking on singletons (volatile on the instance field)
      • synchronized on this and on a class's class object are different locks — easy to confuse
      • For very-high-contention counters, LongAdder outperforms AtomicLong (striped internal state)

      What NOT to say:

      • " volatile makes operations atomic" — common mistake, wrong
      • "Just use synchronized everywhere, it's safer" — performance-killing advice, gets you marked as junior

      Common follow-up: "What's the double-checked locking pattern, and why does it need volatile?"

      6. Checked vs unchecked exceptions — when to use which?

      Asked at: Most Java interviews, fresher onwards

      Difficulty: Easy-Medium · Topic: Exception handling

      The question: "Difference between checked and unchecked exceptions? When would you create a checked exception vs an unchecked one in your own code?"

      The 30-second answer: Checked extends Exception (not RuntimeException), must be declared or caught — compiler enforces. Unchecked extends RuntimeException, no enforcement. Use checked for recoverable conditions the caller MUST handle (e.g. file not found, network unavailable). Use unchecked for programming errors and conditions the caller can't reasonably recover from (e.g. null argument, illegal state).

      Step-by-step thought process:

      1. "Java's exception hierarchy: Throwable → Error or Exception. Exception → RuntimeException (unchecked) or all others (checked)."
      2. "Checked exceptions force the caller to handle or propagate at compile time — throws declaration required."
      3. "Unchecked exceptions can be thrown anywhere with no declaration. RuntimeException, NullPointerException, IllegalArgumentException are all unchecked."
      4. "When designing my own API: if the caller can REASONABLY recover (retry the network call, ask user for a different file path), make it checked. If it's a bug in the caller (passed null, called methods out of order), make it unchecked."
      5. "In practice, modern Java (Spring, etc.) leans heavily toward unchecked — checked exceptions force boilerplate that often gets caught-and-ignored or wrapped meaninglessly. Spring even wraps JDBC's checked SQLExceptions into unchecked DataAccessException."

      Edge cases to mention:

      • Errors (OutOfMemoryError, StackOverflowError) are not exceptions you should catch — they signal JVM-level problems
      • Lambda expressions can't throw checked exceptions unless the functional interface declares them — a common pain point with Stream.map()
      • Try-withresources auto-closes AutoCloseable resources and propagates suppressed exceptions correctly

      What NOT to say:

      • "Checked exceptions are bad, never use them" — opinionated and absolute; nuanced answer is better
      • "Just catch Exception everywhere" — anti-pattern, hides real bugs

      Common follow-up: "Why doesn't Stream.map() let you throw checked exceptions easily?"

      7. JDK vs JRE vs JVM — what's the difference?

      Asked at: TCS · Infosys · most fresher rounds

      Difficulty: Easy · Topic: Java platform

      The question: "Explain the difference between JDK, JRE, and JVM."

      The 30-second answer: JVM = runtime engine that executes bytecode. JRE = JVM + standard libraries (everything needed to RUN Java apps). JDK = JRE + development tools like javac, jdb, jar (everything needed to BUILD Java apps).

      Step-by-step thought process:

      1. "JVM (Java Virtual Machine) is the abstract specification of a stackbased machine that executes Java bytecode. HotSpot, OpenJ9, GraalVM are concrete implementations."
      2. "JRE (Java Runtime Environment) packages a JVM together with the standard Java class library — java.lang, java.util, java.io, etc."
      3. "JDK (Java Development Kit) packages a JRE plus development tools: javac (compiler), jar (packager), jdb (debugger), javadoc, plus internal APIs for tools."
      4. "Oracle stopped shipping a standalone JRE distribution starting with Java 11. You typically install a JDK and use jlink to build a slim runtime image if you need a JRE-equivalent."
      5. "For a developer's mental model: write .java → compile with javac (JDK) → produces .class bytecode → executed by JVM (JRE)."

      Edge cases to mention:

      • The JVM doesn't only run Java — Kotlin, Scala, Clojure, Groovy all compile to JVM bytecode
      • Multiple JVM implementations exist: HotSpot (Oracle), OpenJ9 (IBM/Eclipse), GraalVM (polyglot, ahead-of-time compilation)
      • Since Java 9, modules let you build a custom JRE containing only the modules your app uses — smaller runtime footprint

      What NOT to say:

      • "JDK runs Java programs" — wrong; JVM runs them. JDK builds them.
      • "JRE is needed at runtime" — true historically, but Java 9+ blurs this with jlink

      Common follow-up: "What does javac actually produce? What's bytecode?"

      8. final vs finally vs finalize — three different things

      Asked at: TCS · Infosys · Cognizant · classic fresher question

      Difficulty: Easy · Topic: Java language

      The question: "What's the difference between final, finally, and finalize?"

      The 30-second answer: final = keyword for immutability (final variable, final method, final class). finally = block that always runs after try/catch (for cleanup). finalize() = legacy Object method called by GC before reclaiming an object — deprecated since Java 9, deprecated-for-removal since Java 18 (still present in Java 21 but treat it as gone).

      Step-by-step thought process:

      1. " final has three uses: final variable = can't reassign after init, final method = can't override in subclass, final class = can't extend."
      2. " finally is the try/catch/finally block — code inside finally runs whether the try block completes normally, throws, or returns early. Used for cleanup: closing resources, releasing locks."
      3. " finalize() was a method on Object — the GC would call it before reclaiming an object, giving the object a chance to clean up. It was deprecated in Java 9 and marked deprecated-for-removal in Java 18 (JEP 421), and is still present in Java 21 — but treat it as gone."
      4. "Modern equivalent of finalize: implement AutoCloseable and use try-withresources, OR use Cleaner (Java 9+) which decouples cleanup logic from the object lifecycle."

      Edge cases to mention:

      • final parameters can't be reassigned inside the method — useful for closures, prevents accidental mutation
      • try-with-resources is the preferred pattern over manual finally { close(); } — handles suppressed exceptions correctly
      • Even before Java 18, finalize() was unreliable — the GC made no guarantees about WHEN or IF it would be called

      What NOT to say:

      • "Finalize is called when an object is destroyed" — vague and outdated; GC reclaims, doesn't "destroy"
      • Confusing them with one another — interviewer will downgrade you to fresher-tier on this question

      Common follow-up: "How would you replace finalize() in modern Java?"

      9. Singleton pattern — 4 ways to implement it, which is thread-safe?

      Asked at: Common at all levels

      Difficulty: Medium · Topic: Design patterns + concurrency

      The question: "Show me how to implement a Singleton in Java. Walk me through the trade-offs."

      The 30-second answer: Four common ways — eager init (simple, thread-safe via class loading), lazy init with synchronized method (thread-safe but slow), double-checked locking with volatile (thread-safe and fast), enum (Bloch's preferred — handles serialization and reflection attacks). Enum is the cleanest for most cases.

      Step-by-step thought process:

      1. "Eager initialization: private static final Singleton INSTANCE = new Singleton(); — thread-safe because class loading is thread-safe per the JLS. Downside: instantiated even if never used."
      2. "Lazy with synchronized: method returns instance, creating it on first call. Thread-safe but every call pays synchronization cost."
      3. "Double-checked locking: check instance == null without lock, lock only if null, check again inside lock. Faster than synchronized method but requires volatile on the instance field — otherwise the partially-constructed object can be visible to other threads."
      4. "Enum singleton: public enum Singleton { INSTANCE; } — handles serialization automatically, prevents reflection attacks, lazy by default. Joshua Bloch's recommended approach in Effective Java."
      5. "For most code, enum is the right pick. Spring's @Service / @Component (default scope=singleton) handles this for managed beans."

      Edge cases to mention:

      • Without volatile in DCL, the JIT can reorder writes — another thread might see a non-null reference to a not-yet-initialized object
      • Reflection can bypass private constructors — only the enum approach is truly bulletproof
      • Serialization can create a new instance via deserialization — enum handles this; other approaches need readResolve()

      What NOT to say:

      • "Just use synchronized on getInstance" — works but slow, and shows you don't know DCL
      • "Singleton is an anti-pattern, never use it" — opinionated; the interviewer wants to see you can implement it correctly

      Common follow-up: "Why does double-checked locking specifically require volatile?"

      10. Garbage collection — what are the major collectors and when each?

      Asked at: Mid-to-senior backend rounds

      Difficulty: Medium-Hard · Topic: JVM internals

      The question: "Walk me through the major garbage collectors in modern Java. When would you choose each?"

      The 30-second answer: G1 (default since Java 9) — balanced throughput and pause times, good for most server apps. ZGC and Shenandoah — ultra-low pause (sub-millisecond), for latency-sensitive systems. Parallel GC — throughput-optimized, batch jobs. Serial GC — single-threaded, small heaps only.

      Step-by-step thought process:

      1. "All major GCs are generational — heap split into young generation (Eden + 2 survivor spaces) and old generation. Most allocations happen in Eden; most objects die young."
      2. "G1 (Garbage First) — default since Java 9. Divides heap into regions, prioritizes collecting regions with the most garbage. Targets predictable pause times (MaxGCPauseMillis). Good default for most apps."
      3. "ZGC — concurrent, low-latency. Pause times under 1ms even on huge heaps (TBscale). Trade-off: slightly lower throughput. Production-ready since Java 15."
      4. "Shenandoah — similar low-pause design, developed at Red Hat. Comparable to ZGC for most workloads."
      5. "Parallel GC — older, throughput-optimized, stop-the-world. Good for batch processing where pauses don't matter but total time does."
      6. "Serial GC — single-threaded. Only for small heaps and embedded systems."

      Edge cases to mention:

      • G1 has a humongous object threshold — objects ≥ ½ region size allocate directly in old gen
      • ZGC supports colored pointers (uses 64-bit pointer metadata) — required for its concurrent design
      • Java 21 introduced generational ZGC as opt-in (non-generational remained default in 21); generational became default in Java 24 — improved throughput either way

      What NOT to say:

      • "Java's GC handles everything automatically, don't worry about it" — true for helloworld, wrong for production
      • "CMS is the best low-latency option" — CMS was REMOVED in Java 14, this dates you badly

      Common follow-up: "How do you tune G1 for a Spring Boot app with bursty traffic?"

      11. ConcurrentHashMap — how is it different from HashMap?

      Asked at: Razorpay · Cred · senior backend rounds

      Difficulty: Medium-Hard · Topic: Concurrency + Collections

      The question: "How does ConcurrentHashMap differ from HashMap, and what changed between Java 7 and Java 8?"

      The 30-second answer: HashMap is not thread-safe. ConcurrentHashMap is. Java 7 used segmentbased locking (16 segments by default, each locked independently). Java 8 ditched segments — uses CAS for inserts on empty buckets, synchronizes on the first node of a bucket for collisions. Much higher concurrency in Java 8+.

      Step-by-step thought process:

      1. "HashMap is fast but unsafe for concurrent writes — you can get corrupted state, infinite loops on resize (classic Java 7 bug), or lost updates."
      2. "ConcurrentHashMap (Java 7) divided the table into 16 segments, each with its own lock. Writers held only one segment's lock at a time, so up to 16 writers could proceed in parallel."
      3. "Java 8 rewrote it: lock-free on empty buckets using compareAndSwap, fine-grained synchronization on the first node of a bucket when there's a collision. No more segments."
      4. "Reads are completely lock-free in both versions — you can read while others write."
      5. " computeIfAbsent, merge, compute are the atomic compound operations — use these instead of check-then-put."

      Edge cases to mention:

      • ConcurrentHashMap forbids null keys and null values (HashMap allows both) — null would create ambiguity in get/contains return values
      • Iterators are weakly consistent — may or may not reflect modifications made after iteration started, but won't throw ConcurrentModificationException
      • For high-concurrency counts, prefer mappingCount() (returns long) over size() (returns int)

      What NOT to say:

      • "Just use Collections.synchronizedMap(new HashMap())" — that wraps with one giant lock, much slower than ConcurrentHashMap
      • "ConcurrentHashMap is always faster than HashMap" — false; HashMap is faster single-threaded

      Common follow-up: "When would you use computeIfAbsent vs putIfAbsent?"

      12. Fail-fast vs fail-safe iterators

      Asked at: Common in Indian product company senior rounds

      Difficulty: Medium · Topic: Collections + iterators

      The question: "What's the difference between fail-fast and fail-safe iterators? Give an example of each."

      The 30-second answer: Fail-fast iterators throw ConcurrentModificationException if the underlying collection is modified during iteration (ArrayList, HashMap iterators). Fail-safe iterators work on a snapshot or use copy-on-write semantics, so concurrent modification is allowed (ConcurrentHashMap, CopyOnWriteArrayList iterators).

      Step-by-step thought process:

      1. "Most JCF collections (ArrayList, HashMap, HashSet) keep an internal modCount counter. The iterator captures modCount at creation; each next() checks it hasn't changed."
      2. "If something modifies the collection (even via another iterator), modCount increments. The next next() call detects the mismatch and throws ConcurrentModificationException."
      3. "This is fail-FAST — fails immediately to prevent silently inconsistent iteration."
      4. "Fail-SAFE iterators (ConcurrentHashMap, CopyOnWriteArrayList, ConcurrentLinkedQueue) don't throw on concurrent modification. They either iterate over a snapshot (CopyOnWriteArrayList) or are weakly consistent (ConcurrentHashMap)."
      5. "Important caveat: 'fail-safe' doesn't mean 'sees all updates' — you may miss modifications made during iteration."

      Edge cases to mention:

      • Iterator.remove() is the only safe way to modify a fail-fast collection during iteration
      • Single-threaded code can hit ConcurrentModificationException too — if you call list.remove(x) directly inside an enhanced for-loop
      • Collections.unmodifiableList returns a wrapper — modification attempts throw immediately, not on next iteration

      What NOT to say:

      • "Fail-safe is always better" — copy-on-write has heavy write cost; fail-fast is correct for single-threaded code
      • "ConcurrentHashMap iterators throw on modification" — wrong, they don't

      Common follow-up: "When would CopyOnWriteArrayList actually be the right choice?"

      13. CopyOnWriteArrayList — when is it the right pick?

      Asked at: Product cos · senior rounds

      Difficulty: Medium · Topic: Concurrent collections

      The question: "When would you actually use CopyOnWriteArrayList? What are the trade-offs?"

      The 30-second answer: Use when reads vastly outnumber writes — listener lists, configuration data, observer patterns. Every write copies the entire underlying array (O(n)), but reads need zero synchronization. Iterators are guaranteed snapshot-consistent.

      Step-by-step thought process:

      1. "On every mutation (add, remove, set), CopyOnWriteArrayList creates a brand new copy of the underlying array with the change applied, then replaces the reference."
      2. "Reads — including iteration — happen against whichever array the reference pointed to at read-time. Zero synchronization, no locks."
      3. "Iterators capture the array reference at creation, so they iterate a consistent snapshot — modifications during iteration don't affect them and don't throw."
      4. "Cost: O(n) per write, plus garbage from the discarded array. Reads are O(1) lock-free."
      5. "Sweet spot: small to medium lists, many readers (e.g. event listeners, plugin registries), few writers."

      Edge cases to mention:

      • iterator().remove() throws UnsupportedOperationException — iterators are snapshot, can't reach back to mutate
      • For maps, CopyOnWriteArrayMap doesn't exist; use ConcurrentHashMap instead
      • If your collection has more than a few thousand elements with even moderate writes, this is the wrong choice — the copy cost dominates

      What NOT to say:

      • "It's just a thread-safe ArrayList" — true but hides the copy-on-write cost
      • "Use it for queues" — use ConcurrentLinkedQueue or ArrayBlockingQueue for queues

      Common follow-up: "How does CopyOnWriteArraySet relate to this?"

      14. TreeMap and red-black trees

      Asked at: Common in mid-level rounds

      Difficulty: Medium · Topic: Sorted collections

      The question: "What's the underlying data structure of TreeMap, and what guarantees does it give you over HashMap?"

      The 30-second answer: TreeMap is a self-balancing red-black tree. Operations are O(log n) instead of HashMap's O(1) average. In exchange: keys are kept in sorted order, and you get navigation methods (floorKey, ceilingKey, headMap, tailMap, subMap).

      Step-by-step thought process:

      1. "Red-black tree is a self-balancing binary search tree with five invariants — most importantly, no red node has a red parent, and every path from root to null has the same number of black nodes."
      2. "These invariants ensure the tree stays approximately balanced — height is O(log n) — guaranteeing O(log n) for get/put/remove."
      3. "Keys must be Comparable (or you supply a Comparator at construction). The tree uses comparison, not hash."
      4. "Navigation methods are TreeMap's killer feature: firstKey, lastKey, floorKey(k) (largest key ≤ k), ceilingKey(k) (smallest key ≥ k), headMap(k) (entries < k), etc."
      5. "Use TreeMap when you need ordered iteration, range queries, or 'find closest key' operations. Use HashMap when you only need fast lookup and don't care about order."

      Edge cases to mention:

      • TreeMap doesn't allow null keys (uses comparison; null can't be compared) but allows null values
      • firstEntry, lastEntry, pollFirstEntry, pollLastEntry are useful for priority-queue-like patterns
      • ConcurrentSkipListMap is the concurrent equivalent — also sorted, also O(log n), thread-safe

      What NOT to say:

      • "TreeMap is faster than HashMap" — wrong, HashMap is faster for plain lookups
      • "TreeMap is a B-tree" — wrong, it's a red-black tree

      Common follow-up: "How would you find all entries with keys between X and Y?"

      15. LinkedHashMap and LRU cache

      Asked at: System design adjacent · mid-level rounds

      Difficulty: Medium · Topic: Specialized collections

      The question: "How would you implement an LRU cache in Java in 10 lines?"

      The 30-second answer: Extend LinkedHashMap with accessOrder=true and override removeEldestEntry() to return true when size exceeds capacity. LinkedHashMap maintains a doubly-linked list of entries in access order; the eldest (least recently accessed) is at the head, ready to be evicted.

      Step-by-step thought process:

      1. "LinkedHashMap is HashMap + a doubly-linked list threading through all entries. Iteration order can be insertion order (default) or access order (constructor flag)."
      2. "With accessOrder=true, every get() and put() moves the touched entry to the tail of the linked list. The head is always the least-recently-used."
      3. " removeEldestEntry(Map.Entry) is called after every put. Default returns false. Override to return true when size() > maxCapacity — entry gets removed automatically."
      4. "Result: a self-maintaining LRU cache with O(1) get/put/evict."
      5. "Code: new LinkedHashMap<K, V>(capacity, 0.75f, true) { protected boolean removeEldestEntry(Map.Entry<K,V> eldest) { return size() > maxCapacity; } } "

      Edge cases to mention:

      • Not thread-safe — wrap with Collections.synchronizedMap if needed (or use Caffeine library for production)
      • For production use, Caffeine (W-TinyLFU eviction) is dramatically better than LRU for most access patterns
      • Guava's CacheBuilder is also an option but Caffeine has largely superseded it

      What NOT to say:

      • "Use HashMap + a separate list" — works but you have to maintain both manually, error-prone
      • "Just use Redis" — out-of-scope, interviewer wants a Java answer

      Common follow-up: "What if you needed time-based expiration in addition to LRU?"

      16. HashSet vs TreeSet vs LinkedHashSet

      Asked at: Fresher to mid-level

      Difficulty: Easy-Medium · Topic: Sets

      The question: "Compare HashSet, TreeSet, and LinkedHashSet."

      The 30-second answer: HashSet — hash-based, O(1) ops, no order. TreeSet — red-black tree, O(log n) ops, sorted order. LinkedHashSet — HashSet + linked list, O(1) ops, insertion order. Pick HashSet by default; TreeSet for sorted; LinkedHashSet when you want predictable iteration.

      Step-by-step thought process:

      1. "HashSet wraps a HashMap internally — your set elements are the keys, with a dummy constant value. O(1) average for add/remove/contains."
      2. "TreeSet wraps a TreeMap — same red-black tree, sorted order, O(log n) ops. Navigation methods (first, last, floor, ceiling, headSet, tailSet) available."
      3. "LinkedHashSet wraps LinkedHashMap — O(1) ops like HashSet, but iteration is in insertion order (or access order with the constructor flag)."
      4. "Memory: LinkedHashSet has overhead per element (linked list pointers); TreeSet has tree-node overhead; HashSet is lightest."
      5. "Default pick: HashSet. When you need sorted output: TreeSet. When you need stable iteration order (e.g. for testing, deterministic output): LinkedHashSet."

      Edge cases to mention:

      • HashSet allows one null; TreeSet doesn't (uses comparison)
      • All three require correctly-implemented equals()/hashCode() (HashSet/LinkedHashSet) or Comparable / Comparator (TreeSet)
      • EnumSet is a specialized, bitmap-based set for enums — dramatically faster than HashSet for enum values

      What NOT to say:

      • "TreeSet is faster because it's sorted" — wrong, log n > 1
      • "Use LinkedHashSet for thread safety" — none of these are thread-safe; use ConcurrentSkipListSet or CopyOnWriteArraySet

      Common follow-up: "How do you make any of these thread-safe?"

      17. Comparable vs Comparator

      Asked at: Common at all levels

      Difficulty: Easy-Medium · Topic: Sorting

      The question: "What's the difference between Comparable and Comparator? When would you use each?"

      The 30-second answer: Comparable is implemented BY the class itself — defines the class's natural ordering via compareTo(). Comparator is a separate object — defines an alternative ordering, useful when you don't own the class or need multiple orderings.

      Step-by-step thought process:

      1. " Comparable<T> has one method: int compareTo(T other). Returns negative if this < other, zero if equal, positive if this > other."
      2. "You implement Comparable on a class to give it a natural ordering — Integer compares numerically, String compares lexicographically, your Employee class might compare by ID."
      3. "Comparator is external. Useful when: (a) you don't control the class, (b) you need multiple different orderings (e.g. employees by name vs by salary), (c) you want ad-hoc sorting without modifying the class."
      4. "Java 8 made Comparators dramatically nicer: Comparator.comparing(Employee::getName).thenComparing(Employee::getSalary) chains naturally."
      5. " reversed(), nullsFirst(), nullsLast() are built-in modifiers."

      Edge cases to mention:

      • The contract: compare(a, b) and compare(b, a) must have opposite signs; transitive ordering required
      • TreeSet and TreeMap silently misbehave if your Comparable is inconsistent with equals
      • Modern Java preference: define Comparable for natural ordering, use Comparator factory methods for everything else

      What NOT to say:

      • "Comparable is for sorting, Comparator is for searching" — wrong, both are for ordering
      • Returning subtractions in compareTo (return this.value
      • other.value) — integer overflow risk; use Integer.compare() instead

      Common follow-up: "How would you sort a List of Employees by department, then by salary descending?"

      18. Queue vs Deque vs Stack

      Asked at: Common in mid-level rounds

      Difficulty: Medium · Topic: Collections

      The question: "When would you use a Deque vs a Queue vs a Stack in Java? Are Stack and Vector still relevant?"

      The 30-second answer: Stack and Vector are legacy — synchronized, slow, avoid. For LIFO (stack semantics), use Deque (ArrayDeque recommended). For FIFO (queue), use Queue interface with LinkedList or ArrayDeque. For concurrent queues, use BlockingQueue implementations like LinkedBlockingQueue or ArrayBlockingQueue.

      Step-by-step thought process:

      1. " Stack extends Vector — both are from Java 1.0, both fully synchronized (slow), both deprecated in spirit if not officially."
      2. "Modern preferred Stack: Deque<T> stack = new ArrayDeque<>(); then use push, pop, peek."
      3. "Modern preferred Queue: Queue<T> q = new ArrayDeque<>(); or new LinkedList<>();. Use offer, poll, peek."
      4. "For producer-consumer: BlockingQueue implementations — ArrayBlockingQueue (bounded), LinkedBlockingQueue (optionally bounded), PriorityBlockingQueue, SynchronousQueue. put / take block as needed."
      5. "For lock-free concurrent queues: ConcurrentLinkedQueue (unbounded), ConcurrentLinkedDeque."

      Edge cases to mention:

      • ArrayDeque is generally faster than LinkedList for both queue and stack ops (CPU cache locality)
      • PriorityQueue is a heap-backed priority queue — not FIFO, ordered by Comparator/Comparable
      • Java 21 added SequencedCollection interface — adds getFirst, getLast, addFirst, addLast, reversed() to ordered collections

      What NOT to say:

      • "Use Stack class for LIFO" — legacy, marks you as not following modern Java
      • "LinkedList is the best Deque" — ArrayDeque outperforms it for almost all access patterns

      Common follow-up: "How does BlockingQueue help in a producer-consumer setup?"

      19. Iterator vs ListIterator vs Spliterator

      Asked at: Mid-level rounds

      Difficulty: Medium · Topic: Iterators

      The question: "What's a Spliterator, and how is it different from a regular Iterator?"

      The 30-second answer: Iterator = sequential, forward-only, optional remove. ListIterator = bidirectional, can add/set/remove. Spliterator (Java 8+) = supports parallel processing via trySplit(), used internally by streams. It can describe characteristics of the underlying source (ORDERED, SIZED, IMMUTABLE, etc.) so the stream pipeline can optimize.

      Step-by-step thought process:

      1. "Iterator: hasNext, next, optional remove. One direction. Used by enhanced for-loop."
      2. "ListIterator (lists only): adds hasPrevious, previous, add, set, nextIndex, previousIndex. Bidirectional, mutating."
      3. "Spliterator: designed for parallel traversal. tryAdvance(action) processes one element. trySplit() returns a NEW Spliterator covering a portion of the source — the original now covers the rest."
      4. " characteristics() returns a bitmask: ORDERED, SIZED, SUBSIZED, IMMUTABLE, CONCURRENT, NONNULL, DISTINCT, SORTED. Stream operations check these to pick optimal execution strategies."
      5. "You rarely use Spliterator directly — Collection.stream() builds one for you. But if you write a custom collection, you might implement one to get good stream performance."

      Edge cases to mention:

      • Spliterator.estimateSize() returns the estimated element count if SIZED; otherwise an estimate
      • Custom Spliterators are essential for IO-bound or generator-style streams (e.g. wrapping BufferedReader.lines())
      • Stream.iterate(seed, hasNext, next) (Java 9+) is a friendlier way to build streams that previously needed custom Spliterators

      What NOT to say:

      • "Spliterator is just a parallel iterator" — incomplete; the characteristics flags are the real win
      • "Always use parallel streams for performance" — overhead often exceeds benefits for small or non-CPU-bound work

      Common follow-up: "When does parallelStream() actually outperform stream()?"

      20. Map.Entry, computeIfAbsent, and the Java 8 Map enhancements

      Asked at: Mid-level + senior rounds

      Difficulty: Medium · Topic: Collections + idiomatic Java

      The question: "What new methods were added to Map in Java 8, and when would you use computeIfAbsent over putIfAbsent?"

      The 30-second answer: Java 8 added getOrDefault, putIfAbsent, compute, computeIfAbsent, computeIfPresent, merge, replace, replaceAll, forEach. Use computeIfAbsent when you need to LAZILY compute the value (expensive call). Use putIfAbsent when you already have the value ready.

      Step-by-step thought process:

      1. " getOrDefault(key, default) — replaces the map.containsKey(k)? map.get(k): default pattern."
      2. " putIfAbsent(k, v) — puts only if key absent. Returns existing value if present, null otherwise."
      3. " computeIfAbsent(k, key -> expensiveCompute(key)) — same idea but the value is computed by a function ONLY if the key is absent. Avoids wasting work."
      4. " compute(k, (k, oldV) -> newV) — always invokes the function, even if oldV is null. Useful for counters: map.compute(word, (k, v) -> v == null? 1: v + 1)."
      5. " merge(k, value, BiFunction) — if absent, put value; if present, apply function to (oldValue, value). Cleanest counter increment: map.merge(word, 1, Integer::sum)."

      Edge cases to mention:

      • computeIfAbsent is atomic on ConcurrentHashMap — the function is invoked at most once per key
      • compute / merge returning null deletes the entry forEach((k, v) ->...) replaces the verbose entrySet().iterator() loop

      What NOT to say:

      • "putIfAbsent and computeIfAbsent are the same" — wrong; eager vs lazy value construction is the key distinction
      • "Just use containsKey + get" — works but slow on ConcurrentHashMap (two lookups) and not atomic

      Common follow-up: "How would you build a word-count Map with one line of Java?"
