    Lecture 06 — Circular Dependency in Spring

    17 sections · 5,100 words

    Lecture 06

    Scope evidence: "Circular Dependency in Spring | Bean Scope, Lazy & Eager Beans" (playlist map, verified). Repo lecture folder holds three demo Maven projects plus notes: BeanInitializationDemo (in.strikes.AppConfig, Main, OrderService, PaymentService), BeanScopeDemo (in.strikes.A, B, AppConfig, Main, OrderService, User), and CircularDependencyDemo (in.strikes.AppConfig, Main, OrderService, PaymentService, plus in.strikes.simple.A, simple.B). Coverage below = circular dependency, the early-reference idea, bean scopes, eager vs lazy initialization, and a brief bean lifecycle preview; the full lifecycle is Lecture 07.

    Two beans that need each other create the classic Spring startup deadlock, and the way out is not a trick but better design. Around that problem sit two everyday controls: bean scope decides how many objects Spring makes for a bean definition, and eager vs lazy decides when those objects appear. This lecture ties all three together: why constructor injection fails on a cycle, why setter/field injection can sometimes sneak through via an early reference, what Spring Boot does about it by default, and how @Lazy can break a constructor cycle when refactoring is not an option. The demo classes OrderService and PaymentService in CircularDependencyDemo are the running example.

    1. Quick Recap: DI, IoC, and Beans

    Before circular dependency, scope, or initialization, three ideas must be solid:

    Concept Meaning
    DI Dependency Injection. Spring provides the required dependency to a class instead of the class creating it manually.
    IoC Inversion of Control. Control of object creation and dependency management is given to the Spring container.
    Bean An object created, managed, and maintained by the Spring IoC container.

    A class becomes a bean when it carries one of the stereotype annotations and is picked up by component scanning:

    • @Component
    • @Service
    • @Repository
    • @Controller
    • or a method annotated with @Bean inside a configuration class.

    Important: DI, IoC, and beans are one story told from three angles. DI is the mechanism (who supplies the dependency), IoC is the direction of control (who owns creation), and a bean is the resulting managed object.

    2. @Configuration Is Also a Spring Component

    @Configuration marks a class as a source of bean definitions. A configuration class can hold @Bean methods that hand objects to the container:

    @Configuration
public class AppConfig {
    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}

    The important, often-missed point: @Configuration internally contains @Component. So a configuration class is itself detected by component scanning and registered as a Spring bean.

    @Configuration
    |
    v
@Component
    |
    v
Spring can detect and manage this class

    That is why configuration classes appear in the container and why they can be injected elsewhere, just like any other bean.

    3. Bean Creation Order: Why It Matters

    Spring does not create beans in a random order. It creates them based on their dependencies.

    Take this chain:

    OrderController depends on OrderService
OrderService depends on PaymentService
PaymentService depends on PaymentGateway

    Spring resolves the deepest dependency first:

    PaymentGateway
    |
    v
PaymentService
    |
    v
OrderService
    |
    v
OrderController

    In one sentence: Spring tries to create the dependency first, and then the class that depends on it. That rule is exactly what makes a cycle fatal, because in a cycle there is no "first" bean to create.

    4. What Is Circular Dependency? (and It Is Not Only a Spring Problem)

    Circular dependency means two or more classes depend on each other directly or indirectly.

    A needs B
B needs A

    Spring starts creating A, but to create A it needs B. It starts creating B, but to create B it needs A. The container is stuck in a loop:

    To create A, I need B.
To create B, I need A.
To create A, I need B.
...

    Spring normally relies on dependency order, but when that order becomes circular, there is no clear starting point. The note's example is exactly the OrderService / PaymentService pair.

    It is not only a Spring problem

    A plain Java constructor cycle produces the same failure with no Spring involved:

    // in.strikes.simple.A / simple.B - plain Java, no framework
public class A {
    private B b;
    public A() { this.b = new B(); }
}

public class B {
    private A a;
    public B() { this.a = new A(); }
}

    Calling new A() runs the A constructor, which calls new B(), which calls new A() again, forever. Java eventually throws StackOverflowError, because constructor calls keep stacking up.

    Golden rule: A circular dependency is a design problem first. Spring does not create it; Spring only exposes it during bean creation.

    5. Constructor Injection: Why It Fails, and Why It Is Still Recommended

    Constructor injection has one strict rule: an object cannot be created until all its constructor arguments are available.

    @Service
public class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

@Service
public class PaymentService {
    private final OrderService orderService;

    public PaymentService(OrderService orderService) {
        this.orderService = orderService;
    }
}

    To create OrderService, Spring must already have a PaymentService. To create PaymentService, Spring must already have an OrderService. There is no starting point, so the loop becomes:

    Create OrderService -> needs PaymentService
Create PaymentService -> needs OrderService
Create OrderService -> needs PaymentService
...

    Spring detects this at startup and throws BeanCurrentlyInCreationException. The application fails to start.

    Why constructor injection is still recommended

    Failing on a cycle is not a reason to abandon constructor injection. Its strength is that it makes dependencies clear and mandatory:

    @Service
public class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

    This code plainly says OrderService cannot exist without PaymentService. Field and setter injection leave that dependency optional-looking and hidden. So constructor injection is not the problem, the real problem is the circular design.

    Interviewer's perspective: The mature answer separates mechanism from cause. "Constructor injection fails on a cycle" is the mechanism; "the cycle is a design smell" is the cause. Candidates who only repeat the first half sound like they blame the tool.

    6. Setter and Field Injection: Why Circular May Sometimes Work

    Now rewrite the same pair with setter injection:

    @Service
public class OrderService {
    private PaymentService paymentService;

    @Autowired
    public void setPaymentService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

@Service
public class PaymentService {
    private OrderService orderService;

    @Autowired
    public void setOrderService(OrderService orderService) {
        this.orderService = orderService;
    }
}

    The key difference: with setters, object creation and dependency injection are separate steps. Spring can conceptually do this:

    Step 1: Create empty OrderService object
Step 2: Create empty PaymentService object
Step 3: Inject PaymentService into OrderService
Step 4: Inject OrderService into PaymentService

    Compare the two styles:

    Constructor injection:
Dependency must exist before object creation.

Setter injection:
Object can be created first.
Dependency can be injected later.

    Field injection works the same way. Spring creates the object first and injects the dependency later:

    @Service
public class OrderService {
    @Autowired
    private PaymentService paymentService;
}
    Injection style When the dependency arrives Circular dependency outcome
    Constructor Must exist before the object is built Fails with BeanCurrentlyInCreationException
    Setter After object creation, via a setter call May be resolved via an early reference
    Field After object creation, by direct field write May be resolved via an early reference

    Important: "May be resolved" is not the same as "good practice." Setter and field injection only mean Spring can handle some circular dependencies when object creation and dependency injection are separated.

    7. Early Reference and the Two Dependency Flows

    Why can setter/field injection sometimes work? Because the constructor does not require the dependency immediately. OrderService can be created even though PaymentService is not ready yet.

    Normal dependency flow

    Create B
Inject dependencies into B
Initialize B
B is ready
Create A
Inject B into A
Initialize A
A is ready

    In a normal dependency, the dependent bean receives a fully created and initialized dependency.

    Circular flow with an early reference

    A needs B
B needs A

    Spring may create one object first and expose an early reference to it:

    A a = new A();
// A exists, but dependencies are not injected yet

B b = new B();
// B exists

b.setA(a);
// B receives the early reference of A

a.setB(b);
// A receives B

    An early reference means Spring exposes a reference of a bean before that bean is fully initialized, so another bean can temporarily use it while the cycle is resolved.

    I have created OrderService object,
but it is not fully initialized yet.
Still, I can keep an early reference to it.
Now I create PaymentService.
PaymentService needs OrderService.
I can give it the early reference of OrderService.
Then I come back and inject PaymentService into OrderService.

    Interviewer's perspective: The interview-grade phrase is "the container separates instantiation from population." In setter/field injection a bean can be instantiated, exposed early, and populated afterwards, which is exactly what breaks the strict constructor ordering.

    8. Spring Boot Point, the Design Smell, and the Best Fix

    Spring Boot disables circular references by default

    The Spring Framework has internal mechanisms to resolve some setter- or field-based circular dependencies. Spring Boot, however, discourages them. From Spring Boot 2.6 onward, circular references are disabled by default:

    spring.main.allow-circular-references=false

    The default value is false. You can technically turn it back on:

    spring.main.allow-circular-references=true

    But this should not be treated as the solution. The better answer is to improve the design.

    Circular dependency usually signals mixed responsibilities

    A cycle is usually not only a technical issue; it often shows that responsibilities are not clearly separated. Ask:

    1. Why does A need B?
    2. Why does B also need A?
    3. Are both classes doing too much?
    4. Can we move common logic to a third class?
    5. Can one dependency direction be removed?

    If OrderService and PaymentService depend on each other, order logic and payment logic may be mixed. Better shapes might be:

    OrderService -> PaymentService

or

OrderService -> PaymentService
PaymentService -> PaymentStatusRepository

or

OrderService -> PaymentProcessor
PaymentService -> PaymentProcessor

    The best way to solve it

    The best solution is refactoring:

    Problem Better design
    Two services call each other Move shared logic to a third service
    One service has too many responsibilities Split responsibilities
    Both classes depend on each other's internal behavior Introduce an interface or event-based communication
    Service does orchestration and business logic together Create a separate coordinator/orchestrator class

    Golden rule: Avoid circular dependency by designing clear responsibility boundaries. The framework flags the symptom; you fix the design.

    9. Bean Scope: Singleton and Prototype

    Bean scope answers two questions:

    1. How many objects will Spring create for one bean definition?
    2. How long will those objects live?

    The two core scopes are singleton and prototype. Web applications add request, session, application, and websocket.

    Singleton scope

    Singleton scope means Spring creates exactly one object for a bean definition inside the container, stores it, and returns the same object whenever it is needed. It is the default:

    @Component
public class PaymentService { }

    is the same as:

    @Component
@Scope("singleton")
public class PaymentService { }

    We usually do not write @Scope("singleton") explicitly.

    Demo behavior (from BeanScopeDemo):

    PaymentService p1 = context.getBean(PaymentService.class);
PaymentService p2 = context.getBean(PaymentService.class);
System.out.println(p1 == p2);   // true

    Both references point to the same Spring-managed singleton bean.

    Prototype scope

    Prototype scope means Spring creates a new object every time the bean is requested from the container.

    @Component
@Scope("prototype")
public class OrderRequest {
    public OrderRequest() {
        System.out.println("OrderRequest object created");
    }
}

    OrderRequest r1 = context.getBean(OrderRequest.class);
OrderRequest r2 = context.getBean(OrderRequest.class);
System.out.println(r1 == r2);   // false

    Each request gives a new object. Prototype feels closer to manual new:

    context.getBean(OrderRequest.class) -> new object
context.getBean(OrderRequest.class) -> new object
context.getBean(OrderRequest.class) -> new object

    But the object is still created by Spring, not manually by us.

    Choosing a scope

    Scope Best for
    Singleton Stateless beans that provide behavior
    Prototype Stateful beans that store changing data

    Services are usually singleton because they hold behavior, not user-specific data: processPayment(), validateOrder(), sendEmail(), calculateDiscount(). These methods can be reused safely. Prototype fits cases where each request needs a fresh object with its own state, such as OrderRequest.

    Mnemonic: singleton beans are Eager and stateless by intent; prototype beans are Lazy and stateful by intent (remember E-L).

    10. Singleton Per Bean Definition, the Prototype Gotcha, and Web Scopes

    Singleton is per bean definition, not per class

    Spring singleton does not mean only one object of this class can ever exist in the JVM. You can still write new PaymentService() yourself; that object is simply not managed by Spring. The precise meaning is: inside this Spring container, for this bean definition, Spring keeps one shared object.

    Consider two @Bean methods returning the same type:

    @Bean
public User createUser() {
    return new User();
}

@Bean
public User createUser2() {
    return new User();
}

    Spring creates two different bean definitions, createUser and createUser2. Both are singleton by default, so Spring creates one User object per definition:

    2 bean definitions
2 singleton objects

    In Spring, singleton means one object per bean name / bean definition inside the container, not one object per class. This is different from the classic Singleton design pattern.

    Important: If someone asks "is Spring's singleton the same as the Singleton Design Pattern?", the answer is no. Spring's singleton is scoped to the container and to the bean definition, and per-definition duplicates are allowed.

    Prototype bean injected into a singleton

    Common trap: if you inject a prototype bean into a singleton bean, does the singleton get a new prototype object every time? No.

    @Service
public class OrderService {
    private final OrderRequest orderRequest;

    public OrderService(OrderRequest orderRequest) {
        this.orderRequest = orderRequest;
    }
}

    If OrderService is singleton and OrderRequest is prototype, Spring injects one OrderRequest when OrderService is created. After that, the same reference stays inside the singleton.

    Prototype does not mean:

    new object every time a singleton method runs

    It means:

    new object every time the prototype bean is requested from the container

    Web scopes

    Scope One object for
    request One HTTP request
    session One user session
    application One ServletContext / whole web application
    websocket One WebSocket session

    These scopes are available only in a web-aware Spring ApplicationContext. For beginner Spring MVC or Spring Boot Web, the most important are request, session, and application:

    • Request scope: one bean object per HTTP request; request 1 and request 2 get different beans. Useful when data should live only during one request.
    • Session scope: one bean object per user session; user A and user B get different beans. Useful for user-specific session data.
    • Application scope: one bean object for the entire web application, tied to the ServletContext and shared across it.

    Mnemonic for scopes: Singleton and Prototype live in core; Request, Session, Application, Websocket need the web (SP-RSAW).

    11. Bean Initialization: Eager, Lazy, @Lazy, Global Lazy, and Bean Lifecycle

    Spring must answer one question for every bean: when should I create this bean?

    Initialization type Meaning
    Eager initialization Create the bean during application startup
    Lazy initialization Create the bean only when it is actually needed

    By default: singleton beans are eagerly initialized; prototype beans are created lazily, when requested. Lazy initialization can also be enabled with @Lazy.

    Eager initialization and why it is the default

    Eager initialization means Spring creates the bean as soon as the application context starts. It is the default for singleton beans.

    @Component
public class PaymentService {
    public PaymentService() {
        System.out.println("PaymentService object created");
    }
}

    At first eager initialization looks wasteful ("why create everything if the user may not use it?"), but it buys one big advantage: fail fast. If a bean has a configuration issue, missing dependency, or invalid setup, the application fails during startup instead of succeeding and then failing only when the first user hits that feature. Eager initialization gives fast failure, early error detection, and predictable startup validation.

    Lazy initialization

    Lazy initialization means: do not create the bean at startup; create it only when someone actually asks for it.

    @Component
@Lazy
public class ReportService {
    public ReportService() {
        System.out.println("ReportService object created");
    }

    public void generateReport() {
        System.out.println("Report generated");
    }
}

    Spring knows about ReportService but does not immediately create the object; it only keeps the bean definition, which contains information such as:

    • class name
    • bean name
    • scope
    • dependencies
    • lifecycle details

    The object is created only when requested:

    ReportService reportService = context.getBean(ReportService.class);
reportService.generateReport();

    Order of output:

    Application started
ReportService object created
Report generated

    A lazy bean needed by an eager bean

    If a lazy bean is required by an eager singleton bean, the lazy bean may still be created at startup, because Spring must satisfy the dependencies of the eager singleton. If UserService is eager and needs ReportService, Spring has to provide ReportService while creating UserService. Unless @Lazy is used at the injection point, where Spring can inject a proxy instead.

    Lazy injection using a proxy

    Instead of making the whole bean lazy, you can mark the injection point as lazy:

    @Component
public class UserService {
    private final EmailService emailService;

    public UserService(@Lazy EmailService emailService) {
        this.emailService = emailService;
        System.out.println("UserService created");
    }

    public void registerUser() {
        System.out.println("User registered");
        emailService.sendEmail();
    }
}

    Spring does not inject the real EmailService immediately. It injects a proxy, a placeholder that looks like EmailService. When a method is actually called on it, Spring creates or fetches the real bean.

    Startup output:

    UserService created
Application started

    Later, when emailService.sendEmail() runs:

    User registered
EmailService created
Email sent

    Bean-level @Lazy vs injection-point @Lazy

    Usage Meaning
    @Lazy on the class Do not create this bean until it is requested
    @Lazy on the injection point Inject a proxy and resolve the real dependency only when it is used 
    @Component
@Lazy
public class ReportService {
}

    public UserService(@Lazy EmailService emailService) {
    this.emailService = emailService;
}

    Global lazy initialization and opting out

    Spring Boot can make the whole application lazy:

    spring.main.lazy-initialization=true

    In YAML:

    spring:
  main:
    lazy-initialization: true

    This means beans are created only when needed, which can reduce startup time. The trade-off: misconfiguration errors may be discovered later, only when the lazy bean is initialized. By default:

    spring.main.lazy-initialization=false

    If global lazy initialization is enabled, a particular bean can still be forced eager:

    @Component
@Lazy(false)
public class ImportantStartupBean {
}

    Lazy/eager dependency combinations

    1. Eager bean depends on lazy bean. Spring may still create the lazy dependency at startup to satisfy the eager bean, unless @Lazy is used at the injection point so a proxy is injected instead.
    2. Lazy bean depends on eager bean. The eager dependency is usually created during startup; the lazy bean is created when needed, and Spring injects the already-created eager dependency into it.
    3. Lazy bean depends on lazy bean. Neither is created at startup. When the first is requested, Spring creates it; if it directly needs the second, Spring may create the second at that time as well. If @Lazy is on the injection point, Spring may inject a proxy and delay the real dependency until a method is called.

    Breaking a constructor circular dependency with @Lazy

    @Lazy can break a constructor cycle by injecting a proxy instead of the real object:

    // CircularDependencyDemo - proxy at the injection point breaks the cycle
@Service
public class OrderService {
    private final PaymentService paymentService;

    public OrderService(@Lazy PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

@Service
public class PaymentService {
    private final OrderService orderService;

    public PaymentService(OrderService orderService) {
        this.orderService = orderService;
    }
}

    Here Spring does not need to create the real PaymentService immediately while creating OrderService; it injects a proxy, and the real PaymentService is resolved later when actually used.

    Warning: @Lazy is a workaround

    Using @Lazy to solve circular dependency should be treated as a workaround, not the best design. Use it only when:

    • you understand the dependency flow clearly;
    • refactoring is not immediately possible;
    • you are dealing with legacy code;
    • you want a temporary solution.

    The best long-term solution is to fix the design, separate responsibilities, and remove the circular dependency.

    Bean lifecycle: a brief look ahead

    Bean lifecycle means the complete journey of a Spring bean: discovery, creation, dependency injection, initialization, use, and destruction.

    Bean Definition
    |
    v
Object Creation
    |
    v
Dependency Injection
    |
    v
Initialization
    |
    v
Ready to Use
    |
    v
Destruction

    Six steps at a glance: a bean definition is created (discovery via @Component types, XML, or a @Bean method, storing name, class, scope, dependencies, lazy/eager behavior, and lifecycle methods); the object is created via its constructor; dependencies are injected; initialization logic runs (@PostConstruct, InitializingBean, or a custom init method) for validation, opening resources, loading data, and checking fields; the bean is ready to use; and on container shutdown singleton beans are destroyed (@PreDestroy, DisposableBean, or a custom destroy method) to close resources and stop background tasks. For prototype beans, Spring creates the object and injects dependencies, but it does not fully manage the destruction lifecycle the way it does for singletons. This is only a preview; the full treatment is Lecture 07.

    12. Myth vs Reality

    Myth Reality
    "Circular dependency is a Spring-only problem" It exists in plain Java too; two constructors calling each other end in StackOverflowError. Spring merely exposes it at startup.
    "Constructor injection is bad because it fails on cycles" Constructor injection is preferred; it makes dependencies clear and mandatory. The cycle is the real defect, not the injection style.
    "Setter/field injection fixes circular dependencies" It may let Spring resolve some cycles via an early reference, but that is not a license to keep a bad design.
    "Enabling allow-circular-references is the solution" It is a technical escape hatch. The correct solution is to refactor responsibilities.
    "Spring singleton means one object per class in the JVM" It means one object per bean definition inside the container; manual new objects and duplicate bean definitions are still possible.
    "A prototype injected into a singleton becomes new on every call" The singleton receives one prototype instance at creation and keeps that same reference.
    "Eager initialization is wasteful, so Spring avoids it" Eager is the default for singletons because failing fast at startup beats failing when the first user hits a feature.
    "Marking a bean @Lazy guarantees it is never created at startup" If an eager singleton depends on it, Spring may still create it at startup unless @Lazy is placed on the injection point.

    13. Common Trap Questions

    Trap 1 — "Circular dependency is only a Spring problem." Verdict: False. Plain Java shows the same failure as unbounded constructor recursion ending in StackOverflowError; Spring just detects it during bean creation.

    Trap 2 — "Constructor injection is wrong because it cannot handle cycles." Verdict: False. Constructor injection is still the recommended style because it makes dependencies explicit and mandatory. The circular design is what is wrong.

    Trap 3 — "Setter/field injection permanently solves circular dependency." Verdict: Misleading. It may let Spring resolve some cases through an early reference, but circular dependency remains a design smell that should be refactored away.

    Trap 4 — "Since Spring Boot 2.6 circular references still work by default." Verdict: False. From Spring Boot 2.6 onward circular references are disabled by default (spring.main.allow-circular-references=false).

    Trap 5 — "Spring singleton equals the Singleton Design Pattern." Verdict: False. Spring keeps one object per bean definition inside the container; two bean definitions of the same class produce two singleton objects, and manual new still works.

    Trap 6 — "A prototype bean injected into a singleton is fresh on every method call." Verdict: False. The prototype is resolved once, when the singleton is created, and that same reference is reused.

    Trap 7 — "@Lazy always prevents a bean from being created at startup." Verdict: False. An eager singleton that directly depends on a lazy bean can force its creation at startup unless @Lazy is applied at the injection point (proxy).

    14. Points to Remember

    1. DI supplies dependencies, IoC hands control of creation to the container, and a bean is the managed object; @Configuration is itself a @Component.
    2. Spring creates beans in dependency order; a circular dependency removes any starting point and stalls the container.
    3. Circular dependency is a design problem, not a framework defect; plain Java shows it as StackOverflowError.
    4. Constructor injection fails on a cycle because all constructor arguments must exist before the object is built, giving BeanCurrentlyInCreationException.
    5. Constructor injection is still preferred because dependencies become clear and mandatory; the cycle, not the style, is the defect.
    6. Setter and field injection separate creation from injection, so Spring may resolve some cycles by exposing an early reference before full initialization.
    7. Spring Boot disables circular references by default (spring.main.allow-circular-references=false); the real fix is refactoring into clear responsibilities.
    8. Singleton scope means one object per bean definition inside the container (not per class); prototype scope means a new object every time the bean is requested.
    9. Web scopes request, session, and application live only in a web-aware context; a prototype injected into a singleton is resolved once and reused.
    10. Eager initialization (default for singletons) creates beans at startup for fail-fast validation; lazy initialization delays creation, and @Lazy on an injection point injects a proxy that resolves the real bean on first use.

    15. Likely Interview Questions

    Question Crisp Answer
    What is circular dependency? Two or more beans depend on each other directly or indirectly, so Spring cannot find a valid creation order.
    Why does constructor injection fail on a cycle? An object cannot be created until all constructor arguments exist, so neither bean can be built first; startup throws BeanCurrentlyInCreationException.
    Why is constructor injection still recommended? It makes dependencies explicit and mandatory; the failure exposes a design problem, it is not a reason to abandon the style.
    Why can setter/field injection sometimes work? Creation and injection are separate steps, so Spring can expose an early reference to a partially initialized bean and finish wiring later.
    What is an early reference? A reference Spring exposes before a bean is fully initialized so another bean can temporarily use it during circular resolution.
    What does Spring Boot do about circular references? It discourages them; since Spring Boot 2.6 they are disabled by default via spring.main.allow-circular-references=false.
    What is the best way to solve a circular dependency? Refactor: move shared logic to a third service, split responsibilities, use an interface or events, or add a coordinator class.
    Singleton vs prototype? Singleton: one object per bean definition inside the container (default). Prototype: a new object on every request to the container.
    Is Spring singleton the same as the Singleton pattern? No; it is one object per bean definition inside the container, not one object per class in the JVM.
    What happens when a prototype is injected into a singleton? The singleton gets one prototype instance at creation and keeps that same reference afterwards.
    What is the difference between eager and lazy initialization? Eager creates the bean at startup (default for singletons) for fail-fast validation; lazy creates it only when needed.
    What does @Lazy on an injection point do? Injects a proxy and resolves the real dependency only when a method is called, which can break a constructor cycle.
