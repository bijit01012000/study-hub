    Lecture 30 — JPA Relationships

    17 sections · 4,452 words

    Lecture 30

    Scope evidence: "JPA Relationships | @OneToMany, @ManyToOne, @OneToOne & @ManyToMany" (playlist map, verified). Repo folder is the jpaRelationshipDemo project (package com.coderarmy.jpaRelationshipDemo): model.Student, model.Department, model.Profile, model.Course, model.User, model.Student2 covering the four relationship types, with repository.StudentRepository / repository.DepartmentRepository, service.StudentService / service.DepartmentService, controller.StudentController / controller.DepartmentController, plus the lecture notes.

    Java connects objects with references; a relational database connects rows with foreign keys. JPA relationship mapping is the layer that translates one into the other, and every annotation in this lecture (@ManyToOne, @OneToMany, @OneToOne, @ManyToMany) is one rule about how that translation is performed. The lecture moves from the fundamental problem, through cardinality, navigation direction and ownership, into each concrete mapping, the helper methods that keep both sides consistent, and the Lombok traps that break otherwise correct entities.

    1. The Fundamental Problem and Entity Relationships

    Start with a plain Java model:

    class Student {
    Long id;
    String name;
    Department department;   // an object reference
}

    Here student.getDepartment() returns a live reference to a Department object. A relational database cannot place a Java object inside a column, so it represents the same fact with a foreign key:

    students                          departments
------------------------------    ----------------
id | name  | department_id        id | name
------------------------------    ----------------
1  | Rahul | 10                   10 | Engineering
2  | Aman  | 10                   20 | HR
3  | Priya | 20

    So the Java relationship student.department must become students.department_id -> departments.id. Relationship mapping is exactly the configuration that tells JPA how an object reference should be represented in the database.

    Without ORM, a class might only store the raw key:

    @Entity
class Student {
    @Id private Long id;
    private String name;
    private Long departmentId;   // foreign key copied in by hand
}

    With JPA, the object model can hold a real entity reference instead:

    @Entity
class Student {
    @Id private Long id;
    private String name;

    @ManyToOne
    private Department department;   // Hibernate turns this into the FK value
}

    Hibernate then converts the entity reference into the required SQL and foreign-key value.

    The second idea is that real applications are not sets of isolated objects. They are a graph of connected objects, and those connections are called relationships or associations:

    • Student has a Department.
    • Order has a List<OrderItem> items.
    • Employee has an Employee manager (self-reference).
    • User has a Profile.

    Important: The database never sees a graph. It only sees tables, rows, foreign keys and join tables. Relationship mapping is the complete set of instructions that compiles the Java graph down to that relational shape.

    2. Relationship Cardinality

    Cardinality answers one question: how many entities on one side can be associated with how many entities on the other side? JPA supports four basic cardinalities.

    Relationship Meaning Common example Annotation
    One-to-One One entity is associated with one other entity User and Profile @OneToOne
    One-to-Many One entity is associated with many entities Department and Students @OneToMany
    Many-to-One Many entities are associated with one entity Students and Department @ManyToOne
    Many-to-Many Many entities on both sides can be associated Students and Courses @ManyToMany

    The single most important sentence in this lecture:

    Golden rule: One-to-many and many-to-one are two views of the same relationship. The database does not create two separate relationships; both directions normally describe the same foreign key students.department_id.

    Suppose the Engineering department contains three students:

    Engineering
  |- Rahul
  |- Aman
  `- Priya

    From the department's perspective this is One Department -> Many Students, which is @OneToMany. From a student's perspective this is Many Students -> One Department, which is @ManyToOne. Same three rows, same foreign key, two Java viewpoints.

    Interviewer's perspective: Candidates often treat @OneToMany and @ManyToOne as separate database relationships and worry that a bidirectional mapping "duplicates" data. It does not. There is one foreign key column; the two annotations are two navigation handles onto it.

    3. Unidirectional vs Bidirectional Relationships

    These terms describe navigation in the Java object model. They do not describe how many directions SQL can query; SQL can always join either way.

    Unidirectional means only one entity contains a reference to the other:

    class Student {
    Department department;
}

class Department {
}

    You can navigate student.getDepartment(), but department.getStudents() does not exist because there is no such field. The direction is Student -> Department.

    Bidirectional means both entities contain a reference to the other:

    class Student {
    Department department;
}

class Department {
    List<Student> students;
}

    Now both student.getDepartment() and department.getStudents() work. The direction is Student <-> Department.

    Aspect Unidirectional Bidirectional
    References present One side only Both sides
    Java navigation Single direction Both directions
    Database relationships One (FK or join table) Still one
    Foreign keys in the example students.department_id students.department_id (same one)
    Extra responsibility None Both sides must be synchronized in Java

    A bidirectional mapping still represents one database relationship. In the example there is still only one foreign key: students.department_id.

    Bidirectional fields do not synchronize themselves:

    student.setDepartment(engineering);          // updates Student only
engineering.getStudents().add(student);      // must be called separately

    Calling the first statement does not automatically execute the second. It is therefore possible to create an inconsistent in-memory object graph:

    student.department = Engineering
engineering.students = []

    The application must keep both sides synchronized.

    Important: A bidirectional relationship is a convenience for navigation, not a guarantee of consistency. If you only set one side, you own that bug.

    4. Owning Side vs Inverse Side (mappedBy)

    When the same database relationship is mapped on two entities, JPA needs one authoritative side. The owning side is the side JPA uses to determine the database value of the relationship. The inverse side provides the opposite navigation path but does not independently control the same relationship.

    For a department-student relationship, this field makes Student the owning side:

    @ManyToOne
@JoinColumn(name = "department_id")
private Department department;

    It owns the relationship because changing student.setDepartment(department) changes students.department_id. On the other side:

    @OneToMany(mappedBy = "department")
private List<Student> students = new ArrayList<>();

    Here Department.students is the inverse side. mappedBy = "department" refers to the name of the Java field in Student; it does not refer to the database column department_id.

    Owning side does NOT mean:

    • the parent entity;
    • the more important entity;
    • the entity that conceptually contains the other entity.

    It means only that this side controls the database representation of the relationship. For database relationship updates, the owning side is authoritative.

    Aspect Owning Side Inverse Side
    Controls the DB value Yes No
    Typical marker @JoinColumn (or @JoinTable) mappedBy = "..."
    mappedBy target Not used A Java field name, never a column
    In dept-student example Student.department Department.students
    Changing it updates FK Yes Only after the owning side changes too

    Mnemonic: the side that holds the column holds the truth; the mappedBy side is only a mirror.

    Interviewer's perspective: "Which side is the owner?" is almost always answered by pointing at the @JoinColumn or @JoinTable, not at the entity that seems more important. mappedBy on an entity is the tell that it is the inverse side.

    5. Many-to-One Mapping (@ManyToOne)

    Many students can belong to one department: Student N -> 1 Department.

    Database design: students.department_id is a foreign key referencing departments.id. Multiple student rows may contain the same department ID, and that repetition is what creates the many-to-one relationship.

    Mapping with @ManyToOne:

    // model/Student.java -- the many side owns the foreign key
@Entity
public class Student {
    @Id
    @GeneratedValue
    private Long id;
    private String name;

    @ManyToOne(optional = false)                    // required relationship
    @JoinColumn(name = "department_id", nullable = false)
    private Department department;                  // owning side
}

    @ManyToOne tells JPA that the field references another entity and that many Student entities may reference the same Department. @JoinColumn specifies the foreign-key column used to store the relationship:

    • Student.department -> students.department_id
    • By default the join column references the primary key of the target entity.

    If engineering.getId() == 5L and student.setDepartment(engineering) runs, the database relationship becomes students.department_id = 5.

    Nullable and mandatory relationships:

    • If a student may exist without a department, the foreign key may be NULL (the default mapping permits this).
    • If every student must belong to a department, use both settings:
    @ManyToOne(optional = false)
@JoinColumn(name = "department_id", nullable = false)
private Department department;

    The two settings express the same rule at different layers:

    Setting Layer Meaning
    optional = false JPA object/persistence model The association is required
    nullable = false Generated database schema The foreign-key column must be NOT NULL

    Important: optional = false is a JPA-model rule; nullable = false is a schema rule. Declaring both keeps the in-memory contract and the generated DDL consistent instead of validating only one of them.

    6. One-to-Many Mapping (@OneToMany) and Helper Methods

    @OneToMany represents the same department-student relationship from the department side: Department 1 -> N Students. No additional foreign key is required; all three students simply share department_id = 10, and the collection in Department is an object-side view of those rows.

    Mapping with @OneToMany:

    @Entity
class Department {
    @Id
    private Long id;
    private String name;

    @OneToMany(mappedBy = "department")
    private List<Student> students = new ArrayList<>();
}

    mappedBy = "department" refers to the Java field name in Student, not the column name department_id. The meaning is: Department.students is the inverse view of the relationship owned by Student.department.

    The complete bidirectional mapping pairs the two annotations:

    @Entity
class Student {
    @ManyToOne
    @JoinColumn(name = "department_id")
    private Department department;
}

@Entity
class Department {
    @OneToMany(mappedBy = "department")
    private List<Student> students = new ArrayList<>();
}

    This creates two Java navigation paths, student.getDepartment() and department.getStudents(), and both describe the same foreign key students.department_id.

    Maintaining both sides is the responsibility of application code. student.setDepartment(engineering) updates only the Student object; the department collection must also be updated with engineering.getStudents().add(student). For removal, both engineering.getStudents().remove(student) and student.setDepartment(null) must run.

    Relationship helper methods place that synchronization inside the entity instead of repeating it everywhere:

    // model/Department.java -- inverse side plus synchronization helpers
@Entity
public class Department {
    @Id
    @GeneratedValue
    private Long id;
    private String name;

    @OneToMany(mappedBy = "department")             // "department" is Student's field
    private List<Student> students = new ArrayList<>();

    public void addStudent(Student student) {
        students.add(student);
        student.setDepartment(this);                // keep the owning side in sync
    }

    public void removeStudent(Student student) {
        students.remove(student);
        student.setDepartment(null);
    }
}

    The application can now call engineering.addStudent(rahul) and engineering.removeStudent(rahul), and both sides stay consistent.

    Collection dirty checking: Hibernate can detect changes made to a managed relationship collection, for example department.getStudents().remove(student) on a managed Department. However, detecting a collection change is not the same as deciding which side controls the foreign key. Because Department.students uses mappedBy, it is the inverse side, and the owning side must also be changed with student.setDepartment(null). That is precisely why helper methods matter.

    Important: Mutating the inverse collection alone is dangerous. Hibernate may notice the collection changed but the owning side still points at the old value, so the foreign key does not move. Always change the owning side and let the helper update the inverse.

    7. One-to-One Mapping (@OneToOne)

    A one-to-one relationship means each entity can be associated with at most one entity on the other side: User 1 <-> 1 Profile.

    A foreign key alone does not guarantee one-to-one. Without a uniqueness constraint, the database could allow several profile rows pointing at user 1, which would mean one user has many profiles. The usual relational representation is:

    Foreign key + unique constraint

    Mapping with @OneToOne:

    @Entity
class Profile {
    @Id
    @GeneratedValue
    private Long id;
    private String bio;

    @OneToOne
    @JoinColumn(name = "user_id", unique = true)
    private User user;
}

    The essential database difference between many-to-one and one-to-one is uniqueness:

    Mapping Foreign key Uniqueness
    Many-to-one Present Repeated values allowed
    One-to-one Present Foreign-key value must be unique

    Owning and inverse sides: Profile is the owning side because it contains the join column. The inverse side in User is:

    @Entity
class User {
    @OneToOne(mappedBy = "user")
    private Profile profile;
}

    Here "user" refers to Profile.user, so Profile.user is the owning side and User.profile is the inverse side.

    If a profile must always belong to a user:

    @OneToOne(optional = false)
@JoinColumn(name = "user_id", nullable = false, unique = true)
private User user;

    Shared primary-key mapping: some one-to-one entities cannot exist independently, and a profile can use the same identifier as its user. Then the profiles.id column acts as both the primary key of Profile and a foreign key referencing users.id. JPA models this with @MapsId:

    // model/Profile.java -- shared primary key with User
@Entity
public class Profile {
    @Id
    private Long id;
    private String bio;

    @OneToOne(optional = false)
    @MapsId                                         // Profile.id = User.id
    @JoinColumn(name = "id")
    private User user;
}

    @MapsId means the associated user's ID is also used as the profile's ID. This mapping is useful when the dependent entity has no meaningful identity or lifecycle without its parent.

    8. Many-to-Many Mapping (@ManyToMany)

    A many-to-many relationship allows multiple entities on each side to be connected: Student N <-> N Course. A student can enroll in many courses, and a course can contain many students.

    Neither table can represent the relationship with one foreign-key column, so a third table is required:

    student_course
----------------------
student_id | course_id
----------------------
1          | 101
1          | 102
2          | 101
2          | 103

    Each row represents one association between one student and one course. This middle table is called a join table, association table, or junction table. It contains two foreign keys, student_id -> students.id and course_id -> courses.id, and the pair (student_id, course_id) should normally be unique so the same enrollment cannot be inserted twice.

    Owning side with @JoinTable:

    // model/Student.java -- owning side of the many-to-many
@ManyToMany
@JoinTable(
    name = "student_course",
    joinColumns = @JoinColumn(name = "student_id"),
    inverseJoinColumns = @JoinColumn(name = "course_id"),
    uniqueConstraints = @UniqueConstraint(columnNames = {"student_id", "course_id"})
)
private Set<Course> courses = new HashSet<>();

// model/Course.java -- inverse side
@ManyToMany(mappedBy = "courses")
private Set<Student> students = new HashSet<>();

    @JoinTable describes the middle table:

    Attribute Meaning
    name Name of the join table
    joinColumns Foreign key pointing to the owning entity
    inverseJoinColumns Foreign key pointing to the other entity

    Student.courses is the owning side. Changes to this collection control rows in student_course, so student.getCourses().add(javaCourse) can make Hibernate insert INSERT INTO student_course (student_id, course_id) VALUES (1, 101). On the inverse side, mappedBy = "courses" points to the courses field in Student, giving Student.courses -> Owning side and Course.students -> Inverse side.

    The mapping creates two Java navigation paths, student.getCourses() and course.getStudents(), and both represent rows in the same student_course table.

    Maintaining both sides: adding a course to only one collection leaves the in-memory model inconsistent. Use helper methods:

    public void addCourse(Course course) {
    courses.add(course);
    course.getStudents().add(this);
}

public void removeCourse(Course course) {
    courses.remove(course);
    course.getStudents().remove(this);
}

    Now student.addCourse(course) and student.removeCourse(course) keep both sides synchronized.

    Important: Unlike @OneToMany, the inverse @ManyToMany side has no foreign key to fix up, but it still has a collection to keep consistent. Helper methods are the only reliable way to do that.

    9. Lombok with JPA Entities

    Lombok removes boilerplate from entities, but it also generates methods you may not want on them.

    Annotation Generated code
    @Getter Getter methods
    @Setter Setter methods
    @NoArgsConstructor Constructor without parameters
    @AllArgsConstructor Constructor containing all fields
    @RequiredArgsConstructor Constructor for final and @NonNull fields
    @Builder Builder-pattern API

    Be careful with @Data on JPA entities. In addition to getters and setters, it generates toString(), equals() and hashCode(). When relationships are bidirectional, generated methods may:

    • recursively move from one entity to the other;
    • trigger lazy relationship loading unexpectedly;
    • cause a StackOverflowError;
    • produce unstable equality or hash-code behaviour for entities;
    • compare large relationship collections.

    For JPA entities, explicit Lombok annotations are usually safer:

    @Getter
@Setter
@NoArgsConstructor
@Entity
public class Student {
    // fields
}
    Aspect @Data on an entity Explicit @Getter / @Setter
    Getters and setters Generated Generated
    toString() Generated, walks relationships Not generated
    equals() / hashCode() Generated, id and relationship risk Not generated
    Bidirectional recursion Possible, can StackOverflowError Avoided
    Lazy loading side effects Can trigger on access Controlled
    Recommended for entities No Yes

    If toString(), equals() or hashCode() is generated, relationship fields should generally be excluded and entity identity should be designed deliberately.

    Interviewer's perspective: "Why not @Data on an entity?" The expected answer names the bidirectional recursion, the lazy-loading side effect, and the unstable equals() / hashCode() for entities. "Because Lombok is bad" is not the answer; the problem is specifically which methods @Data adds to relationship-bearing classes.

    10. Relationship Lifecycle: Insert, Update, Dirty Checking, and Cascading

    Setting an entity reference and managing the lifecycle of the referenced entity are separate concerns.

    If the department already exists, Hibernate stores its identifier as the foreign key instead of inserting the department again:

    Department department = entityManager.find(Department.class, 1L);

Student student = new Student();
student.setName("Rahul");
student.setDepartment(department);
entityManager.persist(student);

    Hibernate logically executes INSERT INTO students (name, department_id) VALUES ('Rahul', 1).

    If both entities are new, then without cascading they must be persisted explicitly in the correct lifecycle order:

    Department department = new Department();
department.setName("Engineering");

Student student = new Student();
student.setName("Rahul");
student.setDepartment(department);

entityManager.persist(department);
entityManager.persist(student);

    With cascade persist, persisting the student can also persist the new department:

    @ManyToOne(cascade = CascadeType.PERSIST)
private Department department;

    Update behaviour and dirty checking: suppose Rahul currently has department_id = 10. Changing the department of a managed student,

    Department hr = entityManager.find(Department.class, 20L);
student.setDepartment(hr);

    changes the relationship from department 10 to 20. During flush, Hibernate can issue:

    UPDATE students
SET department_id = 20
WHERE id = 1;

    This is relationship dirty checking.

    Important: Setting an entity reference does not automatically persist the referenced entity. Cascading controls lifecycle propagation; it does not define relationship ownership. Two different concerns, two different settings.

    11. Quick Reference

    Relationship annotations and their typical database representation:

    Annotation Typical database representation
    @ManyToOne Foreign key on the many side
    @OneToMany(mappedBy = "...") Inverse collection over an existing foreign key
    @OneToOne Foreign key with a uniqueness constraint
    @ManyToMany Join table containing two foreign keys

    Ownership rules:

    Mapping Typical owning side
    Bidirectional one-to-many / many-to-one The @ManyToOne side containing @JoinColumn
    Bidirectional one-to-one The side containing @JoinColumn
    Bidirectional many-to-many The side containing @JoinTable

    Core principles:

    1. Java stores entity references; relational databases store foreign keys.
    2. Cardinality describes how many entities can be associated on each side.
    3. Unidirectional and bidirectional describe Java navigation.
    4. A bidirectional mapping still represents one database relationship.
    5. The owning side determines what relationship value JPA writes.
    6. mappedBy points to a Java field on the owning entity, not a database column.
    7. Both sides of a bidirectional relationship must be synchronized in Java.
    8. Helper methods are the safest way to preserve relationship consistency.
    9. Setting an entity reference does not automatically persist the referenced entity.
    10. Cascading controls lifecycle propagation; it does not define relationship ownership.

    12. Myth vs Reality

    Myth Reality
    "They are separate relationships." @OneToMany and @ManyToOne are two views of one foreign key.
    "A bidirectional mapping stores the data twice." It still maps one database relationship and one foreign key.
    "Setting one side is enough." Both sides of a bidirectional relationship must be synchronized in Java.
    "Owning side means the parent or more important entity." Owning side means only which side controls the database value.
    "mappedBy points to a column." It points to a Java field name on the owning entity, such as "department".
    "A foreign key alone gives one-to-one." One-to-one also needs a uniqueness constraint on that foreign key.
    "Many-to-many can use one foreign-key column." It needs a join table with two foreign keys.
    "Setting a reference persists the target." Persisting the referenced entity is a separate lifecycle decision, often via cascade.
    "@Data is always fine on an entity." It generates toString/equals/hashCode that can recurse, lazy-load, or misbehave.

    13. Common Trap Questions

    Trap 1 - Identify the owning side. Verdict: The side with @JoinColumn (one-to-many/many-to-one, one-to-one) or @JoinTable (many-to-many) owns it. In dept-student, Student.department owns because it holds @JoinColumn(name = "department_id").

    Trap 2 - mappedBy = "department_id". Verdict: Wrong. mappedBy refers to the Java field name on the owning entity, "department", never the database column department_id.

    Trap 3 - One-to-many and many-to-one are different DB relationships. Verdict: False. They are two views of the same relationship and typically share one foreign key, students.department_id.

    Trap 4 - Setting student.setDepartment(engineering) updates the department's list. Verdict: False. The two Java fields are independent; engineering.getStudents().add(student) must also run. Helper methods exist to do both.

    Trap 5 - One-to-one needs only a foreign key. Verdict: False. It needs a foreign key plus a unique constraint; otherwise the schema allows one user to have many profiles.

    Trap 6 - Setting a reference also persists the target. Verdict: False. Association and lifecycle are separate concerns; use entityManager.persist(...) or cascading such as @ManyToOne(cascade = CascadeType.PERSIST).

    Trap 7 - @Data on a bidirectional entity is fine. Verdict: Risky. @Data generates toString/equals/hashCode that can recurse across relationships, trigger lazy loading, throw StackOverflowError, or produce unstable equality. Use @Getter and @Setter.

    14. Points to Remember

    1. Java stores entity references; relational databases store foreign keys, and relationship mapping translates one into the other.
    2. Cardinality describes how many entities can be associated on each side: one-to-one, one-to-many, many-to-one, many-to-many.
    3. Unidirectional and bidirectional describe Java navigation, not SQL query directions.
    4. A bidirectional mapping still represents one database relationship, normally one foreign key.
    5. The owning side determines what relationship value JPA writes; mappedBy marks the inverse side.
    6. mappedBy points to a Java field on the owning entity, never to a database column name.
    7. Both sides of a bidirectional relationship must be synchronized in Java, because the fields do not synchronize themselves.
    8. Helper methods such as addStudent / removeStudent and addCourse / removeCourse are the safest way to keep both sides consistent.
    9. Setting an entity reference does not automatically persist the referenced entity; optional / nullable describe requirements, not lifecycles.
    10. Cascading controls lifecycle propagation and does not define relationship ownership.

    15. Likely Interview Questions

    Question Crisp Answer
    Why is relationship mapping needed? Java stores object references; the database stores foreign keys, so JPA must translate one into the other.
    What is cardinality? How many entities on one side can be associated with how many on the other: one-to-one, one-to-many, many-to-one, many-to-many.
    Difference between unidirectional and bidirectional? Unidirectional has a reference on one side only; bidirectional has references on both, still mapping one DB relationship.
    What is the owning side? The side JPA uses to determine the database value of the relationship, typically the one with @JoinColumn or @JoinTable.
    What does mappedBy point to? A Java field name on the owning entity, not a database column name.
    Difference between @ManyToOne and @OneToMany? Two views of one relationship: @ManyToOne holds the @JoinColumn (owning), @OneToMany(mappedBy=...) is the inverse collection.
    How do you keep a bidirectional relationship consistent? Synchronize both sides in Java, best via helper methods like addStudent / removeStudent.
    Why does one-to-one need a unique constraint? A foreign key alone allows repeated values, so uniqueness is what enforces at most one profile per user.
    What is @MapsId used for? Sharing the parent's identifier as the dependent entity's primary key in a one-to-one relationship.
    How is many-to-many represented in the database? A join table with two foreign keys, managed in JPA by @JoinTable with joinColumns and inverseJoinColumns.
    Does setting a reference persist the target? No; persistence is a separate lifecycle concern, handled by explicit persist or cascading.
    Why avoid @Data on JPA entities? Generated toString/equals/hashCode can recurse across bidirectional relationships, trigger lazy loading, or go unstable.

    • Cardinality names the shape; the annotation names the mapping; the owning side names who writes the foreign key.
    • @ManyToOne owns via @JoinColumn; @OneToMany(mappedBy=...) is the inverse view of that same key.
    • One-to-one adds a unique constraint; many-to-many needs a join table with joinColumns and inverseJoinColumns.
    • Both sides of a bidirectional relationship must be synchronized, which is what helper methods are for.
    • Association and lifecycle are separate: setting a reference never persists the referenced entity by itself.

    One-line takeaway: Every JPA relationship is one database fact (a foreign key or a join table) with two possible Java views, so figure out the owning side first and keep both sides synchronized in code.
