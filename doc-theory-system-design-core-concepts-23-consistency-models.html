    Consistency Models

    6 sections · 445 words

    How stale can a read be. Consistency & Coordination, concept 23 of 36.

    The Idea

    • Strong: every read sees the latest write, from whichever replica answers. Expensive, since it needs coordination between nodes on every read or write.
    • Eventual: replicas agree eventually. A read right after a write might still see the old value. Cheap, fast, and fine for things like counts and feeds.
    • Causal: a middle ground. Writes that caused each other, like a reply to a comment, are seen in that order everywhere. Unrelated writes can arrive in any order.

    A write, then a stale read: Write v2 -> Leader v2 -> lag -> Replica v1 (stale). A read hitting the replica right after the write can still see the old value.

    Watch Out For

    • Paying for strong consistency on data where staleness genuinely does not matter just adds latency for nothing.
    • Assuming eventual consistency means eventually within milliseconds. In a real incident, lag can stretch to seconds or longer.

    Where You Will See It

    • Bank balances and inventory counts: strong consistency, where a stale answer is a real problem.
    • Social media like counts and view counts: eventual consistency, where a slightly stale number is invisible to users.
    • Threaded comments and chat replies: causal consistency, so a reply never appears before the message it replies to.

    How It Connects

    • CAP Theorem: consistency models are the detailed answer to what exactly gets traded away on the A side of CAP.
    • Replication: the mechanism that creates replicas, and therefore the staleness question in the first place.
    • Caching: a cache is, by nature, an eventually consistent copy of whatever it is caching.

    Follow-Up Questions

    1. A user posts a comment, then immediately refreshes and does not see it. What consistency model explains this? Eventual consistency: the write has not yet propagated to the replica that answered the refresh.

    2. A banking app cannot ever show a stale balance. What consistency model does that require? Strong consistency: every read must see the latest write, no exceptions.

    3. A reply to a comment always needs to appear after the comment itself, everywhere. What is that guarantee called? Causal consistency: writes that caused each other stay in order, even while unrelated writes can arrive in any order.

    4. Why would a system deliberately choose eventual consistency instead of strong? Speed and availability. Strong consistency needs coordination on every read or write, which costs latency the use case may not need.

    Recall It As

    Pick the weakest consistency model that is still correct. Anything stronger is paying for nothing.
