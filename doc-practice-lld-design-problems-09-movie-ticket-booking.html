    Design a Movie Ticket Booking System

    15 sections · 1,920 words

    LLD Design Problems, problem 09 of 20.

    The Ask

    Build

    • City -> theatre -> screen -> show.
    • A screen has a fixed seat grid; each seat is regular, premium or recliner.
    • A show is a movie on a screen at a start time, with its own seat map and a price per type.
    • Pick a show, see the live seat map.
    • Select one or more seats, all or nothing.
    • System holds them for 5 minutes while the user pays.
    • Pay in time -> booking confirmed, seats booked for good.
    • Miss the TTL -> the hold expires, seats go back to free.
    • Seat-map changes pushed to others viewing the show.

    Skip

    • A real payment gateway.
    • Drawing the seat-map UI.
    • Recommendations, personalisation.
    • Refund-policy detail.
    • Surge pricing from an ML model.

    Our Model

    A catalogue of shows, each owning its own seat map, and a booking whose hold has a deadline. The service takes a short per-show lock at select.

    Actors and classes

    • User — id, name, email; pick a show, select seats, pay, calling svc.hold(s, ids, bId) and svc.confirm(bId, p).
    • BookingService (singleton + factory) — shows: Map<String, Show>, bookings: Map<String, Booking>, pricing: PricingStrategy, pay: PaymentGateway, lockOf: Map<String, Object> (one per show); hold(Show s, List<String> seatIds, String bookingId): boolean, confirm(String bookingId, Payment p): Ticket, release(String bookingId): void, availableSeats(Show s): List<Seat>.
    • Catalogue — cities: Map<String, City>, shows(city, movie, date): List<Show>. A Screen belongs to one Theatre.
    • Screen — id, name, rows, cols.
    • Show (movie x screen x time) — id, movie: Movie, screen: Screen, startsAt: Instant, holds: Map<String, SeatHold>, priceByType: Map<SeatType, int>; seatState(id): FREE | HELD | BOOKED, book(id, bId), free(id), isBooked(id), seatType(id): SeatType. The live seat map for THIS show.
    • Movie — id, title, runtime: Duration.
    • Seat — seatType(id): SeatType (REGULAR, PREMIUM, RECLINER).
    • SeatHold — seatId, bookingId, heldAt, expiresAt: Instant; live(Instant now): boolean (now < expiresAt, else swept).
    • Booking (context object) — id, showId, userId, seatIds: List<String>, amount: int (minor units), state: BookingState.
    • BookingState (abstract) — hold(), pay(Payment p), confirm(): Ticket, expire(); each state answers all four, wrong call throws. States: Created, SeatsHeld, Paid, Confirmed, Expired.
    • PricingStrategy (interface) — priceFor(Show s, List<Seat> seats): int.
    • PaymentGateway (interface) — charge(String bookingId, int amountMinor): PaymentResult; Razorpay, Stripe, a stub in tests.

    The seat hold lifecycle

    Created -> hold -> SeatsHeld. SeatsHeld -> pay -> Paid; TTL -> Expired. Paid -> confirm -> Confirmed. Confirmed and Cancelled are terminal.

    The pricing rules

    • TieredPricing -> base by seat type.
    • WeekendSurcharge -> +20% Sat / Sun.
    • PeakHour -> +Rs 40 after 6pm; rules chain.

    Key operations

    1. hold(Show s, List<String> seatIds, String bookingId): boolean — takes the per-show lock. Every seat must be FREE, or a stale HELD past its expiresAt. All N or none; stamps a now + 5 min deadline. Returns false the moment one seat is taken.
    2. confirm(String bookingId, Payment p): Ticket — re-checks every hold is still live before it charges, and again under the show lock before it books; charging never happens under the lock. Idempotent on bookingId. A lapse past the charge refunds, then throws HoldExpiredException.
    3. release(String bookingId): void — frees every seat this booking holds. A no-op once CONFIRMED or already released. Called on cancel and by the sweeper.
    4. availableSeats(Show s): List<Seat> — seats with no live hold and not booked. A HELD past expiresAt counts as free. O(seats), read off the show's own map.

    hold when every seat is FREE or HELD past expiresAt; booked when paid before expiresAt. lock(show); every seat FREE? -> hold(bId, now+5m); any taken -> roll back, false.

    The One Run to Hold in Your Head

    Two friends open show S7 at 6pm and both tap seats D4 and D5 in the same second. One taps Pay 20s later, the other after 6 min. Who gets the seats, what does each see, and which objects touched the request?

    The Change

    They ask for "the price climbs as the show fills". Add a DynamicPricing strategy that reads live occupancy off the Show and scales the base. It slots into PricingStrategy; the seat map and the booking flow never change. Strategy, a second time on this sheet.

    What the Picture Can't Show

    The race: two people tap seat D4 in the same moment, both read it FREE. The fix is not a class, it is a per-show lock taken at select, re-checking every seat under it, all N or none.

    If They Make You Code It

    hold and confirm, the whole thing:

    class BookingService {                           // one instance
    Map<String,Show> shows;
    Map<String,Booking> bookings;
    PricingStrategy pricing;
    PaymentGateway pay;
    Map<String,Object> lockOf = new ConcurrentHashMap<>();

    boolean hold(Show s, List<String> seatIds, String bId) {
        synchronized (lockOf.computeIfAbsent(s.id(), k -> new Object())) {
            long deadline = now() + TTL;              // TTL = 5 min
            for (String id : seatIds) {              // pass 1: check all
                SeatHold h = s.holds().get(id);
                if (h != null && h.live(now())) return false;
                if (s.isBooked(id)) return false;
            }
            for (String id : seatIds)                // pass 2: commit all
                s.holds().put(id, new SeatHold(id, bId, deadline));
            return true;                             // all N held, or none
        }
    }

    Ticket confirm(String bId, Payment p) {
        Booking b = bookings.get(bId);
        if (b.state() == CONFIRMED) return b.ticket(); // idempotent
        Show s = shows.get(b.showId());
        if (!allHeld(s, b))                          // hold still live?
            throw new HoldExpiredException(bId);
        int amt = pricing.priceFor(s, b.seats());
        pay.charge(bId, amt);                        // never under the lock
        synchronized (lockOf.get(s.id())) {          // commit under it
            if (!allHeld(s, b)) {                    // TTL lapsed while paying
                pay.refund(bId, amt);
                throw new HoldExpiredException(bId); }
            for (String id : b.seatIds()) s.book(id, bId);
            b.onConfirm();                           // SEATS_HELD -> CONFIRMED
        }
        return b.ticket();
    }
}

    The Four Hazards

    1. Two users, one seat. hold() is not the commit until it takes the lock. With none, both reads of D4 see FREE and both write a hold. One per-show lock, re-read every seat inside it, one hold wins.
    2. Hold dies on the payment page. The 5-minute TTL lapses while the card form is open. Payment then succeeds but the seat is gone. confirm re-checks holdLive before charging; on a miss, refund or offer a re-pick, never charge blind.
    3. Partial multi-seat hold. A 5-seat pick where 2 are already held. Grab 3, block on 2, and the group is broken. Two-pass check-then-commit under the lock; roll back the 3, return false with the seats that went.
    4. A hold no one releases. The user closes the tab. Nothing calls release and the seats sit HELD forever. A sweeper frees holds past expiresAt every minute; reads also treat a stale HELD as FREE.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. synchronized (lockOf...) + re-check every seat — the lock is taken at select, not at pay. Two friends tap D4, one hold wins.
    2. Two passes: check all seats free, then commit all — a 5-seat select is all-or-nothing, never 3 held and 2 lost.
    3. confirm re-checks the hold again after charging, under the show lock — the TTL can lapse on the payment page, so the commit is guarded too, and a lapse refunds.

    How to Hold a Seat

    Approach Lock held for Other viewers On abandon Fails when Extra cost
    DB row lock at select (pessimistic) the whole payment blocked, spinner lock leaks till timeout the pool drains under load a scarce DB lock per seat
    TTL hold + sweeper (the default) microseconds at select see HELD at once sweeper frees at TTL clock skew across nodes a sweeper + a lock per show
    Version check at pay (optimistic) none see FREE, clash later nothing to undo two pay together, one loses after paying a refund / re-pick path

    TTL hold plus sweeper. The lock is held for microseconds at select, the hold is a plain record with a deadline, and every other viewer sees HELD at once. A DB lock across a human's payment time drains the pool; checking only at pay makes a user pay, then lose the seat.

    Rejection Signals

    These end the interview:

    • Marking seats BOOKED at select with no payment step — one slow user freezes a row for everyone.
    • Taking the seat lock at pay, not at select — two users both see FREE, both pay, one is refunded and furious.
    • A DB row lock held open across the whole payment — the connection pool drains under a popular show.
    • No TTL and no sweeper — an abandoned cart holds its seats until a human clears them.
    • A 5-seat select that commits 3 and returns success — the customer pays for a broken group.
    • confirm with no idempotency — the payment callback fires twice and books or charges twice.

    Patterns Used

    State — the Booking lifecycle, one class per phase. Strategy — pricing (base + weekend + peak) and payment. Observer — push the seat map to everyone watching the show. Factory — BookingService builds a Booking from a hold.

    Say It Like This

    "A Show owns a per-seat map. Pick seats and the service takes a short per-show lock, checks every seat is free, writes a HELD record with a 5-minute deadline, all or none. Pay in time and confirm re-checks the hold, charges through a thin seam, flips the seats to BOOKED. Miss the window and a sweeper frees them. Pricing and payment are strategies; the lifecycle is a State machine."

    The Follow-ups That Decide It

    1. Two users tap the last two seats together. Walk it. Per-show lock, re-check every seat, one hold wins.
    2. The hold expires while they are paying. confirm re-checks holdLive, refund or re-pick, never a silent loss.
    3. Select 5 seats, 2 already held. Two-pass check-then-commit, roll back, name the seats that went.
    4. The user closes the tab mid-booking. A sweeper frees holds past expiresAt; a stale HELD reads as FREE.
    5. Show the live seat map to everyone watching. Observer on hold / release / book, push the delta.
    6. "Cheaper on weekday mornings." A PricingStrategy chain; the seat map never changes.
    7. Aisle seats must sell as a block of three. hold reserves the run; release frees the whole run.
    8. One hot show, thousands picking at once. The lock is per show, holds are per seat; shard by showId.

    Deliberately Not Built

    • A real payment gateway — a PSP behind PaymentGateway. The seam is the point; the integration is not.
    • Rendering the seat map — the grid UI and its live socket. Observer names the push; the pixels are not ours.
    • Recommendations — "Because you watched" is a separate ranking service. A different question.
    • Refund rules — a RefundStrategy on cancel, tiered by how close to showtime. Name the hook.
    • Surge pricing from a model — a PricingStrategy that reads live occupancy. Drops in, no flow change.
