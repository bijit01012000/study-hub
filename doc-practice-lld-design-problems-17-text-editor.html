    Design a Text Editor

    15 sections · 1,969 words

    LLD Design Problems, problem 17 of 20.

    The Ask

    Build

    • A Document: a text buffer plus a cursor / selection.
    • Edits: insert(pos, text), delete(pos, len), replace(pos, len, text).
    • Every edit is a command with apply and undo.
    • Undo and redo, unlimited within a memory cap.
    • Typing a word is one undo step.
    • A paste, a cursor jump or a delete starts a new step.
    • The buffer representation is swappable.

    Skip

    • Rendering, layout, syntax highlighting.
    • File open / save, autosave.
    • Search & replace UI, multiple cursors.
    • Collaborative editing, OT / CRDT.
    • Buffer internals (gap buffer, rope).

    Our Model

    Editor to Document to Cursor. An Editor invoker holds a Document and two stacks; every change is an Edit object with an exact inverse.

    Actors and classes

    • Typist — editor: Editor; execute(new InsertEdit(pos, "a")), undo(), redo().
    • Editor (invoker) — doc: Document, history: History; execute(Edit e): void, undo(): void, redo(): void.
    • Document — buffer: Buffer, cursor: Cursor; insert(int pos, String s): void, delete(int pos, int len): void, replace(int pos, int len, String s), text(int pos, int len): String.
    • Buffer (interface) — charAt(int), slice(from, to): String. StringBuilder shifts on every edit; GapBuffer is cheap at the cursor; PieceTable keeps append-only spans; Rope is a tree, O(log n). Strategy: the model never names one.
    • Cursor — pos: int, anchor: int; moveTo(int), selection(): Range. Any move or click breaks the coalescing run.
    • Edit (interface) — apply(Document d): void, undo(Document d): void, merge(Edit next): boolean. Undo is the exact inverse of apply. Implemented by InsertEdit, DeleteEdit, CompoundEdit.
    • InsertEdit — pos: int, text: String; apply -> d.insert(pos, text), undo -> d.delete(pos, text.length).
    • DeleteEdit — pos, len; captures removed on apply. apply reads d.text(pos, len) into a field first, then deletes; undo -> d.insert(pos, removed).
    • CompoundEdit (composite) — parts: List<Edit>; apply -> each part front to back, undo -> each part back to front. One macro = one undo step. replace -> CompoundEdit(delete, insert).
    • History — undo: Deque<Edit>, redo: Deque<Edit>, limit: int; push(Edit e) -> undo.push, redo.clear; pop(): Edit; move(from, to). Drops the oldest when undo grows past limit.
    • SnapshotStore (memento) — past: Deque<String>; snapshot() copies the whole document, restore(s) undoes with no inverse written. Simple, O(document) per step, the fallback.
    • EditorView (interface) — onEdit(Document d): void. StatusBar, Minimap, Gutter. Observer: redraw after every change.
    • KeyMap — "a".."z" -> InsertEdit; Backspace / Del -> DeleteEdit; paste -> InsertEdit(whole payload); Ctrl+Z -> undo(), Ctrl+Y -> redo().

    The invariants

    • execute() pushes on top; undo() pops from top.
    • A fresh edit clears the redo stack.
    • coalesce when the last edit is an insert, adjacent, no move intervened, and under N ms.
    • Every edit is a Command; undo is its exact inverse.

    Key operations

    1. execute(Edit e): void — runs e.apply(doc) now. Tries to merge e into the top of the undo stack, else pushes it. Always clears the redo stack. The only entry point for a change.
    2. undo(): void — no-op on an empty stack. Pops the top edit, calls its undo(doc) — the exact inverse — and moves it to the redo stack. O(1) plus the edit's own work.
    3. redo(): void — the mirror. Pops redo, re-applies, pushes back to undo. Reachable only until the next fresh edit wipes the redo stack.
    4. apply(Document d): void — each Edit type's forward step. DeleteEdit captures the removed text here so undo can put it back. replace is a CompoundEdit of delete then insert.

    From memory

    • execute(e): e.apply(doc); undo.push(e); redo.clear();.
    • undo(): e = undo.pop(); e.undo(doc); redo.push(e);.
    • redo(): e = redo.pop(); e.apply(doc); undo.push(e);.

    Recall drill: cover the operations column, write the four with their guarantee. Blank on the guarantee means that method is your gap.

    The One Run to Hold in Your Head

    Cursor at 0 in an empty document. The user types c, a, t, then Backspace, then Ctrl+Z, then types !. What is on screen, what sits on each stack, and how many undo steps did the word "cat" cost?

    The three inserts coalesce into one InsertEdit "cat". Backspace pushes a DeleteEdit "t", leaving "ca". Ctrl+Z pops the DeleteEdit and moves it to redo, restoring "cat". Typing ! clears the redo stack. The word "cat" costs one undo step.

    The Change

    Two people edit the same document at once. A CollabSession sits between execute() and the History: local edits apply at once, remote edits are transformed against everything not yet acknowledged (OT) or merged as a CRDT, and undo becomes per-user. The Edit objects stay; the pipeline in front of them changes. A new layer on the same seam.

    What the Picture Can't Show

    Undo is a write path. Every Edit runs apply now, then sits on a stack as its own inverse. Miss merge() and one Ctrl+Z is one letter. Miss redo.clear() and redo re-applies into text that moved on.

    If They Make You Code It

    Execute, undo, redo and a DeleteEdit:

    class Editor {                                     // invoker, the two stacks
    final Document doc;
    final Deque<Edit> undo = new ArrayDeque<>();
    final Deque<Edit> redo = new ArrayDeque<>();
    Edit open;                                     // the run still merging

    void execute(Edit e) {
        e.apply(doc);                              // do the change now
        if (open != null && open.merge(e)) {
            redo.clear(); return; }                // same run
        undo.push(e); open = e;                    // a fresh run
        redo.clear();                              // clears the redo branch
    }
    void undo() {
        if (undo.isEmpty()) return;
        Edit e = undo.pop();
        e.undo(doc); redo.push(e);                 // exact inverse
        open = null;                               // run is closed
    }
    void redo() {
        if (redo.isEmpty()) return;
        Edit e = redo.pop();
        e.apply(doc); undo.push(e);
    }
}

class DeleteEdit implements Edit {
    final int pos, len;
    String removed;                                // filled by apply
    public void apply(Document d) {
        removed = d.text(pos, len);                // save before delete
        d.delete(pos, len);
    }
    public void undo(Document d) { d.insert(pos, removed); }
    public boolean merge(Edit next) { return false; }
}

    The Four Hazards

    1. Redo stack not cleared on a fresh edit. Undo a few times, then type. If execute() forgets redo.clear(), the redo stack still holds edits built against the old text. A later Ctrl+Y re-applies one at a stale position and the document quietly diverges from anything the user ever saw.
    2. A delete that keeps no copy. insert only needs its position and text to invert. delete must record the exact characters it removed before it removes them, or undo has nothing to re-insert. DeleteEdit reads d.text(pos, len) into a field first, then deletes.
    3. Coalescing that never stops. Merging every insert into the last one feels tidy until one Ctrl+Z deletes a paragraph. A run must break on a cursor move, a click, a paste, a selection replace, a delete, or a pause past about 500 ms.
    4. History with no ceiling. Every keystroke that does not coalesce is an object pinned for the whole session. A long editing day is millions of edits. Cap the undo stack; past the limit drop from the bottom — that history is simply gone, the accepted trade.

    Name them before they are asked.

    The Lines They Are Watching

    1. redo.clear() on every fresh edit — without it a later redo replays an edit into text that moved on.
    2. removed = d.text(pos, len) before the delete — a DeleteEdit with no captured text cannot be undone.
    3. merge(e) at the top of the stack — one Ctrl+Z undoes a word, and it must stop at a cursor jump or a paste.

    Where the Undo Information Lives

    Approach Per step Undo cost Redo Coalescing Cost to build Reach for it
    Command + inverse (the standard answer) the delta + how to reverse call edit.undo() re-apply the edit merge two edits into one an inverse per edit type the normal case
    Memento snapshots a full document copy swap in the old copy keep a forward copy too diff two snapshots (hard) trivial inverses are painful to write
    Persistent rope one new root, shared nodes point at the old root point at the newer root snapshot granularity only rope + structural sharing edits are huge and frequent

    Command with an inverse per edit type. O(1) memory per step, coalescing is natural, and replace is just a CompoundEdit. Fall back to Memento when an operation has no clean inverse; reach for a persistent rope only when the buffer itself is the bottleneck.

    Rejection Signals

    These end the interview:

    • A DeleteEdit that stores only position and length — undo cannot rebuild the text it threw away.
    • execute() that never clears the redo stack — redo later replays an edit into a document it no longer fits.
    • One undo() reversing a whole sentence — a coalescing rule with no break on cursor move or paste.
    • replace written as a third primitive instead of delete + insert — two more code paths to keep reversible.
    • Edits holding absolute offsets reused after later edits shifted the text — the inverse lands in the wrong place.
    • No bound on the undo stack — a full day of typing kept live in memory.

    Patterns Used

    Command — every edit is apply / undo. Memento — the snapshot fallback when an inverse is hard. Composite — a CompoundEdit undoes a macro as one. Strategy — the Buffer representation, StringBuilder to rope.

    Say It Like This

    "Every change is an Edit object with apply and undo. The Editor runs apply, pushes the edit onto an undo stack and clears the redo stack. Undo pops it, runs its inverse, moves it to redo. Consecutive single-character inserts merge so one Ctrl+Z reverses a word. replace is a CompoundEdit of delete plus insert."

    The Follow-ups That Decide It

    1. Type "hello", one Ctrl+Z. What disappears? All five letters — the run coalesced into one InsertEdit.
    2. What breaks a coalescing run? A cursor move, a paste, a delete, a selection replace, or a pause past N ms.
    3. Undo, then type. Can you still redo? No — the fresh edit cleared the redo stack.
    4. How does undo of a delete restore text? DeleteEdit captured the removed substring on apply.
    5. Implement replace. A CompoundEdit of delete then insert; undo runs its children in reverse.
    6. Cap memory for a long session. Bound the undo stack, drop the oldest edit; that history is gone.
    7. Undo a paste of 2000 chars. One InsertEdit with the whole payload; O(1) units, O(n) buffer work.
    8. Two users editing at once. The ghost — OT / CRDT rebases remote edits; per-user undo.

    Deliberately Not Built

    • Collaborative editing — OT or CRDT rebasing remote edits against local ones. The ghost; a different interview.
    • The buffer data structure — gap buffer, piece table, rope behind the Buffer seam. Name the trade, don't whiteboard it.
    • Rendering & highlighting — a view over the Document, not part of the edit model. Observer fans it out.
    • Search / replace UI, macros — all expressed as insert / delete / CompoundEdit underneath.
    • Persistence, crash recovery — a journal of Edits flushed to disk, replayed on open. Name it and move on.
