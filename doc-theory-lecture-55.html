    Lock-Free Concurrency in Java - 2 | CAS Retry, Compare-and-Swap & ABA Problem

    21 sections · 4,542 words

    Lecture 55

    Scope evidence: "Lock-Free Concurrency in Java - 2 | CAS Retry, Compare-and-Swap & ABA Problem" plus the lecture's own repo notes (CAS retry, contention, atomic arrays, ABA, high-contention counters), playlist map, verified. Repo evidence: code/Demo.java.

    Lecture 54 introduced atomic variables and the idea of updating a single value without a traditional lock. This lecture opens the mechanism that makes those updates possible: Compare-And-Set. It covers the CAS retry loop that every lock-free algorithm is built on, what happens under contention, atomic arrays for independently updated slots, the memory-visibility role of atomic classes, the ABA problem and its fixes, and high-contention counters. The central recipe is simple: read the current state, calculate the desired state, and update it only if no other thread changed it in the meantime.

    1. Compare-And-Set (CAS): One Atomic Step

    CAS stands for Compare-And-Set or Compare-And-Swap. The Java method is named:

    compareAndSet(expectedValue, newValue)

    Its meaning is exact:

    • If the current value equals the expected value: replace it with the new value and return true.
    • Otherwise: leave the value unchanged and return false.

    CAS combines the comparison and the update into one atomic operation. No thread can observe or interleave a half-finished compare-and-set, which is precisely what makes it usable as the primitive for lock-free code.

    // Demo.java — the CAS contract: success and failure
import java.util.concurrent.atomic.AtomicInteger;

public class CasBasics {
    public static void main(String[] args) {
        AtomicInteger number = new AtomicInteger(10);
        boolean changed = number.compareAndSet(10, 20);
        System.out.println(changed);      // true
        System.out.println(number.get()); // 20

        AtomicInteger other = new AtomicInteger(30);
        boolean failed = other.compareAndSet(10, 20);
        System.out.println(failed);       // false
        System.out.println(other.get());  // 30
    }
}
    Situation Current value Expected value Result Return value
    Match 10 10 replaced with 20 true
    Mismatch 30 10 left at 30 false

    Important CAS cannot "force" a write. It is a conditional update: it succeeds only when the value is still exactly what the caller assumed, which is why a failed CAS always means "someone else got there first, reread and try again".

    2. CAS as Optimistic Concurrency — The Lock-Free Recipe

    CAS uses an optimistic strategy: assume nothing will change, and detect the violation at update time rather than preventing it up front.

    I read state X
   →
I calculate a new state Y
   →
I assume nobody changed X
   →
I attempt CAS(X, Y)
   |-- assumption correct  → update succeeds
   `-- someone changed X   → update fails → reread and retry

    This is the opposite of pessimistic locking, which prevents interference before it can happen:

    Lock first → prevent others from entering → read and update → unlock

    The lock-free recipe in three words: read → compute → CAS. If the assumption behind the computed value is still true, the update lands; if not, the thread discards its stale calculation and starts over. That retry capability is what allows a lock-free algorithm to keep making progress without any thread ever owning a lock.

    Memory aid CAS is a friendly transaction: "I believe the value is X; here is the Y I computed from X." If the clerk says the value is still X, the trade goes through; if the value moved, the whole computation is thrown away and recomputed.

    3. Lock vs CAS

    Both approaches can be correct. The difference is where the coordination happens.

    Aspect Lock-based update CAS-based update
    Coordination point Before the critical section (acquire lock) At the update itself (conditional replacement)
    Strategy Pessimistic: prevent interference Optimistic: detect interference
    Flow Acquire lock → read → modify → release Read → compute → CAS → success or retry
    Other threads May block while waiting May proceed and simply fail their CAS
    Progress guarantee Blocking: a stalled owner stalls others System-wide progress without ownership
    Best for Multi-variable invariants, awaited conditions Small, single-value atomic transitions
    Failure mode Deadlock, long blocking, convoying Retry storms, starvation, wasted CPU

    Several threads may race, but only an update based on the current expected value succeeds. CAS avoids lock ownership, but it does not eliminate contention (Section 7).

    4. How CAS Is Implemented

    At the Java level, atomic classes expose operations such as compareAndSet(), getAndAdd(), and getAndSet(). The JVM usually maps these operations to platform-specific atomic instructions, or intrinsics. On modern x86 processors a CAS operation may use an instruction such as locked CMPXCHG.

    The important points are:

    • comparison and update are performed atomically;
    • the operation participates in the processor's cache-coherence protocol;
    • competing cores cannot both successfully update the same memory location from the same expected state;
    • the JVM provides the Java Memory Model guarantees required by the atomic API.

    Important It is usually inaccurate to imagine that every CAS locks the entire system bus. Modern processors commonly coordinate atomic updates at the cache-line and coherence-protocol level. Application code should rely on Java's documented atomicity and memory-ordering guarantees, never on one specific CPU implementation.

    5. The CAS Retry Loop

    A CAS can fail when another thread changes the value after it was read. The retry loop handles exactly that situation:

    while (true) {
    int current = value.get();
    int updated = calculate(current);
    if (value.compareAndSet(current, updated)) {
        break;
    }
}

    On failure the flow is always the same:

    previously read state is stale
   →
read the latest state
   →
recalculate the update
   →
try again

    This pattern is the foundation of many lock-free algorithms. It terminates because every failed attempt re-reads a fresh state and recomputes against it. If interference stops, the next CAS compares against an unchanged value and succeeds. Only continuous interference from other threads keeps a particular thread looping.

    // Demo.java — a counter built from a manual CAS loop
import java.util.concurrent.atomic.AtomicInteger;

class LikeCounter {
    private final AtomicInteger totalLikes = new AtomicInteger(0);

    public void like() {
        while (true) {
            int current = totalLikes.get();
            int updated = current + 1;
            if (totalLikes.compareAndSet(current, updated)) {
                return;
            }
        }
    }

    public int getTotalLikes() {
        return totalLikes.get();
    }
}

public class LikeCounterDemo {
    public static void main(String[] args) throws InterruptedException {
        LikeCounter counter = new LikeCounter();
        Thread[] threads = new Thread[7];
        for (int i = 0; i < threads.length; i++) {
            threads[i] = new Thread(counter::like);
            threads[i].start();
        }
        for (Thread thread : threads) {
            thread.join();
        }
        System.out.println("Total likes: " + counter.getTotalLikes()); // 7
    }
}

    For this exact operation, prefer totalLikes.incrementAndGet(): it is clearer and lets the JVM choose the most efficient supported atomic operation. The manual loop is shown because it exposes the algorithm.

    Golden rule A CAS loop is safe only when the whole operation can be recomputed from the freshly read state. If the computation has side effects, the side effect may run more than once across retries.

    6. Coordination: Why Not Thread.sleep()

    Using Thread.sleep() to sequence threads is unreliable:

    firstThread.start();
Thread.sleep(3000);   // three seconds may be enough ... or not
secondThread.start();
System.out.println(counter.get());

    Three seconds may be more than necessary, less than necessary, and is affected by machine load and scheduling. It is a guess, not coordination.

    Use join() when waiting for threads:

    firstThread.join();
secondThread.join();

    For executor tasks, prefer:

    • Future.get()
    • CompletableFuture.join()
    • ExecutorService.awaitTermination()
    • coordination utilities such as CountDownLatch

    7. CAS Contention, Spinning and Starvation

    Under low contention a CAS update can complete quickly. Under high contention the picture changes:

    many threads read the same old state
   →
one update succeeds, many updates fail
   →
losers retry
   →
CPU time is spent recalculating and retrying

    Lock-free code removes lock ownership, but contention remains. Possible effects include:

    • wasted CPU cycles;
    • cache-line bouncing between cores;
    • increased latency;
    • starvation of unlucky threads;
    • reduced throughput under extreme contention.

    Lock-free is not automatically faster than a well-designed lock.

    Important A lock-free algorithm guarantees system-wide progress, not progress for every thread. Thread A may succeed repeatedly while Thread B repeatedly loses its CAS and retries many times. This is why lock-free does not mean wait-free. When fairness is a requirement, an explicit fair lock or another coordination mechanism may be more suitable.

    8. Backoff in Retry Loops

    A tight retry loop can consume significant CPU during contention. A common mitigation is to hint the CPU that the thread is spinning:

    while (true) {
    State current = state.get();
    State updated = calculate(current);
    if (state.compareAndSet(current, updated)) {
        return;
    }
    Thread.onSpinWait();   // "I am spinning", not "sleep"
}

    For custom low-level algorithms, techniques include:

    • rereading the latest value;
    • Thread.onSpinWait();
    • bounded spinning;
    • yielding (for example Thread.yield());
    • exponential backoff;
    • eventually falling back to a lock.

    Important Do not add spinning mechanically. Backoff must be justified by measurement and by the expected contention duration; otherwise it adds latency without removing work.

    9. Atomic Arrays

    A normal array does not make updates to its elements safely composable across threads:

    int[] counters = new int[10];
counters[0]++;   // still a non-atomic read-modify-write

    Java therefore provides:

    • AtomicIntegerArray
    • AtomicLongArray
    • AtomicReferenceArray<E>

    Each element can be accessed and updated atomically, and each index behaves like an independent atomic value.

    // Demo.java — per-index atomic integer operations
import java.util.concurrent.atomic.AtomicIntegerArray;

public class AtomicArrayDemo {
    public static void main(String[] args) {
        AtomicIntegerArray counters = new AtomicIntegerArray(3);
        counters.incrementAndGet(0);
        counters.addAndGet(1, 5);
        System.out.println(counters.get(0)); // 1
        System.out.println(counters.get(1)); // 5
    }
}

    For references, AtomicReferenceArray<E> adds conditional replacement by index:

    boolean changed = values.compareAndSet(1, "B", "X");
// if index 1 currently contains the expected reference,
// replace it with X

    As with AtomicReference, expected object values are matched by reference identity.

    The theatre-seat example shows the pattern in use — each seat is updated independently:

    // Demo.java — independently bookable seats
import java.util.concurrent.atomic.AtomicReferenceArray;

class MovieTheatre {
    private final AtomicReferenceArray<String> seats;

    MovieTheatre(int totalSeats) {
        seats = new AtomicReferenceArray<>(totalSeats);
    }

    public boolean bookSeat(int seatNumber, String userName) {
        validateSeatNumber(seatNumber);
        return seats.compareAndSet(seatNumber, null, userName);
    }

    public String getBookedBy(int seatNumber) {
        validateSeatNumber(seatNumber);
        return seats.get(seatNumber);
    }

    private void validateSeatNumber(int seatNumber) {
        if (seatNumber < 0 || seatNumber >= seats.length()) {
            throw new IllegalArgumentException("Invalid seat number: " + seatNumber);
        }
    }
}

    Important Each seat can be updated independently. Booking several seats as one indivisible transaction would require a broader coordination strategy — an array of atomics gives atomicity per slot, not across slots.

    10. volatile vs Atomic Variables

    A volatile field provides visibility and ordering guarantees:

    private volatile boolean running = true;

    When one thread writes running = false, other threads reading the field are guaranteed to observe that update according to the Java Memory Model. A volatile read and write of the field itself is atomic for supported field types.

    What volatile does not provide is atomicity for a compound read-modify-write:

    private volatile int count = 0;
public void increment() {
    count++;   // read → modify → write, still non-atomic
}

    Two threads can still lose an update, because count++ is conceptually read, modify, write.

    Requirement volatile Atomic class
    Latest value is visible across threads Yes Yes
    Atomic plain read/write Yes Yes
    Atomic increment No Yes
    Atomic compare-and-set No Yes
    Atomic functional update No Yes
    Supports compound state transition No For one atomic value

    Use volatile for a visibility-based state flag when no compound atomic transition is required. Use an atomic class for operations such as increment, decrement, get-and-set, compare-and-set, and update based on the current value.

    Memory aid volatile is a window — everyone sees the latest value. An atomic class is a turnstile — one thread passes through a read-modify-write at a time, atomically.

    11. Memory Visibility, Happens-Before and the Atomic Barrier

    Atomic variables provide more than indivisible updates: their reads and writes have volatile-like memory effects. A write to a volatile or atomic variable happens-before a subsequent read of that same variable. A successful CAS therefore acts as a barrier: state written before the update is safely published to any thread that later reads the updated value, provided the design follows the Java Memory Model correctly.

    // Demo.java — an atomic flag publishes the configuration set before it
import java.util.concurrent.atomic.AtomicBoolean;

class ConfigurationHolder {
    private String configuration;
    private final AtomicBoolean ready = new AtomicBoolean(false);

    public void initialize() {
        configuration = "production";   // ordinary write
        ready.set(true);                // atomic write publishes it
    }

    public String getConfiguration() {
        if (!ready.get()) {             // atomic read acquires it
            throw new IllegalStateException("Not ready");
        }
        return configuration;
    }
}

    The atomic flag supplies visibility, but this design still needs careful lifecycle control to ensure initialization happens only once (for example, a compareAndSet(false, true) guard, as seen in Lecture 54).

    Interviewer's perspective "Does an atomic variable only give atomicity?" No — it also supplies the memory-ordering effects of volatile. That is why publishing immutable state through an atomic reference is a common safe-publication idiom.

    12. The ABA Problem

    CAS asks only one question:

    Is the current value equal to my expected value now?

    It does not automatically record whether the value changed earlier, how many times it changed, or which intermediate values existed. That omission creates the ABA problem.

    Initial state:                        A
Thread A reads:                       A
Before Thread A updates, Thread B changes:   A → B → A
Thread A performs:                    CAS(A → X)
Result:                               succeeds, because the current value is again A

    Thread A cannot tell that the state changed temporarily. In a simple counter, 10 → 11 → 10 may not matter. In a lock-free data structure, the intermediate changes may represent important history. Consider a stack:

    Node A is at the top of the stack
   →
Node A is removed
   →
the node or its memory is reused
   →
a reference resembling the old state appears again

    A thread may then incorrectly assume the structure is unchanged because the reference looks identical, and its CAS corrupts the structure.

    Important ABA is about identity versus history. CAS compares the current appearance; it does not know what happened in between. A reused node can make a changed structure look unchanged.

    13. ABA Solutions: AtomicStampedReference and AtomicMarkableReference

    The classic fix is versioning: store the value together with a version (a stamp), and increment the version on every change.

    (A, 1)  →  (B, 2)  →  (A, 3)

Thread A expects:  (A, 1)
Current state is:  (A, 3)
CAS fails even though the visible value is again A.

    // Demo.java — an ABA sequence, then the AtomicStampedReference fix
import java.util.concurrent.atomic.AtomicStampedReference;

public class AbaDemo {
    public static void main(String[] args) {
        AtomicStampedReference<String> ref =
                new AtomicStampedReference<>("A", 0);

        int[] stampHolder = new int[1];
        String expected = ref.get(stampHolder);
        int expectedStamp = stampHolder[0];

        // Thread B performs A -> B -> A, bumping the stamp each time.
        ref.compareAndSet("A", "B", expectedStamp, expectedStamp + 1);
        ref.compareAndSet("B", "A", expectedStamp + 1, expectedStamp + 2);

        // Thread A's stale snapshot expects (A, 0), but the stamp is now 2.
        boolean changed =
                ref.compareAndSet(expected, "X", expectedStamp, expectedStamp + 1);

        System.out.println("Value: " + ref.getReference() + ", stamp: " + ref.getStamp());
        System.out.println("Changed from stale snapshot? " + changed); // false
    }
}

    AtomicMarkableReference is the lighter variant: it pairs the reference with a single boolean mark instead of an integer version, useful when the only question is "has this been touched".

    Problem Tool What it adds Use when
    Plain CAS AtomicReference reference only, no history the referenced object is never reused or mutated
    ABA risk AtomicStampedReference reference + integer version the full change history must be detected
    ABA (lighter) AtomicMarkableReference reference + boolean mark only a touched/untouched flag is needed

    14. High-Contention Counters: LongAdder, DoubleAdder, LongAccumulator

    When many threads increment a single AtomicLong, every increment CASes the same cell. Under heavy contention most attempts fail and retry, and throughput collapses. LongAdder solves this by keeping one or more cells and letting threads update different cells, then combining them on sum().

    // Demo.java — a striped adder under many threads
import java.util.concurrent.atomic.LongAdder;

public class LongAdderDemo {
    public static void main(String[] args) throws InterruptedException {
        LongAdder total = new LongAdder();
        Thread[] threads = new Thread[8];
        for (int i = 0; i < threads.length; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 100_000; j++) {
                    total.increment();
                }
            });
            threads[i].start();
        }
        for (Thread thread : threads) {
            thread.join();
        }
        System.out.println("Total: " + total.sum()); // 800000
    }
}

    DoubleAdder is the same idea for doubles. LongAccumulator generalizes it: it holds an associative combination function (for example Long::sum, or Math::max) and a running accumulated value.

    Aspect AtomicLong LongAdder
    Internal structure one value one or more striped cells
    Read exact value get() is atomic sum() is not an atomic snapshot
    Write under contention CAS retries on one cell threads spread across cells
    Throughput (high contention) lower higher
    Memory footprint smaller larger
    Update returns result yes (incrementAndGet) no (increment returns void)
    Best for exact current value, CAS, sequencing high-throughput statistics and monitoring

    Important sum() walks the cells and is not a single atomic read. Concurrent updates during the summation may or may not be included, so sum() is suitable for statistics, not for a value that must be an exact instantaneous snapshot. Prefer AtomicLong when you need an exact current value or a CAS.

    15. When NOT to Go Lock-Free

    CAS works best for small, clearly defined state transitions. It becomes less attractive when several mutable objects, external side effects, or complex business rules must be coordinated together.

    Situation Prefer Why
    One independent value, one atomic transition Atomic variable / CAS Exactly what CAS models well
    Several fields must change together Lock or concurrent collection No single atomic value expresses the invariant
    Multiple steps form one invariant Lock (critical section) Individual atomics do not compose across calls
    A condition must be awaited Lock / Condition CAS cannot park and wait
    External side effects involved Lock or immutable publication CAS may recompute and replay effects

    A concrete warning: individual atomic methods do not make a sequence atomic.

    if (count.get() > 0) {
    count.decrementAndGet();
}

    The check and the decrement are two independent operations; two threads can both pass the check before either decrements, and the count becomes negative. The atomicity of each method is real, but the compound rule is not.

    Golden rule The right question is not "Can this be written without a lock?" but "Which concurrency mechanism makes the invariant correct, understandable and efficient?" Correctness is more important than avoiding locks.

    16. Myth vs Reality

    Myth Reality
    "Lock-free is always faster than locks." Under high contention CAS retries waste CPU and bounce cache lines; a well-designed lock can win. Lock-free is a tool, not a speed guarantee.
    "CAS checks whether the value changed since I read it." CAS checks only whether the current value equals the expected value now; earlier A → B → A changes are invisible (ABA).
    "A volatile int makes count++ thread-safe." volatile gives visibility and ordering, not atomicity; count++ is still a non-atomic read-modify-write.
    "Atomic methods make every sequence of operations atomic." Each method is atomic on its own; a check-then-act spanning two calls is not.
    "LongAdder.sum() gives an exact instantaneous count." sum() traverses cells and is not a single atomic snapshot; concurrent updates may not all be reflected.
    "Every CAS locks the entire system bus." Modern processors coordinate atomic updates at the cache-line and coherence-protocol level; the JVM hides the exact instruction.

    17. Common Trap Questions

    Trap 1 — Retry termination: "Can a CAS retry loop spin forever?" For a given thread, yes, if it repeatedly loses the race — that is starvation. The loop guarantees system-wide progress, not per-thread progress, which is why lock-free is not wait-free.

    Trap 2 — ABA in a counter: "Does ABA matter for an AtomicInteger counter?" Usually not, because only the final numeric value matters. It matters when intermediate states carry meaning, as when nodes are removed and reused in a lock-free stack.

    Trap 3 — Reference equality: "Does AtomicReference.compareAndSet use equals()?" No. It compares references by identity (==). Pass the exact reference previously obtained from get(), or pass null as the expected value when appropriate.

    Trap 4 — Per-slot atomicity: "Can I book two seats in one AtomicReferenceArray CAS?" No. Each index is an independent atomic value; a multi-seat transaction needs broader coordination.

    Trap 5 — Visibility versus atomicity: "If a volatile flag is set, is a following compound update safe?" Setting the flag publishes prior writes, but any read-modify-write or check-then-act after it still needs an atomic class or a lock.

    Trap 6 — Adder exactness: "Is LongAdder a drop-in replacement for AtomicLong?" Not for exact reads or CAS. LongAdder has no CAS and its sum() is not an atomic snapshot; use it for write-mostly counters.

    Trap 7 — Spin hint: "Does Thread.onSpinWait() pause the thread?" No. It is a CPU hint that the thread is spinning; it does not sleep, yield, or release anything.

    18. Points to Remember

    1. CAS means compare-and-set (compare-and-swap): compareAndSet(expected, new) atomically replaces the value only when it still equals the expected value, returning a boolean.
    2. The lock-free recipe is read current state, compute the desired state, CAS, and retry on failure.
    3. A CAS retry loop terminates once interference stops; it guarantees system-wide progress, not per-thread progress.
    4. High contention causes retries, cache-line bouncing, latency, starvation, and lower throughput; lock-free is not automatically faster.
    5. Backoff (reread, Thread.onSpinWait(), bounded spinning, yielding, exponential backoff, fallback to a lock) must be measurement-driven.
    6. Atomic arrays (AtomicIntegerArray, AtomicLongArray, AtomicReferenceArray) give each index independent atomic access; AtomicReferenceArray compares by reference identity.
    7. volatile gives visibility and ordering but not compound atomicity; atomic classes give indivisible read-modify-write for one value.
    8. Atomic reads and writes have volatile-like memory effects: a successful update can publish prior state (happens-before) when the JMM is respected.
    9. ABA exists because CAS compares the current value only; fix it with a version via AtomicStampedReference or a mark via AtomicMarkableReference.
    10. LongAdder, DoubleAdder, and LongAccumulator reduce contention with striped cells, but sum() is not an atomic snapshot; use locks or concurrent collections when an invariant spans multiple variables or steps.

    19. Likely Interview Questions

    Question Crisp Answer
    What is CAS? Compare-And-Set (or Compare-And-Swap): an atomic conditional update that replaces the value only if it still equals the expected value, returning a boolean.
    What does compareAndSet(expected, new) return? true if the current value equaled expected and was replaced; false if it did not and the value was left unchanged.
    Why is CAS called optimistic? It assumes no interference, computes the update, and detects any interference at update time instead of blocking other threads first.
    What is the lock-free recipe? Read the current state, compute the desired state, attempt CAS, and retry after re-reading if the CAS fails.
    Why does a CAS retry loop terminate? Each failure re-reads a fresh state; once interference stops, the next CAS compares against an unchanged value and succeeds.
    How is CAS implemented? The JVM maps it to platform atomic instructions or intrinsics (for example locked CMPXCHG on x86), coordinated at the cache-line/coherence level with JMM guarantees.
    Does CAS eliminate contention? No. It removes lock ownership, but concurrent CAS attempts on the same value still fail and retry, wasting CPU under high contention.
    What is starvation in a lock-free algorithm? An unlucky thread repeatedly loses the race while others make progress; lock-free guarantees system-wide, not per-thread, progress.
    What is the ABA problem? A value changes A → B → A between a thread's read and its CAS, so the CAS succeeds even though the state changed, potentially corrupting a reused-node structure.
    How do you fix ABA? Add a version or mark: AtomicStampedReference (reference + integer version) or AtomicMarkableReference (reference + boolean mark).
    Why use atomic arrays? They make each array element independently atomic, unlike a plain array where array[i]++ is a non-atomic read-modify-write.
    What do LongAdder and friends solve? Single-cell counters suffer under high contention; striped cells spread writes across threads, and sum() combines them, though it is not an atomic snapshot.

    20. Final Summary

    read X  →  compute Y  →  compareAndSet(X, Y)
                                |-- true  →  done
                                `-- false →  reread (backoff) → retry

versioned CAS :  (A, 1) → (B, 2) → (A, 3)
                 expected (A, 1)  ≠  current (A, 3)   →  ABA detected, CAS fails

contention  →  retries, cache-line bouncing, starvation   (lock-free ≠ wait-free)

LongAdder : many threads  →  striped cells  →  sum() combines  (not a snapshot)
    • CAS → one atomic conditional update; the primitive behind lock-free code.
    • Recipe → read, compute, compare-and-set; on failure reread and retry.
    • Guarantees → system-wide progress; not wait-free, and not automatically faster under contention.
    • Atomic arrays → independent atomic slot per index; multi-slot transactions need broader coordination.
    • Visibility → atomic reads/writes behave like volatile; a successful update publishes prior writes (happens-before).
    • ABA → equal-looking value with changed history; fix with AtomicStampedReference or AtomicMarkableReference.
    • High contention → LongAdder/DoubleAdder/LongAccumulator with striped cells; sum() is not atomic.
    • Boundaries → multi-variable or multi-step invariants belong in locks or concurrent collections.

    Golden rule Reach for CAS only when the invariant fits one small, recomputable atomic transition; otherwise choose the mechanism that keeps the invariant correct, understandable, and efficient.

    One-line takeaway: CAS makes a conditional single-value update atomic, the read → compute → CAS retry loop turns that into lock-free progress, and versioning, atomic arrays, and striped adders handle the cases where the simple value alone is not enough.
