    Circuit Breaker + Retry

    6 sections · 532 words

    Stop hammering what is already down. Reliability & Resilience, concept 32 of 36.

    The Idea

    Retrying every request against a service that is already failing just adds more load to something already struggling, and makes the calling service slow while it sits waiting on failures that were never going to succeed.

    A circuit breaker tracks failures and trips once there are too many: it moves from Closed (calls flow normally) to Open (every call fails immediately). After a cooldown it moves to Half-Open and lets through a small, limited number of test calls: enough successes close it again, a failure reopens it.

    Three states:

    1. Closed: calls flow.
    2. Open: fails fast.
    3. Half-Open: limited test calls; a healthy test call resets it back to Closed.
    • Retries, when they do happen, should use backoff, waiting longer between each attempt, so they do not all pile onto a recovering service at once.
    • Pair this with health checks (is the instance actually alive) and failover (send traffic to a standby): three layers of the same idea, notice failure, react to it.

    Watch Out For

    • A threshold set too sensitive trips the circuit on ordinary, transient blips, cutting off a service that did not actually need it.
    • A threshold set too loose lets real outages keep hammering a struggling dependency far longer than necessary.

    Where You Will See It

    • Netflix's Hystrix, the library that popularized this exact pattern for microservices.
    • Resilience4j and Polly, modern circuit-breaker libraries for Java and .NET.
    • Any service-to-service call in a microservices architecture where a failing dependency should not cascade into a failing caller.

    How It Connects

    • Service Discovery: both answer the same underlying question, is this instance healthy, at different points in the call path.
    • Idempotency: retries triggered after a circuit closes again need to be safe to repeat.
    • Load Balancing: a health check and a circuit breaker solve a similar problem at different layers, one before routing, one at the call site.

    Follow-Up Questions

    1. A downstream service starts failing every request. What does a circuit breaker do after enough failures? It trips to Open: every call fails immediately, with no network call even attempted, giving the struggling service room to recover.

    2. The circuit is Open. After a cooldown, what happens next? It moves to Half-Open and lets through a small, limited number of test calls, one in some implementations, a few in others that want a more meaningful sample. Enough succeed, and it closes again. A failure reopens it.

    3. Why is failing fast, while Open, better than letting every request time out slowly against the failing service? It stops adding load to something already struggling, and keeps the calling service responsive instead of piling up slow, doomed requests.

    4. Retries are paired with a circuit breaker. Why do they need backoff, waiting longer between each attempt? So retries do not all pile onto a recovering service at once, which could trip it straight back to failing.

    Recall It As

    Closed means normal. Open means fail fast. Half-open means test carefully before trusting it again.
