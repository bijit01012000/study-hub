    Lecture 02 — Build Your First Spring Boot Application

    17 sections · 3,503 words

    Lecture 02

    Scope evidence: "Build Your First Spring Boot Application | REST API" (playlist map, verified). The repo Lecture 02 folder contains a complete Maven Spring Boot demo project under code/demo (mvnw, pom.xml, DemoApplication.java, HelloController.java, application.properties) plus its tests (DemoApplicationTests.java, HelloControllerTest.java), alongside the lecture notes.

    This lecture takes the theory of Lecture 01 and turns it into a running web application. We build a tiny Spring Boot app, open it in a browser, and watch a request travel from a URL to a Java method and back. The point is not to understand every internal detail yet -- it is to feel how fast Spring Boot is, and to get curious about the machinery working behind one line in the browser.

    1. What We Are Building

    We are building a simple web application where the browser sends a request to our Spring Boot application, and the application sends back a response:

    Browser
   |
   | Request
   v
Spring Boot Application
   |
   | Response
   v
Browser

    We create exactly one endpoint:

    localhost:8080/hello

    Opening that URL in the browser returns:

    Hello World

    The output looks trivial, but many important questions are hidden behind it:

    • How does the browser talk to Java?
    • How does Java understand URLs?
    • Who starts the server?
    • Who listens on port 8080?
    • How does /hello get connected to our Java method?

    Important: We will not answer all of these deeply today. This lecture builds the curiosity; the later lectures build the internals.

    2. Ports, Localhost, and How the Browser Finds the Server

    Before running anything, we need the idea of a port. Suppose your laptop is connected to a network and it has an IP address, for example:

    192.168.1.10

    Now imagine many applications running on that same laptop: Chrome, WhatsApp, Zoom, Spotify, and our Spring Boot application. When data arrives at the laptop, how does the operating system know which application should receive it? That is exactly what a port number solves.

    • An IP address identifies the machine.
    • A port number identifies the application running inside that machine.
    192.168.1.10:8080
     |         |
   machine   application (listening on port 8080)
    Part Example Identifies
    IP address 192.168.1.10 The machine on the network
    Port number 8080 The application inside that machine

    A single machine can host many applications, each on its own port:

    Application Port
    Chrome 5000
    WhatsApp 5222
    Zoom 8801
    Spring Boot app 8080

    Memory aid: IP = which building, port = which door. The IP brings the data to the correct building; the port delivers it to the correct flat inside.

    Localhost

    Students often confuse localhost, an IP address, and a port number. In simple words:

    localhost = your own machine

    localhost is equivalent to:

    127.0.0.1

    So localhost:8080 means: send the request to my own machine on port 8080. If our Spring Boot application is running on port 8080, the browser reaches it through:

    http://localhost:8080

    How the browser knows which port to use

    When we type a normal website URL such as www.coderarmy.in, we usually do not mention any port. Browsers use default ports:

    Protocol Default port
    http 80
    https 443

    So when we write https://www.coderarmy.in, the browser automatically assumes port 443. When we write http://www.coderarmy.in, it assumes port 80. But a local Spring Boot application usually runs on port 8080, so we mention it manually: http://localhost:8080.

    Important: DNS gives the IP address of a domain. The port is either mentioned in the URL or decided by the protocol default. For https://www.coderarmy.in: DNS resolves the domain to an IP, and HTTPS tells the browser to use port 443 by default.

    3. Development Setup

    For this series we use IntelliJ IDEA. You can use any editor, but IntelliJ is widely preferred for Java and Spring Boot development because it has strong support for:

    • Java
    • Maven
    • Spring Boot
    • code navigation
    • auto-completion
    • project structure
    • debugging

    Before creating the project, make sure Java is installed and working. Verify it with:

    java -version

    If Java is not installed, install it first before moving ahead.

    4. Why Spring Initializr Exists (and Choosing a Version)

    Imagine starting a Java web project from scratch. Before writing even one line of business logic, you would have to do a lot of repetitive setup:

    1. Create the folder structure.
    2. Create the Maven configuration.
    3. Select the Spring Boot version.
    4. Select the Java version.
    5. Add the required dependencies.
    6. Configure the package structure.
    7. Prepare the project metadata.

    Every Spring Boot project needs a similar basic structure, and doing that setup by hand every time is wasted effort. To solve this problem, the Spring team created Spring Initializr, a project generator for Spring applications. It creates the basic project skeleton so we can quickly start writing application logic.

    Put simply: Spring Initializr helps us create a ready-to-use Spring Boot project. The repetitive setup it removes is exactly the list above.

    Repetitive task Handled by Spring Initializr
    Folder structure Generated automatically
    Maven configuration Generated automatically
    Spring Boot version Selected for us
    Java version Selected for us
    Dependencies Added from our choices
    Package structure Generated automatically
    Project metadata Captured from our choices

    Spring Initializr lets us choose:

    • project type
    • programming language
    • Spring Boot version
    • project metadata
    • packaging type
    • Java version
    • dependencies

    Choosing the right Spring Boot version

    On Spring Initializr we may see versions tagged as a stable release, SNAPSHOT, or RC:

    Version kind Meaning Suitable for us?
    Stable release Tested, finished, suitable for normal development Yes -- prefer this
    RC (Release Candidate) Almost ready, but still not the final stable release Not for beginners
    SNAPSHOT Work in progress, may contain bugs, not final No

    Golden rule: For beginners and real projects, always prefer a stable release. It is tested and suitable for normal development.

    5. What is a Dependency

    When we build a Java project, we often need external libraries. For example, if we want our Java application to connect with MySQL, we need a MySQL connector library. That reusable external code is called a library; when our project needs that library to work, it becomes a dependency.

    Simple definition:

    A dependency is an external library required by our project.

    Typical examples:

    Dependency What it gives us
    Spring Web Web layer, controllers, embedded server
    MySQL Connector Database connectivity to MySQL
    Spring Data JPA Repository-style database access
    Spring Security Authentication and authorization
    Lombok Less boilerplate (getters, constructors)
    Hibernate ORM implementation

    In Maven projects, dependencies are added inside the pom.xml file. When we select "Spring Web" in Spring Initializr, that dependency is written into pom.xml for us.

    6. JAR Packaging and Project Tour

    Modern Spring Boot applications usually use JAR packaging. JAR stands for Java Archive. A Spring Boot JAR can contain our application code along with the required setup to run the application. This is one reason Spring Boot applications are easy to run: instead of manually deploying to an external server, we can run the application directly.

    After creating the project from Spring Initializr and opening it in IntelliJ, we see a standard structure:

    Path Purpose
    src/main/java Our Java source code (including the main application class)
    src/main/resources Configuration files and static resources
    pom.xml Maven configuration: project information and dependencies
    application.properties Configuration for our Spring Boot application

    application.properties is important early on: for example, we can change the server port from here.

    The main application class is the class from where the Spring Boot application starts. It usually contains the main() method:

    @SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

    In the repo, this class is com/example/demo/DemoApplication.java. For now we only need to understand that this class starts our Spring Boot application; @SpringBootApplication is explained deeply later.

    7. What is a Controller and @RestController

    A Controller is the entry point for incoming web requests. A simple way to think about it:

    • A controller is like the receptionist of our application.
    • When a request comes to the application, the controller receives it and decides what response should be sent back.

    For example:

    Browser sends request to /hello
Controller receives the request
Controller returns Hello World

    @RestController is an annotation in Spring. It tells Spring:

    This class can handle HTTP requests and return data directly as a response.

    It makes the class eligible to receive web requests:

    @RestController
public class HelloController {
}

    Interviewer's perspective: Do not memorize annotations in isolation. @RestController answers the question "which classes may receive web requests?" -- that is the first thing a component-scanning Spring looks for at startup. We revisit annotations and controllers in detail later.

    8. Creating Our First Endpoint

    Now we add a method to the controller and map a URL to it:

    @RestController
public class HelloController {

    @GetMapping("/hello")
    public String sayHello() {
        return "Hello World";
    }
}

    Breaking it down:

    Piece What it tells Spring
    @RestController This class can handle HTTP requests
    @GetMapping("/hello") Run this method when a GET request comes to /hello
    sayHello() The Java method that gets executed
    return "Hello World"; The response sent back to the browser

    In the repo, this class is com/example/demo/HelloController.java. So when we open:

    http://localhost:8080/hello

    the browser displays Hello World.

    Important: The mapping annotation is what makes the method reachable. Without @GetMapping("/hello"), sayHello() is just an ordinary Java method that nothing calls over HTTP.

    9. What Happened When We Ran the Application

    When we run the Spring Boot application, we may see a message like:

    Tomcat started on port 8080

    This is very important, so let us state it plainly. We did not install Tomcat separately. We did not write socket programming code. We did not manually create a server. Still, Tomcat started. Why?

    Because Spring Boot includes and configures an embedded Tomcat server for us when we use the web dependency. Spring Boot starts the application and also starts the embedded Tomcat server. Tomcat is the actual server listening on the port.

    The correct understanding of the layers:

    • Spring Boot starts and configures the application.
    • Spring MVC maps the request to the correct controller method.
    • Embedded Tomcat listens for HTTP requests.

    Important: Tomcat is the actual server listening on the port -- not our HelloController. Our job is to write the controller; Spring Boot's job is to stand up the server around it.

    10. Changing the Port and the Complete Request Flow

    By default, Spring Boot runs on port 8080. We can change it using application.properties:

    server.port=9090

    After changing this and restarting the application, the app runs on http://localhost:9090, and our endpoint becomes:

    http://localhost:9090/hello

    Important: Spring Boot reads the configuration, but the embedded Tomcat server listens on the configured port. If we set server.port=9090, Tomcat starts listening on port 9090.

    Note that the change takes effect only after a restart. Updating application.properties while the app is running does not move the listener; the embedded Tomcat must start again on the new port.

    The complete flow of our first Spring Boot application:

    Browser sends request to localhost:8080/hello
        |
        v
Request reaches embedded Tomcat
        |
        v
Spring MVC checks the available mappings
        |
        v
/hello is matched with sayHello()
        |
        v
sayHello() returns "Hello World"
        |
        v
Response goes back to the browser
        |
        v
Browser displays Hello World

    This is what happens behind one simple line in the browser: localhost:8080/hello.

    11. Why This Feels So Fast -- and Why Internals Still Matter

    In less than a few minutes we created a working web application. We wrote very little code. But behind that simple controller, Spring Boot did many things for us:

    • created the application context
    • started embedded Tomcat
    • configured Spring MVC
    • detected the controller class
    • registered the /hello endpoint
    • handled the HTTP request and response
    • returned the data to the browser

    That is the power of Spring Boot: it lets developers focus on business logic instead of repeating infrastructure setup again and again.

    Then why learn internals?

    A common question: if Spring Boot does everything automatically, why learn Tomcat, Servlets, Maven, Spring Core, MVC, IoC, and Dependency Injection? The answer is simple: Spring Boot helps us start fast, but internals help us solve real problems. Writing basic annotations is easy -- many tools and code generators can produce @RestController and @GetMapping. Real engineering starts when something does not work.

    Example 1 -- the browser shows:

    404 Not Found

    Now we must ask: Did Spring detect my controller? Is the package structure correct? Did component scanning happen? Was the bean created? Did Spring MVC register the mapping? Is the URL correct? Did Tomcat receive the request? These questions cannot be answered by memorizing annotations; they require understanding the internal flow.

    Example 2 -- the application starts slowly (say, 10 seconds). Possible causes:

    • too many beans being created
    • database connection taking time
    • heavy startup logic running
    • external service call blocking startup
    • auto-configuration doing extra work

    Example 3 -- the controller never receives the request. Possible reasons:

    • wrong port
    • wrong URL
    • application not running
    • controller not detected
    • incorrect annotation
    • context path configured
    • request blocked by security

    The industry reality

    In real projects, companies do not pay engineers only for writing @RestController -- that part is easy, and AI tools, code generators, and IDEs can write basic code. Companies pay engineers for understanding:

    • why something is not working
    • how different layers communicate
    • how to debug production issues
    • how to design maintainable systems
    • how to make the application reliable

    Golden rule: Spring Boot gives speed; Spring fundamentals give control. That is why learning the internals is worth it.

    12. Myth vs Reality

    Myth Reality
    "We must install Tomcat to run a Spring Boot app" Spring Boot includes and configures an embedded Tomcat when the web dependency is present
    "localhost and 127.0.0.1 are different machines" localhost is equivalent to 127.0.0.1 -- both mean your own machine
    "An IP address alone delivers data to the right app" The IP identifies the machine; the port identifies the application inside it
    "A URL without a port has no port" The browser fills in the protocol default: 80 for http, 443 for https
    "SNAPSHOT is the newest, so it is the best choice" SNAPSHOT is work in progress and may contain bugs; prefer a stable release
    "A dependency is code we write" A dependency is an external library our project needs; it lives in pom.xml
    "The controller is the server that listens on the port" Embedded Tomcat listens; the controller only handles a matched request

    13. Common Trap Questions

    Trap 1 — "The IP address is enough to reach an application." Verdict: False. The IP gets the data to the machine; the port number tells the OS which application should receive it.

    Trap 2 — "localhost is a special server on the internet." Verdict: False. localhost means your own machine and is equivalent to 127.0.0.1.

    Trap 3 — "Spring Boot requires us to install Tomcat separately." Verdict: False. Spring Boot includes and configures an embedded Tomcat server when the web dependency is used, which is why Tomcat started on port 8080 appears without any manual setup.

    Trap 4 — "We can pick any Spring Boot version; SNAPSHOT is fine." Verdict: False. SNAPSHOT is work in progress and RC is not final; beginners and real projects should prefer a tested stable release.

    Trap 5 — "The controller method is invoked because it returns a String." Verdict: False. The method runs because @GetMapping("/hello") maps the /hello GET request to it; without the mapping it is never called over HTTP.

    Trap 6 — "Changing server.port changes which class handles the request." Verdict: False. It changes the port embedded Tomcat listens on; Spring MVC still maps /hello to sayHello() the same way.

    Trap 7 — "If Spring Boot automates everything, internals are unnecessary." Verdict: False. Automation handles the happy path; debugging 404s, slow startup, and missing requests requires understanding what happens behind the scenes.

    14. Points to Remember

    1. An endpoint is a URL our application answers, here localhost:8080/hello, which returns Hello World.
    2. An IP address identifies the machine; a port number identifies the application running inside that machine.
    3. localhost means our own machine and is equivalent to 127.0.0.1.
    4. Browsers use protocol defaults: port 80 for http and port 443 for https; DNS resolves domains to IPs.
    5. Spring Initializr is a project generator that creates a ready-to-use Spring Boot skeleton.
    6. A dependency is an external library our project requires, and in Maven it is declared in pom.xml.
    7. Prefer a stable Spring Boot release over SNAPSHOT or RC.
    8. @RestController marks a class as able to handle web requests; @GetMapping("/hello") maps a GET request to a method.
    9. Spring Boot starts the app and an embedded Tomcat server; Tomcat is the actual server listening on the port.
    10. Spring Boot gives speed, but internals give control -- that is what lets us fix real production problems.

    15. Likely Interview Questions

    Question Crisp Answer
    What is a port? A number that identifies an application running inside a machine, so the OS delivers data to the right program.
    Difference between an IP address and a port? IP identifies the machine on the network; the port identifies the application inside it.
    What is localhost? Your own machine; it is equivalent to 127.0.0.1.
    How does the browser choose a port for https://site? It uses the protocol default: 443 for https (and 80 for http) unless a port is explicitly given.
    Why does Spring Initializr exist? To generate the repetitive Spring Boot project skeleton -- structure, Maven config, versions, and dependencies -- quickly.
    What is a dependency? An external library required by our project, declared in pom.xml in Maven projects.
    Stable vs SNAPSHOT vs RC? Stable is tested and final; RC is almost ready but not final; SNAPSHOT is work in progress that may contain bugs.
    What is a Spring Boot controller? The entry point for incoming web requests; it receives a request and decides the response.
    What does @RestController do? Marks a class as able to handle HTTP requests and return data directly as the response.
    What does @GetMapping("/hello") do? Maps a GET request for /hello to the annotated Java method.
    What is embedded Tomcat? A Tomcat server bundled and configured inside the Spring Boot app; it actually listens on the port.
    How do we change the server port? Set server.port=9090 in application.properties and restart; the embedded Tomcat then listens on that port.

    16. Final Summary

    Browser -> localhost:8080/hello
        |
        v
Embedded Tomcat (listens on the port)
        |
        v
Spring MVC (checks mappings)
        |
        v
HelloController.sayHello() -> "Hello World"
        |
        v
Response back to browser
    • A port identifies the application; an IP identifies the machine; localhost is our own machine.
    • Spring Initializr generates the project; dependencies live in pom.xml.
    • @RestController + @GetMapping("/hello") create our first endpoint.
    • Spring Boot starts the app and embedded Tomcat, which does the actual listening.
    • Changing server.port moves the port Tomcat listens on.
    • Spring Boot gives speed; internals (Maven, Servlets, Tomcat, Spring Core, IoC, DI, beans, Spring MVC, auto-configuration) give control.

    One-line takeaway: one tiny controller produced a working web application because Spring Boot silently stood up embedded Tomcat and Spring MVC behind it -- and understanding that machinery is what turns "it works" into "I know why."
