    SOLID Principles

    10 sections · 763 words

    Principle · LLD Core Concepts · Concept 02 of 09

    The Idea

    The Five, One Line Each

    • S: one class, one reason to change.
    • O: open to behaviour, closed to edits.
    • L: a subtype honors the parent's promises.
    • I: thin, focused interfaces only.
    • D: depend on abstractions, not concretes.

    One job each. One per letter.

    Before

    class ReportManager {
    // S: content + format + storage
    MySqlDatabase db = new MySqlDatabase();
    // D: tied to one concrete DB
    void generate(String type, Data d) {
        Report r = build(d);
        if (type.equals("CSV"))
            writeCsv(r);
            // O: a new format means editing this method
        else if (type.equals("PDF"))
            writePdf(r);
        else
            throw new IllegalArgumentException(type);
        db.save(r);
    }
}

    Three reasons to change: content, format, storage.

    After

    interface Formatter {
    // the step that changes
    byte[] format(Report r);
}
class CsvFormatter implements Formatter { .. }
class PdfFormatter implements Formatter { .. }
interface Database { void save(Report r); }
// not MySqlDatabase
class ReportManager {
    private final Formatter fmt;  // both injected, never built here
    private final Database db;
    ReportManager(Formatter fmt, Database db) {
        this.fmt = fmt; this.db = db;
    }
    void generate(Data d) {
        // one job: build, then save
        db.save(build(d));
    }
}

    Don't Force All Five At Once

    • A 2-method, 1-impl class doesn't need an interface yet.
    • Injecting 6 interfaces "to be SOLID" is its own smell.

    Quick Check

    Say it in one breath: one reason, open/closed, substitutable, thin interfaces, depend on abstractions.

ADD A FORMAT, NOTHING ELSE CHANGES

    The Move (3 Steps)

    1. Find what's actually growing. New formats, new storage backends. That growth line is your SRP/OCP boundary.
    2. Extract an interface where a second case already exists (or is clearly coming), not before.
    3. Inject the interface, never the concrete class. The holder depends on the abstraction; the abstraction never depends back.

    In The Interview

    "This class has three reasons to change: content, format, storage. I'd keep content in ReportManager, put format behind a Formatter interface so a new format is a new class, and inject Database instead of newing a concrete one so it's swappable and testable."

    How It's Different

    The Confusion Pairs

    SRP vs one class per file. SRP is about reasons to change, not size. A small class can still violate it if two unrelated people can each force an edit.

    LSP vs "it compiles." Compiling isn't enough. A subtype that throws on a method the parent always allowed, or narrows what it accepts, breaks LSP even with a green build.

    OCP vs YAGNI. OCP says stay open to extension. YAGNI says don't build the extension point yet. Resolve it by adding the seam when the second real case shows up, not the first.

    ISP vs DIP. DIP says depend on an interface. ISP says keep that interface thin. One fat interface can satisfy DIP and still violate ISP.

    They Say: "now add a JSON report format"

    • With it: write one JsonFormatter class, hand it in. Nothing else moves.
    • Without: they watch you reopen generate() and add another else if.

    Watch Out For

    • S: count reasons to change, not method count. A class with 10 tiny related methods can still have one job.
    • O: don't add an extension seam nobody asked for yet: that's OCP fighting YAGNI and losing on purpose.
    • L: a subtype throwing UnsupportedOperationException on an inherited method is an LSP violation, not an edge case.
    • I: a 12-method "Manager" interface that forces every implementer to stub 9 of them is the smell: split it by caller.
    • D: DIP means depend on an abstraction, not "add an interface to everything." A concrete class you will never swap doesn't need one.
