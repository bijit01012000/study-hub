    Design a Search System

    3 sections · 3,433 words

    Three levels: Level 1 — The Shape, Level 2 — The Defence, Level 3 — The Edges.

    Level 1 — The Shape (Foundation)

    Pacing: 3 min ask · 5 min trace flow · 7 min read why.

    The Ask

    Functional

    • Full-text query → ranked results
    • Index tracks primary writes, no dualwrite

    Non-Functional

    • No dual-write from the app ← forces CDC off the primary's own log

    Agree These First

    Auth and query-parsing (booleans, facets) are out of scope. Launch defaults: 5 s freshness SLA (p99, write → searchable), 8 shards, 10-min CDC durability buffer.

    The Shape

    Components and flow:

    • App — Writes documents · later issues search queries; writes avg 200/s · peak 600/s
    • (2) Primary Store — Durable source of truth for document rows — NOT shaped for full-text search
    • (3) CDC Stream — Tails the Primary Store's own change log · ordered, durable
    • (4) Search Store — Inverted index · term → postings list — what queries actually hit
    • search query

    Data model: documents doc_id PK → content, updated_at.

    Line = flow type: INDEX · write → derived store; QUERY · read & rank.

    Say It Like This

    "Search needs a fundamentally different structure than the primary store — an inverted index, not a row store's WHERE clause. So instead of dual-writing from the app, I'd tail the Primary Store's own change log with CDC — one source of truth, so a partial failure can always be replayed. And I wouldn't force every write to be synchronously reflected in search — bounded staleness, not zero lag, is the honest target."

    Defend It

    Decision Prefer Avoid
    (4) A second store, not a WHERE Inverted index — term → docs, ranked. The shape matching actually needs A row store's own indexes aren't built for "find every doc with these terms"
    (3) CDC, not dual writes Tails one durable log — always catches up from what actually happened Dual writes can partially fail — no single log to recover from
    (2) Bounded staleness A bounded lag, not zero lag — the honest, statable target Sync-index every write → ties write latency to the indexing pipeline

    Capacity Math

    Quantity Derivation Value
    Primary Store 50,000,000 docs × 2,000 B avg 100.0 GB
    Writes 200/s avg · peak × 3 600 /s
    In-flight buffer Little's Law: 600/s peak × 5 s SLA 3,000 docs
    Index size 50,000,000 × 50 terms/doc × 12 B/posting 30.0 GB
    Index : Primary 30.0 GB ÷ 100.0 GB — differently shaped, not smaller 0.30×
    Shards ≤4 GB/shard → 8 shards, 3.75 GB each 8

    Round hard, out loud. The index (30.0 GB) is smaller than the primary store (100 GB) — but that's not the point. It's a differently-shaped structure a row store's own indexes can't produce.

    Before You Draw Anything — The Four Moves

    1. Clarify, don't assume. Search over what — documents, products, one field or many? Say ranked results matter, not just matching. — Two minutes of questions buys the whole design.
    2. Agree the scale out loud. "50M documents, 200 writes/s avg, a 5-second p99 freshness SLA." Now every choice has a reason. — An unstated number is an undefendable design.
    3. Draw the happy path only. Application → Primary Store → CDC Stream → Search Store. Get agreement before adding anything. — Boxes you add before agreement are boxes you'll defend alone.
    4. Name one trade-off unprompted. "I wouldn't dual-write from the app — I'd tail the Primary Store's own change log so there's one source of truth to recover from." — This is the single move that separates L1 from a junior answer.

    What L1 Is Testing

    • Do you name the inverted index unprompted, not a WHERE clause?
    • Do you reach for CDC over dual writes, and say why?
    • Did you separate matching from ranking, unasked?

    The Follow-Ups That Decide It

    1. Why not just add a full-text WHERE clause to the Primary Store instead of a whole second store? (ref 4 — tests: recall that a row store's own indexes aren't shaped for term → doc lookups, ranked by relevance)
    2. The app just wrote a document. Why not have it write to the Search Store too, right then? (ref 3 — tests: dual-write failure awareness — CDC as the single source of truth to recover from)
    3. If the index can lag, why isn't every search just wrong? (ref 4 — tests: bounded lag vs. zero lag — the honest target, not a hand-wave)

    At L1 you are being judged on one thing: can you produce a coherent shape and defend three choices inside it. Depth is page 2 — do not reach for it here. Ghosted boxes are what arrives next; you should be able to guess two of them.

    Level 2 — The Defence (Intermediate)

    Pacing: 5 min ask · 15 min trace flow · 10 min read why · 30 min cover & answer.

    The Ask

    Functional

    • Full-text query → ranked results
    • Index tracks primary writes, no dualwrite
    • Corpus outgrows one index node's memory

    Non-Functional

    • No dual-write from the app ← forces CDC off the primary's own log
    • Staleness must be measured ← forces a lag/staleness monitor
    • Index outgrows one node ← forces sharding + fan-out/merge

    Out of Scope — Say It Aloud

    • Auth/authz for who may write or search
    • Query parsing — booleans, facets
    • Personalization / per-user ranking

    Agree These First

    Auth and query-parsing (booleans, facets) are out of scope. Launch defaults: 5 s freshness SLA (p99, write → searchable), 8 shards, 10-min CDC durability buffer.

    The Shape

    Components and flow:

    • App — Writes documents · later issues search queries; writes avg 200/s · peak 600/s
    • (2) Primary Store — Durable source of truth for document rows — NOT shaped for full-text search; 50,000,000 docs · 100.0 GB
    • (3) CDC Stream — Tails the Primary Store's own change log · ordered, durable
    • (5) Indexing Pipeline — Consumes CDC events · transforms rows into indexable documents
    • (4) Search Store — Inverted index · term → postings list — what queries actually hit; 30.0 GB · 8 shards · 3.75 GB/shard
    • (6) Query Service
    • (9) Index Shard Router — Routes writes to a shard · fans queries across all shards
    • (7) Ranking / Scorer — Term frequency, doc frequency, field boosts — matching ≠ ranking
    • (8) Staleness Monitor — Measures CDC/indexing lag between ② and ④
    • search query — avg 2,000/s · peak 6,000/s

    Data model:

    • documents doc_id PK · content · updated_at · version
    • postings term PK → doc_id[], tf, positions

    Line = flow type: INDEX · write → derived store; QUERY · read & rank; CHECK · dependency / monitor.

    Say It Like This

    "Search needs a fundamentally different structure than the primary store — an inverted index, not a row store's WHERE clause. So instead of dual-writing from the app, I'd tail the Primary Store's own change log with CDC — one source of truth, so a partial failure can always be replayed. And I wouldn't force every write to be synchronously reflected in search — bounded staleness, not zero lag, is the honest target."

    Defend It

    Decision Prefer Avoid
    (4) A second store, not a WHERE Inverted index — term → docs, ranked. The shape matching actually needs A row store's own indexes aren't built for "find every doc with these terms"
    (3) CDC, not dual writes Tails one durable log — always catches up from what actually happened Dual writes can partially fail — no single log to recover from
    (2) Bounded staleness A bounded lag, not zero lag — the honest, statable target Sync-index every write → ties write latency to the indexing pipeline
    (5) Its own pipeline stage Tokenizing is real work — its own scalable, retryable stage CDC straight into the index → couples ingestion to indexing
    (7) A separate ranking step Matching ≠ ranking — relevance scoring is its own problem Matched order alone → a term match says nothing about relevance
    (9) Sharding the index The corpus outgrows one node's memory — build the seam early Single node → a forced migration once memory runs out

    Capacity Math

    Quantity Derivation Value
    Primary Store 50,000,000 docs × 2,000 B avg 100.0 GB
    Writes 200/s avg · peak × 3 600 /s
    In-flight buffer Little's Law: 600/s peak × 5 s SLA 3,000 docs
    Index size 50,000,000 × 50 terms/doc × 12 B/posting 30.0 GB
    Index : Primary 30.0 GB ÷ 100.0 GB — differently shaped, not smaller 0.30×
    Shards ≤4 GB/shard → 8 shards, 3.75 GB each 8
    Postings 50,000,000 docs × 50 terms/doc 2,500,000,000
    Queries 2,000/s avg · peak × 3 6,000 /s

    Storage was never the constraint — staying hot and fresh is. 30 GB needs 8 shards to fit in-memory, and every write has a 5-second budget to become searchable, measured via a 3,000-document buffer.

    What Breaks — Say It Before They Ask

    • (5) Indexing Pipeline falls behind. CDC events pile up in ③'s durable log; nothing is lost, but staleness (⑧) grows until it catches up. — Fix: drain the backlog at a steady rate — never fire the whole thing into ④ at once
    • (3) A CDC connector loses its offset. It crashes without checkpointing and doesn't know where it left off. — Fix: resume from the LAST ACKNOWLEDGED offset in ②'s own log, never from "now"

    The Follow-Ups That Decide It

    1. Why not just add a full-text WHERE clause to the Primary Store instead of a whole second store? (ref 4 — tests: recall that a row store's own indexes aren't shaped for term → doc lookups, ranked by relevance)
    2. The app just wrote a document. Why not have it write to the Search Store too, right then? (ref 3 — tests: dual-write failure awareness — CDC as the single source of truth to recover from)
    3. If the index can lag, why isn't every search just wrong? (ref 4 — tests: bounded lag vs. zero lag — the honest target, not a hand-wave)
    4. Why not have the CDC stream write straight into the inverted index? (ref 5 — tests: recall that turning a row into indexable terms is real work, worth its own retryable stage)
    5. The index lookup already returns the matching documents. Why rank them separately? (ref 7 — tests: matching vs. ranking as different problems)
    6. Why shard the index instead of just scaling up one node's RAM? (ref 9 — tests: the corpus outgrowing single-node memory, and building the seam in early)

    Cover The Sheet · Answer Aloud

    Use it as revision: cover the right rail and the two panels to your left, then walk the numbered path out loud. If you cannot say why a box is there and what breaks it, that box is your gap.

    Level 3 — The Edges (Advanced)

    Pacing: 10 min ask · 25 min trace flow · 15 min read why · 40 min cover & answer.

    The Ask

    Functional

    • Full-text query → ranked results
    • Index tracks primary writes, no dualwrite
    • Corpus outgrows one index node's memory
    • Rebuild the index from scratch
    • Opt-in check: is my write visible yet?

    Non-Functional

    • No dual-write from the app ← forces CDC off the primary's own log
    • Staleness must be measured ← forces a lag/staleness monitor
    • Index outgrows one node ← forces sharding + fan-out/merge
    • Index/query text rules must match ← forces one shared tokenizer
    • Standard SLA can't block the rare case ← forces an opt-in freshness check

    Out of Scope — Say It Aloud

    • Auth/authz for who may write or search
    • Query parsing — booleans, facets
    • Personalization / per-user ranking

    Agree These First

    Auth and query-parsing (booleans, facets) are out of scope. Launch defaults: 5 s freshness SLA (p99, write → searchable), 8 shards, 10-min CDC durability buffer.

    The Shape

    Components and flow:

    • App — Writes documents · later issues search queries; writes avg 200/s · peak 600/s
    • (2) Primary Store — Durable source of truth for document rows — NOT shaped for full-text search; 50,000,000 docs · 100.0 GB
    • (3) CDC Stream — Tails the Primary Store's own change log · ordered, durable
    • (5) Indexing Pipeline — Consumes CDC events · transforms rows into indexable documents
    • (12) Tokenizer / Analyzer — Shared by indexing & query — one point of truth
    • (4) Search Store — Inverted index · term → postings list — what queries actually hit; 30.0 GB · 8 shards · 3.75 GB/shard
    • (6) Query Service
    • (9) Index Shard Router — Routes writes to a shard · fans queries across all shards
    • (7) Ranking / Scorer — Term frequency, doc frequency, field boosts — matching ≠ ranking
    • (8) Staleness Monitor — Measures CDC/indexing lag between ② and ④
    • (11) Dead Letter / Reindex Queue — Events ⑤ couldn't apply — retried, never dropped
    • (10) Reindex / Backfill Job — Bulk-rebuilds ④ from ② — schema change, ranking change, or drift too severe to catch up
    • (13) Freshness Token Check — Opt-in: is my own recent write guaranteed visible yet?
    • search query — avg 2,000/s · peak 6,000/s

    Data model:

    • documents doc_id PK · content · updated_at · version
    • postings term PK → doc_id[], tf, positions

    Line = flow type: INDEX · write → derived store; QUERY · read & rank; CHECK · dependency / monitor; BACKFILL · bypasses CDC.

    Say It Like This

    "Search needs a fundamentally different structure than the primary store — an inverted index, not a row store's WHERE clause. So instead of dual-writing from the app, I'd tail the Primary Store's own change log with CDC — one source of truth, so a partial failure can always be replayed. And I wouldn't force every write to be synchronously reflected in search — bounded staleness, not zero lag, is the honest target."

    Defend It

    Decision Prefer Avoid

    (3) CDC, not dual writes Tails one durable log — always catches up from what actually happened Dual writes can partially fail — no single log to recover from
    (2) Bounded staleness A bounded lag, not zero lag — the honest, statable target Sync-index every write → ties write latency to the indexing pipeline
    (5) Its own pipeline stage Tokenizing is real work — its own scalable, retryable stage CDC straight into the index → couples ingestion to indexing
    (7) A separate ranking step Matching ≠ ranking — relevance scoring is its own problem Matched order alone → a term match says nothing about relevance
    (9) Sharding the index The corpus outgrows one node's memory — build the seam early Single node → a forced migration once memory runs out
    (8) An explicit staleness monitor "Eventually" needs a number — lag surfaced and alertable Assume eventual consistency → a backlog grows for hours, unnoticed
    (13) Opt-in freshness check A narrow, opt-in check for the caller who can't tolerate the SLA Trust the standard SLA always → "it's not there yet" for your own new post

    Capacity Math

    Quantity Derivation Value
    Primary Store 50,000,000 docs × 2,000 B avg 100.0 GB
    Writes 200/s avg · peak × 3 600 /s
    In-flight buffer Little's Law: 600/s peak × 5 s SLA 3,000 docs
    Index size 50,000,000 × 50 terms/doc × 12 B/posting 30.0 GB
    Index : Primary 30.0 GB ÷ 100.0 GB — differently shaped, not smaller 0.30×
    Shards ≤4 GB/shard → 8 shards, 3.75 GB each 8
    Postings 50,000,000 docs × 50 terms/doc 2,500,000,000
    Queries 2,000/s avg · peak × 3 6,000 /s
    Fan-out 8 shards × top-50/shard, merged before rerank 400
    CDC buffer 600/s × 600 s → 360,000 events × 1,000 B 360 MB

    At-least-once sync has a real, nameable cost. 360 MB of buffered CDC events survives a 10-minute outage, and every query still fans out to all 8 shards and merges 400 candidates before ranking runs.

    What Breaks — Say It Before They Ask

    • (5) Indexing Pipeline falls behind. CDC events pile up in ③'s durable log; nothing is lost, but staleness (⑧) grows until it catches up. — Fix: drain the backlog at a steady rate — never fire the whole thing into ④ at once
    • (3) A CDC connector loses its offset. It crashes without checkpointing and doesn't know where it left off. — Fix: resume from the LAST ACKNOWLEDGED offset in ②'s own log, never from "now"
    • (12) Indexing-time and query-time tokenization diverge. Someone updates the analyzer for indexing but the query path still uses the old rules. — Fix: one shared Tokenizer/Analyzer — documents that obviously match stop appearing otherwise, with no error anywhere
    • (9) One shard runs hot. Uneven term distribution or a popular category clusters on one shard. — Fix: that shard's tail latency drags down the whole fan-out — a query isn't done until every shard responds
    • (10) Backfill races live updates. A Reindex job runs concurrently with CDC-driven updates to the same documents. — Fix: an ordering/version guard — only apply if the backfill's source version is newer than what's already indexed

    The Follow-Ups That Decide It

    1. Why not just add a full-text WHERE clause to the Primary Store instead of a whole second store? (ref 4 — tests: recall that a row store's own indexes aren't shaped for term → doc lookups, ranked by relevance)
    2. The app just wrote a document. Why not have it write to the Search Store too, right then? (ref 3 — tests: dual-write failure awareness — CDC as the single source of truth to recover from)
    3. If the index can lag, why isn't every search just wrong? (ref 4 — tests: bounded lag vs. zero lag — the honest target, not a hand-wave)
    4. Why not have the CDC stream write straight into the inverted index? (ref 5 — tests: recall that turning a row into indexable terms is real work, worth its own retryable stage)
    5. The index lookup already returns the matching documents. Why rank them separately? (ref 7 — tests: matching vs. ranking as different problems)
    6. Why shard the index instead of just scaling up one node's RAM? (ref 9 — tests: the corpus outgrowing single-node memory, and building the seam in early)
    7. CDC is "eventually consistent" by design. Why do you still need a monitor? (ref 8 — tests: recall that "eventually" needs a measured, alertable number)
    8. A user just created a document and immediately searches for it. What do they see? (ref 13 — tests: the opt-in freshness check for the narrow case that needs it, not default behaviour)
