    Design a Car Rental System

    15 sections · 1,890 words

    LLD Design Problems, problem 11 of 20.

    The Ask

    Build

    • Many branches, each a location with its own fleet.
    • A vehicle has a class: economy, SUV, luxury, van.
    • Reserve a class for a window, not a named car.
    • A pickup branch, and an optional different return branch.
    • At the counter, assign a concrete VIN, mark it rented.
    • Return records odometer and time, maybe elsewhere.
    • Bill: daily rate x days + mileage + insurance + one-way fee.
    • Live per-branch fleet count for the dashboard.

    Skip

    • Real card / cash capture.
    • Telematics, GPS, fuel level.
    • Damage claims and disputes.
    • Driver-license / KYC checks.
    • Demand-based dynamic pricing.
    • A database, login.

    Our Model

    One company, branches, a VIN fleet. Reserve a class now, hand over a concrete car at the counter.

    Actors and classes

    • Customer — id, svc: RentalService; reserve a class, pick up, drop off, calling svc.reserve(cls, br, s, e).
    • CounterAgent — branch: Branch; handOver(resId): Vehicle calls svc.assignVehicle(resId), takeReturn(resId, odo): Invoice calls svc.returnVehicle(id, at, odo).
    • RentalService (singleton) — branches: Map<String, Branch>, fleet: Map<String, Vehicle> (by VIN), reservations: Map<String, Reservation>, pricing: PricingStrategy, assign: VinAssignmentStrategy; reserve(VehicleClass c, Branch pickup, LocalDateTime start, LocalDateTime end): Reservation, assignVehicle(String resId): Vehicle, checkAvailability(...): int, returnVehicle(String resId, Branch at, int odometer): Invoice. Every write goes under a (branch, class) lock.
    • Branch — id: String, name: String, homeFleet: Set<String> (VINs based here); classFleet(VehicleClass c): int, onDepart(vin), onArrive(vin) (Observer; a one-way drop re-homes the VIN here).
    • Vehicle — vin: String, cls: VehicleClass, homeBranch: Branch, odometer: int, status: AVAILABLE | RENTED | SERVICE; markRented(), markAvailable(Branch at). Status flips here, never on the Reservation.
    • VehicleClass (enum) — ECONOMY, SUV, LUXURY, VAN.
    • Reservation — id, cls: VehicleClass, pickup, returnTo: Branch, start, end: LocalDateTime, vin: String (null until pickup), state: ReservationState; overlaps(s, e): boolean, active(): boolean, bind(Vehicle v), id(): String.
    • ReservationState (interface) — assign(Reservation r, String vin), cancel(Reservation r), close(Reservation r, Invoice inv). States: Reserved -> assign at counter -> PickedUp; PickedUp -> return -> Returned; Cancelled before pickup frees the count; NoShow after the deadline frees the count.
    • VinAssignmentStrategy (interface) — pick(List<Vehicle> free, Reservation r): Vehicle; NewestFirst, LowestOdometer, SoonestService.
    • PricingStrategy (interface) — price(Reservation r, int miles, List<AddOn> ins): Invoice.
    • Invoice — resId, days: int, miles: int; base + mileage + insurance + oneWayFee; total: Money.

    Two phases, one class

    Phase 1 holds a count; phase 2 binds a VIN.

    The pricing rules

    • DailyPlusMileage -> rate[cls] x days + Rs/km.
    • WeekendFlat -> flat Fri-Sun block.
    • CorporateRate -> contract table, one-way fee waived.

    Key operations

    1. reserve(VehicleClass c, Branch pickup, LocalDateTime start, LocalDateTime end): Reservation — under a lock on (pickup, c), counts reservations that overlap [start, end). Throws NoInventory when the count has reached the class fleet. Binds no VIN.
    2. assignVehicle(String resId): Vehicle — at the counter. Picks one AVAILABLE VIN of the class through VinAssignmentStrategy, marks it RENTED, binds it. State RESERVED to PICKED_UP.
    3. checkAvailability(VehicleClass c, Branch b, LocalDateTime start, LocalDateTime end): int — read only, for the search page. Class fleet at b minus reservations overlapping the window. Never negative, never reserves anything.
    4. returnVehicle(String resId, Branch at, int odometer): Invoice — records odometer and end time. Frees the VIN AVAILABLE at the return branch (re-homes it on a one-way). PricingStrategy bills days + miles + insurance + one-way fee; late adds a penalty.

    reserve when overlapping res < fleet(cls, br); one-way fee when returnTo != pickup. Reserve: n = free(cls, br, [start,end)); if (n <= 0) reject; res.hold(); a count, no VIN. Assign: free = available(cls, br); v = strategy.pick(free, res); v.markRented(); res.bind(v);.

    The One Run to Hold in Your Head

    An SUV is reserved at Airport for Fri to Mon, dropping at Downtown. Two SUVs are free that weekend. What does the counter hand over, what does the return bill, and which objects touched the request?

    The counter picks one free SUV via the strategy (lowest odometer), marks it RENTED and binds it. The return bills days + miles + insurance plus the one-way fee, then re-homes the VIN to Downtown.

    The Change

    One-way rentals drift the fleet — Airport empties, Downtown piles up. Add a RepositioningStrategy that reads the Observer's per-branch counts and plans moves of idle cars back toward balance, run off-peak. Strategy, a third time on this sheet.

    What the Picture Can't Show

    The overbook race: two agents reserve the last SUV for one week. The fix is not a class, it is a lock on (branch, class) inventory with a re-count before the reservation is written.

    If They Make You Code It

    reserve and assignVehicle, the whole thing:

    class RentalService {                            // one instance
    Map<String,Branch> branches;
    Map<String,Vehicle> fleet;                   // key = VIN
    Map<String,Reservation> reservations;
    PricingStrategy pricing;
    VinAssignmentStrategy assign;                // which VIN

    Reservation reserve(VehicleClass c, Branch b,
                        LocalDateTime s, LocalDateTime e) {
        Object key = lockFor(b, c);              // per branch+class
        synchronized (key) {
            int fleetN = b.classFleet(c);        // cars of c at b
            int held = 0;
            for (Reservation r : reservations.values())
                if (r.branch() == b && r.cls() == c
                    && r.overlaps(s, e) && r.active()) held++;
            if (held >= fleetN) throw new NoInventory(c, b);
            Reservation r = new Reservation(c, b, s, e); // no VIN
            reservations.put(r.id(), r);
            return r;                            // RESERVED, unbound
        }
    }

    Vehicle assignVehicle(String resId) {
        Reservation r = reservations.get(resId);
        synchronized (lockFor(r.pickup(), r.cls())) { // same key
            List<Vehicle> free = available(r.cls(), r.pickup());
            if (free.isEmpty()) throw new NoCarAtCounter(r);
            Vehicle v = assign.pick(free, r);    // newest / low odo
            v.markRented();                      // AVAILABLE -> RENTED
            r.bind(v);                           // RESERVED -> PICKED_UP
            return v;
        }
    }
}

    The Four Hazards

    1. Two reservations, one car. checkAvailability is not the commit. With no lock, two agents both see one SUV free that week and both write a reservation. Lock (branch, class), re-count overlaps inside, one write wins.
    2. One-way leaves a branch short. A car reserved out of Airport is dropped at Downtown. A later Airport reservation counted on it and now has none. Count inventory against the branch that will have the car, or refuse the one-way when it oversells the pickup branch.
    3. No-show holds the count. The customer never collects. The reservation still counts against the class inventory and blocks others. A deadline flips it to NO_SHOW and releases the count; charge a no-show fee if policy says so.
    4. Late return hits the next booking. The car comes back after the next reservation's start. That booking has a VIN promised and no car. A grace window, then reassign the next reservation to another AVAILABLE VIN, or bump it and notify.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. synchronized (key) on (branch, class) with the count re-read inside — two agents cannot both take the last car.
    2. new Reservation(c, b, s, e) binds no VIN — the concrete car is chosen only in assignVehicle.
    3. available(...) filters AVAILABLE at the pickup branch — a one-way arrival or a SERVICE flag is seen live.

    Tracking Availability

    Approach "Free that week?" Name the exact car Reserve cost One-way move Best when
    Per-car booking list (scan the fleet, the default) walk every car's bookings falls out of the scan O(cars x bookings) edit that car's home tiny one-branch fleet
    Per-class branch counter count overlaps, one number not until pickup O(overlapping res) flip which branch counts it "how many free"
    Interval tree per (branch, class) a range query falls out of the node O(log n) move it between trees must name cars up front

    Per-class, per-branch overlap count. The reservation only has to not oversell, and one integer answers that. Go to an interval tree per (branch, class) only when a specific VIN must be named at booking, or the reservation list is large enough that scanning hurts.

    Rejection Signals

    These end the interview:

    • A specific VIN pinned at reserve time — one car sent to SERVICE strands every booking made against it.
    • Availability checked with no lock and no re-count — two customers reserve the last van for the same week.
    • One inventory count for the whole company, not per branch — a full Airport and an empty Downtown both read "cars free".
    • Money as a double — daily rate plus per-km plus tax stops adding up and the invoice drifts.
    • No answer for a no-show or a late return — the two cases every interviewer probes.
    • Pricing by instanceof or a switch on VehicleClass instead of a strategy.

    Patterns Used

    State — the Reservation lifecycle: RESERVED to PICKED_UP to RETURNED, plus CANCELLED / NO_SHOW. Strategy — pricing, and which VIN to hand over. Observer — the branch dashboard follows every pick and drop. Factory — build Vehicle / Branch from a config row.

    Say It Like This

    "One company, many branches, each a location with a fleet typed by class. A customer reserves a class for a window at a pickup branch, maybe returning elsewhere. Reserve checks a count under a per-branch-per-class lock and holds no car. The counter assigns a concrete AVAILABLE VIN and marks it rented. Return re-homes the VIN, then a PricingStrategy bills days, miles, insurance and a one-way fee. Money is integer minor units."

    The Follow-ups That Decide It

    1. Two customers race the last car of a class. Lock (branch, class), re-count overlaps inside, one wins.
    2. Reservation is a class — when is the real car chosen? At assignVehicle, the counter, via VinAssignmentStrategy.
    3. One-way rental leaves the pickup branch short. Count against the branch that will hold the car, or refuse it.
    4. The customer never shows for pickup. A deadline flips it to NO_SHOW and frees the count.
    5. Car comes back late, the next booking is waiting. Grace window, then reassign that booking or bump it.
    6. "Cars free at Airport next weekend?" no scan. checkAvailability = class fleet minus overlapping res, one int.
    7. "Charge more for luxury on weekends." A new PricingStrategy; the service is untouched.
    8. The fleet drifts branch to branch over one-ways. A RepositioningStrategy moves idle cars back to balance.

    Deliberately Not Built

    • Real payment capture — a PSP behind a thin PaymentMethod seam. The seam is the point; the integration is not.
    • Telematics and GPS — a live feed of location and fuel. Hardware — name it and move on.
    • Damage-claim workflow — an inspection record and a dispute flow. A different question.
    • License / KYC checks — verifying the driver at pickup. Assume it passed.
    • Demand-based pricing — a PricingStrategy that reads live utilisation. Drops in, no service change.
