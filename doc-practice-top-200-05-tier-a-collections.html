      Top 200 Java Questions — Tier A: Collections

      0 sections · 3,293 words

      Tier A — Asked in 50-80% of Java interviews (80 Qs). These questions live in the bulk of mid-level interview rounds — past the headline Top 50 and into the meat of what gets asked in a typical 45-60 minute Java round. Work through Tier A over a weekend; you don't need to memorize, but you should be able to sketch the answer within 20 seconds for any of them.

      51. HashSet vs TreeSet vs LinkedHashSet — when each?

      Asked at: TCS · Infosys · Razorpay · Swiggy · most mid-level rounds

      Difficulty: Easy-Medium · Topic: Collections

      The question: "Walk me through the difference between HashSet, TreeSet, and LinkedHashSet. When would you reach for each one?"

      The 30-second answer: HashSet = backed by HashMap, O(1) add/contains, no ordering. LinkedHashSet = HashSet + a doubly-linked list of insertion order, O(1) ops, predictable iteration. TreeSet = backed by a red-black tree, O(log n) ops, sorted order (natural or via Comparator). Default to HashSet unless you need ordering.

      Step-by-step thought process:

      1. "All three implement Set, so duplicates are rejected via equals() / hashCode(). The difference is iteration order and operation cost."
      2. "HashSet — no ordering at all. The iteration order can change after a resize. Use when you only care about membership."
      3. "LinkedHashSet — maintains insertion order. Same O(1) ops as HashSet, slightly more memory because of the linked list pointers. Use when iteration order needs to be predictable, e.g. when you're deduplicating a sequence and want to keep first-seen order."
      4. "TreeSet — sorted order, but every op becomes O(log n). It also gives you NavigableSet methods like floor, ceiling, headSet, tailSet — useful for range queries."
      5. "Concrete pick: I store unique merchantId s seen during a batch in a HashSet; if I need to dedupe order events while preserving arrival order, LinkedHashSet; if I need to find 'the next refund slot after timestamp T', TreeSet."

      Edge cases to mention:

      • TreeSet requires either elements implementing Comparable or a Comparator — otherwise ClassCastException at runtime on first insert
      • TreeSet uses compareTo() for equality, NOT equals() — easy way to silently lose elements if your compareTo returns 0 for "different" objects
      • LinkedHashSet has a constructor LinkedHashSet<>(map, accessOrder=true) — wait, that's LinkedHashMap, not Set. LinkedHashSet is always insertionorder

      What NOT to say:

      • "TreeSet is just a sorted HashSet" — wrong, underlying data structure is completely different
      • "Use LinkedHashSet for thread safety" — none of these are thread-safe by default

      Common follow-up: "How would you make a TreeSet thread-safe?"

      52. HashMap vs Hashtable vs ConcurrentHashMap

      Asked at: TCS · Infosys · Wipro · Cognizant · almost every L1/L2 round

      Difficulty: Easy-Medium · Topic: Collections

      The question: "Compare HashMap, Hashtable, and ConcurrentHashMap. Which one would you pick for a multi-threaded application?"

      The 30-second answer: HashMap = unsynchronized, fastest, nulls allowed. Hashtable = legacy, every method synchronized on this, no nulls. ConcurrentHashMap = modern, bucket-level striping (Java 8: CAS + synchronized on bucket head), high concurrency, no nulls. For multi-threaded code, always pick ConcurrentHashMap — Hashtable is effectively deprecated.

      Step-by-step thought process:

      1. "HashMap is unsynchronized — fastest in single-threaded code, but two threads writing concurrently can corrupt the internal structure (infinite loop on resize in Java 7 was the classic bug)."
      2. "Hashtable is the old JDK 1.0 class — every method is synchronized on the table object. Coarse-grained lock, terrible throughput under contention. Disallows null keys and values."
      3. "ConcurrentHashMap (Java 8+) gave up the segment-based locking of Java 7 and switched to a perbucket strategy: CAS for insert into empty bucket, synchronized on the first node when there's a collision."
      4. "Iteration on ConcurrentHashMap is weakly consistent — it won't throw ConcurrentModificationException, but it may or may not reflect updates that happen during iteration."
      5. "Default pick today: HashMap if single-threaded, ConcurrentHashMap if shared across threads. Never new Hashtable."

      Edge cases to mention:

      • ConcurrentHashMap doesn't allow null keys or null values — historical reason: ambiguity between "key missing" and "key mapped to null" in concurrent context Collections.synchronizedMap(new HashMap<>()) wraps HashMap with method-level synchronization — same throughput problem as Hashtable, only use if you need a stable iterator with external locking
      • ConcurrentHashMap has compute, computeIfAbsent, merge which are atomic — use them instead of get-then-put

      What NOT to say:

      • "Hashtable is thread-safe and HashMap isn't, so use Hashtable" — outdated by ~15 years
      • "ConcurrentHashMap locks the whole map on writes" — wrong, that's Hashtable

      Common follow-up: "What does ConcurrentHashMap do under the hood when two threads call computeIfAbsent on the same key?"

      53. ConcurrentHashMap internals — what changed in Java 8?

      Asked at: Razorpay · Cred · Swiggy · Flipkart · senior backend rounds

      Difficulty: Medium-Hard · Topic: Concurrency / Collections

      The question: "What changed in ConcurrentHashMap from Java 7 to Java 8 internally?"

      The 30-second answer: Java 7 used 16 fixed segments, each a mini-HashMap with its own ReentrantLock — concurrency level was capped at 16. Java 8 dropped segments, switched to one big table where insert into an empty bucket uses CAS, and collisions sync on the first node of that bucket. Treeification kicks in at 8 nodes per bucket (same as HashMap).

      Step-by-step thought process:

      1. "In Java 7, the map was split into Segments — a Segment was essentially a mini-HashMap protected by a ReentrantLock. Default 16 segments, so at most 16 threads could write concurrently without blocking."
      2. "Each segment maintained its own count and resized independently. Memory overhead was significant — every segment carried its own table and lock."
      3. "Java 8 rewrote it: one table, no segments. Insert into an empty bucket uses Unsafe's CAS. When a bucket has at least one node, the writer acquires synchronized on the head node of the chain."
      4. "Counts are tracked via a LongAdder -style striped counter (CounterCell array) to avoid contention on a single size field."
      5. "Treeification at 8 nodes per bucket — same as HashMap. So worst-case bucket lookup is O(log n) instead of O(n)."

      Edge cases to mention:

      • size() is approximate — it sums the striped counter, but writes that race during the sum can be off by a few
      • Iterators are weakly consistent — they see a snapshot of buckets as of when they reached each one
      • forEach, reduce, and search have parallel variants that take a parallelism threshold — used when you actually have a huge map

      What NOT to say:

      • "It still uses segments" — wrong post-Java 8
      • "ConcurrentHashMap is just a HashMap with synchronized methods" — that's Collections.synchronizedMap, completely different mechanism

      Common follow-up: "What's the cost of computeIfAbsent if the same key is hit by 100 threads simultaneously?"

      54. EnumMap and EnumSet — why bother?

      Asked at: Goldman · JP Morgan India · Morgan Stanley · senior rounds

      Difficulty: Medium · Topic: Collections

      The question: "When would you choose EnumMap over HashMap, and EnumSet over HashSet?"

      The 30-second answer: When the key (or element) is an enum, EnumMap/EnumSet are dramatically faster and smaller. EnumMap is internally an array indexed by enum ordinal — O(1) without hashing. EnumSet is a bitmask (a long for ≤ 64 values, long[] otherwise) — set operations become bitwise AND/OR.

      Step-by-step thought process:

      1. "Both are part of the JDK since Java 5 but underused. The trick: when your keys are enum constants, you don't need hashing — the ordinal IS the index."
      2. "EnumMap holds an internal Object[] of size equal to the number of enum constants. get(key) is just array[key.ordinal()] — no hashing, no equals, no boxing."
      3. "EnumSet is even better — for enums with ≤ 64 constants, the entire set is a single long. contains(v) is (bits & (1L << v.ordinal()))!= 0. addAll(otherSet) is one OR instruction."
      4. "Concrete example: I track order states (PLACED, PAID, SHIPPED, DELIVERED, CANCELLED) — EnumMap is faster, smaller, and iterates in declaration order."
      5. "Both reject nulls and disallow non-enum keys at compile time — type system enforces correctness."

      Edge cases to mention:

      • EnumMap iteration is always in enum declaration order — no LinkedEnumMap needed
      • EnumSet has nice factory methods: EnumSet.of(STATE_A, STATE_B), EnumSet.complementOf(set), EnumSet.range(LOW, HIGH)
      • Neither is thread-safe — wrap with Collections.synchronizedMap / synchronizedSet if you must, but usually you don't need concurrent enum-keyed maps

      What NOT to say:

      • "Just use HashMap, it's general-purpose" — leaves performance on the table for no reason
      • "EnumSet is a sorted set" — it iterates in declaration order, not sorted order

      Common follow-up: "What happens to EnumSet if you have 1000 enum constants?"

      55. Iterator vs ListIterator vs Spliterator

      Asked at: Most Java mid-level rounds · Infosys · Wipro · Wells Fargo

      Difficulty: Medium · Topic: Collections

      The question: "What's the difference between Iterator, ListIterator, and Spliterator?"

      The 30-second answer: Iterator = forward-only, can remove. ListIterator = bidirectional + can add/set/ remove, only available on Lists. Spliterator = Java 8, designed for parallel traversal — can split itself into halves for fork-join, reports characteristics (SIZED, SORTED, ORDERED, etc.).

      Step-by-step thought process:

      1. "Iterator (since Java 1.2) has hasNext, next, and remove. Forward-only. Works on any Collection."
      2. "ListIterator extends Iterator with hasPrevious, previous, add, set. Bidirectional and mutating. Only Lists expose it via listIterator()."
      3. "Spliterator (Java 8) was added for the Stream API. Its key method is trySplit() — it returns a new Spliterator covering half the remaining elements, so parallel streams can fork the work."
      4. "Spliterators report characteristics — SIZED (size is known), ORDERED, SORTED, DISTINCT, IMMUTABLE, CONCURRENT, NONNULL, SUBSIZED. The stream pipeline uses these to optimize."
      5. "Practical use: I rarely write Spliterators by hand. I use them indirectly via stream() or parallelStream(). Custom Spliterators are useful when wrapping a non-standard data source for streaming."

      Edge cases to mention:

      • Iterator.remove() is the ONLY safe way to mutate a collection during iteration — calling list.remove() inside an enhanced for-loop throws ConcurrentModificationException
      • ListIterator's nextIndex() and previousIndex() help when you need both position and value
      • A Spliterator that can't split returns null from trySplit() — the stream still works, just serial

      What NOT to say:

      • "Spliterator is just an Iterator" — misses the split + characteristics design
      • "ListIterator works on any Collection" — wrong, Lists only

      Common follow-up: "How does a Spliterator decide when to stop splitting?"

      56. fail-fast vs fail-safe iterators

      Asked at: TCS · Infosys · Accenture · standard L1/L2 question

      Difficulty: Medium · Topic: Collections

      The question: "What's the difference between a fail-fast and a fail-safe iterator? Give me examples."

      The 30-second answer: Fail-fast = throws ConcurrentModificationException if the collection is structurally modified during iteration (via the collection's own methods or another thread). Fail-safe = doesn't throw; iterates over a snapshot or a weakly-consistent view. ArrayList, HashMap, HashSet are fail-fast. CopyOnWriteArrayList, ConcurrentHashMap are fail-safe.

      Step-by-step thought process:

      1. "Fail-fast iterators track a modCount field — every structural modification (add, remove, clear) increments it. On next(), the iterator compares modCount to its captured expectedModCount — mismatch throws CME."
      2. "This is a best-effort detection — it's NOT a thread-safety guarantee. The CME is raised on a best-effort basis; you can have races where it's missed."
      3. "Fail-safe iterators work on a snapshot or a concurrent-aware structure. CopyOnWriteArrayList iterates over the array as it was when the iterator was created — writes after that don't affect iteration."
      4. "ConcurrentHashMap's iterator is weakly consistent — it sees buckets as they were when the iterator reached them. No CME, but you don't get a clean snapshot either."
      5. "Practical rule: if you must mutate during iteration, use iterator.remove() (works on fail-fast iterators) or pick a concurrent collection."

      Edge cases to mention:

      • Calling list.remove(item) inside for (T item: list) triggers CME — that's just an iterator under the hood
      • iterator.remove() is allowed because it updates expectedModCount along with modCount
      • CopyOnWriteArrayList is fail-safe but expensive — every write copies the whole array; only sensible for read-heavy workloads (event listeners, observers)

      What NOT to say:

      • "Fail-safe means thread-safe" — partially true but misleading; the iterator is safe, mutations may still race
      • "Use try/catch on CME" — terrible code smell; fix the iteration, don't swallow it

      Common follow-up: "How would you safely remove items from an ArrayList while iterating?"

      57. WeakHashMap and IdentityHashMap — when?

      Asked at: Senior rounds · Cred · Goldman · Walmart Labs

      Difficulty: Medium-Hard · Topic: Collections

      The question: "What do WeakHashMap and IdentityHashMap solve? Give a real use case for each."

      The 30-second answer: WeakHashMap holds keys by weak reference — when the key has no strong references elsewhere, the GC can reclaim it and the entry is removed from the map. Useful for caches and metadata tied to object lifetime. IdentityHashMap uses == for key comparison instead of equals() — useful when you need to track objects by identity, not value.

      Step-by-step thought process:

      1. "Regular HashMap holds strong references — keys never get GC'd as long as they're in the map. That's a memory leak if you're using objects as cache keys and forget to remove them."
      2. "WeakHashMap wraps each key in a WeakReference. When the GC determines the key is otherwise unreachable, the reference is cleared and the entry is removed on the next map operation."
      3. "Use case: I cache parsed configurations keyed by a Merchant object. If the merchant is no longer in use anywhere else, I don't want the cache to keep it alive."
      4. "IdentityHashMap replaces equals() and hashCode() with == and System.identityHashCode(). Two different objects with the same content are different keys."
      5. "Use case: I'm walking an object graph and tracking which objects I've already visited — I want identity-based deduplication, not value-based. Serialization frameworks do this."

      Edge cases to mention:

      • WeakHashMap values are still strong references — if a value points back to the key, the entry never gets cleaned up
      • IdentityHashMap is also used for thread-stack tracking and some reflection internals
      • Neither is thread-safe; both have subtle gotchas — read the Javadoc before using

      What NOT to say:

      • "WeakHashMap is for thread safety" — wrong, completely unrelated
      • "IdentityHashMap is faster than HashMap" — irrelevant comparison; they solve different problems

      Common follow-up: "What happens to a WeakHashMap entry if the value strongly references the key?"

      58. PriorityQueue — internals and gotchas

      Asked at: Razorpay · Swiggy · most product co rounds, often via DSA

      Difficulty: Medium · Topic: Collections

      The question: "How is PriorityQueue implemented in Java? What are the common mistakes when using it?"

      The 30-second answer: PriorityQueue is a binary min-heap stored in an array. offer and poll are O(log n); peek is O(1). It's NOT sorted in iteration order — iterating gives you heap order, not sort order. Not thread-safe; use PriorityBlockingQueue for concurrent code.

      Step-by-step thought process:

      1. "Internally it's an Object[] holding a heap. Parent of index i is at (i-1)/2, children at 2i+1 and 2i+2. Default capacity is 11 and grows by ~50% when full."
      2. " offer adds to the end, then sifts up to maintain heap property — O(log n). poll removes root, moves last element to root, sifts down — O(log n). peek is just array[0]."
      3. "By default, it's a MIN-heap using natural ordering. For a max-heap, pass Comparator.reverseOrder() or a custom comparator."
      4. "Critical gotcha: iterator() does NOT iterate in priority order — it's heap order. If you need sorted output, repeatedly poll until empty (and that mutates the heap)."
      5. " remove(Object o) is O(n) — it scans the array linearly to find o, then sifts. For a fast removal-by-object, use a separate index map."

      Edge cases to mention:

      • Nulls are rejected — NullPointerException on offer
      • Custom comparator with inconsistent compare (not following total ordering) produces undefined behavior
      • For producer-consumer between threads, use PriorityBlockingQueue — same semantics, but offers take() that blocks until an element arrives

      What NOT to say:

      • "PriorityQueue is sorted" — wrong, only the head is guaranteed to be the smallest
      • "Iteration gives sorted order" — wrong, it's heap order

      Common follow-up: "How would you implement a top-K-frequent-elements problem with a PriorityQueue?"

      59. Deque — ArrayDeque vs LinkedList

      Asked at: Most Java mid-level rounds · Wipro · Cognizant

      Difficulty: Easy-Medium · Topic: Collections

      The question: "For a stack or queue use case, would you pick ArrayDeque or LinkedList?"

      The 30-second answer: ArrayDeque almost always. It's a circular array, O(1) add/remove at either end, cache-friendly, no per-element overhead. LinkedList works but each node carries prev/next pointers, hurts cache locality, and most operations are slower in practice.

      Step-by-step thought process:

      1. "For stack semantics — push and pop — Stack is legacy (synchronized, extends Vector). The recommended replacement is Deque<T> stack = new ArrayDeque<>(); then use push() and pop()."
      2. "For queue semantics — FIFO — Deque<T> queue = new ArrayDeque<>(); then offer() and poll(). Or use ArrayDeque directly as a Queue."
      3. "ArrayDeque is a circular buffer — head and tail indices wrap around. Resize doubles the capacity when full."
      4. "LinkedList does the same job but every element has 24 bytes of node overhead on top of the value. CPU prefetching doesn't help linked lists."
      5. "Concrete pick: I'm implementing a recursion-to-iteration conversion (DFS with explicit stack) — ArrayDeque every time."

      Edge cases to mention:

      • ArrayDeque rejects nulls; LinkedList accepts them. If null is a sentinel for "no value" in your design, you can't use ArrayDeque
      • Neither is thread-safe — use LinkedBlockingDeque or ConcurrentLinkedDeque for concurrent code ArrayDeque.iterator() and descendingIterator() are both fail-fast

      What NOT to say:

      • "Use Stack class — it's the Java way" — Stack is legacy, the docs recommend Deque
      • "LinkedList is faster because it's a linked structure" — almost always wrong on modern CPUs

      Common follow-up: "What's the difference between ConcurrentLinkedDeque and LinkedBlockingDeque?"

      60. Comparable vs Comparator — design and use

      Asked at: Almost every Java interview

      Difficulty: Easy-Medium · Topic: Collections / OOP

      The question: "Explain the difference between Comparable and Comparator. Which one would you use when?"

      The 30-second answer: Comparable = natural ordering, implemented inside the class itself via compareTo(). Comparator = external ordering, you pass it to sort/treemap when you want a different order. Use Comparable for the class's "obvious" order (e.g. dates by chronology); use Comparator for everything else and for classes you don't own.

      Step-by-step thought process:

      1. "Comparable is a single-method interface — int compareTo(T other). Returns negative if this < other, 0 if equal, positive if this > other. Implemented by Integer, String, LocalDate — anything with one obvious natural order."
      2. "Comparator is also a functional interface — int compare(T a, T b). You pass an instance to Collections.sort(list, comparator) or to a TreeMap/TreeSet constructor."
      3. "Java 8 made Comparator much nicer: Comparator.comparing(Order::getAmount).thenComparing(Order::getCreatedAt).reversed() reads naturally."
      4. "Use Comparable when the class has ONE canonical order — e.g. money amounts, timestamps. Use Comparator when there are multiple valid sort orders, or when sorting a third-party class."
      5. "Both must follow total ordering — antisymmetry, transitivity, consistency. A broken comparator corrupts TreeSet and gives wildly wrong sort results."

      Edge cases to mention:

      • compareTo must be consistent with equals — strictly, if compareTo returns 0, equals should return true. TreeSet/TreeMap use compareTo for equality, so inconsistency causes "missing" elements
      • Comparator.naturalOrder() and reverseOrder() exist for cases where you'd otherwise write a one-liner
      • Comparator.nullsFirst(comparator) / nullsLast handle nulls gracefully — useful when sorting columns that may have nulls

      What NOT to say:

      • "Comparable is for objects, Comparator is for primitives" — completely wrong
      • "Use Comparable so you can sort with Collections.sort(list) without arguments" — true but incomplete — explain WHY (natural order)

      Common follow-up: "How does Comparator.comparing() work under the hood?"
