    Observability

    6 sections · 652 words

    Section 8 of 11

    Three Pillars

    Pillar Local/Demo Tool Cloud Tool Status
    Metrics Prometheus + Grafana CloudWatch + Micrometer Phase 9
    Logs Loki + Promtail CloudWatch Logs Phase 9
    Traces OpenTelemetry (stretch) X-Ray (stretch) Deferred

    Local observability stack runs via docker-compose.observability.yml — optional, separate from the main docker-compose so it doesn't add startup overhead during feature development.

    Metrics (Prometheus + Grafana)

    Every Service Exposes

    • Spring Boot Actuator at /actuator/health and /actuator/prometheus
    • Micrometer auto-instruments: HTTP request rate, latency (p50/p95/p99), error rate, JVM heap, GC pause, thread pool, HikariCP connection pool

    Standard Grafana Dashboard (per service)

    • Request rate (req/s)
    • p95 latency
    • Error rate (4xx, 5xx)
    • JVM heap used/max
    • HikariCP active/idle/pending connections

    RAG-Specific Dashboard (knowledge-service + chat-service)

    Metric What it tells you
    Ingestion queue depth How many outbox events are pending publication — spikes indicate Kafka problems
    Embedding latency (p50, p95) How long the embedding model call takes — degrades ingestion throughput
    Retrieval hit rate % of queries where max similarity score > 0.6 — low = knowledge base coverage gap
    Average similarity score Trends downward as knowledge base quality degrades
    Escalation rate % of conversations that escalate — high = AI isn't answering well
    Chat response latency (p95) End-to-end: retrieval + LLM call + first token

    Why RAG-specific metrics? Standard HTTP metrics don't tell you if the AI pipeline is actually useful. A 200 OK with retrieved chunks at 0.3 similarity is a functional failure you'd miss without domain metrics. This is the kind of observability thinking that distinguishes senior engineers.

    Structured Logging (Loki + Promtail)

    Every service uses Logback with a JSON encoder. Every log line includes:

    {
  "timestamp": "2026-07-19T10:30:00.123Z",
  "level": "INFO",
  "service": "chat-service",
  "traceId": "a1b2c3d4e5f6",
  "spanId": "f1e2d3",
  "tenantId": "tenant-acme",
  "userId": "user-42",
  "conversationId": "conv-789",
  "message": "RAG retrieval completed",
  "retrievedChunks": 5,
  "maxSimilarityScore": 0.87,
  "retrievalLatencyMs": 45
}

    Why traceId, tenantId, userId on every line? When debugging a production issue, you can filter all logs across all 6 services by traceId to see the exact path a request took. Without this, correlating logs across services requires timestamp range guessing which is nearly impossible at any real traffic volume.

    MDC Population

    // Gateway filter adds headers
// Each service reads headers and populates MDC at filter/interceptor layer:
MDC.put("traceId", request.getHeader("X-Trace-Id"));
MDC.put("tenantId", request.getHeader("X-Tenant-Id"));
MDC.put("userId", request.getHeader("X-User-Id"));
// Logback JSON encoder automatically includes all MDC keys in every log line

    Health Checks

    Every service exposes /actuator/health with component-level details:

    {
  "status": "UP",
  "components": {
    "db":    { "status": "UP" },
    "kafka": { "status": "UP" },
    "redis": { "status": "UP" },
    "s3":    { "status": "UP" }
  }
}

    Docker Compose uses these for healthcheck directives — services won't start until their dependencies are healthy.

    Load Testing (k6)

    A k6 script exercises the full happy path:

    1. Login (Keycloak token exchange)
    2. Create a conversation
    3. Send a message (triggers RAG + LLM call)
    4. Create a ticket
    5. Update ticket status

    Target metrics measured under load:

    • chat-service p95 latency under 3 seconds (LLM call dominates)
    • ticket-service p95 latency under 200ms
    • knowledge-service search p95 under 300ms
    • Zero 5xx errors under 50 concurrent users

    Distributed Tracing (Stretch Goal)

    OpenTelemetry SDK in each service, exporting to Tempo (local) / X-Ray (AWS). Would enable:

    • Waterfall view of a request across all service hops
    • Identify which service is the bottleneck in the chat pipeline
    • Correlate a slow user experience to a specific downstream call

    Not in MVP. Noted as the next step in observability maturity after metrics and logs are solid.
