      Top 200 Java Questions — Tier B: Concurrency Advanced

      0 sections · 3,205 words

      Tier B — Asked in 25-50% of Java interviews (70 Qs). These are the depth-layer questions — they don't show up in every interview, but when they do, getting them right is the difference between an "okay" round and a "this candidate is senior" signal. Skim Tier B the week of your interview; focus harder if you are targeting senior or staff-level roles, or if the JD lists a specific area (Spring Security, JVM tuning, JPA performance) in detail.

      131. Designing a custom ThreadPoolExecutor — what knobs matter?

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · JP Morgan India

      Difficulty: Medium-Hard · Topic: Concurrency advanced

      The question: "You can't use Executors.newFixedThreadPool() in production. Build me a thread pool from scratch — what parameters do you pick and why?"

      The 30-second answer: Seven knobs — corePoolSize, maximumPoolSize, keepAliveTime, BlockingQueue choice, ThreadFactory (named threads for logs), RejectedExecutionHandler, and allowCoreThreadTimeOut. The queue choice is the highest-impact decision — LinkedBlockingQueue (unbounded) makes maximumPoolSize meaningless, SynchronousQueue forces immediate handoff.

      Step-by-step thought process:

      1. " Executors.newFixedThreadPool uses an unbounded LinkedBlockingQueue — under load, tasks pile up and you OOM before threads spawn. That's why we avoid it."
      2. "For a payments-callback worker, I'd use new ThreadPoolExecutor(8, 32, 60, SECONDS, new ArrayBlockingQueue<>(500), factory, CallerRunsPolicy) — bounded queue, capped threads, and back-pressure when full."
      3. " ThreadFactory must name threads — razorpay-webhook-worker-1, 2, 3. Default thread names like pool-3-thread-7 make production thread dumps unreadable."
      4. "RejectedExecutionHandler: AbortPolicy throws (good for fail-fast APIs), CallerRunsPolicy makes the submitter run it (natural back-pressure), DiscardOldest for telemetry-style workloads where stale events don't matter."

      Edge cases to mention:

      • A pool with LinkedBlockingQueue never grows past corePoolSize — maximumPoolSize is dead config unless the queue is bounded or SynchronousQueue allowCoreThreadTimeOut(true) lets even core threads die after keepAlive — useful for low-traffic services
      • For Java 21+, virtual threads via Executors.newVirtualThreadPerTaskExecutor() replace most blocking-I/O pools entirely

      What NOT to say:

      • "I'd use Executors.newCachedThreadPool " — unbounded thread creation, will exhaust the OS process limit
      • "Pick maximumPoolSize = number of cores" — wrong for I/O-bound work; cores matter for CPU-bound only

      Common follow-up: "What's the difference between submit() and execute() on this pool?"

      132. ForkJoinPool work-stealing — how does it actually work?

      Asked at: Senior rounds at Flipkart · Walmart Labs · Goldman · Morgan Stanley

      Difficulty: Hard · Topic: Concurrency advanced

      The question: "Explain ForkJoinPool's work-stealing algorithm. Why is it different from a regular thread pool?"

      The 30-second answer: Each worker thread has its own deque. Tasks are pushed/popped from the LIFO end (cache-friendly). When a worker's deque is empty, it steals from the FIFO end of a random victim's deque — this minimizes contention and keeps cache-hot work local.

      Step-by-step thought process:

      1. "Regular pools have one shared queue — every worker contends for the head. With many short tasks, that lock becomes a bottleneck."
      2. "ForkJoinPool gives each worker its own deque. Local work — push/pop from the top, LIFO, no synchronization on the fast path."
      3. "When a worker runs dry, it picks a random victim and steals from the bottom of that deque, FIFO order — stealing happens on the opposite end from local work, minimizing CAS contention."
      4. " fork() pushes onto your own deque, join() either runs the task (if still on your deque) or helps the stealer — workers never just block waiting."

      Edge cases to mention:

      • ForkJoinPool.commonPool() is shared across the JVM — parallel streams use it, so blocking inside a parallel stream starves every other parallel stream
      • Submitting blocking I/O to a FJP is an anti-pattern — use ManagedBlocker to inform the pool a thread will block, so it can spawn a compensator
      • Parallelism level defaults to Runtime.availableProcessors() 1 — explicit constructor takes a parallelism arg

      What NOT to say:

      • "It's just a faster thread pool" — misses the algorithmic point; interviewer wants the deque-per-worker detail
      • "Work-stealing means threads share queues" — wrong direction; the point is they don't share, they only steal occasionally

      Common follow-up: "What's the right pool for blocking I/O — ForkJoinPool, ThreadPoolExecutor, or virtual threads?"

      133. Happens-before relationship — what does it formally guarantee?

      Asked at: Senior rounds at Razorpay · Cred · Flipkart · Goldman

      Difficulty: Hard · Topic: Concurrency advanced

      The question: "What does 'happens-before' mean in the Java Memory Model? Give me three concrete examples."

      The 30-second answer: Happens-before is a partial ordering that says: if A happens-before B, then the effects of A (writes, side effects) are visible to B. Without it, the JVM and CPU can reorder operations freely. Three examples — monitor unlock-then-lock on the same lock, volatile write-then-read of the same field, Thread.start() before any action in the new thread.

      Step-by-step thought process:

      1. "The JMM allows aggressive reordering — compiler hoists loads, CPU executes out-of-order. Happens-before is the one guarantee about what writes another thread is allowed to see."
      2. "Monitor rule — synchronized exit happens-before next synchronized entry on the same object. That's why writes inside one synchronized block are visible to the next thread that enters."
      3. "Volatile rule — write to a volatile field happens-before every subsequent read of that field by any thread."
      4. "Thread rules — Thread.start() happens-before any action in the new thread; final actions in a thread happen-before Thread.join() returns."
      5. "Transitivity — if A happens-before B and B happens-before C, then A happens-before C. This is how you reason about chains across multiple locks/volatiles."

      Edge cases to mention:

      • final fields have their own rule — properly constructed objects (no this leak in constructor) guarantee final-field visibility without sync
      • Double-checked locking requires volatile on the instance field — without it, partially-constructed object is visible to a second thread
      • Happens-before doesn't imply real-time ordering — it's about visibility, not wall-clock sequence

      What NOT to say:

      • "It means A runs before B" — wrong, that's real-time; happens-before is about visibility
      • "Synchronized always gives happens-before" — only on the same lock, not across different locks

      Common follow-up: "Why does volatile not solve the read-modify-write race for a counter?"

      134. Volatile vs synchronized — when each fails

      Asked at: Senior rounds at Swiggy · PhonePe · Razorpay · TCS Digital

      Difficulty: Medium-Hard · Topic: Concurrency advanced

      The question: "Give me a case where volatile is enough and a case where it isn't."

      The 30-second answer: volatile guarantees visibility of writes and prevents reordering across the volatile access — enough for single-write flags (boolean shutdown). It is NOT enough for compound operations like counter++ because increment is read-modify-write — two threads can read the same value, increment, and write back losing one update.

      Step-by-step thought process:

      1. " volatile boolean running = true works for a worker loop — one thread writes false to stop, others see it on next read. No race because there's only one writer of the flag."
      2. " volatile int counter; counter++ does NOT work — that's three operations (load, add, store). Two threads can read 5, both compute 6, both store 6 — one increment lost."
      3. "For counters use AtomicInteger (uses CAS), or LongAdder (better under contention — striped counters merged on read)."
      4. " synchronized gives both visibility AND atomicity — but at the cost of blocking and a happens-before edge on every entry/exit."

      Edge cases to mention:

      • volatile arrays — the reference is volatile, not the elements. Use AtomicReferenceArray for element-level guarantees
      • Double-checked locking pattern needs volatile on the instance — otherwise the partially-constructed object publish race kicks in volatile long and volatile double — pre-Java 5, 64-bit reads weren't atomic on 32-bit JVMs; volatile fixes that

      What NOT to say:

      • "Volatile is just synchronized but lighter" — wrong; they solve different problems
      • "Atomic is always faster than synchronized" — under heavy contention, CAS retry loops can be slower than a fair lock

      Common follow-up: "How does AtomicInteger achieve thread-safety without locks?"

      135. Lock-free data structures — how does ConcurrentLinkedQueue work?

      Asked at: Staff+ rounds at Cred · Flipkart · Goldman · Walmart Labs

      Difficulty: Hard · Topic: Concurrency advanced

      The question: " ConcurrentLinkedQueue claims to be non-blocking. How? What algorithm does it use?"

      The 30-second answer: It uses the Michael-Scott non-blocking queue algorithm — head and tail pointers updated via CAS (compare-and-swap), not locks. Enqueue: CAS the tail's next pointer to the new node, then CAS the tail pointer forward. Dequeue: CAS the head pointer forward. Readers can see a stale tail briefly — they help advance it.

      Step-by-step thought process:

      1. "The structure is a singly-linked list with head and tail references, both volatile. No locks anywhere on the fast path."
      2. "Enqueue is two steps — CAS tail.next from null to the new node, then CAS tail to point at the new node. The second CAS can fail; another thread will help by retrying."
      3. "That's the 'helping' pattern — non-blocking algorithms often have threads cooperate to finish each other's in-progress operations, so no thread can stall the others."
      4. " size() is O(n) — it traverses the list — because maintaining a counter would require contention. Don't call size() in hot paths."

      Edge cases to mention:

      • The ABA problem — if a node is removed and re-added, a CAS comparing the reference returns true even though the queue changed. JDK uses AtomicMarkableReference / AtomicStampedReference to add a counter
      • ConcurrentLinkedQueue is unbounded — if producers outpace consumers, memory grows; use LinkedBlockingQueue with a capacity for back-pressure
      • Memory consistency — operations are happens-before consistent across enqueue/ dequeue, so handoff semantics are safe

      What NOT to say:

      • "It uses fine-grained locks per node" — wrong; that would be a different data structure (lock-coupling)
      • "It's the same as ArrayDeque" — wrong; ArrayDeque is single-threaded

      Common follow-up: "What's false sharing and how would it affect this queue?"

      136. False sharing — what is it and how do you fix it?

      Asked at: Staff rounds at Flipkart · Cred · Goldman · Morgan Stanley

      Difficulty: Hard · Topic: Concurrency advanced

      The question: "Explain false sharing. Why does it matter? How does Java solve it?"

      The 30-second answer: CPUs cache memory in 64-byte cache lines. If two threads modify two different variables that happen to sit in the same cache line, each modification invalidates the other CPU's cache — so you get cache-line ping-pong even though there's no logical sharing. Fix: padding or @Contended annotation.

      Step-by-step thought process:

      1. "Modern CPUs don't fetch one byte at a time — they fetch a cache line, typically 64 bytes. The MESI cache coherence protocol invalidates the line on any write."
      2. "Two long variables (8 bytes each) sitting next to each other in a class share a cache line. Thread A writes one, Thread B writes the other — both lines invalidate constantly. Performance falls off a cliff."
      3. "Java 8 introduced @jdk.internal.vm.annotation.Contended — JVM pads the field with 128 bytes on each side. Used inside LongAdder, Striped64, ConcurrentHashMap 's counter cells."
      4. "For application code you can't use the internal annotation directly without -XX:-RestrictContended. Manual padding (7 dummy longs) is the workaround."

      Edge cases to mention:

      • 128 bytes of padding (not 64) — some CPUs prefetch adjacent cache lines, so two-line padding is safer
      • LongAdder beats AtomicLong under contention precisely because of @Contended padding on its striped cells
      • JOL (Java Object Layout) library can show actual field offsets — use it to diagnose suspected false sharing

      What NOT to say:

      • "It's a Java bug" — no, it's a CPU-level effect; Java only exposes it
      • "Use synchronized to fix it" — opposite of useful; sync makes contention explicit instead of hidden

      Common follow-up: "Walk me through LongAdder vs AtomicLong — when do you prefer which?"

      137. ReadWriteLock vs StampedLock — when do you upgrade?

      Asked at: Senior rounds at Razorpay · Swiggy · Goldman

      Difficulty: Medium-Hard · Topic: Concurrency advanced

      The question: "You have a cache that's read 100x more than written. Walk me through the lock options."

      The 30-second answer: ReentrantReadWriteLock lets multiple readers in concurrently and locks out readers when a writer wants in — but readers still acquire a real lock (CAS on a counter). StampedLock (Java 8+) adds an optimistic read mode — no lock, just a version stamp you validate after reading.

      Step-by-step thought process:

      1. " ReentrantReadWriteLock — readers share, writer is exclusive. Fair vs unfair mode controls writer starvation. Downside: read lock still does a CAS, which hurts under massive read contention."
      2. " StampedLock — tryOptimisticRead() returns a stamp without acquiring anything. You read your fields, then call validate(stamp) — if anyone wrote, validate returns false and you fall back to a real read lock."
      3. "That makes pure reads almost free under low write contention — typical web cache pattern."
      4. "StampedLock is NOT reentrant and has no Condition variables — it's a lower-level primitive. Don't use it when you need either."

      Edge cases to mention:

      • Optimistic read returns 0 if a write is in progress — must fall back to readLock()
      • Lock upgrade (read → write) requires tryConvertToWriteLock(stamp) — returns 0 on failure; never just acquire write after read or you deadlock
      • ReentrantReadWriteLock reader can be starved by a steady stream of writers in fair mode — measure before assuming fairness is free

      What NOT to say:

      • "ReadWriteLock is always faster than synchronized" — false under heavy write contention; the read/write tracking has overhead
      • "Just use ConcurrentHashMap" — fine for maps, but ReadWriteLock generalizes to any shared structure

      Common follow-up: "What's the deadlock risk with lock upgrade?"

      138. CompletableFuture — composing async pipelines

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Walmart Labs

      Difficulty: Medium-Hard · Topic: Concurrency advanced

      The question: "I need to call three downstream services in parallel and combine the results. Show me the CompletableFuture chain."

      The 30-second answer: allOf(f1, f2, f3).thenApply(v -> combine(f1.join(), f2.join(), f3.join())) — allOf returns a CompletableFuture<Void> that completes when all three complete; then you join each (safe because they're already done) and combine. Use supplyAsync(..., executor) to feed each one with your own pool.

      Step-by-step thought process:

      1. "Default executor is ForkJoinPool.commonPool() — fine for CPU work, bad for blocking I/O. Pass your own Executor to every Async method."
      2. "For three independent downstream calls: CompletableFuture<PaymentStatus> p = supplyAsync(() -> paymentApi.fetch(id), pool); CompletableFuture<UserProfile> u = supplyAsync(() -> userApi.fetch(id), pool); — etc."
      3. "Combine with allOf — allOf(p, u, o).thenApply(v -> new OrderView(p.join(), u.join(), o.join())). join() won't block here because allOf only completes when each underlying is done."
      4. "For exception handling: .exceptionally(ex -> fallback) or .handle((result, ex) ->...) — handle gets both, exceptionally only the failure path."

      Edge cases to mention:

      • thenApply vs thenApplyAsync — the first runs on whatever thread completed the previous stage (could be the caller); Async re-submits to your executor
      • join() vs get() — join throws unchecked CompletionException, get throws checked; prefer join in pipelines
      • orTimeout(2, SECONDS) (Java 9+) cancels the future after the timeout instead of forever-blocking — critical for production

      What NOT to say:

      • "Just use Thread.sleep between calls" — sequential, defeats the point
      • "Future is the same as CompletableFuture" — Future has no chaining, no completion handlers, no combiner methods

      Common follow-up: "What's thenCompose and when do you use it over thenApply?"

      139. Virtual threads pinning — what causes it and what's the fix?

      Asked at: Senior rounds at Razorpay · Swiggy · Cred · Walmart Labs

      Difficulty: Hard · Topic: Concurrency advanced

      The question: "Virtual threads in Java 21 — what does 'pinning' mean and when does it happen?"

      The 30-second answer: A virtual thread normally parks itself when it blocks, freeing its carrier (platform thread) to run another virtual thread. Pinning means the virtual thread can't unmount and instead blocks the carrier — happens inside synchronized blocks and JNI calls in Java 21. Fix: replace synchronized with ReentrantLock. Java 24 (JEP 491) removes the synchronized pinning entirely.

      Step-by-step thought process:

      1. "Virtual threads are M:N — many virtual threads multiplexed over a small pool of platform carriers. Mounting/unmounting on blocking is the whole point."
      2. "Inside synchronized, the JVM tracks the monitor on the native stack of the carrier — if the virtual thread unmounted, the monitor would be lost. So Java 21 just pins."
      3. "In Java 21-23, replace hot synchronized blocks with ReentrantLock — its state lives on the heap, no native stack dependency, so the virtual thread can unmount and another virtual thread runs on the carrier."
      4. "From Java 24 (JEP 491) onwards this is fixed — synchronized no longer pins. So this question's importance fades over time, but for any service still on Java 21 LTS, it matters."

      Edge cases to mention:

      • Detect pinning with -Djdk.tracePinnedThreads=full — logs the stack trace every time a virtual thread pins
      • JNI / native code pins too — unavoidable when calling C libraries; usually rare enough to ignore
      • Object.wait() inside synchronized still pins until Java 24

      What NOT to say:

      • "Virtual threads replace ThreadPoolExecutor everywhere" — not for CPU-bound work; carriers are still limited to core count
      • "synchronized is deprecated in Java 21" — no, just imperfect with virtual threads on that version

      Common follow-up: "How would you migrate a JDBC-heavy service from platform threads to virtual threads?"

      140. Reentrant lock fairness — when to set it true?

      Asked at: Senior rounds at JP Morgan India · Goldman · Wells Fargo

      Difficulty: Medium · Topic: Concurrency advanced

      The question: " ReentrantLock has a fairness flag — what does it do and when do you turn it on?"

      The 30-second answer: Fair mode grants the lock to threads in FIFO order of arrival — no thread starves. Unfair (default) lets a thread that's about to release the lock barge ahead of waiting threads — much higher throughput but the unlucky waiter can wait a long time. Use fair only when you genuinely need bounded wait time.

      Step-by-step thought process:

      1. "Default is unfair — it's barge-friendly. Total throughput is much higher because the just-released-the-lock thread is hot in cache, so back-to-back acquires are cheap."
      2. "Fair mode forces queueing — every acquire goes through the wait queue. Throughput can be 5-10x lower, but the longest wait is bounded by N other waiters."
      3. "Reach for fair when you have a constrained shared resource (e.g., 10 DB connections, 100 threads competing) and you need to prevent starvation that breaks SLAs."
      4. "Don't use fair as a default — most code wants throughput, not fairness."

      Edge cases to mention:

      • tryLock() (without timeout) bargers even in fair mode — it doesn't honour the queue
      • Semaphore has the same fairness flag with the same semantics ReentrantReadWriteLock fairness applies to both reader and writer queues — fair readers can be starved by a steady writer

      What NOT to say:

      • "Always use fair mode for safety" — performance hit is real; only use when starvation is a known problem
      • "Fair means random" — no, fair means FIFO

      Common follow-up: "Compare ReentrantLock and synchronized — when do you reach for which?"
