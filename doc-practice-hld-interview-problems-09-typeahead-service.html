    Design a Typeahead Service

    3 sections · 3,256 words

    Three levels: Level 1 — The Shape, Level 2 — The Defence, Level 3 — The Edges.

    Level 1 — The Shape (Foundation)

    Pacing: 3 min ask · 5 min trace flow · 7 min read why.

    The Ask

    Functional

    • Type a query prefix → return the top-N most likely completions
    • Suggestions reflect real popularity, not just alphabetical match

    Non-Functional

    • Tens of ms per keystroke ← forces precomputed, indexed lookups
    • Every keystroke is a new request ← forces cheap, high-QPS reads
    • Fresh, with bounded staleness ← forces periodic batch recompute

    Agree These First

    50,000,000 completed searches/day · an average query is ~12 characters typed · suggestions are precomputed for the ~10,000,000 distinct prefixes that actually get typed often enough to clear the frequency floor — any length, not just short ones — each storing its top 10 completions. Round, illustrative numbers, not any named company's.

    The Shape

    Components and flow:

    • Client — Typing a prefix — one keystroke, one new request
    • (8) every keystroke fires a lookup
    • Typeahead Service — GET /suggest?prefix= · stateless · looks up the index only
    • prefix lookup — ≈6.9K /s
    • Suggestion Index — prefix → top-10 completions · in-memory hash / trie; ≈3 GB total · fits in RAM
    • (9) rebuilt periodically — bounded staleness, never fully live

    Data model: suggestions prefix PK → top10[].

    12 lookups : 1 completed search.

    Line = speed, not traffic: LOOKUP · fast, ~6.9K/s.

    Say It Like This

    "This is a latency problem before it's anything else — tens of milliseconds, keystroke to render. So I'd precompute the top completions for every prefix, not rank live, because live ranking can't hit that budget at this volume. One user typing fires many requests, not one, so the lookup has to be a purpose-built prefix index, not a general search engine. And I'd keep it fresh with a periodic batch rebuild, not a perfectly live index — bounded staleness is cheap, perfectly live isn't."

    Defend It

    Decision Prefer Avoid
    (2) Precompute vs live rank Top-N precomputed per prefix — a keystroke is a near-O(1) lookup Score every matching query live → too slow at this latency budget
    (1) Prefix structure Purpose-built prefix index — built for exact-prefix completion, nothing else A full-text search engine → ranking over documents, a heavier job
    (9) Freshness window Bounded staleness, periodic rebuild — nearly as good, far cheaper Perfectly live index → re-rank on every single search event

    Capacity Math

    Quantity Derivation Value
    Searches 50,000,000 ÷ 86,400 s 579 /s
    Lookups/day 50,000,000 × 12 chars typed/query 600 M/day
    Lookups/s 600,000,000 ÷ 86,400 s ≈6.9K /s
    Ratio 6,944 lookups ÷ 579 searches — the headline number 12 : 1
    Index size 10 M live prefixes × 10 completions × ~30 B 3 GB

    Round hard, out loud. Every completed search costs the system about 12 lookups, not 1 — that ratio, not storage, is the whole design problem.

    Before You Draw Anything — The Four Moves

    1. Clarify, don't assume. Personalization? Typo-tolerance? Say these are out of scope — separate, harder problems layered on top of this one. — Two minutes of questions buys the whole design.
    2. Agree the scale out loud. "50 M searches/day, ~12 chars typed per query, 10 M precomputed prefixes." Now every later choice has a reason. — An unstated number is an undefendable design.
    3. Draw the happy path only. Client → Typeahead Service → Suggestion Index. Get agreement before adding anything. — Boxes you add before agreement are boxes you'll defend alone.
    4. Name one trade-off unprompted. "I'd precompute the top completions per prefix, not rank live, because the latency budget doesn't allow live ranking at this rate." — This is the single move that separates L1 from a junior answer.

    What L1 Is Testing

    • Do you reach for precompute over live ranking, unprompted?
    • Do you notice one keystroke = one request, and say so?
    • Did you ask what's out of scope before drawing anything?

    The Follow-Ups That Decide It

    1. Why not just run a live search ranking on every keystroke? (ref 2 — tests: latency-budget-vs-live-computation awareness)
    2. You type a 12-character query. How many suggestion lookups actually happen? (ref 8 — tests: can you reach for the amplification ratio unprompted)
    3. How fresh do suggestions need to be, and what does making them fresher cost you? (ref 9 — tests: staleness-vs-cost trade-off reasoning)

    At L1 you are being judged on one thing: can you produce a coherent shape and defend three choices inside it. Depth is page 2 — do not reach for it here. Ghosted boxes are what arrives next; you should be able to guess two of them.

    Level 2 — The Defence (Intermediate)

    Pacing: 5 min ask · 15 min trace flow · 10 min read why · 30 min cover & answer.

    The Ask

    Functional

    • Type a query prefix → return the top-N most likely completions
    • Suggestions reflect real popularity, not just alphabetical match
    • Suggestions stay reasonably fresh as new queries trend

    Non-Functional

    • Tens of ms per keystroke ← forces precomputed, indexed lookups
    • Every keystroke is a new request ← forces cheap, high-QPS reads
    • Fresh, with bounded staleness ← forces periodic batch recompute
    • Never surface garbage / private input ← forces a min frequency floor

    Out of Scope — Say It Aloud

    • Personalization per-user — a separate, harder problem
    • Typo / fuzzy correction
    • Multi-language ranking nuance

    Agree These First

    50,000,000 completed searches/day · an average query is ~12 characters typed · suggestions are precomputed for the ~10,000,000 distinct prefixes that actually get typed often enough to clear the frequency floor — any length, not just short ones — each storing its top 10 completions. Round, illustrative numbers, not any named company's.

    The Shape

    Components and flow:

    • Client — Typing a prefix — one keystroke, one new request
    • (8) every keystroke fires a lookup
    • Typeahead Service — GET /suggest?prefix= · stateless · looks up the index only
    • prefix lookup — ≈6.9K /s
    • (3) Query Log — Raw completed searches — never read on the hot path; completed search only, not every keystroke
    • (4) Batch Ranker — Periodic job: aggregate frequency, recompute top-N, publish; nightly rebuild; replaces the whole index
    • (5) Frequency Filter — Below the floor → never eligible to be suggested
    • Suggestion Index — prefix → top-10 completions · in-memory hash / trie; ≈3 GB total · fits in RAM
    • (9) rebuilt periodically — bounded staleness, never fully live

    Data model:

    • suggestions prefix PK · completions[] · updated_at
    • query_log query · ts — rolled up, not read on the hot path

    12 lookups : 1 completed search.

    Line = speed, not traffic: LOOKUP · fast, ~6.9K/s; BATCH · slow, periodic; ASYNC · off critical path.

    Say It Like This

    "This is a latency problem before it's anything else — tens of milliseconds, keystroke to render. So I'd precompute the top completions for every prefix, not rank live, because live ranking can't hit that budget at this volume. One user typing fires many requests, not one, so the lookup has to be a purpose-built prefix index, not a general search engine. And I'd keep it fresh with a periodic batch rebuild, not a perfectly live index — bounded staleness is cheap, perfectly live isn't."

    Defend It

    Decision Prefer Avoid
    (2) Precompute vs live rank Top-N precomputed per prefix — a keystroke is a near-O(1) lookup Score every matching query live → too slow at this latency budget
    (1) Prefix structure Purpose-built prefix index — built for exact-prefix completion, nothing else A full-text search engine → ranking over documents, a heavier job
    (9) Freshness window Bounded staleness, periodic rebuild — nearly as good, far cheaper Perfectly live index → re-rank on every single search event
    (3) Query log Fire-and-forget, off the hot path — never read by a live lookup Log synchronously on the read path → pays write latency per keystroke
    (5) Frequency floor A minimum frequency before a query is even eligible Suggest anything ever typed → one typo or private string leaks to everyone
    (8) Client throttling Debounce client-side — a small delay, not every keystroke fires Fire on every keystroke, unthrottled → needlessly high request rate

    Capacity Math

    Quantity Derivation Value
    Searches 50,000,000 ÷ 86,400 s 579 /s
    Lookups/day 50,000,000 × 12 chars typed/query 600 M/day
    Lookups/s 600,000,000 ÷ 86,400 s ≈6.9K /s
    Ratio 6,944 lookups ÷ 579 searches — the headline number 12 : 1
    Index size 10 M live prefixes × 10 completions × ~30 B 3 GB
    Per completion short string + popularity score, illustrative ≈30 B
    Completions 10,000,000 prefixes × 10 each 100 M rows
    RAM fit 3 GB vs a typical 64–256 GB/node — trivial no sharding

    Storage is trivial here — 3 GB fits in RAM on one box. The 12:1 ratio is the real load: throughput measured in lookups, not searches.

    What Breaks — Say It Before They Ask

    • (4) Batch job can't keep up with a genuine spike. A huge, fast-breaking event isn't reflected until the next scheduled rebuild — by then it's stale news. — Fix: the trending layer exists exactly for this — batch handles steady-state, the fast layer handles spikes
    • (8) Unthrottled client hammers the service. At high typing speed with no client-side moderation, the effective request rate is needlessly high. — Fix: client-side debouncing/throttling — a small delay before firing a lookup
    • (5) A rare or sensitive one-off string leaks as a suggestion. Without a floor, an unusual or private string could surface to other users on the same prefix. — Fix: minimum frequency threshold before a completion is eligible at all

    The Follow-Ups That Decide It

    1. Why not just run a live search ranking on every keystroke? (ref 2 — tests: latency-budget-vs-live-computation awareness)
    2. You type a 12-character query. How many suggestion lookups actually happen? (ref 8 — tests: can you reach for the amplification ratio unprompted)
    3. How fresh do suggestions need to be, and what does making them fresher cost you? (ref 9 — tests: staleness-vs-cost trade-off reasoning)
    4. A major trending event breaks and everyone starts typing it. Does your system show it as a suggestion right away? (ref 6 — tests: awareness that batch-only misses fast-moving trends)
    5. Someone types a rare or sensitive string as a search. Could it show up as a suggestion to someone else typing the same prefix? (ref 5 — tests: minimum-frequency-threshold awareness, not a hand-wave)

    Cover The Sheet · Answer Aloud

    Use it as revision: cover the right rail and the two panels to your left, then walk the numbered path out loud. If you cannot say why a box is there and what breaks it, that box is your gap.

    Level 3 — The Edges (Advanced)

    Pacing: 10 min ask · 25 min trace flow · 15 min read why · 40 min cover & answer.

    The Ask

    Functional

    • Type a query prefix → return the top-N most likely completions
    • Suggestions reflect real popularity, not just alphabetical match
    • Suggestions stay reasonably fresh as new queries trend

    Non-Functional

    • Tens of ms per keystroke ← forces precomputed, indexed lookups
    • Every keystroke is a new request ← forces cheap, high-QPS reads
    • Fresh, with bounded staleness ← forces periodic batch recompute
    • Never surface garbage / private input ← forces a min frequency floor
    • A spike beats the next rebuild ← forces a faster signal on top of batch

    Out of Scope — Say It Aloud

    • Personalization per-user — a separate, harder problem
    • Typo / fuzzy correction
    • Multi-language ranking nuance

    Agree These First

    50,000,000 completed searches/day · an average query is ~12 characters typed · suggestions are precomputed for the ~10,000,000 distinct prefixes that actually get typed often enough to clear the frequency floor — any length, not just short ones — each storing its top 10 completions.     • (7) Cold-Prefix Fallback — Live, best-effort lookup — rare, not from the index; prefix miss (rare)
    • (9) rebuilt periodically — bounded staleness, never fully live; faster cadence — minutes, not a full rebuild

    Data model:

    • suggestions prefix PK · completions[] · updated_at
    • query_log query · ts — rolled up, not read on the hot path
