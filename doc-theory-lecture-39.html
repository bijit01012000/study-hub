    Lecture 39 — OAuth 2.0 Masterclass with Google Login

    20 sections · 4,878 words

    Lecture 39

    Scope evidence: "OAuth 2.0 Masterclass | Google Login with Spring Boot, OIDC & PKCE" (playlist map, verified). The repo folder is an oauthDemo project: SecurityConfig with oauth2Login, CustomOidcUserService, a User entity/repository, and application.properties client registration; the cached lecture text is the ground truth for every step below.

    This lecture moves security beyond our own username/password system: instead of issuing our own JWTs, the app delegates authentication and limited authorization to Google using OAuth 2.0 and OpenID Connect. We cover the delegated access problem, the four roles, scopes, access vs ID tokens, the authorization code flow, PKCE, and the full Spring Boot Google-login implementation.

    1. Moving Beyond Our Own Authentication System

    Until now our application controlled the complete flow: the user sends a username and password, Spring Boot authenticates, the app generates a JWT, and the client sends that JWT with future requests; the API validates the signature and trusts the claims only when it is valid. JWT solved one problem: how can an API verify the information inside a token without trusting the client?

    Now consider a new requirement, "Continue with Google." We cannot ask the user to send their Google password to our application:

    POST /login-with-google
email=student@gmail.com
googlePassword=???

    Our application should never receive, process, or store the user's Google password. That constraint forces us to leave self-managed login behind and adopt a delegated model.

    Aspect Our own login (username/password + JWT) Delegated OAuth login (Continue with Google)
    Who verifies the password Our application Google (the authorization server)
    Does our app see the password Yes, it receives and hashes it No, it never receives it
    Credential our app stores A password hash No password at all
    Identity source Email created in our database provider + provider subject
    Main purpose Authenticate our own users Delegate authentication and limited access
    Token the client holds Our JWT Provider access token (and OIDC ID token)

    Important: Once "Continue with Google" appears, our application stops being the identity provider. Google becomes the authority for the external identity, and our app only keeps an internal record linked to it.

    2. The Delegated Access Problem

    A productivity app adds the feature "Connect your Google Calendar." The app needs permission to read the user's calendar. A dangerous design would be: the user gives Google credentials to the app, the app logs in to Google as the user, and then accesses Google Calendar. This creates two problems:

    1. The user must share their Google password with another application.
    2. The application receives far more access than it needs.

    The same Google credentials could expose Gmail, Drive, Photos, Calendar, YouTube, and more, even though only calendar access is needed. OAuth 2.0 replaces shared credentials with delegated, limited access: the user signs in directly with Google, allows the application to read the calendar, Google gives the application an access token, and the application uses that token with Google Calendar API (never the password).

    OAuth 2.0 is primarily a framework for delegated authorization. Authorization answers: "What are you allowed to do?"

    Golden rule: Never let a third-party application hold the user's real password. Replace "here is my password" with "here is a limited, revocable token for exactly what you asked". That is the whole idea of delegated access.

    3. The Four OAuth Roles

    Every OAuth conversation has four participants. Interviewers test the vocabulary, not just the flow.

    Role Example Responsibility
    Resource Owner User Owns or controls access to the protected resource
    Client CoderArmy application Requests delegated access on behalf of the user
    Authorization Server Google's authorization system Authenticates the user, obtains consent, and issues tokens
    Resource Server Google Calendar API Hosts the protected resource and validates access tokens

    Resource Owner: the user controlling the protected data. Client: the application requesting access (Spring Boot, mobile, desktop, or browser-based), not necessarily the browser. Authorization Server: authenticates the user, asks for consent, and issues tokens. Resource Server: hosts the resource; Google Calendar API receives Authorization: Bearer <access-token>, validates it, and decides if the operation is allowed.

    Mnemonic: R-C-A-R - Resource owner, Client, Authorization server, Resource server ("Real Clients Ask Resources"). Our Spring Boot app is the Client; Google is the Authorization Server and, for APIs like Calendar, the Resource Server.

    4. Scope and Consent

    The authorization server must know exactly what the client wants. OAuth represents this requested access through scopes. A calendar app could request calendar.read instead of unrestricted access to the whole Google account. A scope represents the access being requested or granted. Google then displays a consent screen:

    CoderArmy App wants permission to:
  View your basic profile
  Read your calendar

    The client requests specific scopes, the authorization server displays consent, and the user approves or rejects. For a basic OIDC login, the application requests openid, profile, and email; the same three scopes are configured under data access in the Google Cloud Console.

    Important: The scope openid is special: it tells the provider that this is an OpenID Connect request, not a plain OAuth 2.0 request. Without it, the provider will not return an ID token.

    Follow the principle of least privilege: request only what the application genuinely needs. calendar.read is safer than full account access, and openid profile email is enough for login.

    5. OAuth vs OIDC Tokens

    After authorization, the client needs a credential it can present to the resource server: the access token.

    Authorization Server -- access token --> Client -- bearer token --> Resource Server

    An access token is a credential used by a client to access a protected resource. It may be a JWT, but OAuth 2.0 does not require it; it can also be an opaque, random-looking value. Treat it as opaque unless the authorization server explicitly documents its format.

    OAuth solves delegated authorization ("What can this client access?"), but login requires an identity answer ("Who signed in?"). OAuth 2.0 alone is not an identity protocol; OpenID Connect (OIDC) adds authentication and identity on top of it.

    Protocol Primary purpose Main question
    OAuth 2.0 Delegated authorization What can this application access?
    OpenID Connect Authentication and identity Who signed in?

    The ID token is intended for the client and describes the authentication event and the user's identity. It is normally a signed JWT:

    {
  "sub": "123456789",
  "iss": "https://accounts.google.com",
  "aud": "our-google-client-id",
  "name": "Aditya",
  "email": "adi@gmail.com"
}
    Claim Meaning
    sub Stable subject identifier for the user at that provider
    iss Issuer that created the token
    aud Client for which the token was issued
    exp Expiration time

    Access tokens should expire. A refresh token lets the client obtain a new access token without repeating the whole login and consent flow; it is sent to the authorization server's token endpoint, not to a resource API.

    Token Used by Sent to Purpose
    Access token Client Resource server Access a protected API
    ID token Client Client application Verify authentication and obtain identity information
    Refresh token Client Authorization server Obtain a new access token

    An ID token is not a replacement for an access token; do not use it to call a protected API unless that API explicitly supports it.

    6. Authorization Code Flow

    The client must obtain tokens without exposing them through browser redirects. The Authorization Code Flow has two stages: the browser receives a short-lived authorization code, and the backend exchanges that code for tokens through a direct server-to-server request.

    Step 1: Start the Authorization Request

    The user clicks "Continue with Google," and the app redirects the browser to Google's authorization endpoint with:

    • client_id: the ID Google gives the registered app (for example coderarmy-app-123); an identifier, not a secret.
    • redirect_uri: where Google returns the browser, here http://localhost:8080/login/oauth2/code/google; it must exactly match a registered URI.
    • scope: openid, profile, email; openid marks the request as OpenID Connect.
    • response_type=code: asks for a code rather than placing final tokens in the browser redirect.
    • state: a random value verified by the client; it correlates the callback with the request and guards against login CSRF.

    Step 2: Google Authenticates the User

    The browser is on Google's domain. Google may use a password, passkey, or two-factor authentication. The security boundary is: Google credentials go from the browser to Google and never to our Spring Boot application.

    Step 3: The User Gives Consent

    Google shows the requested permissions (profile and email for basic login; calendar access for a Calendar integration). After approval, Google knows the user authenticated and approved the access.

    Step 4: Google Returns an Authorization Code

    Google redirects the browser to the registered callback:

    http://localhost:8080/login/oauth2/code/google
?code=A7D91XYZ
&state=abc123

    The code is a short-lived temporary credential representing the successful authorization step. Authorization code != Access token: it is not normally used to call a resource API; its purpose is to be exchanged.

    Step 5: The Backend Exchanges the Code for Tokens

    The Spring Boot backend contacts Google's token endpoint with the authorization code, the redirect URI, and client authentication and/or PKCE proof. Google responds with an access token, an ID token, and optionally a refresh token.

    Channel Communication path Typical data
    Front channel Through the user's browser Authorization request, code and state
    Back channel Directly between backend and token endpoint Code exchange and tokens

    The code passes through the browser, but the final tokens arrive through the back channel.

    Interviewer's perspective: If asked "why not return the tokens directly to the browser?", the answer is that tokens in a redirect URL can leak through browser history, logs, or the referrer header. The code flow keeps tokens on the back channel; only the short-lived code travels through the browser.

    7. PKCE from First Principles

    An attacker who steals an authorization code may try to exchange it before the legitimate client. PKCE binds the authorization request to the client instance that later performs the token exchange. PKCE stands for "Proof Key for Code Exchange," pronounced "pixy."

    Before starting authorization, the client generates a long, random code_verifier, then hashes it (normally SHA-256) to produce the code_challenge:

    SHA-256(code_verifier) -> code_challenge

    During the authorization request the client sends the code_challenge but keeps the code_verifier locally; the server remembers the challenge. During the token exchange the client sends the authorization_code plus the code_verifier, and the server compares SHA-256(received code_verifier) with the original code_challenge. If they match, tokens are issued; if not, the request is rejected. An attacker may steal the code, but without the verifier it cannot be exchanged.

    Aspect Authorization code flow without PKCE Authorization code flow with PKCE
    Client type it suits Confidential clients that can hold a secret Public clients (SPA, mobile, desktop) and confidential ones
    Secret needed to exchange code Client secret None; the code_verifier acts as the proof
    What travels in the auth request No challenge code_challenge (hash of the verifier)
    What is kept locally Nothing extra code_verifier, kept private by the client
    Protection against stolen code Weak for public clients Strong; stolen code is useless without the verifier
    Idea Prove identity with a shared secret Bind the request to the instance that started it

    Important: PKCE is not a replacement for a client secret. The secret proves what the application is; PKCE proves the same client instance that started the flow is finishing it. For a Spring Boot server-side app, Spring Security handles PKCE automatically.

    8. Registering the Application with Google

    Google must know which application is requesting login and which callbacks it can trust: register the app, receive the Client ID and Client Secret, and register the allowed redirect URI. For this local demo the authorized redirect URI is http://localhost:8080/login/oauth2/code/google. Spring Security uses this default redirect URI template:

    {baseUrl}/login/oauth2/code/{registrationId}

    Here baseUrl = http://localhost:8080 and registrationId = google. The registration ID is the name given in application.properties, so the callback becomes /login/oauth2/code/google.

    Important: The scheme, host, port, and path of the configured redirect URI must exactly match what Google has on record. Even a small mismatch causes a redirect_uri_mismatch error before any code is issued.

    10. User Entity, Repository, and Application User Service

    @Entity
public class AppUser {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private String email;
    private String provider;
    @Column(name = "provider_subject")
    private String providerSubject;
    private String role;
    // No password field; constructors plus getters and setters omitted.
}

    There is deliberately no password field: Google owns and verifies the password, and our app never receives it.

    Why store providerSubject? Google puts a sub claim in the ID token:

    { "sub": "109324823948234", "email": "student@gmail.com", "name": "Rohit" }

    sub means subject, the provider's stable identifier for the user. We store provider = google and providerSubject = value of sub, and this pair should normally be unique. It is a better external identity key than email because an email may be changed, missing, or unverified depending on the provider and scopes.

    Golden rule: Link external identities by provider + subject, never by email. Emails change; the provider's subject does not, which is why the unique constraint belongs on the pair.

    public interface AppUserRepository extends JpaRepository<AppUser, Long> {
    Optional<AppUser> findByProviderAndProviderSubject(
        String provider, String providerSubject);
}

    The signup happens inside our app after Google authenticates the user:

    @Service
public class AppUserService {
    private final AppUserRepository appUserRepository;
    public AppUserService(AppUserRepository appUserRepository) {
        this.appUserRepository = appUserRepository;
    }
    @Transactional
    public AppUser registerOrUpdate(String provider, OidcUser oidcUser) {
        String providerSubject = oidcUser.getSubject();
        String name = oidcUser.getClaimAsString("name");
        String email = oidcUser.getClaimAsString("email");
        Optional<AppUser> existingUser = appUserRepository
            .findByProviderAndProviderSubject(provider, providerSubject);
        if (existingUser.isPresent()) {
            AppUser user = existingUser.get();
            user.setName(name);
            user.setEmail(email);
            return user; // updated via JPA dirty checking
        }
        return appUserRepository.save(
            new AppUser(name, email, provider, providerSubject, "USER"));
    }
    public Optional<AppUser> findByProviderAndSubject(String provider, String subject) {
        return appUserRepository.findByProviderAndProviderSubject(provider, subject);
    }
}

    The query is SELECT * FROM app_user WHERE provider = 'google' AND provider_subject = '123';. If the user exists, update the profile and load the account; otherwise insert a new AppUser with the default USER role. This is the OAuth/OIDC signup process.

    11. CustomOidcUserService and SecurityConfig

    Spring Security already talks to OIDC providers. Preserve that processing and add only our database logic: Spring returns an OidcUser, our code saves or updates the internal user, and we return the OidcUser to Spring Security.

    @Service
public class CustomOidcUserService
        implements OAuth2UserService<OidcUserRequest, OidcUser> {
    private final OidcUserService delegate;
    private final AppUserService appUserService;
    public CustomOidcUserService(AppUserService appUserService) {
        this.appUserService = appUserService;
        this.delegate = new OidcUserService();
    }
    @Override
    public OidcUser loadUser(OidcUserRequest userRequest)
            throws OAuth2AuthenticationException {
        // Let Spring perform the provider interaction and OIDC processing.
        OidcUser oidcUser = delegate.loadUser(userRequest);
        String provider = userRequest
                .getClientRegistration()
                .getRegistrationId();
        // Run our application-specific signup/update logic.
        appUserService.registerOrUpdate(provider, oidcUser);
        return oidcUser;
    }
}

    The line delegate.loadUser(userRequest) hides a lot: by then the code has been exchanged, the tokens are available, Spring has validated the OIDC response (possibly calling the UserInfo endpoint), and Spring has built the OidcUser. The pattern is "delegate then decorate."

    @Configuration
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(
            HttpSecurity http,
            CustomOidcUserService customOidcUserService) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/").permitAll()
                .anyRequest().authenticated()
            )
            .oauth2Login(oauth -> oauth
                .userInfoEndpoint(userInfo -> userInfo
                    .oidcUserService(customOidcUserService)
                )
                .defaultSuccessUrl("/profile", true)
            );
        return http.build();
    }
}

    oauth2Login() enables the OAuth 2.0 Login and OIDC flow and manages the endpoints: authorization (redirect to Google), token (exchange code for tokens), redirection (/login/oauth2/code/google), and UserInfo (extra profile claims). requestMatchers("/").permitAll() keeps the home page public, anyRequest().authenticated() protects the rest, and defaultSuccessUrl("/profile", true) lands the user on /profile after login.

    Important: Register CustomOidcUserService through userInfoEndpoint().oidcUserService(...) rather than replacing the whole OAuth2 login machinery. Spring keeps doing the protocol work; we only add the AppUser upsert.

    12. Controller and Client Registration Properties

    @RestController
public class UserController {
    private final AppUserService appUserService;
    public UserController(AppUserService appUserService) {
        this.appUserService = appUserService;
    }
    @GetMapping("/")
    public String home() {
        return "Public Home. Login using: "
            + "http://localhost:8080/oauth2/authorization/google";
    }
    @GetMapping("/profile")
    public Map<String, Object> profile(
            @AuthenticationPrincipal OidcUser oidcUser) {
        AppUser appUser = appUserService
            .findByProviderAndSubject("google", oidcUser.getSubject())
            .orElseThrow();
        Map<String, Object> response = new LinkedHashMap<>();
        response.put("internalUserId", appUser.getId());
        response.put("provider", appUser.getProvider());
        response.put("subject", oidcUser.getSubject());
        response.put("name", oidcUser.getClaimAsString("name"));
        response.put("email", oidcUser.getClaimAsString("email"));
        response.put("role", appUser.getRole());
        return response;
    }
}

    After login the response may look like:

    { "internalUserId": 1, "provider": "google",
  "subject": "108293472983749823749", "name": "Rohit Negi",
  "email": "example@gmail.com", "role": "USER" }
    Data Source
    subject, name, email Google/OIDC claims
    internalUserId, role Our application database 
    spring.application.name=oauth2-demo

# Google OAuth 2.0 / OIDC
spring.security.oauth2.client.registration.google.client-id=${GOOGLE_CLIENT_ID}
spring.security.oauth2.client.registration.google.client-secret=${GOOGLE_CLIENT_SECRET}
spring.security.oauth2.client.registration.google.scope=openid,profile,email

# JPA demo configuration

    Google is a recognized provider, so the authorization, token, and UserInfo endpoint URLs need no manual configuration. Do not hardcode the client secret: keep the placeholders and supply GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET through environment variables (IntelliJ: Run -> Edit Configurations -> Environment variables). Never commit a real secret to Git.

    Interviewer's perspective: Putting the client secret directly in application.properties and committing it fails the security-judgment test. The expected answer is externalized configuration: placeholders in the properties file, real values in environment variables or a secrets manager.

    13. Google Cloud Console Setup and Running/Testing

    Setup steps:

    1. Create a Google Cloud project and open Google Auth Platform (select Get Started if new).
    2. Configure branding: app name CoderArmy OAuth Demo plus support email and developer contact.
    3. Select audience External for normal Gmail accounts; in testing mode add tester accounts.
    4. Configure data access: request only openid, profile, email (least privilege).
    5. Create an OAuth client (Clients -> Create Client), type Web application; JavaScript origins stay empty for this server-side demo.
    6. Add the authorized redirect URI http://localhost:8080/login/oauth2/code/google; scheme, host, port, and path must match, or you get redirect_uri_mismatch.
    7. Create the client; Google generates a Client ID and Client Secret, stored as environment variables.

    Running: start the app and open http://localhost:8080/, or start login at http://localhost:8080/oauth2/authorization/google (the endpoint name is the registration ID google). Spring finds the ClientRegistration "google", builds the authorization request (client_id, redirect_uri, scope, state, response_type=code), and sends a 302 redirect. The user enters credentials on Google's domain, never at localhost:8080. Google redirects to http://localhost:8080/login/oauth2/code/google?code=ABC...&state=XYZ...; Spring validates it, performs the back-channel code exchange, processes the OIDC result into an OidcUser, CustomOidcUserService saves or updates the AppUser, and the success handler redirects to /profile.

    14. What Authenticates Later /profile Requests, and the Complete Flow Recap

    In this server-side OAuth2 Login flow the browser does not send Google's ID token with every /profile request. After login:

    Spring authenticates the user
        |
        v
Authentication is stored in the SecurityContext
        |
        v
The SecurityContext is tied to the HTTP session
        |
        v
The browser sends the session cookie on later requests

    The app is therefore session-based after login.

    Feature Typical use
    oauth2Login() Log a browser user in and usually maintain a session
    oauth2ResourceServer().jwt() Protect an API that receives bearer access tokens

    Important: Here the ID token is consumed at login time to build the OidcUser; it is not replayed on each /profile call. The session cookie keeps the browser authenticated with our Spring application.

    Complete flow recap (11 steps):

    1.  User opens /oauth2/authorization/google
2.  Spring redirects the browser to Google
3.  Google authenticates the user
4.  User approves the requested scopes
5.  Google redirects back with an authorization code
6.  Spring exchanges the code through the back channel
7.  Spring validates and processes the OIDC response
8.  Spring creates an OidcUser
9.  CustomOidcUserService saves or updates AppUser
10. Spring stores the authenticated state in the session
11. The user accesses /profile as an authenticated user

    Google proves the external identity; our application still owns its internal user record, roles, and business rules.

    15. Myth vs Reality

    Myth Reality
    "OAuth 2.0 is a login protocol" OAuth 2.0 is delegated authorization; OpenID Connect adds authentication and identity on top of it.
    "The client is always the browser" The client is the application requesting access: Spring Boot, mobile, desktop, or browser-based.
    "An access token must be a JWT" It may be a JWT, but OAuth 2.0 does not require it; it can be an opaque value.
    "The ID token is used to call APIs" The ID token is for the client to verify authentication; calling an API needs the access token.
    "OAuth scopes grant full account access" Scopes slice access; a calendar app can request calendar.read and nothing more.
    "PKCE and client secrets are the same thing" A client secret authenticates a confidential client; PKCE binds the code exchange to the client instance.
    "The browser sends Google's ID token to /profile on every request" After login the app is session-based; the browser sends the session cookie.
    "oauth2Login and oauth2ResourceServer are interchangeable" oauth2Login logs a browser user in (session); oauth2ResourceServer protects an API using bearer tokens.

    16. Common Trap Questions

    Trap 1 - "The app gets the user's Google password." Verdict: False. The password goes from the browser to Google and never to our Spring Boot application; we receive an authorization code and then tokens.

    Trap 2 - "OAuth 2.0 can also tell us who the user is." Verdict: False. OAuth 2.0 answers "what can this application access?". Identity ("who signed in?") comes from OpenID Connect's ID token.

    Trap 3 - "The authorization code is the access token." Verdict: False. The code is a short-lived temporary credential; its purpose is to be exchanged on the back channel for access and ID tokens.

    Trap 4 - "The tokens come back through the browser redirect." Verdict: False. Only the code and state travel through the browser (front channel); the code exchange and tokens happen directly between the backend and Google's token endpoint (back channel).

    Trap 5 - "PKCE is pointless when we already have a client secret." Verdict: False. A client secret proves what the application is; PKCE binds the code exchange to the client instance that started the flow, protecting against stolen codes, especially for public clients.

    Trap 6 - "After Google login, every /profile request carries the ID token." Verdict: False. In this server-side flow the ID token is processed at login time; later requests are authenticated by the session cookie tied to the SecurityContext.

    Trap 7 - "Storing the email is enough to identify the user." Verdict: False. Email can change, be missing, or be unverified; store provider + providerSubject (the sub claim) as the stable external identity key.

    17. Points to Remember

    1. OAuth 2.0 is delegated authorization ("what can this app access?"); OpenID Connect adds authentication and identity ("who signed in?") on top of it.
    2. The four roles are Resource Owner, Client, Authorization Server, and Resource Server (remember R-C-A-R).
    3. The user's Google password never reaches our application; credentials stay between the browser and Google.
    4. Scopes (openid, profile, email, or calendar.read) define limited access; openid marks an OIDC request and enables the ID token.
    5. An access token may be a JWT or opaque and goes to the resource server; an ID token is normally a signed JWT meant for the client.
    6. The authorization code is short-lived and exchanged on the back channel; the code and state travel through the browser (front channel).
    7. PKCE sends a code_challenge in the authorization request and the code_verifier at token exchange, so a stolen code is useless without the verifier.
    8. Spring Security's default redirect URI is {baseUrl}/login/oauth2/code/{registrationId}, which for Google is /login/oauth2/code/google, and it must match Google exactly.
    9. CustomOidcUserService delegates OIDC processing to Spring and then upserts the internal AppUser via provider + providerSubject, storing no password.
    10. The app is session-based after login: oauth2Login() stores authentication in the session, while oauth2ResourceServer().jwt() is the separate choice for bearer-token APIs.

    18. Likely Interview Questions

    Question Crisp Answer
    What is OAuth 2.0 primarily for? Delegated authorization: letting an app access a user's resource without sharing the password.
    What does OIDC add on top of OAuth 2.0? Authentication and identity through the ID token, answering "who signed in?".
    Name the four OAuth roles. Resource Owner, Client, Authorization Server, Resource Server.
    What is the client in OAuth? The application requesting delegated access (Spring Boot, mobile, desktop, or browser app), not necessarily the browser.
    Access token vs ID token? Access token calls protected APIs; ID token tells the client who authenticated. Neither replaces the other.
    Why the authorization code flow? To keep tokens off the browser redirect: only a short-lived code travels the front channel; tokens are fetched on the back channel.
    What is PKCE and why is it needed? Proof Key for Code Exchange: a verifier/challenge pair that binds the code exchange to the client instance, defeating stolen-code attacks.
    Why store provider and subject? They form a stable external identity key; email can change or be unverified.
    What does oauth2Login() do? Enables OAuth2/OIDC login, delegates OIDC processing, and typically maintains a session.
    How does CustomOidcUserService fit in? It calls Spring's OidcUserService, upserts the internal AppUser, and returns the OidcUser.
    What authenticates later /profile requests? The Spring Security session (session cookie), not the Google ID token replayed per request.
