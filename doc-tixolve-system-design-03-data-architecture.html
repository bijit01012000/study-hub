    Database-Per-Service

    Each service owns its own database — separate schema, no cross-service SQL joins allowed.

    Service Database Key Tables
    auth-service auth_db users, role_mappings
    knowledge-service knowledge_db documents, chunks, embeddings, ingestion_jobs
    chat-service chat_db conversations, messages
    ticket-service ticket_db tickets, ticket_events
    notification-service notification_db notifications

    Dev trade-off: In local dev and demo, all schemas share one Postgres instance to save cost. Production would use separate RDS instances with separate credentials and no network path between them at the DB layer. This is noted in code comments where relevant.

    Why database-per-service? Schema autonomy — services evolve their data model independently. If ticket-service needs a new column, it doesn't require coordinating with knowledge-service. In a shared DB, any migration is a cross-team negotiation and any schema change can break other services' queries. Database-per-service also prevents the "lazy join" — where a developer writes a cross-service SQL join because it's easy, creating invisible tight coupling.

    Outbox Pattern

    The Problem (Dual-Write)

    You need to write to your database AND publish a Kafka event. If you do them as two separate calls:

    ticketRepository.save(ticket)     // succeeds
kafkaTemplate.send(event)         // crashes here

    Your DB has the change but the event is never published — consumers never find out. Or:

    kafkaTemplate.send(event)         // succeeds — event published
ticketRepository.save(ticket)     // crashes here

    You've announced a change that was actually rolled back. Either way, your data and your events are inconsistent.

    The Solution

    Write the business entity AND an outbox row in a single database transaction. A separate background process reads unpublished outbox rows and sends them to Kafka.

    @Transactional
public Ticket createTicket(CreateTicketRequest req) {
    Ticket ticket = ticketRepository.save(new Ticket(req));
    // Same transaction — both commit or both rollback atomically
    outboxRepository.save(OutboxEvent.of("ticket.created", ticket.toPayload()));
    return ticket;
}

// Separate @Scheduled process (every 100ms):
@Scheduled(fixedDelay = 100)
public void publishPendingEvents() {
    List<OutboxEvent> pending = outboxRepository.findUnpublished();
    for (OutboxEvent event : pending) {
        kafkaTemplate.send(event.getTopic(), event.getPayload());
        outboxRepository.markPublished(event.getId());
    }
}

    Guarantee: The business change and the outbox row either both commit or both roll back — you can never have a committed DB change with no corresponding event, or an event for a rolled-back change.

    Scheduler vs Debezium

    Approach How it works Pros Cons
    Scheduler (polling) App polls outbox table on an interval Simple, no extra infra ~100ms latency, polling overhead
    Debezium (CDC) Reads Postgres WAL directly Near-real-time, no polling More complex, extra container, handles DB restart edge cases

    Decision: Scheduler for MVP. Debezium is the production upgrade path — noted in code comments. This is a defensible trade-off: at low event volume, polling every 100ms is negligible overhead.

    Vector Storage (pgvector)

    Why pgvector over a dedicated vector DB?

    For this data volume (thousands of document chunks, not millions), pgvector performs well and eliminates an extra infrastructure component. Vectors are co-located with chunk metadata — no cross-DB lookups needed for the hybrid search merge step.

    The trade-off: Purpose-built vector DBs (Qdrant, Pinecone, Weaviate) have better ANN index structures and query performance at tens of millions of vectors. pgvector's HNSW and IVFFlat indexes degrade in performance at that scale. Migration to a dedicated vector DB is the right call when data volume justifies the operational complexity.

    Schema

    CREATE TABLE chunks (
    id           UUID PRIMARY KEY,
    document_id  UUID NOT NULL REFERENCES documents(id),
    chunk_index  INT NOT NULL,
    content      TEXT NOT NULL,
    source_page  INT,
    embedding    vector(1536),   -- pgvector column
    fts_vector   tsvector,       -- full-text search
    created_at   TIMESTAMPTZ DEFAULT now()
);

-- Approximate nearest neighbor index for vector search
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

-- Full-text search index
CREATE INDEX ON chunks USING gin(fts_vector);

    Hybrid Search — How It Works

    Two parallel searches, merged with Reciprocal Rank Fusion (RRF):

    Step 1 — Vector search:

    SELECT id, content, 1 - (embedding <=> query_embedding) AS score
FROM chunks
ORDER BY embedding <=> query_embedding
LIMIT 20;

    Step 2 — Full-text search:

    SELECT id, content, ts_rank(fts_vector, query) AS score
FROM chunks
WHERE fts_vector @@ to_tsquery('english', 'keyword1 & keyword2')
ORDER BY score DESC
LIMIT 20;

    Step 3 — RRF merge:

    rrf_score(doc) = Σ 1 / (rank_in_list + k)

where k = 60

    Each document's RRF score is the sum of its rank-based scores from both lists. Documents appearing high in both lists get the strongest combined score. Re-sort by RRF score, return top-K.

    Why hybrid over pure vector?

    • Pure vector misses exact matches: product names, ticket IDs, version numbers, acronyms
    • Pure keyword misses paraphrased queries and semantic meaning
    • Hybrid captures both — this is production practice (Azure AI Search, Elasticsearch, etc.)

    Ticket Event Log

    ticket-service uses an append-only ticket_events table alongside tickets:

    CREATE TABLE ticket_events (
    id          UUID PRIMARY KEY,
    ticket_id   UUID NOT NULL REFERENCES tickets(id),
    event_type  VARCHAR(50) NOT NULL,   -- STATUS_CHANGED, ASSIGNED, COMMENTED
    old_value   TEXT,
    new_value   TEXT,
    changed_by  UUID NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT now()
);

    Every status change is recorded, never overwritten. This gives:

    • Full audit trail
    • SLA tracking (time between state transitions is calculable)
    • Foundation for event sourcing patterns (awareness demonstrated even though this isn't full event sourcing)
