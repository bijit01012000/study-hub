    Coupling & Cohesion

    10 sections · 700 words

    Foundation · LLD Core Concepts · Concept 01 of 09

    The Idea

    • High cohesion: everything in a class serves one purpose.
    • Low coupling: classes know as little as possible about each other.
    • The goal: change one class without rippling into ten others.

    Before

    class OrderProcessor {
    // two jobs: orders + email
    void checkout(Order o, Inventory inv) {
        for (Item i : o.items())
            inv.items.get(i.sku()).qty -= i.qty();
            // reaches into Inventory's own map
        emailReceipt(o); // unrelated 2nd job
    }
}
// any change to how Inventory stores items breaks this too

    The class reaches into another class's internals.

    After

    class Inventory {
    void reserve(String sku, int qty) { .. }
    // owns its own storage
}
class OrderProcessor {
    // one job: process the order
    Notifier notifier;
    // email moved out entirely
    void checkout(Order o, Inventory inv) {
        for (Item i : o.items())
            inv.reserve(i.sku(), i.qty());
            // never sees the map
        notifier.sendReceipt(o);
    }
}

    The class talks through the interface.

    Don't Over-Correct

    • Some coupling is unavoidable; a class must call something.
    • Splitting one cohesive class into three tiny ones can raise coupling.

    Quick Check

    High cohesion inside a class, low coupling between classes, one sentence, both halves.

    How It's Built

    The Shape

    OrderProcessor
    + checkout(o)          one job: process orders
    knows one Inventory method
    calls one method

Inventory
    + reserve(sku, qty)    owns its own storage
    free to change internally

ONE THIN EDGE. NO REACHING INTO THE OTHER'S DATA

    The Move (3 Steps)

    1. Find the reach-through. One class touching another's field or internal collection directly is the coupling to cut.
    2. Ask what a class's methods share. If half serve one purpose and half serve another, that's the split (cohesion).
    3. Talk to the smallest interface that does the job: a reserve() call, not the whole object's guts.

    In The Interview

    "OrderProcessor was reaching into Inventory's own map to decrement stock, so any change to how Inventory stores items would break checkout too. I gave Inventory a reserve(sku, qty) method and had OrderProcessor call that instead, it no longer knows how inventory is stored."

    How It's Different

    The Confusion Pairs

    Coupling vs dependency. Every class depends on something. The question is whether it depends on a stable abstraction or a volatile concrete detail.

    Low coupling vs no coupling. Zero coupling means the classes can't collaborate at all. The goal is the loosest coupling that still gets the job done.

    Cohesion vs SRP. SRP is cohesion's interview name: one reason to change is exactly "does everything in here serve one purpose."

    Coupling vs performance. An interface hop costs one virtual call, not a redesign. Don't skip abstraction to "save a function call."

    They Say: "Inventory moves from a HashMap to a database"

    • With it: OrderProcessor's code doesn't change, it only ever called reserve().
    • Without: every direct map access in OrderProcessor has to be found and rewritten.

    Watch Out For

    • A "train wreck," a.getB().getC().getD(), is a coupling smell even when it compiles cleanly.
    • A class importing 15 others isn't automatically low-cohesion. Check what its own methods do, not what it depends on.
    • Global or static state couples every caller to it invisibly: no import in any diagram shows it.
    • Cohesion isn't "small file." A 200-line class doing one job beats five 20-line classes each doing a third of two jobs.
    • An interface only reduces coupling if callers actually depend on the interface, not the concrete class behind it.
