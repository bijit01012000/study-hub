    Exception Hierarchy Deep Dive | throw vs throws | Custom Exceptions

    18 sections · 4,069 words

    Lecture 44

    Scope evidence: "Exception Hierarchy Deep Dive | throw vs throws | Custom Exceptions" (playlist map, verified). Repo evidence: 6 Demo files.

    Lecture 43 established what an exception is and how try, catch and finally cooperate. This lecture goes one level deeper into the type system that makes those blocks meaningful: the complete Throwable tree, the checked versus unchecked split, the precise difference between throw and throws, how an uncaught exception unwinds the call stack, and how exception chaining preserves the original cause. It then builds the skill that every production codebase needs — writing custom exceptions that carry meaning instead of leaking implementation details. The governing idea is that an exception type is part of a method's contract, so choosing it well is an API design decision, not an afterthought.

    1. The Throwable Tree

    Throwable is the root of every object that Java allows to be thrown or caught. The language enforces this: only a subclass of Throwable may appear after throw, and a catch clause must name a Throwable subtype. The tree splits immediately into two branches — Error and Exception — and the Exception branch splits again into RuntimeException (unchecked) and everything else (checked).

    Throwable
  Error
    VirtualMachineError
      OutOfMemoryError
      StackOverflowError
    AssertionError, LinkageError
  Exception
    RuntimeException
      NullPointerException
      ArithmeticException
      ArrayIndexOutOfBoundsException
      ClassCastException
      IllegalArgumentException
    IOException
      FileNotFoundException
    SQLException
    ClassNotFoundException
    InterruptedException

    Because every type above inherits from Throwable, a single catch (Throwable t) would match all of them; that is exactly why catching Throwable is discouraged (Section 12). Catching the most specific subtype is always preferable.

    // Demo.java — catching specific subtypes from the Throwable tree
public class Demo {
    public static void main(String[] args) {
        Object[] data = {10, 0};
        try {
            int result = (int) data[0] / (int) data[1];
            System.out.println(result);
        } catch (ArithmeticException e) {
            System.out.println("Arithmetic: " + e.getMessage());
        }

        try {
            String s = null;
            System.out.println(s.length());
        } catch (NullPointerException e) {
            System.out.println("NPE caught: " + e.getMessage());
        }
    }
}

    Memory aid Error = the environment broke; Exception = the program can react. OutOfMemoryError and StackOverflowError are conditions the JVM reports and rarely lets you fix in place; the Exception branch is where handling logic belongs.

    2. Error versus Exception

    Error and Exception share a parent but describe opposite situations: an unrecoverable failure of the runtime versus a condition a program might survive.

    Aspect Error Exception
    Meaning Serious problem in the JVM/environment Condition arising during normal execution
    Typical members OutOfMemoryError, StackOverflowError, VirtualMachineError IOException, SQLException, NullPointerException
    Checked? Unchecked (never declared) Either checked or unchecked
    Recoverable? Generally not — the process is compromised Often yes, if the caller acts
    Should you catch it? Almost never Yes, at the layer that can respond
    Common cause Resource exhaustion, JVM defect, bad recursion Bad input, missing file, null, illegal state

    The practical rule: handle Exception subtypes you understand; let Error propagate, because a program that has run out of memory or overflowed its stack cannot be trusted to continue.

    3. Checked versus Unchecked Exceptions

    The compiler enforces a distinction that no other mainstream language draws so strictly.

    • A checked exception is any Throwable that is not a RuntimeException and not an Error — that is, Exception and its subclasses excluding RuntimeException and its subclasses. It must be either caught or declared in a throws clause.
    • An unchecked exception is a RuntimeException (or an Error) and any of their subclasses. The compiler does not require it to be caught or declared.
    Aspect Checked exception Unchecked exception
    Root types Exception (excluding RuntimeException) RuntimeException and Error
    Examples IOException, SQLException, ClassNotFoundException, InterruptedException, FileNotFoundException NullPointerException, ArithmeticException, ArrayIndexOutOfBoundsException, ClassCastException, IllegalArgumentException
    Compiler enforcement Must catch or declare Not enforced
    Represents Recoverable, caller-actionable condition Programming error or domain rule violation
    Typical fix Retry, fall back, report to user Repair the code or reject the input
    Propagation Caller is forced to acknowledge it Propagates silently until caught

    Important "Checked" and "unchecked" are compile-time categories, not runtime ones. The JVM throws a NullPointerException with exactly the same mechanism as an IOException; only the compiler treats them differently.

    4. Why Some Exceptions Are Checked and Others Are Not

    The designers chose the split deliberately. Checked exceptions model conditions outside the program's control that a caller can plausibly recover from:

    • IOException means a file is missing, a disk is full, or a socket dropped. The caller can retry, use a fallback path, or report the problem — the program's logic is not necessarily wrong.
    • InterruptedException means a thread blocked in sleep, wait or join was asked to stop. This is a normal coordination signal that the caller is expected to handle by restoring the interrupt flag or terminating cleanly.

    Unchecked exceptions model programming defects and violated preconditions, where no sensible recovery exists at the call site:

    • NullPointerException means a reference that should have been non-null was null — a bug in the code that produced it.
    • IllegalArgumentException means a caller passed an argument that violates the method's contract — again a bug, best surfaced loudly.
    • ClassCastException, ArithmeticException (integer division by zero) and ArrayIndexOutOfBoundsException are all symptoms of incorrect logic.

    Forcing every caller to declare these defects would bury method signatures under noise without improving safety, so the compiler leaves them unchecked.

    Interviewer's perspective The clean answer is one sentence: checked exceptions describe recoverable external conditions the caller can act on; unchecked exceptions describe defects in the program. When asked "why is InterruptedException checked?", tie it to thread coordination: interruption is a request the blocked thread must honour, not a bug.

    5. throw versus throws

    These two keywords look alike and are asked about constantly, yet they live in different parts of the language. throw is a statement executed at runtime that raises one exception instance at a specific point in the code. throws is a declaration in a method signature that tells the compiler which checked exceptions may escape the method, so every caller can handle them.

    Aspect throw throws
    Kind Statement inside a method body Clause in a method signature
    Purpose Actually raise an exception instance Declare possible escape routes
    Operand One Throwable instance A comma-separated list of exception types
    When it runs At runtime, when execution reaches it At compile time, part of the contract
    Count One exception per throw Multiple types: throws A, B
    Required for unchecked? Yes, to raise one No, but allowed
    Example throw new IllegalArgumentException("bad"); void read() throws IOException 
    // Demo2.java — throw raises an instance; throws declares what may escape
import java.io.*;

public class Demo2 {
    static int divide(int a, int b) {
        if (b == 0) {
            throw new ArithmeticException("divide by zero");
        }
        return a / b;
    }

    static String readLine(String path) throws IOException {
        try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
            return reader.readLine();
        }
    }

    public static void main(String[] args) {
        try {
            System.out.println(divide(10, 0));
        } catch (ArithmeticException e) {
            System.out.println("Caught: " + e.getMessage());
        }

        try {
            readLine("missing.txt");
        } catch (IOException e) {
            System.out.println("IO: " + e.getMessage());
        }
    }
}

    divide may throw ArithmeticException, an unchecked type, so no throws clause is needed. readLine performs file I/O, which can raise the checked IOException, so it must declare throws IOException and main must handle it. Multiple checked types are listed with commas: void work() throws IOException, SQLException.

    Memory aid throw = the verb (do it now); throws = the warning label (may happen here). A method that declares throws does not necessarily throw; a method that executes throw necessarily does.

    6. Exception Propagation and Reading a Stack Trace

    When an exception is raised and the current method does not catch it, the JVM unwinds the call stack: the exception propagates outward one frame at a time until some catch matches or it reaches the top of the thread, where the default handler prints a stack trace and terminates that thread. At each frame the caller has two choices: catch and handle, or re-declare with throws and pass the responsibility up.

    A stack trace is read top-down. The first line names the exception type and message; the next line is the frame where the exception was created, and each subsequent line is its caller, ending at main.

    java.lang.ArithmeticException: / by zero
    at Demo2.divide(Demo2.java:6)      <- where it was thrown
    at Demo2.main(Demo2.java:22)       <- its caller, then the top

    Reading it: the top frame is the origin, the bottom frame is the entry point, and every frame between them is part of the call chain. Locating the topmost frame in your own source is usually the fastest path to the defect.

    Important An exception does not "lose" its path when it propagates. The trace records the frames captured at construction time, so wrapping it later (Section 7) does not erase the original origin.

    7. Exception Chaining and Wrapping

    When a low-level exception is not meaningful to the caller, the method may wrap it in a higher-level exception that speaks the caller's language, while preserving the original as the cause. The standard constructors accept a Throwable cause, and getCause() returns it; initCause is the fallback for exceptions constructed before the cause was known.

    // Demo3.java — wrapping preserves the original cause
import java.io.*;

public class Demo3 {
    static class ServiceException extends Exception {
        ServiceException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    static String load(String path) throws ServiceException {
        try {
            BufferedReader reader = new BufferedReader(new FileReader(path));
            return reader.readLine();
        } catch (IOException e) {
            throw new ServiceException("failed to load " + path, e);
        }
    }

    public static void main(String[] args) {
        try {
            load("missing.txt");
        } catch (ServiceException e) {
            System.out.println(e.getMessage());
            System.out.println("cause = " + e.getCause());
        }
    }
}

    Wrapping matters for three reasons: it hides implementation details from callers, it translates one exception vocabulary into another at a layer boundary, and it keeps the diagnostic chain intact so printStackTrace prints both the wrapper and the cause. The anti-pattern is throw new ServiceException(e.getMessage()), which discards the cause and with it the stack trace of the real failure.

    8. Custom Exceptions

    Java allows you to define your own exception types, and a well-named custom exception communicates intent far better than a generic RuntimeException. A custom exception extends either Exception (making it checked, so callers must handle it) or RuntimeException (making it unchecked, so it propagates freely). The conventional constructors mirror the JDK: a message-only form and a message-plus-cause form, optionally extended with context fields such as an error code.

    Aspect Custom checked exception Custom unchecked exception
    Extends Exception RuntimeException
    Handling forced? Yes — callers must catch or declare No
    Signals Recoverable, expected business condition Programming error or domain rule violation
    Caller obligation Acknowledge and decide Usually let it surface
    Typical use InsufficientBalanceException, PaymentDeclinedException InvalidAgeException, DuplicateOrderException
    Construction cost Heavier: signatures and callers must adapt Light: no signature churn
    Modern preference When recovery is genuinely required For most domain errors in new APIs

    A good custom exception is specific (one clearly named condition), meaningful (its name is self-documenting), and informative (it carries a message and, where useful, structured context such as an error code or the offending value).

    9. When to Choose Checked versus Unchecked

    The choice is an API design decision with a durable cost, because converting a checked exception to unchecked later removes a compile-time obligation that existing callers may depend on, and the reverse breaks compilation everywhere.

    1. Recoverable and caller-actionable → checked. If the caller has a real, different action for the failure (retry, fall back, prompt the user), a checked exception forces that decision at the call site.
    2. Programming error or broken precondition → unchecked. Null arguments, illegal state and bad indexes should crash early and loudly, not clutter signatures.
    3. Domain errors in modern APIs → lean unchecked. Many teams model business rule violations (for example InsufficientBalanceException) as unchecked, especially when the exception must cross layers or be thrown inside lambdas and streams, where checked exceptions are awkward (Section 12).
    4. Do not create a checked exception you cannot handle. If every caller immediately wraps or rethrows it, the check is pure ceremony and an unchecked type would serve better.

    Golden rule Use checked exceptions for conditions from which the caller can reasonably be expected to recover; use unchecked exceptions for programming errors and domain rule violations. When in doubt, the cost of a checked exception falls on every caller forever.

    10. Worked Example: A Custom Checked Exception

    InsufficientBalanceException is a checked exception because an insufficient balance is a predictable, recoverable business condition: the caller may choose to top up the account, reduce the withdrawal, or inform the user. Extending Exception forces that decision to be made explicitly. The class also carries a deficit field, showing how a custom exception can transport structured context beyond a message string.

    // Demo4.java — a custom checked exception forces the caller to handle it
public class Demo4 {
    static class InsufficientBalanceException extends Exception {
        private final double deficit;
        InsufficientBalanceException(String message, double deficit) {
            super(message);
            this.deficit = deficit;
        }
        double deficit() {
            return deficit;
        }
    }

    static class Account {
        private double balance;
        Account(double balance) { this.balance = balance; }

        void withdraw(double amount) throws InsufficientBalanceException {
            if (amount > balance) {
                throw new InsufficientBalanceException(
                        "balance too low by " + (amount - balance),
                        amount - balance);
            }
            balance -= amount;
        }
    }

    public static void main(String[] args) {
        Account account = new Account(100);
        try {
            account.withdraw(150);
        } catch (InsufficientBalanceException e) {
            System.out.println(e.getMessage() + " (deficit " + e.deficit() + ")");
        }
    }
}

    Because the type is checked, the withdraw signature must declare throws InsufficientBalanceException and main must catch it. The deficit() accessor lets the caller react with data, not just text.

    11. Worked Example: A Custom Unchecked Exception and a Wrapping Caller

    InvalidAgeException is an unchecked exception because an out-of-range age is a violated precondition and a domain rule, not a condition the caller can recover from at that point. Extending RuntimeException keeps register free of a throws clause while still allowing a caller to catch the type when it wants a friendly message.

    // Demo5.java — a custom unchecked exception for a domain rule violation
public class Demo5 {
    static class InvalidAgeException extends RuntimeException {
        InvalidAgeException(String message) {
            super(message);
        }
    }

    static void register(String name, int age) {
        if (age < 0 || age > 150) {
            throw new InvalidAgeException("invalid age for " + name + ": " + age);
        }
        System.out.println(name + " registered at age " + age);
    }

    public static void main(String[] args) {
        register("Ada", 36);
        try {
            register("Bob", -5);
        } catch (InvalidAgeException e) {
            System.out.println("Rejected: " + e.getMessage());
        }
    }
}

    A caller that wants to translate the domain error into a service-level error would wrap it: throw new RegistrationException("cannot register " + name, e), preserving the InvalidAgeException as the cause exactly as in Section 7.

    12. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    throws Exception too broad Callers must handle everything and learn nothing Declare the narrowest checked types actually thrown
    Swallowing an exception Empty catch hides failures and corrupts state Handle, log with context, or rethrow
    Losing the cause throw new X(e.getMessage()) discards the original trace Use throw new X(message, e)
    Declaring then ignoring A throws clause whose exception is never handled meaningfully Handle it or remove the check by design
    Checked exception inside a lambda A Stream/lambda cannot declare checked exceptions Wrap in an unchecked type or a helper that rethrows
    Over-creating exception types One exception class per trivial case bloats the API Add a type only when the caller needs to distinguish it
    Custom exception without context A bare type with no message is undebuggable Always pass a message; add context fields when useful
    Exceptions for control flow Using try/catch instead of ordinary branching Reserve exceptions for exceptional conditions
    Catching Throwable or Error Swallows OutOfMemoryError and hides real faults Catch specific Exception subtypes
    Reusing a thrown instance Rethrowing the same instance accumulates misleading frames Construct a fresh exception for each throw

    Important A checked exception cannot be thrown directly from inside a lambda or stream pipeline because Stream methods declare no checked exceptions. The usual remedy is to catch it and rethrow wrapped in an unchecked exception, then unwrap at the boundary.

    13. Myth vs Reality

    Myth Reality
    "throw and throws are the same keyword with different spelling." throw raises an instance at runtime; throws declares possible escape types in a signature.
    "Unchecked exceptions cannot be declared with throws." They may be declared — it is legal and sometimes documents intent — but the compiler does not require it.
    "Catching Throwable catches everything safely." It also catches Error and other faults the program should not attempt to survive.
    "Wrapping an exception loses the original stack trace." Wrapping with a cause preserves it; only discarding the cause loses it.
    "A custom exception must always be checked." It can extend Exception (checked) or RuntimeException (unchecked), per design.

    14. Common Trap Questions

    Trap 1 — Keyword confusion: "What is the difference between throw and throws?" throw is a statement that raises one exception instance; throws is a method-signature clause listing the checked types that may escape the method. One acts at runtime, the other is a compile-time contract.

    Trap 2 — Checked in a lambda: "Can I call a method that declares throws IOException directly inside stream.map(...)?" No. The functional interface declares no checked exception, so the code does not compile; wrap the checked exception in an unchecked type and unwrap it at the boundary.

    Trap 3 — Overbroad declaration: "Is void run() throws Exception good practice?" No. It forces callers to handle the entire hierarchy and communicates nothing; declare the specific checked types.

    Trap 4 — Lost cause: "catch (IOException e) { throw new ServiceException(e.getMessage()); } — is anything lost?" Yes, the cause. Use new ServiceException(message, e) so getCause() and the full trace survive.

    Trap 5 — Catching Error: "Should I catch Throwable in a top-level handler to be safe?" Only with great care and rethrow semantics. Catching Throwable also catches Error; catching Exception is almost always the right boundary.

    Trap 6 — Unchecked declaration: "Does throws RuntimeException change anything?" No compiler obligation is added; it merely documents. The method could throw the type whether or not it is declared.

    Trap 7 — Reuse: "Can I create one exception instance and throw it from several places?" You can, but you should not: each throw should create a fresh instance so its stack trace reflects the actual origin.

    Trap 8 — Checked intent: "If I declare a checked exception but every caller wraps it, was the check useful?" No. If no caller can recover, an unchecked exception communicates the same intent without the ceremony.

    15. Points to Remember

    1. Throwable is the root; only its subclasses may be thrown or caught.
    2. The two branches are Error (unrecoverable environment faults) and Exception (program conditions).
    3. RuntimeException and its subclasses, plus Error, are unchecked; all other Exception subclasses are checked.
    4. Checked exceptions must be caught or declared; unchecked ones need not be.
    5. IOException and InterruptedException are checked because callers can recover; NullPointerException and IllegalArgumentException are unchecked because they signal defects.
    6. throw raises an instance; throws declares checked types, and multiple types are comma-separated.
    7. An uncaught exception unwinds the stack and prints a trace whose top frame is the origin.
    8. Wrapping with a cause preserves the original trace; initCause sets it after construction.
    9. A custom exception extends Exception for checked behaviour or RuntimeException for unchecked behaviour, and should carry a message and, when useful, context.
    10. Prefer checked exceptions for recoverable, caller-actionable conditions and unchecked exceptions for programming and domain errors.

    16. Likely Interview Questions

    Question Crisp Answer
    What is the root of the exception hierarchy? Throwable; only its subclasses can be thrown or caught.
    Difference between Error and Exception? Error is an unrecoverable environment/JVM fault; Exception is a condition arising in normal execution.
    What is a checked exception? A Throwable that is not RuntimeException or Error; the compiler requires it to be caught or declared.
    What is an unchecked exception? A RuntimeException or Error subtype; the compiler does not force handling.
    Difference between throw and throws? throw raises one instance at runtime; throws declares, in a signature, the checked types a method may let escape.
    Can a method declare multiple exceptions? Yes: void f() throws IOException, SQLException.
    Why is IOException checked? It models an external, recoverable condition (missing file, failed I/O) the caller can act on.
    Why is NullPointerException unchecked? It signals a programming defect; recovery at the call site is not meaningful.
    What is exception chaining? Wrapping a low-level exception in a higher-level one while passing the original as the cause, preserving its trace.
    How do you create a custom exception? Extend Exception for checked or RuntimeException for unchecked; provide message and message-plus-cause constructors.
    When should you prefer unchecked? For programming errors and many domain errors, especially in modern APIs and inside lambdas/streams.
    What is wrong with catch (Throwable t)? It also catches Error and can hide unrecoverable faults the program should not survive.

    17. Final Summary

    Throwable
  Error      (unchecked)  -> OutOfMemoryError, StackOverflowError, VirtualMachineError
  Exception
    RuntimeException (unchecked) -> NPE, ArithmeticException, AIOOBE, ClassCastException, IllegalArgumentException
    checked                      -> IOException (FileNotFoundException), SQLException,
                                    ClassNotFoundException, InterruptedException

throw   : statement  -> raises one Throwable instance now
throws  : signature  -> declares checked types that may escape; comma-separated; unchecked optional

propagation : uncaught -> unwind stack -> stack trace (top frame = origin)
chaining    : throw new ServiceException(message, e)  -> getCause() preserves the original
custom      : extends Exception (checked)  OR  extends RuntimeException (unchecked)
              message-only and message+cause constructors; add context fields such as errorCode
    • Hierarchy → Throwable ⊃ {Error, Exception}; Exception ⊃ {RuntimeException (unchecked), checked types}.
    • Checked vs unchecked → recoverable external condition versus programming defect.
    • throw vs throws → raise an instance versus declare a contract.
    • Propagation → unwind the stack, print a trace whose top frame is the origin, and either catch or re-declare.
    • Chaining → always pass the cause so the real failure is never lost.
    • Custom exceptions → specific, meaningful, informative; checked when recovery is required, unchecked otherwise.

    Golden rule An exception type is part of a method's contract: raise the right instance with throw, declare the checked ones with throws, preserve the cause when wrapping, and choose checked or unchecked by asking whether the caller can actually recover.

    One-line takeaway: master the Throwable tree, use throw to raise and throws to declare, wrap without losing the cause, and let custom exceptions name each condition so callers know exactly what went wrong and what to do.
