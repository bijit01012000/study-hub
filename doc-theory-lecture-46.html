    Java Heap Memory Deep Dive | Garbage Collection Algorithms Explained

    20 sections · 3,919 words

    Lecture 46

    Scope evidence: "Java Heap Memory Deep Dive | Garbage Collection Algorithms Explained" (playlist map, verified). Repo evidence: code/Demo.java.

    Lecture 45 mapped the runtime memory areas and showed that every new places an object on the heap with no matching free in sight. This lecture answers the obvious follow-up: who reclaims that memory, and when. It defines garbage collection, GC roots and reachability, the generational heap, minor versus full collections, the classic algorithms, the modern collector families, reference types, and the flags that tune them. The governing idea is that Java guarantees memory safety, not memory economy: unreachable objects are reclaimed automatically, while reachable-but-unused objects remain a leak under any collector.

    1. What Garbage Collection Is and Why It Exists

    Garbage Collection (GC) is the automatic process that identifies heap objects which are no longer reachable from GC roots and reclaims the space they occupy. In C and C++, the programmer pairs malloc with free and owns every mistake: a missed free leaks, a doubled free corrupts. Java removes that burden: you call new, and the runtime decides when the object's memory returns to a free pool.

    Three facts frame every later section:

    1. The programmer never frees memory. There is no delete; the last reference simply goes out of scope or is overwritten, and the object becomes eligible for collection.
    2. GC is not free. It consumes CPU time and, for most collectors, stops application threads briefly while it walks the object graph.
    3. GC reclaims memory, not intent. It cannot know that an object is still referenced but useless; handling that is the programmer's job (Section 12).

    Important The stack, the program counter and the method area were fixed structures in Lecture 45. The heap is the one region whose live content is decided at runtime by reachability, which is exactly why GC exists.

    2. GC Roots and Reachability

    An object is reachable when a chain of references leads to it from at least one GC root. Reachable objects are alive and are never collected; everything else is garbage. The root set is small and precise:

    1. Local variables and operand-stack entries in the stack of every active thread.
    2. Static fields of every loaded class.
    3. JNI references held by native code.
    4. Class metadata — the loaded classes, their Class objects and constant pools.
    5. Active monitors — objects locked by a synchronized block on any live thread.

    A subtle but important consequence: Java does not use reference counting. It uses tracing reachability, so a cycle of objects that only point at each other, with no root above them, is still collected. Reference counting would leak such cycles; tracing does not.

    Memory aid Ask not "does it have a reference?" but "can a live thread starting at a root walk to it?" If no walk exists, it is garbage no matter how many objects point at it.

    3. The Generational Hypothesis and Heap Layout

    GC design is built on one empirical observation, the weak generational hypothesis: the overwhelming majority of objects die young, while the few that survive their youth tend to survive for a long time. The strong generational hypothesis adds that survivors keep surviving.

    The heap is therefore divided by object age:

    Young Generation                     Old Generation (Tenured)
+-------------------+---------------+
|  Eden  | S0 | S1  |   Old / Tenured  |
+-------------------+---------------+
| new objects land  | long-lived and promoted objects |
+-------------------+---------------+
    • Young generation holds newly created objects and is collected frequently and cheaply; it consists of Eden plus two survivor spaces, S0 and S1.
    • Old (tenured) generation holds objects that survived enough young collections; it is collected rarely and at higher cost.

    The payoff is efficiency: collecting a small region that is mostly dead is fast, so the frequent collections stay cheap.

    4. Young vs Old Generation

    Aspect Young Generation Old Generation
    Contents freshly allocated, short-lived objects long-lived and promoted objects
    Internal spaces Eden, Survivor S0, Survivor S1 a single tenured space
    Collection name Minor GC Major GC (often Full GC)
    Frequency frequent rare
    Typical algorithm copying mark-sweep-compact
    Relative pause short long
    Trigger Eden fills up old-occupancy threshold reached
    Default share smaller portion of the heap larger portion of the heap

    Reading the table: the young generation is optimized for high mortality, the old generation for low mortality and compact layout.

    5. Allocation, Minor GC, and Promotion

    Allocation is trivial and fast: new bumps a pointer inside Eden, normally inside a thread-private TLAB (Thread-Local Allocation Buffer) so threads rarely contend. Nothing is collected until Eden is full.

    When Eden fills, the JVM runs a Minor GC:

    1. Every live object in Eden is copied into the current survivor space (a copying collector).
    2. Live objects already in the other survivor space are copied across as well.
    3. S0 and S1 swap roles: the new empty space becomes the destination for the next cycle.
    4. Each survivor's age counter is incremented.

    When an object's age reaches the tenuring threshold (HotSpot default 15), it is promoted to the Old Generation. A copy is expensive only in proportion to the number of survivors, and because most young objects are already dead, that number is small — this is why copying is ideal for the young generation.

    // Demo.java — most allocations die immediately, so the young GC stays cheap
public class Demo {
    public static void main(String[] args) {
        long total = 0;
        for (int i = 0; i < 1_000_000; i++) {
            String s = "item-" + i;   // a new String each iteration
            total += s.length();      // s dies as the loop advances
        }
        System.out.println(total);
    }
}

    Interviewer's perspective "Why does the young generation use a copying collector rather than mark-and-sweep?" Because nearly everything there is garbage, so the collector copies only the small live remainder and can use one free pointer for allocation. Marking everything to find that small remainder would do far more work than the copy itself.

    6. Major GC, Full GC, and Stop-the-World Pauses

    A Major GC reclaims the Old Generation once its occupancy crosses a threshold. A Full GC is the broadest case: it collects young and old (and can include metaspace cleanup) and is the most expensive operation the collector performs.

    Most collectors stop every application thread during parts of a collection. Such a Stop-The-World (STW) pause freezes the program so that the object graph cannot change while it is being traced. Two metrics describe the cost:

    • Throughput — the fraction of time spent doing application work rather than GC.
    • Latency — the length of an individual pause; users feel this directly.

    The trade-off is real: a larger young generation produces fewer but longer pauses and better throughput; a smaller one produces more frequent but shorter pauses and better latency.

    Important A "concurrent" collector does not eliminate pauses; it moves most work off the application threads and leaves only short STW phases. Pauses are reduced, never removed entirely.

    7. GC Algorithms Compared

    Algorithm How it works Strength Weakness
    Mark-and-Sweep mark all reachable objects, then sweep unreachable ones simple; no object copying free space becomes fragmented; pause scales with live set
    Mark-Sweep-Compact mark, sweep, then slide live objects together no fragmentation; fast bump allocation afterwards extra moving cost; longer pauses
    Copying split space into from and to; copy live objects into the empty half very cheap when few objects survive; no fragmentation wastes half the space; costly if many survive
    Generational divide the heap by age; copying for young, mark-sweep-compact for old exploits the generational hypothesis; balanced more complex; requires promotion tuning

    The generational design is the synthesis: it applies copying where survival is low (Section 5) and compaction where survival is high, which is why it underpins every production collector.

    8. Garbage Collectors Compared

    Modern JVMs ship several collectors. They share the algorithms above but differ in threading and concurrency, which is what decides the throughput-versus-latency result.

    Collector Selection flag Primary focus Notes
    Serial -XX:+UseSerialGC smallest footprint single-threaded, STW; best for tiny heaps and clients
    Parallel -XX:+UseParallelGC throughput multi-threaded; the default in JDK 8
    CMS -XX:+UseConcMarkSweepGC low pause concurrent mark-sweep; deprecated in Java 9, removed in Java 14
    G1 -XX:+UseG1GC balanced latency and throughput region-based with a soft pause target; default since Java 9
    ZGC -XX:+UseZGC ultra-low latency concurrent and highly scalable; suited to very large heaps
    Shenandoah -XX:+UseShenandoahGC ultra-low latency concurrent compaction; originated with Red Hat

    G1 (Garbage-First) is the modern default because it treats the heap as many equal regions rather than two fixed generations, prioritizes the regions with the most garbage, and honors a pause target (-XX:MaxGCPauseMillis) as a goal rather than a guarantee.

    Golden rule There is no best collector, only a best collector for a stated goal. Parallel maximizes throughput, G1 balances it with predictable pauses, and ZGC or Shenandoah chase latency for large heaps.

    9. Reference Types: Strong, Soft, Weak, Phantom

    Reachability has strengths, and Java exposes four reference types that let a program express how eagerly an object may be reclaimed.

    Type Class When collected Typical use
    Strong default reference never while any strong reference exists ordinary object references
    Soft SoftReference only when memory is under pressure memory-sensitive caches
    Weak WeakReference as soon as only weak references remain WeakHashMap keys, canonicalizing maps
    Phantom PhantomReference after the object has been finalized post-mortem cleanup; get() always returns null 
    // Demo.java — a weak reference does not keep its referent alive
import java.lang.ref.WeakReference;

public class Demo {
    public static void main(String[] args) {
        Object strong = new Object();
        WeakReference<Object> weak = new WeakReference<>(strong);
        System.out.println(weak.get());   // reference is reachable here

        strong = null;                     // now only weakly reachable
        System.gc();                       // a request, not a command

        System.out.println(weak.get());    // usually null, but not guaranteed
    }
}

    System.gc() merely suggests a collection; the JVM is free to ignore it, and good code never depends on it.

    Memory aid Survival strength falls left to right: Strong > Soft > Weak > Phantom, while the eagerness to reclaim rises in the same direction.

    10. finalize() Is Deprecated: Cleaner and try-with-resources

    Object.finalize() was once the advertised cleanup hook. In practice it is unreliable: it runs on a GC-owned thread at an unpredictable time, may never run at all if GC never occurs, can be delayed arbitrarily, and can even resurrect an object by re-publishing this. It was deprecated in Java 9 and marked for removal.

    Prefer deterministic mechanisms:

    1. try-with-resources for anything implementing AutoCloseable — the resource closes at the end of the block, on the normal path and on exceptions alike (cross-ref Lecture 43).
    2. java.lang.ref.Cleaner for cleanup triggered when an object becomes phantom-reachable, without overriding finalize.
    // Demo.java — deterministic cleanup with a Cleaner instead of finalize()
import java.lang.ref.Cleaner;

public class Demo implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;

    Demo() {
        this.cleanable = CLEANER.register(this, () -> System.out.println("released"));
    }

    @Override
    public void close() {
        cleanable.clean();   // runs exactly once, eagerly
    }
}

    11. Tuning Flags Overview

    These flags shape the heap and the collector. Treat them as instruments to be adjusted after measurement, not as defaults to copy from a blog.

    Flag Meaning
    -Xms initial heap size
    -Xmx maximum heap size
    -Xmn size of the young generation
    -XX:MaxTenuringThreshold survivor age at which an object is promoted
    -XX:+UseG1GC select the G1 collector
    -XX:MaxGCPauseMillis G1's soft target for a single pause
    -XX:+HeapDumpOnOutOfMemoryError write a heap dump when an OOM occurs

    Important -Xmx should generally equal -Xms in a server so the heap does not repeatedly grow and shrink. Beyond that, tune only against a measured problem: enabling GC logging and reading it beats guessing flags.

    12. Memory Leaks in a GC Language

    A memory leak here is a reachable but unused object: something the program will never read again, yet a root still points at it, so no collector may touch it. Classic sources:

    • Static collections that only grow — a static Map used as a registry and never pruned.
    • Caches without eviction — unbounded maps where entries are added but never removed.
    • ThreadLocal leaks — values left on long-lived pool threads (cross-ref Lecture 57).
    • Listeners and callbacks — registered but never unregistered, holding the listener's enclosing object alive.
    • Class loader leaks — in application servers, a discarded class loader kept reachable prevents every class it loaded from being collected.
    • Unclosed resources — streams and connections that keep buffers and native handles reachable.

    The fix is ownership discipline: null out references you are done with, bound caches and evict, remove listeners, and call remove() on ThreadLocal. GC handles unreachability; it cannot infer disuse.

    Trap "It is garbage collected, so it cannot leak" is the single most expensive misconception in this lecture. Reachability and usefulness are different properties, and only the first is automatic.

    13. Major vs Minor Collection at a Glance

    Dimension Minor GC Major / Full GC
    Region collected young generation (Eden plus survivors) old generation, and the whole heap for Full GC
    Frequency high low
    Relative duration short long
    Typical cause Eden exhausted old-occupancy threshold or a metadata/commit request
    Effect on latency small, frequent pauses large, rarer pauses
    Algorithm copying mark-sweep-compact

    Keeping allocation rates modest and object lifetimes short keeps collections in the cheap Minor column, which is the single most effective GC optimization available to application code.

    14. Pitfalls and Common Errors

    Pitfall What goes wrong Correct approach
    Calling System.gc() to force a collection it is only a hint and may be ignored fix ownership and reference leaks instead
    Relying on finalize() for cleanup timing is unpredictable and it may never run use try-with-resources or a Cleaner
    Believing GC prevents all leaks reachable-but-unused objects survive collection null references, evict caches, remove listeners
    Confusing StackOverflowError with heap OOM different regions and causes stack: deep recursion; heap: allocation shortfall
    Assuming one algorithm fits all wrong throughput or latency result choose per workload and measure
    Mixing up survivors and promotion objects promoted prematurely; old-gen pressure size survivor spaces and the tenuring threshold correctly
    Tuning flags without measuring random changes, worse pauses enable GC logs, read them, then adjust
    Ignoring allocation rate constant Minor GCs and CPU burn reduce short-lived allocations where it matters

    15. Myth vs Reality

    Myth Reality
    "System.gc() forces immediate collection." It is a request; the JVM may ignore it, and code must not depend on it.
    "finalize() reliably cleans up resources." It is deprecated, timing is unpredictable, and it may never run; prefer try-with-resources or Cleaner.
    "A garbage-collected language cannot leak memory." Reachable-but-unused objects leak; GC only removes unreachable ones.
    "GC eliminates all pauses." Every collector has Stop-The-World phases; concurrency reduces them, never removes them.
    "G1 is always the fastest collector." G1 trades throughput for predictable pauses; Parallel wins raw throughput and ZGC wins latency.

    16. Common Trap Questions

    Trap 1 — System.gc(): "I called System.gc() and the object was freed, so it is a command, right?" No. It is a hint. The JVM may ignore it, may defer it, or may collect unrelated objects; any behavior that depends on it is broken.

    Trap 2 — finalize(): "My resource is closed in finalize(), so it is safe." No. finalize() runs on a GC-owned thread at an unpredictable time and may never run; try-with-resources or Cleaner is required.

    Trap 3 — Leak definition: "Java has GC, so memory leaks are impossible." No. An object still reachable from a root but never used again is a leak; static collections, unbounded caches and ThreadLocal values are common sources.

    Trap 4 — Error type: "My program throws StackOverflowError, so the heap ran out." No. StackOverflowError means the thread stack was exhausted, typically by deep recursion; heap exhaustion produces OutOfMemoryError.

    Trap 5 — Promotion: "Survivor spaces and the young generation are the same thing." No. Eden and the two survivor spaces together form the young generation; survivors are copied between S0 and S1 and promoted to the old generation at the tenuring threshold.

    Trap 6 — Default collector: "Parallel GC is always the default." No. Parallel was the JDK 8 default; G1 has been the default since Java 9. The right choice depends on the throughput-versus-latency requirement.

    Trap 7 — Cyclic garbage: "Objects that reference each other can never be collected." No. Java traces reachability from roots, not reference counts, so an unreachable cycle is collected in full.

    17. Points to Remember

    1. GC automatically reclaims heap memory of objects unreachable from GC roots; the programmer never frees memory (cross-ref Lecture 45).
    2. GC roots are active thread stacks and local references, static fields, JNI references, class metadata, and active monitors.
    3. Reachability is traced from roots, so unreachable cycles are collected despite pointing at each other.
    4. The generational hypothesis — most objects die young — drives the Young (Eden plus S0 and S1) and Old design.
    5. Allocation happens in Eden; a Minor GC copies survivors between S0 and S1 and promotes them at the tenuring threshold.
    6. Minor GCs are frequent and cheap; Major and Full GCs are rarer and expensive, and cause longer Stop-The-World pauses.
    7. Algorithms: mark-and-sweep fragments, mark-sweep-compact moves, copying duplicates-space but is ideal when few survive, and generational combines them.
    8. Collectors: Serial (footprint), Parallel (throughput), CMS (deprecated), G1 (default since Java 9, pause target), ZGC or Shenandoah (ultra-low latency).
    9. Reference types run Strong, Soft, Weak, Phantom by survival; finalize() is deprecated in favor of Cleaner and try-with-resources.
    10. Tune with -Xms, -Xmx, -Xmn, -XX:+UseG1GC and -XX:MaxGCPauseMillis only after measuring, and hunt reachable-but-unused objects for leaks.

    18. Likely Interview Questions

    Question Crisp Answer
    What is garbage collection? The automatic reclamation of heap memory occupied by objects no longer reachable from GC roots; the programmer never frees memory explicitly.
    What are GC roots? Thread stacks and local references, static fields, JNI references, class metadata, and active monitors; reachable objects are alive.
    What is the generational hypothesis? Most objects die young and the few survivors tend to keep surviving, which justifies splitting the heap into young and old generations.
    What is the difference between Minor and Major GC? Minor GC collects the young generation frequently and cheaply; Major or Full GC collects the old generation (or the whole heap) rarely and expensively.
    What is promotion and the tenuring threshold? A survivor is promoted to the old generation once its age reaches the tenuring threshold (HotSpot default 15); Eden plus S0 and S1 form the young generation.
    What causes Stop-The-World pauses? Most collectors must freeze application threads while tracing the object graph, so references cannot change mid-collection.
    Which collector is the default in modern Java? G1 since Java 9; siblings are Serial, Parallel, CMS (removed), ZGC and Shenandoah, each trading throughput against latency.
    What is the difference between Mark-and-Sweep and Mark-Sweep-Compact? Mark-and-Sweep leaves fragmented free space; Mark-Sweep-Compact slides live objects together so allocation stays fast.
    What are the four reference types? Strong, Soft (memory-pressure caches), Weak (weakly reachable), and Phantom (post-mortem cleanup); strengths fall in that order.
    Can a GC language leak memory? Yes: a reachable-but-unused object is never collected; static collections, unbounded caches and ThreadLocal values are common causes.
    Why is finalize() discouraged? It is deprecated, runs at an unpredictable time and may never run; use try-with-resources or Cleaner instead.
    Does System.gc() force collection? No. It is a hint the JVM may ignore; correctness must never depend on it.

    19. Final Summary

    new Object() --> Eden (allocation)
      Eden full --> Minor GC --> copy live survivors into S0 or S1
      age reaches tenuring threshold --> promote to Old Generation
      Old full --> Major / Full GC (mark -> sweep -> compact) --> memory reclaimed

roots        : thread stacks · static fields · JNI refs · class metadata · monitors
algorithms   : mark-sweep · mark-sweep-compact · copying · generational
collectors   : Serial · Parallel · CMS (deprecated) · G1 (default) · ZGC / Shenandoah
references   : Strong > Soft > Weak > Phantom
pauses       : Stop-The-World ; throughput vs latency trade-off
leaks        : reachable but unused (static maps · caches · ThreadLocal · listeners)
    • Roots and reachability → decide what is alive; tracing collects unreachable cycles that reference counting would keep.
    • Generational heap → Eden plus S0 and S1 for the young, a tenured space for the old; Minor GC is cheap, Major or Full GC is not.
    • Algorithms → mark-and-sweep fragments, mark-sweep-compact moves, copying duplicates space but suits low survival, generational combines them.
    • Collectors → Serial for footprint, Parallel for throughput, G1 for balanced predictable pauses, ZGC or Shenandoah for ultra-low latency.
    • Pauses → concurrency reduces Stop-The-World time but never removes it; the goal is a chosen throughput-versus-latency point.
    • References and cleanup → Soft, Weak and Phantom tune reclamation eagerness; finalize() is deprecated in favor of Cleaner and try-with-resources.
    • Leaks → reachable-but-unused objects survive every collector, so ownership and eviction remain the programmer's responsibility.

    Golden rule Garbage collection reclaims what is unreachable, not what is unwanted; write code that drops references you no longer need and let the collector do the rest.

    One-line takeaway: the collector traces roots through a generational heap — copying live young survivors into the old generation, reclaiming the rest under a chosen throughput-versus-latency trade-off — while reachable-but-unused objects remain a leak you alone must fix.
