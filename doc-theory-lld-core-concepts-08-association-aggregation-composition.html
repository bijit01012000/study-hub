    Association, Aggregation, Composition

    10 sections · 747 words

    Notation · LLD Core Concepts · Concept 08 of 09

    The Idea

    Three arrows, three stories.

    The Three

    • Association: plain line. Two classes just know each other. A Driver knows a Car.
    • Aggregation: open diamond. A whole holds parts that outlive it. A Playlist holds Songs.
    • Composition: filled diamond. The whole owns the parts' lifetime. An Order owns its Lines.

    Composition, In Code

    class Order {
    private final List<OrderLine> lines = new ArrayList<>();
    void addLine(Item i, int qty) {
        lines.add(new OrderLine(i, qty));
        // Order creates its own lines
    }
    void cancel() {
        lines.clear();
        // lines die when the order does
    }
}
// an OrderLine has no meaning outside an Order

    Owns the lifetime.

    Aggregation, In Code

    class Playlist {
    private final List<Song> songs = new ArrayList<>();
    void add(Song s) { songs.add(s); }
    // Song already exists elsewhere
    void remove(Song s) { songs.remove(s); }
    // doesn't delete the Song
}
// a Song is built and owned by a Library, only referenced here

    Borrows a reference.

    Don't Bother If

    • The ownership question genuinely doesn't matter. Say "association" and move on.
    • Multiplicity (1, 0..1, , 1..) usually matters more than the diamond. Get it right first.

    Quick Check

    Delete the whole: do the parts get deleted too? Yes: composition. No, just orphaned: aggregation. Not even that: association.

    How It's Drawn

    The Three Arrows

    Driver ----------- Car
    ASSOCIATION

Playlist <>------- Song
    AGGREGATION: OPEN DIAMOND, PARTS OUTLIVE IT

Order <#>--------- OrderLine
    COMPOSITION: FILLED DIAMOND, OWNS THE LIFETIME

THE DIAMOND SITS ON THE WHOLE'S END, NOT THE PART'S.

    The Move (3 Steps)

    1. Ask the lifetime question first. Does the part's existence depend on the whole? Yes means composition.
    2. If the part is borrowed and survives independently, it's aggregation.
    3. If neither owns or contains the other, and they just call each other's methods, it's a plain association.

    In The Interview

    "OrderLines don't exist outside an Order, so that's composition, a filled diamond: the Order creates and clears them. Songs outlive any one Playlist, so that's aggregation, an open diamond: the Playlist only holds a reference it didn't create."

    How It's Different

    The Confusion Pairs

    UML composition vs OOP composition. The OOP principle uses "composition" loosely for "holds a reference to," covering both aggregation and composition. The UML term is the stricter, lifetime-bound one.

    Association vs dependency. Association is a structural reference held over time (a field). A dependency is used briefly inside one method (a parameter), gone after the call returns.

    Aggregation vs shared ownership. Aggregation doesn't require exactly one owner. A Song can sit in many Playlists at once, which is exactly why deleting one can't delete it.

    Composition vs a nested class. Composition is about object lifetime, not about whether the part happens to be a literal inner class in the code.

    They Say: "quick, on the whiteboard: is a Team's Players composition or aggregation?"

    • With it: ask if a Player still exists after being cut from the Team. Yes means aggregation, open diamond.
    • Without: guessing at the diamond without the lifetime question, and getting caught if they push on it.

    Watch Out For

    • The diamond sits on the whole's end of the line, not the part's. A common drawing mistake.
    • Multiplicity labels (1, 0..1, , 1..) carry information the relationship type alone doesn't. Always add them.
    • A List field alone doesn't tell you which relationship it is. The ownership question decides it, not the data structure.
    • Association can be one-directional or bidirectional, say which; it changes what the diagram claims.
    • Getting composition vs aggregation "wrong" rarely fails an interview alone; not being able to say why usually does.
