    Monitor Locks in Java | Synchronized Keyword, Static Sync & Custom Locks

    26 sections · 5,048 words

    Lecture 51

    Scope evidence: "Monitor Locks in Java | Synchronized Keyword, Static Sync & Custom Locks" plus the lecture's own repo notes (intrinsic monitor lock), playlist map, verified. Repo evidence: 5 Demo files.

    Synchronization is the mechanism Java uses to control concurrent access to shared mutable data. When several threads operate on the same object or variable, their steps can overlap and produce results no correct program would ever intend. This lecture explains why that happens with the classic count++ counter, then builds the full monitor-lock model: what an intrinsic monitor is, how a thread acquires and releases it, what each form of synchronized actually locks, how static synchronization differs, how to design custom lock objects, and the mistakes that quietly defeat the whole mechanism. The governing idea is that synchronization works only when every competing thread agrees on the same monitor object.

    1. Multithreading and Shared Data

    Multithreading means that more than one thread can make progress within the same program. Consider the simplest possible shared-state example, a counter:

    // Demo.java — the lost-update problem on shared mutable state
class Counter {
    int count = 0;
    void increment() {
        count++;
    }
}

public class Demo {
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Thread t1 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.increment(); });
        Thread t2 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.increment(); });
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(counter.count);
    }
}

    The expected result is 2000. The actual result may be less than 2000. The reason is that count++ is not one indivisible operation; conceptually it performs three steps:

    1. Read the current value of count.
    2. Add 1.
    3. Write the new value back.

    Two threads can overlap during these steps:

    Thread-1 reads 10          Thread-2 reads 10
Thread-1 writes 11         Thread-2 writes 11

    Two increments were attempted, but the value increased only once. This is called a lost update.

    Important The bug is invisible in source: count++ looks like a single action. It is actually a read-modify-write sequence with a window during which another thread can read the same stale value.

    2. What Synchronization Does

    Synchronization allows a thread to enter a protected section only after acquiring the required monitor lock. Marking the method synchronized makes the read-modify-write sequence execute under that lock:

    // Demo2.java — synchronized instance method closes the lost-update window
class Counter {
    private int count = 0;

    synchronized void increment() {
        count++;
    }

    int getCount() {
        return count;
    }

    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Thread t1 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.increment(); });
        Thread t2 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.increment(); });
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(counter.getCount());
    }
}

    If Thread-1 is executing increment() on a particular Counter object, Thread-2 cannot enter another synchronized instance method guarded by the same object until Thread-1 releases the monitor. Using synchronized here prevents the read-modify-write steps of count++ from overlapping.

    3. Why Synchronization Is Needed

    Synchronization mainly provides three things.

    3.1 Protection of shared data. When multiple threads access the same mutable data, synchronization prevents conflicting operations from running at the same time. Examples include updating a counter, modifying a bank balance, adding or removing elements from a shared collection, and changing the state of a shared resource.

    3.2 Atomicity. An operation is atomic when other threads cannot observe or interfere with it halfway through. In synchronized void increment() { count++; }, the complete count++ operation is protected by one monitor. This does not mean that every statement inside Java automatically becomes a hardware-level atomic instruction. It means that no other thread using the same monitor can enter the protected section until the current thread completes it.

    3.3 Memory visibility. Modern processors and compilers may keep values in registers, processor caches, or reordered instruction sequences. Without proper synchronization, one thread may update a variable while another thread continues observing an older value. Monitor synchronization establishes a happens-before relationship:

    a thread releases a monitor
   → another thread later acquires the same monitor
   → the acquiring thread can observe the writes made before the release

    Therefore, synchronization provides both mutual exclusion + memory visibility.

    Property What it guarantees What it does not guarantee
    Mutual exclusion Only one thread at a time enters code guarded by the same monitor Anything about code guarded by a different monitor
    Atomicity The protected section runs as one unit with respect to the same monitor Hardware-level atomicity of each Java statement
    Memory visibility Writes before a release become visible after a later acquire of the same monitor Visibility between threads that never share the monitor

    4. Synchronization Does Not Stop All Threads

    Synchronization does not pause the entire application. It only controls access to the code protected by a particular monitor. If Thread-1 holds the monitor of an object:

    • Thread-2 cannot enter code protected by the same monitor.
    • Thread-2 can still execute unrelated code.
    • Thread-2 can enter code protected by a different monitor.
    • Other threads can continue running normally.

    The correct mental model is: synchronization restricts access to a protected region; it does not stop multithreading.

    Memory aid A monitor is a single key to a single door, not a building-wide power switch. Holding the key blocks only the people waiting at that door.

    5. What Is a Monitor Lock?

    Every Java object can be used as a monitor. A monitor acts like a permission mechanism: a thread must acquire the object's monitor before entering code synchronized on that object. The monitor is managed by the JVM and is not a normal field that appears inside the Java class.

    The lock object can be used as a monitor:

    Object lock = new Object();

synchronized (lock) {
    // protected code
}

    This intrinsic monitor is the mechanism behind every synchronized construct in Java; it is the same object-level monitor regardless of whether it is used through a method or a block.

    6. How Monitor Acquisition Works

    When a thread reaches synchronized code:

    1. It attempts to acquire the required monitor.
    2. If the monitor is available, the thread acquires it and enters.
    3. If another thread owns the monitor, the current thread cannot enter.
    4. The current thread remains blocked until the monitor becomes available.
    5. The monitor is released when the owning thread exits the synchronized region.

    The canonical demonstration uses a method that sleeps while holding the monitor:

    class Test {
    synchronized void show() {
        System.out.println(Thread.currentThread().getName() + " entered");
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        System.out.println(Thread.currentThread().getName() + " exiting");
    }
}

    Both threads call the same synchronized method on the same object, so only one thread can execute show() at a time. The second thread is BLOCKED until the first releases the monitor (Lecture 48).

    7. The Lock Belongs to the Object, Not the Method

    A synchronized method does not have its own independent lock. For an instance method:

    synchronized void show() {
    // code
}

    the monitor belongs to the current object, this. The method is conceptually equivalent to:

    void show() {
    synchronized (this) {
        // code
    }
}

    This distinction is important because multiple synchronized methods on the same object use the same monitor.

    Form Conceptual expansion Monitor acquired
    synchronized void m() synchronized (this) { ... } the current instance
    static synchronized void s() synchronized (ClassName.class) { ... } the Class object
    synchronized (expr) { ... } itself the object that expr evaluates to

    Important Two different synchronized instance methods do not lock two different things. They lock the same object, so they block each other.

    8. Multiple Synchronized Methods on the Same Object

    Consider two synchronized methods on one class:

    class Test {
    synchronized void m1() { System.out.println("m1"); }
    synchronized void m2() { System.out.println("m2"); }
}

    Suppose Thread-1 enters m1() on a particular Test object. Thread-2 cannot enter m2() on that same object, because both methods require the monitor of the same object:

    Thread-1 -> test.m1()
Thread-2 -> test.m2()
same object -> same monitor -> mutual blocking

    The methods are different, but the monitor is the same.

    9. Different Objects Use Different Monitors

    Now suppose two instances exist:

    Test first  = new Test();
Test second = new Test();

Thread-1 -> first.m1()
Thread-2 -> second.m1()

    Both threads may execute simultaneously, because the two objects have different monitors:

    first object  -> first monitor
second object -> second monitor

    Therefore, synchronization depends on the monitor object being shared, not merely on the method or class containing the code.

    10. Synchronized Blocks and the Critical Section

    A synchronized instance method protects the entire method. Sometimes only a small part of the method accesses shared mutable data, and protecting the whole method may keep the monitor occupied longer than necessary. A synchronized block protects only the critical section:

    // Demo3.java — protect only the critical section, not the whole method
class Counter {
    private int count = 0;

    void increment() {
        System.out.println("Before increment");
        synchronized (this) {
            count++;
        }
        System.out.println("After increment");
    }

    public static void main(String[] args) {
        Counter counter = new Counter();
        counter.increment();
        System.out.println(counter.count);
    }
}

    Only the code inside synchronized (this) requires the monitor of the current Counter object; the code before and after does not. This can reduce unnecessary contention, provided the shared state is still protected correctly.

    A critical section is the part of the program that accesses shared mutable state and must not be executed concurrently by threads using the same synchronization policy. The goal is not to make synchronized blocks as small as possible at any cost; the complete operation that must remain consistent should be protected under the same monitor. For example:

    synchronized (this) {
    if (balance >= amount) {
        balance = balance - amount;
    }
}

    The condition check and the update must remain inside the same synchronized section.

    11. Custom Lock Objects: Dedicated Locks

    A class does not have to synchronize on this. It can use a dedicated private object:

    // Demo4.java — a dedicated private final lock object
class Counter {
    private final Object lock = new Object();
    private int count = 0;

    void increment() {
        synchronized (lock) {
            count++;
        }
    }

    int getCount() {
        synchronized (lock) {
            return count;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();
        Thread t1 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.increment(); });
        Thread t2 = new Thread(() -> { for (int i = 0; i < 1000; i++) counter.increment(); });
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(counter.getCount());
    }
}

    Here the critical section is protected by the monitor of lock, not by the monitor of the Counter instance itself. A dedicated lock object gives the class more control over which operations block one another. It should normally be private final: private prevents external code from acquiring the same monitor accidentally, and final prevents the lock reference from being replaced.

    12. Multiple Locks and Independent State

    A class may use different monitors for independent state:

    class AccountManager {
    private final Object accountLock = new Object();
    private final Object auditLock = new Object();
    private int balance;
    private int auditEntries;

    void updateBalance(int amount) {
        synchronized (accountLock) { balance += amount; }
    }

    void recordAuditEntry() {
        synchronized (auditLock) { auditEntries++; }
    }
}

    The two methods may run concurrently because they use different monitors and protect independent state:

    updateBalance()    -> accountLock
recordAuditEntry() -> auditLock

    13. The One-Monitor Rule: Same State, Same Lock

    Different locks are safe only for independent state. Consider this flawed design:

    class Bank {
    private final Object depositLock  = new Object();
    private final Object withdrawLock = new Object();
    private int balance;

    void deposit(int amount) {
        synchronized (depositLock)  { balance += amount; }
    }
    void withdraw(int amount) {
        synchronized (withdrawLock) { balance -= amount; }
    }
}

    Although deposit() and withdraw() use synchronized blocks, they modify the same balance using different monitors. They can still execute concurrently and corrupt the shared state. To protect the same invariant, use the same monitor:

    class Bank {
    private final Object balanceLock = new Object();
    private int balance;

    void deposit(int amount)  { synchronized (balanceLock) { balance += amount; } }
    void withdraw(int amount) { synchronized (balanceLock) { balance -= amount; } }
}

    The rule is: data that participates in the same consistency rule must be protected by the same lock. Two pieces of identical code are not synchronized with each other merely because they look the same; they coordinate only when they acquire the same monitor object. All threads must use the same lock reference for the protection to work.

    14. Common Mistake: A New Lock Every Time

    This attempt at synchronization silently does nothing:

    synchronized (new Object()) {   // INCORRECT
    count++;
}

    Every execution creates a new object, so every call uses a different monitor:

    Call 1 -> monitor A
Call 2 -> monitor B
Call 3 -> monitor C

    Because the threads acquire different monitors, they do not block one another. The correct form keeps one stable reference:

    class Counter {
    private final Object lock = new Object();
    private int count;

    void increment() {
        synchronized (lock) { count++; }   // every call uses the same monitor
    }
}

    15. Static Synchronization: The Class Monitor

    Instance fields belong to individual objects; static fields belong to the class:

    class Counter { int count; }          // instance field
class Counter { static int count; }   // static field

    A synchronized instance method uses the current object's monitor, which is not enough to coordinate access to static state across multiple objects. For static synchronized methods, Java uses the monitor of the corresponding Class object:

    // Demo5.java — static synchronized methods share the class monitor
class Counter {
    private static int count = 0;

    static synchronized void increment() {
        count++;
    }

    static int getCount() {
        synchronized (Counter.class) {
            return count;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Counter::increment);
        Thread t2 = new Thread(Counter::increment);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(Counter.getCount());
    }
}

    The static synchronized method is conceptually equivalent to:

    static void increment() {
    synchronized (Counter.class) {
        count++;
    }
}

    The monitor is Counter.class, not this; a static method has no this reference.

    16. Object Monitor vs Class Monitor

    Multiple objects still share the class monitor:

    Counter first  = new Counter();
Counter second = new Counter();

Thread t1 = new Thread(Counter::increment);
Thread t2 = new Thread(Counter::increment);

    Both calls require the same monitor Counter.class, so they cannot execute the static synchronized method simultaneously. The number of Counter objects does not create additional class monitors.

    Now compare the two method kinds inside one class:

    class Test {
    synchronized void instanceMethod() { /* monitor: this */ }
    static synchronized void staticMethod() { /* monitor: Test.class */ }
}

    Suppose Thread-1 calls test.instanceMethod() and Thread-2 calls Test.staticMethod(). These methods can execute concurrently, because they use different monitors:

    instanceMethod() -> test object
staticMethod()   -> Test.class object

    Therefore, a synchronized instance method and a synchronized static method do not automatically block one another. They block only if both are explicitly synchronized on the same monitor. The comparison table below is the single most useful summary of what synchronized locks.

    Construct Monitor acquired Blocks which other constructs
    synchronized instance method this (the instance) Other synchronized instance methods and synchronized (this) on the same instance
    static synchronized method ClassName.class Other static synchronized methods and synchronized (ClassName.class)
    synchronized (lock) block the object lock evaluates to Any synchronized code using that same object
    synchronized (new Object()) a brand-new object each call Nothing in practice, because no other thread uses that object

    17. Monitor Internals, Entry and Exit, and Reentrancy

    Conceptually, a monitor must track information such as the current owning thread, a re-entry count, threads waiting to acquire the monitor, and threads waiting after calling wait(). A simplified teaching model might look like:

    Monitor {
    owner
    holdCount
    entrySet
    waitSet
}

    This is a teaching model, not the exact JVM memory layout. The JVM may use optimized representations such as lightweight locking, lock inflation, operating-system primitives, or other implementation-specific mechanisms.

    When a thread reaches synchronized (lock), conceptually the JVM checks whether it can acquire lock's monitor; if available, the thread becomes its owner; if another thread owns it, the current thread cannot enter and becomes eligible again when the monitor is released. Acquiring the monitor is performed atomically by the JVM: two threads cannot both successfully become the first owner of the same monitor at the same time. The exact implementation is JVM-dependent and should not be reduced to a guarantee that one particular CAS instruction is always used.

    The monitor is released when execution leaves the synchronized method or block. This applies during normal completion:

    synchronized (lock) {
    // work
}

    It also applies when the code exits because of an exception:

    synchronized (lock) {
    throw new RuntimeException();
}

    The JVM still releases the monitor while unwinding the synchronized region. This automatic release is one major advantage of synchronized.

    Java monitors are reentrant: a thread that already owns a monitor may acquire the same monitor again.

    class Service {
    synchronized void methodA() { methodB(); }
    synchronized void methodB() { System.out.println("Inside methodB"); }
}

    When a thread enters methodA(), it acquires the monitor of this. It can then call methodB() on the same object without blocking itself, because it already owns that monitor. The JVM tracks the number of times the thread has acquired the monitor, and the monitor is fully released only after the matching synchronized entries are exited.

    18. Common Synchronization Mistakes

    Beyond the "new lock every time" error, the repo notes collect several more.

    Mistake What goes wrong Correct approach
    Synchronizing on different objects (lock1 vs lock2) The two blocks do not protect the shared state from each other Use one consistent lock reference for that state
    Replacing the lock reference (lock = new Object()) Threads may begin synchronizing on different monitor objects Declare the lock private final
    Exposing the lock publicly External code could synchronize on it and unexpectedly block the class Keep the lock private
    Protecting only part of a compound operation A check performed outside the monitor can be invalidated before the update Put check and update in the same synchronized section

    The compound-operation trap is worth spelling out. Incorrect:

    if (balance >= amount) {
    synchronized (lock) {
        balance -= amount;   // condition checked outside the monitor
    }
}

    The condition is checked outside the monitor, so another thread may change balance before the synchronized update begins. Correct:

    synchronized (lock) {
    if (balance >= amount) {
        balance -= amount;   // check and update form one atomic operation
    }
}

    The check and update form one atomic operation with respect to the same monitor.

    19. Synchronized vs Explicit Lock (Preview)

    The intrinsic monitor is Java's built-in locking tool, and it is enough for most sharing problems. The java.util.concurrent.locks package offers explicit Lock implementations (such as ReentrantLock) that expose the same exclusivity with more control. This is a forward-looking comparison; the full API belongs to the concurrency-utilities lectures.

    Aspect synchronized (intrinsic monitor) Explicit Lock (e.g. ReentrantLock)
    Acquire / release Automatic on entering and leaving the region Explicit lock() and unlock() calls
    Release on exception Automatic while unwinding Must be released in a finally block
    Monitor object Any Java object's intrinsic monitor The Lock instance itself
    Try to acquire without blocking Not supported by the keyword tryLock() returns or times out
    Interruptible acquisition Not offered lockInterruptibly()
    Lock ownership fairness No fairness option Optional fairness policy
    Best fit Simple, well-contained critical sections Advanced coordination, timeouts, fairness
    \|Composability\| Cannot be composed arbitrarily Can wrap multiple lock objects in one holder

    Golden rule Prefer synchronized when the critical section is simple, because it can never be forgotten. Reach for an explicit Lock only when you truly need timeouts, interruptibility, or fairness, and always release it in finally.

    20. Deadlock and Safe Lock Ordering

    The blocking rule of monitors has a well-known consequence: if two threads each hold one lock and each waits for the lock the other holds, both wait forever. This is a deadlock, and it is entirely consistent with the acquisition rules of Section 6.

    Thread-1                                  Thread-2
  owns lockA                                owns lockB
  waits for lockB                           waits for lockA
              -> neither can proceed (deadlock)

    The safe design is to impose a global lock ordering and to always acquire monitors in that order.

    Design Interleaving Outcome
    Lock ordering A then B T1 takes A then waits for B; T2 waits for A No cycle; progress continues
    Lock ordering B then A T1 waits for B; T2 owns B and waits for A Cycle; deadlock
    Always same order Every thread requests locks in A -> B No circular wait can form
    Nested acquisition without a rule Each thread may hold one lock while requesting another Risk of deadlock 
    deadlock : Thread-1 holds A, wants B  |  Thread-2 holds B, wants A
safe     : every thread takes A, then B, and releases in reverse order

    Interviewer's perspective The classic one-liner: deadlock needs a cycle of threads each holding a resource and waiting for another. Break the cycle by consistent ordering, by acquiring all locks at once, or by not holding a monitor while calling into unknown code (which may itself lock).

    21. Myth vs Reality

    Myth Reality
    "synchronized on a method locks the method." It locks the object (this) or the class object; the method has no lock of its own.
    "Two synchronized methods on one object can run together." No; both need the same object monitor, so they block each other.
    "Synchronization pauses the whole program." It restricts only code guarded by the same monitor; other threads keep running.
    "Marking a method synchronized makes count++ a hardware atomic instruction." No; it excludes other threads using the same monitor, which is what makes the sequence safe.
    "A synchronized instance method also controls static state." Static state needs the class monitor; instance and class monitors are different and do not block each other.

    22. Common Trap Questions

    Trap 1 — Same object, two methods: "Thread-1 is in m1(); can Thread-2 enter m2() on the same object?" No. Both methods require the same object monitor, so Thread-2 blocks until Thread-1 exits.

    Trap 2 — Different objects: "Thread-1 uses first.m1(), Thread-2 uses second.m1(). Do they block?" No. Different objects have different monitors, so both may execute simultaneously.

    Trap 3 — The disappearing lock: "Is synchronized (new Object()) valid synchronization?" It compiles and runs, but each call locks a fresh object, so no two threads ever contend for the same monitor. It protects nothing.

    Trap 4 — Instance vs static: "Does synchronized void f() block static synchronized void g() on the same class?" Not automatically. f() uses this; g() uses ClassName.class. They block only if explicitly synchronized on the same monitor.

    Trap 5 — Reentrancy: "If a synchronized method calls another synchronized method on the same object, does it deadlock itself?" No. Java monitors are reentrant; the thread already owns the monitor and re-acquires it, incrementing the hold count.

    Trap 6 — Exception path: "Does an exception thrown inside synchronized leave the monitor locked forever?" No. The JVM releases the monitor while unwinding the synchronized region.

    Trap 7 — Split locks: "deposit() locks depositLock and withdraw() locks withdrawLock, both touching balance. Is balance safe?" No. They protect the same state with different monitors, so they can still corrupt it. Data under one consistency rule needs one lock.

    23. Points to Remember

    1. Synchronization coordinates threads that access shared mutable state; count++ is a non-atomic read-modify-write sequence.
    2. Both forms use the intrinsic monitor: instance methods lock this, static synchronized methods lock ClassName.class, and blocks lock the object written in parentheses.
    3. Synchronization provides mutual exclusion and memory visibility (a happens-before relationship) at the same time.
    4. Synchronization restricts only code guarded by a particular monitor; it does not stop multithreading.
    5. A lock belongs to an object, not to a method, so multiple synchronized methods on one object share one monitor.
    6. Different objects have different monitors, and different monitors do not block one another.
    7. Data that participates in the same consistency rule must be protected by the same lock; a new lock per call protects nothing.
    8. Dedicated lock objects should normally be private final; never replace the lock reference or expose it publicly.
    9. A monitor is released automatically on normal exit, on exception, and after reentrant calls finish; Java monitors are reentrant.
    10. A synchronized instance method and a synchronized static method do not automatically block one another; a whole compound operation (check plus update) must sit under one monitor.

    24. Likely Interview Questions

    Question Crisp Answer
    What is synchronization in Java? The mechanism that controls concurrent access to shared mutable data by making threads acquire a monitor before entering a protected region.
    Why can count++ lose updates? It is read-modify-write; two threads can read the same value and both write the same incremented result, so one update is lost.
    What is a monitor lock? An intrinsic per-object lock managed by the JVM that a thread must acquire to enter code synchronized on that object.
    Which monitor does a synchronized instance method use? The monitor of this; conceptually it is synchronized (this) { ... }.
    Which monitor does a static synchronized method use? The monitor of ClassName.class, not this; a static method has no this.
    Why are two synchronized methods on one object mutually blocking? Both require the same object monitor, and the lock belongs to the object, not to the method, so only one thread can hold it at a time.
    What does a synchronized block lock? The object expression written in parentheses, chosen explicitly by the programmer.
    Why use a separate lock object instead of this? It decouples the class's locking policy from the instance monitor and can protect independent state with independent locks.
    What does synchronization guarantee besides mutual exclusion? Memory visibility: a release followed by a later acquire of the same monitor makes prior writes visible.
    Are Java monitors reentrant? Yes; a thread that owns a monitor may re-acquire it, and the monitor is fully released only after the matching exits.
    What is the difference between an intrinsic lock and a ReentrantLock? The intrinsic lock is automatic (release on exit/exception) with no try/fairness/interruption; a ReentrantLock adds explicit release, tryLock(), interruptibility and fairness.
    What condition can consistent lock ordering prevent? Deadlock, where two threads each hold one lock and wait for the lock held by the other.

    25. Final Summary

    count++                     -> read, add, write (non-atomic)          -> lost update

synchronized method         -> lock this
static synchronized method  -> lock ClassName.class
synchronized (obj) block    -> lock obj          (obj must be shared)

release a monitor  -> later acquire the same monitor  -> happens-before + mutual exclusion

same object  -> same monitor -> mutual blocking
different objects -> different monitors -> concurrent
    • Shared data → count++ is a three-step sequence; without coordination, increments are lost.
    • Monitor → every object has an intrinsic monitor managed by the JVM; a thread must own it to enter protected code.
    • What synchronized locks → instance method locks this, static method locks ClassName.class, block locks the object in parentheses.
    • Consistency → the whole invariant must sit under one monitor; a new lock per call, a replaced lock, an exposed lock, or a partially protected operation all break safety.
    • Guarantees → mutual exclusion plus memory visibility, automatic release on normal exit or exception, and reentrant acquisition.
    • Forward → explicit Lock, tryLock() and fairness belong to the concurrency utilities; this lecture's monitor rules and safe lock ordering are the foundation.

    Golden rule Synchronization works only when every competing thread uses the same monitor for the same state; choose the monitor deliberately, keep it private final, and wrap the entire compound operation inside it.

    One-line takeaway: synchronized is not a property of a method but an agreement on one shared monitor object, and it provides mutual exclusion and memory visibility only when all threads guarding the same state hold that same lock.
