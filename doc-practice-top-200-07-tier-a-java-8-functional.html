      71. Stream collectors — what's available?

      Asked at: Razorpay · Swiggy · Cred · most mid-level rounds

      Difficulty: Medium · Topic: Java 8 Functional

      The question: "What collectors do you reach for most often in the Stream API?"

      The 30-second answer: toList(), toSet(), toMap(keyFn, valueFn), groupingBy(keyFn), partitioningBy(predicate), joining(", "), counting(), summingInt / averagingDouble, reducing, mapping(...) and filtering(...) as downstream collectors. Java 16 added toUnmodifiableList/Set/Map which return immutable results.

      Step-by-step thought process:

      1. " Collectors.toList() is the workhorse — collect a stream into a List. Java 16 added Stream.toList() directly which returns unmodifiable; Collectors.toList() returns ArrayList."
      2. " toMap(keyFn, valueFn) — careful: throws on duplicate keys. Use the 3-arg overload with a merge function: toMap(Order::getId, Function.identity(), (a, b) -> a) to keep first or merge."
      3. " groupingBy(Order::getStatus) returns Map<Status, List<Order>>. Pass a downstream collector to transform the value: groupingBy(Order::getStatus, counting()) returns Map<Status, Long>."
      4. " partitioningBy(Order::isPaid) returns Map<Boolean, List<Order>> — split into two buckets. Often clearer than groupingBy when the key is binary."
      5. " joining(", ", "[", "]") for string joining with separator + prefix + suffix. Beats StringBuilder manually."

      Edge cases to mention:

      • Collectors.toMap with duplicate keys throws IllegalStateException — always pass a merge function if duplicates are possible groupingBy returns a HashMap by default; use the 3-arg overload to get a TreeMap (groupingBy(keyFn, TreeMap::new, downstream))
      • For null keys, groupingBy accepts them but Collectors.toMap does not — common surprise

      What NOT to say:

      • "Collectors are just for collecting into lists" — they're a mini-DSL for terminal reductions
      • "Use forEach and a manual map" — defeats the point of streams

      Common follow-up: "How would you group orders by status and sum amount within each group?"

      72. Parallel streams — when do they help?

      Asked at: Razorpay · Swiggy · most product co backend rounds

      Difficulty: Medium-Hard · Topic: Java 8 Functional

      The question: "When should you actually use a parallel stream? When would it hurt?"

      The 30-second answer: Parallel streams help when: (1) the data set is large enough for splitting to amortize overhead, (2) the per-element work is CPU-bound and stateless, (3) the source splits cheaply (ArrayList yes, LinkedList no). They hurt for: small datasets, blocking I/O, contended shared state, or when you're already inside another parallel context.

      Step-by-step thought process:

      1. "Parallel streams use ForkJoinPool.commonPool() by default — same pool that other parts of your app may use. A slow parallel stream starves them."
      2. "For meaningful speedup, you need: N >> threads × overhead. As a rule of thumb, ~10,000 elements with non-trivial work per element is the breakeven for many workloads."
      3. "Splittable sources matter: ArrayList, arrays, IntStream.range — all split cheaply (O(1) bisection). LinkedList must walk to find the midpoint — kills parallelism."
      4. "Blocking I/O in a parallel stream is a disaster — you tie up the common pool, your app's other parallel work stalls. Use CompletableFuture or virtual threads for I/O concurrency instead."
      5. "Stateful operations (sorted on a non-comparable, limit on an unordered stream) make parallel streams either slower or buggy — read the Stream API contract."

      Edge cases to mention:

      • .parallel() doesn't preserve order in unordered streams; use .forEachOrdered() if you need encounter order
      • Java 21 virtual threads do NOT help with parallel streams (parallel streams are CPU-parallel, not I/O-parallel)
      • Use ManagedBlocker if you absolutely must block in a parallel stream — but really, prefer CompletableFuture

      What NOT to say:

      • "Always use parallel streams for performance" — usually slower for small data and I/O-bound work
      • "Parallel streams use threads I can configure" — they use the common pool, period (without ugly hacks)

      Common follow-up: "Why does using parallel stream with database calls usually slow things down?"

      73. Optional — proper use and abuse

      Asked at: Most modern Java rounds · Razorpay · Swiggy · Walmart Labs

      Difficulty: Easy-Medium · Topic: Java 8 Functional

      The question: "What is Optional intended for? What are common misuses?"

      The 30-second answer: Optional is a return type for methods that may have no result — it forces the caller to handle the absence explicitly. Use it as a return type. Don't use it as a field, parameter, or in collections — it adds overhead and the spec explicitly warns against it.

      Step-by-step thought process:

      1. "Original intent (from the JDK designers): return type for methods like findFirst(), stream().max() — anywhere you'd otherwise return null."
      2. " Optional.empty() represents absence. Optional.of(value) requires non-null. Optional.ofNullable(maybe) accepts null and produces empty."
      3. "Consume via ifPresent(x ->...), orElse(default), orElseGet(supplier), orElseThrow(), map / flatMap. The whole point is no .get() without a presence check."
      4. "Don't use as a field — Optional isn't Serializable, adds an allocation per field, and tools/frameworks (Jackson, JPA) don't always play well."
      5. "Don't use as a method parameter — overloading or just passing null is clearer. Don't put inside a collection — List<Optional<T>> is a code smell; use a different structure."

      Edge cases to mention:

      • Optional.get() without a presence check throws NoSuchElementException — same bug as a NullPointer with extra steps orElse(expensiveValue) always evaluates the default; use orElseGet(() ->...) for lazy evaluation
      • For primitive types, OptionalInt, OptionalLong, OptionalDouble exist — avoid Optional<Integer> boxing

      What NOT to say:

      • "Optional is a null replacement everywhere" — explicitly discouraged in the API docs
      • "Use Optional in fields for null safety" — adds overhead, breaks frameworks

      Common follow-up: "What's the difference between orElse and orElseGet?"

      74. Method references — when more readable than lambdas?

      Asked at: Most Java mid-level rounds

      Difficulty: Easy · Topic: Java 8 Functional

      The question: "When would you use a method reference instead of a lambda?"

      The 30-second answer: Use a method reference when the lambda is just a single method call passing its arguments through unchanged — s -> s.toUpperCase() becomes String::toUpperCase. It's shorter and signals "this is a direct call, no extra logic". When you need to transform arguments or add logic, stick with the lambda.

      Step-by-step thought process:

      1. "Four forms: ClassName::staticMethod (e.g. Integer::parseInt), ClassName::instanceMethod (e.g. String::length), instance::method (e.g. out::println), ClassName::new (constructor reference)."
      2. "Method references shine when the lambda is literally just a delegation: .map(s -> s.toUpperCase()) is noise compared to .map(String::toUpperCase)."
      3. "They lose clarity when context matters: customers.forEach(this::process) is fine, but customers.forEach(c -> process(c, currentTime)) can't be a reference because of the second argument."
      4. "Constructor references are useful in factories — stream.map(Order::new) turns a stream of inputs into a stream of new Orders."
      5. "Don't over-apply: if c -> c.getName().toLowerCase() is doing two things, leaving it as a lambda may be clearer than splitting into helper methods just to get a reference."

      Edge cases to mention:

      • For overloaded methods, the compiler picks based on the functional interface's signature — sometimes ambiguous, then you must use a lambda
      • Bound method references (instance::method) capture the instance at the point of reference — be careful with mutable state For streams over arrays, Arrays::asList and Arrays::stream are constructor-like references

      What NOT to say:

      • "Always replace lambdas with method references" — overreach; sometimes lambda is clearer
      • "Method references are faster" — same compiled bytecode in most cases

      Common follow-up: "What's the difference between String::length and s -> s.length() at the bytecode level?"

      75. reduce() vs collect() — when each?

      Asked at: Senior rounds · Razorpay · Swiggy

      Difficulty: Medium-Hard · Topic: Java 8 Functional

      The question: "What's the difference between Stream.reduce and Stream.collect? When would you use each?"

      The 30-second answer: reduce produces a single immutable result from associative combination — sum, product, max. collect produces a mutable container (List, Map, StringBuilder) via a supplier + accumulator + combiner. Use reduce for value reductions; use collect for building containers.

      Step-by-step thought process:

      1. " reduce(identity, accumulator) — repeatedly applies the accumulator (BinaryOperator) starting from identity. Result type matches the stream's element type."
      2. " reduce(identity, accumulator, combiner) — three-arg form for streams where the result type differs (and for parallel correctness)."
      3. " collect(supplier, accumulator, combiner) — the low-level form. Supplier creates the container, accumulator adds an element, combiner merges two partial containers (for parallel)."
      4. " collect(Collector) — the high-level form. Collector is a wrapper bundling supplier + accumulator + combiner + finisher. The Collectors.* factory has the common ones."
      5. "Practical rule: if I'm summing or maxing or producing a single value, reduce. If I'm building a List/Map/String/joined output, collect."

      Edge cases to mention:

      • For parallel reduce, the operation MUST be associative — a op b op c must equal (a op b) op c equal a op (b op c)
      • reduce without identity returns Optional<T> — the stream could be empty
      • collect is the only way to perform mutable reduction safely in parallel — never accumulate into a shared mutable collection inside reduce

      What NOT to say:

      • "reduce and collect are interchangeable" — they have different semantics and parallel behaviors
      • "reduce works for any combination" — only for associative operations in parallel

      Common follow-up: "Why is reduce dangerous if your combiner isn't associative?"

      76. Functional interfaces — which built-in to use?

      Asked at: Most Java mid-level rounds

      Difficulty: Easy-Medium · Topic: Java 8 Functional

      The question: "What are the main functional interfaces in java.util.function? When would you pick each?"

      The 30-second answer: Function<T,R> takes T, returns R. Predicate<T> takes T, returns boolean. Consumer<T> takes T, returns nothing (side effect). Supplier<T> takes nothing, returns T. BiFunction<T,U,R>, BiPredicate, BiConsumer for two args. UnaryOperator<T> and BinaryOperator<T> for same-type-in-same-type-out.

      Step-by-step thought process:

      1. "Function — transformations. Function<Order, BigDecimal> getAmount = Order::getAmount;."
      2. "Predicate — filtering, testing. Predicate<Order> isPaid = o -> o.getStatus() == PAID; then stream.filter(isPaid)."
      3. "Consumer — side effects, especially in forEach. Consumer<String> log = System.out::println;."
      4. "Supplier — lazy generators. Supplier<UUID> ids = UUID::randomUUID;. Used in Optional.orElseGet(supplier)."
      5. "For primitives, there are specialized versions to avoid boxing: IntPredicate, ToIntFunction<T>, IntFunction<R>, ObjIntConsumer<T>, etc. Use these in hot paths."

      Edge cases to mention:

      • Predicate has and, or, negate for composing — isPaid.and(isLarge) is cleaner than nested lambdas
      • Function has andThen and compose — composable transformations
      • For three or more args, no built-in TriFunction — you'd define your own

      What NOT to say:

      • "Just use Function for everything" — losing intent and forcing boxing
      • "I write my own functional interfaces" — overkill 95% of the time; the built-ins cover what you need

      Common follow-up: "What's the difference between Function.compose and Function.andThen?"

      77. Stream lazy evaluation — what does it mean?

      Asked at: Razorpay · Swiggy · most product co rounds

      Difficulty: Medium · Topic: Java 8 Functional

      The question: "What does it mean that streams are lazy? Why does it matter?"

      The 30-second answer: Intermediate operations (map, filter, sorted, limit) don't run when called — they build up a pipeline. The pipeline only executes when you call a terminal operation (collect, forEach, count, etc.). This enables short-circuiting and fusion — limit(10) after a filter only processes elements until 10 pass.

      Step-by-step thought process:

      1. " stream.filter(p).map(f).collect(toList()) — when you call filter, nothing runs. Same for map. The pipeline is built but inert."
      2. " collect is terminal. It pulls elements one by one through the pipeline: each element flows through filter, then map, then into the collector."
      3. "Short-circuiting: findFirst, limit, anyMatch, allMatch, noneMatch can stop early. stream.filter(p).findFirst() stops at the first element that passes p — doesn't process the rest."
      4. "Fusion: the JIT can often fold multiple intermediate ops into a single loop, avoiding intermediate collections."
      5. "A stream can only be consumed once — calling count() then collect() on the same stream throws IllegalStateException. Recreate the stream if you need to traverse twice."

      Edge cases to mention:

      • Infinite streams (Stream.iterate(0, i -> i+1)) only work because of laziness — must use a short-circuiting op like limit(n) to terminate
      • Stateful intermediate ops (sorted, distinct) buffer elements — break the lazy property for the rest of the pipeline
      • Side effects in intermediate ops are evaluated unpredictably if at all — never put state-mutating code in peek or map

      What NOT to say:

      • "Streams just iterate over a collection" — misses the entire execution model
      • "Lazy means asynchronous" — it doesn't, lazy and async are different

      Common follow-up: "What happens if you call .filter().peek().filter().collect()? When does peek run?"
