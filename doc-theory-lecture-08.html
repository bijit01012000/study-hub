    Lecture 08 — Spring XML Configuration Explained

    22 sections · 4,178 words

    Lecture 08

    Scope evidence: "Spring XML Configuration Explained | Beans, DI, Scopes & Lifecycle" (playlist map, verified). The repo folder is the XMLBasedConfigDemo Maven project, holding resources/beans.xml, beans2.xml and appConfig.xml plus the in.strikes classes (AppConfig, Main, OrderService, UserService, payment.PaymentService, CardPaymentService, UPIPaymentService) and this lecture's notes.

    Annotations are not the only way to tell Spring what to manage. This lecture builds an XML project step by step: one bean, then dependency injection, then scopes, lifecycle, collections, and split context files. By the end, XML stops looking like legacy noise and starts looking like the plain, explicit foundation annotations hide.

    1. Why XML Configuration Exists and What Spring Needs

    In Spring, annotations are not the only way to tell the IoC container which objects to manage. Before annotation-based configuration became common, applications were mostly configured using XML. XML configuration tells Spring:

    • These are my classes.
    • These are the objects you need to create.
    • These are their dependencies.
    • Please manage them inside the IoC container.

    The Spring IoC container creates objects, connects their dependencies, manages their lifecycle, and destroys them when required. To do that, Spring needs configuration information:

    1. Which classes should become beans?
    2. What should be the bean name?
    3. Should the bean be singleton or prototype?
    4. Which dependency should be injected?
    5. Which bean should be preferred if multiple beans of the same type exist?
    6. Which method should run after bean creation?
    7. Which method should run before bean destruction?

    That information is called configuration metadata. XML, annotations, and Java config are only different ways of giving instructions to Spring.

    Important: XML does not change what Spring does. It only changes where you write the instructions. The container still creates, wires, and manages the same beans.

    2. Configuration Styles and BeanDefinition

    Spring can receive configuration metadata in different ways, but the destination is always the same.

    Configuration Style Where Configuration Is Written
    XML-based configuration Inside an XML file
    Annotation-based configuration Inside Java classes
    Java-based configuration Inside Java config classes using @Configuration and @Bean

    Spring converts this metadata into BeanDefinition objects: Configuration Metadata (XML / annotations / Java config) -> BeanDefinition -> IoC Container -> Creates + Wires + Manages Beans. The container works from bean definitions, so a bean declared in XML and the same class annotated with @Component behave identically at runtime.

    3. Why Learn XML Configuration

    Even though modern Spring projects mostly use annotations and Java-based configuration, XML is still worth understanding for two reasons.

    Reason 1: Legacy projects. Many old Spring applications still use XML. On an older enterprise project you may find files like:

    beans.xml
applicationContext.xml
spring-context.xml

    Understanding XML configuration helps you read and maintain such projects.

    Reason 2: Better understanding of Spring internals. Annotations sometimes hide what Spring does internally. XML makes the wiring visible because we manually write which bean to create, its name, which dependency to inject, and which lifecycle method to call. This makes XML a good way to understand the foundation of Spring.

    Golden rule: every annotation you have ever trusted is just a shortcut for a bean definition that XML would have written out in full. Learn the long form once and the shortcuts stop being mysterious.

    4. Recommended Project Structure

    A simple XML-based Spring project can follow this structure:

    src
+-- main
    +-- java
    |   +-- in
    |       +-- strikes
    |           +-- Main.java
    |           +-- PaymentService.java
    |           +-- OrderService.java
    +-- resources
        +-- beans.xml

    Place the XML file inside src/main/resources, because files there become available on the classpath. So new ClassPathXmlApplicationContext("beans.xml") searches for beans.xml from the classpath, not an absolute disk path.

    5. Creating a Simple Java Class and beans.xml

    First we make a normal Java class. There is no annotation like @Component on it, so Spring will not automatically detect it; we will register it as a bean manually using XML. Inside src/main/resources, create beans.xml. The root <beans> tag holds all bean definitions. With the first bean registered:

    <?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="
           http://www.springframework.org/schema/beans
           http://www.springframework.org/schema/beans/spring-beans.xsd">

    <bean id="paymentService" class="in.strikes.PaymentService"/>
</beans>

    The PaymentService class behind that bean is plain Java, with a constructor that prints a message and a pay() method:

    package in.strikes;

public class PaymentService {
    public PaymentService() {
        System.out.println("PaymentService object created");
    }
    public void pay() {
        System.out.println("Payment successful");
    }
}

    6. Registering the First Bean and XML vs @Component

    We add this line inside the <beans> tag:

    <bean id="paymentService" class="in.strikes.PaymentService"/>

    This line means: Spring, create and manage one object of PaymentService, and keep its bean name as paymentService. The two attributes carry all the meaning:

    XML Attribute Meaning
    id Name of the bean inside the Spring container
    class Fully qualified class name whose object Spring should create

    In annotation-based configuration, @Component on the class makes Spring give the bean the default name paymentService, so the XML <bean id="paymentService" class="in.strikes.PaymentService"/> is conceptually similar to @Component("paymentService"). The difference is where configuration lives:

    Annotation Config XML Config
    Configuration is written inside Java class Configuration is written inside XML file
    Spring detects class using component scanning Spring reads bean definition from XML
    Bean name may be generated automatically Bean name is usually written manually

    Interviewer's perspective: "XML or annotations?" Both produce the same bean definitions, so it is not about power: XML is explicit and inspectable, annotations are concise and colocated.

    7. Loading XML Configuration and Eager Singleton Behavior

    The entry point loads the XML file and hands back an ApplicationContext. The type actually instantiated is ClassPathXmlApplicationContext, which reads the file from the classpath:

    package in.strikes;

import org.springframework.context.ApplicationContext;
import org.springframework.context.support.ClassPathXmlApplicationContext;

public class Main {
    public static void main(String[] args) {
        ApplicationContext context =
                new ClassPathXmlApplicationContext("beans.xml");

        PaymentService paymentService =
                context.getBean("paymentService", PaymentService.class);
        paymentService.pay();
    }
}

    The output is:

    PaymentService object created
Payment successful

    Notice that PaymentService object created prints before we call getBean(). Building the context loads the XML and creates the beans. By default Spring beans are singleton + eager, so the bean is created immediately when the container starts, which is why the constructor message appears first.

    Important: ApplicationContext is eager by default. The object exists the moment the context is built, so the constructor runs during startup, not on first request.

    8. Getting Beans from the Container

    There are three common ways to fetch a bean, and they trade safety for typing convenience.

    By name (with manual cast). This works, but we need manual type casting:

    PaymentService paymentService =
        (PaymentService) context.getBean("paymentService");

    By name and type (preferred). This is safer and cleaner because it avoids manual casting:

    PaymentService paymentService =
        context.getBean("paymentService", PaymentService.class);

    By type only. This works only when Spring has exactly one matching bean of that type:

    PaymentService paymentService =
        context.getBean(PaymentService.class);

    If we register two beans of the same type:

    <bean id="paymentService1" class="in.strikes.PaymentService"/>
<bean id="paymentService2" class="in.strikes.PaymentService"/>

    and then call context.getBean(PaymentService.class), Spring will not randomly choose one. It will throw NoUniqueBeanDefinitionException, because multiple beans match the same type.

    Method Cast Needed Safe When
    getBean(name) Yes Bean name is known and trusted
    getBean(name, type) No Name and type are both known
    getBean(type) No Exactly one bean of that type exists

    9. Bean Naming: id, name, and Alias

    Bean names usually follow Java variable naming style, for example paymentService.

    The id attribute gives one unique name to a bean. XML also supports name, which also allows access by that name. Both look similar at a beginner level, but they differ in intent: id is one main name, while name can add aliases:

    <bean id="paymentService"
      name="payService, gatewayService, transactionService"
      class="in.strikes.PaymentService"/>

    Now the same bean can be accessed using different names:

    context.getBean("paymentService", PaymentService.class);
context.getBean("payService", PaymentService.class);
context.getBean("gatewayService", PaymentService.class);
context.getBean("transactionService", PaymentService.class);

    All of these refer to the same bean. Sometimes a bean is already defined and we want to give it another name without changing the original definition. We can use the <alias> element:

    <alias name="paymentService" alias="payService"/>

    Now context.getBean("payService", PaymentService.class) also works.

    Concept What it gives Example
    id One main unique name id="paymentService"
    name One name or many comma-separated aliases name="payService, gatewayService"
    alias An extra name for an already-defined bean alias name="paymentService" alias="payService"

    Mnemonic for the naming trio: id is the identity, name is the tag list, alias is the nickname added later.

    10. Dependency Injection in XML: Constructor Injection

    In XML configuration, dependency injection is mainly done in two ways: constructor injection and setter injection. XML does not do field injection in the common style, because it works by calling constructors or setters.

    Suppose OrderService depends on PaymentService and takes it through the constructor. The XML registers both beans and passes the dependency with constructor-arg:

    <bean id="paymentService" class="in.strikes.PaymentService"/>

<bean id="orderService" class="in.strikes.OrderService">
    <constructor-arg ref="paymentService"/>
</bean>

    This means: create the PaymentService bean, create the OrderService bean, and while creating OrderService, pass paymentService into its constructor.

    Attribute Meaning
    constructor-arg Pass value/dependency through constructor
    ref Reference to another bean in the Spring container

    If the constructor takes a simple value, use value instead. Here value="Razorpay" means Spring passes "Razorpay" as a normal value, not as a bean reference:

    <bean id="paymentService" class="in.strikes.PaymentService">
    <constructor-arg value="Razorpay"/>
</bean>

    With multiple arguments, Spring tries to match constructor arguments by order and type. To make the order clear, we can use index; index="0" means the first constructor parameter, index="1" means the second:

    <bean id="paymentService" class="in.strikes.PaymentService">
    <constructor-arg index="0" value="Razorpay"/>
    <constructor-arg index="1" value="3"/>
</bean>

    If constructor parameter names are available, we can match by name, which is more readable:

    <bean id="paymentService" class="in.strikes.PaymentService">
    <constructor-arg name="providerName" value="Razorpay"/>
    <constructor-arg name="retryCount" value="3"/>
</bean>

    By-name matching depends on whether Spring can discover parameter names, so index is usually easier to demonstrate reliably. We can also specify the type, which helps when matching becomes confusing:

    <bean id="paymentService" class="in.strikes.PaymentService">
    <constructor-arg type="java.lang.String" value="Razorpay"/>
    <constructor-arg type="int" value="3"/>
</bean>
    Method Example Use Case
    By order <constructor-arg value="Razorpay"/> Simple cases
    By index <constructor-arg index="0" value="Razorpay"/> When order must be clear
    By name <constructor-arg name="providerName" value="Razorpay"/> When parameter names are available
    By type <constructor-arg type="java.lang.String" value="Razorpay"/> When constructor matching needs help

    Mnemonic for the four matching strategies: O-I-N-T - Order, Index, Name, Type.

    11. Setter Injection and value vs ref

    For setter injection, OrderService exposes a setter method, and XML calls it. The setter method is important because XML setter injection works by calling it:

    public void setPaymentService(PaymentService paymentService) {
    System.out.println("Setter called for paymentService");
    this.paymentService = paymentService;
}

    The XML configuration uses <property> with a name and a ref:

    <bean id="paymentService" class="in.strikes.PaymentService"/>

<bean id="orderService" class="in.strikes.OrderService">
    <property name="paymentService" ref="paymentService"/>
</bean>

    The important line is <property name="paymentService" ref="paymentService"/>. name="paymentService" refers to the property inside OrderService, so Spring looks for setPaymentService(...); ref="paymentService" refers to another bean in the container. So the XML means: create OrderService, call the setter, and pass the bean named paymentService into it.

    The value and ref attributes are not interchangeable:

    Attribute Meaning
    value Injects a simple value like String, int, boolean
    ref Injects another bean from the Spring container

    Example using value: <constructor-arg value="Razorpay"/>. Example using ref: <constructor-arg ref="paymentService"/>.

    Important: Point value at a bean name and Spring injects the literal text; point ref at a non-bean and startup fails. The two answer "is this data?" versus "is this an object in the container?"

    12. Multiple Beans of the Same Type and XML Autowiring

    Suppose OrderService needs one PaymentService, but the XML has two payment service beans:

    <bean id="razorpayPaymentService" class="in.strikes.RazorpayPaymentService"/>
<bean id="stripePaymentService" class="in.strikes.StripePaymentService"/>

    Spring should not guess randomly. It needs to know which one to inject into OrderService, and the cleanest solution in XML is explicit wiring:

    Solution 1: explicit wiring using ref. This removes all confusion:

    <bean id="orderService" class="in.strikes.OrderService">
    <constructor-arg ref="razorpayPaymentService"/>
</bean>

    The line <constructor-arg ref="razorpayPaymentService"/> means: when creating OrderService, inject the bean named razorpayPaymentService, so Spring knows exactly which one to use even when several exist.

    Solution 2: primary="true". We can mark one bean as primary, and when Spring needs a bean by type while multiple options exist, it will prefer the primary bean:

    <bean id="razorpayPaymentService" class="in.strikes.RazorpayPaymentService" primary="true"/>
<bean id="stripePaymentService" class="in.strikes.StripePaymentService"/>

    However, in XML projects, explicit wiring using ref is usually clearer than depending on primary.

    Solution 3: autowire-candidate="false". This tells Spring not to consider a bean as a candidate for autowiring:

    <bean id="razorpayPaymentService" class="in.strikes.RazorpayPaymentService"/>
<bean id="stripePaymentService" class="in.strikes.StripePaymentService" autowire-candidate="false"/>

    This is useful in legacy XML projects, but beginners should first understand explicit wiring with ref.

    XML autowiring means that instead of writing every dependency manually using ref, we ask Spring to find the dependency automatically:

    <bean id="paymentService" class="in.strikes.PaymentService"/>
<bean id="orderService"
      class="in.strikes.OrderService"
      autowire="byName"/>

    The common modes are:

    Mode Meaning
    byName Matches dependency using property name and bean name
    byType Matches dependency using type
    constructor Matches constructor parameters using available beans

    byName matches the setter property name against bean names. byType matches the property type against one clear bean, and fails when several match. constructor matches constructor parameter types against available beans.

    XML Autowiring Mode How Spring Matches Dependency Works Best When
    byName Property name matches bean name Bean names are predictable
    byType Property type matches bean type Only one bean of that type exists
    constructor Constructor parameter type matches bean type Constructor dependencies have clear matching beans

    For beginners, manual dependency injection using ref should come first; autowiring is a convenience feature.

    13. Bean Scopes in XML

    For this video, focus mainly on two scopes: singleton and prototype. By default, Spring beans are singleton.

    Singleton scope. Spring creates only one object of this bean inside the container:

    <bean id="paymentService" class="in.strikes.PaymentService"/>

    If we call getBean() multiple times:

    PaymentService p1 = context.getBean("paymentService", PaymentService.class);
PaymentService p2 = context.getBean("paymentService", PaymentService.class);
System.out.println(p1 == p2);

    the output is true, because both references point to the same object.

    Prototype scope. Prototype means Spring creates a new object every time we request the bean:

    <bean id="paymentService"
      class="in.strikes.PaymentService"
      scope="prototype"/>

    Now the output shows two constructor messages and prints false, because each getBean() call creates a new object.

    Aspect in XML singleton (default) prototype
    Objects created One per container New object per request
    getBean() twice Same reference (p1 == p2 is true) Different references (p1 == p2 is false)
    Default Yes No, must set scope="prototype"
    destroy-method on close Called Not called automatically

    Singleton bean depending on a prototype bean. Suppose OrderService is singleton and PaymentService is prototype:

    <bean id="paymentService"
      class="in.strikes.PaymentService"
      scope="prototype"/>
<bean id="orderService"
      class="in.strikes.OrderService"
      scope="singleton">
    <constructor-arg ref="paymentService"/>
</bean>

    The prototype bean is injected when the singleton is created, so a singleton OrderService receives one PaymentService object at creation time and does not get a new one on every method call. This matters when mixing scopes.

    14. Bean Lifecycle Methods in XML

    In XML we can tell Spring which method runs after bean creation and which runs before destruction. These are normal Java methods: no annotations, no Spring interfaces, just XML telling Spring when to call them. A PaymentService with a constructor, init(), pay(), and cleanup():

    package in.strikes;

public class PaymentService {
    public PaymentService() {
        System.out.println("1. PaymentService constructor called");
    }
    public void init() {
        System.out.println("2. PaymentService init method called");
    }
    public void pay() {
        System.out.println("3. Payment successful");
    }
    public void cleanup() {
        System.out.println("4. PaymentService cleanup method called");
    }
}

    The XML maps the callbacks by name: init-method runs after creation and dependency injection, destroy-method runs before destruction:

    <bean id="paymentService"
      class="in.strikes.PaymentService"
      init-method="init"
      destroy-method="cleanup"/>

    Closing the context. To see the destroy method run, the context must be closed. Use ClassPathXmlApplicationContext for that, because the ApplicationContext interface does not expose close():

    ClassPathXmlApplicationContext context =
        new ClassPathXmlApplicationContext("beans.xml");
PaymentService paymentService =
        context.getBean("paymentService", PaymentService.class);
paymentService.pay();
context.close();

    Try-with-resources is better, so the context always closes. On close, Spring calls the destroy method for singleton beans.

    Prototype scope with init and destroy. For prototype beans, Spring creates the object, injects dependencies, calls the init method, and then hands the object to the application:

    <bean id="paymentService"
      class="in.strikes.PaymentService"
      scope="prototype"
      init-method="init"
      destroy-method="cleanup"/>

    Spring does not call the destroy method for prototype beans when the context closes, because it does not manage their full lifecycle after creation.

    Interviewer's perspective: "Why does my destroy-method not run for a prototype bean?" is a favorite. The answer is ownership: Spring stops tracking the object once it is handed over, so destruction becomes the application's responsibility.

    Important: ApplicationContext does not declare close(). Cast to ClassPathXmlApplicationContext, or use try-with-resources, to trigger singleton destruction callbacks.

    15. Collection Injection in XML

    XML can also inject collections like List, Set, and Map. A UserService that takes a list of names is configured with <list> and <value> elements:

    <bean id="userService" class="in.strikes.UserService">
    <constructor-arg name="userNames">
        <list>
            <value>Aditya</value>
            <value>Rohit</value>
            <value>Rohan</value>
        </list>
    </constructor-arg>
</bean>

    A PaymentService that takes a Map<String, Double> of balances is configured with <map> and <entry>:

    <bean id="paymentService" class="in.strikes.PaymentService">
    <constructor-arg name="userBalances">
        <map>
            <entry key="Aditya" value="2.0"/>
            <entry key="Rohit" value="2.5"/>
            <entry key="Rohan" value="3.0"/>
        </map>
    </constructor-arg>
</bean>

    XML can handle simple beans and complex collections alike. The same <list> and <map> elements also work inside <property> for setter injection.

    16. Splitting XML Files and Mixing XML with Annotations

    In real legacy projects, one XML file can become very large, so we split configuration into multiple XML files instead of one beans.xml:

    src/main/resources
+-- applicationContext.xml
+-- orderContext.xml
+-- userContext.xml

    Each part holds the beans for one area: orderContext.xml has the payment and order beans, userContext.xml has the user bean. The main file imports both:

    <import resource="orderContext.xml"/>
<import resource="userContext.xml"/>

    Now in Java, we only load the main file, and Spring loads applicationContext.xml, which imports the other XML files:

    ClassPathXmlApplicationContext context =
        new ClassPathXmlApplicationContext("applicationContext.xml");

    Can XML and annotations work together? Yes. Both are just ways of giving configuration metadata to Spring. A legacy project may define some beans in XML, detect others by annotations, and create still others via Java config; Spring converts all of them into bean definitions.

    In XML, we can enable annotation scanning using <context:component-scan base-package="in.strikes"/>. For this, the XML file needs the context namespace xmlns:context="http://www.springframework.org/schema/context" along with its schema location:

    <context:component-scan base-package="in.strikes"/>

    This tells Spring to scan the package in.strikes and detect annotation-based components like @Component, @Service, and @Repository.

    Should beginners mix XML and annotations? No - learn each separately first. Mixing too early confuses because XML and annotation beans can depend on each other, and component scanning plus manual registration can create duplicate beans. Best order: pure annotation config, then pure XML config, then note that both work together in legacy projects.

    17. Myth vs Reality

    Myth Reality
    "XML configuration uses a different container" Same IoC container; XML just supplies metadata that becomes BeanDefinitions.
    "@Component and <bean> do different things" Both create a bean definition; the class and name are declared in different places.
    "id and name are exactly the same" id is one main name; name can hold several comma-separated aliases.
    "value and ref are interchangeable" value injects a literal; ref injects another container bean.
    "Spring guesses when two beans share a type" It throws NoUniqueBeanDefinitionException unless resolved.
    "Prototype beans get destroy-method called" Spring does not manage full prototype lifecycle; destroy is not called on close.
    "init-method and destroy-method need annotations" They are plain Java methods; XML tells Spring when to call them.
    "Closing the context is optional detail" Without close(), singleton destroy callbacks never run.

    18. Common Trap Questions

    Trap 1 - "The constructor ran before getBean(), so Spring created it lazily." Verdict: False. Beans are singleton + eager by default, so the object is created when the container starts.

    Trap 2 - "context.getBean(PaymentService.class) is always the safest choice." Verdict: Misleading. By-type lookup throws NoUniqueBeanDefinitionException the moment two beans share the type; name+type avoids that.

    Trap 3 - "id and name are the same attribute." Verdict: False. id is the one main unique name; name can list several aliases, and <alias> adds one more externally.

    Trap 4 - "Two beans with the same id just overwrite each other quietly." Verdict: False. Bean ids should be unique in the same XML file; duplicates make getBean("paymentService") ambiguous.

    Trap 5 - "If two beans of the same type exist, Spring picks the first one." Verdict: False. Spring does not guess; use explicit ref, primary="true", or autowire-candidate="false".

    Trap 6 - "A singleton that depends on a prototype gets a fresh prototype each call." Verdict: False. The prototype is injected once when the singleton is created; later calls reuse that same object.

    Trap 7 - "Prototype beans get destroy-method called when the context closes." Verdict: False. Spring stops managing prototype beans after handing them over.

    19. Points to Remember

    1. XML is one way to give Spring configuration metadata; annotations and Java config are others.
    2. All configuration styles become BeanDefinition objects that the IoC container consumes.
    3. id names the bean; class tells Spring which class to instantiate.
    4. ClassPathXmlApplicationContext loads XML from the classpath, so the file must live in src/main/resources.
    5. Beans are singleton and eager by default, so constructors run during container startup.
    6. getBean(name, type) avoids casting; getBean(type) needs exactly one matching bean.
    7. id is the main name, name can list aliases, and <alias> adds an external nickname.
    8. Constructor injection uses constructor-arg with ref or value, matched by order, index, name, or type.
    9. Setter injection uses <property> with ref; value is for literals and ref is for beans.
    10. Same-type beans resolve via explicit ref, primary="true", or autowire-candidate="false"; singleton destroy runs on close() but prototype destroy does not.

    20. Likely Interview Questions

    Question Crisp Answer
    What is configuration metadata in Spring? The instructions Spring needs (classes, names, scopes, dependencies, init/destroy) to create and manage beans.
    What does Spring convert config metadata into? BeanDefinition objects, whether the source was XML, annotations, or Java config.
    Why learn XML configuration when annotations exist? Legacy enterprise projects use it, and it exposes the explicit wiring annotations hide.
    What does <bean id="x" class="..."/> mean? Create and manage one object of that class inside the container, registered under the name x.
    XML bean vs @Component? Same result (a bean definition); XML declares it in a file, @Component is found by scanning.
    Why does the constructor run before getBean()? Beans are singleton and eager by default, so they are created when the context starts.
    How do you get a bean by type? context.getBean(PaymentService.class); works only when exactly one bean of that type exists.
    What is thrown when two beans match a type lookup? NoUniqueBeanDefinitionException.
    Difference between id and name? id is one main unique name; name can provide multiple comma-separated aliases.
    Difference between value and ref? value injects a simple value; ref injects another bean from the container.
    How do you resolve two beans of the same type? Explicit ref, primary="true" on one, or autowire-candidate="false" on the other.
    Why is prototype destroy-method not called? Spring does not manage the full lifecycle of prototype beans after handing them over.

        +--> injects deps (constructor-arg / property, value vs ref)
        +--> resolves duplicates (ref, primary, autowire-candidate)

        |
        v
Split files via <import>; mix with <context:component-scan>
    • XML, annotations, and Java config all produce BeanDefinitions for the same IoC container.
    • <bean> registers an object; id names it and class says which class to build.
    • Constructor injection uses constructor-arg; setter injection uses <property>; value is literal, ref is a bean.
    • Same-type duplicates resolve with explicit ref, primary="true", or autowire-candidate="false".
    • Singleton is the default scope; prototype returns a new object per request and skips destroy callbacks.
    • Lifecycle callbacks come from init-method and destroy-method; close() triggers singleton destruction.
    • Large configurations split into files linked by <import>, and XML can enable scanning with <context:component-scan>.

    One-line takeaway: XML is the verbose, honest form of the same bean definitions annotations whisper - write it once and Spring's container stops being a black box.
