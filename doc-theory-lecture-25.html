    Lecture 25 — Custom Annotations in Spring AOP

    21 sections · 4,561 words

    Lecture 25

    Scope evidence: "Custom Annotations in Spring AOP | @annotation Binding & Proxies" (playlist map, verified). Repo folder is the aopDemo project: AopDemoApplication, an annotation package holding TrackExecutionTime, an aspect package holding the timing aspect (SimpleAspect in the repo, shown as PerformanceAspect in the notes), plus controller.StudentController, dto.Student, and service.StudentService, together with the lecture notes.

    Custom annotations are how a method declares the behaviour it needs without implementing that behaviour. Spring AOP reads the annotation through the @annotation() pointcut designator and supplies the behaviour from an aspect. This lecture joins the "what" (annotation) to the "how" (aspect), then follows that connection down into the bean lifecycle, proxies, the interceptor chain, and proceed(). The goal is a complete mental model of annotation-driven, proxy-based AOP.

    1. Separating "What" from "How"

    Consider a service method that measures its own execution time:

    public Report generateAnnualReport() {
    long startTime = System.nanoTime();
    try {
        return reportGenerator.generate();
    } finally {
        long duration = System.nanoTime() - startTime;
        System.out.println("Duration: " + duration);
    }
}

    This method now has two responsibilities: generating the report, and measuring execution time. Execution-time measurement is not part of the core business logic. It is a cross-cutting concern that may be required by many methods: execution-time tracking, logging, auditing, authorization, rate limiting, retry handling, validation.

    We can move that behaviour into an aspect (@Around("@annotation(TrackExecutionTime)")), and the business method only declares its intention:

    @TrackExecutionTime
public Report generateAnnualReport() {
    return reportGenerator.generate();
}

    The responsibilities are now separated:

    Part Responsibility
    Annotation Declares what behaviour is required
    Aspect Defines how that behaviour is implemented
    Business method Contains the actual business logic

    This is declarative programming: the method declares the behaviour without implementing it.

    Important: A cross-cutting concern is any behaviour that several unrelated methods need. Moving it out of the business method keeps the method focused on one responsibility.

    2. A Custom Annotation Does Nothing by Itself

    Suppose we create an annotation public @interface TrackExecutionTime {} and apply it to a method @TrackExecutionTime public void generateReport() {}. Nothing happens automatically. An annotation is only metadata attached to a program element:

    Method + Metadata: "Track the execution time of this method"

    Some other component must (1) detect the annotation, (2) read its information, and (3) perform the required behaviour. In this case the Spring AOP aspect performs the work:

    @Around("@annotation(TrackExecutionTime)")
public Object trackTime(ProceedingJoinPoint joinPoint) throws Throwable {
    // Timing implementation
}

    The annotation declares the intention. The aspect gives that annotation its behaviour.

    Question Answer
    Does the annotation run any code? No; it is metadata only
    What detects it? A component such as a Spring AOP aspect
    What reads its properties? The advice method, via binding
    What performs the behaviour? The aspect's advice

    Important: An annotation is passive. It becomes behaviour only when another component detects it, reads it, and acts on it.

    3. Creating a Custom Annotation

    A custom annotation is declared using @interface, not the normal interface keyword. For Spring AOP, the basic declaration is usually not enough. Java must also know:

    • where the annotation can be used;
    • how long the annotation remains available.

    These rules are defined through meta-annotations - an annotation applied to another annotation declaration. The important ones are @Target, @Retention, and @Documented (commonly added).

    An annotation can also carry elements (configuration options):

    import java.lang.annotation.Documented;
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface TrackExecutionTime {
    String operation() default "";
    long warnAfterMillis() default 1000;
}

    Elements are declared like methods but with no parameters; a default makes them optional at the usage site. The aspect can later read trackExecutionTime.operation() and trackExecutionTime.warnAfterMillis().

    Interviewer's perspective: The moment a candidate says "an annotation itself does something," the answer is already weak. The correct framing is metadata plus a detector plus an actor.

    4. Understanding @Target and @Retention (and @Documented)

    @Target defines where an annotation is legally allowed to appear. For an annotation that should be placed on methods we write @Target(ElementType.METHOD). The compiler then permits the annotation on a method but rejects it on a class (@TrackExecutionTime on ReportService is a compilation error with a METHOD-only target).

    Common ElementType values:

    ElementType Where the annotation may be applied
    METHOD Methods (most common for method-level AOP)
    TYPE Classes, interfaces, enums, records, annotation interfaces
    FIELD Fields
    PARAMETER Method or constructor parameters
    CONSTRUCTOR Constructors
    ANNOTATION_TYPE Another annotation declaration

    An annotation may support more than one target via @Target({ ElementType.TYPE, ElementType.METHOD }), allowing it on a class or an individual method. For method-level Spring AOP the usual choice is @Target(ElementType.METHOD), because Spring AOP is proxy-based and primarily intercepts method executions on Spring-managed beans.

    @Retention defines how long annotation information is preserved. Java provides three retention policies:

    Retention policy When the annotation is available
    SOURCE Only in source code; discarded during compilation
    CLASS Stored in the .class file, but not normally available through runtime reflection
    RUNTIME Retained and inspectable at runtime by Spring and Java reflection

    RetentionPolicy.CLASS is Java's default retention policy when @Retention is not specified. Custom annotations used for Spring AOP should normally use @Retention(RetentionPolicy.RUNTIME); without runtime retention, Spring cannot reliably detect and bind the annotation while the application runs.

    @Documented tells Java documentation tools to include the annotation in generated Javadoc. A typical method-level AOP annotation therefore carries @Target(ElementType.METHOD), @Retention(RetentionPolicy.RUNTIME), and @Documented together.

    Mnemonic: T-R-D - Target says where, Retention says how long, Documented says show it in the docs.

    Important: @Target controls legality at compile time; @Retention(RUNTIME) controls availability at run time. Both are needed for annotation-driven Spring AOP.

    5. Marker Annotations and Configured Annotations

    A custom annotation can either act as a simple marker or carry additional configuration. A marker annotation has no properties and communicates only one thing: apply execution-time tracking to this method:

    @TrackExecutionTime
public Report generateReport() {
    return reportGenerator.generate();
}

    An annotation with properties can also carry values. With String operation() default ""; and long warnAfterMillis() default 1000;, a usage site can be:

    @TrackExecutionTime(
    operation = "Generate annual report",
    warnAfterMillis = 500
)
public Report generateAnnualReport() {
    return reportGenerator.generate();
}

    The method now declares that execution time should be measured, the name of the operation, and the threshold after which the operation should be treated as slow. The aspect can read these values with trackExecutionTime.operation() and trackExecutionTime.warnAfterMillis().

    Comparison:

    Aspect Marker annotation Configured annotation
    Properties None One or more elements with values
    What it tells the aspect "Apply this behaviour here" "Apply this behaviour, and here is how"
    Example @TrackExecutionTime @TrackExecutionTime(operation = "...", warnAfterMillis = 500)
    What the aspect reads Only presence Property values such as operation()
    Typical use Pure opt-in flags Tuning behaviour per method

    This makes the annotation both a marker and a small configuration object.

    Important: A marker annotation answers "should this happen?" A configured annotation also answers "with what settings?"

    6. The @annotation() Pointcut Designator

    The @annotation() pointcut designator matches methods based on an annotation present on the method being executed. It has two important uses: type matching and annotation binding.

    Type matching writes the fully qualified annotation name directly inside the pointcut expression:

    @Before("@annotation(com.coderarmy.student.aop.annotation.TrackExecutionTime)")
public void beforeTrackedMethod() {
    System.out.println("Tracked method called");
}

    This asks: is the executed method annotated with TrackExecutionTime? Use it when the advice only needs to know whether the annotation exists.

    The binding form performs two jobs at once: it matches methods containing the annotation, and it passes the actual annotation instance to the advice method.

    @Before("@annotation(trackExecutionTime)")
public void beforeTrackedMethod(TrackExecutionTime trackExecutionTime) {
    System.out.println(trackExecutionTime.operation());
}

    The name used in the pointcut expression corresponds to the advice parameter: the pointcut @annotation(trackExecutionTime) maps to the parameter TrackExecutionTime trackExecutionTime. Binding is required when the aspect needs to read annotation properties such as operation() or warnAfterMillis().

    Comparison:

    Aspect Type matching @annotation(TypeName) Annotation binding @annotation(varName)
    Job Matches methods that carry the annotation Matches methods and injects the annotation instance
    Pointcut example @annotation(com...TrackExecutionTime) @annotation(trackExecutionTime)
    Advice parameter None needed TrackExecutionTime trackExecutionTime
    Access to properties No Yes, for example .operation()
    When to use Only presence matters The aspect must read annotation values

    Interviewer's perspective: The high-value distinction is that @annotation does two jobs at once in its binding form - it selects the join point and it injects the annotation. Candidates who only know the matching half cannot write a configurable aspect.

    7. Complete Example: Measuring Execution Time

    Step 1 defines the annotation (the TrackExecutionTime declaration shown in Section 3, carrying operation and warnAfterMillis). Step 2 applies it to a service method; the service contains only business logic, no timing, logging, or threshold handling:

    @Service
public class ReportService {
    @TrackExecutionTime(operation = "Generate annual student report", warnAfterMillis = 500)
    public StudentReport generateAnnualReport() {
        return createReport();
    }

    private StudentReport createReport() {
        return new StudentReport();
    }
}

    Step 3 creates the aspect:

    package com.coderarmy.student.aop.aspect;

import com.coderarmy.student.aop.annotation.TrackExecutionTime;
import java.util.concurrent.TimeUnit;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class PerformanceAspect {
    @Around("@annotation(trackExecutionTime)")
    public Object measureExecutionTime(
        ProceedingJoinPoint joinPoint,
        TrackExecutionTime trackExecutionTime
    ) throws Throwable {
        long startTime = System.nanoTime();
        try {
            return joinPoint.proceed();
        } finally {
            long durationMillis = TimeUnit.NANOSECONDS.toMillis(System.nanoTime() - startTime);
            String operation = trackExecutionTime.operation();
            if (operation.isBlank()) {
                operation = joinPoint.getSignature().toShortString();
            }
            if (durationMillis >= trackExecutionTime.warnAfterMillis()) {
                System.out.println("SLOW OPERATION: " + operation + " took " + durationMillis + " ms");
            } else {
                System.out.println(operation + " took " + durationMillis + " ms");
            }
        }
    }
}

    Execution flow when another bean calls the method:

    Caller -> AOP proxy -> PerformanceAspect.measureExecutionTime()
       -> joinPoint.proceed() -> ReportService.generateAnnualReport()
       -> result returns to the aspect -> aspect logs duration -> result to caller

    The finally block ensures duration is calculated whether the target returns successfully or throws. The original exception is not swallowed because the advice does not catch and replace it.

    Important: Put the timing calculation in finally so both normal returns and exceptions are measured, and never swallow the original exception.

    8. Where Spring AOP Enters the Bean Lifecycle

    At a simplified level, Spring creates a bean through eight stages:

    1. Read the bean definition.
    2. Instantiate the bean.
    3. Inject dependencies.
    4. Run Aware callbacks.
    5. Run BeanPostProcessors before initialization.
    6. Run initialization callbacks.
    7. Run BeanPostProcessors after initialization.
    8. Store and expose the final bean reference.

    Spring AOP's automatic proxy creation is built on Spring's bean post-processing infrastructure. An AOP auto-proxy creator examines beans during their creation and determines whether any configured advice applies to them:

    target created -> dependencies injected -> init callbacks run
   -> AOP infrastructure examines the bean
   -> advisor matches? no -> return original bean
                       yes -> create AOP proxy -> return the proxy

    For an eligible bean, the final reference exposed by the container is normally Proxy -> Target rather than only Target. Advice does not run during creation; it runs when a method is invoked through the proxy.

    Important: Proxy creation is a lifecycle event; advice execution is a method-call event. Confusing the two is the most common mental-model error in AOP.

    9. BeanPostProcessor from First Principles

    BeanPostProcessor is a Spring extension point that allows infrastructure code to inspect or modify beans created by the container. Its basic idea is: whenever Spring creates a bean, infrastructure components get an opportunity to process it before the bean is finally exposed. A simplified form of the interface is:

    Object postProcessBeforeInitialization(Object bean, String beanName);
Object postProcessAfterInitialization(Object bean, String beanName);

    A post-processor may return the original bean (return bean;) or return a wrapped object (return proxy;). postProcessBeforeInitialization() runs before initialization callbacks such as @PostConstruct or InitializingBean.afterPropertiesSet(), and may inspect the bean, process certain annotations, perform additional configuration, or validate and prepare the bean. postProcessAfterInitialization() runs after initialization callbacks complete; Spring's AOP auto-proxy creation normally wraps eligible beans around this stage and returns the proxy as the final bean reference.

    original bean created -> initialization completed -> AOP post-processing
   -> original bean or proxy returned

    The key point is that Spring AOP uses bean post-processing to replace an eligible bean reference with a proxy reference.

    Golden rule: If a bean is eligible for advice, the object other beans receive is the proxy, not the raw target. Everything downstream follows from that substitution.

    10. How Spring Decides Which Beans Need Proxies

    Consider a LoggingAspect with @Before("within(com.coderarmy.student.service..*)"). Spring processes the aspect and creates an internal representation of two things: the advice (Run log()) and the pointcut (Match classes inside the service package). The combination of a pointcut and advice is commonly represented internally as an advisor.

    As Spring creates beans, the AOP infrastructure checks whether the advisors can apply to each bean:

    • For StudentController: is it inside the service package? No, so no proxy is required for this aspect.
    • For StudentService: is it inside the service package? Yes, so Spring creates an AOP proxy for the service bean.

    The same idea applies to an annotation-based pointcut such as @Around("@annotation(trackExecutionTime)"): Spring checks whether the bean contains methods that can match the annotation-based advisor, and eligible calls are intercepted by the proxy at runtime.

    Bean Advisor pointcut Match? Result
    StudentController within(...service..*) No Original bean exposed
    StudentService within(...service..*) Yes AOP proxy exposed
    StudentService @annotation(trackExecutionTime) Yes if a method carries it Eligible calls intercepted

    Important: An advisor is simply a pointcut plus its advice. Spring asks, per bean, "does any advisor match this bean?" and only then builds a proxy.

    11. The Container Stores the Final (Proxied) Bean

    Suppose Spring first creates the target object T100 and then creates a proxy P200. The relationship is P200: Proxy -> T100: Target. When another bean asks Spring for StudentService, the container supplies P200, not the raw target reference T100:

    public StudentController(StudentService studentService) {
    this.studentService = studentService;
}

    Conceptually the field stores the proxy:

    StudentController -> studentService field -> AOP proxy -> StudentService target

    This is why dependency injection and AOP work together. Spring controls object creation, dependency injection, bean post-processing, and the final reference supplied to other beans, so Spring can inject the proxy instead of the raw object.

    Important: You rarely see the raw target. When you inject a bean, you are normally injecting its proxy.

    12. The Method Interceptor Chain and What proceed() Means

    A single method may match multiple cross-cutting concerns - logging, security, performance measurement. The runtime chain may look like this:

    Caller -> Proxy -> Logging interceptor -> Security interceptor
       -> Performance interceptor -> Target method

    When the target method completes, execution unwinds in reverse order, and the proxy returns the result to the caller. This behaves like nested method calls: Logging(Security(Performance(Target method))). Each interceptor gets an opportunity to run code before continuing the chain and after the chain returns.

    A common beginner interpretation is that proceed() directly calls the target method. That is not always precise. proceed() means: continue to the next interceptor in the current chain. If another interceptor still remains, that interceptor runs next. Only the final proceed() in the chain reaches the target method:

    First around advice -> proceed() -> Second around advice
   -> proceed() -> Third around advice -> proceed() -> Target method

    An @Around advice controls whether the chain continues. If it does not call proceed():

    @Around("execution(* com.coderarmy..*(..))")
public Object intercept(ProceedingJoinPoint joinPoint) {
    return "Blocked";
}

    then the target method is not executed, remaining interceptors are not invoked, and the advice directly returns its own value. Therefore @Around is the most powerful advice type.

    Idea Precise meaning
    proceed() Continue to the next interceptor in the current chain
    Last proceed() Reaches the target method
    Skipping proceed() Short-circuits the rest of the chain, including the target
    @Around power Runs before and after, and can choose not to proceed
    Return value Flows back out through the chain to the caller

    Interviewer's perspective: "Does proceed() call the target?" The precise answer is no - it advances the chain, and only the final advance reaches the target. That wording is what separates a real AOP mental model from a summary.

    13. Controlling Aspect Order with @Order

    When multiple aspects match the same method, @Order controls their precedence. Given SecurityAspect with @Order(1), LoggingAspect with @Order(2), and PerformanceAspect with @Order(3):

    The fundamental rule is: a lower order value has higher precedence. Execution enters the aspects in ascending order and returns in reverse:

    SecurityAspect(1) -> LoggingAspect(2) -> PerformanceAspect(3) -> Target method
Target method -> PerformanceAspect completes -> LoggingAspect completes -> SecurityAspect completes

    Another way to visualize it is Security(Logging(Performance(Target method))). The lower order value forms the outer layer of the interceptor chain.

    Aspect @Order value Layer
    Security 1 Outermost (enters first, exits last)
    Logging 2 Middle
    Performance 3 Innermost (closest to the target)

    Important: Lower number equals higher precedence. The lowest-order aspect wraps everything else and unwinds last.

    14. Important Proxy-Based AOP Boundaries

    Custom annotation-based AOP works only when the method call passes through the Spring AOP proxy.

    • The object must be managed by Spring. A manually created object is not automatically proxied:
    • ReportService service = new ReportService();
    • calling an annotated method on it bypasses Spring AOP; obtain the bean through dependency injection instead.
    • Self-invocation bypasses the proxy. If generateAllReports() calls generateAnnualReport() using this:
    • the call stays inside the target object;
    • it does not return to the proxy, so the advice is not applied to that internal call.
    • Private methods are not suitable join points. Spring AOP intercepts calls through proxies:
    • private methods cannot be overridden or exposed through a proxy in the required way.

    Custom AOP annotations should therefore normally be applied to externally invoked, non-private methods on Spring-managed beans.

    Boundary Does the advice run? Why
    External call, Spring-managed bean Yes The call passes through the proxy
    new ReportService() then call No The object was never proxied by Spring
    Self-invocation via this No The internal call does not re-enter the proxy
    Private method No Proxies cannot intercept private methods
    Final method No A proxy cannot override a final method

    Golden rule: No proxy, no advice. If the call does not pass through the proxy, annotation-based AOP silently does nothing.

    15. Complete Mental Model

    During application startup:

    • Spring reads bean definitions;
    • creates target objects;
    • injects dependencies;
    • runs initialization callbacks;
    • lets the AOP infrastructure check available advisors;
    • creates proxies for eligible beans;
    • stores and injects the final proxy references.

    During method execution:

    • the caller invokes a method;
    • the call reaches the proxy;
    • the proxy finds matching interceptors;
    • the interceptor chain begins;
    • around advice calls proceed();
    • the target executes;
    • the chain unwinds in reverse order;
    • the result or exception returns to the caller.

    Responsibility of each part:

    Part Responsibility
    Custom annotation Declares the required behaviour
    Pointcut expression Selects methods carrying that annotation
    Advice Implements the cross-cutting behaviour
    AOP proxy Intercepts method calls
    BeanPostProcessor infrastructure Creates and exposes the proxy during bean creation
    ProceedingJoinPoint.proceed() Continues the interceptor chain

    Interviewer's perspective: The complete answer to "how does annotation-based AOP work?" walks both timelines: startup (target to proxy) and execution (proxy to interceptor chain to target and back).

    16. Myth vs Reality

    Myth Reality
    "An annotation executes code by itself" An annotation is metadata; a detector and an actor are required
    "A custom annotation works without @Retention(RUNTIME)" Only RUNTIME retention is reliably visible to Spring at run time
    "@Documented affects AOP matching" It only affects generated Javadoc, not proxies or matching
    "@annotation(TypeName) also passes the annotation instance" Type matching only tests presence; binding @annotation(varName) injects the instance
    "Advice runs while the bean is being created" The proxy is created during bean creation; advice runs later, on method invocation
    "proceed() always calls the target method" It advances the chain; only the final proceed() reaches the target
    "Self-invocation still triggers the advice" A call through this never re-enters the proxy, so the advice is skipped
    "Private methods can be advised by Spring AOP" Proxy-based AOP cannot intercept private methods

    17. Common Trap Questions

    Trap 1 - "Does the annotation do the timing by itself?" Verdict: False. The annotation is metadata; the aspect detects, reads, and implements the behaviour.

    Trap 2 - "Is @Target(ElementType.METHOD) enough for Spring AOP?" Verdict: No. @Target controls where it may appear; @Retention(RetentionPolicy.RUNTIME) is also required so Spring can read it at run time.

    Trap 3 - "Does @annotation(com...TrackExecutionTime) give the advice the annotation object?" Verdict: False. That is type matching. To read properties you need binding, @annotation(trackExecutionTime), with a matching advice parameter.

    Trap 4 - "Does proceed() call the target method directly?" Verdict: Not always. It continues to the next interceptor; the target runs only after the final proceed() in the chain.

    Trap 5 - "Will an internal this.generateAnnualReport() call trigger the advice?" Verdict: False. Self-invocation stays inside the target object and never passes through the proxy.

    Trap 6 - "Does @Order(3) run before @Order(1)?" Verdict: False. Lower values have higher precedence, so @Order(1) is the outer layer and runs first.

    Trap 7 - "Is a manually created new ReportService() proxied?" Verdict: False. Only Spring-managed beans receive proxies; obtain the bean through dependency injection.

    18. Points to Remember

    1. A custom annotation is metadata; it has no behaviour by itself and needs a detector plus an actor.
    2. Declare a custom annotation with public @interface, never the normal interface keyword.
    3. Elements are declared like parameterless methods; default values make them optional.
    4. @Target controls where an annotation may be used; @Retention(RUNTIME) keeps it available for Spring at runtime.
    5. @Documented affects generated documentation, not AOP behaviour.
    6. A marker annotation only declares that behaviour is required; annotation properties can pass configuration to an aspect.
    7. @annotation(TypeName) matches an annotation by type; @annotation(variableName) also binds the annotation instance to an advice parameter.
    8. Spring AOP uses bean post-processing infrastructure to create proxies for eligible beans, and the container stores and injects the final proxy reference.
    9. A method call must pass through the proxy for advice to execute; self-invocation and private methods are important limitations of proxy-based Spring AOP.
    10. Multiple interceptors execute as a nested chain and unwind in reverse order; proceed() continues the chain rather than always calling the target, and a lower @Order value gives an aspect higher precedence.

    19. Likely Interview Questions

    Question Crisp Answer
    What does a custom annotation actually do? Nothing by itself; it is metadata. A component such as an aspect must detect it, read it, and act on it.
    Why is @Retention(RUNTIME) needed for AOP? Spring reads annotations at run time through reflection; without runtime retention the annotation is unavailable.
    What is the default retention policy? RetentionPolicy.CLASS is the default when @Retention is not specified.
    What does @Target(ElementType.METHOD) do? Restricts the annotation to methods; placing it on a class becomes a compile error.
    Marker annotation vs configured annotation? A marker has no properties; a configured annotation carries elements the aspect can read.
    What does the @annotation() designator match? Methods that carry the specified annotation on the method being executed.
    Type matching vs annotation binding? Type matching only tests presence; binding injects the annotation instance so advice can read its properties.
    Where does Spring AOP create proxies? During bean creation, in the post-processing stage after initialization callbacks, via the AOP auto-proxy creator.
    What is a BeanPostProcessor? A Spring extension point that can inspect or modify beans before they are exposed, including returning a proxy instead of the bean.
    What does proceed() mean? Continue to the next interceptor in the chain; only the final proceed() reaches the target method.
    How do you order multiple aspects? Use @Order(n); a lower value has higher precedence and forms the outer layer of the chain.
    Why does self-invocation bypass advice? The call through this stays inside the target object and never passes through the proxy.

    20. Final Summary

    Business method declares intent:  @TrackExecutionTime (metadata only)
        |
        v
Aspect implements behaviour:     @Around("@annotation(trackExecutionTime)")
        |
        v
Pointcut designator:             type matching (presence) vs binding (instance)
        |
        v
Bean lifecycle:                  read definition -> instantiate -> inject -> Aware
                                 -> postProcessBeforeInit -> init callbacks
                                 -> postProcessAfterInit (AOP wraps here) -> store
        |
        v
Proxy decision:                  does any advisor match this bean?
                                 no  -> original bean
                                 yes -> proxy wrapping the target
        |
        v
Container stores and injects:    the proxy, not the raw target
        |
        v
Runtime call:                    caller -> proxy -> interceptor chain -> proceed()
                                 -> target -> unwind in reverse -> result/exception
        |
        v
Aspect order:                    lower @Order value = outer layer = higher precedence
        |
        v
Boundaries:                      self-invocation, private/final methods, new objects
                                 all bypass the proxy -> advice does not run
    • Custom annotation -> declares the "what"; the aspect supplies the "how".
    • An annotation is inert metadata: detect it, read it, act on it.
    • @interface plus @Target plus @Retention(RUNTIME) (and @Documented) makes it usable.
    • Marker annotation answers "whether"; configured annotation answers "with what settings".
    • @annotation(TypeName) matches by type; @annotation(varName) binds the instance to advice.
    • Spring AOP proxies eligible beans during bean post-processing; the container injects the proxy.
    • proceed() advances the interceptor chain; only the final call reaches the target.
    • Lower @Order value wins; the chain unwinds in reverse order.
    • No proxy, no advice: self-invocation and private methods silently skip the aspect.

    One-line takeaway: A custom annotation is just a declarative label, and the whole trick of annotation-driven Spring AOP is that the container quietly wraps an eligible bean in a proxy during post-processing, so a method call - not the annotation itself - is what makes the aspect run.
