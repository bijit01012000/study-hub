    Lecture 13 — Spring Boot CRUD Project with Soft Delete

    20 sections · 3,691 words

    Lecture 13

    Scope evidence: "Spring Boot CRUD Project with Soft Delete | Spring JPA custom Methods" (playlist map, verified). The repo keeps the same crudSpringBootDemo project (classes CrudSpringBootDemoApplication, controller.StudentController, service.StudentService, repository.StudentRepository, entity.Student, plus src/main/resources/application.properties and pom.xml) now extended with an is_deleted column and custom repository finder methods.

    So far our CRUD API removed a student by deleting the row. Real applications rarely destroy data; they hide it. This lecture turns the hard delete into a soft delete: a new isDeleted field, a PATCH endpoint that flips it, and custom Spring Data JPA finder methods that keep the hidden rows out of normal reads. The whole lecture is a small, careful extension of the same project, so the code stays familiar and the design reasoning can take center stage.

    1. What Is Soft Delete?

    In hard delete, we permanently remove the row from the database. Once gone, the row is gone: it cannot be restored, and any historical reference to it breaks.

    DELETE /api/students/1

    In soft delete, we do not actually delete the row. Instead, we only update one field:

    isDeleted = true

    So the student record still remains in the database, but it is marked as deleted. The row is physically present; the application simply agrees to treat it as gone.

    The difference is entirely in who enforces the deletion. In hard delete the database enforces it: the row is absent, so every query agrees. In soft delete the application enforces it: the row is present, so every query that should ignore deleted students must say so explicitly.

    Why would a system choose this? Because the data still has value: an audit trail, a possible undo, foreign-key references from other tables, or a reporting history. Soft delete keeps that value while hiding the record from ordinary users.

    Important: Soft delete is a change of state, not a removal. The row survives; only the meaning of the row changes.

    2. Why PATCH Is the Right Verb for Soft Delete

    Because we are only changing one specific field, soft delete is technically a partial update.

    That single sentence decides the HTTP method:

    partial update  ->  PATCH

    A full replacement would need every field of the resource; we are touching exactly one column, so PATCH describes the operation honestly. The endpoint keeps the student id in the path and names the action explicitly:

    PATCH /api/students/1/soft-delete

    Naming soft-delete in the path makes the intent obvious to any reader of the API and keeps it distinct from a normal PATCH that updates a student's profile fields.

    Interviewer's perspective: The expected reasoning is "one field changes, therefore it is a partial update, therefore PATCH." An answer that says "we use PATCH because it feels right" gives no design principle; the partial-update argument is the one that scores.

    3. PATCH vs DELETE

    The two operations differ in intent and in method. This is the table to memorize:

    Operation What happens? HTTP Method
    Hard Delete Row is permanently removed from the database DELETE
    Soft Delete Row remains in the database, but isDeleted becomes true PATCH

    So for hard delete:

    DELETE /api/students/1

    For soft delete:

    PATCH /api/students/1/soft-delete

    The method is not decoration; it is a contract. A caller who sees DELETE expects the resource to stop existing. A caller who sees PATCH expects a modified resource that can still be fetched, at least by an administrator or an audit query.

    Put differently, the endpoint's method should match what the database will actually do. A soft delete runs an UPDATE, so exposing it as PATCH tells the truth; exposing it as DELETE would promise a removal that never happens.

    Mnemonic: PATCH the flag, DELETE the row. One flips a boolean; the other removes a tuple.

    4. Hard Delete vs Soft Delete

    The same design choice seen from the data's point of view:

    Aspect Hard Delete Soft Delete
    Row in database Permanently removed Still present
    Recoverable No Yes, by setting isDeleted = false
    HTTP method DELETE PATCH
    Storage cost Freed Retained
    Normal reads Row disappears naturally Row must be filtered out manually
    Audit / history Lost Preserved
    SQL effect DELETE FROM students ... UPDATE students SET is_deleted = true ...

    The catch is hidden in the "normal reads" row: with hard delete, a naive findAll() is automatically correct. With soft delete, every read path must now decide what to do with the hidden rows.

    Golden rule: Soft delete moves the deletion decision from the database into your query layer. The row is still there, so your reads must be deliberate about excluding it.

    5. Adding the isDeleted Field to the Entity

    When we use soft delete, our table contains a column like this:

    is_deleted

    In the Java entity class, we represent it like this:

    @Column(name = "is_deleted")
private Boolean isDeleted = false;

    Two details matter here:

    1. The field is named isDeleted in Java but maps to is_deleted in the database through @Column(name = "is_deleted"). The two conventions meet cleanly without renaming anything in SQL.
    2. The default value is false, which means the student is active and not deleted. Every newly created student is therefore visible by default, which is exactly the behavior we want.

    When a student is soft deleted, we update this value to:

    isDeleted = true;

    Important: The default is part of the design. Because isDeleted starts false, no old insert statement needs to know about soft delete; only the delete path changes.

    6. The Problem with findAll()

    Normally, when we fetch all students, we may use:

    studentRepository.findAll();

    But there is a problem: findAll() fetches every row from the database, including soft-deleted records.

    Consider this table:

    id name is_deleted
    1 Rahul false
    2 Priya true
    3 Aman false

    If we use findAll(), it may return all three students, including the soft-deleted Priya. But in normal application behavior, soft-deleted students should not be shown. So we only want records where:

    isDeleted = false

    In SQL, the query would look like this:

    SELECT * FROM students
WHERE is_deleted = false;

    The lesson is general: an ORM method does exactly what its name says. findAll() means "all rows," not "all rows the user is allowed to see." Filtering is our responsibility.

    The same leak appears wherever the old hard-delete assumptions survive:

    Call site Under hard delete Under soft delete
    List all findAll() is correct Returns hidden rows too
    Get one findById(id) is correct Returns a hidden row if present
    Existence checks Row absent means deleted Row present but flagged deleted
    Counts and reports Naturally exclude deleted Include deleted rows

    Every one of these reads must now choose a side: show everything (admin or audit) or show only active students (normal APIs). The default inherited behavior is "show everything," which is almost never what a user-facing endpoint wants.

    Important: Soft delete does not change findAll(); it changes the meaning of the rows findAll() returns. The fix belongs in the query methods, not in the database.

    7. Custom Finder Methods: findByIsDeletedFalse()

    Spring Data JPA allows us to create queries by simply writing method names. Instead of writing SQL manually, we can create this method inside the repository:

    List<Student> findByIsDeletedFalse();

    Spring Data JPA reads the method name and automatically generates the required query. This method means:

    Find all students where isDeleted is false.

    This type of method is called a derived query method: the query is derived from the method name, not written by hand. The equivalent SQL idea is:

    SELECT * FROM students
WHERE is_deleted = false;

    That is the entire trick. No @Query, no SQL string, no XML; a correctly spelled method name is the query.

    8. Normal findAll() vs Custom Filtered Finder

    The two reads look almost identical at the call site, but they return different worlds:

    Aspect findAll() findByIsDeletedFalse()
    Returns Every row, including soft-deleted Only active rows (isDeleted = false)
    Query written by Spring Data JPA Spring Data JPA (from the name)
    Filter condition None is_deleted = false
    Good for Admin/audit views that must see everything Normal user-facing lists
    Risk Leaks hidden records Hides records that callers might legitimately need

    The design decision is not "which is better" but "which read path is this." A student list endpoint should use the filtered finder; an internal audit tool may deliberately use findAll().

    Interviewer's perspective: Expect the question "why not just override findAll()?" The answer: derived finders keep both behaviors available and explicit; silently changing findAll() would hide rows from code that genuinely needs them.

    9. How the Derived Query Name Works

    Every derived finder is read in parts. For:

    List<Student> findByIsDeletedFalse();

    the breakdown is:

    Part Meaning
    findBy Query starts here
    IsDeleted Entity field name
    False Condition should be false

    So Spring understands the method as: find students where isDeleted is false.

    This works because Spring Data JPA follows naming conventions. It reads the method name, identifies the field, understands the condition, and creates the query automatically.

    Mnemonic for any derived finder: A-F-C - Action (findBy), Field (IsDeleted), Condition (False). Spell the three parts and the query writes itself.

    10. Why findByIdAndIsDeletedFalse()

    For getting a student by ID, we may normally write:

    studentRepository.findById(id);

    But this can create an issue when soft delete is used. Suppose a student exists in the database but is already soft deleted:

    id name is_deleted
    1 Rahul true

    If we use findById(1L), it will still return Rahul because the row still exists in the database. But from the application's point of view, a soft-deleted student should behave like an inactive or hidden record. So for normal get-by-id APIs, we should fetch only students that are not deleted.

    For that, we create this repository method:

    Optional<Student> findByIdAndIsDeletedFalse(Long id);

    This means: find student where id = given id AND isDeleted = false.

    The equivalent SQL idea is:

    SELECT * FROM students
WHERE id = 1
AND is_deleted = false;

    Its breakdown follows the same grammar as before:

    Part Meaning
    findBy Query starts here
    Id Match the student ID
    And Add another condition
    IsDeleted Check the isDeleted field
    False Value should be false

    So Spring Data JPA understands: find a student where id matches and isDeleted is false. The same findById() that was always correct under hard delete silently returns hidden rows under soft delete; the filtered finder restores the expected behavior.

    11. Final Repository Interface

    Inside the repository interface, we can add both derived methods:

    public interface StudentRepository extends JpaRepository<Student, Long> {
    List<Student> findByIsDeletedFalse();
    Optional<Student> findByIdAndIsDeletedFalse(Long id);
}

    Now we can use findByIsDeletedFalse() to fetch all active students. And findByIdAndIsDeletedFalse(id) to fetch one active student by ID.

    Notice what did not change: the repository still extends JpaRepository<Student, Long>, so all the inherited CRUD methods remain available. The two new methods sit alongside them; nothing is replaced.

    It is worth noting that no @Query and no hand-written SQL appear here. Both filters are simple equality checks on a single field, and that is exactly the shape derived query methods handle best: Spring Data JPA parses the name and builds the query for us. Reach for @Query only when the condition is complex enough that a method name could not express it cleanly; for soft delete, the naming convention is sufficient.

    Important: Derived methods do not remove the inherited ones. findAll() and findById() still exist and still see soft-deleted rows, which is precisely why the new methods are needed.

    12. Service and Controller Changes

    The soft delete operation itself is small: instead of deleting the row permanently with studentRepository.deleteById(id), we first fetch the student, then update the field.

    public void softDeleteStudent(Long id) {
    Student student = studentRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("Student not found"));
    student.setIsDeleted(true);
    studentRepository.save(student);
}

    The controller exposes that service call under the soft-delete path:

    @PatchMapping("/{id}/soft-delete")
public ResponseEntity<String> softDeleteStudent(@PathVariable Long id) {
    studentService.softDeleteStudent(id);
    return ResponseEntity.ok("Student soft deleted");
}

    The read endpoints change in the same spirit: a "get all" endpoint now calls findByIsDeletedFalse() instead of findAll(), and a "get by id" endpoint calls findByIdAndIsDeletedFalse(id) instead of findById(id). The controller signatures stay the same; only the repository method behind the service changes.

    public List<Student> getAllStudents() {
    return studentRepository.findByIsDeletedFalse();
}

public Student getStudentById(Long id) {
    return studentRepository.findByIdAndIsDeletedFalse(id)
            .orElseThrow(() -> new RuntimeException("Student not found"));
}

    This is the quiet part of the feature: the write path adds one boolean update, but the read path must be revisited in every place that expected a missing row to be impossible. Miss a read path and a soft-deleted student reappears in the UI.

    Interviewer's perspective: A strong answer separates the layers: repository owns the query methods, service owns the state transition (setIsDeleted(true) plus save), controller owns the HTTP verb and path. Mixing entity mutation into the controller is a common red flag.

    13. Keeping Hard Delete as an Option

    Soft delete does not have to abolish hard delete; the two can coexist. The original hard-delete endpoint stays available for the cases that genuinely need permanent removal:

    DELETE /api/students/1

    Both operations now live in the same project:

    Goal Method and path Repository call
    Remove forever DELETE /api/students/1 deleteById(id)
    Hide but keep PATCH /api/students/1/soft-delete fetch, setIsDeleted(true), save

    This is a common real-world arrangement: user-facing "delete" is soft, while an admin purge or a data-retention job performs the hard delete. Keeping both is a design decision, not a contradiction.

    The important thing is that the method matches the intent at each endpoint. A single DELETE route that only flips a flag teaches every client the wrong model of the system; a PATCH soft-delete route plus a separate admin DELETE keeps both meanings honest.

    Important: DELETE is suitable when the row is actually removed from the database. Reserve it for that meaning; using DELETE to hide a row confuses every caller who reads the method.

    14. The Complete Soft Delete Flow

    Putting the whole path together, replacing the old hard delete:

    OLD (hard delete):
DELETE /api/students/1
-> service.deleteStudent(id)
-> studentRepository.deleteById(id)
-> row permanently removed

NEW (soft delete):
PATCH /api/students/1/soft-delete
-> service.softDeleteStudent(id)
-> studentRepository.findById(id)          (locate the active row)
-> student.setIsDeleted(true)
-> studentRepository.save(student)         (UPDATE, not DELETE)
-> row remains, is_deleted = true

READ path afterwards:
GET /api/students
-> studentRepository.findByIsDeletedFalse()      (hidden rows excluded)

GET /api/students/1
-> studentRepository.findByIdAndIsDeletedFalse(1) (hidden row treated as absent)

    So the row remains in the database, but it becomes hidden from normal APIs. The only three moving parts are the new column, the two derived finders, and the one state transition in the service.

    Read the flow top to bottom and notice that nothing was destroyed. The write path changed from a DELETE to an UPDATE, and the read path gained a filter. Because the data is still there, the same design leaves a restore path open: setting isDeleted back to false and saving makes the student visible again without any special "undo" storage.

    15. Myth vs Reality

    Myth Reality
    "Soft delete removes the row." The row stays; only isDeleted becomes true. Nothing is deleted physically.
    "Soft delete should use DELETE." Only one field changes, so it is a partial update; PATCH is the honest method.
    "findAll() returns only active students." findAll() returns every row, including soft-deleted ones; filtering is your job.
    "findById(id) is safe with soft delete." It still returns a soft-deleted row because the row exists; use findByIdAndIsDeletedFalse(id).
    "Derived query methods need custom SQL." The query is generated from the method name; findByIsDeletedFalse() is enough.
    "Soft delete replaces hard delete everywhere." Both can coexist: soft for users, hard for admin purge or retention jobs.
    "Soft-deleted records are gone from the database." They are hidden from normal reads only; they remain fully queryable if you ask for them.

    16. Common Trap Questions

    Trap 1 - "Soft delete removes the row from the database." Verdict: False. Soft delete means marking a record as deleted instead of removing it permanently; the row remains and isDeleted becomes true.

    Trap 2 - "Soft delete is a DELETE operation because the word delete appears." Verdict: False. It updates one specific field, which makes it a partial update, so PATCH is the suitable HTTP method.

    Trap 3 - "findAll() is fine after adding soft delete." Verdict: False. findAll() fetches every row, including soft-deleted records. Use findByIsDeletedFalse() for normal user-facing lists.

    Trap 4 - "findById(id) will not return a soft-deleted student." Verdict: False. The row still exists, so findById(1L) returns it. Normal get-by-id APIs should use findByIdAndIsDeletedFalse(id).

    Trap 5 - "findByIsDeletedFalse() needs a hand-written @Query." Verdict: False. It is a derived query method; Spring Data JPA reads findBy + field + condition and generates the query automatically.

    Trap 6 - "Adding the filtered finders removes findAll() and findById()." Verdict: False. The repository still extends JpaRepository, so the inherited methods remain; the new methods simply give explicit filtered alternatives.

    Trap 7 - "A soft-deleted student can never come back." Verdict: False. Because the row is preserved, restoring it is just setting isDeleted = false again; the data was never destroyed.

    17. Points to Remember

    1. Soft delete means marking a record as deleted instead of removing it permanently.
    2. In soft delete, we usually update a field like isDeleted.
    3. Because only one field is updated, PATCH is a suitable HTTP method; DELETE is for actual removal.
    4. The endpoint pattern is PATCH /api/students/{id}/soft-delete.
    5. The entity field is @Column(name = "is_deleted") private Boolean isDeleted = false; with false meaning active.
    6. findAll() may return soft-deleted records too; it does not filter them.
    7. To fetch only active records, use custom finder methods such as findByIsDeletedFalse().
    8. For a single active record by id, use findByIdAndIsDeletedFalse(id).
    9. Spring Data JPA can generate queries automatically from method names; these are called derived query methods.
    10. Soft-deleted records should usually be hidden from normal get APIs but can be kept as an option alongside hard delete.

    18. Likely Interview Questions

    Question Crisp Answer
    What is soft delete? Marking a record as deleted instead of removing it permanently, usually by setting an isDeleted flag to true.
    Why use PATCH for soft delete? Only one field changes, so it is a partial update, and PATCH is the HTTP method for partial updates.
    PATCH vs DELETE? PATCH updates part of a resource (soft delete); DELETE removes the resource permanently (hard delete).
    How do you add the field to the entity? @Column(name = "is_deleted") private Boolean isDeleted = false;, defaulting to active.
    What is the problem with findAll()? It returns every row, including soft-deleted ones, so hidden records leak into normal list APIs.
    How do you fetch only active students? Use the derived method findByIsDeletedFalse(), equivalent to SELECT * FROM students WHERE is_deleted = false.
    What is a derived query method? A repository method whose query Spring Data JPA generates from the method name, such as findByIsDeletedFalse().
    Why findByIdAndIsDeletedFalse(id)? findById(id) returns soft-deleted rows; the filtered method returns a student only when the id matches and isDeleted is false.
    What does findByIsDeletedFalse() mean? Find all students where isDeleted is false, i.e. all active students.
    What happens in the database during soft delete? An UPDATE sets is_deleted = true; the row is not removed, unlike hard delete's DELETE.
    Can hard and soft delete coexist? Yes; keep DELETE for permanent removal and PATCH soft-delete for hiding, choosing per endpoint.
    Can a soft-deleted record be restored? Yes; the row still exists, so setting isDeleted back to false makes it visible again.
