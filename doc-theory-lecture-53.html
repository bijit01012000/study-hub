    Java Locks | ReentrantLock, ReadWriteLock, StampedLock, Semaphore & Condition

    20 sections · 5,729 words

    Lecture 53

    Scope evidence: "Java Locks | ReentrantLock, ReadWriteLock, StampedLock, Semaphore & Condition" plus the lecture's own repo notes (java.util.concurrent.locks: Lock, ReentrantLock, ReentrantReadWriteLock), playlist map, verified. Repo evidence: 3 Demo files.

    The synchronized keyword is often enough for protecting a critical section: it automatically acquires an intrinsic lock on entry and releases it on exit, even when an exception is thrown. Java also provides explicit locking utilities in java.util.concurrent.locks, and those APIs matter when an application needs more control over acquisition, interruption, timeouts, fairness, multiple waiting conditions, or read-heavy access patterns. This lecture covers the Lock interface, ReentrantLock, ReadWriteLock and ReentrantReadWriteLock, StampedLock, Semaphore, and Condition, and ends by choosing the simplest tool that matches the shared-state rule.

    1. Why Go Beyond synchronized

    A synchronized block is simple and safe, and the JVM handles lock release automatically even if the block throws an exception. However, intrinsic locks do not directly provide some forms of control.

    • 1.1 No immediate try-and-fallback operation. There is no direct equivalent of "try once; if the lock is unavailable, do fallback work." With synchronized, a thread waits until the monitor becomes available. Explicit locks provide tryLock() for this purpose.
    • 1.2 No timed lock acquisition. A synchronized block cannot directly express "wait for the lock for at most two seconds; if it is still unavailable, stop waiting." Lock.tryLock(timeout, unit) supports timed acquisition.
    • 1.3 Lock acquisition is not interruptible. A thread waiting to enter a synchronized block cannot use a dedicated interruptible lock-acquisition method. The Lock interface provides lock.lockInterruptibly(), which lets a waiting thread respond to interruption.
    • 1.4 No configurable fairness. Intrinsic locks do not expose a fairness policy. Some explicit-lock implementations can be created in fair mode, which generally favours threads that have waited longer. Fairness can improve predictability but usually reduces throughput.
    • 1.5 Only one monitor wait set. With intrinsic locking, wait(), notify() and notifyAll() operate on the monitor's single wait set. A Lock can create multiple Condition objects (Condition notEmpty = lock.newCondition();), allowing different groups of threads to wait for different state predicates.

    Important synchronized is not weak; it is limited. Every gap above is a genuine capability, not a defect. Use an explicit lock only when one of these five gaps is actually the problem.

    2. The Lock Interface and the finally Pattern

    The Lock interface belongs to java.util.concurrent.locks.Lock and separates lock acquisition and release into explicit method calls. A Lock implementation provides synchronization semantics similar to monitor locking, but with additional capabilities.

    Method Signature Purpose
    lock() void lock() Acquires the lock, blocking if another thread holds it
    lockInterruptibly() void lockInterruptibly() throws InterruptedException Blocking acquisition that can be interrupted
    tryLock() boolean tryLock() Immediate, non-blocking acquisition attempt
    tryLock(time, unit) boolean tryLock(long time, TimeUnit unit) throws InterruptedException Timed acquisition attempt
    unlock() void unlock() Releases the lock
    newCondition() Condition newCondition() Creates a Condition bound to this lock

    The basic locking pattern is:

    Lock lock = new ReentrantLock();

lock.lock();
try {
    // critical section
} finally {
    lock.unlock();
}

    The finally block is essential. If an exception occurs and unlock() is skipped, the lock can remain held indefinitely. Acquire the lock before entering try, and release it in finally. Do not place lock.lock() inside the try block unless the code is carefully structured: if acquisition itself fails before the lock is obtained, finally must not call unlock().

    Golden rule lock() goes immediately before try; unlock() goes immediately inside finally. This pairing is the entire safety contract of explicit locking.

    3. ReentrantLock and Reentrancy

    ReentrantLock is the most commonly used implementation of the Lock interface. It provides mutual exclusion, reentrancy, immediate lock attempts, interruptible acquisition, timed lock attempts, condition variables, diagnostic methods, and optional fairness.

    A reentrant lock allows the thread that already owns the lock to acquire it again without blocking itself. The lock maintains, conceptually, an owner thread plus a hold count: lock.lock(); lock.lock(); takes the count to 1 and then 2, and each unlock() decrements it (2 → 1 → 0). The lock becomes available to another thread only when the hold count reaches zero.

    Reentrancy is necessary because one lock-protected method often calls another that uses the same lock. In the lecture's BankAccount example, deposit() acquires the lock and then calls validateAmount(), which acquires the same lock again. Because the lock is reentrant, the thread does not deadlock with itself. In real code a private validation method may not need to acquire the lock independently; the example demonstrates that independently synchronized methods can safely call one another when they use the same reentrant lock.

    // Demo.java — ReentrantLock: mutual exclusion, reentrancy and tryLock
import java.util.concurrent.locks.ReentrantLock;

class Counter {
    private int count;
    private final ReentrantLock lock = new ReentrantLock();

    public void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();
        }
    }

    public boolean tryIncrement() {
        if (lock.tryLock()) {
            try {
                count++;
                return true;
            } finally {
                lock.unlock();
            }
        }
        return false; // lock was unavailable: fallback path
    }
}

public class Demo {
    public static void main(String[] args) {
        Counter counter = new Counter();
        counter.increment();

        ReentrantLock lock = new ReentrantLock();
        lock.lock();
        lock.lock();
        System.out.println("hold count = " + lock.getHoldCount()); // 2
        lock.unlock();
        lock.unlock();
        System.out.println("tryIncrement = " + counter.tryIncrement());
    }
}

    Intrinsic monitors are reentrant too: a public synchronized void methodA() that calls methodB(), also synchronized, lets the same thread enter both. ReentrantLock is therefore not useful merely because it is reentrant. Its main advantage is the additional acquisition, fairness and condition-management APIs.

    Memory aid The hold count is a per-thread depth counter: lock twice, unlock twice. The lock is free only at depth zero.

    4. ReentrantLock Methods: lock, unlock, tryLock, Timeout and Interruption

    lock() acquires the lock if available; otherwise the current thread waits. unlock() releases the lock. Only the thread that currently owns a ReentrantLock may release it, and every successful acquisition must have a matching release. Calling unlock() without owning the lock throws IllegalMonitorStateException. A double acquisition followed by a single unlock() leaves the lock still held; the second unlock() fully releases it. Avoid defensive patterns that silently unlock whenever isHeldByCurrentThread() returns true; balanced acquisition and release should be clear from the code structure.

    tryLock() attempts to acquire the lock immediately and returns true if the lock was acquired, false if it was unavailable. This is useful when waiting would be more expensive than using an alternative path.

    if (lock.tryLock()) {
    try {
        performCriticalWork();
    } finally {
        lock.unlock();
    }
} else {
    performFallbackWork();
}

    Timed tryLock() waits for up to the requested time with lock.tryLock(2, TimeUnit.SECONDS). It has three outcomes: the lock becomes available in time and returns true; the timeout expires and returns false; the waiting thread is interrupted and InterruptedException is thrown. lockInterruptibly() is like lock() except the waiting thread may respond to interruption, which is useful for cancellable tasks and shutdown-sensitive systems. Both blocking forms should be wrapped so that a caught InterruptedException restores the interrupt status with Thread.currentThread().interrupt(), so the cancellation request is not swallowed.

    Important lock() before try; unlock() in finally. When catching InterruptedException, restore the interrupt flag rather than swallowing the signal.

    5. ReentrantLock Diagnostics, Fairness and Queue Methods

    ReentrantLock exposes several observation-only methods:

    • isLocked() reports whether any thread currently holds the lock. It is mainly useful for monitoring, testing and diagnostics. Do not use it for check-then-act business logic, because the observed state can change immediately.
    • isHeldByCurrentThread() checks whether the current thread owns the lock. It is useful for assertions, diagnostic helpers and validating internal lock requirements.
    • getHoldCount() returns the number of times the current thread has acquired the lock without matching releases; it returns zero for a thread that does not own the lock.
    • Queue diagnostics such as hasQueuedThreads(), getQueueLength() and hasQueuedThread(thread) provide estimates or snapshots useful for monitoring. Do not build correctness rules around them, because queue state can change immediately after inspection.

    Use tryLock() when the action depends on actually acquiring the lock, because a check such as if (!lock.isLocked()) can become false before the next statement runs.

    A non-fair lock is the default (new ReentrantLock()); a fair lock is created with new ReentrantLock(true). In a non-fair lock, a newly arriving thread may acquire the lock before threads that have waited longer; this behaviour is called barging, and non-fair locks usually provide better throughput. A fair lock generally favours the longest-waiting thread under contention, giving approximately arrival-order acquisition. Fairness does not mean mathematically strict scheduling order; thread scheduling and untimed tryLock() can still affect the observed order. Use fair locks only when starvation risk or predictable access order matters more than maximum throughput.

    The classic comparison is:

    Capability synchronized ReentrantLock
    Automatic release Yes No (manual, in finally)
    Reentrant Yes Yes
    Immediate try No Yes (tryLock())
    Timed acquisition No Yes
    Interruptible acquisition No dedicated API Yes (lockInterruptibly())
    Configurable fairness No Yes
    Multiple condition queues No Yes
    Simpler syntax Yes No
    Diagnostic APIs Limited More extensive

    Golden rule Use synchronized when its simpler structure is sufficient. Use ReentrantLock when a specific explicit-lock feature is required.

    6. Read-Write Locks: The Problem and the ReadWriteLock Interface

    A normal exclusive lock allows only one thread inside the protected region. That is necessary for writes, but it can be unnecessarily restrictive for read-only access: Reader 1 enters, Reader 2 waits, Reader 3 waits. If several threads only inspect stable data, they may be able to proceed together. Shared-resource operations can often be divided into reads, which observe data without changing protected state, and writes, which modify protected state. The core rule is:

    Access pattern Allowed
    Multiple readers Allowed
    One writer Allowed alone
    Reader with writer Not allowed
    Multiple writers Not allowed

    ReadWriteLock provides two related locks, Lock readLock() and Lock writeLock(). The standard implementation is ReadWriteLock lock = new ReentrantReadWriteLock();, from which lock.readLock() and lock.writeLock() are obtained.

    Important A read-write lock pays off only when reads dominate. If writes are frequent or critical sections are extremely short, the extra bookkeeping reduces throughput rather than improving it.

    7. ReentrantReadWriteLock in Practice

    // Demo2.java — shared reads, exclusive writes
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

class SharedData {
    private int value;
    private final ReadWriteLock lock = new ReentrantReadWriteLock();
    private final Lock readLock = lock.readLock();
    private final Lock writeLock = lock.writeLock();

    public int read() {
        readLock.lock();
        try {
            return value;
        } finally {
            readLock.unlock();
        }
    }

    public void write(int newValue) {
        writeLock.lock();
        try {
            value = newValue;
        } finally {
            writeLock.unlock();
        }
    }
}

public class Demo2 {
    public static void main(String[] args) {
        SharedData data = new SharedData();
        data.write(10);
        System.out.println(data.read());
    }
}

    Several threads can execute read() together, while a thread executing write() receives exclusive access. Read locks are not mainly used to protect readers from other readers; they coordinate readers with writers. Without a read lock, a reader could begin reading several related fields, a writer could modify those fields midway, and the reader could observe an inconsistent combination. A read lock prevents a writer from modifying the protected state until the reader finishes.

    A read-write lock may improve concurrency when reads are much more frequent than writes, read operations take enough time for concurrency to matter, the protected state is shared by many threads, and writes must remain exclusive. Typical examples are in-memory caches, configuration snapshots, read-heavy registries, shared indexes and lookup tables. It may not help when critical sections are extremely short, writes are frequent, contention is low, or lock-management overhead exceeds the benefit. Measure rather than assuming that a read-write lock is faster.

    8. ReadWriteLock Reentrancy, Downgrading, Upgrading, Fairness and Starvation

    Both the read lock and the write lock are reentrant. The write-lock owner can reacquire the write lock, and a thread holding the write lock may also acquire the read lock, which enables lock downgrading.

    Downgrading means changing a write lock into a read lock. The safe sequence is: acquire the write lock, update the state, acquire the read lock while still holding the write lock, release the write lock, continue reading, then release the read lock.

    writeLock.lock();
try {
    value = 100;
    readLock.lock();
    try {
        System.out.println(value);
    } finally {
        readLock.unlock();
    }
} finally {
    writeLock.unlock();
}

    Acquiring the read lock before releasing the write lock prevents another writer from modifying the state in between.

    Upgrading means changing a read lock into a write lock, and a direct upgrade is not supported safely: calling writeLock.lock() while holding readLock creates a deadlock risk, because several threads may all hold read locks and wait for the write lock, which cannot be granted until all read locks are released. The usual approach is: release the read lock, acquire the write lock, recheck the state, and perform the update. The state must be rechecked because another thread may have changed it during the transition.

    A fair read-write lock is created with new ReentrantReadWriteLock(true); the default is non-fair. A continuous flow of readers can delay a waiting writer in some access patterns (writer starvation). Fair mode generally grants access according to waiting order and can reduce starvation risk, but it usually lowers throughput. Fairness is a policy trade-off, not an absolute guarantee about operating-system scheduling.

    Memory aid Downgrading is allowed because the writer still holds the stronger lock; upgrading is forbidden because readers cannot force other readers to let go.

    9. StampedLock: Stamps, Modes and Optimistic Reads

    StampedLock is an advanced synchronization utility designed for read-heavy workloads. It supports three main modes: writeLock(), readLock() and tryOptimisticRead(), and its distinctive feature is optimistic reading. Lock operations return a long stamp, a token representing that particular lock mode and acquisition state, which must be supplied when releasing or converting the lock (long stamp = lock.readLock(); then lock.unlockRead(stamp);). A stamp should not be treated as a simple application version number or thread ID.

    A pessimistic read lock is an ordinary read lock: several read-lock holders may proceed together, and a writer cannot acquire the write lock until pessimistic readers release their stamps. A write lock is exclusive, and no read or write lock can coexist with it. An optimistic read does not acquire a traditional read lock: the reader obtains an optimistic stamp, copies the required fields into local variables, validates the stamp, and falls back to a read lock if validation fails.

    // Demo2.java — optimistic read with validation
import java.util.concurrent.locks.StampedLock;

class Point {
    private double x;
    private double y;
    private final StampedLock lock = new StampedLock();

    public double distanceFromOrigin() {
        long stamp = lock.tryOptimisticRead();
        double currentX = x;
        double currentY = y;
        if (!lock.validate(stamp)) {
            stamp = lock.readLock();
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return Math.sqrt(currentX * currentX + currentY * currentY);
    }
}

    The flow is: assume no writer interferes, read a local snapshot, validate; if valid use the snapshot, and if invalid reread under a read lock. validate(stamp) reports whether a write-lock acquisition invalidated the optimistic observation. Always copy the shared fields before validation; do not repeatedly read the shared fields after validation, because a writer may change them later.

    Important Copy the fields, then validate. Reading the shared fields again after validation reintroduces the race that the optimistic read was designed to avoid.

    10. StampedLock Validation, Non-Reentrancy, Conversion and Comparison

    The purpose of validation becomes clearer when several related fields form one state, as in the Point example: the optimistic read snapshots both x and y, then validates that no writer slipped in between the two copies. Optimistic reads are useful when reads are extremely frequent, writes are rare, reading the state is quick, retrying under a real read lock is inexpensive, and profiling shows ordinary read locking is a bottleneck. They are less useful when writes are frequent, the read operation is long, the object graph is difficult to copy consistently, or implementation simplicity matters more than marginal throughput.

    StampedLock is not reentrant. This is a major difference from ReentrantLock: a second lock.writeLock() while the same thread already holds a write stamp can deadlock, because the lock does not recognise the second acquisition as belonging to an existing owner in the same way a reentrant lock does. Methods using the same StampedLock must be designed carefully to avoid nested reacquisition. StampedLock also has no traditional thread ownership: it primarily manages lock state through stamps rather than monitor-style ownership checks. The stamp returned by acquisition must be preserved and used correctly, and passing an invalid stamp can result in IllegalMonitorStateException. Do not transfer stamps casually between unrelated operations.

    StampedLock can attempt to convert a held mode without fully releasing it using tryConvertToWriteLock(stamp), tryConvertToReadLock(stamp) and tryConvertToOptimisticRead(stamp). In the common pattern, a thread holding a read stamp loops while the state is unset, tries tryConvertToWriteLock(stamp), keeps the new stamp if the conversion succeeds, and otherwise releases the read lock and reacquires a write lock. Conversions are advanced APIs and require careful tracking of the current stamp mode.

    Feature ReentrantReadWriteLock StampedLock
    Multiple readers Yes Yes
    Exclusive writer Yes Yes
    Optimistic reads No Yes
    Reentrant Yes No
    Condition support Write lock supports conditions No condition support
    Lock ownership model Thread-oriented Stamp-oriented
    Simpler to use Yes No
    Best fit General read-heavy protection Specialised, measured read-heavy optimisation

    Golden rule Prefer ReentrantReadWriteLock unless optimistic reads provide a demonstrated benefit. Do not choose StampedLock merely because it is newer.

    11. Semaphore: Permits and Concurrency Limiting

    A Semaphore maintains a number of permits. A thread must acquire a permit before entering the limited region and release it afterward. With three permits, at most three successful acquirers can proceed concurrently; an available permit lets a thread proceed, and no available permit makes it wait.

    // Demo3.java — limit concurrent access to an external service
import java.util.concurrent.Semaphore;

class ExternalServiceClient {
    private final Semaphore permits = new Semaphore(10);

    public String callService() throws InterruptedException {
        permits.acquire();
        try {
            return performRequest();
        } finally {
            permits.release();
        }
    }

    private String performRequest() {
        return "response";
    }
}

    At most ten calls execute inside performRequest() concurrently, while the number of application threads can be much larger than the number of permits.

    acquire() acquires one permit, waiting if none is available. The operation is interruptible and may throw InterruptedException. Multiple permits can be requested with semaphore.acquire(3). release() returns one permit (semaphore.release()) or several (semaphore.release(3)). A semaphore does not track ownership in the same way as a lock: any thread can call release(), and an incorrect extra release can increase the permit count beyond its intended level. Balanced permit management is the application's responsibility, so a permit should be released only if acquisition succeeded.

    A binary semaphore (new Semaphore(1)) has only one permit, so at most one successful acquirer proceeds at a time. This resembles mutual exclusion, but it is not identical to a lock: no owner thread is tracked, another thread may release the permit, reentrancy is not provided, and extra releases can increase permits. Use a Lock for ownership-based mutual exclusion; use a semaphore when the permit model is the actual requirement. A counting semaphore such as new Semaphore(5) allows up to five permits simultaneously and is useful for limiting access to a finite-capacity resource: database connections, external-service concurrency, file-processing slots, limited hardware devices, and bounded parallel tasks. A semaphore limits concurrent access; it is not by itself a requests-per-second rate limiter.

    Immediate acquisition uses semaphore.tryAcquire() and timed acquisition uses semaphore.tryAcquire(2, TimeUnit.SECONDS), allowing fallback logic when capacity is unavailable. The default is non-fair; a fair semaphore is new Semaphore(3, true). Fair mode generally serves queued blocking acquirers in arrival order, but scheduling is not a perfect strict FIFO guarantee and untimed tryAcquire() may barge. Fairness usually reduces throughput.

    Important Semaphore is a concurrency limiter, not a mutex. Releasing without acquiring, or releasing twice, silently corrupts the permit count because no owner is tracked.

    12. Condition Variables: await, signal and Multiple Wait Sets

    A Condition is a waiting mechanism associated with a Lock: Condition condition = lock.newCondition();. It plays a role similar to Object.wait(), Object.notify() and Object.notifyAll(), with corresponding methods await(), signal() and signalAll(). A lock protects a state transition, and a condition allows a thread to wait until the protected state satisfies a particular predicate, such as "queue is not empty", "queue is not full", "account has enough balance", "resource has become available", or "task has completed". The lock and condition work together.

    await() requires the calling thread to hold the associated lock. Conceptually it atomically releases the lock, places the thread in the condition wait set, suspends the thread, and later reacquires the lock before returning. It can throw InterruptedException. The flow is: hold lock, condition not satisfied, await(), release lock and wait, receive signal, compete to reacquire lock, return only after the lock is reacquired.

    signal() requires the current thread to hold the associated lock. It selects one waiting thread, if one exists. The selected thread does not immediately run inside the critical section; it must first reacquire the lock after the signalling thread releases it. signalAll() signals all threads waiting on that condition, and they then compete to reacquire the lock one at a time. Use signalAll() when several different predicates may depend on the same condition, it is difficult to know which waiter can proceed, or missing a relevant waiter would risk indefinite waiting. Use signal() when one waiter is enough and the waiting design is well understood.

    The current thread must hold the lock before calling condition.await(), condition.signal() or condition.signalAll(); otherwise IllegalMonitorStateException is thrown. Always use a condition inside the lock's critical section. A waiting thread must always recheck the predicate in a while loop, never an if, as in while (queue.isEmpty()) { notEmpty.await(); }. Rechecking is required because spurious wakeups are permitted, another thread may consume the state before this thread reacquires the lock, and the signal indicates that state may have changed, not that the predicate is guaranteed to be true. The condition queue is a notification mechanism; the shared-state predicate is the source of truth.

    Memory aid await = wait + release lock + reacquire; signal = nudge one waiter; signalAll = nudge every waiter. The predicate, not the signal, decides whether to proceed.

    13. Bounded Buffer and Condition vs wait/notify

    A major advantage over intrinsic monitor methods is that one lock can have several conditions. Producers wait only on notFull; consumers wait only on notEmpty. This avoids waking unrelated threads unnecessarily.

    // Demo3.java — bounded buffer with two condition queues
import java.util.ArrayDeque;
import java.util.Queue;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

class BoundedBuffer<T> {
    private final Queue<T> queue = new ArrayDeque<>();
    private final int capacity;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    BoundedBuffer(int capacity) {
        this.capacity = capacity;
    }

    public void put(T item) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.size() == capacity) {
                notFull.await();
            }
            queue.add(item);
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.isEmpty()) {
                notEmpty.await();
            }
            T item = queue.remove();
            notFull.signal();
            return item;
        } finally {
            lock.unlock();
        }
    }
}

    The flow: a producer finding the queue full awaits notFull, and a consumer removing an item signals notFull; a consumer finding the queue empty awaits notEmpty, and a producer adding an item signals notEmpty. A condition also provides timed waiting, such as condition.await(2, TimeUnit.SECONDS), plus awaitNanos(...), awaitUntil(...) and awaitUninterruptibly(). Timed waiting is useful when indefinite blocking is unacceptable; awaitUninterruptibly() delays the thread's response to cancellation and should be used carefully. In production, prefer an existing BlockingQueue unless implementing the mechanism for learning or requiring custom behaviour.

    14. Choosing the Correct Tool

    Each tool encodes a different coordination rule:

    • Use synchronized when mutual exclusion is straightforward, no timed or interruptible acquisition is needed, one wait set is sufficient, automatic lock release is valuable, and simpler code is preferable. For many application-level critical sections, synchronized remains the best default.
    • Use ReentrantLock when tryLock() is required, timed acquisition is required, lock acquisition must be interruptible, optional fairness is required, multiple condition queues are needed, or lock diagnostic methods are useful.
    • Use ReentrantReadWriteLock when the workload is read-heavy, reads can safely overlap, writes must be exclusive, optimistic reads are unnecessary, and reentrancy is needed.
    • Use StampedLock when the workload is strongly read-dominated, writes are rare, optimistic reads can be validated cheaply, profiling justifies additional complexity, and reentrancy and conditions are not required. Do not choose it merely because it is newer.
    • Use Semaphore when the goal is to limit concurrent access, several threads may enter simultaneously, access is represented by permits, and ownership-based mutual exclusion is not required.
    • Use Condition when a thread must wait for a state predicate, separate groups of waiters need separate queues, producer-consumer-style coordination is required, and the state is protected by a Lock.

    synchronized Basic mutual exclusion Automatic acquisition and release Monitor owner

    Use higher-level utilities such as BlockingQueue, CountDownLatch or Semaphore when they directly match the problem. Choose the simplest mechanism that accurately represents the shared-state rule; more advanced locks provide additional control, but they also increase the responsibility placed on the programmer.

    15. Myth vs Reality

    Myth Reality
    "ReentrantLock replaces synchronized everywhere." It is an upgrade only when a specific explicit feature is needed; synchronized stays the simplest safe default.
    "A read lock blocks other readers." Read locks are shared: multiple readers proceed together, and the read lock coordinates readers with writers.
    "You can upgrade a read lock to a write lock." Direct upgrading is not supported safely; release the read lock, acquire the write lock, then recheck state.
    "StampedLock is a better ReentrantReadWriteLock." It is faster for validated read-heavy loads but is not reentrant and has no condition support.
    "A semaphore with one permit is a lock." It resembles mutual exclusion but tracks no owner, allows any thread to release, and is not reentrant.

    16. Common Trap Questions

    Trap 1 — Unlock without ownership: "I called lock.unlock() without acquiring. What happens?" IllegalMonitorStateException. Only the owning thread may release a ReentrantLock, and every acquisition needs a matching release.

    Trap 2 — lock() inside try: "I put lock.lock() as the first line inside try and unlock() in finally. Is that safe?" Not generally. If acquisition fails before the lock is obtained, finally still calls unlock() and throws. Acquire before try.

    Trap 3 — isLocked() check-then-act: "I checked !lock.isLocked() before doing the work. Why is that a bug?" The state can change immediately after inspection. Use tryLock() when the action depends on actually acquiring the lock.

    Trap 4 — Fairness guarantee: "With a fair lock, is order strictly FIFO?" Approximately arrival order, not strict scheduling order. Thread scheduling and untimed tryLock() can still affect the observed order.

    Trap 5 — Optimistic read misuse: "I called tryOptimisticRead(), validated, then read the fields. Is that correct?" No. Copy the fields into locals before validate(stamp); a writer may change them after validation.

    Trap 6 — StampedLock reacquisition: "My method holding a StampedLock calls another method that acquires the same lock. Fine, right?" No. StampedLock is not reentrant; nested reacquisition can deadlock.

    Trap 7 — Condition without the lock: "I called condition.await() outside the lock. What happens?" IllegalMonitorStateException. await(), signal() and signalAll() require the current thread to hold the associated lock.

    Trap 8 — if instead of while: "I wrapped await() in an if because I only expect one signal." Incorrect. Spurious wakeups and competing consumers mean the predicate must be rechecked in a while loop.

    17. Points to Remember

    1. Intrinsic locks lack try-and-fallback, timed acquisition, interruptible acquisition, configurable fairness and multiple wait sets; explicit locks supply these.
    2. Acquire with lock() immediately before try; release in finally. Skipping or misplacing unlock() leaves the lock held indefinitely.
    3. ReentrantLock maintains an owner thread plus a hold count; the lock frees only when the count reaches zero, matching reentrant synchronized semantics.
    4. unlock() without ownership throws IllegalMonitorStateException; getHoldCount(), isLocked() and isHeldByCurrentThread() are diagnostics, not correctness checks.
    5. tryLock() is immediate; timed tryLock(time, unit) can return false; lockInterruptibly() responds to interruption and should restore the interrupt flag.
    6. Fair mode approximates arrival order and reduces starvation but usually lowers throughput; the default non-fair mode permits barging.
    7. ReentrantReadWriteLock allows many readers or one writer; a read lock coordinates readers with writers rather than protecting readers from each other.
    8. Downgrading (write to read) is safe; upgrading (read to write) is not, because the write lock waits for all readers to release.
    9. StampedLock adds optimistic reads with validate(stamp), is stamp-oriented rather than owner-oriented, is not reentrant, and supports no conditions.
    10. Semaphore limits concurrency through permits with no ownership; Condition provides multiple wait sets per lock, and every wait must recheck its predicate in a while loop.

    18. Likely Interview Questions

    Question Crisp Answer
    Why use Lock instead of synchronized? To gain try-and-fallback, timed acquisition, interruptible acquisition, configurable fairness or multiple condition queues.
    What does reentrant mean? The owning thread can reacquire the lock, tracked by a per-thread hold count that is decremented on each unlock().
    Is synchronized reentrant? Yes, intrinsic monitors are reentrant; ReentrantLock adds the extra acquisition, fairness and condition APIs.
    Difference between lock() and lockInterruptibly()? lock() blocks until acquired; lockInterruptibly() can be interrupted while waiting and throws InterruptedException.
    tryLock() vs timed tryLock()? tryLock() returns immediately; tryLock(timeout, unit) waits up to the timeout then returns false or throws on interruption.
    What is a fair lock? A lock created with true that favours the longest-waiting thread, improving predictability at the cost of throughput.
    How does ReentrantReadWriteLock work? Many readers may hold the read lock together, but the write lock is exclusive and excludes all readers and writers.
    Can you upgrade or downgrade a read-write lock? Downgrading write to read is safe; upgrading read to write is not supported safely.
    How does StampedLock optimistic read work? Take an optimistic stamp, copy fields to locals, validate(stamp), and fall back to a read lock if validation fails.
    Is StampedLock reentrant? No; nested reacquisition of the same lock can deadlock, and it has no condition support.
    What does a Semaphore provide? A bounded number of permits to limit concurrency; it tracks no owner, is not reentrant, and any thread may release.
    Condition vs wait()/notify()? Condition attaches to an explicit Lock and supports multiple wait sets per lock, mapping await/signal/signalAll to wait/notify/notifyAll.

    19. Final Summary

    synchronized -------> intrinsic monitor ----> automatic release, one wait set
Lock ---------------> lock()/unlock() in finally ----> explicit acquisition

ReentrantLock            -> one owner + hold count, tryLock, timeout, interruptible, fair option
ReentrantReadWriteLock   -> many readers or one writer; downgrade only
StampedLock              -> optimistic read then validate; stamp-based, not reentrant
Semaphore                -> N permits, no ownership, limit concurrency

    • Explicit locks -> fill the five gaps left by synchronized: try, timeout, interruption, fairness, multiple wait sets.
    • ReentrantLock -> owner plus hold count; lock() before try, unlock() in finally; diagnostics are observation only.
    • Read-write locks -> readers share, writers exclude; downgrade is safe, upgrade is not; continuous readers can starve writers.
    • StampedLock -> copy, validate, fall back; never reacquire it and never trust an unvalidated snapshot.
    • Semaphore -> permit-based concurrency limiting without ownership; Condition -> predicate-based waiting with rechecks.
    • Choosing -> use the simplest mechanism that accurately represents the shared-state rule.

    Golden rule Advanced locking is not about replacing synchronized everywhere; it is about matching a specific coordination rule. More advanced locks buy control and charge responsibility.

    One-line takeaway: explicit locks trade automatic simplicity for control; pick ReentrantLock for one flexible owner, ReentrantReadWriteLock or StampedLock for read-heavy state, Semaphore for permit-limited concurrency, and Condition for predicate-based waiting.
