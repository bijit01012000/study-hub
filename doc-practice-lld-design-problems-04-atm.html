    Design an ATM

    15 sections · 1,942 words

    LLD Design Problems, problem 04 of 20.

    The Ask

    Build

    • Insert a card, read it, take a PIN, the bank authenticates.
    • Pick one: withdraw, deposit, balance, transfer.
    • Withdraw breaks the amount into notes from what the cassettes hold.
    • Money is integer minor units, never a float.
    • A withdrawal holds on the account, dispenses, then commits.
    • One BankService seam: authenticate, hold, commit, credit, balance.
    • Wrong PIN a few times, then the card is kept.
    • Card kept if the session times out mid-transaction.
    • Eject the card at the end.

    Skip

    • Real EMV chip and PIN crypto.
    • The interbank network.
    • Receipt printer, cassette hardware.
    • Multi-currency.
    • Anti-skimming, cameras.
    • A database, login.

    Our Model

    One ATM, a Session for the live request, one cassette per note value. The ATM is a context; every screen delegates to the current state.

    Actors and classes

    • Cardholder — card: Card, atm: ATM; insert card, enter pin, pick txn, take card, calling atm.insertCard(card) and atm.withdraw(amount).
    • ATM (singleton) — cassettes: List<CashCassette>, bank: BankService, dispenser: NoteDispenser, state: ATMState, session: Session; insertCard(Card c), authenticate(int pin): boolean, withdraw(int amount): Cash, deposit(Cash c), balance(): Money, ejectCard(), setState(s). Every call delegates to state.
    • Session — card: Card, acct: String, pinTries: int, startedAt: Instant, chosen: TxnKind, amount: int. Wiped on eject or timeout.
    • BankService (interface) — authenticate(Card c, int pin): AuthResult, hold(String acct, int amt): HoldId, commit(HoldId h), release(HoldId h), credit(String acct, int amt), balance(String acct). Wraps the ISO-8583 host; retries, timeouts, idempotency keys.
    • CoreBankingAdapter — the adapter that implements BankService.
    • ATMState (abstract) — insertCard(Card c), authenticate(int pin): boolean, selectTxn(TxnKind k, int amt), confirm(): Cash. Each state answers all four; wrong state throws.
    • Transaction — acct: String, amount: int; execute(BankService bank). Kinds: Withdrawal, Deposit, BalanceInquiry, Transfer.
    • CashCassette — denom: int, count: int; canDispense(int n): boolean, take(int n), refill(int n). One cassette per denomination.
    • NoteDispenser (interface) — dispense(int amount): List<Note>. Head of the chain.
    • DenominationHandler — denom: int, next: DenominationHandler, box: CashCassette. Chained Rs 2000 -> Rs 500 -> Rs 100, high note first.
    • Card — number, bankId, expiry. The PIN is never stored on the card.

    The states

    Idle -> card in -> CardInserted. CardInserted -> PIN ok -> Authenticated. Authenticated -> pick -> SelectingTxn. SelectingTxn -> confirm -> Dispensing -> Idle. Three wrong PINs or a timeout -> CardRetained.

    Key operations

    1. insertCard(Card c): void — only Idle takes it. Reads the card, opens a Session, moves to CardInserted. A second card is refused until this one ejects.
    2. authenticate(int pin): boolean — legal only in CardInserted. The bank checks the PIN, never the card or the ATM. A wrong PIN bumps pinTries; at three the card is retained. Success moves to Authenticated.
    3. withdraw(int amount): Cash — two-phase. bank.hold escrows the amount, dispenser.dispense counts the notes, then bank.commit. Any failure calls bank.release and nothing leaves the ATM.
    4. dispense(int amount): List<Note> — walks the handlers high note to low. Each takes min(left / denom, stock). Returns the notes when left hits zero, else throws CannotDispense with no cassette touched.

    The chain: serve when left reaches 0 down the chain; atomic when box.take runs after next returns. n = min(left/denom, box.count), left -= n*denom, rest = left == 0 ? [] : next.dispense(left), box.take(n) only after next returns. The tail handler with left > 0 and no next throws CannotDispense, no cassette touched.

    The One Run to Hold in Your Head

    Balance Rs 8,000. The card asks for Rs 3,600. Cassettes hold one Rs 2000, five Rs 500, twenty Rs 100. What notes come out, which state is the ATM in at each step, and which objects touch the request?

    min(3600/2000, 1) = 1 note, 1600 left. min(1600/500, 5) = 3 notes, 100 left. min(100/100, 20) = 1 note, 0 left. So 1 x Rs 2000 + 3 x Rs 500 + 1 x Rs 100 = Rs 3600.

    The Change

    The bank caps a card at Rs 25,000 a day, a premium card at Rs 1,00,000. Pull the limit check out of the withdraw path into a WithdrawalLimitPolicy the ATM asks before it holds. Per-card, per-bank caps drop in, the withdraw path never reopens. Strategy, the seam this pattern is built for.

    What the Picture Can't Show

    The two-phase withdrawal. bank.hold puts the amount in escrow, the chain counts the notes, then bank.commit settles it. A cassette jam between the two calls triggers bank.release, so the account is never short.

    If They Make You Code It

    The withdraw path plus one handler:

    class ATM {                                          // one per machine
    BankService bank; NoteDispenser dispenser;
    ATMState state = new IdleState(this);
    Session session;                                 // the live request

    Cash withdraw(int amount) {
        require(state.isSelectingTxn());             // wrong screen throws
        String acct = session.acct();
        if (amount % 100 != 0) throw new BadAmount(amount);
        HoldId h = bank.hold(acct, amount);          // phase 1: escrow
        List<Note> notes;
        try {
            notes = dispenser.dispense(amount);      // walk the chain
        } catch (CannotDispense e) {
            bank.release(h);                         // roll the hold back
            throw e;                                 // account untouched
        }
        bank.commit(h);                              // phase 2: settle
        session.clear(); state = new IdleState(this);
        return new Cash(notes);
    }
}

class Rs500Handler implements NoteDispenser {
    final int denom = 500; NoteDispenser next;
    CashCassette box;

    public List<Note> dispense(int left) {
        int n = Math.min(left / denom, box.count());
        left -= n * denom;                           // this handler's share
        if (left > 0 && next == null)                // the tail
            throw new CannotDispense(left);          // no box touched
        List<Note> rest = left == 0 ? List.of() : next.dispense(left);
        box.take(n);                                 // commit only after next ok
        return concat(notesOf(denom, n), rest);
    }
}

    The Four Hazards

    1. Debited, then the cassette jams. Debit first, dispense second: the account is short and the cash never left the machine. There is no undo. Hold on the account, dispense, commit; release the hold on any dispense failure.
    2. Card left in mid-session. A user keys the PIN, then walks away. The next person finds a live Authenticated session. A watchdog times out the session, captures the card, wipes the Session, state = Idle.
    3. Amount the notes can't form. Rs 3,650 with only Rs 500 and Rs 100 loaded, or a cassette runs dry mid-count. The chain drives left to 0 or throws before phase 1; the ATM asks for a multiple of the smallest note.
    4. Same account, ATM and app at once. A withdrawal here and a transfer in the mobile app race the same balance. The bank serialises holds per account; the ATM trusts hold and commit, never reads then writes the balance itself.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. bank.hold(acct, amount) before a note moves, bank.release(h) on a jam — the account never debits for cash still in the machine.
    2. dispenser.dispense(amount) throws instead of paying part — the chain is all or nothing.
    3. box.take(n) runs only after next.dispense returns — a downstream shortfall unwinds with no cassette touched.

    Breaking the Amount into Notes

    Approach New note value Per-cassette rule On a shortfall Read at a glance Cost
    Greedy while-loop (the default) edit the loop tangled in the loop silently under-pays one dense loop fine for two notes
    Chain of handlers insert one handler each handler owns its own throws, nothing taken one handler, one denom a class per denomination
    DP / exact split re-run with a new set hard to express reports impossible a DP table build and test the DP

    The chain of handlers. Each denomination is one handler that knows its cassette and its rule, so a new Rs 200 note is one insert and nothing else moves. But know the limit you are accepting: the chain is greedy, and greedy can refuse a split that exists. Rs 600 from one Rs 500 and three Rs 200s takes the Rs 500, is left with Rs 100 and no Rs 100s, while 3 x Rs 200 would have worked. Reach for DP when the note set stops being canonical, or when you must minimise the count.

    Rejection Signals

    These end the interview:

    • Debiting the account before the notes are counted — a jam and the cash is gone with no way back.
    • The ATM branches on a mode with if / switch in every method — a new screen edits five places.
    • One dispense loop that hard-codes Rs 2000, Rs 500, Rs 100 — a new note is a rewrite and per-cassette rules tangle.
    • Money as a double — rounding drift across a million withdrawals.
    • Reading the balance in the ATM and writing it back — the mobile app withdraws in the gap.
    • PIN checked on the card or in the ATM instead of by the bank — a cloned card sets its own PIN.
    • while (left > 0) give the biggest note inline in withdraw instead of a handler chain.

    Patterns Used

    State — one class per screen, transitions inside it. Chain of Responsibility — the note dispenser, one handler per denomination. Strategy — the withdrawal-limit policy on page 2. Adapter — BankService wraps the ISO-8583 host.

    Say It Like This

    "One ATM, a Session for the live request, one cassette per note value. The ATM is a context: every screen delegates to the current state — Idle to CardInserted on a card, to Authenticated when the bank clears the PIN, to SelectingTxn, then Dispensing. Withdrawal is two-phase: hold on the account, count notes down a chain of denomination handlers, commit, or release if a cassette jams. Money is integer paise."

    The Follow-ups That Decide It

    1. Account debited, then the cassette jams. Walk it. Hold, dispense, commit; release on any failure, nothing leaves.
    2. The amount can't be made from the notes on hand. The chain throws before commit; ask for a multiple of Rs 100.
    3. Card left in the slot mid-transaction. A watchdog times out, captures the card, wipes the session.
    4. Same account hit from the mobile app at once. The bank serialises holds per account; the ATM never touches the balance.
    5. Wrong PIN three times. pinTries on the Session, card retained; the real lockout is the bank's, across every ATM.
    6. Add a Rs 200 note. One link in the chain, but note that it breaks greedy, and DP is the fix.
    7. The bank host is slow or down. The Adapter times out; no hold means no cash, the card is ejected.
    8. Cap a card at Rs 25,000 a day. A WithdrawalLimitPolicy the ATM asks before it holds.

    Deliberately Not Built

    • Real EMV / PIN crypto — chip auth, the PIN block, key ceremony. Mocked behind BankService.authenticate.
    • The interbank network — ISO-8583 to the switch, settlement files. That is the HLD version.
    • Receipt printer and cassette hardware — jams, low-paper, note-thickness sensors. Named, mocked.
    • Multi-currency — money carries an amount only. A currency field and a rate table drop in later.
    • Anti-skimming, cameras — physical security, not the object model.
