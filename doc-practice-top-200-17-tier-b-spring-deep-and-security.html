      151. BeanPostProcessor — what does it actually do?

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Walmart Labs

      Difficulty: Medium-Hard · Topic: Spring deep

      The question: "What's a BeanPostProcessor? Walk me through what runs when."

      The 30-second answer: BeanPostProcessor has two callbacks — postProcessBeforeInitialization (after dependency injection, before @PostConstruct / InitializingBean.afterPropertiesSet / init-method) and postProcessAfterInitialization (after init). Spring uses this hook to wrap beans in AOP proxies, apply annotations like @Autowired / @Value, and register lifecycle adapters.

      Step-by-step thought process:

      1. "Order of bean lifecycle — instantiate, populate properties (DI), setBeanName / setBeanFactory / setApplicationContext, postProcessBeforeInitialization, @PostConstruct, afterPropertiesSet, custom init, postProcessAfterInitialization, ready."
      2. " AbstractAutoProxyCreator is a BeanPostProcessor — it's what wraps your @Transactional and @Async beans in CGLIB / JDK proxies during postProcessAfterInitialization."
      3. "To write your own — implement the interface, return a (possibly wrapped) bean from after-init. Use it for cross-cutting bean modification, custom annotations, or metric instrumentation."
      4. " BeanFactoryPostProcessor is different — runs earlier, modifies bean definitions (not instances). Used by PropertySourcesPlaceholderConfigurer to resolve ${} placeholders before any bean is created."

      Edge cases to mention:

      • Order matters — implement Ordered or PriorityOrdered. Wrong order can apply AOP before @Autowired injection
      • BeanPostProcessors themselves aren't postprocessed — they're created early and untouched
      • Use @Lazy carefully — lazy beans skip postprocessing until first access, which can hide order bugs

      What NOT to say:

      • "It's just a lifecycle callback" — undersells it; this is how AOP, @Async, @Cacheable, etc. all work
      • "Same as @PostConstruct " — no, BPP runs around @PostConstruct

      Common follow-up: "How does Spring decide between JDK dynamic proxies and CGLIB?"

      152. BeanFactory vs ApplicationContext

      Asked at: Senior rounds at TCS · Infosys · Cognizant · Wipro

      Difficulty: Medium · Topic: Spring deep

      The question: "What's the difference between BeanFactory and ApplicationContext?"

      The 30-second answer: BeanFactory is the minimal DI container — just lazy bean instantiation. ApplicationContext extends it with enterprise features: eager singleton instantiation, event publishing, internationalization (MessageSource), resource loading, environment / profile abstraction, and parent context chaining.

      Step-by-step thought process:

      1. " BeanFactory — the foundational interface. Lazy by default; beans only created on first getBean(). Useful for memory-constrained scenarios."
      2. " ApplicationContext — what Spring Boot wires up. Eagerly creates singletons at startup (so missing-bean errors surface immediately, not on first request). Publishes lifecycle events (ContextRefreshedEvent, etc.)."
      3. " ApplicationContext adds — MessageSource (i18n), ResourceLoader (classpath / file URLs), ApplicationEventPublisher, Environment for properties and profiles."
      4. "In modern Spring you never touch BeanFactory directly — you depend on ApplicationContext or, more typically, just inject the beans you need."

      Edge cases to mention:

      • BeanFactory#getBean lazy is theoretical — in practice ApplicationContext eager init prevents subtle startup bugs
      • ApplicationContext is itself a BeanFactory — interface hierarchy gives full backward compatibility
      • WebApplicationContext extends ApplicationContext with ServletContext access for web modules

      What NOT to say:

      • "They're basically the same" — true at the basic DI level, false at every enterprise feature
      • "BeanFactory is faster" — slower in steady state because startup-time eager init catches bugs early

      Common follow-up: "What does ContextRefreshedEvent mean and when does it fire?"

      153. AOP weaving — compile-time, load-time, runtime

      Asked at: Senior rounds at Swiggy · Razorpay · JP Morgan India · Walmart Labs

      Difficulty: Hard · Topic: Spring deep

      The question: "Spring AOP is one form of weaving. What are the others?"

      The 30-second answer: Three weaving modes — runtime proxy weaving (Spring AOP — JDK or CGLIB proxies wrapping beans), load-time weaving (AspectJ LTW — bytecode rewritten by a Java agent at class load), and compile-time weaving (AspectJ AJC — bytecode modified by a custom compiler before runtime).

      Step-by-step thought process:

      1. "Spring AOP — proxy-based. @Transactional works because Spring wraps your bean in a proxy that intercepts methods. Limitations: only public methods, only external invocations (a self-call inside the same class bypasses the proxy)."
      2. "AspectJ load-time weaving — -javaagent:aspectjweaver.jar rewrites classes as they load. No proxies, advice woven directly. Catches self-calls and private methods, but adds a JVM agent."
      3. "Compile-time weaving — uses the AspectJ compiler (ajc) instead of javac. Produces classes with the advice baked in. Fastest at runtime, most invasive to build."
      4. "Pick: Spring AOP for 90% of cases (transactions, security, logging on Spring beans). AspectJ when you need to advise non-Spring code or self-calls."

      Edge cases to mention:

      • Self-invocation gotcha — this.transactionalMethod() from within the same class bypasses Spring AOP. Inject a self-reference or use AopContext.currentProxy() @EnableAspectJAutoProxy(proxyTargetClass = true) forces CGLIB even for interfacebased beans
      • AspectJ pointcut expressions are richer than Spring AOP's — full Java type matching, including private/static

      What NOT to say:

      • "AspectJ is just like Spring AOP" — fundamentally different mechanism
      • "AOP is dead, use interceptors" — interceptors are AOP under a different name

      Common follow-up: "Why does @Transactional not work on a self-called method?"

      154. Custom annotations + meta-annotations

      Asked at: Senior rounds at Razorpay · Cred · Swiggy

      Difficulty: Medium-Hard · Topic: Spring deep

      The question: "Build me a @RateLimited annotation that's enforced by Spring."

      The 30-second answer: Define the annotation with @Retention(RUNTIME) @Target(METHOD). Write an @Aspect with a @Around advice targeting @annotation(com.example.RateLimited). Inside the advice, look up the rate limiter bucket for the key (method name + caller IP), allow or reject. Stack with @AliasFor and other Spring metaannotation tricks.

      Step-by-step thought process:

      1. "Annotation declaration — @Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD) public @interface RateLimited { int permitsPerSecond() default 10; }."
      2. "Aspect — @Aspect @Component class RateLimitAspect { @Around("@annotation(rateLimited)") public Object check(ProceedingJoinPoint pjp, RateLimited rateLimited) throws Throwable {... }. Spring passes the matched annotation in for free."
      3. "Meta-annotation pattern — compose your own annotation that itself is annotated with @RateLimited + @Transactional. Spring's annotation discovery follows meta-annotations one level deep by default."
      4. " @AliasFor — lets a custom annotation alias an attribute from a meta-annotation. Used in Spring's own @GetMapping aliasing @RequestMapping(method = GET)."

      Edge cases to mention:

      • RetentionPolicy.SOURCE (Lombok), CLASS (default; in bytecode but not loaded), RUNTIME (reflectable). Spring needs RUNTIME
      • @Inherited only works for class-level annotations and only at one level
      • Aspect must be a Spring bean — otherwise it's just a class with no proxying

      What NOT to say:

      • "I'd write a HandlerInterceptor" — works for controllers only, misses service-layer calls
      • "Annotations can do this by themselves" — no, you always need a runtime processor

      Common follow-up: "What's the difference between RetentionPolicy.SOURCE, CLASS, and RUNTIME?"

      155. Spring AOT and Native Image

      Asked at: Senior rounds at Swiggy · Razorpay · Cred · Walmart Labs

      Difficulty: Hard · Topic: Spring deep

      The question: "Spring Boot 3 added AOT and native image support. What problem does it solve?"

      The 30-second answer: AOT (ahead-of-time) processing analyzes your beans at build time and generates static configuration — no reflection, no classpath scanning at runtime. Combined with GraalVM Native Image, this gives sub-100ms startup and 5-10x lower memory. Trade-off: build time goes up significantly and dynamic features (runtime classpath scan, JDK proxies for unknown interfaces) need explicit hints.

      Step-by-step thought process:

      1. "Standard Spring Boot startup — classpath scan, reflection-based bean instantiation, dynamic proxy generation. Takes seconds, loads metadata for every annotation."
      2. "Spring Boot 3 + Spring Framework 6 — AOT processor runs at build time. Generates Java source files with the bean factory definitions, reflection hints, proxy classes. Runtime startup skips all the scanning."
      3. "GraalVM Native Image — compiles your AOT-processed app to a static binary. Cold start under 100ms, RSS under 100MB. Critical for serverless / FaaS / scale-to-zero containers."
      4. "Caveats — anything not in the AOT hints (@RegisterReflectionForBinding, @ImportRuntimeHints) fails at runtime. Spring covers most common cases; bring-your-own libraries may need work."

      Edge cases to mention:

      • AOT in JVM mode (without native) still helps — about 20% startup improvement, no GraalVM needed
      • spring-boot-starter-parent 3.x integrates AOT into the build automatically — mvn -Pnative package
      • Profiles, conditional beans, and @ConditionalOnProperty are resolved at AOT time — you can't change application.properties at runtime to flip them on/off in native mode

      What NOT to say:

      • "Native image is just a faster JVM" — different runtime, different limitations
      • "Use AOT to make my app faster at peak" — AOT helps startup; peak throughput often slightly lower than C2optimized JVM

      Common follow-up: "What's a reflection hint and when do I need one?"

      156. Conditional beans — @ConditionalOnProperty, @ConditionalOnClass

      Asked at: Senior rounds at Razorpay · Swiggy · Walmart Labs

      Difficulty: Medium · Topic: Spring deep

      The question: "How do Spring Boot starters decide whether to auto-configure a feature?"

      The 30-second answer: @ConditionalOnClass (a class is on the classpath), @ConditionalOnMissingBean (user didn't define their own), @ConditionalOnProperty (a property is set), @ConditionalOnBean (some other bean is registered). Auto-configurations are conditional declarations — they trigger or skip based on classpath + user config.

      Step-by-step thought process:

      1. " spring-boot-starter-data-redis adds Lettuce to the classpath. RedisAutoConfiguration has @ConditionalOnClass(RedisClient.class) — it activates because Lettuce is present."
      2. " @ConditionalOnMissingBean(StringRedisTemplate.class) — only registers if you haven't defined your own. This is the override-default pattern."
      3. " @ConditionalOnProperty(name = "feature.x.enabled", havingValue = "true") — feature flags through config. Useful for canary releases."
      4. "Use --debug flag at startup — Spring Boot prints the conditional report showing why each auto-config was applied or skipped."

      Edge cases to mention:

      • @ConditionalOnClass(name = "...") uses string for cases where the class genuinely isn't on the classpath (so you can't import it for the annotation parameter)
      • Custom Condition classes for complex multi-property logic
      • @Profile is a special case of conditional — activates only when a profile is active

      What NOT to say:

      • "Auto-configuration is magic" — every condition is explicit and inspectable via -debug
      • "It's the same as @Profile" — profiles are one mechanism; conditionals are more general

      Common follow-up: "How do you write your own custom conditional annotation?"

      157. Spring transaction propagation — REQUIRED vs REQUIRES_NEW vs NESTED

      Asked at: Senior rounds at Razorpay · PhonePe · TCS Digital · Wells Fargo

      Difficulty: Hard · Topic: Spring deep

      The question: " @Transactional(propagation = REQUIRES_NEW) inside a @Transactional method — what actually happens?"

      The 30-second answer: REQUIRED (default) joins an existing transaction or starts one. REQUIRES_NEW suspends any existing transaction and starts a brand-new one — even if the inner fails, the outer can still commit (and vice versa). NESTED uses a savepoint inside the current transaction — inner rollback rolls back to the savepoint without aborting the outer.

      Step-by-step thought process:

      1. "REQUIRED — the workhorse default. If the caller has a transaction, join it; otherwise start one. Rollback of inner rolls back the whole thing."
      2. "REQUIRES_NEW — suspends the outer (saves it on the connection, gets a new connection from pool). Inner runs as a fully independent transaction. Use case: audit log that must persist even if business transaction rolls back."
      3. "NESTED — single connection, savepoint-based. Inner can be rolled back without aborting the outer. Less common; only some DBs / JDBC drivers support savepoints reliably."
      4. "NEVER — throws if a transaction exists. MANDATORY — throws if one doesn't. SUPPORTS — runs in the existing one if present, else non-transactional."

      Edge cases to mention:

      • REQUIRES_NEW needs a fresh connection — under heavy load with a small connection pool, you can deadlock holding two connections per thread
      • Self-invocation bypasses propagation — this.innerMethod() doesn't trigger the proxy
      • Read-only optimizations — @Transactional(readOnly = true) lets Hibernate skip dirty checking, JDBC drivers may use read-only connections

      What NOT to say:

      • "REQUIRES_NEW pauses the outer" — close enough but say suspends; it's a specific technical term Spring uses
      • "Just use REQUIRED everywhere" — works most of the time but misses the audit/notify use cases

      Common follow-up: "What's the connection pool risk with REQUIRES_NEW?"

      158. Spring profiles, active vs default vs include

      Asked at: Senior rounds at TCS Digital · Cognizant · Razorpay

      Difficulty: Medium · Topic: Spring deep

      The question: "Walk me through how Spring profile resolution works at startup."

      The 30-second answer: spring.profiles.active is the explicit list (comma-separated). If empty, Spring uses spring.profiles.default (which itself defaults to default). Profiles can include others via spring.profiles.include. application-.yml files load only when the matching profile is active, with property override priority over application.yml.

      Step-by-step thought process:

      1. "Set via --spring.profiles.active=prod,asia on CLI, SPRING_PROFILES_ACTIVE=prod env var, or spring.profiles.active=prod in application.yml."
      2. " application-prod.yml is auto-loaded when prod is active. Properties there override application.yml. Multiple active profiles: later-listed profiles override earlier."
      3. " @Profile("!prod") on a bean — only registers when prod is NOT active. Useful for devonly stubs."
      4. "Common pattern — prod, stage, dev, test for environments; aws, gcp for cloud-specific overrides; mysql, postgres for DB swapping."

      Edge cases to mention:

      • Profile group (spring.profiles.group.prod=asia,observability) — activating prod activates the group transitively
      • Profiles in Spring Boot 2.4+ use the new "config data" API — spring.config.activate.on-profile inside the yaml itself
      • Test profiles via @ActiveProfiles("test") on the test class

      What NOT to say:

      • "Profiles are like environments" — close but they're more flexible (multiple active at once)
      • "You can change profile at runtime" — no, profile resolution happens at context startup only

      Common follow-up: "How does the Spring Boot config data API differ from the older property source approach?"

      159. JWT vs session — when each makes sense

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Walmart Labs

      Difficulty: Medium-Hard · Topic: Spring Security

      The question: "Should I use JWT or session-based auth for my Spring Boot app?"

      The 30-second answer: Session = state in your server (or Redis). JWT = state in the token itself, server stateless. Session is simpler to invalidate (delete from store) but requires sticky session or shared session store. JWT scales horizontally with zero infra but invalidation requires either short expiry + refresh tokens or a blocklist.

      Step-by-step thought process:

      1. "Session cookie — server stores user state, hands client an opaque session ID, validates every request. Logout = delete from session store. Easy invalidation, requires shared state across nodes."
      2. "JWT — server signs a token containing user claims (sub, roles, exp). Validates signature on every request. Stateless on the server. Hard to revoke: token is valid until exp, no central record."
      3. "For a single-app monolith with sticky sessions — session is simpler. For microservices where many services validate the token — JWT avoids the shared session lookup."
      4. "Practical JWT pattern — short-lived access token (15 min), long-lived refresh token (stored as HttpOnly cookie). Revocation list for refresh tokens only."

      Edge cases to mention:

      • Don't put PII or large data in JWT — every request carries the full payload Storage on client — localStorage is XSS-exposed; HttpOnly Secure SameSite cookie is safer Symmetric (HS256) vs asymmetric (RS256) signing — services that only validate need only the public key, never the signing secret

      What NOT to say:

      • "JWT is always better because stateless" — ignores the revocation cost
      • "Just use OAuth" — OAuth is the framework, JWT/session is the token mechanism

      Common follow-up: "How do you handle JWT revocation?"

      160. OAuth2 grant types — pick one for a mobile app

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Walmart Labs

      Difficulty: Medium-Hard · Topic: Spring Security

      The question: "Walk me through OAuth2 grant types. Which one for a mobile app?"

      The 30-second answer: Authorization Code (with PKCE) for any public client (mobile, SPA) — exchange the code for tokens with proof-of-possession. Client Credentials for server-to-server (no user). Resource Owner Password (deprecated) and Implicit (deprecated) — don't use. Device Code for TV / CLI flows. Refresh Token for renewal.

      Step-by-step thought process:

      1. "Authorization Code + PKCE — modern default for any client that can't keep a secret (mobile apps, SPAs). User redirects to auth server, app exchanges short-lived code for tokens, PKCE proof binds the exchange to the original requestor."
      2. "Client Credentials — service A calls service B. No user. Service has a client ID + secret, exchanges them for an access token. Used internally between microservices."
      3. "Refresh Token — separate grant to renew expiring access tokens without reprompting the user. Should be one-time-use + rotation in modern implementations."
      4. "Implicit and Password — both deprecated. Implicit because access token in URL fragment is dangerous; Password because it requires sharing real credentials with the client app."

      Edge cases to mention:

      • PKCE (S256 code challenge) is now recommended for all Auth Code flows, not just public clients
      • Token endpoints should reject Authorization headers without client auth when expected; many services miss this
      • Spring Authorization Server (replaces Spring Security OAuth which was retired) is the modern Java implementation

      What NOT to say:

      • "Use Implicit for mobile apps" — outdated and unsafe
      • "OAuth and authentication are the same" — OAuth is authorization; OpenID Connect on top provides authentication

      Common follow-up: "What does PKCE actually protect against?"

      161. Method-level security — @PreAuthorize vs @Secured

      Asked at: Senior rounds at Razorpay · TCS Digital · Wells Fargo

      Difficulty: Medium · Topic: Spring Security

      The question: "Compare @PreAuthorize, @Secured, and @RolesAllowed."

      The 30-second answer: @Secured("ROLE_ADMIN") is the simplest — checks roles by name. @PreAuthorize("hasRole('ADMIN') and #order.userId == authentication.principal.id") evaluates SpEL expressions, including method-argument references. @RolesAllowed is the JSR-250 standard equivalent of @Secured. Enable with @EnableMethodSecurity (Spring Security 6+).

      Step-by-step thought process:

      1. " @EnableMethodSecurity(prePostEnabled = true) — turns on the SpEL-based annotations. Use it instead of older @EnableGlobalMethodSecurity."
      2. " @PreAuthorize for everything new — SpEL gives you access to method args (#orderId), the authenticated principal, and Spring Security helpers (hasRole, hasAuthority, isAuthenticated)."
      3. " @PostAuthorize("returnObject.userId == authentication.principal.id") — runs after method returns; you can reject access based on what was returned."
      4. " @PreFilter / @PostFilter — filter elements of a collection in/out based on per-element SpEL — niche but powerful."

      Edge cases to mention:

      • Spring Security uses AOP — same proxy / self-invocation gotcha as @Transactional
      • @PreAuthorize on interfaces vs implementations — Spring scans both, prefer the interface for cleanliness
      • Custom PermissionEvaluator for object-level permissions (hasPermission(#order, 'WRITE'))

      What NOT to say:

      • "@Secured is deprecated" — still supported, just older; @PreAuthorize is preferred for new code
      • "Security annotations are slower than filter chains" — both go through filter chain; method-level adds an extra AOP layer

      Common follow-up: "How do you write a custom PermissionEvaluator?"

      162. CSRF — what it is and when Spring Security needs it

      Asked at: Senior rounds at Razorpay · TCS Digital · Wipro · Cognizant

      Difficulty: Medium · Topic: Spring Security

      The question: "What is CSRF and when can I disable Spring's CSRF protection?"

      The 30-second answer: CSRF (Cross-Site Request Forgery) — a malicious site tricks your authenticated browser into submitting a request to a different site (yours). Spring Security defaults to CSRF protection via a synchronizer token. Safe to disable only for stateless APIs that don't use cookies for auth — pure JWT-bearer APIs.

      Step-by-step thought process:

      1. "The attack — user logs into bank.com, gets a session cookie. Then visits attacker.com, which has a hidden form submitting to bank.com/transfer. Browser automatically attaches the cookie. Attack succeeds."
      2. "Defense — CSRF token. Server generates a random token per session, embeds in forms / sends as header. Server verifies the token on state-changing requests. Attacker can't read the token (same-origin policy)."
      3. "Spring Security — CSRF on by default. For JWTbearer APIs (no cookies), CSRF isn't possible — attacker can't fabricate the Authorization header. Disable with http.csrf(csrf -> csrf.disable())."
      4. "If you use cookies for auth and don't want a token, set the cookie to SameSite=Lax or Strict — modern browsers block cross-site requests carrying the cookie."

      Edge cases to mention:

      • CookieCsrfTokenRepository.withHttpOnlyFalse() — token in a JS-readable cookie, app reads and adds as header. Pattern for SPAs
      • GET requests are exempt from CSRF (they should be idempotent) — but if your GET endpoint mutates state, that's the real bug Double-submit cookie pattern is an alternative to synchronizer tokens

      What NOT to say:

      • "Always disable CSRF for APIs" — only safe for non-cookie auth
      • "CSRF and XSS are the same" — completely different attacks

      Common follow-up: "What's SameSite cookie attribute and how does it relate to CSRF?"

      163. Password encoders — BCrypt vs Argon2 vs Scrypt

      Asked at: Senior rounds at Razorpay · Cred · PhonePe · Wells Fargo

      Difficulty: Medium · Topic: Spring Security

      The question: "What password encoder would you pick in 2026 and why?"

      The 30-second answer: Argon2id is the modern OWASP recommendation — memory-hard, GPUresistant. BCrypt is the safe traditional default — well-understood, widely supported, configurable cost. Avoid plain SHA / MD5 / unsalted hashes. Spring Security's DelegatingPasswordEncoder lets you store the algorithm with the hash for graceful migration.

      Step-by-step thought process:

      1. "Password storage must be slow on purpose — to make offline brute-force attacks expensive. BCrypt and friends use a configurable work factor; tune to take ~250-500ms per hash on your hardware."
      2. "BCrypt cost (default 10) — 2^cost rounds. Raise to 12+ for 2026 hardware. BCryptPasswordEncoder(12)."
      3. "Argon2id — winner of the Password Hashing Competition. Tunable memory cost (resists GPU/ASIC attacks better than BCrypt). Spring Security: Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()."
      4. " DelegatingPasswordEncoder — Spring Security default. Stores {bcrypt}$2a$10$... — the prefix tells which encoder to use. Lets you change algorithms without invalidating existing passwords."

      Edge cases to mention:

      • Never reuse a single salt — each password gets its own random salt, stored alongside the hash
      • Peppering (extra secret added to all hashes) is a separate technique — store the pepper in a KMS / secret manager
      • Migration strategy — on user login, re-hash with the new algorithm if the stored prefix is outdated

      What NOT to say:

      • "SHA-256 with salt is fine" — too fast; GPU farms crack billions per second
      • "Just use plain text behind HTTPS" — never

      Common follow-up: "How does DelegatingPasswordEncoder handle migration when you change the encoder?"

      164. CORS configuration in Spring Security

      Asked at: Senior rounds at Razorpay · Swiggy · TCS Digital

      Difficulty: Medium · Topic: Spring Security

      The question: "My React frontend at https://app.example.com can't call my API at https:// api.example.com. What's CORS and how do I fix it in Spring?"

      The 30-second answer: Browsers block cross-origin requests by default. The server has to explicitly allow them by returning Access-Control-Allow-Origin and friends. In Spring Security, configure a CorsConfigurationSource bean and reference it from http.cors(...). Don't use * for production — list exact origins.

      Step-by-step thought process:

      1. "Same-origin policy — JavaScript at origin A can read responses from origin A only. Different protocol/host/port = different origin. CORS is the explicit opt-in."
      2. "Preflight request — for anything beyond simple GET/POST with safe headers, the browser sends an OPTIONS request first. Server responds with allowed origins/methods/headers. Then the real request goes."
      3. "Spring config — @Bean CorsConfigurationSource corsConfigurationSource() {... }. Set allowed origins, methods, headers, allowCredentials = true if you need cookies."
      4. "With Spring Security, .cors(Customizer.withDefaults()) enables CORS handling in the filter chain. Without it, security can block before CORS headers are added."

      Edge cases to mention:

      • allowedOrigins = "*" + allowCredentials = true is invalid per spec — you must list explicit origins
      • setAllowedOriginPatterns (Spring 5.3+) lets you use wildcards like https://*.example.com even with credentials
      • Preflight responses are cached — setMaxAge(3600) reduces preflight overhead

      What NOT to say:

      • "Disable CORS to fix it" — CORS is a browser-enforced policy; you can't disable the browser
      • "Use a wildcard in production" — opens you to arbitrary-origin attacks

      Common follow-up: "What's the difference between a simple request and a preflight request?"
