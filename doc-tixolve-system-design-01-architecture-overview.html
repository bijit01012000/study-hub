    Architecture Overview

    8 sections · 792 words

    Section 1 of 11

    30-Second Project Pitch

    An AI-powered enterprise knowledge assistant and support ticketing platform. Users chat with an AI that answers from company documents with citations. When the AI can't resolve the issue, it auto-escalates to a human support ticket.

    Tech headline: Java 21 + Spring Boot microservices | React + TypeScript | PostgreSQL + pgvector | Apache Kafka | Spring AI + Claude API | AWS ECS Fargate

    Why Microservices?

    Each service has a distinct scaling profile and domain boundary:

    • knowledge-service — async, CPU-heavy batch ingestion. You run it once per document upload.
    • chat-service — sync, latency-sensitive, holds SSE connections open. You scale it per concurrent user.

    These two can't share a process if you want to scale them independently. Forcing them together would mean scaling the entire monolith whenever ingestion spikes, wasting resources on chat instances you don't need.

    Honest trade-off: For a solo portfolio project, microservices add significant operational overhead (6+ services, distributed tracing, eventual consistency). A well-structured monolith delivers an MVP faster. This is microservices by deliberate design choice for interview demonstration — not because it's the simplest tool for this problem size.

    Monorepo Structure

    Tixolve/
├── api-gateway/           Spring Cloud Gateway — single entry point
├── auth-service/          App user/tenant metadata on top of Keycloak
├── knowledge-service/     Document ingestion, chunking, pgvector, search
├── chat-service/          RAG orchestration, Spring AI, SSE streaming
├── ticket-service/        Ticket CRUD, status workflow, SLA
├── notification-service/  Kafka consumer, in-app notifications via WebSocket
├── frontend/              React + TypeScript + MUI
├── observability/         Prometheus, Grafana, Loki config
├── docker-compose.yml
├── docker-compose.observability.yml
└── docs/

    Why monorepo? Atomic commits across services, shared tooling, single docker-compose up for local dev. In a real company this would more likely be polyrepo per team.

    Service Map

    Service Responsibility DB Exposes REST?
    api-gateway Entry point, JWT validation, routing, rate limiting none Routes only
    auth-service App user/tenant metadata, role mappings auth_db Yes
    knowledge-service S3 upload, chunking, pgvector, hybrid search knowledge_db Yes
    chat-service RAG orchestration, Spring AI, SSE streaming, escalation chat_db Yes
    ticket-service Ticket CRUD, status workflow, outbox ticket_db Yes
    notification-service Kafka consumer, WebSocket push to browser notification_db No

    Request Flow — Chat (Happy Path)

    Browser
  → HTTPS
  → api-gateway
      validates JWT (Keycloak JWKS, cached)
      injects X-User-Id, X-Tenant-Id headers
      routes to chat-service
  → chat-service
      loads conversation history
      calls knowledge-service /search (hybrid vector + full-text)
      builds prompt (system + retrieved chunks + history + user message)
      calls Spring AI ChatClient → Claude or Ollama
      streams tokens back via SSE
  → Browser renders tokens as they arrive

    Request Flow — Escalation

    chat-service detects low-confidence answer
  → writes chat.escalated event to outbox (same DB transaction as message save)
  → outbox publisher sends to Kafka topic: chat.escalated
ticket-service (Kafka consumer)
  → creates ticket linked to conversation
  → writes ticket.created to outbox
  → outbox publisher sends to Kafka: ticket.created
notification-service (Kafka consumer of ticket.created)
  → creates notification record
  → pushes to connected browser via WebSocket

    Cross-Service Communication Rules

    Pattern When to use
    Synchronous REST Producer needs the response before proceeding (e.g., chat-service needs search results)
    Kafka events Side effects where producer doesn't need to wait (e.g., ticket created → notify user)

    Hard rules enforced in this codebase:

    • No service reads another service's database tables. Ever.
    • Cross-service data = REST call. Cross-service side effects = Kafka event.
    • knowledge-service and chat-service stay separate — different scaling profiles (see above).

    API Gateway Detail

    Responsibilities:

    • JWT validation against Keycloak JWKS endpoint (public keys cached, not per-request)
    • Injects X-User-Id and X-Tenant-Id as trusted internal headers
    • Rate limiting (Redis-backed sliding window counter)
    • CORS (handled once here, not in every service)
    • Routing rules to each downstream service

    Trust boundary: Downstream services trust the gateway's injected headers. They do NOT re-validate JWTs. The gateway is the sole trust boundary.

    Why not validate JWT in every service? Every service doing its own JWKS call adds latency (even cached) and duplicates security logic. The gateway is already the single ingress — making it the sole trust boundary is the standard pattern (same as AWS ALB + Cognito, or Istio sidecar mTLS). Downstream services are on a private network not exposed publicly.

    What if someone bypasses the gateway on the internal network? In production: security groups / network policy allow inbound only from the gateway's security group. For this demo, it's a known accepted trade-off.
