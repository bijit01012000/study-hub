    Design an Elevator System

    15 sections · 2,035 words

    LLD Design Problems, problem 03 of 20.

    The Ask

    Build

    • N floors, one or more elevator cars.
    • Two calls: hall (up/down on a floor), car (a floor button inside).
    • Each car holds floor, direction, door state, a set of pending stops.
    • A Dispatcher assigns each hall call to one car.
    • Scheduling is SCAN / LOOK: serve the current direction, then reverse.
    • Car calls merge into the same sorted set.
    • Live floor and direction for the displays.

    Skip

    • Acceleration, motor and VFD control.
    • Lobby destination dispatch (follow-up).
    • Door sensors, weight limit.
    • Many buildings, one control room.
    • A database, login.

    Our Model

    A building to cars to stops. One Building holds a few ElevatorCars, each owning an up sweep and a down sweep of pending stops.

    Actors and classes

    • HallPanel — floor: int, building: Building; press(Direction d) calls building.submit(new HallCall(floor, d)).
    • CarPanel — car: ElevatorCar; press(int floor) calls car.addStop(floor, NONE).
    • Building (singleton) — floors: int, cars: List<ElevatorCar>, dispatch: Dispatcher; submit(HallCall c): void, tick(): void (calls car = dispatch.assign(call) then car.addStop(call.floor, call.dir)).
    • Call — floor: int, kind: HALL | CAR, dir: Direction (hall only), at: Instant. A hall call carries a direction, a car call does not.
    • Dispatcher (interface) — assign(HallCall c): ElevatorCar. Reads each car's floor, dir and load; mutates nothing. NearestCar, SameDirectionFirst, LeastBusy.
    • ElevatorCar (one per shaft) — id: String, floor: int, dir: Direction, door: DoorState, up, down: NavigableSet<Integer>; addStop(int floor, Direction d): void, step(): void, nextStop(): Integer, direction(): Direction.
    • CarState (abstract) — onArrive(), onIdle(), onCall(Call); subtypes MovingUp, MovingDown, DoorsOpen, Idle, each the step() move for that phase.
    • Stop — floor: int, kind: CallKind; compareTo(Stop): int by floor. A hall stop orders by the rider's direction; a car stop by position.
    • DoorController (interface) — cycle(): void (open, dwell, close, reopen on a call for this floor). StandardDoors, FreightDoors, NudgeOnBlock.

    The call and the car's phase

    A hall call carries a direction; a car call does not. The car's phase is MovingUp, MovingDown, DoorsOpen or Idle.

    The dispatcher policies

    • NearestCar -> least |delta floor|, able to serve.
    • SameDirectionFirst -> a car already heading that way.
    • LeastBusy -> fewest pending stops.

    Key operations

    1. assign(HallCall c): ElevatorCar — the Dispatcher reads each car's floor, direction and load and returns one car. Pure; it never mutates a car. A repeat of the same hall call resolves to the same car.
    2. addStop(int floor, Direction d): void — a hall call joins the sweep matching the direction the rider asked for; a car call joins by where the car is now. O(log n) into a NavigableSet. A duplicate floor is a no-op; the current floor re-opens the doors.
    3. step(): void — one tick. Moves one floor toward nextStop(), or opens the doors and drops the stop on arrival. Calls flip() when nothing is ahead. Never skips a stop in the current sweep.
    4. nextStop(): Integer — going up: the smallest stop >= floor in up. Going down: the largest stop <= floor in down. Nothing ahead? Deadhead to the far caller in the other sweep. Null only when neither set has work: flip or go idle.

    serve here is true when floor is in the sweep set; reverse is true when ceiling / floor returns null. Step: t = nextStop(); if t == floor: doors.open(), set.remove(t); else floor += sign(t - floor). NextStop: up.ceiling(floor) up, down.floor(floor) down, none means run to the far caller, else null means flip the sweep.

    The One Run to Hold in Your Head

    Car A is at floor 4, going up, stops at 7 and 9. A hall call "down" comes from 5, and a car call for 2. Which stops does A serve, in what order, and which objects touched each request?

    The sweep from floor 4: up.ceiling(4) = 7, then 9. So 4 -> 7 -> 9, doors open at 7, then 9; drop each from up. Then up.ceiling() = null, so flip to DOWN. down = {5, 2}; 9 -> 5 -> 2, the reverse sweep serves 5, then 2. A car call for 2 lands straight in down.

    The Change

    They add lobby destination entry for rush hour. A rider keys the target floor before boarding, so the dispatcher groups riders by destination and gives each car one group, cutting the stops per trip. A new Call kind, same Strategy seam. Strategy, a second time on this sheet.

    What the Picture Can't Show

    The tick. A timer calls tick() on the Building and every car runs one step() — move a floor, or work the doors. Nothing here is real time; a scheduler thread or an event queue drives it.

    If They Make You Code It

    Step and nextStop, LOOK, the whole thing:

    class ElevatorCar {                                 // one per shaft
    int floor; Direction dir = IDLE;
    final NavigableSet<Integer> up = new TreeSet<>();
    final NavigableSet<Integer> down = new TreeSet<>();

    void addStop(int f, Direction call) {           // NONE = car call
        if (f == floor) { openDoors(); return; }
        boolean onUp = call == NONE ? f > floor     // by position
                                    : call == UP;    // the RIDER's
        (onUp ? up : down).add(f);                   // into that sweep
        if (dir == IDLE) dir = f > floor ? UP : DOWN;
    }

    Integer nextStop() {                            // LOOK, then deadhead
        if (dir == IDLE) return null;
        var mine = dir == UP ? up : down;
        var far  = dir == UP ? down : up;
        Integer t = dir == UP ? mine.ceiling(floor) : mine.floor(floor);
        if (t != null) return t;                    // a stop ahead
        if (far.isEmpty()) return null;
        Integer e = dir == UP ? far.last() : far.first();
        return (dir == UP ? e > floor : e < floor) ? e : null;
    }

    void step() {                                   // once per tick
        Integer t = nextStop();
        if (t == null) flip();                      // nothing ahead
        else if (t == floor) {                      // arrived
            openDoors();
            up.remove(floor); down.remove(floor);
        } else floor += (t > floor ? 1 : -1);
    }

    void flip() {                                   // reverse, or park
        if (up.isEmpty() && down.isEmpty()) { dir = IDLE; return; }
        dir = dir == UP ? DOWN : UP;                // turn, then LOOK
    }
}

    The Four Hazards

    1. Call during the door close. The doors are latched closing when a rider presses this floor. If the press just joins the set, the car leaves and comes back a whole sweep later. A press for the current floor inside the close latch cancels the close and re-opens; a different floor just joins the set.
    2. Early reversal. Car climbs from 3 to 9. A hall call "down" from 5 must not flip the car at 5 — riders above are still waiting. Reverse only when nextStop() is null; the down call sits in the down set until the top is served.
    3. A starved top floor. Floor 20 keeps getting passed as nearer lobby calls keep arriving. Pure LOOK can defer it forever under load. Age each stop; past a cap it jumps the sweep order, or a second car is dispatched.
    4. One call, two cars. The dispatcher assigns floor 6 to car A, then a tick later hands it to car B before A is marked. Both roll to 6. Claim the hall call atomically on assign; clear it only when a car opens its doors there.

    Name them before they are asked. A car that flips only when its sweep is empty never strands the riders above it.

    The Three Lines They Are Watching

    1. nextStop() serves only the current sweep — a down call joins the down set wherever the car is, so it waits for the reverse.
    2. t == floor opens the doors and drops the stop in the same tick — no re-visit next tick.
    3. flip() turns around while either set still has work, and parks IDLE only when both are empty.

    Choosing a Dispatch Policy

    Approach Assign a call Order in a car Recompute Starvation Use when
    Nearest car (greedy assign, the default) O(cars) by pickup time one car possible 1-2 cars, light
    Per-car LOOK O(cars) + O(log n) sweep, no wasted reversal one car bounded by the sweep most interviews
    Global re-optimize O(cars · stops) solve re-derived each call every car, every call solver can forbid it few floors, heavy, latency-critical

    Per-car LOOK behind a nearest / same-direction dispatcher. Each car runs its own sweep, a new call touches one car, and assignment is O(log n). Reach for a global solver only when they name heavy traffic and ask for provable optimality.

    Rejection Signals

    These end the interview:

    • One tick() that rescans every floor of every car instead of a per-car sorted set.
    • A car that flips direction the instant a closer opposite call arrives, stranding riders it passed.
    • Dispatch chosen by an if on car count, with no seam for same-direction or zoning.
    • Hall calls and car calls kept in two queues that never merge into one sweep.
    • No answer for a starved floor under constant lobby traffic.
    • Direction held as a bare boolean with no idle state — the car cannot tell stopped from down.
    • if (cars.size() == 1) branching inside submit instead of a dispatch seam.

    Patterns Used

    State — the car's Idle / Moving / DoorsOpen phases. Strategy — the dispatch and the sweep policy. Command — a Call is a queued request object. Observer — floor and car displays follow the car.

    Say It Like This

    "One building, a few cars. Each car owns a sorted set of stops, split into an up sweep and a down sweep. A hall call goes to a Dispatcher that picks a car; a car call drops straight into that car's set. Every tick the car moves one floor toward its nearest stop ahead, opens the doors on arrival, and reverses only when nothing is left that way. Dispatch and the sweep are strategies, so a new policy never reopens the car."

    The Follow-ups That Decide It

    1. Hall call "down" from 5 while the car climbs to 9. It sits in the down set, served on the reverse sweep.
    2. Rider selects the floor the car is already stopped at. addStop sees f == floor and just re-opens the doors.
    3. The top floor starves under constant lobby calls. Age the stop; past a cap it jumps the sweep.
    4. Two cars sent to the same hall call. Claim the call on assign, clear it on arrival.
    5. How does the dispatcher pick a car? Assign nearest, or one already heading that way.
    6. Rush hour, lobby to many floors. Zone the cars, or destination-dispatch by group.
    7. A car goes out of service mid-sweep. Reassign its hall calls; car calls are lost, riders re-press.
    8. Where do idle cars wait? A policy: park at the lobby, or spread across zones.

    Deliberately Not Built

    • Destination dispatch — riders key their floor in the lobby; the dispatcher groups them. A new Call kind, same Strategy seam.
    • Real motion — acceleration, jerk limits, VFD control. The sim moves one floor per tick. Another problem.
    • Door hardware — light curtains, obstruction sensors, nudge mode. Named, mocked behind DoorState.
    • A building control room — many buildings, one operator view. That is the HLD version.
    • Fire and freight modes — an override Strategy that pre-empts the stop set. Drops in, no car change.
