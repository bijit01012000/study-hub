    Caching

    7 sections · 614 words

    Temporary storage that trades memory for latency.

    1. The Idea

    A cache stores data temporarily to serve it faster than the DB can:

    • Server asks for key1; the DB takes about 200 ms, the cache about 20 ms.
    • A cache is limited and has a TTL (Time to Live).

    Example scale: a server with an expensive 1 GB of data while the DB holds 2000 TB.

    2. Types of Cache

    • CDN - caches static resources.
    • Load balancer - caches web pages.
    • Server-side caching - Redis.
    • Proxies also use caching.
    • Distributed caching - across cache nodes c1, c2, c3, using consistent hashing.

    3. Cache Data: Retrieval Strategies

    3.1 Cache Aside Technique (Retrieve)

    1. Check the cache.
    2. If found (cache hit), return the data.
    3. If not (cache miss), fetch the data from the DB, put it into the cache, then return the data.
    • Pros: simple to implement; the DB document structure and the cache can differ.
    • Cons: for every new piece of data there will always be a cache miss; pre-heating the cache is needed.

    3.2 Read Through Cache (Retrieval)

    1. If found (cache hit), return the data.
    2. On a cache miss, the cache's internal library automatically fetches the data from the DB, puts it in the cache, and returns it to the server.
    • Pros: the client does not need to bother about DB logic.
    • Cons: the cache document structure must be the same as the DB; there is a cache miss at the start, so the cache must be pre-heated.

    4. Cache Data: Write Strategies

    4.1 Write Through Cache (POST data)

    Write to the cache and DB simultaneously.

    • Pros: consistency will be high.
    • Cons: slow; it uses a two-phase commit (overhead).

    4.2 Write Back / Write Behind Cache

    Write into the cache and asynchronously write to the DB.

    • Pros: fast.
    • Disadvantage: inconsistency can occur.

    4.3 Write Around Technique

    Write data directly to the DB; do not write it to the cache, just invalidate the data in the cache (mark it dirty, for example key = 0 (DIRTY) while key = 1 lives in the DB).

    • Advantage: without using any 2PL, it can maintain consistency.

    5. Cache Eviction Policies

    Because storage is limited and data has a TTL, a policy is needed for how to and what to remove. The candidates:

    • LRU (Least Recently Used).
    • MRU (Most Recently Used).
    • LFU (Least Frequently Used).
    • FIFO (First In First Out).
    • Random.

    5.1 LRU (Least Recently Used)

    When the cache is full, LRU evicts the item that has not been accessed for the longest time.

    • Pros: simplicity.
    • Cons: it assumes past access patterns will repeat in the future.

    5.2 MRU (Most Recently Used)

    • Disadvantage: it does not bother about past records.

    5.3 LFU (Least Frequently Used)

    Evicts the item with the lowest access frequency (for example frequencies 3, 2, 1, 1).

    5.4 FIFO (First In First Out)

    • Pros: simplicity; no need to maintain any timestamp or frequency.
    • Cons: cache misses will be higher.
    • Practically, FIFO is common.

    5.5 Random Cache Eviction

    Assumptions replace algorithms: pick an item at random.

    6. Redis and TTL

    Redis is used for time-bounded entries, for example:

    • key: userName, value: Aditya.
    • TTL is cache specific (Redis).
    • Auth tokens, user ids, and session ids are time bounded.

    7. Where Caching Appears

    • Load balancers.
    • CDN (dynamic caching is also supported).
    • API gateway.
    • Proxies.
    • Server-side caching.
    • Client-side caching - cookies.
