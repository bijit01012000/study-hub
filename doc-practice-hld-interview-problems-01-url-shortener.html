    Design a URL Shortener

    3 sections · 3,639 words

    Three levels: Level 1 — The Shape, Level 2 — The Defence, Level 3 — The Edges.

    Level 1 — The Shape (Foundation)

    Pacing: 3 min ask · 5 min trace flow · 7 min read why.

    The Ask

    Functional

    • Shorten a long URL → short code
    • Redirect short code → original
    • Custom alias (optional)

    Non-Functional

    • p99 redirect < 50 ms ← forces the cache
    • 99.99% read availability ← forces multi-AZ + edge
    • Read : write = 100 : 1 ← forces the path split

    Agree These First

    100 M new links/day · 5-year retention · global traffic. Every number on this sheet falls out of these three. State them before you draw.

    The Shape

    Components and flow:

    • Client — Browser, app, QR scan, email client
    • (1) POST /links — 1 157 rps
    • API Gateway — Auth on write, quota, path split
    • Write Service — POST /links · validate · claim alias
    • ID Generator — Base62 over a leased counter range (1 000/lease)
    • KV Store — links short_code PK → long_url; Cassandra / DynamoDB · partition by hash(short_code) · RF 3; 91 TB @ 5 yr
    • (2) GET /{code} — 115 700 rps · peak 347 K
    • Read Service — GET /{code} · stateless · autoscaled
    • Cache · Redis — Cache-aside · LRU · 24 h TTL · 25 GB hot set; miss ≈ 2%; ≈ 98% hit → DB sees ~7 K rps

    Data model: links short_code PK → long_url.

    Line weight = traffic: READ · 115 K rps; WRITE · 1.1 K rps.

    Say It Like This

    "Two operations — create and resolve — and resolve dominates, call it 100 : 1. So I'd split them: a write service that mints a code, a read service that only looks one up. A lookup is one exact key, so a KV store, not SQL. At 115 K reads a second I put a cache in front of it — that's what buys the 50 ms p99. And I'd return 302, not 301, so the clicks still reach me."

    Defend It

    Decision Prefer Avoid
    (5) Short code Base62 over a leased counter range — 7 chars, no collision UUID → 22 chars, unusable in a URL; MD5 truncated → read-before-write on every insert
    (9) Redirect code 302 Found — clicks reach you, links stay expirable 301 → cached forever; clicks vanish, link can't be re-pointed
    (6) Store Wide-column KV — one exact key, no joins, shards to 91 TB Single-primary Postgres → you'd shard it by year two

    Note (9): 302 Found · Location: original — p99 8 ms, never touches the DB.

    Capacity Math

    Quantity Derivation Value
    Writes 100 M/day ÷ 86 400 s 1 157 /s
    Reads × 100 ratio · peak × 3 347 K /s
    Storage 100 M × 500 B × 365 × 5 yr 91 TB
    Hot set 24 h of active links × ~250 B 25 GB
    DB load peak 347 K × 2% miss — what the cache saves you ≈ 7 K /s

    Round hard, out loud. Nobody is checking your arithmetic — they are checking whether you reach for a number at all. "About a thousand writes a second, a hundred thousand reads" beats a silent exact answer.

    Before You Draw Anything — The Four Moves

    1. Clarify, don't assume. Ask what "shorten" means here: custom aliases? expiry? analytics? Each answer adds a box. — Two minutes of questions buys the whole design.
    2. Agree the scale out loud. "Let's say 100 M links a day, 100:1 reads." Now every later choice has a reason. — An unstated number is an undefendable design.
    3. Draw the happy path only. Client → gateway → service → store. Get agreement before adding anything. — Boxes you add before agreement are boxes you'll defend alone.
    4. Name one trade-off unprompted. Even at L1: "I'd use 302 not 301, because 301 kills the click data." — This is the single move that separates L1 from a junior answer.

    What L1 Is Testing

    • Can you produce a shape without being led to it?
    • Does every box have a reason you volunteered?
    • Did you reach for a number before being asked?

    The Follow-Ups That Decide It

    1. 301 or 302 — and what does each one cost you? (ref 9 — tests: do you know caching has a product consequence)
    2. Why not just hash the URL and take 7 chars? (ref 5 — tests: can you reject the obvious alternative)
    3. Why is there a cache at all? Justify it with a number. (ref 8 — tests: does the box exist for a reason or by habit)
    4. Why two services and not one? (ref 7 — tests: do you split on load profile, or out of habit)
    5. Day one the cache is empty. What does a user see? (ref 8 — tests: can you walk a cold path, not only the happy one)

    At L1 you are being judged on one thing: can you produce a coherent shape and defend three choices inside it. Depth is page 2 — do not reach for it here. Ghosted boxes are what arrives next; you should be able to guess two of them.

    Level 2 — The Defence (Intermediate)

    Pacing: 5 min ask · 15 min trace flow · 10 min read why · 30 min cover & answer.

    The Ask

    Functional

    • Shorten a long URL → short code
    • Redirect short code → original
    • Custom alias (optional)
    • Link expiry / TTL
    • Click analytics

    Non-Functional

    • p99 redirect < 50 ms ← forces the cache
    • 99.99% read availability ← forces multi-AZ + edge
    • Read : write = 100 : 1 ← forces the path split
    • 99.9% write availability ← writes may degrade
    • Links immutable once created ← makes caching safe
    • Codes not sequentially guessable

    Out of Scope — Say It Aloud

    • Accounts, billing, teams
    • Editing a live link
    • Preview / interstitial pages

    Agree These First

    100 M new links/day · 5-year retention · global traffic. Every number on this sheet falls out of these three. State them before you draw.

    The Shape

    Components and flow:

    • Client — Browser, app, QR scan, email client
    • (1) resolve → anycast IP
    • DNS — Anycast · 60 s TTL
    • Edge PoP — TLS · WAF · per-IP rate limit · geo-route
    • (2) POST /links — 1 157 rps
    • API Gateway — Auth on write, quota, path split
    • Write Service — POST /links · validate · claim alias
    • ID Generator — Base62 over a leased counter range (1 000/lease) · scrambled before encoding
    • (7) GET /{code} — 115 700 rps · peak 347 K
    • Read Service — GET /{code} · stateless · autoscaled
    • Cache · Redis — Cache-aside · LRU · 24 h TTL · 25 GB hot set; miss ≈ 2%; ≈ 98% hit → DB sees ~7 K rps
    • (6) Store — Cassandra / DynamoDB · partition by hash(short_code) · RF 3; 91 TB @ 5 yr
    • Kafka — fire-and-forget, click events
    • Consumer — batch + roll up
    • ClickHouse — counts by code / day / geo / referrer

    Data model:

    • links short_code PK · long_url · owner_id · created_at · expires_at
    • clicks rolled up — code · day · geo · referrer · n

    Line weight = traffic: READ · 115 K rps; WRITE · 1.1 K rps; ASYNC · off critical path.

    Say It Like This

    "Two operations — create and resolve — and resolve dominates, call it 100 : 1. So I'd split them: a write service that mints a code, a read service that only looks one up. A lookup is one exact key, so a KV store, not SQL. At 115 K reads a second I put a cache in front of it — that's what buys the 50 ms p99. And I'd return 302, not 301, so the clicks still reach me."

    Defend It

    Decision Prefer Avoid
    (5) Short code Base62 over a leased counter range — 7 chars, no collision; ×coprime mod 62⁷ before encoding — raw counters are walkable UUID → 22 chars, unusable in a URL; MD5 truncated → read-before-write on every insert
    (9) Redirect code 302 Found — clicks reach you, links stay expirable 301 → cached forever; clicks vanish, link can't be re-pointed
    (6) Store Wide-column KV — one exact key, no joins, shards to 91 TB Single-primary Postgres → you'd shard it by year two
    (8) Cache strategy Cache-aside — only links people fetch occupy RAM Write-through → caches 100 M cold links/day
    (2) Rate limit At the edge, before the request enters your VPC In the service → you already paid for the hop and a DB connection
    (10) Click analytics Fire-and-forget to a bus, aggregate offline Sync insert per click → 347 K writes/s on an 8 ms redirect

    Note (9): 302 Found · Location: original — p99 8 ms, never touches the DB.

    Capacity Math

    Quantity Derivation Value
    Writes 100 M/day ÷ 86 400 s 1 157 /s
    Reads × 100 ratio · peak × 3 347 K /s
    Row code 7 B + url ~200 B + owner, ts, ttl + overhead ≈ 500 B
    Storage 100 M × 500 B × 365 × 5 yr 91 TB
    Replicated × RF 3 — the number you actually provision 274 TB
    Keyspace 62⁷ = 3.52 × 10¹² ÷ 100 M/day 96 years
    Hot set 24 h of active links × ~250 B 25 GB
    DB load peak 347 K × 2% miss — what the cache saves you ≈ 7 K /s

    Storage is never the constraint here — read throughput is. 91 TB is unremarkable. 347 K rps against it is the whole problem, and it is why the cache exists rather than a bigger database.

    What Breaks — Say It Before They Ask

    • (8) Cache stampede. A viral link's TTL expires and 50 K concurrent misses hit one partition. — Fix: single-flight on miss + jittered TTL
    • (5) Counter restart. ID service dies mid-lease and re-issues a range it already handed out. — Fix: persist the high-water mark before leasing, never after
    • (6) Hot partition. Sharding cannot split a single key — one viral code is one partition. — Fix: the cache absorbs it. If Redis dies, that shard is your outage
    • (4) Alias race. Two users POST the same custom alias in the same millisecond; both read "free", both write. — Fix: conditional write (IF NOT EXISTS), not read-then-write
    • (2) Open redirect. Your domain becomes a phishing laundromat and gets blocklisted. — Fix: scan on create + domain blocklist + interstitial for new domains

    The Follow-Ups That Decide It

    1. 301 or 302 — and what does each one cost you? (ref 9 — tests: do you know caching has a product consequence)
    2. Why not just hash the URL and take 7 chars? (ref 5 — tests: can you reject the obvious alternative)
    3. Why is there a cache at all? Justify it with a number. (ref 8 — tests: does the box exist for a reason or by habit)
    4. Your codes come off a counter. Can I enumerate every link you hold? (ref 5 — tests: did you notice your own requirement was unmet)
    5. One link hits 50 K rps. What saturates first? (ref 8 — tests: can you find your own bottleneck)
    6. Two users claim the same alias in the same millisecond. (ref 4 — tests: concurrency instinct, not vocabulary)
    7. How do you expire 100 M links/day without scanning? (ref 6 — tests: do you know what a full scan costs at 91 TB)

    Cover The Sheet · Answer Aloud

    Use it as revision: cover the right rail and the two panels to your left, then walk the numbered path out loud. If you cannot say why a box is there and what breaks it, that box is your gap.

    Level 3 — The Edges (Advanced)

    Pacing: 10 min ask · 25 min trace flow · 15 min read why · 40 min cover & answer.

    The Ask

    Functional

    • Shorten a long URL → short code
    • Redirect short code → original
    • Custom alias (optional)
    • Link expiry / TTL
    • Click analytics

    Non-Functional

    • p99 redirect < 50 ms ← forces the cache
    • 99.99% read availability ← forces multi-AZ + edge
    • Read : write = 100 : 1 ← forces the path split
    • 99.9% write availability ← writes may degrade
    • Links immutable once created ← makes caching safe
    • Codes not sequentially guessable
    • Redirect works if a whole region is lost ← forces multi-region

    Out of Scope — Say It Aloud

    • Accounts, billing, teams
    • Editing a live link
    • Preview / interstitial pages

    Agree These First

    100 M new links/day · 5-year retention · global traffic. Every number on this sheet falls out of these three. State them before you draw.

    Components and flow:

    Egress 347 K/s × ~400 B of redirect headers 139 MB/s
    Nodes 274 TB ÷ ~2 TB usable per node ≈ 140
    After edge 347 K/s − 40% at the PoP → origin sees 208 K /s
