    System design (the blank-page round)

    9 sections · 3,934 words

    Module 11 - 9 questions - 1 practical drill

    Drive the blank page with estimates, explicit trade-offs and failure paths.

    The open-ended round where candidates either drive a structured design or freeze. The follow-ups here aren't gotchas - they're the interviewer pushing on scale estimates, the bottleneck you hand-waved, and the failure mode you skipped. Every design question below includes the drill of actually estimating and defending.

    Inside this module: Requirements - Capacity estimates - Architecture - Bottlenecks

    Q11.1 - Design a URL shortener.

    What it really tests: Whether the candidate drives a structured design - requirements, estimates, key generation, storage, scale - rather than jumping to code.

    Weak answer: "I'd have a database mapping short codes to long URLs. When someone creates a short URL I generate a random code and store it, and when they visit it I look it up and redirect."

    Why it fails: - No requirements clarification or scale estimation first. - "Random code" - no collision handling or length reasoning. - No read/write ratio driving the storage and caching choices. - No discussion of the redirect path being the hot path.

    Follow-up ladder: 1. MEASUREMENT - How long is the short code, and how did you calculate that? - Back-of-envelope from the key space. 2. TECHNICAL - How do you generate codes without collisions at scale? - Counter+base62 vs hash vs random. 3. TRADEOFF - Reads vastly outnumber writes here - how does that shape the design? - Read-heavy optimisation / caching. 4. REFLECTION - 301 or 302 redirect, and what does that choice cost you? - Caching vs analytics trade-off.

    Answer framework: 1. Clarify requirements + scale 2. Estimate traffic and storage 3. Key generation strategy (length, collisions) 4. Storage choice by access pattern 5. Cache the hot read path 6. Redirect semantics 7. Scale out (stateless web, replicas/sharding) 8. Failure and analytics considerations

    Rejection signals: - Jumps to schema with no requirements or estimates. - No collision strategy. - Ignores the read-heavy nature. - Can't justify code length.

    Model answer skeleton: First I clarify scope and estimate: say 100M new URLs a month and a 100:1 read-to-write ratio, which tells me it's overwhelmingly a read system and drives every later choice. For the code length, with base62 (a-z, A-Z, 0-9), 7 characters gives 62^7 of roughly 3.5 trillion combinations, comfortably enough for years, so 7 chars it is.

    For generation I'd use a distributed counter encoded in base62 rather than random-and-check, because a counter never collides and avoids a read-before-write, whereas random needs a uniqueness check that gets slow as the space fills.

    The mapping lives in a store keyed by short code - a simple KV access pattern, so it shards cleanly - and because reads dominate I put a cache (Redis) in front, where the hot codes live so most redirects never touch the database. The redirect path is the hot path, so I keep it dead simple.

    I'd use a 302 rather than 301 if I want click analytics, accepting that 301s would be cached by browsers and cut my traffic but also my data.

    Web tier is stateless so it scales horizontally, and the store scales via replicas for reads and sharding by code for writes.

    Q11.2 - Design a rate limiter that works across a fleet of servers.

    What it really tests: Distributed counting, algorithm choice, and the accuracy-vs-performance trade-off.

    Weak answer: "Each server keeps a counter of requests per user, and if it exceeds the limit we reject the request with an error."

    Why it fails: - Per-server counters let a user exceed the global limit N-fold across N servers. - No algorithm named (token bucket, sliding window). - No shared state for distributed counting. - Doesn't return 429 / Retry-After.

    Follow-up ladder: 1. FAILURE - Per-server counters - how does a user beat the global limit? - The distributed-counting problem. 2. TECHNICAL - Token bucket vs sliding window - trade-offs? - Algorithm understanding. 3. TRADEOFF - Where does the shared counter live and what's the latency cost? - Redis + per-request round trip. 4. MEASUREMENT - Redis is down - do you fail open or closed on rate limiting? - Availability vs protection.

    Answer framework: 1. Choose the limit dimension 2. Algorithm (token bucket / sliding window) 3. Shared store for the count (Redis) 4. Atomic increment/check 5. Return 429 + Retry-After 6. Local approximation to cut round trips 7. Fail-open vs fail-closed on store outage 8. Per-tenant fairness

    Rejection signals: - Per-server counters, no shared state. - No algorithm. - No 429/Retry-After. - No plan for the rate-limiter store failing.

    Model answer skeleton: The core problem is that per-server counters don't hold globally - with 10 servers and a per-server limit, a user spreading requests across them gets 10x the intended limit - so the count has to be shared. I'd use Redis for the shared counter and a token-bucket algorithm, which allows short legitimate bursts while capping the sustained rate, implemented atomically with a Lua script so the check-and-decrement can't race.

    Sliding-window log is more precise but memory-heavy; sliding-window counter is a good middle ground; token bucket wins for burst tolerance, so I'd pick by whether bursts are desirable.

    I limit per API key for fairness so one tenant can't starve others, and I return 429 with a Retry-After so well-behaved clients back off precisely.

    The per-request Redis round trip adds latency, so at very high scale I'd approximate locally - each server takes a lease of tokens from Redis and limits locally between syncs - trading a little accuracy for far fewer round trips.

    And I'd decide deliberately that if Redis is down I fail open, because blocking all traffic to protect against overuse is usually worse than briefly under-enforcing the limit.

    Q11.3 - Design a notification system that sends push, email, and SMS.

    What it really tests: Event-driven design, fan-out, user preferences, delivery reliability, and rate control.

    Weak answer: "There'd be a notification service that takes a request and sends the notification through the right channel - push, email, or SMS - based on the type."

    Why it fails: - Synchronous sending couples the caller to slow third-party providers. - No queue/decoupling for reliability and retries. - No user preference / opt-out handling. - No dedup, rate limiting, or delivery-failure handling.

    Follow-up ladder: 1. FAILURE - The SMS provider is slow or down - how does that not block the sender? - Async decoupling + retries. 2. TRADEOFF - How do you respect user preferences and prevent notification fatigue? - Preference store + rate control. 3. TECHNICAL - How do you avoid sending the same notification twice? - Idempotency / dedup. 4. MEASUREMENT - Which notifications need real-time vs batched delivery? - Priority-aware routing.

    Answer framework: 1. Event ingress 2. Queue for decoupling 3. Preference/opt-out check 4. Template rendering 5. Per-channel delivery workers 6. Retries + DLQ on provider failure 7. Idempotency/dedup 8. Rate limiting per user 9. Priority lanes 10. Delivery status tracking

    Rejection signals: - Synchronous sending, no queue. - No preference handling. - No retry/DLQ for provider failures. - No dedup.

    Model answer skeleton: I'd make it event-driven so the caller isn't coupled to slow providers. A producer emits a notification event onto a queue; the notification service consumes it, checks the user's preferences and opt-outs (a preference store), renders the template, and hands off to a per-channel delivery worker - push, email, SMS - each talking to its provider.

    Decoupling via the queue is what gives reliability: if the SMS provider is down, the sender isn't blocked, and the worker retries with backoff and, after N failures, dead-letters the message for inspection rather than losing it.

    I make delivery idempotent with a notification id so a redelivered event doesn't double-send, which matters a lot for SMS and push. Preferences plus per-user rate limiting prevent notification fatigue - I cap how many a user gets in a window and let them opt out per channel.

    I'd add priority lanes: an urgent security alert goes real-time while a digest can be batched.

    And I track delivery status per channel so we know what actually landed, with the provider webhooks feeding back delivery/bounce events.

    Q11.4 - Design a system to process a large uploaded file (say a 5GB CSV) reliably.

    What it really tests: Streaming vs loading into memory, chunking, idempotency, progress, and failure recovery on long jobs.

    Weak answer: "I'd read the file, parse the rows, and insert them into the database. If it's large I'd maybe do it in the background so it doesn't block the request."

    Why it fails: - "Read the file" implies loading 5GB into memory - OOM. - No chunking or streaming. - No resumability if the job fails at row 4 million. - No idempotency, so a retry re-inserts everything.

    Follow-up ladder: 1. FAILURE - Loading 5GB into memory - what happens? - Streaming vs buffering. 2. TECHNICAL - The job dies at row 4M of 5M - how do you resume without duplicating? - Checkpointing + idempotency. 3. MEASUREMENT - How do you show progress and handle partial failures / bad rows? - Progress + error handling. 4. TRADEOFF - How would you parallelise this safely? - Chunk-level parallelism.

    Answer framework: 1. Accept upload to object storage 2. Process asynchronously (job) 3. Stream/parse in chunks, never load whole 4. Checkpoint progress 5. Idempotent per-row/per-chunk writes 6. Handle and quarantine bad rows 7. Report progress + final status 8. Parallelise by chunk 9. Retry/resume from checkpoint

    Rejection signals: - Loads the whole file into memory. - No resumability. - No idempotency on retry. - No bad-row handling.

    Model answer skeleton: First I decouple: the upload lands in object storage (S3) and returns immediately, then an async job processes it, because a 5GB file has no business being handled in a request. The job streams the file rather than loading it - read and parse in chunks so memory stays flat regardless of file size, since loading 5GB into memory just OOMs the worker.

    For reliability on a long job I checkpoint progress - record the last processed offset or row batch - so if the worker dies at row 4M it resumes from the last checkpoint instead of restarting, and I make the writes idempotent (upsert on a natural key, or track processed chunk ids) so resuming or retrying can't double-insert.

    Bad rows don't kill the job: I validate per row, write failures to a quarantine/error report with row numbers, and keep going, so one malformed line doesn't sink 5 million good ones.

    I surface progress - percentage and a final summary of inserted vs failed - via the job status.

    To speed it up I split the file into chunks processed in parallel by multiple workers, each idempotent and checkpointed independently, which also makes retries granular.

    Q11.5 - Design the backend for a feature that shows a user's activity feed.

    What it really tests: The fan-out-on-write vs fan-out-on-read trade-off, caching, and pagination - a canonical design.

    Weak answer: "When a user opens their feed, I query all the people they follow and get the recent posts, sort by time, and return them."

    Why it fails: - Fan-out-on-read for a user following thousands is a huge, slow query on every open. - No caching of the assembled feed. - No pagination strategy (offset drift under new posts). - Doesn't consider the celebrity / high-follow-count problem.

    Follow-up ladder: 1. TECHNICAL - A user follows 5,000 people - what's the cost of building the feed on read? - Fan-out-on-read cost. 2. TRADEOFF - Fan-out-on-write vs on-read - when each? - The core design trade-off. 3. FAILURE - A celebrity with 10M followers posts - what breaks in fan-out-on-write? - The hot-key / write-amplification problem. 4. MEASUREMENT - How do you paginate a feed that's changing as you scroll? - Cursor pagination.

    Answer framework: 1. Clarify scale and read/write ratio 2. Fan-out-on-write (precompute feeds) as default 3. Store per-user feed in a fast store 4. Cache hot feeds 5. Hybrid for high-follow-count / celebrities (pull on read) 6. Cursor pagination 7. Handle deletes/edits 8. Trade latency vs write cost

    Rejection signals: - Only fan-out-on-read, unaware of the cost. - No caching or precomputation. - No celebrity-case handling. - Offset pagination on a changing feed.

    Model answer skeleton: The central decision is fan-out-on-write versus on-read. On-read - query everyone you follow at open time - is simple but for a user following thousands it's a massive scatter-gather on every single feed load, which is too slow at scale.

    So my default is fan-out-on-write: when someone posts, I push that post id into the precomputed feed of each follower, stored in a fast per-user structure (a Redis list or a feeds table), so opening the feed is a cheap read of an already-assembled list.

    I cache the hot feeds. The failure mode of pure fan-out-on-write is the celebrity: a user with 10M followers posting means 10M writes per post, a write-amplification spike - so I go hybrid, keeping fan-out-on-write for normal accounts but pulling posts from high-follow-count accounts on read and merging them in, which caps the write blast radius.

    I paginate with cursors keyed on (timestamp, post id) rather than offset, so new posts arriving while the user scrolls don't cause duplicates or skips.

    Edits and deletes are handled by storing post ids in the feed and resolving content at read time, so I don't have to rewrite every follower's feed on an edit.

    Q11.6 - How do you approach a system design question you've never seen before?

    What it really tests: Whether the candidate has a repeatable method, or relies on having memorised specific designs.

    Weak answer: "I'd think about what components are needed - a database, an API, maybe a cache and a queue - and put them together into an architecture."

    Why it fails: - Jumps to components before requirements and scale. - No clarifying questions. - No estimation to drive decisions. - No structured progression or trade-off discussion.

    Follow-up ladder: 1. TECHNICAL - What do you nail down before drawing a single box? - Requirements-first discipline. 2. MEASUREMENT - How do estimates change your design decisions? - Numbers driving architecture. 3. TRADEOFF - How do you decide what to go deep on versus keep shallow? - Time management / signalling depth. 4. REFLECTION - How do you surface bottlenecks before the interviewer does? - Proactive failure analysis.

    Answer framework: 1. Clarify functional + non-functional requirements 2. Estimate scale (QPS, storage, read/write ratio) 3. Define the API 4. Sketch high-level components 5. Identify the bottleneck and go deep there 6. Discuss trade-offs explicitly 7. Address failure modes and scaling 8. Summarise

    Rejection signals: - Starts drawing boxes with no requirements. - No estimation. - Uniform shallow coverage, no depth anywhere. - Waits for the interviewer to find the bottleneck.

    Model answer skeleton: I run the same method regardless of the problem, which is what makes an unseen question fine. First I clarify requirements - functional (what must it do) and non-functional (scale, latency, consistency, availability) - and I ask questions rather than assume, because the constraints decide the design.

    Then I estimate: expected QPS, read/write ratio, storage growth - back-of-envelope numbers, because '100:1 reads' or '10M writes a day' directly drives whether I cache, shard, or precompute.

    I define the API next so the data flow is concrete, then sketch the high-level components, then pick the one part that's the real bottleneck and go deep there - the feed assembly, the rate-limiter counter, whatever it is - rather than spreading shallow attention everywhere. Throughout I make trade-offs explicit ('SQL for the transactions, but I'll denormalise this read path'), and I proactively call out failure modes and how I'd scale each tier, so I'm surfacing the hard parts before the interviewer has to.

    I close with a short summary of the design and its main trade-offs.

    The structure is the signal - it shows I can drive a design, not just recite one.

    Q11.7 - Where's the bottleneck in your design, and what happens when you 10x the traffic?

    What it really tests: Whether the candidate can critique their own design and reason about the next scaling wall.

    Weak answer: "I think the design scales well. We could add more servers if traffic increased, so it should handle 10x fine."

    Why it fails: - "Add more servers" ignores stateful bottlenecks (the database). - No identification of the actual first thing to break. - No reasoning about which tier saturates first. - Overconfident, no self-critique.

    Follow-up ladder: 1. TECHNICAL - The web tier scales - but what about the single database? - Stateful bottleneck awareness. 2. FAILURE - What breaks first at 10x, and what's the symptom? - Predicting the failure. 3. TRADEOFF - Reads or writes - which wall do you hit first, and how do you push it back? - Replicas vs sharding. 4. REFLECTION - What's the next bottleneck after you fix that one? - Iterative scaling thinking.

    Answer framework: 1. Identify stateless vs stateful tiers 2. Stateless scales horizontally 3. The database is the usual first wall 4. Reads: add replicas/cache 5. Writes: shard/partition 6. Predict the symptom (latency, pool exhaustion) 7. Then the next bottleneck (hot shard, cache capacity) 8. Trade-offs of each fix

    Rejection signals: - "Add more servers" for a database bottleneck. - Can't name what breaks first. - No reads-vs-writes distinction. - No self-critique.

    Model answer skeleton: The stateless tiers - the web and application servers - scale by adding instances behind a load balancer, so they're not my worry. The bottleneck is almost always the stateful tier, the database, because you can't just clone it.

    At 10x, the first symptom I'd expect is the primary saturating - connection pool exhaustion and rising query latency under the write and read load.

    For reads I push that wall back with read replicas and aggressive caching, so most reads never touch the primary. But replicas don't help writes, so once writes are the ceiling I have to shard - partition the data by a key like user id or tenant so writes spread across shards - accepting the complexity that brings, like cross-shard queries and rebalancing.

    And I'd be honest that fixing one bottleneck reveals the next: after sharding, a hot shard from a skewed key becomes the problem, or the cache's memory becomes the limit, so scaling is iterative.

    The point is I can tell you the order things break in and the specific lever for each, rather than waving 'add servers'.

    Q11.8 - Design a system that must never lose a submitted order, even during failures.

    What it really tests: Durability, at-least-once processing, idempotency, and the outbox pattern - reliability-first design.

    Weak answer: "I'd save the order to the database as soon as it comes in, and use transactions to make sure it's saved reliably. Then process it."

    Why it fails: - Saving to the DB is necessary but doesn't cover the async processing that follows. - No durable handoff between accepting and processing (dual-write risk). - No idempotency, so retries could duplicate the order. - No acknowledgement semantics to the client.

    Follow-up ladder: 1. TECHNICAL - You save the order, then need to publish it for processing - how do you avoid the dual-write problem? - Transactional outbox. 2. FAILURE - The processing worker crashes mid-order - is it lost or duplicated? - At-least-once + idempotency. 3. TRADEOFF - When do you acknowledge the order to the customer? - Durable-accept before ack. 4. MEASUREMENT - How do you prove nothing was lost - reconciliation? - Auditability.

    Answer framework: 1. Durably persist on accept (in a transaction) 2. Outbox row in the same transaction 3. Ack the customer after durable accept 4. Relay outbox to a queue 5. At-least-once processing 6. Idempotent workers 7. DLQ for poison orders 8. Reconciliation to prove completeness

    Rejection signals: - Dual-write (save then publish) with no outbox. - No idempotency. - Acks before durable persistence. - No reconciliation/audit.

    Model answer skeleton: The durability chain has to be unbroken from accept to done. On submit I persist the order in a database transaction, and in that same transaction I write a row to an outbox table describing the 'process this order' event - so the order and the intent-to-process commit atomically, avoiding the dual-write bug where I save the order but the publish fails and processing never happens.

    Only after that durable commit do I acknowledge the order to the customer, so a crash before persistence means the customer sees a failure and retries, rather than believing an order landed that didn't.

    A relay reads the outbox and publishes to a durable queue, and the processing workers consume at-least-once - so a worker crash mid-order causes redelivery, not loss. Because it's at-least-once, the workers are idempotent, keyed on the order id, so a redelivered order isn't processed twice.

    Orders that repeatedly fail go to a DLQ for a human rather than being dropped.

    And I run a reconciliation job comparing accepted orders to completed ones, which is how I can actually prove nothing was silently lost, rather than just asserting it.

    Q11.9 - [DRILL] Do the back-of-envelope for a service handling 1M daily active users, each making 20 requests/day, with a 100:1 read/write ratio. Derive QPS, storage/year, and where you'd cache.

    What it really tests: Whether the candidate can actually do estimation - the step most people skip and interviewers weight heavily.

    Weak answer: N/A - drill. A weak attempt guesses "it's a lot of traffic" without numbers.

    Why it fails: - No actual arithmetic. - No peak-vs-average QPS distinction. - No storage projection. - Doesn't connect the numbers to a caching/sharding decision.

    Follow-up ladder: 1. MEASUREMENT - What's average QPS, and what peak multiplier do you assume? - Average vs peak reasoning. 2. TECHNICAL - Given 100:1 reads, what does that tell you to cache? - Numbers driving architecture. 3. TRADEOFF - At this storage growth, when do you need to shard? - Projecting the scaling wall.

    Answer framework: 1. Total requests/day = users x req/user 2. Average QPS = requests / 86,400 3. Apply a peak factor (2-3x) 4. Split reads/writes by the ratio 5. Storage/record x writes/day x 365 6. Decide caching from the read share 7. Project when sharding is needed

    Rejection signals: - No arithmetic at all. - Only average QPS, ignores peak. - No storage projection. - Numbers don't inform any decision.

    Model answer skeleton: Drill output: 1M DAU x 20 requests = 20M requests/day.

    Divided by ~86,400 seconds is about 230 average QPS, but traffic isn't flat, so I apply a peak factor of ~3x for busy hours, giving ~700 peak QPS to design for.

    With a 100:1 read/write ratio, of those 20M daily requests roughly 200K are writes and 19.8M are reads - so this is overwhelmingly a read system, which immediately tells me to cache aggressively and add read replicas, because the reads are where the load is and most can be served from cache.

    For storage, say each write stores ~1KB: 200K writes/day x 1KB is about 200MB/day, or ~73GB/year, plus indexes call it ~100GB/year - modest, so a single well-provisioned Postgres with replicas handles it comfortably for a few years, and I wouldn't shard prematurely; I'd project the shard point at maybe 5-10x this growth or when write QPS stresses one primary.

    The value of doing this is that the numbers, not my gut, decided 'cache-heavy, replicas yes, sharding not yet'.
