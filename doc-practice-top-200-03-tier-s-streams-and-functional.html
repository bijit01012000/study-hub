      31. Stream API — lazy evaluation explained

      Asked at: Common at all levels

      Difficulty: Medium · Topic: Streams

      The question: "Explain lazy evaluation in Java streams. What's the difference between intermediate and terminal operations?"

      The 30-second answer: Intermediate operations (map, filter, sorted, etc.) are LAZY — they build up a pipeline but don't execute. Terminal operations (collect, forEach, reduce, count, etc.) TRIGGER execution and consume the stream. Until the terminal op runs, nothing in the chain executes — useful for findFirst over an infinite stream, etc.

      Step-by-step thought process:

      1. " Stream is a lazy pipeline of operations. stream.filter(p).map(f) doesn't iterate the source — it returns a new Stream object describing the intended pipeline."
      2. "Terminal operations (collect, count, forEach, findFirst, reduce, toArray) consume the stream and trigger execution. After a terminal op, the stream is closed — you can't use it again."
      3. "Laziness enables short-circuiting: findFirst() after filter() stops as soon as one match is found, even on an infinite stream from Stream.iterate() or Stream.generate()."
      4. "Laziness also enables fusion: the runtime can combine adjacent map+filter operations into one pass over the source, instead of N intermediate collections."
      5. "Caveat: peek() is sometimes elided if the runtime determines its result is unused — don't rely on peek for side effects you need."

      Edge cases to mention:

      • A Stream can only be consumed once — s.count() then s.collect() throws IllegalStateException
      • Sort is partially lazy — it's intermediate, but to know the order it must consume the entire upstream before emitting
      • Parallel streams change execution strategy but the laziness contract is the same

      What NOT to say:

      • "Stream is just a fancy iterator" — misses the lazy + parallel + functional model
      • "Always materialize to a list with .collect() " — fine for finite, fast streams; wrong for infinite or huge ones

      Common follow-up: "What's the difference between map and flatMap?"

      32. Parallel streams — when do they actually help?

      Asked at: Senior rounds, often as a trap question

      Difficulty: Medium-Hard · Topic: Parallelism

      The question: "When does .parallelStream() actually perform better than .stream(), and when is it a trap?"

      The 30-second answer: Helps when: (1) CPU-bound work per element is non-trivial, (2) source splits well (ArrayList, ranges — not LinkedList or generated streams), (3) you have many elements (rough rule: at least thousands), (4) you're using the commonPool appropriately. Trap when: tasks are IO-bound, source is hard to split, or the work per element is tiny.

      Step-by-step thought process:

      1. " parallelStream() uses ForkJoinPool.commonPool() — by default sized to Runtime.availableProcessors() - 1 (one worker fewer than logical processors, leaving room for the submitting thread)."
      2. "For CPU-bound work, parallelism speedup is roughly bounded by core count, minus overhead."
      3. "The source matters: ArrayList and IntStream.range split cleanly (random access, known size). LinkedList must walk to split — defeats the purpose. Stream.iterate is sequential by design."
      4. "Per-element work cost matters: simple map operations are dominated by stream overhead, often slower than sequential. Heavy work per element wins."
      5. "Element count matters: under ~1000 elements, sequential is usually faster because parallelization setup costs more than the savings."
      6. "Trap: IO-bound work in parallel streams clogs the common ForkJoinPool, slowing every other parallel operation in the JVM."

      Edge cases to mention:

      • forEachOrdered preserves encounter order but kills parallelism — use forEach if order doesn't matter
      • Custom parallel executor: there's no clean API, but submitting via ForkJoinPool.submit(() -> stream.parallel().count()) runs in your pool
      • Java 21 virtual threads + sequential streams is often the better answer for IO-bound work

      What NOT to say:

      • "Parallel is always faster" — common mistake, often false
      • "Use parallel streams for IO-bound work" — actively bad advice

      Common follow-up: "How would you parallelize IO-bound work in Java 21?"

      33. Optional — what NOT to do with it

      Asked at: Code review style questions, all levels

      Difficulty: Medium · Topic: Idiomatic Java

      The question: "Show me the right and wrong ways to use Optional in Java."

      The 30-second answer: Optional was designed for return types where absence is meaningful (e.g. findById()). DON'T use it for: fields, parameters, collection types, or as a generic null-replacement. DON'T call .get() without checking presence. DO use .map, .flatMap, .orElse, .ifPresent for chaining.

      Step-by-step thought process:

      1. "Optional is a return-type contract — 'this method may not return a value, and you must handle that.' Designed for stream terminals (findFirst, findAny, reduce with no identity) and 'lookup by ID' patterns."
      2. "Anti-pattern #1: Optional as field. Adds an extra object, doesn't serialize cleanly, and forces every read to unwrap."
      3. "Anti-pattern #2: Optional as method parameter. Caller can pass Optional.empty() OR null OR a real value — three states instead of two. Just overload or use null."
      4. "Anti-pattern #3: optional.get() without isPresent() check — same NullPointerException-equivalent, but more verbose."
      5. "Idiomatic chaining: findUser(id).map(User::getEmail).orElse("unknown@example.com")."
      6. " ifPresent for side effects, orElseGet(supplier) if the default is expensive to compute."

      Edge cases to mention:

      • Optional.of(value) throws if value is null; Optional.ofNullable(value) doesn't — pick deliberately
      • Optional<List<T>> is almost always wrong — return empty list instead
      • Java 10 added orElseThrow() (no arg) — throws NoSuchElementException, useful when absence is "impossible"

      What NOT to say:

      • "Use Optional everywhere to avoid NullPointerExceptions" — adds boilerplate without solving root cause
      • "Optional is faster than null checking" — has allocation cost, marginally slower

      Common follow-up: "What's orElseGet vs orElse?"

      34. Method references vs lambdas

      Asked at: Common at all levels

      Difficulty: Easy-Medium · Topic: Functional Java

      The question: "When would you use a method reference instead of a lambda?"

      The 30-second answer: When the lambda just delegates to an existing method. s -> s.length() becomes String::length. (a, b) -> Integer.compare(a, b) becomes Integer::compare. Cleaner to read, no extra closure, sometimes more efficient. Four kinds: static, bound instance, unbound instance, constructor.

      Step-by-step thought process:

      1. " Type::staticMethod — Integer::parseInt. Equivalent to s -> Integer.parseInt(s)."
      2. " instance::instanceMethod — out::println. The instance is captured."
      3. " Type::instanceMethod — String::length. The instance becomes the first parameter — s -> s.length()."
      4. " Type::new — constructor reference. ArrayList::new is () -> new ArrayList()."
      5. "Use them when the lambda body is just a method call — primarily a readability win. Bytecode-wise, both lambdas and method references compile to invokedynamic via LambdaMetafactory, so there's no consistent performance difference."

      Edge cases to mention:

      • this::method is fine in OO code — captures this implicitly, equivalent to arg -> this.method(arg)
      • Ambiguous method references (overloaded methods, multiple matches) need a cast to clarify
      • A method reference is just sugar — same Functional Interface invariants apply

      What NOT to say:

      • "Method references are faster than lambdas" — sometimes true, but trivial in practice; don't pick on perf grounds
      • "Use method references everywhere" — sometimes the lambda body adds clarity (renaming variables for readability)

      Common follow-up: "What's a Functional Interface?"

      35. forEach vs for-each loop — which when?

      Asked at: Code review, mid-level

      Difficulty: Easy-Medium · Topic: Idiomatic Java

      The question: "When would you use Collection.forEach() vs the enhanced for-loop? Are they interchangeable?"

      The 30-second answer: Functionally similar for simple iteration. Differences: (1) forEach can't break early or use continue. (2) Enhanced for-loop can mutate the collection only via Iterator.remove; forEach shouldn't mutate. (3) forEach reads better in chains; enhanced for is more flexible for complex logic.

      Step-by-step thought process:

      1. " for (T item: collection) { … } is the enhanced forloop — desugars to an Iterator-based loop. Supports break, continue, return."
      2. " collection.forEach(item -> { … }) is the lambda-based forEach. Cannot break — return inside the lambda only exits the current iteration (like continue)."
      3. "For chained stream operations, stream().filter().map().forEach() reads cleanly. For standalone iteration with control flow, enhanced for is more flexible."
      4. " forEach doesn't guarantee order on parallel streams — use forEachOrdered if you need it."
      5. "Concurrent modification: enhanced for-loop with Iterator.remove() is the safe way to remove during iteration. forEach followed by collection.removeAll(toRemove) is the lambda equivalent."

      Edge cases to mention:

      • Map's forEach((k, v) ->...) replaces for (Map.Entry<K,V> e: map.entrySet()) {... } — usually cleaner
      • Collection.removeIf(predicate) is the cleanest "remove while iterating" pattern
      • forEach is part of Iterable, so any Iterable (not just Collection) supports it

      What NOT to say:

      • "forEach is faster" — usually the same; for tiny operations, enhanced-for can be slightly faster (no lambda boxing)
      • "Always use forEach in modern Java" — sometimes worse readability

      Common follow-up: "How would you remove items from a list while iterating?"

      36. Collectors — beyond toList and toMap

      Asked at: Common in idiomatic-Java rounds

      Difficulty: Medium · Topic: Streams

      The question: "What Collectors do you reach for beyond toList() and toMap()?"

      The 30-second answer: groupingBy for partitioning by key, partitioningBy for boolean split, joining for string concatenation, counting and summingInt / averagingInt for aggregations. Chain these with downstream collectors for sophisticated reductions in one pass.

      Step-by-step thought process:

      1. " groupingBy(classifier) → Map<K, List<T>>. Group employees by department: employees.stream().collect(groupingBy(Employee::getDept))."
      2. " groupingBy(classifier, downstream) chains another collector. groupingBy(Employee::getDept, counting()) → Map<String, Long> of dept → headcount."
      3. " partitioningBy(predicate) → Map<Boolean, List<T>>. Split adults from minors in one pass."
      4. " joining(delimiter, prefix, suffix) → String. Concatenate names with commas: joining(", ", "[", "]")."
      5. " teeing(c1, c2, merger) (Java 12+) feeds the stream to two collectors and combines. E.g. compute min and max in one pass."

      Edge cases to mention:

      • toMap throws on duplicate keys unless you supply a merge function: toMap(K, V, (existing, replacement) -> existing)
      • groupingBy uses a HashMap by default; use the 3-arg version with TreeMap::new for sorted output Collectors.collectingAndThen(downstream, finisher) post-processes the result — e.g. collectingAndThen(toList(), Collections::unmodifiableList) returns an immutable list

      What NOT to say:

      • "Just collect to List and process after" — slower, loses one-pass benefit
      • "Stream collectors are complicated, just use loops" — defeats the point of streams

      Common follow-up: "How would you compute the average salary per department in one pass?"

      37. Lambdas vs anonymous inner classes

      Asked at: Fresher to mid-level

      Difficulty: Easy-Medium · Topic: Lambdas

      The question: "What's the difference between a lambda and an anonymous inner class?"

      The 30-second answer: Both implement a functional interface. Lambda is sugar over invokedynamic (no .class file generated), inherits the enclosing this, can only access effectively-final variables. Anonymous inner class generates an extra class, creates a new this (and a synthetic reference to the enclosing instance), can access effectively-final variables only too.

      Step-by-step thought process:

      1. "Lambda: Runnable r = () -> doSomething(); — no .class file, generated at runtime via invokedynamic. this inside the lambda refers to the enclosing class instance."
      2. "Anonymous inner class: Runnable r = new Runnable() { public void run() { doSomething(); } }; — generates an EnclosingClass$1.class, has its own this (the inner instance), holds an implicit reference to the enclosing instance via EnclosingClass.this."
      3. "Memory: lambdas without captured state can be a single shared instance (constant). Anonymous classes allocate fresh per invocation."
      4. "Variable capture: both can only capture effectively-final local variables — i.e. variables you don't reassign after the lambda/inner-class is defined."
      5. "Use lambdas for short functional bodies. Use anonymous inner classes when you need multiple methods, or when you need a fresh this (rare)."

      Edge cases to mention:

      • Anonymous classes can extend abstract classes; lambdas can only implement single-abstract-method interfaces
      • Lambdas don't introduce a new scope — variable shadowing rules are different
      • Memory footprint: a no-capture lambda is essentially zero allocation per call (cached); an anonymous inner class is at least one allocation

      What NOT to say:

      • "They're the same thing" — close, but this semantics differ
      • "Lambdas are syntactic sugar for inner classes" — close, but invokedynamic doesn't generate an inner class

      Common follow-up: "What does 'effectively final' mean?"

      38. Functional interface — what makes one?

      Asked at: Fresher to mid-level

      Difficulty: Easy-Medium · Topic: Lambdas

      The question: "What's a functional interface? Can you list the most-used ones in java.util.function?"

      The 30-second answer: A functional interface has exactly ONE abstract method (SAM — Single Abstract Method). Lambdas can be assigned to any functional interface. @FunctionalInterface annotation makes the compiler enforce this. Most-used: Function<T,R>, Predicate<T>, Consumer<T>, Supplier<T>, BiFunction<T,U,R>.

      Step-by-step thought process:

      1. "A functional interface has exactly one abstract method. Default and static methods don't count."
      2. " @FunctionalInterface is optional but recommended — the compiler errors if you accidentally add a second abstract method."
      3. "Standard library has Runnable, Callable, Comparator (all SAM) plus the java.util.function package: Function, Predicate, Consumer, Supplier, plus primitive specializations (IntFunction, LongPredicate, etc.) to avoid boxing."
      4. "You can compose them: Predicate.and(), Predicate.or(), Function.andThen(), Function.compose()."
      5. "Custom functional interfaces are useful when standard ones don't fit — e.g. a TriFunction<A, B, C, R> doesn't exist in the JDK."

      Edge cases to mention:

      • Interfaces with one abstract method + multiple defaults are still functional interfaces (e.g. Comparator)
      • Two interfaces with the same method signature are NOT compatible for lambda assignment — you must pick a concrete one
      • Method references give you the same functionalinterface flexibility as lambdas

      What NOT to say:

      • "Functional interface means it works with streams" — sort of, but the definition is just SAM
      • Listing 12 functional interfaces when asked to name "a few" — bloat, picks the bad ones

      Common follow-up: "What's the difference between Function and Consumer?"

      39. default methods — why were they added?

      Asked at: Mid-level rounds

      Difficulty: Easy-Medium · Topic: Java 8 features

      The question: "Why were default methods added to interfaces in Java 8? What problem did they solve?"

      The 30-second answer: To allow adding methods to existing interfaces without breaking existing implementations. The driver was Stream API: Collection had to gain stream(), parallelStream(), forEach(), removeIf() — without default, every existing Collection implementation would have had to add these.

      Step-by-step thought process:

      1. "Pre-Java-8: adding a new abstract method to an interface broke every existing implementation. This blocked Java from evolving its core APIs."
      2. "Java 8 added default methods — implemented in the interface itself. New implementers don't have to override; existing implementers continue to work."
      3. "Used heavily by Java 8 to add Stream support to Collection (stream(), parallelStream(), forEach()), to add compute* / merge to Map, etc."
      4. "Allowed multiple inheritance of behavior (not state) — you can implement two interfaces with default methods that don't conflict. Conflicts must be resolved explicitly via override."
      5. "Caveat: default methods on functional interfaces don't change SAM-ness — you can still lambda-assign them."

      Edge cases to mention:

      • Diamond problem: if two interfaces have conflicting defaults, the implementing class MUST override and pick (InterfaceA.super.method() or InterfaceB.super.method())
      • A class's concrete method always wins over interface defaults (no diamond conflict needed)
      • Static methods on interfaces are also new in Java 8 — bound to the interface, not inherited

      What NOT to say:

      • "Default methods make Java multi-inheritance" — partial truth; state isn't inherited, only behavior
      • "Use default methods instead of abstract classes" — abstract classes still have their place (state, constructors)

      Common follow-up: "What happens if a class implements two interfaces with the same default method?"

      40. CompletableFuture exceptionally vs handle

      Asked at: Senior backend rounds

      Difficulty: Medium · Topic: Async error handling

      The question: "Difference between exceptionally, handle, and whenComplete on CompletableFuture?"

      The 30-second answer: exceptionally(throwable -> fallback) runs ONLY on exception, recovers with a value. handle((value, throwable) -> result) runs on BOTH success and failure, lets you transform either. whenComplete((value, throwable) -> sideEffect) runs on both but doesn't transform — for side effects like logging.

      Step-by-step thought process:

      1. " exceptionally: takes a Function from Throwable to T. Invoked only if the future completed exceptionally. Result is a new future with the recovered value."
      2. " handle: takes a BiFunction of (T, Throwable). Invoked on either outcome — exactly one of value/throwable will be null. Result is a new future with the transformed value."
      3. " whenComplete: takes a BiConsumer of (T, Throwable). Invoked on either outcome. Result is a future with the SAME value as the original (or rethrows the original exception). For side effects: logging, metrics."
      4. "Use exceptionally when you have a sensible fallback. Use handle when the success and failure paths produce the same type but via different logic. Use whenComplete for observation without transformation."
      5. "Chain order matters: future.thenApply(f).exceptionally(g) — g handles exceptions from BOTH the original future AND f."

      Edge cases to mention:

      • exceptionallyCompose (Java 12+) is the async equivalent of exceptionally — recovery via another async call
      • whenComplete rethrows the original exception even if the consumer throws — be careful logging shouldn't mask original errors
      • Java 12+ exceptionallyAsync, handleAsync etc. for executor-control versions

      What NOT to say:

      • "They're all the same, just pick one" — they aren't
      • "Use try-catch on get()" — works but blocks; defeats async

      Common follow-up: "How would you log an async failure without changing the eventual value?"
