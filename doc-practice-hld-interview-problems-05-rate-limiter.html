    Design a Rate Limiter

    3 sections · 3,145 words

    Three levels: Level 1 — The Shape, Level 2 — The Defence, Level 3 — The Edges.

    Level 1 — The Shape (Foundation)

    Pacing: 3 min ask · 5 min trace flow · 7 min read why.

    The Ask

    Functional

    • Limit per client (API key/user) to N per window
    • 429 on limit, with a Retry-After header

    Non-Functional

    • Adds latency to every request ← forces an in-memory check
    • Same limit across many gateways ← forces a shared counter
    • Must not itself be the outage ← forces fail-open/closed

    Agree These First

    ~50 000 rps aggregate across ~2 M active keys · free 100/min · paid 1 000/min. Illustrative, round numbers — not any named company's published limits.

    The Shape

    Components and flow:

    • Client — Any request — GET or POST, doesn't matter here
    • Every request — 50 000 rps aggregate
    • Edge / Gateway — The check happens HERE — before a request costs you a downstream hop
    • if allowed → Downstream API — Out of scope — never reached by a rejected request
    • Counter Store — In-memory KV · atomic INCR + EXPIRE per check

    Data model: counter key PK → count, ttl — the simplest data model of the 16.

    Line weight = traffic: REQUEST · 50 K rps; CHECK · internal.

    Say It Like This

    "One job: count requests per client and reject the ones over the limit, cheaply, on every request. So I'd check it as early as possible — right at the gateway, before it costs you a downstream hop. The counter has to live somewhere fast, so in-memory, not a database round trip. And because you'll run many stateless gateway instances, that counter has to be shared, not counted locally, or you're enforcing some multiple of the limit you agreed to. Over the limit, I return 429 with Retry-After — the client needs an honest contract for when to come back."

    Defend It

    Decision Prefer Avoid
    (1) Check placement At the edge/gateway — as early as possible, before a downstream hop Inside the downstream service → you already paid for the call you're rejecting
    (2) Counter store In-memory KV — an INCR is sub-millisecond, no disk, no query planner A row in a relational DB → transaction overhead on every single request
    (5) 429 + Retry-After An explicit, honest contract for when the client should come back Silently dropping the request → looks like an outage, invites an immediate retry

    Capacity Math

    Quantity Derivation Value
    Requests 50 000 rps aggregate · stated assumption, ~2 M active keys 50 K /s
    Checks every request → exactly 1 check, no exceptions 50 K /s
    Redis ops 1 atomic INCR+EXPIRE (Lua script) per check 50 K /s

    Round hard, out loud. 50 000 requests a second, every one needs a check — that ratio, not the store, is why this system's own latency budget is so tight.

    Before You Draw Anything — The Four Moves

    1. Clarify, don't assume. Per user, per API key, per IP, or some combination? Say so before drawing. — State the limiting key before the first box goes down.
    2. Agree the scale out loud. "Let's say 50 K rps, 2 M keys, free and paid tiers." Now every choice has a reason. — An unstated number is an undefendable design.
    3. Draw the happy path only. Client → gateway check → counter store → allowed through. Get agreement first. — Boxes you add before agreement are boxes you'll defend alone.
    4. Name one trade-off unprompted. "I'd check this at the edge, before it costs you a downstream hop." — This is the single move that separates L1 from a junior answer.

    What L1 Is Testing

    • Can you name the limiting key first?
    • Do you check early, before the expensive part?
    • Did you reach for "centralized" unprompted?

    The Follow-Ups That Decide It

    1. Fixed window, sliding window, or token bucket — and why? (ref 2 — tests: do you know there are multiple algorithms and the trade-off between them)
    2. Ten gateway instances, no shared state. What's your actual effective limit? (ref 1 — tests: can you compute the real number, unprompted)
    3. A client keeps getting rate-limited and retries immediately, every time. What do you tell them? (ref 5 — tests: awareness that the client side of the contract matters too)

    At L1 you are being judged on one thing: can you produce a coherent shape and defend three choices inside it. Depth is page 2 — do not reach for it here. Ghosted boxes are what arrives next; you should be able to guess most of them.

    Level 2 — The Defence (Intermediate)

    Pacing: 5 min ask · 15 min trace flow · 10 min read why · 30 min cover & answer.

    The Ask

    Functional

    • Limit per client (API key/user) to N per window
    • 429 on limit, with a Retry-After header
    • Per-tier limits — free vs paid
    • Bounded burst above the steady rate

    Non-Functional

    • Adds latency to every request ← forces an in-memory check
    • Same limit across many gateways ← forces a shared counter
    • Must not itself be the outage ← forces fail-open/closed
    • Not ~2× the limit at a window edge ← forces sliding window
    • Scales to multi-region traffic ← forces per-region budgets

    Out of Scope — Say It Aloud

    • The downstream API/service itself
    • Billing, plans, accounts
    • Network-layer DDoS — that's the WAF

    Agree These First

    ~50 000 rps aggregate across ~2 M active keys · free 100/min · paid 1 000/min. Illustrative, round numbers — not any named company's published limits.

    The Shape

    Components and flow:

    • Client — Any request — GET or POST, doesn't matter here
    • Every request — 50 000 rps aggregate
    • Edge / Gateway — The check happens HERE — before a request costs you a downstream hop
    • if allowed → Downstream API — Out of scope — never reached by a rejected request
    • (3) Tier Limits — free 100/min · paid 1 000/min
    • Counter Store — In-memory KV · atomic INCR + EXPIRE per check · fixed-window counter; ≈4 M live keys · ≈200 MB total
    • (5) 429 Too Many Requests · Retry-After

    Data model:

    • counter {client_id}:{window} PK · count · ttl
    • tier_limits tier → limit, burst
    • 1 live key vs sheet 01's 2 tables

    Line weight = traffic: REQUEST · 50 K rps; CHECK · internal; ASYNC · off critical path.

    Say It Like This

    "One job: count requests per client and reject the ones over the limit, cheaply, on every request. So I'd check it as early as possible — right at the gateway, before it costs you a downstream hop. The counter has to live somewhere fast, so in-memory, not a database round trip. And because you'll run many stateless gateway instances, that counter has to be shared, not counted locally, or you're enforcing some multiple of the limit you agreed to. Over the limit, I return 429 with Retry-After — the client needs an honest contract for when to come back."

    Defend It

    Decision Prefer Avoid
    (1) Check placement At the edge/gateway — as early as possible, before a downstream hop Inside the downstream service → you already paid for the call you're rejecting
    (2) Counter store In-memory KV — an INCR is sub-millisecond, no disk, no query planner A row in a relational DB → transaction overhead on every single request
    (5) 429 + Retry-After An explicit, honest contract for when the client should come back Silently dropping the request → looks like an outage, invites an immediate retry
    (2) Fixed vs sliding window Fixed window: one INCR, one auto-expiring key — simplest by far Allows up to ~2× the limit across a window edge — sliding window removes it, at more compute per check
    (1) Centralized vs local Centralized shared counter enforces the limit you actually stated Per-instance local counting → 20 instances multiply it to 2 000/min
    (1) Fail-open vs fail-closed Fail-open when the store is down — the limiter should never outrank the API it protects Fail-closed (right for auth) → the limiter becomes the outage it exists to prevent

    Capacity Math

    Quantity Derivation Value
    Requests 50 000 rps aggregate · stated assumption, ~2 M active keys 50 K /s
    Checks every request → exactly 1 check, no exceptions 50 K /s
    Redis ops 1 atomic INCR+EXPIRE (Lua script) per check 50 K /s
    If local 20 gateway instances × 100/min, counted independently 2 000 /min

    Unlike a cache, which only misses ~2% of the time, every single request touches the limiter. That 1:1 ratio is the whole reason its own latency has to stay near-zero.

    What Breaks — Say It Before They Ask

    • (2) Boundary burst. Fixed window allows near-2× the limit across a window edge. — Fix: sliding window (log or weighted counter)
    • (1) Local counting under-enforces. N gateway instances each counting independently multiply the effective limit by N — 2 000/min, not 100. — Fix: centralize the counter in a shared store
    • (2) Hot key. One heavily-limited (or abusive) client hammers a single counter key with INCR calls. — Fix: this is a legitimate, bounded hot key — expected, handled by a fast in-memory store, not sharding
    • (5) Retry storm. A client at the limit retries immediately and aggressively instead of backing off. — Fix: a clear Retry-After header — the rest is a contract with the client, not something the server alone can force
    • (2) Store outage. The counter store goes down. — Fix: fail-open — the API is briefly unprotected, and that trade-off is stated, not hidden

    The Follow-Ups That Decide It

    1. Fixed window, sliding window, or token bucket — and why? (ref 2 — tests: do you know there are multiple algorithms and the trade-off between them)
    2. Ten gateway instances, no shared state. What's your actual effective limit? (ref 1 — tests: can you compute the real number, unprompted)
    3. A client keeps getting rate-limited and retries immediately, every time. What do you tell them? (ref 5 — tests: awareness that the client side of the contract matters too)
    4. 100 requests in the last second of one window, 100 more in the first second of the next. Did you enforce the limit? (ref 2 — tests: boundary-burst awareness with fixed window)
    5. Your counter store goes down. What happens to your API? (ref 2 — tests: fail-open vs fail-closed judgement, and the asymmetry with auth)

    Cover The Sheet · Answer Aloud

    Use it as revision: cover the right rail and the two panels to your left, then walk the numbered path out loud. If you cannot say why a box is there and what breaks it, that box is your gap.

    Level 3 — The Edges (Advanced)

    Pacing: 10 min ask · 25 min trace flow · 15 min read why · 40 min cover & answer.

    The Ask

    Functional

    • Limit per client (API key/user) to N per window
    • 429 on limit, with a Retry-After header
    • Per-tier limits — free vs paid
    • Bounded burst above the steady rate

    Non-Functional

    • Adds latency to every request ← forces an in-memory check
    • Same limit across many gateways ← forces a shared counter
    • Must not itself be the outage ← forces fail-open/closed
    • Not ~2× the limit at a window edge ← forces sliding window
    • Scales to multi-region traffic ← forces per-region budgets

    Out of Scope — Say It Aloud

    • The downstream API/service itself
    • Billing, plans, accounts
    • Network-layer DDoS — that's the WAF

    Components and flow:

    • Client — Any request — GET or POST, doesn't matter here
    • Every request — 50 000 rps aggregate
    • Edge / Gateway — The check happens HERE — before a request costs you a downstream hop · local precheck first
    • if allowed → Downstream API — Out of scope — never reached by a rejected request
    • (4) local check — Local / Edge Budget — A fraction of the global limit, pre-checked at the PoP
    • (3) Tier Limits — free 100/min · paid 1 000/min
    • Counter Store — In-memory KV · atomic INCR + EXPIRE per check · token bucket — bounded burst; ≈4 M live keys · ≈200 MB total; reconcile ~every 5 s · async

    Storage is never the constraint here either — the opposite reason from sheet 01's 91 TB. This system's entire live state is ~200 MB, comfortably inside a single modest Redis instance.
