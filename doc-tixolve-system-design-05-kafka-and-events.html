    Kafka & Event-Driven Design

    6 sections · 795 words

    Section 5 of 11

    Why Kafka (not REST for everything)?

    Concern REST Kafka
    Temporal coupling Producer must wait for consumer Producer publishes and moves on
    Service coupling Producer knows consumer's URL Producer knows only the topic name
    Fan-out Producer must call each consumer Multiple consumers subscribe to same topic
    Durability Response lost if consumer crashes mid-processing Events persisted on disk, replayed on failure
    Backpressure Slow consumer slows producer Consumer processes at its own pace

    When REST is still correct: chat-service calling knowledge-service for search results. Chat needs the result before it can build the prompt — synchronous call is the right tool. Kafka is for side effects where the producer doesn't need to wait for or know about the outcome.

    Topics

    Topic Producer Consumer(s) Minimum Payload
    ticket.created ticket-service notification-service, chat-service ticketId, tenantId, userId, subject, priority
    ticket.status-changed ticket-service notification-service ticketId, oldStatus, newStatus, changedBy
    document.ingested knowledge-service chat-service documentId, tenantId, chunkCount
    chat.escalated chat-service ticket-service conversationId, userId, summary, suggestedPriority

    Outbox Pattern (Critical — most common interview question)

    The Dual-Write Problem

    You must write to DB and publish to Kafka. These are two separate I/O calls. Any failure between them leaves data inconsistent:

    ticketRepository.save(ticket)             // ✓ committed
kafkaTemplate.send("ticket.created", ...) // ✗ Kafka down → event never published
// Result: ticket exists in DB, notification-service never finds out

    Or in reverse:

    kafkaTemplate.send("ticket.created", ...) // ✓ published
ticketRepository.save(ticket)             // ✗ DB crash → ticket rolled back
// Result: event published for a ticket that doesn't exist

    The Solution

    Write the event to an outbox table in the same database transaction as the business entity. A separate process publishes outbox rows to Kafka.

    @Transactional  // Single transaction — atomic
public Ticket createTicket(CreateTicketRequest req) {
    Ticket ticket = ticketRepository.save(new Ticket(req));
    outboxRepository.save(OutboxEvent.of(
        "ticket.created",
        new TicketCreatedPayload(ticket)
    ));
    return ticket;  // Both rows committed, or both rolled back
}

@Scheduled(fixedDelay = 100)  // Separate process, every 100ms
public void publishPendingEvents() {
    outboxRepository.findUnpublishedWithLock().forEach(event -> {
        kafkaTemplate.send(event.getTopic(), event.getPayload())
            .whenComplete((result, ex) -> {
                if (ex == null) outboxRepository.markPublished(event.getId());
                // If Kafka fails: row stays unpublished, retried next cycle
            });
    });
}

    Guarantee: You can never have a committed DB change without a corresponding outbox row. The outbox row will eventually be published to Kafka (retried until success). This gives at-least-once delivery from the producer side.

    Outbox Table Schema

    CREATE TABLE outbox_events (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    topic        VARCHAR(100) NOT NULL,
    payload      JSONB NOT NULL,
    published    BOOLEAN DEFAULT false,
    created_at   TIMESTAMPTZ DEFAULT now(),
    published_at TIMESTAMPTZ
);

CREATE INDEX ON outbox_events (published, created_at) WHERE published = false;

    Consumer Groups

    Each consuming service registers its own consumer group ID:

    notification-service → group ID: notification-service-group
chat-service         → group ID: chat-service-group
ticket-service       → group ID: ticket-service-group

    Effect: Every service gets its own copy of every message (fan-out). Adding a new consumer service requires zero changes to the producer — just register a new consumer group.

    Scaling: Adding a second instance of notification-service uses the same consumer group. Kafka distributes topic partitions across instances in the group automatically. Instance 1 gets partitions 0-1, instance 2 gets partitions 2-3. Load balanced automatically.

    Idempotency (Handling Duplicate Messages)

    Kafka provides at-least-once delivery by default. Network retries or consumer restarts can cause the same message to be delivered twice. Consumers must be idempotent — processing the same event twice must produce the same result as processing it once.

    Implementation:

    @KafkaListener(topics = "ticket.created", groupId = "notification-service-group")
public void handleTicketCreated(TicketCreatedEvent event) {
    // Check if already processed
    if (processedEventRepository.existsByEventId(event.getEventId())) {
        log.info("Duplicate event ignored: {}", event.getEventId());
        return;
    }

    // Process
    notificationService.createTicketNotification(event);

    // Mark as processed (in same transaction as notification creation)
    processedEventRepository.save(new ProcessedEvent(event.getEventId()));
}

    This gives effectively-once semantics: duplicates are detected and skipped. True exactly-once requires Kafka transactions — more complex, added as a production trade-off note.

    Key Configuration

    # Consumer config (application.yml)
spring:
  kafka:
    consumer:
      enable-auto-commit: false        # Manual offset commit after processing
      auto-offset-reset: earliest      # On first start, read from beginning
      isolation-level: read_committed  # Only read committed transactions

    # Producer config
    producer:
      acks: all                        # All replicas must acknowledge
      retries: 3
      enable-idempotence: true         # Prevent duplicate sends from producer side

    enable-auto-commit: false + manual offset commit is critical — it ensures we only commit the offset after the message is successfully processed. If processing fails, the offset isn't advanced, so the message is redelivered on restart.
