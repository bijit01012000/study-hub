    Observer

    11 sections · 794 words

    Behavioural · Design Patterns · Pattern 08 of 12

    Intent

    Let a subject notify a list of interested consumers when it changes, without knowing who they are or hard-coding a call to each one.

    When To Use It

    The Signs

    • One object changes and several others must update.
    • Code that polls on a timer: "is it done yet?".
    • The subject hard-codes a call to every consumer, so adding one means editing the subject.
    • You want listeners to come and go at runtime.

    Don't Bother If

    • There is exactly one consumer and it will stay one. Just call it.
    • The update must be synchronous and transactional with the change.
    • You need a broker between many publishers and subscribers. That is Pub-Sub.

    Before

    class ParkingSpot {
    void free() {
        this.taken = false;
        board.refresh();
        analytics.track("freed");
        app.push(id);
    }
    // take() and reserve() hand-roll the same three calls
}
// every new consumer edits ParkingSpot, in every method
// that changes state. miss one and a screen goes stale.

    The subject knows everyone.

    After

    interface SpotListener { void onChanged(Spot s); }

class ParkingSpot {
    private final List<SpotListener> listeners
        = new CopyOnWriteArrayList<>();
    void subscribe(SpotListener l) { listeners.add(l); }
    void unsubscribe(SpotListener l) { listeners.remove(l); }
    void free() {
        taken = false;
        for (SpotListener l : listeners) l.onChanged(this);
    }
}
// board, analytics and app each implement SpotListener
class Board implements SpotListener {
    public void onChanged(Spot s) { repaint(s); }
}
spot.subscribe(new Board());
// and Analytics, AppPush
// a new consumer subscribes. ParkingSpot never changes.

    Or the consumers poll, which is slower and burns cycles:

    while (true) {
    if (spot.isFree()) update();
    sleep(1000);
}
// a timer hammering a getter, burning cycles,
// and still up to a second behind the change

THE SUBJECT HOLDS THE LIST, NOT THE CONSUMERS

    How It's Built (3 Steps)

    1. The subject keeps a List<Observer> with subscribe and unsubscribe.
    2. On a state change it loops the list and calls observer.onChanged(event).
    3. Consumers implement the interface, register themselves, and unregister when they go away.

    Quick Check

    Ask "when this changes, does a set of other things need to react, and I do not want it to know who they are?" If yes, keep a list of listeners.

    In The Interview

    "The board is an Observer of each spot. On a change the spot fires one event; the board, analytics and the app each update. Nothing polls, and the spot never knows who listens."

    How It's Different

    From The Lookalikes

    Vs Pub-Sub / a message bus. Pub-Sub puts a broker in the middle, so publisher and subscriber never reference each other and messages can be buffered and replayed. Observer is the subject calling a list it owns directly, in process.

    Vs a plain callback. A callback is one function passed in. Observer is a managed list with subscribe / unsubscribe and many listeners.

    Vs Mediator. A Mediator is a hub that coordinates peers in both directions and holds interaction logic. Observer is one-way broadcast with no logic in the middle.

    Vs Chain of Responsibility. CoR passes a request along until one handler consumes it. Observer delivers the same event to every listener.

    They Say: "now log every change to an audit trail"

    • With it: a new AuditListener that subscribes. The spot code does not change.
    • Without: another hard-coded call inside free() and take(), and you hope you covered both.

    Watch Out For

    • Push vs pull. Push puts the data in the event; pull sends a poke, the observer reads back, avoiding stale events.
    • Do not mutate the listener list while iterating it. Use a copy-on-write list or a snapshot.
    • A slow or blocking observer stalls the notify loop and the caller's thread. Hand slow work to a queue.
    • A listener that never unsubscribes is a memory leak. Tie it to a lifecycle, or use weak references.
    • If one observer throws, catch per-listener so the rest still get the event.
