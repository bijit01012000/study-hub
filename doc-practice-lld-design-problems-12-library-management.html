    Design a Library Management System

    15 sections · 1,936 words

    LLD Design Problems, problem 12 of 20.

    The Ask

    Build

    • A catalog: a Book is title, author, ISBN, subject.
    • Each Book has one or more copies, each with a barcode and a rack.
    • Members search, borrow a copy, renew, return.
    • Limits: max books held, loan days, max renewals.
    • A late return adds a fine; fines over a threshold block borrowing.
    • Every copy out -> join a FIFO reservation queue.
    • On return, hold the copy RESERVED for the queue head for 48h, then the next, else free.
    • Librarian: add / remove Books and copies, block a member, waive fines.

    Skip

    • Full-text search, recommendations.
    • Ebooks, DRM, licences.
    • Inter-library loan.
    • Acquisitions / purchasing workflow.
    • A real payment rail for fines.
    • A database, login.

    Our Model

    Member borrows, librarian curates. One ISBN, many copies, a line. The copy is the unit; the Loan is the audit.

    Actors and classes

    • Member — id, name, svc: LibraryService; search, borrow, renew, return, reserve, calling svc.checkout(id, isbn) and svc.reserve(id, isbn).
    • Librarian — id, svc: LibraryService; addBook(b), addCopy(isbn, barcode), blockMember(id), removeCopy(barcode), waiveFine(memberId), collectFine(...).
    • LibraryService (singleton + factory) — catalog: Map<String, Book> (by ISBN), items: Map<String, BookItem> (by barcode), loans: Map<String, Loan>, queue: Map<String, Deque<String>> (ISBN to members), fine: FinePolicy, search: SearchStrategy; checkout(String memberId, String isbn): Loan, returnItem(String barcode): void, reserve(String memberId, String isbn): Reservation, renew(barcode), blockMember(id), waiveFine(id). Every write goes under a per-ISBN lock.
    • Book — isbn, title, author, subject, copies: List<BookItem>; isAvailable(): boolean, freeCopyCount(): int. Available when any copy is AVAILABLE.
    • BookItem (one physical copy) — barcode: String, isbn: String, rack: String, status: AVAILABLE | LOANED | RESERVED | LOST, reservedFor: String, holdUntil: Instant; markLoaned(), markAvailable(), markReserved(memberId, until), markLost().
    • Loan — id, barcode, memberId, issuedAt, dueAt: LocalDate, returnedAt: LocalDate (null until back), renewals: int, state: LoanState; daysLate(LocalDate today): long, renew(), close(today).
    • LoanState (interface) — renew(Loan l), returnItem(Loan l), markOverdue(Loan l). States: Active -> renew -> Active (caps at maxRenewals); Active -> dueAt passed -> Overdue; Active / Overdue -> return -> Returned; Lost is terminal with a flat max fine.
    • Reservation (a place in line) — isbn, memberId, queuedAt: Instant, barcode: String (null until READY), state: WAITING | READY | PICKED | EXPIRED.
    • FinePolicy (interface) — fineFor(Loan l, LocalDate today): Money. FlatPerDay, Escalating, GraceThenFlat.
    • SearchStrategy (interface) — find(Query q): List<Book>; ByTitlePrefix, ByAuthor, BySubjectTag.
    • HoldNotifier (interface) — onReady(Reservation r): void (Observer; email, SMS, push, a stub in tests).

    The fine rules

    • FlatPerDay -> Rs 5/day, cap Rs 500.
    • Escalating -> Rs 5/day, Rs 10 after a week.
    • GraceThenFlat -> 3 free days, then flat.

    Key operations

    1. checkout(String memberId, String isbn): Loan — under a per-ISBN lock, takes a free copy for that ISBN, or the copy already RESERVED for this member. Rejects a blocked member, one at the hold limit, or one over the fine threshold. Marks it LOANED, due = today + loanDays.
    2. returnItem(String barcode): void — closes the loan, posts any fine through FinePolicy. If a queue waits, the copy goes RESERVED for the head with a 48h window, else AVAILABLE. Fine is posted before the copy is offered on.
    3. reserve(String memberId, String isbn): Reservation — only when every copy is out. Appends the member to the ISBN's FIFO queue. Binds no copy. Idempotent per (member, isbn).
    4. fineFor(Loan l, LocalDate today): Money — max(0, daysLate) x ratePerDay, capped. Reads the loan, never writes. A new rule is a new FinePolicy, never an if-ladder in returnItem.

    borrow when held < maxHeld && owed < threshold; hold free when queue empty || now > holdUntil. Checkout: c = free copy for isbn, or the one RESERVED for me; c.markLoaned(); new Loan(due = today + loanDays). Return: l.close(today); post fineFor(l); queue not empty -> c RESERVED for head, 48h; else -> c AVAILABLE.

    The One Run to Hold in Your Head

    Every copy of one ISBN is out. Alice reserves, then Bob. A copy comes back Monday 9am, held for Alice for 48h. She turns up Thursday. Who gets it, what does the late borrower owe, and which objects touched the request?

    The copy comes back -> RESERVED for Alice, 48h. Her window lapses -> RESERVED for Bob, 48h. Queue now empty -> the copy is AVAILABLE. fine = max(0, daysLate) x ratePerDay, capped at a per-loan maximum; a grace day is a policy choice, state it.

    The Change

    They ask for "students get fewer books, staff get longer loans, scholars a lower rate". Add a MembershipTier that supplies the borrow limit, loan days and fine multiplier. checkout reads it; the flow never changes. Strategy, a second time on this sheet.

    What the Picture Can't Show

    The race: two members grab an ISBN's last copy at once, both read one AVAILABLE. The fix is a per-ISBN lock with a re-check before markLoaned. A RESERVED copy also refuses every borrower but its holder.

    If They Make You Code It

    checkout and returnItem, the whole thing:

    class LibraryService {                           // one instance
    Map<String,Book> catalog;                    // key = ISBN
    Map<String,BookItem> items;                  // key = barcode
    Map<String,Deque<String>> queue;             // ISBN -> members
    FinePolicy fine; int maxHeld, loanDays;

    Loan checkout(String memberId, String isbn) {
        Member m = members.get(memberId);
        if (m.blocked()) throw new MemberBlocked();
        if (heldBy(memberId) >= maxHeld) throw new AtLimit();
        if (owed(memberId).gte(fineBlock)) throw new FinesDue();
        synchronized (lockFor(isbn)) {           // one ISBN pool
            BookItem c = freeCopy(isbn, memberId);
            if (c == null) throw new NoCopyAvailable(isbn);
            c.markLoaned();                      // flips on the copy
            Deque<String> q = queue.get(isbn);
            if (q != null) q.remove(memberId);   // my hold
            Loan l = openLoan(c, memberId, loanDays);
            loans.put(l.id(), l); return l;
        }
    }

    void returnItem(String barcode) {
        Loan l = activeLoan(barcode);
        l.close(today());                        // ACTIVE / OVERDUE -> RETURNED
        Money due = fine.fineFor(l, today());
        if (due.amount() > 0) postFine(l.memberId(), due);
        BookItem c = items.get(barcode);
        synchronized (lockFor(c.isbn())) {
            Deque<String> q = queue.get(c.isbn());
            if (q != null && !q.isEmpty())
                c.markReserved(q.peek(), plus48h());
            else c.markAvailable();
        }
    }
}

    The Four Hazards

    1. Two members, one copy. freeCopy is not the commit. With no lock, both members see copy c3 AVAILABLE and both markLoaned. Lock the ISBN copy pool, re-read freeCopy inside, one loan wins.
    2. A walk-in jumps the queue. A just-returned copy is RESERVED for Alice, the head of the queue. Bob walks up and asks for that ISBN. RESERVED blocks every borrower but its holder; only a lapsed window advances the queue.
    3. Off-by-one on the due date. Returned on the dueAt date — one day late or none? Pick half-open: late when today > dueAt, and say whether a grace day applies. One rule, stated, inside FinePolicy.
    4. A hold that never expires. Alice reserves and never collects. The copy sits RESERVED forever and the next member is stuck. A sweeper frees holds past holdUntil each hour; reads treat a past-window RESERVED as free for the next in line.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. synchronized (lockFor(isbn)) + re-check freeCopy inside — two members race the last copy, one wins.
    2. freeCopy(isbn, memberId) returns an AVAILABLE copy or the one RESERVED for this member — a walk-in is refused a held copy.
    3. close then fineFor then re-home the copy — the fine is posted before the copy is offered to the queue.

    Tracking "Is a Copy Free?"

    Approach "Any copy free?" Take a copy Shelf label count Fine / history audit Best when
    Per-ISBN copy list + scan (walk the copies, the default) O(copies) scan flip a status re-scan not here a tiny branch shelf
    Per-ISBN free-list + count count > 0, one number O(1) pop from the deque list.size() not here "how many free"
    Query the loan table (open-loans view) count loans without returnedAt insert a Loan row a group-by the source of truth reporting, overdue sweep

    Per-ISBN free-list for the check, O(1) both ways. The Loan table stays the audit source of truth for history, renewals and fines. A plain scan is fine for a one-shelf branch.

    Rejection Signals

    These end the interview:

    • Marking a copy LOANED with no lock and no re-check — two members walk out with the last copy.
    • An available flag on the Book, not the BookItem — three copies collapse to one and the count drifts.
    • A returned copy handed to the next walk-in while it is RESERVED for the head of the queue.
    • No pickup window on a hold — one member reserves, never collects, the copy is pinned forever.
    • Fines by instanceof or a switch on days late instead of a FinePolicy.
    • Money as a double — Rs 5/day plus a cap stops adding up and the fine drifts.

    Patterns Used

    State — BookItem status and the Loan lifecycle: ACTIVE -> OVERDUE -> RETURNED, plus LOST. Strategy — the fine policy, and search. Observer — "your hold is ready" to the queue head. Factory — the service builds Book / BookItem from a catalog row.

    Say It Like This

    "A Book is a catalog entry keyed by ISBN; a BookItem is one physical copy with a barcode and a status. checkout takes a per-ISBN lock, grabs a free copy or the one RESERVED for this member, checks the borrow limit and fines owed, marks it LOANED with a due date. Return posts a fine through a FinePolicy, then hands the copy to the head of the FIFO reservation queue for 48h, else shelves it. A sweeper frees stale holds. Money is integer minor units."

    The Follow-ups That Decide It

    1. Two members race the last copy. Walk it. Per-ISBN lock, re-check freeCopy inside, one loan wins.
    2. Every copy is out — what does reserve do? Appends to the ISBN's FIFO queue, binds no copy.
    3. A copy returns and Alice is head of the queue. RESERVED for Alice, 48h window, then Bob, else AVAILABLE.
    4. Alice never collects her hold. A sweeper frees holds past holdUntil; next in line or shelved.
    5. Member at the borrow limit or over the fine threshold. checkout checks both before markLoaned.
    6. Late return — what is the fine? FinePolicy: max(0, daysLate) x rate, capped; state the grace day.
    7. "Scholars get a lower rate and longer loans." A MembershipTier read on checkout; no flow change.
    8. "Search by author, then by subject tag." A SearchStrategy; the catalog is untouched.

    Deliberately Not Built

    • Full-text search / recommendations — a ranking service over the catalog. SearchStrategy names the seam; the index is not ours.
    • Ebooks and DRM — a licence with concurrent-use limits. A different question.
    • Inter-library loan — an adapter to another library's catalog. The ghost, out of scope today.
    • A real payment rail for fines — a PSP behind a thin seam. The seam is the point; the integration is not.
    • Acquisitions workflow — how a Book enters the catalog. Assume the Librarian adds it.
