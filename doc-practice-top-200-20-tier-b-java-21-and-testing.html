      186. Virtual threads — when NOT to use them

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Cred · Walmart Labs

      Difficulty: Hard · Topic: Java 21+ cutting-edge

      The question: "Virtual threads are GA in Java 21. Where do they not fit?"

      The 30-second answer: Virtual threads excel at blocking I/O (HTTP servers, JDBC, blocking queues). They do NOT help CPU-bound work — carriers are still bound by core count. Don't use them for ThreadLocal-heavy code (millions of threads × ThreadLocals = OOM). Don't use them with code that pins inside synchronized blocks on Java 21-23 (fixed in Java 24 JEP 491).

      Step-by-step thought process:

      1. "Virtual thread benefit comes from cheap blocking — when one parks, the carrier picks another. CPU-bound work doesn't park, so there's no benefit (slight overhead from continuation machinery)."
      2. "ThreadLocal — each virtual thread inherits or copies. Millions of threads × ThreadLocals = heap explosion. Consider ScopedValue (still preview Java 21-23) as the replacement."
      3. "Pinning — synchronized and JNI pin the virtual thread to its carrier on Java 21. If your hot path is synchronized, no benefit until you switch to ReentrantLock or Java 24."
      4. "Profile first — virtual threads aren't free. The win is for I/O-blocked services with thousands of concurrent connections."

      Edge cases to mention:

      • Frameworks must opt-in — Spring Boot 3.2+ enables virtual threads for Tomcat / Jetty via spring.threads.virtual.enabled=true
      • JDBC drivers: most modern drivers (PostgreSQL, MySQL) work fine; some older ones pin
      • Don't pool virtual threads — they're cheap; use Executors.newVirtualThreadPerTaskExecutor() (thread-per-task)

      What NOT to say:

      • "Virtual threads replace all thread pools" — only blocking-I/O pools
      • "They're like Goroutines" — similar idea, different implementation; Goroutines are full preemptive, virtual threads are cooperative

      Common follow-up: "What's a ScopedValue and why is it the modern alternative to ThreadLocal?"

      187. Structured concurrency — what problem does it solve?

      Asked at: Senior rounds at Razorpay · Cred · Walmart Labs

      Difficulty: Hard · Topic: Java 21+ cutting-edge

      The question: "What's structured concurrency? Is it production-ready?"

      The 30-second answer: Structured concurrency (JEP 480, still preview in Java 22-23 — not GA) treats a group of concurrent subtasks as a single unit. If the parent is cancelled, all subtasks are cancelled. If any subtask fails, siblings are cancelled too. StructuredTaskScope.ShutdownOnFailure for fan-outand-fail-fast; ShutdownOnSuccess for first-completed-wins.

      Step-by-step thought process:

      1. "Problem — CompletableFuture lets subtasks outlive their parent invisibly. You start three async calls, your method returns, a subtask fails — silent leak."
      2. "Structured fix — try (var scope = new StructuredTaskScope.ShutdownOnFailure()) { var p = scope.fork(() -> paymentApi.fetch()); var u = scope.fork(() -> userApi.fetch()); scope.join(); scope.throwIfFailed();... }."
      3. "When the try block exits, the scope closes — any unfinished subtasks are cancelled. Clean lifecycle, easier reasoning."
      4. "Status — preview in Java 21, 22, 23. Don't deploy to production until GA. Watch JEPs 462 / 480 / 499 for the GA target."

      Edge cases to mention:

      • Combines best with virtual threads — both are about making concurrency cheap and bounded
      • Custom StructuredTaskScope subclasses for app-specific aggregation semantics
      • Java agent / IDE / dev-mode preview features need --enable-preview flag

      What NOT to say:

      • "Use it in prod now" — preview means API can change without notice; risky for production
      • "Replaces CompletableFuture" — overlap, but CF is broader (callbacks, composition without scope semantics)

      Common follow-up: "How does StructuredTaskScope.ShutdownOnSuccess work?"

      188. Scoped values — alternative to ThreadLocal

      Asked at: Senior rounds at Razorpay · Cred · Walmart Labs

      Difficulty: Hard · Topic: Java 21+ cutting-edge

      The question: "What's ScopedValue and why is it relevant in the virtual threads world?"

      The 30-second answer: ScopedValue (JEP 446, still preview in Java 21-23, expected GA target Java 25) is a scoped, immutable alternative to ThreadLocal. Set via ScopedValue.where(VAL, value).run(...) — the value is visible to that runnable and its child threads, and is gone when the scope exits. Cheaper than ThreadLocal for virtual threads (no per-thread map allocation).

      Step-by-step thought process:

      1. "ThreadLocal allocates a map per thread to hold values. With millions of virtual threads, the cost adds up."
      2. "ScopedValue stores values in the call stack frame instead. Read is via the binding active in the current scope — O(stack depth) lookup, no per-thread storage."
      3. " ScopedValue<UserId> USER = ScopedValue.newInstance(); ScopedValue.where(USER, currentUserId).run(() -> service.process()); — USER.get() inside process returns the bound value."
      4. "Immutable — you can't set() a ScopedValue from within the scope. Only the binding-establishing call can do it. Eliminates mutation bugs that ThreadLocal allows."

      Edge cases to mention:

      • Inheritance to child threads is opt-in via Scope.where(...) semantics — virtual threads forked inside the scope inherit
      • Preview status — same --enable-preview caveat Use case sweet spot — request-scoped context (current user, trace ID, locale) passed through a deep call stack

      What NOT to say:

      • "ScopedValue is GA" — still preview as of Java 23
      • "It replaces ThreadLocal everywhere" — ThreadLocal-with-mutation still has its place

      Common follow-up: "Why does ThreadLocal hurt under virtual threads?"

      189. Foreign function and memory API — replacing JNI

      Asked at: Senior rounds at Goldman · Walmart Labs · Cred

      Difficulty: Hard · Topic: Java 21+ cutting-edge

      The question: "What's the Foreign Function and Memory API? Why is it a big deal?"

      The 30-second answer: FFM (JEP 442, GA in Java 22) replaces JNI for calling native code from Java. No C glue code required — describe the function signature in Java, JVM generates the trampoline. Also gives you MemorySegment for off-heap memory with explicit lifetime, much safer than Unsafe.

      Step-by-step thought process:

      1. "JNI for 25 years has been the way to call C from Java — required hand-written .c files, JNIEXPORT functions, painful build setup."
      2. "FFM — Linker linker = Linker.nativeLinker(); MemorySegment strlen = linker.defaultLookup().find("strlen").get(); MethodHandle h = linker.downcallHandle(strlen, FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS));. Pure Java."
      3. "MemorySegment + Arena — replace Unsafe and DirectByteBuffer for off-heap memory. Arena gives you explicit free semantics — try (Arena arena = Arena.ofConfined()) {... }."
      4. "Use cases — calling LMDB, OpenSSL, native ML libraries (LLaMA, Whisper) from Java without JNI overhead."

      Edge cases to mention:

      • Confined vs shared arenas — confined is single-thread, shared allows multithread access at slight overhead
      • Memory layout API — describe native struct layouts in Java, FFM handles padding and field offsets
      • Project Panama is the umbrella project; FFM is one deliverable

      What NOT to say:

      • "Still preview" — GA in Java 22, fully production-ready by Java 23
      • "Just like JNI" — fundamentally simpler; no glue code

      Common follow-up: "What's the difference between Arena.ofConfined and Arena.ofShared?"

      190. Vector API — SIMD from Java

      Asked at: Staff rounds at Goldman · Flipkart · Walmart Labs

      Difficulty: Hard · Topic: Java 21+ cutting-edge

      The question: "What's the Vector API and what's its status?"

      The 30-second answer: Vector API (JEP 469 in Java 23 — still incubator, not finalized) exposes CPU SIMD instructions (AVX, NEON) to Java code in a portable way. Write vectorized loops in Java that compile to wide vector instructions. Big wins for numeric workloads — image processing, ML, finance.

      Step-by-step thought process:

      1. "Without Vector API, the JIT auto-vectorizes only simple loops — anything non-trivial stays scalar. Vector API gives explicit control."
      2. "Define a species: VectorSpecies<Float> SPECIES = FloatVector.SPECIES_PREFERRED;. Loop: load N floats, do the op, store. JIT lowers to AVX-512 on supported chips, falls back to scalar elsewhere."
      3. "Status — incubator since Java 16, still incubator in Java 23. API stable in spirit, finalization waits on Valhalla (value types)."
      4. "Use cases — workloads where you'd reach for C / Rust / GPU for vectorization. Now Java can compete on the same workloads at near-native throughput."

      Edge cases to mention:

      • Hardware-specific — SPECIES_PREFERRED adapts at runtime to the JVM's available SIMD width
      • Don't reach for it unless you've measured a scalar bottleneck — adds complexity for routine code
      • Combines well with FFM for hybrid hot loops

      What NOT to say:

      • "It's a numerical library" — it's an SIMD API; libraries built on top would be the numerical layer
      • "GA in Java 21" — still incubator

      Common follow-up: "Why does the Vector API finalization wait on Valhalla?"

      191. Pattern matching for switch — exhaustiveness

      Asked at: Senior rounds at Razorpay · Cred · Swiggy · PhonePe

      Difficulty: Medium-Hard · Topic: Java 21+ cutting-edge

      The question: "Pattern matching switch went GA in Java 21. What's it actually buy you?"

      The 30-second answer: Switch can pattern-match on type (case Integer i ->...), with guards (case Integer i when i > 0 ->...), and on sealed hierarchies the compiler verifies exhaustiveness — no default needed if you cover every subtype. Combines with records for destructuring (case Order(var id, var amount) ->...).

      Step-by-step thought process:

      1. "Old switch — limited to constants of int, enum, String. New switch (Java 21 GA) — patterns over any reference type."
      2. " switch (event) { case OrderPlaced o -> handle(o); case PaymentReceived p -> handle(p); case OrderCancelled c -> handle(c); } — if Event is sealed and these are all its subtypes, compiler accepts (no default)."
      3. "Guards — case Integer i when i > 0 ->...; case Integer i ->... (the second catches zero/negative)."
      4. "Record deconstruction — case Order(long id, BigDecimal amount, String currency) -> processOrder(id, amount, currency). Cleaner than nested ifs and casts."

      Edge cases to mention:

      • null case — explicit case null ->... or it goes to default (NPE in old switch); explicit handling is recommended
      • Pattern-matching switch is an expression (returns a value) or a statement; both work
      • Sealed + pattern switch replaces most Visitor pattern uses

      What NOT to say:

      • "Still preview" — GA in Java 21
      • "It's just type switch" — adds guards, record deconstruction, exhaustiveness checking — much more

      Common follow-up: "How does pattern matching switch combined with sealed classes replace the Visitor pattern?"

      192. JUnit 5 — what's new vs JUnit 4

      Asked at: Senior rounds at Razorpay · TCS Digital · Swiggy · Wells Fargo

      Difficulty: Medium · Topic: Testing / quality

      The question: "What changed from JUnit 4 to JUnit 5?"

      The 30-second answer: New annotations (@Test from org.junit.jupiter.api, @BeforeEach / @AfterEach replace @Before / @After, @BeforeAll / @AfterAll for static-like setup). Native parameterized tests (@ParameterizedTest + @ValueSource / @CsvSource / @MethodSource). Nested test classes (@Nested). Test lifecycle modes (permethod default, per-class opt-in). Extensions replace Rules / Runners.

      Step-by-step thought process:

      1. "Modular — JUnit Platform (runner), JUnit Jupiter (programming model), JUnit Vintage (JUnit 4 compatibility). Run JUnit 4 tests alongside 5 via Vintage."
      2. "Parameterized — @ParameterizedTest @ValueSource(ints = {1, 2, 3}) void test(int x) — generates one test per value. No external runner needed."
      3. "Extensions — @ExtendWith(MockitoExtension.class), @ExtendWith(SpringExtension.class). Single composition mechanism replaces JUnit 4's @Rule and @RunWith."
      4. " assertAll(...) groups multiple assertions — all run even if some fail, all failures reported together. Better than chains of assertEquals that stop at first failure."

      Edge cases to mention:

      • @DisplayName("...") for human-readable test names in reports @TestInstance(Lifecycle.PER_CLASS) — instance reused across tests; lets @BeforeAll / @AfterAll be non-static
      • Assertions.assertThrows(IOException.class, () ->...) — replaces @Test(expected =...) from JUnit 4

      What NOT to say:

      • "Just like JUnit 4" — different module structure, different extension model
      • "JUnit 4 is deprecated" — not deprecated; Vintage runs it indefinitely

      Common follow-up: "How would you write a custom extension for setting up a TestContainers database?"

      193. Mockito argument captors and BDD style

      Asked at: Senior rounds at Razorpay · Swiggy · TCS Digital

      Difficulty: Medium · Topic: Testing / quality

      The question: "How do you verify a mock was called with a specific argument shape?"

      The 30-second answer: ArgumentCaptor<Order>.forClass(Order.class). Use it in verify(repo).save(captor.capture()), then assertThat(captor.getValue().getAmount()).isEqualTo(...). For BDD style — given(...).willReturn(...) reads better than when(...).thenReturn(...) for some teams.

      Step-by-step thought process:

      1. "For simple cases — verify(emailService).send(eq("user@x.com"), anyString()). Matchers like eq, any, anyString."
      2. "For complex object verification — ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class); verify(repo).save(captor.capture()); assertThat(captor.getValue().getStatus()).isEqualTo(PAID);. Inspect any field."
      3. "BDD style — given(repo.findById(1L)).willReturn(Optional.of(order)); and then(emailService).should().send(...). Same mechanics, more natural for Given-WhenThen."
      4. " ArgumentMatchers.argThat(o -> o.getAmount().compareTo(...) > 0) — inline custom predicate when captor is overkill."

      Edge cases to mention:

      • Mixing matchers and literal values — if any argument uses a matcher, all must. verify(repo).save(eq(orderObj)) not verify(repo).save(orderObj) when other args have matchers
      • Strict stubbing (Mockito 3+) fails the test if you stub something never called — catches stale tests
      • @InjectMocks constructs the SUT with mocks injected — handy with @Mock field annotations

      What NOT to say:

      • "Just use raw assertions on the captured object" — yes, that's the workflow
      • "Mockito can mock final classes? No, you need PowerMock" — outdated; Mockito 2+ supports finals via the mock-maker-inline config

      Common follow-up: "What's strict stubbing and why is it the default in modern Mockito?"

      194. TestContainers — Docker for integration tests

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Cred · Walmart Labs

      Difficulty: Medium-Hard · Topic: Testing / quality

      The question: "How do you test code that hits a real Postgres without slow CI?"

      The 30-second answer: TestContainers — Java library that starts Docker containers on demand for tests. @Container PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16"); — JUnit lifecycle starts and stops it. Get JDBC URL via postgres.getJdbcUrl(). Real Postgres, ephemeral, isolated per test class.

      Step-by-step thought process:

      1. "H2 in-memory was the old answer — fake DB. Diverges from real Postgres in many ways (SQL dialects, transaction behavior, lock semantics)."
      2. "TestContainers spins up the real DB image as a Docker container. Tests get a real Postgres, MySQL, Kafka, Redis — whatever you're using in prod."
      3. "Spring Boot 3.1+ has first-class integration — @ServiceConnection on the container bean auto-wires the connection details into Spring's DataSource."
      4. "Reuse — withReuse(true) keeps the container alive across test runs (locally only), big speedup for dev iteration."

      Edge cases to mention:

      • CI runners need Docker-in-Docker or Docker socket access — most modern CI (GitHub Actions, GitLab CI) supports it
      • Startup time per container is 2-10s — group tests in one class to reuse, or use class-level container with cleanup between tests
      • TestContainers Cloud and Desktop reduce local Docker overhead

      What NOT to say:

      • "Mock the database" — for repository tests, you want the real DB behavior
      • "Use H2 for everything" — diverges from production DB in subtle ways that bite

      Common follow-up: "How do you reset state between tests when sharing a container?"

      195. Mutation testing — what is it and when to use

      Asked at: Senior rounds at Cred · Goldman · Walmart Labs

      Difficulty: Hard · Topic: Testing / quality

      The question: "Code coverage is 95%. Is that good?"

      The 30-second answer: Coverage measures executed code, not tested code — a test can execute a line without asserting anything meaningful. Mutation testing (PITest in Java) injects deliberate bugs into your code; if tests still pass, the test suite doesn't actually verify the mutated behavior. Higher mutation score = stronger test suite.

      Step-by-step thought process:

      1. "Coverage can be high while tests are weak. assertNotNull(service.compute()) covers every line but proves almost nothing."
      2. "PITest mutates your code — flips operators (> to >=), removes return statements, swaps constants. Runs your test suite per mutation."
      3. "If a mutation survives (tests still pass), that's a gap. The mutation didn't change behavior in any way your tests check."
      4. "Run mutation testing periodically (slow), not percommit. It's a quality audit, not a CI gate."

      Edge cases to mention:

      • Equivalent mutations — some mutations don't change behavior at all (e.g., dead code paths). Mutation score accounts for these
      • PITest integrates with Maven and Gradle; run on changed files via --features=+CHANGED for faster local runs
      • Combine with line coverage — high coverage + high mutation score = strong suite; high coverage + low mutation score = empty tests

      What NOT to say:

      • "100% coverage means perfect tests" — false; coverage is necessary, not sufficient
      • "Mutation testing is too slow" — yes for CI, run nightly or on PR

      Common follow-up: "What's an equivalent mutation and how do tools handle them?"
