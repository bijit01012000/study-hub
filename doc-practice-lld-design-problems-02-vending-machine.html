    Design a Vending Machine

    15 sections · 1,807 words

    LLD Design Problems, problem 02 of 20.

    The Ask

    Build

    • Many slots, each with a product, a price, a count.
    • The same product may sit in more than one slot.
    • Insert coins of fixed denominations, machine tracks the balance.
    • Select a slot, machine checks stock then funds.
    • Dispense the product and return change.
    • Cancel before dispense returns everything inserted.
    • Admin can restock, set a price, empty the cash box.
    • Goes out of service when it cannot make change.

    Skip

    • Card / UPI payment.
    • Real coin-mechanism hardware.
    • Telemetry, remote monitoring.
    • A fleet of machines, one operator.
    • A database, login.

    Our Model

    One machine, slots, a coin bank. VendingMachine is a context; every press delegates to the current MachineState.

    Actors and classes

    • Buyer — machine: VendingMachine; press insert, select, cancel, calling machine.insertCoin(c) and machine.selectSlot(code).
    • Admin — machine: VendingMachine; restock(code, n), setPrice(code, p), collectCash(): List<Coin> calls machine.enterService().
    • VendingMachine (singleton) — slots: Map<String, Slot>, bank: CoinBank, balance: int, state: MachineState, change: ChangeStrategy; insertCoin(Coin c), selectSlot(String code): Product, cancel(): List<Coin>, dispense(), setState(s). Every call delegates to state.
    • MachineState (interface) — insertCoin(Coin c), selectSlot(String code): Product, dispense(), cancel(): List<Coin>, setState(s). Each state answers all four; wrong state means a no-op or a throw.
    • Slot — code: String, price: int, product: Product, count: int; hasStock(): boolean, deduct(), refill(int n), setPrice(int p). Price and count live on the slot.
    • Product — sku: String, name: String.
    • Coin (enum) — value(): int in minor units; values Rs 1, Rs 2, Rs 5, Rs 10, Rs 20.
    • CoinBank — count: Map<Coin, int>; canMake(int amount): boolean, hold(Coin), commit(), release(int): List<Coin>. Held coins are escrow until dispense.
    • ChangeStrategy (interface) — makeChange(int owed, CoinBank bank): List<Coin>. GreedyChange, ExactChange, FavourSmall.

    The state machine

    • Idle -> take coins -> HasMoney.
    • HasMoney -> more coins, or select.
    • Dispensing -> drop item + change -> Idle.
    • OutOfService -> refuse all but Admin.

    A call in the wrong state is a no-op (a coin during Dispensing rolls to the tray) or a throw (dispense outside Dispensing). It is never a silent jump between states.

    The change rules

    • GreedyChange -> biggest coin first, may fail.
    • ExactChange -> DP over the till, exact or nothing.
    • FavourSmall -> keep big coins for later buyers.

    Key operations

    1. insertCoin(Coin c) — only Idle and HasMoney take it. Anywhere else the coin falls straight to the tray. Adds to balance, moves Idle to HasMoney.
    2. selectSlot(String code): Product — three guards in order: stock, then balance >= price, then bank can make change. Any guard fails: nothing charged, state stays HasMoney.
    3. dispense() — legal only in Dispensing. One guarded step: cut stock, bank the coins, release change, then state = Idle. Never a partial vend.
    4. makeChange(int owed, CoinBank bank): List<Coin> — greedy from the largest coin, or exact-DP over the bank. Returns null when the bank cannot form it: the caller refunds and stays put.

    Recall drill: cover the operations column, write the four with their guarantee. Most people miss that selectSlot charges nothing until all three guards pass.

    The One Run to Hold in Your Head

    Balance is empty. A buyer drops Rs 50 in coins, picks slot A3, priced Rs 35, 2 left. What does the machine hand back, which state is it in at each step, and which objects touched the request?

    The Change

    They ask for "cheaper after 6pm" or "buy 2, get 10 off". Pull price off the Slot into a PricingStrategy the machine asks at selectSlot. Slots keep only stock. Strategy, a second time on this sheet.

    What the Picture Can't Show

    The atomic vend: the item drop and the change return are two motor steps. Lose power between them and the buyer is short-changed. The fix is a write-ahead log of the pending vend, replayed on boot.

    If They Make You Code It

    The state dispatch plus one concrete state:

    class VendingMachine {                                  // the context object
    Map<String,Slot> slots; CoinBank bank;
    ChangeStrategy change;
    MachineState state = new IdleState(this);
    int balance = 0;                                    // paise, never a float

    void insertCoin(Coin c) { state.insertCoin(c); }     // delegate
    Product selectSlot(String c) { return state.selectSlot(c); }
    List<Coin> cancel() { return state.cancel(); }
    void dispense() { state.dispense(); }
    void setState(MachineState s) { state = s; }         // callback
}

class HasMoneyState implements MachineState {
    final VendingMachine m;

    public void insertCoin(Coin c) {                    // stay, take more
        m.bank.hold(c); m.balance += c.value();
    }

    public Product selectSlot(String code) {
        Slot s = m.slots.get(code);
        if (s == null || !s.hasStock()) throw new SoldOut();
        if (m.balance < s.price()) return null;         // wait for more
        int due = m.balance - s.price();
        if (!m.bank.canMake(due)) { refund(); return null; }
        m.setState(new DispensingState(m, s, due));
        return s.product();                             // Dispensing takes over
    }

    public List<Coin> cancel() { return refund(); }

    private List<Coin> refund() {                       // both paths land here
        int all = m.balance; m.balance = 0;             // clear the credit
        m.setState(new IdleState(m));                   // back to Idle
        return m.bank.release(all);
    }
}

    The Four Hazards

    1. Two buyers, one can. selectSlot is not the commit. With no lock, both buyers pass the stock check on count = 1 and both reach Dispensing. Lock the slot (or CAS on count) and re-read stock inside dispense.
    2. Cannot make change. Buyer pays Rs 50 for a Rs 35 can and the till holds no Rs 10 or Rs 5. Paid, no change, argument. Check bank.canMake(due) before you accept the sale; else refund and ask for exact.
    3. Coin mid-dispense. A coin lands while the motor is turning. It must not add to a balance that is already committed. DispensingState.insertCoin is a no-op, the coin drops to the return tray.
    4. Power loss mid-vend. Stock is cut, then the machine dies before change is returned, or the coil turns and the can sticks. The vend is not atomic. Write the pending vend (slot, due) to a non-volatile store first; on boot, finish it or refund.

    Name them before they are asked: lock the slot (or CAS on count) and re-read stock inside dispense.

    The Three Lines They Are Watching

    1. Every press is delegated to state — the machine never branches on which state it is in. A new state is a class, not an if.
    2. bank.canMake(due) before setState(Dispensing) — nothing moves until change is guaranteed.
    3. cancel() returns the whole balance, zeroes it and resets to Idle in one step — never a half refund, never a stale credit.

    Running the State Machine

    Enum + switch a case in every method easy to miss a case scattered by event hard past 3 states drive the whole machine fine for 2 states
    State pattern (the default) a new class, nothing else edits unimplemented method nags with its state one state, one place unit-test one state a class per state
    Transition table (data-driven FSM) a new row + handler explicit in the table in one map whole machine on a page assert transitions build the table + dispatch

    Rejection Signals

    These end the interview:

    • The machine branches on a mode with if / switch in every method — a new state edits five places.
    • Money as a double — Rs 0.10 + Rs 0.20 stops being Rs 0.30 and the till slowly drifts.
    • The item moves before bank.canMake(change) is checked — buyer gets the can, no change, and argues.
    • One state accepts every call always — a double-tap on select vends twice.
    • No answer for cannot make change or last item, two buyers — the two cases every interviewer probes.
    • Price on the Product, not the Slot — the same drink in two slots cannot be priced apart.
    • A coin counted the moment it drops, before it is validated — a washer or a foreign coin buys a drink.
    • Change handed out before the item is confirmed dropped — a jammed coil pays the buyer to take nothing.
    • Greedy change written inline with while (due > 0) give biggest coin in dispense — no seam to swap the rule.

    Patterns Used

    State — one class per machine condition, transitions inside it. Strategy — changemaking now, pricing on page 2. Factory — build a Slot / Product from a config row. Singleton — one machine per cabinet.

    Say It Like This

    "One machine, slots keyed by code, each slot its own price and count, plus a coin bank. The machine is a context: every press delegates to the current state. Idle takes coins to HasMoney; HasMoney takes more or, on a valid select, hands to Dispensing; Dispensing drops the item, returns change from a ChangeStrategy, resets to Idle. Money is integer paise."

    The Follow-ups That Decide It

    1. Two buyers race the last item. Walk the steps. Lock the slot, re-check stock inside dispense, one wins.
    2. The till cannot make exact change. Refuse up front, refund, ask for exact, or drop to OutOfService.
    3. A coin drops while dispensing. DispensingState.insertCoin is a no-op, the coin rolls to the tray.
    4. Power dies mid-vend. Log the pending vend before the motor runs, replay on boot: finish or refund.
    5. Add a maintenance mode. OutOfServiceState — every buyer call refused, only Admin gets through.
    6. "Cheaper after 6pm." A PricingStrategy the machine asks at select; slots keep only stock.
    7. One product in three slots. Many codes map to one Product; select is by code, stock is per slot.
    8. Ten machines, one refiller. State and till are per machine; a fleet service reads counters, never one lock.

    Deliberately Not Built

    • Card / UPI payment — a PaymentMethod beside the coin path. The seam is the point; the PSP is not.
    • Real coin mechanism — validating, sorting and escrowing physical coins. Hardware, name it and move on.
    • Telemetry, remote restock — an Observer on low stock pushing to a fleet service. That is the HLD version.
    • Persistence — slots, till and the in-flight vend in a store, replayed on boot. Name the recovery log.
    • Multi-currency — money carries an amount only. A currency field and a rate table drop in later.
