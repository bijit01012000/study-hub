    Redis and caching

    9 sections · 3,668 words

    Module 05 - 9 questions - 1 practical drill

    Show that speed gains do not come at the cost of invisible inconsistency.

    Caching interviews look easy and aren't. The follow-ups go straight to the hard parts: invalidation, stampedes, consistency between cache and database, and what happens when Redis itself goes down. "We added Redis and it got faster" gets you nowhere.

    Inside this module: Cache patterns - Invalidation - Stampedes - Redis failure modes

    On a read miss the service goes to the cache, then the database; on a write it writes the DB and deletes the cache key. Invalidation is a consistency decision. Name the stale window and its user impact.

    Q5.1 - Tell me about a cache you added. What were you actually caching and why?

    What it really tests: Whether caching was targeted at a measured hot path, or sprinkled on hopefully.

    Weak answer: "We added Redis to cache database results so we didn't hit the DB every time. It reduced load and made the app faster."

    Why it fails: - No specific data or query identified as the hot path. - No hit-rate or latency numbers. - No TTL or invalidation strategy mentioned. - "Made it faster" with no baseline.

    Follow-up ladder: 1. TECHNICAL - What was the read/write ratio on that data? - Whether the data was cache-appropriate. 2. MEASUREMENT - What hit rate did you get, and was that good? - Cache effectiveness measured. 3. TRADEOFF - What TTL did you set and how did you pick it? - Staleness vs freshness reasoning. 4. FAILURE - What did you do when the cached data changed? - Invalidation awareness.

    Answer framework: 1. Identify hot, read-heavy data 2. Read/write ratio 3. Cache pattern chosen 4. Key design 5. TTL and why 6. Invalidation on write 7. Hit rate measured 8. Latency before/after

    Rejection signals: - Caches without knowing the read/write ratio. - No hit rate measured. - No TTL reasoning. - No invalidation plan.

    Model answer skeleton: I cached the product-detail lookup, which was read maybe 500:1 versus writes and sat on the hottest path in the catalogue - perfect cache candidate because it's read-heavy and tolerates brief staleness.

    I used cache-aside: the app checked Redis, and on a miss read Postgres and populated the cache with a 5-minute TTL.

    I picked 5 minutes because a stale price for a few minutes was acceptable to the business but hours weren't, and on any price update I proactively deleted the key so the next read refreshed it.

    We landed around a 94% hit rate, which took DB read load on that query down by roughly an order of magnitude and cut p95 on the endpoint from ~120ms to ~8ms.

    The number I watched was hit rate - if it had been 60% I'd have questioned whether the TTL or the key granularity was wrong rather than declaring victory.

    Q5.2 - How do you keep the cache and the database from drifting out of sync?

    What it really tests: The genuinely hard problem - cache invalidation and the race conditions in it.

    Weak answer: "On every update to the database we also update the cache with the new value, so they stay in sync."

    Why it fails: - Double-write (update DB then update cache) has a race that leaves stale data. - Doesn't consider concurrent writes interleaving. - No discussion of delete-vs-update on write. - Ignores the failure where one of the two writes fails.

    Follow-up ladder: 1. FAILURE - Two writers update the same key concurrently - how can the cache end up stale? - The double-write race. 2. TRADEOFF - Why is deleting the cache entry safer than updating it? - Delete-on-write reasoning. 3. TECHNICAL - DB write succeeds but cache delete fails - now what? - Partial-failure handling. 4. MEASUREMENT - How stale can you tolerate, and how does TTL bound it? - TTL as a safety net.

    Answer framework: 1. Prefer delete-on-write over update-on-write 2. Order: write DB then invalidate 3. Race windows and how TTL bounds them 4. Handle failed invalidation 5. Optionally CDC-driven invalidation 6. Accept a bounded staleness 7. Monitor stale reads

    Rejection signals: - Updates cache and DB as two writes, unaware of the race. - Thinks double-write guarantees consistency. - No fallback if invalidation fails. - No TTL safety net.

    Model answer skeleton: Updating both the database and the cache on write feels right but has a nasty race: two concurrent writers can interleave so the cache ends up holding the older value even though the DB has the newer one. So I invalidate rather than update - on a write I update the DB and then delete the cache key, letting the next read repopulate from the source of truth.

    That collapses the race, because the worst case is an extra cache miss, not a permanently wrong value.

    If the cache delete fails after the DB commit, a short TTL is my backstop - the stale entry self-heals within minutes, so I always set a TTL even with explicit invalidation.

    For data where even minutes of staleness mattered, I drove invalidation off the database change stream via CDC so it wasn't coupled to the application write path at all.

    And I set the TTL based on how much staleness the business could actually tolerate, treating it as the guarantee ceiling.

    Q5.3 - A popular cached key expires and thousands of requests hit the database at once. What is this and how do you prevent it?

    What it really tests: Cache stampede / thundering herd - a classic that separates real operators from theorists.

    Weak answer: "We'd just increase the TTL so the key doesn't expire as often, which reduces how often we hit the database."

    Why it fails: - Longer TTL delays but doesn't prevent the stampede. - Doesn't name the problem or the standard fixes. - No locking, no early recompute, no stale-while-revalidate. - Ignores that a cold cache or eviction triggers it too.

    Follow-up ladder: 1. TECHNICAL - How does a mutex/lock stop the stampede? - Single-flight recompute. 2. TRADEOFF - What's probabilistic early expiration (XFetch)? - Advanced prevention. 3. MEASUREMENT - How does stale-while-revalidate change the user experience? - Serving stale to protect the DB. 4. FAILURE - How would you protect against the same thing on a cold start? - Cold-cache stampede.

    Answer framework: 1. Name it (stampede/thundering herd) 2. Single-flight lock so one request recomputes 3. Warm the cache on deploy 4. Probabilistic early recompute 5. Stale-while-revalidate 6. Others wait or serve stale 7. Jitter TTLs to avoid synchronised expiry

    Rejection signals: - Only fix is a longer TTL. - Can't name the phenomenon. - No locking or single-flight concept. - No cold-start consideration.

    Model answer skeleton: That's a cache stampede, or thundering herd - one hot key expires and every concurrent request misses simultaneously, so a query that normally runs once a minute suddenly runs thousands of times and can take the database down. A longer TTL just postpones it.

    The core fix is single-flight: when the key is missing, requests take a short-lived Redis lock (SET NX), and only the lock winner recomputes and repopulates while the others briefly wait or serve the last stale value.

    I also like stale-while-revalidate - serve the expired value immediately and refresh asynchronously - so users never block on a recompute.

    For very hot keys, probabilistic early expiration (the XFetch approach) has requests randomly refresh slightly before the TTL, spreading the recompute so it never all lands at once.

    And I jitter TTLs so a batch of keys populated together doesn't all expire in the same instant, and warm critical keys on deploy so a cold start doesn't stampede.

    Q5.4 - Redis is full. What gets evicted, and how do you control that?

    What it really tests: Understanding of maxmemory policies and matching eviction to the workload.

    Weak answer: "Redis uses LRU to evict old keys when it's full, so the least recently used stuff gets removed automatically."

    Why it fails: - Assumes LRU is the default and only policy - it's configurable, and default is noeviction. - Doesn't distinguish allkeys- from volatile-. - No LFU consideration. - Doesn't consider using Redis as a store vs a cache (noeviction).

    Follow-up ladder: 1. TECHNICAL - What's the difference between allkeys-lru and volatile-lru? - TTL-scoped vs all-keys eviction. 2. TRADEOFF - When is LFU better than LRU? - Access-pattern fit. 3. FAILURE - What does noeviction do and when would you want it? - Redis-as-store awareness. 4. MEASUREMENT - A key with no TTL under volatile-lru - can it be evicted? - Precise policy semantics.

    Answer framework: 1. Redis is memory-bound 2. maxmemory-policy options 3. allkeys vs volatile scope 4. LRU vs LFU by access pattern 5. noeviction for durable use 6. Set TTLs deliberately 7. Monitor evictions and memory

    Rejection signals: - Thinks LRU is automatic and only option. - Doesn't know default is noeviction. - Can't distinguish allkeys from volatile. - Never heard of LFU.

    Model answer skeleton: What gets evicted depends entirely on maxmemory-policy, and the default is actually noeviction, which returns errors on writes when full - fine if you're using Redis as a durable store but wrong for a cache.

    For a pure cache I set allkeys-lru, which can evict any key by least-recently-used. volatile-lru only evicts keys that have a TTL, so if I mixed cache entries and durable keys in one instance I'd give the durable ones no TTL to protect them - though I generally prefer separate instances.

    I switch to allkeys-lfu when the access pattern is skewed toward a stable set of hot keys, because LFU keeps frequently-used keys even if they weren't touched in the last few seconds, whereas LRU can evict a popular-but-momentarily-idle key.

    I always set TTLs deliberately rather than relying solely on eviction, and I monitor the evicted-keys counter and memory usage, because rising evictions mean the working set no longer fits and hit rate is about to fall.

    Q5.5 - Redis goes down. What happens to your application?

    What it really tests: Whether the cache is a performance optimisation or an accidental hard dependency.

    Weak answer: "If Redis went down we'd have a problem, but we had Redis in a cluster with replication so it basically never went down."

    Why it fails: - Avoids the question by claiming it won't happen. - No graceful-degradation path if it does. - Implies the app hard-depends on Redis. - Ignores the DB load spike when the cache disappears.

    Follow-up ladder: 1. FAILURE - Does your app fail, or fall back to the database? - Graceful degradation. 2. TECHNICAL - The cache vanishes - what does that do to DB load? - Stampede-on-outage awareness. 3. MEASUREMENT - How do you keep a Redis timeout from hanging every request? - Timeouts on cache calls. 4. TRADEOFF - Is Redis your source of truth for anything? What breaks then? - Cache vs store distinction.

    Answer framework: 1. Classify: cache (fall back) vs store (critical) 2. Timeout on Redis calls 3. Fall back to DB on miss/error 4. Protect DB from the resulting surge 5. Rebuild/warm cache 6. Alert on Redis health 7. Avoid making Redis a hidden hard dependency

    Rejection signals: - "It won't go down" is the whole answer. - App fails entirely without Redis. - No timeout, so a slow Redis hangs requests. - Redis is a hidden source of truth with no recovery.

    Model answer skeleton: For anything I treat as a cache, a Redis outage should degrade performance, not availability: the client has a tight timeout - tens of milliseconds - so a slow or dead Redis fails fast instead of hanging every request, and on a cache error the code falls straight through to Postgres.

    The real danger is the load spike, because losing the cache is a total stampede - suddenly 100% of reads hit the database - so I protect the DB with per-key single-flight locking and, in the worst case, load shedding on non-critical reads.

    When Redis comes back I let it warm naturally through cache-aside, or pre-warm the hottest keys.

    What I'm careful never to do is quietly make Redis a source of truth - if I store something in Redis that isn't in a durable store, an outage becomes data loss, not just a slowdown, so anything that must survive lives in Postgres and Redis only accelerates it.

    Q5.6 - Cache-aside, write-through, write-behind - which did you use and why?

    What it really tests: Whether the candidate knows the caching patterns and their consistency/durability trade-offs.

    Weak answer: "We used cache-aside because it's the most common. The app checks the cache, and if it's not there, reads from the DB and stores it."

    Why it fails: - "Most common" is the reason, not a fit-to-requirement. - Doesn't contrast with write-through/write-behind consequences. - No mention of the consistency or durability trade-offs of each. - No case where a different pattern would be right.

    Follow-up ladder: 1. TRADEOFF - What consistency does write-through buy, and at what cost? - Write-through semantics. 2. FAILURE - What's the durability risk of write-behind? - Async write loss window. 3. TECHNICAL - With cache-aside, what's the first-read penalty? - Cold-miss awareness. 4. MEASUREMENT - Which one would you pick for a write-heavy counter? - Pattern-to-workload fit.

    Answer framework: 1. Cache-aside: lazy, app-managed, cold-miss penalty 2. Map to read/write ratio and durability need 3. Write-behind: fast writes, durability risk 4. Write-through: cache always fresh, write latency cost 5. Choice justified 6. Failure mode of the chosen pattern

    Rejection signals: - Picks cache-aside because it's popular, no trade-off. - Doesn't know write-behind's data-loss window. - Can't map pattern to workload. - Thinks one pattern fits all.

    Model answer skeleton: I default to cache-aside for read-heavy data because it's simple and the cache only holds what's actually requested, accepting a cold-miss penalty on the first read of each key.

    I'd use write-through when I need the cache to never be stale relative to the DB - every write goes through the cache to the DB synchronously, so reads are always fresh, at the cost of higher write latency and caching data that may never be read.

    Write-behind - acknowledging the write to the cache and flushing to the DB asynchronously - gives very fast writes and is great for something like a high-frequency view counter, but it has a real durability risk: if Redis dies before the flush, those writes are lost, so I'd only use it where losing a few recent increments is acceptable.

    So the choice tracks the read/write ratio and how much durability I can trade: cache-aside for read-heavy, write-through for freshness-critical, write-behind for write-heavy and loss-tolerant.

    Q5.7 - What's the difference between caching in Redis and using it as a database?

    What it really tests: Whether the candidate understands persistence, durability guarantees, and the danger of conflating the two.

    Weak answer: "Redis is in-memory so it's fast, and you can also persist it to disk, so it can work as a database too if you turn on persistence."

    Why it fails: - Glosses over the durability gap between RDB snapshots and AOF. - Implies persistence makes Redis a safe primary store without caveats. - No mention of the fsync/data-loss window. - Doesn't address memory-bound dataset size.

    Follow-up ladder: 1. TECHNICAL - RDB snapshots vs AOF - what's the durability difference? - Persistence modes. 2. MEASUREMENT - With AOF everysec, how much data can you lose? - The fsync window. 3. FAILURE - Your dataset exceeds RAM - what happens? - Memory-bound reality. 4. TRADEOFF - When is Redis genuinely a fine primary store? - Balanced judgement.

    Answer framework: 1. In-memory, memory-bound 2. Persistence via RDB and/or AOF 3. Durability window of each 4. Data-loss tolerance 5. Dataset must fit RAM 6. When Redis-as-store is acceptable 7. When it must stay a cache in front of a durable DB

    Rejection signals: - Thinks persistence makes Redis fully durable like Postgres. - Unaware of the fsync loss window. - Ignores the RAM limit on dataset size. - Uses Redis as a primary store for critical data blindly.

    Model answer skeleton: As a cache, Redis holds a disposable copy of data whose source of truth is elsewhere, so losing it just means cache misses. As a database it's your source of truth, and that raises two issues.

    First durability: Redis persists via RDB point-in-time snapshots, which can lose everything since the last snapshot on a crash, or AOF, which logs writes - and even AOF with the common everysec fsync can lose up to about a second of writes.

    So it's durable-ish, not Postgres-durable. Second, it's memory-bound: the whole dataset must fit in RAM plus overhead, or you're into eviction or swapping, which a growing primary dataset will eventually hit.

    I'm comfortable using Redis as a primary store for things like session state or rate-limit counters, where sub-second loss on a rare crash is acceptable and the data is naturally bounded.

    For orders or payments - anything I can't lose a second of - Redis stays a cache in front of Postgres, never the system of record.

    Q5.8 - How did you design your cache keys, and why does that matter?

    What it really tests: Whether key design was intentional - namespacing, granularity, versioning - or ad hoc.

    Weak answer: "We used the entity ID as the key, like the user ID, so we could look up the cached user by their ID."

    Why it fails: - No namespacing, risking key collisions across data types. - No versioning, so a schema change can't invalidate cheaply. - No thought about granularity (one big object vs fields). - Doesn't consider how to bulk-invalidate related keys.

    Follow-up ladder: 1. TECHNICAL - How do you avoid collisions between two features using the same id? - Namespacing discipline. 2. TRADEOFF - You change the cached object's shape - how do you invalidate cheaply? - Key versioning. 3. MEASUREMENT - Cache one big user object vs individual fields - trade-off? - Granularity reasoning. 4. FAILURE - How do you invalidate all keys for one tenant at once? - Bulk invalidation strategy.

    Answer framework: 1. Namespace by domain 2. Include entity type and id 3. Version the key on schema change 4. Choose granularity by access pattern 5. Plan bulk invalidation 6. Avoid unbounded key cardinality 7. Document the key scheme

    Rejection signals: - Raw ids as keys, collision-prone. - No versioning for schema changes. - Never thought about granularity. - No way to bulk-invalidate.

    Model answer skeleton: I namespace keys by domain and type so there's no collision - user:profile:v2:{id} rather than a bare id, because two features both keyed on a numeric id would otherwise clobber each other.

    The v2 is deliberate: when I change the cached object's shape, I bump the version in the key, which instantly orphans all old entries so I don't have to hunt down and delete them - they just age out.

    Granularity is an access-pattern call: I cache the whole profile object when it's always read together, but if only a couple of fields are hot and the rest change often, I cache those fields separately to avoid invalidating everything on a minor update.

    For bulk invalidation, like flushing everything for one tenant, I either prefix keys by tenant and use a tag/set of keys to delete, or bump a per-tenant version embedded in the key.

    I avoid keys with unbounded cardinality that would blow up memory, and I keep the scheme documented so the whole team constructs keys the same way.

    Q5.9 - [DRILL] Design the caching for a product page that shows price (changes often) and description (rarely changes) under heavy read load. Specify keys, TTLs, invalidation, and stampede protection.

    What it really tests: Whether the candidate can combine granularity, TTL tuning, invalidation, and stampede defence into one coherent design.

    Weak answer: N/A - drill. A weak attempt caches the whole page under one TTL.

    Why it fails: - One key for the whole page couples volatile price to stable description. - Single TTL is wrong for both - too long for price, too short for description. - No invalidation on price change. - No stampede protection on the hot key.

    Follow-up ladder: 1. TECHNICAL - Why split price and description into separate keys? - Granularity by volatility. 2. FAILURE - How do you protect the hot price key from a stampede? - Single-flight / stale-while-revalidate. 3. MEASUREMENT - What invalidates the price key, and how fast? - Event-driven invalidation.

    Answer framework: 1. Separate keys by volatility 2. Short TTL + event invalidation on price 3. Long TTL on description 4. Namespace and version keys 5. Single-flight lock on the hot price key 6. Stale-while-revalidate 7. Jitter TTLs 8. Monitor hit rate per key

    Rejection signals: - One page-level key and TTL. - No invalidation on price change. - No stampede protection. - Same TTL for volatile and stable data.

    Model answer skeleton: Drill output: I split by volatility - product:price:v1:{id} and product:desc:v1:{id} - because bundling them forces one TTL onto two very different change rates.

    Description gets a long TTL, say an hour, since it rarely changes and I invalidate it explicitly on the rare edit.

    Price gets a short TTL, say 30-60 seconds, plus event-driven invalidation: the pricing service publishes a price-changed event and the consumer deletes that key so a change propagates in seconds rather than waiting out the TTL.

    Because the price key is extremely hot, I guard against stampede with single-flight - on a miss, one request takes a Redis SET-NX lock and recomputes while others serve the last stale price via stale-while-revalidate - and I jitter TTLs so keys populated together don't expire in lockstep.

    I monitor hit rate per key type separately, because a falling price hit rate is expected (short TTL) but a falling description hit rate would signal something wrong.
