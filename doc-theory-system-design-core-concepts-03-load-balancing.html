    Load Balancing

    6 sections · 631 words

    Spread the traffic. Scaling & Distribution, concept 03 of 36.

    The Idea

    A load balancer sits in front of many servers, spreads requests across them, and stops sending traffic to a server that is unhealthy. Without one, every client has to know exactly which server to hit. Traffic clumps unevenly, and a dead server just keeps getting requests nobody answers.

    One request is routed and one server is skipped:

    • Client -> Load Balancer
    • counter: next = 3
    • request -> to 1, skip, to 3
    • Server 1 healthy, Server 2 down, Server 3 healthy
    • The LB reads its round-robin counter, skips the unhealthy server, and Server 3 gets the request.

    How It Decides

    Algorithm How it decides Best for
    Round robin rotate through servers in order equal-cost requests, simplest to reason about
    Least connections whoever has the fewest active requests requests that take unequal time to finish
    Consistent hashing same client or key always picks the same server the server holds a cache or a session

    L4 vs L7: L4 routes by IP and port only, fast, and never reads the request. L7 reads the HTTP request and can route by URL, header, or cookie. Slower per request, but far more flexible.

    Watch Out For

    • Sticky sessions fight horizontal scaling. Move the session data instead of pinning the client to one server.
    • A health check that only pings the root path can miss a server whose database connection is dead. Check something that proves the server can do its actual job.

    Where You Will See It

    • AWS ALB/NLB: L7 and L4 managed load balancers in front of most AWS web workloads.
    • NGINX / HAProxy: the self-hosted default for years, and still everywhere.
    • Kubernetes Service: a built-in load balancer across the pods behind one service name.
    • DNS round robin: the cheapest, crudest form. Multiple IPs on one A record, with no health awareness at all.

    How It Connects

    • Consistent Hashing: the algorithm behind the same client, same server routing option.
    • Service Discovery: how the LB learns which server instances currently even exist.
    • Stateless Services: what makes it safe for the LB to send any request to any server in the first place.
    • Circuit Breaker: a different layer's answer to the same question a health check asks. Is this thing still healthy?

    Follow-Up Questions

    1. Round robin is about to send request 4 to Server 2, which just went down. What happens? The health check already marked it down, so request 4 skips straight to Server 3.

    2. Two requests from the same user need to land on the same server. How? Consistent hashing, or better, move the session data out so any server can serve it.

    3. The load balancer itself goes down. Now what? Run at least two behind a floating IP or DNS failover. One LB is a new single point of failure.

    4. Route requests by URL path, /api here, /static there. L4 or L7? L7. Only L7 actually reads the HTTP request far enough to see the path.

    5. One server is twice as powerful as the other two. Is round robin still fair? No, it sends equal traffic to unequal machines. Use weighted round robin instead.

    6. A health check passes but the server is still timing out real requests. Why? The check probably pings a cheap endpoint. Check something that exercises the real dependency, like the database.

    Recall It As

    The LB is the traffic cop: one entrance, many roads, never send a car down a closed one.
