    Lecture 21 — Spring Boot Interceptors

    17 sections · 4,439 words

    Lecture 21

    Scope evidence: "Spring Boot Interceptors | preHandle, postHandle & afterCompletion" (playlist map, verified). Repo folder is the interceptorDemo project: an interceptor package holding LoggingInterceptor, AuthenticationInterceptor, and AuthorizationInterceptor, plus config.WebConfig and controller.StudentController, together with the notes.

    Controllers should handle business use cases, not plumbing. A Spring MVC interceptor is the handler-aware checkpoint that runs common logic before a controller, after it, and once the whole MVC cycle finishes. This lecture covers where it fits in the request flow, its three lifecycle callbacks, how to register one with WebMvcConfigurer, and how it differs from a servlet Filter.

    1. The Problem Interceptors Solve

    Consider a controller with several endpoints:

    @RestController
@RequestMapping("/api/students")
public class StudentController {
    @GetMapping
    public String getAllStudents() { return "All students"; }

    @PostMapping
    public String createStudent() { return "Student created"; }

    @DeleteMapping("/{id}")
    public String deleteStudent(@PathVariable Long id) { return "Student deleted"; }
}

    Suppose every request needs the same common operations: log the requested URL, check authentication or authorization, record execution time, identify the controller method being executed, add request attributes, and read common request information.

    Adding that logic directly to every controller method creates four problems:

    1. Controller methods become cluttered.
    2. The same code is duplicated across endpoints.
    3. A small change must be repeated in several places.
    4. Business logic becomes mixed with infrastructure logic.

    An interceptor provides one central place for such cross-cutting MVC logic.

    Definition: a Spring MVC interceptor is a component that executes before a handler, after a handler, and after the complete MVC request-processing cycle.

    Request -> Interceptor -> Controller -> Interceptor -> Response

    An interceptor does not normally replace the controller. It surrounds its execution.

    Important: Interceptors exist so infrastructure logic - logging, auth checks, timing - is written once and surrounds handler execution, instead of being copy-pasted into every endpoint.

    2. Where an Interceptor Fits in Spring MVC

    The DispatcherServlet is the central servlet of Spring MVC. When a request reaches a Spring MVC application:

    1. The DispatcherServlet receives the request.
    2. A HandlerMapping identifies the matching handler.
    3. Spring creates a handler execution chain.
    4. Registered interceptors execute around the handler.
    5. A HandlerAdapter invokes the controller method.
    6. Spring processes the controller's return value.
    7. The response is sent to the client.
    Client -> Servlet Container -> DispatcherServlet
       -> HandlerMapping finds the handler
       -> Interceptor
       -> HandlerAdapter invokes the controller
       -> Response processing -> Client

    Why is it called HandlerInterceptor? Spring uses the general term handler because the selected handler is not always a controller method. It may be a controller method, a static-resource handler, or another handler type supported by Spring MVC.

    For normal controller requests, the handler is commonly represented by a HandlerMethod.

    When Spring finds a handler, it conceptually creates a chain containing the handler and its interceptors:

    HandlerExecutionChain
|-- Interceptor 1
|-- Interceptor 2
|-- Interceptor 3
`-- Controller handler

    The DispatcherServlet executes this chain. An interceptor can therefore allow or stop the request before the controller runs.

    3. The Three Interceptor Lifecycle Methods

    A HandlerInterceptor provides three main callback methods: preHandle(), postHandle(), and afterCompletion().

    Request -> preHandle() -> Controller method -> postHandle()
        -> Response processing or view rendering
        -> afterCompletion() -> Response
    Method Execution point Main purpose
    preHandle() Before the selected handler executes Validation, logging, authentication checks, starting timers
    postHandle() After successful handler execution, before traditional view rendering Model or view-related postprocessing
    afterCompletion() After MVC request processing finishes Cleanup, final logging, timing, status inspection

    A fuller comparison makes the ordering rule obvious:

    Aspect preHandle() postHandle() afterCompletion()
    When it runs Before the handler After the handler succeeds After the whole MVC cycle
    Return type boolean void void
    Extra parameter none ModelAndView Exception
    Can it stop the chain Yes, by returning false No No
    Typical use Logging, auth, timers Model/view attributes Cleanup, timing, status, errors
    Runs on request failure Yes (before failure) No Yes

    Mnemonic: the three callbacks are P-P-A - Pre, Post, After - framing controller execution on all three sides.

    4. Creating a Custom Interceptor and Its Method Parameters

    Create a Spring component that implements HandlerInterceptor (annotate it with @Component). Modern versions of HandlerInterceptor provide default method implementations, so an interceptor only needs to override the callbacks it actually uses.

    package in.strikes.crudDemo.interceptor;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.lang.Nullable;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;
import org.springframework.web.servlet.ModelAndView;

@Component
public class LoggingInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) throws Exception {
        System.out.println("preHandle executed");
        return true;
    }

    @Override
    public void postHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            @Nullable ModelAndView modelAndView
    ) throws Exception {
        System.out.println("postHandle executed");
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            @Nullable Exception ex
    ) throws Exception {
        System.out.println("afterCompletion executed");
    }
}

    For an interceptor that only checks something before the controller, overriding only preHandle() is sufficient.

    The Method Parameters

    HttpServletRequest request represents the incoming HTTP request. Commonly used methods include request.getMethod(), request.getRequestURI(), request.getQueryString(), request.getHeader("Authorization"), request.getRemoteAddr(), request.getParameter("name"), and request.getSession().

    Request-specific values can also be stored as attributes for later retrieval:

    request.setAttribute("requestStartTime", System.nanoTime());
Long startTime = (Long) request.getAttribute("requestStartTime");

    HttpServletResponse response represents the outgoing HTTP response. It can set the status, headers, content type, or response content:

    response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
response.setHeader("X-App-Name", "Student Management System");
response.setContentType("application/json");
response.getWriter().write("""
{ "message": "Unauthorized" }
""");

    Important: Once a response is committed, some changes may be too late. This is especially important when working with REST response bodies.

    Object handler represents the handler selected by Spring. For a normal controller request, it is commonly a HandlerMethod:

    if (handler instanceof HandlerMethod handlerMethod) {
    String controllerName = handlerMethod.getBeanType().getSimpleName();
    String methodName = handlerMethod.getMethod().getName();
}

    Possible output: StudentController and getAllStudents.

    Do not cast the handler blindly with (HandlerMethod) handler. Some requests may be handled by something other than a controller method, such as a static-resource handler. Use pattern matching with instanceof instead. This ability to inspect the selected controller and method is one of the major differences between an interceptor and a servlet filter.

    5. preHandle(): Continue or Stop the Chain

    boolean preHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler
) throws Exception

    It executes after Spring has selected the handler but before the handler is invoked.

    Why does it return boolean? The return value tells Spring whether request processing should continue.

    • Returning true: Spring continues to the next interceptor or the controller.
    • Returning false: Spring stops the execution chain, and the controller is not called.

    When returning false, the interceptor should usually prepare an appropriate response. Otherwise, the client may receive an empty or confusing response:

    response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
response.setContentType("application/json");
response.getWriter().write("""
{ "message": "Authentication required" }
""");
return false;

    Common uses of preHandle(): logging request arrival, starting an execution timer, reading a tenant or organization ID, creating a correlation ID, adding request attributes, validating custom headers, checking custom annotations, and rejecting a request before the controller.

    Interviewer's perspective: The boolean return is the heart of preHandle(). Saying "true continues, false stops the chain, and when you stop it you must write the response yourself" marks a candidate who has actually used interceptors.

    For production-grade authentication and authorization, prefer Spring Security instead of building a complete security system through a custom interceptor.

    6. postHandle(): The View-Rendering Hook

    void postHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler,
        ModelAndView modelAndView
) throws Exception

    It executes after the handler completes successfully but before traditional MVC view rendering.

    preHandle() -> Controller -> postHandle() -> View rendering

    Why does it receive ModelAndView? Traditional Spring MVC controllers may return a view; Spring stores the selected view and model data inside a ModelAndView. An interceptor can add common model information:

    @Override
public void postHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler,
        ModelAndView modelAndView
) {
    if (modelAndView != null) {
        modelAndView.addObject("applicationName", "Student Management System");
    }
}

    What happens with REST controllers? A @RestController normally returns data that Spring serializes directly into the response body. In such cases modelAndView == null.

    For methods using @ResponseBody or ResponseEntity, Spring may already have written the response before postHandle() executes. Therefore, postHandle() is not a reliable place to redesign or wrap a REST response body. Use ResponseBodyAdvice (for example with @ControllerAdvice) when a common REST response transformation is required.

    Good uses of postHandle(): updating a traditional MVC model, adding common view attributes, logging successful controller completion, inspecting the selected handler, and running logic before view rendering. For REST APIs, afterCompletion() is often more useful for final logging and timing.

    7. afterCompletion(): Cleanup, Timing, and Exceptions

    void afterCompletion(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler,
        Exception ex
) throws Exception

    It executes after the complete Spring MVC request-processing cycle finishes.

    preHandle() -> Controller -> postHandle()
            -> Response processing or view rendering
            -> afterCompletion()

    It is similar to a finally block and is commonly used for cleanup, final request logging, execution-time calculation, releasing request-related resources, recording the final response status, and inspecting an unhandled exception.

    @Override
public void afterCompletion(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler,
        Exception ex
) {
    if (ex != null) {
        System.out.println("Request failed: " + ex.getMessage());
    } else {
        System.out.println("Request completed with status: "
                + response.getStatus());
    }
}

    Important: ex == null does not always prove that no exception occurred. An exception may have been handled by Spring through @ExceptionHandler, @ControllerAdvice, @RestControllerAdvice, or another exception resolver, and already converted into a valid HTTP response. Final monitoring should also inspect response.getStatus();.

    8. Registering an Interceptor with WebMvcConfigurer: Patterns, Exclusions, and Order

    Creating an interceptor bean is not enough. It must also be added to Spring MVC's interceptor registry.

    package in.strikes.crudDemo.config;

import in.strikes.crudDemo.interceptor.LoggingInterceptor;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class WebConfig implements WebMvcConfigurer {

    private final LoggingInterceptor loggingInterceptor;

    public WebConfig(LoggingInterceptor loggingInterceptor) {
        this.loggingInterceptor = loggingInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loggingInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/auth/login", "/api/public/**")
                .order(1);
    }
}

    Role of each part: @Configuration marks the class as an application configuration class; WebMvcConfigurer provides callback methods for customizing Spring MVC; addInterceptors() registers MVC interceptors; and registry.addInterceptor() adds an interceptor to the MVC handler chain. Constructor injection provides the interceptor bean to the configuration class.

    The addInterceptor() method returns an InterceptorRegistration, which configures included URL patterns, excluded URL patterns, and execution order.

    Without path configuration (registry.addInterceptor(loggingInterceptor);) the interceptor may apply broadly to requests handled by Spring MVC's configured handler mappings. With patterns, it is scoped:

    registry.addInterceptor(loggingInterceptor)
        .addPathPatterns("/api/students/**")
        .addPathPatterns("/api/students/**", "/api/teachers/**", "/api/courses/**");

    Common patterns:

    Pattern Meaning
    /api/students Exact path
    /api/students/* One path segment after /students
    /api/students/** Any nested path under /students
    /api/** All API paths
    /** All matching MVC paths

    Included and excluded patterns can be combined on the same interceptor registration, for example including /api/** while excluding /api/auth/login and /api/auth/register.

    Multiple Interceptors and Execution Order

    Suppose two interceptors, A and B, are registered in that order. Their successful execution flow is:

    A.preHandle() -> B.preHandle() -> Controller
             -> B.postHandle() -> A.postHandle()
             -> Response processing / view rendering
             -> B.afterCompletion() -> A.afterCompletion()

    The pattern is: preHandle() executes in forward order, while postHandle() and afterCompletion() execute in reverse order. This resembles nested method calls - A opens, B opens, the controller executes, B closes, A closes.

    Configuring the order:

    registry.addInterceptor(loggingInterceptor).order(1);
registry.addInterceptor(authInterceptor).order(2);
registry.addInterceptor(timingInterceptor).order(3);

    Lower order values have higher priority and execute earlier during preHandle(). Only interceptors whose preHandle() successfully participated in the chain are eligible for the corresponding completion callbacks.

    Mnemonic: preHandle runs like a queue (first in, first run); postHandle and afterCompletion unwind like a stack (last in, first run).

    9. Practical Interceptors: Logging, Authentication, Authorization, and Timing

    Logging Request Details

    A practical logging interceptor can access both HTTP information and the selected controller method. In preHandle() it prints the method, URI, query string, client IP, and - using handler instanceof HandlerMethod handlerMethod - the controller name (getBeanType().getSimpleName()) and method name (getMethod().getName()), then returns true.

    System.out.println() is acceptable for learning examples. In a real application, use a logging framework such as SLF4J:

    private static final Logger log =
        LoggerFactory.getLogger(RequestLoggingInterceptor.class);

    Authentication Demonstration with an API Key

    The following example demonstrates how an interceptor can stop a request. It is useful for understanding the flow but should not replace Spring Security in a production application.

    Requirement: the client sends X-API-KEY: student-secret-key; a correct key continues to the controller; a missing or incorrect key returns 401 Unauthorized; and the controller must not execute.

    package in.strikes.crudDemo.interceptor;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.http.MediaType;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

@Component
public class ApiKeyAuthenticationInterceptor implements HandlerInterceptor {

    private static final String VALID_API_KEY = "student-secret-key";

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) throws Exception {
        String apiKey = request.getHeader("X-API-KEY");
        if (apiKey == null) {
            writeUnauthorizedResponse(response, "API key is missing");
            return false;
        }
        if (!VALID_API_KEY.equals(apiKey)) {
            writeUnauthorizedResponse(response, "Invalid API key");
            return false;
        }
        return true;
    }

    private void writeUnauthorizedResponse(
            HttpServletResponse response,
            String message
    ) throws Exception {
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType(MediaType.APPLICATION_JSON_VALUE);
        response.getWriter().write("""
        {
          "message": "%s"
        }
        """.formatted(message));
    }
}

    The response is written before returning false because the controller will not execute and will not create a response. Register it for selected paths with addPathPatterns("/api/**") and excludePathPatterns("/api/auth/login", "/api/public/**").

    Authorization Demonstration

    Suppose only users with the ADMIN role can access a delete operation, and the client sends X-USER-ROLE: ADMIN. A simplified check inside preHandle() reads request.getMethod(), and if it equals DELETE it reads the X-USER-ROLE header. If the role is not ADMIN, it sets SC_FORBIDDEN, writes a "Admin access required" JSON body, and returns false; otherwise it returns true. This is a learning example - real authorization rules should normally go through Spring Security.

    401 vs 403

    Status Meaning Example
    401 Unauthorized The client has not been successfully authenticated Missing, invalid, or expired token
    403 Forbidden The client is authenticated but lacks permission A normal user attempts an admin-only operation

    The constants are HttpServletResponse.SC_UNAUTHORIZED (401) and HttpServletResponse.SC_FORBIDDEN (403).

    Measuring Request Execution Time

    The flow is: record start time, execute the controller, then calculate the total duration.

    The incorrect approach stores the start time in an instance field. This is unsafe because Spring components are singleton-scoped by default, so multiple requests may use the same interceptor instance concurrently (Request A starts at 1000, Request B starts at 1100, and Request A ends up incorrectly using 1100). Request-specific mutable data should never live in a normal interceptor instance field.

    The correct approach uses request attributes: each request has its own HttpServletRequest, so store the start time there and read it back in afterCompletion().

    package in.strikes.crudDemo.interceptor;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;
import java.util.concurrent.TimeUnit;

@Component
public class RequestTimingInterceptor implements HandlerInterceptor {

    private static final String START_TIME_ATTRIBUTE = "requestStartTime";

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler
    ) {
        request.setAttribute(START_TIME_ATTRIBUTE, System.nanoTime());
        return true;
    }

    @Override
    public void afterCompletion(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler,
            Exception ex
    ) {
        Long startTime = (Long) request.getAttribute(START_TIME_ATTRIBUTE);
        if (startTime == null) {
            return;
        }
        long durationNanos = System.nanoTime() - startTime;
        long durationMillis = TimeUnit.NANOSECONDS.toMillis(durationNanos);

        System.out.println("Request: " + request.getMethod()
                + " " + request.getRequestURI());
        System.out.println("Status: " + response.getStatus());
        System.out.println("Execution time: " + durationMillis + " ms");
    }
}

    Why afterCompletion()? postHandle() runs after successful handler execution, but afterCompletion() measures closer to the end of the complete MVC lifecycle, including later processing such as exception resolution and traditional view handling.

    Why System.nanoTime()? System.currentTimeMillis() represents wall-clock time and the system clock can be adjusted, whereas System.nanoTime() is designed for measuring elapsed time.

    10. Filters and Interceptors Together

    A filter surrounds servlet processing. An interceptor surrounds a Spring MVC handler.

    HTTP Request
   -> Filter 1 / Filter 2: before chain.doFilter()
   -> Servlet Container -> DispatcherServlet -> HandlerMapping finds controller
   -> Interceptor 1.preHandle() -> Interceptor 2.preHandle()
   -> Controller
   -> Interceptor 2.postHandle() -> Interceptor 1.postHandle()
   -> Response processing or view rendering
   -> Interceptor 2.afterCompletion() -> Interceptor 1.afterCompletion()
   -> Filter 2 / Filter 1: after chain.doFilter()
   -> HTTP Response

    Core difference: a filter works at the Servlet layer, while an interceptor works inside Spring MVC after a handler has been selected.

    Request and Response Wrapping

    A filter can wrap or replace the request and response objects passed further into the chain with chain.doFilter(wrappedRequest, wrappedResponse). This makes filters suitable for caching a request body, reading a request body multiple times, capturing a response body, transforming request or response data, and compression and encoding concerns. An interceptor receives the request and response after processing has already entered Spring MVC; it cannot replace the objects used by the entire servlet chain in the same way.

    Filter vs Interceptor

    Point Filter Interceptor
    Layer Servlet layer Spring MVC layer
    Main target Servlet request and response Selected MVC handler
    Knows controller method Normally no Yes, through HandlerMethod
    Main before callback Code before chain.doFilter() preHandle()
    Main after callback Code after chain.doFilter() postHandle() / afterCompletion()
    Can wrap request/response Yes Not in the same chain-wide manner
    Can block processing Yes, by skipping chain.doFilter() Yes, by returning false from preHandle()
    Suitable for body wrapping Yes No
    Suitable for controller annotations No Yes
    Common security mechanism Spring Security filter chain Not a replacement for Spring Security

    When to Use a Filter

    Use a filter when the concern applies to the complete HTTP or servlet request rather than specifically to a controller method. Common examples:

    1. Request or response body wrapping.
    2. Request-body caching.
    3. Response-body capture or transformation.
    4. Character encoding.
    5. Compression.
    6. CORS-related processing.
    7. Logging all servlet traffic.
    8. Security processing before Spring MVC.

    Spring Security uses servlet filters because authentication and authorization generally need to happen before a request reaches the controller layer.

    When to Use an Interceptor

    Use an interceptor when the requirement depends on Spring MVC or the selected handler. Common examples:

    1. Logging controller and method names.
    2. Reading custom annotations from controller methods.
    3. Starting and completing controller-related timing.
    4. Adding common request attributes.
    5. Adding common model attributes in traditional MVC.
    6. Collecting MVC-specific metrics.
    7. Applying tenant or organization context based on handler rules.
    8. Running logic before and after a particular group of controller endpoints.

    Golden rule: if the logic depends on the selected handler, use an interceptor; if it depends only on the raw HTTP request or response, use a filter.

    11. Common Mistakes

    Mistake 1 - Creating an interceptor but not registering it. @Component creates the bean, but addInterceptors() places it in the Spring MVC chain.

    Mistake 2 - Returning false without writing a response. When preHandle() returns false, the controller does not execute. Prepare an appropriate status and body before stopping the chain.

    Mistake 3 - Storing request data in an interceptor field. Interceptors are normally singleton beans. Store request-specific values in request attributes instead.

    Mistake 4 - Blindly casting the handler. Not every handler is a HandlerMethod. Always check with instanceof.

    Mistake 5 - Modifying a REST body inside postHandle(). The response may already have been written. Use ResponseBodyAdvice or a filter-based wrapper, depending on the requirement.

    Mistake 6 - Building production security manually. A custom API-key interceptor is useful for learning request flow, but production authentication and authorization should normally use Spring Security.

    Mistake 7 - Assuming ex == null means no error occurred. A global exception handler may already have handled the exception. Also inspect the final HTTP status.

    12. Myth vs Reality

    Myth Reality
    "An interceptor replaces the controller" It surrounds controller execution; it does not replace it.
    "Creating the interceptor bean is enough" It must also be registered through addInterceptors().
    "Returning false just skips to the next interceptor" Returning false stops the whole chain; the controller never runs.
    "Returning false is enough on its own" You should also write the response; otherwise the client gets an empty or confusing reply.
    "You can cast handler directly to HandlerMethod" Only controller requests are HandlerMethod; guard with instanceof.
    "postHandle() can wrap a REST response body" For @ResponseBody/ResponseEntity the response may already be written; use ResponseBodyAdvice.
    "ex == null proves no exception happened" A global handler may have caught it; also check response.getStatus().
    "An instance field is fine for request timing" Interceptors are singletons; store per-request data in request attributes.
    "A custom API-key interceptor equals real security" It is a learning example; production auth belongs in Spring Security.

    13. Common Trap Questions

    Trap 1 - "An interceptor can run before the handler is selected." Verdict: False. The HandlerMapping selects the handler first; preHandle() runs after selection but before invocation, which is exactly why it can inspect the HandlerMethod.

    Trap 2 - "preHandle() returning false continues to the controller." Verdict: False. Returning false stops the execution chain, so the controller is not called; write the response before returning false.

    Trap 3 - "postHandle() runs even when the controller throws." Verdict: False. postHandle() runs only after successful handler execution. afterCompletion() still runs and is the place for final logging and cleanup.

    Trap 4 - "afterCompletion() with ex == null means success." Verdict: False. An exception may already have been resolved by @ExceptionHandler, @ControllerAdvice, or another resolver; always inspect response.getStatus() too.

    Trap 5 - "A @Component interceptor is automatically active." Verdict: False. The bean exists, but it must be added to the registry with addInterceptors() to join the Spring MVC chain.

    Trap 6 - "All interceptors run in the same direction in every phase." Verdict: False. preHandle() runs in forward order; postHandle() and afterCompletion() run in reverse order.

    Trap 7 - "Interceptors are the correct tool for body wrapping or real security." Verdict: Misleading. Body wrapping needs a filter, and production authentication and authorization belong in Spring Security, not a hand-written interceptor.

    14. Points to Remember

    1. An interceptor is a handler-aware MVC component that runs before a handler, after it, and after the complete MVC cycle.
    2. The flow is HandlerMapping -> HandlerExecutionChain -> interceptors -> HandlerAdapter -> controller -> return value -> response.
    3. The three callbacks are preHandle(), postHandle(), and afterCompletion() (mnemonic: P-P-A).
    4. preHandle() returns boolean: true continues, false stops the chain and the controller does not run.
    5. When preHandle() returns false, write the response yourself, or the client sees an empty or confusing reply.
    6. postHandle() runs after successful execution and receives a ModelAndView; for REST it is often null, and REST bodies may already be written.
    7. afterCompletion() is finally-like; use it for cleanup, final logging, timing, and status inspection.
    8. ex == null does not prove success; also check response.getStatus() because an exception may already have been handled.
    9. Register interceptors with WebMvcConfigurer.addInterceptors(); configure included patterns, excluded patterns, and order() on the returned registration.
    10. preHandle() runs forward while postHandle() and afterCompletion() run in reverse; keep per-request state in request attributes, never in singleton fields.

    15. Likely Interview Questions

    Question Crisp Answer
    What is a Spring MVC interceptor? A handler-aware component that runs logic before a handler, after it, and after the complete MVC request cycle.
    Why do we need interceptors? To centralize cross-cutting MVC logic (logging, auth checks, timing, request attributes) so controllers stay clean and no endpoint is forgotten.
    Where does an interceptor fit in Spring MVC? Inside DispatcherServlet's flow, after HandlerMapping selects a handler and around the HandlerAdapter invoking the controller.
    What is a HandlerExecutionChain? The object holding the selected handler plus its registered interceptors, executed around the handler.
    How do you create an interceptor? Implement HandlerInterceptor (annotated @Component) and override only the callbacks you need.
    How do you register an interceptor? Implement WebMvcConfigurer and call registry.addInterceptor(...) inside addInterceptors().
    What does preHandle() return and why? A boolean: true continues the chain, false stops it so the controller is not called.
    Difference between preHandle and postHandle? preHandle runs before the handler and can stop the chain; postHandle runs after successful execution and can adjust the ModelAndView.
    What is afterCompletion() for? finally-like cleanup, final logging, elapsed-time calculation, and status inspection after the whole MVC cycle.
    Why must timing use request attributes? Interceptors are singleton beans; an instance field is shared across concurrent requests, while each request has its own HttpServletRequest.
    What is the execution order with multiple interceptors? preHandle in forward order, postHandle and afterCompletion in reverse order; lower order() values run earlier.
    Filter vs Interceptor? A filter is Servlet-layer and cannot see the handler; an interceptor is Spring MVC-layer and can inspect the selected HandlerMethod.

    16. Final Summary

    HTTP Request
   -> Servlet Container / Filter chain -> DispatcherServlet
   -> HandlerMapping -> HandlerExecutionChain (interceptors + handler)
   -> preHandle()  (forward order; can return false to stop)
   -> HandlerAdapter -> Controller method
   -> postHandle()  (reverse order; ModelAndView)
   -> Response processing / view rendering
   -> afterCompletion()  (reverse order; cleanup, timing, status, exception)
   -> HTTP Response
    • An interceptor surrounds handler execution; it does not replace the controller.
    • preHandle() decides true = continue or false = stop (and write the response).
    • postHandle() is the view/model hook and is unreliable for REST bodies.
    • afterCompletion() is the finally hook for cleanup, timing, and status.
    • Register via WebMvcConfigurer.addInterceptors() with patterns, exclusions, and order().
    • Forward before the controller, reverse after it.
    • Keep per-request state in request attributes, not singleton fields.
    • Use a filter for HTTP-level concerns; use an interceptor for handler-aware concerns.
    • Real authentication and authorization belong in Spring Security.

    One-line takeaway: A Spring MVC interceptor is a handler-aware wrapper - preHandle gates the request in forward order, postHandle and afterCompletion unwind in reverse, and the logic lives once instead of in every controller.
