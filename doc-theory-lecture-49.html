    Thread Methods | sleep, join, yield, interrupt, isAlive, priority & more

    26 sections · 4,769 words

    Lecture 49

    Scope evidence: "Thread Methods | sleep, join, yield, interrupt, isAlive, priority & more" plus the lecture's own repo notes (sleep/join/yield/interrupt/isInterrupted/currentThread), playlist map, verified. Repo evidence: 8 Demo files.

    Lecture 48 established how a thread is created and how its lifecycle is modelled. This lecture catalogues the methods that control, coordinate, inspect and configure a running thread: sleep(), join(), yield(), interrupt(), isInterrupted(), interrupted(), isAlive(), currentThread(), setName()/getName(), setPriority() and setDaemon(). Each method is examined through five questions: which thread is affected, whether it blocks, whether a lock is released, which thread state is entered, and whether the behaviour is guaranteed or merely suggested. The recurring lesson is that most cross-thread control in Java is cooperative and hint-based, so correctness must never rest on scheduling.

    1. The Method Map — What This Lecture Covers

    Java provides several methods for controlling, coordinating, inspecting and configuring threads. The methods covered here are:

    sleep()      join()       yield()     interrupt()   isInterrupted()
interrupted()  isAlive()  currentThread()  setName()  getName()
setPriority()  setDaemon()

    Each method affects a thread differently, so it is important to understand five axes for every one of them:

    1. Which thread is affected.
    2. Whether the thread blocks.
    3. Whether a lock is released.
    4. Which thread state is entered.
    5. Whether the behaviour is guaranteed or only suggested.

    Memory aid Group the methods by role: pause (sleep), wait for another (join), suggest (yield), request (interrupt), inspect (isInterrupted, interrupted, isAlive, currentThread), and configure (setName, getPriority, setDaemon). The role tells you the guarantee.

    2. Thread.sleep() — Pausing the Current Thread

    Thread.sleep() pauses the currently executing thread for a specified duration. The basic call is Thread.sleep(milliseconds);.

    // Demo.java — sleep pauses the currently executing thread
public class Demo {
    public static void main(String[] args) {
        System.out.println("Start");
        try {
            Thread.sleep(2000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        System.out.println("End");
    }
}

    The main thread pauses for approximately two seconds before printing End.

    3. The sleep() Trap — Which Thread Actually Sleeps?

    sleep() is a static method of the Thread class. The thread that executes the statement is the thread that sleeps, and no other. In a lambda body such as Thread t1 = new Thread(() -> { Thread.sleep(2000); });, t1 sleeps because t1 executes the method call.

    But consider calling it through a reference:

    t1.sleep(2000);   // compiles, but still pauses the CURRENT thread, not t1

    Although this compiles, it still pauses the current thread, not necessarily t1. Therefore always write it as the static call it is: Thread.sleep(2000);. Calling sleep() through a thread reference does not make that referenced thread sleep.

    Golden rule sleep() ignores the receiver. It always sleeps the thread that is running the line of code, so prefer the static form Thread.sleep(ms) and never believe t1.sleep() naps on t1.

    4. sleep(), State, Locks and Interruption

    State during sleep. While sleeping, the thread enters TIMED_WAITING. Conceptually: executing → TIMED_WAITING → eligible to run again. After the duration ends, the thread becomes runnable, but it does not necessarily resume immediately because the scheduler must select it.

    Does sleep() release a lock? No. If a thread calls sleep() while holding a monitor, it continues holding that monitor. Inside synchronized (lock) { Thread.sleep(2000); }, the current thread is sleeping and still owns the lock for those two seconds, so other threads that require the same monitor remain blocked. This is the important difference between Thread.sleep() and wait(): wait() releases the monitor on which it is called, while sleep() does not.

    InterruptedException. sleep() throws InterruptedException. If another thread interrupts a sleeping thread (thread.interrupt();), the sleeping thread wakes early and sleep() throws InterruptedException. When the exception is thrown, the interrupted status is cleared; if the method cannot fully handle the interruption, it commonly restores the status with Thread.currentThread().interrupt();.

    Important points about sleep():

    1. It pauses the currently executing thread.
    2. It normally places the thread in TIMED_WAITING.
    3. It does not release monitors held by the thread.
    4. It does not guarantee an exact wake-up time.
    5. It may return later than requested because of scheduling.
    6. It throws InterruptedException if the sleeping thread is interrupted.

    Important sleep() is a request to the OS/JVM, not a promise. The thread returns no earlier than the requested time and possibly later, never earlier.

    5. Thread.join() — Waiting for Another Thread to Finish

    join() makes the current thread wait for another thread to finish. In targetThread.join();, the calling thread waits and the target thread continues running.

    // Demo2.java — join makes the calling thread wait for the target
public class Demo2 {
    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            try {
                Thread.sleep(2000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            System.out.println("t1 finished");
        });
        t1.start();
        t1.join();
        System.out.println("Main finished");
    }
}

    Output:

    t1 finished
Main finished

    The main thread waits at t1.join(); until t1 terminates.

    Which thread waits? Given t1.join();, the current thread waits until t1 terminates. If the main thread executes that statement, the main thread waits and t1 keeps running. A common misunderstanding is that join() pauses the thread on which it is called. It does not; it pauses the thread that calls join().

    State during join(). For an untimed t1.join(); the calling thread generally enters WAITING. Conceptually: main thread waits → t1 finishes → main thread becomes runnable again. The target thread eventually enters TERMINATED.

    Timed join. Java provides t1.join(2000);, meaning: wait until t1 finishes, but for no longer than approximately two seconds. The calling thread enters TIMED_WAITING. It may continue because the target finished, the timeout expired, or the calling thread was interrupted. A timed join does not terminate the target thread when the timeout expires.

    Important points about join():

    1. The calling thread waits.
    2. The target thread continues running.
    3. Untimed join() normally places the caller in WAITING.
    4. Timed join() normally places the caller in TIMED_WAITING.
    5. join() throws InterruptedException.
    6. A timed join does not stop the target thread.
    7. join() creates a happens-before relationship: actions in the completed thread become visible to the thread that successfully returns from join().

    Interviewer's perspective The happens-before point is the subtle one. Once t1.join() returns, every write t1 made before terminating is guaranteed visible to the joining thread. That makes join() both an ordering tool and a memory-visibility tool, not merely a delay.

    6. Timed join() and Controlling Execution Order

    join() can enforce partial ordering. The sequence t1.start(); t1.join(); t2.start(); guarantees that t1 completes before t2 is started. However, excessive use of join() can remove concurrency by forcing threads to run sequentially. Use it where a genuine dependency exists, not as a default.

    Common misconception t1.join(2000) is often read as "cancel t1 after two seconds". It is not. It stops waiting after roughly two seconds; the target thread keeps running to completion in the background.

    7. Thread.yield() — A Scheduler Hint, Never a Guarantee

    yield() is a hint to the scheduler that the current thread is willing to give other runnable threads an opportunity to execute. The call is simply Thread.yield();.

    // Demo3.java — yield only suggests that the scheduler look elsewhere
public class Demo3 {
    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                System.out.println("T1: " + i);
                Thread.yield();
            }
        });
        Thread t2 = new Thread(() -> {
            for (int i = 0; i < 5; i++) {
                System.out.println("T2: " + i);
            }
        });
        t1.start();
        t2.start();
    }
}

    The exact output order is unpredictable.

    yield() is only a hint. The scheduler may run another thread, continue running the same thread, or ignore the hint completely. yield() does not guarantee a context switch and should never be used to enforce program correctness or thread ordering.

    State during yield(). yield() does not place the thread in WAITING or TIMED_WAITING. The thread remains runnable and eligible for execution. Conceptually: running thread → gives the scheduler another scheduling opportunity → may continue or may be replaced.

    When is yield() used? It is rarely needed in production application code. It may be useful for learning thread scheduling, experiments, testing unusual scheduling behaviour, and very specialized low-level code. It should not be used as a replacement for locks, synchronization, wait()/notifyAll(), join(), executors, or coordination utilities.

    8. Thread.interrupt() — Cooperative Cancellation

    interrupt() requests that a thread stop or change what it is currently doing. The call is thread.interrupt();. It does not forcibly kill the target thread. Interruption is a cooperative cancellation mechanism: one thread requests interruption → the target thread detects the request → the target thread decides how to respond.

    Interrupting a running thread. Consider a thread whose body is while (true) { System.out.println("Running..."); }. Calling t.interrupt(); does not automatically terminate the loop; the thread may continue running forever because its code never checks the interrupted status.

    Interrupted status. Each thread has an interrupted status: not interrupted → false, interrupted → true. When another thread calls t.interrupt(); and t is actively running, its interrupted status is normally set to true. The target thread must inspect that status.

    Cooperative cancellation pattern. The worker checks the flag on every iteration:

    // Demo4.java — interruption is cooperative: the task checks the flag
public class Demo4 {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                System.out.println("Working...");
            }
            System.out.println("Stopped gracefully");
        });
        worker.start();
        Thread.sleep(10);
        worker.interrupt();
    }
}

    The worker notices the interrupt request and exits its loop cleanly.

    Important interrupt() sets a flag; it does not pull the plug. If the target never checks isInterrupted() and never calls an interruptible blocking method, the interrupt has no visible effect.

    9. Interrupting sleep(), wait() and join()

    If a thread is blocked in an interruptible method such as Thread.sleep(), Object.wait() or Thread.join(), and another thread interrupts it (thread.interrupt();), the blocking method throws InterruptedException. A worker that calls Thread.sleep(10_000) and is interrupted needs no wait at all; it wakes at once, catches the exception, prints a message such as "Sleep interrupted", and restores the flag with Thread.currentThread().interrupt();.

    Interrupt status after InterruptedException. When sleep(), wait() or join() throws InterruptedException, the interrupted status is cleared. Therefore a catch block that prints Thread.currentThread().isInterrupted() normally prints false. If higher-level code must know that interruption occurred, restore the status:

    catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}

    10. Handling InterruptedException Correctly

    There are three correct responses, and one common mistake.

    1. Propagate the exception. Declare void performTask() throws InterruptedException { Thread.sleep(1000); } and let callers decide.
    2. Restore the interrupt status and stop. In the catch block call Thread.currentThread().interrupt(); then return;.
    3. Perform cleanup and stop. Catch the exception, run cleanup();, then Thread.currentThread().interrupt();.

    Silently ignoring interruption is usually a mistake: an empty catch (InterruptedException e) { } swallows the request so callers can no longer see it.

    Golden rule Never swallow InterruptedException. Either rethrow it, or restore the flag with Thread.currentThread().interrupt() before returning. Swallowing it destroys the only signal the rest of the call chain has.

    11. isInterrupted() vs Thread.interrupted()

    Both methods inspect interrupted status, but they behave differently.

    isInterrupted() is an instance method, thread.isInterrupted();. It checks the interrupted status of a particular thread, returns true or false, and does not clear the status. For example, boolean interrupted = worker.isInterrupted();.

    Thread.interrupted() is a static method, Thread.interrupted();. It checks the interrupted status of the current thread and clears that status after reading it. Thus boolean first = Thread.interrupted(); boolean second = Thread.interrupted(); yields first → true and second → false if the status was initially true; the first call cleared it.

    Method Checks which thread? Clears status?
    thread.isInterrupted() The referenced thread No
    Thread.interrupted() The current thread Yes

    Memory aid Thread.interrupted() has no receiver, so it can only mean "me" — and it clears the flag as it reads. isInterrupted() names a target, so it changes nothing; it is a pure peek.

    12. Why Java Uses Cooperative Cancellation

    Forcibly stopping a thread can leave shared state inconsistent. The thread may be terminated while holding a lock, updating a collection, modifying several related fields, transferring money, or writing a file.

    Cooperative interruption allows the thread to release resources, restore invariants, finish or abandon work safely, and exit at a controlled point. Deprecated methods such as Thread.stop() should not be used.

    Interruption is used for cancelling long-running tasks, stopping worker threads, shutting down thread pools, ending blocking operations, responding to application shutdown, and cancelling futures and executor tasks.

    13. isAlive() — Has the Thread Started and Not Terminated?

    isAlive() checks whether a thread has been started and has not yet terminated. The call is thread.isAlive();. The three moments to remember:

    before start()                        -> false
after start(), before termination     -> true
after the thread terminates           -> false

    isAlive() does not tell whether the thread is currently using the CPU. A thread may be sleeping, waiting, blocked, or runnable and still be alive.

    Important isAlive() answers one question only: "started and not yet finished?" Do not read it as "running on a processor right now" — the JVM exposes no such public query.

    14. Thread.currentThread() — The Executing Thread

    Thread.currentThread() returns a reference to the thread currently executing the code. Thread current = Thread.currentThread(); System.out.println(current.getName()); usually prints main.

    Inside a task, the code may not have direct access to the original thread variable, so the running task calls Thread.currentThread() to obtain its own Thread object. Common uses include logging, debugging, reading the current thread name, checking interrupted status, restoring interrupted status, inspecting thread priority, and identifying which worker executed a task.

    15. Thread Naming — setName() and getName()

    A thread name can be assigned using setName(): create the worker, call worker.setName("Worker-1"), then worker.start(). A cleaner approach is to pass the name to the constructor, new Thread(task, "Worker-1"), so the name is set before the thread ever runs. Read a name with thread.getName();, or inside the running task with Thread.currentThread().getName();.

    Meaningful thread names improve log readability, debugging, stack-trace analysis, thread-dump analysis, production monitoring, and identification of worker responsibilities. Compare Thread-7 failed with payment-worker-3 failed; the second message provides far more context.

    Memory aid A thread name is not decoration; it is the cheapest diagnostic you will ever add. Name threads like functions: after what they do, not when they were created.

    16. Thread Priority — setPriority()

    Thread priority is a scheduling hint that indicates the relative importance of a thread. Java defines priorities from 1 to 10:

    Thread.MIN_PRIORITY    // 1
Thread.NORM_PRIORITY   // 5
Thread.MAX_PRIORITY    // 10

    The default priority is normally Thread.NORM_PRIORITY, and a new thread generally inherits the priority of the thread that creates it. Calling worker.setPriority(Thread.MAX_PRIORITY); offers the scheduler a hint.

    Priority does not guarantee execution order. The operating system and JVM ultimately influence scheduling. Different platforms may respect priorities differently, map several Java priorities to the same native priority, partially ignore priority differences, and produce different execution orders. Therefore: higher priority ≠ guaranteed first execution, and higher priority ≠ guaranteed more CPU time. Never use thread priority to guarantee program correctness.

    Priority is rarely needed in normal application code. Possible specialized uses include low-level performance tuning, background maintenance work, platform-specific systems, and carefully measured real-time-like workloads. In most applications, use executors, queue policies, separate thread pools, task prioritization and proper concurrency utilities, which provide more predictable control than raw thread priorities.

    17. Daemon Threads — setDaemon()

    A daemon thread is a background-support thread that does not keep the JVM alive by itself. The call is thread.setDaemon(true);.

    A normal thread is a non-daemon (user) thread; the JVM remains alive while a user thread is running. Examples of user-thread work are main application logic, business operations, request processing, and important file or database work. A daemon thread performs background-support work such as runtime maintenance, monitoring helpers, cache cleanup and background housekeeping; the JVM does not remain alive solely for daemon threads.

    // Demo5.java — a daemon thread cannot keep the JVM alive
public class Demo5 {
    public static void main(String[] args) {
        Thread daemon = new Thread(() -> {
            while (true) {
                System.out.println("Daemon running...");
            }
        });
        daemon.setDaemon(true);
        daemon.start();
        System.out.println("Main finished");
    }
}

    Once the main thread finishes, the JVM may exit because only the daemon thread remains. The daemon thread is not allowed to keep the process alive.

    The daemon rule. A thread must be marked as daemon before it is started:

    Thread worker = new Thread(task);
worker.setDaemon(true);   // correct: before start
worker.start();

worker.start();
worker.setDaemon(true);   // incorrect: throws IllegalThreadStateException

    Daemon threads can stop abruptly. When the JVM exits because only daemon threads remain, daemon threads may be terminated without completing their work. They are not guaranteed to execute remaining statements, cleanup code, finally blocks, file flushes, database commits, or network operations. Therefore daemon threads should not perform work that must complete reliably: saving critical data, completing financial transactions, writing essential files, sending guaranteed messages, or releasing important external resources.

    JVM exit rule. The JVM continues running while at least one live non-daemon thread exists. When the last non-daemon thread finishes, only daemon threads remain and the JVM may terminate. The main thread itself is normally a non-daemon thread.

    Important Daemon status is a lifecycle contract, not an optimization. If losing the work at JVM shutdown would be unacceptable, the thread must be a non-daemon thread.

    20. Important Rules

    1. Thread.sleep() always pauses the currently executing thread.
    2. sleep() does not release a monitor held by the sleeping thread.
    3. join() pauses the calling thread, not the target thread.
    4. yield() is only a scheduling hint and may be ignored.
    5. interrupt() does not forcibly terminate a thread.
    6. Interruption requires cooperation from the target task.
    7. Interrupting sleep(), wait() or join() causes InterruptedException.
    8. InterruptedException clears the interrupted status.
    9. Restore the status when interruption cannot be fully handled.
    10. isInterrupted() does not clear the status.
    11. Thread.interrupted() checks and clears the current thread's status.
    12. isAlive() is true after start() and before termination.
    13. Thread names are important for logs and debugging.
    14. Thread priority does not guarantee execution order.
    15. Set daemon status before calling start().
    16. Daemon threads should not be used for work that must finish reliably.
    17. The JVM can exit when only daemon threads remain.

    21. Myth vs Reality

    Myth Reality
    "t1.sleep(2000) makes t1 sleep." sleep() is static and pauses the currently executing thread; the receiver is ignored.
    "join() pauses the target thread." join() pauses the calling thread until the target terminates; the target keeps running.
    "yield() guarantees another thread runs." yield() is only a hint; the scheduler may ignore it completely.
    "interrupt() forcibly stops a thread." It sets a request; the target must check the flag or hit an interruptible blocking call.
    "Higher priority always runs first." Priority (1-10) is a hint the OS may map or ignore; order is never guaranteed.

    22. Common Trap Questions

    Trap 1 — Static sneak: "I wrote t1.sleep(2000), so t1 sleeps, right?" No. sleep() is static; it pauses the thread that executes the statement, which is the caller, not necessarily t1.

    Trap 2 — Lock release: "Does sleep() release the monitor so other threads can enter?" No. sleep() holds every monitor it owns; wait() is the method that releases the monitor.

    Trap 3 — join target: "t1.join() pauses t1 until the caller is ready." Backwards. join() pauses the caller until t1 terminates; t1 is unaffected and keeps running.

    Trap 4 — Timed join: "t1.join(2000) cancels t1 after two seconds." No. It stops waiting after roughly two seconds; the target thread continues running.

    Trap 5 — Interrupt a busy loop: "interrupt() will break a while (true) loop." Only if that loop checks isInterrupted() or calls an interruptible method. Otherwise the flag is set but never observed and the loop runs forever.

    Trap 6 — Wrong inspector: "Thread.interrupted() reports whether another thread was interrupted." No. It inspects and clears the current thread's status. To inspect another thread, use thread.isInterrupted(), which does not clear.

    Trap 7 — Daemon timing: "I can mark a running thread as a daemon." No. setDaemon() must be called before start(); calling it later throws IllegalThreadStateException.

    Trap 8 — Alive means on CPU: "isAlive() returning true means the thread is currently running on the CPU." No. A sleeping, waiting, blocked or runnable thread is all alive; isAlive() only means started and not yet terminated.

    23. Points to Remember

    1. sleep() is static and always pauses the currently executing thread, regardless of the reference used.
    2. sleep() places the thread in TIMED_WAITING and does not release a monitor; wait() does release it.
    3. join() pauses the calling thread, not the target; untimed join enters WAITING, timed join enters TIMED_WAITING.
    4. A timed join does not terminate the target thread, and join() establishes a happens-before relationship.
    5. yield() is only a hint and never places the thread in WAITING or TIMED_WAITING.
    6. interrupt() requests cooperative cancellation; it never forcibly kills a thread.
    7. Interrupting sleep(), wait() or join() throws InterruptedException and clears the interrupted status.
    8. isInterrupted() reads without clearing; Thread.interrupted() reads and clears the current thread's status.
    9. Restore the interrupt flag with Thread.currentThread().interrupt() when interruption cannot be fully handled.
    10. isAlive() is true after start() and before termination; it does not mean "currently on the CPU".
    11. currentThread() supplies the executing thread's object, which is why it powers getName() and interrupt status checks.
    12. Priority is a 1-10 hint (default 5) and never guarantees order; names greatly aid logs and thread dumps.
    13. Set daemon before start(); the JVM exits when only daemon threads remain, and daemon work may be abandoned.
    14. These methods are low-level; production lifecycle management usually moves to executors, futures and concurrent collections.

    24. Likely Interview Questions

    Question Crisp Answer
    Which thread does sleep() pause? The currently executing thread. sleep() is static, so a reference like t1.sleep() still pauses the caller.
    Does sleep() release a lock? No. The sleeping thread keeps its monitors. wait() releases the monitor; sleep() does not.
    What state does sleep() enter? TIMED_WAITING, returning to runnable after the duration (possibly later, never earlier).
    Which thread does join() pause? The calling thread. The target thread continues running until it terminates.
    Untimed vs timed join() state? Untimed join() puts the caller in WAITING; join(ms) puts it in TIMED_WAITING.
    Does timed join() stop the target? No. It only bounds how long the caller waits.
    What does yield() do? Offers a scheduling hint. It may be ignored and never guarantees a context switch.
    Does yield() change state? No. The thread stays RUNNABLE; it never enters WAITING or TIMED_WAITING.
    Does interrupt() stop a thread? No. It sets the interrupted flag and relies on the target to cooperate.
    isInterrupted() vs Thread.interrupted()? The former inspects a referenced thread and does not clear; the latter inspects and clears the current thread's status.
    What happens when you interrupt sleep()/wait()/join()? The blocking call throws InterruptedException, and the interrupted status is cleared.
    What does isAlive() mean? Started and not yet terminated. It does not mean currently executing on the CPU.
    Does priority guarantee execution order? No. Priorities are 1-10 hints; the OS/JVM may map or ignore them.
    When can setDaemon() be called? Only before start(); afterwards it throws IllegalThreadStateException.
    When does the JVM exit? When no live non-daemon threads remain; daemon threads do not keep it alive and may be stopped abruptly.

    25. Final Summary

    sleep()              → pause the current thread for a duration
join()               → make the current thread wait for another thread
yield()              → suggest that the scheduler consider another runnable thread
interrupt()          → request cooperative cancellation
isInterrupted()      → inspect status without clearing it
Thread.interrupted() → inspect and clear the current thread's status
isAlive()            → check whether a thread has started and not terminated
currentThread()      → obtain the currently executing thread
setName()/getName()  → assign and read a meaningful thread name
setPriority()        → provide a non-guaranteed scheduling hint (1-10)
setDaemon()          → mark a thread as background support work (before start)
    • Pause → sleep() sends the current thread to TIMED_WAITING and holds its locks.
    • Wait → join() parks the caller (WAITING) or bounded-waits (TIMED_WAITING) for the target.
    • Hint → yield() and priority only suggest; neither guarantees scheduling or order.
    • Cancel → interrupt() is cooperative; sleep/wait/join react with InterruptedException.
    • Inspect → isInterrupted, interrupted, isAlive, currentThread observe without necessarily changing state.
    • Configure → names aid diagnostics; daemon threads must be set before start() and cannot keep the JVM alive.

    Golden rule Every one of these methods is a low-level control lever, not a correctness guarantee. Guarantee ordering with coordination and visibility, request cancellation cooperatively, and reach for executors and concurrency utilities in production code.

    One-line takeaway: sleep pauses the current thread without releasing locks, join waits for another thread, yield and priority only hint, interrupt requests cooperative cancellation, and isAlive, currentThread, naming and daemon status let you inspect and configure threads without ever assuming the scheduler obeys.
