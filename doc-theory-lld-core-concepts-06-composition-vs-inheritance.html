    Composition vs Inheritance

    10 sections · 658 words

    Comparison · LLD Core Concepts · Concept 06 of 09

    The Idea

    Favor composition.

    You'll See This

    • A subclass overriding a method just to throw or do nothing.
    • A subclass tree exploding for every combination (Flying+Swimming, Flying-only...).
    • "Is-a" doesn't hold: resizing one dimension breaks another's invariant.

    Has-a, not is-a.

    Before

    class Bird {
    void fly() { .. }
}
class Penguin extends Bird {
    void fly() {
        throw new UnsupportedOperationException();
    }
    // LSP breaks
}
// Penguin "is-a" Bird, but can't do what a Bird does

    Is-a breaks.

    After

    interface Flyer { void fly(); }
class Sparrow implements Flyer {
    public void fly() { .. }
}
class Penguin {
    // no Flyer at all
    Swimmer swim = new Swimmer();
    // has-a swim behaviour
    void swim() { swim.doSwim(); }
}
// Penguin never claims to fly. nothing to override.

    Inheritance Is Still Fine When

    • A genuine, stable is-a relationship shares real implementation.
    • You want polymorphism through a real type hierarchy, not just code reuse.

    Quick Check

    Ask "is-a" or "has-a." A Car has-an Engine. A Car is-a Vehicle, only if every Vehicle method truly applies.

    How It's Built

    The Shape

    «INTERFACE»
Flyer
    + fly()

Penguin
    has-a (composition)
        Swimmer

Sparrow
    is-a (implements)
        Flyer

PENGUIN HOLDS A SWIMMER. SPARROW IMPLEMENTS FLYER.
NEITHER EXTENDS BIRD.

    The Move (3 Steps)

    1. Ask is-a or has-a. Pick composition by default; inheritance only when is-a never breaks.
    2. A subclass that overrides to throw or no-op is the LSP alarm saying it should never have been a subclass.
    3. Prefer implementing a small interface over extending a shared base: you can hold many, but extend only one.

    In The Interview

    "Penguin extending Bird forced it to override fly() with an exception, which breaks Liskov substitution. I gave flying birds a Flyer interface and let Penguin hold a Swimmer instead. Penguin never claims to fly."

    How It's Different

    The Confusion Pairs

    Composition (OOP) vs composition (UML). As a principle, composition loosely means "holds a reference to." In UML diagram notation, Composition is the strict version: the part cannot outlive the whole.

    Composition vs Strategy. Strategy is composition, formalized: the has-a object is swapped in through a constructor specifically to vary one behaviour.

    Composition vs inheritance for reuse. Inheritance reuses through a fixed parent. Composition reuses by holding whatever object you choose, swappable at runtime.

    Single inheritance vs many interfaces. Most languages allow extending one class but implementing many interfaces. Composition sidesteps the one-parent limit entirely.

    They Say: "add a bird that both flies and swims"

    • With it: implement Flyer and hold a Swimmer, no new subclass tangle.
    • Without: you're stuck deciding which base class it "is," or a subclass for every combination.

    Watch Out For

    • Overriding a method to throw or no-op is the single loudest inheritance-gone-wrong signal.
    • Deep chains (4-5 levels) make it hard to know which ancestor a behaviour actually comes from.
    • Composition needs a forwarding call written by hand; inheritance gives you the method free: that convenience is why it gets overused.
    • "Is-a" can read true in English and still be false in behaviour (a Square "is-a" Rectangle in geometry, not in code with independent width/height).
    • This isn't "never inherit." A genuinely closed, stable hierarchy (Shape to Circle/Rectangle for one shared method) is legitimate.
