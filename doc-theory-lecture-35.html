    Lecture 35 — Spring Security (Authentication, Authorization & SecurityContext)

    17 sections · 6,563 words

    Lecture 35

    Scope evidence: "Spring Security | Authentication, Authorization & SecurityContext" (playlist map, verified). The repo folder contains the springSecurityDemo project (SpringSecurityDemoApplication, controller.StudentController) secured only by the Security starter plus application.properties, and this lecture's notes. Coverage below = what application security means, assets/threats/trust boundaries, authentication vs authorization, the identity model, authentication state, mechanism vs session policy, Spring Boot auto-configuration, the default user and generated password, the CSRF 403 surprise, SecurityContext/SecurityContextHolder, and a first SecurityFilterChain customization. Deeper flows belong to Lectures 36-37.

    Security is the part of a backend that decides whether a request may do anything at all. This lecture builds the model behind Spring Security: what we protect, how a request proves an identity, how that identity is authorized, where it is stored during a request, and why one dependency puts a login page and a random password in front of every endpoint. The default behavior - including the surprising 403 on a POST - stops being magic and becomes explainable.

    1. What Application Security Means

    Application security means protecting the application's valuable resources and operations from unauthorized access, modification, destruction, disclosure, or misuse. It is not limited to protecting data: an application may need to protect information, business operations, user identities, system availability, financial transactions, administrative capabilities, secrets and credentials, and application reputation.

    Consider a banking application. Its assets are not only rows in a table: account balance, transaction history, the transfer-money operation, customer identity, bank availability, and administrative access. An attacker may not need to steal information - making the bank unavailable through excessive requests is also a security problem.

    Security is not one feature. Security is a collection of controls:

    Control What it guards Why it is separate
    Authentication Who the actor is Identity must be established first
    Authorization What the actor may do Identity does not imply permission
    Input validation Data entering the system Blocks malformed or hostile input
    Session protection The authenticated session Stops theft and fixation
    Password protection Stored credentials Keeps credentials from leaking
    CSRF protection State-changing browser requests Stops forged authenticated requests
    CORS policies Which origins may call the API Controls cross-origin access
    Secure communication Data in transit Protects credentials and tokens on the wire
    Rate limiting Request volume Protects availability
    Audit logging What happened Enables detection and accountability
    Error handling Failure information Avoids leaking internal details
    Secret management Keys and secrets Keeps signing keys safe

    Spring Security primarily helps with authentication, authorization, security-context management, session security, protection against several common web attacks, and integration with security protocols.

    Important: Spring Security does not magically make all application code secure. It will not automatically fix SQL injection from unsafe queries, insecure file uploads, weak business rules, secrets committed to Git, vulnerable dependencies, incorrect database permissions, or sensitive information written into logs.

    Therefore: security is not something added only to the login page. It must exist wherever an untrusted actor can affect a valuable resource.

    2. Assets, Threats, and Trust Boundaries

    Before deciding how to secure an application, understand three concepts.

    Assets. An asset is anything valuable that should be protected: data assets (passwords, email addresses, phone numbers, health records, payment information, source code, API keys, business documents); operational assets (creating an order, transferring money, approving a refund, changing another user's password, deleting an account, publishing content); infrastructure assets (database, server, cloud account, message broker, file storage, deployment pipeline); and security assets (session IDs, JWT signing keys, encryption keys, OAuth client secrets, password-reset tokens, CSRF tokens).

    Availability as an asset. Even when an attacker cannot access data, they might prevent legitimate users from reaching the application: thousands of expensive requests, repeated login attempts, resource exhaustion, database connection exhaustion. Availability itself is an asset.

    Threats. A threat is something that could harm an asset: an attacker stealing credentials, a malicious employee reading restricted data, a bot repeatedly guessing passwords, a user changing another user's order, a script flooding an endpoint, or a browser sending an unwanted authenticated request. A threat is not the same thing as a vulnerability; a vulnerability is a weakness that makes an attack possible.

    Threat:          An attacker wants to access an administrator account.
Vulnerability:   The application allows unlimited password attempts.
Attack:          The attacker runs an automated password-guessing tool.
Impact:          The administrator account is compromised.

Threat + Vulnerability -> Possible Attack

    Trust boundaries. A trust boundary is a point where information moves from one trust level to another:

    Browser -> Internet -> Spring Boot application -> Database

    Every transition is a possible trust boundary: Browser -> Server, Server -> Database, Service A -> Service B, Mobile application -> API gateway, Public network -> Internal network, External identity provider -> Application.

    Why is the browser untrusted? A common beginner assumption is: "The frontend only shows the delete button to admins, so normal users cannot delete anything." But users control their browsers. They can change JavaScript, modify HTML, use Postman, use curl, manually call hidden endpoints, manipulate request parameters, and replay old requests. Suppose the frontend contains if (user.role === "ADMIN") { showDeleteButton(); } - this improves the interface but does not provide security, because a non-admin can still send DELETE /api/users/57. Therefore, authorization must be enforced on the server.

    Trust-boundary rule. Whenever data crosses a trust boundary, ask: Who produced this data? Can it be modified? Should it be authenticated? Should it be authorized? Should it be validated? Should it be encrypted?

    3. Security Foundations: The Questions Before an Operation

    Suppose we have an endpoint: DELETE /api/users/57. From a normal Spring MVC perspective, we think Request -> Controller -> Service -> Repository -> Database.

    From a security perspective, several questions must be answered before the business operation is allowed:

    • Who is sending this request?
    • Has that identity been verified?
    • Is that identity allowed to delete users?
    • Is that identity allowed to delete this particular user?
    • Has the request been manipulated?
    • Was the request genuinely created by the user?
    • Could an attacker repeat or forge this request?

    Authentication usually comes before authorization. A typical flow is:

    Request -> Extract credentials -> Authenticate identity -> Determine authorities
        -> Evaluate authorization rule -> Allow or deny

    Interviewer's perspective: The two famous questions are "who are you?" (authentication) and "what are you allowed to do?" (authorization). Every other control here - sessions, tokens, CSRF, context - exists to answer those two questions reliably on every request.

    Mnemonic for the pre-operation questions: W-I-A-W-R (Who sends it, Is the identity verified, is the identity Allowed, is this operation allowed, was the Request manipulated).

    4. Authentication: Verifying an Identity Claim

    Authentication answers: Who are you, and what evidence proves that claim? If someone enters a company office and says, "I am Aditya," that is only an identity claim. The security guard may ask for an employee card:

    Claimed identity:  Aditya
Evidence:          Employee card
Verification:      Card is checked
Result:            Identity accepted or rejected

    That process is authentication - the process of verifying an identity claim.

    Username and password example. Claim: "My username is aditya." Credential: "My password is secret123." Verification: compare the supplied password with the stored encoded password. Result: authentication succeeds or fails. The username usually identifies the account; the password provides evidence that the requester is entitled to use that account.

    Authentication factors commonly fall into three categories:

    Category Meaning Examples
    Something you know Knowledge held by the user Password, PIN, security answer
    Something you have An object the user possesses Smart card, authenticator application, private key
    Something you are A physical trait Fingerprint, face, iris

    Multi-Factor Authentication (MFA). Using two credentials from the same category is not necessarily strong multifactor authentication. Password + authenticator application OTP uses knowledge and possession.

    Important: In Spring Security, the authenticated representation is usually stored in an Authentication object. Authentication is a process that produces an object; the object is then carried through the rest of the request.

    5. Authentication Failures vs Security Attacks

    An authentication failure and a security attack are not necessarily the same thing.

    Authentication failure means the presented evidence could not establish an acceptable identity: wrong password, unknown username, expired token, invalid token signature, malformed Authorization header, disabled account, expired account, expired session, incorrect OTP.

    Security attack involves intentional attempts to defeat, misuse, bypass, or exploit security controls.

    • Brute-force attack: an attacker tries many passwords for one account (aditya / password1, password2, password3, ...). Each individual request produces an authentication failure; the pattern across thousands of requests reveals an attack.
    • Credential stuffing: an attacker uses username-password combinations stolen from another website (user@example.com / reusedPassword123). The password may even be correct, so authentication could succeed even though the request is malicious.

    Golden rule: Successful authentication does not prove that the human behind the request is legitimate. It proves only that acceptable credentials were presented.

    Additional controls may be needed: MFA, anomaly detection, login notifications, device verification, rate limiting, credential-breach detection.

    Do not reveal unnecessary failure details. If the application responds "Username exists, but password is incorrect," an attacker now knows the account exists. A safer external response is often Invalid username or password. Internally, the application may log more precise information (password mismatch, account disabled, token expired, user not found). The external message and internal diagnostic information need not be identical.

    6. Authorization: What an Identity May Do

    Authorization answers: What is this identity allowed to do? Authentication establishes identity; authorization evaluates access. Suppose the guard has verified that a person is Aditya - that does not mean Aditya can enter every room:

    Authentication:  You are Aditya.
Authorization:   Aditya may enter the training room,
                 but may not enter the finance department.

    Authorization as a decision usually needs four pieces of information:

    Piece Question Examples
    Subject Who is acting? User 51, Administrator, Manager, Service account, Anonymous visitor
    Action What are they doing? Read, Create, Update, Delete, Approve, Transfer, Download
    Resource What are they accessing? Order 101, Employee record 57, Bank account 9001, Admin dashboard
    Context Under what conditions? Owner? Business hours? Account active? Below limit? MFA done?

    Therefore, authorization can be thought of as: can subject S perform action A on resource R under context C? Example: can employee 27 update leave request 91 when employee 27 owns leave request 91?

    Public access is also an authorization decision. For GET /api/courses/public, the application may allow everyone access; that is still a policy: "Permit all requests."

    Aspect Authentication Authorization
    Question Who are you? What may you do?
    Purpose Verify an identity claim Evaluate access for that identity
    Inputs Credentials (password, token, certificate) Subject, action, resource, context
    When Usually first Usually after authentication succeeds
    Result Identity accepted or rejected Access allowed or denied
    Example Password matches the stored hash Aditya may read the course, not delete the user

    7. The Spring Security Identity Model

    Spring Security's identity model uses a specific vocabulary. The concepts are related but not interchangeable.

    Identity means the entity whose actions the system wants to recognize: a human user, an administrator, a customer, another application, a microservice, a scheduled job, or an IoT device. It is broader than a database row; an account is a stored application record that represents and manages an identity.

    users table
------------------------------------------------
id | username | password_hash | enabled
42 | aditya   | ...           | true

    A person may have multiple accounts, an employee identity, a customer identity, and an administrator identity.

    Credentials are evidence used to prove an identity claim: password, OTP, private key, certificate, API key, bearer token.

    Principal is the identity currently represented inside the security system.

    Authorities represent a capability or high-level security attribute granted to a principal: COURSE_READ, COURSE_WRITE, USER_DELETE, PAYMENT_REFUND, ROLE_ADMIN, SCOPE_orders.read. They are represented through GrantedAuthority objects stored inside the current Authentication. Spring describes authorities as high-level permissions such as roles and scopes.

    Granted versus claimed authority. An authority should be trusted only when assigned by a trusted authentication process. A client should not be able to send:

    {
  "username": "aditya",
  "role": "ADMIN"
}

    and become an administrator merely because it claimed that role. The role or authority must be loaded from a trusted database, derived from a verified token, supplied by a trusted identity provider, or assigned by a trusted AuthenticationProvider. The Authentication API treats its authorities as values granted by the AuthenticationManager, not arbitrary client claims.

    Roles are a named grouping of responsibilities or access privileges (USER, INSTRUCTOR, MANAGER, ADMIN, SUPER_ADMIN) and are usually broader than an individual permission:

    ROLE_INSTRUCTOR
  +-- COURSE_READ
  +-- COURSE_CREATE
  +-- COURSE_UPDATE
  +-- STUDENT_PROGRESS_READ
    Term One-line meaning
    Identity The conceptual subject the system recognizes
    Account A stored record representing an identity
    Credentials Evidence proving an identity claim
    Principal The identity currently inside the security system
    Authority A capability granted to a principal (GrantedAuthority)
    Role A named grouping of privileges, usually broader than one permission
    Permission A specific allowed operation

    Important: A role name is USER; the granted authority is ROLE_USER. The ROLE_ prefix is what the default role-based checks expect, so the two strings are not interchangeable.

    8. Authentication, SecurityContext, and SecurityContextHolder

    Authentication is one of the most important Spring Security interfaces, and it has two different roles.

    Role 1 - authentication request. Before credentials are verified, an Authentication object can represent an attempt (for example UsernamePasswordAuthenticationToken): principal = "aditya", credentials = "raw-password", authorities = [], authenticated = false. Someone claims to be Aditya and has supplied this password; the claim is not yet accepted.

    Role 2 - authenticated principal. After successful verification, another Authentication object represents the accepted identity: principal = UserDetails("aditya"), credentials = null, authorities = [ROLE_USER, COURSE_READ], authenticated = true. Spring Security formally defines Authentication as both the token for an authentication request and the representation of an authenticated principal after processing.

    Important Authentication information. Conceptually it contains:

    • principal - the identity; before authentication it may be "aditya", afterward a UserDetails object.
    • credentials - the evidence (password, bearer token, certificate, API key); may be removed after successful authentication.
    • authorities - the capabilities granted to the principal, used later during authorization.
    • details - additional information such as remote address or session identifier.
    • isAuthenticated() - whether the token has been accepted; false before verification, true after trusted verification.

    Application code should not simply mark arbitrary client-created authentication objects as trusted; the authenticated result should normally come from the trusted authentication infrastructure.

    Authentication transformation:

    Unauthenticated Authentication            Authenticated Authentication
+---------------------------+             +---------------------------+
| principal   = "aditya"    |             | principal   = UserDetails |
| credentials = "raw-pass"  |  -------->  | credentials = null        |
| authorities = []          |  AuthManager| authorities = [ROLE_USER] |
| authenticated = false     |  verifies   | authenticated = true      |
+---------------------------+             +---------------------------+

    That authenticated object becomes the security identity used for the current request.

    SecurityContext. The SecurityContext is a container that holds the current Authentication:

    public interface SecurityContext {
    Authentication getAuthentication();
    void setAuthentication(Authentication authentication);
}

    Why a wrapper at all? Instead of passing the current user manually (courseService.createCourse(courseRequest, currentUser)) through every method, Spring Security establishes a request-associated security context that can be loaded at the start of a request, updated after authentication, stored for future requests, and cleared after request completion.

    SecurityContextHolder. It provides access to the current SecurityContext:

    SecurityContext context = SecurityContextHolder.getContext();
Authentication authentication = context.getAuthentication();

String username = authentication.getName();
Object principal = authentication.getPrincipal();
Collection<? extends GrantedAuthority> authorities = authentication.getAuthorities();

    Spring Security describes SecurityContextHolder as the central location where the framework stores details about the currently authenticated user.

    Why a holder is necessary. The authentication filter learns the user's identity, and later components still need it: the authorization component asks "who is the current user?", the controller asks "who submitted this request?", the audit service asks "which user performed this action?" The holder gives them access to the current security context without manually passing the user through every method.

    Default ThreadLocal strategy. In servlet applications, one request is commonly processed by one thread at a time, so Spring Security uses a ThreadLocal strategy by default. Each thread sees its own current context. The context is also cleared after request processing to prevent one request's identity from leaking into another request handled by a reused server thread.

    Why clearing matters. Application servers reuse threads. Without clearing, request 1 on thread 7 as ADMIN could leave the old context behind, and request 2 on the same thread 7 as anonymous might incorrectly inherit the administrator identity. Therefore:

    Request begins -> Load or create SecurityContext -> Process security and application logic
-> Thread returns to pool -> Clear SecurityContextHolder

    9. Authentication State, Tokens, and Session Policy

    By default HTTP requests are independent (POST /login, GET /profile, GET /orders, POST /logout). The server must decide how request 2 knows that the user authenticated during request 1. There are two broad models.

    Stateful authentication. The server retains authentication-related state between requests - commonly session-based:

    User logs in once -> Server verifies credentials -> Server stores authentication in session
-> Client receives session identifier -> Client sends it on later requests
-> Server retrieves stored authentication

    First request:

    POST /login
Content-Type: application/x-www-form-urlencoded

username=aditya&password=secret

    The application verifies the credentials and stores information representing the authenticated user in server-side session state:

    Session ID: ABC123
Session data:
  SecurityContext / Authentication
  principal = aditya
  authorities = [ROLE_USER]

    The response sends the identifier to the browser, commonly as a cookie (Set-Cookie: JSESSIONID=ABC123). A later request sends Cookie: JSESSIONID=ABC123; the server uses the identifier to retrieve the session and the Authentication for Aditya, so the user does not send the password again.

    Stateful does not mean all data is in the cookie. In ordinary server-side session authentication the cookie normally contains only a session identifier; the important authentication state is held server-side, and the cookie lets the server locate it. Session state may live in application memory, a distributed cache, a database, or an external session store such as Redis.

    Advantages: authenticate once without resending the password; immediate server-side invalidation (delete session ABC123 and further requests using it fail); the server controls session state (last access time, expiry, concurrent sessions, security context, extra attributes). Costs: each active session consumes server resources, and several servers need shared session storage, sticky sessions, or another consistent strategy.

    Cookie does not necessarily mean session. Cookies may store a session identifier, language preference, theme preference, analytics identifier, CSRF token, or authentication token; a token-based system can also place an access token inside a cookie.

    Session cookie as a bearer credential. If an attacker steals JSESSIONID=ABC123, the attacker may not know the password but the identifier may be enough to retrieve the authenticated session. Possession of the session cookie can grant access, so it must be protected like a credential: HTTPS, Secure cookie attribute, HttpOnly, SameSite policy, session expiration, session invalidation, and session ID rotation.

    Session fixation. An attacker somehow causes a victim to use a session identifier known to the attacker:

    Attacker knows session ID = XYZ -> Victim logs in using session XYZ
-> Session XYZ becomes authenticated -> Attacker reuses XYZ

    To reduce this risk, the application can change the session identifier on successful authentication (XYZ -> NEW-789). Spring Security includes session-fixation protection and can change the session ID after authentication.

    Stateless authentication. The server does not rely on a stored login session on later requests; each request carries the information needed for authentication (Authorization: Bearer TOKEN). For every request: extract credential -> validate credential -> create Authentication -> place it in SecurityContext -> authorize -> clear request context. The next request starts again.

    Stateless does not mean no data exists anywhere. The application may still store users, passwords, permissions, roles, business data, refresh tokens, revoked token records, audit logs, rate-limit counters, and signing keys. Stateless specifically means the server does not depend on a previously stored HTTP login session to reconstruct authentication for the next request.

    Aspect Stateful session Stateless token
    Where auth state lives Server-side session store In the credential carried by each request
    What the client sends Session ID cookie (JSESSIONID) Token (for example Bearer token)
    Server storage Per-session memory/resources No HTTP login session required
    Invalidation Immediate server-side invalidation Harder; needs revocation or short expiry
    Scaling across servers Needs shared store or sticky sessions Naturally fits multiple servers
    Typical shape Traditional web application REST/mobile API

    Authentication mechanism vs session policy. The mechanism answers how credentials are obtained and verified; the session policy answers whether, after success, the resulting SecurityContext is persisted in an HTTP session. Form login describes how username and password are submitted (POST /login, username=aditya&password=secret). The application may then create a session (authenticate, store the SecurityContext in the session, send a cookie - the traditional stateful app) or issue a token (authenticate, generate an access token, do not create a login session - stateless API). HTTP Basic is likewise a credential transport mechanism: it sends credentials through the Authorization header (Authorization: Basic YWRpdHlhOnNlY3JldA==) and the client usually presents it repeatedly.

    HTTP Basic = credential transport mechanism
STATELESS  = session persistence decision

    JWT is not automatically stateless. A JWT is a token format; statelessness depends on how it is used.

    Usage Stateless use Session-backed use
    JWT sent every request Yes No (validated once)
    JWT validated every request Yes No
    HTTP-session authentication used No Yes, afterward
    Later requests identified by The token Session cookie

    The session-backed design uses a JWT during authentication but becomes session-based afterward, so token format does not determine session policy. Conversely, a non-JWT opaque token can be processed every request without creating an HTTP session.

    Cookie does not automatically mean stateful. A stateless application may store a bearer token in a secure cookie (Cookie: access_token=eyJhbGciOi...): on every request read the token, validate it, create Authentication, with no server-side login session. This is still stateless regarding authentication persistence, although automatically submitted cookies introduce CSRF concerns that must be addressed separately.

    Tokens and bearer credentials. A token is a credential presented by the client:

    GET /api/profile
Authorization: Bearer eyJhbGciOi...

    The server extracts and validates it (check signature, expiry, issuer, audience, read subject, determine authorities) and may then create Authentication (principal = user 42, authorities = [SCOPE_profile.read], authenticated = true), used only for the current request unless explicitly persisted.

    • A self-contained token contains signed information the server validates locally; a JWT may carry claims such as sub, scope, iat, exp, and the server needs no HTTP session lookup.
    • An opaque token looks like a random identifier (a8f2b9137c45d...) and reveals nothing to the application; the application asks an authorization server or token store whether it is active, which user it represents, and what scopes it contains. Opaque-token authentication can still be stateless from the application's HTTP-session perspective, even though a token service maintains token state.

    Bearer token means whoever possesses the token may present it - possession is enough, like cash. The same applies to an ordinary session cookie: someone with a valid JSESSIONID may be able to act as the user. Bearer tokens must be protected from network interception, accidental sharing, browser storage attacks, logging, URL leakage, and source-code commits. A valid token is not safe merely because it is a JWT; security still depends on strong signing keys, correct signature verification, expiry, issuer and audience validation, secure transport, safe client storage, and appropriate scopes. JWT stands for JSON Web Token - a token format; access tokens are self-contained (often JWT) or opaque, and either is often used as a bearer token.

    Per-request flow:

    HTTP Request --Authorization: Bearer TOKEN--> Authentication filter --extracts--> Token validator
--validates--> Authenticated Authentication --> SecurityContext --> SecurityContextHolder
--> Authorization --> Controller --> SecurityContextHolder cleared

    On the next request, the token must be presented and processed again.

    Interviewer's perspective: The trap is to treat the token format as the answer. Statefulness is a decision about where authentication state lives between requests, not about whether the credential is a JWT, an opaque token, or a cookie.

    10. Spring Boot Security Auto-Configuration, Default User, and the CSRF 403

    Spring Boot's job is not to implement authentication itself. Spring Security provides the framework; Spring Boot observes what is available and creates a sensible initial configuration:

    Dependency added -> Spring Security classes found on classpath -> auto-configuration activates
-> Security beans created -> Security filter chain registered -> every matching request passes through security

    The servlet defaults are primarily coordinated through SecurityAutoConfiguration (default web-security setup) and UserDetailsServiceAutoConfiguration (default username-password user). Spring Boot is solving two problems: which requests should be protected and which mechanisms should be available; and which user can authenticate and where that user is loaded from. These correspond conceptually to a default SecurityFilterChain plus a default UserDetailsService. The effective default configuration can be understood approximately as:

    @Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(authorize -> authorize
            .anyRequest().authenticated()
        )
        .formLogin(Customizer.withDefaults())
        .httpBasic(Customizer.withDefaults());
    return http.build();
}

    This means anyRequest().authenticated() (every request requires authentication), formLogin() (username-password through an HTML login form), and httpBasic() (username-password through the Authorization header). Spring Security documents this as the default filter-chain configuration.

    Important: Adding the security starter secures everything by default. No endpoint is left open unless you say so.

    Auto-configuration is conditional: provide defaults only when the developer has not provided their own configuration. If no SecurityFilterChain bean exists, Spring Boot creates the default web-security configuration; if one exists, it backs off and lets the developer control web security. But a custom SecurityFilterChain replaces the default access rules without removing the generated default user; to replace the user setup too, provide one of UserDetailsService, AuthenticationProvider, or AuthenticationManager. These are independent:

    SecurityFilterChain                          -> How requests are secured
UserDetailsService / AuthenticationProvider  -> How users are authenticated

    Default user. Spring Boot needs at least one identity that can authenticate; without a user, the application would present a login page but no credentials could ever succeed. It therefore creates a default in-memory user with username user, stored through UserDetailsService rather than a database:

    InMemoryUserDetailsManager
   +-- UserDetails
       +-- username    = "user"
       +-- password    = generated password
       +-- authorities = ["ROLE_USER"]
       +-- enabled     = true

    This user is not created by your controller, saved through JPA or MySQL, a permanent production account, or related to registration; it exists only because Spring Boot needs a development-time identity for testing its default security configuration.

    What happens when we enter user? The login request provides a principal claim (user) and a credential (the form password). Spring Security asks the user store to load the user whose username is user; the in-memory store returns a UserDetails with an encoded stored password and ROLE_USER. The submitted password is checked against the stored representation. If it matches, Spring Security creates an authenticated Authentication object (principal = UserDetails("user"), credentials = cleared, authorities = [ROLE_USER], authenticated = true) and places it in the SecurityContext.

    Default role. The default user normally has ROLE_USER; remember role name USER versus granted authority ROLE_USER. For the default rule anyRequest().authenticated(), the actual role does not matter - Spring Security only asks whether there is an accepted authenticated identity, not whether the user has ROLE_ADMIN. Therefore the default user can access every endpoint after authentication, because the default rule requires authentication, not a particular authority.

    Configuring the default user through properties. For demonstration purposes we can replace the generated credentials:

    spring.security.user.name=aditya
spring.security.user.password=secret123
spring.security.user.roles=USER,ADMIN

    Now the user becomes conceptually: username aditya, password secret123, authorities ROLE_USER, ROLE_ADMIN.

    Generated password. When the application starts, the console displays something similar to:

    Using generated security password:
78fa095d-3f4c-48b1-ad50-e24c31d5cf35

This generated password is for development use only.
Your security configuration must be updated before
running your application in production.

    The generated value is the password entered with username user. Spring Boot generates a random default password and logs it at WARN level during startup; the documentation explicitly describes it as development-only.

    The CSRF 403 Forbidden surprise. Suppose a user successfully logs in and then sends POST /api/courses. They may receive 403 Forbidden and conclude that the user does not have permission - but that is not necessarily the reason. Spring Security enables CSRF protection by default for servlet web applications, so a state-changing request (POST, PUT, PATCH, DELETE) may be rejected when it lacks the expected CSRF token. The request may have a valid authenticated user, a valid ROLE_USER, and the correct endpoint, but still fail because the required CSRF proof is missing.

    Important: Why does GET usually work? CSRF protection targets state-changing methods, so a plain GET is not blocked by a missing CSRF token the way a POST is, even though both pass through the same authenticated session.

    Key takeaway: 401 Unauthorized usually means acceptable authentication is missing or has failed; 403 Forbidden means the request was understood but rejected. With Spring Security, a 403 on a state-changing request may be caused by a missing CSRF token, not only by insufficient roles or authorities.

    11. First Customization: SecurityFilterChain

    The first customization is to provide our own SecurityFilterChain. Because Spring Boot backs off when it sees a developer-supplied chain, this bean replaces the default web-security rules. A minimal chain can open a public endpoint while keeping everything else authenticated:

    @Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(authorize -> authorize
            .requestMatchers("/api/courses/public/**").permitAll()
            .anyRequest().authenticated()
        )
        .formLogin(Customizer.withDefaults());
    return http.build();
}

    permitAll() expresses the "permit all requests" authorization policy for that matcher; anyRequest().authenticated() requires an accepted authenticated identity for everything else. Providing this bean removes the default access rules, but the generated default user still exists until a custom UserDetailsService, AuthenticationProvider, or AuthenticationManager is supplied.

    Golden rule: Write your own SecurityFilterChain to control which requests are secured; supply your own user source to control who can authenticate. They are separate back-off conditions, so fixing one does not fix the other.

    12. Myth vs Reality

    Myth Reality
    "Security is only about protecting data" Security protects resources and operations too, including availability, identities, and administrative actions.
    "Authorization is the frontend hiding buttons" Users control the browser; authorization must be enforced on the server.
    "Authentication and authorization are the same" Authentication verifies who you are; authorization decides what you may do.
    "The cookie contains the logged-in user" Server-side session cookies normally hold only a session identifier; the state lives server-side.
    "A token is stateless because it is a JWT" Token format does not determine session policy; a JWT can be used in a session-backed design.
    "Stateless means no data is stored anywhere" Stateless only means no stored HTTP login session is needed to identify the user.
    "A 403 always means the user lacks a role" A 403 on a state-changing request may be a missing CSRF token, not insufficient authority.

    13. Common Trap Questions

    Trap 1 - "Authentication and authorization are the same thing." Verdict: False. Authentication verifies an identity claim ("who are you?"); authorization evaluates what that identity may do. Authorization normally follows authentication.

    Trap 2 - "The frontend only shows the delete button to admins, so normal users cannot delete." Verdict: False. Users control their browsers and can call hidden endpoints with Postman or curl. Authorization must be enforced on the server, not the UI.

    Trap 3 - "The session cookie contains the complete logged-in user." Verdict: False in ordinary server-side sessions. The cookie usually holds only a session identifier; the SecurityContext lives server-side and is looked up using that identifier.

    Trap 4 - "JWT means the application is stateless." Verdict: Not necessarily. A JWT is a token format; statelessness depends on whether the server persists the resulting SecurityContext in an HTTP session.

    Trap 5 - "A 403 Forbidden means the user has no permission." Verdict: Not always. 401 means authentication is missing or failed; 403 means the request was understood but rejected. With Spring Security, a 403 on POST/PUT/PATCH/DELETE may be a missing CSRF token.

    Trap 6 - "Adding my own SecurityFilterChain also removes the generated default user." Verdict: False. A custom SecurityFilterChain replaces the default web-security rules, but the generated user remains until you provide your own UserDetailsService, AuthenticationProvider, or AuthenticationManager.

    Trap 7 - "The default user is privileged and can do everything because it has a role." Verdict: Misleading. The default user has ROLE_USER, and the default rule anyRequest().authenticated() only checks that an identity is authenticated - not that it holds any particular role.

    14. Points to Remember

    1. Application security protects valuable resources and operations, not only data; availability itself is an asset.
    2. Security is a collection of controls (authentication, authorization, validation, sessions, passwords, CSRF, CORS, transport), and Spring Security does not fix insecure queries, uploads, secrets, or dependencies.
    3. A threat is not a vulnerability; Threat + Vulnerability -> Possible Attack.
    4. A trust boundary is where data moves between trust levels; the browser is untrusted, so authorization must be enforced server-side.
    5. Authentication verifies an identity claim; authorization decides access from subject, action, resource, and context.
    6. In the identity model, identity is the concept and account is the record; credentials are evidence; principal is the current identity; authorities/roles are granted capabilities that must be trusted, never claimed.
    7. Authentication is both an unverified request token (authenticated = false) and the accepted principal after verification (authenticated = true).
    8. SecurityContext holds the current Authentication; SecurityContextHolder exposes it via ThreadLocal by default and clears it after each request to prevent identity leakage.
    9. Stateful authentication keeps state server-side (session cookie, invalidatable); stateless authentication relies on a per-request credential; mechanism (form login, HTTP Basic) and session policy are separate, and token format does not decide statelessness.
    10. Adding the Security starter secures everything by default; auto-configuration backs off when you provide your own SecurityFilterChain, the default user user gets a generated development-only password logged at WARN, and a CSRF-protected POST can return 403 even for a valid authenticated user.

    15. Likely Interview Questions

    Question Crisp Answer
    What is application security? Protecting valuable resources and operations from unauthorized access, modification, destruction, disclosure, or misuse; it is a collection of controls, not one feature.
    Authentication vs authorization? Authentication verifies an identity claim ("who are you?"); authorization evaluates whether that identity may perform an action on a resource in a context.
    What is a trust boundary? A point where information moves from one trust level to another (browser -> server -> database); data crossing it must be questioned, authenticated, authorized, validated, and possibly encrypted.
    Why can we not trust the frontend for security? Users control the browser and can modify JS/HTML, call hidden endpoints with Postman or curl, and replay requests; authorization must run on the server.
    Threat vs vulnerability? A threat is something that could harm an asset; a vulnerability is a weakness that makes the attack possible; together they enable a possible attack.
    What is the Spring Security identity model? Identity (concept) vs account (record), credentials (evidence), principal (current identity), authorities/roles (granted capabilities), Authentication, SecurityContext, and SecurityContextHolder.
    What is the Authentication interface? It represents both an authentication request (unverified, authenticated = false) and the authenticated principal after verification, exposing principal, credentials, authorities, details, and status.
    What is SecurityContext and SecurityContextHolder? SecurityContext holds the current Authentication; SecurityContextHolder exposes it via a ThreadLocal strategy and is cleared after each request, because reused threads would otherwise leak a previous identity.
    Stateful vs stateless authentication? Stateful keeps authentication state in a server-side session (cookie carries a session ID); stateless makes each request carry its own credential and needs no stored HTTP login session.
    Is a JWT always stateless? No. A JWT is a token format; statelessness depends on whether the server persists the resulting context in an HTTP session.
    Why does the default Spring Boot app show a generated password? Auto-configuration creates an in-memory development user user; Spring Boot generates a random password (logged at WARN, development-only) so the default security config works immediately.
    Why can a POST return 403 after a successful login? Spring Security enables CSRF protection by default for servlet apps; a state-changing request without the expected CSRF token is rejected with 403, even for a valid authenticated user.
