      61. ExecutorService — types and when each

      Asked at: Razorpay · Swiggy · Cred · most product co backend rounds

      Difficulty: Medium · Topic: Concurrency

      The question: "Walk me through the different ExecutorService implementations you get from Executors.*. When would you use each?"

      The 30-second answer: FixedThreadPool(n) — N permanent threads, unbounded queue. CachedThreadPool — threads spawned on demand, idle threads die after 60s, unbounded thread creation. SingleThreadExecutor — 1 thread, unbounded queue, sequential. ScheduledThreadPool(n) — for delayed/periodic tasks. For production, prefer new ThreadPoolExecutor(...) directly — the Executors factories have dangerous defaults.

      Step-by-step thought process:

      1. "FixedThreadPool is the workhorse — N threads, an unbounded LinkedBlockingQueue. Risk: if producers outpace consumers, the queue grows unbounded and you OOM."
      2. "CachedThreadPool spawns a thread per task if no idle thread is available. Threads die after 60s idle. Risk: a flood of tasks spawns unlimited threads and crashes the JVM."
      3. "SingleThreadExecutor is one thread + unbounded queue. Useful when you need strict ordering of tasks but want them off the calling thread."
      4. "ScheduledThreadPool gives you schedule(...) and scheduleAtFixedRate(...). Important: if a scheduled task throws, subsequent runs are silently cancelled — always wrap with try/catch."
      5. "For real systems, I instantiate ThreadPoolExecutor directly with a bounded queue and a sensible RejectedExecutionHandler — usually CallerRunsPolicy to backpressure the producer."

      Edge cases to mention:

      • Always call executor.shutdown() followed by awaitTermination on JVM exit — orphan threads keep the JVM running
      • ThreadPoolExecutor has a customizable ThreadFactory — use it to name threads (payment-worker-1) so thread dumps are debuggable
      • For Java 21+ virtual threads, Executors.newVirtualThreadPerTaskExecutor() is the modern alternative for I/O-heavy work

      What NOT to say:

      • "Always use FixedThreadPool" — fine for small workloads, dangerous at scale because of the unbounded queue
      • "CachedThreadPool scales automatically" — yes, into OOM

      Common follow-up: "What's the difference between scheduleAtFixedRate and scheduleWithFixedDelay?"

      62. Future vs CompletableFuture — what's the difference?

      Asked at: Razorpay · Cred · Flipkart · Swiggy · most product co rounds

      Difficulty: Medium-Hard · Topic: Concurrency

      The question: "What does CompletableFuture give you that plain Future doesn't?"

      The 30-second answer: Future = poll-and-block. You submit a task, get() blocks until done, cancel() may stop it. CompletableFuture = composable. You chain thenApply, thenCompose, thenCombine, register whenComplete callbacks, build pipelines of dependent async operations, handle errors with exceptionally — all without blocking.

      Step-by-step thought process:

      1. "Future (Java 5) lets you submit work and get() the result. That's it. You can't react to completion, you can't chain another async step, you can't combine multiple futures elegantly."
      2. "CompletableFuture (Java 8) implements Future + CompletionStage. thenApply chains a transformation, thenCompose chains another async step (flatMap-like), thenCombine joins two futures."
      3. "Error handling: exceptionally provides a fallback value if the chain failed. handle always runs and gets both result and throwable."
      4. "Concrete: I fetch the customer, then in parallel fetch their orders and their wallet balance, then build a response. CompletableFuture.supplyAsync(...).thenCombine(...) does this cleanly."
      5. "The default executor for CompletableFuture is ForkJoinPool.commonPool() — if your work is blocking I/O, pass your own executor as the second arg to every async method."

      Edge cases to mention:

      • cancel() on CompletableFuture only sets the state to cancelled — it doesn't actually interrupt the running task (unlike Future from ExecutorService)
      • A single throw inside a chain propagates as CompletionException wrapping the original — your handlers must unwrap allOf(...) returns CompletableFuture<Void> — use thenApply after it to collect results from each individual future

      What NOT to say:

      • "Future and CompletableFuture are basically the same" — misses the entire point of composability
      • "CompletableFuture is faster than Future" — wrong framing; it's a different programming model

      Common follow-up: "What's the difference between thenApply and thenCompose?"

      63. ReentrantLock vs synchronized — when each?

      Asked at: Razorpay · Cred · Wells Fargo · senior rounds

      Difficulty: Medium · Topic: Concurrency

      The question: "When would you reach for ReentrantLock instead of the synchronized keyword?"

      The 30-second answer: synchronized is simpler and integrates with the JVM — biased locking, monitor inflation, just works for 90% of cases. ReentrantLock gives you tryLock (non-blocking attempt), tryLock(timeout), fair ordering, multiple condition variables via newCondition(), and lockable across method boundaries. Use ReentrantLock when you need any of those features.

      Step-by-step thought process:

      1. "synchronized is a JVM-level construct — concise, ties to a monitor on an object, automatically released when the block exits (even on exception)."
      2. "ReentrantLock is a class. You explicitly lock() and must unlock() in a finally block — otherwise you leak the lock and deadlock everything else."
      3. "Things you can't do with synchronized: tryLock() to attempt acquisition without blocking, lockInterruptibly() to back out if interrupted, tryLock(5, SECONDS) to time out."
      4. "ReentrantLock supports fair ordering via constructor flag — threads acquire in FIFO order rather than first-to-grab. Costs throughput, but avoids starvation."
      5. "With ReentrantLock you can create multiple Condition objects (lock.newCondition()) — equivalent to multiple wait sets on the same monitor. synchronized has one wait set."

      Edge cases to mention:

      • Both are reentrant — the same thread can lock multiple times without deadlocking itself, and must unlock the same number of times
      • Java 24's JEP 491 means synchronized no longer pins virtual threads — pre-Java 24, you needed ReentrantLock to avoid pinning
      • Always try { lock.lock();... } finally { lock.unlock(); } — never call lock() outside a try block

      What NOT to say:

      • "ReentrantLock is faster than synchronized" — modern JVMs optimize synchronized aggressively; benchmark before assuming
      • "synchronized is deprecated" — completely wrong

      Common follow-up: "Why was the JEP 491 change in Java 24 important for virtual threads?"

      64. CountDownLatch vs CyclicBarrier vs Semaphore vs Phaser

      Asked at: Razorpay · Cred · senior backend rounds

      Difficulty: Hard · Topic: Concurrency

      The question: "When would you use CountDownLatch, CyclicBarrier, Semaphore, and Phaser? Give me one use case each."

      The 30-second answer: CountDownLatch = one-shot "wait for N events" gate (e.g. wait for N services to be ready before starting). CyclicBarrier = reusable "wait for N threads to reach a barrier, then all proceed". Semaphore = N permits to control concurrent access to a resource (e.g. limit DB connections). Phaser = dynamic, multi-phase barrier where threads can register/deregister between phases.

      Step-by-step thought process:

      1. "CountDownLatch is initialized with a count. countDown() decrements; await() blocks until count is zero. One-shot — once at zero, it stays there."
      2. "Use CountDownLatch for: 'block this thread until N async setup tasks finish'. I use it in tests — fire N concurrent calls, latch waits until they all return."
      3. "CyclicBarrier is initialized with parties. Each thread calls await(); when all N have arrived, they're all released simultaneously. Resets and is reusable."
      4. "Use CyclicBarrier for: parallel-phase algorithms. All workers compute phase 1, sync at barrier, all proceed to phase 2."
      5. "Semaphore holds N permits. acquire() blocks if none available; release() returns one. Use it to throttle: 'no more than 10 concurrent calls to the payment gateway'."
      6. "Phaser is the flexible one — parties can register and deregister between phases, multiple phases supported. Replaces both CountDownLatch and CyclicBarrier in newer code when you need that flexibility."

      Edge cases to mention:

      • CountDownLatch can't be reset — if you need reuse, use CyclicBarrier or Phaser
      • CyclicBarrier supports a barrier action (Runnable run when the last thread arrives) — useful for merging phase results
      • Semaphore has tryAcquire() and tryAcquire(timeout) — same throttling pattern as connection pools

      What NOT to say:

      • "They're all basically the same" — they solve different problems
      • "Just use synchronized for everything" — non-answer that admits you don't know the tools

      Common follow-up: "How would you implement a connection pool using Semaphore?"

      65. AtomicInteger and CAS — how does it work?

      Asked at: Razorpay · Cred · Goldman · senior rounds

      Difficulty: Medium-Hard · Topic: Concurrency

      The question: "How does AtomicInteger achieve thread safety without locks?"

      The 30-second answer: It uses Compare-And-Swap (CAS) — a hardware instruction that atomically reads a memory location, compares it to an expected value, and writes a new value only if the comparison matches. AtomicInteger wraps a volatile int and uses Unsafe's CAS primitive in a retry loop.

      Step-by-step thought process:

      1. "Under the hood: AtomicInteger holds a volatile int value plus an internal handle to Unsafe (or VarHandle in modern Java)."
      2. " incrementAndGet() does: read current value, compute current+1, call compareAndSet(current, current+1). If another thread changed value in the meantime, CAS fails and we retry."
      3. "CAS maps to a single hardware instruction — CMPXCHG on x86, LDREX/STREX pair on ARM. Atomic in hardware, no OS-level lock needed."
      4. "Cost is much lower than synchronized for low-to-moderate contention. For very high contention, CAS retries thrash — LongAdder is faster (striped per-thread cells)."
      5. "The Atomic family covers Integer, Long, Boolean, Reference, plus AtomicReferenceArray and field updaters for atomic operations on fields you don't own."*

      Edge cases to mention:

      • ABA problem: a value can change from A to B and back to A — CAS sees A and succeeds, even though the value was modified. Use AtomicStampedReference if you need to detect ABA
      • getAndAdd(delta) is preferred over incrementAndGet() if you need addition by a value other than 1
      • For very high write contention on a counter, LongAdder and LongAccumulator distribute writes across cells and sum on read

      What NOT to say:

      • "AtomicInteger uses synchronized internally" — wrong, the whole point is lock-free
      • "CAS is always faster than synchronized" — true at low contention, false at very high contention

      Common follow-up: "What's the ABA problem and how do you handle it?"

      66. ThreadLocal — uses and gotchas

      Asked at: Most Spring backend rounds · Razorpay · Wells Fargo

      Difficulty: Medium · Topic: Concurrency

      The question: "What is ThreadLocal? What are the typical pitfalls?"

      The 30-second answer: ThreadLocal gives each thread its own copy of a variable — no sharing, no synchronization needed. Common uses: per-request context in web servers (e.g. tracing IDs), SimpleDateFormat per-thread caches. Main pitfall: in thread-pooled environments, you MUST call remove() at the end of each task or you leak state into the next task — and the value (often a large object) prevents GC.

      Step-by-step thought process:

      1. " ThreadLocal<T> is a holder. Each thread that calls get() sees its own value. set(value) stores into the calling thread's slot."
      2. "Internally, each Thread has a ThreadLocalMap keyed by ThreadLocal instances. The map is per-thread, not per-ThreadLocal."
      3. "Classic use: SimpleDateFormat is not thread-safe. Wrapping it in a ThreadLocal lets each thread reuse its own formatter."
      4. "In Spring MVC, request-scoped data (trace ID, tenant ID, security context) lives in ThreadLocals so any code in the request can access them without passing them everywhere."
      5. "Critical pitfall: thread pools reuse threads. If a request sets a ThreadLocal and doesn't remove() it, the next request handled by that thread sees stale data. Always clear in a finally block, or use a filter/interceptor that wraps the request."

      Edge cases to mention:

      • ThreadLocal entries can leak memory if the ThreadLocal object is GC'd but the thread keeps the value alive in its map — remove() is the cure
      • InheritableThreadLocal propagates the value to child threads created from this thread — but NOT to thread pool threads
      • Java 21 added ScopedValue as a modern replacement for ThreadLocal — immutable, scoped to a block, virtual-thread friendly

      What NOT to say:

      • "ThreadLocal is thread-safe sharing" — contradiction; it's per-thread NOT shared
      • "Just set it once and forget" — leaks state into pooled threads

      Common follow-up: "How does ScopedValue improve on ThreadLocal?"

      67. Fork-Join framework — when to use it

      Asked at: Goldman · Morgan Stanley · senior rounds

      Difficulty: Hard · Topic: Concurrency

      The question: "What is the Fork-Join framework and when would you use it?"

      The 30-second answer: Fork-Join (Java 7) is designed for divide-and-conquer parallelism — recursive problems where you split work into halves, solve in parallel, combine results. The pool has work-stealing: idle threads steal tasks from busy threads' queues. Use it for CPU-bound recursive problems; not great for blocking I/O.

      Step-by-step thought process:

      1. "The framework has ForkJoinPool, RecursiveTask<V> (returns a value), and RecursiveAction (no return)."
      2. "You implement compute(). If the task is small enough, solve directly. Otherwise, split into subtasks, fork() them, then join() each."
      3. "Work stealing: every worker thread has its own deque. When a thread runs out of its own work, it steals from another's deque. This balances load without central coordination."
      4. " ForkJoinPool.commonPool() is the default pool used by parallel streams. Size defaults to Runtime.availableProcessors() - 1."
      5. "Use cases: parallel quicksort, parallel matrix operations, large array reductions. Bad fit: tasks that block on I/O — they tie up worker threads and starve other work."

      Edge cases to mention:

      • Avoid blocking I/O in fork-join tasks — use ManagedBlocker if you must block, so the pool can spawn a compensating thread
      • Parallel streams use the common pool — a slow parallel stream can starve other parts of your app
      • Java 21's virtual threads are usually a better choice for I/O-heavy concurrency

      What NOT to say:

      • "Fork-Join is for any kind of concurrency" — it's specifically for recursive CPUbound work
      • "Work stealing means there's no scheduler" — there is, it's just decentralized

      Common follow-up: "How does parallelStream() decide how many threads to use?"

      68. BlockingQueue family — which when?

      Asked at: Razorpay · Swiggy · Walmart Labs · most backend rounds

      Difficulty: Medium · Topic: Concurrency

      The question: "Walk me through the BlockingQueue implementations and when you'd pick each."

      The 30-second answer: ArrayBlockingQueue = bounded, single-lock, fixed capacity. LinkedBlockingQueue = optionally bounded, two-lock (separate head and tail), better throughput. PriorityBlockingQueue = unbounded priority heap, no FIFO. SynchronousQueue = zero-capacity hand-off — every put blocks until a take. DelayQueue = elements become available after their delay expires.

      Step-by-step thought process:

      1. "For producer-consumer with bounded capacity (backpressure on producers when consumer is slow): ArrayBlockingQueue."
      2. "For higher throughput with separate locks on head and tail, set a sensible capacity — bounded LinkedBlockingQueue. Unbounded is dangerous in production."
      3. "For priority-ordered consumption: PriorityBlockingQueue. Unbounded, so still need flow control upstream."
      4. "For hand-off semantics where you want zero queuing: SynchronousQueue. CachedThreadPool uses it internally."
      5. "For 'process this task in 5 minutes': DelayQueue. Each element must implement Delayed; only elements whose delay has expired can be taken."

      Edge cases to mention:

      • LinkedTransferQueue extends LinkedBlockingQueue with transfer() — block until a consumer takes the element (like SynchronousQueue but with optional queueing) take() blocks indefinitely; poll(timeout) returns null if nothing arrives — almost always prefer poll with timeout in production
      • All BlockingQueue impls throw InterruptedException from blocking methods — propagate properly, don't swallow

      What NOT to say:

      • "Use LinkedBlockingQueue, it's the most flexible" — unbounded by default is a footgun
      • "BlockingQueue is just a Queue with locks" — misses the timeout, take, drainTo, hand-off semantics

      Common follow-up: "What happens in a SynchronousQueue if the producer puts and no consumer is waiting?"

      69. Producer-consumer with BlockingQueue — code it

      Asked at: Wells Fargo · Walmart Labs · most backend rounds

      Difficulty: Medium · Topic: Concurrency

      The question: "Implement a producer-consumer pattern using BlockingQueue."

      The 30-second answer: One BlockingQueue (bounded), one or more producer threads calling queue.put(), one or more consumers calling queue.take(). BlockingQueue handles all the locking and waiting — your code becomes trivial. Signal shutdown via a poison pill (a sentinel object) so consumers know when to exit.

      Step-by-step thought process:

      1. "Pick a bounded queue — new ArrayBlockingQueue<Order>(1000). Bounded means producers backpressure when consumers fall behind."
      2. "Producer thread loops: build an Order, call queue.put(order). put blocks if the queue is full."
      3. "Consumer thread loops: Order order = queue.take(); process(order);. take blocks if the queue is empty."
      4. "For graceful shutdown, the producer puts a known poison pill (or a special 'shutdown' Order). Consumer checks for it and exits the loop. With multiple consumers, put N pills for N consumers."
      5. "Handle InterruptedException properly: catch, restore the interrupt flag via Thread.currentThread().interrupt(), then break out of the loop."

      Edge cases to mention:

      • Don't use a sentinel value like null for poison pill — BlockingQueue rejects nulls
      • For multiple producers AND multiple consumers, the queue still works — it's thread-safe — but coordinating shutdown is trickier (use AtomicInteger countdown of remaining producers) For unbounded throughput, consider LinkedTransferQueue — slightly better performance under contention

      What NOT to say:

      • "Use wait/notify directly" — that's what BlockingQueue exists to avoid
      • "Make it unbounded so producers never block" — that's just moving the OOM to a different line

      Common follow-up: "How would you implement backpressure if producers can't be blocked?"

      70. Deadlock — how to detect and prevent

      Asked at: Most senior backend rounds · Razorpay · Goldman

      Difficulty: Medium · Topic: Concurrency

      The question: "How do you detect a deadlock in production? How would you prevent one?"

      The 30-second answer: Detect: take a thread dump (jstack or kill -3) — the JVM reports any monitor-deadlock cycles it can detect. Prevent: acquire locks in a consistent global order, use tryLock(timeout) to fail fast instead of deadlocking, minimize lock scope, prefer immutable data and message-passing over shared mutable state.

      Step-by-step thought process:

      1. "Classic deadlock: thread A holds lock 1 and wants lock 2; thread B holds lock 2 and wants lock 1. Both wait forever."
      2. "Detection in production: jstack prints all threads, their stacks, and any 'Found one Java-level deadlock' summary at the bottom. Modern monitoring (Datadog, NewRelic) flags this automatically."
      3. "Prevention strategy 1: consistent lock ordering. If every thread that needs both locks acquires them in the same order, no cycle is possible."
      4. "Prevention strategy 2: ReentrantLock with tryLock(timeout) — if you can't acquire the second lock in N seconds, release the first and retry."
      5. "Prevention strategy 3: design out the problem. Use immutable objects, message queues, single-writer patterns. The locks you don't take can't deadlock."

      Edge cases to mention:

      • jstack only detects monitor-based deadlocks (from synchronized) — Lock-based deadlocks (ReentrantLock) need ThreadMXBean.findDeadlockedThreads() to detect programmatically
      • Livelock is a related issue — threads keep retrying without progress; harder to detect than deadlock
      • Database deadlocks are separate — those happen at the DB level; the JVM thread is just waiting on a row lock

      What NOT to say:

      • "Use synchronized on this everywhere" — doesn't prevent deadlock; encourages it
      • "Deadlocks resolve themselves eventually" — they don't, that's the definition

      Common follow-up: "Walk me through a real deadlock you've debugged."
