    Auth & Security

    7 sections · 868 words

    Section 4 of 11

    Auth Stack

    • Keycloak — Identity Provider (IdP): handles login, token issuance, PKCE flow, JWKS endpoint
    • auth-service — App-layer metadata: user profiles, tenant assignments, app-specific role mappings
    • api-gateway — JWT validation, trust boundary, header injection
    • Spring Security — @PreAuthorize role enforcement in downstream services

    Full Auth Flow

    1. User clicks Login → Frontend redirects to Keycloak (Authorization Code + PKCE)
    2. Keycloak login page → User enters credentials → Keycloak redirects back with authorization code
    3. Frontend exchanges code for tokens (Keycloak token endpoint) → Includes code_verifier to complete PKCE → Receives: access_token (JWT, short-lived ~5min) + refresh_token (longer-lived)
    4. Token storage → access_token: JavaScript memory variable (NOT localStorage) → refresh_token: httpOnly cookie (NOT readable by JS)
    5. API calls → Authorization: Bearer <access_token> on every request → api-gateway validates JWT signature against Keycloak JWKS (cached public keys) → Gateway extracts sub (userId) and tenant_id custom claim → Gateway injects X-User-Id and X-Tenant-Id as trusted internal headers → Downstream services use injected headers, skip JWT re-validation
    6. Token refresh (silent) → Before access_token expiry, frontend hits Keycloak refresh endpoint → Browser automatically sends httpOnly refresh cookie (no JS involvement) → Keycloak returns new access_token → Stored back in memory
    7. Page reload → access_token in memory is gone → App init sequence: attempt silent refresh via httpOnly cookie → If refresh succeeds: proceed as authenticated → If refresh fails (expired/revoked): redirect to Keycloak login

    Why PKCE?

    The attack PKCE prevents: Authorization code interception. In the standard Authorization Code flow, an attacker who intercepts the auth code (via a malicious redirect URI, shared device, logs) can exchange it for tokens at the token endpoint.

    How PKCE stops it:

    1. Frontend generates a random code_verifier string (stored in memory only for the duration of the flow)
    2. Frontend hashes it: code_challenge = BASE64URL(SHA256(code_verifier))
    3. code_challenge is sent in the initial authorization request
    4. Keycloak stores the challenge with the code
    5. When exchanging the code for tokens, the frontend must provide the original code_verifier
    6. Keycloak verifies: SHA256(code_verifier) == stored code_challenge
    7. An attacker who intercepted the code doesn't have code_verifier — exchange fails

    Why required for SPAs: SPAs cannot keep a client_secret confidential (it would be visible in the JavaScript bundle). PKCE is the approved substitute for public clients.

    Why Not localStorage for Tokens?

    Storage XSS accessible? Notes
    localStorage Yes Persists across page loads but readable by any JS on the page
    sessionStorage Yes Same as localStorage for XSS risk
    Memory (JS var) No Cleared on page refresh; re-acquired via silent refresh
    httpOnly cookie No Not readable by JS; browser sends it automatically on matching requests

    A single XSS vulnerability (injected script from any source) can read localStorage and exfiltrate your access token. Memory variables are isolated to the running page context and inaccessible to injected scripts.

    The refresh token in an httpOnly cookie: Not readable by JS at all. The browser sends it automatically when the page makes a request to the Keycloak token refresh endpoint — which is the only place it should ever go.

    Multi-Tenancy

    Approach: Logical isolation via row-level tenant_id filtering.

    1. tenant_id is a custom claim embedded in the JWT at login time
    2. api-gateway extracts it → injects X-Tenant-Id header
    3. Every service reads X-Tenant-Id from the header
    4. Every database query includes WHERE tenant_id = :tenantId
    5. Users can only see and modify data belonging to their tenant

    Logical vs Physical isolation:

    Type How Strength Cost
    Logical (this project) Shared DB, separate rows with tenant_id Good — depends on no WHERE clause being forgotten Low
    Physical (production) Separate schemas or separate DB instances per tenant Strong — DB-enforced isolation High

    Trade-off acknowledged: Logical isolation depends on every query including the tenant filter. A missed WHERE clause could expose cross-tenant data. In production for sensitive data, physical isolation (separate schemas, RLS in Postgres, or separate DB instances) is the safer choice.

    Roles & Authorization

    Roles: ROLE_USER, ROLE_AGENT, ROLE_ADMIN

    Enforced via Spring Security @PreAuthorize on controller methods:

    @PreAuthorize("hasRole('ADMIN')")
@PostMapping("/documents")
public ResponseEntity<DocumentResponse> uploadDocument(...) { ... }

@PreAuthorize("hasAnyRole('AGENT', 'ADMIN')")
@PatchMapping("/tickets/{id}/assign")
public ResponseEntity<TicketResponse> assignTicket(...) { ... }

    Role is extracted from the JWT claims by the gateway, forwarded in the X-User-Role header, and mapped to Spring Security's GrantedAuthority in a gateway filter. Downstream services use Spring Security's standard method security without touching JWTs.

    Why Keycloak and Not Auth0 / Cognito?

    For this project:

    • Open-source, self-hosted — no external SaaS dependency, works fully offline in Docker
    • Demonstrates understanding of OAuth2 / OIDC internals (not just "plug in Auth0 and it works")
    • No cost

    In a real product: Managed services (Auth0, AWS Cognito) reduce operational burden significantly. You're not running, patching, or scaling an IdP. I'd choose managed for a real product — and I can articulate exactly why I chose self-hosted for this one.
