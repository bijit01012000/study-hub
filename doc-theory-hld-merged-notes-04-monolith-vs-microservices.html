    Monolith vs Microservices

    8 sections · 632 words

    Breaking one codebase into many services, and the trade-offs at every phase.

    1. Monolith

    A monolith is a legacy-style application with a single code repository. The example is a Zomato/Tomato-like app whose modules sit together:

    • orders
    • payments
    • restaurants
    • users

    Disadvantages:

    1. Scalability (important) - the whole app must scale together.
    2. Heavy - CI/CD builds and deploys the entire application.
    3. Debugging and testing - harder because everything is entangled.

    2. Microservice

    A microservice architecture splits the app into independent services (for example users, restaurants, orders, payments) that talk to each other over HTTP. It is fast to change and deploy.

    Disadvantages:

    1. Slow comparatively - extra network latency between services.
    2. Transaction management - a single logical transaction now spans services.
    3. Multiple microservice join - data that used to be one SQL JOIN is now spread out.

    Related concerns in the diagram: a code change touches ms1/ms2/ms3, a network issue can break u1 -> u2, and a transaction may need a rollback. ACID matters here, starting with atomicity; a failed step means a transaction rollback.

    3. The Five Phases of a Microservice

    1. Decomposition - how to move from monolith to microservice (and when it is complete).
    2. Database - shared DB or unique DB.
    3. Communication - API or event-driven system.
    4. Deployment (DevOps) - how the app will be deployed, i.e. CI/CD.
    5. Observability (DevOps) - how the application will be monitored.

    4. Decomposition Phase

    Given a monolith, how do you break it into a microservice architecture? The design patterns are:

    • Decomposition by business logic.
    • Decomposition by sub-domains.

    For Zomato, the business areas are orders, payments, users, and restaurants. A sub-domain view of orders might expose routes such as:

    • www.zomato.com/orders/pay
    • www.zomato.com/payments/

    Mapping each route to its own service:

    • /orders -> 1 microservice
    • /payments -> 1 microservice
    • /add/user -> user service

    Disadvantage: the developer should be aware of the entire business.

    5. Strangler Pattern

    The strangler pattern is how the migration is actually carried out: you route a growing share of traffic to the new microservices while the monolith still serves the rest. The deck shows a monolith exposing 10 APIs and later 100 APIs, with microservices for payments (40%) and orders (90 out of 100), and the client (100 users) split across old and new paths.

    6. DB Phase

    Each microservice can have:

    1. A shared DB.
    2. A unique DB.

    Shared DB (example: Tomato with restaurant, payment, and order services on SQL):

    • Advantage: simple to carry operations, JOIN (SQL), and transactions managed with ACID.
    • Disadvantage: cannot be scaled properly, and it has the limitation of being either SQL or NoSQL.

    Unique DB (example: order, payment, and user on NoSQL; restaurant and orders on SQL):

    • Advantage: each service picks the store that fits it.
    • Disadvantage: JOIN must be handled with CQRS, and transaction management with SAGA.

    7. Transactions Across Services

    When a user creates an order, the payment, order, and restaurant services all participate:

    • A transaction has states like rollback and success.
    • Choreography: services emit and listen to events (an event-driven system); each service reacts and can roll back. It is complex to make. Listeners react to events.
    • Orchestration: a central orchestrator calls each service over an API, and on an error triggers rollbacks (order rollback, payment rollback, restaurant error).

    8. CQRS (Command Query Responsibility Separation)

    • Command: write operations (update, delete, insert).
    • Query: read operations (SELECT).

    The pattern uses separate models: order and payment write to SQL, while reads (JOINs) are served from a view DB. This maps onto a master-slave model: the master handles writes and the read side is served from the replicated view.
