    Adapter

    10 sections · 781 words

    Structural · Design Patterns · Pattern 04 of 12

    Intent

    Convert the interface of an incompatible class into the interface your code expects, keeping the translation in one seam. The adapter changes the interface and adds nothing.

    When To Use It

    The Signs

    • A class you must use whose method names and shapes do not match what your code expects.
    • A third-party or legacy SDK you cannot change.
    • Two systems that should talk but pass incompatible types.
    • Call sites littered with tiny inline translations of the same foreign API.

    Don't Bother If

    • You own both sides and can just change one interface.
    • The mismatch is one method you call once. An inline lambda is fine.
    • The two interfaces are already compatible.
    • You need to simplify a whole subsystem, not translate one class. That is Facade.

    Before

    class Atm {
    // the wire format leaks in
    void withdraw(String pan, int cents) {
        Iso8583Msg m = new Iso8583Msg();
        m.setField(2, pan);
        m.setField(4, cents);
        Iso8583Resp r = host.send(m);
        if (!r.getField(39).equals("00"))
            throw new DeclinedException();
    }
    // deposit() hand-rolls the very same ISO-8583
}
// every method that touches money re-encodes ISO-8583

    The wire leaks in.

    After

    interface BankService {
    // what the ATM wants
    boolean debit(String acct, int amount);
    Money balance(String acct);
}

class CoreBankingAdapter implements BankService {
    private final Iso8583Host host; // the adaptee

    public boolean debit(String acct, int amt) {
        Iso8583Msg m = new Iso8583Msg();
        m.setField(2, acct);
        m.setField(4, amt);
        Iso8583Resp r = host.send(m);
        return "00".equals(r.getField(39));
    }
    public Money balance(String acct) { ... }

}
// the ATM depends only on BankService. ~18 lines.

    Or a static helper next to it, which still leaks the raw response:

    int rc = BankUtils.debit(host, pan, cents);
// static helper, but still hands back the raw
// Iso8583Resp: every caller re-checks "00"

    Structure

    «INTERFACE»
Atm  «uses»  BankService
    + debit(acct, amt): boolean
    + balance(acct): Money
    holds a BankService
    calls debit(), balance()
    the interface the ATM wants

«realizes»
CoreBankingAdapter
    - host: Iso8583Host
    wraps
    debit(): builds Iso8583Msg,
    reads field 39, maps errors

Iso8583Host
    + send(Iso8583Msg)
    the adaptee
    never changes

THE ADAPTER SPEAKS THE CLIENT'S INTERFACE

    How It's Built (3 Steps)

    1. Define the target interface your code actually wants: BankService with debit() and balance().
    2. The Adapter implements that interface and holds the adaptee as a field (composition, not inheritance).
    3. Each target method calls the adaptee and converts the types both ways. Translate the adaptee's errors too.

    In The Interview

    "The bank speaks ISO-8583. I would put a CoreBankingAdapter behind our own BankService interface, so the ATM only ever calls debit() and balance() and never sees the wire format. Swapping banks is a new adapter."

    How It's Different

    From The Lookalikes

    Vs Decorator. A Decorator keeps the same interface in and out and adds behaviour; you stack many. An Adapter changes the interface and adds nothing.

    Vs Proxy. A Proxy keeps the same interface and controls access (lazy, remote, guarded). An Adapter is about shape mismatch, not access.

    Vs Facade. A Facade is a simple front over a whole subsystem of classes. An Adapter retrofits one class to a specific expected interface.

    Vs Bridge. Bridge is designed up front so an abstraction and its implementation vary independently. Adapter is glued on after the fact.

    They Say: "we are moving to a REST bank API"

    • With it: write a second adapter, RestBankAdapter implements BankService. The ATM does not change a line.
    • Without: you find and rewrite the ISO encoding in every method that moves money.

    Watch Out For

    • Prefer an object adapter (holds the adaptee by composition) over a class adapter (inherits it). Composition does not lock you to one adaptee type, and Java has no multiple inheritance anyway.
    • Keep it a thin translation. No business rules in the adapter.
    • Translate the adaptee's exceptions into your own. A leaking Iso8583Exception defeats the point.
    • A two-way adapter can implement BOTH interfaces when each side sometimes needs the other.
    • An adapter plus a domain interface is the core of an anti-corruption layer between your model and someone else's.
