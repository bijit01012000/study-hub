    Lecture 05 — Spring IOC Container

    18 sections · 4,796 words

    Lecture 05

    Scope evidence: "Spring IOC Container | Beans, @Component, @Autowired & @Bean" (playlist map, verified). The lecture folder holds two Maven projects, SpringCoreDemo and SpringCoreDemo2, plus these notes. Coverage = IoC first principles, Maven + spring-context setup, Spring Beans, XML vs annotation configuration, reflection and Student.class, @Component, @ComponentScan, ApplicationContext, AnnotationConfigApplicationContext, AppConfig.class, @Configuration, getBean(), the three DI styles, internal startup steps, @Primary, @Qualifier, custom bean names, @Bean, @Component vs @Bean, and BeanFactory vs ApplicationContext.

    Spring Core answers one question every growing application hits: who builds the objects, and who connects them? This lecture moves that responsibility out of our code and into the Spring IoC container. We start from a tightly coupled OrderService, watch Spring invert control, and finish with a precise picture of what happens when the container starts. Every later Spring feature (MVC, Data, Security) sits on top of this container.

    1. The Core Idea: Classes Should Not Create Their Own Dependencies

    A class should focus on its own responsibility. OrderService should focus on placing an order; it should not also create the object of PaymentService. The moment a class calls new on its collaborator, the two become welded together:

    public class OrderService {
    private PaymentService paymentService = new PaymentService();

    public void placeOrder() {
        paymentService.pay();
        System.out.println("Order placed");
    }
}

    The problem is tight coupling: if we later swap in another implementation (a card gateway, a mock for tests, a UPI provider), we must edit OrderService, and the consumer can never be tested without the real dependency.

    A better design removes the new. The class declares what it needs and receives it from outside:

    public class OrderService {
    private final PaymentService paymentService;

    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void placeOrder() {
        paymentService.pay();
        System.out.println("Order placed");
    }
}

    Now OrderService does not create its dependency; it receives it from outside. This is Dependency Injection (DI): the dependency is injected, not manufactured.

    Important: DI is the "how"; IoC is the "who". Spring owns creation and wiring (IoC), and fulfils that ownership by injecting dependencies (DI). One concept enables the other.

    Two consequences follow, and interviewers love both:

    • Loose coupling. The class depends on the PaymentService abstraction, not on new PaymentService(). Swapping the implementation no longer touches the consumer.
    • Testability. We can pass a fake PaymentService in a unit test without starting Spring.

    Golden rule: A class should ask for what it needs, never build it. Ask, do not new.

    2. First-Principles: Who Creates, Connects, and Manages Objects?

    Every application needs objects, and those objects may need other objects. So the real questions are:

    1. Who will create these objects?
    2. Who will connect them together?
    3. Who will manage their lifecycle?

    Without Spring, we do this manually. main() creates objects, connects them, and behaves like a small manual container:

    main()
  -> new PaymentService()
  -> new OrderService(paymentService)
  -> orderService.placeOrder()

    With Spring, this responsibility shifts to the Spring IoC container: Spring creates objects, connects them, and manages their lifecycle. Instead of our code pulling dependencies, the container pushes them in. That is IoC, Inversion of Control.

    Interviewer's perspective: IoC is not a synonym for DI. IoC is the broad principle (the framework calls you, not the reverse - the Hollywood principle). DI is one technique for achieving it. Distinguish the two.

    A shorthand for the container's four jobs: C-W-L-G - Create, Wire, manage the Lifecycle, and Give it back when asked.

    3. Basic Project Setup: Maven + spring-context

    The setup is deliberately small: create a Maven project, then add the spring-context dependency. That one dependency is the heart of the story and gives us:

    • ApplicationContext - the IoC container interface;
    • annotation-based configuration - @Configuration, @Component, @Autowired, @Bean;
    • component scanning - @ComponentScan;
    • bean creation and dependency injection.

    Two projects are used. SpringCoreDemo demonstrates registration and injection with our own classes; SpringCoreDemo2 demonstrates the @Bean style, where object creation is written by hand inside a configuration class. Both are plain Maven projects pulling spring-context from the central repository.

    Important: There is no spring-boot-starter here on purpose. This is pure Spring Core. Understanding spring-context without auto-configuration is what makes Boot's automation legible instead of magical.

    Repository layout (conceptual)
SpringCoreDemo/
  pom.xml
  src/main/java/in/coderarmy/AppConfig.java, Main.java, OrderService.java, ...
SpringCoreDemo2/
  pom.xml
  src/main/java/in/coderarmy/...

    4. What Is a Spring Bean? and the Two Configuration Styles

    A Spring Bean is an object whose creation, dependency wiring, and lifecycle are managed by the Spring IoC container. Spring is responsible for creating the object, wiring its dependencies, managing its lifecycle, and giving it to us when we ask. The bean is ordinary Java; what makes it special is that Spring, not us, owns it.

    Spring manages objects through two configuration styles:

    Aspect XML-based configuration Annotation-based configuration
    Where declared In XML files In Java classes with annotations
    Era Older Spring applications Modern and commonly used
    Example <bean id="paymentService" class="..."/> @Component, @Bean
    Readability Separate from source Lives next to the code
    Today Mostly legacy projects Default for new projects

    XML was widely used in older Spring applications and is still common in legacy projects, so it is useful to understand. Annotation-based configuration is the modern approach.

    Important: Both styles populate the same container with the same kind of beans. The container is indifferent to how a bean was declared; only where the instructions live differs.

    5. Telling Spring Which Classes to Manage (Reflection, @Component, @ComponentScan)

    Spring does not automatically manage every class. We must tell it which classes are eligible to become beans. One common way is @Component:

    @Component
public class PaymentService {
    public void pay() {
        System.out.println("Payment done");
    }
}

    @Component says: "this class is eligible to become a Spring bean." But that alone is not enough; Spring also needs to know where to search. That is where @ComponentScan comes in:

    @Configuration
@ComponentScan("in.coderarmy")
public class AppConfig {
}

    @ComponentScan tells Spring: scan the given package and its sub-packages, find classes marked with @Component (and @Service, @Repository, @Controller), and register them as beans. The two annotations are two halves of one sentence:

    Annotation Level Meaning
    @Component Class Marks a class as eligible to become a bean
    @ComponentScan Configuration class Tells Spring where to search

    Can we write @ComponentScan without a package name? Yes:

    @Configuration
@ComponentScan
public class AppConfig {
}

    Spring then scans the package where AppConfig is present and its sub-packages. If AppConfig is at in.coderarmy.AppConfig, Spring scans in.coderarmy and below. Leaving the package off is convenient: the configuration class's own location becomes the scan origin.

    Reflection: Why Student.class Matters

    Student.class does not create a Student object. It refers to a special object of type Class:

    Class<Student> c = Student.class;

    c contains metadata about the Student class, such as:

    • class name -> Student;
    • fields -> name, age;
    • methods -> study();
    • constructors -> Student();
    • annotations -> @Component, @Service, and so on.

    Spring uses this metadata internally. This is reflection: reading a class's shape at runtime instead of compile time. Passing new AnnotationConfigApplicationContext(AppConfig.class) gives Spring metadata about AppConfig, so it can read the configuration instructions inside.

    Important: AppConfig.class is not an AppConfig instance. It is a Class object describing AppConfig. Spring asks that metadata "which annotations do you carry?", and the answers drive everything that follows.

    6. ApplicationContext: The Spring IoC Container

    In normal Spring applications we commonly work with ApplicationContext:

    ApplicationContext context =
        new AnnotationConfigApplicationContext(AppConfig.class);

    ApplicationContext represents the Spring IoC container. It reads configuration, creates beans, resolves dependencies, manages bean lifecycle, and provides beans when requested.

    One point trips up beginners: new ApplicationContext() is not possible, because ApplicationContext is an interface. We use an implementation. For annotation-based configuration, we commonly use AnnotationConfigApplicationContext, which starts a container using Java annotation-based configuration. Concretely, the line above means:

    1. Start the Spring container.
    2. Read instructions from AppConfig.class.
    3. Use annotation-based configuration.
    4. Create and manage beans accordingly.

    AppConfig.class and @Configuration

    AppConfig is a configuration class (Section 5 shows it: @Configuration plus @ComponentScan("in.coderarmy")). It tells Spring: scan in.coderarmy; find classes marked with @Component; create their beans; wire their dependencies. So passing AppConfig.class to the container is handing Spring its startup instruction file.

    @Configuration tells Spring that a class contains Spring configuration instructions. Spring then understands this is not a normal class, that it may contain setup instructions, and that it can be a source of bean definitions. A configuration class may contain @ComponentScan, @Bean methods, and other instructions. Definition: @Configuration marks a class as a source of bean definitions.

    Class or annotation Role
    AppConfig The configuration class carrying startup instructions
    @Configuration Marks a class as a source of bean definitions
    @ComponentScan Tells the container which packages to search
    AnnotationConfigApplicationContext Reads AppConfig.class and starts the container

    Golden rule: @Configuration is the recipe book, @ComponentScan finds the ingredients, and the container is the kitchen that turns both into ready-to-use beans.

    7. getBean(): Asking the Container for a Bean

    After beans are stored in the container, we can ask for one:

    public class Main {
    public static void main(String[] args) {
        ApplicationContext context =
                new AnnotationConfigApplicationContext(AppConfig.class);
        OrderService orderService = context.getBean(OrderService.class);
        orderService.placeOrder();
    }
}

    This means: "Spring, give me the OrderService bean from your container." If Spring already created the bean, it returns that object; if Spring does not know about OrderService, we get an error. Common reasons:

    • OrderService is not annotated with @Component;
    • its package is not included in @ComponentScan;
    • the bean is not registered using @Bean or XML.

    Two overloads matter: getBean(Class<T>) asks by type, and getBean(String) asks by name. The by-name form matters the moment two beans share a type: context.getBean(OrderService.class) versus context.getBean("orderService").

    Important: getBean() is a lookup. For singleton beans the object already exists inside the container; getBean hands back the same instance each time.

    8. Dependency Injection in Spring: Constructor, Field, Setter

    Spring supports three types of dependency injection: constructor, field, and setter. This table is the most reused comparison in Spring interviews:

    Aspect Constructor Field Setter
    Injection point Constructor parameters Directly on a field Via a setter method
    @Autowired needed Optional for a single constructor Required Required
    final possible Yes No No
    Complete after creation Yes No, may be null until injected Only after the setter runs
    Testable without Spring Yes, call the constructor Hard Yes, call the setter
    Recommended for Mandatory dependencies Avoid Optional or changeable dependencies

    Constructor Injection

    Dependencies are provided through the constructor - exactly the OrderService from Section 1. In modern Spring, if a bean has only one constructor, @Autowired on it is optional; Spring automatically uses that constructor for injection. Writing @Autowired explicitly is equally valid.

    Why Constructor Injection Is Preferred

    A constructor is called when an object is created, so the cleanest time to supply PaymentService is while creating OrderService. The object is then created in a complete, usable state.

    • Benefit 1 - the dependency is mandatory. The object cannot be created without its required dependency; there is no window in which it exists half-built.
    • Benefit 2 - we can use final. private final PaymentService paymentService; means the dependency cannot be changed accidentally, making the class safer.
    • Benefit 3 - easy to test without Spring. We can call new OrderService(new PaymentService()) directly; no container is needed.

    Field Injection

    Spring directly injects into a field, most commonly with @Autowired on the field and no constructor. This works because Spring can use reflection to set the field. However, field injection is generally not preferred, for four reasons:

    • the dependency is hidden (not visible in the class's API);
    • the class cannot easily be tested without Spring;
    • the field cannot be marked final;
    • the object can exist in an incomplete state before injection.

    Constructor injection is usually the better choice for required dependencies.

    Setter Injection

    Spring creates the object first, then calls a setter to provide the dependency:

    1. Create OrderService using the no-argument constructor.
    2. Call setPaymentService().
    3. Pass PaymentService into the setter.

    Setter injection is useful when a dependency is optional or can change after creation. For mandatory dependencies, constructor injection is usually preferred.

    Interviewer's perspective: The expected ranking is constructor > setter > field. Constructor injection guarantees a fully initialised, immutable object, while field injection hides dependencies and blocks final. Give the reason, not just the ranking.

    Mnemonic: C-S-F - Constructor for what is mandatory, Setter for what is optional, Field for almost nothing.

    9. What Happens Internally When Spring Starts (BeanDefinitions First)

    When we write new AnnotationConfigApplicationContext(AppConfig.class), Spring performs several steps:

    1. Start the container. Spring creates an ApplicationContext, the IoC container.
    2. Read AppConfig.class. Spring understands it contains configuration instructions and reads the annotations on it.
    3. Process @ComponentScan. With @ComponentScan("in.coderarmy"), Spring searches that package and its sub-packages.
    4. Find component classes. Spring finds classes marked @Component, @Service, @Repository, and @Controller, for example PaymentService and OrderService.
    5. Create BeanDefinitions. Before creating objects, Spring stores information about them:
    Bean name          -> paymentService
Bean class         -> in.coderarmy.PaymentService
Scope              -> singleton
Dependencies       -> none
Creation strategy  -> constructor

    This metadata is a BeanDefinition. It is not the object; it is information about how the object should be created and managed.

    1. Create bean objects. Spring now instantiates beans from the definitions. If PaymentService has no dependency, Spring creates it: conceptually new PaymentService(), internally.
    2. Create OrderService and resolve dependencies. Spring reads OrderService(PaymentService) and understands it needs PaymentService. This is dependency resolution. Spring checks whether a PaymentService bean exists; if yes, it passes that bean into the constructor: conceptually new OrderService(paymentService).
    3. Inject dependencies. In constructor injection, injection happens at creation time, so OrderService is ready immediately after construction.
    4. Our application uses the bean. Calling orderService.placeOrder(); prints Payment done then Order placed.

    Why Does Spring Create Bean Definitions First?

    Spring is not creating one object; it is managing a whole application. Before instantiating, it must know which beans exist, their classes, scopes, dependencies, creation strategy, and lifecycle methods. That is why it builds bean definitions first. Conceptually:

    BeanDefinition list
  |
  +-- paymentService
  +-- orderService

Then: beans are instantiated, wired, and stored.

    Important: Definitions before instances. Spring plans the whole graph from metadata first, then instantiates. This ordering is what lets dependency resolution and lifecycle callbacks work consistently.

    10. No Matching Bean vs Multiple Matching Beans (@Primary, @Qualifier, Custom Names)

    What If No Matching Bean Exists?

    Suppose OrderService needs PaymentService, but Spring has no PaymentService bean. Spring cannot create OrderService and we may get:

    No qualifying bean of type 'PaymentService' available

    Common reasons: PaymentService is not annotated @Component; its package is not in @ComponentScan; the dependency is not registered; no @Bean method creates it.

    What If Multiple Matching Beans Exist?

    Two implementations of one interface: PaymentService has pay(); UpiPayment prints "UPI payment done" and CardPayment prints "Card payment done", both annotated @Component. OrderService depends on the interface, and the container now has two matching beans:

    upiPayment   -> UpiPayment  -> PaymentService
cardPayment  -> CardPayment -> PaymentService

    Both are valid. Spring is confused: should it inject UpiPayment or CardPayment? This is a bean ambiguity problem, solved with @Primary or @Qualifier.

    Aspect @Primary @Qualifier
    Purpose Default choice among candidates Selects one specific bean by name
    Placement On the bean class or @Bean method At the injection point
    Scope Global default for that type Local, only where written
    If both present Loses Wins: specific beats default

    Using @Primary

    @Primary marks the default choice. Adding @Primary next to @Component on UpiPayment tells Spring: if multiple PaymentService beans exist, prefer this one. Then OrderService receives UpiPayment.

    Using @Qualifier

    @Qualifier explicitly chooses a bean. Writing @Qualifier("cardPayment") on the constructor parameter tells Spring: inject the bean named cardPayment here.

    How Did Spring Get the Bean Name?

    By default, the bean name comes from the class name: CardPayment becomes cardPayment, UpiPayment becomes upiPayment. The first letter is usually lowercased, but acronyms can behave differently under Java bean naming rules. To avoid confusion, give a custom name:

    @Component("upi")
public class UpiPayment implements PaymentService {
}

@Component("card")
public class CardPayment implements PaymentService {
}

// Then inject the specific one:
public OrderService(@Qualifier("card") PaymentService paymentService) {
    this.paymentService = paymentService;
}

    This is clearer and easier to control. @Qualifier also works with field injection (@Autowired @Qualifier("upiPayment") on the field) and setter injection (@Qualifier("cardPayment") on the setter parameter), though constructor injection is still preferred.

    What If Both @Primary and @Qualifier Are Used?

    @Qualifier gets priority. @Primary gives a default choice; @Qualifier gives a specific choice, and a specific choice wins over a default choice.

    Golden rule: @Primary answers "which one if nobody says anything?" @Qualifier answers "exactly this one, right here." When they disagree, the explicit instruction beats the ambient default.

    Mnemonic: Primary is the default, Qualifier is the order. The chef's daily special is @Primary, but pointing at a dish and naming it is @Qualifier, which wins.

    11. @Bean: Manual Registration, Dependencies, and @Component vs @Bean

    So far we used @Component to register our own classes. But sometimes we cannot use it. Suppose a class comes from an external library:

    public class EmailClient {
    private final String apiKey;

    public EmailClient(String apiKey) {
        this.apiKey = apiKey;
    }

    public void sendEmail() {
        System.out.println("Email sent using API key: " + apiKey);
    }
}

    We cannot open a library class and add @Component, yet we may still want Spring to manage its object. In such cases we use @Bean.

    Another Case: Custom Object Creation

    Sometimes creation is not simple. A User class with a User(String name, String email) constructor is a good example: if we simply ask Spring to create it, Spring may not know what values to pass for name and email. So we tell Spring exactly how to create it. That is what @Bean helps us do.

    What Exactly Does @Bean Mean?

    @Bean is used on a method inside a configuration class:

    @Configuration
public class AppConfig {
    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }
}

    This means: Spring, call this method; take the returned object; register it in your container; manage it as a Spring bean. For singleton beans, Spring usually creates and stores the object when the context starts.

    Custom Bean Name with @Bean

    By default the bean name is the method name: paymentService() gives paymentService. We can give a custom name with @Bean("myPaymentService") and fetch it by name: (PaymentService) context.getBean("myPaymentService").

    @Bean with Dependencies

    Suppose OrderService needs PaymentService and no @Component is used anywhere. We can create both beans with @Bean:

    @Configuration
public class AppConfig {
    @Bean
    public PaymentService paymentService() {
        return new PaymentService();
    }

    @Bean
    public OrderService orderService(PaymentService paymentService) {
        return new OrderService(paymentService);
    }
}

    Spring first creates PaymentService, then passes it into orderService(). Another style is orderService() calling paymentService() directly; in a full @Configuration class Spring ensures singleton behaviour for such calls (the call is intercepted and returns the existing bean). Using method parameters is usually cleaner.

    @Component vs @Bean

    Point @Component @Bean
    Where used On a class On a method in a configuration class
    Style Automatic detection Manual registration
    Best for Our own classes Library classes or custom creation
    Needs scanning Yes No, but the config class must be loaded
    Bean name Class name based Method name by default

    Simple comparison: @Component means Spring finds the class automatically; @Bean means we manually tell Spring how to create the object.

    Important Note: Avoid Creating the Same Bean Twice

    Do not register the same object through both @Component and @Bean unless you intentionally want multiple beans. Registering PaymentService with @Component and also returning it from an @Bean method can create confusion. Possible outcomes:

    • Spring may treat them as two different beans if their names differ;
    • dependency injection by type may become ambiguous;
    • if the names are the same, bean overriding rules may apply depending on configuration.

    The clean rule: register a bean using either @Component or @Bean, not both, unless you have a clear reason.

    Dependency Resolution with @Bean

    If multiple beans of the same type exist, the same rules apply. Use @Primary on the @Bean method (for example @Bean @Primary public PaymentService upiPaymentService()), or @Qualifier on the @Bean method parameter (@Qualifier("cardPaymentService") PaymentService paymentService). In short, @Primary and @Qualifier behave identically whether candidates came from @Component or @Bean.

    Important: @Component is for classes you own and can annotate; @Bean is for everything else - third-party classes, configured objects, and conditional or complex construction.

    12. Why Not Put Everything in main()? BeanFactory vs ApplicationContext

    Why Not Put Everything in main()?

    A common question: why do we need AppConfig? Why not create everything in main()? Because main() should only start the application. Putting all creation and wiring inside main() makes it responsible for configuration and object management again, which is back to manual object creation. Instead we keep main() simple - exactly the Main from Section 7. main() is a launcher, not a factory.

    BeanFactory vs ApplicationContext

    Internally, Spring has a BeanFactory: the basic container interface. ApplicationContext builds on top of it and provides more complete features for real applications.

    Aspect BeanFactory ApplicationContext
    Role Basic container interface Advanced container on BeanFactory
    Bean loading Lazy by default Eager for singleton beans at startup
    Feature set Bean creation and DI DI plus events, i18n, lifecycle
    Usage Rare, low-level The normal choice in applications

    ApplicationContext gives bean creation and dependency injection, lifecycle management, event publishing, internationalization support, and integration with other Spring features. In normal Spring applications, we commonly use ApplicationContext.

    Interviewer's perspective: "BeanFactory vs ApplicationContext" is a classic one-liner check. ApplicationContext is a superset of BeanFactory with eager singleton loading plus enterprise features; BeanFactory is the minimal, mostly lazy core.

    13. Myth vs Reality

    Myth Reality
    "Spring manages every class automatically." Only classes it is told about, via @ComponentScan, @Bean, or XML.
    "Student.class creates a Student." It is Class metadata; no instance is created.
    "@Component alone is enough." @ComponentScan must point Spring at the package.
    "new ApplicationContext() works." It is an interface; instantiate an implementation.
    "Field injection is fine, it is shorter." It hides deps, blocks final, and is hard to test.
    "Spring creates objects, then finds deps." BeanDefinition metadata is built first, then instantiation.
    "@Component and @Bean are interchangeable." Class-level automatic vs method-level manual registration.
    "@Primary beats @Qualifier." Backwards: an explicit @Qualifier wins.

    14. Common Trap Questions

    Trap 1 — "Spring creates the bean before it knows the dependencies." Verdict: False. Spring records BeanDefinition metadata first, then instantiates and injects. Definitions before instances.

    Trap 2 — "@Component is enough to register a bean." Verdict: False. @Component marks eligibility, but nothing happens unless @ComponentScan (or XML and @Bean) makes Spring look in that package.

    Trap 3 — "ApplicationContext can be instantiated directly." Verdict: False. It is an interface; we instantiate AnnotationConfigApplicationContext or another implementation.

    Trap 4 — "Field injection is preferred because it is concise." Verdict: False. It hides dependencies, prevents final, and is hard to test. Constructor injection is preferred for mandatory dependencies.

    Trap 5 — "@Primary wins over @Qualifier when both are present." Verdict: False. Specific beats default: @Qualifier names a bean and takes priority.

    Trap 6 — "@Bean needs component scanning like @Component." Verdict: False. @Bean methods are read from a loaded configuration class; scanning is not required, though the config class itself must be registered.

    Trap 7 — "Mixing @Component and @Bean for the same type is harmless." Verdict: Misleading. It can create two beans, ambiguous by-type injection, or overriding rules. Register the bean one way unless you want multiple beans.

    15. Points to Remember

    1. A Spring Bean is an object whose creation, wiring, and lifecycle are managed by the IoC container.
    2. A class should ask for its dependencies, never create them; IoC is the principle, DI the mechanism.
    3. Setup is a Maven project plus the spring-context dependency; no Boot or auto-configuration.
    4. @Component marks a class as bean-eligible; @ComponentScan says which package to search.
    5. Student.class and AppConfig.class are Class metadata, not instances; read via reflection.
    6. ApplicationContext is the interface; AnnotationConfigApplicationContext is the annotation-based implementation.
    7. @Configuration marks a class as a source of bean definitions; getBean() asks for a bean.
    8. Injection types: constructor (mandatory deps), setter (optional or changeable), field (avoid).
    9. Spring builds BeanDefinition metadata first, then resolves, creates, and injects.
    10. No matching bean errors; multiple matching beans need @Primary (default) or @Qualifier (specific, which wins).

    What is a Spring Bean? An object whose creation, wiring, and lifecycle are managed by the container.
    IoC vs DI? IoC: the container controls creation and wiring; DI: dependencies are passed in.
    What does @Component do? Marks a class as bean-eligible; @ComponentScan must point at its package.
    What does @ComponentScan do? Tells Spring which package and sub-packages to search.
    What is @Configuration? Marks a class as a source of Spring configuration and bean definitions.
    Why does Student.class matter? It is Class metadata read by reflection, so Spring can inspect the class.
    ApplicationContext vs AnnotationConfigApplicationContext? Interface vs the annotation-based implementation we instantiate.
    What does getBean() do? Looks up and returns a managed bean by type or by name.
    Which DI type is best? Constructor injection: complete, immutable, testable without Spring.
    What if multiple beans match? Ambiguity error unless @Primary or @Qualifier decides; @Qualifier wins.
    @Component vs @Bean? Class-level automatic detection vs method-level manual registration (use @Bean for library classes).
    BeanFactory vs ApplicationContext? Minimal, mostly lazy core vs advanced superset with events and i18n.

Container features: ApplicationContext over BeanFactory
    • A Spring Bean is an object managed end to end by the IoC container.
    • @Component marks, @ComponentScan locates, @Configuration declares, @Bean registers manually.
    • ApplicationContext is the interface; AnnotationConfigApplicationContext starts it from AppConfig.class.
    • Constructor injection is preferred; setter serves optional deps; field injection is discouraged.
    • Spring builds BeanDefinition metadata before creating anything, then resolves, creates, injects.
    • No bean means an error; many beans mean @Primary (default) or @Qualifier (specific, wins).
    • main() starts the application; the container manages the graph; BeanFactory is the minimal core, ApplicationContext the practical choice.

    One-line takeaway: Spring IoC Container creates objects, wires dependencies, manages lifecycle, and gives us ready-to-use beans when required.
