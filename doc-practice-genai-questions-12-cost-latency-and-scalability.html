      Cost, latency and scalability

      0 sections · 4,021 words

      Module 12 · 9 questions · 1 practical drill

      Know what your system costs and where its time goes.

      Q12.1 — Walk me through where your token bill actually comes from.

      Weak answer: "We logged token count per request and multiplied by the rate, a few lakh rupees a month for invoice extraction. It tracked with volume."

      Why it fails: - Treats input and output tokens as one count, when output usually costs more per token, the mechanism is Module 3 Q3.12. - "Tracked with volume" is a correlation, not a decomposition of which requests cost more per unit.

      Instant rejection: - Never noticed the same fixed system prompt and examples are billed again on every single call. - No breakdown by document size, so a flat average hides a wide spread across the fleet.

      Model answer: 1. On invoice extraction I split cost into input tokens, output tokens, model tier, and how much of the input is fixed versus variable. 2. Output dominated per token, structured JSON on our chosen model was priced several times higher per token than input, the mechanism is Module 3 Q3.12. 3. About 600 tokens of every call were the fixed system prompt, schema and four examples, sent identically on every invoice regardless of size. 4. That fixed block alone cost real money at volume before a single document specific token was processed, roughly four lakh rupees a month at our scale. 5. I normalised cost per page rather than per document, since our ninety fifth percentile document cost nearly ten times the median one.

      Follow-ups: 1. MEASUREMENT — Which dominated the bill, input or output tokens, and does that match this task's shape? · Whether the two are actually split and reasoned about, not treated as one number. 2. TECHNICAL — How much of every call's input is the same fixed content, versus the actual document? · Awareness that fixed context is billed repeatedly and is the first thing worth cutting. 3. TRADEOFF — You double the few shot examples to improve accuracy. What does that do to cost per document? · Connects a quality lever to its direct cost consequence, not treated as unrelated. 4. FAILURE — A batch of long documents spikes the bill for a day. How would you have caught that early? · Whether cost is monitored per unit of work, or only as a monthly total.

      Tip: If you have profiled a cloud bill by service and split fixed versus variable infrastructure cost, that is the same skill. Don't claim you have optimised a token bill. Say you would split a cost line into its input and output components first.

      Numbers worth quoting: - Output costs more, see Q3.12 - Fixed prefix billed every call - Normalise cost per page - p95 far above the median

      Q12.2 — How do you know what a request, a user or a feature actually costs?

      Weak answer: "We check the provider dashboard at month end for total spend, and roughly know chat is the biggest source since it is most used."

      Why it fails: - The dashboard gives one total, not a breakdown by feature or team, so "roughly know" is a guess dressed as an answer. - Waiting until month end means a cost regression is invisible for weeks before anyone notices.

      Instant rejection: - No per-request tagging at all, so attribution cannot be confirmed, only assumed. - No cost per outcome number exists, only a raw monthly total with nothing to compare it against.

      Model answer: 1. Every call logs a structured event at generation time, feature id, team, user id, model and token counts, and that is what everything is built on. 2. We keep our own per model price table and compute cost per call from logged tokens, then aggregate by whatever dimension is being asked about. 3. That is how we found sales, not support, was the largest line item, since sales generated far longer outputs per call despite fewer requests. 4. We track cost per resolved query too, since a costlier call that resolves in one turn can beat a cheap one needing three follow ups. 5. We alert daily on per team spend crossing a rolling baseline, since a retry loop once burned most of a week's budget before month end would have shown it.

      Follow-ups: 1. MEASUREMENT — If finance asked which team's usage costs the most, could you answer that today, and how? · Whether attribution exists as queryable data, or only as an assumption. 2. TECHNICAL — What metadata gets attached to a request at generation time to make attribution possible? · Concrete tagging, feature, team and user id logged with token counts, not reconstructed later. 3. TRADEOFF — Would you track cost per request or cost per successful outcome? What is the difference? · Whether spend is tied to value delivered, not only raw volume. 4. FAILURE — One team's usage spikes five times overnight. How would you catch that the same day? · Whether alerting exists at a finer grain than the monthly total.

      Tip: If you have tagged cloud resources by team or feature so a bill could actually be split, that is the same attribution instinct. Don't claim you have built LLM cost attribution. Say you have tagged spend by owner before, on any metered resource.

      Numbers worth quoting: - Tag: feature, team, user id - Own price table beats dashboard - Cost per outcome, not request - Alert daily, not monthly

      Q12.3 — Talk me through prompt caching versus semantic caching, and where each breaks.

      Weak answer: "We added caching and cut costs by close to half. We cache the response, and if a similar question comes in we serve the cached answer."

      Why it fails: - Conflates reusing an exact processed prefix with matching a new query to a past one by similarity, two different mechanisms. - "Similar question" with no stated threshold, exactly where a wrong but close answer gets served with confidence.

      Instant rejection: - No invalidation path when the underlying knowledge base content actually changes. - Reports a cost saving with no check that cache served answers are still correct.

      Model answer: 1. These solve different problems and fail differently, so we run them separately rather than under one label. 2. Prompt caching reuses the processed state of an identical prefix, the mechanism is the KV cache from Module 3 Q3.11, it needs a byte exact match. 3. The first time a timestamp landed before the cached block instead of after it, our hit rate silently dropped and took a day to notice. 4. Semantic caching embeds the query and matches it to past query answer pairs by similarity, which is a different, riskier trade. 5. Two close queries, reset versus revoke a VPN token, once collided at a loose threshold, so we tightened it and tracked cache served accuracy separately.

      Follow-ups: 1. TECHNICAL — What has to stay identical for a prompt cache hit, and what upstream change breaks it silently? · Whether the exact prefix mechanism from Module 3 Q3.11 is known, not just the word cache. 2. MEASUREMENT — What similarity threshold does the semantic cache use, and was it ever tuned? · Whether the threshold was measured, or picked once and left alone. 3. FAILURE — Give two queries that are close but should get different answers. What does the cache do? · Concrete grasp of the classic semantic cache failure, a wrong but similar answer. 4. TRADEOFF — The knowledge base document changes. How long until that is reflected for a cached user? · Freshness cost of caching weighed against the saving it buys.

      Tip: If you have used an HTTP cache with an ETag versus a fuzzy search index, you have used both kinds of matching before. Don't claim you have run semantic caching in production. Say you understand exact match reuse versus similarity based reuse.

      Numbers worth quoting: - Prompt cache: exact prefix only - Semantic cache: similarity match - See Module 3 Q3.11 for the why - Track cache-served accuracy too

      Q12.4 — How do you decide when to route to a small model versus a large one?

      Weak answer: "We send everything through the cheap model by default, and retry with the bigger one if output looks malformed. Average cost dropped a lot."

      Why it fails: - The only escalation trigger is a hard failure, missing the larger risk of a confidently wrong tag that still parses fine. - No content based routing signal, ambiguous and edge case items get the same treatment as easy ones.

      Instant rejection: - No labelled sample was ever used to validate the small model's accuracy before trusting it at scale. - Assumes the routing split, once set, stays correct indefinitely with no re-check.

      Model answer: 1. We ran a golden sample of about two thousand human tagged items through both models and measured accuracy, not only cost. 2. The small model matched the large one on roughly ninety one percent of items, but misses clustered hard in a few ambiguous categories. 3. So the signal is pre-emptive, not reactive, a cheap rarity and length check routes ambiguous or short items to the large model before generation. 4. A wrong but well formed tag never errors, it just puts a product in the wrong search facet, a cost the token bill never shows. 5. We re-run the accuracy sample quarterly, since a new product line once dropped the small model's accuracy on it well below baseline unnoticed.

      Follow-ups: 1. MEASUREMENT — How do you know the small model's accuracy on items that never got escalated? · Whether accuracy was validated against a golden sample, not inferred from silence. 2. TECHNICAL — What signal routes an item to the large model before generation, not after a failure? · Pre-emptive routing on length or rarity, versus reactive retry on error. 3. TRADEOFF — Where does a wrong but cheap tag cost more downstream than the model saving? · Whether routing is connected to a downstream cost of errors, not only call savings. 4. FAILURE — The catalogue shifts toward a category the small model handles badly. How do you catch it? · Whether the routing policy is monitored ongoing, or set once and assumed stable.

      Tip: If you have routed traffic by rules, a cheap path for common cases and a slower path for edge cases, that is the same design. Don't claim you have tuned model routing. Say you would validate a cheaper path against a labelled sample before trusting it.

      Numbers worth quoting: - ~2,000 item golden sample - ~91% match on easy items - Route before, not after failure - Re-check the split quarterly

      Q12.5 — You add streaming to a slow chat interface. What actually changes, and what doesn't?

      Weak answer: "We turned on streaming so the response appears as it generates, users said it felt a lot faster, that basically solved our latency complaints."

      Why it fails: - Does not separate time to first token from total completion time, streaming only changes the former's visibility. - "Felt faster" is a perception claim, with neither metric ever measured before or after the change.

      Instant rejection: - Implies streaming fixed latency, when a slow retrieval step upstream still delays the first token regardless. - Never checked whether total completion time, governed by output length, changed at all.

      Model answer: 1. We measured time to first token and total completion time separately, since they have different causes. 2. Time to first token was around one point four seconds, almost all of it upstream, a retrieval call plus a long system prompt processed before generation. 3. Streaming changed none of that number, what changed was when the user started seeing tokens instead of waiting for the full response at once. 4. Why output then trails behind that first token is the decode mechanism in Module 3 Q3.12, one sequential step per token, reading the cache each time. 5. We shrank time to first token separately, trimming and caching the system prompt, and left streaming off our structured extraction endpoint entirely.

      Follow-ups: 1. MEASUREMENT — What was your time to first token before and after adding streaming? · Whether streaming is known to leave time to first token itself unchanged. 2. TECHNICAL — For a long detailed answer, does streaming change how long the full response takes to finish? · Whether total time is known to be governed by output length and decode speed, per Module 3 Q3.12. 3. FAILURE — Retrieval takes 800ms before generation starts. What does streaming actually fix there? · Recognising streaming cannot hide latency that happens upstream of the first token. 4. TRADEOFF — For an answer that must be parsed whole before use, is streaming worth implementing at all? · Whether the benefit is known to be perceived latency for a reader, not a machine consumer.

      Tip: If you have separated a page's first paint from its full load time when debugging performance, that is the same distinction. Don't claim you have tuned inference latency. Say you would measure first response time apart from total completion time first.

      Numbers worth quoting: - TTFT vs total time, separate - ~1.4s TTFT, mostly upstream - Streaming changes visibility only - See Module 3 Q3.12: decode

      Q12.6 — Someone suggests batching your interactive chat calls the way you batch overnight jobs. Your answer?

      Weak answer: "Batching saves money since you process more at once, so if it worked for the catalogue job it should help chat costs too."

      Why it fails: - Applies the offline batch API's savings logic to a workload with a synchronous latency requirement it cannot serve. - No recognition that batch turnaround is measured in hours, which no chat user waiting on a reply can tolerate.

      Instant rejection: - Conflates the provider's asynchronous batch API with simply grouping requests together client side. - Treats cost as the only variable, ignoring that the interactive path carries a real latency requirement.

      Model answer: 1. The batch API is an asynchronous submission model, results come back hours later against a meaningfully lower rate, spare capacity pricing. 2. That fits the catalogue job, nobody waits on any one of fifty thousand overnight results, but it is structurally wrong for a person waiting on a reply. 3. Queueing a chat message into a batch job would mean an answer sometime later that day, which is not a chat feature any more. 4. What actually helps chat is client side batching, combining a few small independent sub tasks into one call to amortise fixed prompt overhead. 5. Even the catalogue job checks its freshness need first, a same day promotion tag skips the overnight batch and pays full rate on the interactive path.

      Follow-ups: 1. TECHNICAL — What turnaround does a batch API guarantee, and is that fine for someone waiting on chat? · Concrete knowledge that batch APIs suit delay tolerant, not interactive, turnaround. 2. FAILURE — What is the batch discount actually paying for, is it the same mechanism chat would invoke? · Whether the candidate can name what the discount is for, not assume any grouping earns it. 3. TRADEOFF — Is there a form of batching that helps chat without breaking interactivity? · Distinguishing provider batch APIs from client side prompt batching as a separate technique. 4. MEASUREMENT — What would make batching the wrong choice even for the overnight job itself? · Recognising batching has a real turnaround cost checked against the freshness need.

      Tip: If you have chosen a queued background job over a synchronous API call because the caller could tolerate delay, that is this trade. Don't claim you have used an LLM batch API. Say you would separate delay tolerant work from work someone is waiting on live.

      Numbers worth quoting: - Batch: hours, discounted rate - Wrong for a waiting user - Client batching amortises prefix - Check freshness need first

      Q12.7 — Your document search feature has a high p95 latency. How do you find where the time goes?

      Weak answer: "Generation is almost always the slowest part of a RAG pipeline, so we looked at a faster model and a shorter output cap."

      Why it fails: - Assumes which stage dominates instead of measuring it, the p95 tail is often produced by a different stage than the mean. - Changes two things at once, model and output cap, with no measurement of which stage either was meant to fix.

      Instant rejection: - No per-stage tracing across embedding, vector search, reranking and generation, the whole chain is one black box. - No distinction made between a mean latency problem and a tail latency problem at all.

      Model answer: 1. We put timing spans around every stage, embedding, vector search, reranking, generation and the network hops, and looked at p95 per stage. 2. Mean was dominated by generation as expected, but the p95 tail was not, reranking was the largest contributor on the slow five percent. 3. That turned out to be input size dependent, a metadata filter was occasionally not narrowing the candidate set before reranking ran. 4. A model swap for a faster generation step would have shaved the mean and left the actual p95 problem completely untouched. 5. Once the filter was fixed we re-measured the same percentiles, and when we later tested dropping reranking we checked it against the retrieval eval set first.

      Follow-ups: 1. MEASUREMENT — Break the request into stages and give me the p95 for each one individually. · Whether per-stage tracing actually exists, or the pipeline is only measured end to end. 2. TECHNICAL — Mean latency is fine but p95 is high. What does that tell you about where to look? · Understanding a tail problem often comes from an intermittent stage, not a uniformly slow one. 3. FAILURE — The reranker is your worst p95 offender on eight percent of requests. What do you check first? · A concrete diagnostic instinct, cold starts or input size, not a generic optimise instruction. 4. TRADEOFF — You could drop reranking to save latency. What is the trade, and how would you know it hurt? · Ties a latency fix back to the quality cost it might introduce, and whether it is checked.

      Tip: If you have profiled a slow API by tracing each downstream call it makes, that is the same per stage instinct. Don't claim you have traced a RAG pipeline. Say you would instrument each stage before guessing which one is slow.

      Numbers worth quoting: - Mean and p95 can differ - Trace every stage separately - Tail often hides in one stage - Re-measure after every fix

      Q12.8 — Cut your copilot's cost without users noticing a quality drop. Walk me through it.

      Weak answer: "We switched to a cheaper model for most requests and cost dropped by about half. Users did not complain, so it seems to have worked."

      Why it fails: - A single blanket model swap with no measurement of which requests were actually driving the spend. - "No complaints" is the absence of a loud signal, not a quality measurement against a baseline.

      Instant rejection: - No per request type breakdown, so a harder slice may have quietly gotten worse unnoticed. - Treats cost cutting as one action rather than several levers, each with a distinct risk.

      Model answer: 1. We started from the per feature cost breakdown, which showed quick lookup queries were high volume and disproportionately expensive. 2. Instead of a blanket swap we routed only lookup queries to a smaller model, trimmed that path's prompt, and added caching on the shorter prefix. 3. Before shipping we ran the affected slice against an existing two hundred query golden set and compared quality to the previous pipeline. 4. Quality held within noise on that slice, and the harder multi step slice we deliberately left untouched, on the larger model still. 5. Cost fell by a bit over a third, less dramatic than switching everything, but we could name exactly which requests moved and what we checked.

      Follow-ups: 1. MEASUREMENT — How did you verify quality after the swap, did you test it or just wait for complaints? · Whether an actual quality check ran, versus relying on the absence of complaints. 2. TECHNICAL — Was the saving uniform across request types, or did some categories save more than others? · Whether the swap was informed by which request types the smaller model handles well. 3. TRADEOFF — Name one other lever besides the model swap, and what it costs you to use it. · Whether cost cutting is a set of levers with distinct trade-offs, not one switch. 4. FAILURE — A team says answers on their domain got worse weeks later. How would you trace that back? · Whether a quality complaint can be attributed back to a specific cost change.

      Tip: If you have optimised a slow code path by profiling first and changing only the hot function, that is this same targeted approach. Don't claim you have cut an LLM bill. Say you would target the highest cost, lowest risk slice first and measure quality after.

      Numbers worth quoting: - Target the cheapest-risk slice - Golden set before shipping - ~1/3 cost cut, not blanket - No complaints isn't a metric

      Q12.9 — DRILL: produce a costed reduction plan for a slow, expensive document processing pipeline. (practical drill)

      Weak answer: "N/A, this is a drill. A weak attempt picks one lever, usually a cheaper model everywhere, with no per stage breakdown first."

      Why it fails: - No initial decomposition, does not separate the two LLM calls' cost and latency or check if OCR itself is a contributor. - A blanket lever ignores that extraction needs precision while classification may not, and misses the caching opportunity.

      Instant rejection: - No named quality risk attached to any proposed change, and no stated way to check for it. - Misses that the classification step's reference examples are a stable, near ideal caching target.

      Model answer: 1. First I would instrument every stage, OCR time, extraction call, classification call and storage, since slow and expensive is not actionable yet. 2. Say classification turns out to be the bigger cost driver, its prompt resends five to ten reference examples on every document though the set barely changes. 3. That reference block is a near ideal caching target, the same exact prefix mechanism from Q12.3, with staleness as the risk if the set updates and the cache does not. 4. On extraction I would only route simple single page forms to a smaller model, based on a labelled sample, leaving ambiguous documents on the larger one. 5. I would ship the caching change first, since hit rate and cost delta are visible within a day, before the routing change, which needs the labelled sample validated properly.

      Follow-ups: 1. MEASUREMENT — Before proposing a fix, what would you measure first, and in what order? · Whether cost and latency are decomposed per stage before changes are proposed. 2. TECHNICAL — Classification retrieves reference examples that rarely change. What is the caching angle? · Recognising a stable retrieved context as a caching case, tied back to Q12.3. 3. TRADEOFF — Which change would you ship first, and why that one before the others? · Sequencing levers by risk and measurability, not proposing everything at once. 4. FAILURE — Which of your two model calls tolerates a smaller model, and how would you know? · Whether the calls are treated as having different accuracy tolerances, not identical.

      Tip: This is a drill, you are not expected to have run this pipeline. Say how you would decompose and sequence the fix. Don't invent a pipeline story. Say plainly you would measure per stage first and name a risk for every lever proposed.

      Numbers worth quoting: - Decompose before proposing fixes - Cache the stable reference set - Route only the easy slice - Ship lowest-risk lever first
