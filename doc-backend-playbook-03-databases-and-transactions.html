    Databases and transactions

    9 sections · 3,487 words

    Module 03 - 9 questions - 1 practical drill

    Reason about what the database does when real transactions collide.

    This round separates people who use an ORM from people who understand what the database does under concurrency. Follow-ups drive straight at isolation anomalies, locking, and what happens when two transactions collide in production.

    Inside this module: Isolation & locking - Index design - Schema evolution - Replication

    Q3.1 - Explain a transaction you had to get exactly right, and what would have broken without it.

    What it really tests: Whether you reach for transactions deliberately around a real invariant, or wrap everything in BEGIN out of habit.

    Weak answer: "We used transactions to make sure our database operations were atomic. If something failed it would roll back, which kept the data consistent."

    Why it fails: - Textbook definition of atomicity, no actual scenario. - No named invariant that a transaction protected. - No concurrency angle - atomicity alone isn't the interesting part. - Cannot say what specifically would corrupt without it.

    Follow-up ladder: 1. TECHNICAL - What invariant were you protecting, exactly? - A concrete correctness rule. 2. TRADEOFF - What isolation level did you run it at, and why? - Beyond default settings. 3. FAILURE - Two of these run concurrently - what anomaly could occur? - Concurrency reasoning. 4. MEASUREMENT - How did you keep the transaction short? - Lock-hold discipline.

    Answer framework: 1. The invariant 2. Operations that must be atomic 3. Isolation level chosen 4. Concurrency anomaly guarded against 5. How locks were held 6. Keeping it short 7. What would corrupt without it

    Rejection signals: - Only recites ACID, no scenario. - Doesn't know what isolation level they ran at. - Cannot describe a concurrency anomaly. - Wraps unrelated work in one long transaction.

    Model answer skeleton: The invariant was 'an account balance never goes negative' in our wallet service.

    A debit was two steps - check the balance, then write the new balance and a ledger row - and without a transaction two concurrent debits could both read the same balance and both succeed, overdrawing the account.

    I ran it at READ COMMITTED but took an explicit SELECT balance ... FOR UPDATE on the account row, which serialises debits on the same account while letting different accounts proceed in parallel.

    I kept the transaction tight - no external HTTP calls inside it, just the read, the check, and two writes - because holding that row lock across a slow call would have serialised the whole service.

    Without it, our load test reliably produced negative balances; with it, zero.

    Q3.2 - Walk me through the isolation levels and which anomaly each one lets through.

    What it really tests: Precise knowledge of READ COMMITTED / REPEATABLE READ / SERIALIZABLE and dirty/non-repeatable/phantom reads.

    Weak answer: "There are a few isolation levels - read committed, repeatable read, serializable. Higher levels are safer but slower. We mostly used the default."

    Why it fails: - Names the levels but not the anomalies each prevents. - "Safer but slower" without the mechanism. - Doesn't know which anomaly their default actually allows. - No mention of dirty/non-repeatable/phantom reads or write skew.

    Follow-up ladder: 1. TECHNICAL - What's a non-repeatable read versus a phantom read? - Precise anomaly definitions. 2. TECHNICAL - What's the default in your database, and what does it allow? - Knows their own stack. 3. TRADEOFF - What is write skew and which level stops it? - The subtle SERIALIZABLE case. 4. FAILURE - When did a default isolation level bite you in production? - Lived experience.

    Answer framework: 1. READ UNCOMMITTED 2. READ COMMITTED 3. dirty reads 4. non-repeatable reads remain 5. REPEATABLE READ / snapshot 6. phantoms and write skew remain 7. SERIALIZABLE 8. cost of each 9. your default and its exposure

    Rejection signals: - Lists levels without mapping to anomalies. - Doesn't know their DB's default. - Never heard of write skew. - Thinks REPEATABLE READ prevents everything.

    Model answer skeleton: READ UNCOMMITTED allows dirty reads - seeing another transaction's uncommitted writes - and almost nobody uses it.

    READ COMMITTED, which is Postgres's default, prevents dirty reads but allows non-repeatable reads: read a row twice in one transaction and it can change because another commit landed in between.

    REPEATABLE READ - snapshot isolation in Postgres - gives you a stable snapshot so re-reads are consistent, but it still allows write skew, where two transactions each read a set, each decide their write is fine, and together they violate an invariant.

    SERIALIZABLE is the only level that stops write skew, at the cost of serialization failures you must retry.

    This bit me once: an on-call scheduling check ran at READ COMMITTED and two people got approved for the last on-call-free slot via write skew; moving that specific check to SERIALIZABLE with a retry loop fixed it.

    Q3.3 - Optimistic or pessimistic locking - which did you use and why?

    What it really tests: Whether the choice was matched to contention level, or picked by default.

    Weak answer: "We used optimistic locking with a version column. If the version didn't match we'd throw an error and the user could retry."

    Why it fails: - Describes the mechanism but not why it fit the workload. - No mention of contention rate driving the choice. - No handling story for the retry storm under high contention. - Doesn't contrast with the pessimistic case where it would've been wrong.

    Follow-up ladder: 1. TRADEOFF - At what contention level does optimistic locking fall apart? - Knows the crossover point. 2. FAILURE - What does the user experience on a version conflict? - UX of the failure path. 3. TECHNICAL - Where would pessimistic locking have been the right call instead? - Understands both sides. 4. MEASUREMENT - How did you avoid a retry storm? - Backoff and contention control.

    Answer framework: 1. Workload contention profile 2. Optimistic mechanism (version/CAS) 3. When conflicts are rare 4. Retry/backoff on conflict 5. When pessimistic wins 6. Lock-hold cost of pessimistic 7. Choice justified by data

    Rejection signals: - Picks one without referencing contention. - No conflict-handling UX. - Can't say when the other approach wins. - Ignores retry storms.

    Model answer skeleton: For editing a user profile I used optimistic locking with a version column, because two people editing the same profile at the same second is genuinely rare - conflicts were well under 1% - so paying for a lock on every read would be waste. On the update I did UPDATE ... WHERE id=? AND version=?; zero rows affected meant someone else won, and I surfaced a 'this was changed, reload' message rather than silently clobbering.

    Where I went the other way was the wallet debit path from earlier - there, contention on a hot account is high and a lost update is money, so I used pessimistic SELECT ... FOR UPDATE, accepting that debits on one account serialise. The rule I follow is: optimistic when conflicts are rare and retryable, pessimistic when conflicts are likely or the cost of a lost update is severe.

    To avoid retry storms on the optimistic path I capped retries and added jitter.

    Q3.4 - You're getting deadlocks in production. How do you diagnose and fix them?

    What it really tests: Whether you understand deadlock mechanics (lock ordering) and the standard fixes, or just increase timeouts.

    Weak answer: "We'd see deadlock errors in the logs. We increased the timeout and added retries so the transaction would just try again, which mostly solved it."

    Why it fails: - Retrying masks the deadlock instead of removing the cause. - No mention of lock-ordering, the actual root cause. - Never inspected the deadlock graph to see which locks collided. - "Mostly solved" - the deadlocks are still happening.

    Follow-up ladder: 1. TECHNICAL - What's the root cause of a two-transaction deadlock? - Lock-ordering understanding. 2. MEASUREMENT - How did you see which two statements deadlocked? - Uses the deadlock log/graph. 3. TRADEOFF - How does consistent lock ordering prevent it? - The real fix. 4. FAILURE - Why can retries alone be dangerous here? - Understands masking vs fixing.

    Answer framework: 1. Reproduce/observe the deadlock 2. Read the deadlock graph 3. Identify the two lock-acquisition orders 4. Impose a consistent order 5. Shorten transactions / reduce lock scope 6. Add bounded retry as a safety net 7. Verify frequency dropped

    Rejection signals: - Only solution is retry + timeout. - Never looked at what actually deadlocked. - Doesn't know lock ordering causes it. - Thinks a bigger timeout is a fix.

    Model answer skeleton: Deadlocks in production almost always mean two transactions acquire the same locks in opposite orders - transaction A locks row 1 then waits on row 2, B locks row 2 then waits on row 1. First I read the database's deadlock log, which in Postgres tells you the two statements and the rows involved.

    In one case we had a transfer that locked the two accounts in the order they appeared in the request, so A->B and B->A transfers deadlocked.

    The fix wasn't a bigger timeout - it was to always lock accounts in a deterministic order, e.g. ascending by account id, so both transactions grab them in the same sequence and one simply waits instead of deadlocking.

    I also shortened the transactions to reduce the window.

    I kept a bounded retry with backoff as a safety net for the rare residual case, but retries were the seatbelt, not the fix - the lock ordering was.

    Q3.5 - How did you decide between a relational database and a NoSQL store for a given feature?

    What it really tests: Whether the choice was driven by access patterns and consistency needs, or by hype.

    Weak answer: "NoSQL scales better and is more flexible, so for anything that needed to scale we used something like MongoDB, and relational for the rest."

    Why it fails: - "Scales better" as a blanket claim ignores relational scaling options. - No access pattern named. - Ignores transactional and join requirements. - "Flexible" schema stated as pure upside, no downside.

    Follow-up ladder: 1. TECHNICAL - What access pattern made NoSQL the right fit? - Pattern-driven modelling. 2. TRADEOFF - What did you give up on consistency or joins? - Honest trade-offs. 3. TECHNICAL - How would you model a many-to-many relationship in that store? - Data-modelling depth. 4. FAILURE - When did the flexible schema cause you a problem? - Schema-on-read pain.

    Answer framework: 1. Access patterns and query shapes 2. Consistency and transaction needs 3. Relationship complexity 4. Scale and write pattern 5. What each store gives up 6. Choice justified 7. What the flexible schema cost later

    Rejection signals: - "NoSQL scales, SQL doesn't." - No access pattern mentioned. - Unaware of relational sharding/read-replicas. - Treats schemaless as free.

    Model answer skeleton: I chose based on the access pattern and the shape of the relationships.

    For our core orders - which had strong invariants, needed multi-row transactions, and got queried by lots of ad-hoc reporting joins - I kept Postgres, because relational is exactly what 'joins plus transactions' wants and we were nowhere near a scale it couldn't handle.

    For a high-write event/audit log that was only ever queried by a single partition key and time range, I used DynamoDB, because the access pattern was fixed and known, and it scaled writes horizontally without me babysitting shards.

    What I gave up there was ad-hoc querying - you can't just JOIN in Dynamo - and I designed the partition and sort keys up front around the exact queries.

    The flexible schema did bite once: an optional field drifted across three shapes over time, and a consumer choked on the old shape, so I learned to validate at the write boundary even in a schemaless store.

    Q3.6 - A query got slow as the table grew. Walk me through how you'd fix it.

    What it really tests: Systematic query optimisation via EXPLAIN, indexing, and understanding why a plan changed.

    Weak answer: "We added an index on the column we were filtering by, and that made it fast again. Indexes speed up queries so we just made sure the important columns had them."

    Why it fails: - "Just index the important columns" ignores composite/covering indexes and write cost. - Never mentions EXPLAIN to confirm the plan. - No awareness that indexes slow writes and cost storage. - Doesn't consider selectivity or index-not-used cases.

    Follow-up ladder: 1. MEASUREMENT - How did you confirm the index was actually used? - EXPLAIN over assumption. 2. TECHNICAL - Why might Postgres ignore an index you added? - Selectivity/planner understanding. 3. TRADEOFF - What's a covering index and when does it help? - Depth beyond single-column indexes. 4. FAILURE - What did adding that index cost you? - Write amplification / storage awareness.

    Answer framework: 1. Confirm the slow query 2. EXPLAIN ANALYZE the plan 3. Identify the scan 4. Choose index type/columns/order 5. Verify plan changed 6. Measure before/after 7. Weigh write and storage cost 8. Add regression guard

    Rejection signals: - Adds indexes without EXPLAIN. - Doesn't know why an index might be ignored. - Ignores write-side cost of indexes. - No before/after measurement.

    Model answer skeleton: I start with EXPLAIN ANALYZE, not guesses. On one slow report the plan showed a sequential scan of a 20M-row table filtering on (tenant_id, status) and sorting by created_at.

    A single-column index on tenant_id barely helped because within a big tenant it was still scanning and sorting, so I built a composite index on (tenant_id, status, created_at) - column order matters, equality columns first, then the sort column - which let the planner satisfy filter and sort from the index.

    I confirmed the new plan actually used it, because Postgres will ignore an index if it thinks a scan is cheaper, e.g. on a low-selectivity predicate.

    The query went from ~3s to ~30ms.

    The cost I accepted was slightly slower writes and extra storage from the index, which was fine here because this table was read-heavy; on a write-heavy table I'd have thought harder before adding it.

    Q3.7 - How did you run a schema migration on a large table without downtime?

    What it really tests: Whether you know that naive ALTER TABLE locks, and the expand/contract pattern.

    Weak answer: "We wrote a migration script and ran it during a low-traffic window. It added the column and we deployed the new code afterwards."

    Why it fails: - "Low-traffic window" implies accepting downtime rather than avoiding a lock. - No awareness that some ALTERs take a long exclusive lock. - Single-step migration couples schema and code deploy. - No backfill strategy for a new NOT NULL column.

    Follow-up ladder: 1. TECHNICAL - Adding a NOT NULL column with a default on a huge table - what's the risk? - Lock/rewrite awareness. 2. TRADEOFF - Describe the expand/contract (parallel change) pattern. - Safe migration methodology. 3. MEASUREMENT - How do you backfill millions of rows without locking? - Batched backfill. 4. FAILURE - How do you make the migration reversible? - Rollback planning.

    Answer framework: 1. Assess lock behaviour of the change 2. Expand: add nullable column / new structure 3. Deploy code that writes both 4. Backfill in batches 5. Switch reads 6. Contract: drop old 7. Keep each step reversible

    Rejection signals: - Relies on a maintenance window instead of avoiding locks. - Doesn't know NOT NULL + default can rewrite the table. - Single big-bang migration. - No batched backfill, no rollback.

    Model answer skeleton: I use expand/contract so there's never a moment the old and new code can't both run. Say I'm splitting full_name into first_name / last_name: first I add the new nullable columns - on Postgres this is a fast metadata-only change, whereas adding a NOT NULL column with a volatile default on old versions would rewrite the whole table under an exclusive lock.

    Then I deploy code that writes both the old and new columns.

    Next I backfill existing rows in batches - a few thousand at a time in separate transactions with a short sleep - so I never hold a long lock or blow up replication lag.

    Once the backfill is done and verified, I switch reads to the new columns, and only in a later, separate deploy do I contract by dropping the old column.

    Every step is independently reversible, so if the new code misbehaves I roll back the deploy without touching the schema.

    Q3.8 - How did you handle the read load when a single database couldn't keep up?

    What it really tests: Understanding of read replicas, replication lag, and when sharding becomes necessary.

    Weak answer: "We added read replicas and sent read queries to them. That spread the load and the primary only handled writes."

    Why it fails: - Ignores replication lag and read-your-writes issues. - No mention of which reads are safe to send to a replica. - Doesn't address the write-scaling ceiling. - No monitoring of lag.

    Follow-up ladder: 1. FAILURE - A user writes then immediately reads from a replica - what can go wrong? - Read-your-writes / replication lag. 2. TRADEOFF - Which queries did you keep on the primary? - Routing judgement. 3. TECHNICAL - Replicas help reads - what about write scaling? - Knows the ceiling / sharding. 4. MEASUREMENT - How did you monitor replication lag? - Operational awareness.

    Answer framework: 1. Read/write split 2. Route reads to replicas 3. Handle replication lag / read-your-writes 4. Keep critical reads on primary 5. Monitor lag 6. When writes still bottleneck 7. Sharding or partitioning as the next step

    Rejection signals: - Ignores replication lag entirely. - Sends read-after-write to a replica blindly. - Thinks replicas scale writes. - No lag monitoring.

    Model answer skeleton: We were read-heavy, so I added read replicas and routed most reads there while the primary took all writes.

    The catch is replication lag - a user who just placed an order and immediately loaded their order list could hit a replica that hadn't caught up and see an empty list.

    So I routed read-your-writes cases and anything on a critical consistency path to the primary, and sent only lag-tolerant reads like search and browse to replicas.

    I monitored replica lag as a first-class metric and alerted if it crossed a couple of seconds, because rising lag was an early warning of primary write pressure.

    Replicas bought us a lot of headroom on reads, but they do nothing for write throughput - so I noted that if writes became the ceiling the next step was partitioning by tenant, which we hadn't yet needed.

    Q3.9 - [DRILL] Given a transfer(from, to, amount) between two accounts, write the transaction and name every failure mode you're guarding against.

    What it really tests: Whether the candidate can reason about atomicity, locking order, isolation, and overdraw all at once.

    Weak answer: N/A - drill. A weak attempt wraps two UPDATEs in a transaction and stops.

    Why it fails: - Two blind UPDATEs with no balance check. - No lock ordering, so concurrent opposite transfers deadlock. - No overdraw guard. - No idempotency, so a retried transfer runs twice.

    Follow-up ladder: 1. TECHNICAL - How do you stop A->B and B->A deadlocking? - Deterministic lock ordering. 2. FAILURE - Where's the overdraw check and is it race-safe? - Invariant under concurrency. 3. MEASUREMENT - If the client retries the transfer, does it run twice? - Idempotency of money movement.

    Answer framework: 1. Begin transaction 2. Lock both accounts in deterministic order 3. Record idempotency key 4. Check overdraw 5. Debit and credit 6. Insert ledger rows 7. Re-read balances under lock 8. Commit; on serialization failure retry

    Rejection signals: - No balance check or a check outside the lock. - Locks in request order (deadlock-prone). - No idempotency. - Does external calls inside the transaction.

    Model answer skeleton: Drill output: I begin a transaction, then SELECT ... FOR UPDATE both account rows ordered by ascending account id - deterministic ordering is what stops A->B and B->A deadlocking, because both transactions grab the lower id first.

    Under the lock I re-read the source balance and check balance >= amount; doing the check after taking the lock is what makes the overdraw guard race-safe.

    Then I decrement the source, increment the destination, and insert two ledger rows in the same transaction so the money-moved record is atomic with the balances. I record a client-supplied idempotency key in a unique-constrained table inside the same transaction, so a retried transfer hits the constraint and returns the original result instead of moving money twice.

    No HTTP or external calls happen inside the transaction - those would hold the row locks across network latency.

    On a serialization failure I retry the whole thing with backoff.
