      Scaling & Production-Readiness

      0 sections · 273 words

      96. How would you scale if traffic 10×'d?

      Per service. ticket-service and auth-service are stateless REST — scale horizontally behind the LB. notification-service — more instances in one consumer group, Kafka redistributes partitions. knowledge-service ingestion — add partitions so more workers embed in parallel. chat-service scales horizontally, but SSE connections are stateful, so I'd need sticky sessions or externalize connection state. pgvector — read replicas for search; a dedicated vector DB at very high vector counts.

      97. What's the biggest bottleneck / risk?

      The synchronous chat path has the most dependencies in one request: SSE lifecycle + knowledge-service REST + LLM call + (Redis). The LLM latency is the unpredictable one. First thing I'd harden is a circuit breaker + timeout on the LLM and retrieval calls with graceful degradation — respond with a clear error and an immediate escalation offer instead of hanging.

      98. What would you add before calling this production-ready?

      In priority: automated tests (esp. idempotency + outbox integration), distributed tracing (OpenTelemetry), circuit breakers on chat's downstream calls, a Kafka dead-letter topic with retry policy, and cancel-on-disconnect for the LLM stream. Then structured output for escalation and semantic chunking for retrieval quality.

      99. How do you keep an eye on RAG quality specifically?

      The RAG Grafana dashboard tracks ingestion queue depth, embedding latency, and retrieval hit rate. The next step is a feedback loop — thumbs up/down on answers feeding a re-ranking signal — plus offline evaluation of retrieval (do the right chunks show up for a labeled question set). Retrieval quality is measurable, and I'd measure it rather than eyeball it.
