    Lecture 23 — Spring AOP Advice Types

    22 sections · 4,579 words

    Lecture 23

    Scope evidence: "Spring AOP Advice Types Explained | @Before, @After, @Around" (playlist map, verified). Repo aopDemo project: aspect.LoggingAspect, service.StudentService, controller.StudentController, dto.Student, plus notes (source tree plus a PaymentService failure example).

    Spring AOP runs extra logic before, after, or around selected bean methods without mixing it into the business code. This lecture implements five advice types - @Before, @AfterReturning, @AfterThrowing, @After, and @Around - and shows when each fires and what each may change. A proxy wraps the target bean and intercepts matching calls. Map each advice onto try-catch-finally and the topic collapses.

    1. The Five Advice Types and Cross-Cutting Concerns

    Logic kept out of the business method is a cross-cutting concern, because it cuts across many classes. Typical examples:

    • Logging
    • Authorization
    • Auditing
    • Performance measurement
    • Metrics
    • Technical validation
    • Context management

    The five principal advice types provided by Spring AOP:

    1. @Before
    2. @AfterReturning
    3. @AfterThrowing
    4. @After
    5. @Around
    Advice When it runs Position in try-catch-finally Typical use
    @Before before the target method begins before the try block entry logging, reading args, authorization, preconditions
    @AfterReturning only when the target returns normally after a successful return inside try log or record the returned value
    @AfterThrowing only when the target exits by throwing inside catch log or record the exception
    @After on success and on failure inside finally cleanup that is outcome-neutral
    @Around surrounds the whole invocation the entire try-catch-finally control, timing, retry, fallback, transformation

    Important: The advice type says where in the invocation lifecycle the extra logic belongs. Choosing the wrong type is not a performance sin but a readability sin.

    2. Adding the AOP Dependency

    The dependency name differs between Spring Boot 3 and Spring Boot 4. Add the one matching your Boot line.

    Spring Boot 3.x -> org.springframework.boot : spring-boot-starter-aop
Spring Boot 4.x -> org.springframework.boot : spring-boot-starter-aspectj

    Once the appropriate starter is present, Spring Boot configures the required AOP infrastructure automatically. In a normal Spring Boot application we do not need to manually add @EnableAspectJAutoProxy.

    Golden rule: The starter turns AOP on; the annotations describe what to do. Add the dependency once, then everything afterwards is @Aspect, pointcuts, and advice.

    3. Recommended Package Structure

    The aspect class should normally sit inside the main application package or one of its subpackages, so component scanning can discover it automatically.

    com.coderarmy.aopdemo
|-- AopDemoApplication
|-- controller/StudentController
|-- service/StudentService
|-- repository/StudentRepository
|-- dto/Student
|-- aspect/LoggingAspect

    Two rules of thumb:

    1. Keep the aspect near the code it advises, but in its own aspect package.
    2. Keep everything under the main application package. An aspect outside the scan base package is never registered.

    4. Creating the Target Bean

    A target bean is the ordinary Spring bean whose method we want to intercept. Here it is StudentService.

    package com.coderarmy.aopdemo.service;

import org.springframework.stereotype.Service;

@Service
public class StudentService {

    public String createStudent() {
        System.out.println("Actual createStudent() method executed");
        return "Student created successfully";
    }

    public String getStudent() {
        System.out.println("Actual getStudent() method executed");
        return "Student details";
    }
}

    Here:

    • StudentService is the target class.
    • The Spring-managed StudentService instance is the target object.
    • createStudent() and getStudent() are possible target methods.

    There is no logging, timing, or security code here. That is the point: the business method says only what the business does.

    5. Creating the Aspect Class

    This class contains three important annotations.

    • @Aspect declares that the class contains AOP configuration, such as pointcuts and advice. It tells Spring that this class describes cross-cutting behaviour to apply to selected method executions.
    • @Component registers the aspect as a Spring bean.
    • @Before declares that the advice method must execute before every method matched by its pointcut expression.

    @Aspect describes the role of the class, but does not register it in the Spring container. @Component makes it discoverable through component scanning. This is the most common reason a new aspect "does nothing": it was annotated @Aspect but never became a bean.

    package com.coderarmy.aopdemo.aspect;

import java.util.Arrays;
import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.annotation.Aspect;
import org.aspectj.lang.annotation.Before;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class LoggingAspect {

    @Before("execution(String com.coderarmy.aopdemo.service.StudentService.createStudent())")
    public void logBeforeMethodExecution(JoinPoint joinPoint) {
        System.out.println("Entering method: " + joinPoint.getSignature().getName());
        System.out.println("Arguments: " + Arrays.toString(joinPoint.getArgs()));
    }
}

    The method containing the additional behaviour is the advice. The matched business method is the target method.

    6. Understanding the Pointcut Expression

    The complete string inside @Before is a pointcut expression:

    execution(String com.coderarmy.aopdemo.service.StudentService.createStudent())

    Read from left to right:

    Part Meaning
    execution match a method execution
    String the method must return String
    StudentService the method must belong to this class
    createStudent the method name must be createStudent
    () the method must take no arguments

    A wildcard pointcut generalizes the pattern:

    execution(* com.coderarmy.aopdemo.service.StudentService.*(..))
    • * in the return position: any return type.
    • * in the name position: any method of this class.
    • (..): any number of arguments of any type.

    Interviewer's perspective: Expect "what does (..) mean versus ()?" The answer is any arguments versus zero arguments, and it is the fastest way to show you have actually written a pointcut rather than copied one.

    7. How Advice Executes Automatically: Target Object vs Proxy Object

    StudentService never calls LoggingAspect, yet the advice executes before the service method. Spring makes this possible by placing a proxy object in front of the target object. Conceptually the proxy behaves like a wrapper:

    public String createStudent() {
    loggingAspect.logBeforeMethodExecution();
    return target.createStudent();
}

    Spring's real proxy is more sophisticated, but this is the right model.

    • Target object. Contains the actual business implementation; conceptually the actual StudentService instance.
    • Proxy object. The Spring-generated object that stands in front of the target and intercepts matching method calls. It can run additional behaviour before or after delegating the call to the target.
    Caller -> Proxy -> Advice chain -> Target object

    Are the target and the proxy two different objects? Conceptually yes: Spring may hold a proxy object and a target object behind it. But they are not two ordinary, independently injectable beans. The normal bean name exposes the proxy:

    studentService -> proxy object

    The target sits behind the proxy; the container manages the advised service as one logical bean, while callers interact with the proxy.

    Important: The proxy is why self-invocation is a known AOP trap. A call that never passes through the proxy - for example, a method calling another method on this - never meets the advice.

    8. What Is an Advice? The try-catch-finally Mental Model

    An advice answers one question: what additional logic should run before, after, or around a matched method execution? The advice types can be understood by comparing them with ordinary Java control flow:

    beforeLogic();
try {
    Object result = targetMethod();
    afterReturningLogic(result);
    return result;
} catch (Throwable exception) {
    afterThrowingLogic(exception);
    throw exception;
} finally {
    afterLogic();
}

    Approximate mapping:

    Java control-flow position Spring advice
    Before entering try @Before
    After a successful return @AfterReturning
    Inside catch @AfterThrowing
    Inside finally @After
    The entire surrounding block @Around

    @Around is more powerful than simply combining the other four. It controls whether, when, and how the remaining invocation chain proceeds.

    Mnemonic: "Before enters, Returning succeeds, Throwing fails, After cleans up, Around controls them all." Before the try, after the return, inside the catch, inside the finally, around the whole block.

    9. @Before: Advice Before the Target

    @Before executes before the matched target method begins. Common uses: logging method entry, reading method arguments, checking authorization, checking preconditions, and populating context.

    JoinPoint represents the current intercepted method execution and lets the advice inspect contextual information:

    Method Information returned
    joinPoint.getSignature() method signature information
    joinPoint.getSignature().getName() the method name
    joinPoint.getArgs() arguments passed to the target method
    joinPoint.getTarget() the underlying target object
    joinPoint.getThis() the proxy object currently handling the call

    JoinPoint allows inspection, but does not allow the advice to continue, skip, or repeat the target invocation.

    Can @Before prevent the target method? Not through the API: it has no doNotProceed() because it does not directly control the invocation. But it can throw an exception:

    @Before("execution(* com.coderarmy.aopdemo.service.PaymentService.makePayment(..))")
public void checkAccess() {
    boolean allowed = false;
    if (!allowed) {
        throw new SecurityException("You cannot make this payment");
    }
}

    If the advice throws, execution stops before the target is reached. So @Before cannot directly skip the method and return an alternative result; it can only stop execution by throwing. Use @Around for controlled short-circuiting.

    Can @Before modify method arguments? It can read them with Object[] arguments = joinPoint.getArgs();, but provides no controlled mechanism to replace the arguments used for the target invocation. For replacement use @Around: joinPoint.proceed(modifiedArguments);.

    Interviewer's perspective: The precise answer to "can @Before block a method?" is "no, not by control; only by throwing." Candidates who say "yes, it can return early" have confused @Before with @Around.

    10. @AfterReturning: Advice on Normal Completion

    @AfterReturning executes only when the matched method completes normally: the target returns normally and the advice runs; the target throws and the advice does not run.

    Accessing the returned value. Use the returning attribute to bind the returned value to an advice parameter:

    @AfterReturning(
    pointcut = "execution(* com.coderarmy.aopdemo.service.StudentService.*(..))",
    returning = "result")
public void logReturnedValue(Object result) {
    System.out.println("Method returned: " + result);
}

    The value of returning must match the parameter name. The parameter type also affects matching: String result applies only when the return is compatible with String; for a generic advice use Object. (All five advice types appear together in Section 13.)

    Can @AfterReturning replace the returned value? No. If the advice declares a return value, it is ignored - it does not replace the value returned by the target. Therefore an @AfterReturning method should normally return void.

    What about mutating the returned object? If the target returns a mutable object, the advice gets the same reference and could modify it, e.g. receipt.setStatus("CHANGED BY ASPECT");. Poor design: it hides transformation outside the visible business flow. Use @AfterReturning mainly for observation: logging, a metric, or an audit record. Use @Around to change, wrap, or replace the result.

    What "normal completion" means. If a target method catches an internal exception and returns a fallback, the exception did not escape and the method returned a value, so @AfterReturning executes and @AfterThrowing does not. Advice reacts to how the method exits, not to internal events.

    11. @AfterThrowing: Advice on Exceptional Exit

    @AfterThrowing runs when the matched target method exits by throwing an exception. The exception escapes the method, the advice executes, and the exception continues toward the caller.

    Accessing the exception. Use the throwing attribute to bind the exception to an advice parameter:

    @AfterThrowing(
    pointcut = "execution(* com.coderarmy.aopdemo.service.PaymentService.*(..))",
    throwing = "exception")
public void logException(Throwable exception) {
    System.out.println("Exception type: " + exception.getClass().getSimpleName());
    System.out.println("Exception message: " + exception.getMessage());
}

    The throwing value must match the parameter name.

    Restricting advice to a specific exception type. The parameter type restricts when the advice executes: handleInvalidAmount(IllegalArgumentException exception) runs for IllegalArgumentException and its subclasses, and not for unrelated types.

    Does @AfterThrowing handle the exception? Not automatically. It observes the failed exit, but the original still propagates: target throws, advice logs, original continues, caller receives it. The advice may itself throw, but merely returning from @AfterThrowing does not consume the original failure.

    Can @AfterThrowing return a fallback value? No. The target already completed exceptionally, so the advice's return value is not a recovery result. Use @Around to catch the invocation and convert it into a fallback, carefully: silently swallowing failures can create incorrect behaviour.

    Suitable uses: error logging, failure metrics, failed-operation audit records, alert creation, recording exception type and message, and technical cleanup only on failure.

    12. @After: Finally-style Advice

    @After means after-finally. The name misleads: it does not mean "after successful completion." It behaves like a finally block:

    try {
    targetMethod();
} finally {
    afterAdvice();
}

    It executes whether the target returns or throws; Spring calls it after-finally advice. A typical example is clearContext(), printing "Clearing method context". On success @After executes after the return; on failure it executes after the throw and the exception continues.

    Use @After for logic that must happen regardless of outcome:

    • Clearing contextual data
    • Releasing a lock
    • Generic method-exit logging
    • Removing a ThreadLocal value

    Use @AfterReturning when the returned value is needed. Use @AfterThrowing when the thrown exception is needed. @After is intentionally outcome-neutral.

    13. Comparing the Three After Advices

    Advice Success Failure Direct access to result Direct access to exception
    @AfterReturning Yes No Yes No
    @AfterThrowing No Yes No Yes
    @After Yes Yes No No

    The two contrasts that summarize the family:

    • @After -> success or failure; @AfterReturning -> success only.
    • @After -> every outcome; @AfterThrowing -> failure only.

    The three after advices inside one aspect:

    @Aspect
@Component
public class LoggingAspect {

    @AfterReturning(
        pointcut = "execution(* com.coderarmy.aopdemo.service.StudentService.*(..))",
        returning = "result")
    public void logReturnedValue(Object result) {
        System.out.println("Method returned: " + result);
    }

    @AfterThrowing(
        pointcut = "execution(* com.coderarmy.aopdemo.service.StudentService.*(..))",
        throwing = "exception")
    public void logException(Throwable exception) {
        System.out.println("Exception type: " + exception.getClass().getSimpleName());
    }

    @After("execution(* com.coderarmy.aopdemo.service.StudentService.*(..))")
    public void clearContext() {
        System.out.println("Clearing method context");
    }
}
    Advice Can do Cannot do
    @Before inspect JoinPoint, read arguments, throw to stop skip the target, replace arguments, return a value
    @AfterReturning observe the returned value replace the returned value, run on failure
    @AfterThrowing observe the exception, restrict by type consume the exception, return a fallback
    @After run cleanup on every outcome access the result or the exception
    @Around modify arguments, replace result, skip, repeat, catch (nothing - but the power is easy to misuse)

    14. @Around: The Most Powerful Advice

    @Around surrounds the complete invocation: code before the target, the target, code after. Unlike the other types it controls the target's execution. It can run logic before and after, replace arguments and the result, catch/rethrow/wrap exceptions, skip or repeat the target, and measure duration. Use it only when control is needed.

    Basic @Around syntax:

    @Around("execution(* com.coderarmy.aopdemo.service.StudentService.*(..))")
public Object measureExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
    long startTime = System.nanoTime();
    try {
        return joinPoint.proceed();
    } finally {
        long executionTime = System.nanoTime() - startTime;
        System.out.println(joinPoint.getSignature().getName()
                + " took " + executionTime + " nanoseconds");
    }
}

    Execution flow: enter @Around, run code before proceed(), call proceed(), let the remaining advice and target execute, receive the result, run code after proceed(), return to caller.

    What is ProceedingJoinPoint? Used specifically with @Around, it represents the current intercepted invocation and extends JoinPoint, adding proceed(); and proceed(Object[] arguments);. The core distinction: JoinPoint inspects the invocation; ProceedingJoinPoint inspects and controls it.

    What does proceed() do? Object result = joinPoint.proceed(); continues the remaining interceptor chain and eventually invokes the actual target method. It is not always equivalent to directly calling the business method, because other interceptors or advice may remain:

    First around advice -> proceed() -> Second advice
    -> Security interceptor -> Transaction interceptor -> Actual target method

    So proceed() means: continue to the next step in the current invocation chain.

    When proceed() is not called. The target never executes: the caller reaches the advice, no proceed() runs, the target is skipped, an alternative value is returned. This supports caching, feature flags, access rejection, idempotency, and circuit-breaking - and can make behaviour hard to understand, since the source calls a method the aspect blocks.

    Why return the result of proceed()? If an advice calls joinPoint.proceed(); return null;, then even when the target returns "Payment successful" the caller receives null. What @Around returns is what the caller observes. Normal pattern: Object result = joinPoint.proceed(); return result;. Return something else only to deliberately replace the result.

    Why return Object? A generic aspect may intercept many return types: String, Student, PaymentReceipt, List<Order>, int, boolean, void. So reusable around advice uses public Object advice(...) throws Throwable. Primitives box and a void target yields null. A void advice discards the proceed() value, so the caller sees null.

    Golden rule: Inside @Around, treat proceed() like an ordinary method call you must both invoke and relay. Forget to return its result and you have silently rewritten the target's contract to return null.

    15. Practical Uses of @Around

    Measuring execution time. Timing needs state that exists before and after the same invocation, making @Around natural. Using finally around proceed() records timing on success and failure; without it, a thrown exception skips the duration calculation.

    Exception behaviour inside @Around. proceed() behaves like an ordinary Java call. For "Before"; proceed(); "After";, when the target throws: "Before" prints, proceed() throws, "After" does not print, and the exception propagates. Code after proceed() runs only if the exception is caught or a finally block is used.

    Observing success and failure in one advice. A single @Around can reproduce the lifecycle positions of @Before, @AfterReturning, @AfterThrowing, and @After:

    try {
    Object result = joinPoint.proceed();
    System.out.println("Execution successful");
    return result;
} catch (Throwable exception) {
    System.out.println("Execution failed: " + exception.getMessage());
    throw exception;
} finally {
    System.out.println("Execution completed");
}

    That does not mean @Around should always be used. When only one lifecycle position is required, a narrower advice communicates the intention more clearly.

    Converting an exception into a fallback. Around advice can catch a specific exception and return substitute data, for example new PaymentReceipt("PENDING", "Payment will be retried") on a PaymentGatewayException, so the caller never sees the original exception. Dangerous: callers may think the call succeeded and monitoring may miss the failure. Prefer resilience infrastructure.

    Modifying method arguments. For greetStudent(String name), read Object[] arguments = joinPoint.getArgs();, cast arguments[0] to String, compute originalName.trim().toUpperCase(), and call joinPoint.proceed(modifiedArguments);. Calling greetStudent(" aditya ") makes the target receive ADITYA. The array must stay compatible with parameter types and order.

    Modifying the returned value. After Object originalResult = joinPoint.proceed();, return new ApiResponse<>(true, "Operation completed", originalResult); so the caller gets the wrapper, not the direct result. The replacement must match the target's declared return type or the caller may hit a runtime type error.

    Calling proceed() more than once. Around advice may call proceed() once, many times, or never. Retry calls it again after a temporary exception, so the target may run twice - dangerous for transferMoney(), sendEmail(), and chargeCard(), where duplicates result. Do it only when the operation is safe to retry, idempotent, with a clear policy. Prefer dedicated retry infrastructure.

    Interviewer's perspective: The strongest @Around candidates say when NOT to use it. "Use @Around everywhere because it can do everything" admits you have not debugged a hidden aspect yet.

    16. Choosing the Correct Advice Type and the Complete Invocation Flow

    Requirement Best advice type
    Run logic before a method @Before
    Observe a successful result @AfterReturning
    Observe a failure and access the exception @AfterThrowing
    Run cleanup regardless of outcome @After
    Measure complete execution time @Around
    Replace method arguments @Around
    Replace or wrap the return value @Around
    Skip the method and return another value @Around
    Catch an exception and return a fallback @Around
    Retry the invocation @Around

    Prefer the narrowest suitable advice. The most powerful tool is not always the clearest. Use @Before for pre-execution only; @AfterReturning for success only; @AfterThrowing for failure only; @After for cleanup on every outcome; @Around only when the invocation itself must be controlled. A narrow advice makes the lifecycle obvious and avoids accidental changes.

    Complete invocation flow:

    Caller
  |
  v
Spring proxy
  |
  v
@Around: code before proceed()
  |
  v
@Before
  |
  v
Target method
  |-- Returns normally --> @AfterReturning
  |-- Throws exception  --> @AfterThrowing
  |
  v
@After executes in either case
  |
  v
Control returns to @Around
  |
  v
@Around returns a result or propagates an exception
  |
  v
Caller

    The ordering becomes more nuanced with several aspects and interceptors, but this flow is the correct conceptual foundation for each advice type.

    Important: Advice reacts to how the method exits, not to what happened internally. That sentence answers most "which advice runs?" questions correctly.

    17. Myth vs Reality

    Myth Reality
    "@After runs only when the method succeeds" @After is after-finally advice; it runs on success and failure.
    "@AfterReturning can change the returned value" The advice's return value is ignored; it should return void. Use @Around to replace or wrap.
    "@AfterThrowing handles the exception" It observes the failed exit; the original exception still propagates unless @Around catches it.
    "@Before can change method arguments" It can read them, but cannot replace them. Use @Around.
    "proceed() equals calling the target directly" It continues the remaining advice/interceptor chain and only eventually reaches the target.
    "@Around must always call proceed()" Skipping proceed() is exactly how caching, feature flags, and short-circuiting are built.
    "Calling proceed() twice is harmless" It may invoke the target twice; dangerous for side-effecting operations such as transferMoney().
    "Normal completion means no exception occurred" It means no exception escaped; an internally caught exception still counts as normal completion.

    18. Common Trap Questions

    Trap 1 - "@AfterReturning can replace the returned value." Verdict: False. The advice's return value is ignored; an @AfterReturning method should normally return void. Use @Around when the caller must receive a changed value.

    Trap 2 - "@AfterThrowing handles the exception." Verdict: False. It observes the failed exit, but the original exception keeps propagating toward the caller. Only @Around can catch and replace it.

    Trap 3 - "@After runs only when the method succeeds." Verdict: False. @After behaves like a finally block and runs on success and failure. That is why it is called after-finally advice.

    Trap 4 - "@Before can block the target with doNotProceed()." Verdict: False. JoinPoint has no such operation; @Before can only stop execution by throwing. Controlled skipping belongs to @Around.

    Trap 5 - "proceed() is the same as calling the target method directly." Verdict: False. proceed() continues the remaining interceptor chain, which may still contain advice, security, or transaction interceptors before the target.

    Trap 6 - "A method that catches its own exception is treated as failing." Verdict: False. Advice reacts to how the method exits. If the exception does not escape, @AfterReturning runs and @AfterThrowing does not.

    Trap 7 - "Calling proceed() twice is always safe." Verdict: False. It may invoke the target twice. Acceptable only for safe-to-retry, idempotent operations with a clearly defined retry policy.

    19. Points to Remember

    1. Advice is the additional behaviour applied to matched method executions; a pointcut expression decides which methods are matched.
    2. Add spring-boot-starter-aop (Boot 3.x) or spring-boot-starter-aspectj (Boot 4.x); Boot then configures AOP without @EnableAspectJAutoProxy.
    3. An aspect needs both @Aspect and @Component; @Aspect describes the role, @Component registers the bean.
    4. Spring normally exposes a proxy in place of the original target object; callers talk to the proxy, the target hides behind it.
    5. Map the five advice types to try-catch-finally: @Before before try, @AfterReturning after normal return, @AfterThrowing in catch, @After in finally, @Around around the whole block.
    6. @Before can inspect a JoinPoint and read arguments, but cannot skip the target or replace arguments; it can only stop execution by throwing.
    7. @AfterReturning runs only on normal completion, reads the returned value via returning, cannot replace it, and should return void.
    8. @AfterThrowing runs only when an exception escapes the target, can restrict by exception type, and does not consume the exception or return a fallback.
    9. @After is outcome-neutral cleanup; @Around uses ProceedingJoinPoint.proceed() to inspect and control the invocation, including skipping, repeating, and replacing arguments or results.
    10. Prefer the narrowest advice that correctly expresses the requirement; @Around is the most powerful and easiest to misuse.

    20. Likely Interview Questions

    Question Crisp Answer
    What are the five advice types in Spring AOP? @Before, @AfterReturning, @AfterThrowing, @After, and @Around.
    Which dependency enables AOP in Spring Boot? spring-boot-starter-aop for Boot 3.x; spring-boot-starter-aspectj for Boot 4.x.
    Why does an aspect need both @Aspect and @Component? @Aspect marks it as AOP configuration; @Component makes it a bean so scanning registers it.
    When does @AfterReturning run? Only when the target method completes normally without letting an exception escape.
    Can @AfterReturning change the returned value? No; its return value is ignored, so it should return void. Use @Around to replace or wrap.
    When does @AfterThrowing run? Only when the target exits by throwing an exception; the exception still propagates.
    How do you restrict @AfterThrowing to one exception type? Declare the advice parameter as that type; it then runs for it and compatible subclasses only.
    Difference between @After and @AfterReturning? @After runs on success and failure (finally); @AfterReturning runs on success only.
    Why is @Around the most powerful advice? It controls the invocation: modify arguments, replace the result, skip, repeat, catch, and measure.
    What does ProceedingJoinPoint.proceed() do? Continues the remaining interceptor chain and eventually invokes the actual target method.
    What if @Around does not call proceed()? The target never executes; the advice returns an alternative value (caching, rejection, circuit-breaking).
    Why does a generic @Around return Object? It may intercept methods with many return types; primitives are boxed and void becomes null.

    • Aspect registration needs @Aspect plus @Component; the proxy is what makes advice run without an explicit call.
    • @Before and the three after advices are observational; @Around is the control point.
    • @After is finally semantics, so it runs no matter how the method exits.
    • proceed() continues the remaining chain, its result must be relayed, and skipping it skips the target.
    • The narrowest advice that expresses the requirement is the correct one.

    One-line takeaway: the five advice types are five labelled positions around a method call - @Before, @AfterReturning, @AfterThrowing, @After, and @Around - and the whole skill is picking the narrowest one that says exactly where the extra logic belongs.
