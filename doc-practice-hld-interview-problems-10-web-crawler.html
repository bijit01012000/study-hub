    Design a Web Crawler

    3 sections · 3,415 words

    Three levels: Level 1 — The Shape, Level 2 — The Defence, Level 3 — The Edges.

    Level 1 — The Shape (Foundation)

    Pacing: 3 min ask · 5 min trace flow · 7 min read why.

    The Ask

    Functional

    • Given seed URLs, fetch pages
    • Extract links; queue new URLs
    • Never re-crawl a fetched URL
    • Respect robots.txt + politeness
    • Store content — indexing out of scope

    Non-Functional

    • Graph is unbounded ← forces disk-backed frontier
    • Never overwhelm one domain ← forces per-domain limits
    • Never re-fetch a crawled URL ← forces a scalable seen-check
    • Prioritize fresh content ← forces priority, not FIFO
    • Fetches can hang or fail ← forces timeouts + backoff

    Agree These First

    5,000 pages/s sustained fetch rate · ~50 links discovered per page · ~90% of discovered links already seen · 10B distinct URLs seen so far. Round, illustrative numbers, not any named company's.

    The Shape

    Components and flow:

    • Seed URLs — One-time input, not a persistent actor
    • Frontier — Priority-ordered queue · disk-backed, not RAM
    • Fetcher — Pulls a URL, issues the HTTP request
    • Target Servers — The open web — not ours, for context; fetch ⇄ response
    • Parser — Extracts links & content from the page
    • Dedup Check — Checks each link against what's already seen
    • Content Store — Fetched page content — indexing is out of scope
    • new URL → back into Frontier — the loop closes

    Data model: frontier url PK → priority, domain.

    50 checks / fetch · ≈90% already seen · discarded.

    Line = crawl flow: FETCH · discover & fetch; LOOP · new URL → Frontier.

    Say It Like This

    "Given seed URLs, I'd run a loop — a Frontier of URLs to fetch, Fetch workers that pull from it, a Parser that extracts links, and a dedup check before anything new goes back into the Frontier. At ten billion URLs seen, I wouldn't store an exact set — I'd use a bloom filter, because exact hashes don't fit in memory at this scale. And I'd never fetch more than one thing at a time from the same domain — that's not optional, it's how you avoid getting blocked."

    Defend It

    Decision Prefer Avoid
    (1) Priority frontier Priority-ordered queue — spends budget on valuable URLs first Pure FIFO — wastes budget on whatever was found first
    (2) Fetch timeout Timeout + retry-with-backoff — a slow server can't hold a worker forever No timeout — one hung server drains the whole pool
    (4) Seen-set Bloom filter — ≈12 GB at 10B URLs, ~7× smaller than exact Exact hash set — 80 GB, and it only grows

    Capacity Math

    Quantity Derivation Value
    Fetch rate assumed, sustained across the fleet 5,000 /s
    Links found 5,000 × 50 discovered/page 250,000 /s
    Check ratio 250,000 ÷ 5,000 — checks per fetch 50 : 1
    New to frontier 250,000 × 10% not-yet-seen 25,000 /s
    Exact seen-set 10B URLs × 8 B/hash — naive 80 GB
    Bloom seen-set 10B × ~9.6 bits/item @ 1% FP rate ≈12 GB
    Frontier size 1B queued × ~200 B/entry, illustrative ≈200 GB

    50 : 1 is the headline number. Every fetch you complete triggers roughly fifty "have we seen this?" checks — that ratio, not the fetch rate itself, is what the seen-set has to survive.

    Before You Draw Anything — The Four Moves

    1. Clarify, don't assume. General-purpose crawler or scoped to a domain set? Say general-purpose — it's the harder, more interesting case. Is indexing in scope? No, that's a different sheet's job. — Two minutes of questions buys the whole design.
    2. Agree the scale out loud. "5,000 pages/s, 10 billion URLs seen, ~90% of links already known." Now every later choice has a reason. — An unstated number is an undefendable design.
    3. Draw the happy path only. Frontier → Fetcher → Parser → Dedup, and back into Frontier. Get agreement before adding anything. — Boxes you add before agreement are boxes you'll defend alone.
    4. Name one trade-off unprompted. "I'd use a bloom filter for the seen-set, not an exact set, because storing every hash exactly doesn't fit in memory at this scale." — This is the single move that separates L1 from a junior answer.

    What L1 Is Testing

    • Do you reach for a bloom filter unprompted, or assume exact storage?
    • Do you separate "have we seen this" from "should we crawl this next"?
    • Did you ask whether this is one domain or the whole web?

    The Follow-Ups That Decide It

    1. You've seen 10 billion URLs. How do you check if a new one is a duplicate without storing all 10 billion exactly? What does a false positive cost? (ref 4 — tests: the structure, and that an FP means a page never crawled)
    2. Why not just have one global rate limit for the whole crawl? (ref 6 — tests: per-domain politeness awareness, and can they name what breaks without it)
    3. A calendar page links to "next month" forever. What happens to your crawler? (ref 11 — tests: crawl-trap awareness, not a hand-wave)

    At L1 you are being judged on one thing: can you produce a coherent shape and defend three choices inside it. Depth is page 2 — do not reach for it here. Ghosted boxes are what arrives next; you should be able to guess two of them.

    Level 2 — The Defence (Intermediate)

    Pacing: 5 min ask · 15 min trace flow · 10 min read why · 30 min cover & answer.

    The Ask

    Functional

    • Given seed URLs, fetch pages
    • Extract links; queue new URLs
    • Never re-crawl a fetched URL
    • Respect robots.txt + politeness
    • Store content — indexing out of scope

    Non-Functional

    • Graph is unbounded ← forces disk-backed frontier
    • Never overwhelm one domain ← forces per-domain limits
    • Never re-fetch a crawled URL ← forces a scalable seen-check
    • Prioritize fresh content ← forces priority, not FIFO
    • Fetches can hang or fail ← forces timeouts + backoff

    Out of Scope — Say It Aloud

    • Indexing, ranking, search
    • Rendering JS-heavy pages
    • Moderation / takedowns

    Agree These First

    5,000 pages/s sustained fetch rate · ~50 links discovered per page · ~90% of discovered links already seen · 10B distinct URLs seen so far. Round, illustrative numbers, not any named company's.

    The Shape

    Components and flow:

    • Seed URLs — One-time input, not a persistent actor
    • (1) Frontier — Priority-ordered queue · disk-backed, not RAM; ≈1B URLs queued · ≈200 GB
    • (2) Fetcher — Pulls a URL, issues the HTTP request
    • robots.txt Cache — Fetched & cached per domain, TTL'd; robots.txt allowed?
    • Target Servers — The open web — not ours, for context; fetch ⇄ response
    • (6) Politeness Queue — Per-domain gate, checked before every request; mirrors Sheet 5's Gatekeeper, reversed
    • (3) Parser — Extracts links & content from the page
    • (4) Dedup Check — Checks each link against what's already seen; Bloom filter · ≈12 GB @ 10B URLs
    • (5) Content Store — Fetched page content — indexing is out of scope
    • new URL → back into Frontier — the loop closes

    Data model:

    • frontier url PK · priority · domain · discovered_at
    • seen_set bloom filter — membership only, no rows
    • pages url PK · content_hash · fetched_at · content_ref

    Line = crawl flow: FETCH · discover & fetch; LOOP · new URL → Frontier; ASYNC · off critical path.

    Say It Like This

    "Given seed URLs, I'd run a loop — a Frontier of URLs to fetch, Fetch workers that pull from it, a Parser that extracts links, and a dedup check before anything new goes back into the Frontier. At ten billion URLs seen, I wouldn't store an exact set — I'd use a bloom filter, because exact hashes don't fit in memory at this scale. And I'd never fetch more than one thing at a time from the same domain — that's not optional, it's how you avoid getting blocked."

    Defend It

    Decision Prefer Avoid
    (1) Priority frontier Priority-ordered queue — spends budget on valuable URLs first Pure FIFO — wastes budget on whatever was found first
    (2) Fetch timeout Timeout + retry-with-backoff — a slow server can't hold a worker forever No timeout — one hung server drains the whole pool
    (4) Seen-set Bloom filter — ≈12 GB at 10B URLs, ~7× smaller than exact; a false positive costs you a page you never crawled — size the filter to the loss you accept Exact hash set — 80 GB, and it only grows
    (6) Politeness queue Per-domain, centralized — mirrors Sheet 5's Gatekeeper One global limit — hammers small sites, spares big ones
    (7) robots.txt cache Fetch once per domain, TTL'd — checked before every page Every request — doubles calls, breaks politeness itself

    Capacity Math

    Quantity Derivation Value
    Fetch rate assumed, sustained across the fleet 5,000 /s
    Links found 5,000 × 50 discovered/page 250,000 /s
    Check ratio 250,000 ÷ 5,000 — checks per fetch 50 : 1
    New to frontier 250,000 × 10% not-yet-seen 25,000 /s
    Exact seen-set 10B URLs × 8 B/hash — naive 80 GB
    Bloom seen-set 10B × ~9.6 bits/item @ 1% FP rate ≈12 GB
    Frontier size 1B queued × ~200 B/entry, illustrative ≈200 GB
    Savings 80 GB exact ÷ 12 GB bloom ≈6.7×

    Storage isn't the constraint — the access pattern is. 80 GB of exact hashes fits on one box; the problem is answering 10B+ membership checks a second, and a bloom filter answers them ~7× smaller.

    What Breaks — Say It Before They Ask

    • (11) Crawl trap. Infinite calendar pagination or session IDs create an effectively infinite branch of the graph. — Fix: per-domain depth limits, and flag a domain generating URLs far faster than any real site would
    • (6) Politeness violated, IP blocked. Each worker enforcing the limit only locally under-enforces it — a site sees a burst of concurrent requests. — Fix: the politeness queue must be centralized across the fleet, not per-worker-local — the exact lesson of Sheet 5's "local counting under-enforces"
    • (2) Fetcher hangs on a slow server. Without a timeout, one slow server ties up a worker indefinitely. — Fix: strict per-fetch timeouts; a timeout means retry-with-backoff, not blocking forever

    The Follow-Ups That Decide It

    1. You've seen 10 billion URLs. How do you check if a new one is a duplicate without storing all 10 billion exactly? What does a false positive cost? (ref 4 — tests: the structure, and that an FP means a page never crawled)
    2. Why not just have one global rate limit for the whole crawl? (ref 6 — tests: per-domain politeness awareness, and can they name what breaks without it)
    3. A calendar page links to "next month" forever. What happens to your crawler? (ref 11 — tests: crawl-trap awareness, not a hand-wave)
    4. A server takes 90 seconds to respond. What happens to the fetcher that's waiting on it? (ref 2 — tests: timeout / non-blocking awareness)
    5. Two different URLs serve nearly-identical content. Does your crawler notice? (ref 9 — tests: URL-based dedup is not the same as content-based dedup)

    Cover The Sheet · Answer Aloud

    Use it as revision: cover the right rail and the two panels to your left, then walk the numbered path out loud. If you cannot say why a box is there and what breaks it, that box is your gap.

    Level 3 — The Edges (Advanced)

    Pacing: 10 min ask · 25 min trace flow · 15 min read why · 40 min cover & answer.

    The Ask

    Functional

    • Given seed URLs, fetch pages
    • Extract links; queue new URLs
    • Never re-crawl a fetched URL
    • Respect robots.txt + politeness
    • Store content — indexing out of scope

    Non-Functional

    • Graph is unbounded ← forces disk-backed frontier
    • Never overwhelm one domain ← forces per-domain limits
    • Never re-fetch a crawled URL ← forces a scalable seen-check
    • Prioritize fresh content ← forces priority, not FIFO
    • Fetches can hang or fail ← forces timeouts + backoff

    Out of Scope — Say It Aloud

    • Indexing, ranking, search
    • Rendering JS-heavy pages
    • Moderation / takedowns

    Agree These First

    5,000 pages/s sustained fetch rate · ~50 links discovered per page · ~90% of discovered links already seen · 10B distinct URLs seen so far. Round, illustrative numbers, not any named company's.

    The Shape

    Components and flow:

    • Seed URLs — One-time input, not a persistent actor
    • (1) Frontier — Priority-ordered queue · disk-backed, not RAM; ≈1B URLs queued · ≈200 GB
    • (2) Fetcher — Pulls a URL, issues the HTTP request
    • robots.txt Cache — Fetched & cached per domain, TTL'd; robots.txt allowed?
    • Target Servers — The open web — not ours, for context; fetch ⇄ response
    • (6) Politeness Queue — Per-domain gate, checked before every request; mirrors Sheet 5's Gatekeeper, reversed
    • (3) Parser — Extracts links & content from the page
    • (4) Dedup Check — Checks each link against what's already seen; Bloom filter · ≈12 GB @ 10B URLs
    • (5) Content Store — Fetched page content — indexing is out of scope
    • (9) Near-Dup Detector — Content fingerprint — same content, different URL
    • (8) Trap Detector — Flags a domain generating URLs too fast
    • (10) Priority Scorer — Freshness/value score orders the queue
    • (11) Recrawl Scheduler — Re-queues crawled URLs to catch changes; recrawl: re-queue, freq ~ change rate
    • (12) Sharded storage — frontier & seen-set sharded by domain hash
    • new URL → back into Frontier — the loop closes

    Data model:

    • frontier url PK · priority · domain · discovered_at
    • seen_set bloom filter — membership only, no rows
    • pages url PK · content_hash · fetched_at · content_ref

    Line = crawl flow: FETCH · discover & fetch; LOOP · new URL → Frontier; ASYNC · off critical path.

    Say It Like This

    "Given seed URLs, I'd run a loop — a Frontier of URLs to fetch, Fetch workers that pull from it, a Parser that extracts links, and a dedup check before anything new goes back into the Frontier. At ten billion URLs seen, I wouldn't store an exact set — I'd use a bloom filter, because exact hashes don't fit in memory at this scale. And I'd never fetch more than one thing at a time from the same domain — that's not optional, it's how you avoid getting blocked."

    Defend It

    Decision Prefer Avoid
    (1) Priority frontier Priority-ordered queue — spends budget on valuable URLs first; order comes from the Priority Scorer, not a static rule Pure FIFO — wastes budget on whatever was found first
    (2) Fetch timeout Timeout + retry-with-backoff — a slow server can't hold a worker forever No timeout — one hung server drains the whole pool
    (4) Seen-set Bloom filter — ≈12 GB at 10B URLs, ~7× smaller than exact; a false positive costs you a page you never crawled — size the filter to the loss you accept Exact hash set — 80 GB, and it only grows
    (6) Politeness queue Per-domain, centralized — mirrors Sheet 5's Gatekeeper One global limit — hammers small sites, spares big ones
    (7) robots.txt cache Fetch once per domain, TTL'd — checked before every page Every request — doubles calls, breaks politeness itself
    (12) Sharded storage Disk-backed, sharded by domain hash — ≈200 GB + ≈12 GB All in memory, one machine — breaks when either outgrows RAM
    (9) Content fingerprint Fingerprint the content — catches mirrors, tracking-param variants URL-only dedup — two URLs, one page, both get crawled
    (10) Recrawl scheduler Periodic re-queue, freq ~ change rate — catches staleness Crawl once, never revisit — content goes stale, unnoticed

    Capacity Math

    Quantity Derivation Value
    Fetch rate assumed, sustained across the fleet 5,000 /s
    Links found 5,000 × 50 discovered/page 250,000 /s
    Check ratio 250,000 ÷ 5,000 — checks per fetch 50 : 1
    New to frontier 250,000 × 10% not-yet-seen 25,000 /s
    Exact seen-set 10B URLs × 8 B/hash — naive 80 GB
    Bloom seen-set 10B × ~9.6 bits/item @ 1% FP rate ≈12 GB
    Frontier size 1B queued × ~200 B/entry, illustrative ≈200 GB
    Savings 80 GB exact ÷ 12 GB bloom ≈6.7×
    Shards ≈200 GB frontier ÷ ~50 GB/node, illustrative ≈4+ nodes

    Both the frontier (≈200 GB) and the seen-set (≈12 GB) outgrow one machine's comfortable RAM at this scale — both get sharded, typically by domain hash, which also keeps one domain's URLs together for the politeness check.

    What Breaks — Say It Before They Ask

    • (11) Crawl trap. Infinite calendar pagination or session IDs create an effectively infinite branch of the graph. — Fix: per-domain depth limits, and flag a domain generating URLs far faster than any real site would
    • (6) Politeness violated, IP blocked. Each worker enforcing the limit only locally under-enforces it — a site sees a burst of concurrent requests. — Fix: the politeness queue must be centralized across the fleet, not per-worker-local
    • (2) Fetcher hangs on a slow server. Without a timeout, one slow server ties up a worker indefinitely. — Fix: strict per-fetch timeouts; a timeout means retry-with-backoff, not blocking forever
    • (4) Bloom filter false-positive rate creeping up. An undersized filter's FP rate rises as the seen-set grows, and the crawler starts silently skipping URLs it never fetched. — Fix: size for the final n — a Bloom filter cannot be resized
    • (10) Content never re-crawled, goes stale. A page fetched once and never revisited eventually has dead links or outdated content. — Fix: a recrawl scheduler that re-queues at a frequency proportional to how often that page tends to change

    The Follow-Ups That Decide It

    1. You've seen 10 billion URLs. How do you check if a new one is a duplicate without storing all 10 billion exactly? What does a false positive cost? (ref 4 — tests: the structure, and that an FP means a page never crawled)
    2. Why not just have one global rate limit for the whole crawl? (ref 6 — tests: per-domain politeness awareness, and can they name what breaks without it)
    3. A calendar page links to "next month" forever. What happens to your crawler? (ref 11 — tests: crawl-trap awareness, not a hand-wave)
    4. A server takes 90 seconds to respond. What happens to the fetcher that's waiting on it? (ref 2 — tests: timeout / non-blocking awareness)
    5. Two different URLs serve nearly-identical content. Does your crawler notice? (ref 9 — tests: URL-based dedup is not the same as content-based dedup)
    6. You crawled a page a year ago. Is it still accurate today? (ref 10 — tests: recrawl/freshness awareness, not treating a single crawl as permanently done)
