    State

    11 sections · 843 words

    Behavioural · Design Patterns · Pattern 09 of 12

    Intent

    Give each mode its own class behind a state interface, so per-state behaviour is polymorphism instead of a switch repeated in every method.

    When To Use It

    The Signs

    • A big switch (state) repeated in every method.
    • Boolean flags checked together: isPaid, isShipped, isCancelled.
    • Illegal transitions slip through; nothing centralises them.
    • Behaviour depends entirely on "what mode am I in right now".

    Don't Bother If

    • Two states and one flag says it all.
    • The state never changes after construction.
    • Per-state differences are one line each and won't grow.
    • A plain enum + transition table is enough; nobody needs per-state behaviour.

    Before

    class VendingMachine {
    private Mode mode = IDLE;
    // a plain enum
    void insertCoin(Coin c) {
        switch (mode) {
        case IDLE -> {
            bank.hold(c); mode = HAS_MONEY; }
        case DISPENSING -> refund(c); // wrong moment
        case OUT_OF_STOCK -> refund(c);
        }
    }
}

Product selectSlot(String code) {
    return switch (mode) {
        // ladder #2
    case IDLE -> throw new IllegalStateException();
    case HAS_MONEY -> vend(code);
    default -> throw new IllegalStateException();
    };
}
void dispense() { switch (mode) { /* #3 */ } }
// a new state edits every method

    Switch in every method, and the same ladder in selectSlot() and dispense().

    After

    interface MachineState {
    void insertCoin(Coin c);
    Product selectSlot(String code);
}
class IdleState implements MachineState {
    private final VendingMachine m;
    IdleState(VendingMachine m) { this.m = m; }
    public void insertCoin(Coin c) {
        m.bank.hold(c); m.setState(new HasMoneyState(m));
    }
    public Product selectSlot(String s) {
        throw new IllegalStateException("insert coin first"); }
}
// HasMoneyState, DispensingState: same shape
class VendingMachine {
    private MachineState state = new IdleState(this);
    void insertCoin(Coin c) { state.insertCoin(c); }
    Product selectSlot(String c) { return state.selectSlot(c); }
    void setState(MachineState s) { state = s; }
}
// add a state = add a class. the machine stays put.

    Structure

    «INTERFACE»

    + selectSlot(code)

    the events, as methods

    holds one

    never switches on state

    each state sets the next
    reject

ADD A STATE = ADD A CLASS. NO SWITCH TO EDIT

    How It's Built (3 Steps)

    1. A State interface with the events as methods. insertCoin(Coin), selectSlot(String).
    2. One class per state. Each handles the events it allows, rejects the rest, and moves the context to the next state.
    3. The context holds a state field and forwards every call to it. No switch, no instanceof.

    Quick Check

    List the states and, for each event, what happens. If most cells differ and some read not allowed, that grid is a State machine.

    In The Interview

    "The machine is Idle, HasMoney or Dispensing. insertCoin and selectSlot mean different things in each, so I make each a class implementing MachineState. The machine just delegates and each state sets the next. An illegal call throws instead of silently doing nothing."

    How It's Different

    From The Lookalikes

    Vs Strategy. Both hold a swappable object behind an interface. With Strategy, someone outside picks it once and it stays. With State, the object switches itself as events happen.

    Vs if / else on flags. That is exactly what State replaces. Flags let you reach impossible combinations; a state object cannot.

    Vs enum + transition table. A table is data: from-state, event, to-state. State is polymorphism: each state is a class with its own behaviour. Good when the states do different work, not just move.

    Vs a hierarchical FSM. When states share a lot, an HSM nests them so common handling lives in a parent state. Plain State is the flat version.

    They Say: "add an OutOfService state"

    • With it: one OutOfServiceState where every method throws or refunds. Nothing else changes.
    • Without: a new case in every switch, and a new flag to keep consistent with the others.

    Watch Out For

    • Decide who creates the next state: the current state (m.setState(new HasMoneyState(m))) or a table the context owns. Be consistent.
    • If states hold no per-instance data, make them once and share them (flyweight).
    • Do not hand each state the whole context. Pass only what it needs, or the two are tangled again.
    • Entry and exit actions (start a timer on entering Dispensing) belong in the state's transition, not scattered in the context.
    • If states share most handling, reach for a hierarchical state machine before you copy-paste across state classes.
