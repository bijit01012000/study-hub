    Design a Digital Wallet

    15 sections · 1,987 words

    LLD Design Problems, problem 14 of 20.

    The Ask

    Build

    • Users, each with a Wallet holding a balance.
    • Top-up, withdraw, and transfer wallet to wallet.
    • Every transfer writes two ledger entries: a debit and a credit, equal size.
    • balance = the sum of a wallet's entries.
    • A transfer commits both legs or neither.
    • A retried request with the same requestId applies once.
    • A Transaction moves PENDING to COMPLETED or FAILED.
    • A completed one can be REVERSED by a compensating pair.
    • Money is integer paise, never a float.

    Skip

    • KYC, onboarding, tiers.
    • Real bank / UPI rails.
    • Fraud ML, risk scoring.
    • Interest, cashback, rewards.
    • Statement rendering, crypto.
    • A database, login.

    Our Model

    One service, many wallets, one double-entry ledger. A WalletService owns the wallets and the append-only Ledger; a Transaction is the command that applies and reverses itself.

    Actors and classes

    • User — id, wallet: Wallet. Sends, tops up, withdraws, undoes.
    • WalletService (singleton) — wallets: Map<String, Wallet>, ledger: Ledger, seen: Map<String, String> (requestId to txnId), fee: FeePolicy, alerts: NotificationChannel; transfer(String from, String to, int amount, String requestId): Transaction, topUp(String walletId, int amount, String requestId): Transaction, reverse(String txnId): Transaction, balance(String walletId): int, withdraw(String walletId, int amount, String requestId): Transaction. A seen requestId returns its Transaction.
    • TopUpSource (interface, seam) — pull(String ref, int amount): boolean. The bank / card / UPI seam, mocked. CardRail, UpiRail, NetBankingRail, BankRail.
    • Wallet — id: String, owner: String, cached: int (paise, kept in step); balance(): int, entries(): List<Entry>. The lock is ordered by id.
    • Ledger — entries: List<LedgerEntry>; append(LedgerEntry a, LedgerEntry b), entriesOf(String walletId), txn(String txnId). Append only: two rows or none, never update or delete.
    • LedgerEntry (value) — txnId, walletId, at: Instant, delta: int (signed: +credit, -debit).
    • Transaction — id, from, to, amount: int, requestId, createdAt: Instant, state: TxnState; apply(Ledger l), reverse(Ledger l). A command: applies and reverses itself.
    • TxnState (interface) — onComplete(): TxnState, onFail(): TxnState, onReverse(): TxnState. Each state returns the next; a bad move throws. PendingState is the live one.
    • FeePolicy (interface) — feeFor(String from, String to, int amount): int. The cut on a transfer; never touches the ledger.
    • NotificationChannel (interface) — onEntry(String walletId, Transaction t). SmsChannel, PushChannel, StatementLog. Observer fired after the pair commits.

    Relationships

    WalletService owns 1..* wallets and one ledger. A Wallet derives from its entries. A Transaction owns its entries.

    The four states

    • PENDING -> complete -> COMPLETED.
    • PENDING -> fail -> FAILED.
    • COMPLETED -> reverse -> REVERSED.
    • FAILED and REVERSED are terminal.

    The three fee rules

    • FreeP2PFee -> 0 between wallets.
    • FlatFee -> 200 paise per transfer.
    • PercentFee -> 0.5 percent of amount, capped.

    Key operations

    1. transfer(String from, String to, int amount, String requestId): Transaction — A seen requestId returns its Transaction, no new rows, claimed under the lock, so concurrent retries collapse. Else locks both wallets low id first, checks balance(from) >= amount under the lock, appends the debit and credit as one pair, marks it COMPLETED.
    2. balance(String walletId): int — the sum of the wallet's ledger deltas, or a cached column written in the same commit as the entries. Integer paise, never a float.
    3. reverse(String txnId): Transaction — only a COMPLETED txn. Appends the mirror pair (credit the sender, debit the receiver) under its own new txnId referencing the original, and marks that original REVERSED. Never deletes a row. A second call throws.
    4. topUp(String walletId, int amount, String requestId): Transaction — pulls from a TopUpSource, then credits the wallet with the matching debit on a house external wallet, so the sum stays zero. Idempotent on requestId.

    The transactions and entries

    • transfer -> ledger.append(entry(t,from,-amt), entry(t,to,+amt)) — atomic.
    • balance(w) -> sum of delta for every entry where wallet == w.
    • Consistency check -> sum of delta over all entries == 0 — the check that never drifts.

    Recall drill: cover the operations column, write the four with their guarantee. Most people forget transfer returns the same txn on a retry, and that reverse appends rather than deletes.

    The One Run to Hold in Your Head

    Wallet A holds Rs 1,000, wallet B holds Rs 200. A sends Rs 500 to B with requestId R1. The reply is lost and the client retries R1. What rows sit in the ledger, what are balance(A) and balance(B), and which objects touched the request?

    Opening: A 1000, B 200. T1 debits A -500 and credits B +500, so balance(A) = 500, balance(B) = 700. The retry finds seen maps R1 to T1, returns Transaction T1 and appends 0 new rows.

    The Change

    They ask for a daily cap or a per-transfer limit. Pull the check out of transfer into a SpendingLimitPolicy the service asks before it locks the wallets. Per-wallet and per-tier caps drop in, the transfer path never reopens. Strategy, the seam this pattern is built for.

    What the Picture Can't Show

    The atomic pair. transfer appends the debit and the credit in one ledger.append under both wallet locks, so no instant exists where only one leg is written. reverse appends the mirror pair and marks the txn REVERSED; no row is ever updated or deleted.

    If They Make You Code It

    Transfer and reverse, the whole thing:

    class WalletService {                          // one node, one ledger
    final Map<String,Wallet> wallets;
    final Ledger ledger;
    final Map<String,String> seen;             // requestId -> txnId

    Transaction transfer(String from, String to,
                         int amount, String requestId) {
        String prior = seen.get(requestId);    // fast path
        if (prior != null) return ledger.txn(prior);   // replay
        Wallet a = wallets.get(from), b = wallets.get(to);
        boolean fl = from.compareTo(to) < 0;   // fixed order
        Wallet lo = fl ? a : b, hi = fl ? b : a;
        synchronized (lo) { synchronized (hi) {
            prior = seen.get(requestId);       // re-check INSIDE
            if (prior != null) return ledger.txn(prior);
            if (balance(from) < amount)
                throw new InsufficientFunds(from);     // under lock
            Transaction t =
                new Transaction(from, to, amount, requestId);
            ledger.append(new Entry(t.id(), from, -amount),
                          new Entry(t.id(), to, +amount));
            t.complete();                      // PENDING -> COMPLETED
            seen.put(requestId, t.id());       // retries now replay
            return t;
        }}
    }

    Transaction reverse(String txnId) {
        Transaction t = ledger.txn(txnId);
        if (t.state() != COMPLETED)
            throw new NotReversible(txnId);    // only once
        lockPair(t.from(), t.to());            // same id order
        Transaction r = t.mirror();            // NEW id, refs txnId
        ledger.append(new Entry(r.id(), t.to(), -t.amount()),
                      new Entry(r.id(), t.from(), +t.amount()));
        t.markReversed();                      // appends, never deletes
        return r;
    }
}

    The Four Hazards

    1. Half a transfer. Written as two commits: the debit lands, then the credit throws or the process dies. Money is destroyed and there is no undo. append(debit, credit) is one write under both locks — both rows or none.
    2. Two debits, one balance. Two transfers read balance 500, both pass the check, both append -500, the wallet goes to -500. Lock the wallet, check balance then append under the same lock.
    3. A retry with no requestId. The client resends after a timeout. With no idempotency key the service appends a second pair and the money moves twice. The requestId is mandatory; reject a transfer that arrives without one.
    4. Lock-ordering deadlock. A to B grabs A then waits for B; B to A grabs B then waits for A. Both stall forever. Always lock the lower wallet id first, so both threads take the same wallet first.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. seen.get(requestId) is re-read inside the lock — two concurrent retries of one requestId cannot both append a pair.
    2. lo then hi by id order — A to B and B to A cannot deadlock.
    3. ledger.append(debit, credit) is one call — both entries land or neither, the sum stays 0.

    Tracking a Wallet Balance

    Approach Read cost Source of truth On a bug Write cost Dispute / audit
    Cached balance column O(1) the column, must not drift balance wrong silently update column in same commit replay entries to check
    Ledger sum + snapshot (the default) O(entries since snapshot) the entries wrong only back to last snapshot append + a snapshot job entries + snapshots
    Fold the ledger (event-sourced) O(entries) the entries always correct nothing extra entries are the ledger

    Ledger sum plus a periodic snapshot row. The snapshot bounds read cost, the entries stay the source of truth. A cached column is fine on a single store only if it is written in the same transaction as the pair and a sweeper reconciles it.

    Rejection Signals

    These end the interview:

    • Moving money with from.balance -= x; to.balance += x and no ledger — nothing to reconcile or dispute against.
    • Appending the debit, then the credit, as two separate commits — a crash between them destroys money.
    • Money as a double — drift across millions of transfers, and the sum of entries never quite zero.
    • No idempotency key, or one that is optional — a client retry sends twice.
    • Reading the balance, then appending in a separate unlocked step — two debits drive it negative.
    • reverse that deletes the original rows — the ledger stops being an audit trail.

    Patterns Used

    State — the Transaction lifecycle, PENDING to COMPLETED / FAILED / REVERSED. Strategy — the fee / limit policy, swapped without touching the ledger. Command — a Transaction applies and reverses itself. Observer — statements and alerts follow a committed entry.

    Say It Like This

    "Every wallet is a row of ledger entries and the balance is their sum. A transfer is one Transaction that appends two entries — a debit on the sender, a credit on the receiver — in a single commit under both wallet locks, lower id first. A requestId makes a retry return the same Transaction. A completed transfer is undone by appending the mirror pair, never by deleting. Money is integer paise."

    The Follow-ups That Decide It

    1. The response is lost and the client retries. Walk it. seen[requestId] returns the same Transaction, zero new entries.
    2. Two transfers drain the same wallet at once. Lock the wallet, check balance then append under it.
    3. The debit lands, the credit throws. One append call, both entries or none; the txn is FAILED.
    4. A to B and B to A run together. Lock the lower wallet id first, no cycle.
    5. Undo a completed transfer. reverse appends the mirror pair, marks it REVERSED, never deletes.
    6. Reverse a transfer that is still PENDING. Refuse — only COMPLETED reverses, and only once.
    7. Cap a wallet at Rs 1,00,000 a day. A SpendingLimitPolicy the service consults before it locks.
    8. The balance read is slow at a billion entries. Keep a snapshot row per wallet, fold only the tail.

    Deliberately Not Built

    • KYC / onboarding — identity checks, limits by tier. A gate before the wallet exists.
    • Real bank / UPI rails — settlement, webhooks, chargebacks. Mocked behind TopUpSource.
    • Fraud / risk scoring — an ML service that can hold a Transaction. An Observer hook, not the model.
    • Interest, cashback, rewards — a scheduled job that appends entries. Drops in later, no path change.
    • Statement rendering — pagination, PDF, currency formatting. The entries are the data; the view is not.
