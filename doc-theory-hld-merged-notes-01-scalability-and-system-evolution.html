    Scalability and System Evolution

    14 sections · 825 words

    From a single client and server to a full distributed system.

    1. The One Goal

    Anything that we will do in HLD is to make our application scale better.

    2. Simple Client-Server Architecture

    The starting point is a two-tier system:

    • Client tier - the web browser or the mobile app.
    • Web server tier - the server that answers requests.

    The client reaches the server through a URL, an IP address, HTTP, and DNS:

    • A browser or app resolves www.example.com through DNS to an IP such as 223.23.23.34.
    • Requests are sent with HTTP methods such as POST, GET, or PUT.
    • A request carries a URL (www.example.com), headers, and a body, for example:
    {
  "userId": 1,
  "name": "Aditya"
}
    • The server responds with HTML or JSON over HTTP.

    3. Introducing the DB Layer

    Once state exists, a database tier is added. The question becomes: which DB to use?

    • Relational (SQL based) - MySQL, PostgreSQL, Oracle SQL.
    • Non-relational - used because every kind of data cannot be structured:
    • Key-value store: Amazon DynamoDB.
    • Column based store: Cassandra DB.
    • Document based store: MongoDB.
    • Graph store: Instagram, Facebook, Twitter, and similar social graphs.

    4. Multiple Servers and the Load Balancer

    To stop relying on one machine, we add multiple servers behind a load balancer (LB):

    • The LB has a public IP (for example 123.24.23.34).
    • The web servers sit on private IPs (for example 10.0.0.1 and 10.0.0.2).
    • Traffic flow: client (1) -> DNS/IP (2) -> public IP (3) -> LB (4) -> web server.
    • A single server is a SPOF (single point of failure), which is why we scale out.

    5. DB Scaling

    Reads and writes behave differently:

    • Read: SELECT.
    • Write: INSERT, UPDATE, DELETE.

    The standard first scaling move is master-slave architecture:

    • The master DB takes writes.
    • One or more slave DBs take reads.
    • The read path is parallelised across slaves while the master stays authoritative.
    • A possible downside is stale data, because a slave may lag behind the master.
    • Example layout: web servers 10.0.0.1 and 10.0.0.2, with master DB and slave DB1/DB2/DB3.

    6. Introducing the Cache

    A cache tier sits between the web server and the DB:

    • A request first checks the cache: a cache miss sends it onward to the DB.
    • The cache exists to improve latency.
    • Because cache space is limited, we need a cache eviction algorithm.
    • The example keeps the same public IP/LB and private IP web server layout as before.

    7. Content Delivery Network (CDN)

    Static content is moved close to the user with a CDN:

    • Amazon's CDN is CloudFront; Akamai is another provider.
    • Static content includes HTML, CSS, JS, and images.
    • Example mapping: www.cloudfront.com/img1 -> 120.20.20.23.
    • The flow again passes through the public IP and the LB, with the cache lowering latency.

    8. Proxies and Regional Caching

    A proxy can also hold a cache. The diagram contrasts South India and North India, showing that caching close to each region reduces latency.

    9. Auto Scaling and Stateless Architecture

    Servers can be scaled automatically, but this works cleanly only with a stateless architecture:

    • Cookies and sticky sessions create a stateful architecture (a user is tied to one server).
    • With a stateless architecture, shared state lives in a shared DB/cache, so any server can serve any request and servers can be added or removed freely.

    10. Multiple Data Centres

    For global reach we run multiple data centres:

    • A geo-enabled DNS routes users to the nearest data centre.
    • Example: DC1 in India and DC2 in the USA, each with web servers ws1/ws2.
    • The data centres share the DB layer and each has its own cache.

    11. Messaging Queues

    Work that does not need to finish before the response is moved off the request path:

    • Tools: Kafka and RabbitMQ.
    • The pattern is asynchronous: a producer pushes a message onto a messaging queue, and a worker later dequeues it.
    • The diagram places a queue between the web server and the DB layer, with caches on either side.

    12. Publish-Subscribe

    The pub-sub (publisher-subscriber) model extends the queue idea: a publisher broadcasts a message and multiple subscribers receive it. Messaging queues are shown alongside the geo-DNS, multi-data-centre layout, with caches, messaging queue, and workers.

    13. Sharding (DB Partitioning)

    As data grows, a single DB is split into shards:

    • Sharding is horizontal scaling of the DB.
    • A simple illustration uses MOD % 4 to distribute rows across DB0, DB1, DB2, and DB3.
    • Data de-normalization goes together with sharding.
    • A cache sits in front of the sharded DB layer.
