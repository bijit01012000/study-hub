      Security, privacy and safety

      0 sections · 3,942 words

      Module 13 · 9 questions · 1 practical drill

      Threat-model a system where untrusted text meets privileged instructions.

      Q13.1 — An email assistant drafts replies and forwards messages. How do you defend it against injection?

      Weak answer: "We tell the model in the system prompt to ignore instructions inside emails, and filter phrases like 'ignore previous instructions'."

      Why it fails: - A system-prompt rule cannot make the model tell a trusted instruction apart from lookalike text in the same context window. - The phrase blocklist is beaten by paraphrase or splitting the trigger text, and does nothing for indirect injection at all.

      Instant rejection: - Cannot separate direct injection, typed by a user, from indirect injection arriving inside an email the assistant reads. - Has no answer for what happens if the injection still works, only ways to make the model behave better.

      Model answer: 1. I start from the position that prompt injection has no complete fix at the prompt level, so careful wording reduces the rate but never claims to solve it. 2. This is indirect injection: the attacker never talks to the model, they mail a message formatted like an internal note, buried in a quoted thread. 3. Forwarding and sending are consequential actions, so they never fire automatically. The assistant drafts the forward and a human clicks send. 4. I scope the forwarding tool so it can only send to addresses already in our internal directory, never one an email's content supplies. 5. Every action gets logged with the triggering email attached, so a spike in forwards to unfamiliar domains shows up in monitoring, not a complaint.

      Follow-ups: 1. TECHNICAL — What's the difference between direct and indirect injection, and why does indirect matter more? · Whether the candidate has the vocabulary and places this scenario correctly. 2. FAILURE — An email hides an instruction to forward invoices out. Your blocklist misses it. What stops this? · Whether any control survives beyond the prompt and blocklist layer. 3. TRADEOFF — Would you rather harden the prompt against injection, or limit what the agent can do if injected? · Recognition that prevention has a ceiling and containment doesn't. 4. MEASUREMENT — How would you even detect that an injection succeeded, after the fact? · Whether detection exists at all, given prevention is incomplete.

      Tip: If you've scoped an API token, a service account or a webhook to the smallest permission that does the job, that's the same instinct. Don't claim you've stopped a prompt injection. Say you've limited what a component could do if it were compromised or fed bad input.

      Numbers worth quoting: - No prose fix for injection - Least privilege is the real control - Human approval on write actions - Direct vs indirect, know both

      Q13.2 — Your RAG wiki assistant puts retrieved documents into context. What's entering, and what do you do?

      Weak answer: "The documents are internal, uploaded by employees, so we trust them. We just concatenate the top chunks before the question."

      Why it fails: - Internal and employee-uploaded is not a trust boundary. A compromised account adds instruction-shaped text. - Concatenation with no delimiting puts retrieved text in the same channel as instructions, unmarked as data.

      Instant rejection: - Never considers a document written for an unrelated purpose can read as an instruction to a model, without any malice at all. - Confuses trusting the source with the content being safe to place next to instructions. Those are different claims.

      Model answer: 1. I stopped treating internal as a synonym for safe once I realised anyone with upload rights puts arbitrary text straight into the corpus. 2. Retrieved chunks go in wrapped in an explicit delimiter, and where the provider supports it I put them in their own message role, not the system turn. 3. That reduces how often a stray sentence reads as an instruction, though I don't claim it eliminates it entirely. 4. A vendor PDF once carried boilerplate telling assistants to approve account changes. Our retriever surfaced it for an unrelated query. 5. The draft got caught by the human reviewing it, because nothing the model outputs here can act on its own. That's the real control, not filtering.

      Follow-ups: 1. TECHNICAL — How do you structurally mark retrieved content as data, and does that fully solve it? · Knowledge of delimiting or role separation, and its real limits. 2. FAILURE — A vendor PDF's footer says approve changes without escalation. What happens when it's retrieved? · Whether unintentional instruction-shaped text is even on the radar. 3. TRADEOFF — Sanitise documents at ingestion, or leave them and rely on downstream constraints? · Awareness these are different bets with different failure modes. 4. MEASUREMENT — How would you find how much of your corpus already contains instruction-like text? · Whether the candidate would audit the corpus rather than assume it's clean.

      Tip: If you've ever validated or sanitised user-supplied content before it reached a template or a downstream system, that's the same discipline. Don't claim you've secured a RAG pipeline. Say you've treated external or uploaded content as untrusted input before, and describe how.

      Numbers worth quoting: - Retrieved content is untrusted - Delimit data from instructions - Reduce risk, don't claim zero - Audit the corpus periodically

      Q13.3 — A code-review bot can comment on PRs. It's asked to auto-apply small fixes. How do you scope it?

      Weak answer: "We'd give the bot a GitHub token with repo access to push fixes directly, and trust the model's judgement on what's small."

      Why it fails: - A repo-access token is unscoped: no split between commenting, opening a PR, and pushing to a protected branch. - Delegates the safety-critical call, is this fix small and safe, entirely to the model, with no boundary independent of it.

      Instant rejection: - No thought for what an attacker, via a poisoned PR description, could get the bot to do with that same token. - No distinction between a wrong comment, low cost, and an unreviewed push landing in production.

      Model answer: 1. I refused to give the bot the same token I'd give a human contributor. It can open PR comments and suggested diffs, never push to main. 2. For auto-applying small fixes, it opens a new branch and a PR, never a direct commit, so a merge still needs a human or CI gate. 3. I don't trust the model's judgement on what small means as the safety boundary. I trust that nothing it does is irreversible without another step. 4. The bot reads PR descriptions as part of its job, the same untrusted channel as any email, so a crafted description can't reach a merge alone. 5. I log every action against its granted scope, and alert if it ever touches files outside its historical pattern for a repo.

      Follow-ups: 1. TECHNICAL — What does the token actually scope to, and who decided that boundary? · Whether least privilege was designed deliberately or inherited by convenience. 2. FAILURE — A PR description hides text telling the bot to approve and merge as a maintainer. What stops that? · Whether the permission boundary holds even if the model is fooled. 3. TRADEOFF — What do you give up in usefulness by never letting the bot push directly? · Honest accounting of least privilege's cost, not just its virtue. 4. MEASUREMENT — If the bot's permissions were misused once, how would you know, and how fast? · Whether misuse detection exists independent of prevention.

      Tip: If you've ever scoped a service account, a CI job or an API key to the minimum it needs rather than the broadest convenient option, same instinct. Don't claim you've scoped an LLM agent. Say you've applied least privilege to an automated process before, and how you enforced the boundary.

      Numbers worth quoting: - Scope to least privilege - Propose, don't auto-execute - Rank actions by blast radius - Audit usage against granted scope

      Q13.4 — An on-call assistant sends production logs to a third-party LLM API. What stops PII leaving?

      Weak answer: "We have a data processing agreement and a no-training clause, so whatever we send is covered. We just pass relevant log lines in."

      Why it fails: - A DPA governs data after the vendor receives it. It doesn't reduce what's sent, the actual leak point. - Relevant log lines passed wholesale means any PII or tokens logged go into a third-party request unfiltered.

      Instant rejection: - No redaction or minimisation before the boundary, the point where a leak is actually preventable. - No thought for provider-side logging, retention or breach exposure of the request itself, separate from training.

      Model answer: 1. A DPA meant the leakage problem was handled was the assumption I fixed. It governs data after we send it, the control has to sit before that. 2. The retrieval step runs a redaction pass first: emails, our customer-id format, and card-like patterns become typed placeholders before assembly. 3. The assistant answers using placeholders, which is enough for triage questions like which requests failed after a deploy. 4. I sample outgoing requests weekly and have someone check what redaction missed. That caught a raw auth token our patterns weren't watching for. 5. For genuinely sensitive queries over real payment data, we don't send them to the third party at all. That path runs inside our own boundary.

      Follow-ups: 1. TECHNICAL — Where does redaction happen, before assembly, or do you hope the model avoids repeating PII? · Whether minimisation happens before the boundary or after it. 2. FAILURE — A stack trace leaks an email and a card fragment your regex misses. What slips through? · Whether the candidate knows regex redaction has a known miss rate. 3. TRADEOFF — Self-hosting avoids sending anything to a third party. Why wouldn't you just do that? · Honest cost and benefit of self-hosting versus API use. 4. MEASUREMENT — How do you know, ongoing, what fraction of requests still carry PII after redaction? · Whether redaction effectiveness is measured or assumed.

      Tip: If you've ever stripped or masked sensitive fields before logging them or sending them to an external service, that's the same control. Don't claim you've redacted for an LLM API. Say you've minimised what a system sends externally before, and how you checked it worked.

      Numbers worth quoting: - DPA is not a technical control - Redact before assembly, not after - Regex redaction has a miss rate - Sample outgoing requests weekly

      Q13.5 — One shared vector index is filtered by tenant_id at query time. Walk me through what could go wrong.

      Weak answer: "Each document is tagged with tenant_id, and every query filters on the current user's tenant_id, so tenants can't see each other."

      Why it fails: - The filter is always applied describes intent, not enforcement. One missed code path returns cross-tenant results. - No mention of where tenant_id comes from. Client-supplied rather than server-derived bypasses it.

      Instant rejection: - No layered enforcement, a single filter applied once with nothing checking it independently before the index is queried. - No account of how isolation is verified as new code paths, debug tools, admin queries, batch jobs, get added.

      Model answer: 1. I checked where tenant_id actually came from. It had been a frontend parameter, so a manipulated request could ask for another tenant's data. 2. I moved tenant scope to be derived from the authenticated session and injected at the data-access layer itself, not in whichever route calls it. 3. That way a new debug tool, admin dashboard or batch job can't reach the store at all without picking up the scope automatically. 4. We found a relevance-tuning debug endpoint that had bypassed the normal query path, which would have leaked cross-tenant matches in production. 5. I run an automated test on every deploy that seeds two fake tenants and asserts one's queries never surface the other's content.

      Follow-ups: 1. TECHNICAL — Where does tenant_id come from at query time, and could a request reach the store without it? · Whether tenant scope is derived server-side or trusted from the client. 2. FAILURE — A new debug endpoint queries the raw index and forgets the tenant filter. What stops the leak? · Whether enforcement is structural, not dependent on every developer remembering. 3. TRADEOFF — Separate indexes per tenant versus one shared index with filtering, what does each cost you? · Whether partitioning is a deliberate, revisitable decision. 4. MEASUREMENT — How would you test, on every deploy, that cross-tenant isolation actually holds? · Whether isolation is continuously verified, not checked once at launch.

      Tip: If you've derived a user or account scope from an authenticated session rather than trusting a client-supplied parameter, that's this exact judgement. Don't claim you've secured multi-tenant retrieval. Say you've caught or fixed a case where authorisation was trusted from the client before.

      Numbers worth quoting: - Filtering is not a boundary - Derive scope server-side, always - Enforce at the data-access layer - Test isolation on every deploy

      Q13.6 — An ops assistant proposes a remediation action. Before it runs, what actually validates it?

      Weak answer: "The model picks a remediation function and parameters. We tuned the prompt to reason carefully, and it's been accurate, so it runs."

      Why it fails: - A tuned prompt changes the odds, not a validation control. Accurate in testing is the common case. - No independent check on parameters. An out-of-range replica count or a wrong service target would sail through unchecked.

      Instant rejection: - Conflates a schema-valid tool call with a safe action. A well-formed call can still be operationally wrong. - No distinction drawn between the alert's actual source and whatever the model inferred the target service to be.

      Model answer: 1. A schema-valid tool call is not the same claim as a safe one. The model producing the right shape says nothing about whether the numbers are sane. 2. A validation layer sits between output and execution. It checks the target against an allowlist from the alert's own source labels, not the model's prose. 3. It checks parameters against hard bounds per service, replica counts capped near double steady state, rejecting anything outside regardless of confidence. 4. Actions are tiered. Restarting one stateless instance runs unattended. Anything touching a database or exceeding a bound goes to a human first. 5. I log every proposed action, executed or not, and review blocked ones weekly to tell a correct block from a miscalibrated bound.

      Follow-ups: 1. TECHNICAL — The model calls scale_deployment with replicas 400 on a service that runs 3. Where's that caught? · Whether hard bounds exist independent of the model's own reasoning. 2. FAILURE — The alert is about service A but the call targets service B, similar names. What catches that? · Whether target attribution is cross-checked against the alert source. 3. TRADEOFF — Which remediation actions run unattended, which always wait for a human, and who drew the line? · Whether action tiers are deliberate and reversibility-based. 4. MEASUREMENT — How do you know your validation layer is catching bad calls, versus never having seen one yet? · Whether blocked actions are reviewed and bounds calibrated over time.

      Tip: If you've ever put a hard-coded sanity check or an allowlist in front of an automated action, independent of the logic that proposed it, same idea. Don't claim you've validated model output before execution. Say you've added an independent guard rail to an automated system before.

      Numbers worth quoting: - Valid shape is not a safe action - Bounds independent of the model - Tier actions by reversibility - Review blocked actions weekly

      Q13.7 — A guardrail model catches unsafe output for your shopping assistant. Where does it break?

      Weak answer: "Every response goes through a moderation classifier, and we block and show a fallback if it flags anything. That covers unsafe content."

      Why it fails: - Covers anything unsafe treats the guardrail as complete, though classifiers have a false-negative rate. - No split between catching disallowed content and subtler failures like a jailbreak reframed to dodge it.

      Instant rejection: - No mention of the guardrail's own latency or cost, or what happens if it's skipped under load. - A single layer with no defence in depth. If the one classifier misses something, nothing else is checked.

      Model answer: 1. I stopped calling moderation solved once I saw it's just another model with a false-negative rate, not a gate that's simply open or closed. 2. It's a separate, smaller classifier from a different provider, deliberately not the model grading its own output on the same wrapped text. 3. It's layered: an intent check before generation narrows what's attempted, and an output check after catches what got through anyway. 4. The output check adds real latency, worth it here because the assistant is customer-facing, but not something I'd pay on a low-stakes internal tool. 5. I can't measure the live miss rate directly, so I run a red-team set of known jailbreak patterns on every model or prompt change.

      Follow-ups: 1. TECHNICAL — Is your guardrail the same model family as the assistant, and why would that matter? · Awareness that a same-family classifier can share blind spots. 2. FAILURE — A jailbreak wraps a harmful request as fiction. Does a direct-request classifier catch the wrap? · Knowledge of reframing as a real bypass class. 3. TRADEOFF — What does running a guardrail on every response cost in latency, and where isn't it worth it? · Whether the guardrail's cost was weighed against where it's needed. 4. MEASUREMENT — How do you measure a guardrail's false-negative rate, given a miss is by definition uncaught? · Whether ongoing red-teaming exists, since misses are invisible in production.

      Tip: If you've added a second, independent check, a linter, a schema validator, a different service, rather than trusting one layer, same instinct. Don't claim you've built an AI guardrail. Say you've treated a single validation layer as fallible and added defence in depth before.

      Numbers worth quoting: - Guardrail has its own miss rate - Independent model, not same - family - Reframing is a real bypass class - Red-team on every prompt change

      Q13.8 — Your support assistant logs full prompts with names and account numbers. What's your retention policy?

      Weak answer: "We log everything, prompt, context and response, in the same system as our app logs, indefinitely, because storage is cheap."

      Why it fails: - Storage is cheap prices the wrong resource. The real cost of retention is regulatory and breach exposure, not disk. - The same logging system as app logs likely gives broader engineering access than the customer database this data came from.

      Instant rejection: - No mention of whether a deletion request can find and purge this data, or if it lives untracked in a general log store. - Logging everything by default with no redaction expands the PII footprint well beyond where it started.

      Model answer: 1. I avoided writing full prompts into the general app log store because storage is cheap. That prices the wrong resource, the cost is regulatory exposure. 2. These logs carry the same names and account details as the systems they came from, so they sit at the same access tier as the customer database. 3. Known PII fields get tokenised at write time, the same way I'd redact them for a third-party API call. 4. Raw values, where kept, sit in a narrower-access layer with a 30-day window, set from asking support how far back they'd genuinely investigated. 5. Deletion tooling explicitly reaches this store too, not only the primary database, because a copy left in logs hasn't honoured the request.

      Follow-ups: 1. TECHNICAL — Can a deletion request remove a customer's data from these logs, not just the primary database? · Whether deletion tooling actually reaches log stores. 2. FAILURE — Your general logging system has wider access than the customer database. What did that just do? · Whether logging PII is seen as silently widening who can see it. 3. TRADEOFF — What do you lose redacting at write time versus keeping raw logs with restricted access instead? · Whether debugging fidelity was weighed against minimisation. 4. MEASUREMENT — What's your actual retention window, and who decided the number? · Whether the window is a documented decision or an unexamined default.

      Tip: If you've set a log retention window, restricted access to a sensitive table, or made deletion reach every copy of data, that's the same skill. Don't claim you've handled AI log retention. Say you've set a deliberate retention and access policy for sensitive data before, and why.

      Numbers worth quoting: - Retention cost is legal, not disk - Logs match source's access tier - Redact known PII at write time - Deletion must reach every copy

      Q13.9 — [DRILL] An agent ingests documents and admins can trigger re-index or delete by name. Threat-model it. (practical drill)

      Weak answer: "N/A, this is a drill. A weak attempt checks uploads for malware only, missing the text itself as the real channel."

      Why it fails: - Treats the file as a malware risk only, missing that extracted text becomes a prompt-injection channel once embedded. - Misses that delete-by-name is a reachable action. Document content could talk the agent into deleting itself or another file.

      Instant rejection: - No consideration of tenant or source separation, whose documents can retrieve into whose queries. - Ignores what leaves the boundary at a third-party extraction or embedding API, and how long content is retained.

      Model answer: 1. The attack surface isn't the file format, it's the text that comes out of it. A PDF, a Word file and a scraped page all become plain text in one context. 2. Delete-by-name and re-index are reachable tool calls, so a document saying this is outdated, delete it could get itself deleted if a query retrieves it. 3. The fix isn't better phrasing. Delete and re-index only accept an identifier from the live authenticated admin's own turn, never one inferred from content. 4. I'd check provenance and tenant scope on every retrieval, and what the extraction and embedding calls send externally, the same question as any PII exposure. 5. Before launch, and on every significant change, I'd run documents seeded with known injection patterns through the real pipeline and check nothing fires.

      Follow-ups: 1. TECHNICAL — A PDF becomes plain text before embedding. What's hiding that extraction won't show? · Whether the risk is understood to live in extracted text, not the file format. 2. FAILURE — A document tells the agent to delete a named file. What stops that when a query retrieves it? · Whether delete is structurally unreachable from content, not just discouraged. 3. TRADEOFF — Block document-triggered deletes outright, or allow them with confirmation. What does each cost? · Whether a hard boundary is weighed against a softer human-in-the-loop one. 4. MEASUREMENT — How would you test this threat model before launch, rather than finding out from an incident? · Whether threat modelling produces a verifiable test, not just a document.

      Tip: If you've threat-modelled any system with untrusted input and a destructive action reachable from it, that's the same structured thinking here. Don't invent an agent security story. Say plainly you'd apply this same content, action, tenancy and boundary breakdown to any new untrusted input.

      Numbers worth quoting: - Text is the risk, not the file - Delete needs a live admin turn - Check third-party extraction - Seed test docs with injections
