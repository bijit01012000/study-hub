      165. Second-level cache in Hibernate

      Asked at: Senior rounds at Razorpay · Cred · Swiggy · PhonePe

      Difficulty: Medium-Hard · Topic: Hibernate advanced

      The question: "What's the second-level cache in Hibernate? When does it help?"

      The 30-second answer: First-level cache = Session / EntityManager scope (per-transaction). Secondlevel cache = SessionFactory scope, shared across sessions. Stores entities by ID across the entire app. Helps for read-mostly entities (Country, MerchantConfig). Hibernate ships pluggable providers — Ehcache, Hazelcast, Infinispan, Caffeine.

      Step-by-step thought process:

      1. "Enable globally — hibernate.cache.use_second_level_cache=true, set provider with hibernate.cache.region.factory_class. Annotate cacheable entities with @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)."
      2. "L2 stores hydrated state (field values), not object instances — so each session that loads an entity from L2 gets its own instance. This is correct for the JPA contract."
      3. " @Cache concurrency strategies — READ_ONLY (no updates, fastest), NONSTRICT_READ_WRITE (no locking, can stale briefly), READ_WRITE (soft lock during commit), TRANSACTIONAL (full XA — rarely worth it)."
      4. "L2 only helps for EntityManager.find(id) style lookups. JPQL queries don't hit L2 by default — they hit the query cache, which is separate."

      Edge cases to mention:

      • Stale data — if another app or raw SQL updates the table, L2 doesn't know. Bypass with cache.evict(...) or design L2 only for truly immutable entities
      • Distributed L2 (Infinispan, Hazelcast) — invalidation messages across nodes. Adds network cost; benchmark before assuming benefit
      • Collection caching — @Cache on the entity is separate from @Cache on a @OneToMany collection; both must be annotated

      What NOT to say:

      • "L2 makes Hibernate fast" — only for specific patterns; bad fit for write-heavy entities
      • "L2 is global cache" — it's a per-SessionFactory cache; multiple apps each have their own

      Common follow-up: "What's the query cache and why is it usually a bad idea?"

      166. N+1 problem — find it and fix it

      Asked at: Senior rounds at Razorpay · Swiggy · Cred · TCS Digital · Wells Fargo

      Difficulty: Medium-Hard · Topic: Hibernate advanced

      The question: "What's the N+1 problem and how do you diagnose it?"

      The 30-second answer: You execute one query to fetch N parent entities (SELECT * FROM order), then your code accesses a lazy collection on each, causing N more queries (SELECT * FROM order_item WHERE order_id =?). Total: N+1 queries. Diagnose: enable SQL logging or add a query counter assertion. Fix: JOIN FETCH, @EntityGraph, batch fetching.

      Step-by-step thought process:

      1. "Symptom — a page response that should be one query ends up being 100. SQL log shows the same query template repeating."
      2. " JOIN FETCH in JPQL — SELECT o FROM Order o JOIN FETCH o.items WHERE o.status =:status. Single query with a join. Watch out for Cartesian products with multiple bag fetches."
      3. " @EntityGraph — declarative version. @EntityGraph(attributePaths = {"items", "customer"}) on the repository method. Hibernate generates the joins automatically."
      4. "Batch fetching — @BatchSize(size = 25) on the collection. Instead of N queries, Hibernate batches them: WHERE order_id IN (?,?,?,...). Constant 1 extra query regardless of N. Works for many one-tomany relationships at once."

      Edge cases to mention:

      • JOIN FETCH with pagination is a footgun — Hibernate fetches everything then paginates in memory. Use EntityGraph + native pagination instead
      • Multiple bag fetches in one query — MultipleBagFetchException. Either use Set instead of List or fetch separately
      • Hibernate stats — hibernate.generate_statistics=true exposes query count via JMX; assert on it in integration tests

      What NOT to say:

      • "Use eager loading" — fixes N+1 but creates over-fetching; lazy + batch is usually better
      • "Hibernate is slow" — N+1 is a usage issue, not a Hibernate flaw

      Common follow-up: "Show me a JPQL JOIN FETCH that would fail and why."

      167. EntityGraph vs JOIN FETCH vs @BatchSize

      Asked at: Senior rounds at Razorpay · Swiggy · Cred · Walmart Labs

      Difficulty: Medium-Hard · Topic: Hibernate advanced

      The question: "You have three tools to fix N+1. When do you reach for which?"

      The 30-second answer: JOIN FETCH for one-off ad-hoc queries — quick fix. @EntityGraph for repository-level reusable graphs — cleaner long-term. @BatchSize as a global default for relationships where you usually want them loaded — set-and-forget.

      Step-by-step thought process:

      1. "JOIN FETCH — JPQL keyword. Inline in your query. Fast to add, easy to misuse with pagination. Per-query."
      2. "@EntityGraph — declares which subgraph to load. Attach to a repository method via @EntityGraph(attributePaths =...). Generates the joins. Reusable across multiple queries."
      3. "@BatchSize — on a collection (@OneToMany @BatchSize(size = 25)) or entity. When Hibernate is about to lazy-load N proxies, it batches them. Doesn't avoid the problem entirely but reduces N+1 to N/25 + 1."
      4. "Pattern — make collections lazy + BatchSize globally. Use EntityGraph for known-fat operations (admin views, exports). JOIN FETCH for one-off endpoints."

      Edge cases to mention:

      • EntityGraphs come in two flavours — LOAD (graph attributes + entity defaults) and FETCH (graph attributes only, everything else lazy)
      • @BatchSize on the entity class affects how lazy proxies of that entity are batched — different from collection BatchSize
      • Open-SessionIn-View pattern hides N+1 — endpoints work but performance is poor; either disable OSIV or strictly use DTOs

      What NOT to say:

      • "Just eager-load everything" — kills performance and creates Cartesian explosions
      • "Hibernate auto-detects N+1" — no, you have to spot it

      Common follow-up: "What's MultipleBagFetchException and how do you fix it?"

      168. JPA Criteria API — type-safe dynamic queries

      Asked at: Senior rounds at JP Morgan India · Wells Fargo · Goldman · Walmart Labs

      Difficulty: Medium-Hard · Topic: Hibernate advanced

      The question: "You need a search endpoint with 8 optional filters. JPQL is painful. What's the alternative?"

      The 30-second answer: JPA Criteria API — build queries programmatically as a tree of Predicate objects. Type-safe via the generated metamodel (Order_.merchantId). Build a list of predicates conditionally based on which filters are set, combine with cb.and(...). Spring Data JPA Specification is a thin wrapper that's more ergonomic.

      Step-by-step thought process:

      1. " CriteriaBuilder cb = entityManager.getCriteriaBuilder(); CriteriaQuery<Order> q = cb.createQuery(Order.class); Root<Order> root = q.from(Order.class); — boilerplate to get started."
      2. "Build predicates conditionally — List<Predicate> ps = new ArrayList<>(); if (status!= null) ps.add(cb.equal(root.get("status"), status));. Combine: q.where(cb.and(ps.toArray(new Predicate[0])));."
      3. "Type-safe access via metamodel — root.get(Order_.merchantId) instead of string "merchantId". Generated at compile time by hibernate-jpamodelgen."
      4. "Spring Data Specification — Specification<Order> hasStatus(Status s) = (root, q, cb) -> cb.equal(root.get(Order_.status), s);. Compose with .and() / .or() / Specification.where(...)."

      Edge cases to mention:

      • Criteria queries are verbose — for static queries with no conditionals, JPQL is far cleaner
      • jOOQ and QueryDSL are popular alternatives — more concise DSLs, but extra build tooling
      • Pagination with Criteria — q.setFirstResult / setMaxResults on the typed query, separate from the criteria builder

      What NOT to say:

      • "Use string concatenation to build JPQL dynamically" — SQL injection risk, fragile
      • "Always use Criteria" — over-engineering for static queries

      Common follow-up: "What's QueryDSL and how does it compare to Criteria?"

      169. Hibernate batch fetching, batch inserts, batch updates

      Asked at: Senior rounds at Razorpay · Cred · Wells Fargo · PhonePe

      Difficulty: Medium-Hard · Topic: Hibernate advanced

      The question: "I'm inserting 10,000 entities and Hibernate is slow. What do I tune?"

      The 30-second answer: Set hibernate.jdbc.batch_size=50 to enable JDBC batching, hibernate.order_inserts=true and hibernate.order_updates=true so Hibernate groups same-type statements together. Flush + clear the session every batch to keep memory bounded. Use IDENTITY generators carefully — they disable batching.

      Step-by-step thought process:

      1. "By default Hibernate sends each INSERT as a separate JDBC roundtrip. With batch_size=50, it accumulates 50 then sends them as one batch — orders of magnitude faster network-wise."
      2. "Order inserts/updates — without ordering, an INSERT order, INSERT customer, INSERT order sequence breaks the batch (different SQL statements). Ordering groups same-table operations together."
      3. "Memory — Session keeps every persisted entity in the first-level cache. After every 50 entities, call em.flush(); em.clear(); to evict and avoid OOM."
      4. " @GeneratedValue(strategy = IDENTITY) — the DB assigns the ID, but Hibernate needs the ID before batching can complete. Switch to SEQUENCE (PostgreSQL/Oracle) or pre-allocate via hi/lo optimizer."

      Edge cases to mention:

      • StatelessSession — bypasses first-level cache entirely. Best for bulk ETL where you don't need entity lifecycle
      • For pure SQL-fast bulk, drop Hibernate and use JdbcTemplate.batchUpdate(...) directly
      • MySQL has rewriteBatchedStatements=true JDBC URL param — actual batching at the driver level; without it the driver fakes batching

      What NOT to say:

      • "Use saveAll(...) and it'll batch" — only if you've also set batch_size and ID generation supports it
      • "Hibernate is too slow for bulk" — depends on tuning; well-tuned Hibernate is close to raw JDBC

      Common follow-up: "Why does @GeneratedValue(IDENTITY) disable batching?"

      170. Custom Hibernate dialects

      Asked at: Senior rounds at Wells Fargo · Goldman · TCS Digital

      Difficulty: Medium-Hard · Topic: Hibernate advanced

      The question: "When would you write a custom Hibernate dialect?"

      The 30-second answer: Dialects translate JPQL/HQL to vendor-specific SQL — pagination syntax, sequence syntax, function names. Write a custom dialect to register vendor-specific SQL functions (Postgres array_agg, MySQL JSON_EXTRACT), override pagination, or change identifier quoting.

      Step-by-step thought process:

      1. "Out of the box — PostgreSQLDialect, MySQLDialect, OracleDialect, etc. Extending one and overriding a couple of methods is the normal path."
      2. "Custom function — registerFunction("jsonb_path", new StandardSQLFunction("jsonb_path_query", StandardBasicTypes.STRING)). Now JPQL can call jsonb_path(...) and Hibernate emits the right SQL."
      3. "Identifier quoting — override quote(...) if your DB has unusual escape rules. Rare for mainstream DBs."
      4. "Hibernate 6 changes — dialects modernized, version-specific dialects auto-selected, much less manual config than Hibernate 5 needed."

      Edge cases to mention:

      • Hibernate 6 dropped many legacy dialects (MySQL5Dialect, MySQL57Dialect — now just MySQLDialect with version detection)
      • For Postgres JSONB, hibernate-types library has community-maintained user types worth using
      • Don't write a dialect to fix a JPA / Hibernate version mismatch — fix the version

      What NOT to say:

      • "Just use native SQL everywhere" — fine but loses JPQL portability and Hibernate's L1 cache integration
      • "Dialects are deprecated" — no, just consolidated

      Common follow-up: "How do you map a Postgres JSONB column to a Java object?"

      171. Circuit breaker — what does it actually do?

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Cred · Walmart Labs

      Difficulty: Medium-Hard · Topic: Microservices / distributed

      The question: "Explain the circuit breaker pattern. Walk me through the state transitions."

      The 30-second answer: Three states — CLOSED (passes calls through, counts failures), OPEN (fails fast without calling — usually after failure threshold hits), HALF_OPEN (lets a few trial calls through after a cooldown; if they succeed, back to CLOSED). Protects you from cascading failures when a downstream is dead — your threads aren't blocked waiting for a doomed call.

      Step-by-step thought process:

      1. "CLOSED — normal mode. Calls pass through. We count failures over a window (count-based or time-based)."
      2. "OPEN — failure threshold exceeded (e.g., 50% failure rate over the last 100 calls). Now we fail fast for every call without touching the downstream. Saves us from blowing up thread pools waiting on a dead service."
      3. "HALF_OPEN — after a configured wait (waitDurationInOpenState, e.g., 60s), allow N trial calls. If they mostly succeed, transition back to CLOSED. If they fail, back to OPEN."
      4. "Resilience4j is the modern Java library — Hystrix is dead (retired by Netflix). Spring Cloud Circuit Breaker has Resilience4j as the default."

      Edge cases to mention:

      • Tune thresholds carefully — too sensitive flaps the breaker open on transient noise; too loose lets bad services drain your threads
      • Use slidingWindowType = COUNT_BASED for predictable evaluation; TIME_BASED for variable call rates
      • Combine with retry, bulkhead, timeout — Resilience4j composes them via decorators

      What NOT to say:

      • "Use Hystrix" — retired in 2018; new code goes to Resilience4j
      • "Circuit breaker replaces timeouts" — they're complementary; breaker reacts to repeated timeouts

      Common follow-up: "What's a bulkhead and how is it different from a circuit breaker?"

      172. Distributed tracing — span, trace, context propagation

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Cred · Flipkart

      Difficulty: Medium-Hard · Topic: Microservices / distributed

      The question: "How does distributed tracing work? Explain trace, span, and context propagation."

      The 30-second answer: A trace is the full journey of a request across services. Each unit of work is a span (e.g., one HTTP call, one DB query). Spans have parent/child relationships. Each carries a traceId (shared across the trace) and spanId (unique). Context propagation = passing the IDs via HTTP headers (traceparent, tracestate — W3C Trace Context standard) so downstream services join the trace.

      Step-by-step thought process:

      1. "Client calls service A → A creates root span with new traceId. A calls B → A passes traceId + its spanId as B's parent via traceparent header."
      2. "Each service emits spans to a collector (Jaeger, Zipkin, Tempo). Collector reconstructs the tree by joining traceId + parentSpanId."
      3. "Spring Boot 3 uses Micrometer Tracing as the abstraction — defaults to Brave (Zipkin) or OpenTelemetry as the backend. Replaces Spring Cloud Sleuth from Boot 2.x."
      4. "Instrumentation — RestTemplate, WebClient, Kafka, JDBC all have auto-instrumentation; spans are created automatically. Custom spans via Tracer.nextSpan().start() for business logic boundaries."

      Edge cases to mention:

      • Sampling — at high volume you can't store every trace. Head-based sampling (decide at root, propagate) vs tail-based (decide after seeing the full trace, smarter but harder) Log correlation — inject traceId into MDC so each log line has it; combine with central logging for fast incident response
      • Baggage — propagate arbitrary key/value alongside trace IDs (e.g., userId, tenantId) for filtered traces

      What NOT to say:

      • "Just log everything" — logs don't reconstruct the call tree; traces do
      • "Tracing is for debugging only" — also for SLO monitoring, dependency mapping, error attribution

      Common follow-up: "What's tail-based vs head-based sampling?"

      173. Saga pattern — choreography vs orchestration

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Flipkart

      Difficulty: Hard · Topic: Microservices / distributed

      The question: "Explain the saga pattern. What's choreography vs orchestration?"

      The 30-second answer: Saga = long-running multi-service transaction implemented as a sequence of local transactions, each with a compensating action. Choreography — services react to events from each other, no central coordinator. Orchestration — a central saga orchestrator (e.g., Camunda, Temporal) drives the steps explicitly.

      Step-by-step thought process:

      1. "Distributed transactions (2PC) don't scale — locking across services is a SPOF. Saga replaces ACID across services with eventually-consistent business workflow."
      2. "Order saga — OrderCreated → PaymentReserved → InventoryReserved → OrderConfirmed. Each step is a local transaction. If payment fails, the saga compensates: cancel reservation, mark order failed."
      3. "Choreography — Payment service listens to OrderCreated, charges, emits PaymentReserved. Inventory listens to PaymentReserved. No coordinator. Simple at small scale, hard to reason about at large scale."
      4. "Orchestration — A saga orchestrator (Temporal, Camunda, Spring State Machine) calls each service in turn and tracks state. Easier to visualize and debug, but introduces a central service to operate."

      Edge cases to mention:

      • Compensating actions are not always perfect inverses — refund!= un-charge if the order was partially shipped. Sagas need explicit business semantics for compensation Idempotency is essential — every saga step might be re-delivered (at-least-once messaging); steps must tolerate duplicates
      • Saga timeout — what happens if a step never completes? Orchestrator usually has a per-step timeout that triggers compensation

      What NOT to say:

      • "Use 2PC instead" — doesn't scale across heterogeneous services
      • "Saga is just retry logic" — undersells; compensation is the key insight

      Common follow-up: "Why is idempotency so important in saga steps?"

      174. Idempotency keys — design and storage

      Asked at: Senior rounds at Razorpay · PhonePe · Swiggy · Cred

      Difficulty: Medium-Hard · Topic: Microservices / distributed

      The question: "How do you implement idempotency for a payment API?"

      The 30-second answer: Client sends an Idempotency-Key header (UUID) on every payment request. Server stores (key → response) mapping. On duplicate request with the same key, return the stored response instead of processing again. Storage in Redis with TTL (24 hours typical). Race condition: two simultaneous requests with same key — use atomic SETNX or a state machine.

      Step-by-step thought process:

      1. "Stripe popularized this — client generates a UUID per logical request. Header Idempotency-Key: . Server looks it up before processing."
      2. "Storage — Redis is typical. Key = idempotency key. Value = serialized response + status. TTL 24h to bound storage."
      3. "Race — two retries hit the server within ms. Both look up the key (not found), both start processing. Use SET NX to atomically claim the key with status PROCESSING. Loser waits or returns 409 Conflict."
      4. "On completion, write the final response into the key. Next duplicate retry returns the cached response."

      Edge cases to mention:

      • Validate request payload matches stored payload — same key with different body should reject (422 Unprocessable Entity)
      • For very long operations, return 202 Accepted immediately and poll status by the key
      • Cleanup — TTL handles expiration; for foreveridempotent operations (refunds), store in a real DB instead

      What NOT to say:

      • "Use the request hash as the key" — clients can't reliably reproduce the hash on retry across SDK versions
      • "DB unique constraint is enough" — only after the row is created; pre-insert race still exists

      Common follow-up: "How would you design the database schema to enforce idempotency on a refund?"

      175. Eventual consistency — how to communicate to product

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe

      Difficulty: Medium-Hard · Topic: Microservices / distributed

      The question: "Product wants 'real-time consistency' across all services. How do you handle that conversation?"

      The 30-second answer: In a distributed system, strong consistency requires synchronous coordination — every service waits for every other. That kills latency and availability. Eventual consistency is the price of horizontal scale. The conversation is about acceptable convergence window (50ms? 500ms? 5s?) and what UX patterns mask the gap (optimistic UI, polling, retries, read-after-write hints).

      Step-by-step thought process:

      1. "Distributed transactions across services either lock everything (no throughput) or fail open (data inconsistency). Eventual consistency is the practical choice."
      2. "User pays → payment service updates → emits event → order service updates → emits event → notification service sends SMS. Total convergence: 100-500ms typically."
      3. "Mask the gap — show optimistic UI (assume success, roll back on failure), use 'read your own writes' guarantees by routing the user's reads back to the writer node, poll for completion."
      4. "Read-after-write — within the same session, route reads to the primary or to a session-pinned replica. Beyond that session, eventual consistency is fine."

      Edge cases to mention:

      • Some operations are inherently strongly consistent (deducting balance, reserving inventory) — these stay synchronous or use sagas with compensation
      • CRDTs (conflict-free replicated data types) for distributed counters / sets where order doesn't matter
      • Discuss SLOs in terms of convergence percentiles — p99 < 1s — not "instantaneous"

      What NOT to say:

      • "Stronger consistency is always better" — performance and availability suffer
      • "Just use Kafka and it'll be fine" — Kafka is at-least-once, not magic consistency

      Common follow-up: "What's the CAP theorem and how does it apply here?"

      176. Retry strategies — exponential backoff, jitter, retry budget

      Asked at: Senior rounds at Razorpay · Swiggy · PhonePe · Cred · Walmart Labs

      Difficulty: Medium · Topic: Microservices / distributed

      The question: "You're retrying a flaky downstream. Walk me through your retry strategy."

      The 30-second answer: Exponential backoff (100ms, 200ms, 400ms, 800ms) with jitter (randomize ±20%) to avoid synchronized retries thundering the downstream. Cap retries (3-5 typical). Differentiate retryable errors (5xx, timeout, connection reset) from non-retryable (4xx). Wrap in a circuit breaker so a sustained outage doesn't cause retries forever.

      Step-by-step thought process:

      1. "Naive retry — fixed delay, fixed count. Causes thundering herd: every client retries at the same moment, downstream gets a synchronized spike."
      2. "Exponential backoff — double the delay each time. Spreads retries out. With jitter (random ±20%), clients diverge instead of synchronizing."
      3. "Retry only on retryable errors — 5xx, timeout, connection reset. Don't retry 400, 401, 404 — they're permanent (idempotent retries only)."
      4. "Retry budget — limit aggregate retries (e.g., max 10% of total calls). Without it, retries during an outage amplify load by 5x and hurt recovery."

      Edge cases to mention:

      • Idempotency — retrying a POST that creates a resource without an idempotency key creates duplicates
      • Retry-After header — server can tell client when to retry; respect it
      • Resilience4j and Spring Retry both implement the pattern — Resilience4j composes better with circuit breaker

      What NOT to say:

      • "Retry until it works" — guarantees you'll DDoS your downstream during their outage
      • "Retry every error" — 400 means "your request is broken", retrying won't fix it

      Common follow-up: "What's a retry storm and how do retry budgets prevent it?"
