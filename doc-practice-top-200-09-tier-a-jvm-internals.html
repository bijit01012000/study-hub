      85. Heap structure — Young Gen, Old Gen, Metaspace

      Asked at: Senior backend rounds · Razorpay · Goldman · Walmart

      Difficulty: Medium · Topic: JVM internals

      The question: "Walk me through the structure of the JVM heap in modern Java."

      The 30-second answer: Heap splits into Young Generation (Eden + two Survivor spaces, S0 and S1) and Old Generation. New objects go to Eden. After a minor GC, surviving objects move to a Survivor space; after several minor GCs (typically 15), they're promoted to Old Gen. Metaspace (off-heap since Java 8) holds class metadata. Large objects can be allocated directly in Old Gen.

      Step-by-step thought process:

      1. "Young Gen is where new allocation happens. Eden is the largest part; S0 and S1 are the two survivor spaces."
      2. "Minor GC (Young Gen collection): live objects in Eden + one survivor move to the other survivor. Eden and the source survivor become empty."
      3. "Tenuring threshold (default 15 minor GCs survived) — objects that keep surviving get promoted to Old Gen. The assumption: most objects die young."
      4. "Old Gen GC is more expensive — full GCs touch the whole heap and historically were stop-the-world. Modern collectors (G1, ZGC, Shenandoah) make this concurrent."
      5. "Metaspace (off-heap, replaced PermGen in Java 8) holds class definitions. Grows dynamically — set -XX:MaxMetaspaceSize if you don't want it unbounded."

      Edge cases to mention:

      • TLAB (Thread-Local Allocation Buffer) — each thread gets a private region in Eden so allocation is just a pointer bump, no synchronization
      • Humongous objects (larger than half a G1 region) go straight to Old Gen
      • ZGC and Shenandoah are concurrent low-latency collectors — they target sub-10ms pauses on heaps up to TBs

      What NOT to say:

      • "There's also PermGen" — removed in Java 8
      • "Old Gen is collected by every GC" — minor GC only touches Young Gen

      Common follow-up: "What's the difference between a minor GC and a major GC?"

      86. GC algorithms — G1 vs ZGC vs Parallel

      Asked at: Senior backend rounds · Razorpay · Goldman · Walmart Labs

      Difficulty: Hard · Topic: JVM internals

      The question: "Walk me through the major GC algorithms. When would you pick each?"

      The 30-second answer: Serial GC — single-threaded, small heaps, simple apps. Parallel GC — throughput-focused, multi-threaded for both young and old. G1 GC (default since Java 9) — regionbased, predictable pause targets, default for most apps. ZGC — concurrent, sub-millisecond pauses, multi-TB heaps. Shenandoah — similar to ZGC, Red Hat-led. For modern Java, G1 by default, ZGC when latency matters more than throughput.

      Step-by-step thought process:

      1. "Serial GC (-XX:+UseSerialGC) — single-threaded mark-sweepcompact. Smallest footprint. Containers with one CPU and ~100MB heap."
      2. "Parallel GC (-XX: +UseParallelGC) — multi-threaded but still stop-the-world. Maximizes throughput; long pauses on big heaps. Was the default through Java 8."
      3. "G1 (-XX:+UseG1GC, default since Java 9) — splits heap into ~2000 regions, each can be Eden/Survivor/Old/Humongous. Predictable pause goal via -XX:MaxGCPauseMillis."
      4. "ZGC (-XX:+UseZGC, production-ready since Java 15, generational in Java 21+, default-generational in Java 23) — concurrent collector with sub-10ms pauses (often submillisecond). For latency-sensitive services with multi-GB to TB heaps."
      5. "Shenandoah — Red Hat's concurrent collector. Similar profile to ZGC. Often available in OpenJDK distributions."

      Edge cases to mention:

      • Generational ZGC (Java 21 JEP 439, default in Java 23 JEP 474) — major throughput improvement over single-gen ZGC
      • For containerized apps, the JVM auto-detects container memory limits since Java 10 — set heap with -XX:MaxRAMPercentage rather than fixed -Xmx Tail latency matters more than average latency for user-facing APIs — pick ZGC over G1 if p99 matters

      What NOT to say:

      • "CMS is still recommended" — removed in Java 14
      • "Just use defaults" — fine for many apps, but knowing why the default fits helps in interviews

      Common follow-up: "What's the trade-off between throughput and latency in GC choice?"

      87. JIT compilation tiers — C1 and C2

      Asked at: Senior rounds · Goldman · JP Morgan · Morgan Stanley

      Difficulty: Hard · Topic: JVM internals

      The question: "How does the JIT compiler work in HotSpot? What's tiered compilation?"

      The 30-second answer: HotSpot runs bytecode through an interpreter first. Hot methods get compiled by C1 (client compiler) for quick startup, then re-compiled by C2 (server compiler) for peak performance. Tiered compilation (default since Java 8) progresses through 5 levels — interpreter → C1 with profiling → C2 — collecting profile data along the way so C2 can make aggressive speculative optimizations.

      Step-by-step thought process:

      1. "Interpretation is slow but starts immediately. Methods get an invocation counter — once it crosses a threshold (10K by default in tiered), the method is queued for compilation."
      2. "C1 (client compiler) — fast compilation, modest optimization. Produces decent code quickly. Adds profile data collection (branch counts, type profiles)."
      3. "C2 (server compiler) — slower compilation, aggressive optimization. Uses profile data from C1 to inline hot calls, eliminate dead branches, speculate on types."
      4. "Speculative optimizations can be wrong — C2 inserts uncommon traps. When a trap fires (e.g. a previously-unseen type), execution falls back to the interpreter and the method is re-profiled."
      5. "GraalVM and the Graal compiler are alternative C2 replacements written in Java itself — sometimes faster on certain workloads."

      Edge cases to mention:

      • AOT compilation (Java 9 jaotc, removed in Java 17; modern alternative is GraalVM native-image) compiles ahead of time — no warmup, but no speculative optimizations either JIT compilation happens on background threads — see warmup behavior in microbenchmarks
      • Use JMH for benchmarking — it handles warmup correctly so you measure peak JIT performance

      What NOT to say:

      • "Java is interpreted" — true initially, false after warmup
      • "C1 and C2 do the same thing" — they have very different optimization strategies

      Common follow-up: "What's a deoptimization trap and when does it happen?"

      88. Class loaders — delegation model

      Asked at: Most Spring rounds · Razorpay · Goldman

      Difficulty: Medium-Hard · Topic: JVM internals

      The question: "Explain the class loader hierarchy and the parent-first delegation model."

      The 30-second answer: Bootstrap loader (native, loads java. from rt.jar / modules) → Platform/ Extension loader (loads java.sql., etc.) → Application/System loader (loads classpath classes). Parent-first delegation: every loader asks its parent first; only loads itself if parent can't find the class. This prevents your code from shadowing core classes.

      Step-by-step thought process:

      1. "Three (or more) loaders form a chain. Bootstrap is the root — written in C++, loads core JDK classes."
      2. "Platform loader (Java 9+) — loads platform modules like java.sql, java.xml. Was called the extension loader pre-Java 9 with a different scope."
      3. "Application/System loader — loads your classpath and module path. This is what Class.forName(name) uses by default."
      4. "Delegation: when asked to load com.merchant.Order, the app loader first asks its parent (platform), which asks bootstrap. Bootstrap doesn't find it, returns null. Platform doesn't find it, returns null. App loader then searches its classpath."
      5. "Why parent-first? Security — if you put a java.lang.String on the classpath, your version is ignored because bootstrap loads its String first."

      Edge cases to mention:

      • App servers (Tomcat, WebLogic) use NON-standard child-first loaders for web apps — your app's classes shadow the server's. That's why version conflicts get weird
      • Each loader has its own namespace — com.foo.Bar loaded by loader A and the same class loaded by loader B are DIFFERENT classes, can't cast between them
      • OSGi and JPMS modules add their own layering on top of class loading

      What NOT to say:

      • "There's just one class loader" — depends on the app, but rarely true
      • "Class loading is single-threaded" — it's thread-safe but multi-threaded

      Common follow-up: "What's a ClassCastException across class loaders and how do you debug it?"

      89. Memory leaks in Java — common causes

      Asked at: Senior backend rounds · Razorpay · Goldman

      Difficulty: Medium-Hard · Topic: JVM internals

      The question: "What are the common causes of memory leaks in a long-running Java app?"

      The 30-second answer: ThreadLocal not removed (lingers in pool threads), static collections that grow unbounded (caches, listeners), unclosed resources (streams, connections), inner classes holding outer references, classloader leaks in hot-deploy environments, listener registrations never deregistered.

      Step-by-step thought process:

      1. "Java has GC, but 'leak' means reachable objects that should no longer be reachable. Common cause: a long-lived object holding a reference to something short-lived."
      2. "Static caches — static Map<String, Result> cache = new HashMap<>(); and you never evict. Use Caffeine or Guava cache with size or time eviction instead."
      3. "ThreadLocal — in a thread pool, if you set a ThreadLocal and never remove it, the value lives as long as the thread does. Add a finally { tl.remove(); }."
      4. "Listener registrations — EventBus.register(this) in a short-lived object that's never deregistered. The bus holds a strong reference forever."
      5. "Classloader leaks — hot-deploy app server unloads the webapp, but a Thread started by your code still holds a reference to the old classloader. Whole old classloader graph leaks."

      Edge cases to mention:

      • Use jcmd GC.heap_dump then analyze with Eclipse MAT for production heap dumps
      • WeakReference / SoftReference / PhantomReference give you control when caches must be GC-aware
      • Native memory leaks (NIO ByteBuffer, JNI) don't show up in heap dumps — use Native Memory Tracking (-XX:NativeMemoryTracking=summary)

      What NOT to say:

      • "Java has GC, so there are no leaks" — naive
      • "Just call System.gc() more often" — doesn't fix leaks

      Common follow-up: "You've got a heap growing 100MB per hour. How do you debug it?"

      90. String pool and interning

      Asked at: Most Java mid-level rounds

      Difficulty: Medium · Topic: JVM internals / Strings

      The question: "What is the String pool and what does .intern() do?"

      The 30-second answer: The String pool is a JVM-managed cache (in heap since Java 7) of String literals — "hello" in source code goes there automatically. .intern() puts a programmaticallycreated String into the pool (or returns the existing pooled instance if one matches). Two interned identical Strings can be compared with ==.

      Step-by-step thought process:

      1. "At class load, every String literal in your source becomes an entry in the pool. String a = "hi"; String b = "hi"; — both reference the same pooled String. a == b is true."
      2. " new String("hi") creates a new object on the heap, distinct from the pooled one. a == new String("hi") is false."
      3. " .intern() says 'either give me the pooled String equal to this one, or add this one to the pool and return it'. After interning, == works."
      4. "The pool was in PermGen pre-Java 7, in main heap since. Default pool table size 60013, tunable via -XX:StringTableSize."
      5. "When is interning worth it? When you have lots of duplicate strings in memory (e.g. parsed log lines, repeated dictionary keys). Saves memory but costs CPU on each intern call."

      Edge cases to mention:

      • == on Strings is almost always wrong — use .equals(). Only exception: comparing known-interned values like enum names
      • Java 9 introduced compact strings (byte[] instead of char[] for ASCII-only) — independent of the pool but cuts String memory by ~50%
      • For high-throughput interning, consider a ConcurrentHashMap -based custom intern rather than String.intern() — JDK's intern table is global

      What NOT to say:

      • "All Strings live in the pool" — only literals and intern'd ones; new String does not
      • "Intern is free" — has CPU cost; profile before sprinkling everywhere

      Common follow-up: "What's the difference between String a = "x" + "y" and String a = "xy"?"
