    Lecture 07 — Bean Lifecycle Explained

    21 sections · 3,733 words

    Lecture 07

    Scope evidence: "Bean Lifecycle Explained | @PostConstruct, @PreDestroy, Scopes & @Lazy" (playlist map, verified). The repo folder is a Maven project BeanLifeCycleDemo under package in.strikes (classes such as AppConfig, PaymentService, OrderService, CartService, UserService, A, B, Main) plus the matching lecture notes.

    A Spring bean is not created and forgotten; it is born, wired, prepared, used, and destroyed under the container's supervision. This lecture walks that journey: creation versus initialization, singleton versus prototype, and how @Lazy and @PostConstruct bend the order.

    1. What is Bean Lifecycle?

    In normal Java, when we create an object manually, we are responsible for everything:

    PaymentService paymentService = new PaymentService();

    We handle the complete object journey ourselves:

    create object
-> set required values
-> call required methods
-> clean up resources if needed

    In Spring, we usually do not create important application objects manually. We tell Spring which classes or methods to manage, using @Component or an @Bean method. The object becomes Spring's responsibility, and Spring will:

    • discover the bean;
    • create the object;
    • inject dependencies;
    • call lifecycle methods;
    • keep the bean ready;
    • destroy it when required.

    Important: Once a class is annotated with @Component or returned from an @Bean method, control of its construction and cleanup shifts from your code to the container.

    2. Simple Definition

    Bean lifecycle means the complete journey of a Spring-managed object from definition discovery until destruction. A Spring-managed object is called a bean, so "bean lifecycle" means how Spring creates, prepares, manages, and destroys a bean.

    Lifecycle concern Question Spring answers
    Discovery Which classes or methods should I manage?
    Creation When and how do I build the object?
    Preparation Who supplies dependencies, and when?
    Initialization Which startup logic should run before use?
    Usage How long should the same instance live?
    Destruction Who cleans up resources when the container closes?

    Golden rule: Lifecycle is a sequence of phases, not a single event, and each phase exists so that beans are valid and safe before the application touches them.

    3. Complete Bean Lifecycle Flow (Overview)

    container starts
-> reads configuration/annotations
-> creates BeanDefinition
-> instantiates bean
-> injects dependencies
-> calls Aware interfaces
-> runs initialization callbacks
-> bean ready
-> application uses bean
-> runs destruction callbacks
-> bean removed

    The early phases (container start, configuration read, BeanDefinition) run before any object exists. The middle phases (instantiation, injection, Aware, initialization) produce a usable bean. The final phases (destruction, removal) run at shutdown and differ by scope.

    4. Step 0 and Step 1: Container Starts and Bean Definition is Read

    Step 0: Spring container starts

    When we write new AnnotationConfigApplicationContext(AppConfig.class), we pass class metadata, not an object. Spring uses reflection to inspect that class and checks:

    • Does this class have @Configuration?
    • Does it have @ComponentScan?
    • Does it have @Bean methods?
    • Which package should be scanned?
    • Which bean definitions should be registered?

    Step 1: Bean definition is read

    Before creating objects, Spring collects metadata about beans. This metadata is called a BeanDefinition.

    Field Example value
    Bean class PaymentService
    Bean name paymentService
    Scope singleton
    Lazy false
    Dependencies check later
    Init method check later
    Destroy method check later

    At this stage the object is not necessarily created; Spring is only registering information. It needs BeanDefinition first because it builds a whole network (OrderService -> PaymentService -> PaymentGateway -> ApiClient), recording names, scopes, dependencies, laziness, and init or destroy methods.

    Spring can read bean definitions from three sources:

    1. Annotation-based configuration (@Configuration, @ComponentScan, @Component).
    2. Java-based @Bean configuration.
    3. XML-based configuration, for example <bean id="paymentService" class="in.strikes.PaymentService"/>.

    Important: BeanDefinition is metadata, not the bean. A definition can be registered yet never produce an object, for example a lazy or unrequested prototype.

    5. Step 2 and Step 3: Instantiation and Dependency Injection

    Step 2: Bean object is instantiated

    After reading the bean definition, Spring creates the actual object. This step is called instantiation, and the constructor is called.

    Instantiation  = object is created
Initialization = object is prepared after creation

    These are not the same. A common beginner mistake is thinking that object creation and initialization are the same thing.

    Step 3: Dependencies are injected

    After or during object creation, Spring supplies the required dependencies. This is dependency injection, and the exact timing depends on the type of injection.

    Injection type When the dependency arrives Timing relative to construction
    Constructor While creating the object Before the object is fully built
    Setter After creation, via a setter call After the object exists
    Field After creation, via reflection After the object exists

    Constructor injection flow for OrderService(PaymentService):

    Spring needs OrderService
-> OrderService needs PaymentService
-> Spring creates or finds PaymentService
-> passes it into the constructor

    Setter injection assigns the dependency after creation via a setter; field injection assigns it after creation via reflection.

    Interviewer's perspective: Field injection is common in examples, but constructor injection is preferred for clean, testable code: dependencies are mandatory and the object is valid from birth.

    6. Step 4: Aware Interfaces are Called

    Sometimes a bean wants to know about the container: its bean name, which BeanFactory created it, and which ApplicationContext it runs in. Spring provides this using Aware interfaces, which are callback interfaces Spring calls automatically at the right time.

    Common Aware interfaces are BeanNameAware and ApplicationContextAware. If MyBean is annotated @Component("myCustomBeanName") and implements both, the output idea is:

    1. Constructor called
2. BeanNameAware called
3. ApplicationContextAware called

    Two questions this step always raises:

    1. Why is the method called setBeanName() and not getBeanName()? Because Spring is giving the bean information; the direction is Spring container -> bean.
    2. If we call setBeanName() manually, it behaves like a normal Java method and does not change the name registered inside the container.

    Do we use Aware interfaces in normal business logic? Usually, no; they suit framework and infrastructure code. At this point the bean is created, dependencies injected, and Aware callbacks complete.

    Important: Aware callbacks are a read-only conversation from container to bean. They exist for infrastructure-style beans, not for ordinary service logic.

    7. Step 5: Initialization Callbacks

    Now Spring lets the bean run startup logic before use: the initialization phase. It can validate configuration, initialize a cache, check setup, prepare resources, fill a HashMap, or log startup state.

    There are three common ways to write initialization logic:

    1. @PostConstruct - a Jakarta annotation on a method; Spring calls the method once, after dependencies are injected. In Spring 6/7 use import jakarta.annotation.PostConstruct;. Without Spring Boot you may need the jakarta.annotation-api:3.0.0 dependency.
    2. InitializingBean - the bean implements a Spring interface and Spring calls afterPropertiesSet(). This works, but tightly couples the class with Spring.
    3. Custom initMethod - @Bean(initMethod = "start") names a method Spring calls after injection. This keeps the class free from Spring-specific interfaces.

    Initialization callback order, if all three are used together:

    @PostConstruct
-> InitializingBean.afterPropertiesSet()
-> custom initMethod
    Aspect @PostConstruct InitializingBean.afterPropertiesSet() Custom initMethod
    Where it lives Annotation on a method Interface implemented by the class Method named in @Bean(initMethod = ...)
    Coupling to Spring None (Jakarta annotation) Tight - class implements a Spring type None
    Runs After dependency injection After @PostConstruct Last of the three
    Typical choice Modern default Framework/legacy code Third-party classes you cannot annotate

    8. Step 6 and Step 7: Ready to Use and Destruction Callbacks

    Step 6: Bean is ready to use

    After initialization is complete the bean is fully ready and other beans can use it. For singleton beans, Spring stores the object and reuses the same instance again and again:

    Bean created
-> dependencies injected
-> initialization completed
-> bean ready

    Step 7: Destruction callbacks

    When the container shuts down, Spring lets beans clean up: the destruction phase. Cleanup can close a connection, stop a thread, release a file handle, flush data, or clear a resource.

    There are three common ways to write destruction logic:

    1. @PreDestroy - a Jakarta annotation; Spring calls the method before destroying the bean.
    2. DisposableBean - the bean implements the Spring interface and Spring calls destroy(); this couples the class with Spring.
    3. Custom destroyMethod - @Bean(destroyMethod = "stop") names a method Spring calls at shutdown.

    Destruction callback order, if all three are used together:

    @PreDestroy
-> DisposableBean.destroy()
-> custom destroyMethod
    Aspect Initialization callbacks Destruction callbacks
    When they run After dependency injection, before use When the container shuts down
    Purpose Prepare resources, validate, warm caches Release resources, flush, stop threads
    Methods @PostConstruct, afterPropertiesSet(), initMethod @PreDestroy, destroy(), destroyMethod
    Order @PostConstruct -> afterPropertiesSet() -> initMethod @PreDestroy -> destroy() -> destroyMethod
    Jakarta annotation jakarta.annotation.PostConstruct jakarta.annotation.PreDestroy

    Golden rule: Initialization is about becoming usable; destruction is about leaving cleanly. A bean that opens a resource in initialization should close it in destruction.

    9. Full Lifecycle Summary

    Putting every phase in order, the complete lifecycle is:

    1. Spring container starts.
    2. Spring reads configuration and annotations.
    3. Spring creates BeanDefinition.
    4. Spring instantiates the bean object.
    5. Spring injects dependencies.
    6. Spring calls Aware interfaces.
    7. Spring runs initialization callbacks (@PostConstruct, InitializingBean, custom initMethod).
    8. Bean is ready to use.
    9. Application uses the bean.
    10. Spring runs destruction callbacks (@PreDestroy, DisposableBean, custom destroyMethod).
    11. Bean is removed.

    Between Aware callbacks and initialization, the framework invokes BeanPostProcessor hooks (a "before initialization" pass), and another "after initialization" pass runs afterwards.

    Memory aid for the order, R-C-I-A-I-U-D:

    Read (BeanDefinition)
-> Create (instantiate)
-> Inject (dependencies)
-> Aware (callbacks)
-> Init (initialization callbacks)
-> Use (ready/used)
-> Destroy (destruction callbacks)

    Sentence mnemonic: "Real Coders Inject Aware, Init, Use, Destroy." The first letters trace the lifecycle from metadata to cleanup.

    Interviewer's perspective: Recite R-C-I-A-I-U-D, then name the three initialization and three destruction mechanisms, and you have answered most lifecycle questions.

    10. Singleton Bean Lifecycle

    By default, Spring beans are singleton scoped: Spring creates only one object for that bean and manages the complete lifecycle from creation to destruction.

    @Component
public class PaymentService {
    public PaymentService() { System.out.println("Constructor called"); }
    @PostConstruct public void init() { System.out.println("@PostConstruct called"); }
    @PreDestroy public void destroy() { System.out.println("@PreDestroy called"); }
}

    When the context starts:

    Constructor called
@PostConstruct called

    When the context closes:

    @PreDestroy called

    11. Prototype Bean Lifecycle

    Prototype means a new object is created every time the bean is requested.

    @Component
@Scope("prototype")
public class PaymentService {
    public PaymentService() { System.out.println("Constructor called"); }
}

    Requesting it twice with context.getBean(...) creates two different objects; p1 and p2 differ. The prototype flow is:

    container starts
-> BeanDefinition is read
-> no object usually created at startup
-> client requests prototype bean
-> Spring creates a new object
-> dependencies injected
-> Aware callbacks
-> initialization callbacks
-> Spring hands object to the client
-> Spring does not track it for normal destruction

    Singleton versus prototype lifecycle:

    Phase Singleton Prototype
    Object per One per bean One per request
    Created at startup Yes, by default (eager) Usually no
    Dependencies injected Yes Yes
    Aware callbacks Yes Yes
    Initialization callbacks Yes Yes
    Stored and reused by Spring Yes No
    Destruction callbacks by Spring Yes, on shutdown No
    Who owns the object afterwards Spring The caller

    Compact way to remember the difference:

    Singleton: Spring creates it, stores it, reuses it, destroys it.
Prototype: Spring creates it, prepares it, gives it to the caller;
           after that the caller is responsible for it.

    12. Prototype Destruction is Not Called by Spring

    A @Scope("prototype") PaymentService logs in its constructor, @PostConstruct init(), and @PreDestroy destroy(). Main gets one bean, then calls context.close(). Expected output:

    Constructor called
@PostConstruct called

    Usually, we will not see:

    @PreDestroy called

    Why does @PreDestroy not run for prototype beans? Once Spring hands a prototype to the caller it stops tracking it. Singletons are cached and destroyed on close; prototypes the caller may use, store, discard, or copy many times.

    Why not keep a list of every prototype? Storing them all forever would prevent garbage collection and cause memory leaks.

    Does context.close() destroy prototype beans? Usually no. It destroys tracked singletons, but prototypes already handed out are not automatically destroyed. Clean them manually:

    • close the resource manually;
    • use try-with-resources where possible;
    • avoid putting heavy resource cleanup responsibility inside prototype beans.

    Java can still garbage collect the prototype when unreferenced, but GC and Spring destruction callbacks are not the same thing.

    Important: @PreDestroy on a prototype bean is not a cleanup guarantee. GC and Spring destruction are different mechanisms; never rely on one to stand in for the other.

    13. Important Case: Singleton Depends on Prototype

    Consider OrderService (singleton) depending through its constructor on PaymentSession (prototype). OrderService is created once, so Spring creates one PaymentSession and injects it, and that same instance stays inside. A new object is not used for every method call.

    When the context closes, will Spring call @PreDestroy on PaymentSession? No, usually not. It is prototype scoped; Spring created and handed it over, and does not manage its destruction.

    Key learning:

    Prototype scope means: new object per request from Spring.
It does not mean: new object every time a singleton method runs.

    If a singleton needs a fresh prototype instance every time, use other approaches such as ObjectProvider, Provider, lookup method injection, or applicationContext.getBean().

    @Component
public class OrderService {
    private final ObjectProvider<PaymentSession> paymentSessionProvider;
    public OrderService(ObjectProvider<PaymentSession> paymentSessionProvider) {
        this.paymentSessionProvider = paymentSessionProvider;
    }
    public void createOrder() {
        PaymentSession session = paymentSessionProvider.getObject();
        System.out.println(session);
    }
}

    Interviewer's perspective: The classic "prototype injected into singleton" question - the prototype is resolved once at injection, and for fresh instances you inject ObjectProvider or use lookup method injection.

    14. @Lazy and Bean Lifecycle

    By default, singleton beans are eager: they are created when the container starts. If we mark a singleton @Lazy, Spring reads its bean definition but does not create the object immediately. Flow for a lazy singleton:

    container starts
-> BeanDefinition is registered
-> object is not created yet
-> bean is created only when someone asks for it

    So for a lazy singleton the BeanDefinition is read at startup, while object creation, dependency injection, and initialization happen later.

    Aspect Eager singleton (default) @Lazy singleton
    BeanDefinition read at startup Yes Yes
    Object created at startup Yes No
    Dependency injection timing At startup When first requested
    Initialization timing At startup When first requested
    Still a single instance Yes Yes

    Important: @Lazy changes when the bean is created, not how often. A lazy singleton is still a singleton; only its birth is postponed.

    15. @PostConstruct and Circular Dependency

    Consider a constructor cycle: A needs B, and B needs A. Spring cannot create either without the other, so constructor circular dependency fails.

    Where can @PostConstruct help? By letting each bean finish construction, then wire the back-reference. A is built with B; then @PostConstruct on A calls b.setA(this), while B holds A via an ordinary setter, not its constructor.

    Important: @PostConstruct runs after dependency injection, which is why it can complete a relationship that would deadlock in constructors. Prefer redesigning to avoid cycles.

    16. Myth vs Reality

    Myth Reality
    "Instantiation and initialization are the same" Instantiation creates the object; initialization prepares it afterwards. They are distinct phases.
    "Spring creates all beans immediately" Singletons are eager by default, but prototypes and @Lazy singletons are created later.
    "@PreDestroy always runs" It runs for managed singletons; handed-out prototypes are not tracked and are not destroyed by Spring.
    "Prototype means a new object per method call in a singleton" Prototype means a new object per request from Spring; an injected prototype in a singleton is resolved once.
    "Aware interfaces are needed in normal services" They are for framework and infrastructure code; ordinary business services rarely need them.
    "Calling setBeanName() manually renames the bean" It behaves like a plain Java method and does not change the name registered in the container.
    "Garbage collection equals Spring destruction" GC reclaims memory; Spring destruction callbacks release resources. They differ.

    17. Common Trap Questions

    Trap 1 - "Object creation is the same as initialization." Verdict: False. Creation is instantiation (constructor runs); initialization is the separate phase where @PostConstruct, afterPropertiesSet(), or the custom init method runs.

    Trap 2 - "Spring calls @PreDestroy for prototype beans automatically." Verdict: False, usually. Spring stops tracking a prototype once it hands it to the caller, so its destruction callbacks are not invoked on context close.

    Trap 3 - "A prototype injected into a singleton gives a new instance per method call." Verdict: False. The prototype is resolved once at injection; for fresh instances per call, inject ObjectProvider or use lookup method injection.

    Trap 4 - "context.close() destroys every bean, including prototypes already handed out." Verdict: False. It destroys tracked singletons; handed-out prototypes are not automatically destroyed.

    Trap 5 - "BeanDefinition means the bean object exists." Verdict: False. BeanDefinition is only metadata; for lazy beans and prototypes, object creation is deferred or may never happen.

    Trap 6 - "@Lazy makes the bean a prototype." Verdict: False. @Lazy changes when the bean is created, not its scope. The lazy bean is still a singleton unless declared otherwise.

    Trap 7 - "Calling setBeanName() yourself changes the registered bean name." Verdict: False. It is a normal method call; only Spring's own callback sets the actual container name.

    18. Points to Remember

    1. Bean lifecycle is the complete journey of a Spring-managed object from definition discovery to destruction.
    2. Step 0/1 run before objects exist: the container starts, inspects metadata via reflection, and registers BeanDefinitions.
    3. Instantiation (constructor) and initialization (@PostConstruct and friends) are different phases.
    4. Injection timing depends on type: constructor injection runs during creation; setter and field injection run after.
    5. Aware interfaces (BeanNameAware, ApplicationContextAware) are callbacks used mostly by framework and infrastructure code.
    6. Initialization order: @PostConstruct then afterPropertiesSet() then custom initMethod.
    7. Destruction order: @PreDestroy then destroy() then custom destroyMethod.
    8. Singletons are eager by default and fully managed: Spring creates, stores, reuses, and destroys them.
    9. Prototypes are created per request and not tracked for automatic destruction; clean them up manually.
    10. @Lazy delays creation of a singleton, and @PostConstruct can break a constructor circular dependency.

    19. Likely Interview Questions

    Question Crisp Answer
    What is the Spring bean lifecycle? The journey of a managed object: definition read, instantiation, injection, Aware callbacks, initialization, use, destruction, removal.
    What is a BeanDefinition? Metadata (class, name, scope, lazy flag, dependencies, init/destroy methods) registered before any object is created.
    Instantiation vs initialization? Instantiation creates the object (constructor); initialization prepares it afterwards (@PostConstruct, afterPropertiesSet(), init method).
    Name the three initialization callbacks and their order. @PostConstruct, then InitializingBean.afterPropertiesSet(), then a custom initMethod.
    Name the three destruction callbacks and their order. @PreDestroy, then DisposableBean.destroy(), then a custom destroyMethod.
    What are Aware interfaces for? Callbacks giving a bean container information such as its bean name or the ApplicationContext it runs in.
    Singleton vs prototype lifecycle? Singleton: one instance, stored, reused, destroyed by Spring. Prototype: new instance per request, not auto-destroyed.
    Why is @PreDestroy not called on prototype beans? After handing over the prototype, Spring stops tracking it; tracking all instances would prevent GC and cause leaks.
    Singleton depends on prototype - what happens? The prototype is resolved once at injection; for fresh instances per call use ObjectProvider or lookup method injection.
    What does @Lazy change in the lifecycle? It defers object creation, dependency injection, and initialization of a singleton until first requested.
    How does @PostConstruct help with circular dependency? It runs after injection, letting a bean complete a back-reference that would deadlock in constructors.
    Why does the bean name setter start with set? The container pushes information into the bean (Spring -> bean), so it sets rather than gets.

    20. Final Summary

    container starts -> read configuration/annotations -> create BeanDefinition
-> instantiate bean -> inject dependencies -> call Aware interfaces
-> run initialization callbacks -> bean ready -> application uses bean
-> run destruction callbacks -> bean removed
    • R-C-I-A-I-U-D: Read, Create, Inject, Aware, Init, Use, Destroy.
    • Singleton: one instance, eager by default, fully managed from creation to destruction.
    • Prototype: new instance per request, handed to the caller, not tracked for destruction.
    • @Lazy defers creation, injection, and initialization of a singleton until first use.
    • Aware interfaces and BeanPostProcessor hooks are extension points around initialization.
    • The singleton-depends-on-prototype case resolves the prototype once; use ObjectProvider for fresh instances.
    • @PostConstruct runs after injection and can break constructor circular dependencies.

    One-line takeaway: Spring Bean Lifecycle is not just object creation; it is the complete process through which Spring discovers, creates, prepares, manages, and destroys a bean, with singletons managed end to end and prototypes handed over with only their beginning managed.
