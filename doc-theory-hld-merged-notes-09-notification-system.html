    Notification System

    8 sections · 692 words

    Fan out push, SMS, email, and in-app notifications without blocking the caller.

    1. Clarifying Questions

    What types of notifications?

    • Push notification (mobile push).
    • SMS notification.
    • Email notification.
    • In-app notification.

    Real time or soft real time?

    • A real-time system sends the notification to the user immediately.
    • A soft real-time system tries to send as soon as possible, but there can be exceptions: the system is down, or the server is busy.
    • Answer: soft real time.

    Device type? iOS, Android, and web (Windows, macOS).

    2. Core Entities

    • Notification service.
    • Executor.
    • Create payload (API).
    • Templates.
    • Client.

    3. Back-of-the-Envelope Calculation

    QPS (read/write), storage unit, and bandwidth calculations.

    Assumptions:

    • Daily active users: 1 million.
    • One user receives 10 notifications, so total notifications = 1 million * 10 = 10 million/day.

    Storage:

    1 notification = 200 bytes (content, timestamp, userId, notificationId, etc.)
Total = 10 million * 200 bytes
      = 10 * 2^20 * 0.2 * 10^3
      = 10 * 2^20 * 0.2 * 2^10
      = 2^30 * 2
      = ~2GB/day

Store for 1 month = 2GB * 30 days = ~60GB

    Bandwidth:

    • Bandwidth is the maximum amount of data that can be transmitted through the network in a given time; it answers "how busy will our server be?".
    • Notification payload: 1KB (upload/download) covering headers, body, and request params.
    • DAU = 1 million; total notifications/day = 10 million; 1KB * 10 million = 10GB/day.
    Bandwidth = 10 million * 1KB / 86,400 seconds
          = 10 * 2^20 * 1 * 2^10 / 86.4 * 2^10
          = 0.115 * 2^20
          = 115 * 10^-3 * 2^20
          = 115 * 2^-10 * 2^20
          = ~115KB/sec

    Server: handle server scaling and increasing server RAM.

    4. API Interactions

    The notification service needs user information. The user store is SQL with fields like userId, Name, mobile.

    1. Retrieve user information

    GET : /fetchuser/{{userId}}
Response: 200 OK
{
  "userId": 101,
  "userName": "Aditya",
  "notificationPermissions": {
    "push": true,
    "email": true,
    "sms": false
  }
}

    2. Send notification

    POST : /sendNotification/{{userId}}
Body:
{
  "from": null,
  "to": "202",
  "subject": "",
  "content": "",
  "type": "push/email/sms"
}
Response: 200 OK
{
  "status": "sent",
  "notificationId": "301"
}

    3. Fetch notification history (optional)

    GET : /fetchAllNotifications
Query params / filters:
  date: from, to
  type: email/sms etc.
Response: 200 OK
[
  { "status": "sent", "content": "" },
  { "status": "sent", "content": "" }
]

    5. Basic Design

    The notification types map to third-party providers:

    Type Provider
    Push - iOS (Apple) APNs (Apple Push Notifications)
    Push - Android FCM (Firebase Cloud Messaging)
    SMS Twilio, Nexmo, etc.
    Email MailChimp, Sendgrid, etc.

    Components: services 1-3, cron jobs, the notification server, and the providers (APNs, FCM, Twilio, MailChimp), each reaching the client.

    Flow:

    1. Any service (microservice, cron job) triggers notifications and sends them to our notification server.
    2. The notification server has APIs that build the payload for the third-party APIs.
    3. The third-party service actually sends the notification to the client.

    6. Problems with the Initial Design

    1. SPOF (single point of failure) - the notification server must be scaled.
    2. Hard to scale.
    3. Retry mechanism missing.
    4. Tight coupling (synchronous).

    7. Shift to Async

    Message queues are placed in front of every provider, with workers consuming them:

    • Publisher / service 1 -> MQ -> workers -> APNs -> client.
    • Similarly for FCM, Twilio, and MailChimp.

    • A notification DB and cache back the services.

    • Cache and DB hold user info and notification templates.

    • MQ removes the dependency between third-party APIs and our notification server, so the service is now async.

    8. Improvements

    1. Notification templates.
    2. Notification settings at user level: a user can turn a particular type of notification on or off.
    3. Rate limiting.
    4. API authentication.
    5. Monitoring logic.
    6. Notification log.

    The improved diagram adds rate limiting, authentication, cache, notification DB, notification log, and an analytics service.
