      AI / RAG — Retrieval & Hybrid Search

      0 sections · 392 words

      50. How does hybrid search work?

      Two parallel queries. Vector: embed the query with the same model used at ingestion, then ORDER BY embedding <=> ?::vector — pgvector's cosine-distance operator (lower = closer), returning top-20. Keyword: Postgres full-text with to_tsvector / plainto_tsquery and ts_rank, top-20. Then I merge the two ranked lists with Reciprocal Rank Fusion and return top-K (default 5).

      51. Why hybrid instead of pure vector?

      Pure vector nails semantic paraphrase but misses exact literals — product names, ticket IDs, version numbers, error codes — because those aren't semantically "close" to anything. Pure keyword nails literals but misses paraphrase. Hybrid gets both, which is why production RAG systems use it.

      52. Explain RRF and why not just add the raw scores?

      Reciprocal Rank Fusion: score(chunk) = Σ 1/(rank + k) across both lists, k=60 (Cormack et al. 2009). You can't add raw scores because cosine similarity and ts_rank are on totally different, non-comparable scales — you'd need normalization, which is fragile. Ranks are comparable. RRF rewards chunks that appear high in either list and especially in both, and k=60 dampens the dominance of a single #1 hit so one list can't monopolize the result.

      53. What does the <=> operator do and why is it fast?

      It's pgvector's cosine-distance operator. The HNSW index on chunk_embeddings turns the nearest-neighbor search from O(n) linear scan into roughly O(log n) approximate search. HNSW is a navigable small-world graph — you hop through the graph toward the query vector instead of comparing against every row.

      54. Why pgvector instead of Pinecone/Qdrant?

      At this scale — thousands of chunks, not millions — pgvector is plenty and it's one less piece of infrastructure. Chunk metadata already lives in Postgres, so co-locating vectors means no cross-DB lookup in the RRF merge. The honest trade-off: at tens of millions of vectors, a purpose-built vector DB has better-tuned ANN indexes and query performance. I'd migrate when scale justifies the operational cost, not before.

      55. Where do you filter by tenant in search?

      In the SQL itself: both the vector and keyword queries have WHERE d.tenant_id = ? AND d.status = 'COMPLETED'. Tenant isolation is enforced at the query layer, and the tenant comes from the gateway header (validated JWT), never from the request body.
