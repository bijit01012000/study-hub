    Consistent Hashing

    6 sections · 452 words

    Add a server, move little. Data & Storage, concept 11 of 36.

    The Idea

    Consistent hashing spreads keys across servers so that adding or removing one server only moves a small fraction of keys, not all of them. Servers and keys are both placed on a ring using a hash function. A key belongs to whichever server sits next, going clockwise.

    A key's spot on the ring: servers N1, N2, N3, and N4 sit on the ring, and a key belongs to the next server clockwise from it on the ring.

    Plain hash-mod-N reshuffles almost every key the moment a server is added or removed. This ring trick is exactly the fix. Virtual nodes, where each real server appears at several points around the ring, keep the load spread evenly instead of by luck.

    Watch Out For

    • Too few virtual nodes per server can still leave load noticeably uneven, since it depends on where each server happens to land on the ring.
    • Consistent hashing solves rebalancing, not replication. A separate mechanism is still needed to store each key on more than one server for durability.

    Where You Will See It

    • DynamoDB, whose original design (Amazon's Dynamo paper) popularized consistent hashing for distributed storage.
    • Cassandra, which uses it to place partitions across the cluster.
    • Content delivery networks and load balancers, where the same client should keep hitting the same cache server.

    How It Connects

    • Sharding: consistent hashing is the smarter, rebalance-friendly version of hash-based sharding.
    • Load Balancing: the algorithm behind the same client, same server routing option.
    • Replication: usually layered on top, so each ring position is actually backed by more than one physical server.

    Follow-Up Questions

    1. A cache cluster has 4 servers, addressed with hash(key) mod 4. A 5th server is added. What happens? Almost every key remaps to a different server, since mod 5 gives completely different answers than mod 4. That is the exact problem consistent hashing avoids.

    2. The same cluster uses consistent hashing instead. A 5th server is added. What happens? Only the keys in the slice of the ring the new server takes over need to move. Everything else stays put.

    3. A server is removed from the ring. What happens to its keys? They fall to the next server clockwise, and only that server's load increases.

    4. Why does consistent hashing use virtual nodes instead of placing each real server once? One placement per server can leave load uneven by luck. Multiple virtual nodes per server spread the load evenly.

    Recall It As

    Servers and keys share one ring. A key belongs to whoever is next clockwise.
