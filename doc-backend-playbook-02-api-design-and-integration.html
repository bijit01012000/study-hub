    API design and integration

    9 sections · 3,555 words

    Module 02 - 9 questions - 1 practical drill

    Design contracts that remain correct through retries, change and failure.

    APIs are contracts between teams. This round tests whether you designed the contract on purpose - versioning, idempotency, error semantics, backward compatibility - or just wrote CRUD endpoints and hoped. The follow-ups always chase the failure path: timeouts, retries, duplicates.

    Inside this module: Contracts & versioning - Idempotency - Failure semantics - Integration choices

    A request travels CLIENT -> API -> DEPENDENCY within a 200ms budget, and a retry carries the same key. Retries are part of the contract. Design the duplicate path before production does it for you.

    Q2.1 - Tell me about an API you designed.

    What it really tests: Whether you designed a contract deliberately, thinking about consumers, failure, and evolution - or just exposed a database.

    Weak answer: "We designed a REST API for our order service using standard CRUD endpoints and JSON payloads, following best practices."

    Why it fails: - "Standard CRUD" and "best practices" are filler that describe nothing specific. - No consumer named, so no requirement drove the design. - No mention of versioning, errors, idempotency, or evolution. - "We designed" hides who decided what. - No failure path considered at all.

    Follow-up ladder: 1. TECHNICAL - Who consumed the API? - Whether a real consumer shaped the design. 2. TRADEOFF - How was the contract decided? - Deliberate contract negotiation vs convenience. 3. FAILURE - What happened after a timeout? - Failure-path design. 4. TECHNICAL - How was duplicate processing prevented? - Idempotency awareness. 5. FAILURE - What failed in production? - Real operational experience. 6. REFLECTION - What would you redesign? - Hindsight and judgement.

    Answer framework: 1. Consumer 2. Requirement 3. Constraint 4. Personal responsibility 5. Design decision 6. Alternative rejected 7. Failure handling 8. Production outcome 9. Reflection

    Rejection signals: - Cannot name who consumed the API. - Cannot describe any alternative considered and rejected. - No answer for what happens on failure or timeout. - Never uses "I" to describe a specific decision.

    Model answer skeleton: I designed the reservations API consumed by our web checkout and, later, a partner mobile app. The core requirement was that a 'reserve seat' call had to be safe to retry, because mobile networks dropped and clients retried aggressively.

    I made the POST idempotent with a client-supplied Idempotency-Key header; the server stored the key with the first response for 24 hours and replayed it on retries, so a duplicate reserve returned the original reservation instead of a second one.

    I rejected keying idempotency on request-body hashing because two genuinely different reservations could hash-collide on identical payloads.

    In production our first bug was that we didn't expire the keys, so the table grew unbounded; I added a TTL and a nightly cleanup.

    If I redid it I'd return Retry-After on our 429s from day one instead of bolting it on after the partner hammered us.

    Q2.2 - How do you version an API without breaking existing clients?

    What it really tests: Understanding that clients you don't control can't be forced to upgrade, and how to evolve a contract safely.

    Weak answer: "We put a version number in the URL like /v1 and /v2. When we made changes we'd release a v2 and tell clients to migrate."

    Why it fails: - Stops at URL versioning without discussing when a new version is actually needed. - No distinction between breaking and non-breaking changes. - "Tell clients to migrate" ignores clients that never do. - No deprecation or sunset strategy.

    Follow-up ladder: 1. TECHNICAL - What change is breaking versus additive? - Precise understanding of compatibility. 2. MEASUREMENT - How long did you support the old version, and how did you know when to kill it? - Data-driven deprecation. 3. TRADEOFF - Why URL versioning over header or media-type versioning? - Considered alternatives. 4. FAILURE - A client depended on a bug you fixed - now what? - The classic Hyrum's Law situation.

    Answer framework: 1. Breaking vs additive rule 2. Default to additive 3. When a new version is justified 4. Versioning mechanism chosen 5. Deprecation policy 6. How you measured remaining old-version traffic 7. Sunset decision

    Rejection signals: - Thinks every change needs a new version. - No rule for what counts as breaking. - Never measured old-version usage before removing it. - No plan for clients that won't migrate.

    Model answer skeleton: My rule was additive-by-default: adding an optional field or a new endpoint never breaks a client that ignores unknown fields, so those went out without a version bump.

    I only cut a new major version for genuinely breaking changes - removing a field, changing a type, tightening validation.

    We used URL versioning (/v2/) because it was trivial for our partners to see and test in a browser, over header versioning which was cleaner but invisible and harder to debug on their side.

    When we shipped v2 we kept v1 alive and instrumented per-version request counts; we only sunset v1 once it dropped below 0.5% of traffic and we'd emailed the three remaining partners.

    The trickiest case was a client relying on a leading-zero formatting bug - we treated the fix as breaking, gated it behind v2, and left v1 returning the old format until they migrated.

    Q2.3 - A client calls your API, times out, and retries. Walk me through what your server does.

    What it really tests: Whether idempotency and duplicate-handling are designed in, or the system silently double-processes.

    Weak answer: "The retry would just come in as a new request and get processed. Usually that's fine because most of our operations were reads."

    Why it fails: - Assumes retries are harmless without checking write semantics. - No idempotency mechanism for the writes that aren't safe. - Doesn't consider the timeout might have fired after the server committed. - No dedupe, no idempotency key.

    Follow-up ladder: 1. FAILURE - The first request actually succeeded but the response was lost - what does the retry do? - The hard case that breaks naive designs. 2. TECHNICAL - How do you make a POST idempotent? - Concrete mechanism. 3. TRADEOFF - Where do you store the idempotency key and for how long? - Practical implementation detail. 4. MEASUREMENT - What status code does the replay return? - Contract precision.

    Answer framework: 1. Classify the operation 2. Safe-to-retry check 3. Idempotency key on unsafe writes 4. Storage and TTL of keys 5. What the replay returns 6. Distinguish 'in progress' from 'completed' 7. Guard against concurrent duplicates

    Rejection signals: - Assumes all retries are safe. - No mechanism for the lost-response case. - Cannot describe idempotency key storage. - Confuses idempotency with retries themselves.

    Model answer skeleton: First I classify: GETs and PUTs are naturally idempotent, so a retry is fine. For a POST that creates a charge, a naive retry double-charges, so I require an Idempotency-Key.

    On the first request I insert the key into a table inside the same transaction that does the work; if the client retries and the response was lost, the retry hits a unique-constraint violation on the key, and I return the stored original response with the original 201 rather than re-executing.

    To handle the case where the first request is still in flight, the key row has a status - in_progress returns a 409 or makes the retry wait, completed replays the result.

    I keep keys for 24 hours, which comfortably covers client retry windows, and expire them to bound the table.

    That way 'timed out and retried' always converges to exactly one charge.

    Q2.4 - How do you design error responses so that clients can actually handle them?

    What it really tests: Whether errors are part of the contract or an afterthought - machine-readable codes, right status, no leaking internals.

    Weak answer: "We returned appropriate HTTP status codes and an error message in the JSON body so the client knew what went wrong."

    Why it fails: - "Appropriate status codes" with no examples of the tricky ones (409, 422, 429). - Human-readable message only - nothing a client can branch on programmatically. - No stable machine-readable error code. - No mention of not leaking stack traces or internal detail.

    Follow-up ladder: 1. TECHNICAL - How does a client distinguish 'retry this' from 'never retry this'? - Actionable error semantics. 2. TRADEOFF - 400 vs 422 vs 409 - when each? - Precise status semantics. 3. TECHNICAL - How do you return multiple validation errors at once? - Practical DX design. 4. FAILURE - What did you make sure never appeared in an error body? - Security and information leakage.

    Answer framework: 1. Status code taxonomy 2. Stable machine code field 3. Retryable flag or convention 4. Human message separate from code 5. Validation error shape 6. Correlation/trace id 7. What you redact

    Rejection signals: - Only human-readable messages, no codes. - Returns 200 with an error inside the body. - Leaks stack traces or SQL to clients. - No way for clients to tell retryable from fatal.

    Model answer skeleton: I treat the error body as part of the contract: every error returns the right HTTP status plus a stable code string, a human message, and a trace_id.

    The code is what clients branch on - INSUFFICIENT_STOCK never changes even if we reword the message.

    I map 400 to malformed syntax, 422 to well-formed but semantically invalid input, 409 to a state conflict like a duplicate reservation, and 429 to rate limiting with a Retry-After.

    For validation I return 422 with an array of field-level errors so the client can highlight every bad field in one pass instead of round-tripping.

    I make sure stack traces, SQL, and internal hostnames never reach the client - those go to logs keyed by the same trace_id so support can correlate without us leaking internals.

    Q2.5 - When would you choose gRPC over REST, or the other way around?

    What it really tests: Whether you can justify a protocol choice by constraints rather than fashion.

    Weak answer: "gRPC is faster because it uses binary and HTTP/2, so for high-performance stuff we'd use gRPC and REST for everything else."

    Why it fails: - "Faster" as the whole justification, no numbers or context. - Ignores tooling, browser support, debuggability trade-offs. - No mention of streaming, contracts, or codegen. - Binary "internal vs external" split stated as a slogan, not reasoned.

    Follow-up ladder: 1. TECHNICAL - Why is gRPC awkward from a browser? - Knows gRPC-web and its limits. 2. TRADEOFF - What do you lose in debuggability with gRPC? - Honest downsides. 3. TECHNICAL - How do Protobuf field numbers help with versioning? - Schema evolution depth. 4. MEASUREMENT - When would streaming actually change your choice? - Concrete use-case fit.

    Answer framework: 1. Consumer type (browser/partner/internal) 2. Latency and payload constraints 3. Streaming needs 4. Contract and codegen value 5. Debuggability cost 6. Ecosystem/tooling 7. Decision and rejected option

    Rejection signals: - "gRPC is just faster" with no context. - Doesn't know browser limitations. - No awareness of the debuggability trade-off. - Picks by trend, not constraint.

    Model answer skeleton: I default to REST for anything a browser or an external partner touches, because it's debuggable with curl, cacheable, and every client can speak it.

    I reach for gRPC on internal service-to-service paths where the strong Protobuf contract and generated clients kill a whole class of integration bugs, and where the binary framing and HTTP/2 multiplexing matter - on one high-fanout path it cut serialization overhead and p99 noticeably versus JSON.

    The costs I accept with gRPC are real: it's painful from a browser without gRPC-web and a proxy, and you can't just eyeball traffic, so I lean harder on tracing.

    Protobuf's numbered fields are a genuine versioning win - you add a field with a new number and old clients ignore it - so schema evolution is safer than with loosely-typed JSON.

    So the rule is consumer and contract strength decide it, not raw speed.

    Q2.6 - How did you handle pagination on a large collection endpoint?

    What it really tests: Whether you understand offset pagination's failure modes under concurrent writes and at depth.

    Weak answer: "We used offset and limit - page and page size parameters - so clients could fetch data in chunks. It worked fine for our use case."

    Why it fails: - Offset pagination without mentioning its drift/duplication under inserts. - No awareness of deep-offset performance collapse. - "Worked fine" with no scale stated. - No cursor alternative considered.

    Follow-up ladder: 1. FAILURE - A row is inserted while a client pages - what does the client see? - Understanding of offset drift. 2. TECHNICAL - What happens to OFFSET 1000000 performance-wise? - Deep pagination cost. 3. TRADEOFF - How does cursor pagination fix that, and what does it cost? - Cursor mechanics and limits. 4. REFLECTION - How would a client jump to page 500 with cursors? - Honest about cursor's weakness.

    Answer framework: 1. Access pattern (feed vs jump-to-page) 2. Offset drawbacks under inserts 3. Deep-offset cost 4. Cursor design (stable sort key) 5. What cursors give up 6. Choice justified by pattern 7. Page-size limits and defaults

    Rejection signals: - Only knows offset, unaware of its drift. - No idea why deep offsets are slow. - Cannot describe a cursor. - Ignores the sort-stability requirement for cursors.

    Model answer skeleton: For our activity feed I moved from offset to cursor pagination because offset broke under concurrent inserts - a new event at the top pushed everything down, so a client fetching page 2 saw an item it already saw on page 1.

    Offset also died at depth: OFFSET 100000 still scans and discards 100k rows, so deep pages got slow.

    I used a cursor built from (created_at, id) - the client passes the last-seen tuple and I query WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20, which is index-friendly and stable under inserts.

    The cost I accepted is that cursors can't jump to an arbitrary page 500, but a feed doesn't need that - nobody deep-links to page 500 of a feed.

    For an admin table where users genuinely wanted numbered pages, I kept offset but capped it and pushed heavy users to filters instead.

    Q2.7 - Two services need to stay in sync. Do you make a synchronous call or publish an event? Walk me through the trade-off.

    What it really tests: Whether you understand coupling, and that synchronous calls chain failures while events add eventual-consistency complexity.

    Weak answer: "We'd just call the other service's API directly since it's simpler and we get an immediate response. Events are more complex so we avoided them."

    Why it fails: - Never weighs the failure coupling a synchronous call creates. - "Events are complex so we avoided them" - dismisses without reasoning. - No mention of what happens when the callee is down. - No sense of consistency requirements driving the choice.

    Follow-up ladder: 1. FAILURE - The downstream service is down during your call - what does the user see? - Failure coupling awareness. 2. TECHNICAL - With events, how do you handle the consumer being down for an hour? - Durability and replay. 3. TRADEOFF - Which path can the user tolerate being eventually consistent? - Mapping consistency need to mechanism. 4. TECHNICAL - How do you avoid the dual-write problem publishing an event after a DB commit? - Outbox pattern awareness.

    Answer framework: 1. Consistency requirement 2. Latency/user-facing need 3. Failure coupling of sync 4. Durability of async 5. Dual-write hazard and outbox 6. Choice per path 7. How you'd monitor the async lag

    Rejection signals: - Always picks sync for simplicity, ignores coupling. - No idea what happens when the callee is down. - Unaware of the dual-write problem. - Cannot tie the choice to a consistency requirement.

    Model answer skeleton: I decide by whether the caller needs the result to proceed and how much it can tolerate staleness.

    Checkout needs a synchronous stock check because it can't confirm an order without knowing stock exists - but I accept that this couples checkout's availability to inventory's, so I wrap it in a timeout and a circuit breaker.

    For 'order placed, now update the loyalty points and send the email', I publish an event, because the user doesn't need points updated in the same 50ms and the loyalty service being down for an hour shouldn't fail the order - the event sits durably in Kafka and is processed when it recovers.

    The trap with events is the dual-write: if I commit the order then publish and the publish fails, they diverge, so I use the transactional outbox - write the event to an outbox table in the same DB transaction and relay it to Kafka separately.

    I'd watch consumer lag as the health signal for the async path.

    Q2.8 - How do you protect an API from a client that starts sending ten times its normal traffic?

    What it really tests: Rate limiting, quotas, and fair-use design - protecting the system and other tenants.

    Weak answer: "We'd add rate limiting to cap how many requests they can make, maybe using a library, and return an error if they went over."

    Why it fails: - No algorithm named (token bucket, sliding window). - No dimension - per user, per IP, per API key? - Doesn't mention 429 or Retry-After. - Ignores distributed rate-limiting across multiple servers.

    Follow-up ladder: 1. TECHNICAL - Token bucket vs sliding window - which and why? - Algorithm understanding. 2. TECHNICAL - You have 10 API servers - where does the counter live? - Distributed limiting with Redis. 3. MEASUREMENT - What do you return, and how does the client know when to retry? - Correct 429 + Retry-After contract. 4. TRADEOFF - How do you avoid one noisy client starving the others? - Fairness / per-tenant isolation.

    Answer framework: 1. Dimension to limit on 2. Algorithm choice 3. Where the counter lives (shared store) 4. Burst vs steady handling 5. Response and Retry-After 6. Per-tenant fairness 7. Graceful degradation vs hard reject

    Rejection signals: - No algorithm, just "a library". - Counter is per-server, so limits don't hold in aggregate. - Returns 500 or 200 instead of 429. - No per-tenant isolation.

    Model answer skeleton: I rate-limit per API key, not per IP, because our clients sat behind shared NATs and IP-level limiting punished innocent users.

    I used a token-bucket algorithm because it allows short legitimate bursts while capping the sustained rate, implemented in Redis so the count is shared across all our API servers - a per-server counter would let a client do N times the limit by spreading requests.

    When a client exceeds the bucket, I return 429 with a Retry-After header so well-behaved clients back off precisely instead of hammering.

    To stop one tenant starving others, each key has its own bucket, so a misbehaving client only exhausts its own quota.

    For internal callers I preferred shedding load gracefully - degrade to cached data - over hard rejects, but for external abuse a hard 429 was the right call.

    Q2.9 - [DRILL] Write the full contract for a single POST /payments endpoint: request shape, success response, and every error response with its status code and machine code.

    What it really tests: Forces the candidate to think in contracts and failure paths, not happy-path CRUD.

    Weak answer: N/A - drill. A weak attempt lists only the 200 case and a generic 400.

    Why it fails: - Only happy path plus one vague error. - No idempotency key in the request. - No 409/422/429 distinction. - Error bodies have no stable machine code.

    Follow-up ladder: 1. TECHNICAL - Where's the idempotency key, and what does a replay return? - Idempotency baked into the contract. 2. FAILURE - Which of your errors is retryable and how does the client tell? - Actionable error design. 3. MEASUREMENT - What's in the response that lets support trace a failed call? - Observability in the contract.

    Answer framework: 1. Request fields + idempotency key 2. 201 success shape 3. 422 validation array 4. 409 duplicate/conflict 5. 402/422 for declined 6. 429 with Retry-After 7. 5xx retryable 8. trace id in every response

    Rejection signals: - Only documents the success case. - No idempotency in the request. - Errors carry no stable codes. - No trace id anywhere.

    Model answer skeleton: Drill output: POST /payments takes { amount, currency, source_id, order_id } plus a required Idempotency-Key header. 201 returns { payment_id, status: 'captured', trace_id }.

    A replay of the same key returns the original 201 body, not a new payment. 422 returns { code: 'INVALID_CURRENCY', errors: [{field, message}], trace_id } for well-formed-but-invalid input. 409 { code: 'DUPLICATE_ORDER', trace_id } if that order_id already has a captured payment under a different key. 402 { code: 'CARD_DECLINED', decline_reason, trace_id } - not retryable without a new source. 429 with Retry-After for rate limiting. 503 { code: 'PROCESSOR_UNAVAILABLE', trace_id } is the only safe-to-retry error, since the processor call may not have landed.

    Every response, success or failure, carries trace_id so support can find the exact call in logs.
