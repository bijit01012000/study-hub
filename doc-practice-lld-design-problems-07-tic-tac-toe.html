    Design a Tic-Tac-Toe Game

    15 sections · 2,022 words

    LLD Design Problems, problem 07 of 20.

    The Ask

    Build

    • An n x n board, default 3 x 3; win on k in a row, k = n by default.
    • Two players alternate, each drops their mark (X / O) on an empty cell.
    • After each move decide: this player wins, board full (draw), or play on.
    • The win check is O(1) per move, not a board rescan.
    • A player may be a human or a bot; a Player holds a PlayingPiece.
    • Live board and a move log for the display.
    • reset() starts a fresh game on the same board.

    Skip

    • A minimax / unbeatable AI (the follow-up).
    • Network or online multiplayer.
    • Arbitrary non-square boards.
    • A graphical UI.
    • Persistence, accounts.

    Our Model

    Game to board to cells. The board carries a signed counter per row, per column and for the two diagonals, so a move updates at most four counters and the win test is O(1).

    Actors and classes

    • Player — name: String, piece: PlayingPiece; takeTurn(Board b): Move (human reads r, c; bot calls bot.pick(b)).
    • Game (the context) — board: Board, players: Player[2], turn: int, winner: Player, state: GameState; move(int r, int c, Player p): Result, reset(): void (place, bump counters, isWin, flip).
    • Board — n: int, k: int, filled: int, cells: Cell[n][n], rowCount: int[n], colCount: int[n], diag: int, antiDiag: int, win: WinStrategy; isWin(int r, int c, int mark): boolean, isFull(): boolean, place(r, c, mark), cell(r, c): Cell.
    • Cell — row: int, col: int, mark: Mark = EMPTY; isEmpty(): boolean, set(PlayingPiece), clear().
    • PlayingPiece — mark: Mark (X or O); sign(): int (+1 for X, -1 for O).
    • Move (value record) — row: int, col: int, piece: PlayingPiece, by: Player, delta: the up-to-4 counters it moved.
    • GameState (interface) — advance(Game g): GameState; in progress -> won on isWin, draw on isFull. States: InProgress, Won, Draw.
    • WinStrategy (interface) — check(Board b, Move last): boolean; runs after every move, reads the counters, never the grid.
    • BoardObserver (interface) — onMove(Move m): void; ConsoleView, MoveLog, ScoreBoard.

    The three win policies

    • CounterCheck -> abs(a touched counter) == n, O(1).
    • LineScan -> walk the last move's row, col, 2 diagonals, O(n).
    • FullScan -> every line, every move, O(n*n).

    Same seam, only the cost differs.

    The states

    • InProgress -> take moves, alternate.
    • Won -> freeze, expose the winner.
    • Draw -> board full, no line of n.

    move() is a no-op unless InProgress.

    The four counters

    X adds +1, O adds -1; a full row, column or diagonal has magnitude n. A move touches at most four counters.

    Key operations

    1. move(int r, int c, Player p): Result — rejects an off-board or occupied cell before touching state. Places the mark, bumps the up-to-four counters, asks isWin, then isFull. Returns WIN / DRAW / NEXT / OCCUPIED / OFF_BOARD. A no-op once the game is over.
    2. isWin(int r, int c, int mark): boolean — the O(1) check. Looks only at the counters the last move moved: abs(rowCount[r]), abs(colCount[c]), and a diagonal when the cell is on one. True when any equals n. Never walks the grid.
    3. isFull(): boolean — filled == n * n. Tested only after isWin returns false, so a winning last move is never miscounted as a draw.
    4. reset(): void — clears every cell, zeroes the 2n + 2 counters and filled, and sets the state back to InProgress. Same Board, fresh game.

    win when abs(a touched counter) == n; draw when filled == n*n and no line hit n. Place: s = (mark == X) ? +1 : -1; row[r] += s; col[c] += s; if (r == c) diag += s; if (r+c == n-1) anti += s;. IsWin: abs(row[r]) == n || abs(col[c]) == n || (r == c && abs(diag) == n) || (r+c==n-1 && abs(anti) == n).

    The One Run to Hold in Your Head

    X holds (0,0) and (0,1); O holds (1,0) and (1,1). X plays (0,2). Walk move(): check the cell, bump rowCount[0] to +3, colCount[2], antiDiag, then test abs(rowCount[0]) == 3. Which objects touched the turn?

    After the move: rowCount[0]: +2 -> +3, colCount[2]: 0 -> +1, r + c = 2 = n-1 so antiDiag +1, r != c so the main diag is untouched. 3 counters moved. The grid is never read.

    The Change

    They ask the machine to play. An AiPlayer supplies a Minimax MoveStrategy to a Player: list the empty cells, score each with minimax and alpha-beta, return the best Move. It only reads the board and the win rule; not one existing class changes. Strategy, a second time on this sheet.

    What the Picture Can't Show

    The incremental update. The four counter arrays live on the Board. Every move mutates at most four of them in place and nothing re-derives them from the grid. reset() zeroes all 2n + 2. That is the whole trick.

    If They Make You Code It

    move and isWin:

    class Game {                                     // the context
    final Board board; final Player[] players;
    int turn = 0; GameState state = IN_PROGRESS;
    Player winner;

    Result move(int r, int c, Player p) {
        if (state != IN_PROGRESS) return Result.OVER;
        if (r < 0 || r >= board.n ||
            c < 0 || c >= board.n) return Result.OFF_BOARD;
        Cell cell = board.cell(r, c);
        if (!cell.isEmpty()) return Result.OCCUPIED;
        int mark = p.piece().sign();             // +1 X, -1 O
        cell.set(p.piece()); board.filled++;
        board.rowCount[r] += mark;               // at most 4 counters
        board.colCount[c] += mark;
        if (r == c) board.diag += mark;
        if (r + c == board.n - 1) board.antiDiag += mark;
        if (board.isWin(r, c, mark)) {           // O(1), last move
            state = WON; winner = p; return Result.WIN;
        }
        if (board.filled == board.n * board.n)   // full
            { state = DRAW; return Result.DRAW; }
        turn ^= 1;                               // flip the player
        return Result.NEXT;
    }
}

class Board {                                    // grid + the four counters
    final int n, k; int diag, antiDiag, filled;
    final int[] rowCount, colCount;

    boolean isWin(int r, int c, int mark) {      // CounterCheck
        return Math.abs(rowCount[r]) == n
            || Math.abs(colCount[c]) == n
            || (r == c && Math.abs(diag) == n)
            || (r + c == n - 1 && Math.abs(antiDiag) == n);
    }
}

    The Four Hazards

    1. Rescanning the whole board every move. After a move you only need the line the move is on. Walking all n rows, n columns and both diagonals every turn is O(n*n) work for an O(1) answer, and it gets worse as n grows.
    2. Draw called before the win. Move nine fills the board and can also complete a line. Test the last move for a win first, the full board second. Reverse the order and a winning final move is scored a draw.
    3. A hardcoded list of winning lines. Writing out all eight winning triples works for 3x3 and only 3x3. Ask for a 5x5 board or four in a row and the list is silently wrong.
    4. A move on an occupied or off-board cell. If move() bumps the counters before it checks range and emptiness, one bad call corrupts the counts and a later legal move reads a phantom win. Validate range, then emptiness, then mutate; return OFF_BOARD or OCCUPIED and change nothing.

    Name them before they are asked.

    The Three Lines They Are Watching

    1. move() checks the cell is on the board and empty before it touches a counter.
    2. One move bumps rowCount[r], colCount[c] and at most one diagonal. The grid is never scanned.
    3. isWin tests abs(counter) == n on those lines only, and runs before the board-full draw test.

    Deciding the Win

    Approach Per move Extra state K in a row, k < n reset() cost Use when
    Full-board scan (brute force) O(n*n), rescans all lines none re-list every window none never
    Last-move lines (the simple correct one) O(n), walk 4 lines none scan the last move's k-window none 3x3, clarity first
    Incremental counters (the O(1) trick) O(1) bump + test 2n + 2 ints on the Board a run-length count per line zero 2n + 2 ints large n, or many replays

    Check only the last move's lines. For a 3x3 board it is the simplest thing that is correct, and it is already O(1) since n is 3. Move to running counters when the board grows or you replay thousands of games and the constant starts to matter.

    Rejection Signals

    These end the interview:

    • Rescanning every row, column and diagonal on each move when four counters answer in O(1).
    • Declaring a draw on a full board without first testing the last move for a win.
    • A hardcoded list of the eight winning lines that breaks the moment the board is n x n or the target is k < n.
    • Mutating the counters in move() before validating that the cell is on the board and empty.
    • X and O as subclasses of Cell rather than a Mark enum — three behaviourless classes.
    • The win rule written as loops inside move(), with no seam to swap in a scan or a bot's look-ahead.

    Patterns Used

    Strategy — the win-check policy (counters vs scan) and the bot's move choice. State — InProgress / Won / Draw drive what move() accepts. Observer — the grid and the move log follow every move. Factory — build the board and the two players.

    Say It Like This

    "An n by n board, default 3, win on k in a row with k = n. The Board carries a signed counter for each row, each column and the two diagonals. X adds one, O subtracts one. A move bumps at most four counters and the win test is abs(counter) == n, so it is O(1) whatever the move count. The Game is a small state machine, in progress to won or draw, and it notifies its observers after every move."

    The Follow-ups That Decide It

    1. Generalise to 10x10, five in a row. Parameterise n and k; the counters, or a scan of the last move's k-window, generalise. The list does not.
    2. The ninth move fills the board and completes a line. Test isWin first, isFull second; the win takes it.
    3. A player clicks a cell that is already taken. move() returns OCCUPIED and changes nothing.
    4. Add a third player with mark Z. The signed counter breaks; go to one count per (line, mark).
    5. Make the machine play. An AiPlayer plugs a Minimax MoveStrategy into Player; nothing else moves.
    6. Call the draw early, before the board is full. No line can still reach magnitude n for either side.
    7. Undo the last move. Pop the Move, subtract its four deltas, clear the cell, flip back.
    8. Replay a saved game. Feed the Move list through move() in order; observers redraw each step.

    Deliberately Not Built

    • A minimax opponent — an AiPlayer behind MoveStrategy that only reads the board. Named on page 1, not built.
    • Network play — two clients, a server relays each Move. A thin seam behind move().
    • Non-square boards — the diagonal counters assume n x n; a rectangle needs per-line run counts. Different problem.
    • A graphical UI — the board renders through a BoardObserver; console or pixels is one seam. Out of scope.
    • Undo and replay — a stack of Moves, each unapplied by subtracting its four counter deltas. Mentioned, skipped.
