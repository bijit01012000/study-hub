      115. HashMap.computeIfAbsent vs putIfAbsent

      Asked at: Most Java mid-level rounds

      Difficulty: Medium · Topic: Collections

      The question: "What's the difference between computeIfAbsent and putIfAbsent in HashMap?"

      The 30-second answer: putIfAbsent(key, value) puts the given value if absent. computeIfAbsent(key, k -> compute(k)) invokes the function ONLY if absent — value is lazily computed. For expensive default values, use computeIfAbsent. Both return the existing value if present, or the new value if not.

      Step-by-step thought process:

      1. " putIfAbsent(key, valueAlreadyComputed) — you've already built the value, just want to insert if missing."
      2. " computeIfAbsent(key, k -> expensive(k)) — function runs only when key is absent. Save the cost when the entry already exists."
      3. "Common use: building multi-maps. map.computeIfAbsent(merchantId, id -> new ArrayList<>()).add(order);. Creates the list only if needed."
      4. "In ConcurrentHashMap, both are atomic. computeIfAbsent's function holds a lock on the bucket — keep it short, don't call other map operations inside."
      5. " compute(key, (k, v) ->...) is the variant for 'transform existing value or insert new'. merge(key, value, mergeFn) for accumulating."

      Edge cases to mention:

      • ConcurrentHashMap's computeIfAbsent throws if the function tries to recurse into the same map — deadlock detection
      • In plain HashMap, mutating the map inside the function is allowed but discouraged
      • If the function returns null, no entry is added — useful for conditional insertion

      What NOT to say:

      • "They're the same" — laziness matters for expensive defaults
      • "computeIfAbsent always runs the function" — it doesn't if the key is present

      Common follow-up: "What happens if your computeIfAbsent function returns null?"

      116. StringBuilder vs StringBuffer

      Asked at: TCS · Infosys · Wipro · most fresher and mid rounds

      Difficulty: Easy · Topic: Strings

      The question: "Difference between StringBuilder and StringBuffer?"

      The 30-second answer: Both are mutable string builders. StringBuffer is synchronized (thread-safe but slower). StringBuilder is not synchronized (faster). For single-threaded use — which is 99% of cases — StringBuilder is the right choice. StringBuffer dates from Java 1.0 before there were better concurrency tools.

      Step-by-step thought process:

      1. "Both have append, insert, delete, replace, reverse, toString. Same API."
      2. "StringBuffer (Java 1.0) — every method is synchronized on this. Thread-safe for single-builder access from multiple threads."
      3. "StringBuilder (Java 5) — same API, no synchronization. Faster in single-threaded code. Use this by default."
      4. "In modern code, building a String concurrently from many threads is rare — you'd use a ConcurrentMap or join after each thread finishes. So StringBuffer is essentially obsolete."
      5. "Both auto-grow an internal char[] (or byte[] since Java 9 compact strings). Initial capacity 16; doubles when full. Pre-size if you know the approximate result length."

      Edge cases to mention:

      • Java 9+ uses compact strings — internal storage is byte[] for ASCII, char[] for non-ASCII. Halves memory for ASCII-heavy content
      • String.join(", ", parts) is often clearer than manual building
      • Modern JIT can sometimes optimize String concatenation into StringBuilder under the hood — but be explicit in loops

      What NOT to say:

      • "Use StringBuffer for safety" — paying for synchronization you almost never need
      • "String concatenation is fine in loops" — creates O(n) intermediate strings; use StringBuilder

      Common follow-up: "What does Java do under the hood for String x = a + b + c?"

      117. final keyword — three contexts

      Asked at: Most Java mid-level rounds

      Difficulty: Easy · Topic: OOP

      The question: "What does the final keyword do in Java? List the contexts where you can use it."

      The 30-second answer: On a variable: can't be reassigned after initialization (reference is fixed, but contents of mutable object can change). On a method: can't be overridden by subclasses. On a class: can't be subclassed. Plus final parameters (can't be reassigned within the method). Critical for immutable classes and for lambda capture.

      Step-by-step thought process:

      1. " final int x = 5; — x can't be reassigned. For primitives, also means the value is constant."
      2. " final List<String> list = new ArrayList<>(); — the REFERENCE is fixed. You can still call list.add(...) because the object itself is mutable."
      3. " final void process() — can't be overridden by subclasses. Useful for invariants you don't want subclasses to break."
      4. " final class Order — can't be subclassed. Used for immutable classes like String, Integer, all wrappers."
      5. "Lambdas/anonymous inner classes can only capture effectively-final local variables — Java enforces this so captured values don't change unexpectedly under the lambda."

      Edge cases to mention:

      • final on parameters is rarely written but enforced by some style guides — adds clarity, no perf impact
      • final field initialization: must happen in constructor or inline; uninitialized at end of constructor is a compile error
      • static final for constants — convention is ALL_CAPS naming

      What NOT to say:

      • "final makes the object immutable" — only the reference; object can still mutate
      • "final is just an optimization hint" — has compile-time semantics, not just a hint

      Common follow-up: "Why must captured variables in a lambda be effectively final?"

      118. static keyword and static blocks

      Asked at: Most Java mid-level rounds

      Difficulty: Easy-Medium · Topic: OOP

      The question: "Explain the static keyword. What's a static initialization block?"

      The 30-second answer: static makes a member belong to the class, not instances — one copy shared. Static fields, methods, nested classes, and initialization blocks. Static blocks run once when the class is first loaded — useful for complex initialization of static fields. Order: static blocks run in source order during class loading.

      Step-by-step thought process:

      1. " static int counter; — one counter shared by all instances. Accessed via ClassName.counter."
      2. " static method() — no this reference, can't access non-static members directly. Called via class name."
      3. " static class Inner (nested class) — does NOT have an implicit reference to outer instance. Use this; non-static inner classes are usually a memory leak waiting to happen."
      4. " static { / init code / } block — runs once, when class is first loaded by ClassLoader. Used to populate static fields that need logic to compute."
      5. "Order: static blocks and static field initializers run in source order at class load time. Instance fields and instance blocks run for each new instance at construction."

      Edge cases to mention:

      • Static fields aren't thread-safe by default — concurrent writes can race. Use AtomicInteger / synchronized / final
      • A class is loaded lazily, on first access (constructor call, static method call, static field access). Forcing load: Class.forName("...")
      • Static fields hold strong references — common source of leaks in long-running apps (large caches kept by classloader)

      What NOT to say:

      • "Static methods can be overridden" — they're hidden, not overridden — completely different dispatch
      • "Static blocks run every time you create an instance" — they run ONCE at class load

      Common follow-up: "What's the difference between static and instance initialization blocks?"

      119. Generics — type erasure and its consequences

      Asked at: Senior rounds · Razorpay · Goldman · Cred

      Difficulty: Medium-Hard · Topic: OOP / Generics

      The question: "What is type erasure in Java generics and what limits does it impose?"

      The 30-second answer: Java generics are compile-time only — at runtime, List<String> and List<Integer> are both just List. The compiler inserts casts and checks; the JVM sees raw types. Consequences: can't do new T[], can't check instanceof List<String>, can't have two methods that differ only in generic parameter, no primitive generics (need wrappers).

      Step-by-step thought process:

      1. "At compile, List<String> enforces type safety. At runtime, only List exists — the is erased."
      2. "Can't do new T[10] — JVM doesn't know what T is at runtime. Workaround: pass Class<T> to the constructor."
      3. "Can't do if (x instanceof List<String>) — erasure removes the type parameter. Only instanceof List<?> works."
      4. "Method overload conflict: void process(List<String>) and void process(List<Integer>) are compile errors — same erasure."
      5. "No List<int> — primitives can't be generic parameters. Use List<Integer> with autoboxing cost, or specialized IntStream / int[]."

      Edge cases to mention:

      • Project Valhalla (in progress for Java 24+) may eventually bring primitive generics and reified types
      • @SuppressWarnings("unchecked") is sometimes necessary when casting raw types — use sparingly with a comment why
      • List.class is Class<List> — you can't write List<String>.class for the same reason

      What NOT to say:

      • "Java generics are like C++ templates" — C++ creates a new class per parameterization; Java erases
      • "Erasure is removed in Java 21" — still erased; Valhalla is the long-term project

      Common follow-up: "How would you create a generic array workaround?"

      120. Wildcards —? extends vs? super

      Asked at: Senior Java rounds · Razorpay · Wells Fargo

      Difficulty: Medium-Hard · Topic: Generics

      The question: "Explain PECS — Producer Extends, Consumer Super. Give a concrete example."

      The 30-second answer: List<? extends Number> — you can READ Numbers from it (producer), can't add (you don't know if it's List<Integer> or List<Double>). List<? super Integer> — you can ADD Integers (consumer), can only read as Object. PECS = Producer Extends, Consumer Super.

      Step-by-step thought process:

      1. "PECS is a mnemonic for choosing wildcards. If a collection PRODUCES values you'll read, use? extends. If it CONSUMES values you'll add, use? super."
      2. " Collections.copy(List<? super T> dest, List<? extends T> src) — src is the producer (read T from it), dest is the consumer (write T to it). Textbook PECS."
      3. " List<? extends Number> nums = new ArrayList<Integer>();. You can Number n = nums.get(0);. You CANNOT nums.add(1); — because the actual list might be List<Double> and 1 isn't a Double."
      4. " List<? super Integer> ints = new ArrayList<Number>();. You CAN ints.add(1); because Integer is-a Number is-a Object. You read as Object o = ints.get(0); — that's the most specific known type."
      5. "Without wildcards, List<Number> is INVARIANT — List<Integer> is NOT a List<Number>. Wildcards introduce variance into Java's generics."

      Edge cases to mention:

      • List<?> is List<? extends Object> — read-only (well, can add null)
      • For method parameters, prefer the narrowest wildcard that still serves your use case — flexibility for callers
      • Self-referential bounds: Comparable<T>> is a common idiom for "must be comparable to its own type"

      What NOT to say:

      • "Just use raw types, it's simpler" — defeats type safety
      • "Wildcards make code generic" — they make APIs flexible while preserving type safety

      Common follow-up: "Why can't you add anything except null to a List<? extends Number>?"

      121. Stream.flatMap — the flatten operation

      Asked at: Most Java mid-level rounds · Razorpay · Swiggy

      Difficulty: Medium · Topic: Java 8 Functional

      The question: "What does Stream.flatMap do and when is it useful?"

      The 30-second answer: flatMap maps each element to a stream of values, then concatenates all those streams into one flat stream. Use it to flatten nested structures — List<Customer> where each has List<Order> becomes a flat Stream<Order> via customers.stream().flatMap(c -> c.orders().stream()).

      Step-by-step thought process:

      1. " map(fn) is 1-to-1 — each element becomes exactly one output. flatMap(fn) is 1-to-N — each element becomes 0 or more outputs."
      2. "Function signature: flatMap(T -> Stream<R>). The result streams are concatenated lazily."
      3. "Classic example: split each sentence into words. sentences.stream().flatMap(s -> Arrays.stream(s.split(" ")))."
      4. "For nested collections: users.stream().flatMap(u -> u.getOrders().stream()).filter(o -> o.amount() > 1000) — work on a flat stream of orders."
      5. "Also exists on Optional: optional.flatMap(value -> compute(value)) for chaining computations that themselves return Optional — avoids Optional<Optional<T>>."

      Edge cases to mention:

      • For primitives, flatMapToInt, flatMapToLong, flatMapToDouble avoid boxing — use them when the inner streams are primitive
      • The inner stream from the function is closed automatically — usually you don't care, but matters for Files.lines() style streams
      • Empty inner stream is fine — that element contributes nothing to the output

      What NOT to say:

      • "flatMap is just map with extra steps" — different cardinality semantics
      • "Use flatMap to filter" — wrong tool; filter is filter

      Common follow-up: "How would you flatten a List> into a Stream?"

      122. Stream.peek — debugging or never?

      Asked at: Most Java mid-level rounds

      Difficulty: Easy-Medium · Topic: Java 8 Functional

      The question: "What's Stream.peek for? Is it safe to use in production?"

      The 30-second answer: peek lets you observe each element as it flows through the stream — typically for debugging or logging. It's intermediate, so it only runs when a terminal operation pulls elements through. Don't use peek for side effects in production code — the JVM may skip peek calls if the result is unused (e.g. stream().peek(...).count() with a SIZED source).

      Step-by-step thought process:

      1. " stream.peek(System.out::println) — prints each element as the stream is consumed. Returns the stream unchanged."
      2. "Peek doesn't trigger consumption — it's intermediate. stream().peek(...) without a terminal doesn't run."
      3. "Useful for debugging: stream().filter(...).peek(this::debug).map(...).collect(...) — see what survives the filter."
      4. "Trap: stream().peek(this::addToCache).count() — for a SIZED source, the JVM knows the count without iterating. peek may not run. Don't use peek for state-changing side effects."
      5. "For real side effects, use forEach (terminal). For per-element processing in a pipeline, use map."

      Edge cases to mention:

      • Parallel streams: peek runs on the pool thread, not the calling thread — thread-safe code only
      • The Stream API spec explicitly says peek MAY be optimized away in some cases
      • Modern Java may skip peek entirely if downstream operations don't need the element — don't rely on it

      What NOT to say:

      • "peek is the right way to add side effects" — explicitly warned against in the spec
      • "peek is exactly like forEach" — peek is intermediate; forEach is terminal

      Common follow-up: "Why does peek sometimes not run when chained with count?"
