      Know the mechanics under the vocabulary on your CV.

      Q3.1 — What's a token, and why is cost, latency and limits all counted in them?

      Weak answer: "Tokens are chunks of words, roughly four characters or three-quarters of a word in English. You get billed and limited by them."

      Why it fails: - Recites the rule of thumb without knowing where it breaks, which is the only interesting part. - Treats input and output tokens as the same thing, when they're priced and generated differently.

      Instant rejection: - No awareness that non-English text, code and identifiers tokenise far worse than English prose. - Has never actually counted tokens with a real tokeniser, only ever estimated.

      Model answer: 1. A token is the unit a model's own tokeniser splits text into, mostly sub-word fragments learned from a training corpus. 2. It's model-specific: the same paragraph is a different token count on two providers, so one cost estimate doesn't transfer to another. 3. The four-characters rule holds for English prose and falls apart elsewhere, Devanagari or Tamil text can run several tokens per character. 4. Input and output aren't symmetric: input is one parallel pass, output is generated one token at a time, which is why output is slower and usually pricier. 5. I never estimate. I run the real tokeniser over a sample of actual production inputs before committing to a number.

      Follow-ups: 1. TECHNICAL — Your product launches in Hindi and the bill triples on the same traffic. Why? · Whether non-Latin scripts fragmenting into more tokens per character is known. 2. TECHNICAL — Is 1,000 input tokens the same cost and latency as 1,000 output tokens? · Whether prefill and decode are understood as different, unequal operations. 3. MEASUREMENT — How would you actually measure token counts before shipping? · Whether the candidate tokenises with the real tokeniser, not a heuristic. 4. TRADEOFF — You're extracting into JSON. Does the schema shape affect the bill? · Awareness that verbose keys and nesting are paid for on every response.

      Tip: You can say you understand tokenisation mechanically and its cost link, even without ever billing real API traffic yourself. Don't claim you've optimised token spend in production if you haven't, say instead you've counted tokens on a test prompt before.

      Numbers worth quoting: - ~4 chars, ~0.75 words a token - Non-Latin scripts cost more - Output priced above input - Always tokenise, never guess

      Q3.2 — What actually happens as the context window fills up?

      Weak answer: "It's how much the model can see at once. Go over it and you get an error, newer models have bigger windows so it matters less now."

      Why it fails: - Describes only the hard failure at the boundary, the interesting failures happen well before it. - "Bigger windows so it matters less" is the exact belief this question is designed to catch.

      Instant rejection: - Unaware that recall degrades for information placed in the middle of a long context. - Has never tested where quality actually falls off for their own task.

      Model answer: 1. The hard limit is the least interesting part, quality degrades well before it, not just at the boundary. 2. Material in the middle of a long context gets attended to less reliably than material at the start or end. 3. So being in the window isn't the same as being used, I've seen answers get worse after adding more retrieved chunks despite the right one still being present. 4. Cost and latency scale with everything you put in, on every call, so a full window is a recurring cost, not a one-off. 5. I'd find the usable limit empirically: fixed questions with a known source, placed at varying depth, and measure how often the answer actually uses it.

      Follow-ups: 1. TECHNICAL — You put the relevant document at position 40 of 60. As likely to be used as position 1? · Whether positional recall degradation in the middle is known. 2. TRADEOFF — If a bigger window is strictly better, why not always fill it? · Whether cost, latency and accuracy costs of a full window are understood. 3. MEASUREMENT — How would you find your own usable limit, not trust the spec sheet? · Whether the candidate would test recall against context length. 4. FAILURE — What's the failure mode when you truncate silently instead of erroring? · Awareness that silent truncation gives confident, incomplete answers.

      Tip: You can say you understand the usable-versus-advertised window gap from reading about it, even without measuring it on a live system. Don't claim you've tuned retrieval depth in production. Say instead how you'd test your own usable limit before trusting the spec sheet.

      Numbers worth quoting: - Middle-of-context recall drops - Full window costs every call - Test recall at varying depth - Silent truncation hides failure

      Q3.3 — What do temperature and top_p actually do, and when does it matter?

      Weak answer: "Temperature controls randomness, lower is more factual, higher is more creative. top_p is another way of controlling the same thing."

      Why it fails: - "top_p is another way of controlling the same thing" is the exact error this question exists to find. - "Lower is more factual" conflates determinism with correctness, a confident wrong answer at zero is still wrong.

      Instant rejection: - Claims temperature 0 guarantees the same output every time. - Cannot say what top_p removes from the candidate set, versus what temperature does.

      Model answer: 1. At each step the model produces a probability distribution over the vocabulary, and these two parameters act at different points in it. 2. Temperature rescales the distribution before sampling, below one it sharpens towards likely tokens, above one it flattens it out. 3. top_p truncates instead, keeping the smallest set of tokens whose probabilities sum to p, then samples within that set. 4. The conflation to avoid is determinism with accuracy, temperature 0 picks the most likely token, and the most likely token can still be confidently wrong. 5. I don't treat 0 as a reproducibility guarantee either, batching and floating point mean identical inputs can still diverge, so tests assert on properties, not exact strings.

      Follow-ups: 1. TECHNICAL — Walk me through the actual difference between temperature and top_p at the sampling step. · Whether one reshapes and the other truncates, or they're believed identical. 2. FAILURE — Does temperature 0 guarantee the same output twice? Bet your on-call on it? · Whether determinism at zero is known to not be reliably guaranteed. 3. TECHNICAL — Lower temperature makes it more factual, does it? What does it actually make it? · Separating determinism from correctness, the common conflation here. 4. MEASUREMENT — You're testing a model at temperature 0.7. What changes about the tests? · Whether non-determinism is handled by asserting on properties, not exact strings.

      Tip: You can explain what each parameter mechanically does from study alone, that's a fair claim without ever running a model in production. Don't claim you've tuned these for a live product. Say instead which one you'd reach for first, and why the other one isn't equivalent.

      Numbers worth quoting: - Temp reshapes, top_p truncates - Temp 0 still not reproducible - Determinism is not correctness - Assert properties, not strings

      Q3.4 — What does an embedding actually represent, and what does it fail to capture?

      Weak answer: "An embedding is a vector of the semantic meaning of text. Similar meanings end up close together, which is what lets you do semantic search."

      Why it fails: - Correct as a definition and empty as an answer, the question asked what it fails to capture. - Assumes nearest neighbour equals relevant, which is exactly where retrieval fails.

      Instant rejection: - Cannot name a single category of text embeddings handle badly. - Believes vectors from two different models can be compared directly.

      Model answer: 1. An embedding is a fixed-length vector from a model trained so texts its training objective considered related land near each other. 2. That's the whole answer, it encodes whatever notion of similarity was in its training data, not meaning in general. 3. Negation is the blind spot that bites most, 'covers water damage' and 'does not cover water damage' are near-identical vectors since they share almost every token. 4. Exact identifiers are the other, an invoice number has no useful semantic neighbourhood, which is the real argument for lexical search alongside dense retrieval. 5. Spaces aren't interoperable either, you can't compare a vector from one model with another, so changing embedding models means reindexing everything.

      Follow-ups: 1. TECHNICAL — 'Covers water damage' versus 'does not cover water damage', how far apart are those vectors? · Whether negation is known to be weakly encoded. 2. FAILURE — A user searches for invoice INV-2024-8891. Does embedding search find it? · Whether exact identifiers are known to be handled badly by dense retrieval. 3. TRADEOFF — Two embedding models both claim good benchmark scores. Do they agree on similar? · Whether similarity is understood as model-specific, not universal. 4. TECHNICAL — Can you compare a vector from one model against a vector from another? · Whether embedding spaces are known to be non-interoperable.

      Tip: You can describe these blind spots from reading and reasoning about the mechanism, without having run retrieval on a real corpus yourself. Don't claim you've hit a negation or identifier failure in production if you haven't, say instead which one you'd test for first.

      Numbers worth quoting: - Negation vectors sit near-identical - IDs need lexical, not just dense - Similarity is model-specific - New model means full reindex

      Q3.5 — Cosine, dot product, Euclidean distance, which do you use, and does it matter?

      Weak answer: "I use cosine similarity, it's the standard for text embeddings because it measures angle and ignores magnitude."

      Why it fails: - States a correct default as a universal rule rather than a model-dependent choice. - No mention that for normalised vectors, cosine and dot product rank identically.

      Instant rejection: - Never checked what metric the embedding model was actually trained for. - Cannot describe what a metric mismatch would look like in production.

      Model answer: 1. The choice isn't really mine, it's determined by what the embedding model was trained against, and the model card says which. 2. Cosine is the usual answer for text, it measures angle and discards magnitude, and most text embedding models are trained with a cosine objective. 3. If vectors are already normalised, cosine and dot product give identical rankings, so the argument between them is often about compute, not results. 4. The failure mode is what makes this worth asking, a metric mismatch doesn't throw, it silently returns slightly worse neighbours with nothing in the logs. 5. I check this at index setup now, after once inheriting an index built with the wrong distance metric where results just felt a bit off for months.

      Follow-ups: 1. TECHNICAL — Your vectors are already normalised. What's the difference between cosine and dot product then? · Whether they coincide in ranking on unit vectors, differing only in compute. 2. TECHNICAL — How do you know which metric your embedding model was actually trained for? · Whether the model card is the authority, or the metric is chosen by habit. 3. FAILURE — You configure the index with the wrong metric. What does that look like? · Whether the candidate can predict a silent, hard-to-spot degradation. 4. TRADEOFF — When would magnitude actually carry information you want to keep? · Whether the candidate understands what cosine discards.

      Tip: You can explain why the metric must match the model's training objective from reading the model card, without ever having built an index yourself. Don't claim you've caught a real metric mismatch if you haven't, say instead you'd check the model card before configuring any index.

      Numbers worth quoting: - Metric follows the model card - Normalised: cosine = dot product - Mismatch is silent, not an error - Cosine discards magnitude

      Q3.6 — DRILL: a user uploads a 60-page PDF to summarise. Budget the tokens and context. (practical drill)

      Weak answer: "N/A, this is a drill. A weak attempt says "send the whole document", with no token estimate or chunking plan."

      Why it fails: - No attempt to estimate the actual token count, so "it depends" stands in for a real number. - No plan for what happens when the document doesn't fit one call, beyond "use a bigger window".

      Instant rejection: - Cannot name a rough token-per-page figure, even a loose one, to reason from. - No mention of the summary needing its own output budget, separate from the input.

      Model answer: 1. A rough anchor: a page runs a few hundred words, so 60 pages is roughly 30 to 40 thousand tokens of input, before I check with a real tokeniser. 2. That's likely over a comfortable single-call budget once I add a system prompt and instructions, so I'd plan for chunking rather than one call. 3. I'd split by section or page range, summarise each chunk, then run a second pass summarising the summaries, a map-reduce shape, not one giant prompt. 4. I'd cap the output summary itself at a fixed token count, since an uncapped summary of a long document can balloon and blow the latency budget too. 5. I'd measure real cost per document on a handful of actual PDFs before shipping, not estimate from a words-per-page guess and hope it holds.

      Follow-ups: 1. TECHNICAL — Roughly how many tokens is a 60-page PDF, and how did you get that number? · Whether a real estimate exists, from a tokeniser or a sane rule of thumb. 2. TRADEOFF — Full document in one call versus map-reduce summarisation, what changes? · Whether the cost, latency and coherence trade-off is understood. 3. FAILURE — The document doesn't fit one context window. What breaks first if you ignore it? · Whether silent truncation is named as the actual failure mode. 4. MEASUREMENT — How would you keep the output summary itself within a token budget? · Whether output length is treated as its own budget, separate from input.

      Tip: This drill works on any document length you pick, run the numbers on something you've actually handled, even a long report or a codebase file. Don't invent a precise token count you haven't checked. Say honestly it's an estimate, and name the rule of thumb you used to get there.

      Numbers worth quoting: - ~30-40k tokens for 60 pages - Map-reduce beats one huge call - Cap output tokens separately - Verify with a real tokeniser

      Q3.7 — What does attention actually do, at the level you'd explain it to a colleague?

      Weak answer: "Attention lets the model focus on the relevant parts of the input when producing each output token."

      Why it fails: - This is the standard definition and explains nothing about how relevance gets computed. - No mention of query, key and value vectors, or that every token attends to every other token.

      Instant rejection: - Cannot say what a query, key or value vector is when asked directly. - Believes attention only looks back at instructions, not at every token including itself.

      Model answer: 1. For every token the model builds a query, and every token in context offers a key and a value; the query is compared against every key to score relevance for that pair. 2. Those scores become weights that sum to one, and the output for that token is a weighted blend of every value, so each token's new representation mixes in context from the whole sequence. 3. This runs in parallel across many attention heads, so different heads can pick up different relationships at once, say grammar in one head and topic in another. 4. It happens at every layer, so relevance gets refined and re-mixed repeatedly rather than computed once, which is why a single 'attention map' undersells what's going on. 5. The practical upshot is that relevance is soft and distributed, not a hard lookup, which is why instructions can get diluted by volume rather than dropped outright.

      Follow-ups: 1. TECHNICAL — What are query, key and value vectors, and how do they combine? · Whether the QKV mechanism is known beyond the acronym. 2. FAILURE — Why does a long, repetitive document sometimes bury a key instruction? · Whether attention dilution across many similar tokens is understood as a failure mode. 3. TRADEOFF — Attention compares every token against every other token. What does that cost? · Whether the quadratic cost of full attention is connected to context length limits. 4. MEASUREMENT — How would you show a teammate the model attended to the wrong part of a document? · Whether the candidate can reason about attention behaviourally, not just recite theory.

      Tip: You can say you understand attention mechanically from study, not from building an attention layer yourself. That's a fair claim at this level. Don't claim you've "debugged attention" or written an attention kernel unless you have; say instead you've diagnosed context-dilution failures in a prompt.

      Numbers worth quoting: - Attention cost is O(n squared) - Multi-head: many views per layer - QKV: query, key, value per token - Attention re-runs at every layer

      Q3.8 — What is the KV cache, and why does it change your cost and latency?

      Weak answer: "The KV cache stores past computations so the model doesn't redo work for every new token, which makes generation faster."

      Why it fails: - Names the benefit without saying what's cached: the key and value vectors from attention, per layer. - Doesn't connect the cache to why input and output tokens are priced and timed so differently.

      Instant rejection: - Cannot say the cache holds key and value vectors, not raw tokens or the output text itself. - Thinks the cache is optional or only relevant to unusually long conversations.

      Model answer: 1. The KV cache stores the key and value vectors attention produces for every token, at every layer, so the model doesn't recompute them for tokens it has already processed. 2. During prefill the model reads the whole prompt and builds this cache in one pass; during decode it generates one token at a time, reusing the cache instead of reprocessing everything before it. 3. That's why the first token is comparatively slow, that's the prefill pass over the whole prompt, and later tokens come faster, since decode only has to read the cache, not rebuild it. 4. It's also why input and output are priced differently: input is one parallel pass, but output tokens each trigger a cache read and a new cache write, which is a different, repeated cost. 5. Prompt caching is this same mechanism made explicit: if a prefix repeats across calls, the provider can reuse its KV cache instead of rebuilding it, which is what makes a repeated system prompt cheaper.

      Follow-ups: 1. TECHNICAL — What exactly gets stored in the KV cache, and at what granularity? · Whether the candidate knows it's key and value vectors, per layer, per token, not raw text. 2. FAILURE — A chat grows to 50k tokens. What gets strained first, quality or infrastructure? · Whether cache memory growth is understood as a real serving constraint, not an abstract cost. 3. TRADEOFF — Why is the first response token slow but every token after it fast? · Whether the candidate connects cache-building during prefill to the latency shape they've observed. 4. MEASUREMENT — How would you tell, from your own bill, whether prompt caching is helping you? · Whether the candidate reasons about cached-token pricing and hit rate rather than assuming it just works.

      Tip: You can honestly say you understand what the KV cache is and why it shapes pricing and latency, even without ever tuning inference infrastructure. Don't claim you've done KV cache quantisation or built a serving stack unless you have; say instead you've picked providers partly for prompt-caching support.

      Numbers worth quoting: - Cache holds K,V per token per layer - Prefill: 1 pass, decode: per token - First token slow, later ones fast - Repeated prefix, cheaper via cache

      Q3.9 — Why is generating output slower than reading the same amount of input?

      Weak answer: "Generating is slower because the model has to think about each word one at a time, while reading input happens all at once."

      Why it fails: - "Thinking about each word" isn't a mechanism; it doesn't say why one-at-a-time is unavoidable for output. - Doesn't name prefill and decode, or say which is compute-bound and which is bandwidth-bound.

      Instant rejection: - Cannot explain why decode can't process the whole output in parallel the way prefill processes input. - Confuses which stage scales quadratically and which scales roughly linearly with length.

      Model answer: 1. Prefill processes the whole prompt in one pass because every input token is already known, so attention over the prompt runs in parallel across all positions at once. 2. Decode can't do that, because each new token depends on every token generated before it, so output comes out one token at a time, each step waiting on the last. 3. Prefill's attention cost grows quadratically with input length, since every token attends to every other token, which is why very long prompts slow that first pass down noticeably. 4. Decode's per-step cost is closer to linear in the cached tokens, but it runs once per output token and re-reads the whole growing cache every time, so it's bound by memory bandwidth, not compute. 5. That's the mechanical reason output tokens are slower and usually costlier than input tokens: input is one parallel pass, output is many sequential passes each paying to read the cache.

      Follow-ups: 1. TECHNICAL — Why can prefill process the whole prompt in parallel but decode can't do the same for output? · Whether the causal, autoregressive dependency of decode is understood as the real constraint. 2. FAILURE — Context is 100k tokens and users complain the first word takes forever. What stage is that? · Whether quadratic prefill cost at long context is linked to observed time-to-first-token. 3. TRADEOFF — Is decode compute-bound or memory-bandwidth-bound, and why does that distinction matter? · Whether the candidate knows decode is bandwidth bound, which is why batching and quantisation help. 4. MEASUREMENT — How would you separately measure time-to-first-token from per-token decode speed? · Whether the candidate treats these as two numbers to instrument, not one aggregate latency.

      Tip: You can say you understand the prefill/decode split and have noticed its effects, like slow first tokens on long prompts, without profiling an inference engine. Don't claim to have optimised prefill or decode yourself unless you have; say instead you've used shorter prompts or streaming to work around the latency shape.

      Numbers worth quoting: - Prefill: parallel, O(n squared) - Decode: sequential, one token/step - Decode is bandwidth bound - Long prompt, slow first token

      Q3.10 — Beyond temperature, what do top_k, repetition penalties and seeds control?

      Weak answer: "top_k limits the choices like top_p does, a repetition penalty stops it repeating itself, and a seed makes output reproducible."

      Why it fails: - Treats top_k and top_p as the same idea when one truncates by count and the other by probability mass. - Says a seed "makes output reproducible" with no caveat about batching or hardware non-determinism.

      Instant rejection: - Cannot explain the actual difference between truncating by a fixed count versus a probability mass. - Believes a repetition penalty has no downside and can be raised freely without harming quality.

      Model answer: 1. top_k keeps only the k most likely next tokens by count, then samples among them; top_p keeps the smallest set whose probabilities add up to p, so its size changes with the model's confidence. 2. A repetition penalty lowers the score of tokens already used, which stops loops, but push it too high and the model avoids natural repeats like 'the' and starts choosing stranger words to comply. 3. A seed fixes the random draw used at each sampling step, so given the same distribution it makes the choice reproducible, which matters for debugging and for comparing prompt changes fairly. 4. None of this is a reliability guarantee end to end: batching, parallel execution and floating-point non-associativity mean the same seed and temperature 0 can still diverge slightly in production. 5. I pick these per task rather than by default: tight top_k or top_p and no penalty for extraction, a light repetition penalty and higher temperature for long-form generation that tends to loop.

      Follow-ups: 1. TECHNICAL — How does top_k differ from top_p in what it removes from the candidate set? · Whether fixed-count versus cumulative-probability truncation is actually understood. 2. FAILURE — You raise the repetition penalty to stop a looping output. What new problem can that cause? · Whether over-penalising is known to push the model toward incoherent or off-topic word choices. 3. TRADEOFF — You set a seed and temperature 0. Are you guaranteed the same output every time? · Whether the candidate knows batching and hardware non-determinism can still break reproducibility. 4. MEASUREMENT — How would you actually choose a repetition penalty for a summarisation task? · Whether the candidate would test against real outputs rather than pick a default and move on.

      Tip: You can honestly say you understand what each parameter changes mechanically, even if you've only ever used the provider's defaults in practice. Don't claim you've tuned these in production if you haven't; say instead which one you'd reach for first for a looping-output problem.

      Numbers worth quoting: - top_k: fixed count of tokens - top_p: cumulative probability mass - Seed does not guarantee - reproducing - High penalty can hurt coherence

      Q3.11 — Mechanically, why does a model hallucinate instead of saying it doesn't know?

      Weak answer: "It's just predicting the next most likely word, so sometimes it generates something false that sounds plausible."

      Why it fails: - True but generic; doesn't explain why "sounds plausible" beats "admits uncertainty" at the token level. - No mention that training rewards a fluent, confident-sounding answer over an honest "I don't know".

      Instant rejection: - Thinks hallucination is a bug that a bigger model or more training data alone will fix. - Cannot name any mitigation beyond "better prompting", with no mention of grounding or abstention.

      Model answer: 1. At each step the model chooses the statistically likely next token given everything before it, not a fact checked against a source, so nothing built in distinguishes true from fluent. 2. When the model lacks the knowledge to answer, nothing forces it to stop; it keeps generating locally plausible tokens, which produces a confident, well-formed sentence that happens to be false. 3. Training pushes this further: instruction tuning and human feedback tend to reward complete, confident-sounding answers, so 'I don't know' is often a lower-reward output than a plausible guess. 4. This is why hallucination shows up worst exactly where training signal is thin, obscure facts, recent events, very specific numbers, rather than uniformly across everything the model says. 5. The mitigations follow from the mechanism: ground the answer in retrieved sources so there's something to check against, and design the product to treat abstaining as an acceptable output.

      Follow-ups: 1. TECHNICAL — Why does the model rarely say 'I don't know' even when it should? · Whether the candidate knows instruction tuning tends to reward confident, complete-sounding answers. 2. FAILURE — You ask for a citation and get a real-looking but fake one. Why a fake citation specifically? · Whether the candidate knows the model generates plausible-shaped text, not looking anything up. 3. TRADEOFF — Would a bigger, more capable model hallucinate less on your task? Always? · Whether scale is understood as reducing but not eliminating hallucination, especially on missing knowledge. 4. MEASUREMENT — How would you actually measure a hallucination rate for your feature, not spot-check it? · Whether the candidate has a concrete evaluation method against a labelled, ground-truth set.

      Tip: You can say you understand why hallucination happens mechanically and how retrieval and abstention reduce it, without shipping a hallucination-mitigation system yourself. Don't claim you've "solved hallucination" anywhere; say instead how you'd measure it and which mitigation you'd reach for first.

      Numbers worth quoting: - No built-in fact-check step - Thin training signal, more errors - Confident guess often rewarded - Grounding plus abstention help

      Q3.12 — What changes mechanically when the input is an image or audio, not text?

      Weak answer: "Multimodal models can just take images or audio directly and understand them the same way they understand text."

      Why it fails: - Skips the actual step: the input is converted into embeddings the model attends over, at a real token cost. - No mention that images and audio consume context budget too, often a surprisingly large amount.

      Instant rejection: - Doesn't know an image is chopped into patches, or audio into frames, before the model ever attends over it. - Assumes image or audio input is free or negligible against the context window.

      Model answer: 1. An image is chopped into fixed-size patches, each patch is turned into an embedding, and those embeddings are fed in alongside text token embeddings, so attention treats them uniformly from there on. 2. Audio goes through a similar conversion, split into short frames and encoded into embeddings, though many production pipelines still transcribe to text first, since that's simpler to build and debug. 3. Because patches and frames become tokens, they consume context budget and are billed like any other token, so a large or high-resolution image can cost as much as several paragraphs of text. 4. Fine detail can be lost before attention even runs, because a fixed patch size limits how much small text or structure survives encoding, which is why tiny print in a screenshot gets misread. 5. In practice I still favour transcribing audio and running OCR on dense documents where accuracy matters most, and keep native image input for layout, charts or scenes where text would lose the structure.

      Follow-ups: 1. TECHNICAL — How does an image actually become something the model can attend over? · Whether patch-based encoding into embeddings is known, even at a high level. 2. FAILURE — A screenshot has small text and the model misreads a number. Why, mechanically? · Whether patch-size limits are connected to fine detail being lost before attention even runs. 3. TRADEOFF — Why can a single image cost as many tokens as a page of text? · Whether the candidate knows image patches are billed as tokens, which changes cost planning. 4. MEASUREMENT — How would you check the model is actually using the image, not guessing from surrounding text? · Whether the candidate would test with an image-only prompt to isolate reliance on the image.

      Tip: You can say you understand how images and audio get tokenised and what that costs, even without having shipped a multimodal feature yourself. Don't claim you've tuned a vision pipeline in production if you haven't; say instead you'd test image reliance directly before trusting it.

      Numbers worth quoting: - Image: patches to token - embeddings - Audio: frames to token embeddings - One image can cost many tokens - Fixed patch size caps fine detail
