      Chat Service & SSE Streaming

      0 sections · 413 words

      62. Why SSE instead of WebSocket for the chat stream?

      Token streaming is unidirectional — server pushes tokens. SSE is plain HTTP/1.1, so it traverses proxies/CDNs/load balancers with no upgrade handshake, and the browser's EventSource auto-reconnects. WebSocket is bidirectional with more overhead and only pays off if the client sends data mid-stream (e.g. interrupting generation). For readonly streaming, SSE is the right, simpler choice.

      63. How does streaming not block Tomcat threads?

      The controller creates an SseEmitter and returns it in ~1ms; the actual LLM call runs on the chatExecutor pool via @Async. Spring MVC hands the emitter to Tomcat's async processing, releasing the servlet thread. Tokens are pushed from the async thread. No servlet thread is held during the 10–60s generation — same idea as DeferredResult, applied to streaming.

      64. Walk me through what happens on send-message.

      POST /conversations/{id}/messages → controller makes an SseEmitter, calls streamChat (@Async), returns immediately. On the async thread: load + validate conversation is ACTIVE → save the user message → call knowledge-service /search for top chunks → fetch last ~10 messages, oldest-first, excluding the just-saved turn → build the 3-layer prompt → chatClient.prompt().stream().content() gives a Flux<String> → each token emitter.send(...) → on complete: save assistant message with citation refs, bump conversation timestamp, check escalation marker, write outbox if escalating, send done event with messageId + citations + escalated flag → emitter.complete().

      65. How does the SecurityContext reach the async thread?

      SecurityContextHolder is ThreadLocal — not inherited by child threads. I wrap the executor with DelegatingSecurityContextAsyncTaskExecutor, which snapshots the context at dispatch and restores it on the worker. Without it, Spring Security's cleanup on the async thread sees an empty context and throws AccessDeniedException after the stream finishes — a race that only shows up under real concurrent load.

      66. What happens if the client disconnects mid-stream?

      emitter.send throws IOException; I catch it and log "client disconnected" rather than crashing the worker. The Flux subscription continues on the server briefly but the emitter is done. In production I'd also cancel the upstream LLM subscription on disconnect to stop paying for tokens nobody will read — a noted refinement.

      67. Where do conversation history limits come from?

      Configurable app.chat.max-history-messages (default 10). I fetch the last N messages, reverse to oldest-first for prompt order, and drop the current turn. Bounding history controls prompt token cost and latency; unbounded history would blow the context window and slow every call.
